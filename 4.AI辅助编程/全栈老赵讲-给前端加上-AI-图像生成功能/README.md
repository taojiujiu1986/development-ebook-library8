## 开篇引入：先想清楚“要解决什么问题”

第一次接触 AI 图片生成，很多人会先问“模型怎么画得更好”。但如果你的目标是在前端产品里真正做出一个可用功能，重点不是“怎么画”，而是**怎么让用户顺畅完成一次生成任务**。

所以，这本书不是讲模型训练，也不是讲绘图技巧，而是讲**前端产品如何接入 AI 图片生成能力**：把提示词、尺寸选择、图片上传、任务等待、结果展示、下载、历史记录这些环节串成一个真实可用的网页功能。

如果你的产品要支持封面生成、海报生成、营销配图、头像生成，甚至灵感图探索，你首先要回答的不是“用哪个模型”，而是：

- 用户从哪里进入这个功能？
- 输入什么内容最合适？
- 生成要等多久，怎么让用户不焦虑？
- 结果出现后，用户下一步能做什么？
- 如何保存历史记录，避免重复劳动？

这些问题决定了产品能不能用，也决定了后面的页面设计。

## 一、AI 图片生成在网页产品里，最常见的场景是什么？

在前端产品中，AI 图片生成通常不是孤立功能，而是服务于具体业务目标。场景不同，页面重点也不同。

### 1. 封面生成

适用于文章封面、课程封面、活动页头图。  
用户更关心主题、尺寸和风格，比如输入“科技感蓝色封面，适合 AI 工具介绍”，再选 16:9，就能直接用于页面头图。

页面上通常要提供：

- 尺寸快捷选项
- 简洁的提示词输入框
- 生成后直接下载按钮
- 结果预览弹窗

### 2. 海报生成

适用于营销活动、宣传页、社群海报。  
这个场景更看重氛围和排版，常常还要上传参考图或品牌素材。用户要的是快速出图，不是学习绘画。

页面上可以增加：

- 图片上传入口
- 风格标签选择
- 文案提示词模板
- 失败重试按钮

### 3. 营销配图

适用于商品详情、Banner 图、活动弹窗。  
这类图片通常需要频繁调整，所以“再次编辑”很重要。用户可能先试一个版本，再改提示词、改尺寸、换参考图，然后继续生成。

### 4. 头像与灵感图

适用于社交头像、角色设定、风格探索。  
这类场景下，用户会连续生成多张图并对比结果，因此画廊式展示、历史记录、收藏功能会更重要。

这些场景有一个共同点：**用户不是来学画画的，而是来完成一张可用图片的**。页面要服务的是“生成结果可用”，不是“生成过程好看”。

## 二、本书要做的，不是训练模型，而是把能力接到前端流程里

这一点必须先讲清楚。很多初学者会把注意力放在模型原理、绘图参数、算法细节上，但在前端产品里，真正落地的是完整流程。

一个完整的图像生成流程通常是这样的：

1. 用户输入提示词  
2. 选择尺寸和风格  
3. 可选上传参考图  
4. 提交生成任务  
5. 页面显示加载态，等待异步结果  
6. 结果返回后展示图片  
7. 支持预览、下载、收藏、再次编辑  
8. 保存历史记录，方便回看和复用

所以，本书关注的是**前端产品接入能力**，而不是模型训练。你需要会的是：

- 页面结构怎么拆
- 表单怎么收集参数
- API 怎么调用
- 异步任务怎么轮询或等待
- 结果怎么展示、怎么下载
- 历史记录怎么存
- 本地缓存怎么保留

换句话说，这本书是教你把 AI 图片生成能力做成一个真正能上线的产品功能。

## 三、一个可落地的图像生成页面，应该具备哪些核心能力？

如果一个页面只有“生成”按钮，那还不算完整。真正可用的页面，至少要有下面这些能力。

### 1. 提示词输入

这是最基础的入口。用户通过它表达“要生成什么”。  
建议设计成多行文本框，并配上：

- 示例提示词
- 清空按钮
- 字数提示
- 常用模板快捷填充

例如，用户不想从零开始写，可以点一下“科技感封面”“电商海报”“极简头像”直接带入示例。

### 2. 尺寸选择

不同内容需要不同尺寸。封面适合横图，头像适合正方形，海报常常需要竖版。  
建议用按钮组或下拉菜单做快捷选择，例如：

- 1:1
- 16:9
- 9:16
- 4:3

尺寸不是装饰项，而是决定结果是否可用的关键参数。

### 3. 图片上传

这一项很重要，但经常被新手漏掉。很多场景都需要图片上传，比如：

- 参考图生成
- 风格迁移
- 基于已有素材继续创作
- 上传品牌图做视觉对齐

页面应支持：

- 本地选择图片
- 展示缩略图
- 显示文件名
- 删除重选
- 限制格式和大小

图片上传直接影响产品可用性，因为它决定了用户能否把自己的素材带进流程里。

### 4. 结果展示

生成结果不能只给一个链接，必须在页面里清楚展示。  
建议采用画廊式缩略图布局，方便一次看到多张结果，并支持点击打开结果预览弹窗，查看大图细节。

结果区最好同时展示：

- 生成时间
- 尺寸
- 状态
- 是否可下载

### 5. 下载

用户最终需要的是图片文件，所以下载是基础能力。  
建议在预览弹窗和缩略图卡片上都放下载入口，减少操作路径。下载后给出明确反馈，例如“已开始下载”或“下载成功”。

### 6. 历史记录与本地缓存

用户通常不会只生成一次。历史记录能帮助他们：

- 找回上次输入的提示词
- 复用尺寸和参考图
- 再次编辑某个结果
- 对比不同版本

如果页面一刷新，历史全没了，体验会很差。  
因此可以把最近的输入、结果和记录保存在本地缓存里。这样即使用户关闭页面再回来，也能继续接着用。

## 四、页面形态怎么拆？把大功能拆成五个区域

一个好用的 AI 图片生成页面，通常可以拆成五块。

### 1. 输入区

放提示词输入框、示例按钮、清空按钮。  
它回答的是：**“我想生成什么？”**

### 2. 参数区

放尺寸选择、图片上传、风格选项等。  
它回答的是：**“我要按什么规则生成？”**

### 3. 状态区

放加载态、任务进度、失败提示、消耗提示。  
它回答的是：**“现在生成到哪一步了？”**

### 4. 结果区

用缩略图网格展示图片，点击后打开结果预览弹窗。  
它回答的是：**“生成结果长什么样？”**

### 5. 历史区

展示最近生成记录，支持一键再次编辑。  
它回答的是：**“我之前做过什么？”**

这个拆分方式对新手很友好，因为你可以先完成最小闭环，再逐步扩展下载、收藏、重试、分享等功能。

## 五、从“能生成”到“能用起来”，验收标准是什么？

不要只看“接口通了没有”，还要看“用户能不能完成任务”。

### 基础验收标准

- 能输入提示词
- 能选择图片尺寸
- 能上传参考图
- 点击后能发起生成任务
- 生成过程中有加载态
- 异步任务完成后能展示结果
- 支持结果预览弹窗
- 支持下载图片
- 支持查看历史记录
- 刷新后本地缓存仍可保留最近数据
- 移动端页面能正常使用

### 常见误区

- 只做一个按钮，不做状态反馈
- 只展示结果，不提供下载
- 只考虑桌面端，忽略移动端适配
- 只管接口成功，不管失败重试
- 只关注“图有没有生成”，不关注“用户能不能继续编辑和复用”

## 结尾小结：先做产品视角，再做技术实现

这一章最重要的结论只有一句：**AI 图片生成在前端里不是“画图功能”，而是“生成流程功能”**。

你真正要交付的，不是一张图，而是一套完整可用的页面：有输入、有参数、有图片上传、有等待、有结果、有下载、有历史记录，还能在移动端正常使用。

下一章开始，我们会把这个目标拆成具体页面结构，先从表单与参数面板做起，逐步搭出一个真正能落地的图像生成页面。

### 本章行动建议

如果你现在就要开始做，可以先只完成这 5 件事：

1. 做一个提示词输入框  
2. 加上尺寸选择  
3. 支持图片上传  
4. 做出加载态和结果区  
5. 把最近一次生成记录存到本地缓存里  

先把“能生成、能看见、能找回”做出来，再继续扩展下载、收藏、重试和上线能力。

## 开篇引入：这一章只做“页面骨架与状态准备”

这一章先不讲图像生成原理，也不讲模型怎么画图。我们的目标只有一个：**先把能承载 AI 图像生成流程的前端页面搭起来**，这样后面接接口、做异步任务、加下载和历史记录时，页面才不会乱。

前端新手常见的问题，是一上来就写请求和回调，结果页面结构不清楚，状态也散在各处。正确顺序应该是：**先定页面结构，再定状态，再定样式，最后再接功能**。

本章完成后，你应该得到一个稳定的基础页面，它至少能支持：

- 输入提示词
- 选择图片尺寸
- 上传参考图片
- 显示加载态
- 展示结果区域和预览入口
- 记录历史列表
- 为后续下载、收藏、再次编辑预留位置

换句话说，这一章不是“生成图片”，而是**为图像生成产品搭好工作台**。

## 一、项目初始化与目录规划：先把职责拆开

### 1.1 为什么要拆分目录

AI 图像生成页面看起来不复杂，但实际会涉及表单、结果展示、历史记录、本地缓存、图片上传、任务状态和错误提示。  
如果所有逻辑都写在一个页面里，后面很容易出现状态膨胀、组件耦合、异步任务和 UI 更新混在一起的问题。

所以第一步不是写页面，而是先把职责拆开。

### 1.2 推荐目录结构

```bash
src/
  pages/
    image-gen/
      index.tsx
      index.module.css
  components/
    PromptPanel/
    ResultGallery/
    HistoryList/
    LoadingState/
    PreviewModal/
  api/
    imageGen.ts
  store/
    imageGenStore.ts
  utils/
    cache.ts
    format.ts
    upload.ts
```

### 1.3 每层负责什么

- **pages**：负责页面组合和整体布局
- **components**：负责参数面板、结果画廊、历史列表、预览弹窗等模块
- **api**：负责图像生成接口、任务查询接口、上传接口封装
- **store**：负责提示词、尺寸、加载态、结果和历史记录等状态流转
- **utils**：负责本地缓存、文件处理、时间格式化等通用能力

### 1.4 先做“能跑起来”的基础

新手不需要一开始就把状态管理做得很重。这个页面最重要的是把流程跑通：  
**输入 → 提交 → 等待 → 展示 → 回看**。  
先用清晰的本地状态把骨架搭好，后面再决定要不要接更复杂的状态方案。

---

## 二、页面骨架：固定成四段式结构

### 2.1 页面结构先定死

为了让用户一眼看懂怎么用，页面建议固定成四块：

1. **顶部说明区**：说明这是一个什么页面
2. **左侧输入与参数面板**：输入提示词、选择尺寸、上传参考图
3. **右侧状态与结果展示区**：显示加载态、结果预览、缩略图布局
4. **底部历史记录区**：回看最近任务、再次编辑、继续生成

左侧是输入区，右侧是状态区。这样划分后，后续接异步任务、结果展示和历史回看时，结构会更清晰。

### 2.2 页面骨架示例

```tsx
export default function ImageGenPage() {
  return (
    <main className="page">
      <header className="hero">
        <h1>AI 图像生成</h1>
        <p>输入提示词，选择尺寸，上传参考图，生成图片并保存历史记录。</p>
      </header>

      <section className="content">
        <aside className="panel">{/* 输入区 + 参数面板 */}</aside>
        <section className="result">{/* 状态区 + 结果展示 */}</section>
      </section>

      <section className="history">{/* 历史记录区 */}</section>
    </main>
  );
}
```

### 2.3 交互细节

- 顶部文案要直接说明页面用途
- 左侧按钮在条件不满足时应禁用
- 右侧结果区不能空白，要有空状态和引导文案
- 底部历史记录默认只展示最近几条
- 历史记录中的每一条都应预留“再次编辑”和“查看详情”的入口

### 2.4 预留结果预览弹窗入口

结果区的缩略图点击后，需要进入预览弹窗。  
所以在搭骨架时，就应该把“缩略图 + 弹窗”当成一个整体设计，而不是后面再补。预览弹窗最好支持查看大图、切换上一张下一张，并为下载按钮留出位置。

## 三、状态设计：把页面会用到的字段一次准备齐

### 3.1 本章需要的核心状态

这个页面最少要准备这些字段：

- `prompt`：用户输入的提示词
- `size`：图片尺寸，比如 `1024x1024`
- `uploadFile`：用户上传的参考图片
- `loading`：是否正在生成
- `taskId`：异步任务 ID
- `resultList`：当前任务生成结果
- `errorMessage`：错误信息
- `historyList`：历史记录
- `selectedHistoryId`：当前选中的历史任务

### 3.2 状态结构示例

```ts
type ImageGenState = {
  prompt: string;
  size: string;
  uploadFile: File | null;
  loading: boolean;
  taskId: string | null;
  resultList: string[];
  errorMessage: string;
  historyList: Array<{
    id: string;
    prompt: string;
    size: string;
    cover: string;
    createdAt: string;
  }>;
  selectedHistoryId: string | null;
};
```

### 3.3 字段来源和用途

- `prompt`：来自输入框，决定用户要生成什么内容
- `size`：来自尺寸选择器，决定输出图片比例
- `uploadFile`：来自图片上传，用作参考图或辅助素材
- `loading`：用于控制按钮禁用、加载态和轮询状态
- `taskId`：后续请求任务结果时会用到
- `resultList`：保存当前任务返回的图片地址或缩略图地址
- `errorMessage`：用于显示失败原因，方便重试
- `historyList`：保存最近生成记录，支持回看和再次编辑
- `selectedHistoryId`：用于标识当前正在查看哪条历史记录

### 3.4 更清晰的数据分层

可以把这些字段理解成三层：

- **输入层**：`prompt`、`size`、`uploadFile`
- **过程层**：`loading`、`taskId`、`errorMessage`
- **结果层**：`resultList`、`historyList`、`selectedHistoryId`

这样设计的好处是：后面接异步任务时，不会把“正在生成”和“生成完成”混在一起。

### 3.5 本地缓存先预留好

历史记录通常要支持本地缓存，哪怕后面接了服务端存储，本地缓存也能让页面打开时更快恢复最近使用状态。

```ts
export function saveHistory(list: ImageGenState["historyList"]) {
  localStorage.setItem("image-gen-history", JSON.stringify(list));
}

export function loadHistory() {
  const raw = localStorage.getItem("image-gen-history");
  return raw ? JSON.parse(raw) : [];
}
```

### 3.6 交互细节

- 输入框变化时，实时更新 `prompt`
- 上传图片后，显示文件名和缩略图
- 开始生成后，立即切换 `loading` 状态
- 报错时保留已输入内容，方便直接重试
- 历史记录从本地缓存恢复后，页面打开就能继续使用
- 从历史记录点“再次编辑”时，尽量回填旧提示词、旧尺寸和旧参考图

## 四、基础样式与移动端适配：桌面双栏，手机单列

### 4.1 布局策略

图像生成页面在桌面端和手机端的使用方式不同：

- **桌面端**：左侧放输入与参数，右侧看状态和结果，效率更高
- **移动端**：上下排列，先输入再看结果，更符合单手操作

所以样式上建议采用“桌面双栏、移动端单列”的响应式布局。

### 4.2 样式示例

```css
.page {
  max-width: 1200px;
  margin: 0 auto;
```

### 4.4 移动端要特别注意什么

## 五、首屏交互：空状态、按钮禁用和加载态要能看懂

### 5.1 空状态不能是“空白页”

用户第一次进入页面时，如果结果区什么都没有，就会不知道下一步做什么。  
所以空状态要明确给出引导：

- 一句提示：输入提示词后点击生成
- 一个示例按钮：比如“赛博风城市海报”
- 一个占位区域：让用户知道结果会出现在这里

### 5.2 按钮什么时候禁用

生成按钮建议在以下情况禁用：

- 提示词为空
- 正在加载中
- 当前流程要求上传参考图，但用户还没上传

```tsx
<button disabled={loading || !prompt.trim()}>
  {loading ? "生成中..." : "开始生成"}
</button>
```

### 5.3 加载态要足够明显

图像生成是异步任务，不会点一下就出结果，所以加载态一定要明确。建议同时做三层反馈：

- 按钮文案变成“生成中...”
- 结果区显示 skeleton 或占位卡片
- 文案提示“任务已提交，正在等待结果”

这样用户会知道系统还在处理，而不是卡死了。

### 5.4 图片上传和结果预览先接上思路

本章虽然不展开完整上传流程和预览弹窗实现，但布局上要提前预留位置：

- 上传区要能显示已选文件
- 结果区要能承接缩略图列表
- 缩略图点击后能弹出大图预览
- 预览弹窗里最好能看到图片信息、下载按钮和再次编辑入口

这一步很重要，因为后续做下载、收藏、再次编辑时，结果区结构都要依赖它。

# 第3章：做出输入区——提示词、尺寸选择与图片上传表单

做 AI 图像生成产品，第一步不是“怎么画”，而是“用户怎么把需求准确告诉系统”。输入区是流程起点，决定用户是否愿意提交、是否能快速试错，也决定后续的异步任务、结果展示、下载和历史记录能否顺利衔接。  
这一章只做前端产品里的**发起生成表单**：提示词输入、尺寸选择、参考图上传、校验与按钮状态。

## 一、输入区的页面结构：先把表单骨架搭起来

一个真正能发起请求的输入区，建议按下面的结构组织：

1. **提示词输入区**：填写生成描述，支持示例填充  
2. **尺寸选择区**：横图、方图、竖图、自定义  
3. **参考图上传区**：上传、预览、替换、删除  
4. **辅助操作区**：清空、随机示例、一键填充  
5. **提交区**：生成按钮、加载态、错误提示  

```html
<form class="generator-form">
  <section class="prompt-panel">
    <label for="prompt">提示词</label>
    <textarea
      id="prompt"
      placeholder="输入你想生成的图片描述，例如：一张夜晚城市霓虹风海报，蓝紫配色，高对比度"
    ></textarea>
    <div class="meta">
      <span>建议 20-200 字</span>
      <span class="count">0 / 200</span>
    </div>
    <div class="quick-actions">
      <button type="button">一键填充示例</button>
      <button type="button">随机示例</button>
      <button type="button">清空</button>
    </div>
  </section>

  <section class="size-picker">
    <button type="button" data-size="landscape">横图 16:9</button>
    <button type="button" data-size="square">方图 1:1</button>
    <button type="button" data-size="portrait">竖图 9:16</button>
    <button type="button" data-size="custom">自定义</button>
  </section>

  <section class="upload-panel">
    <label class="upload-box">
      <input type="file" accept="image/*" />
      <div>点击上传参考图，或拖拽到此处</div>
      <small>支持 JPG / PNG / WebP，建议小于 5MB</small>
    </label>
    <div class="thumb-list"></div>
  </section>

  <div class="submit-row">
    <button type="submit">生成图片</button>
  </div>
</form>
```

重点不是把控件堆满，而是让用户一眼知道：**写什么、选什么、传什么、点哪里开始生成**。这才是图像生成产品里的输入区。

## 二、提示词输入框：让用户写得下、写得准、写得快

### 1. 输入框的基本结构

提示词区至少要有三部分：

- **主输入框**：填写生成描述  
- **辅助信息**：字数提示、示例提示  
- **快捷操作**：一键填充、清空、随机示例  

```html
<section class="prompt-panel">
  <label for="prompt">提示词</label>
  <textarea id="prompt" placeholder="输入你想生成的图片描述，例如：一张夜晚城市霓虹风海报，蓝紫配色，高对比度"></textarea>
  <div class="meta">
    <span>建议 20-200 字</span>
    <span class="count">0 / 200</span>
  </div>
  <div class="quick-actions">
    <button>一键填充示例</button>
    <button>随机示例</button>
    <button>清空</button>
  </div>
</section>
```

建议用多行文本域，方便用户写完整需求。对新手来说，**写得下** 比 **样式炫** 更重要。

### 2. 占位文案怎么写

占位文案要直接告诉用户写什么，最好包含：

- 主体：人物、产品、场景、物体  
- 风格：写实、扁平、赛博、插画  
- 用途：封面、海报、社媒配图  
- 画面要求：色调、构图、光线  

例如：

> 输入你想生成的图片描述，例如：一张极简风科技产品海报，深色背景，银白色字体，居中构图

如果面向前端新手，下方再补一句“写清楚主体、风格和用途，越具体越容易接近预期”会更实用。

### 3. 字数提示和最小长度

字数提示不是装饰，而是帮助用户判断输入是否足够。可以分三种状态：

- **过短**：提示补充主体或风格  
- **合适**：允许提交  
- **过长**：提示精简  

建议设置一个最小输入长度，比如 10 个字符起步；更复杂的场景可以提高到 20 字。前端重点不是严格“审稿”，而是尽量在提交前挡住明显无效输入。

例如：

- 过短：`再写一点细节，至少说明主体和风格`
- 合适：`可以提交`

### 4. 快捷示例的价值

新手最怕“不知道怎么写”，所以最好提供可点击示例：

- 电商风产品图
- 社媒封面图
- 赛博城市夜景
- 儿童绘本插画

点击后可直接填入文本框，必要时同步切换推荐尺寸。比如“海报示例”默认竖图，“Banner 示例”默认横图，能减少来回调整。

---

## 三、尺寸选择器：把宽高变成场景选择

### 1. 尺寸不是参数而是产品决策

用户通常不是来“设置宽高”，而是来生成某种用途的图片。  
所以尺寸选择最好不要直接暴露复杂数字，而是用**场景化选项**：

- **横图**：适合头图、Banner、封面  
- **方图**：适合头像、社媒卡片、通用素材  
- **竖图**：适合海报、手机长图、故事封面  
- **自定义尺寸**：给进阶用户  

用户选的是“图片放哪里”，不是单纯比例。

### 2. UI 设计建议

建议用卡片式按钮：

```html
<div class="size-picker">
  <button data-size="landscape">横图 16:9</button>
  <button data-size="square">方图 1:1</button>
  <button data-size="portrait">竖图 9:16</button>
  <button data-size="custom">自定义</button>
</div>
```

自定义尺寸最好在用户选择后再展开宽高输入框，避免界面一开始就过重。

### 3. 默认值和联动逻辑

为了降低新手成本，页面进入时最好给一个默认尺寸，例如“方图 1:1”或“横图 16:9”。  
同时可以做简单联动：

- 点击“海报示例”时自动切到竖图
- 点击“封面示例”时自动切到横图
- 上传手机截图时，推荐方图或竖图

目的不是替用户决定，而是减少来回调整，让输入更顺畅。

### 4. 常见误区

- 直接让用户输入宽高，学习成本高
- 尺寸太多，用户不会选
- 只给技术比例，不讲使用场景

如果一上来给很多比例，用户很容易放弃。前端产品里，**少而清楚** 往往比 **多而专业** 更有效。

## 四、图片上传能力：参考图不是附件，而是生成输入

### 1. 为什么要支持图片上传

在图像生成产品里，上传图片不是附件功能，而是用户的参考输入。  
它可以用于：

- 提供构图参考
- 上传草图、照片、品牌素材
- 做图生图或风格参考
- 让结果更贴近现有视觉资产

所以上传区不是装饰，而是覆盖复杂生成场景的关键能力。

### 2. 上传区页面结构

```html
<section class="upload-panel">
  <label class="upload-box">
    <input type="file" accept="image/*" />
    <div>点击上传参考图，或拖拽到此处</div>
    <small>支持 JPG / PNG / WebP，建议小于 5MB</small>
  </label>
  <div class="thumb-list">
    <div class="thumb-item">
      <img src="preview.jpg" alt="预览缩略图" />
      <button>替换</button>
      <button>删除</button>
    </div>
  </div>
</section>
```

移动端要把上传区做大，保证容易点击；拖拽可以作为加分项，但不要成为唯一入口。

### 3. 预览缩略图与替换删除

上传后不要只显示文件名，最好立即生成缩略图，让用户确认是否传对了。  
推荐交互：

- 上传后立即显示缩略图
- 点击缩略图可放大预览
- 支持替换
- 支持删除并恢复初始状态

缩略图点击后可以打开一个**结果预览弹窗**式的大图查看层，方便用户确认图片细节。参考图同样需要“先看清再提交”。

### 4. 文件限制要明确

前端要明确告诉用户：

- 支持格式：JPG、PNG、WebP
- 文件大小限制：例如 5MB
- 是否允许多张：单张或多张
- 是否支持拖拽：如果支持，要给视觉反馈

同时准备异常反馈：

- 格式不支持：`图片格式不支持，请上传 JPG、PNG 或 WebP`
- 文件过大：`图片超过 5MB，请压缩后再试`
- 读取失败：`图片预览失败，请重新选择文件`

不要把错误只放在页面顶部，那样用户很难知道该改哪里。

## 五、表单校验与禁用逻辑：什么时候允许点击“生成”？

### 1. 生成按钮的启用条件

按钮状态必须跟表单状态绑定，避免用户提交空请求。常见判断标准：

- 提示词达到最小长度
- 尺寸已选择
- 上传图片格式合法
- 文件大小不超限
- 当前没有正在提交的任务

### 2. 示例逻辑

```js
const canSubmit =
  prompt.trim().length >= 10 &&
  selectedSize &&
  !isSubmitting &&
  uploadError == null;
```

如果参考图是必填项，也可以改成：

```js
const canSubmit = promptOk && sizeOk && hasImage && !isSubmitting;
```

这类判断最好集中管理，不要散在多个事件里，否则后续接异步任务会很乱。

### 3. 错误提示要贴近字段

不要只在页面顶部写一句“提交失败”。更好的方式是：

- 提示词过短：显示在输入框下方
- 文件过大：显示在上传区
- 尺寸未选：在尺寸卡片附近提示
- 图片读取失败：在缩略图位置提示

局部提示更利于新手定位问题，也更符合表单产品的习惯。

### 4. 加载态与提交态

点击生成后，按钮应进入加载态：

- 文案从“生成图片”变成“生成中…”
- 按钮禁用，避免重复提交
- 输入内容保留，方便稍后修改
- 接口较慢时显示微型加载提示或骨架状态

这一步是后续**异步任务处理**的前提：前端要先告诉用户“请求已提交，正在生成中”。  
如果接口只是提交任务成功，也不要假装已经出图。

## 六、辅助操作：清空、一键填充、随机示例怎么设计才有用？

### 1. 清空

清空按钮只清除当前表单，不删除历史记录。  
如果已经上传了图片，最好弹出轻确认，避免误删参考图。

### 2. 一键填充示例

适合新手引导。点击后填入完整示例，包括提示词和尺寸建议，例如：

- 提示词：一张极简科技风产品海报，深蓝背景，居中排版，留白充足
- 尺寸：竖图 9:16

它的作用不是让用户偷懒，而是让用户知道“有效提示词”是什么样。

### 3. 随机示例

随机示例主要是帮助用户理解不同写法的差异。  
你可以准备几类模板：

- 电商图
- 海报图
- 头像图
- 封面图

每次点击替换一条，并同步风格关键词，能更快帮助用户建立输入感。

## 七、参考图联动提示词：别把上传区写成普通文件页

如果只把上传做成“选文件”，它就会退化成普通附件上传。图像生成产品里，更好的做法是让参考图和提示词互相补充：

- 上传产品图后，提示词可自动补一句“保持原产品结构”
- 上传人物照片后，提示词可提醒“保留人物姿态与构图”
- 上传品牌素材后，提示词可提示“保持品牌色和版式节奏”

哪怕只是一个轻提示，也有价值。  
例如用户上传后，提示区旁边出现一条说明：

> 已上传参考图，可在提示词中补充“保留构图”“延续色调”“参考这个风格”

这样能帮助用户理解：**图片上传不是独立功能，而是生成输入的一部分**。

## 八、一个可直接落地的表单实现思路

最小实现可以按下面的步骤做：

1. 用一个 `form` 包住提示词、尺寸、上传区  
2. 用 `textarea` 采集提示词  
3. 用按钮组切换尺寸  
4. 用 `input type="file"` 接收参考图  
5. 前端完成基础校验  
6. 生成按钮根据校验结果动态启用  
7. 提交时把表单数据交给后续 API 流程  

```js
function handleSubmit() {
  if (!canSubmit) return;
  setSubmitting(true);
  // 后续章节会接入 API、轮询任务状态和结果展示
}
```

如果想更像真实产品，建议再补两个状态：文件已选中状态、表单已修改但未提交状态。这样用户在反复改提示词和图片时，会更清楚自己当前处于哪一步。

## 九、本章小结：输入区要解决的不是“输入”，而是“发起请求”

这一章完成了 AI 图像生成页面的起点：

- 提示词输入要清晰、可引导、可补充
- 尺寸选择要场景化，不要把用户丢进技术参数
- 图片上传要能预览、替换、删除，并明确限制
- 表单校验要前置，按钮状态要实时变化
- 辅助操作要帮助新手快速开始
- 参考图要和提示词联动，避免变成普通文件上传页

如果这一页已经做好，下一步就可以进入真正的业务主线：**把表单数据转成生成请求，并处理异步任务返回结果**。  
前端接入 AI 图像生成，核心不是炫技，而是把“用户想要什么”稳定送到“模型能处理什么”之间。

# 第4章：接入生成接口——调用 AI 图像生成 API 的完整流程

## 开篇引入：前端接入的第一道门，不是“画图”，而是“发起一次可靠请求”

新手接入 AI 图像生成时，最容易盯着“图像好不好看”，但从前端产品看，真正决定体验的不是模型会不会画，而是**请求能不能稳定发出去、结果能不能正确等回来、生成后的数据能不能继续用**。

这一章解决的是接入问题：把页面里的提示词、尺寸、数量、参考图等信息整理成标准请求，并正确处理接口返回的同步结果或异步任务结果。只要这条链路打通，后面的结果展示、下载、历史记录、收藏和再次编辑都会顺畅很多。

本章要建立的完整流程是：

1. 用户填写提示词，选择尺寸和数量；
2. 可选上传参考图；
3. 点击生成后进入加载态；
4. 前端统一发起请求并处理返回；
5. 如果是异步任务，就轮询结果；
6. 成功后整理成可展示、可下载、可继续编辑的数据结构；
7. 同步写入历史记录和本地缓存。

## 一、图像生成 API 的常见入参：前端到底要收集哪些信息？

### 1. 这类接口通常需要哪些字段？

图像生成接口通常不只传一句话。为了让结果可控，前端一般要收集这些信息：

- **提示词 prompt**：用户想要什么图
- **尺寸 size**：如 `1024x1024`、`1024x1792`、`1792x1024`
- **生成数量 count**：一次生成几张
- **风格 style**：如写实、插画、海报、赛博风
- **参考图 referenceImage**：用于参考构图、风格或局部编辑
- **负向提示词 negativePrompt**：不希望出现的内容
- **质量参数 quality**：高质量、快速模式等

有些平台还会返回 `taskId`、`status`、`imageUrls` 等字段。前端不必一开始支持全部能力，但要预留扩展空间，避免后面接口升级时重做。

### 2. 前端表单结构怎么设计？

建议把页面分成“基础输入”和“高级参数”两层。基础输入尽量清晰，高级参数可以折叠，减少干扰。

#### 页面结构
- 提示词输入框
- 尺寸选择器
- 数量选择器
- 风格下拉框
- 图片上传区
- 生成按钮
- 参数说明区

#### 交互细节
- 提示词为空时禁止提交
- 尺寸和数量用按钮组选项，降低输入成本
- 上传参考图后立即显示缩略图，方便确认
- 高级参数默认收起，保持界面简洁
- 移动端采用纵向排列，确保单手可操作

### 3. 一个适合前端的参数对象

```ts
type GenerateImageParams = {
  prompt: string;
  size: "1024x1024" | "1024x1792" | "1792x1024";
  count: number;
  style?: string;
  negativePrompt?: string;
  referenceImage?: File | string;
};
```

这个对象的核心原则是：**只描述生成请求，不混入页面状态**。像 `loading`、`error`、`previewOpen` 这类 UI 状态，不应该放进请求参数里。

## 二、前端请求封装：如何把表单数据变成统一请求？

### 1. 为什么一定要封装请求函数？

如果把接口调用直接写在组件里，后续很容易出现这些问题：

- 参数转换散落在多个地方
- 错误处理不统一
- 同步接口和异步接口切换困难
- 历史记录、重试、收藏接入时越来越乱

所以建议把“请求”单独抽出来，让页面只负责收集参数和展示结果。

### 2. 页面结构

- `GenerateForm`：负责表单填写
- `useGenerateImage`：管理调用过程、加载态和返回结果
- `api/generateImage.ts`：请求封装
- `types.ts`：统一声明返回结构

### 3. 核心代码：请求封装

```ts
import axios from "axios";

export type GenerateResult = {
  taskId?: string;
  status: "queued" | "processing" | "succeeded" | "failed";
  imageUrls?: string[];
  costMs?: number;
  message?: string;
};

export async function generateImage(params: FormData): Promise<GenerateResult> {
  try {
    const res = await axios.post("/api/image-generate", params, {
      headers: { "Content-Type": "multipart/form-data" },
    });

    return {
      taskId: res.data.taskId,
      status: res.data.status,
      imageUrls: res.data.imageUrls || [],
      costMs: res.data.costMs,
      message: res.data.message,
    };
  } catch (err: any) {
    throw {
      message: err?.response?.data?.message || "图像生成请求失败",
      code: err?.response?.status || 500,
      raw: err,
    };
  }
}
```

这里把错误对象统一了。组件层不需要去猜 `axios` 的内部结构，只要按 `message`、`code`、`raw` 处理即可。这样后面做失败重试、消耗提示、日志上报时，数据就很稳定。

### 4. 参数转换怎么做？

如果包含图片上传，统一用 `FormData`，这样既能传文本，也能传文件。

```ts
export function buildGenerateFormData(params: GenerateImageParams) {
  const formData = new FormData();
  formData.append("prompt", params.prompt);
  formData.append("size", params.size);
  formData.append("count", String(params.count));

  if (params.style) formData.append("style", params.style);
  if (params.negativePrompt) formData.append("negativePrompt", params.negativePrompt);
  if (params.referenceImage instanceof File) {
    formData.append("referenceImage", params.referenceImage);
  }

  return formData;
}
```

### 5. 常见误区

- 把 `File` 直接放进 JSON
- 请求逻辑和页面状态耦合
- 错误文案不统一，用户看不懂
- 组件里写死接口地址，后面切换供应商很痛苦

## 三、同步返回与异步任务：为什么前端必须区分两类接口？

### 1. 同步返回接口是什么？

同步返回指的是：前端发出请求后，接口很快直接返回图片地址或图片数据。它实现简单，但不一定适合真实的图像生成场景，因为生成过程可能较慢，尤其在高质量模式下。

### 2. 异步任务接口是什么？

异步任务更常见：前端提交请求后，接口先返回一个 `taskId`，真正结果稍后再获取。对生成类能力来说，这种方式更稳妥，也更符合用户预期。

### 3. 两类接口在前端的适配方式

#### 同步返回
- 点击生成后立即进入加载态
- 接口成功后直接展示图片
- 适合结果快、流程简单的接口

#### 异步任务
- 点击生成后先拿到 `taskId`
- 页面显示“生成中”
- 轮询任务状态直到成功或失败
- 成功后拿到图片地址并刷新结果区

### 4. 推荐统一返回结构

前端最好无论面对哪种接口，都转成同一套结构处理：

```ts
type TaskResponse = {
  taskId: string;
  status: "queued" | "processing" | "succeeded" | "failed";
  imageUrls: string[];
  costMs?: number;
  message?: string;
};
```

这样页面逻辑就不用分太多支路，后续接入结果预览弹窗、下载、历史记录时也更方便。

### 5. 判断标准

如果接口返回里有 `taskId` 和 `status`，就按异步任务设计；  
如果接口直接返回 `imageUrls`，就按同步展示处理，但也要保留以后升级为异步的空间。

## 四、提交生成请求时的加载态：如何让用户知道“正在处理”？

### 1. 为什么加载态不能省？

图像生成不是普通表单提交。用户点下按钮后，往往要等几秒甚至更久。如果页面没有任何反馈，用户会重复点击，甚至刷新页面，造成重复请求和状态错乱。

### 2. 页面结构

- 生成按钮
- 状态文案区域
- 骨架屏或占位卡片
- 进度提示区

### 3. 核心交互设计

#### 按钮锁定
- 点击后按钮禁用
- 文案改成“生成中...”
- 防止重复提交

#### 骨架屏
- 结果区域先显示灰色占位卡
- 让用户知道不是页面失效，而是在等待结果

#### 状态文案
建议按阶段展示：

- 正在提交任务...
- 正在生成图片，请稍候
- 仍在排队中
- 生成完成
- 生成失败，请重试

### 4. 核心代码：加载态控制

```ts
const [loading, setLoading] = useState(false);
const [statusText, setStatusText] = useState("");
const [submitDisabled, setSubmitDisabled] = useState(false);

async function handleGenerate() {
  if (loading) return;
  setLoading(true);
  setSubmitDisabled(true);
  setStatusText("正在提交任务...");

  try {
    const formData = buildGenerateFormData(params);
    const result = await generateImage(formData);

    if (result.status === "succeeded") {
      setStatusText("生成完成");
    } else {
      setStatusText("正在生成图片，请稍候");
    }
  } catch (e: any) {
    setStatusText(e.message || "生成失败，请重试");
  } finally {
    setLoading(false);
    setTimeout(() => setSubmitDisabled(false), 300);
  }
}
```

### 5. 交互细节

- 移动端按钮最好固定在底部，但不要遮挡状态信息
- 骨架屏数量不要过多，避免像页面卡死
- 如果等待时间较长，可以加一句“系统正在排队，请稍后查看”，减少焦虑
- 当任务从“提交中”进入“生成中”时，文案要及时切换，别一直停留在同一个状态

## 五、异步任务处理：轮询结果、失败分支与结果落地

### 1. 异步任务为什么必须单独处理？

图像生成类接口里，最常见的就是“先提交，后出图”。前端拿到 `taskId` 之后，不能假设下一秒就有结果，而要持续查询任务状态，直到成功、失败或超时。

### 2. 页面结构

- 任务状态卡片
- 轮询提示
- 成功结果区
- 失败重试入口

### 3. 核心代码：轮询任务状态

```ts
async function pollTaskResult(taskId: string) {
  for (let i = 0; i < 30; i++) {
    const res = await axios.get(`/api/image-generate/${taskId}`);
    const data = res.data;

    if (data.status === "succeeded") {
      return {
        taskId,
        status: "succeeded",
        imageUrls: data.imageUrls || [],
        costMs: data.costMs,
      };
    }

    if (data.status === "failed") {
      throw new Error(data.message || "任务生成失败");
    }

    await new Promise((r) => setTimeout(r, 2000));
  }

  throw new Error("任务超时，请稍后在历史记录中查看");
}
```

### 4. 交互细节

- 轮询期间给出明确文案，如“正在排队”“正在出图”
- 超过一定时间后提示用户去历史记录查看，避免一直空等
- 如果页面刷新，任务信息应还能从本地缓存恢复
- 失败时不要清空表单，保留原始输入，方便再次编辑

## 六、结果结构、历史记录与本地缓存：让生成结果能继续用

### 1. 结果结构不能只返回图片地址

如果只保留图片 URL，后面做历史记录、再次编辑、失败重试都会比较被动。更合理的做法，是把一次生成记录整理成完整对象。

### 2. 推荐统一结果模型

```ts
type GenerateRecord = {
  taskId: string;
  prompt: string;
  size: string;
  status: "queued" | "processing" | "succeeded" | "failed";
  imageUrls: string[];
  costMs?: number;
  createdAt: number;
  updatedAt?: number;
  errorMessage?: string;
};
```

这个结构至少能支持三件事：

1. 结果展示  
2. 历史记录保存  
3. 再次编辑时回填参数  

如果任务失败，`errorMessage` 也能直接用于提示用户，而不需要临时拼文案。

### 3. 如何和历史记录衔接？

生成成功后，可以把记录存到本地缓存中。对新手项目来说，`localStorage` 足够满足基础需求；如果后续要做账号体系或跨设备同步，再接后端存储即可。

建议保存这些内容：

- prompt
- 尺寸
- 状态
- 图片地址
- 创建时间
- 失败原因
- 耗时

这样即使用户刷新页面，也能在“历史记录”里找到最近生成过的内容。

### 4. 本地缓存示例

```ts
const HISTORY_KEY = "ai_image_history";

export function saveHistory(record: GenerateRecord) {
  const list = JSON.parse(localStorage.getItem(HISTORY_KEY) || "[]");
  list.unshift(record);
  localStorage.setItem(HISTORY_KEY, JSON.stringify(list.slice(0, 20)));
}

export function loadHistory(): GenerateRecord[] {
  return JSON.parse(localStorage.getItem(HISTORY_KEY) || "[]");
}
```

### 5. 结果展示的基础形态

#### 页面结构
- 结果主图区域
- 缩略图列表
- 下载按钮
- 再次编辑按钮
- 历史记录入口

#### 交互细节
- 点击缩略图打开结果预览弹窗
- 弹窗内支持放大查看
- 每张图都能单独下载
- 点击“再次编辑”时，自动把 prompt 回填到输入框
- 历史记录中的失败任务也要保留，方便用户理解上次为什么没成功

### 1. 为什么要有预览弹窗？

缩略图适合快速浏览，但当用户想检查细节、准备下载或继续编辑时，就需要一个更大的查看层。结果预览弹窗是生成页面里很关键的一个交互点。

## 八、失败重试与消耗提示：别让用户在失败后无从下手

### 1. 失败不是结束，而是下一次操作的入口

图像生成任务失败的原因很多：参数不合法、队列拥堵、图片上传失败、服务限流、网络中断。前端不能只显示一句“失败了”，而要告诉用户还能做什么。

### 2. 页面结构

- 失败提示条
- 重试按钮
- 消耗信息区
- 最近任务状态卡片

### 3. 交互细节

- 失败后保留用户刚才填写的参数
- 提供“一键重试”
- 如果请求已产生消耗，要显示“本次任务已扣除次数/额度”或“本次请求未成功计费”的明确提示
- 重试前可检查图片上传是否还有效，避免用户重复踩坑

### 4. 建议文案

- 任务生成失败，请检查网络后重试
- 当前请求已进入队列，稍后可在历史记录中查看
- 本次任务已消耗 1 次生成额度
- 图片参考文件失效，请重新上传

### 5. 核心代码：重试入口

```ts
async function handleRetry(record: GenerateRecord) {
  setStatusText("正在重新提交...");
  const formData = buildGenerateFormData({
    prompt: record.prompt,
    size: record.size as any,
    count: 1,
  });

  const result = await generateImage(formData);
  return result;
}
```

这一步的重点不是“再发一次请求”，而是把失败后的路径也设计清楚，让用户知道下一步怎么做。

# 第5章：处理异步任务——轮询等待、状态更新与失败重试

## 开篇引入：为什么图像生成页面一定要先处理“等待”

AI 图像生成通常是异步接口。用户提交提示词、上传参考图、选择尺寸后，前端往往先拿到一个 `taskId`，真正的图片要等后台排队、推理、合成完成后才返回。对前端来说，重点不是“怎么发请求”，而是**怎么把等待变成清晰、可恢复、可操作的流程**。

如果这一层没做好，页面就会出现几个典型问题：

- 用户不知道任务有没有发出去；
- 页面一直转圈，但没有结果；
- 刷新后任务丢失；
- 失败后只能重来，提示词、尺寸、上传图片都得重新填。

所以本章要解决的是**任务处理能力**：识别状态、处理异步等待、支持失败重试，并在刷新后恢复任务。把这一层做好，后面的画廊展示、下载、历史记录、本地缓存才真正能连成完整产品。

## 一、异步任务的状态机：排队中、生成中、成功、失败、超时、取消

### 这一节要回答的问题
**用户点击“生成”后，页面该如何判断当前任务走到哪一步了？**

### 1.1 为什么要先定义状态机

图像生成接口通常不是直接返回图片，而是先返回任务编号，再由前端持续查询结果。也就是说，你面对的不是一个请求，而是一段流程。

建议先定义一个最小但完整的状态机：

- `queued`：排队中，任务已提交但还没开始处理；
- `processing`：生成中，模型正在执行；
- `success`：成功，已拿到图片地址或图片数组；
- `failed`：失败，任务执行出错；
- `timeout`：超时，等待过久仍未完成；
- `canceled`：取消，用户主动中止任务。

有了状态机，页面才能明确知道该显示什么、按钮怎么变、用户下一步能做什么。

### 1.2 状态如何转换

可以按下面的路线理解：

- 提交任务后：`idle -> queued`
- 后端开始处理：`queued -> processing`
- 正常返回结果：`processing -> success`
- 服务报错或参数不合法：`queued/processing -> failed`
- 等待超过阈值：`queued/processing -> timeout`
- 用户主动取消：`queued/processing -> canceled`

其中 `timeout` 不等于 `failed`。超时更像“暂时没查到结果”，而失败是“明确终止”。这两个状态在页面上的文案和按钮应该不同。

### 1.3 页面结构

```markdown
- 顶部任务状态条
- 中部预览区
  - 占位图
  - 加载动画
  - 结果图片
- 底部状态说明
  - 排队中/生成中/失败原因/超时提示
  - 重试按钮
  - 取消按钮
  - 继续查询按钮
```

### 1.4 核心代码：状态驱动渲染

```ts
type TaskStatus = 'queued' | 'processing' | 'success' | 'failed' | 'timeout' | 'canceled';

interface TaskState {
  taskId: string;
  status: TaskStatus;
  progressText: string;
  resultUrl?: string;
  errorMessage?: string;
}

function renderStatus(state: TaskState) {
  switch (state.status) {
    case 'queued':
      return '任务已提交，正在排队中';
    case 'processing':
      return '图像生成中，请稍候';
    case 'success':
      return '生成完成';
    case 'failed':
      return state.errorMessage || '生成失败';
    case 'timeout':
      return '等待超时，请重新查询或重试';
    case 'canceled':
      return '任务已取消';
  }
}
```

### 1.5 交互细节

- 排队中显示明确文案，如“正在排队，请不要关闭页面”；
- 生成中保留用户刚填写的提示词、尺寸、上传图片信息，方便失败后重试；
- 成功后立即切换到结果预览，避免继续停留在 loading 状态；
- 失败、超时、取消都要提供明确操作，而不是只显示“出错了”。

## 二、轮询接口设计：间隔、次数、停止条件与清理机制

### 这一节要回答的问题
**怎么持续查询任务结果，又不把页面和接口打爆？**

### 2.1 轮询的基本思路

提交生成任务后，后端通常会返回 `taskId`。前端接下来要定时查询任务接口，比如 `/api/image/task/{taskId}`，直到拿到成功、失败、超时或取消结果。

轮询要控制好五件事：

1. **轮询间隔**：太短会浪费请求，太长会让用户焦虑；
2. **最大次数**：防止无限轮询；
3. **停止条件**：成功、失败、取消、超时；
4. **清理机制**：页面卸载或切换路由时，定时器必须清掉；
5. **恢复机制**：刷新后继续根据 `taskId` 查询，不重复创建新任务。

新手可以先用固定间隔，比如 2 秒一次，简单且稳定。

### 2.2 页面结构

```markdown
- 任务提交后进入等待面板
  - 任务编号
  - 当前轮询状态
  - 预计刷新频率
- 失败或超时后显示操作区
  - 重新查询
  - 手动重试
  - 返回编辑
```

### 2.3 核心代码：轮询实现

```ts
let timer: number | null = null;
let polling = false;

async function pollTask(taskId: string) {
  if (polling) return;
  polling = true;

  let count = 0;
  const maxCount = 60;
  const interval = 2000;

  const loop = async () => {
    try {
      count += 1;
      const res = await fetch(`/api/image/task/${taskId}`);
      const data = await res.json();

      if (data.status === 'success') {
        stopPolling();
        updateState({ status: 'success', resultUrl: data.resultUrl });
        return;
      }

      if (data.status === 'failed') {
        stopPolling();
        updateState({ status: 'failed', errorMessage: data.message });
        return;
      }

      if (data.status === 'canceled') {
        stopPolling();
        updateState({ status: 'canceled' });
        return;
      }

      if (count >= maxCount) {
        stopPolling();
        updateState({ status: 'timeout', errorMessage: '任务等待超时' });
        return;
      }

      timer = window.setTimeout(loop, interval);
    } catch {
      if (count >= maxCount) {
        stopPolling();
        updateState({ status: 'timeout', errorMessage: '网络异常，任务暂时无法确认' });
        return;
      }
      timer = window.setTimeout(loop, interval);
    }
  };

  await loop();
}

function stopPolling() {
  if (timer !== null) {
    clearTimeout(timer);
    timer = null;
  }
  polling = false;
}
```

### 2.4 交互细节

- 用户点击“取消”时，必须停止轮询，并把任务标记为已取消；
- 切换路由、关闭弹窗、离开页面时要自动清理定时器；
- 查询接口返回处理中时，只更新局部状态，不要整页刷新；
- 如果接口偶发失败，可以允许再查一次再判断失败，避免误报；
- 超时后保留 `taskId`，让用户还能点“继续查询”。

### 2.5 生命周期清理，避免重复请求

轮询最容易出问题的地方，不是接口本身，而是组件卸载后还在跑定时器。新手项目里很常见：页面切走了，`setTimeout` 还在继续发请求，最后造成重复查询。

```ts
function onUnmount() {
  stopPolling();
}
```

如果是 React，可以在 `useEffect` 的清理函数里做；如果是 Vue，可以在 `onUnmounted` 里做。核心原则只有一句：**任务没了，轮询也必须停。**

## 三、任务等待页与加载态文案：进度提示、预计等待、用户可取消

### 这一节要回答的问题
**等待过程中，页面怎么设计才能让用户不焦虑？**

### 3.1 页面结构

```markdown
- 中央加载卡片
  - 动态图标或骨架屏
  - 文案提示
  - 预计等待时间
- 右下角操作区
  - 取消任务
  - 后台继续
- 下方补充信息
  - 提示词摘要
  - 当前尺寸
  - 已消耗次数/点数
```

### 3.2 加载态文案要分层

加载态最怕只有一句“Loading”。更好的方式是让文案跟着状态变化：

- 排队中：`正在排队，请稍候`
- 生成中：`模型正在生成中，请不要关闭页面`
- 接近超时：`生成时间较长，你可以先离开页面，结果会保留`
- 失败：`本次生成未完成，可保留参数重试`

如果产品有“点数”或“次数”消耗，也可以在等待页顺手提示一次。

### 3.4 交互细节

- “取消任务”旁边最好说明取消后是否还会扣费；
- 移动端按钮要足够大，避免误触；
- 进度条可以是伪进度，但不要假装真实百分比；
- 若任务较慢，可以提示用户“切换到其他页面，完成后结果会保留”；
- 等待页应提供一个“继续查询”按钮，方便超时后的二次恢复。

## 四、失败重试策略：保留参数、提示错误、提供兜底方案

### 这一节要回答的问题
**当任务失败时，前端怎样让用户快速再来一次？**

### 4.1 失败不等于结束

图像生成失败很常见，可能是提示词不合规、服务繁忙、网络中断、额度不足、图片上传格式不支持，甚至只是后端短暂抖动。前端要做的不是“展示错误”这么简单，而是**让用户少重复输入**。

因此，失败页要尽量保留上一次的表单数据：提示词、尺寸、图片上传、风格选项都应该继续可用。

### 4.2 页面结构

```markdown
- 失败提示区
  - 错误原因
  - 重试按钮
  - 修改提示词按钮
- 参数保留区
  - 提示词
  - 尺寸
  - 图片上传
  - 风格选项
```

### 4.3 核心代码：重试时保留参数

```ts
function retryGenerate(savedForm: any) {
  setFormState({
    prompt: savedForm.prompt,
    size: savedForm.size,
    imageFile: savedForm.imageFile,
    style: savedForm.style,
  });

  submitGenerate(savedForm);
}
```

### 4.4 兜底方案

如果失败原因不明确，可以按这个顺序处理：

1. **立即重试一次**：适合网络抖动；
2. **重新查询任务**：适合任务其实已完成，但结果回传延迟；
3. **重新提交任务**：适合任务查询超时；
4. **返回编辑页修改参数**：适合提示词过长、图片上传不合规、尺寸不支持等情况。

### 4.5 消耗提示联动

失败重试时，最好把“消耗”讲清楚：

- 如果这次失败没有扣费，就明确说明“本次未扣除次数”；
- 如果失败也会消耗一次，就在按钮旁写明“重试会重新占用 1 次额度”；
- 如果任务状态不确定，先执行“继续查询”而不是直接重提，避免重复扣费。

这部分很关键，因为它会直接影响用户对产品的信任。

### 4.6 交互细节

- 错误提示要尽量具体，例如“图片上传格式不支持”比“生成失败”更有用；
- 重试按钮旁边可以提示“不会重新填写表单”；
- 超时后先提供“继续查询”，再提供“重新生成”；
- 如果失败已经扣费，必须说明消耗情况，避免用户误解。

## 五、任务超时与异常恢复：刷新后重新查询结果

### 这一节要回答的问题
**用户刷新页面后，任务还能找回来吗？**

### 5.1 为什么必须支持恢复

AI 图像生成往往需要较长时间，用户中途刷新、切后台、网络短暂中断都很常见。如果不做恢复，用户会以为任务丢失了，体验会很差。

前端至少要把以下信息放到本地缓存里：

- `taskId`
- 提交时间
- 当前参数
- 当前状态
- 结果地址（如果已成功）

页面初始化时，先读本地缓存，再决定下一步怎么做。

### 5.2 恢复思路

- 如果任务处于 `queued` 或 `processing`，自动继续查询；
- 如果任务已 `success`，直接恢复结果预览；
- 如果任务已 `failed` 或 `timeout`，展示失败状态并允许重试；
- 如果本地缓存里只剩 `taskId`，也可以先查接口再补全状态。

这样用户刷新页面后，不会感觉任务凭空消失。

### 5.3 页面结构

```markdown
- 启动恢复区
  - “检测到未完成任务”
  - “继续查询结果”按钮
- 历史任务列表
  - 最近一次任务
  - 状态标签
  - 重新打开
```

### 5.4 核心代码：本地恢复

```ts
const CACHE_KEY = 'image_gen_task';

function saveTaskCache(task: TaskState) {
  localStorage.setItem(CACHE_KEY, JSON.stringify(task));
}

function loadTaskCache(): TaskState | null {
  const raw = localStorage.getItem(CACHE_KEY);
  return raw ? JSON.parse(raw) : null;
}

async function restoreTask() {
  const task = loadTaskCache();
  if (!task) return;

  if (task.status === 'success') {
    setState(task);
    return;
  }

  if (task.taskId && (task.status === 'queued' || task.status === 'processing' || task.status === 'timeout')) {
    setState(task);
    await pollTask(task.taskId);
    return;
  }

  if (task.status === 'failed') {
    setState(task);
  }
}
```

### 5.5 交互细节

- 页面加载时可以弹出轻提示：“检测到上次未完成任务，是否继续？”；
- 若任务已经超时，不要直接报废，给用户“继续查询”入口；
- 历史记录建议保留最近 5 条，便于用户回看、重新编辑或再次生成；
- 恢复任务时，不要重新创建一个新任务，而是基于原 `taskId` 继续查询。

### 5.6 历史记录与本地缓存怎么配合

如果你还想把“历史记录”做得更完整，可以把每次任务都存成一条轻量记录：提示词摘要、尺寸、状态、缩略图、时间。这样用户一刷新页面，不仅能恢复当前任务，还能从历史列表里找到之前生成过的结果。

```ts
interface TaskHistoryItem {
  taskId: string;
  prompt: string;
  size: string;
  status: TaskStatus;
  thumbnail?: string;
  createdAt: number;
}
```

历史记录不必一开始就做成复杂数据库，本地缓存先够用。等产品成熟后，再同步到服务端。

## 六、基础版权与内容安全提醒：把风险提示放进等待和结果流程

### 这一节要回答的问题
**怎么在不打断体验的前提下，提醒用户注意版权与内容安全？**

### 6.1 为什么要单独处理这一层

图像生成功能很容易被用户拿来做封面、海报、头像、营销图，所以前端页面最好在等待页、结果页、历史记录页都放一个轻量提醒，而不是只在协议里写一段没人看的文字。

这不是“增加负担”，而是让产品更稳定、更容易上线。

### 6.2 页面结构

```markdown
- 底部提示条
  - 内容合规提醒
  - 版权声明
  - 使用范围说明
- 结果页操作区
  - 仅供个人/项目测试
  - 下载前确认素材来源
```

### 6.3 可复制的提示文案

你可以直接放类似文案：

> 请确保你上传的图片和输入的提示词不侵犯他人版权、肖像权或商标权。  
> 本功能生成结果仅用于你有权使用的场景，涉及商用前请再次确认授权与合规要求。

如果产品接入了图片上传，也要提醒用户：

- 不要上传无授权的人像、品牌图、受保护作品；
- 不要把敏感内容当作参考图；
- 生成结果如需公开发布，建议先做人工审核。

### 6.4 交互细节

- 提示条用折叠式更好，不要占太多空间；
- 在“下载”“保存到历史”“再次生成”按钮附近放一个小型安全提示；
- 如果接口返回内容不合规，页面要明确告知原因，并给出修改建议，而不是只显示失败。

## 结尾小结：把“等待、恢复、重试”做成闭环

这一章的核心不是轮询本身，而是把 AI 图像生成的异步过程做成一个**用户可理解、可中断、可重试、可恢复**的完整流程。

你至少要记住六件事：

1. 先定义状态机，再写界面；
2. 轮询必须有限制、有停止条件、有清理；
3. 等待页要有清晰文案、取消入口和加载态；
4. 失败后要保留原参数，并把重试和消耗提示说清楚；
5. 刷新后要能通过 `taskId` 继续查询结果；
6. 版权与内容安全提醒要放进真实流程里，而不是只写在说明页。

如果这一层做稳了，后面的结果展示、下载、历史记录、本地缓存就会顺畅很多。下一步建议你把本章的状态机直接接到生成页里，再把任务记录写入本地缓存，这样你的 AI 图像生成前端流程就已经真正跑起来了。

## 6.1 结果区页面结构：主图区、缩略图区、操作区和弹窗区

先别急着写样式，先把结果区拆成固定区域。一个可用的结果页，至少要有四块：

- **主图区**：展示当前选中的大图
- **缩略图区**：展示同一批结果，方便切换
- **操作区**：下载、收藏、再次编辑、重试
- **弹窗区**：用于放大预览、切换上一张下一张

### 推荐页面结构
```html
<div class="result-panel">
  <div class="result-main">
    <div class="result-status-badge">生成成功</div>
    <img src="..." alt="生成结果主图" />
  </div>

  <div class="result-actions">
    <button>下载</button>
    <button>收藏</button>
    <button>再次编辑</button>
  </div>

  <div class="thumb-list">
    <!-- 缩略图列表 -->
  </div>

  <div class="preview-mask" v-if="previewOpen">
    <div class="preview-dialog">
      <!-- 预览弹窗 -->
    </div>
  </div>
</div>
```

### 这几块的关系
- 主图区负责“当前看哪张”
- 缩略图区负责“同一批图怎么切换”
- 操作区负责“用户下一步能做什么”
- 弹窗区负责“看细节、做比较、快速操作”

如果把按钮都堆在图上，移动端会很挤；如果把操作藏到详情页里，用户又会反复跳转。更稳妥的方式，是把结果区做成一个**可直接操作的工作台**。

### 适合的展示方式
- **主图 + 缩略图列表**：适合单次生成、强调对比
- **卡片网格**：适合历史记录和批量管理
- **瀑布流**：适合作品墙浏览，但不适合高频编辑

其中，本章最推荐“主图 + 缩略图列表”，因为它最符合“生成后立刻看、立刻换、立刻操作”的流程。

## 6.2 缩略图布局实现：统一比例、懒加载、占位图和骨架屏

缩略图不是装饰，它是结果画廊的核心控制面板。用户要靠它快速扫图、切图、找图，所以这里必须稳定。

### 1）统一比例，避免布局跳动
缩略图建议固定比例，比如 1:1 或 4:3，这样不会因为图片宽高不同导致列表高低不齐。

```css
.thumb-item {
  aspect-ratio: 1 / 1;
  overflow: hidden;
  border-radius: 12px;
  background: #f3f4f6;
  position: relative;
}
.thumb-item img {
  width: 100%;
  height: 100%;
  object-fit: cover;
}
```

统一比例后，卡片更整齐，也方便做移动端横向滚动。

### 2）懒加载，减少首屏压力
历史记录一多，图片数量会变大。不要一次性加载全部原图，缩略图可以懒加载，原图留到预览弹窗再加载。

```html
<img src="thumb.jpg" loading="lazy" alt="缩略图" />
```

如果后端返回任务列表，最好先返回缩略图地址和状态，不要直接把原图塞进列表页。

### 3）占位图与骨架屏，避免空白等待
生成过程中，列表里不能是空白块，要让用户知道系统正在工作。建议分两层：

- **骨架屏**：表示正在生成或正在加载
- **占位图**：表示图片地址已返回，但资源还在加载

```html
<div class="thumb-skeleton"></div>
```

```css
.thumb-skeleton {
  aspect-ratio: 1 / 1;
  border-radius: 12px;
  background: linear-gradient(90deg, #eee, #f5f5f5, #eee);
  animation: shimmer 1.2s infinite;
}
```

骨架屏适合“任务还没完成”，占位图适合“图片快到了”。两者配合，界面会更稳。

### 4）失败兜底图要保留入口
有些缩略图可能加载失败，不能只显示破图图标。建议直接替换成失败兜底图，并保留重试按钮。

```html
<div class="thumb-item thumb-failed">
  <span>加载失败</span>
  <button>重试</button>
</div>
```

### 5）状态直接写在缩略图上
缩略图上最好直接显示状态角标，用户一眼就知道当前是哪种结果：

- 生成中
- 成功
- 失败
- 可下载
- 可收藏

当前选中的图片再加一个高亮边框，方便用户确认正在操作哪一张。

## 6.3 结果状态展示：生成中、成功、失败、可下载、可收藏

这一部分是结果页的“反馈系统”。用户看结果，不只是看图，也是在看系统是否可靠。

### 状态模型建议
```js
{
  id: 'img_001',
  status: 'generating', // generating | success | failed
  url: '',
  thumbUrl: '',
  prompt: '...',
  canDownload: false,
  canFavorite: false,
  retryCount: 0
}
```

### 1）生成中
生成中时，主图和缩略图区域都要显示加载态。建议明确写出任务状态，比如：

- 正在生成第 2/4 张
- 任务已提交，等待返回
- 预计还需几秒到几十秒

如果后端是异步任务，前端要把“提交成功”和“图片完成”拆成两个状态：先显示任务已进入队列，再轮询或等待结果返回。这样用户不会以为点击后没有反应。

### 2）成功
成功后，结果区要立刻出现：

- 主图
- 缩略图
- 下载按钮
- 收藏按钮
- 再次编辑按钮

如果一次生成多张图，建议默认选中第一张或模型推荐图，减少第一次进入时的选择压力。

### 3）失败
失败态必须可操作，不能只显示“失败了”。

建议同时提供：

- 简短错误说明
- 重试按钮
- 失败原因提示：网络异常、任务超时、内容不合规、参数错误

如果是网络异常，可以保留上一次任务参数，点击重试直接重新提交。  
如果是内容被拦截，就不要机械重试，而要提示用户修改提示词或上传的参考图。

### 4）可下载、可收藏
这两个按钮职责不同：

- **下载**：导出当前图片
- **收藏**：加入历史或喜欢列表
- **再次编辑**：带着原提示词和参数回到输入区

按钮状态也要同步变化。比如收藏成功后，按钮文案可以切成“已收藏”，避免重复点击。

## 6.4 结果预览弹窗：放大查看、上一张下一张、键盘操作与遮罩关闭

点击缩略图后，不建议直接跳转页面。更好的方式是打开预览弹窗，在当前上下文里继续看图和操作。

### 页面结构
```html
<div class="preview-mask" v-if="previewOpen">
  <div class="preview-dialog">
    <button class="close-btn">×</button>
    <button class="prev-btn">‹</button>
    <img :src="currentImage.url" alt="预览图" />
    <button class="next-btn">›</button>

    <div class="preview-actions">
      <button>下载</button>
      <button>收藏</button>
      <button>再次编辑</button>
    </div>
  </div>
</div>
```

### 1）放大查看细节
预览弹窗的首要任务是看清细节。原图应在弹窗里单独加载，不要直接复用列表缩略图，否则会模糊。

### 2）切换上一张、下一张
如果一次生成多张图，预览里一定要支持左右切换。这样用户可以快速比较构图、颜色和细节，不用反复关闭再打开。

```js
function prevImage() {
  currentIndex.value = (currentIndex.value - 1 + images.length) % images.length;
}

function nextImage() {
  currentIndex.value = (currentIndex.value + 1) % images.length;
}
```

### 3）键盘操作
桌面端建议支持：

- `Esc`：关闭弹窗
- `←`：上一张
- `→`：下一张

```js
window.addEventListener('keydown', (e) => {
  if (!previewOpen.value) return;
  if (e.key === 'Escape') closePreview();
  if (e.key === 'ArrowLeft') prevImage();
  if (e.key === 'ArrowRight') nextImage();
});
```

### 4）点击遮罩关闭
弹窗外层遮罩点击后应直接关闭，返回原来的结果画廊。  
但点击图片内容本身不能关闭，避免误触。

### 5）操作区保持简洁
预览弹窗里的操作区建议只保留高频动作：

- 下载
- 收藏
- 再次编辑

按钮太多会分散注意力，影响看图和比较。

## 6.5 移动端适配：单列展示、底部操作栏、弹窗全屏化

移动端不是桌面端的缩小版，而是要重新安排信息层级。

### 1）单列展示
手机屏幕窄，结果区建议改成单列布局。缩略图可以横向滚动，也可以做成单列卡片流；如果结果很多，单列更容易连续浏览。

### 2）底部操作栏
在移动端，最方便的是把核心动作放到底部，方便拇指点击。

```html
<div class="mobile-actions">
  <button>下载</button>
  <button>收藏</button>
  <button>编辑</button>
</div>
```

### 3）弹窗全屏化
移动端弹窗不要做成小居中框，最好直接全屏展示，减少遮挡。

```css
@media (max-width: 768px) {
  .preview-dialog {
    width: 100vw;
    height: 100vh;
    border-radius: 0;
  }

  .thumb-list {
    display: flex;
    overflow-x: auto;
    gap: 12px;
  }

  .result-actions {
    position: sticky;
    bottom: 0;
    background: #fff;
  }
}
```

### 4）触摸体验
- 支持左右滑动切换图片
- 按钮间距足够大，避免误触
- 图片上下留出安全边距
- 横屏和竖屏切换后布局不崩

### 常见误区
- 弹窗仍然像桌面端那样窄小
- 操作按钮挤成一团
- 缩略图太小，看不清当前选中项
- 没有考虑历史记录页的移动端浏览体验

## 6.6 与失败重试、消耗提示、历史记录和本地缓存的联动

结果区不是孤立的，它还要跟任务状态、余额消耗和历史记录连起来。

### 1）失败重试联动
如果某张图失败了，缩略图上要直接给出重试入口。重试后保留原提示词、尺寸和上传参考图，避免用户重新填一遍。

### 2）消耗提示联动
如果一次生成会消耗积分或次数，结果出来时最好同步提示：

- 已消耗 1 次生成额度
- 当前剩余 3 次
- 重试将再次扣减额度

这类提示放在结果区顶部或操作按钮附近最清楚，避免用户在不知情的情况下连续点重试。

### 3）历史记录联动
生成成功后，自动把结果写入历史记录，并在本地缓存一份最近查看项。这样用户关闭页面后，重新打开还能继续看到上次结果，不会丢失浏览上下文。

### 4）本地缓存联动
本地缓存不一定存完整原图，但至少要保存这些信息：

- 最近一次查看的图片 id
- 当前选中的缩略图索引
- 预览弹窗是否打开
- 最近一次的任务状态

这样用户刷新页面后，可以快速恢复到上次查看的位置，尤其适合移动端和弱网场景。

## 本章小结：让结果区既能看，也能操作

画廊式结果展示的目标，不是把图片堆出来，而是让用户能：

- 快速看见结果
- 在多张图之间比较
- 通过结果预览弹窗细看
- 对图片执行下载、收藏、再次编辑
- 在移动端也能顺畅操作
- 和失败重试、消耗提示、历史记录、本地缓存形成闭环

如果你准备把这一章落到产品里，建议按这个顺序做：

1. 先实现主图和缩略图列表  
2. 再补加载骨架、占位图、失败兜底图和状态角标  
3. 接着做预览弹窗、上一张下一张、键盘切换和遮罩关闭  
4. 最后做移动端适配、底部操作栏，以及与历史记录和本地缓存的联动  

**这一节你要做出的页面**，不是一个静态图片墙，而是一个可以继续操作的结果工作台：用户能看、能切、能放大、能下载、能收藏、能重试，也能在手机上继续浏览。  
当这些能力接上后，你的前端就不只是“能生成图”，而是已经具备了一个完整的结果管理界面。下一章，我们就把结果继续往前串，补上下载、收藏和历史记录的完整流程。

## 7.1 下载功能实现：图片下载、文件命名、跨域与权限注意事项

### 这一步解决什么问题？

用户生成完图片后，最直接的动作就是下载。下载做不好，用户就只能停留在网页里看图，体验会很弱。  
在实际产品里，下载不是一个按钮，而是一整套流程：获取资源、处理跨域、生成文件名、提示进度、处理失败。

### 页面结构

结果卡片顶部保留图片预览，底部放一排操作按钮：

- 下载原图
- 收藏
- 再次编辑
- 分享

如果是多张结果，建议每张卡片都独立带下载按钮，避免用户找不到对应作品。  
在移动端，可以把按钮收进底部操作栏，保证单手操作方便。若用户点击缩略图，则打开**结果预览弹窗**，在弹窗内完成下载和查看。

### 核心代码

```js
async function downloadImage(url, name) {
  try {
    const res = await fetch(url, { mode: 'cors' });
    if (!res.ok) throw new Error('图片获取失败');

    const blob = await res.blob();
    const objectUrl = URL.createObjectURL(blob);

    const a = document.createElement('a');
    a.href = objectUrl;
    a.download = `${name || 'ai-image'}.png`;
    document.body.appendChild(a);
    a.click();
    a.remove();

    URL.revokeObjectURL(objectUrl);
  } catch (err) {
    throw err;
  }
}
```

### 交互细节

1. 点击下载后按钮立刻进入**加载态**，防止连续点击。  
2. 文件名建议包含提示词关键词、时间戳、尺寸，例如：`sunset-poster-1024x1024-20250101.png`。  
3. 如果下载失败，提示“图片下载失败，请重试或检查图片地址是否允许跨域”。  
4. 在结果预览弹窗中点击下载时，最好先确认当前看的就是哪一张，避免多图场景下下错。  
5. 如果是对象存储地址，下载前最好确认服务端已经配置好 CORS，否则浏览器可能无法拉取 blob。  
6. 在移动端，如果浏览器对直接下载支持有限，可以同时提供“长按保存”的备用提示。  

### 常见误区

- **直接用 `<img>` 地址下载**：有些跨域图片不能直接触发下载，最好先 `fetch -> blob`。  
- **不做文件名规范**：用户最后会得到一堆 `image.png`，管理困难。  
- **忽略权限与跨域**：如果图片来自对象存储或第三方域名，要确认 CORS 配置正确。  
- **没有失败反馈**：用户点了下载却没反应，会误以为页面卡住了。  

### 检查清单

- [ ] 下载按钮是否有加载态  
- [ ] 是否支持跨域图片下载  
- [ ] 是否生成可读文件名  
- [ ] 是否能在移动端正常触发下载  
- [ ] 是否在下载失败时给出明确提示

## 7.2 收藏能力设计：收藏状态、收藏列表、取消收藏与本地持久化

### 这一步解决什么问题？

收藏不是装饰功能，而是帮助用户把高质量结果沉淀下来，方便复用、二次编辑和对比筛选。  
对于前端产品来说，收藏最重要的是轻量和即时：用户点一下就能保存，不必先注册登录，也能先把结果留住。

### 页面结构

建议在结果页增加两个区域：

- **当前结果操作区**：收藏 / 取消收藏按钮  
- **收藏列表区**：缩略图网格，按时间倒序展示  

缩略图布局适合高密度浏览，用户可以快速判断哪张图值得保留。  
列表里除了图片，还建议显示简短提示词摘要和尺寸，方便回忆上下文。收藏列表和历史记录可以共用同一套卡片组件，只是标记不同。

### 核心代码

```js
const STORAGE_KEY = 'ai_image_favorites';

function loadFavorites() {
  return JSON.parse(localStorage.getItem(STORAGE_KEY) || '[]');
}

function saveFavorites(list) {
  localStorage.setItem(STORAGE_KEY, JSON.stringify(list));
}

function toggleFavorite(item) {
  const list = loadFavorites();
  const exists = list.find(x => x.id === item.id);

  const next = exists
    ? list.filter(x => x.id !== item.id)
    : [{ ...item, favoritedAt: Date.now() }, ...list];

  saveFavorites(next);
  return next;
}
```

### 交互细节

1. 收藏按钮要有明显状态：空心星标 / 实心星标。  
2. 收藏成功后提示“已收藏”，取消收藏提示“已取消收藏”。  
3. 收藏列表建议支持删除、查看大图、再次编辑。  
4. 本地持久化优先使用 `localStorage`，新手最容易落地；后期要多端同步，再接后端接口。  
5. 列表为空时，要展示引导文案，比如“收藏后会出现在这里，方便你随时回看”。  
6. 收藏后最好同步到历史记录中的标记位，用户从历史页也能一眼识别哪些作品已经保留。  
7. 用户刷新页面后，收藏状态应从本地缓存恢复，避免按钮状态和真实数据不一致。  

### 常见误区

- **只改 UI 不存储**：刷新页面后收藏丢失。  
- **收藏与当前结果混在一起**：建议分开管理，避免逻辑混乱。  
- **列表没有空状态**：第一次进入收藏页要提示“暂无收藏内容”。  
- **不考虑历史记录**：收藏最好能和历史生成记录联动，方便用户从记录里找回作品。  

---

## 7.3 再次编辑流程：从结果回填提示词、尺寸与参考图，快速二次生成

### 这一步解决什么问题？

很多时候用户不会一次生成满意结果，而是需要基于上一张图继续调整。所以再次编辑的关键不是重新输入，而是**把已有结果变成新的生成起点**。  
如果你的产品支持图片上传，那么再次编辑还应该把参考图一起带回来，让用户少走一步。

### 页面结构

在图片预览弹窗或结果卡片中增加“再次编辑”按钮，点击后进入编辑面板，并自动回填：

- 提示词
- 尺寸
- 风格参数
- 参考图（如果产品支持图片上传）

如果当前结果来自历史记录，也可以直接进入生成页并定位到对应表单项，让用户快速修改后再次提交。  
这里建议把“再次编辑”放在结果预览弹窗的主操作区，用户放大查看后最容易决定要怎么改。

### 核心代码

```js
function editAgain(result) {
  setPrompt(result.prompt || '');
  setSize(result.size || '1024x1024');
  setReferenceImage(result.referenceImage || null);
  setActiveTab('create');
}
```

### 交互细节

1. 点击“再次编辑”后，直接跳回生成表单，不要让用户自己复制粘贴。  
2. 如果原结果带有图片上传参考图，回填参考图缩略图。  
3. 保留用户上次的局部修改，让再次生成更像“迭代”，而不是“重来”。  
4. 可以在按钮旁边加一句小提示，例如“基于当前结果继续优化”。  
5. 如果结果来自历史记录，建议同时恢复当时的尺寸、风格和备注信息。  
6. 二次生成前，明确说明哪些参数会保留，哪些参数会沿用当前表单默认值，避免用户误解。  

### 典型流程

- 用户在结果页看到一张满意但还不够理想的图  
- 点击“再次编辑”  
- 系统自动带入原提示词和尺寸  
- 用户补充“更明亮、更简洁、背景留白”  
- 重新提交异步任务生成新图  

### 常见误区

- **只回填提示词，不回填尺寸**：会导致用户以为自己在微调，其实输出规格变了。  
- **参考图丢失**：如果有图片上传输入，二次生成最好保留原参考图入口。  
- **重置过度**：不要把所有字段清空，否则用户会觉得“再次编辑”没意义。  
- **没有结果预览弹窗入口**：用户常常是在放大查看后才决定是否再次编辑，所以弹窗里也要保留这个操作。

## 7.4 分享入口设计：复制链接、复制图片信息、导出海报预览

### 这一步解决什么问题？

分享让作品从“个人结果”变成“传播资产”。在前端产品里，分享不仅是转发，还包括复制信息、生成预览图、导出适合社交传播的海报。  
如果没有公开详情页，也可以先做“复制文案 + 参数 + 图片地址”的轻量分享，实用性已经很强。若篇幅或产品目标有限，分享可以作为下载、收藏、再次编辑之外的可选扩展。

### 页面结构

分享入口可以放在弹窗内，提供三种能力：

- 复制分享链接
- 复制图片信息
- 导出海报预览

### 核心代码

```js
async function copyText(text) {
  await navigator.clipboard.writeText(text);
  alert('已复制');
}

function buildShareText(item) {
  return `我生成了一张AI图片：${item.prompt}\n尺寸：${item.size}\n链接：${location.origin}/share/${item.id}`;
}
```

### 交互细节

1. “复制图片信息”建议包含提示词、尺寸、生成时间，方便用户转述。  
2. 如果产品有公开页，可生成可访问的分享链接；如果没有详情页，也可以只复制信息文本。  
3. 海报预览适合做成固定比例画布，展示图片、标题、参数和品牌信息，便于导出。  
4. 分享按钮最好放在结果预览弹窗里，用户查看大图时顺手就能操作，不需要回到列表。  
5. 分享前可以补一条轻量提醒：若图片包含他人肖像、品牌元素或敏感内容，不建议直接外发。  

### 结果预览弹窗

分享、下载、再次编辑都最好在**结果预览弹窗**里完成。弹窗中可以放大查看图片，右侧放操作按钮，底部显示基础信息，用户无需离开当前页面。  
在手机上，弹窗建议改成全屏抽屉式，底部保留固定操作栏，避免按钮被系统栏遮挡。  
弹窗里还应明确几个操作说明：可以切换上一张/下一张、可以放大查看细节、可以下载当前图，也可以直接关闭返回列表。

### 常见误区

- **分享没有预览图**：链接发出去后不够直观。  
- **只做“复制链接”**：很多场景下用户更需要“复制文案 + 参数”。  
- **导出尺寸不统一**：海报预览最好固定模板，避免前端适配混乱。  
- **忽略图片上传信息**：如果作品由参考图生成，分享时可以保留“参考图来源”字段，便于复盘。

## 7.5 失败重试、消耗提示与历史联动

### 这一步解决什么问题？

结果页不是只处理成功状态。只要涉及下载、收藏、分享、再次编辑，就一定会遇到失败、超时或重复提交。  
此外，如果前端产品接了计费或额度控制，用户在结果页也需要知道“这次操作是否消耗次数”“失败后要不要重试”，否则很容易产生误解。

### 页面结构

在结果卡片和历史记录中增加三类信息：

- 操作状态：成功、失败、处理中  
- 消耗提示：本次生成是否消耗次数，重试是否会再次计费  
- 历史标记：已收藏、已分享、已下载  

### 核心代码

```js
async function retryAction(fn) {
  try {
    return await fn();
  } catch (err) {
    throw new Error('操作失败，请稍后重试');
  }
}
```

### 交互细节

1. 如果下载失败，明确告诉用户“可以重试，原图不会丢失”。  
2. 如果再次编辑会触发新的生成任务，要提示“将重新消耗一次生成次数”。  
3. 收藏、分享这类本地操作通常不应扣次数，但页面文案要讲清楚。  
4. 历史记录里建议显示“最近一次操作结果”，例如已下载、已收藏，方便用户快速回看。  
5. 当用户重复点击按钮时，直接拦截即可，不要同时发起多个重复请求。  
6. 成功或失败都要给出短反馈，最好在按钮旁边或弹窗底部就地提示，不要让用户找半天。  

### 常见误区

- **失败后只提示“错误”**：用户不知道是网络、权限还是资源问题。  
- **消耗规则不透明**：如果重试会再次扣次数，必须提前说明。  
- **历史记录不联动**：结果页操作成功后，历史页没有同步更新，用户会觉得功能失效。

## 7.6 结果页里的版权与使用提醒

### 这一步解决什么问题？

这一节不是把产品写成法律教程，而是在结果页里补一层最基础、最实用的提醒：用户生成的图片可能包含敏感信息、品牌元素、他人肖像或受版权保护的素材，分享和下载前要先确认用途。  
这个提示不需要长，但要稳定出现，尤其适合放在分享和导出海报附近。

### 页面结构

在分享按钮下方或弹窗底部增加一行小字提示：

- 请确保生成内容符合平台规范与使用场景
- 涉及他人肖像、品牌标识或受版权保护素材时，请先确认授权
- 若用于公开发布，建议再次检查内容安全与文案合规

### 交互细节

1. 提示文案保持简短，不要打断主要操作。  
2. 对于导出海报或复制分享链接，可以在点击前短暂展示确认框。  
3. 如果产品面向企业内部使用，提醒文案可以更偏向“内部审核后再外发”。  
4. 当用户从历史记录批量重新导出时，同样要保留这类提醒，避免只在首次生成时出现。

## 本章小结：让结果“可用”，而不是“可看”

一个成熟的 AI 图片生成页面，不只是把图生成出来，更要让用户能**下载、收藏、再次编辑、分享、反复使用**。  
你可以把本章落地为一个结果操作闭环：

1. 结果卡片展示缩略图和基础信息  
2. 支持下载原图，处理跨域、命名和失败提示  
3. 收藏结果并用本地缓存保存，同时联动历史记录  
4. 一键回填提示词、尺寸和参考图再次编辑  
5. 提供复制链接、复制信息、导出海报预览作为可选扩展  
6. 全程带加载态、失败提示、消耗提示和防重复点击  
7. 在移动端通过结果预览弹窗或底部抽屉完成主要操作  
8. 在分享和导出前加入基础版权与内容安全提醒  

如果你已经有了生成页，下一步就按本章把结果操作区补齐。**真正能用的前端 AI 产品，往往不是“生成得多”，而是“结果处理得顺”。**

## 一、历史记录的数据结构：先把“要记什么”定义清楚

历史记录不是只存一张图，而是一条完整的生成事件。你记录的不是“结果”，而是**从输入到输出的全过程**，这样用户才能回退、复用和追踪。

建议至少包含这些字段：

- `id`：唯一标识
- `createdAt`：生成时间
- `prompt`：提示词
- `size`：尺寸，例如 `1024x1024`
- `status`：`pending | success | failed`
- `resultUrl`：结果地址
- `thumbUrl`：缩略图地址
- `isFavorite`：是否收藏
- `sourceImage`：上传图片信息，可选
- `errorMsg`：失败原因，可选

如果页面还支持风格、种子值、模型选择，也可以继续扩展。原则很简单：**凡是会影响结果、值得复用的参数，都应该进入记录。**

### 页面结构

- 左侧：历史记录列表
- 右侧：当前生成区
- 列表项：缩略图、提示词、时间、尺寸、状态、收藏按钮
- 操作区：再次生成、删除、清空、筛选
- 顶部提示条：显示“已保存到本地”或“有 1 条待恢复任务”

### 核心代码

```ts
type GenRecord = {
  id: string
  createdAt: number
  prompt: string
  size: string
  status: 'pending' | 'success' | 'failed'
  resultUrl?: string
  thumbUrl?: string
  isFavorite: boolean
  sourceImage?: { name: string; url: string }
  errorMsg?: string
}
```

### 交互细节

1. `pending` 记录先入库，避免刷新后丢失任务。
2. 成功后补写 `resultUrl` 和 `thumbUrl`。
3. 失败后保留错误信息，方便重试。
4. 收藏状态单独更新，不影响主记录。
5. 列表默认按时间倒序，便于快速找到最近结果。

## 二、本地缓存方案：localStorage 还是 IndexedDB？

关键不是哪个更高级，而是**你要缓存什么、数据多大、保留多久**。很多新手会把所有内容塞进 `localStorage`，结果图片一多就超限，页面还会卡。

### 1. localStorage 适合什么

适合存：

- 草稿提示词
- 当前尺寸选择
- 最近一次生成的轻量记录
- 收藏标记、筛选条件
- 上传图片的文件名、临时预览地址

特点是简单、同步、容易上手，但容量小，不适合存大量图片数据。轻量工具或 MVP 场景下，`localStorage` 足够。

### 2. IndexedDB 适合什么

适合存：

- 较多历史记录
- 缩略图 blob
- 上传图片的本地副本
- 需要分页和查询的数据

它容量更大，适合结构化存储，更接近真实产品。

### 3. 什么时候存、存什么、何时清理

可以按这条规则做：

- **输入中实时变化的内容**：延迟保存到 `localStorage`，如提示词、尺寸、上传图片名
- **生成完成的正式记录**：写入历史记录区；轻量场景用 `localStorage`，图片较多时用 `IndexedDB`
- **临时任务状态**：`pending` 任务单独保存，方便刷新后继续轮询
- **过期数据**：到期自动清理，避免无限增长

### 页面结构

- 设置面板增加“本地保存”开关
- 历史记录区增加“缓存状态说明”
- 提供“清理本地数据”入口
- 右上角显示本地缓存条数与占用提示

### 核心代码

```ts
const STORAGE_KEY = 'ai-image-drafts'

function saveDraft(draft: any) {
  localStorage.setItem(STORAGE_KEY, JSON.stringify(draft))
}

function loadDraft() {
  const raw = localStorage.getItem(STORAGE_KEY)
  return raw ? JSON.parse(raw) : null
}
```

### 交互细节

- 输入框失焦时自动保存草稿。
- 尺寸、风格、上传图变动后自动同步缓存。
- 页面加载时优先恢复缓存，再请求历史记录。
- 缓存失败不阻塞生成流程，只提示“本地保存失败，当前内容不会自动恢复”。

## 三、刷新恢复与草稿保存：怎么让用户“回来还能继续”？

草稿恢复的目标不是永久保存所有内容，而是让用户在中断后能快速接上。常见中断包括切换标签页、误刷新、临时离开、网络波动、设备休眠。

建议至少恢复四类内容：

1. **输入内容**：提示词、负面提示词、尺寸选择  
2. **上传记录**：已上传图片的文件名、预览地址或本地缓存标识  
3. **最后一次结果**：最近生成成功的一张图  
4. **待处理任务**：仍在 `pending` 的异步任务状态  

### 页面结构

- 顶部提示条：`已恢复上次草稿`
- 表单区：自动回填
- 上传区：显示已上传图片缩略图与文件名
- 结果区：显示最后一次成功结果
- 操作按钮：`继续编辑`、`重新生成`、`清除草稿`

### 核心代码

```ts
useEffect(() => {
  const draft = loadDraft()
  if (!draft) return
  setPrompt(draft.prompt || '')
  setSize(draft.size || '1024x1024')
  setUploadedImage(draft.uploadedImage || null)
  setLastResult(draft.lastResult || null)
}, [])

useEffect(() => {
  saveDraft({
    prompt,
    size,
    uploadedImage,
    lastResult
  })
}, [prompt, size, uploadedImage, lastResult])
```

### 交互细节

- 首次进入页面恢复成功时，只做轻提示，不打断操作。
- 若最后一次结果仍有效，允许直接下载或再次编辑。
- 若上传文件无法跨刷新保留，至少保留文件名与预览 URL；重新上传时提示用户。
- 用户手动清空输入框时，要同步清除草稿，避免下次又被自动恢复。
- 对于 `pending` 任务，恢复后要展示“继续等待”或“重新轮询”按钮，避免用户误以为任务丢了。

**常见误区**：把草稿和历史记录混在一起。草稿是“正在编辑的状态”，历史记录是“已经发生过的生成事件”，职责不同。

## 四、历史记录区交互：筛选、删除、清空、再次生成

历史记录不是静态列表，而是一个可操作的工作台。用户来这里不是只看结果，而是继续工作，所以交互要围绕效率设计。

### 1. 筛选

建议支持：

- 全部
- 成功
- 失败
- 收藏
- 最近 7 天

筛选的目的不是好看，而是帮助用户快速找到某一版结果。尤其是封面生成、海报生成这类场景，用户往往会连续试很多次，没有筛选就很难翻找。

### 2. 删除与清空

- 删除单条：用于修正错误记录
- 清空全部：用于重新开始或释放空间
- 清空前弹窗确认，避免误删
- 删除本地缓存后，同时清掉对应缩略图和草稿，避免残留脏数据

### 3. 再次生成

再次生成按钮应自动带回：

- 提示词
- 尺寸
- 上传图
- 风格参数

如果原记录是失败状态，也可以直接用“重试”替代“再次生成”，把用户重新带回生成流程。

### 页面结构

- 顶部筛选条
- 中间列表/网格
- 每条记录右侧按钮：`再来一次`、`收藏`、`删除`
- 空状态页：提示“暂无记录，去生成第一张图”
- 失败态记录卡片：增加 `重试` 与错误说明

### 核心代码

```ts
function handleRegenerate(record: GenRecord) {
  setPrompt(record.prompt)
  setSize(record.size)
  if (record.sourceImage) setUploadedImage(record.sourceImage)
  setActiveTab('generator')
}

function handleRetry(record: GenRecord) {
  handleRegenerate(record)
  startGenerate()
}
```

### 交互细节

- 点击缩略图打开结果预览弹窗。
- 弹窗里支持下载、收藏、再次编辑。
- 失败记录优先显示重试入口，而不是只显示报错。
- 删除后列表即时更新，不要等用户刷新页面。
- 再次生成时，若原记录包含上传图片，应提示用户确认是否重新使用该图片。

---

## 五、加载态、异步任务与历史联动：让用户知道发生了什么

图像生成往往不是点击后立刻出图，而是一个**异步任务**：先提交，再轮询，最后拿到结果。这个过程如果和历史记录联动不好，用户就会觉得页面“卡住了”或者“结果丢了”。

### 页面结构

- 表单提交后显示加载态
- 历史记录里同步插入一条 `pending` 记录
- 任务轮询中显示“正在生成”与进度文案
- 结果返回后自动更新缩略图和状态
- 失败时保留错误原因和重试入口

### 核心代码

```ts
function updateRecordStatus(id: string, patch: Partial<GenRecord>) {
  setRecords(prev =>
    prev.map(item => (item.id === id ? { ...item, ...patch } : item))
  )
}
```

### 交互细节

- 提交生成前先提示可能消耗的额度或次数。
- 任务失败后保留原参数，用户一键重试即可。
- 重试成功后自动回写历史记录，避免出现两条孤立记录。
- 如果后端返回“超出次数”，应明确告诉用户剩余额度或下一步处理方式。
- 加载态期间禁止重复提交，但允许用户返回历史区查看其他记录。
- 刷新后如果还有 `pending` 记录，页面应自动重新轮询，而不是当成普通失败项。

这样处理后，历史记录不只是存档，还成了“可继续操作的工作台”。

---

## 六、隐私、容量与清理：别让缓存越存越大

本地缓存的好处是快，风险是无限增长。尤其当你保存图片、缩略图、上传记录时，容量和隐私都要管住。真正可用的产品必须有边界。

### 1. 缓存上限

建议设置：

- 最多保留最近 20～50 条记录
- 收藏记录可单独保留更久
- 超出上限时自动删除最旧的非收藏项

### 2. 过期策略

- 草稿：24 小时或 7 天过期
- 临时上传图：生成成功后可清理
- 失败记录：保留更短时间，便于排查
- `pending` 任务：若超过一定时间未完成，可提示用户重新发起

### 3. 用户可清理

提供三个入口更清晰：

- 清理草稿
- 清理历史记录
- 清理全部本地数据

### 4. 隐私提醒

如果用户上传了个人照片、品牌素材或商业海报底图，要明确提示：

- 本地缓存仅用于当前设备
- 不要在共享设备上保存敏感图片
- 清理浏览器数据可能导致记录丢失

### 页面结构

- 设置页增加“缓存管理”
- 显示当前缓存条数、占用提示
- 一键清理按钮
- 清理前二次确认
- 清理结果 toast 提示

### 核心代码

```ts
function trimRecords(records: GenRecord[]) {
  const favorites = records.filter(r => r.isFavorite)
  const normal = records.filter(r => !r.isFavorite)
  const keepNormal = normal.slice(0, 30)
  return [...favorites, ...keepNormal].sort((a, b) => b.createdAt - a.createdAt)
}
```

### 交互细节

- 缓存接近上限时，显示轻量提醒。
- 用户点击“清理”后，立即刷新列表。
- 收藏项和普通项分开管理，避免误删。
- 移动端适当压缩列表信息，只保留关键字段，减少拥挤。

## 七、移动端适配与结果预览弹窗：让历史记录真能用

很多记录页在桌面端看起来正常，一到手机上就会出问题：列表太挤、按钮太小、预览图超出屏幕、下载入口不明显。所以历史记录不仅要能存，还要能在移动端顺手使用。

### 页面结构

- 移动端改为单列卡片布局
- 卡片上方放缩略图，下方放提示词与状态
- 底部固定操作栏：`下载`、`收藏`、`再试一次`
- 点击缩略图弹出结果预览弹窗

### 结果预览弹窗建议包含

- 大图预览
- 提示词与尺寸
- 生成时间
- 下载按钮
- 收藏按钮
- 再次编辑按钮

### 核心代码

```ts
function openPreview(record: GenRecord) {
  setPreviewRecord(record)
  setPreviewOpen(true)
}
```

### 交互细节

- 弹窗打开时锁定背景滚动，避免页面错位。
- 点击空白处关闭弹窗，保留当前筛选状态。
- 移动端按钮尺寸要足够大，减少误触。
- 下载按钮放在显眼位置，用户通常会在预览后立即下载。
- 弹窗内可以展示“本次图片来源于历史记录”的说明，帮助用户确认当前操作对象。

## 八、基础版权与内容安全提醒：把可用性做完整

历史记录和草稿恢复做得越好，越要注意内容合规。因为你保存的不只是字符串，还有用户上传的图片、生成的结果和可复用的素材。产品里最好明确告诉用户：哪些可以保存，哪些不建议保存，哪些内容需要自己负责。

### 页面结构

- 历史页顶部增加提示条
- 设置页增加“内容与版权提醒”
- 上传区旁边增加简短说明
- 结果预览弹窗底部增加轻量提示

### 建议文案

- “请确保你上传的图片拥有使用授权。”
- “不要上传包含隐私信息、身份证件或敏感内容的素材。”
- “生成结果用于发布前，请自行检查版权与合规要求。”
- “本地缓存仅保存在当前设备，清理浏览器数据会导致记录丢失。”

### 核心代码

```ts
const safetyTips = [

  '不要上传包含隐私信息或敏感内容的素材。',
  '生成结果发布前请自行检查版权与合规要求。'
]
```

### 交互细节

- 提醒文案不要太长，放在用户最容易看到的位置。
- 上传图片时先提示，再允许进入生成流程。
- 对于历史记录中的图片，提供“移除本地副本”能力，减少隐私风险。
- 如果产品面向团队或公共设备，建议默认关闭自动保存敏感上传图。

# 第9章：做好体验细节——加载态、空状态、消耗提示与防误操作

在前端接入 AI 图像生成功能时，接口能通不代表产品能用。真正影响体验的，往往是这些细节：用户点击后有没有反馈、等待时会不会焦虑、没结果时会不会迷路、额度不够时会不会误以为系统坏了、重复点击会不会造成重复扣费。  
本章的目标，就是把“能生成图片”升级成“能稳定使用的产品页面”。

本章重点解决四类场景：

- **等待中**：按钮 loading、页面骨架、结果占位、进度提示

- **资源消耗**：次数、积分、额度、token 的提示
- **异常与误操作**：失败重试、参数保留、重复提交拦截、离开提示

如果你已经完成了提示词输入、尺寸选择、图片上传、任务轮询和结果展示，这一章就是把这些能力连成完整产品体验的最后一步。

## 一、加载态设计：按钮 loading、页面骨架、结果占位与进度提示

### 1. 这个问题要解决什么？

AI 图片生成通常是异步任务，用户提交后不会立刻看到结果。如果页面没有加载态，用户会反复点击、刷新或关闭页面。加载态的作用，是明确告诉用户：**请求已收到，任务正在处理中，页面没有卡死**。

加载态不只是按钮变灰，而是覆盖从提交到出图的整个等待过程。

### 2. 页面结构怎么设计？

建议分成四层：

- **提交按钮 loading**：防止重复提交
- **结果区骨架屏**：保持布局稳定
- **缩略图占位卡片**：预留结果位置
- **进度文案**：提示排队中、生成中、渲染中

```html
<div class="generator">
  <form class="panel">
    <input type="text" placeholder="输入提示词" />
    <input type="file" accept="image/*" />
    <select>
      <option>1024x1024</option>
      <option>1024x1536</option>
      <option>1536x1024</option>
    </select>
    <button class="generate-btn" disabled>生成中...</button>
  </form>

  <div class="status-bar">
    <span>任务已提交，正在生成第 1 张图片</span>
  </div>

  <div class="result-grid skeleton">
    <div class="card"></div>
    <div class="card"></div>
    <div class="card"></div>
  </div>
</div>
```

如果支持多图，结果区最好一开始就用网格布局预留位置，避免结果出现时页面跳动。

### 3. 核心代码怎么写？

```js
const [isGenerating, setIsGenerating] = useState(false);
const [progressText, setProgressText] = useState('');
const [results, setResults] = useState([]);

async function handleGenerate() {
  if (isGenerating) return;
  setIsGenerating(true);
  setProgressText('任务已提交，正在排队中...');

  try {
    const task = await createImageTask(formData);
    setProgressText('正在生成图片，请稍候...');
    const data = await waitTaskResult(task.id);
    setResults(data.images);
  } finally {
    setIsGenerating(false);
    setProgressText('');
  }
}
```

关键流程是：**先提交任务，再异步等待结果，最后更新页面**。如果接口返回的是任务 ID，就不要在第一次请求里强行拿最终图片。

### 4. 交互细节怎么做更稳？

- 按钮 loading 时禁用提交，防止重复点
- 结果区先显示骨架屏，避免空白
- 等待超过 3 秒后提示“生成时间可能较长，请耐心等待”
- 多图生成时显示“当前已生成 1/4”
- 移动端骨架屏要自适应，避免挤坏布局

### 5. 常见误区

- 只改按钮文案，不做页面级反馈
- 没有骨架屏，结果区长期空白
- 等待过程没有中途提示
- 任务已提交，但页面没有任何“处理中”信息

## 二、空状态设计：首次进入、无历史记录、无搜索结果时怎么办？

### 1. 为什么空状态很重要？

空状态不是“没内容”，而是“引导用户开始下一步”。图像生成产品里，空状态常出现在：

- 首次进入页面
- 历史记录为空
- 搜索结果为空
- 收藏列表为空

如果只写“暂无数据”，用户通常不知道下一步做什么，甚至会以为功能坏了。

### 2. 页面结构怎么设计？

空状态最好包含四部分：

- 图标或插画
- 一句明确说明
- 一个可执行按钮
- 一个示例提示

```html
<div class="empty-state">
  <img src="/empty.png" alt="" />
  <h3>还没有生成过图片</h3>
  <p>输入提示词，选择尺寸，就能开始创建第一张图。</p>
  <button>去生成图片</button>
</div>
```

如果页面同时包含表单和结果区，空状态不要挤掉主操作入口。更好的做法是：上方保留生成入口，下方给出空状态提示。

### 3. 三类空状态分别怎么写？

#### 首次进入
强调从哪里开始：

- “先输入一句你想要的画面描述”
- “支持上传参考图，让结果更接近你的想法”
- “选择图片尺寸后即可开始生成”

#### 无历史记录
强调记录会保存：

- “你生成过的图片会出现在这里”
- “生成完成后可下载、收藏、再次编辑”
- “历史记录会保存在本地缓存中，刷新后也能继续查看最近任务”

#### 无搜索结果
强调条件可能过严：

- “没有找到匹配结果，试试缩短关键词”
- “也可以清空筛选条件重新查看”

### 4. 交互细节

- 空状态按钮直接跳回表单顶部
- 历史为空时保留示例提示词
- 搜索为空时保留“清空筛选”
- 移动端空状态图片要小一些
- 用户已上传图片但未生成时，可提示“你已经准备好了，下一步是点击生成”

### 5. 常见误区

- 只写“暂无数据”，没有下一步引导
- 所有空状态共用一套文案
- 空状态占满屏幕，导致找不到表单
- 首次进入只显示空白结果区，让用户误以为系统在等待自动出图

## 三、消耗提示：次数、积分、额度或 token 怎么展示？

### 1. 用户为什么在意消耗？

图像生成通常会消耗次数、积分、额度或 token。用户最怕的不是扣费，而是不知道“扣了多少、还剩多少、什么时候扣”。如果消耗信息不透明，产品信任感会很差。

### 2. 展示位置怎么选？

建议放在三个地方：

- **表单顶部**：显示剩余额度
- **提交按钮附近**：提示本次生成消耗
- **结果区旁边**：生成后更新余额

### 3. 页面结构示意

```html
<div class="quota-bar">
  <span>剩余额度：12 次</span>
  <a href="/buy">去充值</a>
</div>

<button class="generate-btn">
  生成图片（本次预计消耗 1 次）
</button>
```

如果支持上传参考图、多图生成或高清增强，要把规则写清楚，比如“基础生成 1 次，选择 4 张结果将额外消耗 3 次”。不用复杂，但必须让用户在点击前知道成本。

### 4. 核心原则

- **明确单位**：次、积分、点数、token 不要混用
- **提前提示**：提交前就说明消耗
- **动态更新**：生成成功后刷新余额
- **低余额预警**：少于阈值时提醒“即将用完”

### 5. 交互建议

- 按钮旁显示“预计消耗 1 次”
- 余额不足时按钮置灰，并给出充值入口
- 历史记录中显示每张图的消耗，方便用户理解成本
- 若支持图片上传作为参考图，也要说明是否额外扣费，避免误解

### 6. 常见误区

- 只有成功后才提示消耗
- 余额不足却仍能点击提交
- 不显示单位，用户不知道“3”代表什么
- 消耗规则藏得太深，让用户怀疑被偷偷扣费

---

## 四、失败重试与历史记录恢复：把“失败”变成可继续的流程

很多页面只做了“生成失败”的提示，却没有把失败、重试、历史记录串起来，结果用户只能重新填一遍，体验很差。更好的方式是：**失败后保留参数，重试时自动回填，历史记录里也能再次发起**。

### 1. 页面结构怎么放？

建议把这个流程拆成三个区域：

- **等待区**：显示生成中状态、预计等待时间、剩余次数
- **错误区**：显示失败原因、可重试按钮、额度不足提示
- **历史区**：保存上次成功/失败任务，支持再次编辑

```html
<div class="status-panel">
  <p>任务已提交，预计等待 10-20 秒</p>
  <p>本次将消耗 1 次，当前剩余 3 次</p>
</div>

<div class="error-panel" hidden>
  <p>图片生成失败：服务暂时繁忙</p>
  <button>重试</button>
</div>

<div class="history-panel">
  <!-- 历史记录卡片，支持再次生成 -->
</div>
```

### 2. 状态控制代码怎么写？

下面这段代码可以直接作为状态切换参考，重点是 `loading`、`error`、`retry`、`quota` 四种状态如何联动：

```js
const [status, setStatus] = useState('idle'); // idle | loading | error | success | quota
const [errorMsg, setErrorMsg] = useState('');
const [lastParams, setLastParams] = useState(null);
const [quota, setQuota] = useState(12);

async function submitGenerate(params) {
  if (status === 'loading') return;
  if (quota <= 0) {
    setStatus('quota');
    setErrorMsg('额度不足，请先充值或减少生成数量');
    return;
  }

  setStatus('loading');
  setErrorMsg('');
  setLastParams(params);

  try {
    const task = await createImageTask(params);
    const result = await waitTaskResult(task.id);
    setQuota((q) => q - 1);
    setStatus('success');
    saveToHistory({ params, result, status: 'success' });
  } catch (e) {
    setStatus('error');
    setErrorMsg(e.message || '生成失败，请重试');
    saveToHistory({ params, status: 'error', errorMsg: e.message });
  }
}

function retryLast() {
  if (!lastParams) return;
  submitGenerate(lastParams);
}
```

关键点只有三个：

1. **生成中禁止重复提交**  
2. **失败后保留上一次参数**  
3. **重试直接复用上次参数**

### 3. 联动文案怎么写？

等待页和结果页的文案要让用户知道下一步：

- “任务已提交，正在排队中”
- “预计等待 10-20 秒”
- “本次将消耗 1 次，当前剩余 3 次”
- “生成失败，原因：服务暂时繁忙”
- “可点击重试，系统会自动保留上次参数”
- “额度不足，请先充值后再继续”

如果失败原因是网络问题，文案应偏向重试；如果是额度不足，就不要给用户反复重试按钮，而是直接给充值入口或减少生成数量的建议。

### 4. 历史记录如何参与恢复？

历史记录不只是展示结果，还应该能“再次发起”：

- 点击历史卡片，回填提示词、尺寸、参考图
- 如果是失败任务，直接打开上次参数并显示失败原因
- 如果是成功任务，支持“再次生成”或“用相同参数再来一张”
- 本地缓存先保存最近一次草稿，刷新页面后也能恢复

这样做的好处是，用户即使失败，也不会觉得任务白做了。

---

## 五、防误操作：如何避免重复提交、参数误改和离开丢失？

### 1. 这个问题为什么必须处理？

图像生成页面常见这些误操作：

- 用户连续点两次“生成”
- 任务未结束又修改尺寸
- 编辑中误关页面
- 生成完又重复提交相同参数

这些问题会带来重复扣费、任务混乱和投诉。对前端产品来说，防误操作不是优化项，而是必备项。

### 2. 重复提交怎么拦截？

最简单的规则：**任务进行中，禁止再次提交**。

```js
if (isGenerating) {
  return;
}
```

同时按钮要禁用，并显示 loading。按钮文案最好直接写成“生成中，请稍候”，比单纯变灰更清晰。

### 3. 参数变更提醒怎么做？

当用户在生成过程中修改提示词、尺寸或上传图片时，提示：

- “当前任务正在生成，修改参数不会影响已提交任务”
- “是否取消当前任务并重新生成？”

如果支持取消任务，给出明确按钮；如果不支持，也要让用户知道“改动只对下一次生效”。

这里尤其要注意**图片上传**场景：用户上传参考图后，又在任务进行中换图，前端必须区分“当前任务参数”和“待提交草稿”，避免用户以为改动会影响正在处理的任务。

### 4. 离开页面前提示

当用户有未完成任务或未保存编辑内容时，关闭、刷新、跳转前应提醒：

```js
window.addEventListener('beforeunload', (e) => {
  if (isGenerating || hasUnsavedChange) {
    e.preventDefault();
    e.returnValue = '';
  }
});
```

如果页面有历史草稿，也可以放进本地缓存，减少误关带来的损失。这样即使页面刷新，用户也能恢复刚才的提示词、尺寸选择、图片上传状态和等待中的任务信息。

### 5. 轮询中的取消与恢复规则

如果你的页面用轮询等待任务结果，建议把规则写清楚：

- **可以取消**：只取消前端轮询，不一定取消服务端任务
- **可恢复**：刷新后根据任务 ID 继续查询状态
- **不可重复发起**：同一个任务未结束时不允许再次提交同参数
- **状态恢复**：从本地缓存读到任务 ID 后，自动恢复等待态

这样可以避免用户以为“页面关掉就没了”，也避免系统多次提交同一请求。

### 6. 常见误区

- 只在前端禁用按钮，不考虑刷新后状态恢复
- 任务进行中允许改参数，导致结果不一致
- 页面退出后无任何提醒，用户以为任务丢了
- 只保护“生成按钮”，却忘了“再次编辑”“重新生成”等入口

---

## 六、错误提示分层：参数错误、网络错误、服务端错误、额度不足

### 1. 为什么要分层？

错误提示不能只写“生成失败”。不同错误要不同处理方式，否则用户不知道是该改参数、重试，还是去充值。

一个好的错误提示，至少回答三件事：

1. 发生了什么？
2. 用户该怎么做？
3. 会不会影响已填写内容？

### 2. 分层方式怎么做？

#### 参数错误
用户填写不合法，属于可直接修复的问题。

提示示例：

- “提示词不能为空”
- “图片尺寸格式不正确”
- “参考图大小不能超过 10MB”

处理方式：把错误显示在字段附近，尽量别只弹全局 toast。

#### 网络错误
请求没发出去或中途断开。

提示示例：

- “网络不稳定，请检查连接后重试”

处理方式：保留已填内容，提供重试按钮，最好能一键恢复上次提交参数。

#### 服务端错误
接口异常或任务失败。

提示示例：

- “服务端暂时繁忙，请稍后再试”
- “图片生成失败，任务已中止”

处理方式：保留任务 ID，允许重新发起，避免用户重新填一遍。

#### 额度不足
这是资源问题，不是功能错误。

提示示例：

- “额度不足，无法继续生成”
- “本次生成需要 1 次额度，当前剩余 0 次”

处理方式：引导充值或减少生成次数。

### 3. 核心代码思路

```js
try {
  await generateImage(params);
} catch (err) {
  if (err.code === 'VALIDATION_ERROR') {
    showFormError(err.message);
  } else if (err.code === 'QUOTA_EXCEEDED') {
    showToast('额度不足，请先充值');
  } else if (err.code === 'NETWORK_ERROR') {
    showRetryDialog('网络错误，是否重试？');
  } else {
    showToast('服务暂时异常，请稍后再试');
  }
}
```

如果页面里有“历史记录”和“本地缓存”，建议把失败任务也保留下来，状态标成“失败”，方便用户直接重试，不必重新输入。

### 4. 错误恢复原则

- 能自动修复的，明确告诉用户改哪里
- 能重试的，保留表单和任务信息
- 不能继续的，给出下一步动作
- 失败后保留提示词、上传图和尺寸选择，减少重复劳动

---

## 七、本章落地检查清单

在你把 AI 图像生成功能接入前端产品后，至少检查这些点：

- 点击生成时是否有按钮 loading
- 等待时结果区是否有骨架屏或占位图
- 首次进入、历史为空、搜索为空时是否有对应空状态
- 额度、次数或积分是否在页面中明确展示
- 是否能拦截重复提交
- 参数变更和离开页面是否有提醒
- 错误提示是否按类型分层
- 失败后是否保留用户输入，便于重试
- 图片上传后是否有预览和可移除入口
- 历史记录是否能在本地缓存中恢复
- 移动端上按钮、列表和弹窗是否能正常适配
- 结果预览弹窗是否支持查看大图、关闭和继续操作
- 失败任务是否能在历史记录中再次发起
- 额度不足时是否能明确引导充值或降低生成数量

AI 图像生成页面的核心，不只是“能不能调用接口”，而是“用户在等待、失败、空白、消耗这些场景下是否仍然知道该怎么做”。

如果你已经实现了提示词输入、尺寸选择、图片上传、任务轮询和结果展示，下一步最值得补齐的，就是本章这些体验细节。它们不显眼，但会直接决定你的页面能不能真正用于前端产品中。

1. 先补齐加载态和空状态，让页面不再“像坏了”

3. 最后加上防误操作和离开提醒，减少重复扣费和任务丢失

把这些做好，你的 AI 图片生成页面才算真正具备了可上线的产品体验。

## 一、环境配置管理：API 地址、密钥注入、开发测试生产如何区分？

### 1. 先解决什么问题

AI 图像生成通常依赖外部接口，最容易出错的是环境混用：

- 开发环境误连生产接口，造成真实消耗
- 生产环境仍然使用本地 Mock
- API 密钥被直接写进前端代码
- 不同环境的生成、上传、轮询地址不一致，导致任务失败

所以，上线前第一件事不是改样式，而是把环境配置分清楚。前端页面本身不需要知道“这是开发还是生产”，它只需要读取统一配置。

### 2. 页面结构怎么配合配置管理

建议页面保留一个清晰的信息区，帮助开发和测试快速识别当前环境：

- 顶部状态栏：显示环境标识，如 `DEV / TEST / PROD`
- 表单区：提示词、尺寸、图片上传入口
- 结果区：生成中、成功、失败三种状态
- 历史区：本地缓存的生成记录
- 设置区：仅开发态展示调试开关

联调时能一眼看出当前连的是哪个环境，避免误操作生产环境。

### 3. 推荐的配置拆分方式

```ts
// src/config/env.ts
export const envConfig = {
  apiBaseUrl: import.meta.env.VITE_API_BASE_URL,
  uploadBaseUrl: import.meta.env.VITE_UPLOAD_BASE_URL,
  enableMock: import.meta.env.VITE_ENABLE_MOCK === 'true',
  appEnv: import.meta.env.MODE,
};
```

前端请求只连自己的业务接口，不直接暴露第三方密钥。更稳妥的方式是：

- 前端只请求自有后端代理接口
- 后端再转发到图像生成服务
- 前端通过环境变量拿到后端地址，而不是拿到密钥

```ts
await fetch(`${envConfig.apiBaseUrl}/ai-image/generate`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify(payload),
});
```

如果项目里包含图片上传接口，也建议统一由后端代理，减少跨域和鉴权问题。

### 4. 常见误区

- 把 API Key 写进前端文件并提交仓库
- 只有一个 `.env`，没有 dev/test/prod 区分
- 上传接口和生成接口来自不同域名，但没配跨域
- 本地能跑，部署后因环境变量未注入而报错

### 5. 交互细节

建议在页面右下角显示小型环境标识，避免测试时误操作生产环境。对于会消耗额度的生成按钮，可以在生产环境弹出二次确认，提醒用户这会消耗次数或积分。

## 二、接口联调流程：本地调试、Mock 数据、真实接口如何切换？

### 1. 你要解决的不是“写接口”，而是“稳定联调”

图像生成接口通常是异步的：提交任务、返回任务 ID、轮询结果、拿到图片地址、展示和下载。联调最容易卡在三处：

- 提交成功但轮询失败
- 任务返回慢，页面没有加载态
- 接口偶发报错，没有兜底展示

所以，联调时不能只看“请求发出去没有”，更要看“整个流程是否闭环”。

### 2. 页面结构：联调期必须保留的调试面板

建议保留这些区域：

- 表单区：提示词、尺寸、风格、上传参考图
- 调试区：Mock / 真实接口开关
- 状态区：任务 ID、轮询次数、当前耗时
- 结果区：缩略图布局 + 点击预览弹窗
- 错误区：错误信息、重试按钮

这些区域能帮助快速定位问题：是生成失败，还是轮询断了；是接口返回慢，还是前端状态没更新。

### 3. 本地调试与 Mock 的意义

Mock 不是替代真实接口，而是先验证页面流程：

- 点击“生成”后，按钮是否变成 loading
- 轮询期间是否显示进度
- 结果列表是否按缩略图布局渲染
- 历史记录是否能写入本地缓存
- 下载按钮是否能正确生成链接

```ts
async function generateImage(payload: GeneratePayload) {
  if (envConfig.enableMock) {
    return mockGenerate(payload);
  }
  return request('/ai-image/generate', payload);
}
```

如果页面流程在 Mock 下都不稳定，直接接真实接口只会更难排查。

### 4. 真实接口切换策略

建议使用“一个入口，两套实现”：

- `mockGenerate()`：返回模拟任务 ID 和图片地址
- `requestGenerate()`：走真实后端接口
- 页面层不关心差异，只处理统一返回结构

```ts
type GenerateResult = {
  taskId: string;
  status: 'pending' | 'success' | 'failed';
  imageUrls?: string[];
  errorMessage?: string;
};
```

统一返回结构很重要，因为它能让页面状态机更简单：不管来自 Mock 还是线上接口，最终都转成同一种状态处理。

### 5. 交互细节

联调时最重要的是让用户感知“正在工作”：

- 提交后按钮锁定，防止重复点击
- 加载态显示“正在生成第 1 张……”
- 轮询中展示进度条或时间提示
- 失败后保留用户输入，方便再次编辑
- 上传图片时同步显示进度，避免用户误以为卡死

## 三、发布前总验收清单：从上传到缓存恢复，一项都不能漏

这一节不是原则说明，而是上线前的“逐项勾选表”。发布前，建议按下面的顺序走一遍。

### 1. 表单、上传与移动端适配

- 提示词输入正常
- 图片上传可用，支持常见格式
- 上传后缩略图可预览
- 删除上传图后能重新选择
- 移动端选择图片不遮挡输入框
- 输入框、按钮、上传区在小屏幕下不会挤压成一列看不清

这里必须强调：**图片上传**不是附加项，而是前端接入图像生成能力时常见的核心入口之一，尤其在“参考图生成”“封面生成”“海报生成”场景里更重要。

### 2. 生成、轮询与加载态

- 点击生成后进入加载态
- 任务 ID 能正确保存
- 轮询能从 pending 进入 success / failed
- 页面刷新后能恢复未完成任务状态
- 超时后能给出明确提示，而不是一直转圈
- 轮询中显示“第 1 次查询 / 第 2 次查询”，方便排查慢接口

```ts
if (pollCount > MAX_POLL_COUNT) {
  setStatus('timeout');
  setMessage('生成超时，请稍后在历史记录中查看结果');
}
```

关键不是“转圈好不好看”，而是要让用户明确知道：任务在异步处理中，页面没有卡死。

### 3. 结果展示、预览弹窗与下载

- 生成结果以缩略图网格展示
- 点击缩略图打开结果预览弹窗
- 多张结果可横向切换或分页
- 预览弹窗在手机端能完整显示，并支持关闭
- 下载按钮可导出图片
- 下载失败时给出可复制图片地址的备用方案

结果页建议同时保留“缩略图布局”和“大图预览”。缩略图用于快速扫视结果，预览弹窗用于确认细节，下载入口则固定在弹窗底部，减少误触。

### 4. 历史记录与本地缓存恢复

- 历史记录能记录提示词、尺寸、时间、结果链接
- 本地缓存刷新后可恢复最近记录
- 再次点击历史记录可以快速回填表单，继续编辑生成
- 删除历史记录要二次确认，避免误删
- 如果本地缓存被清理，不要让页面空白，至少显示“暂无历史记录”

```ts
const HISTORY_KEY = 'ai_image_history';

export function saveHistory(item: HistoryItem) {
  const list = JSON.parse(localStorage.getItem(HISTORY_KEY) || '[]');
  list.unshift(item);
  localStorage.setItem(HISTORY_KEY, JSON.stringify(list.slice(0, 20)));
}
```

本地缓存的作用不是替代数据库，而是让用户在刷新、误关、弱网情况下尽量不丢上下文。

## 四、发布后的基础版权与内容安全提醒：页面里要说清楚什么？

上线前检查里，不能只看功能通不通，还要看提示是否清楚。图像生成产品很容易碰到版权、素材来源和内容安全问题，所以页面必须有明确提醒。

### 1. 页面结构：建议固定一个合规提示区

建议在生成按钮下方或结果区底部加入一个“使用提示”模块，包含：

- 版权提示
- 内容安全提示
- 素材来源提示
- 用户责任提示

### 2. 可直接复用的页面文案

你可以在页面里放这样的提示：

> 请确保你上传的图片、输入的提示词和生成用途符合相关法律法规及平台规范。  
> 不要上传未授权素材，不要生成侵权、违法或不适当内容。  
> 生成结果仅供当前使用场景参考，发布前请再次确认版权与合规要求。

如果产品支持图片上传，尤其要明确：用户上传的参考图由用户自行确保拥有使用权，平台只提供生成服务，不替代版权审查。

### 3. 交互细节

- 首次使用时显示一次性提示
- 上传图片后弹出“请确认素材来源”提醒
- 结果下载前再展示一次轻量提示
- 如果用户频繁尝试敏感内容，可在前端给出友好拦截说明

这一部分看起来简单，但它是上线产品里非常重要的收尾动作，能减少后续沟通成本。

## 五、部署方案：静态站点、前后端分离、边缘部署和 CDN 要注意什么？

### 1. 你该选哪种部署方式

如果前端只负责展示和发起请求，可以优先考虑：

- **静态站点部署**：适合纯前端页面
- **前后端分离部署**：适合有后端代理、任务轮询、鉴权的场景
- **边缘部署 + CDN**：适合全球访问和静态资源加速

对于 AI 图像生成类产品，更建议“前端静态部署 + 后端代理接口”这种结构，最容易控制安全性和稳定性。

### 2. 静态站点部署

适合 React、Vue、Next 静态导出等场景。重点是：

- 构建产物正确
- 路由刷新不 404
- 环境变量在构建时注入
- 资源路径与 CDN 一致

如果页面用了前端路由，记得在托管平台配置回退规则，否则用户刷新历史记录页时可能直接 404。

### 3. 前后端分离部署

更适合需要代理密钥和异步任务处理的产品：

- 前端部署到静态托管平台
- 后端负责转发生成接口、处理回调、查询任务状态
- 前端只与自己的后端通信，避免泄露密钥

这种方式虽然多了一层后端，但对图像生成产品非常必要。因为你通常还会接入上传、下载、轮询、鉴权、配额控制等逻辑，后端代理能把这些流程统一起来。

### 4. CDN 与边缘部署注意事项

图像生成页面通常会加载大量缩略图和预览图，CDN 很重要，但要注意：

- 图片链接是否允许跨域展示
- 缩略图是否设置合理缓存
- 轮询接口不要被 CDN 缓存
- 下载链接不要过期过快
- 上传后的临时图和最终结果图要区分权限

### 5. 交互细节

结果预览弹窗中可以直接展示原图与缩略图两种尺寸，便于手机端查看。移动端要保证按钮足够大，下载入口明显，避免误触。下载按钮最好固定在弹窗底部，用户不用来回滚动就能操作。

## 六、上线后的监控点：失败率、等待时长、点击率和告警看什么？

### 1. 上线后不是结束，而是开始观察

上线后要盯的不是“有没有页面”，而是“用户是否顺利完成生成”。建议重点看四类指标：

- **失败率**：生成任务失败、上传失败、下载失败
- **等待时长**：从点击到拿到结果的平均时间
- **点击率**：生成按钮、预览弹窗、下载按钮的使用情况
- **异常告警**：接口超时、轮询过久、缓存恢复失败

### 2. 需要埋点的关键节点

至少记录这些行为：

- 点击生成
- 上传成功
- 任务提交成功
- 轮询成功 / 失败
- 打开结果预览弹窗
- 点击下载
- 收藏历史记录
- 再次编辑并重新生成

这些埋点不是为了“多收集数据”，而是为了判断页面哪个环节掉了用户。

### 3. 告警与兜底

如果轮询超过设定次数还没结果，要提示用户：

“当前任务仍在处理中，你可以稍后在历史记录里继续查看。”

如果接口不可用，则立即切换到友好错误态，并保留表单内容和上传信息，避免用户重新输入一遍。

```ts
if (pollCount > MAX_POLL_COUNT) {
  setStatus('timeout');
  setMessage('生成超时，请稍后在历史记录中查看结果');
}
```

同时，建议把失败后的重试按钮放在错误提示下方，用户可以直接重试，而不是返回表单重新找入口。

### 4. 交互细节

成功不只是“图片出现”，还包括：

- 用户知道下一步该做什么
- 可直接下载
- 可收藏到历史记录
- 可再次编辑提示词继续生成
- 失败时知道问题出在哪，不会陷入无反馈等待

## 结尾小结：上线前你至少要确认这五件事

上线前检查不是形式，它决定图像生成能力能不能真正落到产品里。

你至少要确认：

1. **目录与正文编号统一**：全书保持一套编号体系，章节跳转、页眉页脚、引用都一致  
2. **环境配置正确**：开发、测试、生产分离，密钥不暴露  
3. **接口联调闭环**：Mock 与真实接口可切换，异步任务能跑通  
4. **核心流程完整**：上传、生成、轮询、下载、历史记录、缓存恢复、移动端适配、加载态、预览弹窗都可用  
5. **合规提醒到位**：版权、素材来源、内容安全提示明确可见  
6. **部署方式合理**：静态资源、后端代理、CDN 与跨域都配置正确，发布后还能监控失败率和等待时长  

如果你已经完成前面的页面与流程，那么这一章的工作，就是把它从“能演示”变成“能交付”。真正成熟的前端图像生成产品，不只是把结果展示出来，而是把整个使用路径稳定地送到用户手里。
