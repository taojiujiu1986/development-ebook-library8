# 第1章 先搞明白：MySQL、数据库、表到底是在干啥

## 开篇引入：先别急着写 SQL，先把“仓库”想明白

很多刚开始学 MySQL 的朋友，一上来就盯着 `CREATE TABLE`，语法背了不少，真到业务里还是不知道该怎么建表。问题不在 SQL 难，而在于你还没想清楚：**你到底要存什么数据、给谁存、为什么这么存。**

老赵先给你一句最实在的话：**建表不是写作文，先有业务，再有表，最后才有 SQL。**

这一章，我们先把最基础的概念捋顺：MySQL 是什么、数据库是什么、表是什么、字段是什么，以及它们在真实业务里怎么配合工作。把这一章吃透了，后面学主键、字段类型、约束、索引，就不会像背咒语了。

## 一、什么是关系型数据库？MySQL 在里面扮演什么角色？

### 1. 关系型数据库，先理解“按表存数据”

关系型数据库，就是把数据放进“表”里管理的数据库。它不是把所有东西乱塞一堆，而是按规则分门别类，放到不同的表中。

比如一个电商系统，常见数据会分成：

- 用户数据：谁注册了
- 商品数据：卖什么
- 订单数据：买了什么
- 订单明细：一个订单里具体买了哪些商品

这些数据彼此有关联，所以叫“关系型”。说白了就是：**一张表的数据，可能要和另一张表的数据对应起来。** 比如订单里有用户编号，订单明细里有订单编号和商品编号，这些编号就是后面表和表之间建立联系的关键。

### 2. MySQL 是什么

MySQL 是一种很常见的关系型数据库管理系统。你可以把它理解成：**MySQL 是帮你管理这些表、存取这些数据的工具。**

它负责的事情包括：

- 创建数据库和表
- 保存、查询、修改、删除数据
- 控制字段规则，比如不能为空、默认值、唯一性等

简单说，MySQL 就像一个认真管账的仓库管理员。你先规定好仓库怎么分、每个货架放什么、每一格能不能空着，系统才能稳定运行。

## 二、数据库、表、字段分别是什么？和 Excel 有什么区别？

### 1. 数据库是什么

数据库可以理解成一个大容器，里面放着很多表。

比如你可以有一个叫 `shop_db` 的数据库，里面放：

- `user` 表
- `product` 表
- `orders` 表

数据库的作用，就是把一类业务的数据统一管理起来。做电商就放电商相关数据，做学习系统就放课程、学生、报名记录。分类清楚，后面维护也方便。

### 2. 表是什么

表是数据的具体存放单元，由很多行、很多列组成。

- 一行：一条记录，比如一个用户
- 一列：一个字段，比如用户名、手机号、注册时间

表就像一张结构化清单。比如“会员信息表”，每一行是一个会员，每一列是会员的一个属性。表不是随便摆数据，而是要让数据有固定格式，这样程序才能稳定读写。

### 3. 字段是什么

字段就是表中的列。字段不仅有名字，还要定义规则：这列是什么类型、能不能空、默认值是什么、是否唯一。

比如用户表里常见字段：

- `id`：用户编号
- `name`：用户名
- `phone`：手机号
- `created_at`：创建时间

很多新手以为建表就是起几个列名，其实不对。真正的建表，是在给每个字段定身份、定范围、定约束。

### 4. 它和 Excel 有什么区别

这个类比能帮助入门，但不能完全等同。

相似点：

- 都是行和列
- 都能放数据

不同点：

- Excel 更像手工表格，适合人看
- 数据库更适合程序自动读写
- Excel 不会强制你写规则，数据库可以限制字段类型、是否为空、是否唯一
- 数据库支持高并发查询和业务系统运行，Excel 不擅长这个

所以，**Excel 适合临时整理，数据库适合正式业务系统。** 只要是要被程序频繁使用的数据，基本都要落到数据库里。

## 三、为什么业务系统离不开建表？订单、用户、商品数据怎么放？

业务系统一旦上线，就不是“记一下”这么简单了。用户注册、下单、支付、发货、登录，这些数据都得有地方存，而且得存得规范。

### 1. 用户数据怎么放

比如用户注册时，至少要记录：

- 用户编号
- 用户名
- 手机号
- 注册时间

这些信息放到一张 `user` 表里最合适。以后登录查用户、订单关联用户，也都靠它。你如果把用户信息散着存，后面查起来会很麻烦。

### 2. 商品数据怎么放

商品一般会有：

- 商品编号
- 商品名称
- 价格
- 库存
- 状态

这些字段集中放到 `product` 表里，查询和维护都方便。比如商品改价，只改商品表里的价格字段就行。

### 3. 订单数据怎么放

订单通常会有：

- 订单编号
- 用户编号
- 订单金额
- 下单时间
- 订单状态

如果一个订单里有多个商品，通常还会再拆出订单明细表。

你会发现，**数据库不是把所有内容塞到一张大表里，而是按业务对象拆分成多个表。** 这样结构清楚、数据好查、后期也好改。反过来，如果什么都塞一张表，字段会越来越多，重复数据也会越来越多，维护成本会直线上升。

## 四、建表前先看业务需求：先有模型，再有 SQL

### 1. 先别急着写 `CREATE TABLE`

新手最容易犯的错，就是看到需求直接开写 SQL。老赵提醒你：**先把业务模型想清楚，再动手建表。**

比如现在有个简单需求：

> 需要记录会员信息，包含会员编号、姓名、手机号、性别、注册时间。

先别管 SQL，先回答几个问题：

- 这是一个什么对象？——会员
- 这是不是一张表能描述？——可以
- 哪些信息必须保存？——编号、姓名、手机号、性别、注册时间
- 哪个字段能唯一标识一条记录？——会员编号

把这些问题答出来，表结构就差不多出来了。这里最关键的不是背语法，而是把“业务对象”拆成“字段”。

### 2. 从模型到 SQL 的基本思路

可以按这个顺序走：

1. 识别业务对象
2. 拆出需要保存的信息
3. 判断哪些是字段
4. 确定哪个字段做主键
5. 再写建表 SQL

这就是从业务模型走向数据库设计的第一步。后面学主键、约束、索引，都建立在这个基础上。

你可以先在纸上画一下：对象是什么、有哪些属性、哪些是必填、哪些能重复、哪些需要默认值。等这些问题清楚了，再写 SQL，反而更快，也更少返工。

## 五、本书的学习路线：概念讲解 + SQL 示例 + 小案例练习

这本书不打算把你带进一堆晦涩术语里打转，而是用更直接的方式往前走：

### 1. 先讲概念，知道“是什么”

比如：

- 数据库、表、字段分别是什么
- MySQL 在系统里干什么
- 为什么要建表
- 主键、索引、默认值这些规则是干嘛的

这些概念不是为了考试，而是为了让你做需求时知道该想什么。你只有先弄清“它是什么”，后面才知道“它为什么要这样设计”。

### 2. 再给 SQL 示例，知道“怎么写”

比如后面你会看到：

```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY,
  name VARCHAR(50) NOT NULL
);
```

你不用一开始就全背住，但你要知道每一部分为什么这么写。比如为什么 `id` 常做主键，为什么 `name` 不能空，为什么这里用 `VARCHAR`。学 SQL 不是只记格式，是要理解字段背后的业务含义。

### 3. 最后做小案例练习，知道“怎么落地”

比如给你一个业务需求：

> 做一个商品表，要求商品编号唯一，商品名称不能为空，价格有默认值。

你要试着自己分析，然后写出建表语句。  
这一步最重要，因为**会看不等于会做，会做才是真的学会。**

如果你能把一个需求先拆成表，再把表拆成字段，再把字段写成 SQL，那你就已经迈过建表入门最关键的一道坎了。

## 老赵提醒：建表最怕这几个坑

1. **只看语法，不看业务**  
   SQL 写得再漂亮，业务不对也是白搭。

2. **一张表想装所有东西**  
   这样后面维护很痛苦，查起来也乱。

3. **字段名随便起**  
   比如一会儿叫 `userName`，一会儿叫 `username`，后期很容易乱套。命名要统一。

4. **没想清楚主键是谁**  
   没有主键的表，后面更新、关联、去重都会很麻烦。

老赵先说句实话：**建表不是先背语法，而是先看业务。**  
很多初学者一拿到需求就急着写 `CREATE TABLE`，结果表建完才发现字段少了、名字乱了，后面还得大改。根本原因就一个：你还没把“业务语言”翻译成“数据库语言”。

这一章，咱们就拿最常见的“用户注册”来练手。你会看到一个完整过程：**从业务需求拆出字段，再落到表结构，最后写成 MySQL 建表 SQL。**

## 一、从“注册用户”业务里提取需要保存的信息

假设产品经理给你的需求是：

- 用户可以注册
- 注册时要填写用户名、手机号和密码
- 系统要记录用户状态，比如正常、禁用
- 要保存用户创建时间

这段话看起来像功能描述，实际上是在说：**这个业务对象要长期保存哪些数据。**  
数据库表的本质，就是把这些信息一项一项存下来。

### 1.1 业务名词和数据库字段，不是一回事

“用户注册”是业务动作，不能直接当字段名。  
它背后真正需要保存的是一组数据项：

- 用户名
- 手机号
- 密码
- 状态
- 创建时间

这些才是后面要进表里的内容。

### 1.2 先问三个问题，再决定怎么建表

老赵建议你先问自己三个问题：

1. **这个对象是谁？**  
   这里是“用户”。

2. **这个对象要存什么？**  
   用户名、手机号、密码、状态、创建时间。

3. **这些信息要不要长期保存？**  
   要，因为登录、查询、管理都会用到。

问完这三个问题，表的大方向就出来了：**一张用户表，专门保存用户注册相关信息。**

---

## 二、识别字段：用户名、手机号、密码、状态、创建时间

字段拆分是从业务到表结构最关键的一步。

### 2.1 先把业务信息拆成字段

把需求拆开，可以得到这些字段：

- 用户名：`username`
- 手机号：`phone`
- 密码：`password`
- 状态：`status`
- 创建时间：`created_at`

字段名建议统一、清晰、便于维护，常见做法是英文小写加下划线。  
记住一句话：**字段名是给团队长期维护用的，不是给人炫技用的。**

### 2.2 字段不是越多越好，也不是越少越好

新手常犯两个错：

- **字段太少**：漏掉状态、创建时间，后面没法管理和统计。
- **字段太多**：把头像、昵称、生日、地址全塞进去，结果表一开始就变复杂。

第一版建表要讲究一个词：**够用。**  
先把当前业务最核心的信息存起来，后续再按需扩展。

### 2.3 每个字段都要想清楚它的作用

#### 用户名 `username`
用户登录或展示时会用到，通常要控制长度，避免太短或太长。

#### 手机号 `phone`
常用于注册、登录、找回密码，一般要考虑唯一性，避免重复。

#### 密码 `password`
这里存的是密码信息，实际开发中一般不会直接存明文。先记住：密码字段通常不能空。

#### 状态 `status`
表示用户是否正常，例如：

- 1：正常
- 0：禁用

后台管理时，临时停用用户就很常见。

#### 创建时间 `created_at`
记录用户什么时候注册，方便排序、筛选和统计。

## 三、判断哪些字段必须有，哪些字段可以先留空

拆完字段后，要判断：**哪些字段创建记录时必须填写，哪些可以用默认值。**

### 3.1 什么叫“必须有”

就是这条记录创建时，这个字段不能空。  
比如用户注册时：

- 用户名不能空
- 手机号不能空
- 密码不能空

没有这些信息，注册这件事就不完整。

### 3.2 什么叫“可以先留空”

有些字段创建时不一定要手动传，比如：

- 状态可以给默认值
- 创建时间可以自动生成

这样做的好处是：应用层少传参数，数据库也更统一。

### 3.3 `NOT NULL` 和 `DEFAULT` 不是一回事

- `NOT NULL`：表示不能为空
- `DEFAULT`：表示没传值时使用默认值

比如状态字段可以设计成：

- 不能为空
- 默认值为 `1`，表示正常

创建时间也常用数据库自动记录当前时间。  
你可以把它理解成：

- `NOT NULL` 是“必须交”
- `DEFAULT` 是“没交就给标准答案”

## 四、如何把业务名词转成表名和字段名

名字起得乱，后面整张表都会乱。

### 4.1 表名怎么起

这里的业务对象是“用户”，表名通常可以叫：

- `user`
- `users`
- `t_user`

本书先用直观的 `user`，你也可以按团队规范加前缀。  
重点不是名字本身，而是**表名要表达它存的是什么。**

### 4.2 字段名怎么起

字段名尽量做到：

- 见名知意
- 风格统一
- 不要乱缩写

比如：

- `username`：用户名
- `phone`：手机号
- `password`：密码
- `status`：状态
- `created_at`：创建时间

### 4.3 不要把业务话术直接原样搬进字段

比如“账号状态是否可用”这种话，不要硬翻成超长字段名。  
字段名要的是**清楚**，不是照搬业务原话。短、准、统一，才好维护。

## 五、先画出简化的数据模型，再写建表 SQL

先把前面的内容落成一个最小可用模型。

| 字段名 | 含义 | 是否必填 | 备注 |
|---|---|---:|---|
| id | 用户编号 | 是 | 主键 |
| username | 用户名 | 是 | 用户识别 |
| phone | 手机号 | 是 | 常用于登录或联系 |
| password | 密码 | 是 | 实际中一般存加密结果 |
| status | 状态 | 否 | 默认正常 |
| created_at | 创建时间 | 否 | 自动记录 |

这里的 `id` 虽然需求里没明说，但建表时通常都会加主键，方便唯一标识每条记录。  
这就是从业务模型到表结构的过渡。

### 5.1 主键为什么要加

主键可以理解成一张表里每条数据的“身份证号”。  
有了主键，数据库才能更快、更准确地区分不同用户。

入门阶段先记住：**一张表通常要有一个主键，最常见的是自增整数主键。**

### 5.2 索引先露个脸

像手机号这种经常查询、又要求唯一的字段，通常会考虑加索引。  
你先把它理解成“加速查找的目录”就行。索引不只是为了存数据，更是为了检索。

## 六、第一版建表 SQL：把模型变成真正的表

下面把上面的模型写成 MySQL 建表语句，先以“入门可读”为主。

```sql
CREATE TABLE user (
    id BIGINT NOT NULL AUTO_INCREMENT COMMENT '用户ID',
    username VARCHAR(50) NOT NULL COMMENT '用户名',
    phone VARCHAR(20) NOT NULL COMMENT '手机号',
    password VARCHAR(255) NOT NULL COMMENT '密码',
    status TINYINT NOT NULL DEFAULT 1 COMMENT '用户状态：1正常，0禁用',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_phone (phone)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

### 6.1 这段 SQL 里有哪些关键点

这里包含了本章必须掌握的基础内容：

- **数据类型**：`BIGINT`、`VARCHAR`、`TINYINT`、`DATETIME`
- **主键**：`PRIMARY KEY (id)`
- **AUTO_INCREMENT**：`id` 自动递增
- **NOT NULL**：字段不能为空
- **DEFAULT**：字段默认值
- **UNIQUE**：手机号不能重复
- **注释**：字段和表都有说明
- **字符集**：`utf8mb4`
- **存储引擎**：`InnoDB`

### 6.2 为什么 `id` 用 `BIGINT` 和 `AUTO_INCREMENT`

`id` 作为主键，需要唯一。`AUTO_INCREMENT` 的意思是：插入新数据时，这个值自动增长，不用程序手动填。

好处很直接：

- 不容易重复
- 插入方便
- 作为主键查询效率高
- 后续关联其他表也方便

### 6.3 为什么手机号要加唯一约束

手机号通常对应唯一用户，不加约束就可能出现重复注册。  
`UNIQUE KEY uk_phone (phone)` 的作用，就是告诉数据库：**手机号不能重复。**

很多重复数据，不是程序先发现的，而是数据库先帮你拦住的。

### 6.4 为什么字符集用 `utf8mb4`

`utf8mb4` 是 MySQL 里常用的字符集，兼容性更好，能处理更多字符。  
入门阶段你先记住：**中文系统一般优先考虑 `utf8mb4`。**

### 6.5 注释为什么要写

`COMMENT` 就是给字段和表做说明。  
别小看它，过几个月再看表结构时，注释真的能救命：

- `status` 到底是 0 表示禁用还是 1 表示禁用？
- `phone` 是手机号还是电话？
- `created_at` 是创建时间还是更新时间？

有注释，维护就省很多事。

## 八、常见误区：新手第一次建表最容易踩的坑

### 8.1 只看业务名字，不拆字段

看到“用户注册”就直接想表名，字段却没理清。  
正确顺序是：先拆字段，再定表名，最后写 SQL。

### 8.2 所有字段都设成可空

这样短期看似省事，长期维护会很麻烦。  
能确定必填的字段，就应该明确写 `NOT NULL`。

### 8.3 不加主键

没有主键，查询、更新、关联都会别扭。  
主键不是装饰，是基础。

### 8.4 不加唯一约束

像手机号、邮箱这类业务唯一值，不加约束很容易出重复数据，后面处理很麻烦。

### 8.5 表名、字段名随便写

今天 `user1`，明天 `user_info`，后天又 `user_table`，看起来都像用户表，实际维护会越来越乱。  
命名统一，是长期维护的底层能力。

# 第3章 建表 SQL 怎么写：`CREATE TABLE` 的基本语法和结构

前面我们已经把业务模型拆得差不多了，接下来就要落地：**把脑子里的表，写成 MySQL 里能执行的建表 SQL**。

很多同学一看到 `CREATE TABLE` 就紧张，其实不用先背整段语法。你只要先记住一句话：

> 建表 SQL，本质上就是把“这张表有什么字段、每个字段是什么类型、哪些不能为空、哪个是主键、默认值是什么、要不要加说明”一次性交给 MySQL。

这一章，老赵带你把 `CREATE TABLE` 拆开看懂，再用一个“用户表”案例，完整写出第一版建表语句。你把这一章吃透，后面再建订单表、商品表、文章表，思路都一样。

## 一、`CREATE TABLE` 的基本语法长什么样？

先看最基础的写法：

```sql
CREATE TABLE 表名 (
    字段名1 字段类型 约束,
    字段名2 字段类型 约束,
    字段名3 字段类型 约束
);
```

你可以把它理解成：

- `CREATE TABLE`：我要创建一张表
- `表名`：这张表叫什么
- 括号里面：这张表有哪些字段
- 每个字段后面：告诉 MySQL 这个字段怎么存、能不能空、有没有默认值

比如一个很粗的用户表：

```sql
CREATE TABLE user (
    id BIGINT,
    username VARCHAR(50),
    phone VARCHAR(20)
);
```

这段 SQL 能跑，但不够好。因为它只说了“有哪些列”，没说：

- 哪个字段是主键
- `id` 能不能重复
- `username` 能不能为空
- `phone` 要不要唯一
- 默认值是什么
- 字符集怎么设置
- 字段注释是什么

所以，**能写出来不代表写得好**。建表不是堆字段，而是把规则写完整。

### 老赵提醒
初学者最容易犯的错，就是只写字段名，不写约束。表虽然建出来了，但后面插数据、查数据、做关联时，全是坑。

---

## 二、表名、字段名、字段类型、约束、表级选项分别是什么？

先把 `CREATE TABLE` 拆成 5 个部分看。

### 1）表名：这张表存什么

表名最好一眼能看出业务含义，比如：

- `user`：用户表
- `product`：商品表
- `order_info`：订单表
- `article`：文章表

命名风格尽量统一，别今天拼音、明天缩写、后天驼峰乱飞。团队协作里，统一命名很重要。

### 2）字段名：这一列存什么数据

字段名就是列名，描述一条记录里的某个属性，比如：

- `id`
- `username`
- `phone`
- `create_time`

字段名要短，但含义要明确。时间字段常见写法有：

- `create_time`
- `update_time`

状态字段常见写法有：

- `status`
- `is_deleted`

这些名字一眼就知道用途，后面维护省很多事。

### 3）字段类型：这一列怎么存

字段类型决定了数据怎么存、能存多大、占多少空间、能不能比较和排序。常见基础类型先记住这些：

- `INT`：整数
- `BIGINT`：更大的整数，常用作主键
- `VARCHAR(n)`：可变长度字符串，常用来存用户名、手机号、邮箱
- `CHAR(n)`：固定长度字符串，适合长度固定的数据
- `DATETIME`：日期时间
- `DATE`：日期
- `DECIMAL(m,n)`：精确小数，适合金额
- `TINYINT`：很小的整数，常用作状态值

比如：

```sql
id BIGINT
username VARCHAR(50)
created_at DATETIME
price DECIMAL(10,2)
status TINYINT
```

### 4）约束：这一列必须遵守什么规则

常见约束有：

- `NOT NULL`：不允许为空
- `DEFAULT`：默认值
- `UNIQUE`：不能重复
- `PRIMARY KEY`：主键，唯一标识一条记录
- `AUTO_INCREMENT`：自增，常配合主键使用

你先记住：**字段类型决定“怎么存”，约束决定“怎么管”。**

### 5）表级选项：整张表的设置

表级选项最常见的是：

- 字符集：`DEFAULT CHARSET=utf8mb4`
- 排序规则：`COLLATE=utf8mb4_unicode_ci`

这部分很容易被忽略，但会影响中文、表情符号和字符串排序。很多业务都有昵称、备注、表情，不设置好字符集，后面容易出乱码。

### 老赵提醒
字段类型别拍脑袋选。手机号别用 `INT`，因为可能有前导 0；金额别用 `FLOAT`，因为有精度问题。先记住：**能精确就用精确类型，能用字符串就别硬转数字。**

## 三、主键、默认值、注释在建表语句里怎么放？

这一节，把最常用的几个基础约束直接放进 SQL 看。

### 1）主键怎么写

主键用来唯一标识一条记录。比如用户表里，每个用户都应该有一个唯一 `id`。

常见写法有两种：

**字段后面直接写：**

```sql
id BIGINT PRIMARY KEY
```

**单独写成表级主键：**

```sql
PRIMARY KEY (id)
```

实际项目里第二种更常见，也更方便以后扩展联合主键。入门阶段先会看，后面再理解差别。

### 2）`AUTO_INCREMENT` 怎么写

`AUTO_INCREMENT` 表示这个字段由 MySQL 自动递增赋值，通常跟主键配合使用：

```sql
id BIGINT NOT NULL AUTO_INCREMENT
```

意思是：

- 这个字段不能为空
- 每插入一条新数据，MySQL 自动加 1
- 一般不用自己手动写 `id`

它特别适合：

- 用户表主键
- 订单表主键
- 商品表主键

好处很明显：开发省事，数据规整，减少重复和冲突。

### 3）默认值 `DEFAULT` 怎么写

默认值的作用是：插入数据时，如果某个字段没写，MySQL 自动给它一个默认值。

比如：

```sql
status TINYINT NOT NULL DEFAULT 1
```

表示状态默认是 `1`，比如代表“正常”。

再比如：

```sql
create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
```

表示创建时间默认是当前时间。

很多字段不需要每次手工传值，比如状态、创建时间、是否删除，交给数据库兜底就行。

### 4）注释 `COMMENT` 怎么写

字段注释：

```sql
username VARCHAR(50) NOT NULL COMMENT '用户名'
```

表注释：

```sql
COMMENT='用户表'
```

注释不是装饰，是给人看的。表结构一复杂，没有注释就很难维护。

### 老赵提醒
`AUTO_INCREMENT` 一般只用于整数型主键，不要随便给业务字段加自增。手机号、身份证号这种字段，不该自增，也不该拿来自增。

## 四、建表时常见的书写顺序和格式习惯是什么？

很多人不是不会写 SQL，而是写得乱。乱 SQL 后面不好维护，查问题也费劲。老赵建议固定一个顺序。

### 推荐顺序

1. 主键字段  
2. 普通业务字段  
3. 时间字段  
4. 主键约束  
5. 唯一约束  
6. 索引  
7. 表级选项  

这样写，结构清晰，一眼就知道这张表的核心内容。

### 推荐排版

```sql
CREATE TABLE user (
    id BIGINT NOT NULL AUTO_INCREMENT COMMENT '用户ID',
    username VARCHAR(50) NOT NULL COMMENT '用户名',
    phone VARCHAR(20) NOT NULL COMMENT '手机号',
    status TINYINT NOT NULL DEFAULT 1 COMMENT '用户状态，1正常，0禁用',
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_phone (phone)
) COMMENT='用户表' DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

这个结构有几个好处：

- 每个字段独占一行
- 字段类型和约束直接写在后面
- 表级约束统一放后面
- 表选项放最后

### 书写习惯建议

- 字段对齐，别东一行西一行
- 关键字尽量大写，字段名小写
- 每个字段都加注释
- 表名、字段名统一命名风格
- 先写核心字段，再补辅助字段

### 老赵提醒
SQL 不是“能执行就行”，而是“别人一看就懂”。很多表后面出问题，不是因为数据错了，而是因为最开始写得太随意。

## 五、结合用户表案例，完整写出第一版 `CREATE TABLE`

下面用一个最常见的业务模型来落地：**用户表**。

### 先想业务，不要先背 SQL

假设我们做一个简单会员系统，用户表至少要存：

- 用户编号
- 用户名
- 手机号
- 状态
- 创建时间
- 更新时间

从业务上看，有几个规则：

- 每个用户必须有唯一编号
- 用户名不能为空
- 手机号不能为空，而且最好唯一
- 用户状态应该有默认值
- 创建时间和更新时间应该自动记录
- 表要支持中文，注释要写清楚

这个过程很重要。先问“业务要什么”，再翻译成表结构。

### 第一版建表 SQL

```sql
CREATE TABLE user (
    id BIGINT NOT NULL AUTO_INCREMENT COMMENT '用户ID',
    username VARCHAR(50) NOT NULL COMMENT '用户名',
    phone VARCHAR(20) NOT NULL COMMENT '手机号',
    status TINYINT NOT NULL DEFAULT 1 COMMENT '用户状态，1正常，0禁用',
    create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_phone (phone),
    UNIQUE KEY uk_username (username)
) COMMENT='用户表' DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### 这段 SQL 用到了什么

- `id BIGINT NOT NULL AUTO_INCREMENT`  
  主键自增，保证每条数据都有唯一编号

- `username VARCHAR(50) NOT NULL`  
  用户名是字符串，不能为空

- `phone VARCHAR(20) NOT NULL`  
  手机号通常也是字符串，不要乱用数字型

- `status TINYINT NOT NULL DEFAULT 1`  
  用户状态默认正常

- `create_time` / `update_time`  
  自动记录时间，方便追踪数据变化

- `PRIMARY KEY (id)`  
  指定主键

- `UNIQUE KEY uk_phone (phone)`  
  手机号唯一

- `UNIQUE KEY uk_username (username)`  
  用户名唯一，避免重复注册

- `COMMENT='用户表'`  
  表注释

- `DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci`  
  支持中文和更丰富的字符场景

### 顺便说一下索引基础

你会看到 `UNIQUE KEY` 这种写法。它不仅是唯一约束，也会创建索引。也就是说，**唯一约束和索引在建表里经常是连着出现的**。你现在先记住：

- `PRIMARY KEY` 是最重要的索引
- `UNIQUE KEY` 既限制重复，也有索引效果
- 普通字段以后也可以单独加索引

这章先把基本结构写对，后面再专门讲索引怎么用。

### 老赵提醒
用户表第一版别追求炫技，先把核心字段、约束和字符集写稳。很多项目一开始就是靠这种基础表跑起来的，不需要一上来就搞复杂分库分表。

## 六、建完表之后，怎么查看、修改和删除？

建表不是终点。开发里你还会经常查表、改表、删表，几个基础命令要认识。

### 1）查看表结构

```sql
DESC user;
```

或者：

```sql
SHOW CREATE TABLE user;
```

- `DESC`：看字段概况，简单直接
- `SHOW CREATE TABLE`：看完整建表语句，更适合排查问题

如果你想快速确认某个字段是不是 `NOT NULL`、默认值是什么、有没有索引，`DESC` 就够了。  
如果你想知道这张表最初到底怎么建出来的，`SHOW CREATE TABLE` 更合适。

### 2）修改表结构

新增邮箱字段：

```sql
ALTER TABLE user
ADD email VARCHAR(100) DEFAULT NULL COMMENT '邮箱';
```

修改字段类型：

```sql
ALTER TABLE user
MODIFY phone VARCHAR(30) NOT NULL COMMENT '手机号';
```

改字段名：

```sql
ALTER TABLE user
CHANGE username user_name VARCHAR(50) NOT NULL COMMENT '用户名';
```

最常见的就是这三种：

- `ADD`：新增字段
- `MODIFY`：修改字段类型或属性
- `CHANGE`：修改字段名，也能同时改类型和属性

### 3）删除表

如果确认不需要这张表了：

```sql
DROP TABLE user;
```

这个命令要非常小心，一删就没了。生产环境里执行前一定要确认。

### 老赵提醒
`ALTER TABLE` 和 `DROP TABLE` 都是危险操作。开发环境随便练，正式环境一定先确认、先备份、再执行。手快一时爽，回滚火葬场，不是吓你。

## 七、小案例练习：把“用户需求”翻成建表 SQL

### 需求

现在有一个简化需求：

- 要有用户编号
- 要有用户名
- 要有手机号
- 要有用户状态，默认正常
- 要有创建时间
- 用户名和手机号都不能重复

### 你先自己判断

先想这几个问题：

1. 哪个字段适合做主键？
2. 哪些字段不能为空？
3. 哪些字段要唯一？
4. 哪些字段需要默认值？
5. 哪些字段适合字符串类型？

### 参考答案

```sql
CREATE TABLE user (
    id BIGINT NOT NULL AUTO_INCREMENT COMMENT '用户ID',
    username VARCHAR(50) NOT NULL COMMENT '用户名',
    phone VARCHAR(20) NOT NULL COMMENT '手机号',
    status TINYINT NOT NULL DEFAULT 1 COMMENT '用户状态，1正常，0禁用',

    PRIMARY KEY (id),
```

# 第4章 字段类型怎么选：常见数据类型别乱用

## 开篇引入：字段类型选错，后面很容易返工

老赵跟你说，建表这事儿，很多人最先盯着表名、索引，其实最容易埋雷的是**字段类型**。

字段类型不是小事，它直接影响字段能不能装得下、查起来快不快、后面会不会频繁改表。你今天图省事，后面业务一起来，改类型、迁数据、改代码，往往就不是一条 SQL 的事了。

常见坑你肯定不陌生：

- 手机号存成整数，前导 0 没了
- 金额用了浮点数，算着算着有误差
- 状态字段随手写字符串，数据越来越乱
- 时间字段乱存，后面排序、筛选都麻烦
- 字段长度拍脑袋，最后不是浪费就是装不下

这一章，老赵就带你把常见字段类型怎么选讲清楚，并结合用户表、订单表，带你从业务需求落到建表字段上。

先记住一句话：

> 字段类型不是“差不多就行”，而是要“刚刚好够用，还方便维护”。

---

## 一、整数类型怎么选：TINYINT、INT、BIGINT 各管什么

很多初学者一看到数字就统一写 `INT`，这不是不行，但不够细。

### 1. TINYINT：适合很小的范围

`TINYINT` 常用来存**状态、标记、开关**，不是拿来存大数字的。

比如：

- 性别：`0` 女，`1` 男，`2` 未知
- 用户状态：`0` 禁用，`1` 正常
- 是否删除：`0` 否，`1` 是

示例：

```sql
status TINYINT NOT NULL DEFAULT 1 COMMENT '用户状态：0禁用，1正常',
is_deleted TINYINT NOT NULL DEFAULT 0 COMMENT '是否删除：0否，1是'
```

### 2. INT：大多数普通整数字段的默认选择

`INT` 适合普通数量、年龄、库存、浏览次数、排序号这类字段。

```sql
quantity INT NOT NULL DEFAULT 1 COMMENT '购买数量',
stock INT NOT NULL DEFAULT 0 COMMENT '库存数量'
```

如果没有特别理由，很多普通数字字段用 `INT` 就够了。

### 3. BIGINT：适合很大的数字

`BIGINT` 适合：

- 数据量很大的主键 ID
- 大规模日志表
- 长期增长的计数
- 按“分”存储的大额金额

比如：

```sql
id BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID'
```

### 怎么判断用哪种整数？

- **状态/开关**：优先 `TINYINT`
- **普通数量/年龄/库存**：优先 `INT`
- **主键、超大数字、长期增长字段**：考虑 `BIGINT`

### 老赵提醒

> 不要觉得数字字段都用 `INT` 就省事。  
> 状态字段用 `INT` 不是不能用，但不够清晰；主键一开始就用 `TINYINT`，那是迟早要爆。

---

## 二、字符串类型怎么选：CHAR、VARCHAR、TEXT

字符串字段最容易被乱用，尤其是手机号、昵称、备注经常混着来。

### 1. CHAR：长度固定的字符串

`CHAR` 适合长度固定的字段，比如：

- 国家代码
- 固定长度编码
- 简单验证码
- 性别码、状态码

示例：

```sql
gender_code CHAR(1) NOT NULL DEFAULT 'U' COMMENT '性别码：M男/F女/U未知'
```

### 2. VARCHAR：最常用的可变长度字符串

`VARCHAR` 适合大多数日常业务字段：

- 用户名
- 手机号
- 邮箱
- 商品名称
- 地址
- 订单号

```sql
username VARCHAR(50) NOT NULL COMMENT '用户名',
phone VARCHAR(20) NOT NULL COMMENT '手机号',
email VARCHAR(100) DEFAULT NULL COMMENT '邮箱'
```

### 3. TEXT：长文本，别乱用

`TEXT` 适合：

- 商品详情
- 文章正文
- 备注说明
- 大段描述

```sql
remark TEXT COMMENT '备注说明'
```

但 `TEXT` 不适合拿来当普通字段，空间大、处理不如 `VARCHAR` 灵活。

### 字符串字段怎么判断？

- 长度固定：`CHAR`
- 长度不固定但不长：`VARCHAR`
- 内容很长：`TEXT`

### 老赵提醒

> 手机号不要用整数存。  
> 前导 0 会没，国际区号也不好处理。手机号本质是编号，不是拿来做数学运算的。

---

## 三、日期时间类型怎么选：DATE、DATETIME、TIMESTAMP

时间字段看着简单，最容易乱。

### 1. DATE：只存日期

只关心“哪一天”，就用 `DATE`。比如：

- 生日
- 入职日期
- 预约日期
- 发货日期

```sql
birthday DATE DEFAULT NULL COMMENT '生日',
delivery_date DATE DEFAULT NULL COMMENT '发货日期'
```

### 2. DATETIME：存完整的日期和时间

`DATETIME` 适合记录具体时间点，比如：

- 创建时间
- 下单时间
- 支付时间
- 更新时间

```sql
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间'
```

### 3. TIMESTAMP：也表示时间点，常用于系统时间

`TIMESTAMP` 也能存时间点，常见于系统自动维护的时间字段。刚入门时，你可以先把 `DATETIME` 用熟，它已经能覆盖大多数场景。

### 时间字段怎么选？

- 只要日期：`DATE`
- 需要精确到时分秒：`DATETIME`
- 系统自动维护时间：`TIMESTAMP` 常见

### 老赵提醒

> 时间字段别乱写成字符串。  
> 今天偷懒存成 `VARCHAR`，明天想排序、筛选、统计，就会很难受。

---

## 四、金额、状态、布尔值这类字段怎么设计

这部分最实用，也最容易出错。

### 1. 金额字段：不要用浮点数

金额别用 `FLOAT`、`DOUBLE`，会有精度问题。更稳妥的做法是：**用整数存“分”**。

```sql
amount_cents BIGINT NOT NULL DEFAULT 0 COMMENT '金额，单位：分'
```

这样计算稳定，也方便对账。

### 2. 状态字段：用小整数表达

不要写成：

```sql
status VARCHAR(20)
```

然后里面放“待支付”“已支付”“已取消”。这样后期容易乱。

更好的方式是：

```sql
status TINYINT NOT NULL DEFAULT 0 COMMENT '订单状态：0待支付，1已支付，2已取消'
```

### 3. 布尔值字段：通常用 TINYINT

例如：

```sql
is_vip TINYINT NOT NULL DEFAULT 0 COMMENT '是否会员：0否，1是'
```

这类字段通常只有两个明确状态，适合用 `TINYINT` 表达。

### 老赵提醒

> 金额别用 float，状态别用字符串，布尔别写得模棱两可。  
> 字段设计的核心不是“能不能存”，而是“以后好不好用、好不好查、好不好维护”。

## 五、结合用户表、订单表，怎么把业务需求翻译成字段类型

光讲概念不够，咱们直接从业务落表。

### 1. 用户表：先看需求

假设用户表要存：

- 用户ID
- 用户名
- 手机号
- 邮箱
- 性别
- 状态
- 生日
- 创建时间

对应字段类型可以这样选：

- `id`：`BIGINT`
- `username`：`VARCHAR(50)`
- `phone`：`VARCHAR(20)`
- `email`：`VARCHAR(100)`
- `gender`：`TINYINT`
- `status`：`TINYINT`
- `birthday`：`DATE`
- `created_at`：`DATETIME`

示例：

```sql
CREATE TABLE user (
  id BIGINT NOT NULL AUTO_INCREMENT COMMENT '用户ID',
  username VARCHAR(50) NOT NULL COMMENT '用户名',
  phone VARCHAR(20) NOT NULL COMMENT '手机号',
  email VARCHAR(100) DEFAULT NULL COMMENT '邮箱',
  gender TINYINT NOT NULL DEFAULT 0 COMMENT '性别：0未知，1男，2女',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：0禁用，1正常',
  birthday DATE DEFAULT NULL COMMENT '生日',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_phone (phone)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

### 2. 订单表：再看需求

订单表常见字段有：

- 订单ID
- 用户ID
- 订单号
- 金额
- 数量
- 状态
- 下单时间

对应类型一般是：

- `id`：`BIGINT`
- `user_id`：`BIGINT`
- `order_no`：`VARCHAR(32)`
- `amount_cents`：`BIGINT`
- `quantity`：`INT`
- `status`：`TINYINT`
- `created_at`：`DATETIME`

示例：

```sql
CREATE TABLE orders (
  id BIGINT NOT NULL AUTO_INCREMENT COMMENT '订单ID',
  user_id BIGINT NOT NULL COMMENT '用户ID',
  order_no VARCHAR(32) NOT NULL COMMENT '订单号',
  amount_cents BIGINT NOT NULL DEFAULT 0 COMMENT '订单金额，单位：分',
  quantity INT NOT NULL DEFAULT 1 COMMENT '购买数量',
  status TINYINT NOT NULL DEFAULT 0 COMMENT '订单状态：0待支付，1已支付，2已取消',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '下单时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_user_id (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单表';
```

你会发现，建表不是背类型，而是根据业务含义选合适的数据表达方式。订单号是编码，不是数字；金额要稳定，不是随便写小数；状态最好统一编码，不要堆文字。

## 六、小案例练习：你来判断字段该怎么选

下面几个题，你可以先自己想想。

### 练习1：商品库存应该用什么类型？

库存是整数，通常不需要特别大范围：

- `INT NOT NULL DEFAULT 0`

### 练习2：用户昵称应该用什么类型？

昵称长度不固定，一般也不长：

- `VARCHAR(50)` 或 `VARCHAR(100)`

### 练习3：用户生日应该用什么类型？

只关心年月日，不需要时间：

- `DATE`

### 练习4：订单金额应该怎么存？

金额不能有精度误差：

- 用整数存分，如 `BIGINT`

### 练习5：是否会员字段怎么存？

只有是/否两个状态：

- `TINYINT NOT NULL DEFAULT 0`

# 第5章 字符集与排序规则：中文表怎么建才不容易踩坑

## 开篇引入：你以为建表只要写字段，其实中文最容易在这里翻车

前面我们已经把“数据库、表、字段、主键、约束”这些基础概念搭起来了。接下来，老赵要提醒你一个很现实的问题：**只要业务里有中文，字符集和排序规则就不是可选项，而是建表时必须先想清楚的事。**

很多新手建表时只盯着字段类型，觉得 `id` 用整型、`name` 用字符串、`create_time` 用时间就够了。结果一到真实项目里就出问题：

- 中文存进去乱码
- “张三”和“张三 ”比较结果不对
- 排序结果不符合预期
- 表之间一联查，字符集不一致报错
- 手机端、后台、接口各用各的编码，数据互相打架

所以这一章我们不空讲概念，而是围绕一个很实际的问题来讲：

> **中文业务的表，到底怎么选字符集和排序规则，才不会后面一堆坑？**

你可以把这一章理解成建表前的“编码统一课”。表面上讲的是字符集，实际上解决的是很多数据问题的根源。

---

## 一、什么是字符集，为什么中文项目不能随便选？

### 1. 字符集到底是什么

字符集就是：**数据库用来“认识文字”的编码规则**。  
人类写字靠字母、汉字、数字、符号；数据库要把这些内容存起来，就得先知道怎么把字符转成机器能保存的数据。这个规则，就是字符集。

常见字符集你会看到这些：

- `latin1`：偏西文，中文项目通常不合适
- `utf8`：MySQL 里常见，但有历史局限
- `utf8mb4`：更完整，现代项目更推荐

你先记住一句话：

> **字符集决定“能不能正确存和读”中文、表情和特殊符号。**

所以它不是装饰项，而是决定表能不能靠谱接住业务数据的基础配置。

### 2. 中文项目为什么不能随便选

因为中文业务里经常不止有汉字，还会有：

- 用户昵称：`老赵`
- 商品标题：`超值套餐 2 件装`
- 评论：`好用👍`
- 地址：`北京市朝阳区望京`
- 备注：`含税/不含税`

如果字符集选得不对，就可能出现：

- 中文显示异常
- 特殊字符无法保存
- 表情符号丢失
- 字节长度限制导致插入失败

所以，**中文项目不能只考虑“能存中文”，还要考虑“能不能稳定存各种真实业务文本”。**

### 3. 老赵给你的判断标准

建表前先问自己三个问题：

1. 这张表有没有中文？
2. 会不会出现表情、特殊符号？
3. 后续会不会和其他系统、接口、前端交换数据？

只要有中文业务，通常就不要再随便用老旧字符集了。现代项目里，更稳妥的选择通常是围绕 `utf8mb4` 来设计。

---

## 二、什么是排序规则，为什么会影响比较和排序？

### 1. 排序规则不只是“排序顺序”

很多人一听“排序规则”，就以为只是 `order by` 排一下顺序。其实不是。

**排序规则**更准确地说，是数据库在比较字符串时采用的规则。它影响的不只是谁排前谁排后，还包括：

- 字符串是否相等
- 大小写是否敏感
- 中文字符比较时的表现
- 唯一约束是否判定重复

比如：

- `abc` 和 `ABC` 算不算一样？
- `张三` 和 `张三 ` 算不算一样？
- 插入重复用户名时，数据库认为是不是同一个值？

这些都可能受排序规则影响。

### 2. 为什么它会影响比较和排序

因为数据库做这些事情时，底层都要按规则比较字符串：

- `where name = '老赵'`
- `order by name`
- `unique key` 判断是否重复
- `join` 两张表的字符串字段匹配

如果排序规则不合适，可能出现：

- 你以为是两个不同值，数据库却认为一样
- 你想区分大小写，结果没区分
- 排序结果不符合业务预期

所以别小看排序规则。它不是只有“排序”时才生效，**字符串比较、唯一约束、联表匹配都会碰到它。**

### 3. 初学阶段先抓住一个判断思路

> **字符集管“能不能存”，排序规则管“怎么比”。**

这个理解很重要。建表时最好一起考虑，而不是只选字符集不管排序规则。否则默认值一变，后面排查问题会很麻烦。

---

## 三、utf8 和 utf8mb4 的区别与实际选择建议

### 1. 它们看起来像，其实不一样

很多新手最容易踩的坑，就是把 `utf8` 和 `utf8mb4` 当成一回事。名字虽然像，但在 MySQL 里并不是完全等价的。

你先不用死抠底层细节，按本书语境理解就行：

- `utf8`：历史上常见，但能力不够完整
- `utf8mb4`：更完整，更适合现代中文和互联网业务

### 2. 为什么更推荐 utf8mb4

现实项目里，业务文本经常不止中文和英文，还可能有：

- emoji 表情
- 特殊符号
- 社交昵称
- 复杂输入内容

如果字符集不完整，就可能出现“有些字符存不进去”的问题。这个问题一旦上线，排查起来很烦，因为表面看是插入失败，根因却在字符集。

所以老赵给你的实战建议很简单：

> **只要不是非常特殊的历史兼容场景，新项目优先考虑 `utf8mb4`。**

### 3. 实际选择建议

#### 适合优先选 `utf8mb4` 的场景
- 中文网站
- 电商系统
- 内容平台
- IM、评论、昵称类业务
- 任何可能出现表情和复杂文本的系统

#### 需要谨慎的场景
- 老系统迁移，要兼容旧数据
- 已有历史字符集约束，不能随意改
- 第三方系统强制指定编码

### 4. 最实用的结论

如果你现在是入门阶段，记住这个就够了：

> **中文项目默认往 `utf8mb4` 想，除非有历史包袱。**

这是更接近真实生产环境的稳妥选择。

---

## 四、表级和库级字符集如何配合？

### 1. 字符集不是只写一次就完事

MySQL 里常见的层级有：

- 数据库级
- 表级
- 字段级（部分字段类型相关）

这意味着：**上层和下层最好统一，不要一边一个样。**

### 2. 库级和表级怎么配合

最稳的做法是：

- 数据库创建时统一字符集和排序规则
- 表创建时显式继承或再次指定
- 字段层面保持一致，不要混用奇怪编码

比如：

```sql
CREATE DATABASE shopdb
DEFAULT CHARACTER SET utf8mb4
DEFAULT COLLATE utf8mb4_general_ci;
```

然后建表时继续保持一致：

```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(50) NOT NULL
) DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci;
```

这样做的好处很直接：

- 避免不同表之间字符集不一致
- 避免 join 时字符比较出问题
- 后期维护更省心

### 3. 常见误区

#### 误区一：数据库是 utf8mb4，表随便写
不行。虽然数据库层有默认值，但你最好在建表时明确写出来，减少误会。

#### 误区二：只有中文字段才关心字符集
也不对。只要是字符串，最好统一管理。

#### 误区三：一张表里混几种字符集更灵活
实际更容易出问题。初学阶段先学会统一，再谈特殊场景。

---

## 五、建表时如何把字符集与排序规则写进去？

### 1. 标准建表写法

结合前面拆出来的业务模型，假设我们要建一张用户表，保存：

- 用户ID
- 用户名
- 手机号
- 备注
- 创建时间

可以这样写：

```sql
CREATE TABLE user (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '用户ID',
  username VARCHAR(50) NOT NULL COMMENT '用户名',
  phone VARCHAR(20) NOT NULL COMMENT '手机号',
  remark VARCHAR(200) DEFAULT NULL COMMENT '备注',
  create_time DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_phone (phone)
) ENGINE=InnoDB
DEFAULT CHARSET=utf8mb4
COLLATE=utf8mb4_general_ci
COMMENT='用户表';
```

这里把几个基础知识点都串起来了：

- `AUTO_INCREMENT`：主键自动增长
- `NOT NULL`：不能为空
- `DEFAULT`：默认值
- `UNIQUE`：手机号唯一
- `COMMENT`：注释
- `DEFAULT CHARSET`：字符集
- `COLLATE`：排序规则

这就是从业务模型走到建表 SQL 的正确姿势，不是零散背语法，而是组合使用。

### 2. 每一段分别干什么

- `DEFAULT CHARSET=utf8mb4`：告诉表使用什么字符集
- `COLLATE=utf8mb4_general_ci`：告诉表字符串怎么比较
- `COMMENT='用户表'`：给表加说明，方便别人看懂

如果你的项目里所有文字型表都统一用这个组合，通常会比较稳。

### 3. 什么时候要特别注意排序规则

如果业务有这些需求，要更关注排序规则：

- 用户名是否区分大小写
- 标签是否严格区分字符差异
- 重复校验是否要精确匹配
- 中文搜索、排序结果是否有特定要求

如果你只是做基础入门项目，先掌握“统一、稳定、少踩坑”就够了。后面业务复杂了，再根据需求细调。

## 六、老赵提醒：新手最容易忽略的几个坑

### 1. 不要数据库、表、字段各选各的

统一比“看起来高级”更重要。  
新手最怕的是一张表一个字符集，另一张表又不一样，最后联表查询和数据导入导出都麻烦。

### 2. 不要只看“能存中文”，还要看“能存完整文本”

中文只是开始，表情、特殊符号、业务备注、营销文案，都是实际场景。  
所以别偷懒，优先考虑更稳的字符集。

### 3. 不要忽略注释

字符集和排序规则本身就容易让人犯迷糊，所以表和字段注释一定要写。  
你自己半年后回来看，也能知道当初是怎么设计的。

### 4. 不要把“排序规则”当成可有可无

它不是装饰品。字符串比较、唯一约束、排序展示，都会碰到它。

### 5. 不要默认一切都“反正能跑”

能跑不代表能用，能用不代表稳定。  
建表这件事，最值钱的不是“写出 SQL”，而是“提前把坑堵上”。

现在有一个简单的商品表，要保存：

# 第6章 主键怎么设计：AUTO_INCREMENT 不是万能钥匙

## 开篇引入：先把“唯一身份”这件事想明白

前面咱们已经把业务模型拆得差不多了，比如用户、商品、订单这些基础表。真正落到建表时，**先要定的往往不是字段名，而是主键怎么设计**。

很多初学者一上来就写：

```sql
id BIGINT PRIMARY KEY AUTO_INCREMENT
```

这没错，而且很常见。但要记住：**不是所有表都适合这么干，也不是有了自增主键就万事大吉了。**

主键，说白了就是给表里的每一条记录发一张“身份证”。这张身份证必须满足两点：

1. **唯一**：不能重复。
2. **稳定**：最好一旦确定就不要改。

没有主键，表也能存数据，但后面查询、更新、删除、关联、去重、同步，都会别扭很多。

老赵先给你一句实话：**建表时把主键想明白，后面能少踩很多坑。**

---

## 一、什么是主键，为什么每张表最好都有主键

### 1. 主键到底是干什么的

主键就是一张表中用来唯一标识每一行数据的字段，或者字段组合。它最核心的作用有三个：

- **保证唯一性**
- **方便定位数据**
- **给关联表提供锚点**

比如用户表里有一条记录：

```text
id = 1001, username = "zhangsan"
```

后面订单表里存“这单是谁下的”，通常就保存 `user_id = 1001`，而不是直接存用户名。因为用户名可能改，`id` 通常不变，关联更稳。

### 2. 为什么每张表最好都有主键

实战里基本都建议每张基础业务表带主键，原因很直接：

- 没主键，重复数据不容易定位
- 没主键，更新删除更容易误伤
- 没主键，表关联不方便
- 很多同步、迁移、备份工具也更喜欢有主键的表

尤其是用户表、商品表、订单表这类核心表，主键几乎是标配。

### 3. 主键和唯一键不是一回事

别把它们混了：

- **主键**：一张表只能有一个，不能重复，不能为 `NULL`
- **唯一键**：可以有多个，也不能重复，但它不是“唯一身份”

简单记：

- 主键是“这张表最核心的身份证”
- 唯一键是“这个字段也不能重复，但它不是主身份”

---

## 二、AUTO_INCREMENT 是什么，适合什么场景

### 1. AUTO_INCREMENT 的意思

`AUTO_INCREMENT` 是 MySQL 里常见的自增属性。插入新记录时，如果这个字段没手动填，MySQL 会自动给你分配一个递增值。

典型写法：

```sql
CREATE TABLE user (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL
);
```

插入数据时：

```sql
INSERT INTO user(username) VALUES ('zhangsan');
INSERT INTO user(username) VALUES ('lisi');
```

MySQL 会自动给 `id` 分配值，比如：

- `1`
- `2`

这样就省去了手工维护编号的麻烦。

### 2. 它适合什么场景

自增主键最适合这类表：

- 单库单表或规模不大的业务表
- 主键只是内部编号，不需要对外展示
- 插入频繁、按主键查得多
- 主键不需要业务含义

比如用户表、商品表、订单表，用自增主键就很常见，也很适合入门。

### 3. 它不适合什么场景

自增主键不是万能钥匙，下面这些情况要小心：

- 分布式多库多表，可能出现冲突
- 需要全局唯一且可离线生成
- 要对外暴露、还带业务含义的编号，比如订单号、运单号
- 多系统合并数据时，自增值容易撞车

老赵提醒你：**自增主键更像数据库内部管理编号，不是万能业务编号。**

---

## 三、单字段主键和业务主键怎么取舍

### 1. 什么是单字段主键

单字段主键，就是主键只用一个字段，比如：

```sql
id BIGINT PRIMARY KEY AUTO_INCREMENT
```

这是最常见、最稳妥的基础方案。优点很明显：

- 简单
- 易读
- 关联方便
- 查询和维护省事

对入门读者来说，先把这种方案用熟，基本就能覆盖大部分基础建表场景。

### 2. 什么是业务主键

业务主键是指主键本身带有业务意义，比如手机号、商品编码、订单号。

例如：

```sql
CREATE TABLE product (
    product_code VARCHAR(32) PRIMARY KEY,
    product_name VARCHAR(100) NOT NULL
);
```

优点是字段一眼就懂，不用再额外设计一个无意义的 `id`。但问题也很明显：

- 业务字段可能会变
- 字段通常更长，索引更大
- 后续业务规则变动时很麻烦

比如手机号做主键，用户换号怎么办？商品编码规则改了怎么办？这些都会很头疼。

### 3. 怎么取舍

老赵给你一个实用标准：

#### 优先选单字段自增主键的情况
- 业务表
- 早期项目
- 需要快速开发
- 主键只用于内部关联

#### 考虑业务主键的情况
- 业务编码天然稳定
- 编码本身就是行业标准
- 这个字段不会改，且天然唯一

### 4. 更推荐的新手方案

多数情况下，建议：

- 主键用 `id`
- 业务唯一字段单独加 `UNIQUE`

比如用户表：

```sql
CREATE TABLE user (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '用户ID',
    username VARCHAR(50) NOT NULL UNIQUE COMMENT '用户名',
    phone VARCHAR(20) UNIQUE COMMENT '手机号',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间'
) COMMENT='用户表';
```

这样做的好处是：

- `id` 负责内部定位
- `username`、`phone` 负责业务唯一性
- 以后改用户名，不影响主键

这套思路非常适合基础建表。

---

## 四、主键与唯一性、查询性能之间的关系

### 1. 主键首先管唯一性

主键的第一职责不是“快”，而是“唯一”。

一张表设置了主键后：

- 同一个主键值不能插两次
- 主键字段不能为 `NULL`

这就保证了“身份证”不会乱。

### 2. 主键为什么也影响性能

MySQL 里主键和索引关系很深。你可以把主键理解成表数据的“主入口”。很多时候，按主键查数据会比较快，因为数据库能更精准地定位。

比如：

```sql
SELECT * FROM user WHERE id = 1001;
```

这类查询通常比全表扫描更高效。

所以主键虽然不是专门拿来“提速”的，但它的设计会直接影响后面的查询和关联效率。

### 3. 主键别选太长

主键越长：

- 索引越大
- 关联表存储成本越高
- 查询和维护开销通常也更大

所以如果没特殊需求，**优先选择短、稳定、简单的主键类型**。入门阶段常见的是 `INT` 或 `BIGINT`。

### 4. 常见误区

#### 误区一：主键越复杂越高级
不对，简单可靠更重要。

#### 误区二：主键就是为了防重复
不完全对，它还负责定位、关联、维护。

#### 误区三：有了自增主键，业务唯一性就不用管了
也不对。用户名、手机号、商品编码，还是要单独做唯一约束。

老赵提醒你：**主键是基础，不是全部。靠谱的表设计，通常是主键 + 唯一约束 + 合理字段设计一起上。**

## 五、用户表、商品表、订单表的主键设计示例

### 1. 用户表：内部用 `id`，业务字段单独约束

用户表一般要保存用户名、手机号、邮箱等信息。推荐这样设计：

```sql
CREATE TABLE user (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '用户ID',
    username VARCHAR(50) NOT NULL UNIQUE COMMENT '用户名',
    phone VARCHAR(20) UNIQUE COMMENT '手机号',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间'
) COMMENT='用户表';
```

这样设计的原因很简单：

- `id` 做主键，稳定好用
- `username` 和 `phone` 保证业务唯一
- 以后手机号变更，不影响主键
- 后续关联也方便

### 2. 商品表：商品编号和主键分开

商品表常见做法也是用自增主键：

```sql
CREATE TABLE product (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '商品ID',
    product_name VARCHAR(100) NOT NULL COMMENT '商品名称',
    product_code VARCHAR(50) NOT NULL UNIQUE COMMENT '商品编码',
    price DECIMAL(10,2) NOT NULL DEFAULT 0.00 COMMENT '价格'
) COMMENT='商品表';
```

这里的 `product_code` 是业务唯一字段，但不是主键。这样既保留了业务编号，又不把主键绑死在业务规则上。

### 3. 订单表：主键和订单号分开考虑

订单表最容易让人犯糊涂。很多人会问：订单号是不是就该当主键？

老赵的建议是：**内部主键和对外订单号最好分开。**

```sql
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '订单ID',
    order_no VARCHAR(32) NOT NULL UNIQUE COMMENT '订单号',
    user_id BIGINT NOT NULL COMMENT '下单用户ID',
    total_amount DECIMAL(10,2) NOT NULL DEFAULT 0.00 COMMENT '订单总金额',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间'
) COMMENT='订单表';
```

这样设计的好处是：

- `id` 方便数据库内部关联
- `order_no` 方便业务对外展示和查询
- 订单号规则变动时，不影响主键体系
- 订单明细表也能通过 `order_id` 关联主表

## 六、建表时怎么检查主键设计是否靠谱

你可以按这个清单判断：

- 这个主键是否唯一？
- 这个主键是否稳定，未来会不会改？
- 这个主键是否短小，便于索引？
- 这个主键是否适合做表关联？
- 这个字段是不是业务字段？如果是，未来变动风险大不大？
- 是否还需要给其他业务字段加 `UNIQUE`？

如果有一半答案不确定，老赵建议你先回到业务模型重新想一遍。别急着写 SQL，先把“这张表到底怎么认人”想清楚。

## 结尾小结：先把主键设计稳，再谈别的

这一章你只要记住一句话：

> **AUTO_INCREMENT 很好用，但它只是主键方案的一种，不是所有场景的标准答案。**

今天咱们把几个关键点捋清了：

- 主键的作用是唯一标识一条记录
- 每张基础业务表最好都有主键
- `AUTO_INCREMENT` 适合内部编号、单库业务表
- 单字段自增主键最适合入门和常规业务
- 业务主键不是不能用，但要看稳定性和变动风险
- 主键不等于唯一性全部，业务唯一字段还要配 `UNIQUE`
- 用户表、商品表、订单表更推荐“内部主键 + 业务唯一字段”的组合

### 老赵最后提醒你

1. **别一上来就拿业务字段硬当主键**，先想清楚它会不会变。
2. **别迷信自增主键万能**，分布式、对外编号、跨系统合并时要谨慎。
3. **别只盯着主键**，业务唯一约束同样重要。
4. **建表前先想模型，再写 SQL**，这是从入门走向实战的关键一步。

下一章咱们继续往下走，看看字段类型、默认值和约束怎么配合主键一起把表建稳。

# 第7章 约束先上手：NOT NULL、DEFAULT、UNIQUE 怎么配合用

上一章把表骨架搭好了，这章往前走一步：**建表时就把规则定好，别等脏数据进来了再补救**。很多空值、重复值、乱填值的问题，不是业务不清楚，而是表结构太宽松。

这章抓住三个最常用的约束：

- **NOT NULL**：这个字段不能空
- **DEFAULT**：如果不填，就给默认值
- **UNIQUE**：这个值不能重复

它们配合起来，能让表从“能存数据”变成“能管住数据”。

---

## 一、NOT NULL：哪些字段必须填？

NOT NULL 表示这个字段不能为空，插入时必须要有值。

**判断方法**：这个字段如果没值，业务还能不能正常往下走？

- **业务上必须知道的字段**：加 NOT NULL（如用户名、手机号、下单时间、商品名称、订单金额）
- **以后可能补录的字段**：先允许为空

`NULL` 和空字符串 `''` 不是一回事：NULL 是“没有值”，空字符串是“有值，但内容为空”。

**示例**：
```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(50) NOT NULL,
  mobile VARCHAR(20) NOT NULL
);
```

**三个常见坑 + 正确做法**：

**坑一：所有字段都加 NOT NULL**
- 后果：业务被迫传无意义的值，比如把备注填成“无”
- 正确做法：只有业务必须知道的字段才加

**坑二：以为 NOT NULL 等于不允许空字符串**
- 后果：`''` 照样能入库
- 正确做法：NOT NULL 只拒绝 NULL，筛空字符串得靠应用层

**坑三：指望数据库约束替代前端和后端校验**
- 后果：用户提交空值，数据库报错
- 正确做法：约束是底线保护，前端和后端校验才是第一道防线

### 老赵提醒
NOT NULL 管的是“有没有值”，不管“值好不好”。它只是第一道门。

---

## 二、DEFAULT：默认值该怎么设？

DEFAULT 的意思是：插入时如果没给这个字段赋值，就自动使用默认值。

**适用场景**：有明确初始状态、不填也能正常运行的字段，如账号状态默认启用、创建时间默认当前时间、订单状态默认待支付。

**示例**：
```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(50) NOT NULL,
  mobile VARCHAR(20) NOT NULL,
  status TINYINT NOT NULL DEFAULT 1
);
```

**常用类型**：数字 `0`、`1`，字符串 `'unknown'`，日期时间 `CURRENT_TIMESTAMP`。
```sql
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
```

**常见误区**：
- 把默认值当业务逻辑本身（如用户名默认“张三”）
- 默认值和业务含义冲突（如“是否审核通过”默认值设错）
- 默认值设太多，有些字段必须明确传入

### 老赵提醒
默认值代表“没传时，系统认为最合理的初始状态”，是对业务意图的预判。

---

## 三、UNIQUE：如何保证唯一性？它和主键有什么区别？

UNIQUE 表示这一列的值不能重复。

**适用场景**：业务上不能重复的字段，如手机号、邮箱、商品编码、身份证号。

**示例**：
```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(50) NOT NULL,
  mobile VARCHAR(20) NOT NULL UNIQUE,
  status TINYINT NOT NULL DEFAULT 1
);
```

**UNIQUE 和主键的区别**：

| 特性 | PRIMARY KEY | UNIQUE |
|------|-------------|--------|
| 作用 | 唯一标识一条记录 | 保证业务字段不重复 |
| 数量 | 一张表通常一个 | 一张表可以有多个 |
| 是否可为NULL | 不能 | 可以（但一般不建议） |
| 典型用途 | id | 手机号、邮箱、编码 |

**UNIQUE 和 NULL 的关系：一个常见的陷阱**

UNIQUE 约束允许 NULL 值，而且多个 NULL 值不视为重复。

```sql
CREATE TABLE test_unique (
  id INT PRIMARY KEY,
  phone VARCHAR(20) UNIQUE
);
INSERT INTO test_unique VALUES (1, NULL);  -- 成功
INSERT INTO test_unique VALUES (2, NULL);  -- 也成功，因为两个 NULL 不被视为重复
```

**正确做法**：业务上要求唯一且必填的字段，一律 `NOT NULL UNIQUE` 双重保障。

**常见误区**：
- 把手机号做成主键（主键最好稳定，手机号可能变）
- 把 UNIQUE 当成索引替代品（核心是“唯一性约束”）
- 一上来给太多字段加唯一约束（会让插入、导数、改数据都很别扭）

### 老赵提醒
主键是“我是谁”，唯一约束是“我不能和别人撞车”。职责不一样，别混用。

---

## 四、常见约束怎么搭配：非空 + 默认值 + 唯一

**典型组合**：
```sql
mobile VARCHAR(20) NOT NULL UNIQUE          -- 不能空，不能重复
status TINYINT NOT NULL DEFAULT 1           -- 不能空，默认启用
created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP  -- 不能空，默认当前时间
```

**完整用户表示例**：
```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '用户ID',
  username VARCHAR(50) NOT NULL COMMENT '用户名',
  mobile VARCHAR(20) NOT NULL UNIQUE COMMENT '手机号',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1启用，0禁用',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间'
) COMMENT='用户表';
```

**建表判断顺序**：
1. 这个字段是不是必须有？→ 加 NOT NULL
2. 如果没传，合理默认值是什么？→ 加 DEFAULT
3. 这个字段会不会重复？→ 加 UNIQUE
4. 它是不是表的身份标识？→ 考虑主键

**注意：约束对性能的浅层影响**

加约束会引入检查开销，但合理的约束对数据质量的保障远大于这点性能损耗。**不要为“炫技”加多余约束，但该加的不能省。**

### 老赵提醒
约束不是越多越好，而是越贴近业务越好。如果业务没要求邮箱唯一，就别硬加 UNIQUE。

---

## 五、从业务模型到建表：用户表实战拆解

**业务需求**：用户表至少存用户ID、用户名、手机号、状态、创建时间。

**思维过程**：
- **用户ID**：主键 + 自增 → `BIGINT PRIMARY KEY AUTO_INCREMENT`
- **用户名**：注册时必填 → `NOT NULL`；业务没要求唯一 → 不加 UNIQUE
- **手机号**：一人一手机，不重复，必填 → `NOT NULL UNIQUE`
- **状态**：默认启用，不能为空 → `NOT NULL DEFAULT 1`
- **创建时间**：自动记录，不能空 → `NOT NULL DEFAULT CURRENT_TIMESTAMP`

**建表 SQL**：
```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '用户ID',
  username VARCHAR(50) NOT NULL COMMENT '用户名',
  mobile VARCHAR(20) NOT NULL UNIQUE COMMENT '手机号',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1启用，0禁用',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间'
) COMMENT='用户表';
```

## 六、查看、修改、删除：约束建完了，怎么检查和调整？

**查看表结构**：
```sql
DESC user;                      -- 快速看字段
SHOW CREATE TABLE user;          -- 看完整建表语句
```

**加默认值**：
```sql
ALTER TABLE user MODIFY status TINYINT NOT NULL DEFAULT 1;
```

**加唯一约束**（注意：已有重复数据会报错）：
```sql
ALTER TABLE user ADD UNIQUE uk_mobile (mobile);
```
解决方法：先查重复数据 `SELECT mobile, COUNT(*) FROM user GROUP BY mobile HAVING COUNT(*) > 1;`，清理后再加。

**加 NOT NULL**（注意：已有 NULL 值会报错）：
```sql
ALTER TABLE user MODIFY mobile VARCHAR(20) NOT NULL;
```
解决方法：先查 NULL 数据 `SELECT * FROM user WHERE mobile IS NULL;`，补值后再加。

**删除唯一约束**：
```sql
ALTER TABLE user DROP INDEX uk_mobile;
```

**删除表**：
```sql
DROP TABLE user;    -- 测试环境可练，生产别乱动
```

### 老赵提醒
改表前先看现有数据，尤其是加 UNIQUE 或 NOT NULL。先把数据清干净，再动手。

## 七、小案例练习：给“会员表”补约束

### 练习一：补全约束

```sql
CREATE TABLE member (

  nickname VARCHAR(50),
  phone VARCHAR(20),
  level TINYINT,
```

业务需求：nickname 必填，phone 必填且唯一，level 默认1（普通会员），status 默认启用。

**参考答案**：
```sql
CREATE TABLE member (

  nickname VARCHAR(50) NOT NULL COMMENT '昵称',

  status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1启用，0禁用'

```

### 练习二：从零设计约束

**业务描述**：商品表，商品编码唯一，名称必填，价格必填，库存默认0，上架状态默认“已下架”（0），创建时间自动记录。

**参考答案**：
```sql
CREATE TABLE product (
  id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '商品ID',
  product_code VARCHAR(50) NOT NULL UNIQUE COMMENT '商品编码',
  name VARCHAR(200) NOT NULL COMMENT '商品名称',
  price DECIMAL(10,2) NOT NULL COMMENT '价格',
  stock INT NOT NULL DEFAULT 0 COMMENT '库存',
  status TINYINT NOT NULL DEFAULT 0 COMMENT '上架状态：0已下架，1已上架',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间'
) COMMENT='商品表';
```

**自查清单**：
- 主键有没有设好？
- NOT NULL 加给了哪些字段？理由是什么？
- UNIQUE 只加给真正需要唯一的字段？
- 默认值是否代表“最合理的初始状态”？
- 注释有没有写清楚？

### 扩展思考
- phone 不加 UNIQUE → 同一个手机号能注册多个会员，业务就乱了
- status 不加 NOT NULL → 插入时可能为空，后面查状态就查不到
- level 不加 DEFAULT → 必须手动传值，少传就报错或留空

# 第8章 索引基础：不是越多越好，但该有的必须有

新手建表两个极端：完全不建索引，查询慢；到处加索引，写入变慢。**索引是给查询提速的工具，不是越多越好。**

---

## 8.1 索引入门：先记住这个比喻就够了

索引就像**书的目录**。MySQL 索引帮数据库快速找到数据，避免全表扫描。

MySQL 的 InnoDB 引擎默认用 **B+ 树** 组织索引：所有数据都存在叶子节点里，叶子节点之间有指针连接，方便范围查找。查数据时从根节点层层往下跳，几步找到目标行。

**做个数字推演**：一张用户表有100万行数据。没有索引时，查 `phone = '13800138000'` 最坏情况得读完100万行。有了B+树索引（假设高3层），只需要读大约10个节点就能定位目标。100万行 vs 10个节点，差距10万倍。

但索引不是免费的：插入、更新、删除时，索引也要同步维护。**每多一个索引，写入操作就要多维护一棵B+树。** 实测中，每多一个索引，写入速度大约下降10%-20%。5个索引的表，插入速度可能只有原来的一半。

**老赵提醒：** 索引提升查询效率，但占空间、拖慢写入。建表时想“这个字段以后会不会经常查”，别想“先全加上”。

---

## 8.2 三种索引，轻松搞明白

入门先搞清三种：**主键索引、唯一索引、普通索引**。

| 索引类型 | 是否允许重复 | 是否允许 NULL | 一张表可有几个 | 主要用途 |
|----------|--------------|----------------|----------------|----------|
| 主键索引 | 否 | 否 | 1个 | 唯一标识一行数据 |
| 唯一索引 | 否 | 可（但只能一个NULL） | 多个 | 业务唯一性约束+查询加速 |
| 普通索引 | 是 | 是 | 多个 | 纯查询加速，无约束 |

### 1. 主键索引：每张表最重要的那一个

```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(50),
  phone VARCHAR(20)
);
```
InnoDB 表**必须要有主键**，没有则 MySQL 会偷偷加隐藏 rowid，但性能不如自己设。

### 2. 唯一索引：不能重复，但不一定是主键

```sql
CREATE UNIQUE INDEX uk_user_phone ON user(phone);
```
主键只能有一个；唯一索引可以有多个。

### 3. 普通索引：最常见的查询加速工具

```sql
CREATE INDEX idx_order_user_id ON orders(user_id);
```

**场景判断简表：**
| 场景 | 推荐索引类型 | 举例 |
|------|-------------|------|
| 记录的唯一业务标识 | 唯一索引 | 手机号、订单号、身份证号 |
| 纯加速查询，允许重复 | 普通索引 | 用户ID、分类ID |
| 表必须有主键 | 主键索引 | 自增ID |

**老赵提醒：** 主键一定唯一，但唯一索引不一定是主键。建表时先确定主键，再看业务唯一约束，最后加普通索引。

---

## 8.3 建索引前，先想清楚三个问题

**1. 这个字段经常出现在查询条件里吗？** 比如 `WHERE phone = ...`  
**2. 区分度够不够高？** 性别区分度低，手机号区分度高  
**3. 这个字段频繁更新吗？** 经常修改的字段维护成本高

**拆解：手机号加索引**
- 经常在 WHERE 条件✅
- 几乎唯一，区分度高✅
- 一般不改✅
```sql
ALTER TABLE user ADD UNIQUE INDEX uk_user_phone (phone);
```

**拆解：订单号加唯一索引** 同样满足三条件：
```sql
ALTER TABLE orders ADD UNIQUE INDEX uk_order_no (order_no);
```

**外键字段：典型关联场景**
```sql
ALTER TABLE orders ADD INDEX idx_orders_user_id (user_id);
```

**反面案例：性别字段加索引** 只有两个值，100万行各占一半，查 `WHERE gender = 'M'` 仍扫50万行——和全表扫描没区别。

**老赵提醒：** 判断索引值不值：经常查？能缩小范围？很少改？全是肯定再加。

---

## 8.4 先别急着加：哪些字段不适合

### 1. 低区分度字段：加也白加
性别、状态等只有几个固定值，直接扫表可能更快。

### 2. 频繁更新的字段：维护成本高
`status`、`balance` 等每次改都要同步索引，写入压力大。

### 3. 不经常查的字段：浪费时间
**1个月内查询次数少于10次的字段**，基本不值得单独加索引。比如订单表的 `remark`，就先别加。

### 4. 字符串过长的字段：又大又慢
如 TEXT 类型、VARCHAR(2048)。索引越长，B+ 树节点能存数据越少。

**解决办法：** 用**前缀索引**，只取前几个字符：
```sql
CREATE INDEX idx_content_prefix ON article(content(10));
```

### 5. 索引成本量化提醒
每多一个索引，写入速度大约下降10%-20%。系统写操作占比超过30%，更要谨慎加索引。

**老赵提醒：** 别把“预防性加索引”当好习惯。尤其是长文本字段，轻易别加全字段索引。

---

## 8.5 复合索引与最左前缀原则

如果查询条件涉及多个字段，比如 `WHERE status = 1 AND created_at > '2024-01-01'`，单列索引只能加速其中一个条件。解决方案是**复合索引**。

```sql
CREATE INDEX idx_status_created ON orders(status, created_at);
```

**最左前缀原则：** 复合索引匹配时，必须从最左边第一个字段开始。`KEY idx_status_created (status, created_at)` 能匹配：
- `WHERE status = 1` ✅
- `WHERE status = 1 AND created_at > '2024-01-01'` ✅
- `WHERE created_at > '2024-01-01'` ❌（跳过了最左边status，不走索引）

**老赵提醒：** 复合索引的顺序很重要：区分度高、经常作为等值条件的字段放前面。写SQL时务必用最左前缀匹配。

---

## 8.6 覆盖索引与避免回表

普通索引流程：先查索引树找到主键值，再用主键值回主表查完整行。**如果索引树里已经包含了查询要的所有字段，MySQL就不用回表了**——这叫覆盖索引。

举例：`SELECT phone FROM user WHERE phone = '13800138000'`。如果 `phone` 上有唯一索引，索引树里已有 `phone` 值，MySQL直接返回。用 `EXPLAIN` 看，`Extra` 列显示 `Using index`。

**老赵提醒：** 查询时尽量只选需要的字段，别用 `SELECT *`。这样更可能触发覆盖索引。

---

## 8.7 查看和删除索引

**查看索引：**
```sql
SHOW INDEX FROM user;
```

**删除索引：**
```sql
DROP INDEX idx_status_created ON orders;
-- 或
ALTER TABLE orders DROP INDEX idx_status_created;
```

**老赵提醒：** 定期用 `SHOW INDEX FROM` 检查表里的索引，删除长期不用的冗余索引。

---

## 8.8 结合用户表和订单表示例

### 1. 用户表：手机号适合唯一索引
```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '用户ID',
  name VARCHAR(50) NOT NULL COMMENT '用户名',
  phone VARCHAR(20) NOT NULL COMMENT '手机号',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  UNIQUE KEY uk_user_phone (phone)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 2. 订单表：订单号唯一，用户ID普通索引，状态+时间用复合索引
```sql
CREATE TABLE orders (
  id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '订单ID',
  order_no VARCHAR(32) NOT NULL COMMENT '订单号',
  user_id BIGINT NOT NULL COMMENT '下单用户ID',
  amount DECIMAL(10,2) NOT NULL DEFAULT 0.00 COMMENT '订单金额',
  status TINYINT NOT NULL DEFAULT 0 COMMENT '订单状态',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_orders_user_id (user_id),
  KEY idx_status_created (status, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 3. 验证索引是否生效

用 **EXPLAIN** 命令：
```sql
EXPLAIN SELECT * FROM user WHERE phone = '13800138000';
```
结果 `type` 显示 `const` 或 `ref`，`key` 显示索引名，说明生效。显示 `ALL` 则是全表扫描。

**老赵提醒：** 建完索引记得用 EXPLAIN 验证，有时候 MySQL 觉得扫表更快，压根没用索引。

## 8.9 小案例练习

用户下单系统两张表：**用户表：** id, name, phone, gender, created_at  
**订单表：** id, order_no, user_id, status, amount, created_at

### 第一步：列出常见查询
1. 用户登录：`WHERE phone = ?`
2. 查询用户所有订单：`WHERE user_id = ?`
3. 根据订单号查订单：`WHERE order_no = ?`
4. 按状态+时间范围：`SELECT COUNT(*) FROM orders WHERE status = ? AND created_at > ?`
5. 金额范围查：`WHERE amount > 1000`

### 第二步：用三个问题判断

| 查询 | 经常查？ | 区分度高？ | 很少改？ | 结论 |
|------|---------|-----------|----------|------|
| 手机号 | ✅ | ✅ | ✅ | 加唯一索引 |
| 用户ID | ✅ | ✅ | ✅ | 加普通索引 |
| 订单号 | ✅ | ✅ | ✅ | 加唯一索引 |
| 状态+时间 | ✅ | 状态低，但联合后能缩小范围 | ✅ | 加复合索引 |
| 金额 | ❌ | ✅ | ❌ | 先不加 |

### 第三步：写出索引 SQL
```sql
ALTER TABLE user ADD UNIQUE INDEX uk_user_phone (phone);
ALTER TABLE orders ADD UNIQUE INDEX uk_order_no (order_no);
ALTER TABLE orders ADD INDEX idx_orders_user_id (user_id);
ALTER TABLE orders ADD INDEX idx_status_created (status, created_at);
```

**自检标准：** 主键唯一稳定✅；手机号唯一约束✅；外键加普通索引✅；复合索引覆盖高频联合查询✅；低区分度字段跳过单独索引✅；频繁更新字段跳过✅。

**练习建议：** 列出自己系统最常见的5个查询，按三步走判断。然后用 `SHOW INDEX FROM` 查看表里的现有索引，看看有没有可以删除的冗余索引。

## 8.10 本章小结

1. **索引能加快查询**，本质减少扫描范围，底层用 B+ 树组织
2. **主键索引、唯一索引、普通索引**各有用途
3. **判断加索引先问三个问题**：经常查？区分度高？很少改？
4. **索引不是越多越好**，每多一个索引，写入速度下降10%-20%
5. **低区分度、频繁更新、字符串过长的字段先别急着加**
6. **复合索引**应对多条件查询，注意最左前缀原则
7. **覆盖索引**能避免回表，查询时只选必要字段
8. **建完索引用 EXPLAIN 验证**，用 SHOW INDEX 查看，用 DROP INDEX 删除

**老赵提醒：** 索引堆得多不如用得准。定期回顾查询日志，动态调整索引策略，这才是一个合格全栈同学的素养。

# 第9章 从模型到表：订单表、商品表的完整建表实战

前面几章讲了数据库、表、字段、主键、数据类型、约束等基础。这一章直接上手：**把真实业务场景拆成表，再写成能跑的建表SQL**。

建表不是“先想SQL，再找业务”，而是反过来：**先看业务模型，再决定表怎么建**。很多新手一上来就问“主键用什么类型”，但连订单和商品该怎么分表都没想清楚，后面SQL写得再漂亮也容易返工。

本章拿电商下单场景练手，先把订单表、商品表建稳。

---

## 一、从业务模型到表的完整流程：先拆需求，再写SQL

以后遇到任何建表任务，按这个步骤来：

**第一步：列出业务中的核心名词**——比如“用户”“商品”“订单”，通常就是表的来源。

**第二步：列出每个名词的核心属性**——比如订单有“订单号”“金额”“状态”，这些就是字段。

**第三步：确定每张表的主键**——通常是一个`id`字段。

**第四步：为每个字段选类型**——金额用`DECIMAL`，状态用小整数，文本用`VARCHAR`或`TEXT`。

**第五步：加约束**——包括`NOT NULL`、`DEFAULT`、`UNIQUE`等。

**第六步：加必要的索引**——特别是查询频繁的字段。

**第七步：写建表SQL**——把上面的信息写成完整的`CREATE TABLE`语句。

很多新手会跳过前两步直接写SQL，结果就是字段漏了、类型错了、约束没加。

### 老赵提醒
建表前先想三个问题：
1. 这个对象是不是一张独立表？
2. 它最核心的属性有哪些？
3. 以后别的表要不要引用它？

---

## 二、订单表设计：从业务需求到字段选择

### 1. 业务拆解：订单有什么属性？

- 唯一的订单编号
- 属于某个用户，需要用户ID
- 总金额，涉及支付
- 状态变化（待支付、已支付、已发货、已完成、已取消）
- 创建时间和更新时间
- 可能含备注

### 2. 字段映射表

| 业务需求 | 字段名 | 类型 | 约束 | 说明 |
|--------|--------|------|------|------|
| 唯一标识 | `id` | `BIGINT UNSIGNED` | 主键、自增 | 数据库内部用 |
| 订单编号 | `order_no` | `VARCHAR(32)` | 非空、唯一 | 业务查单用 |
| 下单用户 | `user_id` | `BIGINT UNSIGNED` | 非空、加索引 | 关联用户表 |
| 订单总金额 | `total_amount` | `DECIMAL(10,2)` | 非空、默认0 | 精度重要 |
| 订单状态 | `status` | `TINYINT` | 非空、默认0 | 小整数够用 |
| 创建时间 | `created_at` | `DATETIME` | 非空、默认当前时间 | 自动填充 |
| 更新时间 | `updated_at` | `DATETIME` | 非空、自动更新 | 自动更新 |
| 备注 | `remark` | `VARCHAR(255)` | 可空 | 可选信息 |

两个注意点：
- **订单号和主键分开**。`id`给数据库内部用，`order_no`给业务用，这样更灵活。
- **金额用`DECIMAL`**。`FLOAT`或`DOUBLE`会有精度误差，金融场景不能接受。

### 3. 订单表完整SQL

```sql
CREATE TABLE `t_order` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `order_no` VARCHAR(32) NOT NULL COMMENT '订单号',
  `user_id` BIGINT UNSIGNED NOT NULL COMMENT '用户ID',
  `total_amount` DECIMAL(10,2) NOT NULL DEFAULT 0.00 COMMENT '订单总金额',
  `status` TINYINT NOT NULL DEFAULT 0 COMMENT '订单状态：0待支付 1已支付 2已发货 3已完成 4已取消',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `remark` VARCHAR(255) DEFAULT NULL COMMENT '备注',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_order_no` (`order_no`),
  KEY `idx_user_id` (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='订单表';
```

### 4. 常见错误写法对比

**错误一：金额用浮点数**
```sql
total_amount FLOAT NOT NULL COMMENT '订单总金额'
```
0.1存进去可能变成0.099999994，对账永远对不上。

**错误二：订单号直接做主键**
```sql
PRIMARY KEY (`order_no`)
```
字符串类型主键会让关联查询变慢。

**错误三：状态字段没有默认值**
```sql
status TINYINT NOT NULL COMMENT '订单状态'
```
插入时如果不指定状态会报错，最好给个合理的默认值。

### 老赵提醒
- 金额别用`FLOAT`、`DOUBLE`
- 订单号别直接拿主键充当业务单号
- 状态字段别写成一堆字符串，初学用整数更稳
- `created_at`、`updated_at`建议一开始就加好

## 三、商品表设计：类型选择和约束的实战应用

### 1. 业务拆解：商品有什么属性？

- 商品名称（文本）
- 价格（精确数字）
- 库存（整数）
- 状态（上架/下架）
- 描述（长文本）
- 创建时间和更新时间

### 2. 字段映射表

| 业务需求 | 字段名 | 类型 | 约束 | 说明 |
|--------|--------|------|------|------|
| 唯一标识 | `id` | `BIGINT UNSIGNED` | 主键、自增 | 内部用 |
| 商品名称 | `product_name` | `VARCHAR(100)` | 非空 | 名称不能为空 |
| 商品价格 | `price` | `DECIMAL(10,2)` | 非空、默认0 | 精度重要 |
| 库存 | `stock` | `INT UNSIGNED` | 非空、默认0 | 正整数 |
| 状态 | `status` | `TINYINT` | 非空、默认1 | 1上架 0下架 |
| 描述 | `description` | `TEXT` | 可空 | 长文本 |
| 创建时间 | `created_at` | `DATETIME` | 非空、默认当前时间 | 自动填充 |
| 更新时间 | `updated_at` | `DATETIME` | 非空、自动更新 | 自动更新 |

### 3. 和订单表的差异

- 订单表有业务单号，商品表没有
- 商品表有库存，订单表没有
- 订单表状态值更多（0-4），商品表更简单（0或1）
- 商品描述用`TEXT`，`VARCHAR(255)`可能不够

### 4. 商品表完整SQL

```sql
CREATE TABLE `t_product` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `product_name` VARCHAR(100) NOT NULL COMMENT '商品名称',
  `price` DECIMAL(10,2) NOT NULL DEFAULT 0.00 COMMENT '商品价格',
  `stock` INT UNSIGNED NOT NULL DEFAULT 0 COMMENT '库存',
  `status` TINYINT NOT NULL DEFAULT 1 COMMENT '商品状态：1上架 0下架',
  `description` TEXT DEFAULT NULL COMMENT '商品描述',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  KEY `idx_status` (`status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='商品表';
```

### 5. 常见错误写法对比

**错误一：价格用整型**
```sql
price INT NOT NULL COMMENT '商品价格'
```
99.99存进去会变成99。

**错误二：库存没有默认值**
```sql
stock INT UNSIGNED NOT NULL COMMENT '库存'
```
插入时必须显式指定，给默认0更合理。

**错误三：描述用太短的VARCHAR**
```sql
description VARCHAR(50) NOT NULL COMMENT '商品描述'
```
50个字符基本不够，应该用`TEXT`或至少`VARCHAR(1000)`。

### 老赵提醒
商品表最容易犯的错：`price`用浮点数或整型、`stock`没有默认值、描述字段一律写很短的`VARCHAR`。**字段类型不是越大越好，而是越贴合业务越好。**

## 四、表间关联的基本思路

### 1. 为什么订单表要有`user_id`？

如果存“用户名”而不是用户ID，会带来两个问题：
- **数据冗余**：用户改名后所有历史订单都得改
- **关联困难**：没法高效查找某个用户的所有订单

关联字段的设计原则：
- 存主键值（数字ID），不存文本信息
- 类型必须和被关联表的主键一致
- 在这个字段上加索引，提高查询效率

### 2. 订单表和商品表的关系

一个订单可能含多个商品，最简单的方案是在订单表加`product_id`。但一个订单买多个商品时放不下，需要“订单明细表”——一张专门记录订单和商品对应关系的表。本章先不展开，但要记住：**“一对多”关系通常需要中间表。**

### 3. 为什么现在不强制加外键？

外键会影响性能，很多实际项目在代码层面处理关联逻辑。你的学习重心应该是**理解关联字段的意义**，而不是把约束加到最死。

### 老赵提醒
别把“关联字段”和“外键约束”混为一谈。有关联字段不代表一定要加外键，但没有关联字段，后面很多业务查询就没法展开。

---

- `book_id`（`BIGINT UNSIGNED`，非空、加索引）
- `quantity`（`INT UNSIGNED`，非空、默认1）
- `total_amount`（`DECIMAL(10,2)`，非空、默认0）
- `status`（`TINYINT`，非空、默认0）
- `created_at`

### 检查清单
- [ ] 主键是否唯一且稳定？
- [ ] 金额字段是否用了`DECIMAL`？
- [ ] 库存和数量是否用了整数类型？
- [ ] 状态字段是否有默认值？
- [ ] 关联字段是否和对应表的主键类型一致？
- [ ] 订单号是否加了唯一约束？

## 本章小结：先看业务，再写SQL

核心观念：**建表是把业务模型翻译成数据库结构**。

记住今天的核心点：
- **建表流程**：拆业务名词→列字段→选类型→加约束→写SQL→检查
- **订单表关键**：订单号与主键分开，金额用`DECIMAL`，状态给默认值
- **商品表关键**：价格用`DECIMAL`，库存用`INT UNSIGNED`，描述用`TEXT`
- **表间关联**：在订单表里放`user_id`，类型和用户表主键一致，加索引
- **修改表**：用`ALTER TABLE`添加、修改、删除字段，用`DROP TABLE`删除表（谨慎）
- **检查**：建表后用`DESC`和`SHOW CREATE TABLE`确认

# 第10章 建表后别急着跑：查看表结构、修改表结构、删除表

前面咱们已经把一张表“造”出来了，但老赵得提醒你一句：**表建完，不代表活儿干完了。**  
真实项目里，表结构往往不是一锤子买卖，后面还会不断调整。

比如业务临时加需求，字段类型选错了，表名字段名起得不清楚，测试库里建错了表，或者设计评审后发现和业务模型对不上，这些都很常见。

所以这一章，咱们就讲三件最常用的事：

1. 怎么查看表结构，确认建得对不对  
2. 怎么修改表结构，补字段、改字段、删字段  
3. 怎么安全删除表，避免误操作把数据一锅端

你可以把这一章理解成：**表建完之后的“体检、修补和收尾”。**

## 一、如何查看表结构：`DESCRIBE`、`SHOW CREATE TABLE`

建完表以后，第一件事不是急着插数据，而是先看一眼：**这张表到底长什么样？**

### 1. `DESCRIBE`：快速看字段清单

```sql
DESCRIBE users;
```

或者：

```sql
DESC users;
```

它会列出字段名、数据类型、是否允许为空、键类型、默认值和额外信息。  
这个命令的特点就两个字：**快、直观**。适合刚建完表，或者临时确认某个字段是不是你记忆中的样子。

#### 适合什么场景？

- 刚建完表，快速确认字段有没有漏
- 记不清字段类型时先看一眼
- 排查插入失败时，看看是不是 `NOT NULL` 或默认值的问题
- 快速了解一张陌生表

### 2. `SHOW CREATE TABLE`：看完整建表语句

```sql
SHOW CREATE TABLE users;
```

它会把 MySQL 实际保存的建表 SQL 展示出来，包括字段定义、主键、索引、字符集、排序规则、注释和引擎。  
如果说 `DESC` 是看“体检报告”，那 `SHOW CREATE TABLE` 就是看“原始设计图”。

#### 这个命令的价值

- 排查建表语句是否按预期生效
- 方便迁移表结构
- 方便复制表结构到别的环境
- 核对索引、约束、注释是否完整
- 看看字符集和排序规则是不是你想要的

### 老赵提醒

- `DESC` 适合快速看字段，**上手快**
- `SHOW CREATE TABLE` 适合看完整结构，**不容易漏细节**
- 建表后，先看结构再写业务代码，这是好习惯

**别嫌这一步慢，很多线上问题，都是因为“以为建对了”。**

---

## 二、怎么判断表结构是不是符合预期

会看表结构只是第一步，更关键的是：**你得知道怎么看对不对。**

老赵给你一个简单判断法：  
**从业务需求倒着检查表结构。**

### 1. 先问自己：这张表要解决什么业务问题？

还是拿用户表举例。用户表通常要做这些事：

- 存用户基本信息
- 支持登录或注册
- 区分用户状态
- 后续还能方便扩展
- 以后要能查得快、改得稳

那你就要反过来检查表结构：

- 主键有没有？
- 必填字段有没有设 `NOT NULL`？
- 经常查询的字段有没有考虑索引？
- 字段类型是不是合适？
- 默认值有没有设置？
- 注释有没有写清楚？

### 2. 一张表建完后看什么

#### 第一项：主键是否明确

一般来说，业务表最好都有一个清晰的主键，比如：

```sql
id BIGINT PRIMARY KEY AUTO_INCREMENT
```

这样后面查数据、改数据、关联其他表，都会顺手很多。

#### 第二项：字段类型是否合适

这个特别容易出问题：

- 年龄用整数，不要用字符串
- 金额用数值类型，不要用 `VARCHAR`
- 时间用日期时间类型，不要硬塞文本
- 手机号通常更适合字符串，不要随便当数字处理
- 邮箱、身份证号这类字段，也常常适合字符串

字段类型一旦选错，后面补救虽然能改，但麻烦会大很多。

#### 第三项：是否该非空的都设了 `NOT NULL`

像用户名、手机号、创建时间、状态这类字段，通常就不该随便为空。  
如果允许为空，业务代码就得处处判断，维护起来会很累。

#### 第四项：默认值是否合理

默认值的作用是：**让常见情况不用每次都手动传。**

比如：

- 状态字段默认启用
- 创建时间默认当前时间
- 订单状态默认待支付

#### 第五项：注释是否足够清楚

- 字段注释要让别人看懂
- 表注释要说明这张表是干什么的

你今天看得懂，不代表三个月后还能看懂。注释是真正的“维护说明书”。

#### 第六项：字符集和排序规则是不是统一

这个点也别忽略。至少要做到：

- 文本字段别乱用默认值，尽量统一风格
- 如果项目规定了统一字符集和排序规则，新增或修改表时要保持一致

### 3. 常见不符合预期的信号

如果你看到下面这些情况，就要警惕了：

- 字段名看不懂，比如 `a1`、`field_x`
- 某个字段应该唯一，但没加 `UNIQUE`
- 该必填的字段允许为空
- 类型太宽松，比如把所有内容都建成 `TEXT`
- 该有索引的字段没加，后面查起来慢
- 表注释和字段注释写得含糊，别人看不明白

### 老赵提醒

别以为“能建出来”就等于“建对了”。  
**建表的正确标准，不是 SQL 能执行，而是结构能支持业务。**

## 三、字段漏了、默认值错了、注释不清楚：怎么改表

表建完以后，业务需求往往还会变。这个时候就要学会改表，而不是一味重建。

MySQL 改表最常见的就是三种：**加字段、改字段、删字段**。  
但老赵先说一句：**改表不是拍脑袋，先看数据，再看影响。**

### 1. 添加字段：`ALTER TABLE ... ADD COLUMN`

比如用户表后来要加一个“头像地址”字段：

```sql
ALTER TABLE users
ADD COLUMN avatar_url VARCHAR(255) DEFAULT NULL COMMENT '头像地址';
```

#### 适合场景

- 业务新增信息项
- 表结构初版漏了字段
- 要支持后续扩展

#### 注意什么？

加字段虽然简单，但也别随便先占着。字段一多，表会越来越臃肿，后面维护也麻烦。  
所以老赵的建议是：**先确认业务真的需要，再补。**

### 2. 修改字段：`ALTER TABLE ... MODIFY COLUMN`

如果字段类型、默认值、是否允许为空要变，用 `MODIFY COLUMN`。

比如原来 `nickname` 允许为空，现在要求不能为空：

```sql
ALTER TABLE users
MODIFY COLUMN nickname VARCHAR(50) NOT NULL COMMENT '昵称';
```

再比如，原来年龄建成了字符串，现在改成整数：

```sql
ALTER TABLE users
MODIFY COLUMN age INT UNSIGNED DEFAULT NULL COMMENT '年龄';
```

如果状态字段默认值不对，也可以改：

```sql
ALTER TABLE users
MODIFY COLUMN status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1启用 0禁用';
```

#### 注意

`MODIFY COLUMN` 是对字段定义整体调整，**不是只改一个小地方**。  
你改的时候，要把这个字段完整写清楚，别漏掉原本需要保留的属性。

#### 修改前先看数据影响

- 把字符串改成整数，老数据能不能转过来？
- 把允许为空改成 `NOT NULL`，空值怎么处理？
- 把默认值改了，后续新增数据会不会被误导？

老赵的经验是：**先看表里有没有历史数据，再决定怎么改。**

### 3. 删除字段：`ALTER TABLE ... DROP COLUMN`

如果某个字段确认不用了，可以删掉：

```sql
ALTER TABLE users
DROP COLUMN temp_flag;
```

#### 适合场景

- 需求废弃
- 字段设计错误，且确认没有数据依赖
- 测试字段不再需要

#### 要特别小心什么？

删字段不是删注释那么简单，它是真的把列去掉。  
所以删之前一定先确认：

- 有没有历史数据依赖
- 有没有业务代码在读这个字段
- 有没有报表、定时任务、接口还在用它

### 老赵提醒

- 加字段可以，但别乱加
- 改字段前，先确认有没有数据、有没有程序在用
- 删字段前，先确认这字段有没有被业务逻辑依赖
- 正式环境改表前，最好先做备份或至少确认可回滚

**改表不是改文档，改错了，影响的可能是线上数据。**

## 四、修改字段类型、默认值、注释的常见场景

真实开发里，最常改的往往就是三样：**类型、默认值、注释**。

### 1. 修改字段类型：避免“开始就选错”

#### 场景一：把年龄建成了字符串

```sql
age VARCHAR(10)
```

后来发现，年龄要做比较、统计平均值，那就不合适了。  
年龄本质上是数字，应该改成整数：

```sql
ALTER TABLE users
MODIFY COLUMN age INT DEFAULT NULL COMMENT '年龄';
```

#### 场景二：手机号别随便用数字类型

手机号通常更适合字符串，因为它可能有前导 0，可能带国家码，而且我们通常不对它做数学运算。  
所以很多时候：

```sql
phone VARCHAR(20) NOT NULL COMMENT '手机号'
```

比直接用整数更稳妥。

#### 场景三：名称、标题、备注别一上来就用太“重”的类型

商品名称、文章标题、留言备注，很多时候用 `VARCHAR` 就够了。  
别一上来就 `TEXT`、`LONGTEXT`，容易让表看起来很“胖”。

记住这个判断思路：  
**字段类型要按业务使用方式来选，不是按“看起来像什么”来选。**

### 2. 修改默认值：让插入更省心

默认值特别适合“业务上有默认状态”的字段。

比如状态字段：

```sql
ALTER TABLE users
MODIFY COLUMN status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1启用 0禁用';
```

这样插入数据时，如果不传 `status`，系统就默认启用。

### 3. 修改注释：让后人看得懂

注释看起来不起眼，实际上特别重要。  
因为很多时候，几年后回头看表的人，不是你自己，是别人。

比如：

```sql
ALTER TABLE users
MODIFY COLUMN remark VARCHAR(255) DEFAULT NULL COMMENT '备注信息';
```

#### 注释的价值

- 降低沟通成本
- 方便交接
- 方便排查问题
- 让表结构更像“文档”

### 老赵提醒

注释不是装饰品，是给后面的人留路。  
**字段没注释，等于把说明书撕了。**

## 五、`DROP TABLE` 删除表要注意什么，老赵提醒哪些坑不能踩

最后讲删除表。这个操作很简单，但也最危险。

```sql
DROP TABLE users;
```

这句的意思是：**把这张表整个删掉。**  
删完以后，表结构和数据都没了。

### 1. 什么情况下会删表？

常见场景有：

- 测试表建错了
- 临时表不再使用
- 旧表废弃，需要重建
- 开发环境清理垃圾表

前提是：**你真的确认可以删。**

### 2. 删除表前一定要确认的事

#### 第一：确认表名没写错

别把 `user_test` 写成 `users`，这种低级错误最冤。  
尤其在命令行里敲 SQL 的时候，一不小心少个字母，后果就很大。

#### 第二：确认这不是正式表

尤其在生产库里，删表前一定要再三确认。

#### 第三：确认数据是否要保留

如果表里有数据，删之前要想清楚：

- 需不需要备份
- 需不需要导出
- 需不需要先迁移到新表

#### 第四：确认程序没有依赖

有些表虽然看起来“没人用”，但实际上后台代码、报表任务、定时任务都可能在读它。  
表一删，别的地方就跟着出问题。

### 3. 更稳妥的习惯：先备份，再删除

如果你不确定表是不是还能用，老赵建议你先：

1. 导出结构或数据  
2. 再考虑删除

至少别在没备份的情况下，直接 `DROP TABLE`。

### 4. 删除表和删数据不是一回事

很多新手会混淆：

- `DROP TABLE`：整张表没了
- `DELETE FROM`：只删数据，表还在
- `TRUNCATE TABLE`：清空数据，表结构还在

这一章重点讲的是 `DROP TABLE`，它是**最彻底**的删除方式。  
所以你一定要记住：**删表不是清空，是直接销毁。**

### 老赵提醒

`DROP TABLE` 这条命令，别拿来练手感。  
**先确认，再执行；先备份，再删除；先想清楚，再敲回车。**

## 六、小案例练习：给用户表补字段、改字段、删字段

咱们拿一个简单的用户表来练习。假设当前表结构大概是这样：

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '用户ID',
  username VARCHAR(50) NOT NULL COMMENT '用户名',
  phone VARCHAR(20) NOT NULL COMMENT '手机号',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1启用 0禁用'
) COMMENT='用户表';
```

### 练习1：查看表结构

```sql
DESC users;
SHOW CREATE TABLE users;
```

重点看：

- `username` 是否 `NOT NULL`
- `status` 是否有默认值
- 表注释是否存在
- 主键和自增是否正确
- 字符集和排序规则是否符合项目统一规范

### 练习2：新增一个邮箱字段

业务要求：用户以后可以绑定邮箱。

```sql
ALTER TABLE users
ADD COLUMN email VARCHAR(100) DEFAULT NULL COMMENT '邮箱';
```

这里邮箱先允许为空，是比较合理的。  
因为不是每个用户注册时都一定会填邮箱。

### 练习3：把手机号字段注释补完整

```sql
ALTER TABLE users
MODIFY COLUMN phone VARCHAR(20) NOT NULL COMMENT '手机号';
```

### 练习4：把状态默认值修正一下

```sql
ALTER TABLE users
MODIFY COLUMN status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1启用 0禁用';
```

改完后，再 `DESC users;` 看一遍，确认默认值真的改对了。

### 练习5：删除一个废弃字段

假设之前加了个测试字段 `test_flag`，现在不用了：

```sql
ALTER TABLE users
DROP COLUMN test_flag;
```

删除前先确认：

- 有没有程序在用
- 有没有数据需要保留
- 会不会影响其他字段逻辑

### 练习6：误建测试表，直接删除

```sql
DROP TABLE users_test;
```

执行前先确认：

- 是不是测试库
- 有没有备份
- 这张表是不是后面还会用

# 第11章 注释、命名和建表习惯：让表结构一眼看懂

## 开篇引入：表能建出来，不代表别人看得懂

老赵先说句实话：**建表只是第一步，建得让人看懂，才算合格。**

很多人表能建、数据能插，就觉得自己会了。可过几天自己再看，或者换人接手，问题就来了：

- `user_name` 到底是用户名还是昵称？
- `status` 的 `0、1、2` 分别表示什么？
- `ct` 是创建时间还是别的时间？
- 表名叫 `t1`，谁知道它装什么？

所以，**命名、注释、排版**不是装饰，是基础功。入门阶段不一定设计得多高级，但至少要做到：**别人拿到表结构，能快速看懂这张表干什么、每个字段是什么意思、怎么用。**

这一章，老赵就带你把这件事讲明白：**表名怎么起、字段名怎么起、注释怎么写、建表 SQL 怎么排版、哪些坏习惯要避开。**

---

## 一、先把名字起明白：表名和字段名怎么起？

### 1. 表名：先说清这张表装什么

表名最核心的原则就一个：**一眼看出这张表存什么数据。**

比如前面拆过的业务，常见表名可以是：

- `user`：用户表
- `order_info`：订单信息表
- `product`：商品表
- `category`：分类表
- `article`：文章表

这些名字直观，业务含义清楚。反过来，`a1`、`tmp_user2`、`test_table` 这种，后面表一多，连自己都会忘。

表名最好保持**统一风格**。单数复数都行，但项目里别混着来。MySQL 入门阶段，老赵更建议统一用**下划线风格**，比如 `order_info`、`user_profile`，可读性最好。

### 2. 字段名：先表达业务，再考虑技术

字段名比表名更讲究，要求很简单：

- **短，但不含糊**
- **统一，不乱缩写**
- **能看出业务含义**

比如：

- `user_name`：用户名
- `mobile`：手机号
- `email`：邮箱
- `created_at`：创建时间
- `updated_at`：更新时间

这些名字一看就知道用途。像 `name1`、`phone_no1`、`time2` 这种，就很别扭。字段名不是拿来炫技的，是拿来让人快速理解的。

### 3. 坏命名 vs 好命名，一看就明白

| 坏命名 | 好命名 | 问题在哪 |
|---|---|---|
| `t1` | `user` | 看不出存什么 |
| `u_name` | `user_name` | 缩写不统一，容易猜错 |
| `ct` | `created_at` | 太短，不好理解 |
| `mobileNo` | `mobile` | 风格混乱，不统一 |
| `data1` | `article_title` | 没有业务含义 |
| `is_del` | `is_deleted` | 含义更完整 |

**好名字不一定更长，但一定更明确。**这是建表时最容易偷懒、也最容易埋坑的地方。

### 4. 命名要统一，别一会儿一种风格

很多人今天写 `userName`，明天写 `user_name`，后天又来个 `USER_NAME`，这就乱了。  
在 MySQL 建表里，最稳妥的还是**下划线命名**：

- 表名：`user`
- 字段名：`user_name`
- 时间字段：`created_at`、`updated_at`

好处很直接：

- 统一
- 可读性强
- 团队协作少混乱
- 后面写 SQL 更顺手

### 5. 避免模糊缩写和无意义名字

下面这些名字尽量别用：

- `u_name`
- `info1`
- `data`
- `time1`
- `xxx`

原因很简单：**看不出业务含义**。如果一个名字需要你猜，那它就不合格。

**老赵提醒：**  
命名不是越短越好，**是越清楚越好**。你今天看得懂，不代表三个月后还看得懂。

---

## 二、字段注释和表注释为什么必须写？

### 1. 注释不是装饰，是说明书

MySQL 支持给**表**和**字段**加注释，这个功能非常实用。因为很多时候字段名只能表达大概，业务含义还得靠注释补全。

比如订单表里的：

- `status`
- `pay_type`
- `source`

只看字段名，知道个大概，但不够精确。加上注释就清楚了：

- `status`：订单状态，1未支付 2已支付 3已取消
- `pay_type`：支付方式，1微信 2支付宝 3银行卡
- `source`：订单来源，1小程序 2APP 3后台创建

这样别人不用翻文档，直接看表结构就能用。

### 2. 表注释告诉别人整张表是干什么的

表注释就是整张表的摘要，比如：

- `用户信息表`
- `订单主表`
- `商品基础信息表`
- `文章内容表`
- `留言板表`

它的价值在于快速定位：这是一张主表、明细表、基础数据表，还是业务流水表。

### 3. 注释要和业务说明对上号

不是写一句“用户表”就完了。好的注释，尤其要说明**业务规则**。下面这些字段特别要写清楚：

- 状态字段
- 类型字段
- 来源字段
- 开关字段
- 码值字段

比如：

```sql
status TINYINT NOT NULL DEFAULT 1 COMMENT '用户状态，1正常 0禁用'
```

这条注释就很实用，因为它告诉你：

- 这个字段表示什么
- 有哪些值
- 每个值代表什么

再比如：

```sql
source TINYINT NOT NULL DEFAULT 1 COMMENT '来源，1小程序 2APP 3后台'
```

字段名负责“叫什么”，注释负责“什么意思”。这俩配在一起，才是真正能用的表结构。

### 4. 注释的价值，往往在维护时才看出来

刚建表时，你可能觉得注释可有可无。  
但等到：

- 自己半年后再看 SQL
- 别的同事接手
- 线上排查问题
- 写接口、写报表、写同步脚本

这时候你就会明白，注释能省多少事。

**老赵提醒：**  
**字段注释不是面子工程，是让系统可维护的基本动作。**

---

## 三、建表 SQL 的排版习惯：怎么写才清爽？

### 1. 好的 SQL，要让人顺着读下去

建表语句不要一股脑堆成一长串。正确做法是：**分层写，结构清楚。**

一般按这个顺序来：

1. 主键字段
2. 业务字段
3. 时间字段
4. 主键约束
5. 唯一约束、索引
6. 表注释、字符集等配置

这个顺序很符合阅读习惯：先看这张表是什么，再看主键，再看字段，最后看约束和表级设置。

### 2. 推荐的排版方式

```sql
CREATE TABLE user (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    user_name VARCHAR(50) NOT NULL COMMENT '用户名',
    mobile VARCHAR(20) NOT NULL COMMENT '手机号',
    email VARCHAR(100) DEFAULT NULL COMMENT '邮箱',
    status TINYINT NOT NULL DEFAULT 1 COMMENT '用户状态，1正常 0禁用',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_mobile (mobile)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户信息表';
```

这样写的好处很明显：

- 每个字段单独一行
- 字段顺序清楚
- 约束放后面
- 一眼能看出重点
- 后续修改也方便

### 3. 为什么不要写成一行？

```sql
CREATE TABLE user(id bigint not null auto_increment,user_name varchar(50) not null,mobile varchar(20) not null,primary key(id));
```

虽然能执行，但不适合维护：

- 字段挤在一起
- 逻辑不清楚
- 后面改表容易出错
- 自己回来看也费劲

SQL 写得清楚一点，不是浪费时间，是给后面省时间。

**老赵提醒：**  
SQL 不是越短越好，**越容易读懂越好**。写给数据库看是一回事，写给未来的自己看更重要。

---

## 四、常见坏习惯有哪些？你要尽量避开

### 1. 字段名看不懂

比如：

- `a1`
- `bb`
- `tmp`
- `data1`
- `xxx`

这些名字基本没有业务信息。后面查询、更新、联调都会很痛苦。

### 2. 一个字段塞太多意思

比如 `status` 里同时混了支付、发货、完成、取消、退款等流程，看起来像一个状态字段，实际业务边界却很乱。  
更好的做法是按业务拆分，或者至少把注释写清楚，避免误用。

### 3. 没有注释

没有注释的表，过一段时间就会变“猜谜表”。尤其这些字段一定要写清楚：

- 状态字段
- 类型字段
- 标志位字段
- 时间字段
- 金额字段
- 来源字段

### 4. 命名风格混乱

比如同一张表里同时出现：

- `user_name`
- `mobileNo`
- `CreateTime`
- `is_del`

这种混搭很不好。入门阶段，建议先把**下划线命名**练扎实。

### 5. 把临时想法直接写进正式表

很多人图快，先随便建，后面再改，结果越改越乱。  
正确做法是：先根据业务模型想清楚，再动手写 SQL。至少要明确：

- 这张表存什么
- 哪些字段必须有
- 哪些字段可以为空
- 哪些字段必须唯一
- 哪些字段要默认值

**老赵提醒：**  
别怕前期多想一点。建表不是抢时间，而是打地基。地基没打稳，后面改一次就多一次成本。

---

## 五、如何把一张表写得别人一看就懂？

老赵给你一个简单方法：**三看法**。

### 1. 看表名：知道管什么

比如 `user`、`order_info`、`product`、`article`，你一看就知道大致业务范围。

### 2. 看字段名：知道有哪些数据

比如：

- `id`
- `user_name`
- `mobile`
- `status`
- `created_at`

你大概就能猜出这张表的结构。

### 3. 看注释：知道怎么用

比如：

- `status`：1正常 0禁用
- `mobile`：手机号，唯一
- `created_at`：创建时间

这样别人不用翻文档，也能直接理解。  
简单说，**表名负责“这是什么”，字段名负责“有什么”，注释负责“怎么用”。**

## 六、从业务模型到 SQL：来做一个完整小案例

### 业务需求

我们要建一张“文章表”，要求：

- 每篇文章有唯一 ID
- 文章标题不能为空
- 作者名不能为空
- 内容可以很长
- 发布状态默认是草稿
- 有创建时间和更新时间
- 要有表注释和字段注释
- SQL 要写得清楚

这次咱们不用用户表、订单表、商品表，换个文章表，避免你老看同一类例子，看多了也腻。

### 先整理表结构思路

先别急着写 SQL，先把业务拆开：

- 表名：`article`
- 主键：`id`
- 字段：
  - `title`
  - `author`
  - `content`
  - `status`
  - `created_at`
  - `updated_at`
- 约束：
  - `id` 主键自增
  - `title`、`author` 不能为空
  - `status` 默认 0
  - `content` 可以为空或者较长文本

这一步很关键。很多人一上来就写 SQL，写着写着才发现少字段、少约束、少注释，最后返工。

### 建表 SQL

```sql
CREATE TABLE article (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    title VARCHAR(200) NOT NULL COMMENT '文章标题',
    author VARCHAR(50) NOT NULL COMMENT '作者',
    content TEXT DEFAULT NULL COMMENT '文章内容',
    status TINYINT NOT NULL DEFAULT 0 COMMENT '发布状态，0草稿 1已发布',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (id),
    INDEX idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='文章信息表';
```

这个表里，`status` 字段后面顺手建了一个索引。你现在不用把索引想得太复杂，先记住一个简单原则：**经常拿来筛选的字段，可以考虑建索引**。  
比如文章列表页，经常按 `status` 查草稿、已发布，这个字段就挺适合做基础索引。

这个表的优点很明确：

- 命名清楚
- 注释完整
- 排版整齐
- 业务含义明确
- 结构一看就懂

以后你写别的表，也可以照这个思路：**先拆业务，再补字段，再加约束，最后加注释和表配置。**

**老赵提醒：**  
建表时别只盯着“能不能执行”，要多想一层：**这张表别人拿去用，能不能一下看懂。**

## 七、查看、修改、删除表：习惯也要统一

### 1. 查看表结构

常用命令：

```sql
DESC article;
```

或者：

```sql
SHOW CREATE TABLE article;
```

`DESC` 适合快速看字段，`SHOW CREATE TABLE` 适合看完整建表语句。前者像快照，后者像原始配方。

### 2. 修改表结构

如果某个字段名、类型、注释不合适，可以改。

新增字段：

```sql
ALTER TABLE article
ADD COLUMN summary VARCHAR(500) DEFAULT NULL COMMENT '摘要';
```

修改字段注释：

```sql
ALTER TABLE article
MODIFY COLUMN status TINYINT NOT NULL DEFAULT 0 COMMENT '发布状态，0草稿 1已发布';
```

实际工作里，建表后改结构很常见。关键是你要知道自己改了什么、为什么改、会不会影响旧数据。

### 3. 删除表

如果一张表确认不要了，可以删除：

```sql
DROP TABLE article;
```

**注意：删除表是大动作，数据会没。**

所以别一上来就 `DROP`，先确认有没有备份、有没有依赖，是不是只是想清空数据。很多新手把“删表”和“删数据”混在一起，这点要特别小心。

**老赵提醒：**  
改表之前先确认需求，删表之前先确认有没有备份。这个习惯很重要。

## 八、小案例练习：把“留言板表”改得更规范

### 业务需求

现在给你一张命名混乱的表，让你改得更像样一点：

```sql
CREATE TABLE t_msg (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    uname VARCHAR(50),
    tel VARCHAR(20),
    msg TEXT,
    st TINYINT NOT NULL DEFAULT 1,
    ct DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

### 先想几个问题

1. `t_msg` 这个表名清楚吗？
2. `uname`、`tel`、`msg`、`st`、`ct` 这些字段好懂吗？
3. 哪些字段应该加 `NOT NULL`？
4. 哪些字段该写注释？
5. 表注释能不能补上？

### 参考改法

```sql
CREATE TABLE message_board (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    user_name VARCHAR(50) NOT NULL COMMENT '留言人姓名',
    mobile VARCHAR(20) DEFAULT NULL COMMENT '联系电话',
    content TEXT NOT NULL COMMENT '留言内容',
    status TINYINT NOT NULL DEFAULT 1 COMMENT '状态，1正常 0隐藏',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    PRIMARY KEY (id),
    INDEX idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='留言板表';
```

这里你能看到，改动不只是改几个字段名字，而是把整个表结构都“讲明白”了：

- 表名更清楚
- 字段名更统一
- 注释更完整
- 排版更整齐
- 索引也更合理

这个练习的重点不是追求花哨，而是训练你形成一个习惯：  
**先从业务需求出发，再落到字段、约束、注释和排版。**

只要这个流程顺了，后面做用户表、订单表、商品表、咨询表、图书表，你都会轻松很多。

**老赵提醒：**  
练习的时候，别只改名字，**要一起改结构、改注释、改习惯**。这样才真有用。

## 结尾小结：让表结构不只是“能用”，还要“好懂”

这一章你要记住的，不是某一条语法，而是一套习惯：

- **表名、字段名要清楚统一**
- **表注释和字段注释尽量写全**
- **建表 SQL 要分行、分层、顺序清晰**
- **少用模糊缩写，少写看不懂的字段名**
- **从业务模型出发，再写 SQL**
- **查看、修改、删除表也要有规范意识**

如果你把这些习惯养成了，不管是用户表、订单表，还是文章表、留言板表、商品表、日志表，你都会轻松很多。

### 老赵最后送你一句话

**会建表不难，难的是把表建得规范、清楚、可维护。**  
你现在多花一点时间写清楚，后面维护时就能少踩很多坑。

### 本章小练习自检点

你改完一张表之后，自己可以检查三件事：

1. **表名能不能一眼看出业务**
2. **字段名能不能直接看懂，不用猜**
3. **注释能不能把业务规则讲清楚**

如果这三条都能过，那你这张表就已经比很多“能跑但难维护”的表强多了。

# 第12章 综合实战：从业务需求独立完成一张基础表

## 开篇引入：别再只会“抄 SQL”，咱们来完整做一遍

前面几章，咱们已经把建表要用的基础零件认了一遍：数据库、表、字段、主键、索引、数据类型、默认值、约束，还有字符集和排序规则。  
但很多读者会发现：**看懂了概念，真要从业务需求自己建表，还是会发懵。**

这很正常。看懂和会做，是两回事。  
这章咱们就从一个完整的小业务出发，把**需求分析 → 字段设计 → 类型和约束 → 建表 SQL → 查看和修改**完整走一遍。

老赵不想让你只会背语法，所以咱们用一个真实感很强的小例子，带你把一张基础表从无到有做出来。学完以后，你至少面对一张基础表，知道该怎么下手。

---

## 一、先看业务：这个表到底是干什么的？

### 1.1 业务场景：网站留言板

咱们做一个很常见的功能：**网站留言板**。  
用户提交留言，管理员后续查看和处理。

先别急着写 SQL，先把业务拆清楚。根据需求，可以整理出这些信息：

- 每条留言要有唯一编号
- 要记录留言人姓名
- 要记录留言内容
- 要记录联系电话，方便联系
- 要记录留言时间
- 系统默认记录留言状态，比如“未处理”
- 同一联系方式不希望重复提交太多次
- 字段最好有说明，后面维护方便

这一步很关键。**建表不是先想类型，而是先想业务要存什么。**

### 1.2 从业务翻译成表的目标

这个场景里，适合先建一张基础表，比如：

- 表名：`message_board`
- 用来存一条条留言记录

表名尽量做到两点：

1. 看得懂
2. 命名统一

别起成 `t1`、`data_table` 这种，后面自己都容易看懵。  
像 `message_board`，一眼就知道是留言板相关的数据。

老赵提醒：**表名一旦定下来，后面字段、约束、索引都围着它转。表名要清楚，别花里胡哨。**

---

## 二、先拆业务名词，再列字段

### 2.1 先列字段，再选类型

一个实用的方法是：**先列“业务需要什么”，再选“能装得下什么”。**

这个留言板表，可以设计这些字段：

- `id`：主键，留言编号
- `name`：留言人姓名
- `phone`：手机号
- `content`：留言内容
- `status`：处理状态
- `created_at`：创建时间
- `updated_at`：更新时间

字段不是越多越好，够用、清楚、方便查询才是第一目标。

### 2.2 常见字段类型怎么选

常用数据类型的思路很简单：

- `id`：整数型，常用 `BIGINT` 或 `INT`
- `name`：短文本，用 `VARCHAR`
- `phone`：手机号也用字符串，不要用整数，避免前导 0、`+86` 等问题
- `content`：内容较长，用 `TEXT`
- `status`：状态值很短，用 `TINYINT`
- 时间字段：用 `DATETIME` 或 `TIMESTAMP`

几个常见坑：

- 手机号不要用数值类型
- 姓名别定太短，`VARCHAR(10)` 往往不稳
- 内容字段别硬塞短字符串
- 状态字段适合用小整数

记住一句话：**字段类型不是越“高级”越好，而是越贴合业务越好。**

### 2.3 主键怎么设计

主键的作用很简单：**唯一标识一条记录**。

这里通常让 `id` 做主键，并配合 `AUTO_INCREMENT` 自动增长。这样每新增一条留言，数据库自动给编号，不用程序手动算。

主键设计的基本原则：

- 唯一
- 不能为空
- 尽量短
- 尽量稳定

留言板这种场景，用自增整数主键最合适。  
不要拿手机号、邮箱直接做主键，因为它们可能变，而且主键最好稳定，不要轻易改。

### 2.4 约束怎么加

这一块很多初学者容易漏。

- `NOT NULL`：不能为空
- `DEFAULT`：默认值
- `UNIQUE`：唯一，不能重复

看看哪些字段适合加：

- `name`：通常 `NOT NULL`
- `phone`：通常 `NOT NULL`，并加 `UNIQUE`
- `content`：通常 `NOT NULL`
- `status`：可设默认值，比如 `0` 表示未处理
- `created_at`：默认当前时间
- `updated_at`：默认当前时间，并自动更新

思路很简单：  
**业务上必须有的，加 `NOT NULL`；业务上有默认状态的，加 `DEFAULT`；业务上不能重复的，加 `UNIQUE`。**

### 2.5 索引基础怎么考虑

索引不是越多越好，但常用查询字段可以考虑加。

留言板常见查询是：

- 按手机号查留言
- 按状态查未处理留言
- 按创建时间倒序看最新留言

所以可以考虑：

- `phone` 做唯一约束，顺便保证不重复
- `status` 加普通索引
- `created_at` 视查询场景加索引

老赵提醒：**索引是给查询提速的，不是给表贴标签的。别什么字段都加。**  
如果字段很少查，或者表本身很小，乱加索引只会增加维护成本。

## 三、把业务设计成一张可用的基础表

### 3.1 写出完整 `CREATE TABLE` 语句

下面把业务思路落成 SQL。

```sql
CREATE TABLE message_board (
    id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '留言ID',
    name VARCHAR(50) NOT NULL COMMENT '留言人姓名',
    phone VARCHAR(20) NOT NULL COMMENT '联系电话',
    content TEXT NOT NULL COMMENT '留言内容',
    status TINYINT NOT NULL DEFAULT 0 COMMENT '处理状态：0未处理，1已处理',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    PRIMARY KEY (id),
    UNIQUE KEY uk_phone (phone),
    KEY idx_status (status),
    KEY idx_created_at (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='留言板表';
```

### 3.2 这段 SQL 里要看懂什么

- `CREATE TABLE`：创建表
- `ENGINE=InnoDB`：常用存储引擎
- `DEFAULT CHARSET=utf8mb4`：支持更完整的字符
- `COLLATE=utf8mb4_0900_ai_ci`：排序规则
- `COMMENT='留言板表'`：表注释
- 字段后面也可以加 `COMMENT`

### 3.3 字符集与排序规则为什么要写

很多人建表时只写字段，忘了字符集。  
中文系统里，建议优先考虑 `utf8mb4`，因为它比普通 `utf8` 更完整，能处理更多字符，包括表情和特殊符号。

排序规则会影响比较和排序。入门阶段不用死记规则名，但要知道：

- **字符集**决定“能存什么”
- **排序规则**决定“怎么比、怎么排”

老赵提醒：**入门阶段你不需要背一堆排序规则名字，但至少要知道建表时字符集别乱省，尤其是中文业务。**

## 四、建完以后怎么检查：别让错误躲在表里

### 4.1 查看表结构

建完表后，先看一眼结构，确认是不是你想要的。

```sql
DESC message_board;
```

或者：

```sql
SHOW CREATE TABLE message_board;
```

- `DESC` 适合快速看字段
- `SHOW CREATE TABLE` 适合看完整建表语句

建议养成习惯：**每次建完表都先查一下结构。**

### 4.2 自检清单：你写的表合不合格？

老赵给你一个最实用的检查清单，建完表后可以逐条对照：

1. 表名是否清楚，能不能一眼看出业务含义？
2. 主键是否稳定，是不是用 `id` 这种简单字段？
3. 主键是否唯一且非空，是否正确设置 `AUTO_INCREMENT`？
4. 手机号是否应该唯一，业务上能不能重复提交？
5. 姓名、内容、手机号是否该设 `NOT NULL`？
6. 状态字段是否有默认值，比如默认 `0` 表示未处理？
7. 字段类型是否合理，有没有用错？
8. 是否写了表注释和字段注释？
9. 是否加了必要索引，比如状态、时间字段？
10. 字符集和排序规则是否适合中文业务，是否统一？

这个清单很重要。你以后自己建表，完全可以照着问自己一遍。

## 五、常见错误修正：把不规范初稿改成可用表

### 5.1 错误初稿

有些同学会写成这样：

```sql
CREATE TABLE message_board (
    id INT,
    name VARCHAR(20),
    phone INT,
    content VARCHAR(100),
    status VARCHAR(10)
);
```

这份表可能能建，但问题不少：

- `id` 没有主键，也没自增
- `phone` 用了整数，手机号不合适
- `content` 太短，留言内容容易装不下
- `status` 用字符串，不如数字统一
- 没有 `NOT NULL`
- 没有默认值
- 没有唯一约束
- 没有注释
- 没有索引
- 没有字符集和排序规则说明

### 5.2 一步步修正

先修主键和自增：

```sql
id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT
```

再修手机号类型：

```sql
phone VARCHAR(20) NOT NULL
```

再把内容改成更合适的类型：

```sql
content TEXT NOT NULL
```

再给状态加默认值：

```sql
status TINYINT NOT NULL DEFAULT 0
```

再补唯一约束、索引、注释和字符集。  
这样一步步修下来，表就从“能凑合”变成“可长期使用”。

老赵提醒：**建表不是比谁写得快，而是看谁写得稳。初稿不完美没关系，关键是你要知道哪里不对、怎么改对。**

## 六、修改表结构、删除表：建完以后还能继续收拾

### 6.1 修改表结构

如果发现字段长度不对，或者想补一个字段，可以用 `ALTER TABLE`。

比如把 `name` 改长一点：

```sql
ALTER TABLE message_board
MODIFY name VARCHAR(100) NOT NULL COMMENT '留言人姓名';
```

比如新增一个邮箱字段：

```sql
ALTER TABLE message_board
ADD email VARCHAR(100) NULL COMMENT '邮箱';
```

入门阶段先记住：  
**表建错了不可怕，关键是你要知道怎么改。**

### 6.2 删除表

如果这张表是测试表，不要的情况下可以删掉：

```sql
DROP TABLE message_board;
```

老赵提醒：**删除表是不可逆的，执行前一定确认是测试环境还是正式环境。**

这一章我们做了一件很重要的事：**从业务需求出发，完整创建了一张基础表**。

这几个点你养成习惯了，后面不管换什么业务表，你都能稳稳落地。
