# 第1章 先别急着建表：从需求截图/原型里先看懂业务

很多同学拿到UI原型，第一反应就是“这个字段放哪张表？”老赵告诉你，先打住。一上来就盯字段，容易把页面信息全塞进一张表，结果字段乱堆、关系不清。

正确的起手式：**先看懂它到底在做什么业务。**

把原型当“业务地图”。地图没看明白就动手，后面必返工。靠谱做法是先搞清楚页面解决什么问题、用户要做什么、数据流向哪里，再进入拆表。

---

## 一、看原型就看这三件事：页面目标、用户动作、结果

先看三件事，别数输入框。

**1. 这个页面的目标是什么？**

页面是为了查、增、改，还是处理流程？比如头像、昵称、手机号加编辑按钮，大概率是**用户信息管理**；商品名称、价格、库存、上下架状态，目标是**管理商品数据**。目标明确了，背后就有存储需求。

**2. 用户在这里要做什么？**

常见动作：搜索筛选、新增编辑删除、详情查看、提交审核支付。按钮是“新增商品”“上架”“下架”，就是商品管理；“提交审核”“驳回”“通过”，就要考虑状态字段和审核记录。

**3. 操作完之后结果是什么？**

点“保存”进用户表，点“下单”生成订单、库存可能变化，点“提交审核”记录状态变化。结果决定数据要不要落库、怎么落库。

**口诀：先看目标、动作、结果，再谈字段。**

---

## 二、从标题、按钮、筛选项、列表列名里抓业务线索

原型里最值钱的是这些“业务词”。

**看标题**：直接告诉你业务域。“订单管理”暗示后面会有订单号、下单人、订单状态。

**看按钮**：代表核心操作。“上架”“下架”“发货”“退款”都是后续要处理的业务动作和状态变化。

**看筛选项**：最暴露数据结构。订单筛选有“订单号”“用户手机号”“订单状态”“下单时间”，订单表大概率要有这些字段。

**看列表列名**：就是数据展示清单。商品列表有商品名称、价格、库存、上架状态，商品实体已初步成型。出现“分类名称”，一般是关联出来的，不是直接存字符串。

## 三、识别页面类型：列表页、详情页、编辑页还是流程页

不同页面拆表思路不同。

- **列表页**：有筛选、分页、多条数据，任务是“查”。适合识别主业务对象、查询字段、状态字段。
- **详情页**：一条记录的完整展示，任务是“看”。适合识别对象属性、固定展示项、关联信息。
- **编辑页**：有表单输入和保存按钮，任务是“写”。适合识别必存字段、可空字段、校验规则。
- **流程页**：有提交、审核、通过、驳回，任务是“变状态”。注意状态字段设计、流程日志是否单独建表。

## 四、完整案例：用用户中心首页原型走一遍

### 原型示意

原型里有：
- 左侧菜单：个人资料、收货地址、账户安全、我的收藏
- 中间区域：头像、昵称、手机号、会员等级
- 按钮：编辑资料、修改手机号、管理地址
- 地址列表：收件人、联系电话、详细地址、默认地址

### 业务拆解

这页围绕**用户账号的个人中心管理**。至少两类业务：用户基础信息管理、用户扩展信息管理。“收货地址”是独立子业务，一个用户有多个地址，不能硬塞进用户主表。

**页面类型**：以编辑和查看为主的综合管理页，含多个子功能区域。

**业务边界**：
- 用户基础信息：头像、昵称、手机号、会员等级
- 用户扩展信息：收货地址、收藏

### 实体识别

核心实体：
- 用户（User）
- 用户地址（User Address）
- 用户收藏（Favorite）

字段来源：
- 用户：昵称、手机号、头像、会员等级、状态
- 地址：收件人、联系电话、省市区、详细地址、是否默认
- 收藏：用户ID、收藏对象ID、收藏时间

注意：“管理地址”是功能不是字段，“默认地址”是地址属性。

### 主键设计

建议：
- 用户表用 `id` 做主键
- 地址表用 `id` 做主键
- 收藏表用 `id` 做主键

别拿手机号做主键，它是业务字段，会变。

### 外键设计

关系：用户地址表 `user_id` 关联用户表 `id`；收藏表 `user_id` 关联用户表 `id`。一对多关系，用户表是主实体，地址表和收藏表是从实体。

### 表结构草案

```
users
  id, nickname, phone, avatar, member_level, status, created_at, updated_at

user_addresses
  id, user_id, receiver_name, receiver_phone, province, city, district, detail_address, is_default, created_at, updated_at

user_favorites
  id, user_id, target_id, target_type, created_at
```

### MySQL落库

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  nickname VARCHAR(50) NOT NULL,
  phone VARCHAR(20) NOT NULL,
  avatar VARCHAR(255),
  member_level TINYINT NOT NULL DEFAULT 1,
  status TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

CREATE TABLE user_addresses (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  receiver_name VARCHAR(50) NOT NULL,
  receiver_phone VARCHAR(20) NOT NULL,
  province VARCHAR(50) NOT NULL,
  city VARCHAR(50) NOT NULL,
  district VARCHAR(50) NOT NULL,
  detail_address VARCHAR(255) NOT NULL,
  is_default TINYINT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_user_id (user_id)
);

CREATE TABLE user_favorites (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  target_id BIGINT NOT NULL,
  target_type VARCHAR(20) NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_user_id (user_id)
);
```

**小结**：从原型到这一步，完成了业务边界识别、实体抽取、关系判断和基础建表。后续根据业务细节补字段、加索引、调类型。先把这一步走稳。

## 五、总结清单：拿到原型后先问的5个问题

1. 这个页面属于什么业务？
2. 用户最核心的动作是什么？
3. 这是列表页、详情页、编辑页还是流程页？
4. 哪些信息是主实体字段，哪些是关联信息？
5. 这页的结果最终要落到哪几张表里？

答不上来就先别写SQL。

## 六、常见错误提醒

- **错误1：把页面上所有字都当字段**。先判断属于“数据本体”还是“业务结果”。
- **错误2：不分页面类型直接拆表**。列表页、编辑页、流程页重点不同。
- **错误3：主键随便选**。基础表优先用`id`，业务编码做唯一约束。
- **错误4：外键关系不先想清楚**。用户、地址、收藏关系没想明白就建表，必返工。
- **错误5：急着追求大而全**。第一版目标是可开发、可落地。

---

## 结尾小结

记住一句话：**先看懂业务，再决定怎么拆表。**

从标题、按钮、筛选项、列表列名里抓线索，判断页面类型，再做业务拆解和实体识别。起手式练顺了，后面建表就轻松了。下一章，我们开始从业务拆解正式把识别出的实体转成完整表结构。

# 第2章 把页面拆开看：表单、列表、详情页各自透露什么表

## 开篇引入：先看页面在说什么，再想怎么建表

很多人拿到需求，第一反应就是先建表。正确顺序是：**先看页面，再拆业务，再找表**。

UI 原型会告诉你业务对象、字段来源、关系边界。你要判断：**谁是主角、谁是配角、哪些是重复信息、哪些是关系信息**。

本节核心：**表单看字段来源，列表看字段类型，详情页看主对象和附属对象**，最后用商品管理案例，拆出商品表、分类表、品牌表，并落到 MySQL。

---

## 一、表单看字段来源：每个控件都在告诉你该存什么

### 1. 输入框→基础文本字段

输入框对应自由填写内容：商品名称、昵称、手机号、备注。这类字段一般是字符串，直接标记为候选字段。注意：“商品描述”用 TEXT 类型；“订单编号”要考虑长度和唯一性。

### 2. 下拉框→字典值或关联对象

下拉框来自有限集合。两类：
- **字典值**：状态、性别、是否上架，用 tinyint 存储。
- **关联对象**：分类、品牌、部门、角色。下拉框显示“女装/男装”，背后是**分类表**；“华为/小米”对应**品牌表**。

下拉框在提醒你：值是有限的，不是任意输入；很可能不是文本，而是引用关系。

### 3. 单选框→状态、类型、开关

和下拉框本质类似，只是展示不同。常见于启用/禁用、是否推荐。用 tinyint 或枚举值。先想清楚：以后会不会扩展？会不会来自别的表？

### 4. 时间选择器→业务时间或系统时间

两类：
- **业务时间**：用户可选，如上架时间、预约时间。
- **系统时间**：自动生成，如创建时间、更新时间。数据库一定要留，否则排序、查询、审计都会麻烦。

### 实战方法：三步拆表单

按三列记录清单：
- **控件类型**：输入框、下拉框、单选框、时间选择器
- **字段名称**：如商品名称、分类、状态
- **字段归属**：属于哪张表？主表字段还是关联字段？

例：
- 输入框 → 商品名称 → 商品表字段
- 下拉框 → 分类 → 关联分类表
- 单选框 → 上架状态 → 商品表状态字段
- 时间选择器 → 上架时间 → 商品表业务时间

扫一遍，字段来源就清楚了。如果字段应引用对象，别当普通文本存。

---

## 二、列表看字段类型：展示字段、统计字段、状态字段

### 1. 列表页暴露“哪些字段必须落库”

列表展示的内容是最常用、最核心、最需要查询的信息。如商品列表：商品名称、分类、品牌、价格、库存、状态、创建时间。可拆出三类。

#### 展示字段
用户直接看到的内容：名称、编码、图片、价格。主表核心字段，必须落库。

#### 统计字段
系统算出来的：销量、浏览量、评论数。不一定一开始就单独建表，但必须识别出来，它决定是冗余存储、实时计算，还是做统计表。

#### 状态字段
决定记录所处阶段：草稿/已上架/已下架、启用/禁用。状态字段常参与筛选、权限控制，是最常查询、修改的字段之一。

### 2. 列表页帮你判断“主表字段还是关联字段”

列表中有“分类”“品牌”，要问自己：是文本还是引用？如果会被单独维护、在别处重复出现，就不要堆成字符串，而用 `category_id`、`brand_id` 外键。列表上显示的名称只是关联对象的展示属性，不是商品自己的数据。

---

## 三、详情页看主对象和附属对象：帮你看清数据边界

### 1. 主对象：这张表的“主角”

页面主角，如商品详情页的“商品”。特征：页面标题指向它；大部分字段围绕它；能独立增删改查。主对象就是最先要定下的主表。

### 2. 附属对象：挂靠主对象的“配角”

围绕主对象但不属同一张表的内容，如：主图、轮播图、规格参数、分类、品牌。
- 主图/轮播图可能是图片集合，需单独做图片表或用扩展字段。
- 分类和品牌是外键关联。
- 规格参数复杂时，可能需单独的规格表、SKU 表。

详情页帮你**把主对象和附属对象分层**，避免把所有信息塞进主表。

## 四、完整案例：商品管理页面拆出商品表、分类表、品牌表

### 1. 需求原型示意

- **列表页**：商品名称、分类、品牌、价格、库存、状态、创建时间
- **新增/编辑表单**：商品名称、商品编码、分类下拉、品牌下拉、售价、成本价、库存、上下架状态、主图、详情描述
- **详情页**：商品基本信息、所属分类、品牌信息、图片展示、商品状态、创建时间、更新时间

### 2. 业务拆解

管理三类业务对象：
1. **商品本身**
2. **分类**
3. **品牌**

商品是主线，分类和品牌是支撑线。主线落主表，支撑线独立成表。

### 3. 实体识别

**商品实体**：主实体。核心字段：商品名称、商品编码、分类 ID、品牌 ID、售价、成本价、库存、状态、主图、详情描述、创建时间、更新时间。

**分类实体**：独立实体。核心字段：分类 ID、分类名称、父级分类 ID、排序、状态、创建时间。

**品牌实体**：独立实体。核心字段：品牌 ID、品牌名称、品牌 Logo、状态、创建时间。

### 4. 主键设计

统一用自增 `id`。主键职责唯一：**唯一标识一条记录**。别把商品编码当主键，业务字段不稳定。**主键要稳，业务字段要活。**

### 5. 外键设计

商品表放 `category_id` 和 `brand_id`，是典型外键思路。是否加约束看团队规范，但逻辑上一定是关联字段。判断标准：不是描述信息；来自下拉框；能指向详情。满足这些条件，就是关联字段，不是普通文本。

### 6. 表结构草案

**商品表 `product`**：`id`、`product_name`、`product_code`、`category_id`、`brand_id`、`sale_price`、`cost_price`、`stock`、`status`、`main_image`、`description`、`created_at`、`updated_at`

**分类表 `product_category`**：`id`、`category_name`、`parent_id`、`sort_no`、`status`、`created_at`

**品牌表 `product_brand`**：`id`、`brand_name`、`logo`、`status`、`created_at`

### 7. MySQL 落库

```sql
CREATE TABLE product_category (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  category_name VARCHAR(100) NOT NULL,
  parent_id BIGINT DEFAULT 0,
  sort_no INT DEFAULT 0,
  status TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE product_brand (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  brand_name VARCHAR(100) NOT NULL,
  logo VARCHAR(255) DEFAULT NULL,
  status TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE product (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  product_name VARCHAR(200) NOT NULL,
  product_code VARCHAR(100) NOT NULL,
  category_id BIGINT NOT NULL,
  brand_id BIGINT NOT NULL,
  sale_price DECIMAL(10,2) NOT NULL DEFAULT 0.00,
  cost_price DECIMAL(10,2) NOT NULL DEFAULT 0.00,
  stock INT NOT NULL DEFAULT 0,
  status TINYINT NOT NULL DEFAULT 1,
  main_image VARCHAR(255) DEFAULT NULL,
  description TEXT DEFAULT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_category_id(category_id),
  INDEX idx_brand_id(brand_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## 五、总结清单：页面到表的映射检查表

### 1. 看表单
- 输入框：是不是基础文本字段？
- 下拉框：是不是字典值或关联表？
- 单选框：是不是状态、类型、开关？
- 时间选择器：是不是业务时间或系统时间？

### 2. 看列表
- 列名是不是核心展示字段？
- 哪些是状态字段？统计字段？
- 哪些只是展示，不一定要单独存？

### 3. 看详情页
- 谁是主对象？哪些是附属对象？
- 哪些字段应该拆表？做关联？

### 4. 看落库
- 主键是否统一？外键字段命名是否清晰？
- 是否避免字段乱堆？

## 六、常见错误提醒：别把页面所有信息都塞进一张表

### 错误 1：把下拉框值直接存成文本

存 `category_name` 导致分类改名后全表更新。应存 `category_id`。

### 错误 2：统计字段和业务字段混在一起

“销量”“浏览量”与基础信息混堆，没人知道哪些是录入、哪些是计算。

### 错误 3：详情页看到什么就存什么

全塞进商品表造成大杂烩，如 30 多个字段含分类名称、品牌名称，改分类名时全表更新。

### 错误 4：外键只会写不会想

知道写 `category_id`，但不知道为什么。**外键不是为了炫技，是为了表达关联。**

### 错误 5：字段命名不统一

有的叫 `cat_id`，有的叫 `categoryId`，有的叫 `category_id`。团队协作混乱。统一用 `snake_case` 风格。

## 结尾小结

记住一句话：**页面不是表，页面只是表的线索。**

拆页面的顺序：
1. 表单看字段来源
2. 列表看字段类型
3. 详情页看主对象和附属对象
4. 最后决定主键、外键和表结构

商品管理场景中，你已经能从 UI 拆出商品表、分类表、品牌表。这是从“页面”走到“表”的第一步。

### 行动建议

拿到页面，先做清单：
- 页面有哪些控件？
- 每个控件对应什么字段？
- 哪些字段是主表？哪些单独成表？
- 哪些是关联字段？

把这五个问题写清楚，数据库设计就不会乱。

# 第3章 业务拆解第一步：先找主对象，再找动作和规则

做数据库设计，最怕一上来就想着“我要建几张表”。方向一偏，字段越堆越乱，主键外键也容易歪。老赵建议你先学会从需求和页面里找**主对象**、**辅助对象**和**动作对象**。这一步抓准了，后面的实体识别、字段梳理、关系判断都会顺很多。

---

## 一、三类对象：用讲故事的方式理解

**主对象：这页最核心的“主角”**  
是需求里最重要的业务实体，通常也是列表页、详情页、编辑页围绕的东西。判断方法：页面里最常被展示、搜索、编辑、保存的对象。

**辅助对象：给主对象补充信息的“配角”**  
比如用户有收货地址，商品有分类，订单有配送信息。很多人只盯着主对象，把这些全塞进一张表，字段越堆越乱。

**动作对象：围绕业务发生的“结果记录”**  
是动作落地后产生的数据对象。下单后产生**订单**，支付后产生**支付记录**。记住：动作是流程，动作结果才是数据。别把“下单、发货、审核”直接当表名。

---

## 二、从业务词汇中提炼核心名词和动词：圈词找线索

看需求时，先抓**名词**和**动词**。

**名词对应实体候选**——用户、商品、订单、支付、地址、分类，先圈出来，再判断主角和辅助。

**动词对应流程和状态变化**——创建、审核、下单、发货、取消，告诉你业务有没有状态流转、哪些对象会新增记录。

老赵办法：**先圈名词，再圈动词。名词找表，动词找流程。**

---

## 三、完整案例：订单管理需求如何拆出对象

### 需求截图/原型示意
- 订单列表：订单号、用户、订单金额、状态、下单时间
- 订单详情：收货人、收货地址、商品明细、支付状态
- 操作按钮：创建订单、审核、发货、取消订单、查看支付记录

### 业务拆解：先找主对象
**订单**是主对象。列表页展示订单，详情页展开订单信息，所有按钮操作订单。

辅助和动作对象：
- **辅助对象**：用户、收货地址
- **动作对象**：订单项（下单结果）、支付记录（支付结果）

### 实体识别：把对象对应成表
- `orders`：订单表，主对象
- `users`：用户表，关联对象
- `order_items`：订单项表，动作结果对象
- `payment_records`：支付记录表，动作结果对象

注意：订单项不是字段，是独立实体。一张订单多个商品，不能全塞进订单表。

### 表结构草案：先搭骨架
**orders**
- id（主键）
- user_id（外键）
- order_no
- order_amount
- status
- created_at

**order_items**
- id（主键）
- order_id（外键）
- product_id
- product_name
- quantity
- price

**payment_records**
- id（主键）
- order_id（外键）
- pay_no
- pay_amount
- pay_status
- paid_at

**users**
- id（主键）
- username
- phone

先抓核心字段：编号、关联键、金额、状态、时间。别一开始就堆备注和扩展字段。

### MySQL落库：确认三件事再写SQL
1. 主对象是谁——订单
2. 有哪些关联对象——用户、订单项、支付记录
3. 动作后要不要留痕——下单、支付、发货都要留数据

手写建表清单：主表、明细表、记录表、主键、外键、状态金额时间字段。这份清单比直接敲SQL更重要。

---

## 四、总结清单：业务拆解四步法

1. **先找主对象**——看列表、详情、编辑页围绕谁展开
2. **再找辅助对象和动作对象**——配角有哪些，动作产生了什么数据
3. **圈名词和动词**——名词找实体，动词找流程和状态
4. **搭表骨架**——先列主表、关联表，再定主键、外键

---

## 五、常见错误提醒

**错误1：把流程当表名**——“下单”“发货”“审核”不是表名，先看会不会产生新数据对象。

**错误2：把订单项塞进订单主表**——一张订单多个商品，明细重复会让表变胖。拆成订单表和订单项表。

**错误3：只看页面按钮，不看业务对象**——按钮是动作入口，设计的是背后的数据实体。先问：按钮按下去，到底记录了什么东西？

**错误4：字段一股脑全堆进主表**——先分清主对象、辅助对象、动作对象，再决定放哪张表。

---

## 结尾小结

一句话：**先找主对象，再找动作和规则。**

从需求到数据库，第一步不是建表，而是把业务拆清楚。如果你手里已经有一个原型，别急着写 SQL，先拿笔把页面里的名词和动词圈出来，这就是你这次建表的起点。

# 第4章 实体识别实战：从名词里挑出真正该建表的对象

## 开篇引入：别一看到名词就想建表

很多同学做数据库设计，最常犯的毛病是：**看到一个名词，就想给它建表**。结果表越来越多，关系越来越乱。打开页面原型，里面全是名词：用户、角色、部门、标签、状态、手机号……哪个该拆成表？哪个该当字段？如果搞不清楚，设计出来的库表要么冗余严重，要么缺漏关键实体。

老赵先说结论：**不是所有名词都值得落表。** 真正要做的，是筛出“真的该建表”的对象。这个过程，就是实体识别。

本章按实战走：**先分清实体、值对象、枚举、统计项，再判断该不该独立成表，最后用“用户中心”完整走一遍。**

---

## 一、实体、值对象、枚举、统计项，一分钟分清

看到任何名词，先往这四个类别里套：

| 类别 | 核心特征 | 典型例子 | 要不要建表 |
|------|----------|----------|------------|
| **实体** | 有唯一身份，需要独立管理，有生命周期 | 用户、角色、订单、商品 | ✅ 建独立表，有主键 |
| **值对象** | 描述属性，不需要身份 | 地址、手机号、价格、颜色 | ❌ 一般做字段，复杂才拆子表 |
| **枚举** | 选项固定 | 性别、状态、订单类型 | ❌ 用枚举常量或字典表 |
| **统计项** | 计算结果 | 用户总数、今日新增 | ❌ 用统计表，不是业务实体 |

### 快速判断口诀

- **实体**：知道自己是谁，别人也要引它。比如“用户”有唯一ID，订单里会引用user_id。
- **值对象**：只描述长啥样，变了无所谓。比如“地址”改了，原记录不要求保留历史身份。
- **枚举和统计项**：不是业务主角，别硬拆成表。

> **实战提醒**：看到名词先归类，别急着写CREATE TABLE。

---

## 二、五问法判断名词是否独立实体

对每个候选实体名词，用五问法走一遍：

### 1）它能不能被单独描述？
- ✅ **正面案例**：用户有账号、昵称、手机号等独立属性。→ 实体
- ❌ **反面案例**：VIP只是一个等级标签，没有属性。→ 字段

### 2）它会不会被单独增删改查？
- ✅ **正面案例**：角色可以在后台新增、编辑、删除、授权。→ 实体
- ❌ **反面案例**：性别固定不变，不会单独新增选项。→ 字段或枚举常量

### 3）它有没有自己的主键？
- ✅ **正面案例**：商品需要主键被订单引用。→ 实体
- ❌ **反面案例**：用户状态只是一个编码，不需要主键。→ 字段

### 4）它会不会被多个对象引用？
- ✅ **正面案例**：部门被多个用户引用。→ 实体
- ❌ **反面案例**：手机号只属于一个用户，不会被其他实体引用。→ 字段

### 5）它变了以后，历史要不要保留？
- ✅ **正面案例**：订单状态变了，订单本身还是那个订单，需保留身份。→ 实体
- ❌ **反面案例**：用户昵称改了，旧昵称不需要保留身份。→ 字段

> **实战提醒**：每次看需求过一遍五问法，能筛掉大部分“伪实体”。

---

## 三、字段 vs 字典表 vs 枚举常量：选型指南

### 适合做字段
- 简单属性：昵称、手机号、邮箱
- 单值描述：性别（男/女/未知）、状态（启用/禁用）
- 不需要独立管理的短文本

**原则：一个字段尽量表达一个稳定含义。**

### 适合做字典表
- 选项可配置，业务方可能改文案
- 多个地方复用
- 需要后台维护，比如运营可以新增“冻结”状态

**举例**：用户状态字典表（1=正常，2=禁用，3=冻结），订单状态字典表（1=待支付，2=已支付，3=已发货，4=已完成，5=已退款）。

### 何时直接用枚举常量？
选项很少且固定。比如“男/女/未知”，业务方从不说“我们要新增一种性别”。用TINYINT即可。

**判断原则**：频繁变化、需后台维护 → 字典表；极少变化、业务固定 → 枚举常量。

> **老赵提醒**：能当字段的就别拆表，能当枚举的就别建字典。

---

## 四、完整案例：用户中心实体识别

### 需求原型示意
- 左侧菜单：用户管理、角色管理、部门管理、标签管理
- 用户列表：用户名、手机号、部门、角色、状态、标签
- 新增用户表单：账号、昵称、手机号、部门、角色、标签、状态
- 角色管理：角色名称、角色编码、权限范围
- 部门管理：部门名称、上级部门、排序
- 标签管理：标签名称、标签颜色

### 第一步：圈出所有名词
用户、角色、部门、标签、状态、手机号、账号、昵称、权限范围、上级部门、排序、标签颜色。

### 第二步：用四类对照表分类

| 名词 | 初步归类 | 理由 |
|------|----------|------|
| 用户 | 实体 | 有唯一身份，需增删改查 |
| 角色 | 实体 | 有名称和权限集合，需独立管理 |
| 部门 | 实体 | 树形结构，需维护 |
| 标签 | 实体 | 后台可新增、删除、配置颜色名称 |
| 状态 | 枚举/字典 | 只有几个固定值，不独立管理 |
| 手机号、账号、昵称 | 字段 | 描述用户属性，无独立身份 |
| 权限范围 | 字典描述 | 配置在角色表中 |
| 上级部门 | 字段（关联） | 部门表中自关联 |
| 排序 | 字段 | 部门表中排序号 |
| 标签颜色 | 字段 | 标签表中属性值 |

### 第三步：用五问法筛选候选实体

- **用户**：有独立身份 → 需单独增删改查 → 有主键 → 被角色、部门引用 → ✅ 实体
- **角色**：有名称和权限集合 → 需单独管理 → 被多个用户引用 → ✅ 实体
- **部门**：树形结构 → 被多个用户引用 → ✅ 实体
- **标签**：后台可维护、可新增删除 → ✅ 实体
- **状态**：属于用户属性，不被其他实体引用，不需要主键 → ❌ 字段/字典项

### 表结构草案

```sql
-- 用户表
CREATE TABLE sys_user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(100) NOT NULL,
  nickname VARCHAR(100) DEFAULT NULL,
  mobile VARCHAR(20) DEFAULT NULL,
  department_id BIGINT DEFAULT NULL,
  status TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- 角色表
CREATE TABLE sys_role (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  role_name VARCHAR(100) NOT NULL,
  role_code VARCHAR(100) NOT NULL,
  status TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- 部门表
CREATE TABLE sys_department (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  dept_name VARCHAR(100) NOT NULL,
  parent_id BIGINT DEFAULT NULL,
  sort_no INT NOT NULL DEFAULT 0,
  status TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- 标签表
CREATE TABLE sys_tag (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  tag_name VARCHAR(100) NOT NULL,
  tag_color VARCHAR(20) DEFAULT NULL,
  status TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- 用户角色关系表
CREATE TABLE sys_user_role (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  role_id BIGINT NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_user_role (user_id, role_id)
);

-- 用户标签关系表
CREATE TABLE sys_user_tag (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  tag_id BIGINT NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_user_tag (user_id, tag_id)
);
```

> **实战提醒**：关系表加唯一约束，防止重复分配。每个表都加status字段和created_at、updated_at时间戳。

## 六、常见错误提醒（附正确做法）

### 1）把“状态”当实体
- ❌ 错误：用户状态单独建表，用户表里存状态ID
- ✅ 正确：用户表直接放status字段（TINYINT），搭配字典表存储文案

### 2）把“临时标签”当实体
- ❌ 错误：给“本周活跃”建标签表
- ✅ 正确：先用统计查询实现，等业务稳定再考虑落表

### 3）把“描述信息”过度拆表
- ❌ 错误：地址中的省、市、区各拆一张表
- ✅ 正确：直接用address字段存完整地址字符串（或JSON）

### 4）把“统计结果”当业务对象
- ❌ 错误：把“新增用户数”当实体建表
- ✅ 正确：用统计表或用查询实时计算

### 5）看到关联就急着建新实体
- ❌ 错误：看到用户和标签就建关联表，但没确认实体定义
- ✅ 正确：先确认用户和标签是独立实体，再建关联表

**实战三步走：**  
1. 从原型里圈出名词  
2. 用“四类对照表”分类，用“五问法”判断  
3. 落到字段、主键、外键和建表清单

# 第5章 字段别乱堆：字段梳理、去重和分组的实战方法

## 开篇引入：字段不是越多越专业，越乱越危险

老赵先把话放这儿：**字段设计最怕的不是少，而是乱**。很多人一看原型就进入“加字段模式”，结果表出来，字段又多又散，重复一堆，后面开发、联调、改需求全被拖住。

字段乱堆的后果：页面改一个小需求，数据库要跟着改一大片；同一信息重复存，容易不一致；查询、统计、联表都变复杂；开发看不出主数据和展示值；规格、状态、历史快照混在一起。

这一章专门解决：**怎么把页面和需求里的字段，梳理成清晰、可落库、可维护的字段草案**。你会学到字段来源、分组方法、去重原则、完整案例和检查清单。

记住一句话：**字段设计不是抄页面，而是抽业务。**

---

## 一、字段从哪里来：五类来源一个都不能漏

新手只盯着表单输入框，这不完整。字段来源通常有五类：表单、列表、详情、规则、日志。

### 1. 表单字段：用户要填什么

比如商品名称、分类、价格、库存、上架状态。这类字段通常是需要持久化保存的业务数据。但注意：表单上每个输入控件不一定都要变成独立字段。像“商品规格”区域里有多个颜色、容量、价格输入框，要先判断是不是同一类数据的多行表达。

### 2. 列表字段：页面展示什么

列表页常见字段有编号、名称、状态、创建时间等。**列表里看到的不一定都要单独存**。比如“状态名称”可能只是状态码映射的展示值。数据库存 `status=1`，页面展示“已上架”，这**不是同一回事**。

### 3. 详情字段：一个对象完整有哪些信息

详情页通常比表单更完整。比如商品详情里可能有主图、图集、规格信息、运费模板、预警库存。新增页没出现的字段，详情页会出现，比如浏览量、审核状态、下架原因。这些不一定让用户填写，但可能是业务必需的。

### 4. 规则字段：业务逻辑要求你保存什么

有些字段不是页面直接出现的，而是业务规则逼出来的。比如是否允许下单、是否需要审批、是否启用规格。这类字段往往是状态控制字段，决定流程能不能走、数据能不能流转。

### 5. 日志字段：为了追踪变化而保存什么

为了审计、追踪、排查问题，需要记录创建人、创建时间、更新人、更新时间、删除标记。别等上线后用户问“这条是谁改的”，你才发现没存。

### 实战判断法

拿到需求后，先问四个问题：
1. 这个字段是用户输入的吗？
2. 这个字段是页面展示的吗？
3. 这个字段是业务规则要求的吗？
4. 这个字段是为了追踪变化吗？

能答出来，字段来源就基本摸清了。建议直接把原型截图圈出来。

## 二、字段分组：基础、业务、状态、审计字段

字段别一股脑堆在一起。先分组，目的是减少混乱、降低重复、方便建表。

### 1. 基础字段：每张表都有的底座

**保留**：`id`、`created_at`、`updated_at`、`deleted`。**不保留**：不要放业务含义的默认值，不要把 `created_at` 和 `updated_at` 混成同一个字段。

### 2. 业务字段：真正表达业务含义的内容

**保留**（比如商品表）：`name`、`category_id`、`brand_id`、`price`、`stock`、`cover_image`。**不保留**：页面只展示一次、业务不需要持久化的字段，以及能通过关联查出来的分类名称、品牌名称。判断标准：**删掉它，业务对象就不完整了**。

### 3. 状态字段：控制流程和可见性的开关

**保留**：`status`、`is_enabled`、`audit_status`、`publish_status`。**不保留**：不要把 `status` 拆成多个布尔字段，不要用字符串存状态描述（靠枚举映射即可）。

### 4. 审计字段：让系统知道“谁在什么时候干了什么”

**保留**：`created_by`、`created_at`、`updated_by`、`updated_at`、`deleted_at`、`deleted_by`。**不保留**：不要把操作日志直接塞进主表。

### 分组的好处

分组后你更容易判断哪些字段必须存库、只用于展示、属于枚举状态、需要索引、可能需要拆子表。建议字段清单直接分四栏写：

| 基础字段 | 业务字段 | 状态字段 | 审计字段 |
|---|---|---|---|
| id | name | status | created_by |
| created_at | price | is_enabled | created_at |
| updated_at | stock | audit_status | updated_by |
| deleted | category_id | publish_status | updated_at |

---

## 三、重复字段、冗余字段、派生字段：别把一份信息存三遍

### 1. 重复字段：同一个信息存了两份

比如商品表同时存 `category_id` 和 `category_name`。如果分类名称会改，就可能数据不一致。**处理原则**：能通过关联查出来的，不要重复存。只有在性能、历史快照等明确场景下才考虑冗余。

### 2. 冗余字段：为了方便查，临时多存一份

比如订单里存 `user_id`、`user_name`、`user_phone`。订单需要保留下单时的快照，用户后面改昵称不应改历史订单。**判断标准**：这个字段是否需要保留“当时的历史值”？是否用于提升查询效率且能接受一致性维护成本？如果是，冗余就有合理性。

### 3. 派生字段：算出来的字段，别和源字段混一起

比如 `total_amount` = 单价 × 数量。**两种处理**：计算简单、实时性强，实时算不存储；计算复杂、查询频繁、要保留快照，存储结果。记住：**展示字段不等于存储字段，计算字段不等于主字段**。

### 4. 核心区分：展示字段、计算字段、存储字段

| 字段类型 | 定义 | 是否存储 | 示例 |
|---|---|---|---|
| 展示字段 | 只用于页面显示 | 一般不存储 | 状态名称（来自枚举映射） |
| 计算字段 | 由其他字段计算得出 | 视场景而定 | total_amount |
| 存储字段 | 业务需要持久化的原始数据 | 必须存储 | sale_price、stock |

**判断原则**：页面里看见的，不一定都要存。

## 四、完整案例：商品管理字段梳理

### 1. 需求示意

假设原型和需求：
- **商品列表页**：商品名称、分类、价格、库存、状态、创建时间
- **新增/编辑页**：商品名称、分类、品牌、主图、图集、销售价、划线价、库存、是否启用规格、商品详情
- **详情页**：基础信息、价格信息、库存信息、规格信息、上下架状态
- **业务规则**：商品可单规格或多规格；上架后才能展示；库存不能小于0；需记录创建人与更新时间

**重点**：注意“库存是否充足”是展示字段，不要存成 `is_stock_enough`；“销售额”没出现在需求里，不要自己加。

### 2. 业务拆解

这个“商品管理”至少管四件事：商品基础信息（名称、分类、品牌、主图、详情）、价格信息（销售价、划线价）、库存信息、规格信息。所以**商品不是一个简单扁平对象**，所有字段硬塞进一张表必乱。

### 3. 实体识别

识别实体：`product`（商品主表）、`product_sku`（商品规格明细）、`product_category`（分类）、`brand`（品牌）。入门阶段抓住两个重点：商品主表保存公共信息，SKU表保存每个规格变化的价格、库存、编码。

### 4. 字段梳理：去重、拆分和合并

#### 商品主表字段：只放所有规格共享的信息

| 字段 | 来源 | 类型 | 说明 |
|---|---|---|---|
| id | — | bigint | 主键 |
| name | 表单输入 | varchar | 商品名称 |
| category_id | 表单选择 | bigint | 关联分类表 |
| brand_id | 表单选择 | bigint | 可选 |
| cover_image | 表单上传 | varchar | 主图地址 |
| gallery | 表单上传 | text/json | 图集集合 |
| detail_content | 表单输入 | longtext | 商品描述 |
| has_sku | 规则字段 | tinyint | 是否启用多规格 |
| status | 规则字段/状态 | tinyint | 草稿/上架/下架 |
| created_by | 日志字段 | bigint | 审计 |
| created_at | 日志字段 | datetime | 审计 |
| updated_by | 日志字段 | bigint | 审计 |
| updated_at | 日志字段 | datetime | 审计 |
| deleted | 日志字段 | tinyint | 软删除 |

**去重说明**：不保留 `category_name`、`brand_name`、`status_name`、`is_stock_enough`；不保留主表版本的 `sale_price` 和 `stock`，因为一旦有多规格，主表最通用。

#### SKU表字段：每个规格变化的信息

| 字段 | 来源 | 类型 | 说明 |
|---|---|---|---|
| id | — | bigint | 主键 |
| product_id | 外键 | bigint | 商品ID |
| sku_name | 规格组合 | varchar | 如“红色/128G” |
| sku_code | 规则字段 | varchar | 唯一编码 |
| sale_price | 表单输入 | decimal | 销售价 |
| market_price | 表单输入 | decimal | 划线价 |
| stock | 表单输入 | int | 库存 |
| warn_stock | 规则字段 | int | 预警库存 |
| spec_value | 规格组合 | varchar/json | 规格维度值 |
| created_at | 日志字段 | datetime | 审计 |
| updated_at | 日志字段 | datetime | 审计 |
| deleted | 日志字段 | tinyint | 软删除 |

**去重说明**：不保留 `stock_status`（可通过 `stock > 0` 计算）、`total_amount`（订单行派生字段）、`is_warn_stock`（可通过 `stock <= warn_stock` 判断）。

#### 字段分组检查

| 字段类 | product 表 | product_sku 表 |
|---|---|---|
| 基础字段 | id, created_at, updated_at, deleted | id, created_at, updated_at, deleted |
| 业务字段 | name, category_id, brand_id, cover_image, gallery, detail_content | sku_name, sku_code, spec_value |
| 状态字段 | status, has_sku | — |
| 审计字段 | created_by, created_at, updated_by, updated_at | created_at, updated_at |
| 存储字段 | 所有业务和状态字段 | sale_price, market_price, stock, warn_stock |
| 展示字段（不存） | category_name, brand_name, status_name | stock_status, is_warn_stock |
| 计算字段（不存） | is_stock_enough | total_amount |

### 5. 字段草案落地

#### 主键设计

`product.id` 和 `product_sku.id` 都是独立主键，与业务解耦。不拿 `sku_code` 或 `sku_name` 做主键。

#### 外键设计

`product_sku.product_id` ➔ `product.id`（一对多关系）；`product.category_id` ➔ 分类表主键。外键不一定非显式加 `FOREIGN KEY`，但逻辑关系必须清楚。

## 五、MySQL 落库：从字段草案到建表

思路：**先主表，再子表，最后补索引**。

### 1. 商品主表建表示例

```sql
CREATE TABLE product (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(200) NOT NULL COMMENT '商品名称',
  category_id BIGINT NOT NULL COMMENT '分类ID',
  brand_id BIGINT NULL COMMENT '品牌ID',
  cover_image VARCHAR(500) NULL COMMENT '主图地址',
  gallery TEXT NULL COMMENT '图集（JSON格式）',
  detail_content LONGTEXT NULL COMMENT '商品详情',
  has_sku TINYINT NOT NULL DEFAULT 0 COMMENT '是否启用规格：0否1是',
  status TINYINT NOT NULL DEFAULT 0 COMMENT '状态：0草稿1待审2上架3下架',
  created_by BIGINT NULL COMMENT '创建人',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_by BIGINT NULL COMMENT '更新人',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  deleted TINYINT NOT NULL DEFAULT 0 COMMENT '删除标记：0未删1已删',
  INDEX idx_category_id (category_id),
  INDEX idx_brand_id (brand_id),
  INDEX idx_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='商品主表';
```

### 2. SKU表建表示例

```sql
CREATE TABLE product_sku (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  product_id BIGINT NOT NULL COMMENT '商品ID',
  sku_name VARCHAR(200) NOT NULL COMMENT 'SKU名称',
  sku_code VARCHAR(100) NOT NULL COMMENT 'SKU编码',
  sale_price DECIMAL(10,2) NOT NULL DEFAULT 0.00 COMMENT '销售价',
  market_price DECIMAL(10,2) NOT NULL DEFAULT 0.00 COMMENT '划线价',
  stock INT NOT NULL DEFAULT 0 COMMENT '库存',
  warn_stock INT NOT NULL DEFAULT 0 COMMENT '预警库存',
  spec_value VARCHAR(500) NULL COMMENT '规格值JSON',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  deleted TINYINT NOT NULL DEFAULT 0 COMMENT '删除标记',
  INDEX idx_product_id (product_id),
  UNIQUE KEY uk_sku_code (sku_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='商品SKU表';
```

### 3. 落库前最后确认三件事

- 这列是不是必须存？——不是业务必需的，删掉
- 这列是不是展示字段或计算字段？——如果是，检查是否需要快照
- 这列是不是会被其他表查出来？——如果是，考虑去掉

三步过不去，先别建。

### 字段来源检查
- [ ] 表单字段（用户输入）都收集了吗？
- [ ] 列表字段（页面展示）都梳理了吗？注意哪些只是展示值
- [ ] 详情字段（补全信息）都补上了吗？
- [ ] 规则字段（业务逻辑要求存储）都找出来了吗？
- [ ] 日志/审计字段（追踪变化）都考虑了吗？

### 字段分组检查
- [ ] 基础字段（id, created_at, updated_at, deleted）单独归类了吗？
- [ ] 业务字段和状态字段分开了吗？
- [ ] 审计字段统一命名了吗？
- [ ] 需要拆子表的字段（如规格、价格）拆了吗？

### 去重检查
- [ ] 有没有重复存储同一含义字段？（如 `category_id` + `category_name`）
- [ ] 有没有把展示字段当存储字段？（如 `status_name`）
- [ ] 有没有把计算字段当主字段？（如 `is_stock_enough`）

- [ ] 哪些字段是外键字段？
- [ ] 哪些是主表字段？

- [ ] 一对多、多对多是否判断清楚？

### 落库检查
- [ ] 主键设计是否稳定、与业务解耦？
- [ ] 索引是否覆盖常用查询？
- [ ] 字段类型是否合适？（价格用 `decimal`，状态用 `tinyint`）
- [ ] 默认值是否合理？
- [ ] 字段命名是否统一？（所有状态字段都叫 `status`，不叫 `state`）

## 七、常见错误提醒：别把展示字段、计算字段和存储字段混为一谈

### 错误1：看到什么就存什么

页面上有“库存是否充足”，你就建一列 `is_stock_enough`；有“销售额”，你就建一列 `sales_amount`。**正确处理**：先判断“这是原始数据，还是算出来的？这是实时展示，还是历史快照？”

### 错误2：把展示字段当成真实业务字段

“分类名称”“品牌名称”“状态名称”通常是展示字段。主表已存 `category_id`，大多数情况下分类名应通过关联查出来。**例外**：如果分类名称经常变化，但历史商品需要保留当时的分类名（快照场景），可以冗余，但需明确告知团队。

### 错误3：把规格字段乱堆在一张表里

最常见错误是把规格拆成一堆列，比如 `red_price`、`blue_price`、`32g_stock`、`64g_stock`。规格一多就炸。**正确处理**：规格必须抽成行，用SKU子表表达。

### 错误4：审计字段不统一

有的表有创建人，有的没有。排查问题时链路断掉。**正确处理**：项目开始就定好审计字段模板，所有表统一。

### 错误5：字段命名随心所欲

同一个“状态”，一会儿叫 `status`，一会儿叫 `state`。**正确处理**：字段命名要统一，比如状态统一用 `status`，是否启用统一用 `is_enabled`。

## 结尾小结：字段设计的核心，不是多，而是准

记住一句话：**字段设计要从业务出发，先分组，再去重，再落库。**

流程：
1. **先看页面**：表单、列表、详情、规则、日志都收集
2. **再做分类**：基础字段、业务字段、状态字段、审计字段分开
3. **再判断去留**：重复字段删掉，冗余字段谨慎保留，派生字段看场景
4. **再做案例拆分**：复杂页面必须拆主表和子表，用SKU表避免字段堆砌
5. **最后进MySQL**：主键稳定，外键关系清楚，索引合理，字段类型合适

### 行动建议

下次拿到原型，按这个顺序写：
- 页面有哪些信息？
- 这些信息属于哪类字段？
- 哪些是主表字段？
- 哪些需要拆子表？
- 哪些字段只是展示，不该入库？
- 哪些字段是计算出来的，不该重复存？

这六步做顺了，字段设计就不会再“越做越胖”。

**页面里看见的，不一定都要存；数据库里存的，一定要有理由。**

# 第6章 主键怎么定：业务主键、雪花ID、自增ID到底怎么选

## 开篇引入：主键不是“随便找个字段顶上去”

有个同学把订单号当成订单表主键，产品改规则后，所有关联表都得改，上线后历史查询直接挂了。

**主键不能只看“能不能唯一”，还得看稳不稳、好不好关联、查起来顺不顺、能不能扩展。**

**本节任务**：拿到用户表、商品表、订单表，能立刻判断出哪个字段该做主键，哪个字段只配做唯一索引，并给出创建SQL。

---

## 一、主键的作用：唯一标识、关联、扩展

主键干三件事：
1. **唯一标识一行数据**
2. **作为其他表的关联入口**
3. **支撑查询和扩展**——影响B+树存储、分页排序、分库分表路由

主键最怕两件事：
- **会变**：手机号、邮箱、商品编码都可能变。改了后所有子表、索引、缓存全要翻新。
- **太长太乱**：主键过长膨胀聚簇索引叶子节点，关联时外键字段也跟着变大。

---

## 二、业务主键和代理主键：别把业务字段硬塞成主键

**业务主键**：天然唯一，如手机号、身份证号。优点直观；缺点会变、有格式约束。

**代理主键**：不承载业务含义，如自增`id`、UUID、雪花ID。稳定、干净、与业务解耦。

**老赵建议**：业务字段优先做唯一约束，主键用代理主键。

**稳定性自测三步法**：
1. **一问历史变更频率**：这个字段之前改过没有？
2. **二问业务规则是否可能调整**：产品说过“以后可能要改”吗？
3. **三问是否依赖外部系统**：数据来源不受你控制？

三步都过“稳定”，才考虑做业务主键；有一项存疑，用代理主键。

**什么时候用业务主键**？字段绝对稳定（如国标城市编码）、长度可控、关联场景简单。大多数互联网业务里，业务主键更适合做唯一索引。

---

## 三、自增ID、UUID、雪花ID：到底怎么选

### 自增ID
**适用场景**：单体项目、数据量不大、不需要跨库统一生成
**优点**：递增，B+树页分裂次数少；生成简单。
**缺点**：易被猜到数据量；分库分表难全局唯一；高并发多节点写入要考虑一致性。
**当它坏掉时**：分库分表后4张表都有`id=1`，合并时全冲突。

### UUID
**适用场景**：全局唯一、分布式、跨系统同步
**优点**：完全全局唯一，多系统合并不冲突。
**缺点**：长度长（36位），索引空间大；无序，频繁随机写；字符串比较慢。
**当它坏掉时**：200万数据时JOIN要100ms以上，换雪花ID后降到10ms内。

### 雪花ID
**适用场景**：多节点生成、分布式、需要趋势递增
**优点**：全局唯一；趋势递增，对B+树友好；不依赖数据库自增。
**缺点**：需要ID生成器；依赖时钟，时间回拨可能重复。
**当它坏掉时**：时钟回拨。解决方案：记录最后一次时间戳，回拨时等待或报错。

### 对比选择表

| 维度         | 自增ID       | UUID        | 雪花ID       |
|-------------|-------------|-------------|--------------|
| 唯一性       | 库内唯一     | 全局唯一     | 全局唯一      |
| 有序性       | 递增         | 无序         | 趋势递增      |
| 性能（写）   | 高           | 中低         | 高            |
| 性能（读）   | 高           | 中低         | 高            |
| 分布式友好度 | 差           | 好           | 好            |
| 依赖组件     | 无           | 无           | 需要生成器     |
| 老赵一句话   | 单机首选     | 跨系统合并用 | 分布式高并发首选 |

### 老赵的选择口诀

- **单机单库**：自增ID
- **分布式、高并发**：雪花ID
- **跨系统唯一、合并数据**：UUID
- **业务编码**：别当主键，做成唯一索引

---

## 四、完整案例：用户表、商品表、订单表主键怎么定

### 1. 用户中心案例：用户表主键

**业务拆解**：用户是主对象，地址和登录记录是子对象。

**主键设计**：用户表用`id` `BIGINT`，自增或雪花ID。手机号不做主键（可能变、多手机号、第三方登录不便），做唯一索引。

**数据流推演**：用户换手机号时，只需要改`user`表的`mobile`字段，`order`表不需要动——因为关联的是`user_id`而不是手机号。

```sql
CREATE TABLE user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(50) NOT NULL,
  mobile VARCHAR(20) NOT NULL,
  avatar VARCHAR(255),
  status TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  UNIQUE KEY uk_user_mobile (mobile)
);
```

### 2. 商品管理案例：商品表主键

**业务拆解**：商品主体存标题、分类、状态；SKU存价格、库存、规格组合。

**主键设计**：全用代理主键`id`，商品编码做唯一索引。商品编码可能因品牌合并或SKU规则调整而变更。

**数据流推演**：商品编码变了，`order_item`里存的`product_sku_id`不受影响——因为关联的是主键，不是编码。

```sql
CREATE TABLE product (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  product_code VARCHAR(50) NOT NULL,
  title VARCHAR(200) NOT NULL,
  category_id BIGINT NOT NULL,
  price DECIMAL(10,2) NOT NULL,
  status TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  UNIQUE KEY uk_product_code (product_code),
  KEY idx_product_category_id (category_id)
);
```

### 3. 订单管理案例：订单表主键

**业务拆解**：订单主体和明细是1对多关系，支付和物流是1对1。

**主键设计**：订单主表用`id`，`order_no`做唯一索引。订单号较长且带业务规则，不适合做主键。

**数据流推演**：用`BIGINT`的`id`关联只需要比较8字节整数，比30位字符串快好几个数量级。

```sql
CREATE TABLE `order` (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  order_no VARCHAR(64) NOT NULL,
  user_id BIGINT NOT NULL,
  total_amount DECIMAL(10,2) NOT NULL,
  status TINYINT NOT NULL,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_order_user_id (user_id)
);
```

---

## 五、MySQL落库：主键设计落地注意点

1. **类型统一用`BIGINT`**：防止数据量超过`INT`上限；雪花ID长度刚好。
2. **自增ID注意步长**：分库时配置`auto_increment_increment`和`auto_increment_offset`。
3. **雪花ID用`BIGINT`**：用`INT`会溢出导致`Duplicate entry`。
4. **UUID用`BINARY(16)`优化**：用`UUID_TO_BIN()`和`BIN_TO_UUID()`转换。
5. **关联字段类型保持一致**：`user.id`是`BIGINT`，`order.user_id`也必须是`BIGINT`，否则隐式类型转换让索引失效。

**主键变更灾难推演**：手机号做主键，半年后要支持换绑。需要新建`id`字段、改唯一索引、改所有关联表、重建关联数据。如果自增ID做主键，一行SQL十分钟搞定。前者折腾十几小时。

---

## 六、总结清单：主键选择决策树

1. **这个字段会不会变？** → 会 → 做唯一索引 → 不会 → 继续
2. **业务含义太重？** → 重 → 做唯一索引 → 轻 → 继续
3. **以后会分布式、多节点写？** → 会 → 雪花ID → 不会 → 继续
4. **单库单表、数据量可控？** → 是 → 自增ID → 否 → 雪花ID或UUID
5. **有跨系统合并需求？** → 有 → UUID或雪花ID → 无 → 自增ID或雪花ID

### 快速选择表

| 表类型     | 主键推荐      | 唯一索引字段  | 说明                     |
|-----------|---------------|---------------|--------------------------|
| 用户表     | 代理主键`id`   | 手机号、邮箱   | 手机号会变，别做主键       |
| 商品表     | 代理主键`id`   | 商品编码       | 编码可能调整               |
| 订单表     | 代理主键`id`   | 订单号         | 订单号长且有规则           |
| 日志表     | 雪花ID         | 无            | 写入量大，分布式场景多      |
| 内部字典表 | 自增ID或业务主键| 编码          | 如城市表，编码稳定可用      |

---

## 七、常见错误提醒

- **错误1**：把手机号、邮箱当主键 → 关联表全跟着动。
- **错误2**：所有表用UUID → 200万数据后JOIN速度断崖下降。
- **错误3**：业务编码和主键混为一谈 → 订单号、商品编码适合唯一索引。
- **错误4**：主键设计完不管索引 → 外键字段和高频查询字段也得加索引。
- **错误5**：图省事后改主键 → 前期10分钟想清楚，省10小时改表时间。
- **错误6**：关联表外键和主键类型不一致 → 隐式类型转换让索引失效。

---

## 结尾小结：先稳，再快

主键设计一句话：**先保证稳定和可扩展，再谈方便和漂亮。**

落地步骤：
1. 看业务对象
2. 用稳定性自测三步法判断字段会不会变
3. 决定业务主键还是代理主键
4. 选自增、UUID、雪花ID
5. 补齐唯一索引和关联字段
6. 检查外键和主键类型是否一致

**行动建议**：下次拿到UI原型，先圈出对象，再问三件事：主角是谁？哪个字段最稳定？哪些字段需要唯一约束和关联索引？拿不准的，一律用代理主键——稳比快更重要。

# 第7章 关系设计不再靠猜：一对一、一对多、多对多怎么判断

## 开篇引入：关系不是拍脑袋，是从业务规则里抠出来的

老赵做数据库设计，最怕新手一句话：“这个表和那个表怎么连？”

很多人一看见两个对象就急着加外键，看到关联就建中间表，结果表越建越乱。根子就一个：**没先看业务规则，只凭感觉猜关系。**

你记住一句话就够了：**A 和 B 之间到底是什么关系，不靠猜，靠业务规则。**

一个用户只能有一个主收货地址，但可以有多个收货地址；一个部门可以有多个员工，但一个员工只能属于一个部门；一个用户可以有多个角色，一个角色也可以赋给多个用户——这些关系是业务规则定死的。

这一章老赵就按实战讲：怎么从业务规则出发，判断一对一、一对多、多对多；外键该放哪边；中间表什么时候必须建；最后用一个完整案例落到MySQL上。

---

## 一、用业务规则判断关系：从“一个A对应几个B”开始

判断方法只有一句口诀：**看一个A能对应几个B，一个B能对应几个A。**

### 1. 一对一：双方都是唯一绑定

**判断标准：** 一个A只能对应一个B，一个B也只能对应一个A。

**典型场景：**
- 用户基本信息`user`和用户扩展资料`user_profile`
- 员工账号`employee`和员工档案`employee_archive`

**怎么从业务规则看：**
- “每个用户只能有一份扩展资料”
- “一份扩展资料只能属于一个用户”

**落表思路：** 主表放核心字段，扩展表拿主表主键做外键，并加唯一约束。只有加上`UNIQUE`才能确保一个用户只能有一条扩展记录。

### 2. 一对多：一个父对象管多个子对象

**判断标准：** 一个A能对应多个B，但一个B只能对应一个A。

**典型场景：**
- 一个部门有多个员工，但一个员工只属于一个部门
- 一个用户有多个收货地址，但一个地址只属于一个用户
- 一个订单有多条明细，但一条明细只属于一个订单

**怎么从业务规则看：**
- “选择部门”：一个用户只能选一个部门
- “新增地址”：一个用户可以新增多个地址

**落表思路：** 外键放在“多”的那一边。为什么？因为多的一方需要知道自己属于谁。

**关键提示：** 千万别把地址拆成`address1、address2、address3`这种字段。用户地址数量不固定，字段模式根本解决不了。

### 3. 多对多：双方都能对应多个对方

**判断标准：** 一个A能对应多个B，一个B也能对应多个A。

**典型场景：**
- 一个用户可以有多个角色，一个角色可以分配给多个用户
- 一个商品可以属于多个分类，一个分类可以有多个商品

**怎么从业务规则看：**
- “分配角色”：用户和角色是多选的关系
- “设置商品分类”：商品和分类也是多选

**落表思路：** 必须有中间表。中间表存双方主键，如果关系本身还有属性（如分配时间），也放中间表。

**为什么不能省？** 你不可能在用户表里塞多个角色ID，也不可能在角色表里塞多个用户ID。

---

## 二、外键放哪边，为什么这么放

### 1. 一对多：外键放在“多”的一边

**举例：**
- 一个部门有多个用户 → `user.dept_id`
- 一个用户有多个地址 → `user_address.user_id`

**原因：** “多”的一方必须知道自己属于谁。查起来也简单：`WHERE user_id = ?`就能拿到这个用户的所有地址。

### 2. 一对一：外键通常放在扩展表上

**举例：** `user`存基础信息，`user_profile`存扩展资料，拿`user_id`做外键并加`UNIQUE`。

**原因：** 主表保持精简，扩展字段后期增删不影响主表结构。

### 3. 多对多：外键全放在中间表里

中间表同时持有两个实体的外键，加上联合唯一约束，避免重复关联。

---

## 三、中间表什么情况下必须建

### 必须建的情况

满足以下任意一条就建中间表：
1. 双方都可能对应多个对象（多对多）
2. 关系本身需要记录附加信息（分配时间、状态）
3. 关系要支持增删改查和统计

### 什么时候可以不建

只有一个场景可以考虑不建：关系永远不会被查询、统计、维护，且一方最多只有一个关联。比如订单里的“收货地址”如果只用一次，可以直接在订单表里放地址所有字段——但这种情况很少见。

**千万别省成逗号分隔的ID字段。** 前期省事，后期拆分和查询都痛苦。

---

## 四、完整案例：用户、角色、部门、地址之间的关系设计

### 1. 需求信息

假设原型里能看到：
- **用户列表页**：用户姓名、手机号、部门、状态
- **用户新增页**：可选择部门、分配角色
- **角色管理页**：角色名称、权限说明
- **部门管理页**：部门树、上级部门、负责人
- **地址管理区**：一个用户可以新增多个收货地址

**从页面看关系线索：**
- “选择部门” → 一对多
- “分配角色” → 多对多
- “新增多个地址” → 一对多

### 2. 业务拆解与实体识别

**业务对象：**
- 用户：系统登录主体
- 角色：权限身份标签
- 部门：组织归属
- 地址：用户收货信息

**业务规则：**
- 一个用户属于一个部门（一对多）
- 一个部门有多个用户（一对多）
- 一个用户可以有多个角色（多对多）
- 一个角色可以给多个用户（多对多）
- 一个用户可以有多个地址（一对多）
- 一个地址只属于一个用户（一对多）

**最终实体：** `user`、`role`、`department`、`user_address`、`user_role`（中间表）

### 3. 表结构草案

**用户表`user`**
- `id`：主键
- `username`：用户名
- `phone`：手机号
- `dept_id`：部门ID（外键）
- `status`：状态
- `created_at`：创建时间

**部门表`department`**
- `id`：主键
- `dept_name`：部门名称
- `parent_id`：上级部门ID（自关联外键）
- `leader_id`：负责人ID
- `created_at`

**角色表`role`**
- `id`：主键
- `role_name`：角色名称
- `role_code`：角色编码（唯一）
- `remark`：备注
- `created_at`

**用户角色中间表`user_role`**
- `id`：主键
- `user_id`：用户ID（外键）
- `role_id`：角色ID（外键）
- `assigned_at`：分配时间

**用户地址表`user_address`**
- `id`：主键
- `user_id`：用户ID（外键）
- `receiver_name`：收货人
- `receiver_phone`：收货电话
- `province`、`city`、`district`、`detail_address`
- `is_default`：是否默认

### 4. 主键设计

主键统一用数值型自增ID（或雪花ID）。三个原则：稳定不变化；不要用手机号、用户名当主键；业务编码可以做唯一键，但别替代主键。

### 5. 外键设计总结

- `user.dept_id → department.id`
- `user_address.user_id → user.id`
- `user_role.user_id → user.id`
- `user_role.role_id → role.id`
- `department.parent_id → department.id`

---

## 五、MySQL落库

```sql
CREATE TABLE department (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  dept_name VARCHAR(50) NOT NULL,
  parent_id BIGINT DEFAULT NULL,
  leader_id BIGINT DEFAULT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE role (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  role_name VARCHAR(50) NOT NULL,
  role_code VARCHAR(50) NOT NULL UNIQUE,
  remark VARCHAR(200),
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(50) NOT NULL,
  phone VARCHAR(20),
  dept_id BIGINT,
  status TINYINT DEFAULT 1,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_user_dept FOREIGN KEY (dept_id) REFERENCES department(id)
);

CREATE TABLE user_address (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  receiver_name VARCHAR(50) NOT NULL,
  receiver_phone VARCHAR(20) NOT NULL,
  province VARCHAR(50),
  city VARCHAR(50),
  district VARCHAR(50),
  detail_address VARCHAR(200) NOT NULL,
  is_default TINYINT DEFAULT 0,
  CONSTRAINT fk_address_user FOREIGN KEY (user_id) REFERENCES user(id)
);

CREATE TABLE user_role (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  role_id BIGINT NOT NULL,
  assigned_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_ur_user FOREIGN KEY (user_id) REFERENCES user(id),
  CONSTRAINT fk_ur_role FOREIGN KEY (role_id) REFERENCES role(id),
  UNIQUE KEY uk_user_role (user_id, role_id)
);
```

`user_role`加了联合唯一约束`(user_id, role_id)`，防止同一个用户重复分配同一个角色。

## 六、总结清单：关系判断与落表对照表

| 关系类型 | 判断依据 | 落表规则 | 示例 |
|---------|---------|---------|------|
| 一对一 | A只能有一个B，B只能有一个A | 扩展表放外键，加唯一约束 | user + user_profile |
| 一对多 | A可以有多个B，B只能有一个A | 外键放在“多”的一边 | user + user_address |
| 多对多 | A可以有多个B，B可以有多个A | 必须建中间表 | user + role → user_role |
| 关系带属性 | 关系本身有额外信息 | 属性放中间表 | assigned_at 放 user_role |
| 层级关系 | 同一实体上下级 | 自关联外键 | department.parent_id |

## 七、常见错误提醒

### 错误1：看到关联就硬加字段，不建中间表
比如在用户表里加`role_id1、role_id2、role_id3`字段，数量不够用，查询也麻烦。

### 错误2：把多对多硬当一对多
比如用户和角色，按一个用户只能选一个角色设计，结果业务来了“多个角色”的变更，整个表都得改。

### 错误3：外键放错位置
比如在部门表里放`user_id`表示“部门有哪些用户”，违反了“谁依赖谁，外键放谁那边”的原则。

### 错误4：中间表不做唯一约束
导致同一个用户被重复分配同一个角色。

### 错误5：把所有字段往一张表堆
关系没理清，用户表里塞角色名、部门名、地址，表又大又乱。

---

## 结尾小结：先看业务规则，再定关系，再落表

老赵给你三句最实在的话：

1. **一对多：父对象管多个子对象，外键放子对象**
2. **多对多：双方都能有多个，中间表来解决**
3. **一对一：唯一绑定，扩展表加唯一约束**

你做关系设计时，按这个顺序走：
1. 看页面和需求里的业务动作
2. 拆出实体
3. 用“一个A对应几个B”判断关系类型
4. 决定外键放哪边
5. 需要中间表就建中间表
6. 最后写MySQL

**行动建议：**
- 拿一个做过的页面，先写出“一个A对应几个B”
- 把每个关系标成一对一/一对多/多对多
- 再画表草图，检查外键位置
- 最后落MySQL

练几次你就会发现：关系设计，真的能从“凭感觉”变成“按规则”。

# 第8章 从原型到建表清单：把页面需求变成可执行的表结构草案

## 开篇引入：别急着画表，先把页面翻译成人话

很多人一看UI原型就想直接开干，结果字段越堆越多，改需求全是补丁。老赵说句实话：**原型不是表结构，页面信息也不是字段清单。** 你要做的，是把页面需求翻译成业务对象，再落成表，最后整理成开发能直接执行的**建表清单**。

这一章只干一件事：从原型出发，输出可落库的表结构草案。

---

## 一、建表清单的标准模板：开发看了就能用

### 1.1 为什么只写字段名不够？

很多表设计文档只写“id、姓名、手机号”，离可开发还差一截。开发需要知道：表存什么、怎么连、怎么查、怎么扩。

### 1.2 建表清单的六项标准内容

| 序号 | 内容 | 说明 |
|------|------|------|
| 1 | 表名 | 按模块和实体命名，如`user_info` |
| 2 | 用途 | 说明表存什么 |
| 3 | 主键 | 无强约束时用自增id或雪花id |
| 4 | 字段 | 字段名、含义、类型、是否为空、默认值、索引 |
| 5 | 索引 | 主键索引、唯一索引、高频查询字段优先 |
| 6 | 关联关系 | 写清和谁连、怎么连 |

**关键提醒：** 关系不写清楚，系统一复杂就乱。

---

## 二、按模块整理表结构草案的三个步骤

### 2.1 先按模块，别按页面

页面是展示层，模块才是业务层。比如“用户中心”包含：登录注册、用户资料、收货地址、账号安全、登录记录。按页面切表容易拆散，正确方式是先按模块识别实体。

### 2.2 步骤一：圈出业务对象

看页面上反复出现的名词：用户、手机号、地址、登录记录。不是所有名词都成实体，比如“收货地址”通常是独立实体，“头像”只是字段。

### 2.3 步骤二：判断对象归属

问三个问题：能不能独立存在？会不会被多次使用？有没有生命周期？满足这三点的，单独成表。

### 2.4 步骤三：按模块分表草案

用户中心可拆为用户基础信息表、用户地址表、登录日志表。目标是先形成**可讨论的草案**。

---

## 三、字段命名一致性规则

### 3.1 命名的第一原则：先统一

最怕同一意思多个名字（`name`可能是用户姓名或商品名），或一个名字多个意思（`status`是启用状态还是订单状态？）。

### 3.2 常用命名建议

| 字段类型 | 命名规则 | 示例 |
|----------|----------|------|
| 基础字段 | 英文小写下划线 | `user_id`、`created_at` |
| 状态字段 | 带语义前缀 | `user_status`、`order_status` |
| 布尔字段 | 用明确语义 | `is_deleted`、`is_default` |
| 时间字段 | 统一格式 | `created_at`、`updated_at` |

**不要所有表都叫`status`。**

### 3.3 字段设计小口诀

> 先看它是不是业务对象，再看它是不是属性，再看它能不能复用。

## 四、完整案例：用户中心从原型到表结构草案

### 4.1 需求截图/原型示意

页面包含：用户头像、昵称、手机号、邮箱、账号状态（正常/禁用），收货地址管理（新增/编辑/删除/设默认），登录记录（时间、设备、IP）。

### 4.2 业务拆解

1. 用户基础资料：头像、昵称、手机号、邮箱、状态
2. 收货地址：收件人、手机号、省市区、详细地址、是否默认
3. 登录记录：登录时间、设备、IP

### 4.3 实体识别

- `user`：用户（主实体）
- `user_address`：用户地址（一对多）
- `login_log`：登录日志（一对多）

### 4.4 主键设计

- 用户表：`id`做主键，`user_no`做业务唯一编号。**别用手机号做主键**，手机号会变。
- 地址表：`id`做主键，`user_id`关联
- 登录日志：`id`做主键，`user_id`关联

### 4.5 关联关系说明

| 关联 | 类型 | 说明 |
|------|------|------|
| 用户 ↔ 地址 | 一对多 | `user_address.user_id` → `user_info.id` |
| 用户 ↔ 登录日志 | 一对多 | `login_log.user_id` → `user_info.id` |

### 4.6 表结构草案

#### 表1：用户基础信息表 `user_info`
**用途：** 存储平台注册用户核心信息

| 字段名 | 含义 | 类型 | 约束 | 索引 |

| phone | 手机号 | varchar(20) | 唯一，可空 | 唯一索引 |

| avatar_url | 头像地址 | varchar(255) | 可空 | — |
| user_status | 用户状态 | tinyint | 默认1 | 普通索引 |
| created_at | 创建时间 | datetime | 不为空 | — |
| updated_at | 更新时间 | datetime | 不为空 | — |

#### 表2：用户地址表 `user_address`
**用途：** 存储用户收货地址

### 4.7 MySQL落库

```sql
CREATE TABLE user_info (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_no VARCHAR(32) NOT NULL UNIQUE,
  nickname VARCHAR(50) DEFAULT NULL,
  phone VARCHAR(20) DEFAULT NULL UNIQUE,
  email VARCHAR(100) DEFAULT NULL UNIQUE,
  avatar_url VARCHAR(255) DEFAULT NULL,
  user_status TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  INDEX idx_user_status (user_status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE user_address (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  receiver_name VARCHAR(50) NOT NULL,
  receiver_phone VARCHAR(20) NOT NULL,
  province VARCHAR(50) NOT NULL,
  city VARCHAR(50) NOT NULL,
  district VARCHAR(50) NOT NULL,
  detail_address VARCHAR(255) NOT NULL,
  is_default TINYINT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  INDEX idx_user_id (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE login_log (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  login_time DATETIME NOT NULL,
  login_ip VARCHAR(45) DEFAULT NULL,
  login_device VARCHAR(100) DEFAULT NULL,
  created_at DATETIME NOT NULL,
  INDEX idx_user_id (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

| 原型区域 | 业务对象 | 是否独立成表 | 对应表 |
|----------|----------|--------------|--------|

## 六、总结清单

检查这8项：
1. ✅ 核心对象是否识别出来
2. ✅ 每个对象是否该单独成表
3. ✅ 表名是否清晰统一
4. ✅ 主键是否稳定
5. ✅ 关联关系是否明确
6. ✅ 字段是否围绕实体核心属性
7. ✅ 索引是否只加在高频查询字段
8. ✅ 字段命名是否一致

---

## 七、常见错误提醒

**错误1：** 把页面上所有文字都当字段。标签、按钮、提示语不一定进表。

**错误2：** 字段越多越安全。先识别实体，再补字段。

**错误3：** 主键随业务变。手机号、邮箱不适合做主键。

**错误4：** 只画表不画关系和约束。没关系的表就是孤岛。

**错误5：** 索引乱加。写入慢、维护成本高。

## 结尾小结

这一章要记住一整套动作：看原型抓业务对象 → 做业务拆解 → 识别实体判断主从 → 定主键外键理清关联 → 整理建表清单 → MySQL落库。

以后再看到页面，先问三句：这是哪个业务模块？有哪些核心实体？每个实体怎么连？想明白这三句，原型到数据库设计就算入门了。

# 第9章 MySQL落库入门：把表结构草案真正建出来

前面我们已经把原型、需求文档一步步拆成了表结构草案。到了这一章，就要真正落到 MySQL 里，写成能执行的建表语句。

很多人表结构画得挺顺，真一落库就开始翻车：字段类型乱选、主键随便定、索引瞎加、关系在脑子里有，SQL 里却没体现出来。老赵这章就干一件事：**把表结构草案，真正变成一套能落库的 MySQL 基础表。**

---

## 一、MySQL建表前先确认什么：字符集、引擎和命名规范

别上来就写 `CREATE TABLE`。先把底层规则统一好，不然后面改起来很烦。

### 1. 字符集先统一

中文业务系统，优先用：

- `utf8mb4`：支持中文、emoji、特殊符号
- 排序规则按项目统一，比如 `utf8mb4_general_ci`

昵称、商品标题、备注、地址这些字段几乎都会出现中文和特殊符号，提前统一能避免乱码、截断等问题。

### 2. 引擎优先 InnoDB

大多数业务表默认选：

- `InnoDB`

原因：支持事务、行级锁、外键，适合用户、商品、订单这类核心业务表。

### 3. 命名规范先统一

建议按这套规则：

- 表名：小写英文 + 下划线，比如 `t_user`、`t_product`、`t_order`
- 字段名：语义明确，比如 `user_id`、`created_at`、`status`
- 避免：拼音缩写、无意义简写、驼峰混写

统一风格：
- 表名前缀：`t_` 或按团队规范
- 主键字段：`id`
- 外键字段：`xxx_id`
- 创建时间：`created_at`
- 更新时间：`updated_at`

---

## 二、字段类型怎么选：整数、字符串、时间、金额、状态

字段类型要考虑**范围、精度、查询和扩展**。

### 1. 整数类字段

适合主键 `id`、外键 `user_id`、状态码 `status`、数量 `quantity`。

常见选择：
- `BIGINT`：主键、外键、数据量可能很大的编号
- `INT`：普通数量、状态值
- `TINYINT`：状态枚举，比如 0/1/2

经验：主键用 `BIGINT UNSIGNED AUTO_INCREMENT`，状态字段别用字符串。

### 2. 字符串类字段

适合用户名、商品标题、手机号、备注、编码。

常见类型：
- `VARCHAR(50)`：短文本，比如手机号
- `VARCHAR(255)`：常规文本，比如商品名称
- `TEXT`：长文本，比如商品详情、备注描述

判断标准：短且经常查的用 `VARCHAR`，长且少查询的用 `TEXT`。

### 3. 时间类字段

常用：
- `DATETIME`：最常见，适合存创建/更新时间

业务表里至少放 `created_at` 和 `updated_at`。订单系统还需 `paid_at`、`shipped_at`。

### 4. 金额字段

金额别用 `FLOAT`、`DOUBLE`，浮点数不适合精确金额计算。

统一用 `DECIMAL(10,2)`，适用于商品价格、订单总金额等。

### 5. 状态字段

用数字。例如订单状态：0 待支付、1 已支付、2 已发货、3 已完成、4 已取消。

存储更省，查询更方便，扩展更灵活。

## 三、主键、外键、唯一索引、普通索引怎么写

表不是孤立的，表和表之间是有关系的。

### 1. 主键设计

主键用于**唯一标识一行数据**。

常见做法：`id BIGINT PRIMARY KEY AUTO_INCREMENT`。业务主键（如订单号）不直接当主键，因为业务编号可能改规则。

主键需满足：唯一、稳定、尽量短、尽量不变。

### 2. 外键设计

外键字段表达表之间关系，如 `t_order.user_id` 指向 `t_user.id`。

设计思路：子表存父表主键，字段类型保持一致，命名用 `xxx_id`。

很多团队在 MySQL 里逻辑上有外键关系，但物理上不一定加外键约束（高并发场景下外键增加维护成本）。但不管加不加约束，**设计上必须先把关系想清楚**。

### 3. 唯一索引

用于保证字段不重复，比如手机号、邮箱、商品编码。

适合场景：业务上必须唯一、查询频率高。用户表的手机号通常加唯一索引。

```sql
UNIQUE KEY uk_mobile (mobile)
```

### 4. 普通索引

用于加速查询，不保证唯一。常见场景：按 `user_id` 查订单、按 `status` 查待处理订单。

```sql
KEY idx_user_id (user_id)
```

索引不是越多越好，影响插入速度、更新速度和存储空间。按查询场景加，不是按心情加。

## 四、完整案例：把订单管理的表结构草案落成 MySQL 建表 SQL

**案例**：订单管理。核心对象：用户、商品、订单、订单明细。

关系：一个用户有多个订单，一个订单包含多个订单明细，一个订单明细对应一个商品。

建表要**注意顺序**：先建没有外键依赖的表。

### 第一步：建 `t_user` 用户表

```sql
CREATE TABLE t_user (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  username VARCHAR(50) NOT NULL COMMENT '用户名',
  mobile VARCHAR(20) NOT NULL COMMENT '手机号',
  email VARCHAR(100) DEFAULT NULL COMMENT '邮箱',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1正常 0禁用',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_mobile (mobile),
  UNIQUE KEY uk_username (username)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';
```

### 第二步：建 `t_product` 商品表

```sql
CREATE TABLE t_product (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  product_name VARCHAR(200) NOT NULL COMMENT '商品名称',
  product_code VARCHAR(50) NOT NULL COMMENT '商品编码',
  price DECIMAL(10,2) NOT NULL COMMENT '商品价格',
  stock INT NOT NULL DEFAULT 0 COMMENT '库存',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1上架 0下架',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_product_code (product_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='商品表';
```

### 第三步：建 `t_order` 订单表

```sql
CREATE TABLE t_order (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  order_no VARCHAR(64) NOT NULL COMMENT '订单号',
  user_id BIGINT UNSIGNED NOT NULL COMMENT '用户ID',
  total_amount DECIMAL(10,2) NOT NULL COMMENT '订单总金额',
  order_status TINYINT NOT NULL DEFAULT 0 COMMENT '订单状态：0待支付 1已支付 2已发货 3已完成 4已取消',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_user_id (user_id),
  KEY idx_order_status (order_status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单表';
```

### 第四步：建 `t_order_item` 订单明细表

```sql
CREATE TABLE t_order_item (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  order_id BIGINT UNSIGNED NOT NULL COMMENT '订单ID',
  product_id BIGINT UNSIGNED NOT NULL COMMENT '商品ID',
  product_name VARCHAR(200) NOT NULL COMMENT '商品名称快照',
  product_price DECIMAL(10,2) NOT NULL COMMENT '成交单价',
  quantity INT NOT NULL COMMENT '购买数量',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (id),
  KEY idx_order_id (order_id),
  KEY idx_product_id (product_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='订单明细表';
```

核心设计点：`product_name` 和 `product_price` 保留快照，避免商品改名、改价影响历史订单。

**建表顺序**：t_user → t_product → t_order → t_order_item。因为 `t_order` 引用 `t_user`，`t_order_item` 引用 `t_order` 和 `t_product`。

## 五、MySQL落库前后的核对项

### 落库前检查
- [ ] 表名是否统一规范
- [ ] 每张表是否有主键
- [ ] 主键类型是否统一（都用 BIGINT）
- [ ] 字段类型是否合理（金额用 DECIMAL，状态用 TINYINT）
- [ ] 关系字段是否命名为 `xxx_id`
- [ ] 唯一约束是否加对
- [ ] 索引是否对应查询场景
- [ ] 字符集和引擎是否统一
- [ ] 建表顺序是否合理（先建父表，再建子表）

### 落库后检查
- [ ] SQL 是否成功执行
- [ ] 表注释是否完整
- [ ] 索引是否生效（可用 `SHOW INDEX FROM 表名;` 查看）
- [ ] 字段默认值是否符合预期
- [ ] 是否能插入测试数据
- [ ] 是否能按业务条件正常查询

建议建表后马上插几条测试数据，跑一下最常见查询条件，尽早发现问题。

## 六、常见错误提醒

### 1. 类型乱选
- ❌ 金额用 `FLOAT`：导致计算误差
- ❌ 主键用字符串：影响查询性能
- ❌ 状态用中文字段：存储浪费、查询不便
- ✅ 金额用 `DECIMAL`，主键用 `BIGINT`，状态用 `TINYINT`

### 2. 索引乱加
- ❌ 所有字段都加索引：写入变慢、空间浪费
- ❌ 不看查询条件就加索引：索引没命中等于白加
- ✅ 只在高频查询字段上加索引

### 3. 约束缺失
- ❌ 手机号本应唯一却不加唯一索引：导致数据脏乱
- ❌ 关联字段类型不一致：关联查询时出错
- ✅ 唯一字段加唯一索引，关联字段类型保持一致

---

## 结尾小结

落库的核心动作就四步：

1. 先统一字符集、引擎、命名规范
2. 再按业务场景选择字段类型
3. 然后设计主键、外键、唯一索引、普通索引，并确定建表顺序
4. 最后把草案翻译成可执行的建表 SQL，并做落库前后检查

真正难的不是写 SQL，而是**把业务想清楚，再把业务翻译成表**。

拿一个真实原型来练：

2. 列出页面上的表单字段、列表字段、筛选字段
3. 抽出实体和关系
4. 写出表结构草案，确定建表顺序

# 第10章 完整案例一：用户中心从原型到表设计全流程复盘

## 开篇引入：别一上来就画表，先看页面到底在说什么

很多同学一拿到“用户中心”需求，就开始脑补 `user`、`role`、`permission` 一堆表，结果字段越堆越乱。老赵先把话放前面：**从 UI 原型到数据库设计，不是先想表名，而是先读页面信息。**

这一章拿“用户中心”做一次完整复盘，按这个顺序走：

> **原型示意 → 业务拆解 → 实体识别 → 字段梳理 → 主键与关联关系设计 → 表结构草案 → MySQL 落库**

你看完这章，至少要能做到两件事：
1. 看到用户中心页面，不再把“用户信息、角色、权限、登录日志”混成一锅；
2. 能从原型直接整理出一份能建表的草案。

## 一、需求截图/原型示意：先把页面信息读明白

假设一个常见的“用户中心”原型，页面包含这几块：

### 1. 个人资料页
- 头像、用户昵称、手机号、邮箱、性别、生日、所在城市、个性签名、修改资料按钮

### 2. 账号安全页
- 登录账号、登录密码修改、手机绑定、邮箱绑定、第三方登录绑定、登录设备记录

### 3. 角色权限页
- 当前角色：普通用户 / 会员 / 管理员
- 可查看的功能菜单、可执行的操作权限

### 4. 登录记录页
- 登录时间、登录 IP、登录设备、登录结果

### 5. 收货地址页
- 收件人、手机号、省市区、详细地址、默认地址标识

看起来都挂在“用户中心”下面，但这里至少有四类不同的信息：

- **用户基本资料**：头像、昵称、性别、生日
- **账号安全与角色权限**：密码、角色、权限
- **登录行为记录**：时间、IP、设备
- **收货地址**：收件人、地址信息

读页面时，老赵建议你先过三个问题：

- 这块内容是“账号自身的属性”，还是“账号关联的其他数据”？
- 这块内容是“一条就够”，还是会“反复新增”？
- 这块内容是“展示字段”，还是“独立的业务实体”？

像头像、昵称、手机号，偏用户自身属性；登录记录、收货地址，明显是围绕用户产生的附属数据。**先读页面，再分对象，这是第一原则。**

---

## 二、业务拆解与实体识别：这个页面到底有哪些业务对象？

### 1. 先找“会被单独管理”的对象

判断一个对象能不能单独成表，常看三点：

- 有没有独立生命周期（增删改查）
- 会不会多次新增、修改、查询
- 会不会被别的业务重复引用

拿用户中心来说，可以识别出以下实体：

#### 用户（User）
核心对象，肯定单独建表。账号、昵称、手机号、状态等都围绕它展开。

#### 角色（Role）
独立实体，不是用户表里的普通字段。一个角色可对应很多用户，也有自己的名称、描述、状态。**注意：不要把角色名称直接写在用户表里。**

#### 权限（Permission）
独立实体，资源级、操作级配置，不适合直接堆在用户表里。权限与角色是多对多关系。

#### 用户角色关联
用户和角色是**多对多**。一个用户可有多个角色，一个角色也可分给多个用户，必须用中间表表达。

#### 登录日志（Login Log）
典型行为记录表，用户可以有多个记录，是**一对多**。

#### 收货地址（Address）
一个用户可有多个地址，天然独立成表，也是**一对多**。

### 2. 实体识别别贪多，先抓主干

刚开始做建模，先抓这四类：

- **主对象**：用户
- **附属对象**：收货地址、登录日志
- **关系对象**：用户角色关联表
- **独立实体**：角色、权限

---

## 三、字段梳理：哪些字段放哪张表？

### 1. 用户表该放什么？

用户表放**账号核心字段**和**稳定基础字段**：

- `id`：主键
- `username`：登录账号
- `password_hash`：密码摘要
- `nickname`：昵称
- `mobile`：手机号
- `email`：邮箱
- `status`：状态
- `created_at`：创建时间
- `updated_at`：更新时间

头像、性别、生日等扩展字段，简单项目可放主表；复杂项目建议拆扩展表。老赵的经验是：**高频核心字段放主表，低频扩展字段放扩展表。**

### 2. 如何避免字段乱堆？

判断法：

- **账号类字段**：用户名、密码、状态 → 放用户表
- **资料类字段**：头像、性别、生日、签名 → 按复杂度放主表或扩展表
- **关系类字段**：用户和角色 → 用中间表
- **行为类字段**：登录时间、IP、设备 → 用日志表
- **重复地址类字段**：收件人、地址信息 → 用地址表

**记住：字段不是看见就放，而是看它属于谁、会不会重复、会不会变化。**

### 3. 主键设计怎么定？

基础库表设计里，主键优先用单列、稳定、好关联的类型：

- `BIGINT UNSIGNED` 自增
- 或业务层生成的长整型 ID

所有表统一用一种主键风格。**每张表都先定主键，再看唯一约束和索引。**

---

## 四、关联关系设计：用户与角色是多对多，别偷懒

### 用户与角色：多对多

必须加中间表 `sys_user_role`。

**错误做法**：在用户表里加一个 `role_id` 字段。  
**正确做法**：用中间表存储关联关系，支持未来扩展。

### 用户与登录日志：一对多

日志表里放 `user_id` 作为外键。

### 用户与地址：一对多

地址表里放 `user_id` 作为外键。

### 关于外键：关联字段设计清楚，不等于必须加物理外键约束

很多项目只保留 `user_id`、`role_id` 关联字段，在应用层保证一致性。**先把字段、主键、索引、关系搞明白，比急着加外键更重要。**

## 六、MySQL落库示例：把草案真正建出来

```sql
-- 1. 用户表
CREATE TABLE sys_user (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  username VARCHAR(64) NOT NULL COMMENT '登录账号',
  password_hash VARCHAR(255) NOT NULL COMMENT '密码摘要',
  nickname VARCHAR(64) NOT NULL COMMENT '昵称',
  mobile VARCHAR(20) DEFAULT NULL COMMENT '手机号',
  email VARCHAR(128) DEFAULT NULL COMMENT '邮箱',
  avatar VARCHAR(255) DEFAULT NULL COMMENT '头像地址',
  gender TINYINT DEFAULT 0 COMMENT '性别：0未知 1男 2女',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1启用 0禁用',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_username (username),
  UNIQUE KEY uk_mobile (mobile),
  UNIQUE KEY uk_email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';

-- 2. 角色表
CREATE TABLE sys_role (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  role_code VARCHAR(64) NOT NULL COMMENT '角色编码',
  role_name VARCHAR(64) NOT NULL COMMENT '角色名称',
  remark VARCHAR(255) DEFAULT NULL COMMENT '备注',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '状态',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_role_code (role_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='角色表';

-- 3. 用户角色关联表
CREATE TABLE sys_user_role (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  user_id BIGINT UNSIGNED NOT NULL COMMENT '用户ID',
  role_id BIGINT UNSIGNED NOT NULL COMMENT '角色ID',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  PRIMARY KEY (id),
  UNIQUE KEY uk_user_role (user_id, role_id),
  KEY idx_user_id (user_id),
  KEY idx_role_id (role_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户角色关联表';

-- 4. 登录日志表
CREATE TABLE sys_login_log (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  user_id BIGINT UNSIGNED NOT NULL COMMENT '用户ID',
  login_time DATETIME NOT NULL COMMENT '登录时间',
  login_ip VARCHAR(64) DEFAULT NULL COMMENT '登录IP',
  device_info VARCHAR(255) DEFAULT NULL COMMENT '设备信息',
  login_result TINYINT NOT NULL DEFAULT 1 COMMENT '登录结果：1成功 0失败',
  PRIMARY KEY (id),
  KEY idx_user_id (user_id),
  KEY idx_login_time (login_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='登录日志表';

-- 5. 收货地址表
CREATE TABLE sys_user_address (
  id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  user_id BIGINT UNSIGNED NOT NULL COMMENT '用户ID',
  recipient_name VARCHAR(64) NOT NULL COMMENT '收件人',
  mobile VARCHAR(20) NOT NULL COMMENT '手机号',
  province VARCHAR(64) NOT NULL COMMENT '省',
  city VARCHAR(64) NOT NULL COMMENT '市',
  district VARCHAR(64) NOT NULL COMMENT '区',
  detail_address VARCHAR(255) NOT NULL COMMENT '详细地址',
  is_default TINYINT NOT NULL DEFAULT 0 COMMENT '是否默认：1是 0否',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (id),
  KEY idx_user_id (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户收货地址表';
```

**建表顺序建议**：先建无外键依赖的表（用户、角色），再建有关联的表。

## 七、总结清单：用户中心案例复盘要点

1. **先看页面，再拆对象**：区分核心账号信息、扩展资料、关系数据、行为日志。
2. **实体识别要落到“表级别”**：用户是主表，角色是独立实体，登录日志是行为记录表，地址是附属表。
3. **主键设计要统一**：所有表采用 `BIGINT UNSIGNED` 自增主键，中间表也单独设主键。
4. **关联关系先判断类型**：用户与角色用中间表，用户与日志、用户与地址在一对多表里放 `user_id`。
5. **字段设计先分层**：核心字段放主表，扩展字段看复杂度拆表，关系字段放关联表，记录字段放日志表。
6. **最后再落 MySQL**：先出草案，再补索引和唯一约束。
7. **落地前再检查一遍**：字段名是否语义明确，是否有重复字段乱堆，是否把页面展示项误当成实体，是否把多对多关系误设计成单字段。

## 八、常见错误提醒

### 错误一：把权限和角色当成用户字段
直接在 `sys_user` 里加 `role_name`、`permission_list`。  
**正确做法：角色和权限独立建模，用户只保持关联。**

### 错误二：把所有资料都塞进用户表
头像、生日、签名、地址、登录日志全往用户表里放。  
**正确做法：主表放稳定核心字段，重复或扩展信息拆出去。**

### 错误三：用户和角色关系设计错
在用户表里放 `role_id`，以为一个用户只能有一个角色。  
**正确做法：先判断是不是多对多，能用关联表就别偷懒。**

### 错误四：日志表和业务表混淆
登录记录不是用户资料，地址也不是账号属性。  
**正确做法：记录类数据单独建表，别污染主表。**

### 错误五：字段命名随意
`name`、`type`、`status` 到处都有。  
**正确做法：字段名语义明确，例如 `role_code`、`login_result`、`recipient_name`。**

2. 拆业务对象
3. 识别实体
4. 判断关系

# 第11章 完整案例二：商品管理与订单管理如何联动设计数据库

做数据库设计，最怕表边界不清。商品管理和订单管理经常互相“借信息”，很多人一上来就把商品字段塞进订单表，或者把订单统计塞进商品表，最后越改越乱。

这一章用两个高频模块练手：**商品管理**和**订单管理**。先拆成两个小闭环，再讲清楚联动关系。按老赵的顺序来：

> **需求截图/原型示意 → 业务拆解 → 实体识别 → 表结构草案 → MySQL落库**

## 一、商品管理小闭环：从商品列表到SKU拆分

### 1. 需求截图/原型示意

商品管理后台页面包括：

- **商品列表**：名称、主图、分类、品牌、售价、库存、状态、操作
- **新增/编辑页**：
  - 基础信息：名称、副标题、品牌、分类、主图、详情图
  - 销售信息：是否多规格、规格名称/值、SKU编码、价格、库存
  - 上架/下架状态
- **分类管理页**：分类名称、上级分类、排序、状态
- **品牌管理页**：品牌名称、logo、简介、状态

先判断层次：商品层、规格层、引用层、资源层。不先分层，后面容易把所有字段堆进 `product` 一张表。

### 2. 业务拆解

常见业务对象：

- **商品 SPU**：抽象主体，如“iPhone 15”
- **SKU**：具体可卖规格，如“iPhone 15 128G 黑色”
- **分类**、**品牌**
- **商品图片**
- **库存和售价**：跟SKU走

最容易犯的错：SPU和SKU混一张表。判断标准：

- 标题、描述、品牌、分类 → 归SPU
- 可下单的规格、库存、价格、编码 → 归SKU
- 分类、品牌是独立对象

### 3. 实体识别

核心实体：

1. `product_spu`：商品主体表
2. `product_sku`：规格表
3. `product_category`：分类表
4. `product_brand`：品牌表
5. `product_image`：图片表
6. `product_sku_attr`：规格属性表

至少搞清三层：商品主体、规格明细、分类/品牌引用。

### 4. 表结构草案

#### 4.1 商品主体表 `product_spu`

| 字段 | 含义 |
|---|---|
| id | 主键 |
| product_name | 名称 |
| subtitle | 副标题 |
| brand_id | 品牌ID |
| category_id | 分类ID |
| status | 上架/下架 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

#### 4.2 SKU表 `product_sku`

| 字段 | 含义 |
|---|---|
| id | 主键 |
| spu_id | 关联商品主体 |
| sku_code | SKU编码 |
| sku_name | SKU名称 |
| price | 销售价 |
| stock | 库存 |
| status | 状态 |
| created_at | 更新时间 |

价格和库存不要直接挂SPU上。

#### 4.3 分类表 `product_category`

| 字段 | 含义 |
|---|---|
| id | 主键 |
| parent_id | 上级分类ID |
| category_name | 名称 |
| sort_no | 排序 |
| status | 状态 |

树形结构，`parent_id`不能少。

#### 4.4 品牌表 `product_brand`

| 字段 | 含义 |
|---|---|
| id | 主键 |
| brand_name | 名称 |
| logo_url | logo |
| description | 简介 |
| status | 状态 |

### 5. 主键设计

统一用自增ID或雪花ID做主键。**不要拿商品名称、SKU编码做主键**——名称会改，编码规则可能变。主键要稳定，业务字段可以变。

### 6. 外键设计

逻辑关系：`spu.brand_id → brand.id`，`spu.category_id → category.id`，`sku.spu_id → spu.id`。物理上是否加MySQL外键约束按项目定，但设计图里要把关系写清楚。

## 二、订单管理小闭环：从订单列表到订单项拆分

### 1. 需求截图/原型示意

订单模块通常有：

- **订单列表**：订单号、用户、下单时间、金额、订单状态、支付状态、发货状态
- **详情页**：买家信息、收货地址、订单项列表（名称、规格、单价、数量、小计）、支付信息、物流信息

**列表页字段不代表都要放同一张表，详情页信息也不代表必须全塞进主表。**

### 2. 业务拆解

四类核心对象：

- **订单主单**：交易核心记录
- **订单项**：买了什么
- **支付记录**：怎么付的
- **物流记录**：货怎么走的

全堆进一张表问题很快：一个订单多个商品、多次支付尝试、多次物流变化。**把主单和明细拆开。** 主表回答“这是一笔什么订单”，明细表回答“具体买了什么”，支付和物流分别回答其他过程。

### 3. 实体识别

建议拆成：

1. `trade_order`：订单主表
2. `trade_order_item`：订单项表
3. `trade_payment`：支付表
4. `trade_delivery`：物流表

### 4. 表结构草案

#### 4.1 订单主表 `trade_order`

| 字段 | 含义 |
|---|---|
| id | 主键 |
| order_no | 订单号 |
| user_id | 用户ID |
| order_amount | 总金额 |
| pay_amount | 实付金额 |
| order_status | 订单状态 |
| pay_status | 支付状态 |
| delivery_status | 发货状态 |
| receiver_name | 收货人 |
| receiver_phone | 电话 |
| receiver_address | 地址快照 |
| created_at | 下单时间 |
| updated_at | 更新时间 |

地址必须存快照，不能跟着用户中心最新地址变。

#### 4.2 订单项表 `trade_order_item`

| 字段 | 含义 |
|---|---|
| id | 主键 |
| order_id | 订单ID |
| spu_id | 商品主体ID |
| sku_id | SKU ID |
| sku_name | SKU名称快照 |
| product_name | 商品名称快照 |
| sku_price | 成交单价快照 |
| quantity | 数量 |
| item_amount | 小计金额 |

这是联动设计的核心——既要保留引用，也要保留成交快照。

#### 4.3 支付表 `trade_payment`

| 字段 | 含义 |
|---|---|
| id | 主键 |
| order_id | 订单ID |
| pay_no | 流水号 |
| pay_channel | 渠道 |
| pay_amount | 金额 |
| pay_time | 时间 |
| pay_status | 状态 |

#### 4.4 物流表 `trade_delivery`

| 字段 | 含义 |
|---|---|
| id | 主键 |
| order_id | 订单ID |
| delivery_no | 发货单号 |
| express_company | 快递公司 |
| tracking_no | 运单号 |
| delivery_status | 状态 |
| shipped_at | 发货时间 |
| received_at | 签收时间 |

### 5. 主键设计

`id` 做技术主键，`order_no` 做业务唯一号建唯一索引。业务规则可能变化，技术主键更适合关联和性能。

### 6. 外键设计

订单项、支付、物流都挂订单主单：`item.order_id → order.id`，`payment.order_id → order.id`，`delivery.order_id → order.id`。

## 三、商品与订单的联动设计：订单项是桥梁

### 1. 业务拆解

订单详情页展示商品信息，**不能只依赖实时读取**。商品可能改名、改价、下架，订单是历史记录，必须保留成交状态。

### 2. 核心原则

**商品表存当前信息，订单表存成交快照。** 订单项保存：

- `spu_id`、`sku_id`：引用原商品
- `product_name`、`sku_name`、`sku_price`：成交快照
- `quantity`：数量

### 3. 区分引用字段和快照字段

**引用字段**：`spu_id`、`sku_id`、`order_id`、`user_id`，负责建立关系。  
**快照字段**：`product_name`、`sku_name`、`sku_price`、收货地址，负责保存当时状态。  
两类都要有，缺一个订单信息就不完整。

### 4. 联动关系

```
商品模块：brand ── spu ── sku
订单模块：order ── order_item ── spu/sku（引用）
                 ├── payment
                 └── delivery
```

`trade_order_item` 是桥梁：通过 `spu_id`/`sku_id` 引用商品，通过 `order_id` 引用订单，同时保存快照。

## 四、主键、外键与索引

### 1. 主键

核心表统一用 `id`，bigint自增或雪花ID。

### 2. 外键

逻辑关联要清晰，物理约束按项目定。设计图要画明白，不能联调时说不清字段挂谁。

### 3. 索引

**商品模块**：`spu.brand_id`、`spu.category_id`、`sku.spu_id`、`sku.sku_code`（唯一索引）  
**订单模块**：`order.order_no`（唯一索引）、`order.user_id`、`order.order_status`、`item.order_id`、`payment.order_id`、`delivery.order_id`

## 七、常见错误提醒

### 错误1：把订单信息塞进商品表
在 `product_spu` 加订单号、购买人、下单时间——这属于污染。

### 错误2：把商品字段复制到订单主表
一单多商品时字段爆炸，正确做法：**订单主表+订单项表**。

### 错误3：把当前商品价格当成交价格
商品价格会变，成交价一定要存快照。

### 错误4：SKU和SPU混为一谈
有颜色、尺码、容量这种规格变化时，别把主体和可售规格揉一起。

### 错误5：只看页面不看关系
看到字段先判断它是：独立实体、引用字段、快照字段，还是统计字段？不同角色归属完全不同。

---

**先分对象，再谈字段，最后才是建表。** 拿到原型别急着写SQL，先画三层：商品层、订单层、关联层。问自己：这个字段是“现在状态”还是“成交快照”？是独立对象还是从属对象？应该挂在哪张表？答顺了这三点，数据库设计就入门了。

# 第12章 最后交付前的自检：总结清单、常见错误和改表思路

## 开篇引入：别急着交付，先做一轮“数据库体检”

前面我们把用户中心、商品管理、订单管理从页面需求一步步拆到了表结构。到了最后交付这一步，最怕的不是“没设计”，而是“设计看起来像样，实际上开发一落地就出问题”。

老赵给你一句实话：**数据库设计交付前，不是看你写了多少表，而是看这套表能不能稳稳接住业务。**

这一章只讲三件事：
1. 交付前怎么检查；
2. 最常见的错误怎么识别；
3. 需求变了以后，表该怎么改才不把系统改崩。

---

## 一、交付前总检查清单：先问自己这 8 个问题

### 1）业务对象是不是都找全了？
先看原型和需求，核心对象有没有漏掉。比如用户中心不只是 `user`，还可能有用户地址、登录日志、角色权限。如果页面里出现了“列表、表单、详情、状态切换”，背后通常就有对应实体。

### 2）一个页面是不是只对应一张表？
不是。很多页面对应的是**主表 + 明细表**。比如订单管理，订单列表是 `order`，订单商品明细是 `order_item`。判断标准：页面里如果既有“汇总信息”又有“重复行信息”，通常就不是一张表能撑住。

### 3）字段是不是都有业务意义？
标准：这个字段是否真的会被查询、筛选、展示、计算、关联。没业务意义的字段，先别往表里堆。**页面上出现，不代表数据库里必须有。**

### 4）主键是不是稳定？
主键最好稳定、唯一、不会随业务变化。常见做法是自增 ID 或雪花 ID。**不要拿手机号、用户名、商品编码这种可能变化的值当主键。** 一旦这些值变了，后面关联就会很难收拾。

### 5）外键关系是不是明确？
先确认是一对一、一对多还是多对多。写表结构草案时，要把关联字段写出来，比如 `user_address.user_id`、`order_item.order_id`、`product_category.product_id`。

### 6）列表筛选字段有没有落库？
页面里常见的筛选条件，如状态、时间、分类、创建人、更新时间，通常都要能查。

### 7）是否区分了“业务字段”和“管理字段”？
管理字段一般包括 `id`、`created_at`、`updated_at`、`deleted_at`、`status`。业务字段才是名称、价格、地址、内容这些。

### 8）这张表未来能不能扩展？
交付前想一秒：这个业务半年后会不会加字段？如果会，当前结构是不是留了空间？能拆的先拆，能扩的留口子。

---

## 二、最常见的 10 类错误：重点记住这 4 条

### 高频错误快速盘点

1. **字段堆砌：** 正确做法：只保留有存储价值的字段。
2. **关系误判：** 把一对多看成一对一，或者把多对多直接塞进主表。比如商品和分类，很多人会直接在商品表里放一个 `category_name`，结果一个商品多个分类时就崩了。
3. **主键不稳：** 把手机号、编码、名称当主键。主键要尽量和业务含义解耦。
4. **外键乱放：** 外键不是越多越好。但关联字段必须设计清楚，字段名、关联方向不能含糊。
5. **状态字段设计混乱：** 设计文档里要写清楚：`0=停用，1=启用`，或者 `0=待支付，1=已支付`。
6. **时间字段缺失：** 没有 `created_at`、`updated_at`，后面查问题很难。
7. **明细表被省掉：** 一条主记录对应多个重复条目时，就该拆明细表。
8. **重复字段太多：** 核心事实尽量保持单一来源。
9. **不考虑删除策略：** 很多业务更适合逻辑删除。
10. **一个页面对应一张表：** 页面是展示层，表是数据层，不能硬一一对应。

---

## 三、需求变更时怎么改表：别硬改，先分层处理

### 情况1：只是新增一个普通字段
比如用户中心新增“生日”。直接在用户表加字段即可：
```sql
ALTER TABLE user ADD COLUMN birthday date NULL COMMENT '生日';
```

### 情况2：新增的是一组重复信息
比如用户要增加多个收货地址。新建地址表：`user` + `user_address`。**拆表，不是堆字段**。

### 情况3：新增的是可选功能模块
比如订单新增“发票信息”。如果字段很多，建议单独建 `order_invoice`，做一对一或一对多关联。

### 情况4：原来的关系判断错了
比如原来以为商品只属于一个分类，后来发现一个商品可以挂多个分类。改成中间表：`product` + `category` + `product_category`。

### 改表原则就一句话：
**优先新增表，其次新增字段，最后才考虑改老结构。**

## 四、完整案例：对前面三个案例做统一复盘

### 1）用户中心案例
**实体识别：** `user`、`user_address`
**表结构草案：**
- `user(id, username, phone, status, created_at, updated_at)`
- `user_address(id, user_id, receiver_name, receiver_phone, detail_address, is_default)`
**MySQL落库：** 先建 `user`，再建 `user_address`。

### 2）商品管理案例
**实体识别：** `product`、`category`、`product_category`
**表结构草案：**
- `product(id, name, price, status, ...)`
- `category(id, name, parent_id)`
- `product_category(product_id, category_id)`
**关键点：** 多分类直接上中间表。

### 3）订单管理案例
**实体识别：** `order`、`order_item`、`order_shipping`
**表结构草案：**
- `order(id, order_no, user_id, total_amount, status, created_at)`
- `order_item(id, order_id, product_id, product_name, price, quantity)`
- `order_shipping(id, order_id, receiver_name, receiver_phone, address)`
**关键点：** 订单表负责“单据头”，明细表负责“明细行”。

## 五、交付给开发的注意事项

交付文档至少包含这5部分：
1. **表清单**：有哪些表，各自负责什么；
2. **字段说明**：字段名、类型、含义、是否必填；
3. **主键设计**：主键是什么，是否自增；
4. **关联关系**：一对一、一对多、多对多怎么连；
5. **建表顺序**：先建主表还是先建关联表。

## 常见错误提醒（快速记忆版）

1. 别把页面元素当字段全塞进去
2. 别把“能显示”误认为“必须落库”
3. 别在主表里硬塞重复明细
4. 别用会变化的业务值做主键
5. 别忽略关系类型，尤其是多对多
6. 别交付一份只有表名、没有说明的文档
7. 别等上线后才想“这个字段应该单独建表”

## 结尾小结：先稳住结构，再谈优化

数据库设计不是一次性写完就结束。真正靠谱的做法是：**先保证结构能支撑业务，再考虑性能和扩展。**

你从UI原型出发，走到实体识别、字段梳理、主键外键设计，最后再做一轮交付前自检——这样出来的表，开发才接得住，后续需求变更也不容易炸。
