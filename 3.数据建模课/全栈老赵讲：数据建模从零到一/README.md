# 第1章：先把话说明白——数据建模到底是在干什么

## 开篇引入：先别急着画表

很多人学数据库，第一反应就是问：表怎么建、字段怎么加、索引怎么配。问题是，如果业务没想明白，表画得再漂亮，后面也容易改到怀疑人生。

老赵见过不少新手，一拿到需求就直接开干：先建用户表，再建订单表，地址不够就塞订单里，状态不够就再加几个字段。短期看挺快，长期看却容易字段打架、查询绕弯，最后不是补丁就是重构。

**数据建模，本质上不是“画表”，而是把业务世界翻译成数据结构。**  
业务里有用户、订单、帖子、预约、支付这些对象；建模要做的，就是把这些对象、动作、关系，整理成一套清晰、可维护、可查询的数据表达方式。

所以，建模不是先问“数据库里放什么字段”，而是先问：

- 业务里有哪些对象？
- 这些对象之间什么关系？
- 哪些信息必须保存？
- 哪些信息会重复？
- 哪些查询要优先支持？

这一步想清楚了，后面落表才不会乱。

---

## 一、数据建模的本质：把业务世界翻译成数据结构

你可以把数据建模理解成一次“翻译工作”。

比如论坛业务里，用户发帖、回帖、点赞、关注，这些是业务语言。落到模型里，就会变成用户表、帖子表、评论表、点赞关系表、关注关系表。这里不是简单列几张表，而是把“谁做了什么、跟谁有关、什么时候发生”拆成可以存、可以查、可以扩展的数据结构。

再比如预约系统，用户预约服务、选择时间、确认状态、取消预约，这些动作看着自然，但落到数据里，你必须想清楚：预约记录是不是独立存在，服务项目是否固定，取消后状态怎么留痕。这些问题不先想明白，后面就会越改越乱。

**判断一个模型好不好，最基本看三点：**

1. 能不能准确表达业务  
2. 能不能支持常见查询  
3. 后续加功能时会不会大改  

如果这三点都顾不上，那通常不是建模，是临时拼凑。

## 二、为什么不能直接拍脑袋建表

新手最常见的问题，就是看到需求就直接开干：

- “先来个用户表”
- “再来个订单表”
- “地址放哪？先塞订单里吧”
- “状态不够？再加几个字段”

这种做法短期看快，长期看问题很多。

### 常见坑有三个

**1. 字段越加越乱**  
一开始“备注”“扩展字段”“状态码”还能凑合，后面业务复杂了，字段语义就开始打架。比如一个“状态”字段，既表示审核状态，又表示支付状态，最后谁看谁迷糊。

**2. 重复数据越来越多**  
比如订单里反复存客户姓名、手机号、地址，看似方便查，实际上改一次信息要同步很多处，容易不一致。今天改了收货地址，历史订单要不要跟着变？这类问题不提前设计，后面一定会出争议。

**3. 关系设计含糊**  
比如帖子和评论、订单和商品、预约和服务项目，如果关系没理清，后面统计、联查、历史追溯都会很别扭。SQL 会越写越长，业务语义却越来越模糊。

所以，拍脑袋建表的问题不在于慢，而在于**把后面的复杂度提前埋进去**。

## 三、建模到底要解决什么问题

数据建模不是为了“显得规范”，而是要同时解决四类问题。

### 1. 表达业务

模型首先要把业务说清楚。  
比如预约系统里，谁预约谁、预约什么、预约在什么时间、是否确认、是否取消，这些都要在模型里有位置。

如果模型表达不清楚，业务说一遍，研发理解一遍，数据库又是另一套，就会反复返工。模型越模糊，沟通成本越高。

### 2. 支撑查询

模型不是纸上结构，它最终要服务查询。

比如论坛要查：

- 某个用户发了什么帖
- 某个帖子有哪些评论
- 最近热门帖子有哪些

如果这些查询在模型里完全没有铺垫，后面就只能靠临时拼 SQL，甚至靠加冗余字段硬扛。建模时就要先想：哪些是高频查询，哪些是关联查询，哪些是统计查询。

### 3. 方便扩展

业务一定会变。今天只有下单，明天可能要退款；今天只有单次预约，明天可能要改成周期预约。

好的模型不是把未来全预测准，而是尽量让变化来时，不至于推倒重来。也就是说，尽量让“新增功能”变成“新增数据”，而不是“重做结构”。

### 4. 降低混乱

一个不好的模型，往往不是性能差，而是**谁都能解释一遍，最后没人说得清**。

模型的价值之一，就是让团队对“这个数据是什么、从哪来、该放哪”有统一理解。统一了，开发、测试、产品、运营沟通起来都会轻松很多。

## 四、建模和“画表设计字段”有什么区别

这两个事相关，但不是一回事。

### 画表设计字段
更像是在做“落地实现”：

- 表名叫什么
- 字段有哪些
- 主键怎么定
- 索引怎么建

### 数据建模
更像是在做“业务结构设计”：

- 先识别实体
- 再理清关系
- 再决定哪些字段属于谁
- 最后才落成表结构

你可以把它理解成：

- **概念模型**：先把业务对象和关系想明白，像画草图
- **逻辑模型**：把对象、属性、关系整理成更规范的结构
- **物理模型**：真正落到 MySQL 表、字段、类型、索引上

也就是说，**建模不等于建表，但建表一定要以建模为基础**。先建模，是为了少走弯路；后建表，是为了把思路落地。

## 五、本书怎么学：三步走，三套小案例

接下来这本书不会只讲概念，而是按“先理解，再拆解，再落地”的顺序来。

### 案例一：论坛系统
用论坛来讲清楚：

- 怎么从原型或文档抽象实体
- 怎么识别用户、帖子、评论、点赞这些对象
- 怎么区分“一对多”和“多对多”

比如，用户和帖子通常是一对多；用户和点赞对象往往是多对多，需要单独设计关系表。这个案例会帮你建立第一层建模直觉。

### 案例二：预约系统
用预约系统来练习：

- 怎么从业务流程抽取数据需求
- 怎么处理状态、时间、取消、确认这些字段
- 怎么平衡规范和查询效率

预约系统特别适合练“从流程看数据”，因为一个动作背后往往对应多个状态变化，最能看出模型是否完整。

### 案例三：订单系统
用订单系统来做综合训练：

- 怎么处理订单、订单项、商品、客户之间的关系
- 怎么处理冗余与重复
- 怎么把逻辑模型真正落到 MySQL

订单系统是很多业务的核心，既能练实体识别，也能练字段拆分和落表实现，后面会反复用到。

---

## 结尾小结：先建立共同语言，再开始动手

这一章你只要记住一句话：

**数据建模，就是把业务世界翻译成能够稳定表达、方便查询、便于扩展的数据结构。**

在动手之前，先别急着拍表，先问自己四个问题：

1. 业务里有哪些对象？
2. 对象之间是什么关系？
3. 哪些信息必须保存？
4. 未来最常见的查询是什么？

后面我们会一步一步从实体识别、字段拆分、关系设计，讲到范式意识、反范式思考、模型校验，最后落到 MySQL 实现。你不用一开始就全会，跟着案例走，慢慢就能把建模思维建立起来。

# 第2章：先看业务，再看表——从业务对象、流程、关系入手

## 开篇引入：别急着画表，先把业务看明白

很多人做数据建模，一上来就问：“这个系统该建几张表？”  
老赵通常会先反问一句：“你这个业务里，到底有哪些人、哪些东西、哪些动作、哪些联系？”

这不是故意刁难，而是建模顺序不能反。数据库表只是业务的落地结果，前面如果没把业务看清楚，后面字段再漂亮、索引再讲究，也容易跑偏。比如把“预约”业务只看成一张预约表，结果后面又冒出确认、取消、核销、改期，最后不是字段越堆越乱，就是状态越写越玄。

所以这一章先不急着落表，先学会三件事：**找业务对象、看业务流程、理业务关系**。这三步走稳了，后面的实体识别、字段拆分、关系设计才有根。

---

## 一、业务对象是什么，怎样从场景里找出来

所谓业务对象，就是业务里“被管理、被记录、被操作”的东西。它可以是人、商品、订单、帖子、预约、课程，也可以是地址、积分、支付记录这类辅助对象。只要这个东西在业务里会被新增、查询、修改、关联、流转，就值得认真看一眼。

### 怎么找？

你可以从三个角度扫一遍场景：

1. **名词法**：先把描述里的名词圈出来。  
   比如“用户发布帖子并评论”，用户、帖子、评论就是候选对象。

2. **动作法**：看谁在做什么。  
   “发布”“预约”“支付”“审核”这些动作，往往会牵出对象和记录。动作一出现，通常就意味着要留痕。

3. **结果法**：看业务最后要留下什么痕迹。  
   例如预约成功后，系统通常要记录预约人、时间、门店、状态；订单支付后，要记录金额、支付方式、支付结果。

### 先别急着分主次

初学者容易一上来就判断：“这个是主表，那个只是附属字段。”  
别着急。先把候选对象都找出来，再判断哪些是核心对象，哪些是辅助对象，哪些只是某个对象的字段。比如“地址”在用户场景里可能只是属性，但在订单场景里又可能是独立的收货信息对象。要看业务，不是看名字。

### 常见误区

- 把页面控件当对象，比如“按钮”“弹窗”不算业务对象。
- 把展示需要的临时信息当核心对象。
- 只找名词，不看动作，容易漏掉记录类对象。
- 一看到“备注”“类型”“状态”就当成独立对象，其实很多时候只是字段。

---

## 二、业务流程如何影响数据需求

同一个业务对象，放在不同流程里，数据需求会完全不同。  
比如“订单”这个对象，如果只看下单，你可能觉得只要订单号、金额、状态就够了；但把流程拉开，就会发现还要有支付时间、发货时间、退款状态、取消原因等信息。

### 先问流程里的几个问题

老赵建议你拿到一个业务，先顺着流程问自己：

- 这个业务是**谁发起**的？
- 中间经过哪些**步骤**？
- 每一步要不要**留痕**？
- 哪些状态会变？
- 哪些信息只在某个环节出现？
- 哪些信息后面还要反复查询、统计？

这几问一过，数据需求基本就显形了。

### 举个简单例子

在“预约系统”里，用户预约后，流程可能是：

1. 用户选择服务和时间  
2. 系统生成预约单  
3. 门店确认是否可接待  
4. 到店后核销  
5. 预约完成或取消  

流程一展开，数据就不只是“预约人+时间”这么简单了，还会自然长出这些内容：

- 预约单主信息
- 预约状态流转
- 确认时间、核销时间
- 取消原因
- 服务项目
- 门店信息

### 流程决定字段，不是反过来

很多人先想到字段，再去硬套流程，结果就会出现“字段看起来不少，但业务一跑就缺”。  
正确顺序是：**先看流程，再想记录点。**  
流程里每个关键动作，通常都对应一个需要记录的时间点、状态点、责任人或者结果值。把这些点找出来，模型就不会太飘。

---

## 三、业务关系如何决定表之间的连接方式

对象之间不是孤立的，真正麻烦的地方，往往在关系。

### 先分清三种常见关系

1. **一对一**  
   比如用户和用户资料。一个用户通常对应一份扩展资料。  
   这种关系常见于主表和扩展表：主表放核心信息，扩展表放不常用、可选填的补充信息。

2. **一对多**  
   比如一个用户发多篇帖子，一个订单包含多个订单明细。  
   这是最常见的关系，通常用外键表达。一个“主对象”管多个“从对象”。

3. **多对多**  
   比如用户和标签、课程和学生、帖子和分类。  
   这种关系不能直接硬连，通常要拆成中间表，不然后面查询、维护、统计都会别扭。

### 判断关系时别只看名字

老赵常用一句最土但很管用的话：“A 记录能不能同时对应多个 B？B 能不能同时对应多个 A？”  
这比死记硬背更靠谱。

比如：

- 一个用户能不能发多篇帖子？能。
- 一篇帖子能不能被多个用户点赞？能。
- 一个用户能不能同时给多个帖子点赞？也能。

那点赞就是典型多对多关系，通常要有“点赞记录表”。

### 关系设计不是为了省表

有些人总觉得“表越少越好”，于是把很多关系揉进一张大表里。短期看好像省事，后面一改需求就开始崩。  
关系设计的目标不是减少表数量，而是让数据表达清楚、维护方便、查询合理。该拆的时候别舍不得拆。

## 四、从原型、文档、口头描述中抓取建模线索

现实项目里，需求往往不是一份标准说明书，而是原型图、聊天记录、口头描述混在一起。  
这时建模的关键，不是“听懂了没有”，而是“能不能抓住线索”。

### 1. 从原型里看什么

- 页面上反复出现的内容，往往是核心对象
- 可编辑的区域，常对应字段
- 列表页、详情页、筛选项，都是数据来源
- 一个按钮背后往往对应一个流程动作，比如提交、审核、取消

### 2. 从文档里看什么

重点看这些词：

- 业务规则
- 状态变化
- 角色权限
- 特殊条件和例外情况

这些内容往往决定字段是否需要保留、是否需要拆表、是否需要记录历史。

### 3. 从口头描述里补什么

口头需求最容易漏边界，所以要追问：

- 这个对象是否需要唯一编号？
- 是否要记录历史？
- 是否允许重复？
- 状态变化是否要保留轨迹？
- 以后是否还会扩展更多类型？

### 实用方法：先整理词汇表

拿到任何材料，先做一张“业务词汇表”：

- 名词：可能的实体
- 动词：可能的流程
- 形容词/限制词：可能的状态、条件、规则

这个动作看似简单，但非常好用。很多模型问题，都是从没整理词汇开始的。

## 五、用一个小案例演示：论坛发帖业务怎么分析

我们用一个小论坛来走一遍。

### 1. 先找业务对象

从“用户发帖、评论、点赞、收藏”里，可以先识别出：

- 用户
- 帖子
- 评论
- 点赞记录
- 收藏记录

这里不要急着细分字段，先把对象找全。找全以后再讨论谁是核心，谁是辅助。

### 2. 再看流程

论坛常见流程是：

- 用户注册/登录
- 用户发帖
- 其他用户评论或点赞
- 帖子被删除、置顶、审核

流程告诉我们，帖子不只是“标题+内容”，还要有状态、发布时间、作者、审核信息等。评论也不只是“内容”，通常还要有评论人、评论时间、所属帖子、是否被删除。

### 3. 再看关系

- 一个用户可以发多篇帖子：一对多
- 一篇帖子可以有多条评论：一对多
- 一个用户可以点赞多篇帖子，一篇帖子也能被很多用户点赞：多对多，需要点赞记录表
- 收藏同理，也通常需要中间记录表

### 4. 初步结论

到这一步，我们还没正式建表，但已经能大致说出模型轮廓：

- 用户表
- 帖子表
- 评论表
- 点赞记录表
- 收藏记录表

这就是从业务出发做建模的第一步：**先把对象、流程、关系看清楚，再进入实体和字段设计。**

---

## 结尾小结：先看业务，再谈结构

这一章你只要记住一句话：**建模不是先画表，而是先还原业务。**

具体做法也不复杂：

1. 先找业务对象  
2. 再看业务流程  
3. 然后理清业务关系  
4. 从原型、文档、口头描述里补线索  
5. 最后才进入实体和字段设计  

如果你以后接到一个新需求，先别急着开 SQL。先问自己：这门业务里到底有哪些对象、哪些动作、哪些关系。这个习惯养成了，后面你做实体识别、属性拆分、关系设计，才会越来越稳。

下一章，我们就从这些业务对象出发，正式进入“实体识别”和“属性拆分”，把业务语言一步步翻成模型语言。

# 第3章：三层模型别搞混——概念模型、逻辑模型、物理模型

## 开篇引入：先把“画图”这件事分清楚

很多初学者一上来就问：

“老赵，我是不是得先把表结构建出来？”

这就是最常见的误区之一。

建模不是先拍脑袋定字段，更不是先把 MySQL 表名、字段类型一股脑写出来。正确顺序是：先看业务，再抽象，再设计，最后才落库。你可以把它理解成盖房子：先看用途和地基，再画结构图，最后才施工。顺序一乱，后面就容易返工。

在数据建模里，最容易混的就是三层模型：

- **概念模型**：站在业务角度，描述“世界里有什么”
- **逻辑模型**：把业务概念变成“可以设计的数据结构”
- **物理模型**：落到具体数据库里，变成“能直接建表的东西”

如果这三层分不清，常见问题就有两个：

1. 业务没搞清，表先建好了，后面改得一团乱；
2. 业务本来很简单，却设计得过重，维护成本很高。

所以这一章，咱们先把这三层模型彻底掰开。你只要能分清它们的职责边界，后面的实体识别、字段拆分、关系设计，才有真正的落点。

---

## 一、概念模型：站在业务角度描述世界

### 1. 概念模型回答的是什么问题？

概念模型只回答一件事：**这个业务里有哪些核心对象，它们之间是什么关系？**

它不关心字段类型，不关心主键怎么选，也不关心是 `varchar(50)` 还是 `bigint`。它只关心业务上的“名词”和“关系”。

你可以把概念模型理解成“业务语言版的地图”。它不是给数据库看的，是给业务、产品、开发一起对齐认知用的。只要大家看到这张图，能说清楚系统里有哪些东西、这些东西怎么互相关联，概念模型就算发挥作用了。

比如做一个论坛系统，概念模型里你会先想到：

- 用户
- 帖子
- 评论
- 版块
- 点赞

再看它们的关系：

- 一个用户可以发多个帖子
- 一个帖子可以有多条评论
- 一个帖子属于一个版块
- 一个用户可以点赞多个帖子

这就是概念模型的价值：**先把业务世界讲明白。**

### 2. 概念模型怎么画、怎么想？

初学者可以按这个顺序来：

**第一步：找业务名词**  
从需求文档、原型图、页面按钮、业务口述里，把名词圈出来。

**第二步：筛核心对象**  
不是所有名词都能当实体。比如“按钮”“页面”“搜索结果”通常不算核心实体，它们更多是界面或结果，不是业务长期存在的对象。

**第三步：识别关系**  
看这些对象之间是“一对一”“一对多”还是“多对多”。

**第四步：只保留业务语言**  
概念模型里尽量不用字段细节，更不要急着写表结构。你现在要做的是“说清楚业务”，不是“写 SQL”。

简单判断：如果你在画图时已经开始纠结 `user_name` 还是 `nickname`，那就说明你已经跑到后面的层次去了。

### 3. 论坛小案例：概念层先别急着落表

假设你在做一个小论坛，业务描述如下：

> 用户可以注册登录，发布帖子，帖子可以被评论和点赞，管理员可以管理版块和帖子。

概念层先抽象出：

- 用户
- 帖子
- 评论
- 点赞
- 版块
- 管理员

这时候你不需要马上问：

- 用户名要不要唯一索引？
- 点赞表是不是要加时间戳？
- 帖子内容是不是要分主表和扩展表？

这些都属于后面层次要解决的问题。概念模型的任务只有一个：**把业务骨架搭出来。**

---

## 二、逻辑模型：把概念转成可设计的数据结构

### 1. 逻辑模型回答什么问题？

如果说概念模型是“业务世界长什么样”，那逻辑模型就是：

**这些对象要怎么组织成可设计、可分析、可讨论的数据结构？**

逻辑模型开始进入数据设计思维，但还没完全绑定数据库产品。你会开始关心：

- 实体怎么拆分
- 属性怎么归类
- 主键怎么选
- 关系怎么表达
- 哪些字段放一起，哪些字段要拆开

简单说，概念模型偏“讲故事”，逻辑模型偏“搭骨架”。

### 2. 逻辑模型里最重要的三件事

#### ① 实体识别

不是所有名词都能直接建实体，要判断它是不是“有独立生命周期”的对象。

比如论坛里：

- 用户：是实体
- 帖子：是实体
- 评论：是实体
- 点赞：通常也是实体，因为它有独立记录和关系
- “热门”：不是实体，通常是统计结果或状态

判断一个对象要不要做实体，主要看三点：

- 它是不是业务中经常单独被引用？
- 它是不是会单独新增、修改、查询？
- 它是不是需要被长期保存和追踪？

如果答案大多是“是”，那它大概率值得成为实体。

#### ② 属性拆分与字段归类

逻辑模型阶段，要开始思考字段怎么放。比如“用户”这个实体，可以拆出：

- 基本信息：用户名、手机号、密码、昵称
- 状态信息：是否禁用、注册时间、最后登录时间
- 扩展信息：头像、简介、地区

这里的关键不是机械拆字段，而是按业务含义归类。字段归类的目的，是让后面建表时结构更清晰、维护更方便。

比如“头像”和“手机号”都属于用户属性，但它们的重要程度不同、修改频率不同、使用场景也不同。把这些字段先分清楚，后面你才知道是放在主表里，还是拆到扩展表里，或者是否需要单独的配置结构。

#### ③ 关系设计

逻辑模型要把业务关系落成数据关系：

- 一对多：用户-帖子
- 多对多：用户-版块关注
- 关联实体：点赞、收藏、报名、预约

很多初学者一看到多对多就想“先放个数组”。这在业务设计里通常是危险信号。多对多关系，往往要通过中间实体来表达。比如“用户关注版块”，不是把版块 ID 填成一个数组塞进用户表，而是要用一张关注关系表来记录谁关注了谁、什么时候关注的、是否取消关注。

### 3. 预约系统小案例：逻辑模型怎么转？

以预约系统为例，业务是：

> 用户可以预约服务，商家可以管理时段，一个预约对应一个用户和一个服务时段。

概念层你会得到：

- 用户
- 商家
- 服务
- 时段
- 预约

逻辑层就开始细化：

- 用户实体：用户ID、姓名、手机号
- 商家实体：商家ID、名称、状态
- 服务实体：服务ID、服务名、价格
- 时段实体：时段ID、商家ID、开始时间、结束时间、可预约人数
- 预约实体：预约ID、用户ID、时段ID、预约状态、创建时间

这里你会看到，逻辑模型已经非常接近建模实战了。它开始有“谁关联谁”“谁依赖谁”“哪些字段是核心”的味道了。

再进一步想一下：如果预约成功后还要记录“取消原因”“服务备注”“到店状态”，这些字段是不是都要塞进预约表？不一定。要看它们是不是预约过程中的核心信息，还是后续才会补充的扩展信息。逻辑层的意义，就是提前把这些问题想清楚，避免后面物理层乱塞字段。

---

## 三、物理模型：落到具体数据库和字段类型

### 1. 物理模型回答什么问题？

物理模型就是把前面的设计，真正变成数据库可以执行的东西。这里开始涉及：

- 表名
- 字段名
- 字段类型
- 主键
- 索引
- 唯一约束
- 是否允许为空
- 字符集、存储引擎等

一句话：**逻辑模型是设计思路，物理模型是落地代码。**

到了这一步，你不能只考虑“业务上说得通”，还要考虑“数据库里跑得动”。同样一个字段，逻辑上都叫手机号，物理上就得决定它是 `varchar(20)` 还是别的类型；同样一条关系，逻辑上能连起来，物理上还得考虑索引和查询效率。

### 2. 物理模型里必须考虑什么？

#### ① 字段类型

比如：

- 用户ID：`bigint`
- 手机号：`varchar(20)`
- 金额：`decimal(10,2)`
- 时间：`datetime`

字段类型不是随便选的。它会影响存储、查询、排序、精度和后续扩展。

比如金额不能用浮点类型去凑合，不然以后订单金额、退款金额、统计汇总都容易出问题。再比如手机号不是数字运算字段，通常用字符串存更稳妥，因为它可能包含前导 0，也不需要做数学计算。

#### ② 主键与索引

物理模型要考虑查询效率。比如预约系统里，常查的字段可能是：

- 用户ID
- 商家ID
- 时段ID
- 预约状态

这些字段在物理层就要考虑是否建索引。

但索引不是越多越好。索引加多了，查询可能快一点，写入和更新就会慢一点。建模不是“字段堆得越满越专业”，而是“该有的有，不该乱加的别加”。

#### ③ 约束

比如：

- 手机号不能重复
- 预约时段不能超卖
- 预约状态只能是固定几个值

这些在逻辑上是规则，在物理上要变成约束或校验逻辑。你可以通过唯一索引、非空约束、默认值、状态码，或者业务层校验来实现。核心是：业务规则不能只停留在嘴上，最终要落到数据层能约束的地方。

### 3. 订单系统小案例：物理模型怎么落 MySQL？

假设我们做一个简化订单系统：

- 用户下单
- 一个订单里可以有多个商品
- 订单有状态、金额、创建时间

逻辑模型里你可能有：

- 用户
- 订单
- 订单明细
- 商品

物理层落到 MySQL 时，通常会考虑：

- `user` 表：用户基础信息
- `order` 表：订单主表
- `order_item` 表：订单明细表
- `product` 表：商品表

其中：

- `order` 和 `order_item` 是典型的一对多
- `order_item` 里会存订单ID、商品ID、数量、成交价
- `order` 里会存总金额、状态、创建时间

如果你在物理模型里直接把所有商品字段都塞进订单表，后面商品改名、价格变动、订单追溯都会很难处理。订单表应该保存“下单那一刻的成交信息”，而不是把商品当前状态全搬进去。这个区别很重要，因为它直接影响历史数据是否可信。

## 四、三层模型之间如何递进转换

### 1. 正确顺序是什么？

建议你按这个链路走：

**业务描述 → 概念模型 → 逻辑模型 → 物理模型**

别倒着来。

很多初学者习惯从表开始想，结果一上来就卡在字段命名、类型选择、外键设计这些细节里，业务反而没看清。正确做法是先把对象和关系理顺，再逐步下沉到表结构。

### 2. 每一层转换时，要做什么？

#### 从业务到概念：抽名词、抽关系

目标是看清业务骨架。你要找的是“谁参与了这个业务”“业务围绕哪些核心对象展开”。

#### 从概念到逻辑：拆实体、理属性、定关系

目标是让业务对象具备数据结构感。你要开始判断哪些对象独立存在，哪些字段应该归类，哪些关系要用中间表表达。

#### 从逻辑到物理：定字段、定类型、定索引、定约束

目标是让设计能在 MySQL 里真正落地。你开始回答的是“字段叫什么”“类型用什么”“能不能为空”“需不需要索引”。

### 3. 一个判断标准：这一层能不能回答当前问题？

- 概念层：回答“系统里有什么”
- 逻辑层：回答“这些东西怎么组织”
- 物理层：回答“数据库里怎么建”

如果你在概念层讨论 `varchar`，那就是跑偏了。  
如果你在物理层还在说“这个业务对象应该是什么”，那就是太晚了。

每一层就做每一层该做的事，别混着来，效率反而更高。

## 五、常见混淆点与实战中的判断方法

### 1. 混淆点一：把概念模型当表结构图

很多人一画图就画成表名、字段名、外键线。这其实已经是物理模型了，不是概念模型。

**判断方法**：  
如果图里出现大量字段、类型、索引，那基本就不是概念模型。概念模型要尽量干净，只保留核心业务对象和关系。

### 2. 混淆点二：把逻辑模型直接跳成 MySQL 表

逻辑模型还没想清楚，表就建好了，常见后果是：

- 表名不统一
- 字段重复
- 关系处理混乱
- 后面一改全改

**判断方法**：  
如果你还没明确业务关系，就先别急着写建表 SQL。先把实体、属性、关系捋顺，再动手会省很多返工。

### 3. 混淆点三：概念、逻辑、物理混成一个东西

这是初学者最容易踩的坑。正确做法是：**每层只解决它该解决的问题。**

你可以把这三层记成一句顺口的话：

- 概念层：看“有什么”
- 逻辑层：想“怎么组织”
- 物理层：定“怎么存”

### 4. 实战检查清单

你可以拿着下面这份清单自检：

- 我是否已经从需求里提取出核心业务对象？
- 我是否区分了业务名词和页面控件？
- 我是否明确了实体之间的关系？
- 我是否给字段做了合理归类？
- 我是否把逻辑设计和数据库实现分开考虑？
- 我是否在物理层考虑了类型、索引和约束？
- 我是否避免了“先建表后补业务”的倒序做法？

如果这几项你都能答上来，说明你已经开始具备建模的基本分层意识了。

---

## 本章小结：先分层，再动手

这一章你只要记住一句话：**数据建模不是一张图，而是三层递进的思考过程。**

- **概念模型**，站在业务角度看世界
- **逻辑模型**，把业务变成可设计的数据结构
- **物理模型**，把设计落成 MySQL 里的表、字段、索引和约束

真正会建模的人，不是表画得最复杂的人，而是能把业务抽象、设计、落地这三件事分清楚的人。

### 行动建议

接下来你可以拿一个小业务练手，比如论坛、预约系统或订单系统，按下面步骤走一遍：

1. 先写业务描述，不要急着建表  
2. 圈出核心名词，画概念模型  
3. 拆实体、理属性、定关系，形成逻辑模型  
4. 最后再转换成 MySQL 表结构  
5. 检查有没有把三层混在一起

下一章开始，我们就按这个思路，真正进入“从业务对象识别实体”的实战环节。

# 第4章：从原型和文档里抠出实体——实体识别的实战方法

## 开篇引入：别急着画表，先把“业务里有什么东西”找出来

很多同学一上来就想建表，看到“用户、帖子、评论、点赞”就直接开画。结果做到后面才发现：有的东西该单独存没存，有的不该拆却拆得太碎；前端一改页面，后端表就跟着乱。

老赵带项目时，先练的不是 ER 图，而是**识别实体**。因为实体识别就是建模入口。你能不能从原型、文档、需求描述里把“值得被数据化的对象”抠出来，直接决定后面的模型稳不稳。

这一章讲三件事：**怎么从页面原型、业务文档里找实体，怎么从名词、动词、状态词里筛候选对象，最后用论坛、预约、订单做完整抽取。**

---

## 一、从页面原型识别实体：先看界面上反复出现了什么

### 1. 原型是线索图，不是 UI 图

看原型时，盯住**反复出现的名词**和**能被操作的数据块**。

比如一个论坛原型里，首页可能有：版块列表、帖子列表、热门标签、最新回复、用户头像、发帖按钮。

按钮只是操作入口，真正要关注的是：版块、帖子、标签、回复、用户。这些才是需要持久化的数据对象。

### 2. 三个抓手帮你快速锁定实体

**抓手一：看“重复出现”的内容。** 如果某个对象在多个页面都出现，比如“用户”在帖子页、评论页、个人中心都出现，它大概率是核心实体。

**抓手二：看“被管理”的内容。** 能新增、编辑、删除、查询的对象，通常有建表价值。

**抓手三：看“有独立生命周期”的内容。** 如果一个对象有自己的创建、审核、取消、关闭流程，就不要塞进别的表里。

### 3. 实操步骤模板

1. 把页面上的所有名词圈出来  
2. 标记哪些是“展示用”，哪些是“业务对象”  
3. 找出跨页面重复出现的名词  
4. 找出有新增、编辑、查询、状态变化的对象  
5. 列出候选实体清单  
6. 判断哪些要建表，哪些只是字段或枚举  

**老赵提醒：** 看到“个人简介”“头像”“昵称”就拆三张表？别急，它们多数只是用户实体的字段。

### 4. 常见误区速查

- ❌ 把页面元素当实体：例如“弹窗”“按钮”不是实体。  
- ❌ 把展示结果当实体：例如“热门”“推荐”通常是查询结果。  
- ❌ 把局部字段拆成表：例如用户昵称、头像、手机号，通常是用户表字段。  

---

## 二、从业务文档识别实体：别只看标题，要抠动词背后的对象

### 1. 动词帮你找到实体之间的关系

需求文档里，动词能帮你定位实体之间的关系。

例如：用户发布帖子、用户回复帖子、管理员删除违规回复、系统给帖子打标签、用户预约某个时间段、用户下单购买服务、订单支付成功生成发货记录。

很多实体，正是在这些动作里“长出来”的。

### 2. 四类信息提取模板

| 信息类型 | 示例 | 处理方法 |
|---------|------|---------|
| 名词对象 | 用户、帖子、预约、订单 | 直接圈出，作为候选实体 |
| 动作对象 | 发布、回复、预约、支付 | 不直接建表，但提示关系 |
| 状态对象 | 待支付、已支付、已取消 | 提示生命周期，决定是否建表 |
| 约束对象 | “每个用户每天只能预约一次” | 影响唯一键和中间表设计 |

### 3. 一句话抽取法：改写“谁对谁做了什么”

比如：用户提交预约 → 系统创建预约单 → 商家确认预约 → 用户取消预约

核心对象是：**用户、商家、预约单**。动作结果落在预约单这个实体。

**实操小技巧：** 不断问自己——这句话里谁是对象，谁是动作，动作结果落在哪里？

---

## 三、从名词、动词、状态词中筛选候选实体

### 1. 名词筛选五问

- 它是不是业务里长期存在的对象？
- 它有没有自己的属性？
- 它会不会被单独查询、修改、统计？
- 它会不会被多处引用？
- 它有没有独立生命周期？

满足得越多，越像实体。例如：“用户”是实体，“用户名”只是它的属性。“订单”是实体，“订单状态”只是属性。

### 2. 动词和状态词的提示作用

**动词**（发布、评论、预约）提示实体之间的关联关系。例如“用户评论帖子”，有“用户”“帖子”“评论”。如果评论还支持回复、删除、审核，它就更像需要独立管理的实体。

**状态词**（待处理、已取消、已完成）说明对象会变化。状态越多，越要提前想清楚状态是否可逆、可追踪、有流转限制。

### 3. 分级筛选模板

| 级别 | 标准 | 示例 | 处理方式 |
|------|------|------|---------|
| 一级候选实体 | 有独立生命周期，被多处引用 | 用户、订单、预约单 | 必须建表 |
| 二级候选实体 | 有多条记录需求，有独立属性 | 评论、订单项、预约时段 | 大概率建表 |
| 字段或枚举 | 无独立生命周期，单一值 | 性别、状态、类型 | 不单独建表 |

**老赵提醒：** 先学会“收”，再学会“拆”。能放字段的先放字段，能放枚举的就别硬拆。

## 四、判断一个对象是否值得单独建表

### 1. 五条判断标准

| 标准 | 问题 | 判断方法 |
|------|------|---------|
| 独立主键 | 能唯一标识吗？ | 有订单号、预约单号等业务标识 |
| 独立属性 | 有自己的字段吗？ | 有多个属性（时间、状态、描述等） |
| 多处引用 | 被多个对象引用？ | 帖子、评论都引用用户 |
| 独立生命周期 | 有状态变化？ | 需新增、修改、冻结、删除、归档 |
| 多条记录 | 天然有多条？ | 多个订单项、多条评论 |

### 2. 不建议单独建表的情况

- **只是枚举值**：性别、支付状态、审核状态。用字段 + 枚举值表达。
- **只是展示标签**：“热门”“推荐”“置顶”。一个标记字段就够了。
- **纯粹的计算结果**：“总价”“总回复数”。先想清楚是否需要持久化。

### 3. 终极判断口诀：能不能“独立说话”

> **这个对象，能不能离开别的对象，自己独立说话？**

如果能，比如“订单”“预约单”，值得单独建表。如果不能，比如“状态”“类型”，往往只是字段。

## 五、案例拆解一：论坛系统——从原型里抽实体

### 1. 列出原型里的对象

一个基础论坛通常出现：用户、版块、帖子、回复、标签、点赞、收藏。

### 2. 分级筛选

| 级别 | 实体 | 理由 |
|------|------|------|
| 主实体 | 用户、版块、帖子、标签 | 有独立生命周期，被多处引用 |
| 关系实体 | 回复、点赞、收藏 | 多对多特征，需单独记录 |
| 字段/枚举 | 帖子状态、用户等级 | 无独立生命周期 |

### 3. 从页面反推字段

帖子页显示：标题、内容、作者、发布时间、所属版块、标签、点赞数、回复数、状态。

这些里：
- 标题、内容、发布时间、状态：帖子表字段
- 作者、所属版块：外键引用
- 标签：多对多关系，需中间表
- 点赞数、回复数：可能是冗余统计字段

## 六、案例拆解二：预约系统——从文档里抽实体

### 1. 文档里的业务句子

- 用户选择服务项目和预约时间
- 系统生成预约单
- 商家确认预约
- 用户取消预约
- 预约完成后生成服务记录

### 2. 实体分级筛选

| 级别 | 实体 | 理由 |
|------|------|------|
| 一级 | 预约单 | 独立生命周期：待确认、已确认、已取消、已完成 |
| 二级 | 预约时间段 | 会被引用，需控制可用性和冲突检查 |
| 二级 | 服务项目 | 有价格、时长、说明，会被管理 |
| 字段 | 用户备注、取消原因 | 无独立生命周期 |

### 3. 最容易犯的错

把“预约时间”直接塞进预约单一个字符串字段里。短期能用，长期难做时间统计、冲突判断和排班控制。

**老赵提醒：** 一开始图省事，后面业务一复杂，原先的“字符串时间”就会变成技术债。

## 七、案例拆解三：订单系统——从需求里抽实体

### 1. 核心实体识别

订单系统最常见的实体：用户、商品、订单、订单项、地址、支付记录、发货记录。

### 2. 为什么订单项必须单独建表

很多初学者把商品信息直接复制进订单表，结果一单买多个商品时就卡住了。订单项承接“一单多商品”的关系：
- 订单：一次交易的总单
- 订单项：总单里具体买了什么

只要订单里可能包含多个商品，订单项几乎就是必需的。

### 3. 哪些信息适合做冗余

订单里常会冗余一些商品信息，如下单时的商品名称、单价、图片。因为商品后面可能改名、改价，但订单历史不能跟着变。

**老赵提醒：** 冗余不是不规范。只要冗余有理由、可解释、服务于业务，就可以存在。

## 八、实体识别检查清单

看完原型或文档后，先回答这几个问题：

1. 业务里反复出现的名词有哪些？  
2. 哪些对象有独立生命周期？  
3. 哪些对象会被多处引用？  
4. 哪些对象有多条记录的天然需求？  
5. 哪些只是枚举、标签、统计值？  
6. 哪些对象可能是关系实体？  
7. 哪些字段后续可能需要拆成独立实体？  

**实操模板：** 每接到一个小需求，先做一张“候选对象清单”：候选名词、是否实体、理由。

## 结尾小结：实体识别，先抓对象，再谈结构

> **实体识别不是背概念，而是从原型、文档、业务动作里，找到值得被持久化和管理的数据对象。**

实战顺序建议：
1. 先看页面原型里的重复名词  
2. 再看文档里的动词和状态词  
3. 把候选对象分三级：主实体、关系实体、字段或枚举  
4. 用“五条标准”判断要不要单独建表

# 第5章：字段别乱堆——属性拆分、字段归类与主键思维

## 开篇引入：字段不是越多越安全

很多初学者做建模，想着“页面上有什么，就全存进去”。结果一张用户表里所有信息全塞在一起，看似齐全，实际一落地就容易出问题。

字段一乱，三个麻烦：语义混乱（如“status”表示用户状态还是订单状态？）、后期难改（地址混了省市区，要单独统计就得改代码）、查询维护费劲（重复数据更新时容易漏）。

这一章只讲一件事：**实体识别之后，怎么把字段拆对、分对、放对。**

---

## 一、什么是属性拆分：把复合信息拆成不可再分的原子字段

**属性拆分**就是把业务中一个“完整”信息，拆成数据库里不能再分的最小存储单元。判断标准：**这个字段是否只表达一个独立含义，且后续可能单独被查询、更新或统计？** 如果可以再分，必须拆。

### 字段拆分三步流程

**第一步：先问它在业务里代表什么** — 用户填的？系统生成的？还是计算出来的？

**第二步：再判断它是否混合了多个语义** — 如“地址”里是否混了省市区？

**第三步：最后决定** — 保留、拆分、枚举化，还是关联化？

**原子性检查原则**：如果字段在某个业务场景下需要单独提取、比较或修改，它就应该独立成字段。

---

## 二、四类常见字段的处理方法

### 1. 复合字段：拆语义，再存

判断标准：**后续是否要分别查询、统计、更新？**

**案例：预约系统里的“预约时间”**  
页面显示“2025-06-18 14:00-15:00”，若需按天统计、按时段筛选、检查冲突，必须拆成三个字段：`appointment_date`、`start_time`、`end_time`。如果只存一个大字符串，查询就得做文本解析。

**原则**：展示可以组合，存储最好分开。

### 2. 可枚举字段：存码不存字

枚举字段值范围有限（如性别、订单状态），建议**存状态码，展示时再映射**。

**案例**：论坛系统中，`post_status = 1` 表示已发布，`post_status = 0` 表示草稿。后台处理稳定，前端展示灵活。

### 3. 状态字段 vs 枚举字段

| 类型 | 用途 | 变化规律 | 示例 |
|------|------|----------|------|
| **枚举字段** | 描述静态取值 | 取值固定，不随流程变化 | `gender`：1-男，2-女 |
| **状态字段** | 标记流程节点 | 随业务流程流转 | `order_status`：待支付→已支付→已发货 |

**判断口诀**：取值是“静态标签”还是“流程标记”？前者用枚举，后者用状态。

**常见误区**：把“是否有效”“是否删除”“是否正常”全塞进一个状态字段。**改善方法**：语义不同就拆成多个字段，如 `is_deleted`、`order_status`、`payment_status`。

### 4. 时间字段：分清业务时点

判断标准：**时间点会参与筛选、排序、核对，就应该独立成字段。**

**案例**：预约系统中，不能把所有时间都叫`time`，要区分：`booked_at`（预约创建时间）、`appointment_at`（实际预约时间）、`confirmed_at`（确认时间）。字段名越清楚，排查问题越省事。

---

## 三、字段归类：四种类型整理思路

先拆后归：先按四类字段处理方式把字段拆成原子，再按四种属性归类。

### 1. 基础属性：描述对象本身  
比较稳定，如用户表的用户名、昵称、手机号、注册时间。  
**示例**：论坛帖子表 — 标题、内容、作者ID、创建时间。

### 2. 业务属性：体现业务规则和状态  
和流程相关，最容易变。设计时要留出扩展空间。

**示例**：订单状态、预约状态、帖子审核状态。

### 3. 统计属性：结果型字段，谨慎存  
如评论数、点赞数。权衡：**高频查询、计算成本高 → 可以冗余存储；变化快、要求绝对准确 → 尽量实时计算。**

### 4. 关联属性：连接别的实体  
如 `user_id`、`order_id`、`post_id`。

---

## 四、主键、唯一键、业务编码：三个角色别混

**主键**：表里的唯一身份标识。MySQL中常见自增ID或雪花ID。  
- **自增ID**：适合单库小表、并发量不大。简单、性能好。  
- **分布式ID（如雪花ID）**：适合高并发、分库分表。全局唯一。

**唯一键**：约束业务上不能重复的字段（如手机号唯一）。主键是“这条记录是谁”，唯一键是“这类业务值不能撞车”。

**业务编码**：给业务看的外部编号（如订单号），可能带日期或前缀。**不一定适合当主键**，因为它可能变化。

**记住一句话**：主键管稳定，唯一键管约束，业务编码管业务识别。

**案例：订单表分工**  
- `id`：主键，系统内部引用  
- `order_no`：订单号，业务编码，唯一  
- `user_id`：关联用户  
- `status`：订单状态  
- `created_at`：创建时间  

**冲突演示**：若把订单号当主键，退货重单时业务要求修改订单号（如加后缀“-R”），此时订单号已被外键引用，一改全乱套。正确做法：主键用自增ID，订单号作为唯一键独立管理。

---

## 五、避免字段冗余和语义混乱的检查清单

### 冗余不是绝对坏

例如论坛帖子里保存作者昵称：方案A（每次连用户表查）更规范，方案B（帖子表冗余昵称快照）更高效。若作者昵称常变但帖子要保留发帖时名字，方案B反而正确。**无脑冗余才是错。**

### 落地检查清单

| 检查项 | 是 | 否 |
|-------|----|----|
| 每个字段是否只有一个明确含义？ | | |
| 是否有“一个字段装多个意思”？ | | |
| 状态值是否有统一定义？ | | |
| 时间字段是否区分了不同业务时点？ | | |
| 统计字段是否明确是缓存还是结果？ | | |
| 关联字段命名是否清晰？ | | |
| 主键、唯一键、业务编码是否各司其职？ | | |
| 是否存在可接受但说明不清的冗余？ | | |

**反例**：地址字段存“北京市朝阳区望京街道”，至少装了三个意思。需统计“有多少用户在北京”就得做字符串分割，既慢又易错。正确做法：拆成 `province`、`city`、`district`。

若八项里有两项以上说不清，字段设计还没稳。

---

## 结尾小结：字段设计不是堆字，是做选择

这一章要记住的思维顺序：

1. 先识别实体  
2. 再拆属性（按复合、枚举、状态、时间四类）  
3. 再归类字段（基础、业务、统计、关联）  
4. 再区分主键、唯一键、业务编码  
5. 最后判断哪些可以冗余，哪些必须规范

**行动建议**：下次看到页面原型或业务文档，先按四列整理：基础属性、业务属性、统计属性、关联属性。再去判断哪些要拆、哪些要合、哪些要加唯一约束、哪些要保留快照。字段设计一清楚，表就不会乱。

# 第6章：关系怎么连才对——一对一、一对多、多对多的设计

## 开篇引入：关系设计，决定你的模型是不是“能跑、好改、查得动”

前面我们已经把实体、字段、模型层次这些基础打下来了。到了这一章，开始真正处理“表和表怎么连”。

很多初学者一做关系设计，就容易掉进两个坑：

- 看到两个对象就硬连，最后一张图里线比字还多，自己都看不懂；
- 怕复杂，能不建中间表就不建，结果查询难、扩展难，业务一变就返工。

老赵先给你一句实在话：**关系不是为了画图好看，是为了让业务说得通、查询跑得动、后续改得动。**

你建的不是“关系线”，而是业务对象之间真实的联系。关系连对了，后面的字段拆分、范式控制、落表实现都会顺很多；关系连错了，表再漂亮也只是空架子。

这一章我们就用最常见的三种关系——**一对一、一对多、多对多**——把设计方法讲清楚，再配论坛、预约、订单三个小案例，带你从业务场景一步步落到表结构。

---

## 一、先别急着画线：三种关系怎么判断

老赵给你一个顺手的判断流程，记住这四步就够用了：

1. **先看业务语义**：这两个对象到底是什么关系，是归属、包含，还是互相选择？
2. **再看数量规则**：一条记录对应一条、很多条，还是双方都很多？
3. **再看是否独立存在**：谁能单独活，谁必须依附另一个对象？
4. **最后看关系本身有没有属性**：如果关系自己带字段，那就不能只当“连线”看。

### 1. 一对一：一条对一条，且通常有分层原因

一对一的意思很直白：**A 的一条记录，只对应 B 的一条记录，反过来也一样。**

常见场景：

- 用户与用户扩展信息
- 订单与发票信息
- 员工与身份证件信息

判断时别只看表名，要看业务规则。比如“一个用户只能有一个实名信息”，那就是一对一；如果未来可能出现多个实名记录，或者一个人可能有多份证件信息，那就不能简单按一对一处理。

#### 怎么落表

一对一通常有两种落法：

- **拆成两个表**：主表放核心信息，扩展表放低频、敏感或变化较大的信息；
- **合并成一个表**：字段很少，而且总是一起查，就没必要拆。

比如用户表里，用户名、手机号、状态是高频信息；身份证号、实名状态、认证时间可能是低频信息，甚至涉及脱敏和权限控制，这时候拆表更合适。

> 判断标准：**是不是经常一起用？是不是生命周期一致？是不是字段明显分层？**

---

### 2. 一对多：最常见，先找“归属关系”

一对多是最常见的关系：**A 的一条记录，对应 B 的多条记录，但 B 的一条记录只归属一个 A。**

常见场景：

- 论坛用户与帖子
- 订单与订单明细
- 预约单与预约记录
- 课程与课时

这里最关键的是“**归属**”。谁是主，谁是从，通常看谁能独立存在，谁必须依附于另一个实体。

比如帖子可以独立存在，但评论必须挂在某个帖子下面；订单明细不能脱离订单单独存在，这些都很典型。

#### 怎么落表

一对多的做法通常是：

- 在“多”的一侧加上“1”的主键作为外键；
- 用外键表达归属关系；
- 如果需要查列表，给外键建索引。

比如 `post.user_id` 表示帖子归属哪个用户，`comment.post_id` 表示评论归属哪个帖子。你查“某个用户发了哪些帖子”，就会很直接。

---

### 3. 多对多：别硬塞，必须靠中间表

多对多最容易让新人犯错：**A 的一条记录对应 B 的多条记录，B 的一条记录也对应 A 的多条记录。**

常见场景：

- 用户与角色
- 学生与课程
- 商品与标签
- 医生与科室（某些业务下）

多对多不能直接靠两个外键硬塞进一张表，不然数据会乱。正确做法是：**拆出中间表。**

---

## 二、中间表什么时候必须存在：只要“互相多”，就不要硬扛

### 1. 必须建中间表的情况

只要你确认是标准多对多，中间表几乎就是必需的。原因很简单：

- 一条记录要对应多个对方对象；
- 对方对象也要对应多个本方对象；
- 关系本身可能还带属性。

例如“学生选课”不是只有学生和课程，还可能带：

- 选课时间
- 成绩
- 学期
- 状态

这些信息放哪？放中间表最自然。

#### 中间表的核心职责

中间表不是“凑数”的，它承担三件事：

1. 记录关联关系；
2. 保存关系属性；
3. 控制重复数据。

也就是说，中间表不只是“连线工具”，它本身就是模型的一部分。很多业务里，中间表甚至会演化成真正的业务单据表。

### 2. 什么时候可以不建中间表

有些场景看起来像多对多，其实可以通过业务简化：

- 如果一边是固定单选，另一边是多选，就退化成一对多；
- 如果关系只是临时展示，不需要持久化，就不用落表；
- 如果系统阶段很早、关系非常简单，也可以先按一对多临时处理，但要为后续扩展留余地。

老赵提醒你：**不要为了图省事，把本来是多对多的关系直接塞进一个字段里，比如“标签1、标签2、标签3”。**

这种设计短期看着省表，长期一定吃亏：

- 查标签不方便；
- 统计困难；
- 不能做唯一约束；
- 后续新增、删除、排序都麻烦。

---

## 三、外键、关联表、桥接表：别把它们混成一锅粥

### 1. 外键：表达“归属”

外键的本质是：**在当前表里，放另一个表的主键，表示我属于谁。**

适用场景：

- 一对多
- 一对一中的从表
- 多对多中中间表的两端引用

比如 `post.user_id` 表示帖子属于哪个用户，`comment.post_id` 表示评论属于哪个帖子。这个字段的意义不是“随便存个编号”，而是业务归属关系。

注意：外键是关系表达，不是“炫技”。在一些高并发系统里，数据库层可能不强制外键约束，但**逻辑上仍然要保留这种关系意识**。

### 2. 关联表：记录“联系”

关联表一般就是中间表，用来记录两个实体之间的联系。

比如：

- `user_role`
- `student_course`
- `post_tag`

建议至少包含：

- 两个外键字段
- 关系属性字段
- 必要的唯一约束，防止重复关联

例如，一个学生对同一门课程只能选一次，就要加联合唯一索引。这样既避免重复数据，也方便后续统计。

### 3. 桥接表：复杂关系的缓冲区

桥接表可以理解为“更有业务味道的中间表”。当关系不仅仅是“连一下”，而且关系本身有业务含义时，桥接表就更合适。

比如预约系统里：

- 用户预约医生
- 预约有时间段、状态、取消原因

这时“用户—医生”之间的桥接表不只是连接，还承载“预约单”本身的业务语义。

换句话说，桥接表不是简单的“转接头”，它可能就是业务事实的载体。

---

## 四、关系设计中的常见错误：别让表结构替你背锅

### 1. 把多对多硬改成一对多

最常见的错法：在一边塞一个“列表字段”，比如 `tag_ids`。

问题很明显：

- 难查询；
- 难统计；
- 难维护；
- 难保证唯一性。

看起来像是把关系“存起来了”，实际上是把问题“藏起来了”。

### 2. 中间表缺少约束

中间表建了，但没有唯一约束，结果同一对关系重复插入多条。

后果：

- 数据重复；
- 统计翻倍；
- 查询结果脏乱；
- 排查问题特别费劲。

所以中间表一定要想清楚：这对关系到底允不允许重复？如果不允许，就老老实实加联合唯一索引。

### 3. 把关系属性放错表

比如预约单的“预约时间”“状态”“取消原因”硬塞到用户表或医生表里，这就是典型放错地方。

记住一句话：**关系本身有字段，就把字段放在关系上。**

### 4. 外键字段命名混乱

比如 `uid`、`userId`、`owner`、`creator` 混着来，后期维护很痛苦。

建议统一规则：

- `user_id`
- `order_id`
- `course_id`

让人一眼知道它引用的是谁。命名统一，不只是为了好看，更是为了后期读表、写 SQL、排查问题都更轻松。

---

## 五、用论坛案例画一张核心关系图：先看线，再看含义

论坛系统最适合拿来练手，因为它把一对多、多对多都放进来了。

### 核心关系图

```text
user 1 ---- n post 1 ---- n comment
post n ---- n tag
```

### 每条线怎么理解

- `user 1 ---- n post`：一个用户可以发很多帖子，帖子只属于一个用户；
- `post 1 ---- n comment`：一个帖子可以有很多评论，评论只属于一个帖子；
- `post n ---- n tag`：一个帖子可以有多个标签，一个标签也可以挂多个帖子，所以必须有 `post_tag` 中间表。

### 表怎么落

- `user`：用户主表
- `post`：帖子表，含 `user_id`
- `comment`：评论表，含 `post_id`
- `tag`：标签表
- `post_tag`：帖子标签关联表，含 `post_id`、`tag_id`

### 这个案例的检查点

- 评论是否允许回复评论？如果允许，再加 `parent_comment_id`
- 标签是否允许重复绑定同一帖子？必须做唯一约束
- 帖子删除后，评论和关联标签怎么办？要提前想好级联还是逻辑删除

---

## 六、落地时怎么检查：给你一个简单的关系设计清单

画完关系图后，别急着写 SQL，先过这 6 个问题：

1. 这个关系是 1:1、1:N 还是 N:N？
2. 谁依附谁，谁能独立存在？
3. 关系本身有没有业务字段？
4. 是否需要唯一约束防重复？
5. 外键放在哪一边最合理？
6. 这个设计未来扩展时会不会卡死？

如果你能把这 6 个问题答顺，关系设计就不会太离谱。

老赵建议你养成一个习惯：每次画完关系图，不要只看“有没有线”，还要看“线背后有没有业务理由”。有理由，关系就站得住；没理由，再漂亮也没用。

---

## 七、落表实现时的 MySQL 提醒

在 MySQL 里实现关系时，建议做到：

- 主键统一用 `bigint` 或业务合适类型；
- 外键字段与被引用字段类型保持一致；
- 常用关联字段建索引；
- 中间表加联合唯一索引；
- 关系属性不要硬塞回主表。

例如帖子标签表可以这样理解：

```sql
post_tag(
  post_id,
  tag_id,
  created_at,
  unique(post_id, tag_id)
)
```

这比把标签写成一串字符串靠谱得多。

如果你后面还要查“某个帖子有哪些标签”“某个标签下有哪些帖子”，这种结构也更容易写 SQL，性能和可维护性都更好。

---

## 结尾小结：关系设计的本质，是把业务说清楚

这一章你要记住的，不是三种关系的名字，而是它们背后的判断逻辑：

- **一对一**：看是否严格单独对应；
- **一对多**：看谁归属谁；
- **多对多**：看中间表是否必需；
- **外键**：表达归属；
- **关联表**：表达联系；
- **桥接表**：承载复杂业务关系；
- **设计错误**：往往来自“先图省事，后面返工”。

### 行动建议

下一次你拿到一个业务，不要先急着画表，先做这三步：

1. 列出所有核心对象；
2. 用一句话说清每个对象之间的关系；
3. 把关系翻译成 1:1、1:N、N:N，再决定要不要中间表。

只要你把这一步走稳，后面的字段拆分、范式控制、落表实现，就会顺很多。

# 第7章：先规整，再优化——范式意识与常见建模原则

## 开篇引入：范式不是炫技，是帮你少踩坑

范式在实战中的作用很朴素：**减少混乱，降低重复，避免改一次数据漏三处。** 比如订单表同时存用户姓名、手机号、商品名、分类、地址、优惠活动名——短期开发快，长期维护出问题：改手机号要改多处，统计分类要补逻辑，历史订单可能被误改。

这一章只讲一件事：**先把数据规整到合理程度，再考虑性能优化和适度冗余。**

---

## 一、范式的目标不是炫技，而是减少混乱

范式主要解决三类问题：
- **重复数据太多**：同一信息多次保存，容易不一致
- **依赖关系混乱**：字段放错地方，查、改、删都别扭
- **更新异常**：改一处没改全，删一处把别的信息带没了

把范式理解成“整理桌面”：同类归类，一个抽屉只放一类东西。不是为了好看，而是为了找得快、改得稳。

**什么时候必须先规整？** 满足以下任意情况：业务对象多且字段交叉缠绕；同一字段值在多条记录重复出现；多个流程共用基础信息；后期需要查询、统计、修改、联动。

---

## 二、第一、第二、第三范式：教你“怎么看出来”

### 2.1 第一范式：字段要“原子化”

**一个字段里不要塞多个意思。** 错误例子：`user` 表里 `phones` 字段存 `"138xx,139xx"`。

**判断标准：** 字段是否只能表示一个值？是否存在逗号拼接、JSON乱塞、备注藏业务值？**怎么改：** 拆成子表 `user_phone`，一个手机号一条记录。

### 2.2 第二范式：字段要完整依赖主键

针对复合主键。**判断标准：** 非主键字段是否只依赖主键的一部分？比如 `post_tag` 表主键 `(post_id, tag_id)`，存 `tag_name` 就是问题——`tag_name` 只依赖 `tag_id`。关系表最适合放“关系本身”的信息。

### 2.3 第三范式：消除传递依赖

**判断标准：** 非主键字段是否依赖另一个非主键字段。如订单表存 `order_id`、`user_id`、`user_name`、`user_phone`——后两者依赖 `user_id`，不是 `order_id`。

**注意：** 不是所有重复都叫错误。如果 `user_name` 是下单时的快照字段，用来保留历史名称，那就是有明确用途的留痕。第三范式提醒你：**默认不要随手塞别的实体属性；如果必须保留，先想清它是主数据还是快照。**

---

## 三、什么时候该继续拆，什么时候可以停？

### 3.1 继续拆的信号
- 一个表混了多个业务对象
- 某些字段明显属于别的实体
- 重复字段越来越多
- 更新基础信息要改多张表
- 同类字段命名混乱（如 `user_name`、`buyer_name`、`contact_name`）

先追问：**这个字段是不是在表达别的对象？** 如果是，通常值得拆。

### 3.2 可以停的信号
- 当前表清楚表达一个业务对象
- 字段归属明确，无明显跨对象混放
- 继续拆会让查询链路过长，成本明显升高
- 业务量不大，后续变化可控

经验：**先问“这是不是另一个对象的属性？”再问“有没有必要为极致规范继续拆？”** 避免两种极端：表太碎开发痛苦，表太乱后期难维护。建模目标是能用、好维护、改得动。

---

## 四、常见规范问题与判断方法

### 4.1 重复字段：最容易埋雷
如订单表重复存用户姓名、手机号、商品名、主图、店铺名称。**判断方法：** 字段值是否经常变动？如果是继续拆；如果是历史快照可保留。

### 4.2 依赖混乱：字段放错地方
常见是把“展示信息”当“主数据”。如预约单存医生姓名、科室名称、医院名称。**处理原则：** 基础资料放基础表，过程结果放业务表；需留痕用快照字段标明用途。

### 4.3 数据更新异常：改、删、增都可能出事
- **更新异常**：同一信息改多处
- **删除异常**：删记录连带删掉有用信息
- **插入异常**：想新增对象因关联对象没准备好而无法插入

**判断方法：** 检查是否存在“为填充字段必须先有另一个对象”的情况。

---

## 五、用小型订单系统解释“规范优先”

### 5.1 不够规范的设计
`order` 表：order_id, user_id, user_name, user_phone, product_id, product_name, product_category_name, address, created_at

问题：用户信息重复；商品分类名属于商品维度；地址字段未说明类型；商品改名后历史订单处理纠结。

### 5.2 规范优先的拆法
- **用户**：`user_id`, `user_name`, `user_phone`
- **商品**：`product_id`, `product_name`, `category_id`
- **分类**：`category_id`, `category_name`
- **订单**：`order_id`, `user_id`, `created_at`
- **订单明细**：`order_item_id`, `order_id`, `product_id`, `price`, `quantity`
- **收货地址快照**：`order_address_snapshot`

拆后：用户改手机号只改用户表；商品改分类名只改分类表；订单保留下单时的价格和地址快照。

### 5.3 为什么保留快照？
订单场景需要保留历史当时的状态（下单价格、收货地址、商品名称快照）。这是**明确区分主数据和业务快照**：能不重复就不重复；必须留痕的重复要说明用途。

---

## 六、规范与效率之间怎么权衡？

### 6.1 先规范，后优化
建模顺序：按业务对象拆清楚 → 消除明显重复和混乱 → 看查询性能和使用成本 → 决定是否增加冗余字段、汇总表、快照表。不要一上来为“快查”乱加字段。

### 6.2 可以接受的适度冗余
- 历史快照：用于追溯当时状态
- 统计字段：如订单数量、已支付金额
- 展示型字段：如列表页需要的冗余名称
- 业务缓存字段：减少高频联表

要点：冗余要有明确目的和同步规则。允许订单明细保留商品名称快照，但不要把商品分类、描述、店铺电话全抄进去。

### 6.3 判断口诀
**先分清对象，再看依赖；先保规范，再做性能；能查主表就别乱抄，必须留痕再做快照。**

---

## 七、小结：规范不是束缚，是让模型站得住

核心：**范式的价值在于“拆得对”，不是“拆得多”。** 做建模时先看：字段属于谁？信息是否重复？关系是否清楚？数据是不是历史快照？再决定：继续拆还是停？保持规范还是适度冗余？优先一致性还是查询效率？

### 与下一章衔接
一味规范有时让查询复杂。订单列表页同时展示用户昵称、商品名称、店铺名称，每次关联四五张表性能可能扛不住。下一章讲：**什么时候“故意”违反规范换性能，以及如何保证这种“故意违规”不搞乱系统。**

### 本章行动建议
拿一个熟悉的小业务做四步练习：找出3个核心实体；检查重复字段；判断哪些是快照、哪些是主数据；画一版“先规范”的表结构，再思考是否需要少量冗余。成熟的建模不是把表拆到最碎，而是把关系理清、把边界定准。

# 第8章：别死磕规范——冗余、重复与反范式的实战思考

## 开篇引入：建模不是“越干净越好”，而是“够用且稳”

刚学建模容易走两个极端：死磕绝对规范，表拆太细导致查询卡顿；或者图省事，字段到处复制，最后数据混乱。老赵的实话：**数据建模不是考试，比的是谁能把系统长期跑稳。**

三类模型对比：

| 模型类型 | 查询速度 | 数据一致性 | 维护成本 | 典型场景 |
|---------|---------|-----------|---------|---------|
| 规范模型（3NF） | 慢（需联表） | 高（无冗余） | 低（写简单） | 核心业务表，低频后台 |
| 反范式模型 | 快（单表查） | 中（快照可容忍） | 中（需管理冗余） | 前端展示、报表、统计 |
| 混乱模型（无规则） | 不一定 | 低（处处冲突） | 高（查错难） | 无设计的早期系统 |

本章帮你从“混乱模型”走向“反范式模型”。**够用且稳，才是好模型。**

---

## 一、冗余和重复的区别

**重复**：同一份业务事实被多次存放，且失去一致性。例如用户表有`user_name`，订单表又存一份，用户改名后订单里的名字要不要同步？本质是**无意散存、无规则、无说明**。

**冗余**：为性能、展示、统计、历史留痕，主动额外保存数据。例如订单表存`user_id`和`user_name_snapshot`，后者是下单时快照，保留业务语义。本质是**有意多存、有规则、有用途**。

**一句话**：重复是本该唯一却多处散存；冗余是为业务目标主动多存，必须有规则。

---

## 二、哪些冗余可以接受？

判断清单：

| 判断标准 | 红色信号（不可接受） | 绿色信号（可接受） |
|---------|-------------------|-------------------|
| 用途 | 没说明为什么存 | 为展示、统计、历史留痕 |
| 更新边界 | 不知道谁更新、何时更新 | 写入同步、定时刷新或触发重算 |
| 风险兜底 | 出错了没法补 | 能通过主数据校验或重算修复 |

例如订单里的商品名是“下单时快照”，用户改商品名不应影响历史订单。快照是保护，不是风险。

**何时停用规范化？** 查询性能无法满足（响应超过1秒）、联表超过4张、字段变动频率极低、展示必须保留历史快照。

---

## 三、反范式的典型场景

**统计场景**：论坛首页展示今日发帖数。反范式方案：新增`stat_daily_forum`表，每次发帖在`reply_count`加1，直接读取。

**快查场景**：订单列表页展示订单号、用户名、金额、状态。在订单表中保留`buyer_name`、`order_status_name`等快照，避免频繁联表。

**报表场景**：销售看板关注今日成交额、月度订单。提前聚合、宽表、汇总表追求“快读”。

**展示场景**：预约详情页展示门店名、地址、服务项名。适度冗余让一个接口返回完整数据。

---

## 四、效率和规范怎么权衡？

**第一步：判断字段类型。** 核心事实（如金额、数量）优先归一化；展示快照（如商品名）可冗余，但要明确是快照。

**第二步：判断变动频率。** 频繁变（如用户昵称）尽量不要多处散存；几乎不变（如门店编号）可适度复制。

**第三步：判断查询频次。** 高并发高频查询适度反范式；低频后台查询优先规范。

**第四步：判断可修复性。** 能通过主数据重算则风险可控；一错就回不来要谨慎。

**实战推演：订单表是否要冗余`buyer_name`？**
- 字段类型：展示快照，不是核心事实
- 变动频率：历史快照不应跟着改，保存的是快照
- 查询频次：列表页每天几千次访问，必须展示用户名
- 可修复性：快照丢失可从`order`表的`buyer_id`联`user`表补充
- 结论：可冗余，但加`_snapshot`后缀，不参与任何更新条件

---

## 五、如何控制反范式风险？五个措施

**先定主数据，再定冗余字段**。主数据表负责权威来源，冗余字段只负责展示、统计。冗余字段永不作为更新约束条件。

**给冗余字段加语义名**。用`xxx_snapshot`、`xxx_cache`、`xxx_summary`，名字就是契约。

**明确更新策略**。三种方案：
- 写时同步：如触发器在用户改名时更新未完成订单快照
- 定时刷新：定时任务每5分钟从主数据拷贝到快照表
- 触发重算：展示时临时联表计算，不存储

**保留校验机制**。定期比对订单快照与主商品信息，对统计表抽样重算。

**控制冗余范围**。只放真正减少成本的字段，能不放就不放，必须放就讲清用途。反范式代价落在写入侧，适合读多写少场景。

---

## 六、三个小案例串起来看

**案例1：论坛帖子列表页**。需求：快速显示帖子、作者名、回复数、最后回复时间。推演：联表查询慢→反范式方案（冗余`author_name_snapshot`、`reply_count`）→风险控制（快照不参与登录校验，统计字段用触发器同步）。

**案例2：预约系统**。需求：门店名称改了，历史预约记录不能跟着变。推演：规范方案联表会查到新名→反范式方案（保存快照）→风险控制（快照名加`_snapshot`，不参与门店搜索）。

**案例3：订单系统**。需求：列表页频繁打开，支持运营看板。推演：规范方案性能差→反范式方案（冗余关键快照字段+每天聚合统计表）→校验（每晚比对快照与主表差异）。

---

## 结尾小结：别让规范成为系统的负担

三句话记住本章：
1. **重复不等于冗余，冗余也不一定是错。**
2. **反范式不是破坏模型，而是为高频场景服务。**
3. **真正好的建模，是在规范、效率、成本之间找到平衡。**

**实战检查清单**：
- 这个字段是不是主数据？
- 是不是快照、统计或展示字段？
- 如果冗余，更新规则是什么？
- 出问题能否重算或修复？
- 这个查询值不值得做反范式？

以后做模型，多问一句：**“这样能不能把业务跑稳、跑快、跑久。”**

# 第9章：用论坛案例串一遍——从业务到模型的完整演练

## 开篇引入：为什么要拿论坛练手

前面讲了不少建模概念，但一到真业务还是容易发懵。这一章直接拿一个**论坛系统**走一遍完整流程：用户发帖、评论、点赞、版块管理。目标明确：**从业务对象和流程出发，抽实体、分字段、理关系、做取舍，最后落到 MySQL 表设计。**

---

## 论坛业务对象与核心流程拆解

### 先别急着建表，先问业务在干什么

建模第一步是看业务怎么跑。论坛核心流程：

1. 用户注册、登录  
2. 用户在某个版块发布帖子  
3. 其他用户浏览帖子、评论帖子  
4. 用户对帖子或评论点赞  
5. 管理员维护版块、审核内容

论坛围绕**用户、内容、互动、分类**这几类对象运转。把流程拆成几个问题：谁在操作？操作了什么？内容属于哪里？系统要保存哪些记录？方向就清楚了。

### 从流程里找数据需求

把流程翻成“系统要记住什么”：

- 用户注册：记住用户名、手机号、昵称、注册时间
- 发帖：记住谁发的、哪个版块、标题、正文、发布时间
- 评论：记住属于哪个帖子、谁评论的、评论内容
- 点赞：记住谁给哪个帖子或评论点了赞
- 版块：记住名称、简介、排序、状态

业务流程背后，最终都落成**可存储的数据**。这一步决定了表是不是贴着业务走。

**老赵提醒：** 不先想流程，容易建出“为了存数据而存数据”的表。比如“热门帖子”多数是查询结果，不是独立业务对象。

### 这一阶段先别纠结细节

第一步要确认：**论坛有哪些核心业务对象？它们在流程里扮演什么角色？** 先把业务看清，后面抽实体才不会乱。

---

## 从原型或文档抽象实体：用户、帖子、评论、点赞、版块

### 什么叫从原型或文档抽实体

用简单办法：**把名词找出来，判断它是不是“需要长期保存、能独立识别”的对象。**

论坛案例初步抽出：

- **用户**：发帖、评论、点赞的主体
- **版块**：帖子的分类容器
- **帖子**：用户发布的主要内容
- **评论**：用户对帖子的回复
- **点赞**：用户对帖子或评论的表达

不是所有名词都建成实体。“首页推荐”“搜索结果”通常是展示或查询结果，不是实体。

**实操踩坑提示：** 两种情况最怕——漏掉核心对象，后面补表痛苦；把所有名词当实体，表多得看不懂。

### 如何判断一个对象是不是实体

三个标准：

1. **能不能独立存在**——用户、帖子、评论都能独立存在
2. **需不需要被单独管理**——版块需要维护，点赞记录需要统计、去重
3. **有没有自己的主键和生命周期**——用户有 `user_id`，帖子有 `post_id`，评论有 `comment_id`

一句话：**能独立识别、能独立管理、能独立变化，通常就值得单独建模。**

### 属性拆分：哪些放一起，哪些要拆开

以“用户”为例：`user_id`、`username`、`password_hash`、`nickname`、`mobile`、`avatar`、`gender`、`status`、`created_at`。这些属于用户实体本身。

“所在地”可作为属性直接放；“最近一次登录IP”可能属于登录记录；“发帖数”是衍生数据，能算出来就别塞。

**老赵的字段归类模板：**

| 字段类型 | 处理原则 | 例子 |
|---------|---------|------|
| 事实字段 | 放原表 | 发帖内容、注册时间 |
| 衍生字段 | 优先计算，谨慎冗余 | 发帖数、点赞数 |
| 跨实体字段 | 通过关联获取 | 作者昵称、版块名称 |
| 统计字段 | 可冗余，但要维护一致 | 帖子表评论数 |

### 评论、点赞、版块怎么抽

- **评论**：`comment_id`、`post_id`、`user_id`、`content`、`parent_comment_id`、`created_at`
- **点赞**：`like_id`、`user_id`、`target_type`、`target_id`、`created_at`
- **版块**：`board_id`、`board_name`、`description`、`sort_order`、`status`

评论支持回复时，`parent_comment_id` 很重要；点赞可点帖子或评论时，`target_type + target_id` 是常见做法。

---

## 关系设计与关系判断

### 先说清楚关系

论坛常见关系：

- 用户和帖子：一对多
- 版块和帖子：一对多
- 帖子和评论：一对多
- 用户和评论：一对多
- 用户和点赞：多对多
- 帖子和版块：多对一

### 关系判断三步走

1. **A 可以对应多个 B 吗？** → 是则继续，否则可能一对一
2. **B 可以对应多个 A 吗？** → 是则多对多，否则一对多
3. **需要记录关系双方信息吗？** → 一对多外键放“多”的一方；多对多建中间表

### 一对多关系设计

做法：**“多”的一方放外键**。

- `post.author_id` 指向用户
- `post.board_id` 指向版块
- `comment.post_id` 指向帖子
- `comment.user_id` 指向用户

**老赵式提醒：** 别在用户表、版块表里塞帖子信息。关系放“多”的那边，结构更清楚。

### 多对多关系处理

点赞：一个用户可点赞很多内容，一个内容可被很多用户点赞。单独建点赞表，不能把点赞信息塞进帖子表。多对多关系优先考虑中间表。

---

## 模型中的冗余与查询效率处理

### 冗余不是原罪

建模要在**规范**和**效率**之间找平衡。论坛常见冗余：

- 帖子表 `comment_count`（评论数）
- 帖子表 `like_count`（点赞数）
- 评论表 `like_count`（点赞数）

列表页要展示评论数、点赞数，实时关联大量数据性能差，适度冗余有业务价值。

### 冗余字段判断清单

1. **是否高频查询？** → 帖子列表每页展示评论数
2. **是否允许短暂不一致？** → 评论数差几秒用户感受不到
3. **是否能通过异步或定时修正？** → 可定时任务同步
4. **是否会明显增加维护成本？** → 写帖子表多更新一个字段

评论数、点赞数通常可冗余；“用户名”“版块名称”以主表为准。

**老赵的实战权衡表：**

| 场景 | 推荐策略 | 原因 |
|------|---------|------|
| 管理后台、低并发 | 尽量规范，少冗余 | 一致性更重要 |
| 高频浏览（如首页） | 适度冗余提升体验 | 查询性能优先 |
| 数据核心字段（金额） | 优先保持一致性 | 不能有误差 |
| 展示型统计（点赞数） | 可冗余缓存 | 允许短暂不一致 |

### 效率和规范权衡

原则：**冗余是为查询服务，不是为偷懒服务。** 控制冗余——谁来维护、何时更新、出错怎么修、以谁为准，都要想清楚。

## 从概念模型到逻辑模型的完整落地过程

### 第一步：概念模型，先画清对象和关系

- 用户 发布 帖子
- 用户 发表 评论
- 用户 点赞 内容
- 帖子 属于 版块
- 帖子 包含 评论

这一层不用写字段，作用是理顺业务关系。

### 第二步：逻辑模型，把对象变成结构

论坛逻辑模型：`user`、`board`、`post`、`comment`、`like_record`。问自己：字段为什么放这里？关系为什么这样连？表能否独立维护？

### 第三步：物理模型，落到 MySQL

```sql
-- 用户表
CREATE TABLE user (
  user_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(50) NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  nickname VARCHAR(50) NOT NULL,
  mobile VARCHAR(20),
  avatar VARCHAR(255),
  status TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 版块表
CREATE TABLE board (
  board_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  board_name VARCHAR(100) NOT NULL,
  description VARCHAR(255),
  sort_order INT NOT NULL DEFAULT 0,
  status TINYINT NOT NULL DEFAULT 1
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 帖子表（含冗余统计字段）
CREATE TABLE post (
  post_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  author_id BIGINT NOT NULL,
  board_id BIGINT NOT NULL,
  title VARCHAR(200) NOT NULL,
  content TEXT NOT NULL,
  comment_count INT NOT NULL DEFAULT 0,
  like_count INT NOT NULL DEFAULT 0,
  post_status TINYINT NOT NULL DEFAULT 1,
  created_at DATETIME NOT NULL,
  updated_at DATETIME NOT NULL,
  INDEX idx_author (author_id),
  INDEX idx_board (board_id),
  INDEX idx_created (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 评论表
CREATE TABLE comment (
  comment_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  post_id BIGINT NOT NULL,
  user_id BIGINT NOT NULL,
  parent_comment_id BIGINT DEFAULT NULL,
  content VARCHAR(1000) NOT NULL,
  like_count INT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL,
  INDEX idx_post (post_id),
  INDEX idx_user (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 点赞记录表（多对多中间表）
CREATE TABLE like_record (
  like_id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  target_type TINYINT NOT NULL COMMENT '1=帖子, 2=评论',
  target_id BIGINT NOT NULL,
  created_at DATETIME NOT NULL,
  UNIQUE KEY uk_user_target (user_id, target_type, target_id),
  INDEX idx_target (target_type, target_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**老赵提醒：** 正确顺序是：**业务理解 → 实体识别 → 关系设计 → 字段归类 → 冗余判断 → 逻辑模型 → MySQL 落表**。这个顺序做订单系统、预约系统也一样能用。

## 论坛案例总结：我们到底学到了什么

### 核心检查清单

拿到类似业务，按这个顺序走：

1. 先看业务流程，不急着建表
2. 找出核心对象，抽实体
3. 判断对象关系，一对多还是多对多
4. 做字段归类，分清主信息和统计信息
5. 对冗余字段做效率评估
6. 先画概念模型，再落逻辑模型
7. 最后映射到 MySQL 表结构

### 这一章最重要的一句话

**建模不是把名词翻译成表，而是把业务流程翻译成可维护、可查询、可扩展的数据结构。**

### 这个案例验证了什么

**已验证：**
- 从业务流程出发抽实体，比直接建表更靠谱
- 字段归类能防止主表过度膨胀
- 冗余字段控制好边界，可提升查询效率

**留到后续：**
- 状态流转管理（订单系统）
- 明细拆分和主从表设计（订单系统）
- 更复杂的反范式权衡（预约系统）

# 第10章：模型不是画完就完——校验、调整与评审方法

## 开篇引入：模型画出来，只算走完一半

很多人把“画完模型”当成“建模完成”。模型图只说明你对业务有了一版理解，不代表它能真正支撑上线。老赵常说：“模型不是拿来好看的，是拿来跑业务的。”一到真实场景，问题就冒出来：字段漏了、关系连错、重复存储、异常流程没考虑。

这一章讲的是**画完以后怎么验**——模型体检、复盘和评审。目标：让模型从“看着对”变成“真的能用”。

## 一、模型校验的核心检查清单

模型校验分四大类：

### 1.1 业务覆盖检查

把业务流程重新过一遍，用**三问法**判断：
1. **核心业务对象是否存在**——如论坛系统：用户、帖子、评论、分类都在吗？
2. **关键业务动作是否有落点**——用户能发帖、回帖、点赞、收藏吗？数据存哪里？
3. **重要状态是否有记录**——审核状态、删除标记、置顶标识，有没有对应字段？

**推演示例：用“三问法”走一遍论坛系统**

假设模型只有用户表、帖子表、评论表、分类表四张表。先问核心对象：都有表，通过。再问关键动作：用户发帖→帖子表新记录，通过；用户回帖→评论表插入，通过；用户点赞→点赞没有对应实体。如果点赞只作为帖子表的数字字段（如`like_count`），谁点的、何时点的、能否取消，全都丢失。缺“点赞记录”实体。再问关键状态：帖子审核通过/驳回→帖子表需要状态字段；用户是否被封禁→用户表需要状态字段；帖子是否被删除→建议加软删除标记。通过三问，发现少了一个实体（点赞记录）、少了一个状态（审核状态、软删除标记）。

**常见误区：** 只按界面画表，不按业务流程；只看主流程，不管审核、取消、失败等边界流程；只建“看得见的数据”，不建“业务必须记住的数据”。

### 1.2 字段完整性检查

分四类检查：**标识字段**（主键、创建时间、更新时间、状态字段、归属字段）；**业务必需字段**（如预约系统至少要有预约人、预约对象、预约时间、预约状态、取消原因）；**可推导字段是否重复存储**（如订单总额可由明细合计得到，冗余必须有理由）；**字段类型匹配业务**（金额不用字符串，状态不用文本，时间不只存日期）。

### 1.3 关系合理性检查

重点检查：一对一是否其实一对多？一对多是否误成多对多？多对多是否缺中间表？外键方向是否符合业务依赖？判断标准：不仅问“能不能连上”，还要问**这个关系是否承载了业务意义**。

### 1.4 异常路径检查

典型异常路径：用户提交后取消、订单支付失败、预约改期、内容审核驳回、帖子被删但评论还在。设计时要留的口子：状态字段可扩展；关键动作有时间记录；取消、失败、驳回有原因字段；必要时保留历史表或日志表。

**额外提醒：区分“流程中的临时数据”和“需要持久化的业务数据”**。如用户填写预约表单时缓存草稿，这不等于持久化业务数据。不要把临时缓存作为实体设计到模型中。

**数据完整性规则校验**：用户删除后帖子如何处理？评论被删除后父帖子下是否还显示评论条数？预约取消后是软删除还是保留？建议附一张“数据完整性规则表”，写明每种删除、更新操作的级联行为。

## 二、如何发现遗漏实体和错误依赖

### 2.1 从业务流程倒推

拿流程图或原型，一步步问：用户点了什么？系统要记住什么？哪些需长期保存？哪些状态变化需追踪？如预约系统，除了“预约表”，往往还需要预约状态流转记录、取消记录、变更记录、通知记录。动作越重要、变化越多、争议越大，越应单独抽实体。倒推时只关注业务提交后的结构化数据，不要把所有中间状态塞进模型。

### 2.2 从依赖关系看错误

**情况一**：用户表放“最新订单号”等结果型信息。这不是用户固有属性，除非为快照，否则不该硬塞进主实体。

**情况二**：强依赖子项设计成独立实体，如订单明细离开订单无意义，应强依赖订单。

**判断原则**：这个数据离开它的主人还成立吗？不成立就是强依赖。

## 三、如何检查重复、空值、异常路径

### 3.1 重复的处理

**业务允许的重复**：用户可多次预约同一服务，是业务行为。

**字段内容重复**：订单表同时存用户名、手机号、用户ID。为订单快照合理；只是图方便则需注意信息变更后的同步问题。

**结构性重复**：多表存同一套地址信息但无统一来源，最危险。正确做法：地址信息只在一个地方维护（如地址字典表），订单表只存地址ID作为引用。只有当订单需要快照当时地址时，才在订单表冗余一份地址字符串，并有清晰理由和同步策略。

**处理原则**：能引用就引用，能复用就复用，必须快照时再冗余。

### 3.2 空值的处理

可选项为空（昵称）、流程未到达为空（未发货时发货时间为空）合理。设计漏了导致为空（订单完成但完成时间为空）则有问题。**实操建议**：给每个关键字段写一句话——这个字段什么时候有值？没有值是否合理？一直为空说明什么？

## 四、如何用查询场景反推模型问题

### 4.1 让查询来“验尸”

列几个常用查询，检查需要哪些表关联？是否需很多层join？是否会因字段缺失查不出来？是否会因关系错误查重、漏数？

### 4.2 完整例子：论坛系统

假设只有用户、帖子、评论、分类四张表。

**场景一**：查“某个帖子最近20条回复”。若评论表只有父评论ID没有帖子ID，需逐层向上追溯——效率极低。调整：加`post_id`字段直接关联帖子。

**场景二**：查“用户发帖总数”。若帖子表用户ID字段支持匿名发帖时为空，统计会漏数。调整：明确规则，匿名时记录虚拟用户ID或空值。

**场景三**：查“某分类下最热门的帖子”。一个帖子属多个分类时，若只用逗号分隔分类ID，查询变成`FIND_IN_SET`——性能很差。调整：增帖子分类关联表（`post_category`）。

**通用链**：查询困难 → 检查关联字段是否缺失或关系不合理 → 反推实体是否需要拆分（如加关联表）或增加冗余字段（如加直接外键）。

### 4.3 三个常见问题

1. 关联链太长——实体拆得过细。
2. 统计很难做——缺状态、时间、归属等关键字段。
3. 结果不稳定——存在重复、冗余不一致、历史快照缺失。

## 五、团队评审时重点看什么

### 5.1 防止后面返工

**重点关注五件事：**
1. **业务是否讲得通**——每张表、每个字段、每条关系能否用业务语言解释清楚。
2. **模型是否覆盖主流程和异常流程**。
3. **字段是否有清晰归属**——主实体、明细、快照必须说清。
4. **是否存在明显重复和冲突**——同一信息多存是否有主来源？字段命名、状态定义是否统一？
5. **是否便于后续实现**——MySQL落表后常用查询是否容易支持？索引是否容易设计？

### 5.2 评审三问法

- **这个实体为什么要有？** *答不出的典型表现：* 讲不清这个实体对应哪个业务对象或动作。
- **这个字段为什么放这里？** *答不出的典型表现：* 解释不了字段归属的业务逻辑。
- **这个关系为什么这么连？** *答不出的典型表现：* 说不出关联的基表是谁、外键方向是否依赖业务。

三个问题有一个答不出来，模型就没站稳。

## 六、完整案例：门诊预约系统校验

### 第一步：已有模型雏形
用户表、医生表、预约表（只有预约时间、预约人、医生ID）、科室表

### 第二步：检查清单过一遍

**业务覆盖：** 核心对象有；❌取消、改期、爽约无对应实体；❌无就诊号追踪流程。

**字段完整性：** ❌预约表无预约状态、取消原因、预约来源、确认时间、就诊时间；❌用户表缺联系电话。

**关系合理性：** ❌医生与科室关系未明确；❌预约挂给医生还是科室未体现。

**异常路径：** ❌取消后预约记录直接删还是保留？❌爽约如何记录？❌改期是改原记录还是新建？

### 第三步：调整方案

**预约表增加字段：** 状态（待就诊/已就诊/已取消/已爽约）、创建时间、确认时间、就诊时间、取消原因、预约来源。

**新增实体：** 预约状态流转记录表、排班表。

**关系调整：** 医生属科室（多对一）；预约挂科室再由系统分配医生（增设科室ID）。

### 第四步：查询验证

查用户当天预约→有用户ID、预约时间、状态→可以。查医生排班→有排班表→可以。查预约状态变更历史→有状态流转记录表→可以。

## 七、校验后如何调整与重新评估

发现模型问题后，按调整流程走：

1. **发现问题**：通过检查清单、查询反推、评审三问法，找到漏洞。
2. **列出影响范围**：修改会影响哪些表、哪些查询、哪些下游接口？
3. **修改实体/字段/关系**：按影响范围依次调整，先补实体，再补关系，最后补字段。
4. **重新过检查清单**：确保新加的实体和关系没有引入新的漏洞。
5. **业务验证**：向业务方或产品走一遍主流程和异常流程，确认模型能支撑需求。

简记为：**发现→评估→修改→复查→验证**。

## 八、落地MySQL的检查清单

1. ✅ 业务对象是否都已覆盖？
2. ✅ 每个核心对象是否有主键？
3. ✅ 每个关键流程是否有状态字段？
4. ✅ 是否存在无法追踪的动作？
5. ✅ 是否存在不必要的重复字段？
6. ✅ 常用查询是否可支持？
7. ✅ 异常流程是否有数据落点？
8. ✅ 每个字段是否已确定类型和是否允许空？

**校对结果记录与版本管理**：每次校验后，记录版本号、修改时间、修改内容、修改原因。方便追溯和多人协作时避免重复踩坑。

## 结尾小结

模型校验主要看四件事：业务覆盖、字段齐全、关系正确、查询和异常场景能撑住。实际操作：从业务流程倒推实体；从字段用途判断归属；从查询场景反推结构；从异常路径检查韧性；评审中用“三问法”抓漏洞。发现问题后，按“发现→评估→修改→复查→验证”流程走一遍，并做好变更记录。

给你一个实战建议：画完任何一版模型，先问自己一句：

> **如果这个模型明天就要上MySQL，最可能在哪三个地方出问题？**

能提前答出来，你的建模能力就开始真正进步了。

# 第11章：落到 MySQL 上——把逻辑模型变成可用的表结构

## 开篇引入：模型画得再好，最后还是要落到表上

这一章进入真正落地的环节——**把逻辑模型变成 MySQL 里能直接用、好维护、跑得动的表结构**。

新手常见问题：逻辑模型画得漂亮，一建表就不知字段类型怎么选；主键、索引、唯一约束、外键混在一起分不清；表名字段名随手起，后面自己都看不懂；效率与规范难以兼顾。

老赵做项目时常说：**建模不是为了画图，而是为了让系统稳稳地跑起来。** 本章用预约系统案例，完整走一遍从逻辑模型到建表 SQL 的全过程。

---

## 一、逻辑模型到物理模型：按这五步走，最稳

### 第一步：实体落表

逻辑模型里的每个实体，优先一张表一个实体。预约系统：
- 用户 → `user`
- 服务项目 → `service_item`
- 预约单 → `appointment`

原则：不要一开始就拆表。只有遇到“部分字段访问频率明显不同”或“单表字段超过30个”时，才考虑拆分。

### 第二步：属性变字段

逻辑模型中的属性转换成字段，同时判断类型和长度。**一个业务属性对应一个字段，不要塞成一个长字符串**。比如“预约时间”不要写成 `appointment_time VARCHAR(50)`，应拆成：
- `appointment_date DATE`
- `start_time TIME`
- `end_time TIME`

字段类型选错，轻则浪费空间，重则排序、查询都出问题。

### 第三步：处理关系

- 一对多：在“多”的一侧放外键字段
- 多对多：需要中间表
- 一对一：检查是否真的需要拆表

### 第四步：补齐约束

约束不是装饰，是保证数据不乱的底线：
- 主键：每张表必须有
- 非空：业务必填字段，数据库层也要卡住
- 唯一：防止重复数据混入
- 外键：小系统可考虑，高并发建议用索引+应用校验
- 默认值：减少程序遗漏写入

**约束就是最后一道闸。**

### 第五步：围绕查询场景补索引

先问三个问题：
1. 业务最常用的查询条件是什么？
2. 哪些字段会出现在 `WHERE`、`JOIN`、`ORDER BY` 中？
3. 哪些字段值区分度高？

重点给这些字段建索引。没有查询场景盲目加索引，只会拖慢写入。

---

## 二、MySQL 字段类型选择：三问定乾坤

选类型前问自己三个问题：这个字段会不会参与排序、筛选、统计？取值范围大不大？后续会不会扩展？

### 数值类型

| 类型 | 适用场景 | 踩坑点 |
|------|----------|--------|
| `INT` | 主键、计数、状态编号 | 别拿来存手机号或订单号 |
| `BIGINT` | 数据量大时用 | 一般主键用 |
| `DECIMAL(10,2)` | 金额 | 优先选，别用 FLOAT/DOUBLE |

**老赵提醒**：金额用 `FLOAT` 精度会出问题；订单号、手机号本质是字符串，用 `VARCHAR`。

### 字符串类型

- `VARCHAR(n)`：最常用，适合姓名、标题、手机号、邮箱
- `CHAR(n)`：长度固定的编码
- `TEXT`：长文本，**不能被唯一约束，也不适合直接排序**

### 时间类型

| 类型 | 适用场景 |
|------|----------|
| `DATETIME` | 记录具体时间点 |
| `DATE` | 只要日期 |
| `TIME` | 只要时分秒 |
| `TIMESTAMP` | 需要时区或自动更新时考虑 |

**不要用字符串存时间**，排序、范围查询会很麻烦。

### 状态字段

用 `TINYINT` 存状态码，配合注释说明含义。例如：`0`待确认，`1`已确认，`2`已取消。不要直接存中文状态名。

---

## 三、主键、索引、唯一约束、外键：各司其职，别混用

### 主键：稳定、单调、无业务含义

建议用 `BIGINT AUTO_INCREMENT`。**不要把手机号、身份证号当主键**，业务字段会变、会被修改。

### 索引：围绕“业务怎么查”来建

常见该建索引的字段：外键字段、高频查询条件、排序分页字段。

### 唯一约束：数据库层防重复的底线

适合场景：用户名唯一、订单号唯一、同一用户同一时段只能预约一次某个服务。**并发场景下，唯一约束是最后一道保险。**

### 外键：能帮你保证一致，但别迷信

- 小系统、强一致：可考虑
- 高并发、复杂分库：用索引+应用校验

### 一句话总结

主键→标识行，索引→加速查，唯一约束→防重复，外键→保关联（选配）

## 四、命名规范和注释：别让三个月后的自己看不懂

### 表名：全小写、下划线

不要驼峰、拼音、缩写混用。

### 字段名：一眼看懂业务含义

好例子：`created_at`、`user_id`、`appointment_status`  
坏例子：`time1`、`flag`、`data`

### 注释：补充业务含义，不是替代命名

重点标注：状态值含义、金额单位、时间口径、是否逻辑删除。

建表前过一遍检查清单：表名统一？字段名准确？没有过度缩写？金额、时间、状态有无注释？

## 五、案例演练：预约系统完整落表

### 业务理解

用户选择服务项目，在指定日期和时间段发起预约，管理员可确认或取消。

### 实体识别

从原型文档中抽出三个实体：用户（`user`）、服务项目（`service_item`）、预约单（`appointment`）。

### 逻辑关系

用户对预约单：一对多；服务项目对预约单：一对多。

### 落表 SQL

```sql
-- 用户表
CREATE TABLE user (
  id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '用户ID，自增主键',
  username VARCHAR(50) NOT NULL COMMENT '用户名，唯一',
  phone VARCHAR(20) NOT NULL COMMENT '手机号',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  UNIQUE KEY uk_username (username)
) COMMENT='用户表';

-- 服务项目表
CREATE TABLE service_item (
  id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '服务项目ID，自增主键',
  service_name VARCHAR(100) NOT NULL COMMENT '服务名称',
  price DECIMAL(10,2) NOT NULL COMMENT '服务价格，单位为元',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '状态：1启用，0停用',
  UNIQUE KEY uk_service_name (service_name)
) COMMENT='服务项目表';

-- 预约表
CREATE TABLE appointment (
  id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '预约ID，自增主键',
  user_id BIGINT NOT NULL COMMENT '用户ID，关联user表',
  service_item_id BIGINT NOT NULL COMMENT '服务项目ID，关联service_item表',
  appointment_date DATE NOT NULL COMMENT '预约日期',
  start_time TIME NOT NULL COMMENT '开始时间',
  end_time TIME NOT NULL COMMENT '结束时间',
  status TINYINT NOT NULL DEFAULT 0 COMMENT '状态：0待确认，1已确认，2已取消',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  
  INDEX idx_user_id (user_id),
  INDEX idx_service_item_id (service_item_id),
  INDEX idx_appointment_date (appointment_date),
  INDEX idx_status (status),
  UNIQUE KEY uk_user_date_time (user_id, appointment_date, start_time) 
    COMMENT '同一用户同一日期同一时段只能有一条预约'
) COMMENT='预约表';
```

### 这个案例体现了什么？

- 字段类型与业务对应：金额用 `DECIMAL`，日期用 `DATE`，状态用 `TINYINT`
- 索引围绕查询设计：高频查询条件均建索引
- 唯一约束防重复：`uk_user_date_time` 防止同一时段重复预约
- 注释帮后人理解：每个字段、索引都有说明

### 防止“同一时段重复预约”的组合方案

1. 唯一约束兜底（数据库层）
2. 程序层校验：插入前先查询
3. 事务控制：`START TRANSACTION ... COMMIT`

---

## 六、效率和规范怎么权衡？（实操判断标准）

### 什么时候优先规范？

核心交易数据、需长期保存分析的数据、被多个模块共享的数据。这类场景宁可多花时间规范，也别后面返工。

### 什么时候可以适当反范式？

查询特别频繁、关联代价太高；派生字段可提前计算好；允许快照场景（如订单中冗余商品名称）。

### 判断标准

**高频读、低频改、允许快照 → 可冗余**  
**核心关系、频繁变化、需要实时一致 → 保持规范**

### 三种冗余场景的处理方式

| 场景 | 处理方案 |
|------|----------|
| 需要保留历史快照 | 冗余在订单表，改商品表时订单不受影响 |
| 实时一致性要求高 | 只存一处，用事务保证 |
| 查询性能瓶颈 | 增加索引，或建冗余汇总表 |

---

## 结尾小结：从“会画图”到“会落表”

这一章要记住的是一套落地的决策方法：
1. **逻辑模型先行**，五步转换法：实体落表→属性变字段→处理关系→补齐约束→补索引
2. **字段类型三问决策**：是否参与排序统计？取值范围？会不会扩展？
3. **主键、索引、唯一约束、外键各司其职**
4. **命名统一、注释清楚**
5. **案例练手**：预约系统从实体、关系到落表完整走一遍
6. **效率和规范要平衡**：用“高频读 vs 频繁变”的判断标准

### 行动建议

拿手头任意一个小业务，按此顺序练一遍：写出实体列表→画出关系→列出字段及类型→加主键和索引→补唯一约束和注释→输出完整建表语句。

照这套方法走一遍，你的表结构就能从“勉强能用”进化到“经得起业务考验”。

# 第12章：再做一个完整案例——预约系统或订单系统的建模实战

## 开篇引入：为什么还要再做一个案例

前面我们已经拿论坛做过一轮建模，这次换个场景，不是为了换口味，而是为了验证你是不是已经能脱离“背模板”，真正从业务出发拆模型。

如果说论坛更偏“内容 + 关系”，那预约系统更偏“流程 + 状态”。它会逼你想清楚：谁在什么时间占用了什么资源，预约从发起到完成经历哪些状态，哪些信息要长期保存，哪些只是临时展示。

数据建模最有价值的地方就在这：不是照着表结构抄，而是先把业务说清楚，再翻译成结构。

这次我们选一个更贴近日常业务的场景：**预约系统**。比如美容预约、诊疗预约、场地预约、教练预约，本质都差不多：用户先选资源，再选时间，生成预约记录，后面还会有确认、取消、完成、改期等状态变化。

这个案例比论坛更适合训练“流程驱动建模”，因为它会把很多细节暴露出来：

- 预约时间到底属于谁？
- 一个资源能不能在同一时段被多次占用？
- 改期算不算一次新的业务行为？
- 取消原因要不要单独保存？
- 列表页常显示的客户姓名、资源名称，要不要冗余？

这些问题想明白了，你的建模思路就会稳很多。

## 一、预约系统的业务边界怎么梳理

### 1. 先别急着画表，先问清楚“系统管什么”

常见误区是：一看到预约系统，就立刻想到“客户表、预约表、资源表”。太快了。先把边界说清楚，模型才不会乱。

以“门店服务预约”为例，系统通常要管这些事：

- 客户查看可预约资源
- 客户提交预约申请
- 系统记录预约时间、资源、服务项目
- 门店人员确认或拒绝预约
- 预约可取消、改期、完成
- 可能要记录备注、来源、支付状态

但有些事不一定都要建进来，比如：

- 资源库存计算如果很复杂，可能由别的系统负责
- 支付明细如果由支付系统处理，本系统只保留支付状态
- 短信发送日志，未必属于核心业务表

也就是说，建模前先做一次“业务边界筛选”。否则你很容易把所有相关信息都塞进去，表会越来越胖，关系也会越来越乱。

### 2. 边界判断标准

你可以用三个问题判断要不要纳入本系统：

1. 这个信息是否影响预约流程？
2. 这个信息是否需要长期保存和查询？
3. 这个信息是否由本系统主导维护？

如果三个问题里至少有两个答案是“是”，通常就值得进入模型。

比如：

- “预约状态”会影响流程，要保存，也由系统维护，应该建。
- “短信是否已发送”会影响结果判断，通常也应该建。
- “客户家庭住址”如果只是偶尔展示，且不参与预约流程，可以先不纳入核心模型。

先定边界，再谈实体，模型才不会失控。

### 3. 概念模型、逻辑模型、物理模型别混

这里顺手把三种模型再捋一遍：

- **概念模型**：看业务对象和关系，比如客户、资源、预约、状态流转
- **逻辑模型**：明确主键、外键、字段归属和业务规则
- **物理模型**：真正落到 MySQL，确定字段类型、索引、唯一约束

很多初学者一上来就写 `CREATE TABLE`，其实是直接跳到物理模型，中间两层没过，表大概率会乱。

---

## 二、核心实体识别：客户、资源、预约记录、状态流转

### 1. 从业务对象里找实体

预约系统里最核心的对象一般有：

- **客户**：发起预约的人
- **资源**：被预约的对象，比如门店、房间、技师、教练、座位
- **服务项目**：预约时选择的具体服务
- **预约记录**：一次预约行为的完整载体
- **状态流转记录**：记录预约从创建到取消、完成的变化过程

如果把“客户”和“资源”混在一起，后面一定会乱。因为客户是发起方，资源是被占用方，它们在业务上是两个不同角色。

### 2. 从原型或文档抽实体

如果你拿到的是原型或说明文档，可以这样抽实体：

- 页面上能被搜索、选择、展示、编辑的对象，优先看作实体候选
- 文案里反复出现的名词，通常就是实体候选
- 带有独立生命周期的对象，往往应该单独成表

比如文档里反复出现“预约单”“预约记录”“改期申请”“确认状态”，说明它们很可能不是一个概念。

这里要区分：

- **预约单/预约记录**：核心主记录，应该落表
- **改期申请**：如果业务里单独有申请、审核、通过/拒绝流程，才适合独立成表；如果只是一次修改操作，也可能只是日志记录
- **确认状态**：多数情况下是预约表里的一个状态字段，不必单独做表

### 3. 抽实体时顺手过一遍检查表

老赵建议你抽实体时按这个小清单来：

1. 这个名词是不是业务里会被单独提到？
2. 它有没有自己的生命周期？
3. 它会不会被单独查询、编辑、统计？
4. 它是“对象”还是“属性”？

比如“预约时间”通常是属性，不是实体；  
“状态”通常是字段，不是表；  
“预约记录”才是实体。

最重要的不是“见名就建表”，而是看它有没有**独立身份、独立生命周期、独立查询价值**。有这三点，才值得独立成实体。

---

## 三、流程驱动下的关系设计与字段设计

### 1. 先画流程，再定关系

预约系统的流程通常是：

1. 客户选择资源和时间
2. 系统校验是否可预约
3. 生成预约记录
4. 人工或系统确认
5. 预约完成、取消或改期

流程一出来，关系也就清楚了：

- 一个客户可以有多条预约记录
- 一个资源在同一时间段可能对应多次预约尝试，但最终只能有一条有效占用
- 一条预约记录只对应一个客户、一个资源、一个时间段

这时你就知道，**预约记录是核心事实表**，它负责把客户、资源、时间、状态串起来。

如果业务更复杂，比如一个预约可以包含多个服务项目，那就继续拆：

- 预约主表保存一次预约的整体信息
- 预约明细表保存具体服务项目或数量

这就是从流程反推结构，而不是先有结构再硬套流程。

### 2. 字段怎么拆

字段设计时，不要只看“页面上有什么”，要想三个问题：**它属于谁、它是否可复用、它是否会变化。**

以预约记录为例，字段可拆成：

- 基础标识：预约ID、预约编号
- 关联字段：客户ID、资源ID、服务项目ID
- 时间字段：预约开始时间、预约结束时间、创建时间、确认时间、取消时间
- 状态字段：预约状态、支付状态
- 业务字段：备注、来源、取消原因

客户表里可放：

- 客户ID
- 姓名
- 手机号
- 性别
- 注册时间

资源表里可放：

- 资源ID
- 资源名称
- 资源类型
- 所属门店
- 可用状态

### 3. 字段归类的判断标准

字段归类可以记住一句话：**谁在业务上拥有它，就尽量放到谁那里。**

比如手机号通常归客户表，因为它描述的是客户；  
预约开始时间归预约表，因为它描述的是一次预约行为；  
资源名称归资源表，因为它描述的是资源本身。

再补一个实战判断：如果一个字段会被多张业务记录引用，优先放到主实体里；如果它只是一次行为的描述，就放在行为表里。

字段类型也别拍脑袋：

- 编号类字段用 `VARCHAR`
- 时间类字段用 `DATETIME`
- 状态类字段先用 `VARCHAR`，后面再考虑枚举或字典
- 备注类字段用较长文本类型

这一步就是从逻辑模型走向物理模型。

## 四、效率和规范之间，怎么再次权衡

### 1. 不要把所有东西都拆得很干净

建模不是越拆越好。预约系统里经常会遇到一个现实问题：为了查询方便，要不要把客户姓名、手机号冗余到预约表里？

从规范上看，不冗余更干净。  
从效率上看，列表页经常要展示客户信息，每次都关联查询，可能会麻烦。

这时就要做权衡：

- 如果客户信息很少变，且查询频率很高，可以适度冗余
- 如果信息变化频繁，宁可关联查询，也不要乱复制
- 如果冗余字段只是为了报表或展示，可以接受，但要明确同步规则

### 2. 重复和冗余怎么处理

重复不是绝对坏事，关键看它是不是**可控重复**。

比如预约表里冗余客户姓名，目的是提升列表查询效率，这种重复可以接受；  
但如果客户改了手机号，预约表里的手机号不同步，就会造成数据不一致，这就不行。

所以你要明确：

- 哪些字段允许冗余
- 谁负责更新冗余字段
- 冗余字段失效时怎么办

如果系统规模不大，可以先做“轻冗余”；如果后面会频繁统计、筛选、导出，再考虑更完整的同步机制。

### 3. 一个实用原则

**核心事实尽量规范，展示字段可以适度冗余。**

也就是说，预约时间、资源ID、客户ID这些核心关联一定要规范；而客户昵称、资源名称这类展示型字段，在高频查询场景下可视情况冗余。

这个原则能帮你避开两个极端：

- 过度规范，导致查询性能差、开发体验差
- 过度冗余，导致数据不一致、后期维护痛苦

## 五、用 MySQL 方案完成最终落表

### 1. 表结构思路

以一个简化版预约系统为例，最少可以落成三张主表：

- `customer` 客户表
- `resource` 资源表
- `appointment` 预约表

如果需要记录状态变化，再加：

- `appointment_status_log` 预约状态流转表

这套结构的好处是：主线清楚，职责明确。客户管人，资源管被预约对象，预约表管一次行为，日志表管过程变化。

### 2. 一个简化的落表示意

```sql
CREATE TABLE customer (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  name VARCHAR(50) NOT NULL,
  phone VARCHAR(20) NOT NULL,
  gender TINYINT DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE resource (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  resource_name VARCHAR(100) NOT NULL,
  resource_type VARCHAR(50) NOT NULL,
  store_name VARCHAR(100),
  is_active TINYINT NOT NULL DEFAULT 1
);

CREATE TABLE appointment (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  appointment_no VARCHAR(32) NOT NULL UNIQUE,
  customer_id BIGINT NOT NULL,
  resource_id BIGINT NOT NULL,
  service_name VARCHAR(100),
  start_time DATETIME NOT NULL,
  end_time DATETIME NOT NULL,
  status VARCHAR(20) NOT NULL,
  remark VARCHAR(500),
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_customer_id (customer_id),
  INDEX idx_resource_time (resource_id, start_time, end_time)
);
```

如果要记录状态流转：

```sql
CREATE TABLE appointment_status_log (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  appointment_id BIGINT NOT NULL,
  from_status VARCHAR(20),
  to_status VARCHAR(20) NOT NULL,
  changed_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  operator_name VARCHAR(50),
  remark VARCHAR(500),
  INDEX idx_appointment_id (appointment_id)
);
```

### 3. 落表时要检查什么

落表不是把字段翻译成 SQL 就完事了，至少要检查这几项：

- 主键是否明确
- 外键关系是否能表达业务关联
- 状态字段是否足够覆盖流程
- 常用查询是否有索引支持
- 冗余字段是否有维护机制

你还可以再多问一句：  
**如果业务从“待确认”变成“已确认”，这次变化要不要留下痕迹？**  
如果要，就加状态日志；如果不要，至少保证主表状态能准确反映当前结果。

## 六、再换一个思路：如果做订单系统，会怎么拆

如果你想再练一遍，可以试着把订单系统也按同样方法拆开：

- 客户/用户
- 商品
- 订单主表
- 订单明细表
- 支付状态
- 发货状态
- 订单日志

你会发现，思路其实一样：

先找业务对象，再看流程，再定关系，最后决定哪些字段放主表，哪些字段放明细表，哪些字段需要冗余，哪些字段必须规范。

这就是建模能力开始成型的标志：**换了场景，你还是知道从哪里下手。**

## 结尾小结：把方法带走

这一个预约系统案例，核心不是记住几张表，而是掌握建模顺序：

1. 先定业务边界  
2. 再找核心实体  
3. 之后按流程梳理关系  
4. 然后做字段归类  
5. 最后在规范与效率之间取平衡，并落到 MySQL

如果你能独立把预约系统做明白，基本就说明你已经具备了分析小型业务的能力。

下一步你可以自己拿一个“订单系统”练手，看看能不能把“客户、商品、订单、明细、状态流转”也拆清楚。真正的建模能力，就是在不同业务里都能保持这套思路不乱。

# 第13章：把方法带走——独立分析小型业务的通用步骤

## 开篇引入：别怕新业务，怕的是没有步骤

你已经掌握实体、属性、关系、模型三层、范式与反范式，但实战中仍易卡壳：老板给一段话，从哪儿下手？需求散乱，怎么整理成表？先画图还是先想字段？

老赵建议：**不要靠感觉建模，要靠一套固定动作。** 小型业务建模不必一次想满所有细节，但必须有清晰流程。这样面对任何系统时，按同一套方法推进，而非每次重来。

本章把前面方法收束为可复用步骤，目标是：**让你独立分析小型业务时，知道先做什么、后做什么、哪里要补问、哪里要校验、最后如何落到 MySQL。**

---

## 一、小型业务建模的通用步骤清单：先有路线，再动手

小型业务建模最怕一上来就写表——表一先定，思路易被字段锁死，结构越补越拧巴。正确顺序是这七步：

**步骤1：理解业务目标**——搞清楚系统支撑什么业务流程。论坛核心是发帖、回帖、点赞；预约系统是预约、排期、取消；订单系统是下单、支付、发货。先定核心动作，数据才能围绕它流转。

**步骤2：抽取业务对象**——圈出需求里的名词。用户、帖子、评论、版块可能是实体；用户名、标题、内容可能是属性。注意：不是所有名词都是实体，“预约”“订单”常是核心业务对象；“提交”“确认”是动作，但也影响状态字段设计。

**步骤3：梳理业务流程**——看对象如何流转：谁创建、谁修改、谁关联谁、先后顺序。流程一清楚，关系就好定。

**步骤4：字段拆分与归类**——将原型、文档中的字段拆开归类，判断归属哪个实体。记住：字段要拆到能表达业务为止。“联系信息”太笼统，要问：是手机号、邮箱还是地址？

**步骤5：设计关系**——判断一对一、一对多或多对多，多对多一般拆中间表。关系设计凭业务事实：一个用户发多帖、一帖只属一作者，是一对多；一帖被多用户点赞、一用户可点赞多帖，需建点赞表。

**步骤6：规范性检查**——检查重复数据、冗余字段、字段独立性。平衡范式与业务效率：有些冗余为提高查询效率，有些则是设计未想清楚。

**步骤7：落表到 MySQL**——将逻辑模型转为具体表结构：主键、外键、索引、字段类型、是否允许为空。让模型在数据库中活起来，考虑存储、查询效率、数据一致性与扩展性。

这套步骤本质：**先理解业务，再抽对象，再定关系，再落字段。**

## 二、实战流水线：从需求到落表的完整操作

### 第一步：把需求文本翻译成业务语言

不要急于建模，先读懂需求。看页面有哪些模块、每个模块有哪些操作、产生什么数据、谁在什么场景使用。

例如预约系统原型有“选择日期、选择时段、填写姓名手机号、提交预约、查看记录”，透出预约时间、预约人、联系方式、状态、记录——这些就是建模线索。

老赵提醒：页面是表现层，真正要抽的是业务事实。按钮是触发点，数据才是重点。

### 第二步：从原型/文档抽象实体

**页面不是表，按钮不是字段，页面只是业务外壳。** 要抽的是“长期存在、可被管理、会被重复引用”的对象。

前三个案例训练能力：
- **论坛案例**（4-6章）：从用户生成内容识别实体——用户、帖子、评论、版块
- **预约案例**（7-9章）：从服务流程抽取实体——会员、服务项目、预约单、时段
- **订单案例**（10-12章）：从交易流程设计实体——订单、商品、客户、支付记录

抽实体先抓主干再补边角。新手常错：一看到页面就想把每个按钮对应成一张表，结果表碎、关系乱。

### 第三步：字段归类

三个判断标准：
- **谁拥有这个信息**：用户名属于用户，不属于订单
- **谁会重复出现**：商品名称出现在多订单明细，但本质属于商品
- **谁决定生命周期**：评论内容跟评论实体绑定，不能挂在帖子上凑合

例如订单系统：“订单号、下单时间、订单状态”属订单；“商品名称、商品单价、购买数量”属订单明细；“收货人、收货电话”属订单快照，而非客户主档——用户可能改地址，但历史订单要保留当时信息。

### 第四步：设计关系

围绕业务事实设计。例如预约系统：一个用户可有多预约单（一对多），一个服务项目被多预约单选择（一对多），一个预约单对应一个时段（具体看是否允许重复预约）。

### 第五步：做模型校验

回到需求检查：
- 所有重要业务动作能否表达？
- 是否能查询关键数据？
- 是否能追踪历史？
- 是否存在无法落表的字段？
- 是否有明显重复与冲突？

订单系统没订单明细表就无法表达一单多商品；预约系统没状态字段就无法区分已预约、已取消、已完成。

### 第六步：落表实现到 MySQL

通用决策标准：
- **字段类型**：文本用 VARCHAR，日期用 DATE/DATETIME，金额用 DECIMAL(10,2)，状态用 TINYINT 或枚举
- **索引**：主键自动建索引；频繁查询的如用户ID、订单号、创建时间需索引；备注等低频检索字段没必要
- **唯一约束**：订单号、账号、手机号需要；状态字段一般不需要
- **外键与冗余**：关联字段建外键约束或至少索引；冗余保留与否看查询频率——常需订单快照地址就保留，否则从客户表查

## 三、面对不完整需求时，怎么补问、补分析？

真实项目需求永远不会一次说全。正确做法：**边分析边补问。**

### 1. 先识别缺口

常见缺口：对象没说全（系统有哪些主体）、规则没说清（能否重复预约、订单能否取消）、状态没说清（过程有哪些阶段）、历史是否保留（改地址后旧订单怎么办）。

### 2. 用业务问题反问需求方

不问“你要几个表”，问业务问题：
- 一个用户能否同时预约多个时段？
- 预约取消后名额是否释放？
- 订单支付失败后是否保留记录？
- 评论删除是物理删除还是逻辑删除？

问得越业务，答案越有用。

### 3. 做合理假设，但要标记出来

一时得不到答案，先按常见规则做临时假设并写清楚。例如：默认一预约单只选一个时段；订单支付信息单独记录；历史地址以订单快照保存。后续需求变化时好改也好解释。

老赵提醒：**建模不是猜题，是把不确定性显性化。**

## 四、新业务建模检查清单：交付前先过一遍

以后接到新业务，用此清单自检：

| 检查项 | 具体问题 | 通过？ |
|--------|----------|--------|
| 实体完整 | 主业务对象是否已识别？从属对象是否已拆出？ | □ |
| 字段归类 | 字段是否放到了正确实体？是否存在跨表混放？ | □ |
| 关系清晰 | 一对多是否明确？多对多是否拆了中间表？ | □ |
| 冗余处理 | 必要快照字段有没有？不必要重复字段有没有？ | □ |
| 规范与效率平衡 | 过度拆表会不会让查询太复杂？适当冗余能否减少关联？ | □ |
| MySQL 可落地 | 字段类型合理吗？索引支持常用查询吗？唯一约束设对了吗？ | □ |

这份清单能帮避免大部分“画得挺美，落不了地”的问题。

## 五、学习后如何继续练习与提升？

建模能力是练出来的，三种最有效方式：

### 1. 拿原型练

选一个简单原型，每次只练一类对象：今天练实体识别，明天练字段归类，后天练关系设计。不求完美，先求能拆开。拆得越多，越能看出页面背后的业务骨架。

### 2. 拿需求文档练

把一段业务描述手工翻译成：核心实体 → 关键字段 → 关系图 → 表结构草案。练久了，看到需求时脑子里会自动浮现模型骨架。

### 3. 拿自己做校验

每次练完问自己：这个模型能否支撑主要业务流程？有没有字段放错地方？有没有不必要冗余？如果现在用 MySQL 建表，哪里会卡住？

**练习题**：微信读书的“书架”功能——用户收藏书籍、阅读、标注、写想法。请按本章七步法，从实体识别开始，完成概念模型、逻辑模型、物理模型。做完后，用检查清单自我校验。

## 结尾小结：把方法装进你的工具箱

本章把前面知识收口：**先理解业务，再抽实体；先拆字段，再定关系；先做校验，再落表；遇到不完整需求，补问、补分析、补假设。**

你以后面对小型业务时，按这七步走：
1. 看业务目标 → 2. 抽业务对象 → 3. 整理流程 → 4. 字段归类 → 5. 设计关系 → 6. 校验模型 → 7. 落到 MySQL

把这七步用熟，哪怕第一次见到新系统，也不会“完全没思路”，而是能稳稳往下推。
