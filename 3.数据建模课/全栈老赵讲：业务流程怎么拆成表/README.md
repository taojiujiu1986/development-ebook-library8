# 第1章：先别画ER图，先看流程图——流程型业务到底在建什么

## 开篇引入：别急着问“表怎么建”，先问“事情怎么走”

很多人第一次接手流程型业务，第一反应是：“这个对象有哪些字段？”、“要不要一张主表？”、“状态加个`status`行不行？”

这套思路做静态信息管理还凑合，一碰到注册、下单、审批、发布、预约、退款这类业务，就很容易翻车。因为流程型业务真正要管的，不是“对象长什么样”，而是**事情怎么走、在哪个节点卡住、谁做了什么、状态怎么变、最后结果是什么**。

所以这本书的第一条原则很简单：**先看流程图，再谈表结构。**

## 一、流程型业务到底长什么样？

### 1.1 有节点，有状态，有流转，有结果

流程型业务有明确节点，比如“提交”→“审核”→“通过/驳回”→“支付”→“完成”。这些节点是数据模型的骨架，每个节点都可能对应一次操作、一个状态变化、一条记录、一次权限判断。

状态不是字段名，而是业务事实。比如订单的“待支付”“已支付”“已完成”，审核单的“草稿”“待审批”“已通过”——状态必须和流程节点对应，否则就会出现“表里写着已完成，实际上还在退款中”的乱象。

流程型业务还会持续流转：今天“待审核”，明天“审核中”，后天“补充材料”。这决定了你不能只存最终结果，还要存每一次状态变更的过程。结果是节点、状态变更、操作日志积累出来的，你需要“结果可见”，更要“结果可解释”。

## 二、流程图与数据模型是什么关系？

### 2.1 先流程，后表结构

很多项目一开始就画ER图，画着画着就把业务画“平”了。流程图更接近业务事实，它会逼你先想清楚：有哪些节点？哪些节点会触发状态变化？谁能操作？每一步要不要留痕？是否允许回退、撤回？

等这些问题想清楚，再拆表，表结构才不会飘。比如订单流程如果只有“下单、支付、完成”，一张订单表可能够；但加上“取消、超时关闭、支付失败重试、售后退款”，单靠主表根本装不下完整过程。

### 2.2 流程图是表结构的说明书

流程图至少要帮你回答三个问题：**当前状态怎么表示？状态怎么从A变到B？历史怎么查？**

如果流程图里有“提交—审批—驳回—再提交”，那表里就不能只有一个状态字段，还要有流转记录表、操作日志表、历史快照表（视业务需要）、关联对象表。流程图的价值，就是让你知道哪些信息必须长期保存，哪些只保留当前值，哪些只记录过程、不参与业务判断。

## 三、用一个订单支付案例，看流程驱动建模怎么做

假设一个简单的订单支付流程：用户创建订单→待支付→完成支付→系统确认→已支付（若超时未付则取消）。

### 3.1 先定义业务表

只放当前订单的核心信息：订单编号、用户ID、金额、当前状态、创建时间、更新时间。这里的`status`只表示当前状态，不负责记录过程。

### 3.2 再定义流转记录表

专门记录状态变化：订单ID、起始状态、目标状态、变更原因、操作来源、操作时间、操作者。这样你就能查到：从待支付到已支付是谁触发的，从待支付到取消是系统超时还是人工关闭。

### 3.3 再补操作日志表

记录“人或系统做了什么动作”，不一定等于状态变更。比如点击提交、发起支付、修改收货地址、手动关闭订单。操作日志记录动作事实，流转记录表记录状态事实，排查时要两张表一起看。

### 3.4 需要历史快照时，再存快照

如果订单在不同阶段展示信息差别很大，比如支付前、支付后、发货后内容不同，就要考虑历史快照。把某一时刻的业务内容原样保存下来，这样即便订单修改了，也能看到当时提交了什么、审核时看见了什么。售后、审批、合同、内容发布这类场景尤其需要快照。

## 四、章节小结：最常见的误区，是先画表后补流程

流程型建模的本质，不是把“东西”存进去，而是把“事情怎么发生”也一起存下来。下次遇到注册、下单、审批、发布、预约、退款这类需求，先别急着建表，先写出三样东西：流程图、状态列表、每个节点会产生什么记录。

### 常见坑总结

- **误区1：先画表后补流程**——忽略流程节点，只盯着对象字段，导致结构对不上业务走向
- **误区2：只存当前状态，不存状态变更**——出了事查不到“为什么到这、谁改的、改了几次”
- **误区3：把业务表和流水表混成一张**——追求“省表”反而把复杂度全塞进一张表，改起来更难
- **误区4：忽略操作日志**——问题排查时查不到人和动作，无法闭环
- **误区5：不做历史快照**——无法回溯关键时点的业务内容
- **误区6：关联对象设计不清**——后面查询全靠联表硬凑，越查越痛苦

# 第2章：业务表和流水表别混了——先把“当前态”和“过程态”分开

## 开篇引入：先问一句，这张表到底是“现在什么样”，还是“怎么走到现在”的？

流程型业务里，最容易犯的错，就是把**业务表**和**流水表**混成一锅粥。你想查“当前订单状态”，它给你一堆支付记录；你想看“审批现在到哪一步”，它给你历史审批日志。最后不是查不出来，就是查出来也不敢信。

这一章先把最基础的事讲清楚：  
**业务表负责当前状态，流水表负责过程变化。**  
不是命名问题，是建模边界问题。

你可以把它理解成两本账：
- 一本账记“现在这件事算什么”
- 一本账记“这件事是怎么一步步变成现在这样的”

这两本账不能混。混在一起，短期像省事，长期就是把查询、审计、排查、统计全埋雷了。

## 一、业务表负责当前状态，流水表负责过程变化

### 1. 什么叫“当前状态”？

业务表存的是这个业务对象**此刻有效的业务事实**。比如订单当前是“待支付”还是“已完成”。它回答的是：**这件事现在到底算什么状态？**

所以业务表通常会包含：
- 业务主键
- 关键业务字段
- 当前状态字段
- 当前责任人/处理人
- 创建时间、更新时间

这些字段的价值在于：**一查就知道现在的业务结论。**

### 2. 什么叫“过程变化”？

流水表记录的是对象在生命周期里经历了什么变化。比如谁在什么时间把状态从“待审批”改成“审批中”。流水表强调的是**过程留痕**，不是最终结果。核心价值是：**可回放、可追踪、可审计。**

### 3. 一条记录到底该放哪边？

判断标准很简单：
- **描述当前有效结果，放业务表**
- **描述一次动作、一段变化、一条轨迹，放流水表**
- **既要当前可查询，又要历史可追溯，通常两张表都要有**

最常见的错误，是把“最近一次操作记录”当业务状态本体。比如有人把 `last_action=同意` 当成“当前已通过”，结果下次撤回、重提，语义就崩了。**业务表是“结论表”，流水表是“经过表”。**

## 二、先定语义，再定表结构

很多团队建表时先想字段，再想业务，最后全乱。正确顺序应该是：
1. 这条记录代表什么对象？
2. 它是当前有效状态，还是历史留痕？
3. 它是可被修改的，还是只追加不更新？
4. 谁会查它？查什么？

**当前有效：**
- 一条对象通常只有一行，允许更新
- 适合做主查询入口，如订单主表、审批单主表

**历史留痕：**
- 同一对象可能对应多条记录，追加写入
- 适合回溯、审计，如状态流转表、操作日志表

### 一个简单的判断口诀
- **“我要看现在” → 查业务表**
- **“我要看过程” → 查流水表**
- **“我要看谁改了什么” → 查操作日志表**
- **“我要看改之前是什么” → 查历史表或快照表**

如果一张表同时承担这四种需求，通常就是建模失控的开始。

## 三、订单、审批单、工单、会员申请，职责划分怎么做？

### 1. 订单场景

**订单主表**负责当前业务事实：订单是谁下的、金额多少、当前状态。尽量稳定，避免把每一次支付尝试都塞进去。

**流水表**负责过程变化：支付流水、发货流水、状态流转记录。例如订单经历待支付→支付中→待发货→已完成，这些都应记录在流水表。

**为什么不能都塞进订单主表？** 会导致业务字段膨胀、状态语义混乱、更新频繁锁竞争、历史痕迹丢失。

### 2. 审批单场景

**主表**存：申请人、申请类型、当前审批状态、当前审批人、最终结果。让系统快速回答：“这张单现在在哪一步？”

**流转记录表**存：节点名称、审批人、审批动作、动作时间、审批意见、前一节点、后一节点。让系统回答：“这张单是怎么走过来的？”

**常见误区**：把审批意见直接写进主表，只剩“最新意见”，无法还原“路径”。

### 3. 工单场景

**工单主表**：工单编号、当前状态、当前负责人、是否关闭。

**工单流水/日志**：创建、受理、转派、处理、恢复、关闭。如果只保留当前负责人，涉及责任归属、超时统计时，过程信息就是核心数据。

### 4. 会员申请场景

**申请单表**：申请人信息、当前审核状态。**会员档案表**：会员编号、当前等级、生效时间。

不要把“申请记录”当“会员档案”用。申请通过前只是申请；通过后才转化为会员档案。正确做法：申请单记录申请过程，会员档案记录当前身份，必要时补会员变更流水表。

## 四、主表、明细表、日志表、历史表之间的关系

### 1. 主表：业务对象的入口
负责核心身份和当前状态，应尽量“少而稳”。

### 2. 明细表：主表下的组成项
存业务对象的组成部分，如订单明细。强调结构拆分，不强调过程变更。

### 3. 日志表：谁在什么时候做了什么
记录操作痕迹：操作人、操作时间、操作类型、操作前后摘要。用于排查问题、审计责任。

### 4. 历史表：记录过去某个时点的状态
保存对象完整状态快照，用于事后追溯、版本对比。与日志表区别：历史表偏“结果快照”，日志表偏“动作轨迹”。

### 5. 四类表如何协作？
- **主表**：当前态入口
- **明细表**：结构化组成项
- **日志表**：操作行为留痕
- **历史表**：阶段性状态备份
- **流水表**：状态流转轨迹

这样拆完后，查业务、查过程、查责任、查版本，各有入口，不会互相污染。

## 五、常见坑总结

- **坑1：把流水数据存入业务主表**  
  查询时不知取最新一条还是中间状态，口径不一致。

- **坑2：未区分当前态和过程态**  
  状态被反复覆盖后无法回溯。例如审批单经历“驳回→重提→通过”，主表只留“通过”，中间信息全丢。

- **坑3：日志表与流水表职责混用**  
  日志表记录操作动作，流水表记录状态变化。混用后既无法快速还原过程，也无法定位责任人。

- **坑4：一张表承担太多职责**  
  既做当前查询，又做历史记录和统计分析，导致字段多、索引复杂、查询慢。表设计一旦失去边界，代码全跟着变重。

## 六、实战拆表时，先问自己这 4 个问题

1. **这张表代表什么对象？** 是申请单、订单，还是某次操作？
2. **这张表存的是当前有效值，还是过程记录？** 当前态要简洁稳定；过程态要明确追加策略。
3. **谁最常查这张表？** 业务人员关心当前结果，审计人员关心操作链路。
4. **这条数据会不会被反复改写？** 如果会，就要考虑历史表、日志表、流水表。

反复改写的数据，最怕丢过程。一旦过程不可追踪，系统就只剩“最后值”，没有“为什么变成这个值”。

---

## 章节小结：先分清“当前态”和“过程态”，再谈拆表

流程型业务建模，最基础的一刀，就是把**业务表**和**流水表**分开。

- **业务表**回答“现在是什么状态”
- **流水表**回答“这个状态是怎么来的”
- **日志表**回答“谁做了什么”
- **历史表**回答“过去某一刻是什么样”

把这几类表的职责边界划清楚，后面的流程节点、状态变更、审批流转，才有地方落。

### 最后给你一句实战建议

以后设计流程型业务时，先别急着画 ER 图，先拿笔写清楚三句话：
1. **这个对象的当前态放哪张表**
2. **这个对象的过程态放哪张表**
3. **谁来查当前态，谁来查过程态**

这三句话写清楚了，表结构基本不会跑偏。写不清楚，后面大概率就是“把流水当业务表”，然后在查询混乱和状态失真里反复补洞。

# 第3章：状态字段怎么设计——别让一个status背锅

# 第3章：状态字段怎么设计——别让一个 `status` 背锅

## 开篇引入：状态不是装饰，它是流程的“门牌号”

做流程型业务，最容易被低估的就是状态字段。很多项目一开始都很朴素：一张订单表，一个 `status` 字段，`0` 表示未支付，`1` 表示已支付，`2` 表示已发货，`3` 表示已完成。看起来够用，直到退款、部分发货、取消订单、超时关闭、售后介入陆续出现，`status` 就开始替整个流程背锅。

状态字段的本质，不是“这个单子现在看起来怎么样”，而是“这个业务对象当前走到了流程的哪一站”。它对应流程图上的节点，而不是页面文案。你今天看到一个“已完成”，背后可能是用户确认收货，也可能是系统超时自动完成；你今天看到一个“已取消”，背后可能是用户主动取消，也可能是支付超时关闭。语义不清，后面一定会乱。

所以，这一章不只讲“怎么定义状态值”，还要讲清楚：**状态字段怎么跟业务动作、流转记录、历史记录、操作日志配合起来，才能让流程可追踪、可查询、可维护。** 这也是流程型建模里最容易踩坑、也最值得先想明白的一环。

---

## 一、状态字段的基本设计：单字段、多字段、主辅状态

### 1. 为什么不是所有状态都塞进一个字段里？

很多人设计流程表时，第一反应是“一个 `status` 搞定”。这在流程简单时可以，但只要业务有多个维度，就容易失真。比如订单业务里，至少会同时存在：

- 主流程状态：待支付、已支付、已发货、已完成、已取消
- 履约状态：待拣货、待出库、运输中、已签收
- 售后状态：无售后、退款中、退款成功、退款失败
- 审核状态：待审核、审核通过、审核拒绝

如果强行混在一个字段里，状态数量会越来越多，语义开始重叠，最后形成“状态爆炸”。短期省事，长期最费事，因为查询条件更长，判断分支更多，连运营筛选都得猜状态含义。

### 2. 单字段状态：适合“单线流程”

单字段适合流程比较线性、不会并行分叉的场景，比如：

- 预约：待确认 → 已确认 → 已取消
- 简单工单：待处理 → 处理中 → 已关闭
- 审核：待审 → 通过 → 驳回

这种场景下，一个主状态字段就够了。建议命名上直接表达业务语义，比如 `order_status`、`audit_status`，别只叫 `status`。一张表不止一个状态字段时，`status` 会越来越不清楚，排查问题也更费劲。

### 3. 多字段状态：适合“多个维度并存”

如果一个业务同时包含多个独立流程，建议拆成多个状态字段，而不是挤在一起。比如订单可以拆成：

- `pay_status`：未支付 / 已支付 / 退款中 / 已退款
- `delivery_status`：未发货 / 部分发货 / 已发货 / 已签收
- `after_sale_status`：无售后 / 售后中 / 已完成
- `order_status`：待支付 / 待发货 / 待收货 / 已完成 / 已取消

这里的关键是：**主状态负责对外展示和列表筛选，辅状态负责局部流程控制。** 主状态给前端和运营看，让人一眼知道大阶段；辅状态给系统内部用，承接支付、发货、售后这些局部动作。

好处是查询不会被一个超长枚举绑死；代价是状态之间需要更清晰的约束，避免出现“订单已完成，但支付状态还是未支付”这种自相矛盾的数据。多字段不是随便拆，拆完还要有统一的状态校验规则。

### 4. 主辅状态：把复杂流程拆开看

主辅状态是实战里很常见的思路。主状态描述业务对象在主流程中的位置，辅状态描述附加流程的子过程。比如内容审核：

- 主状态：草稿 / 待审核 / 已发布 / 已下线
- 辅状态：审核中 / 审核通过 / 审核拒绝 / 申诉中

这样做的好处是，列表页看主状态，详情页看辅状态和历史记录；业务规则也更容易写：主状态不负责解释所有细节，辅状态承接局部复杂度。很多原本纠缠不清的字段，也会因此自然分开。

---

## 二、状态枚举怎么定义，才能撑住扩展和维护？

### 1. 状态枚举不是随便写几个值

很多团队定义状态时，只考虑当前功能，不考虑后续演进。比如：

- `0` 未处理
- `1` 处理中
- `2` 已完成

三个月后需求来了：处理中还要区分“已接单”“待人工”“待自动审核”；已完成还要区分“正常完成”“超时完成”“系统关闭”。这时原来的枚举就会失语。

定义枚举前，先确认两个问题：

1. **这个状态是给谁看的？**
   - 给前端展示
   - 给运营筛选
   - 给后端流程控制
2. **这个状态是结果态还是过程态？**
   - 结果态适合稳定展示
   - 过程态适合短期流转

如果一个状态既要给用户看，又要给系统判断，就要警惕它是不是职责太多。状态一旦承担太多职责，就难维护。

### 2. 状态枚举的设计原则

#### 原则一：语义优先，不要只靠数字记忆

数字可以存储，语义必须可读。代码里最好用常量、枚举类或字典表统一维护，不要散落各处硬编码。否则 `1` 到底是“已支付”还是“待发货”，只能靠记忆，设计本身就不稳。

#### 原则二：状态值要稳定，名称可以演进

状态编码一旦上线，最好不要轻易改。历史数据、日志、报表、接口都可能依赖它。真要改，优先改展示名，不要随意改底层值。老系统里最怕“为了好看重命名状态”，结果历史数据和统计全跟着出问题。

#### 原则三：枚举要分层

不要把所有状态都放一层里。可以按“主流程状态 / 子流程状态 / 终态 / 异常态”来组织。比如“待支付”“待发货”“待收货”是主流程，“退款中”“审核中”是子流程，“已取消”“已关闭”则属于终态或异常终态。这样新增状态时，更容易放到合适位置。

### 3. 什么时候该用字典表，什么时候该用代码枚举？

如果状态只是内部逻辑控制，且变更频率低，代码枚举就够了。

如果状态需要：

- 后台可配置
- 前端可动态展示
- 多语言支持
- 文案经常调整

那就更适合做字典表。但要注意：**字典表只是展示层，流程判断仍然要有统一规则。** 否则字典里有状态，代码里没处理，也会出事故。

说白了，字典表解决“看得懂”，状态机规则解决“走得通”，两者不能互相替代。

---

## 三、状态与业务动作的关系：谁改状态，什么时候改，改完去哪？

### 1. 状态不是自己跳的，是动作触发的

设计状态时，最怕只盯结果，不盯动作。状态变化一定要回答三个问题：

- 谁改的：用户、系统、运营、审核员、定时任务
- 什么时候改：下单后、支付成功后、审核通过后、超时后
- 改完去哪：下一状态是什么，是否允许跳过

如果回答不出来，说明这个状态只是写给人看的，不是写给系统执行的。可维护的状态设计，应该能让你顺着一次动作找到状态变化逻辑，再顺着状态变化找到对应的业务事件和记录。

### 2. 建议把状态变化看成“状态机”

状态机就是：**某个对象只能按照预定义路径从一个状态走向另一个状态。** 比如订单：

- 待支付 → 已支付
- 待支付 → 已取消
- 已支付 → 待发货
- 待发货 → 已发货
- 已发货 → 已完成

要注意：不是所有状态都能互相跳。比如“已完成”一般不能直接回到“待发货”。如果允许乱跳，数据看起来能改，业务规则却全乱了。状态设计不是“能存就行”，而是先画流程图，再把流程图映射成允许的状态迁移表。流程图上的边，才是合法的状态关系。

### 3. 状态变更要配套记录

状态字段只存当前值，不存过程。要想可追踪，必须配套：

- **流转记录表**：记录每次状态从哪来、到哪去、谁操作、何时操作
- **操作日志表**：记录具体做了什么动作、原因、备注
- **历史快照**：记录变更前后关键业务数据，方便回溯

例如：

- 订单主表：只保留当前 `order_status`
- 订单流转表：每次状态变化插一条
- 订单操作日志：记录支付回调、人工关闭、后台退款等动作
- 订单快照表：保留变更时的收货地址、金额、商品信息

这样主表负责现状，流水表负责轨迹，日志负责动作，快照负责当时长什么样。流程型业务里“可追踪”的核心，不是只知道现在在哪，而是知道一路怎么走过来的。

---

## 四、状态字段的常见坑：别让状态膨胀、语义打架

### 1. 状态过多：一个字段装进了整个宇宙

最典型的坑，就是状态定义得太细，细到每个分支都塞进一个字段里。结果是：

- 查询条件复杂
- 前端展示混乱
- 后端分支爆炸
- 新增状态时难兼容老逻辑

判断标准很简单：如果一个状态值只代表某个特殊场景下的临时细节，它通常不该成为主状态。主状态应该承载主流程，不该替所有异常情况背锅。异常情况更适合放到辅状态、原因字段、日志表或事件表里。

### 2. 语义不清：状态名自己都说不明白

比如这些状态名就很危险：

- 处理中
- 待处理
- 进行中
- 已处理

它们看起来像一个意思，实际可能对应完全不同的流程位置。更好的做法是贴近业务动作，比如：

- 待审核
- 审核中
- 审核通过
- 审核驳回

这样团队成员看到名字，就知道大概在什么阶段。状态命名不是文案工作，它其实是建模工作。名字不清，模型就不清。

### 3. 含义重叠：两个状态看起来一样，实际上不同

比如：

- `已支付`
- `支付成功`

如果不区分，一个可能是支付结果，一个可能是支付回调结果，就容易让数据判断错位。还有些场景里，“已取消”和“已关闭”也不一样：一个是用户主动取消，一个是系统超时关闭。业务上应该分开，别硬合并。只要后续处理会分叉，就不要把它们当成同一个值。

### 4. 状态只改字段，不留痕

这是最严重的坑。很多系统只有一个 `status`，每次更新只改当前值，连变更时间都不记。最后出了问题，没人知道是谁改的、为什么改的、从哪改来的。流程型业务一旦没有历史记录，排查只能靠猜。

尤其是审批、退款、售后这类场景，状态不留痕，责任也说不清。

---

## 五、结合下单、支付、发货案例拆解状态演进

### 1. 先看主流程怎么走

订单业务最常见的主流程大概是：

1. 用户提交订单，状态为 `待支付`
2. 支付成功，状态变为 `待发货`
3. 商家发货，状态变为 `待收货`
4. 用户确认收货，状态变为 `已完成`
5. 超时未支付，状态变为 `已取消`
6. 支付后发生退款，进入 `退款中` 或 `已退款`

这里的 `order_status` 负责主线流程就够了，但仅靠它远远不够。支付、发货、售后本来就是不同维度的流程节点，硬塞成一个值，后续一定难查、难扩展、难回溯。

### 2. 为什么还要拆支付状态和发货状态？

因为支付和发货不是一条线：

- 支付关注资金是否到位
- 发货关注履约是否完成

所以更稳妥的设计通常是：

- `order_status`：待支付 / 待发货 / 待收货 / 已完成 / 已取消
- `pay_status`：未支付 / 支付中 / 已支付 / 退款中 / 已退款
- `delivery_status`：未发货 / 已发货 / 部分发货 / 已签收

这样可以处理很多现实问题，比如：

- 订单已取消，但支付回调晚到，如何处理？
- 订单部分发货后是否还能退款？
- 已支付但未发货时，是否允许人工关闭？

这些问题不能只靠一个状态字段回答。你需要的是一个能表达“主流程 + 子流程 + 异常分支”的模型，而不是一个无限膨胀的枚举表。

### 3. 状态变更、历史记录、操作日志怎么配合？

以“支付成功”为例：

- 主表更新 `order_status` 为 `待发货`
- 主表更新 `pay_status` 为 `已支付`
- 流转记录表插入一条：`待支付 -> 待发货`
- 操作日志表记录：支付回调成功、第三方交易号、回调时间、来源
- 历史快照表保存：订单金额、优惠信息、收货地址、商品明细

如果后面发生退款，再补一组记录。这样就能回答：

- 这个订单什么时候支付的？
- 为什么状态从待发货变成退款中？
- 当时商品和收货信息是什么？
- 谁在后台做了人工介入？

这就是“可追踪”的意义。流程型业务不是只看最后结果，而是能把每次状态变更、每次操作动作、每次关键对象变化都串起来。

---

## 六、状态字段设计检查清单：上线前先过一遍

在你准备把状态字段写进表结构之前，建议先过一遍：

- 这个状态是主状态还是辅状态？
- 是否存在多个独立流程，应该拆字段而不是硬合并？
- 每个状态值是否有明确语义，团队成员是否看得懂？
- 状态是否存在合法流转路径，是否允许任意跳转？
- 是否有流转记录表，能记录每次状态变化？
- 是否有操作日志表，能记录是谁、何时、因为什么改的？
- 是否需要历史快照，保留变更时的关键数据？
- 是否区分业务表与流水表，避免把当前态和过程态混在一起？
- 是否考虑了审批、审核、退款、超时等异常路径？
- 是否方便查询当前状态和状态历史？

如果这十个问题里有三个以上答不清楚，说明状态设计还没真正落地。你表面上只是写了一个字段，实际上是在定义整个流程系统的骨架。

---

## 结尾小结：状态字段不是越少越好，而是越清楚越好

流程型业务里，`status` 不是一个简单字段，它是整个流程模型的入口。设计状态字段时，先别急着写代码，先回答三件事：

1. 这个业务的流程节点有哪些？
2. 每个节点之间怎么流转？
3. 哪些信息要写进当前表，哪些要写进流转记录、操作日志和历史快照？

记住一句老赵式经验：**状态字段的目标不是把所有情况都装进去，而是让每一次状态变化都能被解释、被追踪、被查询。**

如果你发现一个 `status` 已经开始背不动了，别硬扛。该拆主辅状态就拆，该加流转记录就加，该建日志就建日志。流程型系统最怕的不是状态多，而是状态乱。

# 第4章：流程节点怎么落表——从“第几步”到“谁处理过”

## 开篇引入：流程图画得再漂亮，最后还是要落到表里

做流程型业务，很多人先画流程图：提交、审核、执行、完成。图画完，真正麻烦的才开始——**数据库里到底怎么存？**

我见过不少项目，流程图挺完整，到了表设计却一下子散了：

- 只存一个 `status`，只能看出“现在大概在哪”；
- 没有节点记录，出了问题追不回“谁卡住了”；
- 审批人换了，历史记录没保留；
- 业务表既存主数据，又存流转信息，最后又乱又难查。

所以这一章只讲一件事：**流程节点怎么落表。**

也就是把“第几步”“谁处理过”“处理结果是什么”“这条流程怎么走过来的”这些抽象问题，变成能存、能查、能追踪的数据结构。

你做审批、审核、工单、售后、发布、预约这类业务，都会遇到同一个问题：  
**流程不是静态数据，它是不断变化的过程。**  
数据库最怕的，就是把过程硬塞成一个结果字段，最后只剩“当前状态”，看不见来路，也看不见去向。

---

## 一、流程节点建模的核心字段：节点编号、节点名称、节点类型、前后关系

### 1. 节点不是“页面上的一步”，而是“流程中的一个可管理单元”

在系统里，节点至少要回答四个问题：

- 这是第几个节点？
- 这个节点做什么？
- 这个节点谁来处理？
- 它前后分别连着谁？

所以节点建模不能只靠名字，通常需要这些字段：

- `node_code`：节点编号，稳定唯一，便于程序判断
- `node_name`：节点名称，比如“主管审批”“财务复核”
- `node_type`：节点类型，比如发起、审批、执行、结束
- `prev_node_code` / `next_node_code`：前后关系，或用关系表表达
- `is_start` / `is_end`：是否开始/结束节点
- `sort_no`：顺序号，便于展示和规则判断

要注意，**节点不是给人看的流程图名字而已，它是业务规则的锚点。**  
“审核”这个词太泛，落到系统里就必须细化：初审、复审、财务审核、内容审核，含义和规则都可能不同。

### 2. 为什么节点编号比节点名称更重要

项目里最常见的坑，就是拿节点名称做主键。今天叫“主管审批”，明天改成“部门审批”，历史数据就乱了。

正确做法是：

- **`node_code` 用来做程序识别**
- **`node_name` 用来做展示**
- 名称可以改，编号尽量不改

这是流程型建模的基本原则：  
**可变的是展示，不可变的是标识。**

实际落地时，`node_code` 可以设计成类似 `start_submit`、`mgr_approve`、`hr_record` 这样的稳定编码。界面文案改了，流程判断也不会受影响。

### 3. 前后关系怎么存

流程图是有方向的。表结构里要么存：

- 每个节点直接记录 `prev_node_code` 和 `next_node_code`
- 要么单独建一张“节点关系表”，记录 `from_node`、`to_node`、`condition`

如果流程是线性的，字段直连就够了。  
如果有分支、会签、条件跳转，就别硬塞在一个节点表里，最好单独建关系表，免得后面规则越来越乱。

审批流里常见“同意走下一步，驳回回上一节点，金额大于阈值进入复审”。这时节点本身不变，**变化的是节点之间的转移条件**。所以流程图和数据模型，不能只看“长什么样”，更要看“怎么走”。

---

## 二、节点定义和节点实例：为什么不能混为一谈？

### 1. 节点定义是“模板”，节点实例是“运行中的一次记录”

这点特别关键。很多人一开始就把两者混了。

- **节点定义**：流程图上的规则说明，描述“应该怎么走”
- **节点实例**：某个具体业务单据在运行过程中，真实走到的节点记录

比如审批流里有一个节点叫“部门经理审批”。  
但某张请假单运行时，这个节点可能已经被张三处理过，也可能被李四驳回后重新提交过。

所以要区分：

- 定义层：流程模板、节点模板、流转规则
- 实例层：某张单据的实际流转过程、当前停在哪、历史走过哪些步

### 2. 定义表和实例表分别管什么

常见拆法如下：

#### 流程定义相关表
- `flow_definition`：流程定义主表
- `flow_node_definition`：节点定义表
- `flow_relation_definition`：节点关系表

#### 流程实例相关表
- `flow_instance`：某张单据对应的一次流程实例
- `flow_node_instance`：实例节点记录
- `flow_action_record`：处理动作记录

这样拆的好处很直接：  
**定义可以复用，实例可以追踪。**

同一个“请假审批流程定义”可以被一千张请假单复用，但每张单的节点实例、处理人、审批结果都不同，不能混在定义表里。  
如果混在一起，流程模板改一处，历史单据跟着变；查一张老单据，看到的是今天的新规则，而不是当时真实走过的规则。

流程系统里最容易踩的坑，就是：  
**把“规则版本”当成“历史事实”。**

---

## 三、如何记录“当前到了哪一步”和“历史走过哪些步”？

### 1. 当前状态不能只靠一个状态字段

很多系统喜欢在业务主表里放一个 `status`，比如：

- `draft`
- `processing`
- `approved`
- `rejected`

它能看出大概进度，但只能回答“现在是什么状态”，回答不了：

- 现在卡在哪个节点？
- 之前经过了哪些节点？
- 是谁审批过的？
- 有没有退回重审？
- 有没有重复提交？

所以，**状态字段是必要的，但不够。**

它更像摘要，不能代替过程记录。你可以把它理解成门口指示牌：告诉你这单业务处于什么阶段，但不会告诉你一路怎么走来的。

### 2. 当前到了哪一步：推荐两层记录

建议业务主表保存“总状态”，流程实例表保存“当前节点”。

例如：

- 业务主表 `biz_order`
  - `biz_status`：整体业务状态
- 流程实例表 `flow_instance`
  - `current_node_code`：当前节点
  - `current_node_name`：当前节点名称
  - `current_handler_id`：当前处理人
  - `current_step_no`：当前步骤序号

这样，主表可以快速判断“单据是否完成”，实例表可以准确知道“流程停在哪一站”。

设计思路很简单：

- **主表负责业务结论**
- **实例表负责流程过程**

别反过来。  
如果把流程状态全塞进主表，后面流程一复杂，主表就会越来越胖，查询和维护都很痛苦。

### 3. 历史走过哪些步：必须靠节点实例表或流转记录表

历史记录不能只靠主表回写，必须单独保存。常见做法有两种：

#### 做法一：节点实例表保存每一步
每次节点流转，就插入一条节点实例记录：

- `instance_id`
- `node_code`
- `node_name`
- `handler_id`
- `start_time`
- `end_time`
- `result`
- `comment`

这个方式适合看“这一步谁处理的、用了多久、结果是什么”。

#### 做法二：流转记录表保存每次动作
每次用户操作都记一条记录：

- `instance_id`
- `from_node_code`
- `to_node_code`
- `action_type`
- `operator_id`
- `action_time`
- `action_result`

这个方式适合看“从哪一步跳到哪一步、谁按了什么按钮”。

两种方式可以同时用。  
**节点实例表强调“走过的节点”，流转记录表强调“发生过的动作”。**

这样就能同时满足两个查询场景：

- 看流程轨迹：查节点实例表
- 看操作过程：查流转记录表

如果想更稳一点，还可以补一张历史快照表，在关键动作发生时，把业务单据的关键字段快照下来。这样即便主表后面被修改，也能还原当时的状态。

## 四、节点分配、处理人、处理结果怎么存？

### 1. 节点分配要解决的是“谁来办”

流程跑起来以后，不是节点自己处理，而是要分配给具体的人或角色。先明确分配粒度：

- 指定某个人：例如法务部张三
- 指定某个角色：例如“部门经理”
- 指定某个组织：例如“财务组”
- 按规则动态分配：例如申请人直属上级

因此，节点分配表里通常要有：

- `instance_id`
- `node_code`
- `assignee_type`：人员、角色、组织、规则
- `assignee_id`
- `assignee_name`
- `assign_time`
- `assign_rule`

这样设计后，后面查“这个节点当时分给了谁”“为什么分给他”都有据可依。  
否则只存一个 `handler_id`，组织架构一变、角色一调、人一离职，历史数据就成黑盒了。

### 2. 处理人不是一个概念，可能有“当前处理人”和“历史处理人”

有些节点是单人审批，有些是多人会签。不能只放一个 `handler_id` 就完事。

建议拆成：

- **当前处理人**：这个节点现在轮到谁
- **历史处理人**：谁已经处理过
- **候选处理人**：谁有资格处理
- **实际处理人**：最后谁点了提交

如果是多人会签，最好有明细表：

- `node_handler_instance`
  - `node_instance_id`
  - `handler_id`
  - `handler_status`
  - `handled_time`
  - `handled_result`

这样以后查询“谁还没处理”“谁已经同意”“谁驳回过”就很清楚。  
这也是“可追踪”的核心：不是只知道节点有结果，而是知道**每个人在节点上的动作**。

### 3. 处理结果怎么设计

结果不要只存“通过/不通过”。实际项目里常见结果至少包括：

- 同意
- 驳回
- 退回上一节点
- 转交
- 撤回
- 取消
- 终止

所以结果字段最好用枚举或字典码，保留扩展性。

同时，结果通常要和意见一起保存：

- `action_result`
- `comment`
- `attachment_url`
- `handled_time`

因为流程业务里，结果本身不够用，**“为什么这么处理”也要能追溯。**  
很多时候，真正有价值的不是“审批通过了”，而是“谁基于什么意见通过的”。出了争议，系统里能不能拿出这条记录，很关键。

## 五、结合审批流讲一个完整落表案例

### 1. 场景：请假审批流

流程很简单：

1. 员工发起请假
2. 部门主管审批
3. 人事备案
4. 流程结束

如果只靠一张请假主表，很容易变成这样：

- `leave_order`
  - `id`
  - `user_id`
  - `leave_days`
  - `status`
  - `approver_id`

看起来够了，但问题很多：

- 主管审批过几次？
- 退回过没有？
- 人事有没有处理？
- 每次操作时间是什么？
- 现在卡在第几步？

这些都查不出来。

### 2. 推荐拆法

#### 业务主表：`leave_order`
存请假业务本身的信息：

- `id`
- `user_id`
- `leave_type`
- `leave_days`
- `reason`
- `biz_status`
- `created_at`

#### 流程实例表：`flow_instance`
存这张请假单对应的一次流程运行：

- `instance_id`
- `biz_type`
- `biz_id`
- `flow_code`
- `current_node_code`
- `current_node_name`
- `instance_status`

#### 节点实例表：`flow_node_instance`
存每个节点的运行记录：

- `node_instance_id`
- `instance_id`
- `node_code`
- `node_name`
- `handler_id`
- `node_status`
- `start_time`
- `end_time`
- `result`

#### 操作日志表：`flow_action_log`
存每一次操作动作：

- `log_id`
- `instance_id`
- `node_code`
- `operator_id`
- `action_type`
- `action_comment`
- `action_time`

如果要更完整，还可以补一张 `flow_history_snapshot`，在关键动作发生时，把请假单的关键字段一起快照下来。比如请假天数、请假类型、审批意见、提交人所属部门等。这样以后即便主表被更新，历史也不会丢。

### 3. 这样设计的好处

你可以直接回答以下问题：

- 当前请假单在哪个节点：查 `flow_instance.current_node_code`
- 谁正在处理：查当前节点分配信息
- 谁审批过：查节点实例表
- 谁驳回过：查操作日志表
- 历史节点怎么走的：查节点实例表和流转记录表联查

这就是流程节点落表的核心价值：  
**不是只存“结果”，而是存“过程”。**

而且这个结构天然适合扩展。以后请假流程从“主管+人事”变成“主管+部门负责人+HRBP”，只需要调整流程定义和节点关系，历史实例照样能保留，查询逻辑也不会推倒重来。

## 六、常见误区：流程节点建模最容易踩的坑

### 1. 只存状态，不存节点

这是最常见的坑。  
只有状态，没有节点，后面排障全靠猜。状态只能说明“结果大概是什么”，不能说明“中间发生了什么”。

### 2. 把流程定义和流程实例混在一张表

定义是模板，实例是运行记录。混在一起后，维护成本会越来越高。  
一改模板，老单据全受影响，这是流程系统的大忌。

### 3. 用一个字段硬塞所有处理人

单人、多人、角色、规则分配，混成一个 `handler_id`，后面一扩展就崩。  
正确做法是分清 assignee、handler、operator 的边界。

### 4. 不存历史，只保留最新结果

这会导致流程不可追溯。线上一旦出问题，你根本不知道中间发生了什么。  
尤其是审批、审核、售后这类场景，历史记录就是证据链。

### 5. 节点名称当主键

名称会改，主键不能飘。流程系统里，稳定标识必须靠编码。  
**名字给人看，编码给系统用。** 这个原则一定要守住。

---

## 结尾小结：把“第几步”变成“可追踪的步骤链”

流程节点落表，本质上是在解决三件事：

1. **当前在哪一步**
2. **谁处理过**
3. **历史怎么走过来的**

你可以记住这个落表顺序：

- 先定流程定义：节点、关系、规则
- 再建流程实例：某张单对应的一次运行
- 然后记节点实例：每一步实际走过的记录
- 最后加动作日志：每一次点击、同意、驳回、转交都留痕

如果你在项目里做审批流、工单流转、内容审核、售后处理，先别急着写代码，先问自己一句：

> 这套流程，我能不能查出“现在在哪、谁处理、以前怎么走的”？

能回答这三个问题，节点表就算立住了。  
回答不了，说明你的表还只是“看起来像流程”，还不是“真正能追踪的流程”。

# 第5章：流转记录表怎么设计——把每一次变化都记下来

## 开篇引入：别只看“现在是什么状态”，要能回答“它是怎么走到这里的”

做流程型业务，最容易犯的错，就是只在主表里放一个状态字段，以为就够了。

比如退款单现在是“已退款”，审批单现在是“已通过”，发布单现在是“已发布”。系统能跑，页面也能展示。但一旦有人追问：

- 这个单子经历了哪些节点？
- 是谁在什么时候把状态从“待审核”改成“审核中”的？
- 哪一步被驳回了，原因是什么？
- 要还原整个流程轨迹，能不能查出来？
- 某个状态卡了两天，到底卡在哪个人、哪个环节上？

这时，只靠主表里的状态字段就不够了。

因为状态字段只能告诉你“现在是什么”，不能告诉你“它是怎么变成这样的”。而流程型业务真正麻烦的地方，不在当前状态，而在**状态是怎么一步一步流转过来的**。

所以这一章讲的是：**流转记录表怎么设计**。它不替代业务主表，而是把每一次状态变化、节点流转、关键动作都记下来。这样既能看当前状态，也能追历史过程，还能支持审计和排障。

如果说业务主表是结果页，那流转记录表就是过程页。没有过程页，很多系统一出问题就只能靠人肉回忆。

---

## 一、流转记录表的作用：追踪过程，不替代主表

先把概念分清楚。

### 1. 业务主表负责“当前事实”

业务主表存的是这个业务对象的核心信息和当前状态。

比如退款业务主表可能有：

- 退款单号
- 订单ID
- 退款金额
- 当前状态
- 申请人
- 创建时间

它回答的是：**这是什么单？现在到哪一步了？**

主表关注“此刻”，适合做列表页、详情页、待办页的基础展示。

### 2. 流转记录表负责“变化过程”

流转记录表记录的是每次状态变化的过程。

它回答的是：

- 从哪个状态变到哪个状态
- 在哪个节点发生
- 谁操作的
- 什么时间发生
- 为什么变更
- 是否成功

也就是说，主表看结果，流转表看过程。

### 3. 为什么必须分开

很多团队一开始喜欢把所有信息都堆进主表，最后会遇到三个问题：

- **状态覆盖历史**：每次更新都把旧状态冲掉，查不到过程
- **排障困难**：线上出问题时，只能看到结果，无法还原路径
- **查询混乱**：既要查当前态，又要查历史态，字段会越来越乱

更麻烦的是，流程越复杂，主表越容易被改成“超级大宽表”。今天加一个驳回原因，明天加一个审核意见，后天再加一个操作人字段，最后表就失去边界了。

正确思路是：

**主表保持业务对象的当前态，流转记录表保存过程态。**

主表负责快查，流转表负责追溯。两者配合起来，流程型业务才真正站得住。

---

## 二、必备字段怎么设计：业务ID、前状态、后状态、操作节点、操作时间、操作人

流转记录表不是越大越好，但有几个字段是底线。少了这些字段，你就很难把一次变化讲完整。

### 1. 业务ID：把记录挂到具体对象上

流转记录必须能关联到某一条业务数据。

例如：

- refund_id：退款单ID
- order_id：订单ID
- approval_id：审批单ID
- publish_id：发布单ID

没有这个字段，流转记录就成了孤岛。后面想按单查轨迹、按单还原历史、按单排查，都会很痛苦。

实战里先想清楚：这条流转记录到底“跟着谁走”。是跟订单走，还是跟订单里的子单走，还是跟审批实例走。对象一旦选错，后面的查询关系就会乱。

### 2. 前状态和后状态：记录“变了什么”

这是流转记录表的核心。

例如：

- from_status：待审核
- to_status：审核中

或者：

- from_status：审核中
- to_status：已驳回

这样你才能还原完整路径，而不是只看到“当前是已驳回”。

很多人会问：主表已经有 current_status 了，为什么还要记 from_status 和 to_status？因为主表只能保存最终态，不能保存中间态。而流程分析、审计、排错，最需要的就是中间态。

### 3. 操作节点：记录“在哪一步变的”

流程不是只有状态，还有节点。

例如审批流程里，节点可能是：

- 提交申请
- 部门经理审核
- 财务复核
- 最终确认

节点字段能帮助你判断：**这次变化发生在流程的哪一环。**

有些业务里，状态和节点并不完全一致。状态是系统层面的结果，节点是流程层面的阶段。比如“审核中”可能对应多个节点：部门审核、法务审核、财务审核。你只看状态，只知道它在审核中；你看节点，才知道它卡在哪一层。

所以，流程设计里不要把“状态”和“节点”混成一回事。状态是面，节点是点；状态适合给人看，节点适合给系统追踪。

### 4. 操作时间：记录“什么时候变的”

这个字段看似简单，但非常重要。

它可以用于：

- 计算每个节点耗时
- 排查卡点
- 做超时提醒
- 统计流程效率

建议用统一的时间精度，至少精确到秒。否则后面排序、判断先后顺序、分析连续动作时，容易出现模糊地带。

### 5. 操作人：记录“谁改的”

操作人可以是：

- 用户
- 审核员
- 系统
- 定时任务
- 第三方回调

这里要注意：**不是所有流转都来自人工操作。**

比如退款成功可能是支付网关回调触发，发布成功可能是部署任务触发。这个时候如果把操作人硬写成某个员工，后面排查就会很别扭。

所以操作人字段最好支持“系统/人工/第三方”的区分，必要时还能带上操作者ID、操作者名称、操作者类型，方便展示和审计。

### 6. 建议补充字段

在实战里，常常还会加：

- action_type：动作类型，如提交、审核、驳回、撤回、确认
- remark：备注或原因
- ext_data：扩展信息，存驳回原因、审批意见、失败码等
- request_id：请求唯一标识，防重复写入
- trace_id：链路追踪ID，方便排查

这些字段不是每个项目都必须有，但在流程复杂时非常有用。

尤其是 remark 和 ext_data。真正有价值的不只是“变更了”，而是“为什么变更”。驳回理由、失败错误码、复核说明，都是流程复盘的重要依据。

---

## 三、一次流转一条记录，还是一次动作一条记录？

这个问题很常见，而且没有绝对答案，要看你要追踪到什么粒度。

### 1. 一次流转一条记录：适合看“状态变化链”

这是最常见的做法。

比如：

- 待审核 → 审核中
- 审核中 → 已通过
- 已通过 → 已发布

每次状态变化插一条记录。

#### 适用场景

- 业务关注状态流转，不关心每个细节动作
- 审计只需要看到“谁把状态从哪改到哪”
- 查询流程轨迹比较直接

#### 优点

- 结构简单
- 历史查询方便
- 记录量相对可控

#### 缺点

- 一个状态变化前有多个动作时，会丢细节
- 无法完整记录“点击、提交、撤回、补充材料”等细粒度行为

### 2. 一次动作一条记录：适合看“行为过程”

比如一个审批单：

- 提交申请
- 上传附件
- 撤回申请
- 重新提交
- 审批通过

这些动作不一定每次都改变状态，但都值得记录。

#### 适用场景

- 审批、审核、工单、售后这类动作密集型流程
- 需要审计所有用户行为
- 需要分析用户操作习惯或流程阻塞点

#### 优点

- 记录更完整
- 更利于审计和追责
- 能还原完整行为链

#### 缺点

- 数据量更大
- 查询逻辑更复杂
- 要明确“动作”和“状态变更”的关系

### 3. 实战建议：两层记录更稳

很多项目里，我更建议你这样设计：

- **流转记录表**：只记状态变化和节点迁移
- **操作日志表**：记所有动作、请求参数、结果、错误信息

这样职责清晰：

- 想看流程怎么走的，查流转记录表
- 想看谁点了什么、传了什么参数，查操作日志表

不要把两件事揉成一锅粥。一旦混在一起，后面既不好查，也不好扩展。

---

## 四、流转记录如何支持查询当前流程进度和历史轨迹？

流转记录表设计得好不好，最后都要落到“能不能查”。

### 1. 查当前流程进度

当前进度通常不是靠流转表直接判断，而是结合主表状态和流转表最近一条记录。

常见做法是：

- 主表存 current_status
- 流转表按业务ID + 操作时间排序
- 最新一条记录作为最近变化依据

这样能回答：

- 当前处在哪个节点
- 最近一次是谁操作的
- 是否已经进入下一环节

如果只依赖流转表去反推当前状态，也不是不行，但会更重。主表保留 current_status，通常更适合高频查询场景。

### 2. 查历史轨迹

历史轨迹通常按时间顺序查流转记录表即可。

展示时建议按以下信息组织：

- 时间
- 节点
- 前状态 → 后状态
- 操作人
- 备注/原因

用户看到的不只是结果，而是完整路径。

如果页面面向业务人员，尽量不要只展示数据库字段名，而是整理成“流程时间线”。比如“10:03 张三提交申请”“10:15 李四驳回，原因：附件不全”“11:20 张三补充材料后重新提交”。这种展示更符合人的认知。

### 3. 支持流程分析

有了流转记录表，还能做一些很实用的分析：

- 哪个节点最容易卡住
- 哪个环节平均耗时最长
- 哪类单子容易被驳回
- 是否存在重复流转、回退频繁

这对业务优化很有价值。很多团队做流程系统，只关注“能不能跑”，不关注“跑得好不好”。其实流转记录表真正的价值，往往在后面：它不只是审计工具，也是业务分析的基础数据。

### 4. 索引建议

常见索引思路是：

- 业务ID + 操作时间
- 业务ID + 节点
- 业务ID + from_status + to_status

如果流程量大，按业务类型或时间分表、分区也很常见。

别忘了，流转记录表往往是高频写入、复杂查询的表。设计时要平衡写入性能和查询效率，不要等数据量上来后才补救。

---

## 五、典型案例拆解：退款、审批、发布分别怎么记

### 1. 退款流程：关注“申请—审核—退款结果”

退款单常见流转如下：

- 待提交
- 已提交
- 审核中
- 已通过 / 已驳回
- 退款处理中
- 已退款 / 退款失败

#### 流转记录怎么记

每次状态变化记一条：

- 退款单ID
- from_status：审核中
- to_status：已通过
- node：财务审核
- operator：财务人员A
- action_time：2025-xx-xx 10:30:00
- remark：材料齐全，准予退款

#### 为什么要这么记

因为退款业务经常要查：

- 谁批准了退款
- 哪一步失败了
- 是人工驳回还是系统退款失败
- 退款失败后是否重试

如果没有流转记录，出了问题就只能看“现在是失败”，不知道失败经过。退款类场景又特别容易扯皮，靠记录才能说清楚。

### 2. 审批流程：关注“谁在什么节点做了什么决定”

审批场景特别适合流转记录表。

常见节点：

- 发起申请
- 部门审批
- 复核
- 终审

#### 记录重点

除了状态变化，最好保留：

- 审批意见
- 审批结果
- 是否加签、会签
- 是否退回到上一步

审批最怕黑盒，所以流转记录一定要支持回看全过程。一个审批单为什么没过，不是只看“已驳回”四个字，还要看是哪个节点驳回、谁驳回、基于什么理由、是否可以补充后重新流转。

### 3. 发布流程：关注“版本发布的每一步”

比如内容发布、商品发布、配置发布。

流程可能是：

- 草稿
- 待审核
- 审核通过
- 待发布
- 发布中
- 已发布
- 发布失败

#### 记录重点

发布流程经常要看：

- 哪个版本被发布
- 谁确认发布
- 发布到哪个环境
- 是否回滚
- 失败原因是什么

这类场景里，流转记录表和版本号字段经常要一起设计。因为业务对象不只是“发布单”，还关联具体版本、环境、渠道等对象。

比如内容发布单，可能关联文章版本、图片资源、发布渠道。流转表记录“发布单怎么走”，历史快照记录“当时发布的内容是什么”。两者缺一不可。

---

## 六、常见误区：别把流转记录表做成“另一个业务主表”

### 误区1：什么都往流转表里塞

有些团队觉得既然是记录，就把订单金额、商品名、用户电话全塞进去。

结果流转表越来越胖，最后既不能查询，也不好维护。

正确做法是：

**流转表只保留过程信息，业务详情放主表，必要时用关联对象补充。**

流转表的职责是追过程，不是替主表存全量业务数据。一旦边界模糊，后续查询和变更都会变得别扭。

### 误区2：只记成功，不记失败

流程里最有价值的往往不是成功，而是失败和回退。

如果只记成功，你永远看不出：

- 为什么卡住
- 为什么退回
- 哪一步反复出错

很多流程问题恰恰发生在失败路径上。系统异常、人工驳回、第三方回调失败、用户撤回重提，这些都应该进入记录。

### 误区3：状态变化和操作日志混在一起

状态变化是流程事实，操作日志是行为记录。两者有关联，但不完全等价。

状态变化告诉你“从A到B”；操作日志告诉你“谁在什么时候提交了什么请求，返回了什么结果”。一个偏业务，一个偏技术。建议分开设计，别混写。

### 误区4：没有历史快照

有些流程对象会被后续修改，比如审批时的申请内容、退款时的地址、发布时的配置。

如果你只记状态，不保存关键字段的历史快照，后面回看时会发现：

- 当时提交的内容已经变了
- 审核时看到的数据和现在不一样
- 无法证明当时的业务事实

所以在关键节点，建议保留**历史快照**或关键字段快照。

这个快照不一定要把整行数据全复制一遍，但至少要保存那些会影响判断的字段，比如金额、标题、审批摘要、版本号、配置内容等。否则流程虽然有记录，却无法还原真实上下文。

---

## 结尾小结：流转记录表的目标，是让流程看得见、查得到、追得回

这一章你只要记住一句话：

> **业务主表管现在，流转记录表管过程。**

设计流转记录表时，先问自己四个问题：

1. 这条记录要追踪什么业务对象？
2. 它记录的是状态变化，还是动作行为？
3. 查询时是看当前进度，还是看完整历史轨迹？
4. 出问题时，能不能还原到具体节点、具体人、具体时间？

如果这四个问题都能答上来，你的流转记录表就不会太差。

### 行动建议

- 先为每个流程梳理节点和状态图
- 再确定哪些变化需要进流转表
- 区分好流转记录表和操作日志表
- 对审批、退款、发布这类流程，务必保留历史快照
- 最后用“能否还原全过程”来检查设计是否合格

流程型业务最怕“只见结果，不见过程”。把每一次变化都记下来，系统才真正可追踪、可查询、可维护。

# 第6章：操作日志表怎么做——谁点了按钮、改了什么、为什么改

## 开篇引入：为什么很多系统“能跑”，却“说不清”

我见过不少系统，审批能过、工单能流转、客服也能处理，页面看着没问题。可一出事，团队就开始翻聊天记录、查数据库、问当事人，最后还是说不清：

- 谁改了这条数据？
- 改之前是什么值？
- 是人点的，还是接口触发的？
- 这次失败是业务失败，还是系统异常？
- 能不能把当时的操作还原出来？

如果没有**操作日志表**，这些问题最后往往只剩一句：**“我不知道。”**

很多人会把“操作日志”和“流转记录”混在一起。其实它们不是一回事：

- **流转记录**记的是“过程”：从哪个节点到哪个节点，状态怎么变，经过了谁的审批。
- **操作日志**记的是“行为”：谁在什么时间、对什么对象、做了什么操作、结果如何。

这章只讲一件事：**如何设计一个不污染业务表，但能支撑审计、排错、追责和回放的操作日志表。**

你可以把它理解成系统的第二条记忆：  
业务表负责“现在是什么样”，流转表负责“它怎么走到这一步”，操作日志负责“是谁按了哪一下、系统当时看到了什么”。

---

## 一、操作日志和流转记录的区别：一个记行为，一个记过程

### 1. 流转记录回答的是“业务走到哪一步了”

比如工单从“新建”到“处理中”再到“已关闭”，你需要一张流转记录表去记：

- 工单 ID
- 当前节点
- 目标节点
- 处理人
- 变更时间
- 变更原因

它的核心是**状态迁移**，关注业务过程本身，而不是每一次点按钮的细节。

### 2. 操作日志回答的是“谁做了什么动作”

同样是工单场景：用户点“转派”，客服点“驳回”，管理员点“强制关闭”，这些都应该进操作日志表。它关注的是**操作行为**：

- 谁操作的
- 从哪里操作的
- 操作针对哪个对象
- 成功还是失败
- 失败原因是什么
- 提交了什么参数

重点是“行为”，不是“结果状态”。

比如“已关闭”这个结果，可能来自三种完全不同的操作：

1. 客服手工关闭；
2. 定时任务自动关闭；
3. 外部系统接口触发关闭。

结果一样，但责任主体、入口和上下文完全不同。没有操作日志，出了问题根本分不清。

### 3. 一个判断标准：能不能单独支撑审计

如果你要查的是：

- 这条审批为什么被拒绝？
- 谁审批通过的？
- 中间经历了几个节点？

看流转记录。

如果你要查的是：

- 谁点了“同意”按钮？
- 谁改了备注？
- 为什么接口报错了？
- 操作是否重复提交？

看操作日志。

> **实战经验**：  
> 流转记录偏业务，操作日志偏技术和行为。两者最好分表，不要互相替代。  
> 流转记录解决“过程可追踪”，操作日志解决“行为可追责”。

---

## 二、日志表应记录哪些字段：别只存一句“操作成功”

很多系统的日志表只有三列：

- 操作人
- 操作时间
- 操作内容

这种日志看起来“有”，实际上几乎不能用。排错、追责、回放时，关键信息全没了。

### 1. 最少要记录的字段

一张可用的操作日志表，至少应包含以下几类信息：

#### 1）操作主体
- `operator_id`：谁操作的
- `operator_name`：展示名
- `operator_type`：用户、管理员、系统任务、API 客户端等

`operator_type` 很重要，因为很多动作不是人点的，比如定时任务自动结算、系统自动补偿、第三方回调触发。

#### 2）操作行为
- `action_type`：新增、修改、删除、审批、驳回、导出、退款等
- `action_name`：可读名称
- `action_code`：统一枚举编码

不要只写“操作”，`保存`、`提交`、`审批`、`驳回`、`撤回`、`导出` 的业务含义完全不同，后续统计和权限控制都靠它区分。

#### 3）目标对象
- `target_type`：订单、工单、会员、内容等
- `target_id`：对象主键
- `target_snapshot`：关键字段快照，必要时保留

没有 `target_type + target_id`，日志就挂不回业务对象，后面很难查某个对象的完整历史。

#### 4）请求来源
- `source_type`：后台、前台、接口、定时任务、移动端
- `request_id`：请求链路 ID
- `trace_id`：链路追踪标识
- `ip_address`：来源 IP
- `user_agent`：客户端信息

这些字段平时不显眼，排错时很值钱，尤其在分布式系统里。

#### 5）结果信息
- `result_status`：成功、失败、部分成功
- `error_code`：错误码
- `error_message`：错误信息
- `duration_ms`：耗时

别只记成功，失败日志往往更有价值。线上问题大多不是“做成了什么”，而是“为什么没做成”。

#### 6）扩展信息
- `remark`：备注
- `ext_data`：扩展字段

扩展字段适合放审批意见、表单差异、附件列表、第三方返回摘要等不稳定信息。

### 2. 为什么要这么细

因为日志不是给人看一眼就完了，而是要支撑三件事：

- **审计**：谁干的，能不能追到人
- **排错**：失败发生在哪一步
- **回放**：当时传了什么参数，系统看到了什么上下文

尤其是审批、客服处理、退款、人工修正这些场景，单纯记录“已处理”没意义。你得知道：**谁在什么入口，对哪个对象，基于什么请求，做了什么动作，结果如何。**

### 3. 一个典型字段组合

以“后台审批”为例，日志表可以这样记：

- 操作人：张三
- 操作类型：审批
- 目标对象：内容 ID=8891
- 来源：后台管理端
- 请求 ID：abc-123
- 结果：成功
- 备注：内容符合规范
- 扩展：审核意见、当前版本号、所属栏目

这样一条日志，基本就能把审计链路打通。出了争议，你能查到“谁、何时、在什么环境、对什么对象、做了什么、结果怎样”。

---

## 三、日志内容是结构化还是半结构化：怎么选才不把自己坑死

### 1. 纯结构化：适合高频查询字段

结构化字段的好处很直接：

- 查询快
- 统计方便
- 好做索引
- 容易做报表

比如：

- 操作类型
- 操作人
- 目标对象 ID
- 操作结果
- 时间

这些都应该放成标准字段。因为你后面大概率会查“某个人今天做了多少次审批”“某类对象最近失败了多少次”。

### 2. 半结构化：适合不稳定扩展字段

现实里，日志总会遇到一些今天想不到、明天要加的字段，比如：

- 审批意见
- 表单提交前后差异
- 客服备注
- 第三方返回包
- 用户选择的附件列表

这类内容不一定适合每次都加列，可以放进 `ext_data`、`request_payload`、`response_payload` 之类的 JSON 字段里。

但注意，JSON 不是垃圾桶。它适合放“偶发、扩展、难固定”的信息，不适合把所有字段都往里塞。

### 3. 怎么判断字段放哪边

#### 放结构化字段的情况
- 经常查询
- 经常筛选
- 经常统计
- 需要建索引
- 值类型稳定

#### 放半结构化字段的情况
- 字段变化频繁
- 只是留痕，不常查
- 内容结构不固定
- 仅用于排查或回放

### 4. 一个常见误区

很多人喜欢把所有信息都塞进一段 JSON，觉得省事。短期看省事，长期看是给自己挖坑：

- 难查询
- 难统计
- 难建索引
- 难做治理
- 字段越来越散

反过来，也有人把所有扩展信息都拆成列，最后日志表越长越宽，改个字段都要发版。

> **建议**：  
> 高频查询字段结构化，低频扩展字段半结构化。  
> 不要把“灵活”理解成“全丢 JSON”，也不要把“规范”理解成“什么都拆列”。

---

## 四、如何在不污染业务表的前提下保留审计能力

操作日志最大的价值之一，是**不改业务表，也能保留足够审计能力**。

### 1. 业务表只管当前状态，日志表负责过程留痕

业务表应该尽量保持干净，只放：

- 当前状态
- 当前负责人
- 当前版本
- 关键业务字段

例如订单表里放：

- `order_status`
- `pay_status`
- `buyer_id`
- `amount`

不要为了审计把所有历史字段都堆进去，否则业务表会越来越臃肿，更新逻辑也越来越复杂。

业务表回答“现在是什么”，日志表回答“刚才发生了什么”。

### 2. 操作日志通过关联对象挂回业务表

日志表里保留：

- `target_type`
- `target_id`

这样就能把任何操作日志挂回对应业务对象。比如查某个订单的所有操作历史：

```sql
select * from operation_log
where target_type = 'order'
  and target_id = 10086
order by created_at asc;
```

这就是典型的“业务表 + 日志表”组合。业务表管当前状态，日志表管历史行为。

如果还要更强的回放能力，可以在日志里补充：
- 操作前快照
- 操作后快照
- 关键字段差异

这样就不只是知道“改过”，还能知道“改了什么”。

### 3. 关键动作要做快照

如果只记“改了订单地址”，但没记改之前和改之后的地址，排查时还是不够。

所以对关键修改建议保留：

- 修改前快照
- 修改后快照
- 差异字段

这些不一定放业务表里，更多放日志表里。尤其是审批、审核、退款、人工修改这类敏感操作，**历史快照非常重要**。

快照不是为了占空间，而是为了事后能还原现场。很多线上争议，不是系统没做，而是做了什么说不清。

### 4. 操作日志不要反向驱动业务状态

日志是“留痕”，不是主数据。业务状态应该由业务表、状态机、流转表决定，不要反过来靠日志推当前状态。

如果试图根据日志最后一条“修改记录”去推算当前状态，迟早会出问题：

- 日志可能有延迟
- 日志可能失败但业务成功
- 日志可能补写
- 日志可能被重放
- 日志可能只记录局部字段

> 记住：  
> **日志是证据，不是事实本身。**

---

## 五、结合后台审批、人工审核、客服处理：怎么落到表设计

### 1. 后台审批：要能看到“谁审批了什么”

场景：内容发布前需要人工审核。业务表记录当前状态，流转记录记审核节点，操作日志记每次点击按钮的行为。

日志里至少要有：

- 审批人
- 审批动作：通过/驳回
- 审批对象：内容 ID
- 审批入口：后台
- 审批意见
- 结果
- 请求参数摘要

一个“同意”按钮看着简单，实际可能包含很多上下文：

- 审核的是哪个版本
- 是否重复提交
- 当前审核人是否有权限
- 是否经过二次确认
- 是否触发自动发布

这些都值得记下来，后面才能回答：
- 是谁批准的
- 为什么批准
- 是否重复审批
- 是否越权操作

### 2. 人工审核：要能追溯“改了什么”

场景：财务审核、资质审核、风控审核。这类操作经常不是简单的“过/不过”，还会修改备注、补充材料、修正分类。

日志建议记录：

- 修改前后字段差异
- 操作原因
- 审核依据
- 附件信息
- 关联任务号

人工审核最怕的不是没日志，而是日志太粗。出了争议时，你得知道改动点在哪里。比如资质审核单，关键往往不是“审核通过”，而是：
- 哪个证件被补充了
- 原来缺了什么材料
- 哪个字段被人工修正
- 最终依据是什么

### 3. 客服处理：要能区分“用户诉求”和“客服动作”

场景：售后退款、退货、补发、工单处理。同一个按钮，可能代表很多不同动作。

比如：

- 标记已联系
- 发起退款
- 转派给物流
- 关闭工单

这些都应该作为不同的 `action_type` 记下来，而不是统一写成“处理工单”。否则后续统计时，你根本不知道客服到底在干什么。

更进一步，可以把“用户诉求”和“客服动作”分开记录：

- 用户诉求：要求退款、要求补发、要求改地址
- 客服动作：同意退款、拒绝退款、补录物流单号、转派

这样就能清楚看到：用户提了什么，客服做了什么，中间有没有偏差，有没有超时，有没有重复处理。

---

## 六、设计操作日志表时最容易踩的坑

### 1. 把日志当业务字段更新记录

业务表更新一次就加一列“修改时间/修改人”，这不叫日志，只是状态附带信息。真正的操作日志要能记录多次行为。

### 2. 只记成功，不记失败

失败日志非常重要。很多线上问题，真正有价值的就是失败那一条。尤其是审批、支付、退款、第三方回调这些流程，失败信息往往能直接告诉你问题出在权限、参数、状态机，还是外部接口。

### 3. 只有文本，没有结构

全靠一段“操作说明”，后面几乎无法检索、统计和分析。你今天觉得“写句话就够了”，明天就会发现：
- 查不了某个人的全部审批
- 统计不了某类操作的成功率
- 排查不了某种失败模式
- 也没法做风控分析

### 4. 没有关联对象

日志不挂 `target_id`，后面只能靠内容模糊匹配，基本等于废。真正可用的日志，一定要能稳定回到业务对象上。

### 5. 不区分操作类型

“保存”“提交”“审批”“驳回”“导出”混成一个动作，系统分析就没法做。看起来都是按钮点击，实际业务含义差很多。

### 6. 不保留上下文

很多团队只记“谁做了什么”，却不记“在什么上下文下做的”。结果一到排错时，入口、请求参数、客户端信息、链路 ID 都没有，最后还是只能靠猜。

---

## 结尾小结：日志不是附属品，是系统的第二条记忆

如果说业务表记录的是“现在”，那操作日志记录的就是“怎么走到现在”。一个成熟的流程型系统，不能只有状态字段，还要有可追踪、可回放、可审计的日志能力。

你可以把这章的设计原则记成一句话：

> **业务表保当前，流转表保过程，操作日志保行为，历史快照保证据。**

### 实战检查清单

落表前，至少检查这几件事：

- 是否明确区分了操作日志和流转记录
- 是否记录了操作人、目标对象、操作类型、结果、错误信息
- 是否为高频字段做了结构化设计
- 是否为扩展字段保留了半结构化空间
- 是否保留了修改前后快照
- 是否能通过 `target_type + target_id` 查回某个对象的所有日志
- 是否能用于审计、排错和回放
- 是否记录了请求来源、入口和链路信息
- 是否区分了成功、失败和部分成功

这些都做到，你的操作日志表就不只是“记一笔”，而是系统里真正能救命的那一层。

# 第7章：历史记录和历史快照怎么存——别只看最新一条

## 开篇引入：为什么流程型业务一定要有“回看能力”

做流程型系统，最容易犯的错就是**只存当前状态**。订单有个`status`，工单有个`state`，审批有个`approve_status`，看起来够用，但业务一跑你就会发现：今天的结果，不代表昨天的过程，更不代表当时的依据。

用户投诉时常说：“我先提交了资料，后面才被驳回”、“客服说退款已经通过了，为什么我现在看不到记录？”这时，**只看最新一条**的设计就会失效。

流程型业务真正需要的，不只是“现在是什么”，还要能回答：什么时候变成了什么？谁改的？改之前是什么？改之后是什么？当时依据的那版数据长什么样？

这就是历史记录、历史快照、版本表存在的意义。本章讲清楚：历史记录为什么必须存；历史表、快照表、版本表怎么区分；全量快照和增量快照怎么选；快照如何和业务主表、流转记录表配合；快照表的索引设计怎么做；退款、售后、内容审核回滚这类场景怎么落表。

---

## 一、为什么需要历史快照：状态变更、数据追溯、争议处理

### 1.1 只有当前状态，不足以支撑流程业务

流程型业务的核心是**状态在流转**。退款单可能经历：待审核→审核通过→待打款→打款成功→已关闭。只保留最终状态`已关闭`，中间过程就没了。审核是谁批的？用户有没有补过材料？打款失败后有没有重试？这些问题只能靠人回忆。

历史快照解决的不是“多存点数据”，而是**保留业务演化的证据链**。流程型业务里，证据链往往比结果更重要，因为结果可能被修改、回滚、驳回，但过程必须可追溯。

### 1.2 历史快照的三类典型价值

**第一类：状态变更追踪**——记录每次状态变化的前后文，便于定位问题和还原过程。

**第二类：数据追溯**——用户信息、商品信息、退款原因都可能变。你必须知道“当时看的到底是哪一版”。

**第三类：争议处理**——当业务、客服、用户之间发生争议时，系统要能拿出时间线和快照，而不是只给一个最终结果。

### 1.3 什么时候一定要考虑历史记录

以下场景基本不能省：有审批、审核、驳回、回滚；有金额、库存、权益、合同等敏感数据；有人工介入或多角色操作；有合规要求；有“以当时数据为准”的业务口径。

老赵一般先问一句：如果未来有人会问“当时为什么这么做”，你能不能回答？答不上来，就该存历史。

---

## 二、历史表、快照表、版本表各自适合什么场景

关键要先搞清楚：**你要记的是操作过程，还是数据版本，还是完整现场？**

### 2.1 历史表：记录“发生过什么”

历史表偏向**事件记录**，适合记流程中的关键动作：退款单审核通过、售后单被驳回、内容审核从待审变成已发布。它记录的是“发生了什么事”，不是“这条业务记录当时完整长什么样”。

**特点**：轻量、可追加、适合流水化查询。  
**适用场景**：流程节点变更日志、操作轨迹、审计追踪。

### 2.2 快照表：记录“某一时刻长什么样”

快照表偏向**状态截面**，保存某个时间点业务对象的完整或部分数据。像拍照，拍的是“当时这一刻的样子”。

**特点**：能还原现场，查询直观。  
**适用场景**：争议处理、审核留档、回滚对比、复核比对。

### 2.3 版本表：记录“第几版是什么”

版本表强调**演进序列**。每次修改生成一个版本号，重点不是“改了什么动作”，而是“哪一版有效、哪一版被采用、哪一版被废弃”。

**适用场景**：表单类业务、配置类业务、审核材料类业务、内容编辑类业务。

### 2.4 三者怎么选

简单说：**想追过程**用历史表；**想还原现场**用快照表；**想区分版本**用版本表。

实际项目里往往组合使用：主表存当前态；历史表存流转；快照表存关键现场；版本表管修改序列。老赵的经验是，别纠结“到底叫历史还是快照”，先想清楚业务问题是什么。

---

## 三、全量快照和增量快照怎么选

### 3.1 全量快照：优点是还原简单

每次存一份完整数据。**优点**：回看不需要拼装，查询简单，排查问题效率高，方便和当前主表做对比。**缺点**：占空间，写入成本高。**适合场景**：审核单、合同、配置单、售后单，要求“必须能还原当时现场”。

### 3.2 增量快照：优点是节省存储

只保存变化字段。**优点**：存储节省，写入轻量。**缺点**：还原复杂，需要拼装。**适合场景**：配置项、富文本内容编辑、频繁修改但单次变化小的对象。

### 3.3 老赵的判断规则

如果审计要求高、查询“某一时刻完整状态”很频繁、数据量不是特别夸张，优先考虑**全量快照**。如果修改特别频繁、单条数据很大、存储压力明显，考虑**增量快照+基线快照**（如每周做全量基线，日常只存增量）。

### 3.4 一个实战建议

别一开始就设计得太省。流程型系统里，**可追溯性往往比节省几张表更重要**。老赵建议先把“能查清楚”做出来，再考虑压缩、归档、分区优化。

---

## 四、快照数据的索引设计——别让查询变成全表扫描

### 4.1 快照表必须加的索引

以全量快照表为例，核心SQL：

```sql
SELECT * FROM refund_snapshot WHERE biz_id = 'REF20241001' AND version_no = 3;
SELECT * FROM refund_snapshot WHERE biz_id = 'REF20241001' ORDER BY version_no ASC;
SELECT * FROM refund_snapshot WHERE biz_id = 'REF20241001' AND created_at BETWEEN '2024-09-01' AND '2024-10-01';
```

对应索引设计：

- **联合索引：`(biz_id, version_no)`**——最常用的查询，必须加。
- **单列索引：`(biz_id, created_at)`**——适合争议处理时按时间线还原。
- **增量快照表**还需加`(biz_id, base_version_no)`索引。

### 4.2 历史表/流转记录的索引建议

核心查询：按业务单查流转过程、按操作人追溯。建议加`(biz_id, created_at)`和`(operator_id, created_at)`索引。

### 4.3 常见索引设计坑

- 忘了给`biz_id`加索引——快照表、历史表都是按业务单查的。
- 只加单列索引不加联合索引——联合索引能让排序不走文件排序，性能差距明显。
- 过度索引——快照表写入频繁，建议控制在2-3个索引。
- 忽略了时间范围查询——按`created_at`查的需求一定要加索引。

### 4.4 快照表与业务主表、流转记录表的关联示例

查“退款单REF20241001在审核通过那一刻的完整申请内容”：

```sql
-- 第一步：从流转记录表找到“审核通过”这条记录
SELECT log_id, snapshot_id FROM refund_log 
WHERE biz_id = 'REF20241001' AND to_status = '审核通过' 
ORDER BY created_at DESC LIMIT 1;

-- 第二步：根据 snapshot_id 拿到当时快照
SELECT * FROM refund_snapshot WHERE snapshot_id = ?;
```

流转记录表里要存`snapshot_id`或`(biz_id, version_no)`以便走联合索引。

---

## 五、结合退款、售后、内容审核回滚看怎么落表

### 5.1 退款场景：争议最典型

退款单至少要有四层：退款主表（当前状态）、流转记录表（每次流转）、快照表（关键状态时申请内容全量快照）、操作日志表（谁做了什么）。

建议保留的关键节点快照：用户提交申请时、审核员处理时、金额变更时、打款成功或失败时、关闭单据时。

### 5.2 售后场景：现场变化快

售后单特点是“人参与多、变化快、节点多”。快照应抓住：申请提交时、审核驳回时、重新提交时、结案时。客服才能对比每次提交的差异。

### 5.3 内容审核回滚：版本表特别好用

一篇文章经历v1初稿→v2修改标题→v3审核通过→v4被投诉回滚到v2。版本表清楚记录“哪一版通过了审核，哪一版被回滚”。这类场景版本表比单纯历史表更贴合。

### 5.4 关联对象不要漏

退款单关联订单、用户、商品、优惠券；售后单关联物流单、收货地址；内容审核关联作者、栏目、标签。关联对象如果不快照，就会出现“主对象没变，关联对象变了，历史对不上”的问题。

---

## 六、落地时的检查清单

- 主表是否只存当前态？
- 是否有独立的流转记录表？
- 是否能查出每次状态变化的前后状态？
- 是否有操作日志记录“谁做了什么”？
- 是否在关键节点保存了快照？
- 快照是否带版本号和时间戳？
- 快照表是否有`(biz_id, version_no)`联合索引？
- 流转记录表是否有`(biz_id, created_at)`索引？
- 是否能按业务主键串起主表、流转记录和快照？
- 是否能回看某个时间点的完整状态？
- 是否支持争议处理和审计追查？

如果三项以上答不上来，说明“历史设计”还不完整。老赵补一句：别把“能查最新”当成“已经能追溯”。最新态只是结果，追溯需要过程、现场、证据三件套。

---

## 常见坑总结

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 快照无索引 | 全表扫描，页面加载几十秒 | 加`(biz_id, version_no)`联合索引和`created_at`索引 |
| 增量快照无基线版本 | 无法还原完整状态 | 定期做全量基线快照，增量快照关联基线版本号 |
| 只存快照不存版本号 | 多条快照顺序混乱 | 每张快照带`version_no`或`snapshot_seq` |
| 主表更新快照没同步 | 当前态和历史态对不上 | 写主表时同步写快照，用事务保证一致性 |
| 只有快照没有流转记录 | 能还原“什么样”，不知“怎么变成的” | 快照和流转记录表一起存，通过`snapshot_id`关联 |
| 关联对象没有快照 | 关联对象变化后历史信息丢失 | 对关键关联对象也做快照，或冗余到快照里 |
| 快照表索引过多 | 写入性能下降 | 控制在2-3个核心索引 |

---

## 结尾小结：别只存结果，要存过程、现场和证据链

流程型业务要同时考虑三件事：**主表**存当前状态；**流转记录表**存状态变化过程；**快照/版本/历史表**存每个关键时刻的现场。

老赵的实战建议：

- 高争议场景优先做全量快照，不要为省存储牺牲可追溯性；
- 高频编辑场景考虑增量快照+全量基线+版本号；
- 关键流程补齐流转记录和操作日志；
- 主表、历史表、快照表之间用`snapshot_id`或`(biz_id, version_no)`串联；
- 快照表加`(biz_id, version_no)`联合索引；
- 关联对象别忘了快照。

记住：流程型系统不是记录“最终答案”，而是保存“答案是怎么来的”。设计时先列出哪些节点需留痕、哪些状态必须回看、哪些对象会被反复修改，再决定快照怎么存。

# 第8章：审批和审核场景怎么拆表——一张单子多个人签字

## 开篇引入：审批流最容易把表设计搞乱

很多项目一碰到审批，就开始往申请单上加字段：`status`、`approver_id`、`approve_time`……后来要支持会签、驳回、加签，一张业务表被塞得臃肿不堪。

审批场景的核心不是“有没有这张单”，而是**这张单走到哪一步、谁处理过、每一步怎么变的、为什么被通过或驳回**。

拆表要围绕四层：申请单、审批节点、审批记录、审批结果。分开后，会签、加签、转交只是流程规则变化，数据模型不用推倒重来。

---

## 一、审批流的典型结构

### 1. 申请单表：只放“这个申请是什么”

申请单表保存申请人、金额、事由、关联业务对象等本体信息。判断标准：**描述“单子本身是什么”的放主表；描述“怎么流转”的不要硬塞。** 流程从“经理审批”改成“主管+财务双审”，主表字段和历史数据不会跟着乱。

### 2. 审批节点表：流程走到哪一关

要能回答：当前节点、上一节点是谁、下一节点是谁、怎么流转。流程经常变化时，建议把**流程定义**（理论上怎么走）和**流程实例**（实际走到了哪）分开。只存“当前节点名称”，后面想统计“哪个节点最容易卡住”，根本没法查。

### 3. 审批记录表：每一步都留下痕迹

每条记录独立回答：谁处理的、处理了什么、处理前状态、处理后状态、影响了哪个节点。关键是**历史可追溯**。

---

## 二、多人审批怎么建模

### 1. 会签：多人都同意才通过

**所有审批人都处理完且都通过，节点才结束。** 要建节点实例表或待办表，记录每个审批人的任务状态。常见错误是只存“节点是否完成”，不存“每个人的处理结果”。

### 2. 或签：任意一人通过即可

表上同样记录每个人的处理结果，但后端状态机必须判断：任一人通过，节点结束，其他未处理任务自动作废。不要把规则只写在前端，否则出现“前端过了，系统不让流转”。

### 3. 加签：中途插入新审批人

节点定义表存原始流转路径，节点实例表存实际执行人，审批记录表存加签动作和新增审批人。回看时能分清原本谁审、谁要求加签、加了谁。

### 4. 驳回：不是结束，而是状态回退

状态设计要拆开：节点结果（通过、驳回、转交、加签）和流程结果（进行中、已通过、已拒绝、已撤回）。节点动作和流程结论分开表达，例如某一步驳回但整个流程尚未结束。

---

## 三、当前状态和历史状态怎么保存

### 1. 当前状态字段

主表保留当前状态字段（draft、pending、approved、rejected），必要时加当前节点字段。主表职责就是**快查当前态**。

### 2. 历史状态

两层：审批记录表记录每次动作，状态变更表记录从什么状态变到什么状态。一条变更记录包含：单据ID、原状态、新状态、触发动作、操作人、操作时间。主表保结果，变更表保路径。

### 3. 历史快照

审核类场景，提交时的证件、内容可能后面会改。只存关联ID，关联对象变了，根本不知道当时审核的是什么。关键节点建议存快照：提交时、通过时、驳回时。关键是能还原当时的判断依据。

---

## 四、审批记录和操作日志怎么分工

### 1. 审批记录表：记录业务过程

关注业务语义：谁审批了、审批意见、是通过还是驳回、对应哪个节点。

### 2. 操作日志表：记录系统行为

记录谁登录了、谁点了提交、谁改了金额、谁导出了单据。审批记录偏业务，操作日志偏审计，不要混用。查流程历史看审批记录，查异常操作看操作日志。

---

## 五、三个典型场景

### 1. 报销单：流程固定，重点是流转记录

主表放报销内容，审批记录表放每一步意见，状态变更表记录每次流转。财务退回补材料时，快照很重要，因为金额、发票在提交后可能被修改。

### 2. 内容审核：重点是历史快照

最怕“审核时看的是A，后来页面展示成了B”。提交审核时保存内容快照：标题、正文、图片、标签。审核记录里要有结果和原因。**快照几乎是必需品**，审核结论对应的是某个时间点的内容。

### 3. 资质审核：重点是关联对象

用“申请单+关联对象表+快照表”组合。关联对象表存的是**这次审批关联了哪些业务实体**，比如多个证件、附件、主体信息。

---

## 结尾小结：审批系统设计先想清楚四件事

拆表前先问自己：1. 申请单本体数据是什么？2. 当前状态和流程节点怎么存？3. 每次流转、驳回、加签怎么留痕？4. 关联对象和历史快照怎么保留？

**常见坑总结：**
- **坑1：未考虑多人会签**——只存一个审批人，无法表达会签/或签
- **坑2：审批记录和操作日志混用**——无法分辨业务流转和系统操作
- **坑3：驳回未重置节点状态**——不记录原因和节点，流程卡死
- **坑4：没有快照**——审核依据丢失，无法还原判断依据
- **坑5：关联对象只存ID**——关联对象变更后，不知道当时审核的是什么

**记住：审批流不是一张单，而是一串可追踪的状态变化。** 把申请单、审批节点、审批记录、状态变更、操作日志、历史快照分开设计，审批系统才能真正落地。

# 第9章：关联对象怎么建——主单、子单、对象链路别断掉

## 开篇引入：流程业务最怕“单子都在，关系没了”

我见过很多流程系统，表面上主表、明细表、日志表都齐了，一到排查问题就卡住：

- “这笔退款对应哪次发货？”
- “这个售后单最初是从哪个订单拆出来的？”
- “审批通过后生成的子任务，后来又流转到哪里去了？”

根子往往不在业务本身，而在数据模型：**关联对象的链路断了**。

流程型业务不是只有一张主单。注册、下单、支付、发货、售后、审批、回退，每一步都会产生新对象，或者引用旧对象。你如果只盯着业务表，不设计关联对象、子对象、扩展对象之间的关系，最后就会出现三种问题：

1. **查不回去**：只能看到当前状态，看不到来源；
2. **串不起来**：知道有支付、发货、售后，但不知道前后关系；
3. **回放不了**：历史记录和操作日志都有了，但对象链路断了，没法复盘。

这一章只讲一件事：**一个流程关联多个对象时，怎么把主单、子单、关联对象、扩展对象建清楚，并让链路可查、可追、可回放。**

---

## 一、主对象、关联对象、子对象、扩展对象，到底怎么分？

### 1. 主对象：流程的“业务载体”

主对象是流程里最核心、最先产生、最能代表业务意图的对象。比如：

- 订单流程里的“订单”
- 审批流程里的“申请单”
- 售后流程里的“售后单”
- 工单流程里的“工单”

主对象通常具备几个特征：

- 有独立业务编号；
- 有自己的状态字段；
- 是后续对象的源头；
- 是查询和统计的主入口。

**判断标准很简单：**  
如果一个流程后续动作都围绕它展开，它大概率就是主对象。

主对象不负责装下所有信息，而是让人一眼看出“这件事现在走到哪了”。所以主对象里通常只保留最核心字段，比如状态、发起人、创建时间、关键金额、关键引用等。

### 2. 关联对象：为了补齐流程链路而存在

关联对象不是主角，但很关键。它负责记录“这个流程还关联了谁”。

比如订单流程里，订单会关联：

- 支付单
- 发货单
- 退款单
- 发票申请
- 售后单

这些对象可能一对多、多对多，甚至异步生成、先后到达，不能硬塞进订单表，而要通过关联关系表或链路表表达。

### 3. 子对象：从主对象派生出来的从属记录

子对象更强调从属关系。比如：

- 订单明细是订单的子对象；
- 申请单中的审批步骤是申请单的子对象；
- 工单中的处理记录是工单的子对象。

子对象一般满足：

- 依附主对象存在；
- 通常随主对象创建、查询、归档；
- 生命周期受主对象影响较大。

子对象的价值，在于把大流程拆成可管理的颗粒度。你想看订单里哪一项商品出了问题，不能只看主单字段，必须落到明细行；你想看审批卡在哪一步，也不能只看申请单当前状态，还得看步骤记录。

### 4. 扩展对象：补充主对象表达能力

扩展对象用于承载主表放不下、又不想把主表撑胖的内容。比如：

- 订单扩展信息
- 用户实名认证信息
- 审批补充材料
- 售后附件、图片、备注

它的特点是：

- 字段变化快；
- 结构可能不稳定；
- 适合独立存储，避免主表频繁变更。

很多系统一开始把“备注、附件、补充说明”都塞进主表，后来需求一变，主表越来越胖，查询也越来越慢。这个时候把扩展对象拆出去，通常更稳。

**一句话区分：**

- **主对象**：流程中心；
- **子对象**：主对象的从属结构；
- **关联对象**：流程中横向连接的其他业务实体；
- **扩展对象**：主对象的信息补充层。

---

## 二、一对多、多对多、链式关联，在流程表里怎么表达？

### 1. 一对多：最常见，别设计复杂了

一对多是流程系统里最常见的关联模式。比如：

- 一个订单对应多个发货记录；
- 一个工单对应多个处理动作；
- 一个申请单对应多个审批节点记录。

最直接的做法是：在“多”的一侧放外键，指向“一”的主对象。

比如：

- `shipment.order_id`
- `approval_step.application_id`
- `after_sales.order_id`

**优点：**简单、查询方便、易维护。

**坑点：**  
如果后续出现“一个发货记录可能同时关联多个订单”，就不能再靠单外键解决。也就是说，**一对多不要写死成永久一对多，要预留升级成多对多的可能。**

### 2. 多对多：必须单独建关联表

多对多场景最容易做乱。比如：

- 一个售后单可能关联多个订单；
- 一个活动任务可能关联多个用户；
- 一个审批结果可能影响多个对象；
- 一个发货包裹可能包含多个订单商品。

这时推荐单独建**关联关系表**：

- `rel_object_link`
- `order_after_sales_link`
- `flow_relation`

关系表至少要记录：

- 主对象ID
- 关联对象ID
- 关联类型
- 关联来源
- 创建时间

不要试图把多对多关系塞进 JSON 字段里就完事。JSON 可以做辅助信息，但**不能替代稳定的可查询关系表**。真正要查“某个售后单关联了哪些订单”“某个订单被哪些售后影响过”，关系表更可靠，也更好建索引。

### 3. 链式关联：要能顺着链路往下追

链式关联是流程系统里最容易被忽略的一种。比如：

订单 → 支付单 → 发货单 → 售后单

它不是简单并列关系，而是有明显前后生成关系。除了“关联对象ID”，最好还要记录：

- 来源对象ID
- 来源对象类型
- 生成动作
- 上一跳对象ID
- 链路层级或顺序

这样才能回答：

- 这个售后是基于哪次发货发起的？
- 这次发货对应哪个支付成功后的订单？
- 订单取消后，哪些下游对象要一起回收？

**链式关联的核心不是“有关联”，而是“能回放”。**

你要的是一条路径，不只是一个点。路径一断，业务分析、问题排查、审计追责都会很难。

---

## 三、关联对象ID、关联类型、关联来源、关联顺序怎么设计？

这一节是落地关键。很多系统不是没有表，而是关联字段设计太粗，最后查不出链路。

### 1. 关联对象ID：必须明确“连的是谁”

不要只存一个笼统的 `ref_id`，要配合类型一起看。因为不同对象可能都用同样的数字主键，单看ID会撞。

建议至少设计：

- `object_id`：当前对象ID
- `object_type`：当前对象类型
- `related_object_id`：关联对象ID
- `related_object_type`：关联对象类型

这样查链路时不会混。

如果对象类型很多，`object_type` 最好设计成明确枚举值，比如 `order`、`pay`、`shipment`、`after_sale`、`approval`。别图省事全写成字符串拼接，后面统计和校验会很痛苦。

### 2. 关联类型：决定“这是什么关系”

关联类型不能省。因为同样是“订单关联售后”，语义可能不同：

- 原始来源
- 处理结果
- 补充信息
- 回退目标
- 并行关联

建议定义成枚举或字典，例如：

- `source`
- `child`
- `related`
- `follow_up`
- `reverse`
- `replacement`

**关系名一定要有业务语义。**  
否则后面做查询、统计、回放、审计时，根本不知道这条关系代表什么。

比如售后单关联订单，如果关系类型是 `source`，说明它是来源；如果是 `related`，说明只是辅助关联；如果是 `reverse`，说明它代表逆向处理。语义不同，后续规则也不同。

### 3. 关联来源：告诉你“谁生成了这条关系”

关联来源要记录产生关系的动作或模块。比如：

- 用户手工发起
- 审批通过自动生成
- 支付回调生成
- 定时任务补全
- 客服后台补录

这对于排查问题非常重要。很多线上纠纷不是对象本身错了，而是“关系怎么来的”没人说得清。

关联来源的价值不只在审计，还在排障。比如某条退款关联是支付回调生成的，就要查回调有没有重复；如果是客服补录的，就要看人工操作是否越权。没有来源字段，出了问题只能猜。

### 4. 关联顺序：处理链式场景的关键

如果一笔流程会串多个对象，顺序字段就很有价值。比如：

- 第1步：下单
- 第2步：支付
- 第3步：发货
- 第4步：签收
- 第5步：售后

可以记录：

- `relation_seq`
- `step_no`
- `chain_level`

这样不仅能排序，还能做流程回放和路径分析。

**实战建议：**  
顺序字段不要只用于展示，更要参与链路推导。否则你看着整齐，底层还是乱的。尤其在审批/审核场景里，多个节点并行、驳回后重走、补充材料后重新提交，如果没顺序和层级，流程很难复盘。

---

## 四、如何避免流程表和关联表之间的耦合失控？

这是老问题。很多团队为了图快，喜欢把所有东西往主表里塞，最后表结构越来越胖，关系越来越乱。

### 1. 主表只放“业务核心状态”

主表应该只保留：

- 核心业务编号
- 当前状态
- 关键时间点
- 主体属性
- 少量高频查询字段

不要把所有关联对象ID都塞进主表列里。一旦关联对象类型多了，字段会膨胀成灾难。

主表的职责，是让人快速看到“这单现在怎样了”；不是承担所有上下游关系。把主表做成流程总览，把关系细节交给关联表，这样边界才清楚。

### 2. 关系独立建模，减少强耦合

建议把关系放进独立表，主对象只持有最核心引用。独立关系表的好处是：

- 新增关联类型不需要改主表；
- 多对多表达自然；
- 可做索引优化；
- 更适合审计和回放。

这也是**业务表与流水表的区别**之一：业务表负责描述业务实体，流水或关系表负责记录变化、关联和过程。别把两者混在一起，不然你既想查当前态，又想查历史链路，最后谁都不好使。

### 3. 关联表要避免“只存结果，不存过程”

很多人只存当前关联结果，比如“订单已关联退款单”。但这样不够。你应该尽量保留：

- 什么时候关联的；
- 谁触发的；
- 关联前是什么状态；
- 关联后为什么变化。

这就把**操作日志**和**流转记录**的思想接进来了。关联关系本身也是一种状态变更，别把它当静态事实。

比如审批通过后自动生成子任务，这个子任务不是凭空出现的，它一定有一个“生成动作”。把动作记下来，后面才能知道对象链路是怎么被拉起来的。

### 4. 历史记录与当前关系分层存储

你要区分两层：

- **当前关系表**：用于快速查询“现在连着谁”
- **历史关系表**：用于回溯“以前连过谁”

尤其在退款、撤销、换货、关闭流程里，关系会变。  
如果只保留现态，不保留历史，最后就只能看到最后一跳，前面全没了。

记住一个原则：**可查询性不等于只查当前，可追踪性必须依赖历史。**  
没有历史记录，你只能回答“现在是什么”，回答不了“它怎么变成现在的”。

---

## 五、订单-支付-发货-售后链路，怎么拆成可追踪结构？

下面用一个典型链路把方法串起来。

### 1. 订单是主对象

订单表记录：

- `order_id`
- `order_no`
- `status`
- `buyer_id`
- `created_at`

这是主单，负责描述交易意图。  
主单的状态字段通常要覆盖流程关键节点，比如待支付、已支付、已发货、已完成、已取消。不要把所有状态搅成一锅粥，状态字段要能反映业务主线。

### 2. 支付单是链式关联对象

支付单表记录：

- `pay_id`
- `pay_no`
- `order_id`
- `pay_status`
- `pay_amount`

这里 `order_id` 是直接来源。  
如果一个支付单支持多订单合并支付，就要加关系表，不要硬塞单外键。

支付单记录的是“我付了多少、什么时候付的、支付是否成功”。订单和支付职责不同，不能混在一张表里。

### 3. 发货单是下游对象

发货单可以直接关联支付完成后的订单，也可以关联支付单，取决于业务。

- 如果发货只认订单，就保留 `order_id`
- 如果发货必须追支付来源，就同时保留 `pay_id`

这就是“主对象 + 关键链路对象”双引用的典型做法。别怕多存一点，怕的是以后追不回来。

很多系统排查“为什么这单发货慢了”，最后发现不是发货表的问题，而是支付单迟迟没确认。如果发货单里只有订单ID，没有支付单ID，排查时就得再绕一圈。链路关键对象最好显式保存，别全靠联查推断。

### 4. 售后单是回流对象

售后单通常是逆向流程对象，要明确它引用的是哪一段链路：

- 来源订单
- 来源发货单
- 来源支付单
- 原因类型
- 处理结果

最好再补一张售后关系表，记录它跟原订单、原发货、原支付之间的多重关系。  
因为售后往往不是只对一个对象负责，而是对整段履约链条负责。

售后场景特别容易出问题：有的只退货不退款，有的先退款后补寄，有的换货会重新生成发货单。你只存一个“关联订单ID”不够，必须把相关对象和关系类型分开存，才能解释清楚业务到底走了哪条支线。

### 5. 操作日志、流转记录、历史快照一起补齐

链路能跑通之后，还要能回放：

- **流转记录表**：记录对象状态如何从A变到B；
- **操作日志表**：记录谁在什么时间做了什么动作；
- **历史快照表**：记录某一时刻对象的完整状态。

三者配合，才能把“对象链路”变成“可审计链路”。

- 流转记录告诉你过程；
- 操作日志告诉你是谁干的；
- 历史快照告诉你当时长什么样。

这三张表跟关联对象表放在一起，整个流程才算闭环。缺一块，后面就容易出现“知道发生过，但说不清怎么发生的”。

---

## 章末小结：对象关系建模，核心是不断链

这一章最重要的一句话是：**流程业务不是把对象堆在一起，而是把关系管清楚。**

你在做关联对象建模时，记住这几个原则：

1. **先分清主对象、子对象、关联对象、扩展对象**；
2. **一对多简单放外键，多对多一定建关系表**；
3. **链式关联要记录来源、类型、顺序，保证能回放**；
4. **主表只放核心状态，关系独立存，别把耦合塞满主表**；
5. **流转记录、操作日志、历史快照要和关联关系一起设计**。

### 常见坑回顾

- 把所有关联都塞进主表字段；
- 只存当前关系，不存历史关系；
- 不区分关联类型，导致后续无法解释业务语义；
- 只记录ID，不记录来源和顺序；
- 售后、退款、审批这类逆向流程没有链路追踪。

### 行动建议

下次你设计流程型业务时，先别急着画表。先拿一张纸，把这几个问题答出来：

- 主对象是谁？
- 它会生成哪些子对象？
- 会关联哪些外部对象？
- 哪些关系是横向关联，哪些是上下游链式关系？
- 哪些关系必须可追溯、可回放、可审计？

只要这五个问题想清楚了，表结构就不会跑偏。  
流程系统真正难的，不是“有没有数据”，而是**每一个对象为什么会和另一个对象连上，什么时候连上的，后面又为什么断开。**

# 第10章：可查询性怎么保证——让运营、客服、技术都能查得动

## 开篇引入：能存不算本事，查得动才算上线

流程型业务上线后，运营要查“工单卡在哪”，客服要查“用户上次处理到哪一步”，技术要拉“最近三个月所有审批链路”，报表还要按渠道看每一步转化。

**可查询性不是上线后的补丁，而是建模时就要预判：谁来查、查什么、按什么条件查、查到什么粒度、能不能接受延迟。**

---

## 一、常见查询场景有哪些？先拆清楚“谁在查”

### 查询场景优先级排序

**第一优先级：当前状态查询（命脉级）**——列表页核心，占日常访问量80%以上，必须毫秒级响应。

**第二优先级：流转历史查询（审计级）**——客服查单、风控追溯、运营复盘，频次低于列表，但查不到直接影响对客响应。

**第三优先级：某人处理记录查询（人员级）**——绩效统计、工作交接、权责追溯，对查询条件灵活性要求高。

**第四优先级：关联链路查询（分析级）**——如“订单关联的支付、退款、发货全链路”，频次低但复杂度高，可接受稍慢响应。

### 1. 查当前状态：这单现在在哪一步

**关键点**：当前状态必须直接落在主表里，不能每次靠流转记录计算。

### 2. 查流转历史：它是怎么走到现在的

靠**流转记录表**和**操作日志表**，主表负责“现在”，历史表负责“过程”。

### 3. 查某人处理过什么：这个人参与了哪些流程

不能只存“当前处理人”，要考虑当前处理人、历史处理人、当前节点负责人、参与记录。

### 4. 查某对象关联链路：这件事跟谁有关

本质是**关联对象建模**问题，一开始没设计好关联字段和关系表，关联越多查询越复杂。

---

## 二、状态字段和索引怎么设计？让查询既快又准

### 1. 主表必须有“当前状态”

工单主表应放：`status`、`current_node`、`current_handler_id`、`updated_at`。列表页一查就出结果，不需要联表计算。

### 2. 状态字段要能筛选，别太语义化

数据库存稳定状态码（如`WAIT_OP_REVIEW`），业务层维护状态映射。数据库关心“能不能稳定存、稳定查”。

### 3. 状态不是历史，状态变化要另存

**主表负责当前态，流转表负责过程态，日志表负责操作痕迹**。

### 4. 索引设计实战：从最频繁的查询开始

**案例：查询某个用户过去30天内所有待处理的工单**，建联合索引：

```sql
CREATE INDEX idx_handler_status_time ON work_order (current_handler_id, status, created_at);
```

**设计原则**：
- 等值条件放前面：`current_handler_id`和`status`
- 范围条件放后面：`created_at`
- 避免索引列上做函数运算
- 覆盖索引更高效

**其他高频索引**：
- `INDEX(status, created_at)`——按状态+时间查询列表
- `INDEX(current_handler_id, status)`——按处理人+状态查询
- `INDEX(biz_id, created_at)`——流转表按业务ID追踪历史

**实战建议**：上生产前用慢查询日志记录一周，找出TOP 5慢查询针对性加索引。

---

## 三、流转记录表和操作日志表怎么配合？别做成一张垃圾桶

### 1. 流转记录表：记录状态怎么变的

关注“流程节点”和“状态变更”，至少包含：`biz_id`、`from_status`、`to_status`、`from_node`、`to_node`、`actor_id`、`action_type`、`remark`、`created_at`。审批场景补`approve_result`、`approve_comment`、`next_handler_id`。

### 2. 操作日志表：记录谁做了什么操作

偏“行为审计”，不一定只围绕状态变化。建议字段：`biz_type`、`biz_id`、`operator_id`、`operation`、`request_data`、`result`、`ip`、`created_at`。

### 3. 历史快照表什么时候单独建

在关键节点（提交、审核通过、驳回重填）保存完整业务数据副本。建议字段：`biz_id`、`snapshot_type`、`snapshot_data`（JSON或大字段）、`created_at`。

### 4. 典型查询SQL对比

| 查询场景 | 用流转记录表 | 用操作日志表 |
|---------|------------|------------|
| 查工单完整流转路径 | `SELECT * FROM flow_record WHERE biz_id=? ORDER BY created_at` | 不适用 |
| 查张三今天操作了哪些工单（含查看详情等） | 仅限状态变更 | `SELECT * FROM op_log WHERE operator_id='zhangsan' AND created_at>=?` |
| 查工单被驳回次数 | `SELECT COUNT(*) FROM flow_record WHERE biz_id=? AND action_type='REJECT'` | 不适用 |
| 查用户是否做过“导出数据”操作 | 不适用 | `SELECT * FROM op_log WHERE operator_id=? AND operation='EXPORT'` |

**流转记录表回答“流程怎么走的”，操作日志表回答“人都干了什么”**。

---

## 四、冗余字段和汇总字段怎么用？让查询快，但别把一致性搞崩

### 1. 冗余字段是为了少联表

适合冗余的字段：用户名快照、处理人姓名、组织名称、当前节点名称、关联对象编号。高变字段慎冗余，展示字段可冗余，业务判断字段必须单一来源。

### 2. 汇总字段适合做统计，不适合当真相源

`approve_count`、`reject_count`等可加速列表和报表，但属于派生数据。汇总字段要有重建机制，真相还是在主表状态和流转记录里。

### 3. 性能优化技巧

**杀手1：分页越翻越慢**——改进为游标分页：
```sql
SELECT * FROM work_order WHERE status='WAIT_HANDLE' AND id > 1000000 ORDER BY id LIMIT 20;
```

**杀手2：全表扫描**——status区分度低时考虑分区表，按月或按状态分区。

**杀手3：大字段拖慢查询**——详情内容、附件路径等单独抽出“详情表”，主表只存轻量字段。

---

## 五、列表页、详情页、报表页分别要什么数据结构？

### 1. 列表页：要“轻、快、能筛选”

只依赖主表+少量冗余字段，不查完整历史、完整审批链。适合展示：编号、标题、状态、当前处理人、创建时间、最近更新时间。

### 2. 详情页：要“全、准、可追溯”

可接受更多联表和多次查询。先查主表获业务主体，再查流转记录表、操作日志表、关联表。

### 3. 报表页：要“可汇总、可分组、口径一致”

适合用预聚合表、统计快照表、定时同步宽表，不要直接拿流转明细硬跑大报表。

---

## 六、案例拆解

### 1. 工单场景

主表建议放：`status`、`current_node`、`current_handler_id`、`priority`、`source_channel`、`last_action_at`。索引：`INDEX(current_handler_id, status, created_at)`和`INDEX(status, created_at)`。

### 2. 订单场景

除了订单主表，还要有支付流水表、退款流水表、状态变更表。**订单表是业务真相，流水表是事件过程，两者不能混成一张表**。

### 3. 审核场景

主表存当前审核状态，流转表存节点与结果，审核意见单独存，原始内容保留历史快照。

---

## 七、避免为了查询方便破坏一致性

### 真实二选一场景推演

**场景**：运营要求列表页显示“当前处理人姓名”，但处理人会变化。决策流程：
1. 展示用还是业务判断用？→ 展示用
2. 变化频率？→ 每次转派才变，频次不高 → 可冗余
3. 不冗余代价？→ 列表页每行联表查姓名，代价高
4. 如何保证一致性？→ 转派操作时同步更新`current_handler_name`

**结论**：冗余，但要保证每次状态变更时同步更新。

### 判断能否冗余的标准
- **展示用**：可适度冗余
- **查询高频**：可预置
- **业务真相**：必须单一来源
- **历史追溯**：必须保留快照或记录

---

## 章节小结：三句话记住本章

1. **当前状态放主表，流转历史另开表，操作日志独立存，历史快照防纠纷**。
2. **列表页轻、详情页全、报表页预聚——各司其职，不要混用**。
3. **冗余之前先问三个问题：展示用还是判断用？变化频率高不高？不同步会导致什么后果？**

- [ ] 当前状态是否直接落在主表字段里？
- [ ] 流转记录表和操作日志表是否职责分离？
- [ ] 历史快照表是否在关键节点存了副本？
- [ ] 列表页查询是否只依赖主表+少数冗余字段？
- [ ] 冗余字段是否有更新机制（在状态变更时同步）？
- [ ] 报表查询是否用了预聚合表或统计快照表？
- [ ] 最频繁的查询场景是否建了联合索引（等值条件放左边）？
- [ ] 分页查询是否避免了`LIMIT`大偏移量？

### 常见坑总结

| 坑 | 后果 | 正确做法 |
|------|------|----------|
| 当前状态靠流转表最新记录算出 | 列表页性能差，分页慢 | 主表直接存当前状态 |
| 状态值用中文或含义模糊的字符串 | 筛选困难，索引效率低 | 使用稳定状态码，业务层做映射 |
| 索引只加在主键上 | 常用查询全表扫描 | 按查询模式建联合索引 |
| 一次加太多索引 | 写入性能下降 | 先通过慢查询日志确定TOP 5 |
| 操作日志和流转记录混在一张表 | 查流程像查日志 | 三张表各司其职 |
| 冗余字段没有更新机制 | 数据不一致 | 展示字段可冗余，业务判断字段单一来源 |
| 报表直接跑业务明细表 | 线上慢查询 | 用预聚合表或统计快照表 |
| 分页用`LIMIT 1000000, 20` | 越翻越慢 | 改用游标分页 |
| 没有历史快照 | 无法复原某刻数据 | 关键节点保存业务数据副本 |

# 第11章：流程型建模常见坑——老赵踩过的坑你别再踩

## 开篇引入

流程型项目常见问题：PPT画得漂亮，落库时只剩一个`status`字段加一张“万能业务表”。流程一复杂，谁改的状态、什么时候改的、状态怎么来回跳的，全答不上来。系统会慢慢失控。

流程型建模最怕的不是流程长，而是**表设计不支持追踪**。没有状态变更记录、操作日志、历史快照，流程图再漂亮，数据库里也存不住过程。

---

## 常见坑一：用一个status字段当万能开关

**问题描述**：很多人觉得流程一个`status`字段就够了：0待处理，1通过，2驳回，3关闭。但流程不只有当前状态，还有怎么走到这里。只保留结果不保留过程，时间一长就是黑盒。

**真实案例**：内容审核。作者提交→驳回→修改重提→复审通过→发布失败回滚。单靠一个`status`，只能看到“现在在哪”，不知道“中间发生了什么”。状态来回跳时，同是“待审核”，分不清是第一次还是第三次补材料。

**解决方案**：
- `status`只负责**当前态**，不作为历史账本
- 配合`status_updated_at`、`status_updated_by`、`version`（防并发覆盖）
- 过程交给**流转记录表**和**操作日志表**

## 常见坑二：业务表、流水表、日志表职责混乱

**问题描述**：所有东西塞进一张表，谁都说不清它到底是“业务表”还是“流水表”。

**三类表的职责**：
- **业务表**：存“这件事是什么、当前到哪一步了”
- **流转记录表**：存“这件事经历了哪些状态变化”
- **操作日志表**：存“谁在什么时间做了什么动作”

**真实案例**：工单系统。业务表存工单编号、标题、当前状态、处理人；流转记录表存起始状态、目标状态、动作类型、操作人、操作时间；操作日志表存操作人、动作、请求参数、结果、IP。三者回答不同问题：业务表回答“现在怎样”，流转表回答“怎么变过来”，日志表回答“谁点了什么按钮”。

**判断法**：问自己“这张表是用来‘看现在’的，还是‘看过程’的？”看现在→业务表，看过程→流转表，看动作→日志表。

## 常见坑三：只记录结果不记录过程

**问题描述**：很多系统只关心“最后成没成”，不关心“怎么成的”。出现争议后没法追责也没法复盘。

**真实案例**：退款场景。业务表只有`refund_status=成功`。用户问为什么晚了两天，运营问是谁审核的，财务问中间是否失败重试——没有过程记录，你只能回答“系统最后显示成功了”。

**解决方案**：可追踪的数据结构至少要回答四个问题——什么时候变的、谁变的、从哪变到哪、为什么这么变。流转记录表至少包含：主对象ID、旧状态、新状态、操作类型、操作人、操作时间、处理意见。涉及审批再加审批节点、审批结果、审批意见、审批链路顺序。

**补充：历史快照也别省**。用户申请退款时提交的破损照片，后来又补了新图。不存历史快照，争议起来你只能看到最新材料。快照是在给争议留证据。

## 常见坑四：表结构过度抽象

**问题描述**：另一种极端是把流程抽得太漂亮——流程定义表、节点定义表、路由规则表、动态上下文表、抽象状态机表。概念完整，代码复杂，业务看不懂，排查问题都不知从哪张表查。

**解决方案**：先做“够用的结构”，再考虑扩展。判断标准：列表页能不能直接查当前状态？详情页能不能看到完整流转？审计页能不能定位每次操作？这些都查不顺，说明抽象过头了。

## 常见坑五：忽略审批/审核/驳回/回退等复杂状态

**问题描述**：审批场景不只是“通过/不通过”，有很多中间态。如内容审核：草稿→待审核→审核中→已通过→已驳回→待修改→已撤回→已发布。容易漏：驳回后回到哪里？回退是否保留原审批记录？撤回算不算状态变更？重复提交是否生成新流程实例？

**解决方案**：把审批分成三层——业务对象（文章、订单）、流程实例（本次审批过程）、节点记录（每个审批环节的处理结果）。至少记录：被谁驳回、驳回到哪个节点、是否允许重新提交、是否保留原意见。

---

## 结尾小结：先分职责，再谈优雅

业务表放当前结果，流转记录表放状态变更过程，操作日志表放谁做了什么，历史快照放关键时刻的业务内容，关联对象单独存清楚。

**检查清单**，设计流程型表结构时问自己五个问题：
1. 当前状态能不能一眼查出来？
2. 每次状态变更能不能追溯？
3. 谁操作的能不能查到？
4. 审批、驳回、回退能不能还原？
5. 关键内容改了以后，历史还能不能对上？

只要有一个答不上来，说明表结构还没为流程服务。别让一个`status`字段背所有锅，也别让一张表干三种活。把当前态、过程态、操作态分清楚，系统才算真正站稳了。

# 第12章：一套可复用的拆表方法——从流程图到表结构的落地步骤

## 开篇引入：拿到一个新流程，先别急着画表

流程型业务包含**当前态、过程态、历史态、审计态**四层信息。只盯着当前状态，后面出现审批、撤回、重试、回看、追责、统计，表结构就只能不断打补丁。

这章给出一套可复用的方法：**先从流程图拆对象，再按状态分层，最后补齐流转记录、操作日志、历史快照。**

团队曾接手退款审批系统。产品经理扔来一张流程图——七个节点、四条退回线、三个超时分支。开发直接按节点建表，每个节点一张表。结果上线两周，查当前状态要联七张表，统计平均审批时长要写二十行SQL。这就是“看图直接建表”的坑。

本章以**退款审批流程**为例，手把手带你从图走到表。

---

## 一、从流程图识别业务主对象、节点、动作、结果、关联对象

### 1. 先用一个完整流程图推演

退款审批流程：
```
用户提交退款申请 → 系统校验订单 → 客服初审 → 财务复审（金额>5000时） → 退款执行 → 完成
   ↑              ↓               ↓           ↓                      ↓
  撤回          校验失败退回    驳回重填    驳回终止               失败重试
```

**核心原则**：流程图里最重要的不是箭头，而是**主对象**。所有箭头围绕着“这个申请单”在画。订单支付流程主对象是订单，内容审核是内容，退款是退款单。

### 2. 判断业务主对象的五个标准

| 候选对象 | 动作是否围绕它展开 | 是否需要统一编号 | 是否要被查询跟踪统计 | 是否承载其他对象 | 结论 |
|---------|------------------|-----------------|-------------------|----------------|------|
| 退款申请单 | 是，所有节点都在处理它 | 是，退款申请编号 | 是 | 是，承载订单信息、金额、原因 | ✅ **主对象** |
| 客服审批节点 | 否，只是其中一个环节 | 否 | 否 | 否 | ❌ 关联对象 |
| 财务复审节点 | 否，仅特定金额才进入 | 否 | 否 | 否 | ❌ 关联对象 |
| 退款记录 | 是，但它是执行结果而非流程载体 | 是 | 部分场景需要 | 否 | ⚠️ 业务子表 |

**判断标准：如果先想到“二级审核”“财务复核”，说明你盯着过程而不是对象。先确定主对象，再想节点的拆分。**

### 3. 再拆五件事：节点、动作、结果、关联对象、触发条件

**① 节点**：流程阶段（待提交、待审核、审核中等），对应状态字段。建议用枚举表或常量类管理，主表只存枚举值。

**② 动作**：人/系统做了什么（提交、审核通过、撤回）。动作落在**流转记录表**和**操作日志表**。动作是“动词”，状态是“名词”，建模时一定分清楚。

**③ 结果**：动作后的状态变更（待审核→审核中）。**动作不一定导致状态改变，但状态改变一定由动作触发。** 用户点“提交”但校验失败时状态可能没变；系统超时取消是系统触发。

**④ 关联对象**：订单关联用户/商品/支付单。决定是否拆**关联表、引用表、快照表**。只存`related_id`却不知关联谁是最常见的坑。要明确：关联只是实时查询用，还是必须保留当时版本。

**⑤ 触发条件**：金额超5000进二级审批、库存不足拦截。表结构要存**条件判断结果**和**触发来源**。比如退款单里有一个字段`trigger_rule`记录“为什么走到这个节点”。

### 4. 流程图不能直接变成表结构

流程图只告诉你“发生了什么”，表结构要解决：现在什么状态、谁在什么时候做了什么、为什么从A变B、历史上经历过哪些步骤、关联对象当时是什么样子。

从流程图到表结构，先拆五层：
1. 主对象是谁  
2. 状态有哪些  
3. 动作有哪些  
4. 记录哪些过程  
5. 需要保留哪些历史

退款流程举例：
- 主对象：退款申请单
- 状态：待提交、待校验、待初审、初审驳回、待复审、复审驳回、待执行、执行中、已完成、已取消
- 动作：提交、校验通过、校验失败、初审通过、初审驳回、复审通过、复审驳回、执行退款、重试、撤回、取消
- 过程：每一步的from→to
- 历史：提交时的申请内容、驳回时的驳回原因、执行退款时的支付快照

## 二、按当前态、过程态、历史态、审计态分层设计表

### 1. 为什么要分层？

信息混在主表，很快出现：状态变因说不清、谁改的不知道、审批过程看不见、统计耗时没数据。

数据分四层：
- **当前态**：现在处于什么状态
- **过程态**：每一步流转怎么发生
- **历史态**：过去状态和内容是什么
- **审计态**：谁在什么时候做了什么

四个问题能闭环，流程型数据结构才算合格。

**关键区分：流转记录是流程轨迹，操作日志是审计痕迹。** 客服后台手工改退款单状态，操作日志能找到“谁改的、为什么改”，但退款单自身的流转轨迹（从待初审到已完成）只记录在流转记录表。不要混，混了之后业务查链路看到接口调试日志，运维查操作看到状态变更记录。

### 2. 当前态：主表只负责“现在是什么”

典型字段：主键id、业务编号、当前状态status、当前处理人current_handler、当前节点current_node、关联对象id、核心业务属性、创建/更新时间。

主表只存三类：当前可见状态、当前定位信息、业务核心字段。不要把流转历史和辅助信息堆进来。

退款单主表示例：
```sql
CREATE TABLE refund_order (
    id BIGINT PRIMARY KEY,
    refund_no VARCHAR(32) UNIQUE,
    order_id BIGINT,
    user_id BIGINT,
    amount DECIMAL(10,2),
    reason VARCHAR(500),
    status VARCHAR(20),
    current_handler_id BIGINT,
    current_node VARCHAR(50),
    created_at DATETIME,
    updated_at DATETIME
);
```

### 3. 过程态：用流转记录表描述“中间发生了什么”

典型字段：id、业务主表id、流转前状态from_status、流转后状态to_status、节点node_code、动作action、操作人operator_id、操作时间operate_time、流转原因reason、来源渠道source_type、是否有效is_valid。

流转记录表不是“状态变更日志”，而是流程轨迹的骨架。至少要写清：谁发起的、系统自动还是人工操作、触发时上下文、是否有效或已被撤销。

退款流转记录表示例：
```sql
CREATE TABLE refund_flow_log (
    id BIGINT PRIMARY KEY,
    refund_id BIGINT,
    from_status VARCHAR(20),
    to_status VARCHAR(20),
    node_code VARCHAR(50),
    action VARCHAR(50),
    operator_id BIGINT,
    operate_time DATETIME,
    reason VARCHAR(500),
    source_type VARCHAR(20),
    is_valid TINYINT DEFAULT 1,
    INDEX idx_refund_id (refund_id),
    INDEX idx_operate_time (operate_time)
);
```

### 4. 历史态：用快照表保留“当时是什么样子”

需要快照的场景：订单发货后商品信息改了但需保留下单价格、审批通过后申请内容被改过但审批版本必须保留、退款时订单地址留档。

快照表字段：id、业务主表id、快照版本version、快照类型snapshot_type、快照内容snapshot_data、生成时间created_at、生成原因snapshot_reason。

快照分两种：**全量快照**（保存全部关键字段，适合节点少的场景）和**增量快照**（只保存变化字段，适合存储敏感场景）。常见索引组合`(biz_id, version)`或`(biz_id, snapshot_type, created_at)`。

退款快照表示例：
```sql
CREATE TABLE refund_snapshot (
    id BIGINT PRIMARY KEY,
    refund_id BIGINT,
    version INT DEFAULT 1,
    snapshot_type VARCHAR(20),
    snapshot_data JSON,
    created_at DATETIME,
    reason VARCHAR(200),
    INDEX idx_refund_version (refund_id, version),
    INDEX idx_refund_type_time (refund_id, snapshot_type, created_at)
);
```

### 5. 审计态：操作日志表记录“谁做了什么”

典型字段：id、业务类型biz_type、业务id biz_id、操作人operator_id、操作动作op_action、操作前摘要before_summary、操作后摘要after_summary、ip/终端/请求来源、操作时间、是否成功、错误信息。

**流转记录关注节点变化（订单从待支付变成已支付），操作日志关注操作行为（客服在后台点了手工退款按钮）。** 流转记录是流程轨迹，操作日志是审计痕迹。两个概念不同，两张表。

## 三、先主表后流水表，再补日志表和快照表

### 1. 为什么要先主表？

主表决定“对象能不能成立”。退款流程先明确：退款单是谁的、退款金额怎么算、是否允许多次退款、是否关联原支付单。

落地顺序：定主对象和主键→定当前状态→定流转记录→定操作日志→补快照和关联对象。

### 2. 再做流水表：只记录变化，不重复堆字段

流水表只存**变化信息**和必要上下文。例如订单支付流水存：order_id、from_status、to_status、action、operator_id、operate_time、payload_snapshot、remark。

判断标准：主表能查到的不要在流水表重复存；只有变化过程中才需要的信息才放流水表。**流水表不承担主表职责。**

### 3. 再补日志表：记录“为什么这样改”

操作日志补上来源系统、操作入口、请求参数、异常原因、成功失败结果。业务查链路看流转记录，查责任看操作日志，查现场看快照。

### 4. 最后补快照表：用于回溯版本和关键时点

适合做快照的场景：审批单内容会被修改、订单关键字段会被改写、需要对比提交时和处理时的差异、发生争议要还原现场。

**节点快照**在关键节点生成完整快照，省存储查得快；**变更快照**每次关键变更时记录前后内容，全程可追溯但注意存储膨胀。

### 5. 关联对象建模方式的选择

| 建模方式 | 适用场景 | 优点 | 缺点 | 典型示例 |
|---------|---------|------|------|---------|
| 外键关联 | 关联对象不变化或变化不影响业务 | 简单、实时 | 历史数据变化后查不到当时值 | 退款单关联用户id |
| 冗余字段 | 关联对象少、且只读展示用 | 查询快、不用联表 | 冗余存储、需同步 | 退款单存用户手机号用于通知 |
| 快照表 | 关联对象会变、且需要历史版本 | 完整保留当时上下文 | 存储大、需维护 | 退款时存订单快照 |
| 关联表 | 多对多关系、且需要独立管理 | 灵活、标准化 | 查询需联表 | 退款审批人历史记录 |

选择建议：**业务上必须知道的显式建模（外键或关联表）；只是展示用的冗余字段；会变化且需追踪的必须用快照。**

## 四、如何在项目中快速评审一套流程表设计

### 1. 先看能否回答四个问题

- 现在是什么状态？——主表没状态不合格
- 为什么变成这个状态？——查不到流转记录不可追踪
- 谁在什么时候做了什么？——没操作日志审计不完整
- 当时数据什么样？——没快照历史不可回放

### 2. 再看主表和流水表是否打架

常见问题：主表塞太多历史字段、流水表重复堆主表字段、状态和流水记录不一致。主表状态是“已通过”，流水最后一条是“待审核”，上线后必出问题。

主表负责当前真相，流水表负责变化轨迹，两者必须可互相验证。

### 3. 再看关联对象是否丢上下文

审批单只有申请单id，没有申请人、审批人、附件版本、触发来源，查数据会很痛苦。

关联对象原则：业务上必须知道的显式建模；只是展示用的冗余快照；会变化且需追踪的不能只靠外键。

### 4. 再看是否支持查询和统计

常用查询应有明确落点：当前列表查主表、流程轨迹查流转记录表、审计追踪查操作日志表、历史版本查快照表。

### 5. 实战演练：评审一个有缺陷的设计

```sql
CREATE TABLE refund (
    id BIGINT PRIMARY KEY,
    refund_no VARCHAR(32),
    order_id BIGINT,
    user_id BIGINT,
    amount DECIMAL(10,2),
    status INT,                          -- 0=待提交 1=审核中 2=通过 3=驳回 4=完成
    history TEXT,                        -- 用逗号分隔的状态变更记录
    operator VARCHAR(50),                -- 最新操作人
    operate_time DATETIME,               -- 最新操作时间
    note TEXT                            -- 最新备注
);
```

按四个问题检查：
1. **现在什么状态？** 主表有status字段，✅
2. **为什么变成这个状态？** history字段是逗号分隔的字符串，查不了具体原因，❌
3. **谁在什么时候做了什么？** 只存了最新一次操作，历史查不到，❌
4. **当时数据什么样？** 完全没快照，❌

**修正建议**：
- 增加流转记录表，记录每一次from→to
- 增加操作日志表，记录每一次人工操作
- 加快照表，在关键节点生成快照
- status加字典约束，不要用数字硬编码

## 五、形成自己的流程型建模检查清单

### 1. 建模前检查清单
- 主对象是什么、唯一标识是什么
- 状态有哪些、是否允许回退/撤回/重试
- 哪些动作会/不会改变状态
- 哪些关联对象必须保留、哪些字段需保留历史版本
- 哪些节点需要审批人/处理人/责任人、哪些操作需要审计日志

### 2. 建表时检查清单
- 主表是否只存当前态和核心字段
- 流转记录表是否记录from/to状态、能否还原完整节点路径
- 操作日志表能否定位到人、时间、入口
- 快照表能否回看关键时点数据、是否区分全量和增量、索引是否合理
- 关联对象是否有明确建模方式（外键/冗余/快照/关联表）
- 状态字段是否有枚举或状态机约束（建议用枚举表或数据库CHECK约束）
- 是否有唯一业务编号和幂等控制（唯一业务编号防重复创建，幂等控制确保同一动作不重复执行）
- 是否考虑异常终止、取消、退回、撤回

### 3. 上线前检查清单
- 流程走到一半挂了能否继续（是否有断点续传或重试机制）
- 重复提交是否产生重复流转（幂等控制）
- 审批人改了历史链路会不会丢（操作日志是否保留）
- 数据改了快照能否对上（快照与主表的一致性校验）
- 运营手工改状态日志能否查出（操作日志有无覆盖）
- 后台补单后主表和流水表能否一致（是否统一入口更新）

## 六、常见坑总结

- **过度抽象**：把主对象抽象成“流程实例”，查询复杂维护成本高。按业务对象建模，先解决80%。
- **忽略业务场景差异**：订单有金额校验和支付回调，审核有退回重填，预约有时间冲突。一套模板解决所有场景每个都用不好。
- **快照表当摆设**：建了没索引或内容不准。按`(biz_id, version)`或`(biz_id, snapshot_type, created_at)`设计索引。
- **状态字段与流转记录不一致**：人工修正状态没走流转记录表。必须统一状态变更入口。
- **操作日志和流转记录混用**：必须分开两张表各司其职。
- **状态枚举没约束**：推荐用枚举表或数据库CHECK约束，防止人工改库或bug产生非法状态。

## 结尾小结

这章方法论：
1. **从流程图识别主对象、节点、动作、结果、关联对象**
2. **按当前态、过程态、历史态、审计态分层**
3. **先做主表，再做流水表，最后补日志表和快照表**
4. **用四个问题快速评审设计**
5. **形成检查清单，避免每次从零开始**

新流程先问：这是谁的流程？哪些状态必须保存？哪些过程必须留痕？哪些历史必须回放？哪些操作必须审计？五件事想清楚，把**状态、流转、历史、审计、关联**拆得清楚，系统就稳了。
