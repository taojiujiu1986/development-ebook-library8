# 第1章 先别怕数据库：前端人为什么一定要懂一点

## 开篇：一个你肯定遇到过的场景

假设你在联调一个“新增用户”的表单。接口调通了，数据也提交成功了，可后端第二天跟你说：“你传的`userName`字段我收不到，数据库里叫`nickname`，你得改一下接口字段名。”

你改完字段名，第三天他又说：“状态这块我表里存的是`0、1、2`，但你页面上只给了我‘启用’和‘停用’，还有‘待审核’你没处理。”

这时候你心里是不是特想说：“我就写个页面，怎么这些事全落我头上了？”

这不是后端故意为难你，而是——**你每天都在碰数据库设计的结果**，只是你自己没意识到。

## 一、为什么前端总是被接口“卡脖子”？

### 你的页面不是在消费接口，而是在消费表结构

前端页面看起来是组件拼出来的，但组件不是凭空变出数据的。你写一个用户列表页，接口返回的`data`里有什么字段，页面才能展示什么字段。而接口里的字段，又来自数据库里那张`user`表。

这条链是这样的：

```
页面组件 → 接口返回结构 → 数据库表结构
```

- 你做“订单列表”，后端能返回哪些字段，取决于订单表里存了哪些字段。
- 你做“编辑用户资料”表单，哪些能改、哪些不能改，本质上是受存储结构约束的。
- 你点搜索，有些条件能搜、有些搜不动，背后往往是表里有没有这个可查询字段。

所以很多前端觉得“接口乱、字段不统一、联调返工多”，根子其实不在接口写得差，而在于**你对表结构没有基本的概念**，不知道哪些问题是表设计阶段就注定的。

## 二、一个最简单的映射：从页面组件到数据库实体

### 拿出你写过的任何一个“管理页”来拆

比如你写过一个“商品管理”页面，里面大概有这些组件：

- 列表表格（展示商品信息）
- 搜索区（按名称、价格、状态搜）
- 新增/编辑弹窗（表单）
- 详情抽屉（展示更多信息）

从前端看，这是 4 个组件；从数据视角看，它们全部围绕一个核心实体：**商品**。

那这个“商品”实体，有哪些稳定信息？

- 商品名称
- 商品价格
- 库存数量
- 商品状态（上架/下架）
- 创建时间
- 更新时间

这些东西，大概率会落到数据库的`product`表里，变成一个个字段。

而页面上那些“当前页码”“每页条数”“搜索关键字”，是页面状态，只在浏览器里活着，不会也不该存到数据库。

**一句话结论：页面组件再多，最终能落库的，永远是那个业务实体的核心特征。** 学会从组件里拆出“谁是实体”，你就算入门了。

## 三、看懂数据库能省多少事？

### 你至少能提前发现三件大事不对

**1. 数据口径不一致**

比如前端理解的“状态”只有“启用”和“停用”，后端数据库里还有“草稿”“审核中”“已归档”。联调时你传“1”表示启用，后端收到“1”却报错，因为你没传“0”后面的状态。

**2. 字段命名混乱**

同一个概念，页面里叫“昵称”，接口里叫`nickName`，数据库里叫`nickname`，另一个接口里又变成`alias`。这种混乱你联调时至少一半时间都在问“这个字段到底是不是那个字段”。

**3. 接口返回≠表结构**

数据库里可能分成`user`表和`user_profile`表两张表存储信息，但接口返回时，后端会把它们拼成一个对象直接给你用。所以你不能默认“接口字段就是数据库字段”，它们之间常常隔着组装层。

**懂一点数据库设计，本质上是在帮你判断“哪些变化会影响页面，哪些不会”。** 你知道了底层的存储逻辑，就能更快判断接口变更的影响范围。

## 四、怎么判断哪些字段该放数据库？一个简单标准

### 适合入库的字段，通常有这四个特征

- **稳定**：不会今天加一个、明天删一个
- **核心**：是这个业务实体必须拥有的数据
- **可查询**：以后大概率要搜索、筛选、排序
- **可复用**：不只是某个页面临时用一下

比如用户的手机号、昵称、状态，通常都适合放数据库。像“本次列表是否展开详情”这种 UI 状态，就没必要入库。**数据库不是前端 state 的备份区。**

### JSON 字段不是万能盒子

有些结构变化快、频繁增删的字段，比如商品规格配置、页面自定义配置，可以考虑用 JSON 存。它的优点是灵活，缺点是后续查询、统计、约束会更麻烦。

一个简单判断：**要稳定查询的，别塞 JSON；只是存一坨扩展信息的，可以塞 JSON。**

## 五、前端提交数据对表设计的影响

### 你提交的不是表单，而是业务意图

每次前端提交表单，实际上是在告诉后端：这个业务对象要怎么创建、怎么修改、怎么验证。

比如收货地址表单里有“省、市、区、详细地址、联系人、电话”。如果前端一直按这套结构提交，后端通常会拆成对应字段，便于查询和展示。如果前端提交的是一个完整地址字符串，后端可能只能先整体存，再想办法解析。

**字段命名要尽量统一。** 同一个概念不要换来换去，前端叫“手机号”，接口和数据库最好都围绕`phone`或`mobile`统一口径，别今天`phone`、明天`tel`。

## 结尾小结：你不是非要会建表，但你要看懂这条链

今天这一章，你先记住一句话就够了：**前端、接口、表结构是一条链，不是三个孤岛。**

从今天开始，你写页面时可以顺手多问自己四个问题：

1. 这个页面到底围绕哪个业务实体？
2. 这些字段哪些是稳定核心数据，哪些只是页面状态？
3. 接口返回和数据库存储是不是同一套结构？
4. 这个字段命名，前后端是不是在讲同一件事？

你不用一下子变成数据库专家，但你只要开始用前端视角去理解数据落地，数据库这件事就不会再那么吓人了。

下一章，我们就直接从你最常见的**页面组件**开始，一步一步拆给你看：一张表到底是怎么从一个列表页面长出来的。

# 第2章 前端数据和数据库数据：同一件事的两种说法

## 开篇引入：你看到的是“页面数据”，后端看到的是“表里的事实”

前端同学刚接触数据库，最容易卡住的不是SQL，而是认知差：  
**页面里拿到的是对象、数组、表单状态，数据库里到底是什么？**

老赵先给你一句最实用的话：**前端看到的是“能渲染、能交互的数据结构”，数据库保存的是“可追溯、可约束的业务事实”。**  
两者说的是同一件事，但站位不同。

比如“用户资料页”——前端有`userInfo`对象，接口返回`{ code, message, data }`，数据库里是一条`user`表记录。它们指向同一个人，但表达方式完全不同。前端关心页面怎么画、字段怎么展示；数据库关心记录是否唯一、能不能更新、有没有历史意义。

所以先把这三层关系捋清楚：**页面状态、接口返回、数据库记录，分别是什么。**

---

## 一、页面状态、接口返回、数据库记录：一条完整的数据流

### 1. 页面状态：像组件里的state，是临时的“快照”

页面状态就是组件里维护的变量：`loading`、`formData`、`list`、`selectedRow`、`pageNum`、`pageSize`……它们支撑当前页面渲染和交互，页面一刷新，状态就丢了。

比如商品列表页：`list`（当前页数据）、`total`（总数）、`loading`、`keyword`、`selectedIds`。这些都是页面状态，本质是**前端临时持有的业务数据副本**，会随着翻页、筛选、刷新、关闭而变化。

所以页面状态的核心要求不是“长期正确”，而是“当前好用”。

### 2. 接口返回：像Promise的resolve值，是“运输箱”里的数据

接口返回是后端打包后传给前端的结果，通常有统一外壳：

```json
{
  "code": 0,
  "message": "ok",
  "data": { "list": [], "total": 100 }
}
```

注意，接口返回不是数据库结构本身。它更像一个“运输箱”：外层是统一协议（成功、失败、提示），内层是业务数据（列表、详情、分页、统计）。前端一般不会原样渲染，而是再整理成组件更好用的状态。

### 3. 数据库记录：像store里的持久化数据，是“仓库里的原件”

数据库记录是一行一行真实保存的数据，关注的是**事实本身**——某个用户手机号是多少、某订单金额是多少、某条记录的创建时间是什么。数据库不关心页面怎么画，只关心这条事实能否稳定存下来、查出来、改得动。

可以这么理解：**页面状态是草稿，接口返回是快递包装，数据库记录是仓库里的原件。**

---

## 二、前端对象和数据库行记录的对应关系：不是简单的一一对应

### 1. 理想状态：一个对象对应一条记录

很多前端默认“接口里的一个对象 = 数据库里的一行”，这个理解**对一半**。比如用户详情`{ id: 1001, name: "老张", phone: "138xxxx", status: 1 }`，如果表设计清晰，大概率对应`user`表中的一行。

这种关系最适合用户信息、商品基础信息、订单主信息、文章详情、配置项——也就是“一个业务实体，能被一个主键标识”的场景。

### 2. 但不是所有对象都能直接等于一行

前端对象常常是“为了页面方便”拼出来的，数据库一行记录则是“为了事实和约束”存的。例如商品列表页的卡片对象：

```js
{
  id: 11, title: "机械键盘", coverUrl: "...",
  price: 399, stock: 20, categoryName: "外设", isHot: true
}
```

这里面至少有两类数据：
- **可直接存表的字段**：`id、title、coverUrl、price、stock、isHot`
- **更像展示结果的字段**：`categoryName`（可能来自分类表关联查询）

所以要记住：**前端对象是视图友好型，数据库行是存储严谨型。**

### 3. 页面列表对象通常比数据库记录更“胖”

前端一个列表项常包含基础字段、展示字段、状态文案、图标标记等。而数据库行通常只存**原始事实**——数据库存`status = 1`，前端显示“已上架”；数据库存`type = 2`，前端显示“限时活动”。

也就是说，**数据库保存原值，前端负责解释成界面语言。** 别把“显示结果”误认为“存储结果”，这是前端最常踩的坑。

---

## 三、为什么前端看到的是结构，数据库看到的是事实？

### 1. 前端的结构，是为了组织组件

前端拿到数据后要做列表渲染、表单回填、条件显示、按钮禁用、分页切换等。所以前端天然需要结构化数据：`list: []`、`formData: {}`、`pagination: { pageNum, pageSize, total }`。组件最怕数据散、结构乱。

### 2. 数据库的事实，是为了保证业务真实

数据库要保证记录是否真实存在、字段是否非空、手机号是否重复、金额是否为负、状态值是否合法。所以数据库更像“事实仓库”，一条记录对应一段业务事实，而不是页面展示结果。

### 3. 一个简单判断：能不能单独成立

判断一个字段要不要进数据库，可以问：**这个字段离开页面还能不能成立？**

- `userId`：能，是真实身份
- `createdAt`：能，是真实时间
- `categoryLabel`：不一定，可能只是展示名
- `canEdit`：通常不入库，是权限计算结果
- `fullNameText`：可能只是前端拼接展示

这就是“结构”和“事实”的分界线。**前端做结构，数据库存事实，中间靠接口翻译。**

---

## 四、一份数据在前后端之间如何流转？——以“编辑个人资料”为例

### 1. 从页面组件开始：表单是一份“待提交状态”

前端页面有输入框、单选框、开关、保存按钮，这些字段汇总到`formData`：

```js
{ name: "老赵", phone: "138xxxx", email: "zhao@example.com", gender: 1, isPublic: true }
```

这是**页面状态**，特点是可编辑、可撤销、可校验。

### 2. 提交给接口：前端提交的结构会影响表设计

点“保存”时，前端提交`formData`。这一步很关键——**前端提交什么，往往会反向影响后端表怎么设计**。

比如“商品发布”表单有基本信息、规格信息、富文本描述、图片、标签数组。后端要判断哪些字段是核心事实（独立列），哪些是可变扩展（JSON），哪些是多对多（拆表）。所以前端提交的结构不只传参形式，它直接影响表设计思路。

### 3. 后端落库：接口字段不等于表字段

接口里叫`userName`，表里叫`name`；接口里叫`avatarUrl`，表里叫`avatar`；接口里叫`isEnabled`，表里叫`status`。这都正常——接口给前端用，表给存储用，命名和粒度可以不同，但要能翻译。

前端最好养成习惯：**不要默认接口字段就是表字段。**

### 4. 再返回给前端：数据库记录会被“再加工”

查询数据库后，后端通常不会直接把表行原样吐给前端，而是字段重命名、状态值转文案、关联表信息拼接、分页结构包装、安全字段脱敏。比如数据库存`status = 1`，返回时带上`statusText = "已启用"`，这样前端少写判断。

所以前端拿到的接口数据，是**面向页面消费的数据模型**，不是“仓库里的毛坯”。

---

## 五、分页列表背后的表设计理解：列表不是表

### 1. 列表页只是查询结果，不等于物理表结构

例如订单列表有订单号、用户名、手机号、金额、状态、下单时间——你看到的是表格，但数据库里可能是`order`表、`user`表、`order_item`表的拼接结果。列表页是查询结果，不是表本身。

### 2. 列表字段多，不代表表就该大杂烩

要区分：
- **事实字段**：订单金额、支付状态、创建时间
- **关联字段**：用户昵称、商品名、分类名
- **计算字段**：是否超时、是否可退款

前两类有时需拆表或关联查询，后两类一般不直接存。计算字段更适合后端现算或前端展示时现算，不要为了省事硬塞进库里。

### 3. 分页的本质：前端看切片，数据库管全集

前端看到的是“一屏数据”，后端处理的是“仓库里的全体记录”。这也是接口里常见`list + total`的原因——前端需要“切片结果 + 总量信息”。

---

## 六、接口字段与表字段命名统一：数据口径的翻译规则

### 1. 一个字段最好有稳定口径

团队里`userName`、`username`、`name`、`nickName`不统一时，前端到处做映射，后端越写越乱。字段命名统一的意义不只是好看，是降低沟通成本。

### 2. 接口名和表字段名不一致也没关系，但要可翻译

接口叫`avatarUrl`，表叫`avatar`，完全没问题——关键是团队知道它们怎么对应，别一个字段改三遍名字。

### 3. 前端最好维护自己的字段视图

如果接口返回字段和页面用字段不一致，前端可以在请求层做一层转换（如`status`转`statusText`、`create_time`映射为`createdAt`）。**统一命名的目标不是强行统一数据库，而是让数据在团队里少拐弯。**

---

## 结尾小结：先学会翻译，再谈设计

理解数据库设计的第一步，不是背表名，而是学会“翻译”：
- 把**页面状态**翻译成临时交互数据
- 把**接口返回**翻译成面向页面的消费结构
- 把**数据库记录**翻译成可约束、可追溯的业务事实

把这三层分清，后面看页面组件拆实体、表单字段对应数据库字段、哪些字段该入库、JSON适用场景、前后端数据口径统一，就不会虚了。

### 检查清单

看到接口数据时，快速问自己：

1. 这是页面状态，还是持久化事实？
2. 这个字段是表里真有，还是后端拼出来的？
3. 这个对象能不能直接对应一条记录？
4. 列表里的展示字段，哪些只是显示结果？
5. 提交表单时，哪些字段该进库，哪些只是前端临时状态？
6. 接口字段和表字段的名字，团队有没有统一口径？

你能回答这些问题，说明你已经开始用前端的脑子理解数据库了。真正的数据库设计，不是先从表开始，而是先从**业务怎么被页面表达出来**开始。

# 第3章 从页面组件拆实体：一个页面到底对应几张表

前端同学刚接触数据库设计时，最容易踩的坑就是：**看到一个页面，就默认背后只要一张表**。这很像做前端时，看到一个组件就以为它只对应一个接口。实际上，**页面是展示层，表是存储层，中间还隔着业务逻辑层**。一个页面里常常同时有主信息、子列表、状态、历史记录、附件、权限等内容，它们通常不属于同一个数据对象。

这章我们就从前端视角，学会反推数据实体：一个页面到底该拆成几张表，哪些是主实体，哪些是附属实体，哪些字段该入库，哪些只是前端展示态。

## 一、一个页面不等于一张表，组件也不等于字段集合

### 1. 页面是“组合视图”，表是“持久化对象”

前端页面通常由筛选区、列表区、详情区、表单区、评论、日志、附件等模块组成。用户看到的是一个页面，但数据上可能是多个对象拼出来的。

数据库表关注的是：**哪些数据需要长期保存、如何唯一标识、彼此如何关联、如何查询和更新**。所以，**页面模块划分 ≠ 表划分**。组件是 UI 结构，表是业务实体。

你可以把它理解成前端里的“页面状态”和“服务端数据”的区别：搜索框输入值、弹窗开关、标签页切换，这些是交互态，不该入库。

### 2. 组件不是字段集合

前端很容易把一个表单组件想成“字段排排坐”，于是觉得这些字段就该放同一张表，但不一定。

比如“商品编辑页”里有：

- 基本信息：名称、类目、价格、封面图
- 规格信息：SKU 列表、库存、条码
- 营销信息：折扣、推荐位
- 发布状态：草稿、上架、下架

它们虽然在同一页，但数据粒度不同。**基本信息**像主表，**SKU 列表**像子表，**营销信息**可能是扩展表，**发布状态**则可能是状态字段或状态记录。

### 3. 判断标准：看是否独立变化

一个页面区域如果能独立新增、编辑、删除、查询，或者有自己的生命周期，那它大概率不只是主表里的一个字段。反过来，标题、创建人、创建时间、当前状态这类跟主对象一起走的信息，通常适合放在主实体里。

这和前端判断“要不要单独抽 store”很像：能被多个地方复用、能独立变化、生命周期不同的状态，值得单拎出来。数据库实体拆分也是同理。

---

## 二、拿一个典型页面拆给你看：订单详情页怎么分

光讲原则不够，咱们来用一个前端很熟的页面做完整拆解：**订单管理页**。你在后台系统里通常会看到这几块：

### 1. 筛选区：不是实体，是查询条件

订单列表上方一般有筛选区：

- 订单号
- 用户名
- 订单状态
- 下单时间范围
- 支付方式

这块很像前端搜索栏的 state。它的作用是发起查询，不是保存业务事实。  
所以，筛选区里的字段，**一般不直接对应数据库字段**，最多对应查询参数和索引字段。

这里有个关键点：**查询条件可以映射表字段，但不等于表字段本身。**  
比如“时间范围”是 `startTime`、`endTime` 两个参数，数据库里不一定有这两个字段，它只是拿来过滤 `create_time`。

### 2. 列表区：主实体的摘要面

分页列表、搜索、排序、批量操作，通常对应的是**主表的摘要查询**：

- 只取少量展示字段
- 不会把所有关联数据一次带回
- 依赖索引支持筛选和排序
- 追求快和够看

比如“订单列表”展示订单号、用户名、金额、状态、下单时间，这不等于订单全量数据。商品明细、收货地址、支付记录一般不会直接塞进列表接口。

所以，**列表页面是主实体的投影，不是完整内容**。列表接口只负责“看一眼”，不是“看全套”。

### 3. 详情区：主实体 + 关联实体的拼装结果

详情页往往是组合视图。比如“订单详情”里会有：

- 订单基础信息
- 收货信息
- 商品明细
- 支付信息
- 发货记录
- 操作日志

这些内容通常来自多张表：订单主表、订单明细表、支付表、发货表、日志表。  
所以要记住：**接口返回结构 ≠ 表结构**。接口可以为了前端方便，把多个表的数据拼成一个对象；表结构则要尽量规范，便于维护。

接口返回更像一个 **DTO**，是“给页面用的结果包”；数据库表更像“原始数据仓库”。DTO 可以把多个对象揉在一起，表不行，表要考虑长期存储和后续维护。

### 4. 表单区：决定写入边界的地方

表单会直接影响入库结构，所以关键不是“输入框放哪儿”，而是：

- 它属于哪个实体？
- 它是创建时就有，还是后续补充？
- 它是固定字段，还是可扩展字段？
- 它是主对象属性，还是关联对象属性？

比如“用户资料表单”里有昵称、手机号、性别、地址、爱好标签、头像、收货地址。这里面，昵称、手机号、性别可能进用户主表；头像可能在扩展表；收货地址通常不该直接塞进用户主表，因为它往往是一人多地址；爱好标签如果是多个值，也要考虑独立表或 JSON。

表单的意义不是把所有输入都收起来，而是帮你暴露：**哪些数据应该落到同一个实体，哪些需要拆出去**。

---

## 三、如何从页面模块识别主实体和附属实体

### 1. 先找主实体

主实体通常满足三个特征：

- 页面标题围绕它命名
- 列表、详情、编辑都围绕它展开
- 它有独立编号或唯一标识

比如：

- 商品管理页的主实体是商品
- 订单管理页的主实体是订单
- 客户管理页的主实体是客户
- 文章管理页的主实体是文章

主实体就是页面的核心，其他模块都围绕它派生。

### 2. 再找附属实体

附属实体通常是：

- 明细项：订单商品、发票明细、费用项
- 扩展信息：商品参数、用户扩展资料
- 记录类：操作日志、支付记录、浏览记录
- 关系类：标签、权限、角色、收藏
- 文件类：附件、图片、视频

判断它是不是附属实体，就看它能不能单独变化。如果它有自己的增删改查，或者数量不止一个，就别把它当普通字段硬塞进主表。

### 3. 关系比字段更重要

页面字段很多时，核心往往不是字段多，而是对象之间有关系。常见关系有三种：

- 一对一：用户与用户扩展资料
- 一对多：订单与订单明细
- 多对多：文章与标签、用户与角色

前端可以把它理解成：

- 一对一：基础信息 + 扩展配置
- 一对多：列表嵌套子列表
- 多对多：多选组件背后挂一张关系表

只要关系复杂，通常就不可能只靠一张表撑住。

---

## 四、从组件拆实体，就像从页面拆子组件

如果你做过前端组件拆分，就会发现这事儿和数据库拆实体很像。

### 1. 父组件像主实体，子组件像附属实体

比如一个“订单详情组件”：

- 父组件负责订单基础信息和页面整体布局
- 子组件 A 负责商品明细列表
- 子组件 B 负责物流信息
- 子组件 C 负责支付信息

前端拆组件时，会考虑数据从哪来、谁负责展示、谁负责交互。  
数据库拆实体时，也是在考虑：

- 谁是主对象
- 谁是附属对象
- 谁单独存
- 谁通过关系表关联

你可以把“组件树”理解成“数据结构树”的前端投影。

### 2. 子组件如果能独立增删改，就该警惕单表硬塞

比如 SKU 编辑器、地址列表编辑器、发票明细编辑器，这些都是典型的子组件。  
如果子组件支持：

- 动态新增多行
- 单行删除
- 单行编辑
- 单行校验

那它后面多半不是一个普通字段，而是一个子表或者关联表。  
这就是前端视角下拆实体最实用的判断法：**能不能像数组一样管理，决定了它能不能像字段一样存。**

### 3. 数据流也能帮你判断边界

前端里常说 props、emit、store、local state。数据库拆分时也可以借这个思路：

- **本地 state**：页面临时状态，不入库
- **props**：从主对象传给子组件展示的摘要信息
- **store**：多个模块共享的核心数据
- **服务端数据**：最终要持久化的业务实体

当一个字段只服务于某个弹窗、某个步骤条、某个选择器中间过程，那大概率只是前端状态。  
当一个字段需要被多个页面复用、被列表查询、被详情页回显，那它更像数据库实体里的正式字段。

## 五、什么情况下一个页面会拆成多张表

### 1. 有重复数据时，考虑拆表

如果页面里有大量重复字段，比如每个订单都带一份用户地址、商品快照、支付信息，就要小心：有些数据是历史快照，有些是可复用主数据，有些则会频繁变化，不适合冗余到主表里。

比如订单里的收货地址，通常要保存下单时的快照，不能只引用用户当前地址，否则用户改了地址，历史订单也会跟着变。

### 2. 有一对多关系时，通常要拆表

如果页面上有一个区域可以动态增删多行，比如 SKU 列表、收货地址列表、课程章节、发票明细、题目选项，这种结构通常不适合全塞在主表一个字段里。大多数情况下，会拆成主表 + 明细表。

一对多的数据本质上就是“一个主对象带一组子对象”，和前端里的数组渲染很像。前端可以渲染成 list，但后端存储通常要单独建子表，方便增删改查。

### 3. 有独立生命周期时，应该拆表

比如文章和评论：

- 文章可独立发布
- 评论可独立新增、删除、审核
- 评论数量可能远超文章主体字段
- 评论还可能继续扩展点赞、举报、楼中楼

这时评论就是独立实体，不该塞进文章主表。附件、操作日志、支付流水、审批记录也一样，应该独立建表。

### 4. 有查询性能要求时，也会拆表

如果所有数据都塞进一张大表：

- 列表查询会慢
- 更新容易影响大字段
- 无关信息也被一起读出
- 后续扩展会越来越痛

所以拆表不只是“好看”，也是为了查询和维护更稳。可以把它类比成前端拆包和按需加载：不是所有代码都要首屏一次性加载完，数据也不是所有内容都要一股脑塞进一张表。

## 六、哪些字段适合放数据库，哪些别硬塞

这一节是前端同学最容易一把抓错的地方，咱们直接说结论。

### 1. 适合放数据库的字段

通常满足这些条件的，才值得入库：

- 是业务事实，不是临时状态
- 需要长期保存
- 需要查询、排序、过滤
- 会被别的页面或接口复用
- 需要参与统计、关联、审核

比如订单号、用户 ID、商品名称快照、创建时间、审核状态，这些都很像正式数据，应该入库。

### 2. 不太适合直接入库的字段

下面这些多数是前端临时态：

- 弹窗开关
- 表单校验提示
- 搜索条件的中间态
- 上传进度
- 页面 Tab 当前选中项
- 选择器打开/关闭状态

这些东西跟组件生命周期绑定得很紧，刷新页面就没了，没必要让数据库替它记忆。

### 3. 前端提交数据，会倒逼表设计

很多时候不是先有表，再有页面，而是页面表单先出来了，后端再反推表设计。

比如前端表单里出现了：

- 可多选标签
- 动态增删明细
- 富文本内容
- 结构不固定的扩展项

后端就得想：这几个字段是分开存？还是做关联表？还是放 JSON？还是加扩展表？

所以前端提交的数据结构，实际上会影响表结构。  
你前端一旦把“一个字段”做成“可重复数组”，后端多半就不能再把它当成一个普通列。

### 4. JSON 字段不是万能桶

JSON 不是不能用，但不是所有东西都适合塞进去。  
适合 JSON 的场景通常是：

- 结构不稳定，未来可能变
- 字段不固定，扩展频繁
- 查询要求不高
- 主要是回显，不是精细筛选

不适合只放 JSON 的场景通常是：

- 要频繁按字段筛选
- 要做排序、统计、关联
- 要参与权限判断
- 这个字段是业务核心

简单说：**JSON 更像“扩展插槽”，不是“业务主干”。**

## 七、前后端协作里，字段命名和口径要统一

这一块虽然不是本章主线，但你拆实体时一定会碰到。

### 1. 接口字段名和表字段名不必完全一样，但语义必须一致

接口更偏前端语义，表字段更偏存储规范。两边名字可以不同，但意思不能乱。

比如：

- 接口叫 `status`，表里也叫 `status`
- 接口叫 `state`，表里叫 `order_status`

都可以，但前提是团队先说好：这个字段到底表示什么，取值有哪些，前端展示什么文案，后端怎么落库。

### 2. 别让一个字段在前后端之间“变脸”

比如前端叫“状态”，后端一会儿说“state”，一会儿说“flag”，一会儿又拆成“是否有效”和“审核中”。  
这种情况最容易让页面开发和数据库设计同时乱套。

正确姿势是：**一个业务概念，对应一个统一口径；一个口径，可以在接口层和表层做不同命名，但不能做不同含义。**

### 3. 详情接口是页面友好结构，不是表复刻

再强调一遍：  
接口返回结构往往是为了页面舒服，不是为了数据库舒服。

它可以把：

- 主实体
- 子列表
- 统计信息
- 状态文案
- 关联对象摘要

都拼在一起。  
但表结构不行，表结构要尽量稳定、清晰、可维护。

---

## 八、结尾小结：看到一个页面，先问这三个问题

这章你别记一堆术语，记住一个顺序就行。

### 1. 先问：谁是主数据？

页面围绕谁展开？  
订单、商品、文章、客户、课程，先把主角找出来。

### 2. 再问：哪些是展示数据，哪些是业务数据？

- 展示数据：标签文案、状态文案、筛选条件、弹窗状态
- 业务数据：名称、价格、数量、地址、明细、关系

展示数据不一定入库，业务数据才是拆实体的重点。

### 3. 最后问：哪些内容可能要拆表？

重点盯这几类：

- 能独立增删改的模块
- 一对多的数组结构
- 多对多的关系选择
- 有历史快照需求的数据
- 会被频繁查询和统计的数据

---

## 本章行动清单

下次你看到一个业务页面时，先按下面这几步过一遍：

- 先找主实体，确认页面到底围着谁转
- 把筛选区、列表区、详情区、表单区分开看
- 标出哪些是临时状态，哪些是业务事实
- 看有没有数组型输入、子列表、动态明细
- 判断有没有一对一、一对多、多对多关系
- 再决定是主表、子表、关联表，还是 JSON 扩展字段
- 最后统一接口命名和表字段口径，别让前后端各说各话

把这个套路练熟，你以后再看页面，就不会只看到“几个输入框、几个表格、几个弹窗”。  
你会开始看到它背后的数据对象边界，这就是前端读数据库设计最值钱的第一步。

# 第4章 从表单字段到数据库字段：输入框背后怎么落表

## 开篇引入

前端对表单太熟了：新增页面，一堆输入框，点“提交”，字段发给接口。  
但数据库不认识“输入框”，它只认识**字段、类型、约束、关系**。

核心问题：**页面上的每一个输入项，最后要不要、能不能、应不应该落到某个表字段里。**  
如果表单是“数据收集器”，数据库就是“仓库结构设计”。

这一章就讲清楚完整链路：**表单项 → 提交参数 → 数据库字段**。重点对比前端校验和数据库约束的区别，以及输入内容如何影响字段长度和类型。

先立住观念：**前端表单往往就是数据库设计的入口。**

---

## 一、表单字段如何映射成数据库字段？

### 1.1 先看这个表单到底在“收什么”

表单设计第一步：**这个页面要采集的是“人”、“商品”、“订单”还是“某个流程中的一条记录”？**  
这就是数据库设计里的“拆实体”。

比如“新增商品”表单，前端眼里是一个表单，数据库眼里对应 `product` 表：

- 表单字段：商品名称、商品编号、类目、价格、库存、描述、上架状态、封面图
- 数据库字段：`name`、`sku`、`category_id`、`price`、`stock`、`description`、`status`、`cover_url`

理解方式：**表单字段 = 页面上让用户输入的内容，数据库字段 = 系统长期保存的内容。**

注意：不是每个表单字段都必须落库。像“确认密码”、“验证码”、“临时搜索条件”只是辅助状态，通常不进业务表。

### 1.2 一个字段是否落库，问三个问题

1. **是不是业务事实的一部分？**（订单金额、收货地址要存）
2. **未来是否还要被查询或展示？**（列表页、详情页、统计报表要用就入库）
3. **是否可以重新计算出来？**（能算出来的不直接存，如“是否超时”、“折扣后价格”）

例子：  
- “收货人姓名”是事实，要存  
- “确认密码”防手滑，不存  
- “搜索框关键字”不存业务表

### 1.3 页面组件到表字段的常见映射

- `Input`：短文本（姓名、标题、编号）
- `Textarea`：长文本（备注、描述）
- `Select`：枚举值（状态、类型、级别）
- `DatePicker`：日期时间
- `Upload`：文件路径、图片地址
- `Switch`：布尔值或状态值
- `CheckboxGroup`/`RadioGroup`：单选/多选语义字段

关键：**组件是界面形态，字段是数据语义。**  
不要因为页面上是下拉框就默认存字符串，也不要因为文本框就默认 `varchar(255)`。  
比如“商品状态”用 `Select`，数据库最好存状态码 `0/1/2`，不要存中文描述，因为码更适合筛选、排序和统计。

---

## 二、必填、可选、默认值的表设计体现

### 2.1 必填字段：前端校验 + 数据库约束双保险

表单红星号 ≠ 只校验前端。  
数据库里体现为：`NOT NULL`、合理默认值，必要时加唯一约束、外键约束。

用户注册表：`username` 必填 `NOT NULL`，`password_hash` 必填 `NOT NULL`，`email` 如果要求邮箱登录也应必填。

**前端校验让用户少走弯路，数据库约束防止“漏网之鱼”**——接口不只前端调用，脚本、后台、导入工具都可能绕过。

### 2.2 可选字段：业务允许为空

头像、备注、次要联系人等，数据库允许 `NULL` 或给默认空值。  
分清：  
- **“空”** = 业务上没值  
- **“默认值”** = 系统替你填了一个值  

订单 `status` 默认 `pending` 是默认值，备注用户不填就是空。

### 2.3 默认值：减少提交负担，保证数据一致

价值：  
- 减少前端必须提交的字段  
- 保证记录创建后状态一致  
- 避免漏传导致脏数据  

商品上架页：`status` 默认 `0`（草稿），`is_deleted` 默认 `0`，`created_at`/`updated_at` 由系统自动填充。  
理解成“表单没显示，但系统自动补齐的后台默认状态”。

### 2.4 常见误区：把前端默认值当数据库默认值

前端设初始值只对当前页面生效。接口直调、批量导入时默认值就没了。  
三层各自独立：  
- 页面初始值：服务交互  
- 接口默认补齐：服务业务  
- 数据库默认值：守数据底线

---

## 三、前端校验和数据库约束：谁拦截，谁兜底？

### 3.1 前端校验职责：尽早告诉用户错误

快、直观、体验好。手机号格式不对、密码长度不足、必填项没填——前端先拦住。  
目标：**减少无效提交，提高交互效率。**

### 3.2 数据库约束职责：保证数据底线

兜底作用：  
- `NOT NULL`：不能为空  
- `UNIQUE`：不能重复  
- `CHECK`：必须满足范围规则  
- 外键：关联对象必须存在  

手机号若业务上要求唯一，数据库最好也加唯一约束。否则并发请求、接口绕过仍可能产生重复数据。

### 3.3 关系：前端负责体验，数据库负责安全

两道门：  
- **前端校验**：门口保安，先看一眼  
- **数据库约束**：最后闸机，再确认一次  

两边都做才是最佳方案。

### 3.4 常见误区：只做前端校验

一旦接口脚本调用、多人成交、旧版本页面、后台导入，就容易出事。  
记住：**前端校验不是数据库设计的替代品，只是第一层防线。**

---

## 四、表单提交数据如何影响字段类型和长度设计？

### 4.1 先看用户怎么填，再定字段

不是先拍脑袋 `varchar(255)`，而是看输入特征：  
- 最长多长？是否纯数字？有没有小数？  
- 是否有国际化字符？是否可能增长为长文本？  

“商品名称”适合短文本，“商品详情”是富文本，不适合塞进短字符串。

### 4.2 字段类型匹配提交内容

价格不要存字符串，时间存时间类型，状态存枚举值或数字码。  
页面“￥199.00”传数值 `199.00`，数据库也存数值，别把货币符号存进去。

### 4.3 长度不是越大越好

影响：存储效率、索引效果、后续扩展成本、数据一致性。  
业务限制20字以内，就别给夸张长度。页面输入限制和字段长度最好同步。

### 4.4 前端提交格式反作用于字段设计

提交单个值还是数组？提交ID还是对象？提交URL还是文件元信息？日期字符串还是时间戳？

“标签”字段：  
- 单选 → 单值  
- 多选 → 数组、关联表或JSON  
- 按标签检索 → JSON不如拆表  

**表单提交结构直接影响数据库是简单存值还是需要拆关系。**

---

## 五、JSON字段适用场景

### 5.1 适合“变化快、结构不稳定”的数据

配置项、自定义表单、扩展属性、第三方回传参数、临时复杂筛选条件。  
比如页面装修配置，今天加按钮颜色，明天加弹窗开关，JSON很灵活。

### 5.2 JSON不是万能桶

**适合装“不好定型”的东西，不适合装“核心业务字段”。**  
如果一个字段常用作：搜索、排序、统计、唯一校验、联表查询，就别塞进JSON。

订单里的收货人电话要经常按手机号查，就不能放JSON，应独立字段。

### 5.3 判断口诀

- **稳定、常查、强约束** → 单独字段  
- **变化快、少查询、弱约束** → JSON  
- **多对多、可独立管理** → 拆关联表  

这不是非黑即白，而是取舍。

---

## 六、前端和数据库的“口径”对齐

### 6.1 页面展示口径 vs 数据库原始口径

页面显示：“已上架”、“3小时前”、“￥99.00”  
数据库存：`status = 1`、`created_at = 2025-01-01 10:20:00`、`price = 99`  

前端展示是转换结果，数据库存更基础、适合计算的原始数据。

### 6.2 接口返回结构 ≠ 表结构

接口可能返回：
```json
{
  "id": 1,
  "name": "iPhone",
  "statusText": "已上架",
  "createdAtText": "3小时前"
}
```
数据库未必有这些字段，可能是后端拼的或前端加工的。  
接口“面向页面”，表结构“面向存储和约束”，两者天然不同。

### 6.3 表单提交口径必须统一

口径不统一的后果：  
- 一个叫“手机号”，另一个叫“联系方式”  
- 有的传 `userId`，有的传 `uid`  
- 状态用 `0/1`，有的用 `true/false`  
- 日期传字符串，有的传时间戳  

前端、后端、产品最好一开始对齐：字段名、必填条件、默认值、类型、是否允许重复、是否保存历史值。

---

## 结尾小结

一句话记住：**表单字段不是页面里的孤立输入框，它是未来数据库字段的候选人。**

设计顺序：
1. 页面要收集什么业务事实  
2. 哪些字段入库，哪些临时交互  
3. 区分必填、可选、默认值  
4. 决定字段类型、长度、约束  
5. 是否需要JSON、关联表或单独拆字段  

实操清单：
- 输入项是不是业务核心数据？  
- 列表页、详情页、统计会不会用到？  
- 展示值还是原始值？  
- 能否被其他字段推导？  
- 是否需要唯一、非空、默认值？  
- 数据变化快不快，要不要JSON？  
- 接口提交格式和数据库字段类型匹配吗？

把这几个问题想清楚，表单和数据库之间那层“看不懂的墙”就会薄很多。

# 第5章 分页列表背后的表设计：你看到的是表格，后端看到的是查询模型

## 开篇引入：为什么列表页最容易把数据库问题“照出来”

前端最熟的页面，不是详情页，而是**列表页**。它带着分页、筛选、搜索、排序、状态、操作按钮，就是业务日常的缩影。你看它像一张表格，后端看它却是一套查询模型。

点“按创建时间倒序”，接口开始跑；加“名称搜索”，全表扫描就出来了；补“状态筛选”，后端可能要先看索引；再来“负责人+部门+标签”组合条件，查询复杂度立刻上去。

原因很简单：**前端看到的是展示表格，后端处理的是查询模型**。一个列表页背后要解决的是：查哪张主表、要不要连关联表、哪些字段适合筛选/排序/搜索、分页怎么切、返回的是展示结果还是查询中间态。

所以列表页不是“把数据渲染出来”这么简单，它其实在检验系统的数据结构顺不顺。

---

## 一、列表页为什么最能暴露表设计问题

### 1. 列表页不是“展示”，而是“检索结果”

从数据库角度看，列表页本质上是一次受约束的查询。页面上的每一列，可能来自主表、关联表、计算字段或冗余展示字段；每一个筛选条件，都在告诉后端：这个字段将来会被高频查询。

所以列表页在给数据库“提需求”：这列要不要经常查？这个条件会不会常用？这个字段是不是稳定枚举？这个排序是不是固定方向？搜索是精确查还是模糊查？

表结构顺手的系统，列表查询会很自然；表结构别扭的系统，列表页就像在拼接口。

**前端类比**：就像定义 `columns` 配置时，只写展示列渲染很简单；但加了“列筛选”“排序”“搜索配置”，就需要额外的 `filterConfig`、`sortConfig`、`searchConfig`。数据库表设计也是同理——筛选、排序、搜索这些“配置”，就是表结构和索引设计的源头。

比如订单列表常见字段：订单号、下单用户、支付状态、订单金额、创建时间。如果数据归属清楚，接口就是按条件查、按字段返回。但如果“支付状态”要从支付表算，“下单用户”要连用户表，“订单金额”还要汇总明细表，普通列表就会变成综合题。

### 2. 一个好表结构，能让列表页像写组件一样自然

前端写组件最怕数据源乱、字段乱、状态乱。数据库表设计也一样。结构清楚时，列表页就像写一个干净的组件：
- 主列表字段直接来自主表
- 常用筛选字段归属明确
- 状态字段是统一枚举
- 排序字段稳定
- 展示字段和存储字段有清晰映射

反过来，一张列表要查多张表、一个筛选条件要翻JSON、一个状态要转三次，前端看到的是页面卡顿，后端看到的是查询压力。

所以看列表页时，顺手想一遍：核心数据是谁？哪些字段是主角？哪些只是展示？哪些是高频查询条件？哪些字段其实应该去别的表找？一旦开始这样想，就已经从页面视角往数据模型视角走了。

---

## 二、筛选条件、排序字段、搜索字段如何影响表结构

### 1. 筛选条件：谁经常被筛，谁就该被认真对待

筛选条件是业务常用维度。**前端类比**：`columns`里加`filter: true`，意味着需要配置筛选器。数据库表设计也一样——筛选条件就是给字段打上“高频查询”标记。

常见筛选条件：状态（启用/停用/草稿/已发布）、时间（创建/更新/发布时间）、归属（创建人/负责人/部门）、分类（类型/标签/渠道）、业务标识（订单号/用户ID/商品编码）。

这些字段如果经常被筛，设计时要考虑是否：放在主表、方便直接建索引、值域稳定、适合组合查询。

判断字段适不适合做筛选条件，看三点：
1. **高频**：业务上是不是常查
2. **稳定**：值会不会频繁变
3. **低歧义**：字段含义是否清楚

“状态”“创建时间”适合筛选，“备注内容”“富文本摘要”通常不适合。

### 2. 排序字段：能稳定排序的字段，更适合做列表主轴

常见排序字段：创建时间、更新时间、金额、优先级、排序号。特点：**顺序明确**，**适合单列或少量组合排序**。

**前端类比**：像表格组件里的`sorter: true`，需要指定排序字段。如果值嵌套在JSON里或是多选集合，排序就无法高效稳定。

数据库最擅长结构化、稳定、可比较的字段。排序需求最好在设计阶段说清楚：默认按什么排？是否支持切换？排序字段是否固定？是否允许多字段组合？

比如任务列表默认按“优先级+创建时间”排，这种规则应明确写进接口约定，否则前后端容易对不上。

### 3. 搜索字段：能不能搜，决定了字段存储方式

搜索字段，尤其是模糊搜索，是列表页最拖慢性能的地方。需分清：**精确查**(=)、**模糊查**(like)、**全文检索**（按词条或内容索引查）。

订单号、用户ID适合精确查；名称、标题适合搜索；大段备注、富文本正文不该直接搜。

**前端类比**：写搜索组件时，会选择`exactMatch`还是`fuzzyMatch`。如果字段内容很长（如备注），应考虑用“摘要字段”代替“全文搜索”。

如果字段未来可能被搜索，提前考虑：长度是否过长？是否需要拆字段？是否需要摘要字段（如截取前100字）？是否需要全文检索方案（如ElasticSearch）？是否能接受搜索成本？

一句话：**搜索不是“加个输入框”那么简单，它会反推字段设计。**

---

## 三、分页接口返回结构与数据库查询结果的区别

### 1. 接口返回的是“前端可用结构”，不是数据库原样

数据库表存数据，强调规范、可维护、可查询、可约束。接口返回结构给前端用，强调好渲染、好绑定、好理解、好展示。

分页接口通常长这样：
```json
{
  "list": [],
  "page": 1,
  "pageSize": 20,
  "total": 128
}
```
有时还带`hasNext`、`hasPrev`、`summary`、`extra`。这说明接口返回的是**UI友好型结果**，不是数据库原始行。

**前端类比**：可以理解成前端里的`view model`——数据库原始数据是原料，接口返回是整理后的成品。

### 2. 数据库查询结果更像“中间态”，接口返回更像“最终稿”

数据库查出来的数据，通常还要加工：字段重命名(`created_at`→`createdAt`)、枚举翻译(`status=1`→“已启用”)、时间格式化、状态文案映射、关联字段拼装(`owner_id`→`ownerName`)、权限字段裁剪。

比如数据库里：`status=1`、`created_at=1712345678`、`owner_id=10086`；接口返回：`statusText="已启用"`、`createdAt="2024-04-05 10:11:18"`、`ownerName="老赵"`。

最容易出问题的是前后端默认“对方应该懂”。前端觉得`status=1`显示启用，后端觉得1只是存储值；前端觉得`type=2`是企业用户，后端却定义成VIP会员。接口最好把存储值和展示值分开。

### 3. 分页不是把数据切成几页这么简单

分页还涉及：怎么定位起点（`OFFSET`还是`cursor`）？总数是否每次都查（有些场景用`hasNext`代替）？排序字段是否稳定（不稳定会导致重复或丢失）？数据新增后分页是否漂移？

这就是为什么有些列表会出现重复、丢数据、顺序乱掉。分页必须建立在**稳定排序**上。

**前端类比**：就像写虚拟滚动列表时，需要保证`item`唯一且有序。数据不稳定就会出现“跳位”问题。

前端对分页接口时，最好确认：默认排序字段是什么？排序是否唯一（是否加`id`作为第二排序）？翻页时是否可能重复？新增数据后是否影响当前页顺序？很多“偶现分页错乱”，本质是排序和分页规则没说清。

---

## 四、列表性能为什么和字段设计、索引设计有关

### 1. 你看到的是卡顿，后端看到的是查询成本

列表页慢，前端感受到：白屏、loading久、翻页卡顿、筛选没响应、搜索慢半拍。后端看到的：条件太多、排序字段没准备好、模糊搜索太重、关联查询太多、索引不匹配、返回字段太大。

列表性能是前端交互需求反推表设计的结果。多加一个筛选项，后端就多一条查询路径；把字段从下拉改成搜索框，数据库就要面对更重的匹配成本。

### 2. 哪些字段最值得考虑索引

**经常出现在`where`、`order by`、`join`里的字段**，最值得优先考虑索引。常见包括：状态、创建时间、业务编号、外键ID、负责人ID、分类ID、删除标记、高频组合查询字段。

但索引不是越多越好。索引多了查询快，写入却更慢。设计时想清楚：这个字段是不是高频列表条件？是单字段查询多还是组合查询多？是读取多还是写入多？值不值得维护索引？

**前端类比**：像给组件加`memo`缓存，只有高频计算才值得。索引同理——只有高频查询字段才值得建索引。

前端也能帮忙降压：
- 默认只展示必要列（别一次拉50列）
- 高成本字段延迟加载
- 搜索框加防抖
- 筛选项别一次性塞太多
- 复杂联动条件分步请求
- 别让列表接口承载详情页内容

记住：**列表页不是详情页，别把它做成大而全的数据出口。**

---

## 五、前后端协作中的数据口径问题：列表页最容易吵架的地方

### 1. 同一个字段，前后端可能理解不一样

列表页最常见的协作问题：前端认为“状态”是页面文案，后端认为“状态”是存储枚举；前端认为“时间”是创建时间，后端返回的是更新时间；前端认为“总数”是当前条件下的总数，后端返回的是全量总数。

本质是**数据口径不一致**。口径没对齐，页面看起来像bug，实际上是定义没统一。

### 2. 列表页交互越复杂，口径越要提前统一

以下内容最好在接口设计前确定：
- 默认排序是什么
- 筛选条件是精确还是模糊
- 搜索关键词是否忽略大小写
- 时间范围是否左闭右闭
- 分页从0开始还是从1开始
- 总数是当前条件总数还是全部总数
- 空数据是`[]`还是`null`

建议前后端先对一张“查询口径表”：

| 字段名 | 字段含义 | 是否可筛选 | 是否可排序 | 是否可搜索 | 返回类型 | 是否展示文案 | 是否依赖关联表 |
|--------|----------|------------|------------|------------|----------|--------------|----------------|
| status | 支付状态 | 是 | 是 | 否 | int | 是(启用/停用) | 否 |
| created_at | 创建时间 | 是 | 是 | 否 | timestamp | 是(格式化) | 否 |
| owner_id | 负责人 | 是 | 否 | 否 | int | 是(用户姓名) | 是 |

这比“我感觉应该可以”靠谱得多。列表页最怕看起来都懂了，其实各说各话。

---

## 结尾小结：把列表页当作数据库设计的体检单

这一章你只要记住一句话：

> 前端看到的是列表，后端看到的是查询模型；前端做的是交互，数据库承受的是检索压力。

再压缩成几个判断标准：
1. **列表页最能暴露表设计问题**——筛选、排序、搜索、分页都会把字段结构逼出来。
2. **筛选、排序、搜索会反推字段设计**——高频、稳定、清晰的字段更适合结构化存储。
3. **分页接口返回结构≠数据库表结构**——接口是给页面用的最终稿，表是给系统用的底稿。
4. **列表性能与索引设计直接相关**——高频查询字段才值得建索引。
5. **前后端要统一数据口径**——尤其是分页、排序、筛选、搜索、状态文案细节。

**行动建议——下次写列表页时，这样检查：**
- [ ] 这个筛选条件会不会成为高频查询？
- [ ] 这个排序字段好不好排？是不是唯一？
- [ ] 这个搜索字段适不适合模糊查？
- [ ] 返回结构是给页面看的，还是直接搬数据库的？
- [ ] 列表接口是不是承载了太多详情页内容？
- [ ] 前后端对“总数”“排序”“空数据”的定义一致吗？

你开始这么想的时候，就已经不是只会调接口的前端了。你已经在用数据库设计的思维看页面了。

# 第6章 字段命名与接口命名统一：让前后端少打架

## 开篇引入：名字不统一，联调就像“同题不同解”

前端最怕的坑：同一业务，用的名字不同。你写 `userName`，后端回 `username`，数据库叫 `user_name`。表单提交 `phoneNumber`，后端返回 `tel`，数据库存 `mobile_phone`——新增、编辑、详情、列表各处理一遍映射。

**核心问题**：从页面表单、列表展示、接口联调三个场景，讲清“页面文案”“前端变量”“接口字段”“数据库字段”四层命名的关系，并给出可直接套用的规则。

---

## 一、数据库命名、接口命名、前端变量名：各自负责什么

- **数据库字段名**：存储层语言，稳定存数据。强调唯一、精确、易查询。如 `order_id`、`pay_status`。不需要好读。
- **接口字段名**：对外协作语言，前后端交换数据的公共语言。是面向消费的整理版，如 `{"orderId": 1001}`。
- **前端变量名**：页面内部语言，服务组件逻辑，如 `list`、`selectedOrderId`。

**总结**：数据库字段是仓库标签，接口字段是快递面单，前端变量是工位文件夹。三者不必一样，但必须能对上号。

---

## 二、从页面组件到字段命名：一个“编辑用户”表单的完整对照

| 页面组件 | 中文业务名 | 前端变量 | 接口字段 | 数据库字段 |
|---------|-----------|---------|---------|-----------|
| Input | 用户名 | userName | userName | user_name |
| Input | 手机号 | phone | phone | mobile_phone |
| Select | 性别 | gender | gender | gender |
| DatePicker | 出生日期 | birthday | birthday | birth_date |
| Input | 邮箱 | email | email | email |
| TagSelect | 兴趣标签 | tags | tags（JSON数组） | tags（JSON列） |

**关键发现**：
1. 前端变量和接口字段基本一致（驼峰），数据库字段用下划线。
2. “手机号”各层名称不同但映射明确。
3. 兴趣标签用JSON列——当字段是集合且不需要按单个值精确筛选时适用；需要精准搜索时应拆表。

**实战建议**：搭建新页面时，先拉一张“字段映射表”，明确四层名称。

---

## 三、前端表单提交如何反向影响数据库设计

**案例1：必填字段与NULL矛盾**。前端昵称必填，后端为兼容旧数据允许NULL。前端传空字符串，数据库存空串，后续`IS NULL`查不到。

**教训**：前端必填项对应数据库`NOT NULL`。后端允许NULL时，传空串将导致查询条件失效。

**案例2：提交顺序影响默认值**。后端INSERT不加字段列表时，表单字段顺序必须与表定义一致。

**教训**：永远建议INSERT加字段列表。前端必填、可选要同步后端，决定字段用`NOT NULL`、`DEFAULT NULL`或`DEFAULT '默认值'`。

---

## 四、分页列表背后的字段命名统一

常见规范：

```
前端传参 → 接口字段 → 数据库对应
page           page     LIMIT偏移量
pageSize       pageSize LIMIT条目数
sortBy         sortBy   ORDER BY字段（须和数据库字段一致）
sortOrder      sortOrder ASC/DESC
keyword        keyword  LIKE模糊搜索
```

**坑点**：`sortBy`的值用前端字段名还是数据库字段名？前端传`sortBy: "userName"`，后端要映射为`user_name`再拼ORDER BY。更省事：直接约定用数据库字段名，后端不用翻译。筛选条件的映射统一在后端处理。

---

## 五、同一个业务字段，为什么一定要统一口径

统一口径不是名字一样，而是**同一概念在各层有稳定映射**。

**场景1：表单回填对不上**。前端用`phoneNumber`，接口返回`tel`，写三套映射。

**场景2：筛选条件查不到数据**。前端传`createdAtStart`，后端需`start_time`。

**场景3：同一字段意义不同**。`status`在订单列表是支付状态，在详情报物流状态。

统一口径的核心是统一**业务含义**。

---

## 六、驼峰、下划线、中文业务名：怎么对照最省事

- **中文业务名**：给人看，如“订单状态”。
- **驼峰命名**：给前端和接口看，如`orderStatus`。
- **下划线命名**：给数据库看，如`order_status`。

最省事对照：中文 = “订单状态”，接口 = `orderStatus`，数据库 = `order_status`。避免数据库直接返回下划线，前端再转一层。

---

## 七、什么时候必须统一，什么时候可以各自映射

**必须统一**：
1. 核心业务字段：用户ID、订单号、状态，贯穿前后端。
2. 搜索筛选条件：分页、排序、时间段。
3. 主键和关联键：`userId`与`user_id`必须稳定映射。

**可以各自映射**：
1. 计算字段：如“年龄”。数据库只存`birth_date`，前端变量`age`，不互相干扰。
2. 临时数据：验证码、确认密码——不落库，前端随便命名。
3. 展示增强字段：状态文案——数据库存状态码，接口可返回`statusText`，两者分开。

**一句话**：业务事实必须统一，展示增强可以各自处理。

---

## 结尾小结：先统一语言，再谈高效协作

四条落地建议：
1. **页面文案、接口字段、数据库字段**不必完全一致，但必须建立稳定映射。建议用“字段映射表”记录。
2. **前端用驼峰命名**，接口字段也保持统一规则。
3. **核心字段必须统一**：业务字段、搜索条件、关联键。
4. **展示字段可以各自处理**：计算值、临时数据按前端习惯来。

以后看到 `user_name`、`username`、`userName`、“昵称”，先问：**是不是同一个业务概念？** 是就定好映射，否就别硬凑。名字对了，联调少一半火气。

# 第7章 哪些字段适合进数据库，哪些更适合留在前端

## 开篇引入：不是所有数据都值得“上库”

数据库是**业务事实的长期记忆**，前端处理的是**当前页面的运行状态**。字段可分为四类：业务事实、计算结果、展示字段、临时UI状态。

**核心原则**：数据库存的是**不可丢失的事实**，前端管的是**可重建的状态**。

---

## 一、业务事实：必须持久化的字段

业务事实是**一旦发生，就应该长期记录**的字段，比如用户下单时间、订单金额、手机号、文章标题、商品价格。

**判断标准：删掉前端页面，这些数据还要不要留？**

符合以下条件就该入库：
- **要追溯**：能查历史记录
- **要对账**：金额、数量、状态不能丢
- **要同步**：多个页面、多个角色都要看
- **要审计**：谁改了、什么时候改的要留痕
- **要恢复**：页面刷新、系统重启后仍然存在

**反例提醒**：系统默认头像的CDN地址只是配置项，不一定要入库，存在配置文件或前端常量里就行。

---

## 二、计算结果：一般不入库，除非需要快照

计算字段比如年龄、订单总价、累计登录天数。**通常不建议重复存**，容易出现“两个真相”。

**何时可冗余存储**：为了性能、报表、历史快照。比如月底对账时，历史订单的快照总价不能变。

**判断规则：**
- 计算量小→不存，前端直接算
- 需跨表查询且页面频繁请求→考虑快照存储（如首页展示的“收藏文章数”可定时计算，个人中心页则实时count即可）

---

## 三、展示字段与临时UI状态：大部分留在前端

**展示字段**：若来自配置或静态资源，通常不入库；若用户自定义则需入库。

**临时UI状态**：输入框当前值、弹窗开关、loading状态、折叠面板是否展开等，刷新后无所谓，留在前端。

**业务状态**：订单状态、支付状态等，影响流程判断，必须入库。

| 状态类型 | 例子 | 是否入库 | 理由 |
|---------|------|---------|------|
| 业务状态 | 订单状态、支付状态 | 入库 | 影响流程判断，需持久化 |
| 展示状态 | 弹窗已读、滚动条位置 | 前端 | 刷新后可重置 |

---

## 四、从页面组件拆实体：别把一个页面当成一张表

一个页面往往对应多张表。比如“订单详情页”涉及用户表、订单明细表、地址表、支付记录表、物流表。

**误区**：把所有东西塞进一张大表（大宽表）。后果是查询慢、更新锁表范围大、冗余数据爆炸。

**正确做法**：拆分到多张表，通过外键关联，接口层再组装。

**三步推演**：
1. **识别“主体对象”**——订单详情页的主体是“订单”，对应订单表
2. **识别“关联对象”**——用户、地址、商品，有独立生命周期
3. **识别“值对象”**——订单备注、优惠券使用记录，直接挂在订单表

**反例**：在订单表加`user_avatar`字段。用户换头像后历史订单里的头像还是旧的，除非业务需要快照，否则会造成冗余和更新难题。

---

## 五、从表单字段对应数据库字段：提交什么，不等于存什么

**不是每个表单字段都必须落库**：确认密码、验证码、仅用于校验的中间字段不入库。

**复杂表单场景**：一个表单字段对应多张表。比如“收货地址”字段，前端可能只传`region_id`，后端关联地区表、地址表、用户地址表。

**对应原则**：
- 用户真正填写的业务内容，优先入库
- 仅用于校验、展示、引导的字段，不入库
- 前端可计算、后端可推导的字段，尽量不重复存

**注册表单推演**：`confirmPassword`和`captcha`校验后丢弃；`agreeToTerms`若为合规要求则需拆表记录；`username`、`password`、`phone`必须入库。

---

## 六、JSON字段适合放什么，不适合放什么

**适合放**：结构不固定、可扩展的配置，如商品规格、用户个人设置、页面模板配置。

**不适合放**：需要频繁筛选查询、做统计报表、强约束的字段，如订单状态、手机号、价格、身份证号。

**JSON替代关联表的决策**：

| 判断维度 | JSON方案 | 关联表方案 |
|---------|----------|-----------|
| 查询性能 | 需全表扫描 | 可索引，JOIN查询快 |
| 更新一致性 | 需整条替换 | 精确修改单条记录 |
| 数据校验 | 无法加约束 | 可为每个字段加约束 |

**结论**：规格种类固定且不多（3-5种），用JSON方便；需频繁筛选或新增规格，用关联表。

**案例**：手机号存成JSON，搜索需全表扫描；单独作为`varchar(11)`并加唯一索引，查询毫秒级。**需要搜索、唯一校验、统计的字段，永远不要塞进JSON**。

---

## 七、字段入库与否的判断原则：四问法

1. **是不是业务事实？** 是→优先入库
2. **能不能从别的字段推出来？** 能且非性能需要→尽量不重复存
3. **是不是只服务当前页面交互？** 是→留前端
4. **未来会不会被查询、统计、审计、追溯？** 会→认真考虑入库

---

## 八、前后端协作中的数据口径问题

字段名一样，不代表口径一样。比如`totalAmount`，前端认为是“实付金额”，后端实际是“商品总价（含折扣，未扣除运费）”，导致数据对不上。

**口径不一致导致bug的场景**：前端结算页展示实付金额，后端订单查询页展示商品原价+运费，用户以为系统有问题。

**统一三步走**：
1. **定义明确**：每个字段加语义前缀，避免模糊词
2. **文档对齐**：写清楚计算公式、取值范围
3. **双方确认**：前后端逐条过一遍接口字段语义

---

## 九、完整案例：从页面字段到入库决策

以“用户个人中心”页面为例：

| 字段 | 类型 | 入库决策 | 理由 |
|------|------|---------|------|
| 用户名 | 业务事实 | 入库 | 用户身份核心信息 |
| 头像URL | 展示/配置 | 用户上传则入库，默认头像留前端 | 用户上传的是业务事实 |
| 简介 | 业务事实 | 入库 | 用户填写，需持久化 |
| 累计登录天数 | 计算结果 | 不入库，展示时计算 | 由登录记录count得出 |
| 最近登录时间 | 业务事实 | 入库 | 需追溯、安全审计 |
| 当前在线状态 | 临时UI状态 | 留前端 | 刷新后变离线 |
| 收藏文章数 | 计算结果 | 不入库，动态计算 | 访问量不大 |
| 会员等级标签 | 展示字段 | 不入库 | 等级ID入库，文案由代码映射 |
| 弹窗是否已读 | 临时UI状态 | 跨设备则入库，否则localStorage | 根据业务需求决定 |
| 页面主题颜色偏好 | 临时UI状态 | 跨设备则入，否则localStorage | 同上 |

---

## 十、容易踩的坑：五个常见误区

**误区一**：接口返回的值就该入库。很多数据是组装、计算出来的。

**误区二**：为了方便渲染把所有关联字段拼进一张表。正确做法是在接口层面JOIN。

**误区三**：用户输入了就该存下来。确认密码、验证码不用存。

**误区四**：页面结构变了表结构就得跟着变。数据库关心“有什么数据”，不关心“怎么摆页面”。

**误区五**：用store代替数据库存业务数据。Redux、Pinia刷新就丢，不能替代持久化。

接口返回的是**聚合视图**，表结构是**原子存储**。从接口字段反推表结构：标记原子字段、识别关联ID、分离聚合计算字段。

---

## 结尾小结

**数据库存的是业务事实，前端留的是交互状态。**

- 必须长期保留、可追溯、可查询的，进数据库
- 能推导出来的计算字段，尽量别重复存
- 只服务当前页面的临时状态，留在前端
- JSON可以灵活，但别把核心字段都塞进去
- 字段入不入库，最终要看业务口径

**实战检查清单**：加字段时先问——1. 业务事实还是页面状态？2. 刷新后还要保留吗？3. 能从别的字段算出来吗？4. 会被搜索、统计、审核用到吗？5. 前后端对字段含义完全一致吗？

**数据进库之前，先问它值不值得被记住。**

# 第8章 JSON字段什么时候该用：灵活不是万能，别把表写成大杂烩

## 开篇引入：前端最容易把JSON想“美”了

前端第一次接触JSON字段，常觉得这不就是对象？传什么存什么，省事又灵活。但数据库要面对长期存储、筛选、统计、关联和维护——今天图省事把一切塞进JSON，明天就发现列表不好筛选、报表不好统计、索引不好建。

**一个真实失败案例**：某前端同事做商品管理后台，把商品属性全塞进一个JSON字段。存取确实简单，但需求来了：按“库存小于10”筛选商品。后端没法在数据库层直接筛，只能全量拉到内存逐条解析。每次请求扫描十几万条记录，页面卡到崩溃。最后被迫花一周重构，拆出关键字段做普通列。教训是：**别让一时的省事变成明天的噩梦。**

这章只讲一个判断：**什么场景适合用JSON，什么场景该拆成普通列？**

---

## 一、什么场景适合用JSON：三个典型条件

适合放JSON的数据，是**结构不稳定又不常查**的：

1. **扩展项不稳定**。如商品属性“颜色、尺寸、材质”，今天加“环保等级”，明天加“产地证明”，每次都改表结构成本高。
2. **结构变化快，很难提前定义**。如第三方回调原文、支付回传报文，无法预知字段，整包存JSON是务实选择。
3. **字段组装成本高，拆成列浪费**。如“高级配置”对象，只有少数记录用到，拆列后大部分行空值。比如用户表“个性化设置”，90%用户只设基础选项，为10%用户建十几个列不划算。

关键不在于“复杂”，而在于**不稳定**。

### 用JSON的前提：主业务字段必须清晰

- **主流程字段**用普通列：订单号、状态、时间、金额
- **扩展字段**可考虑JSON：用户备注、附加标签、临时配置
- **高频查询字段**不要只放JSON：会员等级、支付方式经常作筛选条件，必须拆列

一句话：**JSON适合“边角料”，不适合“主骨架”。**

---

## 二、什么情况不该用JSON：四个明确边界

### 2.1 只要你要“查、排、筛、统”，就要警惕JSON

列表页按状态筛选、按时间排序、按关键字搜索，本质要求数据库“可计算、可定位”。把这些关键数据藏在JSON里效率很低。**列表页高频用的字段必须摆在明面上。**

### 2.2 不能用JSON替代数据口径

页面A把`vipLevel`存数字1、2、3，页面B存字符串“黄金会员”，页面C加`levelText`，后端取出还得判断转换。**JSON是给变化快的部分留缓冲区，不是替代规范。**

### 2.3 不要把“未来可能会变”当作“现在全塞JSON”的理由

判断三个问题：这个字段现在是核心查询条件吗？是否影响列表展示、筛选、排序？多个页面是否稳定使用？两个以上“是”，就不该只放JSON。比如商品表现在明确要按“品牌”筛选，哪怕品牌以后可能拆成子品牌，现在也必须先建普通列。

### 2.4 避免JSON成为临时方案的“永久化陷阱”

很多团队初期为了“时间紧”把所有字段塞进JSON，结果需求稳定后，JSON里攒了几十个key，没人敢动也没人愿意拆。更实用策略：先用JSON托住变化，等字段稳定下来再逐步提炼成普通列。**灵活是过渡手段，不是最终形态。**

---

## 三、JSON和普通列的取舍：判断矩阵

### 3.1 看“稳定性”和“使用频率”

| 维度 | 适合普通列 | 适合JSON |
|---|---|---|
| 结构稳定性 | 高 | 低 |
| 查询频率 | 高 | 低 |
| 排序筛选 | 经常要 | 很少要 |
| 业务口径 | 明确统一 | 临时扩展 |
| 数据约束 | 需要强校验 | 可以弱校验 |

**长期稳定+经常查询+需要约束** → 普通列；**临时扩展+很少查询+结构变化快** → JSON。

### 3.2 代价对比：JSON到底损失了什么？

| 对比维度 | 普通列 | JSON字段 |
|---|---|---|
| 筛选速度 | 毫秒级，支持索引 | 慢3-5倍，无法加索引 |
| 数据校验 | 数据库自动做类型检查 | 只能靠程序逻辑 |
| 排序效率 | 利用索引排序 | 需逐条解析，大量数据可能超时 |
| 联合查询 | 直接JOIN | 需要JSON函数，复杂且低效 |
| 开发调试 | 字段直观，IDE补全 | 手动提取，容易写错路径 |

### 3.3 实战检查清单

- 是不是核心业务字段？
- 是不是列表筛选、排序、统计常用？
- 结构是否经常变化？
- 是否只在少数场景下用？
- 有没有强校验要求？

前两条“是”优先普通列，后两条“是”考虑JSON。

### 3.4 踩坑补救：如果已经写了一大堆JSON

1. **分析业务查询需求**：列出所有用到的筛选、排序、统计字段。
2. **标记高频访问+结构稳定的字段**：订单状态、手机号、下单时间等优先拆成普通列。
3. **新增普通列，迁移旧数据**：`UPDATE orders SET order_status = JSON_EXTRACT(extra, '$.status');`
4. **逐步清理JSON**：每拆一个字段，删除JSON里对应的key。
5. **给新数据强制约束**：接口层和数据库层都加上校验。

---

## 四、前端传复杂对象时，数据库如何接收

### 4.1 数据库不一定要逐层展开

前端提交复杂对象（如用户注册含地址、偏好设置），后端常用两种处理：

1. **拆成普通列**：核心信息如`name`、`phone`、`province`单独落列，确保筛选、搜索能用索引。
2. **部分拆列+部分存JSON**：核心信息拆列，标签、备注、附加配置存JSON。比如用户表：`user_name`（普通列）、`mobile`（普通列）、`tags`（JSON列）、`preferences`（JSON列）。

关键不是“能不能存”，而是**存进去之后怎么用**。如果频繁按`city`筛选，就不该只躺在JSON里。

### 4.2 表单字段要分层

**基础字段**：最核心、最稳定、最常用（名称、金额、时间、状态），必填项，列表页展示和筛选的基础。**扩展字段**：高级选项、备注、临时信息，非必填，只在详情页展示。基础字段落列，扩展字段进JSON。

**给前端的建议**：设计接口时，主动和后端确认哪些字段进JSON、哪些是普通列。如果前端页面需要对这些字段排序或筛选，一定要要求后端拆成普通列。

---

## 五、前后端协作中的JSON数据口径问题

### 5.1 字段名别乱跳

表里叫`extra_info`，接口叫`extraInfo`，JSON里叫`extra_data`，排查痛苦。建议命名映射稳定，业务语义统一。**JSON key变更要同步**：后端改key名（如“vipLevel”改成“vipGrade”），前端必须同步修改解析逻辑。建议做法：

- 接口文档里明确JSON字段的key列表、类型、示例值
- 前后端共同维护JSON协议文档
- 用TypeScript可定义类型声明：`type ExtraInfo = { vipLevel: number; tags?: string[] }`

### 5.2 JSON也要有边界文档

约定哪些key存在、哪些必填、哪些只在特定场景出现、哪些将来会提为普通列。**JSON是“扩展协议”，不是“垃圾桶”。**

**给前端的建议**：和后端约定JSON里的数据格式规范，比如金额统一用分存储、日期统一用时间戳或ISO格式，避免每次解析做不同格式转换。

---

## 六、实战检查五步走

1. **列出所有页面高频查询字段**：展示字段、筛选条件、排序字段，必须进普通列。
2. **判断稳定性**：稳定字段进普通列，不稳定字段打标记。
3. **标记扩展字段**：“少数场景用、结构变化快、几乎不做查询”的挑出来。
4. **决定列或JSON**：核心+稳定+高频 → 普通列；扩展+不稳定+低频 → JSON。
5. **定期审视JSON，提炼稳定字段**：每三个季度检查一次JSON里的key，已稳定使用半年以上的提取成普通列。

**行动建议**：做表设计时先把高频查询字段列出来；标记不稳定扩展字段考虑JSON；定期审视JSON；约定命名规范和边界文档；不要因“可能变化”就把所有字段塞JSON。

---

## 结尾小结：JSON不是垃圾桶，是缓冲区

> **JSON字段适合装“变化快但不核心”的扩展信息，不适合装“要经常查、经常筛、经常统计”的主数据。**

回到开头——如果那位同事把商品名称、库存、价格拆成普通列，把标签、临时属性放进JSON，就不会有前面的悲剧。JSON不是敌人也不是魔法，有明确的使用边界。下一次设计接口或review表结构时，问自己：**这个字段，到底是JSON的灵活，还是普通列的稳定？** 答清楚了，表设计就不会跑偏。

# 第9章 前端提交数据如何影响表设计：接口参数不是随便拍脑袋

## 开篇引入：你以为是“前端把表单提交过去”，其实是在给数据库“定形”

很多前端同学刚接触数据库设计时，会觉得表单怎么写，接口就怎么收，后端原样塞进库就行。  
但一到项目里，问题马上来了：

- 页面是一次性提交，还是分步保存？
- 用户中途退出，要不要草稿？
- 审批流能不能撤回？
- 批量编辑几十条，传 ID 还是传整包对象？
- 页面上有些字段只是展示用，为什么也被传给后端？
- 一个接口参数，为什么最后会影响表字段、状态字段、关联表？

老赵先给你一句结论：  
**前端提交数据的方式，不只影响接口长什么样，还会反过来影响数据库怎么分表、怎么设计字段、怎么设计状态。**

接口参数不是前端随便拍脑袋，也不是后端随便接一下。  
它其实是前端交互流程和数据库结构之间的一座桥。

---

## 一、先把“接口参数”和“表结构”分清楚：它俩根本不是一回事

### 1. 接口参数是给交互用的

前端发请求时，参数通常长这样：

```json
{
  "title": "新手指南",
  "categoryId": 3,
  "tags": [1, 5, 8],
  "coverUrl": "...",
  "content": "...",
  "isDraft": true
}
```

这套结构是为了让页面好用：该传的能一次传完，前后端沟通成本低。

### 2. 表结构是给持久化用的

数据库不是拿来“像接口一样好看”的，它是拿来长期存、反复查、稳定改的。  
所以同一份数据写入数据库时，往往会拆成几块：

- 主表：标题、分类、封面、状态
- 关联表：标签关系
- 详情表：长文本内容
- 日志表：保存、提交、撤回记录

你看，接口是“页面视角”，表是“数据生命周期视角”。  
这两个东西像不像不重要，**适不适合各自用途才重要。**

---

## 二、一次提交和分步提交：你是“一锤子买卖”，还是“边填边存”？

同样是新增，前端体验差别很大。  
有的页面 30 秒填完，有的页面要填半天还要来回切 tab。它们背后的表设计完全不是一个级别。

### 1. 一次提交：适合简单、短、低风险的表单

比如：

- 登录
- 简单报名
- 反馈留言
- 单页新增商品分类

这类表单字段少、一次提交、不中途保存、失败了重试即可。  
数据库设计通常也直接：

- 一张主表就够了
- 字段按最终提交结果设计
- 不需要为中间态开太多口子

比如“新增分类”：

- `category_name`
- `category_sort`
- `status`

这些基本就是最终态字段，提交一次就落库。

### 2. 分步提交：表设计会明显更复杂

如果流程是：

- 第一步填基础信息
- 第二步填详情
- 第三步上传附件
- 第四步确认提交

那就不是“一个表单”这么简单了。因为用户可能任意一步退出，也可能回来继续编辑。

这时数据库要考虑的不只是最终数据，还有：

- 当前填到哪一步
- 哪些字段已完成
- 哪些字段是临时保存的
- 是否允许重复编辑
- 草稿和正式数据是不是同一份记录

常见做法有两种：

#### 做法 A：同一张表加状态字段
适合流程不复杂的场景。

比如订单草稿：

- `order_no`
- `user_id`
- `status`：draft / submitted / cancelled
- `step_no`
- `total_amount`

优点是简单，前端也好理解：**同一个对象，不同状态。**

#### 做法 B：主表 + 草稿表 / 明细表
适合流程复杂、字段多、改动频繁的场景。

比如课程创建：

- 主表存课程主信息
- 详情表存课程介绍
- 附件表存图片、视频
- 草稿表存未完成内容

这样结构更清晰，不会把临时数据全堆进正式表。

### 判断标准

你可以用前端很容易理解的方法判断：

- 像简单表单：**一张表通常够用**
- 像向导流程：**要考虑状态和分步存储**
- 中途退出频繁：**草稿能力几乎必需**

别只看“有没有提交按钮”，要想的是：  
**这个页面提交的是一份完整结果，还是一个正在生长的对象。**

---

## 三、草稿、正式保存、撤回：状态不是按钮，而是数据生命周期

前端经常把“保存”“提交”“撤回”看成按钮。  
但在数据库设计里，它们不是按钮，它们是**状态机**。

### 1. 草稿：保存的是“未完成的业务对象”

草稿不是废数据，它是合法的中间状态。比如：

- 文章编辑到一半
- 商品资料填了一半
- 报销单还没提交

数据库里通常会有状态字段：

- `status = draft`
- `status = pending`
- `status = approved`
- `status = rejected`
- `status = withdrawn`

要注意：**草稿态的数据，往往允许字段不完整。**

所以前端提交草稿时，后端不能按正式提交那套强校验卡死，否则草稿就失去意义了。

### 2. 正式保存：表示进入业务流程

正式保存通常意味着：

- 校验更严格
- 关键字段必须完整
- 记录进入审核、发货、发布等流程
- 某些字段之后不允许随便改

这对表设计的影响是：  
你得提前想好哪些字段在 `draft` 时可改，哪些字段在 `submitted` 后冻结。

比如采购单：

- 草稿时可以改收货地址
- 提交后地址可能不能改
- 审批通过后金额字段必须锁定

所以数据库不只是存数据，还要存流程控制信息。  
前端页面上的“提交”按钮，本质上对应一次状态迁移：从草稿到待审，从待审到已通过，或者回到编辑。

### 3. 撤回：不是删数据，而是回到某个状态

撤回一般不是直接删除，更常见是：

- `status` 改成 `withdrawn`
- 记录撤回时间
- 记录撤回人
- 必要时保留历史版本

原因很简单：业务系统讲究可追踪。你不能一撤回就把痕迹抹掉，不然后面对账、审计、排查都麻烦。

### 这里的关键点

前端设计按钮时，最好先想数据库状态：

- 草稿按钮对应什么状态？
- 提交按钮是否改变状态？
- 撤回后能否再次编辑？
- 撤回后能否重新提交？
- 这些状态是单字段控制，还是多字段组合控制？

**按钮是交互，状态才是数据。**

---

## 四、一个完整链路：表单组件 -> 请求参数 -> 服务端写入 -> 表状态变化

这一段最适合前端同学理解。咱们拿“文章发布页”举个例子。

### 第一步：页面组件怎么拆

页面上可能有这些组件：

- 标题输入框
- 分类选择器
- 标签选择器
- 封面上传
- 富文本编辑器
- 草稿 / 发布按钮

从前端看，这是一个页面。  
从数据库设计看，这其实是多个实体拼在一起：

- 文章主信息
- 标签关系
- 附件或图片
- 发布状态
- 草稿状态

### 第二步：请求参数怎么组

前端提交时，可能会把这些字段一次打包：

```json
{
  "title": "新手指南",
  "categoryId": 3,
  "tags": [1, 5, 8],
  "coverUrl": "/img/a.png",
  "content": "<p>...</p>",
  "status": "draft"
}
```

这里重点不是字段够不够多，而是交互是否顺手。  
草稿按钮点下去，前端可放宽校验；发布按钮点下去，就得先检查必填项。

### 第三步：服务端怎么写入

服务端收到参数后，不会简单原样塞进一张表：

- `title`、`categoryId`、`coverUrl` 进主表
- `tags` 拆到标签关联表
- `content` 进详情表
- `status` 进状态字段
- 操作动作进日志表

这就是接口和表结构的差异：  
接口是为了页面好传，表是为了后面好存、好查、好追踪。

### 第四步：表状态怎么变化

如果点的是“保存草稿”，状态可能是：

- `draft`

如果点的是“正式发布”，状态可能变成：

- `pending`
- `published`

如果点的是“撤回”，状态可能变成：

- `withdrawn`

前端按钮只是动作，数据库状态才是结果。  
这条链路想通了，很多接口设计就不会拍脑袋了。

---

## 五、批量操作和批量编辑：不是“多传几个 ID”那么简单

批量操作是前端最容易把后端和数据库搞复杂的地方。

### 1. 批量操作：通常不是“整行提交”，而是“意图提交”

比如：

- 批量删除
- 批量上下架
- 批量改分类
- 批量打标签

前端常见提交结构不是整条对象，而是：

- `ids: [1,2,3]`
- `action: "offline"`
- `reason: "违规"`

重点不是数据多完整，而是操作意图明确。

数据库设计上，这意味着你往往需要：

- 主表里有可批量变更的字段，如 `status`、`category_id`
- 有操作日志表，记录批量操作痕迹
- 有更新时间、操作人字段，便于追踪

也就是说，前端传给后端的不是“这几条数据长什么样”，而是“我要对这几条数据做什么”。

### 2. 批量编辑：要考虑字段一致性

批量编辑比批量操作更麻烦，因为它不只是改状态，而是改内容。

比如批量修改商品标题、价格、标签：

- 有些字段所有选中项都能改
- 有些字段只允许部分记录改
- 有些字段值是统一覆盖
- 有些字段是按规则增量更新

所以后端表设计会考虑：

- 哪些字段适合批量修改
- 哪些字段应该拆出去，避免批量误改主信息
- 哪些字段必须进入审核流程

比如价格字段可能需要版本控制，而分类字段可能直接更新。  
因为价格一变，可能影响订单、库存、优惠券计算，这种字段不能像改备注一样随便改。

### 3. 常见误区

#### 误区一：前端一次传很多字段，后端就照单全收  
不行。批量接口最好只接收必要字段，否则容易误改。尤其是组件里带的临时值、展示值、选择状态，混进来后很容易把数据库写脏。

#### 误区二：数据库只要能更新就行  
也不行。你还要考虑：

- 更新失败一部分怎么办
- 是全部成功才算成功，还是允许部分成功
- 要不要事务
- 要不要记录失败原因

前端批量操作看着像一个按钮，背后其实是数据库更新策略。  
你按钮点一下，后端要决定的是：这是一组独立操作，还是一个必须整体成功的事务。

---

## 六、前端提交结构与数据库写入结构的差异：接口不是表的镜像

这个点很重要，很多前端容易误解。

### 1. 前端提交的是“业务动作”，数据库存的是“业务事实”

前端提交的数据通常长这样：

```json
{
  "title": "新手指南",
  "categoryId": 3,
  "tags": [1, 5, 8],
  "coverUrl": "...",
  "content": "...",
  "isDraft": true
}
```

这看起来像一个完整对象。  
但数据库写入时，往往不是一张表全塞进去，而是要拆成：

- 主表：标题、分类、封面、状态
- 关联表：标签关系
- 详情表：长文本内容
- 操作日志表：保存、提交动作

**接口结构通常是面向页面的，表结构通常是面向存储和查询的。**

页面想一次拿齐、一次提交完，接口就倾向于“扁平 + 好用”；  
数据库要考虑范式、关联、查询效率、历史追踪，所以通常拆得更细。

### 2. 接口字段不等于表字段

前端接口里可能有：

- `label`
- `displayName`
- `isChecked`
- `tempId`
- `selectedOptions`

有些是页面展示需要的，有些只是临时状态，根本不该入库。

数据库真正要存的是那些：

- 业务长期需要
- 查询要用
- 统计要用
- 追踪要用

所以前端提交前，最好先问一句：

> 这个字段是“页面状态”，还是“业务数据”？

页面状态，比如展开收起、选中项、临时搜索条件，通常不入库。  
业务数据，比如商品名、订单金额、用户地址，才应该入库。

### 3. JSON 字段的适用场景

有些前端会问：既然接口结构这么灵活，那我全塞 JSON 不就完了？

不一定。

JSON 字段适合：

- 结构不固定
- 扩展频繁
- 查询不强
- 只需要整体存取

比如：

- 页面配置
- 表单自定义项
- 不同类型商品的扩展属性
- 某些低频、弱查询的附加信息

但不适合：

- 经常筛选
- 经常排序
- 经常统计
- 需要强约束的核心字段

比如订单金额、用户 ID、状态、创建时间，这些就不应该随便丢 JSON 里。  
一旦把核心字段塞进 JSON，后面列表筛选、导出、统计、联表查询都会很难受。

### 判断标准

如果某字段满足下面任一条件，通常更适合独立列而不是 JSON：

- 要做筛选
- 要做排序
- 要做统计
- 要做唯一性约束
- 要参与关联查询

前端可以把 JSON 当成扩展槽位，但别把它当万能收纳箱。

---

## 七、从页面组件拆实体：别从“页面长什么样”直接等于“表长什么样”

前端最容易犯的错，就是看到页面组件就直接想表。  
其实应该先拆实体，再定表。

### 一个简单的拆法

拿“商品编辑页”举例：

页面上可能有：

- 基础信息卡片
- 价格设置组件
- 图片上传组件
- 库存设置组件
- 标签选择组件

这些组件不是每个都对应一张表，但它们会提示你：页面里其实包含了多个实体层次。

你要先问：

- 这是商品本身的数据，还是商品的附属数据？
- 这是一个一对一关系，还是一对多关系？
- 这是可重复的明细，还是单值字段？

比如：

- 商品基础信息：主表
- 商品图片：子表
- 商品标签：关联表
- 商品规格：明细表
- 页面临时状态：不入库

这就是从组件拆实体。  
前端看的是组件树，数据库看的是数据关系树。两棵树不一样，但有映射。

---

## 八、从表单字段对应数据库字段：先判断“是不是要长期存在”

表单字段很多，但不是每个都该落库。前端提交前可以用四步判断：

### 1. 这个字段是不是业务核心？
是核心，就大概率要入库。

### 2. 这个字段会不会被查询、筛选、统计？
会，就尽量独立成列。

### 3. 这个字段是不是临时页面状态？
是，就别入库。

### 4. 这个字段是不是会频繁变化且结构不稳定？
是，可以考虑 JSON 或扩展表。

比如一个会员表单：

- `name`：入库
- `phone`：入库
- `avatarUrl`：入库
- `formStep`：通常不入库，除非要恢复草稿
- `uiTheme`：多半不入库
- `extraInfo`：视业务情况决定

可以把这个判断理解成：  
**能不能成为业务事实，决定它能不能进入数据库长期保存。**

---

## 九、分页列表背后的表设计理解：前端看到一页，后端想的是整张表

分页列表是前端最常见的页面之一。  
看起来只是：

- 第几页
- 每页多少条
- 排序
- 筛选

但数据库设计时，后端会倒推：

- 哪些字段要建索引
- 哪些字段要支持筛选
- 哪些字段要支持排序
- 哪些字段要方便分页查询

这也是为什么前端提交字段会影响表结构：  
**因为后端不仅要存，还要查得快。**

如果前端要支持按状态、时间、分类筛选，这些字段通常不能藏起来，得是明确字段。  
如果要支持批量编辑，相关字段最好结构稳定、语义清晰。  
分页列表看起来只是“展示结果”，实际上是在给数据库设计提出查询要求。

---

## 结尾小结：前端提什么，不只是接口问题，而是数据生命周期问题

老赵最后给你收个口：

前端提交数据时，你以为自己在做的是“发请求”；  
其实你在参与定义这份数据的**生命周期**。

你可以记住这几条：

1. **一次提交和分步提交**，会决定你要不要草稿、状态、分步保存。
2. **草稿、正式保存、撤回**，本质上是状态设计，不是按钮设计。
3. **批量操作和批量编辑**，会影响接口结构、日志设计、字段是否适合批改。
4. **前端提交结构不等于数据库写入结构**，接口是给页面用的，表是给存储和查询用的。
5. **JSON 不是万能桶**，适合扩展，不适合核心查询字段。
6. **从页面组件拆实体**，比直接看页面长什么样更靠谱。
7. **从表单字段对应数据库字段**，先看它是不是长期业务数据，再决定要不要入库。
8. **分页列表背后有查询压力**，页面的筛选、排序、批量操作，都会反过来影响表设计。

如果你以后在前端写表单、设计接口时，能多问一句：

> 这个提交方式，会不会影响后端怎么存、怎么查、怎么改？

那你就已经开始站在数据库设计的视角看问题了。  
这一步，特别关键。

# 第10章 接口返回结构与表结构不是一回事：前端看到的只是加工后的结果

## 开篇引入：你在页面里拿到的，不是“原始数据库”

前端最容易踩的坑之一，就是把接口返回的数据当数据库表。比如列表页拿到：

```json
{
  "id": 10086,
  "title": "秋季促销活动",
  "creatorName": "老赵",
  "statusText": "进行中",
  "goodsCount": 18,
  "createdAt": "2025-08-01 10:20:00"
}
```

很多人以为这对应一张活动表。真相是，这个返回值是后端加工过的**视图模型**，不是原始存储模型。

把数据库想成仓库，接口想成快递盒。仓库里是原材料，送到前端手里的是按页面最方便的方式重新打包的。

记住一句话：**接口返回是给页面用的，表结构是给数据存的，两者职责不同。**

---

## 一、接口返回为什么比表结构更好用？

核心原因：**页面需要的是“能直接用”，不是“最原始”。**

数据库关注存得稳、改得方便、数据不乱；前端关注能不能直接渲染、字段名好不好懂。接口把分散在多张表里的字段整理成前端友好的结构。数据库里是 `user_id`、`status_code`，前端想要 `creatorName`、`statusText`。接口不是照抄表，而是按页面需要重组。

此外，同一个接口可能服务不同页面：列表页要摘要，详情页要完整信息，编辑页要表单初始化数据。所以接口不可能等于某张表的全字段输出。不是表变了，而是**页面场景变了**。

---

## 二、接口结构与表结构的核心差异

| 对比维度 | 接口结构（给页面用） | 表结构（给数据存） |
|---------|-------------------|------------------|
| **命名风格** | 通常 `camelCase`，用户友好 | 通常 `snake_case`，通用标准 |
| **字段粒度** | 组合、平铺、拼装 | 原子、最小化、归一化 |
| **字段来源** | 多张表 + 规则计算 + 权限判断 | 单张表的实体属性 |
| **用途** | 渲染页面、绑定组件 | 持久化、更新、查询、索引 |

不能因为接口有 `creatorName`，就以为数据库有 `creator_name`。也不能因为接口没有 `user_id`，就以为表没这个关联。接口和表中间隔着一层加工逻辑。

---

## 三、三种“非表字段”的来源

### 1. 聚合字段：从多行记录统计计算得到

比如 `orderCount` 可能从订单表统计出来，`goodsCount` 来自关联表汇总。**数据库里没有单独的数字存这个值，接口里是实时算出来的**，或者用缓存定期更新。

### 2. 展示字段：数据库存编码，接口翻译成可读字符串

`statusText: "已结束"`（数据库存 `status: 3`），`roleName: "管理员"`（存 `role_id: 1`）。**为什么不在表里直接存字符串？** 编码更容易做筛选、排序、索引。编码和展示分离，是数据库设计的基本功。

### 3. 冗余字段：接口层为减少前端请求主动拼接

比如订单列表直接带 `userName`、`userPhone`，分别来自用户表、地址表、订单表。**接口里的冗余不等于数据库重复存储**，只是传输层为方便页面做的结果。

---

## 四、一个完整的“请求→加工→返回”推演

拿“订单列表”场景走一遍：

1. **前端发起请求**：GET /api/orders?page=1&size=20
2. **后端收到参数**：从订单表查出20条记录
3. **关联查询**：每行订单取用户名称、商品名称、支付状态
4. **加工计算**：order_status=2 翻译成 statusText="已发货"；goods_count 是商品明细表汇总
5. **权限判断**：如果当前用户是超级管理员，返回 canEdit=true
6. **拼装返回**：最终扔给前端的是上面那个 JSON

**前端看到的是流程的终点，不是起点。**

---

## 五、一个接口数据来自多张表的典型场景

### 1. 页面本身就是组合式

数据库为了规范拆表，接口为了方便前端再组装。订单列表前端看到的一行数据，后端拼结果要用到订单主表、用户表、商品表、支付表。**前端眼里是一行数据，后端眼里可能是多张表的联合结果。**

### 2. 分页列表 vs 详情页对表设计的影响

列表页字段少但快，详情页字段多但重。表设计要考虑的是“最常用的查询路径”而不是字段个数——分页列表需要按某些字段排序（如创建时间、状态），所以表上要有合适的索引支持排序性能。

### 3. 接口层常做业务组装

有些字段还经过规则计算，比如 `canEdit`、`canDelete`、`progressText`。这些是“数据 + 规则 + 权限”算出来的，前端拿到后，按钮显隐、状态颜色都能直接用。

---

## 六、字段命名规范：前后端怎么对齐？

后端数据库常用 `snake_case`，接口返回往往用 `camelCase`（看团队约定）。常见问题：后端返回 `user_name`，前端组件绑定 `userName`？解决方案：

- **统一约定**：团队定好接口字段风格，要么全驼峰，要么全蛇形
- **接口文档明确**：每次联调前先看接口字段命名
- **后端正向转换**：主流框架都支持配置自动转驼峰，无需前端手动处理

**最好的方案是后端一步到位，直接返回前端能直接用的字段名。**

---

## 七、前端提交数据如何影响表设计？

考虑一个常见表单：用户提交“活动有效期”，日期选择器返回 `"validPeriod": "2025-08-01 ~ 2025-08-31"`。数据库里可能拆成 `valid_start_at` 和 `valid_end_at` 两个字段——因为数据库需要单独查询开始/结束时间。

再比如前端传标签数组 `{"tags": ["前端", "数据库"]}`，表里可能设计成多对多关联表，或者用 JSON 字段存。选择哪种取决于查询复杂度：如果只是展示不用筛选，JSON 字段足够；如果要筛选“包含‘前端’标签的活动”，关联表更合适。

**所以：前端看到的是一个字段，后端可能拆成多个字段；前端传的一个参数，后端可能拆分存储。**

---

## 八、JSON字段在接口与表之间的角色

有些接口返回嵌套 JSON 对象，比如 `config: { "theme": "dark", "bannerUrl": "..." }`。**什么时候适合用JSON字段？**

- 属性不固定，随时可能新增
- 数据只需要整体存取，不需要单独查询某个属性
- 页面展示时直接解析 JSON 渲染

**什么时候不适合？** 需要按 JSON 里的某个字段做排序、筛选、统计时，JSON 字段会让查询变得复杂甚至不可用。

JSON 字段是“灵活但低查询性能”的取舍。前端看到接口里有嵌套结构，可以猜一下这是数据库里存的 JSON 字段，还是后端动态拼装的。

---

## 九、前端实战：如何避免把接口结构误认为数据库结构？

### 1. 判断字段是“存的”还是“算的”

问三个问题：它是不是业务实体的核心属性？会不会长期保存？能不能从别的数据算出来？

如果更像“算出来”“拼出来”“给页面看的”，那它大概率不是表字段。比如 `statusText`、`goodsCount`、`canEdit`、`searchKeyword`。

### 2. 看有没有明显的“加工痕迹”

发现以下特征，说明不是原始表结构：
- 带 `Text`、`Name`、`Label`、`Desc`（给人看的）
- 带 `Count`、`Total`、`Summary`（计算出来的）
- 带 `canXXX`、`isXXX`（规则/权限字段）
- 一条记录里混有多个实体信息

### 3. 联调时对齐三部曲

**第一步：列出接口所有字段**，包括含义、类型、示例值。

**第二步：标注每个字段类型**：主实体字段、关联字段、展示字段、统计字段、还是权限字段。

**第三步：逐个确认加工逻辑和口径**：这个值怎么算的？前端传的“活动有效期”入库后拆成了哪几列？

---

## 结尾小结：别把接口当表，把页面当需求来理解

**接口返回结构和表结构不是一回事。** 数据库表像仓库的原材料组织方式，接口像前端能直接用的成品数据。接口做了聚合、展示翻译、冗余拼装、权限判断、业务规则加工。

给前端同学一个实用建议：**以后看接口时，先别问“它对应哪张表”，先问“它是给哪个页面、哪个组件、哪个状态用的”。**

---

### 可执行清单

- [ ] 看接口返回时，能区分“主实体字段”“关联字段”“统计字段”“展示字段”“权限字段”
- [ ] 遇到 `Text`、`Name`、`Count`、`can` 开头的字段，知道它们八成不是数据库原始字段
- [ ] 联调前和后端对齐“口径”：同一个值到底是什么意思？
- [ ] 列表页和详情页接口返回字段不一致时，知道这是正常的设计差异
- [ ] 不再拿接口字段去反推数据库表结构
- [ ] 阅读新接口文档时，先问“这个接口是给哪个页面、哪个组件用的？”
- [ ] 前端表单提交字段，确认后端是原样存储还是拆分存储

# 第11章 前后端协作中的数据口径：同一个词，别各说各的

## 开篇引入：接口没错，业务却错了

前端最常见的翻车不是代码报错，而是接口都对，业务结果却不对。比如订单列表里“已支付”，你以为 `pay_status = paid` 就行，后端说还得排除退款中的单；运营又补一句：以用户实际到账为准。大家说同一个词，意思却不一样。这就是**数据口径**的问题。

真正决定业务对不对的，不是“字段叫什么”，而是“这个字段到底代表什么”。这章先讲**前后端为什么总在同一个词上打架**，以及如何通过需求评审把口径对齐。

---

## 什么叫数据口径，为什么比字段名更重要

数据口径可以理解为：**同一个业务词，在什么条件下算成立。**

比如“活跃用户”——当天登录过就算？当天有下单才算？字段名都可以叫 `active_user_count`，结果却差很多。字段名只是壳，口径才是内容。和前端状态同理：`loading / success / error` 只是名字，真正决定显示什么的是状态规则。

---

## 三个口径的区分：存储口径、展示口径、统计口径

### 1. 存储口径：库里到底存什么
数据库里的真实值。比如 `order_status = 2`、`is_refund = 0`、`pay_amount = 19900`。库里存稳定、紧凑、便于查询的值，但**库里存什么，不等于页面就怎么展示**。

### 2. 展示口径：页面上给用户看什么
UI 层看到的内容。比如 `order_status = 2` 显示成“已支付”，`pay_amount = 19900` 显示成“¥199.00”。前端做映射、格式化和文案转换。

### 3. 统计口径：报表里怎么算
最容易出事故。比如“成交订单数”算不算退款单、取消后重付的单、测试单？**展示是给人看的，统计是给业务算账的，存储是给系统留底的。** 三者相关，但不能默认相同。

---

## 需求评审时如何对齐口径：一个真实案例

假设评审“订单列表页”，需求写“展示所有已完成订单”。前端以为后端给 `status = completed` 就行，后端开始纠结：“已完成”指用户确认收货还是系统自动确认？包不包括退款中的订单？运营说“已完成”以用户实际到账为准。

一个看似简单的“已完成”，背后至少三个口径在打架。关键是在需求评审时就把事情说清楚，而不是等接口开发完了再猜。

---

## 需求评审时的对齐清单：问清5个问题

### 问题1：这个词的业务定义是什么？
比如“已完成”是否包含退款后的完成、部分退款、售后中的订单？不要对字段名，要对定义。

### 问题2：这个字段是给谁用的？
页面展示、筛选查询、统计报表、风控判断——不同用途口径不同。“下单时间”给列表展示精确到秒，给统计按天归集。

### 问题3：边界情况怎么算？
超时、取消、退款、补单、人工修正最容易暴露口径不一致。评审时走一遍：“如果用户退款了，这个状态怎么变？”

### 问题4：展示状态和业务状态是否一一对应？
后端业务状态8种，页面只展示4种——提前约定映射关系。否则后端新增“待审核”，前端默认归到“处理中”，用户会困惑为什么“处理中”两天没变化。

### 问题5：这个值是前端算，还是后端算？
前端算要确认规则稳定；后端算要确认接口返回是最终口径。比如“剩余天数”，前端用本地时间算、后端用服务器时间算，结果可能不同。

---

## 从页面组件到实体：别让一个页面塞进一个口径

前端常见误区：页面上有什么，就以为表里也要有什么。其实**页面组件是表现层，实体是稳定层**。

比如“商品编辑页”有基础信息表单、图片上传、规格配置、状态开关、富文本描述。后端未必只对应一张表：哪些是商品主数据、图片列表、规格明细、扩展配置？不同模块口径不同，硬塞一张表很难维护。评审时问一句：**这个页面是一个展示页面，还是多个业务实体的聚合页？**

---

## 结尾小结：先统一意思，再写代码

最怕的不是接口没通，而是接口通了，意思没通。字段名和接口结构可以统一，但**业务口径**没统一，页面照样错，统计照样偏，表设计也会走歪。

简单原则：
- **存储口径**：库里怎么记
- **展示口径**：页面怎么说
- **统计口径**：报表怎么算
- **业务口径**：大家到底在说什么

### 口径检查清单（给前端参考）

1. 这个字段的业务定义是否明确？
2. 边界情况（退款、取消、超时）是否有约定？
3. 展示状态和业务状态是否一一对应？
4. 统计口径和展示口径是否不同？
5. 这个值是前端算还是后端算？
6. 不同页面/组件对这个字段的理解是否一致？
7. 状态枚举是否写进了文档或接口说明？

把这几件事说清楚，前后端才算真的对齐。别让“同一个词，各说各的”成为你项目里的坑。

# 第12章 从一个完整业务场景看表设计：列表、表单、详情、状态一起串起来

## 开篇引入：用一个订单管理页面，把前面学的串联起来

前面几章拆了页面组件、表单字段、接口返回、JSON字段和口径协作。这一章用**订单管理**场景，把列表页、表单页、详情页、状态流转、筛选条件、按钮逻辑，从需求一步步落到数据库表结构上。

场景包含：
- **列表页**：订单号、用户名、金额、状态、创建时间
- **筛选区**：按状态、日期、关键字搜索
- **表单页**：收货人、地址、商品、备注
- **详情页**：订单明细、支付信息、物流轨迹
- **状态流转**：待支付 → 已支付 → 已发货 → 已完成 → 已取消

---

## 一、从需求到页面再到表结构：先拆页面，再看数据

### 第1步：先想业务需求

正确顺序：**先看业务需求，再看页面结构，最后落到数据库字段设计**。

先问几个问题：
- 用户要完成什么业务？
- 哪些信息在列表里快速看见？（高频摘要）
- 哪些信息只在表单里填写？（用户输入）
- 哪些信息只在详情页展开？（关联信息）
- 哪些数据随状态变化？（流程阶段）

### 第2步：拆页面，对应不同表

#### 列表页 → 高频查询的主表 + 索引
只保留排序、筛选、展示必须的字段：订单号、用户名/用户ID、订单金额、订单状态、创建时间。**不是高频字段，别硬塞进主查询。**

#### 表单页 → 主表的核心字段
注意：**表单有几个输入框，不代表表里就要有几个列**。有些字段只是中间态：
- 确认密码 → 不入库
- 省市区联动值 → 可能只存最终地址字符串
- 商品选择器 → 只存商品ID和数量

判断标准：**这个输入，是给页面用的，还是给业务存的？**

#### 详情页 → 多张表的关联组合
订单详情拆成：
- **订单主表**：基本信息（单号、金额、状态）
- **订单明细表**：商品列表（多行）
- **支付记录表**：支付过程
- **物流记录表**：发货和轨迹
- **操作日志表**：谁改过什么

所有内容塞进一个表，短期省事，长期查询慢、字段乱、扩展难。

### 第3步：前端视角下的核心检查点

- 这个表是否对应一个清晰的业务实体？
- 列表常用字段是否集中、稳定？
- 详情数据能否通过关联表补出来？
- 状态字段是否清楚、可流转？（不要用多个bool字段拼状态）
- 扩展信息是不是被硬塞进主表？
- JSON字段是否只承担扩展职责？

---

## 二、列表、表单、详情、状态之间如何串联

### 1. 四层结构，各司其职

| 层次 | 职责 | 示例 |
|------|------|------|
| 表结构 | 稳定存储 | 状态码存 `0/1/2/3` |
| 接口返回结构 | 面向页面 | 映射成 `pending / paid / shipped` |
| 页面组件结构 | 组织展示 | 显示“待支付/已支付/已发货” |
| 业务状态 | 描述流程 | 判断按钮是否可点击 |

同一状态在不同层表达可以不同，但**口径必须一致**。

### 2. 状态不要散落在页面逻辑里

好的状态设计：
- 覆盖主要业务流程
- 每个状态含义明确
- 流转清晰，不会跳步
- 页面按钮、文案、筛选条件能统一判断

如果前端自己拼 `isPaid`、`isShipped`、`isClosed`，页面一多就打架。更稳的做法：**一个主状态字段 + 少量辅助字段**。

### 3. 列表示例：从页面到表

| 列名 | 来源 |
|------|------|
| 订单号 | 订单主表的 `orderNo` |
| 用户名 | 用户表的 `nickname`（关联查询） |
| 金额 | 订单主表的 `totalAmount` |
| 状态 | 订单主表的 `orderStatus` |
| 创建时间 | 订单主表的 `createdAt` |

**列表返回的字段是数据库字段 + 关联字段 + 计算字段的混合体。**

---

## 三、前端提交数据如何影响表设计

### 1. 前端提交是业务输入，后端要收敛成稳定字段

提交地址对象：

```json
{
  "receiverName": "赵老师",
  "receiverPhone": "138xxxx",
  "address": {
    "province": "广东省",
    "city": "深圳市",
    "district": "南山区",
    "detail": "科技园xx号"
  }
}
```

两种处理方式：
- **拆成多个列**：省、市、区、详细地址（适合频繁按地区筛选）
- **存成JSON字段**：整块地址信息（适合只展示不查询）

### 2. 中间要有一个“收敛”

不是所有前端字段都原样入库。需要转换：
- 省市区联动值 → 最终存完整地址字符串
- 日期选择器 "2024-01-01" → 转标准日期格式
- 金额输入 "100.00" → 转数值存

**前端数据结构影响表设计，但不被前端绑死。** 后端要考虑未来怎么查、改、统计。

---

## 四、字段命名与接口命名的统一

### 1. 同一个东西，不要在不同层叫三种名字

至少两层统一：
- **接口命名统一**：约定 camelCase 或 snake_case，不混用
- **业务术语统一**：同一字段在文档、接口、页面、数据库语义一致

### 2. 状态字段命名尤其要小心

“状态”的种类：
- 订单状态（orderStatus）
- 支付状态（payStatus）
- 发货状态（shipStatus）
- 审核状态（auditStatus）

只写一个 `status` 在复杂业务里容易打架。**加前缀，把业务边界说清楚。**

---

## 五、JSON字段适用场景

### 1. 适合什么
- 结构不稳定，字段经常变
- 业务配置类数据
- 小范围扩展信息
- 不太需要按子字段高频查询的数据

### 2. 不适合什么
频繁筛选、排序、统计、单独更新的字段，不适合JSON。查询麻烦、索引不好做、校验不好做。

**原则：能明确结构、会频繁查询的，优先拆字段；结构不稳定、偏扩展的，再考虑JSON。**

---

## 六、前后端协作中的数据口径问题

### 1. 口径不一致翻车案例
订单金额：含税还是不含税？优惠券先减后算还是先算后减？退款后改不改原订单字段？

### 2. 好的协作顺序
1. 先定业务规则
2. 再定数据库字段
3. 再定接口返回格式
4. 最后定页面展示

### 3. 接口返回结构与表结构的区别

| 表结构 | 接口返回结构 |
|--------|--------------|
| 为存储而生 | 为页面而生 |
| 强调稳定、规范 | 强调易用、直观 |
| 字段尽量少 | 字段尽量全 |
| 状态码存数字 | 状态码转可读文本 |

接口做的事：合并多张表数据、编码值翻译、返回列表摘要字段、补充派生字段。

---

## 七、前端视角下检查表设计的3个自检问题

### 1. 列表好不好查？
每次查询跨5张表、关联字段不清晰，说明表设计有问题。

### 2. 表单好不好提？
表单提交一半是页面状态、一半是业务数据，说明没把“业务输入”和“页面状态”分开。

### 3. 状态好不好判断？
按钮是否可点击需判断3个状态字段的组合，说明状态设计有问题。一个好状态字段就能决定按钮、文案、筛选行为。

---

## 八、如何用这套思路继续看懂更多业务场景

任何页面按四步拆：

**第一步：看页面** → 列表、表单、详情，还是组合页？

**第二步：看数据** → 哪些是展示、编辑、筛选字段？

**第三步：看状态** → 对象有哪些状态？是否影响按钮和文案？

**第四步：看落库** → 哪些是业务事实、临时态、适合JSON、该拆字段？

核心映射：
- 页面组件 ≈ 业务视图
- 表单字段 ≈ 业务输入
- 列表字段 ≈ 高频摘要
- 详情页 ≈ 多源信息组合
- 状态字段 ≈ 流程阶段
- 接口返回 ≈ 面向前端的组织结果
- 数据库表 ≈ 面向存储的稳定结构

---

## 结尾小结

**数据库设计不是从字段开始，而是从业务页面和业务流程开始。**

关键是把这几层串起来：列表看什么、表单填什么、详情展什么、状态怎么流、哪些字段该入库、JSON适用场景、接口怎么返回、表结构怎么稳定承接。

### 行动清单（前端视角）
1. 新页面按“看页面→看数据→看状态→看落库”四步拆
2. 列表、表单、详情、状态对应不同表和查询方式
3. 名字统一，口径一致，少用JSON存高频查询字段
4. 页面状态和业务数据分开，临时态不入库
5. 接口返回结构 ≠ 表结构，多了关联、计算、转换

这套方法能看懂80%的业务场景，剩下20%靠项目经验打磨。
