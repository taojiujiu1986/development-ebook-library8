# 第1章 先搞懂 Web 接口：前端到底在和谁说话

## 开篇引入：你不是在“连后端”，你是在“发消息”

如果你有前端经验，那你一定见过这些场景：

- 页面一加载，就拿到列表数据；
- 点一下“提交”，弹出“保存成功”；
- 表单填错了，页面提示“手机号格式不对”；
- 刷新后，数据又变了。

这些动作背后，前端其实一直在跟“看不见的人”说话，这个人就是后端接口。

你可以先把 **Web 接口** 理解成：**前端和后端之间的对话窗口**。  
前端把需求说出去，后端听懂后把结果回回来。

这章先不急着写代码，因为很多新手卡在第一步：名词都认识，放一起就乱了。其实只要先弄明白“接口是在干嘛”，后面学 FastAPI 时，路由、参数、请求体、响应这些概念都会顺很多。FastAPI 本质上就是：**帮你更方便地搭起这个对话窗口**。

---

## 什么是 Web 接口：把它理解成前后端的“对话窗口”

在前端里，你可能更熟悉“调用接口”这个说法。比如：

```js
fetch('/api/user/list')
```

这不是“打开网页”，而是“向某个地址发消息，问它：能不能给我用户列表”。

这里：

- **接口地址**：你找谁说话；
- **请求**：你发出了消息；
- **响应**：对方回给你的内容。

### 一个更直观的类比

接口可以理解成餐厅点餐：

- **前端**：顾客，负责说自己要什么；
- **接口**：传话窗口；
- **后端**：厨房，负责处理和制作；
- **响应**：端上来的菜。

顾客不需要知道厨房怎么炒菜，前端也不需要知道数据库怎么查，只要把需求按规则交出去就行。

### 为什么一定要有接口

如果没有接口，前端和后端就像两个人说不同方言：

- 前端不知道数据从哪来；
- 后端不知道页面想要什么格式；
- 每改一次，都得重新对齐。

接口的作用，就是把双方的约定固定下来。这个约定通常至少包括三件事：

1. **地址是什么**：比如 `/api/user/info`
2. **用什么方式说话**：GET 还是 POST
3. **返回什么内容**：成功给数据，失败给错误信息

这就是后端开发里很重要的“契约意识”。约定清楚了，前端才好写，后端也才好维护。

---

## 请求与响应：一次完整的接口调用长什么样

接口不是单向发消息，它是一个完整的往返流程。

### 第一步：前端发起请求

比如进入“用户详情”页时，前端会请求用户信息：

```js
fetch('/api/user/info?id=1001')
```

这里的 `id=1001` 很明确：我要查 1001 这个用户。

### 第二步：后端接收请求并处理

后端拿到请求后，通常会做几件事：

- 看你请求的是哪个接口；
- 判断你传了哪些参数；
- 可能去查数据库；
- 最后整理成标准结果返回。

你可以把这一步理解成：后端先“读懂”，再决定怎么处理。

### 第三步：后端返回响应

后端通常返回结构化数据，比如 JSON：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 1001,
    "name": "老赵",
    "role": "admin"
  }
}
```

前端拿到结果后，再决定怎么渲染页面、怎么弹提示、怎么处理错误。

### 最容易混淆的一点

很多新手会把“请求成功”当成“业务成功”，其实不是。

- 网络连通了，只能说明 **请求成功**；
- 但后端返回 `code: 1`，说明 **业务失败**；
- 还有可能超时，连响应都没有。

所以联调时，不只是看“有没有返回”，还要看返回内容是不是符合预期。  
接口联调不是“通没通”，而是“通得对不对”。

---

## 请求方法：GET、POST、PUT、DELETE 分别像什么

请求方法就像你和后端说话时的“语气”和“动作”。

### 1. GET：我要查一下

GET 通常用于获取数据，比如列表、详情。

特点很简单：

- 一般用于查询；
- 参数常放在地址后面；
- 不适合提交敏感信息。

### 2. POST：我要新增一条

POST 常用于提交新数据，比如注册、发帖、创建订单。

它更像把一整份内容打包交给后端，让后端去处理。

### 3. PUT：我要整体更新一下

PUT 一般表示更新资源，通常偏“整条更新”。

你可以理解成：不是改一两个点，而是把这个对象整体换成新的状态。

### 4. DELETE：我要删掉它

DELETE 顾名思义，就是删除，比如删除待办事项、移除记录。

### 前端新手最常见的误区

有些同学会觉得：

> 反正都是发请求，随便用一个方法不就行了？

不太行。请求方法本身就是接口设计的一部分，它会影响：

- 后端怎么写逻辑；
- 接口文档怎么写；
- 前端联调时怎么传参；
- 安全和语义是否清晰。

所以接口开发不是“能通就行”，而是要“通得合理”。  
这也是为什么后面学 FastAPI 时，会先讲路由和请求方法，因为这是接口的基本语法。

---

## 接口开发和前端页面开发：有什么区别，又怎么配合

前端页面开发，核心是“展示”和“交互”；接口开发，核心是“收数据”和“给数据”。

### 前端更像在做什么

你会关心：

- 页面布局怎么排；
- 按钮点击后怎么变化；
- 表单校验怎么写；
- 列表加载时怎么展示 loading。

### 后端接口更像在做什么

后端会关心：

- 这个接口收什么参数；
- 参数合法不合法；
- 数据从哪里查；
- 出错时怎么返回；
- 返回结构是否统一。

### 二者怎么配合

前后端是一条流水线：

1. 前端展示页面；
2. 前端发请求；
3. 后端处理数据；
4. 后端返回结果；
5. 前端根据结果更新页面。

你可以把前端当成“表现层”，把后端当成“数据层”。  
前端负责让用户看懂，后端负责让数据跑通。

### 为什么前端新手学接口更容易上手

因为你会天然关注“我发出去的请求，对方为什么没回”：

- 是地址写错了？
- 是方法不对？
- 是参数名不一致？
- 还是返回格式和预期不一样？

这些问题，基本就是联调的日常。前端出身的人，往往更容易从“请求发出去了没有”“返回的数据对不对”这个角度理解后端，这其实是优势。

---

## 为什么前端新手也要懂接口：联调、数据流、页面状态都离不开它

如果你只会写页面，不懂接口，项目做到后面，很容易卡在“数据接不上”。

### 1. 联调离不开接口理解

联调就是前后端一起把功能跑通。你要知道：

- 接口地址是什么；
- 请求方法是什么；
- 参数怎么传；
- 返回值怎么看。

否则你看到报错，只会说“接口坏了”，但说不出到底是哪一环坏了。真正排查问题，靠的是顺着请求链路一层层看。

### 2. 数据流离不开接口理解

页面上的数据不是凭空出现的，它们会经历：

**接口返回 → 前端存起来 → 页面渲染出来 → 用户操作后再发回去**

如果不理解这个流程，就很难明白：

- 为什么要在 `onMounted` 里拉数据；
- 为什么提交后要重新请求；
- 为什么删除后要刷新列表；
- 为什么状态管理和接口请求总绑在一起。

### 3. 页面状态离不开接口理解

“加载中”“空状态”“错误提示”“成功提示”，很多都是围绕接口结果设计的：

- 请求中：显示 loading；
- 请求成功但数据为空：显示空页面；
- 请求失败：显示错误提示；
- 提交成功：关闭弹窗并刷新列表。

也就是说，你前端写得顺不顺，很多时候不只是看 UI，而是看接口设计是不是清楚。

---

## 一个小例子：从按钮点击到页面更新

假设你做了一个“待办事项”页面。

### 用户操作

用户点击“新增待办”，输入内容后提交。

### 前端做的事

- 收集输入框内容；
- 发起 POST 请求；
- 等待后端返回；
- 成功后刷新列表；
- 失败后提示原因。

### 后端做的事

- 接收请求体；
- 检查内容是否为空；
- 保存到数据库；
- 返回新创建的待办数据。

你看，这整个过程就像接力赛。  
前端不是“把数据丢过去就完了”，后端也不是“随便回个字符串就行了”，双方要在接口上把规则对齐。

如果后面要做登录、修改资料、删除订单，流程本质上都差不多：前端发请求，后端处理，最后返回统一格式的数据。

---

## 常见坑点：新手最容易栽在哪

### 坑 1：只看页面效果，不看返回结构

页面能不能显示出来，取决于返回数据结构是不是你想要的。很多时候不是接口没返回，而是你拿错了字段，或者后端字段名变了，前端还按老字段读。

### 坑 2：把 GET 和 POST 混着用

查询一般用 GET，新增一般用 POST。方法乱用，后面写文档、做校验、排查问题都会变麻烦。

### 坑 3：参数名不统一

前端传 `userId`，后端收 `id`，就会出现“明明传了参数却取不到”的问题。接口设计阶段最好先对齐参数名，别等联调时才发现对不上。

### 坑 4：只关心成功，不关心失败

真实项目里，失败才是常态之一。你要提前考虑：

- 参数缺失怎么办；
- 数据不存在怎么办；
- 服务器异常怎么办。

接口写得好，不是只在成功时能跑通，而是在失败时也能给出清楚的反馈。

## 本章小结：先把“说话规则”弄明白，再去学 FastAPI

如果你把这一章吃透，后面学 FastAPI 会轻松很多，因为你已经知道：

- **Web 接口**就是前后端之间的对话窗口；
- 一次请求包含 **请求** 和 **响应**；
- GET、POST、PUT、DELETE 是不同的“说话方式”；
- 前端页面开发和接口开发是配合关系，不是彼此孤立；
- 前端新手理解接口，能直接提升联调、数据流和页面状态处理能力。

你现在不需要把后端想得很复杂，先记住一句话就够了：

> 前端不是在“连后端”，而是在按照规则发消息、收结果。

接下来我们就要真正进入 FastAPI。  
你可以把 FastAPI 理解成：**帮后端更快、更清晰地把接口这套“对话规则”写出来的工具**。

下一章开始，我们会从安装、启动，到第一个接口，一步一步把这个窗口搭起来。

# 第2章 开发前准备：安装 Python、创建项目和跑通第一个 FastAPI

## 开篇引入：先别急着写业务，先把“车”发动起来

很多前端同学第一次学后端，容易一上来就想写“登录”“待办事项”“数据库增删改查”。方向没错，但顺序容易乱，最后常常卡在依赖、环境和启动报错上，连服务有没有跑起来都不确定。

所以这一章先不追功能，先做最重要的一件事：**把 FastAPI 跑起来**。

你可以把它理解成第一次搭前端项目时要做的事：

- 安装基础运行环境
- 初始化项目
- 启动开发服务
- 打开浏览器确认结果

后端也一样。学 FastAPI 的第一步，不是背概念，而是先确认这几件事都成立：

1. Python 环境可用  
2. 依赖装得对  
3. 目录结构清楚  
4. 能启动一个最小接口  
5. 能在浏览器里看到结果  

只要这一步打通，后面学路由、参数、请求体、文档、数据库都会顺很多。

---

## 一、先确认 Python 环境能用

### 1.1 FastAPI 依赖什么版本的 Python

FastAPI 基于 Python，所以第一步不是装 FastAPI，而是确认 Python 环境正常。就像你写 Vue 前先看 `node -v` 一样，基础环境不通，后面全白搭。

建议优先使用：

- **Python 3.10 或 3.11**
- 尽量别用太老的版本

原因很简单：新版 Python 在语法、类型提示和生态兼容性上更友好，而 FastAPI 又很依赖类型提示来做参数校验和自动文档生成。版本太旧，容易遇到兼容问题。

### 1.2 怎么检查 Python 是否安装成功

打开终端：

```bash
python --version
```

或者：

```bash
python3 --version
```

如果输出类似：

```bash
Python 3.11.4
```

说明 Python 基本可用。

#### 常见判断标准

- 能输出版本号：已安装
- 版本太旧：建议升级
- 提示找不到命令：说明环境变量没配好，或者根本没装

Windows 用户如果 `python` 和 `python3` 都不认识，先确认 Python 是否安装，并检查安装时有没有勾选 **Add Python to PATH**。PATH 可以先粗略理解成“系统能不能找到这个命令”。

### 1.3 为什么不要直接往系统环境里乱装依赖

对前端同学来说，这一步最像项目依赖管理：不同项目可能依赖不同版本的库，共用一套环境很容易互相污染。今天装一个库，明天另一个项目可能就冲突。

所以后端项目最常见的做法是：**给每个项目单独建虚拟环境**。这样项目之间互不影响，迁移和复现也更方便。

---

## 二、创建虚拟环境与安装依赖

### 2.1 什么是虚拟环境

虚拟环境就是给当前项目单独开一个“依赖小房间”，里面的库只给这个项目用。

好处很直接：

- 避免依赖冲突
- 项目更容易迁移
- 别人拉代码更容易复现
- 自己切换项目时不容易串环境

如果你熟悉前端的项目依赖管理，这个思路其实很像：**项目归项目，环境归环境**。

### 2.2 创建虚拟环境的步骤

先进入项目目录：

```bash
mkdir fastapi-demo
cd fastapi-demo
```

创建虚拟环境：

```bash
python -m venv .venv
```

推荐用 `.venv` 作为目录名，清楚、常见、不容易混淆。

然后激活它。

#### Windows：

```bash
.venv\Scripts\activate
```

#### macOS / Linux：

```bash
source .venv/bin/activate
```

激活后，命令行前面通常会出现：

```bash
(.venv)
```

这表示你已经在当前项目的独立环境里了。

#### 常见坑点

- 激活后前缀没变化：可能没激活成功
- PowerShell 报权限问题：可能需要调整执行策略
- 切换终端后环境失效：记得重新激活

如果不确定是否成功，再执行一次：

```bash
python --version
```

看是不是当前虚拟环境里的 Python。

### 2.3 安装 FastAPI 和启动服务所需依赖

FastAPI 本身只是框架核心，真正把服务跑起来，还需要一个 ASGI 服务器。入门阶段通常安装：

```bash
pip install fastapi uvicorn
```

这两个包分别负责：

- **fastapi**：接口定义、参数校验、自动文档
- **uvicorn**：把 FastAPI 服务真正启动起来

可以理解成：

- FastAPI = 业务框架
- Uvicorn = 启动器

前端里也有类似分工：

- React / Vue 负责业务逻辑
- Vite / Webpack 负责启动和开发服务

### 2.4 为什么要分开理解“框架”和“服务器”

很多新手会疑惑：为什么装了 FastAPI 还不能直接运行？

因为：

- FastAPI 负责“怎么写接口”
- Uvicorn 负责“怎么把接口服务起来”

FastAPI 像你写业务代码的地方，Uvicorn 像把代码挂到端口上对外提供访问的工具。一个管定义，一个管运行。

### 2.5 检查安装是否成功

执行：

```bash
pip list
```

确认里面有：

- fastapi
- uvicorn

如果想保存依赖清单，后面常用：

```bash
pip freeze > requirements.txt
```

以后别人拿到项目，只要执行：

```bash
pip install -r requirements.txt
```

就能装出相同依赖。

## 三、项目初始化建议：最简单的目录和入口文件怎么放

### 3.1 入门阶段，目录越简单越好

刚开始学 FastAPI，不要一上来就分很多层。目录太复杂，容易把精力浪费在“找文件”上。新手阶段最重要的不是架构好看，而是逻辑清楚、能跑通。

推荐先用最简单的结构：

```text
fastapi-demo/
├── .venv/
├── main.py
└── requirements.txt
```

保留三个关键东西就够了：

- `.venv/`：虚拟环境
- `main.py`：项目入口文件
- `requirements.txt`：依赖记录文件

### 3.2 为什么入口文件建议叫 `main.py`

因为它最直观，启动时也好记。对新手来说，统一入口文件名，可以减少“到底该运行哪个文件”的混乱。

真实项目里当然不一定非得叫这个名字，但入门阶段建议先用最简单的方式，先把流程跑通，再去理解更复杂的拆分。

### 3.3 为什么要保留 `requirements.txt`

这相当于依赖清单。别人拿到代码后，直接执行：

```bash
pip install -r requirements.txt
```

就能复现环境。

生成方式：

```bash
pip freeze > requirements.txt
```

它的价值在于：让项目从“我电脑上能跑”变成“别人也能跑”。对于协作、重装系统，或者和同学一起练习都很有用。

### 3.4 入门阶段的目录原则

记住一句话：

> 入门阶段先追求“能跑”，再追求“好看”。

先让项目有明确入口、清晰依赖、稳定运行方式，后面理解路由、业务层和数据库后，再慢慢拆分也不迟。

---

## 四、编写第一个 FastAPI 接口并启动服务

### 4.1 第一个接口尽量短一点

打开 `main.py`，写入：

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
def hello():
    return {"message": "Hello FastAPI"}
```

这就是最小可运行的 FastAPI 程序。先别嫌它简单，我们现在要做的不是“写得多”，而是“先跑通”。

逐行看：

- `from fastapi import FastAPI`：导入框架
- `app = FastAPI()`：创建应用实例，后面所有路由都挂在它上面
- `@app.get("/")`：定义一个 GET 请求的根路径路由
- `def hello():`：处理请求的函数
- `return {"message": "Hello FastAPI"}`：返回字典，FastAPI 会自动转成 JSON

### 4.2 这段代码为什么这样写

FastAPI 的核心思路就是：**用函数定义接口**。

这和前端写事件处理很像：

- 写一个 `handleClick`
- 某个事件发生时触发它
- 函数返回结果或更新状态

这里只是把“事件”换成了“请求”。也就是说，前端是用户行为触发函数，后端是接口请求触发函数，本质都是“事件来了，执行处理逻辑”。

### 4.3 为什么先只写一个 GET /

入门阶段别急着把参数、请求体、数据库都塞进来。先写一个最简单的接口，目的很明确：

- 先确认项目能跑
- 先确认路由能命中
- 先确认返回值能看到
- 先建立“我真的写出了一个后端接口”的信心

这一步特别重要。很多人学后端卡住，不是卡在难点上，而是卡在一开始就把难度抬得太高。

### 4.4 启动服务

在项目根目录执行：

```bash
uvicorn main:app --reload
```

这里要看懂三部分：

- `main`：文件名，不带 `.py`
- `app`：FastAPI 实例名
- `--reload`：代码修改后自动重启，适合开发阶段

可以理解为：告诉 Uvicorn 去 `main.py` 里找 `app`，把它跑起来。

`--reload` 很像前端开发里的热更新，改完代码不用手动重启，体验更顺。

### 4.5 启动成功后怎么看结果

终端一般会看到：

```text
Uvicorn running on http://127.0.0.1:8000
```

然后打开浏览器访问：

```text
http://127.0.0.1:8000
```

如果看到：

```json
{"message":"Hello FastAPI"}
```

说明第一个接口已经跑通了。

记住：**路由命中后，函数返回什么，浏览器就能看到什么。**

### 4.6 这一步已经串起了最基础的接口流程

你现在已经走通了最基础的接口链路：

1. 访问某个 URL
2. 请求命中路由
3. 路由找到对应函数
4. 函数返回数据
5. FastAPI 自动转成 JSON 响应

这就是接口开发最底层的流程。后面不管是查询参数、路径参数，还是请求体和数据库，本质上都是在这个流程上继续加内容。

## 五、常见坑点：先记住这几个，能少走很多弯路

新手学后端，很多时间不是花在写代码上，而是花在排错上。下面这些坑很常见，早点知道会省很多时间。

### 5.1 端口占用：为什么启动时提示地址已被占用

如果看到：

```text
Address already in use
```

说明 8000 端口被别的程序占了。

#### 解决办法

换端口启动：

```bash
uvicorn main:app --reload --port 8001
```

然后访问：

```text
http://127.0.0.1:8001
```

#### 判断标准

- 能启动：端口可用
- 报端口占用：换端口即可
- 同一时间不要多个服务抢同一个端口

这和前端本地 dev server 端口冲突是一个道理：**一个端口同一时间只能被一个程序正常占用。**

### 5.2 依赖安装失败：为什么 `pip install` 会报错

常见原因有：

- 网络问题，下载慢或失败
- Python 版本太旧
- 虚拟环境没激活
- `pip` 版本太旧

可以先升级：

```bash
python -m pip install --upgrade pip
```

排查顺序建议：

1. 确认虚拟环境已激活
2. 确认 Python 版本合适
3. 再安装 fastapi 和 uvicorn
4. 安装失败时先看报错最后几行

很多时候不是 FastAPI 太难，而是环境没对齐。

### 5.3 启动文件写错：为什么 `uvicorn main:app` 会报找不到

最常见的几种情况：

#### 情况 1：文件名不叫 `main.py`

比如文件是 `app.py`，那命令就要写：

```bash
uvicorn app:app --reload
```

#### 情况 2：FastAPI 实例名不是 `app`

如果你写的是：

```python
server = FastAPI()
```

启动命令就要对应改成：

```bash
uvicorn main:server --reload
```

#### 情况 3：代码里有语法错误

比如少括号、缩进错、导入路径写错，都会导致启动失败。

#### 排查顺序建议

1. 先看文件名  
2. 再看实例名  
3. 再看语法  
4. 再看端口是否被占用  

按这个顺序查，效率会高很多。

# 第3章 路由与请求方法：让接口有“地址”可找

## 开篇引入：接口写出来以后，客户端怎么找到它

前面我们已经知道，FastAPI 可以很快帮我们写出一个接口。  
但接口写出来之后，客户端怎么知道“去哪儿找它”呢？

答案就是：**路由**。

你可以先把它理解成一张“地址卡”：

- **接口** = 一间店
- **路由** = 店铺地址
- **请求方法** = 你来这家店是想“看看”“下单”“修改”还是“退掉”
- **路径** = 具体门牌号，比如 `/todos`、`/users/1`

如果你是前端出身，这个概念其实很好理解。前端有页面路由，比如 `/home`、`/login`、`/user/123`，不同路径会跳到不同页面。后端路由也类似，只不过它不是负责渲染页面，而是负责把请求分发给对应的接口函数。

这一章你先记住一句最核心的话：

> **路由负责把请求送到正确的函数，请求方法负责说明这次请求要做什么。**

这句话先记住，后面你看任何接口定义，都会轻松很多。

---

## 一、什么是路由：接口地址和前端路由思维的类比

### 1. 路由到底是什么

在 FastAPI 里，路由本质上就是：

- 一个**请求路径**
- 加上一个**请求方法**
- 再匹配到一个**处理函数**

比如：

- `GET /users`
- `POST /users`
- `GET /users/1`
- `DELETE /users/1`

它们看起来都和 `users` 有关，但含义完全不同。

你可以把它想成快递柜：

- **路径** 是柜子的编号
- **方法** 是你想做的动作
- **处理函数** 是负责处理这件事的人

同样是访问 `/users/1`，你是要看这个用户、改这个用户，还是删掉这个用户，要靠请求方法区分。

### 2. 为什么路由一定要存在

如果没有路由，服务端就不知道该把请求交给谁处理。  
这就像你到商场只说“我要找个人”，但不说楼层、不说店铺、不说部门，别人根本没法帮你定位。

路由的作用就是做“分发规则”：

- 路径决定找哪类资源
- 方法决定执行哪种操作

这也是 REST 风格接口里最基础的思路。你现在不用把 REST 想得很高深，先把它理解成一种更规整、更好沟通的接口组织方式就够了。

### 3. 前端视角怎么理解

前端同学通常很熟悉这种写法：

```js
router.push('/login')
```

或者：

```js
axios.get('/api/user')
```

前者是页面跳转，后者是请求数据。虽然一个是前端路由，一个是后端路由，但你可以先用一个朴素的类比来记：

- 前端路由：决定显示哪个页面
- 后端路由：决定执行哪个接口逻辑

共同点是：**都通过“路径”来定位目标**。

区别在于，前端路由决定“展示什么”，后端路由决定“处理什么”。这个差别先记住，后面你看接口文档时会非常顺。

---

## 二、GET、POST、PUT、DELETE：先记住它们各自负责什么

### 1. 请求方法是什么

请求方法就是告诉服务端：**这次请求想干什么**。

最常见的四个方法，你先记住它们的“人话含义”：

- **GET**：获取数据
- **POST**：新增数据
- **PUT**：更新数据
- **DELETE**：删除数据

你以后看到一个接口，先别急着看代码，先看方法，基本就能猜到它的用途。

### 2. FastAPI 里的基础写法

FastAPI 写路由很直接，通常就是这样：

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/users")
def get_users():
    return {"message": "获取用户列表"}

@app.post("/users")
def create_user():
    return {"message": "新增用户"}

@app.put("/users/1")
def update_user():
    return {"message": "更新用户"}

@app.delete("/users/1")
def delete_user():
    return {"message": "删除用户"}
```

这里你要看懂三件事：

#### ① `@app.get("/users")`
表示这个函数负责处理 `GET /users` 请求。

#### ② `def get_users():`
这是处理函数，收到请求后就执行它。

#### ③ `return {...}`
表示把响应内容返回给客户端。

也就是说，**装饰器负责注册路由，函数负责处理业务**。

你可以把装饰器理解成“贴标签”：这个函数是给哪个路径、哪个方法用的。FastAPI 看到这个标签之后，就知道请求来了该找谁。

### 3. 四种请求方法的适用场景

先别急着记太多理论，直接记一张对照表最省事。

| 请求方法 | 作用 | 常见场景 | 你可以怎么理解 |
| --- | --- | --- | --- |
| GET | 获取数据 | 列表、详情、搜索 | 只看，不改 |
| POST | 新增数据 | 注册、创建订单、提交表单 | 新建一个资源 |
| PUT | 更新数据 | 修改资料、编辑内容 | 整体替换或更新资源 |
| DELETE | 删除数据 | 删除用户、删除待办 | 把资源移除 |

### 4. 一个简单的理解方式

你可以把它想成去餐厅：

- `GET`：看菜单、看账单
- `POST`：点菜、下单
- `PUT`：改订单
- `DELETE`：取消订单

地址没变，动作变了。  
这就是路由设计里最常见的思路：**路径表达资源，方法表达动作**。

---

## 三、路径设计的基本习惯：接口名要表达清楚资源含义

### 1. 路径不是随便起名字

很多初学者写接口时，最容易犯的错误就是把接口写成“函数名风格”，比如：

- `/getUserList`
- `/createUser`
- `/deleteUser`
- `/doUpdate`

这种写法不是不能用，但它不够清晰，也不太符合接口设计的习惯。

更推荐的方式是：**用资源名来设计路径**。

比如：

- `/users`
- `/users/1`
- `/todos`
- `/todos/12`

这样一看就知道在操作什么资源。

### 2. 推荐的路径设计思路

你可以用这个简单公式来设计路径：

> **资源名 + 资源标识，动作交给请求方法**

比如：

- `/users`：用户集合
- `/users/{id}`：某一个用户
- `/orders`：订单集合
- `/orders/{order_id}`：某个订单

然后再配合方法：

- `GET /users`：查看用户列表
- `POST /users`：新增用户
- `GET /users/1`：查看编号为 1 的用户
- `PUT /users/1`：更新编号为 1 的用户
- `DELETE /users/1`：删除编号为 1 的用户

这样设计的好处很明显：

1. 一眼能看出资源归属  
2. 路径更统一  
3. 后期维护更轻松  
4. 前后端沟通更顺畅  

对前端同学来说，这就像你在代码里给变量起名：名字越直观，后面越省事。

### 3. 尽量用名词，不要把动词写死在路径里

#### 不太推荐：

- `/getUser`
- `/addUser`
- `/removeUser`

#### 更推荐：

- `/users`
- `/users/{id}`

原因很简单：

- 路径里如果写死动词，会把动作和地址绑在一起
- 后面一旦操作方式变化，路径就容易变乱
- 用资源名更符合通用接口设计习惯

你可以先把它记成一句很实用的话：

> **接口地址是“谁”，请求方法是“做什么”。**

这句话以后你写任何接口都可以拿来当判断标准。

### 4. 命名时的几个小建议

#### ① 用复数名词更自然
比如：

- `/users`
- `/products`
- `/todos`

这表示一个资源集合。

#### ② 层级不要太深
路径层级太深会变得很难读。

比如：

- `/api/v1/project/1/task/2/comment/3`

这种不是不能写，但初学阶段建议先写简单一点。路径一深，排查问题也更麻烦，不利于你建立接口直觉。

#### ③ 路径风格统一
团队里最好统一风格：

- 要么都用小写单词
- 要么都用小写加短横线

FastAPI 本身对路径写法要求不复杂，但你自己最好保持一致。统一风格的好处是：你以后看代码时不会被路径命名分散注意力。

---

## 四、同一路径不同请求方法：最适合做资源型接口

### 1. 为什么要区分“同一路径，不同方法”

这是接口设计里很实用的一点。

比如你有一个资源 `/todos`，它既可以：

- 查看列表
- 新增事项

这两个操作都围绕同一个资源，但含义不一样，所以用不同请求方法区分最合理。

这样能避免你写出很多重复路径，比如：

- `/getTodos`
- `/createTodo`
- `/removeTodo`

一旦项目大一点，这种命名会很散，也不利于接口文档整理。

### 2. 一个典型例子：待办事项接口

假设我们做一个待办事项 API。

#### 查看列表
```python
@app.get("/todos")
def list_todos():
    return {"data": ["买菜", "写代码"]}
```

#### 新增待办
```python
@app.post("/todos")
def create_todo():
    return {"message": "新增待办成功"}
```

#### 更新某条待办
```python
@app.put("/todos/1")
def update_todo():
    return {"message": "更新待办成功"}
```

#### 删除某条待办
```python
@app.delete("/todos/1")
def delete_todo():
    return {"message": "删除待办成功"}
```

这里你会发现，路径设计很统一，逻辑也更清晰。

如果后面再扩展一个“查看某一条待办详情”，你可以继续写：

```python
@app.get("/todos/{todo_id}")
def get_todo(todo_id: int):
    return {"todo_id": todo_id}
```

这样一来，资源层级就很明确：

- `/todos`：整个待办集合
- `/todos/{todo_id}`：某一条待办

这比到处起 `/getTodoById` 之类的名字要稳得多。

### 3. 为什么这种习惯对前后端协作很重要

如果前后端一起协作，统一的路径和方法会让大家少很多沟通成本。

前端同学看到：

- `GET /todos`
- `POST /todos`
- `PUT /todos/1`
- `DELETE /todos/1`

基本就知道怎么调了。

因为它符合一种很自然的接口表达方式：

- 资源是什么
- 请求要做什么
- 参数从哪里来

这样写出来的接口文档也更清楚，前端直接照着文档请求就行，不用反复问“这个接口到底是干什么的”。

---

## 五、常见坑点提示：路径写法、斜杠、请求方法不匹配

这一节很重要。新手写路由时，很多报错不是代码逻辑错，而是**路径和方法没对上**。

### 1. 路径写法要统一

#### 坑点一：路径前后的斜杠不统一

比如你定义的是：

```python
@app.get("/users/")
def get_users():
    return {"message": "ok"}
```

但你请求时写成：

```text
/users
```

或者反过来，某些情况下会出现重定向、跳转，甚至你以为能访问其实访问方式不一致。

**建议：**  
尽量统一团队风格，常见做法是路由路径写法保持一致，不要一会儿带斜杠，一会儿不带。

这个坑在小项目里不一定马上爆，但项目一多，风格不统一就很烦人。

### 2. 请求方法不匹配

这是最常见的坑之一。

比如你定义的是：

```python
@app.get("/users")
def get_users():
    return {"message": "ok"}
```

但你在前端或者接口测试工具里发的是 `POST /users`。

这时服务端不会帮你自动猜，而是直接告诉你方法不对。

这就像你去窗口办事，窗口只受理“查询”，你却拿着“办理新业务”的材料过去，工作人员肯定会说你走错了。

**解决思路：**

- 看清楚接口定义的是 GET 还是 POST
- 前端请求方法要和后端一致
- 文档里复制接口时，不要只复制路径，方法也要一起看

### 3. 路径参数位置写错

如果你定义的是：

```python
@app.get("/users/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}
```

那么请求应该是：

```text
/users/1
```

而不是：

```text
/users?user_id=1
```

当然后面你会学查询参数，这里先记住：  
**路径参数必须放在路径里，不能乱放。**

如果你把参数放错位置，FastAPI 可能不会按你想的方式匹配请求，最后就会出现“我明明传了参数，怎么函数里没拿到”的情况。

### 4. 静态路径和动态路径冲突

这个坑很隐蔽，很多人第一次写项目时容易踩。

比如你写了两个很像的路径：

```python
@app.get("/users/me")
def get_me():
    return {"name": "me"}

@app.get("/users/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}
```

如果顺序和设计不注意，`/users/me` 可能会被动态路径当成参数去匹配，导致请求进了错误的函数。

**建议：**

- 静态路径尽量放在动态路径前面
- 命名时避免冲突
- 设计时先想清楚谁更具体

这类问题在项目里很常见，属于“看上去没报错，但请求却进了错误函数”的隐蔽坑。

### 5. 只写接口不测试，很容易以为自己写对了

很多初学者写完路由后，只看代码不发请求，结果后面一测发现方法不对、路径不对、返回也不对。

**建议你养成一个习惯：**

1. 写完一个接口  
2. 立刻用浏览器、Swagger 或工具发请求  
3. 看是否进入预期函数  
4. 看返回内容是否符合预期  

接口开发不是“写完就算完”，而是“写完后验证能不能被正确找到”。

这一步看着简单，但特别关键。很多学习卡住，不是因为不会写，而是因为没养成“写完就测”的习惯。

## 六、把请求方法放到真实场景里看一遍

为了让你更有画面感，我们把这四种请求方法放到一个小项目里看看。

假设你在做一个“用户资料管理”接口。

### 1. 查看用户列表
```python
@app.get("/users")
def list_users():
    return {"data": []}
```

适合页面打开时先拉一批数据，像前端进入列表页就请求接口。

### 2. 新增用户
```python
@app.post("/users")
def create_user():
    return {"message": "新增成功"}
```

适合注册、创建、提交新数据。

### 3. 修改用户资料
```python
@app.put("/users/1")

    return {"message": "更新成功"}
```

适合编辑信息、保存修改。

### 4. 删除用户

```python
@app.delete("/users/1")

```

适合移除不再需要的数据。

一旦资源名统一，方法含义明确，接口就不容易写乱。

## 七、这一章你应该形成的接口设计检查清单

以后你自己写路由时，可以按下面这张清单快速自查。

### 1. 路径是否表达了资源
- 这是用户、订单、待办、文章，还是别的资源？
- 有没有用名词表达清楚？

### 2. 请求方法是否合理
- GET 是不是只做查询？
- POST 是不是做新增？
- PUT 是不是做更新？
- DELETE 是不是做删除？

### 3. 路径是否统一
- 有没有同一项目里一会儿带斜杠、一会儿不带？
- 命名风格是否一致？

### 4. 是否区分了集合和单个资源
- `/users` 和 `/users/1` 有没有区分清楚？
- 是列表还是详情？

### 5. 是否测试过
- 代码写完后有没有真正发请求试一下？
- 是否确认请求方法和路径都正确？

你以后只要养成这个检查习惯，路由部分基本就不会乱。

## 八、一个最小可用的路由示例：先把思路跑通

```python
from fastapi import FastAPI

app = FastAPI()
```

- GET 查列表
- POST 新增
- `/books/1` 是具体某一本书
- PUT 更新
- DELETE 删除

这就是最基础的接口路由思维。

如果你愿意再往前走一步，可以自己把 `1` 换成变量，写成路径参数的形式。先不用着急，现在你只需要先记住：**路径负责定位资源，方法负责说明动作**。

这一章你最该记住的，不是某个固定代码，而是路由的思维方式：

- **路径**负责告诉你资源在哪里
- **请求方法**负责告诉你要对资源做什么
- **处理函数**负责真正执行逻辑

- 路径像页面地址
- 方法像用户动作
- 路由像分发规则

# 第4章 查询参数与路径参数：把前端传来的值接住

## 开篇引入：接口不是“写死的页面”，而是“会接收输入的服务”

前面我们知道，FastAPI 本质上是在写接口。接口真正有价值的地方，不只是“能返回数据”，而是**能接收数据，再根据数据做不同的事**。

如果你有前端经验，可以这样理解：

- **查询参数**：像搜索关键词、分页页码、筛选条件；
- **路径参数**：像详情页里的 ID，比如 `/users/12` 里的 `12`。

这两类参数是接口开发里最常见的基础能力。没弄明白，后面写请求体、做校验、查数据库时，就容易分不清“值到底从哪来”。

这一章只做一件事：**把前端传来的值接住，并且知道该接到哪里。**

---

## 一、先记住最核心的区别：一个负责“筛选”，一个负责“定位”

刚入门时，不用先背术语，先记判断标准就够了：

- **查询参数**：适合筛选、搜索、分页、排序
- **路径参数**：适合表示某个具体资源的 ID

可以把它理解成：

- 查询参数是在说：**“我要怎么找”**
- 路径参数是在说：**“我要找谁”**

### 1.1 查询参数：适合“可变条件”

比如商品列表：

```bash
GET /items?keyword=phone&page=2
```

`keyword`、`page` 不是资源身份，而是查列表时加的条件。它们通常不是每次都必须传，而且经常会变。

### 1.2 路径参数：适合“唯一定位”

比如看某个用户详情：

```bash
GET /users/8
```

这里的 `8` 是在告诉后端：我要的是第 8 个用户。它更适合详情、修改、删除这类必须明确对象的场景。

### 1.3 一个简单判断法

以后看到参数，先问一句：

- 它是“条件”吗？那多半是查询参数。
- 它是“对象 ID”吗？那多半是路径参数。

### 1.4 快速对比

| 对比维度 | 查询参数 | 路径参数 |
| --- | --- | --- |
| 语义 | 筛选条件、附加条件 | 资源唯一标识 |
| 是否必填 | 通常可选 | 通常必填 |
| 典型场景 | 搜索、分页、排序 | 详情、修改、删除 |
| URL 形式 | `/items?keyword=phone&page=2` | `/users/8` |

---

## 二、查询参数是什么：适合列表、搜索、分页

### 2.1 URL 后面那串 `?`，就是查询参数

查询参数通常长这样：

```bash
GET /items?keyword=phone&page=2&page_size=10
```

问号 `?` 后面的部分，就是查询参数。你可以把它想成前端发请求时顺手带上的“小纸条”：

- 我想搜什么：`keyword=phone`
- 我想第几页：`page=2`
- 我想一页几条：`page_size=10`

### 2.2 为什么它适合列表接口

列表接口经常要加条件：

- `/items`：返回默认列表
- `/items?keyword=phone`：只看相关结果
- `/items?page=3`：看第 3 页
- `/items?sort=price_desc`：按价格倒序

这些信息不是资源本身的唯一标识，而是**对结果的附加要求**。说白了，它们是在告诉后端：**“你按这个条件把结果给我。”**

### 2.3 前端里怎么类比

如果你写过 `axios`，大概会这样写：

```js
axios.get('/items', {
  params: {
    keyword: 'phone',
    page: 2
  }
})
```

它最终会变成：

```bash
/items?keyword=phone&page=2
```

所以前端里的 `params`，和后端说的查询参数，本质上是一回事。区别只是：前端负责带出去，后端负责接回来。

---

## 三、路径参数是什么：适合详情、修改、删除

### 3.1 路径参数就是 URL 里“占位置”的变量

路径参数通常长这样：

```bash
GET /users/8
```

这里的 `8` 是路径的一部分，通常表示某个具体资源的 ID。

再比如：

```bash
GET /users/8
DELETE /users/8
PUT /users/8
```

这几个接口都指向同一个目标：第 8 个用户，只是方法不同，动作不同。

### 3.2 路径参数为什么更像“资源定位”

因为它表示的是“哪个对象”，而不是“怎么筛选”。

你可以把它理解成详情页：

- 列表页可以有很多筛选条件
- 详情页必须知道你要看谁

如果没有这个 ID，后端就没法知道你到底要操作哪条数据。所以路径参数语义很强，通常用于资源唯一定位。

### 3.3 路径参数和查询参数别混着用

比如：

```bash
GET /users?user_id=8
```

技术上不是完全不能做，但如果你要的是单个用户详情，更自然的写法应该是：

```bash
GET /users/8
```

简单记：

- **单个对象**：优先路径参数
- **列表筛选**：优先查询参数

---

## 四、FastAPI 中如何声明和读取参数

### 4.1 查询参数：直接写在函数参数里就能接住

FastAPI 很适合新手的一点，就是不用你手动拆请求。

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/items")
def get_items(keyword: str, page: int):
    return {
        "keyword": keyword,
        "page": page
    }
```

请求：

```bash
/items?keyword=phone&page=2
```

FastAPI 会自动把值接进来。

### 4.2 路径参数：名字要和路由里的占位符一致

路径参数必须先在路由里占位：

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/users/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}
```

请求：

```bash
/users/8
```

返回：

```json
{
  "user_id": 8
}
```

### 4.3 为什么函数参数名必须和路由占位符一致

你可以把路由理解成一个模板：

```python
"/users/{user_id}"
```

这里的 `{user_id}` 就是标签。FastAPI 会按这个名字把 URL 里的值塞进去。如果你写成：

```python
@app.get("/users/{uid}")
def get_user(user_id: int):
    return {"user_id": user_id}
```

框架就不知道该把谁接到谁身上，容易报 422。

看到这类报错，先检查三件事：

1. 路由占位符是否写错；
2. 函数参数名是否一致；
3. 是否有必填参数没传。

### 4.4 类型标注不是装饰，是校验规则

写 `user_id: int`，不是只为了好看，它会告诉 FastAPI：

1. 这个值应该是什么类型；
2. 自动帮你转换和校验。

比如 URL 里传来 `"8"`，FastAPI 会尝试转成整数 `8`。如果传的是 `"abc"`，它就会直接报错，而不是把脏数据放进去。

---

## 五、默认值、可选值与类型标注：让参数更好用，也更安全

### 5.1 默认值：不传也能跑

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/items")
def get_items(page: int = 1):
    return {"page": page}
```

不传时：

```bash
/items
```

返回：

```json
{
  "page": 1
}
```

传了时：

```bash
/items?page=3
```

返回：

```json
{
  "page": 3
}
```

分页接口里，这种写法很常见。

### 5.2 可选值：有就传，没有也行

```python
from typing import Optional
from fastapi import FastAPI

app = FastAPI()

@app.get("/items")
def get_items(keyword: Optional[str] = None):
    return {"keyword": keyword}
```

不传：

```bash
/items
```

返回：

```json
{
  "keyword": null
}
```

传了：

```bash
/items?keyword=phone
```

返回：

```json
{
  "keyword": "phone"
}
```

### 5.3 默认值和 Optional 的区别

- `page: int = 1`：不传时用默认值 1
- `keyword: Optional[str] = None`：表示这个参数可以没有，也可以是字符串

一般来说：

- 需要兜底值的，常用默认值；
- 允许“有就传、没有就空着”的，常用 `Optional`。

### 5.4 类型标注别省

常见类型写法有这些：

```python
page: int
keyword: str
price: float
is_active: bool
```

它们会帮助 FastAPI：

- 判断参数类型
- 自动转换类型
- 自动生成文档
- 在参数错误时及时报错

## 六、一个小型参数设计示例：商品列表和商品详情

这一段不只是看语法，还顺手把接口设计思路走一遍。

### 6.1 场景：一个列表接口 + 一个详情接口

我们做两个接口：

1. 商品列表：支持关键词搜索、分页
2. 商品详情：按商品 ID 获取单个商品

这就是最典型的参数设计方式。

### 6.2 参数设计的步骤化思路

以后你自己设计接口时，可以按这个顺序来：

1. **先确定接口用途**：列表、详情，还是修改、删除？
2. **再判断参数是“筛选”还是“定位”**
3. **最后判断是否必填**

这个顺序很实用，因为它是在先把业务意思想清楚，而不是先背代码。

### 6.3 列表接口：用查询参数

```python
from typing import Optional
from fastapi import FastAPI

app = FastAPI()

@app.get("/products")
def list_products(keyword: Optional[str] = None, page: int = 1):
    return {
        "type": "list",
        "keyword": keyword,
        "page": page
    }
```

设计理由：

- `/products` 表示商品集合
- `keyword` 是筛选条件
- `page` 是分页条件
- 它们都属于“怎么查”的信息，所以适合放查询参数里

请求示例：

```bash
/products?keyword=phone&page=2
```

### 6.4 详情接口：用路径参数

```python
@app.get("/products/{product_id}")
def get_product(product_id: int):
    return {
        "type": "detail",
        "product_id": product_id
    }
```

设计理由：

- 你要的是某个具体商品
- `product_id` 是唯一定位
- 所以它应该在路径里

请求示例：

```bash
/products/1001
```

### 6.5 这就是参数设计的基本思路

以后你自己设计接口时，可以先问三个问题：

1. 这是在找“某一个对象”，还是在查“一组列表”？
2. 这个值是不是资源的唯一标识？
3. 这个值是必填的，还是可选的？

一般按这个顺序想，路径参数和查询参数就不容易选错。

## 七、常见坑点提示：参数名不一致、类型转换失败、可选参数写法

### 7.1 坑点一：参数名不一致

错误写法：

```python
@app.get("/users/{uid}")
def get_user(user_id: int):
    return {"user_id": user_id}
```

路由里写的是 `{uid}`，函数里写的是 `user_id`，FastAPI 会找不到对应关系。

正确写法：

```python
@app.get("/users/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}
```

记住一句最稳的：**路径参数名要和函数参数名一致。**

### 7.2 坑点二：类型转换失败

```python
@app.get("/users/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}
```

如果访问：

```bash
/users/abc
```

FastAPI 会发现 `abc` 不能转成整数，就直接报错。这不是坏事，而是在帮你挡住脏数据。

### 7.3 坑点三：可选参数别写得太随意

不推荐这样写：

```python
def get_items(keyword: str = None):
    return {"keyword": keyword}
```

更推荐：

```python
from typing import Optional

def get_items(keyword: Optional[str] = None):
    return {"keyword": keyword}
```

语义更清楚：这个参数是字符串，而且允许为空。

### 7.4 坑点四：把“筛选条件”和“资源 ID”混着放

比如你本来要查单个用户，却写成：

```bash
/users?user_id=8
```

这不是不能实现，但语义上不如 `/users/8` 清楚。接口设计不是为了“能跑就行”，而是为了让别人一看就懂，也方便维护。

---

## 八、这章和请求体有什么区别：别把参数来源搞串了

### 8.1 查询参数和路径参数都在 URL 相关的位置

它们都属于“URL 传参”：

- 路径参数：`/users/8` 里的 `8`
- 查询参数：`/items?keyword=phone` 里的 `keyword=phone`

### 8.2 请求体不是这么来的

请求体一般是 POST、PUT 这类请求里，前端把一整块数据放在 body 里传给后端。比如创建用户、提交表单、上传复杂数据，通常会用请求体。

先记住这个边界：

- **URL 上的值**：路径参数、查询参数
- **请求体里的值**：下一章再讲

---

## 九、快速检查清单：写参数接口前先过一遍

### 9.1 查询参数适用的情况

- 搜索
- 筛选
- 分页
- 排序
- 可选条件查询

### 9.2 路径参数适用的情况

- 查单条详情
- 修改单条数据
- 删除单条数据
- 用 ID 定位对象

### 9.3 FastAPI 写法检查

- 路由里的占位符名字，和函数参数名是否一致
- 参数是否写了类型标注
- 可选参数是否用了 `Optional[...] = None`
- 默认值是否合理
- 参数设计是否符合“定位”或“筛选”的语义

### 9.4 常见错误排查

- 报 422：先看是不是类型错了，或者必填参数没传
- 取不到路径参数：先看名字有没有写错
- 参数总是必传：看看是不是忘了加默认值
- 想做可选参数，却写成必填：改成 `Optional[...] = None`

---

## 结尾小结：先把“值从哪来”搞明白，后面才写得顺

这一章最重要的，不是记住某一段代码，而是建立一个稳定的判断习惯：

- **查询参数**：用来筛选、搜索、分页
- **路径参数**：用来定位具体资源
- **FastAPI**：会根据函数参数和类型标注，自动把值接进来，并帮你做基础校验

也就是说，FastAPI 不是让你手动拆请求，而是让你把规则写清楚，然后它帮你接住前端传来的值。

最后给你一个练手任务：

1. 写一个商品列表接口：`/products`
   - 支持 `keyword`
   - 支持 `page`
2. 写一个商品详情接口：`/products/{product_id}`
   - 用 `product_id` 查单个商品
3. 故意试几次错误输入
   - 不传必填参数
   - 把 `product_id` 传成字母
   - 看看 FastAPI 会怎么报错

你会发现，真正理解参数，不是靠背概念，而是靠你亲手把它跑通。下一章我们就继续往前走，看看请求体是怎么接收一整块数据的。

# 第5章 请求体与 Pydantic 校验：让接口不再“乱收数据”

如果你已经弄懂了查询参数和路径参数，这一章就该进入接口里非常关键的一块：**请求体（Request Body）**。

它是很多接口真正“装数据”的地方。你可以把它理解成前端里 `POST / PUT / PATCH` 这些请求提交出去的那份“内容本体”。比如新增待办事项时，标题、描述、截止时间这类信息，通常不会写进 URL，而是放在请求体里发给后端。

这一章我们重点解决三个问题：

1. 请求体到底是什么，和查询参数、路径参数有什么区别？
2. 为什么 JSON 更适合放在请求体里？
3. FastAPI 里怎么用 Pydantic 做数据校验，避免接口“乱收数据”？

---

## 什么是请求体：和查询参数、路径参数的区别

很多人学接口，卡住的不是代码，而是“参数到底该放哪儿”。这个地方一旦混了，后面接口设计会一直别扭。

### 1. 路径参数：接口地址的一部分

路径参数写在 URL 路径里，通常表示“你要操作哪一个资源”。

```python
@app.get("/users/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}
```

调用时：

```bash
GET /users/1001
```

这里的 `1001` 就是路径参数。它的特点是：

- 跟资源定位强相关
- 通常必传
- 适合表示“哪个对象”

你可以把它理解成前端动态路由参数，比如 `/user/1001`。

---

### 2. 查询参数：附加筛选条件

查询参数挂在 URL `?` 后面，更多是“补充说明”。

```python
@app.get("/users")
def list_users(page: int = 1, size: int = 10):
    return {"page": page, "size": size}
```

调用时：

```bash
GET /users?page=2&size=20
```

查询参数常用于：

- 分页
- 搜索
- 筛选
- 排序

它更像附加条件，可选项多，不强调唯一定位。

---

### 3. 请求体：真正承载复杂数据的地方

请求体就是请求里携带的正文内容，一般不写在 URL 里，而是放在请求消息体中传输。

例如新增待办事项：

```json
{
  "title": "学习 FastAPI",
  "desc": "把请求体和校验搞懂",
  "priority": 2
}
```

这种结构化数据更适合放在请求体里，而不是硬塞到 URL 上。

请求体最常见的用途：

- 创建数据：`POST`
- 更新数据：`PUT` / `PATCH`
- 提交复杂表单
- 传递 JSON 对象

一句话记住：

- 路径参数：你要哪个
- 查询参数：你想怎么查
- 请求体：你要提交什么

---

### 4. 三者怎么区分

| 类型 | 放在哪里 | 典型用途 | 是否适合复杂数据 |
|---|---|---|---|
| 路径参数 | URL 路径里 | 定位某个资源 | 不适合 |
| 查询参数 | URL `?` 后面 | 筛选、分页、搜索 | 不适合太复杂 |
| 请求体 | 请求正文里 | 创建、更新、提交对象 | 最适合 |

如果参数本质上是一个对象、一坨内容，就放请求体；如果是一个 ID，就放路径；如果是筛选条件，就放查询参数。

---

## 为什么 JSON 数据更适合放在请求体里

前端同学对 JSON 都很熟。你可以把 JSON 理解成接口世界里的标准对象格式。

### 1. JSON 天然适合表达复杂结构

比如一个待办事项，不只是标题，还可能有描述、优先级、完成状态、截止日期。如果把这些都放在 URL 里，马上就会又长又乱：

```bash
POST /todos?title=学习FastAPI&desc=...&priority=2&done=false
```

而请求体里用 JSON，就清晰很多：

```json
{
  "title": "学习 FastAPI",
  "desc": "理解请求体和 Pydantic",
  "priority": 2,
  "done": false
}
```

这也是很多业务接口优先选择 JSON 作为请求体格式的原因：结构清晰，也方便前后端统一理解。

---

### 2. 请求体更适合传递对象

前端写接口请求时，经常会这样组织数据：

```js
axios.post("/api/todos", {
  title: "学习 FastAPI",
  priority: 2
})
```

这本质上就是一个对象。请求体和这种对象表达方式非常一致，所以更适合承载业务数据。

---

### 3. 请求体更适合“创建”和“更新”

从接口语义上看：

- `GET`：拿数据
- `POST`：创建数据
- `PUT/PATCH`：修改数据

创建和修改本质上都要提交一坨内容，而这“一坨内容”就很适合放请求体里，尤其是更新接口，放在请求体里更灵活。

---

### 常见坑点：不是所有数据都塞请求体

新手常会想：“既然请求体这么强，那是不是所有参数都放请求体？”

答案是不一定。

如果参数本质上是：

- 资源 ID：用路径参数更自然
- 分页/排序：用查询参数更合适
- 提交对象：才用请求体

参数设计要按语义分工，不要图省事一股脑全塞进去。

---

## Pydantic 模型怎么定义：字段、类型、默认值、可选字段

FastAPI 好用的一个核心原因，就是它和 Pydantic 配合得很顺手。Pydantic 可以先理解成：

> 给请求数据套一个“检查模板”

你告诉它接口期望收到什么字段、字段是什么类型、哪些必填、哪些可选，它就会帮你检查。

---

### 1. 最基础的模型定义

假设我们要做“新增待办事项”的接口：

```python
from pydantic import BaseModel

class TodoCreate(BaseModel):
    title: str
    desc: str
    priority: int
    done: bool = False
```

这里：

- `BaseModel` 是 Pydantic 模型基类
- `title: str` 表示标题必须是字符串
- `priority: int` 表示优先级必须是整数
- `done: bool = False` 表示这是默认值字段，不传也行

你可以把它理解成：先定义一个“数据长什么样”的规格说明书。后端不是看到什么都收，而是先看你有没有按这个规格来。

---

### 2. 字段、类型、默认值分别是什么意思

#### 字段
字段就是模型里一个个属性，比如 `title`、`desc`、`priority`。可以把它想成表单里的输入项。

#### 类型
类型决定字段的数据形状，比如：

- `str`：字符串
- `int`：整数
- `bool`：布尔值
- `float`：小数

类型很重要，因为它决定后端如何理解这份数据。

#### 默认值
默认值就是你不传的时候，系统自动给你一个值。

```python
done: bool = False
```

表示用户没传 `done` 时，默认当成 `False`。这在“是否完成”“是否启用”这类字段里很常见。

---

### 3. 可选字段怎么写

有些字段不是必填，比如备注、图片地址、标签。常见写法是：

```python
from typing import Optional
from pydantic import BaseModel

class TodoCreate(BaseModel):
    title: str
    desc: Optional[str] = None
```

意思是：

- `desc` 可以不传
- 如果不传，它就是 `None`

你可以把它理解成：后端允许这个字段空着，但如果你传了，就按它的类型处理。

---

### 4. 模型拆分：别把一个模型当万能模板

这是新手很容易踩的坑。

很多人会写一个模型：

```python
class Todo(BaseModel):
    id: int
    title: str
    desc: str
    done: bool
    created_at: str
```

然后创建、更新、返回都用它。看起来省事，实际上容易乱。

更合理的做法是按场景拆分模型：

- `TodoCreate`：用于创建时提交数据
- `TodoUpdate`：用于更新时提交数据
- `TodoOut`：用于接口返回数据

例如：

```python
class TodoCreate(BaseModel):
    title: str
    desc: Optional[str] = None
    priority: int = 1

class TodoUpdate(BaseModel):
    title: Optional[str] = None
    desc: Optional[str] = None
    priority: Optional[int] = None
    done: Optional[bool] = None

class TodoOut(BaseModel):
    id: int
    title: str
    desc: Optional[str] = None
    priority: int
    done: bool
```

为什么要拆？

因为：

- 创建时不需要 `id`
- 更新时可能只改部分字段
- 返回时可能会多出 `id`、时间戳等字段

输入模型和输出模型分开，后面项目会更清爽。

---

## 常见校验能力：必填、长度、范围、格式限制

Pydantic 最有价值的地方，不只是定义结构，而是自动帮你校验。

---

### 1. 必填校验：字段没传就报错

如果你写成：

```python
class TodoCreate(BaseModel):
    title: str
```

那 `title` 就是必填。用户不传，FastAPI 会直接报 422 校验错误。

这比你自己在函数里手动判断要省很多事。

---

### 2. 长度限制：别让标题太短或太长

比如标题至少 2 个字，最多 50 个字：

```python
from pydantic import BaseModel, Field

class TodoCreate(BaseModel):
    title: str = Field(..., min_length=2, max_length=50)
    desc: str = Field(default="", max_length=200)
```

这里：

- `...` 表示必填
- `min_length=2` 表示最少 2 个字符
- `max_length=50` 表示最多 50 个字符

适合用于标题、简介、标签名等字段。

---

### 3. 范围限制：优先级不能乱填

比如优先级只能是 1 到 5：

```python
priority: int = Field(1, ge=1, le=5)
```

这里：

- `ge=1`：大于等于 1
- `le=5`：小于等于 5

这相当于在接口入口处先把脏数据拦住。

---

### 4. 格式限制：比如邮箱、日期这类

有些字段不仅看类型，还要看格式。比如邮箱：

```python
from pydantic import BaseModel, EmailStr

class UserCreate(BaseModel):
    email: EmailStr
```

这样用户传明显不是邮箱的值时，接口会直接拒绝。

---

### 5. 为什么校验要放在模型里，而不是函数里

如果你在接口函数里手动判断：

```python
if not title:
    raise ValueError("title 不能为空")
```

也能做，但问题是：

- 每个接口都要写一遍
- 规则分散，不好维护
- 文档自动生成效果不好
- 出错提示不统一

放到 Pydantic 模型里，优点更明显：

- 一处定义，全局复用
- FastAPI 自动接管校验
- Swagger 文档会自动体现字段要求
- 出错时提示更标准

---

## 一个清晰的 JSON 请求体示例：把模型和数据对上

这一节把“模型定义”和“请求体数据”放在一起看，会更直观。

### 接口模型

```python
from pydantic import BaseModel, Field
from typing import Optional

class TodoCreate(BaseModel):
    title: str = Field(..., min_length=2, max_length=50)
    desc: Optional[str] = Field(default=None, max_length=200)
    priority: int = Field(1, ge=1, le=5)
    done: bool = False
```

### 前端提交的 JSON

```json
{
  "title": "学习 FastAPI",
  "desc": "理解请求体和 Pydantic 校验",
  "priority": 3,
  "done": false
}
```

这份 JSON 会被 FastAPI 自动拿来和 `TodoCreate` 对照：

- `title` 是字符串，长度够，合格
- `desc` 是可选字段，传了也没问题
- `priority` 在 1 到 5 之间，合格
- `done` 是布尔值，合格

如果你少传字段、字段名写错，或者类型不对，FastAPI 会直接拦下。

---

## 常见坑点提示：字段名对不上、类型不对、模型拆分不清

这一节专门说坑，因为新手最容易卡在这几个地方。

### 1. 字段名对不上：前端传了，但后端收不到

模型定义的是：

```python
class TodoCreate(BaseModel):
    title: str
```

但前端发的是：

```json
{
  "name": "学习 FastAPI"
}
```

那就会报错，因为字段名不匹配。Pydantic 只认你定义的字段名。

**检查方法：**

- 看模型字段名
- 看前端请求体字段名
- 保证两边一致

---

### 2. 类型不对：字符串和数字别乱传

例如你定义：

```python
priority: int
```

但前端传：

```json
{
  "priority": "高"
}
```

这就不行。接口会提示类型错误。前端表单里很多值默认是字符串，提交前要注意转换。

---

### 3. 模型拆分不清：一个模型管所有场景

记住这个原则：

- 创建时收什么，定义创建模型
- 更新时改什么，定义更新模型
- 返回时给什么，定义输出模型

不要让一个模型同时负责所有事情。

---

### 4. 默认值和可选字段别混了

```python
done: bool = False
```

表示这个字段不传也行，系统会给默认值 `False`。

```python
desc: Optional[str] = None
```

表示这个字段可以不传，也可以传 `null`。

它们看起来都宽松，但语义不一样：

- 默认值：不传时自动补一个值
- 可选字段：允许为空或不传

---

### 5. 请求体、查询参数、路径参数别抢位置

如果你把 `id` 这种资源标识放进请求体，而路径里又没有体现出来，接口语义就会变差。

更自然的写法通常是：

```python
@app.put("/todos/{todo_id}")
def update_todo(todo_id: int, todo: TodoUpdate):
    ...
```

- `todo_id` 放路径里，表示改哪条数据
- `todo` 放请求体里，表示改什么内容

这样一眼就懂。

---

## 一个完整的小例子：待办事项创建接口

我们把上面的知识串起来，写一个新增待办事项接口。

```python
from fastapi import FastAPI
from pydantic import BaseModel, Field
from typing import Optional

app = FastAPI()

class TodoCreate(BaseModel):
    title: str = Field(..., min_length=2, max_length=50)
    desc: Optional[str] = Field(default=None, max_length=200)
    priority: int = Field(1, ge=1, le=5)
    done: bool = False

@app.post("/todos")
def create_todo(todo: TodoCreate):
    return {
        "message": "创建成功",
        "data": todo
    }
```

### 这段代码在干什么

- `@app.post("/todos")`：定义创建接口
- `todo: TodoCreate`：告诉 FastAPI，请求体要按 `TodoCreate` 模型来收
- FastAPI 会自动校验字段
- 校验通过后，进入函数内部
- 你可以直接拿到结构化数据 `todo`

---

### 调用时请求体长什么样

```json
{
  "title": "学习 FastAPI",
  "desc": "理解请求体和 Pydantic 校验",
  "priority": 3,
  "done": false
}
```

结构清晰，和前端提交表单很像。

---

### 如果传错了会怎样

比如：

```json
{
  "title": "A",
  "priority": 10
}
```

可能会出现：

- `title` 太短
- `priority` 超出范围

FastAPI 会直接拒绝这个请求，不让脏数据进入业务逻辑。

这就是输入校验的价值：把问题挡在接口入口。

## 再往前走一步：简单数据库调用的基本流程

这一章虽然重点是请求体和校验，但你最好顺手把后面会用到的“数据库调用思路”先建立起来。

先不用急着上复杂数据库框架，只要理解这个流程就够了：

1. 前端提交请求体数据
2. FastAPI + Pydantic 先校验数据
3. 校验通过后，进入接口函数
4. 在函数里把数据写进数据库
5. 再把写入结果返回给前端

你可以把它理解成一个简单闭环：

> 前端负责发数据，Pydantic 负责验数据，数据库负责存数据，接口负责串起来。

如果后面你要接 SQLite、MySQL 或别的数据库，逻辑也是一样的，只是“存数据”那一步换成了具体的数据库操作。

## 写接口前先过一遍：参数设计检查清单

这一小节很重要，能帮你少走很多弯路。

1. 这个参数是路径参数、查询参数，还是请求体？
2. 请求体里是不是适合放 JSON 对象？
3. 请求体模型是否按场景拆分了？
4. 必填字段有没有明确写出来？
5. 默认值和可选字段有没有区分清楚？
6. 长度、范围、格式有没有做基础校验？
7. 前端传的字段名和后端模型字段名是否一致？
8. 类型是否和前端提交数据匹配？

如果这 8 个问题你都能答得比较顺，那你写请求体接口基本就不会太慌。

这一章你最该记住的一句话是：

> **接口真正稳定，不是因为逻辑写得多复杂，而是因为入口把数据收对了。**

请求体负责承载复杂输入，Pydantic 负责把这些输入规范化、校验化。对前端新手来说，这很好理解：就像表单提交之前你会先做前端校验，FastAPI + Pydantic 做的事情，就是把这层校验放到了后端入口。

你现在应该已经能明白：

- 什么是请求体
- 它和路径参数、查询参数有什么区别
- 为什么 JSON 更适合放在请求体里
- 怎么定义 Pydantic 模型
- 怎么做必填、长度、范围、格式校验
- 常见坑点有哪些
- 简单数据库调用的基本流程是怎样的

### 下一步建议

建议你马上动手做两件事：

1. 用 `TodoCreate` 模型自己写一个 `POST /todos` 接口
2. 故意传一次错误数据，看看 FastAPI 的校验报错长什么样

你会发现：**当接口开始会“拒绝错误数据”时，你才真正进入了 FastAPI 的入门门槛。**

# 第6章 响应数据怎么设计：返回什么、怎么返回更清楚

## 开篇引入：接口不只是“查到数据”，还要“说清楚数据”

前面我们已经讲了怎么接收请求，但接口到这里还不完整，因为真正交付给前端的，不只是“你给我什么”，还有“我返回给你什么”。

很多初学者写接口时，常常只想着：

> 能查到数据就行，直接 `return` 一下。

练习时没问题，但到了真实项目，很容易出乱子：

- 前端分不清成功还是失败；
- 返回字段一会儿叫 `data`，一会儿叫 `result`；
- 有的接口返回对象，有的返回字符串；
- HTTP 状态码是 200，内容却是错误信息；
- 接口一多，联调成本越来越高。

所以这一章要解决的核心问题就是：

> **接口返回值到底怎么设计，才能既清楚、又稳定、还方便前端使用？**

你可以把接口响应理解成“后端发给前端的一份标准快递包裹”。包裹里装什么、外面怎么贴标签，最好统一，不然前端每次拆包都像开盲盒。

---

## 1. 接口返回值的基本形式：字典、列表、JSON 响应

### 1.1 最常见的返回值是什么？

在 FastAPI 里，接口最常见的返回值有三类：

- 字典
- 列表
- JSON 响应

FastAPI 会帮你把 Python 对象转成 JSON 返回给客户端，所以你不用手动拼字符串，这对新手很友好。

### 1.2 返回字典：最常用、最适合结构化数据

最常见的写法就是返回一个字典：

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/user")
def get_user():
    return {
        "id": 1,
        "name": "老赵",
        "age": 30
    }
```

前端收到的会是：

```json
{
  "id": 1,
  "name": "老赵",
  "age": 30
}
```

这种写法最常见，因为字典天然适合接口这种“键值对”结构，前端也容易通过 `res.data.name` 去读取。

### 1.3 返回列表：适合直接返回一组数据

比如文章列表、待办列表、用户列表，可以直接返回一个列表：

```python
@app.get("/todos")
def get_todos():
    return [
        {"id": 1, "title": "学习 FastAPI"},
        {"id": 2, "title": "写接口响应设计"}
    ]
```

前端收到后就是数组：

```json
[
  {"id": 1, "title": "学习 FastAPI"},
  {"id": 2, "title": "写接口响应设计"}
]
```

它适合简单列表查询，但真实项目里通常还要带分页、总数和提示信息，所以直接返回列表未必够用。

### 1.4 返回 JSON 响应：需要更明确控制时使用

FastAPI 也支持显式返回响应对象，比如 `JSONResponse`：

```python
from fastapi.responses import JSONResponse

@app.get("/hello")
def hello():
    return JSONResponse(
        content={"message": "ok"},
        status_code=200
    )
```

这种方式适合需要自定义状态码、响应头或更细控制响应行为的场景。  
但对初学者来说，**直接返回字典**通常就够了，不必一开始把所有接口都写成 `JSONResponse`。

### 1.5 小结：先记住这个判断

- **返回单个资源信息**：用字典
- **返回一组资源列表**：用列表
- **需要精细控制状态码或响应行为**：用 JSON 响应

---

## 2. 为什么要设计统一的响应结构？

### 2.1 统一结构不是形式主义，是为了少踩坑

很多初学者会觉得：

> 接口能返回数据不就行了，为什么还要统一格式？

因为接口一多，统一结构几乎就是必须的。一个典型的统一响应结构，可能是这样：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "id": 1,
    "name": "老赵"
  }
}
```

失败时可能是：

```json
{
  "code": 400,
  "message": "参数错误",
  "data": null
}
```

### 2.2 统一结构的好处

#### 1）前端处理更省心

前端不需要猜：

- 成功时字段叫什么；
- 失败时是不是直接返回字符串；
- 有时候返回对象，有时候返回数组。

统一后，前端只要记住一套规则：

- `code` 判断结果
- `message` 看提示
- `data` 取业务数据

#### 2）后端维护更轻松

如果每个接口都各写各的格式，后面一改就容易牵一大片。统一结构后，后续加字段、加分页、加日志都更稳。

#### 3）更容易表达成功和失败

接口不只是“查到数据”才算完成，还会遇到参数错误、权限不足、数据不存在、系统异常等情况。统一结构能把这些结果清楚表达出来。

### 2.3 统一结构不等于死板模板

统一的意思不是所有接口返回内容都一样，而是**顶层骨架尽量一致**。比如统一成：

```json
{
  "code": 0,
  "message": "success",
  "data": ...
}
```

`data` 里面装什么，可以按业务变化。就像前端页面布局稳定，但内容区域可以不同。

---

## 3. 成功响应和失败响应应该怎么写？

### 3.1 成功响应：把有用数据放进 data

成功响应最常见的写法是：

```python
@app.get("/profile")
def get_profile():
    return {
        "code": 0,
        "message": "success",
        "data": {
            "id": 1,
            "name": "老赵",
            "role": "admin"
        }
    }
```

这里的思路很简单：

- `code = 0` 表示成功；
- `message` 给一个简洁提示；
- `data` 才是前端真正要用的数据。

这样前端一眼就知道：先看 `code`，再决定要不要取 `data`。

### 3.2 失败响应：不要只返回一句话

很多新手会直接写：

```python
return {"message": "参数错误"}
```

这能跑，但前端不知道这是成功还是失败，也没有统一判断标准。更稳妥的写法是：

```python
@app.get("/profile")
def get_profile(user_id: int = 0):
    if user_id <= 0:
        return {
            "code": 400,
            "message": "user_id 必须大于 0",
            "data": None
        }

    return {
        "code": 0,
        "message": "success",
        "data": {
            "id": user_id,
            "name": "老赵"
        }
    }
```

失败时不只是报错，还要把原因讲清楚，这样前端才能直接提示用户。

### 3.3 成功和失败的判断标准建议统一

入门阶段可以先记住这套规则：

- `code == 0`：成功
- `code != 0`：失败
- `message`：告诉人类发生了什么
- `data`：存放业务数据，失败时可为 `null`

不同团队规范会不同，但**先养成统一思维**最重要。

### 3.4 状态码与返回内容要配合，不要各说各话

HTTP 状态码和业务结果不是一回事，但也不能乱配。

比如：

- HTTP 200：请求成功到达服务器；
- 业务 `code = 4001`：用户名不存在；
- 业务 `code = 4002`：密码错误。

所以实际项目里常见做法是：

- HTTP 层返回 200，表示响应正常；
- 业务层用 `code` 表示具体业务结果。

这样前端能同时知道“请求有没有打通”和“业务有没有成功”。  
如果团队对错误处理有更严格的要求，也可以在明显的参数错误、权限错误场景里配合合适的 HTTP 状态码。关键不是死记某一种写法，而是**整套规则要一致**。

## 4. 字段命名为什么会影响前端体验？

### 4.1 字段命名不是小事

很多后端新手觉得字段名只是习惯问题，比如：

- `userName`
- `username`
- `name`
- `user_name`

但对前端来说，字段命名会直接影响可读性、统一性和联调效率。

### 4.2 前端最怕什么样的返回字段？

前端最怕字段风格混乱，比如：

```json
{
  "user_name": "老赵",
  "UserAge": 30,
  "nickname": "赵哥"
}
```

这种返回让人很难维护，因为同一个接口里出现了多种命名习惯。

### 4.3 同一个项目尽量统一风格

一个项目里，接口返回字段尽量使用统一命名风格，不要一会儿驼峰，一会儿下划线。常见做法有两种：

- 驼峰式：`userName`, `createdAt`
- 下划线式：`user_name`, `created_at`

关键不是哪种绝对更好，而是**保持一致**。如果前端一直用驼峰，后端就尽量配合；如果团队习惯下划线，也可以统一约定后再处理转换。

### 4.4 字段设计要考虑前端怎么消费

接口字段不是“看着顺眼就行”，而是“前端好不好用”。建议问自己三个问题：

1. 前端拿到这个字段后，是不是能直接用？
2. 这个字段名有没有歧义？
3. 以后扩展时会不会让前端改很多代码？

比如：

- `title` 比 `t` 更清楚；
- `created_at` 比 `time` 更明确；
- `status` 比 `flag` 更容易理解。

### 4.5 常见坑：返回字段和前端期待不一致

联调中很常见这种问题：

```javascript
res.data.data.list
```

但后端实际返回的是：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": []
  }
}
```

前端就会取不到值。  
所以字段名要么提前约定，要么在文档里写清楚，这也是后面 Swagger 文档为什么重要的原因。

---

## 5. 常见坑点提示：返回对象不符合预期、状态码与返回内容不一致

### 5.1 坑一：以为返回了对象，实际返回的是字符串

比如：

```python
@app.get("/test")
def test():
    return "ok"
```

这个接口能跑，但前端拿到的是字符串，不是结构化数据。正式项目里，尽量不要随手返回字符串就完事，最好统一成响应结构。

### 5.2 坑二：返回对象和状态码不一致

比如业务失败了，但还是返回：

```python
return {
    "code": 400,
    "message": "参数错误",
    "data": None
}
```

同时 HTTP 状态码仍然是 200。  
这不是绝对错误，但你要清楚它的含义：HTTP 层代表请求是否正常，业务层代表业务是否成功。团队怎么约定，就怎么统一。

### 5.3 坑三：返回列表时忘记分页信息

如果直接返回列表：

```python
return [{"id": 1}, {"id": 2}]
```

短期很方便，长期会有问题，因为前端不知道总数、当前页和下一页状态。  
所以列表一旦用于真实页面，建议加上统一响应结构：

```python
return {
    "code": 0,
    "message": "success",
    "data": {
        "list": [{"id": 1}, {"id": 2}],
        "total": 2
    }
}
```

这样前端更容易做分页和展示。

### 5.4 一个实用检查清单

每次写接口返回值时，可以快速检查：

- 返回值是不是统一结构？
- 成功和失败有没有区分清楚？
- `code`、`message`、`data` 职责是否明确？
- 字段名是否统一、易懂？
- 前端能不能一眼知道怎么取值？
- 状态码和业务结果有没有冲突？

如果你还在入门阶段，可以先用这一套简单模板。

### 6.1 成功模板

```python

    "code": 0,
```

### 6.2 失败模板

```python
{
```


## 7. 结合前端协作，再往前走一步

这一章讲“返回什么”，最终目标不是把字段写漂亮，而是让接口更容易协作。

### 7.1 前端最喜欢的接口是什么样

前端最喜欢的接口通常有三个特点：

- 返回结构固定；
- 字段名清楚；
- 成功失败一眼能判断。

因为这样前端写页面时，不需要每个接口都重新思考一遍怎么拆数据。

### 7.2 后端写响应时，尽量站在前端角度想一想

你可以把自己代入前端同学的视角：

- 这个字段我拿到后能不能直接渲染？
- 这次失败是提示用户，还是提示开发者？
- 如果以后加筛选条件，这个结构还能不能继续用？

如果答案都比较顺，那这个响应设计就算合格。

### 7.3 响应设计和后续章节是连着的

这一章虽然讲的是返回值，但它会影响后面很多内容：

- **Swagger 文档**：结构越统一，文档越清楚；
- **Pydantic**：后面不仅请求体能校验，响应也可以更规范；
- **数据库调用**：后面查出来的数据，也要先整理好再返回给前端；
- **完整项目实战**：待办事项 API、用户信息 API 这些项目，最后都要落到“如何返回得清楚”。

也就是说：

> 数据库负责存，接口负责讲明白。

## 8. 如果你要开始规范接口，先从这一版做起

下面给你一个更贴近日常协作的返回示例，适合新手直接套用。

### 8.1 查询成功

```python
@app.get("/todo/{todo_id}")
def get_todo(todo_id: int):
    return {
        "code": 0,
        "message": "success",
        "data": {
            "id": todo_id,
            "title": "学习 FastAPI",
            "done": False
        }
    }
```

### 8.2 参数不合法

```python
@app.get("/todo/{todo_id}")
def get_todo(todo_id: int):
    if todo_id <= 0:
        return {
            "code": 400,
            "message": "todo_id 必须大于 0",
            "data": None
        }
```

### 8.3 列表查询

```python
@app.get("/todos")
def list_todos():
    return {
        "code": 0,
        "message": "success",
        "data": {
            "list": [
                {"id": 1, "title": "学习 FastAPI", "done": False},
                {"id": 2, "title": "复习响应结构", "done": True}
            ],
            "total": 2
        }
    }
```

这套写法不花哨，但很实用。你只要把 `code / message / data` 的逻辑固定下来，后面接口越写越多，也不会乱。

## 结尾小结：后端把数据交给前端，最重要的是“清楚”

这一章我们主要讲了接口返回值怎么设计。你现在应该记住几个关键点：

- 接口返回值常见有 **字典、列表、JSON 响应**；
- 真实项目里，**统一响应结构**很重要；
- 成功和失败最好有明确区分，比如 `code + message + data`；
- 字段命名要考虑前端怎么消费，尽量统一；
- 要特别注意 **返回对象不符合预期** 和 **状态码与返回内容不一致** 这两个常见坑；
- 列表接口别只顾着返回数组，真实页面通常还要考虑分页、总数这些信息。

如果把接口开发比作聊天，那请求是“前端提问”，响应就是“后端回答”。而一个好回答，不是话多，而是**清楚、统一、好接**。

### 给你的行动建议

下一步你可以做两件事：

1. 把前面写过的接口统一改成标准响应结构；
2. 试着为一个列表接口加上 `code / message / data` 三层结构，并让 `data` 里包含列表和总数。

这样做不是为了“看起来专业”，而是为了从一开始就建立规范意识。后面我们讲自动文档、参数设计和实战项目时，你会越来越明显地感觉到：**统一的响应设计，真的能让整个项目顺很多。**

# 第7章 自动生成文档：Swagger 怎么看、怎么用、怎么调试

## 开篇引入：为什么 FastAPI 的文档这么“贴心”？

如果你做过前端接口联调，就会很熟这种场景：后端丢你一份 Markdown、Excel，或者一个 Postman 集合，你还得自己猜：

- 这个字段必填还是选填？
- 类型是字符串还是数字？
- 请求体怎么拼？
- 接口到底通没通？

很多时候，卡住的不是“不会调接口”，而是“接口说明不够清楚”。

FastAPI 的方便之处，就在于它能把接口说明自动生成出来。你只要把路由、参数、请求体按规范写好，文档页面就会自己出现，而且还能直接在线调试。对新手来说，这种体验非常友好：代码写完，文档就有；文档能看，还能直接试；试完有问题，再回代码里改。

这一章你要掌握三件事：

1. FastAPI 为什么能自动生成文档  
2. Swagger UI 和 Redoc 分别怎么看、怎么用  
3. 如何在文档里直接调试接口，并借助文档理解参数、请求体和返回值  

---

## 一、FastAPI 为什么能自动生成文档？

### 1. 它不是额外写出来的，而是从代码里推出来的

FastAPI 的思路很直接：**接口代码本身就是接口说明**。

你写的这些信息：

- 路由路径：`/users/{user_id}`
- 请求方法：`GET`
- 参数类型：`user_id: int`
- 请求体模型：`UserCreate`
- 返回值：`dict`

对框架来说已经足够了。FastAPI 会把这些信息整理成标准接口描述，再生成文档页面。

所以它不要求你再维护一份单独文档，而是直接把代码变成文档来源。这样既省同步成本，也避免“代码改了，文档忘了改”的问题。

### 2. 核心依赖的是类型标注和结构化模型

FastAPI 能生成文档，关键就在于你给参数写了类型标注，并且经常配合 Pydantic 模型使用。

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class Item(BaseModel):
    name: str
    price: float
    is_offer: bool = False

@app.post("/items/")
def create_item(item: Item):
    return item
```

这里的信息已经很完整了：

- `item: Item`：说明请求体结构
- `name: str`：字符串
- `price: float`：浮点数
- `is_offer: bool = False`：可选字段，有默认值

FastAPI 看到这些，就能知道接口需要什么、哪些字段必填、哪些字段有默认值，以及返回值大概长什么样。

你可以把类型标注理解成：**不是给人看的注释，而是给框架和文档系统看的说明书**。写得越清楚，文档就越完整。

### 3. 为什么这对前端新手特别友好？

因为你可以把它理解成：**后端把接口写成了浏览器能直接读懂的说明书**。

以前调接口常常要：

- 找后端确认
- 看代码猜
- 发请求试
- 根据报错倒推

现在则是：

- 打开文档
- 看参数
- 直接试请求
- 看返回结果

这和前端平时“先看接口定义，再去调用”的习惯很像，所以入门时会轻松很多。

---

## 二、Swagger UI 和 Redoc 分别适合看什么？

FastAPI 默认会生成两种文档页面：**Swagger UI** 和 **Redoc**。它们都能看接口，但侧重点不同。

### 1. Swagger UI：适合边看边试

Swagger UI 一般在：

- `/docs`

它的特点是：

- 交互强
- 每个接口都能展开
- 可以直接填参数并发送请求
- 适合开发时调试

它很像一个内置的接口测试台：不用切到 Postman，不用自己拼 URL，直接在页面里点开接口、填参数、点 Execute，就能看到结果。

### 2. Redoc：适合认真看说明

Redoc 一般在：

- `/redoc`

它的特点是：

- 排版清爽
- 更像正式文档
- 适合阅读接口说明、字段说明和返回结构
- 交互没有 Swagger UI 那么强

如果说 Swagger UI 是“带调试按钮的工作台”，那 Redoc 更像“整理好的说明书”。

### 3. 怎么选？

你可以简单记：

- **调试优先：看 Swagger UI**
- **阅读说明优先：看 Redoc**
- **刚入门：先用 Swagger UI**
- **给别人看文档：Redoc 更清爽**

实际学习里，先把 `/docs` 用熟就够了。

---

## 三、如何在文档里直接调试接口？

FastAPI 文档最实用的地方，就是可以直接发请求。

### 1. 基本步骤

以 Swagger UI 为例，操作流程通常是：

1. 打开 `http://127.0.0.1:8000/docs`
2. 找到要测试的接口
3. 展开接口详情
4. 点击 **Try it out**
5. 填写参数或请求体
6. 点击 **Execute**
7. 查看响应结果

这套流程已经能覆盖很多基础调试场景。

### 2. 调试时重点看什么？

点击 Execute 后，页面通常会显示：

- **Request URL**：实际请求地址
- **Response code**：状态码
- **Response body**：响应正文
- **Response headers**：响应头
- **Curl**：可复制到终端的命令

其中最重要的是：

- **状态码**：判断请求是否成功
- **响应正文**：看后端到底返回了什么
- **Curl**：方便复现请求

如果你想确认“浏览器里发的请求到底长什么样”，Curl 很有用。你可以直接复制出来，在终端里再跑一遍。

### 3. 文档调试不是最终联调

文档里能调通，只说明：

- 接口能接收请求
- 参数格式大致正确
- 当前代码逻辑能返回结果

但它不保证：

- 业务逻辑完全正确
- 数据库数据没问题
- 线上权限配置没问题
- 前端真实调用不会遇到跨域、鉴权、代理问题

所以文档调试更像接口联调的第一步，不是全部。

### 4. 新手练习建议：先 GET，再 POST

建议按这个顺序练：

1. 简单 `GET`
2. 带查询参数的 `GET`
3. `POST`
4. 再看路径参数和复杂请求体

这样更稳，不容易一上来就被复杂结构劝退。

---

## 四、文档中的参数说明、请求体示例和返回值示例怎么看？

这一部分最容易“看过就忘”。别把文档当成一大段文字去背，而是把它当成接口说明卡片，一项一项看。

### 1. 先分清参数类型

文档里常见的参数主要有三类：

- **Path Parameter（路径参数）**：如 `/users/123` 里的 `123`
- **Query Parameter（查询参数）**：如 `/users?page=1&size=10`
- **Request Body（请求体）**：通常是 POST/PUT 中提交的 JSON

先判断参数属于哪一类，再看怎么填。

#### 路径参数

路径参数是 URL 的一部分，表示“你要操作哪个对象”。

```python
@app.get("/users/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}
```

这里 `user_id` 是必填的，因为它已经写进路径里了。它和前端动态路由很像，比如 `/users/123` 里的 `123` 就是路径的一部分。

#### 查询参数

查询参数通常用于筛选、分页、搜索。

```python
@app.get("/items/")
def list_items(page: int = 1, keyword: str | None = None):
    return {"page": page, "keyword": keyword}
```

这里：

- `page` 有默认值 1
- `keyword` 可传可不传

这就像前端列表页常见的 `?page=1&keyword=abc`。

### 2. 请求体示例：重点看结构，不只看值

对于 `POST` 接口，文档里一般会给出请求体示例：

```json
{
  "name": "Apple",
  "price": 12.5,
  "is_offer": false
}
```

看示例时，不要只看值，要看：

- 字段名
- 必填项
- 默认值
- 类型
- 是否有嵌套对象或数组

示例值只是示例，不是唯一答案。关键是你有没有按结构和类型传对。

如果你在文档里看到有些字段没填出来，或者示例很简略，不一定是接口坏了，更多时候是模型定义还不够完整。这个时候就回头检查 Pydantic 模型：字段有没有写清楚，默认值有没有补上，是否需要 `Field` 给出更明确的说明。

### 3. 返回值示例：先看外层，再看 data

返回值示例能告诉你：

- 返回的是对象还是数组
- 字段有哪些
- 成功时的结构长什么样
- 失败时是否有错误信息

比如：

```json
{
  "name": "Apple",
  "price": 12.5,
  "is_offer": false
}
```

这说明返回值和请求体结构类似。真实项目里往往还会加统一包装，例如：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "id": 1,
    "name": "Apple"
  }
}
```

所以看返回值时，要先看外层包装，再看 `data` 里的真实数据。

### 4. 建议的阅读顺序

看文档时，推荐按这个顺序：

1. 先看请求方法和路径
2. 再看参数类型
3. 再看请求体结构
4. 再看返回值示例
5. 最后点 Try it out 测试

这样不容易只盯着结果，却忽略了接口结构。

---

## 五、常见坑点提示：文档不显示、路径不一致、示例不完整怎么办？

这一节很重要，很多新手不是不会用文档，而是卡在一些小问题上。

### 1. 文档不显示，先查这几个点

如果 `/docs` 或 `/redoc` 打不开，先排查：

#### 服务有没有启动成功
应用没跑起来，文档自然不会显示。

#### 访问地址对不对
默认通常是：

- `http://127.0.0.1:8000/docs`
- `http://127.0.0.1:8000/redoc`

如果你改了端口，就要按实际端口访问。

#### 有没有关闭文档功能
FastAPI 可以关闭自动文档。如果初始化时做了相关配置，页面就可能不存在。

### 2. 路径和代码不一致，是最常见的坑

比如代码里写的是：

```python
@app.get("/items/{item_id}")
```

但你在文档里找成了 `/item/{item_id}`，或者请求时少填了路径参数。

路由路径哪怕少一个字母，都可能变成另一个接口。

#### 你要养成的习惯

- 代码写完后先看文档显示的路径
- 再确认前端调用地址是否完全一致
- 检查路径参数是否都填了
- 注意尾部斜杠是否统一

路径风格最好保持一致，不然排错会很烦。

### 3. 示例数据不完整，不一定是接口坏了

文档里的示例很多时候只是演示，不是生产数据。比如：

- 字段默认值没写全
- 嵌套对象只展示一层
- 数组只展示一个元素
- 返回值没包含真实数据库字段

这通常说明模型定义还不够细。

#### 怎么改善？

- 用更完整的 Pydantic 模型描述字段
- 给字段加默认值或示例
- 让返回结构更规范

模型越清楚，文档越完整。

### 4. 参数没显示全，常常是类型标注不清楚

FastAPI 文档依赖类型信息。如果写得太随意，文档就推断不出来。

```python
def read_item(q):
    ...
```

和

```python
def read_item(q: str | None = None):
    ...
```

相比，第二种更清楚，文档会知道：

- 这是字符串
- 可以为空
- 有默认值

所以可以把它记成一句话：**类型写得越明确，文档越聪明。**

## 六、把文档当成你的接口调试入口

学到这里，你可以把 FastAPI 文档当成日常开发工具，而不只是展示页面。

它其实同时承担了这些角色：

- 接口说明书
- 在线测试台
- 参数检查器
- 返回值预览器

### 一个推荐的使用流程

写完接口后，按这个顺序检查：

1. 先确认路由和方法
2. 打开 `/docs`
3. 看参数是否显示正确
4. 检查请求体结构
5. 用 Try it out 发一次请求
6. 看状态码和返回值
7. 不对就回代码里改

这个流程很适合新手，因为它把“写代码”和“验证代码”连起来了。

你可以把它类比成前端开发里的“写完页面先预览、点交互、看控制台，再修问题”。FastAPI 的文档就是后端接口的预览环境。

## 七、文档之外，再往前走一步：简单数据库调用怎么串起来？

虽然这一章重点是文档，但你也可以顺手理解接口和数据库是怎么连起来的。

真实项目里，接口通常会经历这样的流程：

1. 前端发请求
2. FastAPI 接收参数
3. 文档展示接口结构
4. 接口函数查询数据库
5. 把数据库结果整理成响应
6. 返回给前端

也就是说，文档不是脱离业务的，它是从接口定义里长出来的；而接口定义最终又会落到数据库查询上。

比如：

- 文档里看到 `GET /users/{user_id}`
- 说明这个接口需要一个用户 ID
- 代码里通常会拿这个 ID 去查数据库
- 查到就返回用户信息
- 查不到就返回错误信息

所以 Swagger 页面不是“单独一个页面”，它其实已经在帮你预览整个接口链路了。你在文档里填参数，就是在模拟前端请求；你在文档里看返回结果，就是在验证数据库查询是否正确。

### 一个最小的调用思路

你可以先记住数据库调用的最简链路：

- 请求进来
- 取出参数
- 调用数据库查询
- 组装响应
- 返回结果

如果你后面要做一个待办事项接口或者用户信息接口，这个链路会反复出现。文档页面能帮你先看清“请求长什么样”，数据库代码再负责把“数据从哪里来”补上。

这一章最该记住的，是下面几个点：

- FastAPI 能自动生成文档，是因为它能从类型标注和 Pydantic 模型里推导接口结构
- Swagger UI 适合调试，Redoc 适合阅读
- 文档里的 Try it out 是快速验证接口的好工具
- 看参数时，先分清路径参数、查询参数和请求体
- 文档不显示、路径不一致、示例不完整，都是常见坑
- 文档不是孤立的，它和接口调用、数据验证、数据库查询是连在一起的

### 本章行动建议

- 打开你的 FastAPI 项目 `/docs`
- 找出至少 2 个接口
- 分别试一次 `GET` 和一次 `POST`
- 记录请求参数、请求体和返回值
- 故意改一个参数名，看看文档和接口会发生什么
- 再把一个接口的返回值改成统一格式，观察文档示例是否变化

你会很快发现：**文档不是附属品，而是接口开发的一部分。**

# 第8章 依赖注入基础：把通用逻辑“顺手带进来”

如果你前面已经写过几个 FastAPI 接口，很快就会遇到一个现实问题：有些逻辑几乎每个接口都要用，比如：

- 判断用户是否登录
- 获取当前用户信息
- 准备数据库对象
- 处理公共参数
- 创建服务层实例

如果每个接口都复制一遍，短期能跑，长期就会变成重复代码满天飞，维护起来很累。  
这时候，FastAPI 的 **依赖注入** 就很有用。

你可以先把它理解成：**把通用能力像参数一样，顺手传给接口函数**。

如果你有前端经验，这个思路其实很好懂。就像写 Vue/React 时，不会把所有逻辑都塞进页面里，而是拆到 hooks、utils、store、service 里。依赖注入做的事情也差不多：**把可复用、可替换、和业务耦合不那么重的东西先准备好，再交给接口使用**。

这一章我们把这个概念讲清楚，顺便说说什么时候该用、怎么用，以及最常见的坑。

---

## 一、依赖注入是什么：把通用能力像参数一样传进接口

先看一个最简单的接口：

```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/profile")
def get_profile():
    return {"msg": "用户资料"}
```

如果这个接口要先判断当前用户是谁，你可能会写成：

```python
@app.get("/profile")
def get_profile():
    user = get_current_user()
    return {"user": user}
```

如果再写一个订单接口，也要拿用户：

```python
@app.get("/orders")
def get_orders():
    user = get_current_user()
    return {"user": user, "orders": []}
```

这样写没问题，但 `get_current_user()` 会到处重复。更合理的做法是把它抽出来，让接口直接使用。这就是依赖注入的核心：

- **依赖**：接口运行时需要的外部能力
- **注入**：由 FastAPI 在合适的时候准备好，再传进来

你可以先记住一句话：

> 接口函数不自己把所有东西都准备齐，而是声明“我需要什么”，FastAPI 会帮我提供。

### 依赖注入解决的不是语法，而是组织问题

很多新手会把 `Depends` 当成一种“高级写法”，其实它真正解决的是代码组织：

- 哪些逻辑是通用的
- 哪些逻辑是业务专属的
- 哪些逻辑该复用
- 哪些逻辑该统一管理

前端同学可以类比成：

- 页面只负责展示和交互
- 公共状态放 store
- 请求封装放 service
- 通用逻辑放 hooks

FastAPI 的依赖注入，本质上也是一种分层复用。

---

## 二、FastAPI 中 Depends 的基本写法和使用场景

### 1. 最基础的写法

FastAPI 里最常见的依赖注入写法就是 `Depends`。

```python
from fastapi import FastAPI, Depends

app = FastAPI()

def get_token():
    return "abc123"

@app.get("/demo")
def demo(token: str = Depends(get_token)):
    return {"token": token}
```

这里的意思是：

- `get_token()` 是依赖函数
- `Depends(get_token)` 表示这个参数不是前端传的，而是让 FastAPI 去执行 `get_token()`
- 执行完后，把返回值传给 `token`

所以接口里的 `token` 看起来像参数，实际是框架注入进来的。

### 2. 依赖函数可以做什么

依赖函数就是普通 Python 函数，只是被 FastAPI 当成“可注入能力”使用。它适合做这些事：

- 返回值：用户信息、数据库连接、配置项
- 检查条件：是否登录、是否有权限
- 预处理参数：分页、排序、过滤条件
- 组装对象：service 实例、工具对象

简单说，依赖函数适合做“准备工作”。

### 3. 更贴近真实业务的例子：当前用户

```python
from fastapi import FastAPI, Depends, Header, HTTPException

app = FastAPI()

def get_current_user(authorization: str = Header(default="")):
    if not authorization:
        raise HTTPException(status_code=401, detail="未登录")
    return {"id": 1, "name": "老赵"}
```

接口中复用：

```python
@app.get("/me")
def me(user=Depends(get_current_user)):
    return {"user": user}
```

这个思路很像前端的请求拦截器：先看有没有 token，没有就拦住，有就继续。

### 4. 一个常见组合：公共参数和当前用户一起带进来

依赖注入最常见的价值，就是把“每个接口都要用的东西”统一处理掉。比如分页参数、当前用户、服务对象，这些都很适合放在依赖里。

先看分页：

```python
from fastapi import Query

def get_pagination(
    page: int = Query(default=1, ge=1),
    page_size: int = Query(default=10, ge=1, le=100)
):
    return {"page": page, "page_size": page_size}
```

再看当前用户：

```python
def get_current_user(authorization: str = Header(default="")):
    if authorization != "Bearer demo-token":
        raise HTTPException(status_code=401, detail="无效登录状态")
    return {"id": 1, "name": "老赵", "role": "admin"}
```

接口里就可以这样组合使用：

```python
@app.get("/todos")
def list_todos(
    user=Depends(get_current_user),
    pagination=Depends(get_pagination)
):
    return {
        "user": user,
        "pagination": pagination,
        "items": []
    }
```

这就很像前端页面里同时拿到了“登录信息”和“分页配置”，页面本身不需要重复处理这些公共逻辑。

### 5. 什么时候适合用 Depends

常见场景包括：

- 认证和鉴权
- 公共参数：分页、排序、过滤
- 公共对象：数据库 session、缓存对象、服务层对象
- 公共逻辑：日志、埋点、环境判断
- 统一预处理：把请求头、路径参数等整理成结构化数据

简单判断标准也很实用：

- 多个接口都要用
- 和具体业务关系不大
- 逻辑相对独立
- 后面可能会变化
- 希望统一管理

只要满足其中两三条，就值得考虑抽成依赖。先从“减少重复”开始，不用一上来就追求架构感。

---

## 三、适合放进依赖的内容：鉴权、公共参数、服务封装

依赖不是“什么都往里塞”，它也有边界。

### 1. 鉴权：最典型的依赖场景

```python
from fastapi import Depends, Header, HTTPException

def get_current_user(authorization: str = Header(default="")):
    if authorization != "Bearer demo-token":
        raise HTTPException(status_code=401, detail="无效登录状态")
    return {"id": 1, "name": "老赵", "role": "admin"}
```

接口中复用：

```python
@app.get("/profile")
def profile(user=Depends(get_current_user)):
    return {"user": user}

@app.get("/admin/data")
def admin_data(user=Depends(get_current_user)):
    if user["role"] != "admin":
        raise HTTPException(status_code=403, detail="没有权限")
    return {"data": "后台数据"}
```

好处很直接：登录态校验只写一次，后面规则变了也只改一个地方。

### 2. 公共参数：把接口参数整理干净

分页、排序、筛选这类东西，很适合集中处理。这样做的好处是参数规则统一，接口代码也更清爽。以后要改分页上限，只改依赖函数就行。

```python
from fastapi import Query

def get_pagination(
    page: int = Query(default=1, ge=1),
    page_size: int = Query(default=10, ge=1, le=100)
):
    return {"page": page, "page_size": page_size}
```

### 3. 服务封装：把“怎么做”和“做什么”分开

业务一复杂，就不该把所有逻辑都塞进路由函数里。比如创建待办事项，通常会包含：

- 校验参数
- 写入数据库
- 返回创建结果

可以先封成服务层，再通过依赖拿到对象。

```python
class TodoService:
    def create_todo(self, user_id: int, title: str):
        return {"id": 1, "user_id": user_id, "title": title}

def get_todo_service():
    return TodoService()
```

接口里这样用：

```python
@app.post("/todos")
def create_todo(
    title: str,
    service: TodoService = Depends(get_todo_service)
):
    return service.create_todo(user_id=1, title=title)
```

这样路由层只负责接收请求和返回结果，业务逻辑放到服务层，后面更好测试，也更好替换。

---

## 四、为什么要用依赖注入：减少重复代码，提升可维护性

很多人会问：我直接在接口里写不行吗？  
短接口当然可以，但项目一大就会暴露问题。

### 1. 减少重复代码

如果 10 个接口都要写登录校验，你就有 10 份重复逻辑。规则一改，很容易漏改。依赖注入把重复逻辑收口到一个地方，接口只声明“我需要这个能力”。

### 2. 让接口职责更清楚

一个好的接口函数，最好只做三件事：

- 接收参数
- 调用业务逻辑
- 返回结果

如果接口里又查用户、又连数据库、又做权限判断、又拼响应，代码会越来越乱。依赖能把公共准备工作先处理掉，让路由函数更像“入口”。

### 3. 更容易测试

如果认证逻辑、数据库对象、服务对象都通过依赖提供，测试时就可以替换成假的数据或假的 service，减少真实依赖带来的麻烦。记住一个原则：

> 能通过依赖拆出去的东西，通常就更容易单独测试。

### 4. 更利于后期扩展

今天是当前用户，明天可能加角色权限、租户信息、日志上下文、请求追踪 ID。  
如果一开始就把这些能力放在依赖里，后面扩展会轻松很多。

---

## 五、常见坑点提示：返回值、执行顺序、参数边界

这一节很重要，`Depends` 初学时最容易卡在这里。

### 坑点 1：注入的是返回值，不是函数本身

```python
def get_current_user():
    return {"id": 1, "name": "老赵"}
```

```python
user = Depends(get_current_user)
```

这里拿到的是 `{"id": 1, "name": "老赵"}`，不是 `get_current_user` 这个函数对象。  
可以把 `Depends` 理解成“调用并取结果”。

### 坑点 2：依赖先执行，接口后执行

顺序通常是：

1. 解析请求参数
2. 执行依赖函数
3. 依赖成功后进入接口函数
4. 返回响应

所以如果依赖里抛了异常，接口函数根本不会继续执行。这个特性非常适合做鉴权：没登录直接拦住，登录成功才进入业务逻辑。

### 坑点 3：不是所有参数都要放进依赖

下面这些更适合直接写在接口参数里：

- 明确属于当前接口的业务参数
- 前端直接传来的数据
- 和接口强绑定的路径参数、查询参数

下面这些更适合放依赖里：

- 公共校验逻辑
- 共用对象
- 鉴权信息
- 统一处理后的公共参数

简单记：

> 业务数据放接口参数，公共能力放依赖。

### 坑点 4：依赖函数也可以继续接收参数

```python
from fastapi import Header

def get_auth(authorization: str = Header(default="")):
    return authorization
```

依赖函数本身也能参与请求解析，但别写得太复杂。一个依赖里又校验、又查库、又组装对象，最后就会变成“第二个接口函数”，可读性会下降。

### 坑点 5：别把依赖理解成全局变量

依赖注入不是全局变量替代品。它的重点是：

- 显式声明需要什么
- 由框架在请求过程中准备
- 每次请求都有清晰的生命周期

像数据库连接、用户上下文这类对象，不应该随便做成全局共享。

---

## 六、一个更完整的小例子：用户、分页和服务对象一起用

下面这个例子把前面讲的内容串起来，逻辑会更像真实项目。

```python
from fastapi import FastAPI, Depends, Header, Query, HTTPException

app = FastAPI()

def get_current_user(authorization: str = Header(default="")):
    if authorization != "Bearer demo-token":
        raise HTTPException(status_code=401, detail="未登录")
    return {"id": 1, "name": "老赵"}

def get_pagination(
    page: int = Query(default=1, ge=1),
    page_size: int = Query(default=10, ge=1, le=100)
):
    return {"page": page, "page_size": page_size}

class TodoService:
    def list_todos(self, user_id: int, page: int, page_size: int):
        return {
            "user_id": user_id,
            "page": page,
            "page_size": page_size,
            "items": [{"id": 1, "title": "学会 Depends"}]
        }

def get_todo_service():
    return TodoService()

@app.get("/todos")
def list_todos(
    user=Depends(get_current_user),
    pagination=Depends(get_pagination),
    service: TodoService = Depends(get_todo_service)
):
    return service.list_todos(
        user_id=user["id"],
        page=pagination["page"],
        page_size=pagination["page_size"]
    )
```

这里的分工很清楚：

- `get_current_user()` 负责鉴权
- `get_pagination()` 负责分页参数
- `get_todo_service()` 负责提供服务对象
- 路由函数只负责把这些东西串起来

这就是依赖注入最常见的用法：**路由变轻，逻辑分层**。

---

## 七、和数据库对象放在一起时，通常怎么做

前面我们提到，数据库对象也很适合放进依赖。因为它属于“通用能力”，而不是某个单独接口的业务数据。

实际项目里，通常会这样拆：

- 先创建数据库连接或 Session
- 再通过依赖把 Session 提供给接口
- 接口拿到 Session 后，调用查询或写入方法
- 请求结束后关闭连接

你可以先把它理解成一个流程，不用一开始就追求特别完整的 ORM 写法。

### 一个最小思路示例

```python
def get_db():
    db = "database_session"
    try:
        yield db
    finally:
        pass
```

接口里使用：

```python
@app.get("/db-demo")
def db_demo(db = Depends(get_db)):
    return {"db": db}
```

这里最重要的不是语法细节，而是思路：**数据库对象不该每个接口自己手动创建，也不该长期挂成全局变量，而是通过依赖按请求提供。**

这就是为什么很多 FastAPI 项目都会把 `get_db` 单独放到依赖文件里。以后接口多了，统一管理会轻松很多。

---

## 八、一个小型使用套路：从接口里抽出通用逻辑

如果你想在自己的项目里试试，可以按这个顺序来。

### 第一步：找重复逻辑

先看看接口里有没有这些内容：

- 重复的登录判断
- 重复的分页参数
- 重复的服务实例创建
- 重复的请求头读取
- 重复的数据库对象获取

这些通常就是适合抽依赖的地方。

### 第二步：把它抽成独立函数

```python
def get_current_user():
    return {"id": 1, "name": "老赵"}
```

先别追求高级，先把职责拆开就行。

### 第三步：在接口里通过 Depends 使用

```python
@app.get("/me")
def me(user=Depends(get_current_user)):
    return user
```

这样接口函数就不用再关心“用户怎么来的”，只关心“拿到用户后做什么”。

### 第四步：检查接口是否更清晰

如果拆完之后，接口函数变短了、更像业务入口了，说明拆分有效；如果反而更绕了，说明抽得太早或者太碎。

---

## 九、你可以直接记住的接口设计原则

依赖注入学到最后，其实可以收敛成几条很实用的原则：

1. **业务参数留在接口本身**
   - 比如标题、内容、ID、页码
2. **公共能力交给依赖**
   - 比如用户、数据库、分页、配置
3. **依赖函数尽量单一**
   - 一个依赖最好只干一类事
4. **接口只负责组装和返回**
   - 别把所有逻辑都堆在路由里
5. **能复用的就不要复制**
   - 这是依赖注入最朴素的价值

如果你以后看到某个接口特别长，先别急着改业务，先看看是不是有一大段“准备工作”可以抽成依赖。很多时候，拆开之后整个项目就会顺眼很多。

---

## 十、本章小结：把通用逻辑从接口里拿出去

依赖注入不是为了炫技，而是为了让代码更清楚、更复用、更好维护。你可以把它理解成一种更成熟的代码组织方式：

- 接口只负责业务入口
- 通用能力交给依赖
- 公共逻辑集中管理
- 后续修改更省事

在 FastAPI 里，`Depends` 就是最常见、最实用的入口。它最适合拿来处理三类事情：

- 当前用户和鉴权
- 公共参数，比如分页和过滤
- 可复用对象，比如服务层和数据库对象

记住一句最实在的话：

> 业务数据放接口参数，通用能力放 Depends。

这样写，接口会更干净，项目也更容易长大。

### 行动建议

下一步你可以做两件事：

1. 给前面写过的某个接口，加一个“获取当前用户”的依赖  
2. 把列表接口里的分页参数抽成一个独立依赖函数

如果你愿意再往前走一步，就试着把数据库 Session 也做成依赖。  
你会发现，代码会突然变干净很多，后面接项目也会顺手很多。

# 第9章 错误处理与调试入门：接口报错时别慌

做接口开发，最常见的感受往往不是“成功了”，而是“怎么又报错了”。  
别怕，这很正常。你可以把接口理解成前后端在对话：前端发消息，后端收消息，再回消息。只要地址、参数、类型或逻辑里有一个环节没对上，报错就会出现。

这章老赵不讲玄学，只讲一件事：**接口报错时，怎么快速看懂、怎么定位、怎么处理**。学会这一套，后面写 FastAPI 会稳很多。

---

## 一、为什么接口会报错：先从最常见的几个方向查

接口报错，本质上不是“坏了”，而是“某一步没对上”。  
入门阶段最常见的问题，基本就四类：**参数、类型、路径、逻辑**。

### 1. 参数不对

前端传过来的参数，后端没收到、少传了、名字写错了，都可能出错。

比如后端定义的是：

```python
@app.get("/users/{user_id}")
def get_user(user_id: int):
    return {"user_id": user_id}
```

但前端如果请求的是：

```js
axios.get("/users/")
```

少了 `user_id`，后端当然接不住。  
再比如前端传了：

```js
axios.get("/users/abc")
```

可后端要求 `user_id: int`，`"abc"` 不是数字，FastAPI 会直接拦下来。

这和前端表单很像：字段名没对上，页面看着“都填了”，后端就是收不到正确数据。  
所以报错时先别急着怀疑逻辑，先看是不是**请求参数本身没对齐**。

### 2. 类型不对

前端同学很容易觉得“值传过去就行”，但后端更在意类型。

例如你定义：

```python
def create_task(title: str, done: bool):
    ...
```

如果前端传来的是 `"done": "yes"`，这在很多场景里就不符合布尔值规范。  
FastAPI + Pydantic 会帮你做类型检查，这其实是好事，因为它能提前发现问题，而不是让错误流进数据库。

你可以把这理解成“后端在验货”：不只看包裹到了没，还要检查里面是不是你要的东西。

### 3. 路径不对

这个和前端路由很像。你请求的 URL 不存在，就会 404。

比如后端定义的是：

```python
@app.get("/tasks")
```

但前端请求：

```js
GET /task
```

少了一个 `s`，接口就不是同一个了。

还有一种常见情况：你以为自己发的是 `GET`，但前端实际是 `POST`；或者接口明明是 `POST /tasks`，你却直接在浏览器地址栏里访问。  
地址对了不代表方法对了，方法不对一样找不到。

### 4. 逻辑出问题

有时候不是参数错，也不是路径错，而是代码内部逻辑错了。

比如：

- 数据库连接失败
- 查不到数据
- 对空值做了操作
- 某个变量还没赋值就被使用
- 判断条件写反了

这一类问题通常不会一开始就被框架拦住，而是运行到那一步时才炸出来。  
所以接口开发里，真正麻烦的往往不是“能不能跑”，而是“跑到一半为什么停了”。

---

## 二、常见错误类型：422、404、500 到底是什么意思

新手看到报错，最容易慌的是一长串英文。其实先别盯全文，先看状态码。  
FastAPI 入门阶段，最常见的就是 **422、404、500**。

### 1. 422：请求格式不对

422 在 FastAPI 里很常见。它通常表示：

- 参数缺失
- 参数类型不对
- 请求体格式不符合 Pydantic 校验规则

比如你定义了一个模型：

```python
from pydantic import BaseModel

class TaskCreate(BaseModel):
    title: str
    done: bool
```

如果前端传：

```json
{
  "title": 123,
  "done": "no"
}
```

FastAPI 就可能返回 422。  
这不是后端坏了，而是后端在认真检查数据：**你给的内容不符合规则**。

**判断标准：**

- 请求能到接口
- 但数据不合格
- 通常和参数校验、Pydantic 有关

第一次碰到 422，很多人会以为接口挂了。其实它恰恰说明接口还活着，而且正在帮你挡住错误数据。

### 2. 404：地址不存在

404 很好理解，就像你输入了一个不存在的页面地址。

比如后端写的是：

```python
@app.get("/tasks/{task_id}")
```

但你请求：

```text
GET /task/1
```

路径不一致，直接 404。

**判断标准：**

- 大概率是 URL 写错了
- 或者请求方法写错了
- 或者访问了没注册的路由

很多时候 404 不是后端逻辑问题，而是“前后端约定没对上”。  
排查时先确认：是不是拼写少了一个字母，或者请求地址还停留在旧版本。

### 3. 500：后端内部出错了

500 通常表示：**接口进来了，但后端代码执行崩了**。  
这类问题范围最广，也最需要调试能力。

可能原因包括：

- 代码里除以 0
- 查数据库时异常
- 访问了不存在的字段
- 变量名写错
- 第三方库报错

**判断标准：**

- 请求已经打到后端
- 但处理过程中异常中断
- 需要看日志和代码堆栈

简单记：

- **422**：你给的数据不合格
- **404**：你找错门了
- **500**：门找对了，但屋里自己炸了

不严谨，但足够帮你建立直觉。

---

## 三、如何返回更友好的错误信息

很多初学者写接口时，喜欢直接 `raise Exception("出错了")`。  
能跑，但体验很差。因为前端看到的只是“500”，根本不知道怎么处理。

更好的做法是：**把能预期到的问题，变成明确、可读、可处理的错误信息。**

### 1. 用 FastAPI 的 HTTPException

FastAPI 提供了常用方式：

```python
from fastapi import FastAPI, HTTPException

app = FastAPI()

@app.get("/tasks/{task_id}")
def get_task(task_id: int):
    if task_id != 1:
        raise HTTPException(status_code=404, detail="任务不存在")
    return {"task_id": task_id, "title": "学习 FastAPI"}
```

这样前端收到的就不是模糊报错，而是清晰信息：

- 状态码：404
- 说明：任务不存在

这很像前端接口返回统一错误结构：不是只给你一个“失败”，而是告诉你“为什么失败”。

### 2. 给前端一个能读懂的提示

友好的错误信息不是“说话客气”，而是“让人知道下一步怎么改”。

不好用的错误信息：

- `error`
- `failed`
- `something wrong`

比较好的错误信息：

- `用户名不能为空`
- `任务不存在`
- `标题长度不能少于 3 个字符`

这些信息越明确，前端越容易做提示，也越容易排查问题。  
如果以后前后端一起联调，你会发现：**一个清晰的错误信息，能省掉很多来回沟通。**

### 3. 不要把能预判的业务错误都交给 500

因为 500 对前端不友好。  
它只知道“服务器炸了”，但不知道：

- 是不是用户名重复了？
- 是不是参数没传？
- 是不是数据不存在？

所以，**能预判的业务错误，尽量返回明确的状态码和文案**。  
比如：

- 参数不合法：422
- 资源不存在：404
- 未授权：401
- 没权限：403

这样前端就能根据状态码决定下一步怎么做。  
这一点先记住就行，后面你做登录、鉴权、数据提交时会更有感觉。

---

## 四、基础调试方法：按顺序排，不要靠猜

遇到报错不要硬猜。入门阶段最实用的思路就三个字：**看、印、试**。

### 1. 打印：先把关键变量打印出来

这是最朴素，但非常有效的方法。

比如：

```python
@app.post("/tasks")
def create_task(title: str):
    print("收到的 title:", title)
    return {"title": title}
```

如果你怀疑参数没进来、值不对、逻辑没走到，就先打印。

**适合打印的内容：**

- 请求参数
- 请求体
- 中间变量
- 分支判断结果
- 数据库查询结果

比如：

```python
print("开始创建任务")
print("请求体内容:", task)
print("准备写入数据库的数据:", data)
```

这样一旦报错，你至少知道程序执行到哪一步了。

**注意坑点：**

- 不要打印密码、token 这类敏感信息
- 不要在正式环境里大量打印，日志会很乱
- 调试完记得删掉多余的 `print`

### 2. 看日志：别只看浏览器报错，要看后端控制台

前端开发者很习惯看页面提示，但接口开发时，后端控制台往往更关键。  
很多时候真正的错误堆栈都在那里。

你要重点看：

- 报错发生在哪一行
- 哪个变量是 `None`
- 哪个类型不匹配
- 哪个函数调用失败

经验法则：

> 报错信息里最后几行，通常是最有用的。

不要只盯着最上面的 `Traceback`，真正的关键在堆栈底部。  
很多新手看报错只看标题，结果越看越糊涂。其实只要学会找“最后一行”和“出错位置”，基本就迈过第一道门槛。

### 3. 借助 Swagger / 自动生成文档调试

FastAPI 的文档非常适合调试。  
它不只是展示接口，还可以直接发请求测试。

你可以打开：

- `/docs`：Swagger 页面
- `/redoc`：另一种文档视图

在 `/docs` 里：

1. 选择接口
2. 点 `Try it out`
3. 填参数
4. 直接发请求
5. 看返回值

这非常适合排查：

- 参数名对不对
- 请求体格式对不对
- 返回数据是否符合预期

对于前端新手来说，这个文档就像“接口自带测试台”。  
不用先写前端页面，就能手动验证接口是否正常。

### 4. 调试时的推荐顺序

老赵建议你按这个顺序来：

1. 先看状态码
2. 再看报错信息
3. 再看后端控制台日志
4. 再用 `/docs` 手动请求
5. 最后回到代码定位问题

这样不会一上来就乱改代码。  
调试最怕的不是不会，而是“上来就猜”。你每猜一次，可能都把问题带偏。

---

## 五、怎么区分前端问题和后端问题

这一节很重要，很多新手调试慢，不是不会写代码，而是**判断方向错了**。

### 1. 先确认请求到底有没有发出去

你在浏览器里点了按钮，不代表请求一定成功发出了。  
先打开开发者工具，看 Network 面板：

- 有没有这个请求
- 请求地址对不对
- 请求方法对不对
- 请求体有没有带上
- 有没有被跨域拦截

如果请求根本没发出去，或者在浏览器里就被拦了，那通常不是后端接口本身的问题。

### 2. 前端问题的常见信号

下面这些情况，往往更像前端问题：

- 接口地址拼错了
- 请求方法错了
- 参数名写错了
- 请求体没按 JSON 发送
- 没设置正确的 `Content-Type`
- 本地开发时被跨域拦住了

这时候你继续改后端代码，通常只会越改越乱。  
正确思路是先把前端请求本身弄对。

### 3. 后端问题的常见信号

如果请求已经明确到了后端，状态码也回来了，但结果不对，那就该看后端：

- 422：多半是参数或校验
- 404：多半是路由没对上
- 500：多半是后端逻辑或数据库出错

所以排错时别急着站队，先判断问题在哪一侧。  
这一步很像联调时的基本功：**先分清是谁的锅，再谈怎么修。**

### 4. 别忽略报错细节

很多初学者看见一大串英文就直接放弃。其实报错信息里经常已经写得很清楚了。

你至少要看这几个东西：

- 状态码是多少
- 哪个字段出错了
- 期望类型是什么
- 实际传入的值是什么
- 报错发生在哪个函数里

比如 Pydantic 报错时，通常会明确告诉你：

- 哪个字段缺失
- 哪个字段类型不对
- 哪个字段不符合约束

这时候你不用猜，顺着提示改就行。

### 5. 不要“改到能跑”为止

有些人一遇到报错，就开始乱试：删代码、加判断、硬转类型。  
结果是接口暂时跑起来了，但逻辑更乱了。

更好的做法是：

- 先复现问题
- 再缩小范围
- 再定位原因
- 最后修复并验证

这比盲改靠谱得多。  
你可以把调试当成找线索，而不是拆盲盒。  
每次只改一个地方，改完就验证，这样你才知道到底是哪一行救了你。

---

## 六、一个小小的实战思路：把报错变成可控流程

我们以“待办事项 API”为例。假设你写了一个创建任务接口：

```python
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI()

class TaskCreate(BaseModel):
    title: str
    done: bool = False

@app.post("/tasks")
def create_task(task: TaskCreate):
    if len(task.title) < 3:
        raise HTTPException(status_code=400, detail="标题至少 3 个字符")
    return {"message": "创建成功", "task": task}
```

这个接口里就包含了几层常见保护：

- Pydantic 先检查请求体结构
- FastAPI 处理类型校验
- 业务逻辑再检查标题长度
- 出问题时返回明确错误

如果前端传：

```json
{
  "title": "a",
  "done": false
}
```

Pydantic 会先确认数据类型没问题，然后业务逻辑发现标题太短，就返回 400。  
如果前端传：

```json
{
  "title": 123,
  "done": "no"
}
```

那可能在进入业务逻辑前就已经被 Pydantic 拦下来了。

这就是比较健康的写法。  
它不是为了“多写代码”，而是为了让错误更早暴露、更容易理解。

如果你再往前一步，给这个接口加上数据库保存逻辑，比如先写入内存列表，后面再换成数据库，你会更清楚地区分：

- 参数校验错了
- 业务规则错了
- 数据存储错了

调试时最怕“所有问题混在一起”，所以拆开验证非常重要。

---

## 七、带着数据库思路看错误：先确认链路，再谈修复

虽然本章重点是错误处理和调试，但你后面一定会碰到数据库。  
到那时候，报错就不只是接口参数问题，还可能是数据库这一环出了岔子。

你可以先把数据库调用理解成三步：

1. 先连接数据库
2. 再执行查询或写入
3. 最后提交或返回结果

如果这条链路里有一步出错，接口就会报错。比如：

- 数据库连不上
- 表不存在
- 字段名写错
- 查询结果为空
- 写入后没提交

这类错误经常表现为 500。  
所以你排查时要问自己三个问题：

- 连接成功了吗？
- SQL 或 ORM 写对了吗？
- 数据有没有真正保存进去？

前端新手常见误区是：页面点了提交，没看到结果，就以为后端没执行。  
其实很可能是数据库里某一步失败了，只是你还没去看日志。  
所以数据库报错的排查方法也一样：**先看状态码，再看日志，再看代码执行到哪一步。**

---

## 结尾：把报错当成信号，不要当成敌人

接口报错不是坏事，它是在提醒你：**请求和后端之间某个环节没对齐**。  
对前端新手来说，最重要的不是一看到错误就慌，而是建立稳定的排查流程：

1. 先看状态码  
2. 再看错误信息  
3. 再看后端日志  
4. 再用文档复现  
5. 最后检查参数、路径、类型和逻辑

你会发现，FastAPI 的错误处理其实很适合新手入门：它会尽量把“哪里错了”说清楚。你要做的，就是学会读懂它。

下一步建议你自己做两件事：

- 故意传一个错误参数，看看 422 长什么样
- 故意访问一个不存在的路由，看看 404 长什么样

再往前走一步，你就可以把前面学过的内容串起来，做一个完整的小接口项目，比如“待办事项 API”或“用户信息 API”。在这个项目里，依次练习：

- 路由设计
- 请求体校验
- 错误处理
- Swagger 调试
- 简单的数据保存

别怕犯错，调试能力就是这样练出来的。

### 本章排错清单

- [ ] 路由地址对不对
- [ ] 请求方法对不对
- [ ] 参数名有没有写错
- [ ] 数据类型是否匹配
- [ ] 请求体格式是否符合模型
- [ ] 状态码是 422、404 还是 500
- [ ] 后端日志里有没有异常堆栈
- [ ] 是否能在 `/docs` 里手动复现
- [ ] 是否其实是前端没发到请求
- [ ] 数据库连接、查询、提交这三步有没有出问题

把这份清单放在手边，后面你写 FastAPI 时会少走很多弯路。

# 第10章 简单数据库调用入门：让接口真正读写数据

## 开篇引入：接口写好了，数据放哪儿？

前面我们已经把 FastAPI 的基础接口、参数和文档跑通了。接下来就会遇到一个很自然的问题：**接口能返回数据了，那这些数据从哪来？新增的数据又放哪？**

如果你只是把数据写死在代码里，比如直接返回一个数组，那这个接口就像临时记事本：页面一刷新、服务一重启，数据就没了。前端同学可以把它理解成只放在组件 `state` 里的数据，刷新后状态清空，程序变量也一样，程序一停就没了。

所以这时候就需要数据库。

你可以把数据库理解成接口背后的“仓库”。前端发请求过来，接口不再现场编答案，而是去仓库里查、拿、放。比如：

- 用户注册时，把信息存进去
- 用户打开列表页时，把数据查出来
- 用户修改标题时，把对应记录更新掉
- 用户删除任务时，把这条数据移除

这一章我们不追求复杂 ORM，也不追求高阶封装，只做一件事：**让你真正理解接口怎么和数据库连接，怎么完成最基础的增删改查。**

---

## 先把思路摆正：数据库不是“高级功能”，而是接口的长期记忆

很多前端新手第一次接触后端时，最容易有一个误解：接口只要能返回 JSON 就行了，数据库是后面的事。其实不是。

你可以把一个小接口项目想成一个前端页面：

- 没数据库时，数据像写在组件里的临时变量
- 有数据库后，数据才真正“存住了”
- 用户下次再来，接口还能把上次保存的内容读出来

这就是数据库最核心的价值：**数据持久化**。

比如待办事项 API，如果没有数据库，用户新增三条待办，刷新一下全没了，那这个产品基本就没法用。数据库做的事情，就是让接口不只是“临时回答问题”，而是真的“记住事情”。

---

## 数据库调用的基本流程：连接、查询、插入、更新

先不纠结用 MySQL、SQLite 还是别的数据库，先把流程想明白。数据库调用本质上就是四步：

1. **连接数据库**
2. **执行 SQL**
3. **拿到结果**
4. **关闭连接**

这四步不管你以后换什么数据库，思路都差不多。

### 1）连接数据库：先建立通信

接口想操作数据库，第一步不是直接查，而是先连上。可以把它理解成先拨通电话，才能开始说话。

连接一般需要这些信息：

- 数据库地址
- 端口
- 用户名
- 密码
- 数据库名

如果连接信息错了，后面所有操作都不会成功。调试时接口一报错，先别急着怀疑 FastAPI，先看数据库连没连上。

### 2）查询：把数据拿出来

查询一般用于读数据，比如查所有待办、根据 id 查单条记录、按条件筛选。SQL 里最常见的是 `SELECT`：

```sql
SELECT * FROM todos;
```

意思就是把 `todos` 表里的数据都拿出来。前端视角下，就是“发请求，让后端把列表数据取回来”。

### 3）插入：把新数据放进去

插入就是新增记录。比如用户提交一个新的待办事项：

```sql
INSERT INTO todos (title, completed) VALUES (?, ?);
```

这里先记住一个重要原则：**前端传过来的内容，不要直接拼进 SQL 里。**先校验，再写入，更安全也更稳。

### 4）更新：修改已有数据

更新就是把某条已有数据改掉，比如：

```sql
UPDATE todos SET completed = ? WHERE id = ?;
```

这里的 `WHERE id = ?` 很关键，意思是只改某一条，不要把整张表都动了。新手最容易犯的错就是少写 `WHERE`，结果把所有记录都更新了，这个坑一定要避开。

### 5）关闭连接：别忘了收尾

连接打开后，用完要关掉。否则连接会越积越多，占住资源，程序跑久了容易出问题。你可以把它理解成开门办事，办完就关门。

### 检查清单

每次写数据库操作时，最好问自己四个问题：

- 有没有先连接数据库？
- SQL 写对了吗？
- 有没有拿到结果并正确返回？
- 最后有没有关闭连接？

这四步能帮你定位大部分基础错误。

---

## 一个最小可运行方案：先用 SQLite 把流程跑通

如果你是第一次做数据库调用，我建议先用 **SQLite**。原因很简单：

- 不用单独安装数据库服务
- 一个文件就能保存数据
- 适合入门练手
- 容易跑通完整流程

等你把“接口读写数据库”这件事理解透了，再去换 MySQL 之类的数据库，成本会低很多。

下面我们就用一个最小待办事项项目来演示。

---

## 项目依赖怎么装：先把工具备齐

这一小节先把依赖说清楚，不然后面代码写出来，你会不知道从哪儿开始跑。

### 推荐依赖

最基础可以准备这些：

```bash
pip install fastapi uvicorn sqlalchemy pydantic
```

如果你用的是 SQLite，Python 自带基础驱动，一般不用额外装太多东西。

### 依赖分别做什么

- `fastapi`：写接口
- `uvicorn`：启动服务
- `sqlalchemy`：先把它当成数据库操作工具来理解，负责连接和执行
- `pydantic`：做请求数据校验

你现在不需要把每个库都研究得特别深，只要知道它们各自负责什么就够了。

### 为什么不直接把 SQL 写进路由里？

因为路由层最适合做的是“接请求、回响应”，而不是“又接请求、又写 SQL、又处理连接、又拼返回值”。代码全挤在一起，后面一定会乱。

所以我们把数据库相关代码放到单独的服务层或数据库层里，路由只负责调用它。这样做的好处很明显：

- 路由更清爽
- 数据库逻辑更集中
- 以后改表结构更方便
- 测试和排错更容易

---

## 数据表结构先定下来：todos 表长什么样？

在写接口之前，先确定表结构。因为接口参数、Pydantic 模型、数据库字段，最好尽量对应起来，不然很容易字段对不上。

### 一个最简单的待办表

我们先设计一张 `todos` 表，字段尽量少：

- `id`：主键，唯一标识一条待办
- `title`：待办标题
- `completed`：是否完成，默认 `false`

### 建表语句示例

```sql
CREATE TABLE IF NOT EXISTS todos (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    completed BOOLEAN NOT NULL DEFAULT 0
);
```

### 这些字段为什么这样设计？

- `id` 用来唯一定位一条记录，更新和删除都要靠它
- `title` 是待办的核心内容
- `completed` 用来表示完成状态，前端展示时很常用

这个结构已经够我们把“新增、查询、修改、删除”完整跑通了。别一开始就把字段设计得太复杂，入门阶段越简单越好。

---

## 服务层怎么拆：别让 SQL 散落在路由里

这一章最重要的实践点，就是**把数据库操作放到服务层**。

### 为什么要这么拆？

因为接口一旦多起来，所有 SQL 都写在路由里，就会出现这些问题：

- 路由函数越来越长
- 不同接口里重复写同样的查库逻辑
- 出错时不知道该先看哪里
- 后面换数据库或改表结构会很痛苦

所以我们把职责分开：

- **路由层**：负责收请求、调服务、返回响应
- **服务层**：负责业务逻辑和数据库操作
- **模型层**：负责请求数据校验和结构定义

这就像前端项目里组件、hooks、API 文件分开管理一样，目的是让每一层只做自己擅长的事。

---

## 最小可运行代码：把增删改查串起来

下面直接给一个小项目骨架。重点不是背代码，而是看懂“数据是怎么流动的”。

### 1）`database.py`：初始化数据库连接

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

DATABASE_URL = "sqlite:///./todos.db"

engine = create_engine(
    DATABASE_URL,
    connect_args={"check_same_thread": False}
)

SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
```

这里先记住两点：

- `DATABASE_URL` 表示数据库地址
- `SessionLocal` 用来创建数据库会话，后面每次请求都可以拿它来查库

`check_same_thread=False` 是 SQLite 常见配置，避免多线程下报错。入门时先照着写，等你更熟了再研究它的细节。

### 2）`models.py`：定义请求体结构

```python
from pydantic import BaseModel

class TodoCreate(BaseModel):
    title: str
    completed: bool = False

class TodoUpdate(BaseModel):
    title: str | None = None
    completed: bool | None = None
```

这里为什么要分成 `TodoCreate` 和 `TodoUpdate`？

- 新增时，标题必须有，所以 `title` 必填
- 更新时，可能只改标题，也可能只改状态，所以字段可以是可选

这就是接口参数设计的基本思路：**按场景建模，不要一套字段到处硬用。**

### 3）`services/todo_service.py`：放数据库操作

```python
from sqlalchemy import text

def get_all_todos(db):
    result = db.execute(text("SELECT id, title, completed FROM todos ORDER BY id DESC"))
    rows = result.fetchall()
    return [
        {"id": row.id, "title": row.title, "completed": bool(row.completed)}
        for row in rows
    ]

def get_todo_by_id(db, todo_id: int):
    result = db.execute(
        text("SELECT id, title, completed FROM todos WHERE id = :id"),
        {"id": todo_id}
    )
    row = result.fetchone()
    if not row:
        return None
    return {"id": row.id, "title": row.title, "completed": bool(row.completed)}

def create_todo(db, title: str, completed: bool = False):
    db.execute(
        text("INSERT INTO todos (title, completed) VALUES (:title, :completed)"),
        {"title": title, "completed": completed}
    )
    db.commit()

def update_todo(db, todo_id: int, title=None, completed=None):
    current = get_todo_by_id(db, todo_id)
    if not current:
        return None

    new_title = title if title is not None else current["title"]
    new_completed = completed if completed is not None else current["completed"]

    db.execute(
        text("UPDATE todos SET title = :title, completed = :completed WHERE id = :id"),
        {"id": todo_id, "title": new_title, "completed": new_completed}
    )
    db.commit()
    return get_todo_by_id(db, todo_id)

def delete_todo(db, todo_id: int):
    db.execute(
        text("DELETE FROM todos WHERE id = :id"),
        {"id": todo_id}
    )
    db.commit()
```

先抓住核心：`SELECT` 查，`INSERT` 增，`UPDATE` 改，`DELETE` 删。并且每次写操作后都要 `commit()`，不然数据可能只改在内存里，没真正写进数据库。

### 4）`routers/todo.py`：写接口路由

```python
from fastapi import APIRouter, Depends, HTTPException
from sqlalchemy.orm import Session
from database import SessionLocal
from models import TodoCreate, TodoUpdate
from services.todo_service import (
    get_all_todos,
    get_todo_by_id,
    create_todo,
    update_todo,
    delete_todo
)

router = APIRouter(prefix="/todos", tags=["todos"])

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

@router.get("")
def read_todos(db: Session = Depends(get_db)):
    return get_all_todos(db)

@router.get("/{todo_id}")
def read_todo(todo_id: int, db: Session = Depends(get_db)):
    todo = get_todo_by_id(db, todo_id)
    if not todo:
        raise HTTPException(status_code=404, detail="Todo not found")
    return todo

@router.post("")
def add_todo(todo: TodoCreate, db: Session = Depends(get_db)):
    create_todo(db, todo.title, todo.completed)
    return {"message": "Todo created successfully"}

@router.put("/{todo_id}")
def edit_todo(todo_id: int, todo: TodoUpdate, db: Session = Depends(get_db)):
    updated = update_todo(db, todo_id, todo.title, todo.completed)
    if not updated:
        raise HTTPException(status_code=404, detail="Todo not found")
    return updated

@router.delete("/{todo_id}")
def remove_todo(todo_id: int, db: Session = Depends(get_db)):
    deleted = get_todo_by_id(db, todo_id)
    if not deleted:
        raise HTTPException(status_code=404, detail="Todo not found")
    delete_todo(db, todo_id)
    return {"message": "Todo deleted successfully"}
```

这里最值得注意的是 `Depends(get_db)`。它的作用就是：**每次请求来时，自动拿一个数据库连接，用完自动关闭。**这比你手动在每个接口里开关连接要稳很多，也更符合 FastAPI 的使用方式。

### 5）`main.py`：把路由挂起来

```python
from fastapi import FastAPI
from sqlalchemy import text
from database import engine
from routers.todo import router

app = FastAPI()
app.include_router(router)

@app.on_event("startup")
def startup():
    with engine.begin() as conn:
        conn.execute(text("""
        CREATE TABLE IF NOT EXISTS todos (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            title TEXT NOT NULL,
            completed BOOLEAN NOT NULL DEFAULT 0
        )
        """))
```

这里的 `startup` 事件表示：**服务启动时先检查表在不在，不在就创建。**这样你就不用每次手动进数据库建表了，运行体验会好很多。

## 常见坑点提示：连接忘记关闭、SQL 注入风险、字段映射错误

这一节很关键，很多入门项目不是写不出来，而是“能跑但不稳”。

### 1）连接忘记关闭

最常见的坑之一。症状通常是：

- 程序跑久了越来越慢
- 连接数异常增多
- 数据库报连接资源不足

避免方式很简单：

- 用完及时关闭
- 尽量交给依赖或上下文管理
- 不要写一堆“开连接但没关连接”的代码

上面我们用 `get_db()` 的 `finally: db.close()`，就是在做这个收尾动作。

### 2）SQL 注入风险

如果你这样写：

```python
sql = f"SELECT * FROM todos WHERE id = {todo_id}"
```

看起来方便，但危险。更安全的做法是使用参数化查询，不要直接拼接用户输入。这个习惯一定要从一开始就养成。

你会发现我们前面的示例都用了 `:id`、`:title` 这种参数占位方式，这就是为了避免把用户输入直接塞进 SQL 字符串里。

### 3）字段映射错误

这个坑也很常见。比如数据库字段叫 `todo_title`，代码里却写成 `title`，结果就会出现：

- 查出来的字段对不上
- 插入时列名写错
- 返回给前端的数据格式混乱

所以建议你在项目里尽量保持这三者一致：

- 数据库字段名
- Pydantic 字段名
- 接口返回字段名

### 4）调试时怎么快速定位问题？

建议按这个顺序排查：

- 接口本身能不能通
- 请求参数有没有传对
- SQL 是否执行成功
- 返回结果是不是你想要的
- 数据库里有没有真正写入

不要一上来就怀疑 FastAPI 或数据库，大多数时候是某一层参数写错了。分层看问题，通常一下就能清楚。

# 第11章 完整实战：做一个可运行的待办事项 API

## 开篇引入：把前面学过的东西串成一个真的项目

前面几章我们已经把 FastAPI 的基础都过了一遍：路由怎么写、请求方法怎么分、查询参数和路径参数怎么拿、请求体怎么接、Pydantic 怎么校验、Swagger 文档怎么看、错误怎么返回。  
但如果只会写一个 `/hello`，还不算真正入门。

这一章我们做一个**待办事项 API**。它不复杂，但很适合新手：能新增、查看、修改、删除待办，还能把数据存到一个简单数据库里。你会发现，前面学的知识不是散的，而是能拼成一个完整的小项目。

你可以把它理解成一个迷你版后端服务：

- 前端发请求，比如“帮我新增一个待办”
- FastAPI 接收到请求
- 校验参数是否正确
- 操作数据库
- 返回结果给前端
- Swagger 文档帮你把流程看清楚

如果你是前端出身，这个流程其实很好理解：像一次表单提交，只不过这里的“表单”变成了请求体，“页面状态”变成了响应 JSON。

这一章不追求花哨，只追求一件事：**把一个最小可运行的小项目真正跑起来**。  
只要你把这一章跑通，后面再加用户、分类、分页、权限，思路都一样。

## 一、项目需求说明：待办事项 API 要提供哪些基础能力？

先别急着写代码，先把需求说清楚。很多新手上来就写接口，最后常常发现字段缺了、接口乱了、数据库也不好改。  
所以第一步不是写，而是**定义最小可用版本**。

### 1.1 这个待办事项 API 需要什么能力？

按本章的入门目标，我们只做一套最基础但完整的功能：

- 创建待办事项
- 查询所有待办事项
- 查询单个待办事项
- 修改待办事项
- 删除待办事项
- 返回统一格式的数据
- 能通过 Swagger 调试
- 能把数据保存到数据库

这套能力看起来朴素，但已经足够你理解真实接口项目的基本骨架。很多业务项目，本质上也都是围绕“增删改查”展开，只是字段更多、规则更复杂。

### 1.2 待办事项应该有哪些字段？

先设计一个最简单的待办模型：

- `id`：待办 ID
- `title`：标题，必填
- `description`：描述，可选
- `done`：是否完成，默认 `false`
- `created_at`：创建时间

这个设计很像前端表单设计。你会先想“用户要填什么，哪些必填，哪些默认值”，后端接口也是同样思路：**先定义数据结构，再定义接口行为**。

比如：

- `title` 像必填输入框，不能为空
- `description` 像备注项，可以不填
- `done` 像勾选框，默认不选
- `created_at` 一般不让前端传，由后端自动生成

最关键的是：**哪些字段由前端传，哪些由后端生成，一开始就要定好**，不然接口会越写越乱。

### 1.3 接口设计的判断标准

一个适合新手的接口设计，通常满足这几个条件：

- 一个接口只做一件事
- 路径清楚，看名字就知道干什么
- 请求参数尽量少而明确
- 返回结果稳定
- 错误信息清楚

比如：

- `POST /todos`：新增待办
- `GET /todos`：查所有待办
- `GET /todos/{todo_id}`：查单个待办
- `PUT /todos/{todo_id}`：更新待办
- `DELETE /todos/{todo_id}`：删除待办

这很像前端 CRUD 页面：列表页负责查看，表单负责新增和编辑，删除是一个动作按钮。后端接口只是把这个流程翻译成网络协议。

还有一个小建议：**接口名字尽量说人话**。新手阶段，统一比花哨更重要。

## 二、项目目录搭建与核心文件分工：代码应该放哪儿？

新手最容易犯的错，就是把所有代码塞进一个 `main.py`。小项目勉强能跑，但稍微复杂一点就会很难维护。  
所以我们先搭一个简单但有分工的目录。

### 2.1 推荐目录结构

```bash
todo_api/
├── main.py
├── schemas.py
├── models.py
├── database.py
├── crud.py
└── requirements.txt
```

各文件职责如下：

- `main.py`：入口文件，创建 FastAPI 应用，挂载路由
- `schemas.py`：Pydantic 数据结构，负责请求体和响应体校验
- `models.py`：数据库表结构
- `database.py`：数据库连接、Session 和初始化
- `crud.py`：增删改查逻辑
- `requirements.txt`：项目依赖清单

### 2.2 为什么要这样拆？

后端项目也要讲“职责分离”。

可以类比成前端项目：

- `main.py` 像入口文件
- `schemas.py` 像类型定义
- `crud.py` 像请求封装或业务函数
- `database.py` 像统一配置
- `models.py` 像数据结构定义

这样拆开有几个好处：

1. 改数据库时，不用大改接口  
2. 改字段时，不会把所有代码搅乱  
3. 调试时容易定位问题  
4. 后面扩展用户、分类、标签更顺

### 2.3 常见坑点

- **坑 1：把 Pydantic 和数据库模型混在一起**  
  它们长得像，但职责不同。前者管接口入参校验，后者管数据落库。

- **坑 2：所有逻辑都写在路由函数里**  
  一开始省事，后面会很乱。路由最好只做“接收参数 + 调业务 + 返回结果”。

- **坑 3：文件分了，名字却很随意**  
  入门阶段文件名要清楚，比如 `schemas.py`、`crud.py`，比 `test2.py` 这种更易维护。

## 四、定义请求体、响应体和数据库表：先把数据结构定下来

这一节是本章的核心之一。接口项目好不好写，很多时候取决于你一开始把数据结构设计得是否清楚。

### 4.1 请求体模型：新增和修改时要传什么？

先看 `schemas.py`。Pydantic 的作用，是让请求进来之前先做一次校验。

```python
from pydantic import BaseModel, Field
from typing import Optional

class TodoCreate(BaseModel):
    title: str = Field(..., min_length=1, max_length=100)
    description: Optional[str] = None
    done: bool = False

class TodoUpdate(BaseModel):
    title: Optional[str] = Field(None, min_length=1, max_length=100)
    description: Optional[str] = None
    done: Optional[bool] = None
```

这里要注意两点：

- `TodoCreate` 用于新增，`title` 必填
- `TodoUpdate` 用于修改，字段可选，方便做部分更新

为什么要分两个模型？  
因为新增和修改的要求不一样。新增时标题必须有；修改时你可能只想改完成状态，不一定每个字段都传。  
这就像前端表单：新建页面和编辑页面，规则一般不完全一样。

### 4.2 响应体模型：返回给前端什么？

```python
from pydantic import BaseModel
from typing import Optional

class TodoResponse(BaseModel):
    id: int
    title: str
    description: Optional[str] = None
    done: bool
    created_at: str
```

这个模型的作用是告诉前端：接口最终会返回什么。  
写清楚它有两个好处：

- Swagger 里能直接看到返回结构
- 前端接数据时心里有数，不容易乱

### 4.3 数据库表结构：数据怎么存？

`models.py` 里定义数据库表。这里我们用 SQLAlchemy 来做基础数据库映射，保持入门友好。

```python
from sqlalchemy import Column, Integer, String, Boolean, DateTime
from database import Base
from datetime import datetime

class Todo(Base):
    __tablename__ = "todos"

    id = Column(Integer, primary_key=True, index=True)
    title = Column(String(100), nullable=False)
    description = Column(String(255), nullable=True)
    done = Column(Boolean, default=False)
    created_at = Column(DateTime, default=datetime.utcnow)
```

这个表结构和前面设计的字段一一对应：

- `id`：主键
- `title`：必填
- `description`：可空
- `done`：默认 `False`
- `created_at`：默认当前时间

### 4.4 为什么请求模型和数据库模型要分开？

这是新手很容易混淆的地方。  
Pydantic 模型是给接口用的，数据库模型是给存储用的。它们长得像，但不完全一样。

比如：

- 请求体里不应该让用户传 `id`
- 数据库里却必须有 `id`
- 响应体里通常要把 `id` 返回给前端
- `created_at` 也一般由后端生成

所以最稳妥的方式就是：**请求、数据库、响应三个层次分开设计**。  
这样接口更清楚，文档也更清楚。

## 五、数据库连接与初始化：让数据真的落地

到这里为止，我们已经有了“表长什么样”的定义。接下来要做的是，把数据库真正连起来。

### 5.1 `database.py` 怎么写？

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, declarative_base

DATABASE_URL = "sqlite:///./todo.db"

engine = create_engine(
    DATABASE_URL,
    connect_args={"check_same_thread": False}
)

SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
Base = declarative_base()
```

这段代码里，最核心的是三件事：

- `engine`：数据库引擎，负责连接数据库
- `SessionLocal`：会话工厂，后面用它拿到数据库操作对象
- `Base`：所有表模型的基类

### 5.2 初始化表结构

在 `main.py` 里启动时建表：

```python
from fastapi import FastAPI
from database import engine, Base
import models

app = FastAPI()

Base.metadata.create_all(bind=engine)
```

这一步的意思是：  
如果数据库里还没有 `todos` 表，就先创建它。  
对新手来说，这样最省事，先把项目跑通，再考虑迁移工具。

### 5.3 基础数据准备

如果你想让项目启动后就有几条测试数据，可以在开发阶段手动插入几条记录，或者第一次调用新增接口时创建。  
入门阶段最简单的方式是：**直接通过 Swagger 新增几条测试数据**。  
这样你不用额外写初始化脚本，也能马上看到列表效果。

### 5.4 常见坑点

- 数据库文件路径写错，结果生成到别的目录
- `Base.metadata.create_all()` 没有执行，表根本没建出来
- SQLite 连接参数没写对，启动时报线程错误
- 修改了表结构后，旧数据库文件没删，导致字段对不上

如果你改了模型但接口还是报错，先看看是不是旧的 `todo.db` 还在。新手阶段最简单的做法，往往是删除旧数据库文件后重新启动。

## 六、实现 CRUD 接口：把待办事项真正做出来

下面开始写核心逻辑。  
这一部分可以理解成“前端页面上的四个动作”：新增、列表、编辑、删除。

### 6.1 `crud.py`：把数据库操作单独放出来

```python
from sqlalchemy.orm import Session
from models import Todo
from schemas import TodoCreate, TodoUpdate

def create_todo(db: Session, todo: TodoCreate):
    db_todo = Todo(
        title=todo.title,
        description=todo.description,
        done=todo.done
    )
    db.add(db_todo)
    db.commit()
    db.refresh(db_todo)
    return db_todo

def get_todos(db: Session):
    return db.query(Todo).order_by(Todo.id.desc()).all()

def get_todo(db: Session, todo_id: int):
    return db.query(Todo).filter(Todo.id == todo_id).first()

def update_todo(db: Session, todo_id: int, todo: TodoUpdate):
    db_todo = get_todo(db, todo_id)
    if not db_todo:
        return None

    if todo.title is not None:
        db_todo.title = todo.title
    if todo.description is not None:
        db_todo.description = todo.description
    if todo.done is not None:
        db_todo.done = todo.done

    db.commit()
    db.refresh(db_todo)
    return db_todo

def delete_todo(db: Session, todo_id: int):
    db_todo = get_todo(db, todo_id)
    if not db_todo:
        return None

    db.delete(db_todo)
    db.commit()
    return True
```

这段代码就是本章的“数据层”。  
你可以把它看成一组独立的业务函数，路由层只负责调用它们。

### 6.2 路由层：对外提供接口

`main.py` 里写路由和依赖注入：

```python
from fastapi import FastAPI, Depends, HTTPException
from sqlalchemy.orm import Session
from database import SessionLocal, engine, Base
import models, crud, schemas

Base.metadata.create_all(bind=engine)

app = FastAPI(title="Todo API", version="1.0.0")

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

@app.post("/todos", response_model=schemas.TodoResponse)
def create_todo(todo: schemas.TodoCreate, db: Session = Depends(get_db)):
    db_todo = crud.create_todo(db, todo)
    return db_todo

@app.get("/todos", response_model=list[schemas.TodoResponse])
def read_todos(db: Session = Depends(get_db)):
    return crud.get_todos(db)

@app.get("/todos/{todo_id}", response_model=schemas.TodoResponse)
def read_todo(todo_id: int, db: Session = Depends(get_db)):
    db_todo = crud.get_todo(db, todo_id)
    if not db_todo:
        raise HTTPException(status_code=404, detail="Todo not found")
    return db_todo

@app.put("/todos/{todo_id}", response_model=schemas.TodoResponse)
def edit_todo(todo_id: int, todo: schemas.TodoUpdate, db: Session = Depends(get_db)):
    db_todo = crud.update_todo(db, todo_id, todo)
    if not db_todo:
        raise HTTPException(status_code=404, detail="Todo not found")
    return db_todo

@app.delete("/todos/{todo_id}")
def remove_todo(todo_id: int, db: Session = Depends(get_db)):
    result = crud.delete_todo(db, todo_id)
    if not result:
        raise HTTPException(status_code=404, detail="Todo not found")
    return {"message": "delete success"}
```

### 6.3 每个接口分别干什么？

#### 1）新增待办：`POST /todos`
- 请求方式：POST
- 请求体：`TodoCreate`
- 用途：创建一条新待办
- 返回值：新增后的待办对象

#### 2）查询所有待办：`GET /todos`
- 请求方式：GET
- 参数：无
- 用途：获取列表页数据
- 返回值：待办数组

#### 3）查询单个待办：`GET /todos/{todo_id}`
- 请求方式：GET
- 参数：路径参数 `todo_id`
- 用途：查看详情
- 返回值：单条待办

#### 4）修改待办：`PUT /todos/{todo_id}`
- 请求方式：PUT
- 参数：路径参数 `todo_id` + 请求体
- 用途：更新待办内容
- 返回值：更新后的待办

#### 5）删除待办：`DELETE /todos/{todo_id}`
- 请求方式：DELETE
- 参数：路径参数 `todo_id`
- 用途：删除指定待办
- 返回值：删除结果提示

### 6.4 为什么这里要用依赖注入？

你会看到每个接口都有 `db: Session = Depends(get_db)`。  
这就是前面学过的依赖注入基础。

它的好处是：

- 每次请求自动拿到数据库连接
- 函数签名清楚
- 用完自动关闭，避免资源泄露

这比你手动在每个接口里开关数据库要稳得多。  
你可以把它理解成：每次页面发请求时，系统自动帮你准备好“工具包”，你只管用。

### 6.5 常见坑点

- `response_model` 和真实返回值不一致
- 修改接口没有先判断记录是否存在
- `PUT` 请求体传了空字段，却把原数据覆盖掉
- 忘记 `db.commit()`，数据库里看不到变化
- `db.refresh()` 漏了，返回值不是最新数据

这些坑在 Swagger 里最容易暴露出来，所以别怕调试，越调越清楚。

## 七、用 Swagger 全流程调试：别光看代码，要真的点一遍

FastAPI 最友好的地方之一，就是自动生成 Swagger 文档。  
对于新手来说，这个文档不只是“说明书”，更是一个调试台。

### 7.1 打开文档

服务启动后，访问：

- `http://127.0.0.1:8000/docs`

你会看到所有接口都列出来了。  
每个接口都能直接点开、填参数、发请求、看返回。

### 7.2 建议的调试顺序

按照这个顺序来最稳：

1. 先测 `POST /todos`，新增一条待办
2. 再测 `GET /todos`，确认列表能查到
3. 再测 `GET /todos/{todo_id}`，查看单条详情
4. 接着测 `PUT /todos/{todo_id}`，修改一条记录
5. 最后测 `DELETE /todos/{todo_id}`，删掉一条数据

这样你能完整看到“创建—查询—修改—删除”的闭环。

### 7.3 在 Swagger 里怎么填？

#### 新增待办
```json
{
  "title": "学习 FastAPI",
  "description": "把待办事项 API 跑通",
  "done": false
}
```

#### 修改待办
```json
{
  "title": "学习 FastAPI 和数据库",
  "done": true
}
```

如果你只想改一个字段，也可以只传那个字段，因为 `TodoUpdate` 里都是可选项。

### 7.4 通过返回结果判断问题

- 返回 `422`：大概率是参数没填对，字段名或类型错了
- 返回 `404`：大概率是 ID 不存在，或者路径写错了
- 返回 `500`：多半是后端代码或数据库连接出了问题

新手调试时，不要一下子改很多地方。  
正确做法是：**每次只改一个点，然后重新测试**。这样你才能知道到底是谁出了问题。

### 8.3 最容易踩的坑

#### 1）接口返回 422
一般是请求体不符合 Pydantic 规则：

- 字段名写错
- 类型不对
- 必填字段没传

#### 2）接口返回 404
一般是：

- 路径写错
- 请求方法用错
- 记录不存在

#### 3）数据库没保存
重点检查：

- 是否执行了 `commit()`
- 数据库文件是不是同一个
- 表有没有成功创建
- 连接有没有正常关闭

#### 4）Swagger 看不到接口
检查：

- `app = FastAPI()` 是否创建了
- 路由有没有写在正确文件里
- 启动命令是不是跑对了
- 有没有导入错误导致应用没加载成功

- 最后用 Swagger 验证

你以后遇到任何接口项目，都可以按这个顺序往下走。
