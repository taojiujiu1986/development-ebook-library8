## 二、Vue 还是 React？先选一个，不要同时学两个

### 2.1 先说结论

这本书兼容 Vue 和 React，但**这一章只需要选一个**。  
不要同时开两条线，不然精力会浪费在框架切换上。

### 2.2 怎么选最省事？

如果你：

- 以前接触过 Vue，就选 Vue
- 以前接触过 React，就选 React
- 两个都不会，就选你以后更想长期用的那个

简单建议：

- 想要模板直观、上手顺：选 Vue
- 想要生态广、招聘常见：选 React

### 2.3 本书后面的兼容方式

后面章节里，核心逻辑是通用的，主要差异只是写法：

- 状态管理：Vue 的 `ref`，React 的 `useState`
- 页面结构：两者都能表达
- 请求逻辑：都可以用 `fetch` 或 `axios`
- 消息列表：都围绕数组来渲染

也就是说，**框架不同，流程相同**。先把一个跑通，再扩展。

### 2.4 本章练习

**练习：**

- 在备忘录里写下你选择 Vue 还是 React
- 用一句话说明理由

**本章结果：**

你明确了后续实战路线，不再左右摇摆。

## 三、用脚手架创建项目，并让默认页面跑起来

### 3.1 推荐直接用 Vite

这一步直接用最省事的方案：**Vite**。  
它的优点很简单：

- 启动快
- 配置少
- 适合新手
- 后面部署也方便

### 3.2 创建项目命令

#### Vue 版

```bash
npm create vite@latest ai-chat-web -- --template vue
cd ai-chat-web
npm install
npm run dev
```

#### React 版

```bash
npm create vite@latest ai-chat-web -- --template react
cd ai-chat-web
npm install
npm run dev
```

你只需要执行你选定的那一套。

### 3.3 运行成功后应该看到什么？

执行 `npm run dev` 后，终端会输出一个本地地址，通常类似：

```bash
http://localhost:5173
```

打开这个地址，如果看到默认欢迎页面，就说明项目已经成功启动。

这一步的意义很直接：

- 项目创建成功
- 依赖安装成功
- 本地开发服务器可用
- 后面接 API 时有稳定基础

### 3.4 如果启动失败，按这个顺序排查

**常见报错排查：**

1. `node` 命令不存在：Node.js 没装好，或者环境变量没配好  
2. `npm install` 失败：网络、缓存或包管理器问题  
3. 页面打不开：终端里的端口号看错了  
4. 空白页：先看浏览器控制台  
5. 端口被占用：换端口，或者关闭占用进程  

建议按这个顺序查：

- 先看终端
- 再看浏览器控制台
- 再看 Network
- 最后再怀疑代码

### 3.5 本章练习

**练习：**

- 成功创建项目
- 成功运行默认页面
- 截图保存首页运行状态

**本章结果：**

你已经拥有一个可运行的前端项目骨架，后续所有 AI 功能都建立在这个基础上。

## 四、先整理一个能直接改造的项目目录

### 4.1 为什么现在就要整理？

很多人项目一开始很简单，后面越写越乱：

- 请求代码散落在页面里
- 聊天消息状态混在一起
- 样式和逻辑互相缠绕
- 后面加流式输出时改不动

所以从一开始就要留好结构。这样后面加“接口请求”“历史记录”“消息气泡”“错误提示”时，不至于推倒重来。

### 4.2 推荐的最小目录模板

```bash
src/
  assets/
  components/
  services/
  styles/
  utils/
  App.vue / App.jsx
  main.js / main.jsx
```

### 4.3 每个目录先放什么

- `components/`：聊天输入框、消息列表、消息气泡
- `services/`：接口请求代码
- `styles/`：公共样式
- `utils/`：格式化、持久化等工具函数
- `assets/`：图片、图标等静态资源

### 4.4 先保留什么，先别动什么

本章先记住一个原则：**保留默认可运行状态，再做增量改造**。

先保留：

- `App.vue` / `App.jsx`
- `main.js` / `main.jsx`
- `src/` 下的基础结构

先别急着删：

- 默认示例代码里的入口文件
- Vite 自动生成的基础配置

先别急着做：

- 过度拆分文件
- 一上来就写太多组件
- 一上来就接 API

后面可以逐步拆成：

- `ChatPage`
- `MessageList`
- `MessageInput`
- `LoadingHint`
- `ErrorBanner`

现在不一定马上创建，但你要提前知道这个方向。这样后面做消息列表、流式输出、Markdown 渲染、历史记录保存时，代码不会全部堆在一个文件里。

### 4.5 本章练习

**练习：**

- 创建 `components/`、`services/`、`utils/` 目录
- 把项目目录整理成可扩展结构

**本章结果：**

# 第2章 第2章 注册并理解 API：拿到可用的模型接口与调用入口

上一章我们已经把项目骨架搭起来了。现在要做的事很明确：**找到能用的模型接口，拿到 API Key，搞清楚前端到底往哪里发请求、发什么、拿回什么**。这一步看起来只是“注册账号”，其实决定了你后面能不能顺利做出聊天页面。很多新手卡住，不是卡在页面，而是卡在“接口地址填错了”“请求头少了个 Key”“返回结果读不出来”。

这一章不讲大模型原理，只做一件事：**让你拿到一个可调用、可调试、可复用的 API 配置模板**。学完之后，你就能把接口接进 Vue 或 React 项目里，为下一章的页面联调做好准备。

---

## 2.1 注册模型服务账号并获取 API Key 或访问凭证

### 你先要知道：API Key 是什么

按本书语境，API Key 就是你调用模型服务时的“通行证”。  
前端请求模型接口时，通常需要它来证明“你有权限使用这项服务”。

你可以把它理解成：

- **账号**：你是谁
- **Key**：你能不能调用接口
- **接口地址**：你要去哪个门
- **请求参数**：你进去后要说什么

如果没有 Key，或者 Key 不对，接口通常会直接拒绝。新手最常见的结果就是：页面点了没反应，控制台里全是 401、403 或鉴权失败。

### 注册时按这个顺序做

不同平台界面不一样，但流程通常类似：

1. 注册模型服务账号
2. 登录并完成平台要求的验证
3. 进入开发者控制台
4. 创建 API Key 或访问凭证
5. 打开接口文档，准备记录基础信息

### 拿到 Key 后，先确认这几项

- Key 是否只显示一次
- 是否有额度限制
- 是否区分测试环境和正式环境
- 是否支持你要用的模型名称
- 是否有“聊天接口”“对话接口”“流式接口”入口

最重要的是：**确认这个 Key 对应的服务，真的能调用你要的功能**。有些平台的 Key 只适用于某个产品线，或者某个模型版本，不看清楚很容易白折腾。

### 常见误区

- 把 Key 直接写进前端代码
- 只拿到 Key，不看文档
- 以为所有平台接口都一样

### 本节练习

完成以下动作：

- 注册并登录模型服务平台
- 找到开发者控制台
- 创建一个 API Key
- 打开接口文档，记录：
  - 接口地址
  - 请求方法
  - 鉴权方式
  - 返回结构示例

**结果要求：**  
你手里至少要有一份“可调用的 Key”和一页“接口文档笔记或截图”。

## 2.2 认识接口地址、请求方式、请求头和返回结构

这一小节最重要的问题是：**前端到底怎么跟模型服务说话？**

### 1）接口地址：请求发往哪里

接口地址就是请求的目标 URL。你先不要纠结名字，重点看三件事：

- 是否是 `https://` 开头
- 是否对应“聊天”或“对话”能力
- 是否支持流式输出

建议把接口地址单独记下来，不要只靠记忆。因为后面写代码时，可能会同时出现开发环境、测试环境、正式环境几个地址，混起来很容易发错。

### 2）请求方式：通常是 POST

大多数大模型调用都会使用 **POST**，因为你要提交消息内容、模型参数等数据。  
在接口文档里优先确认：

- 是 `POST` 还是 `GET`
- 请求体是 JSON 还是表单
- 是否支持流式传输

聊天类接口一般都会带请求体，而且通常是 JSON。后面你在前端写 `fetch` 或 `axios` 时，基本都围绕这个请求体组织数据。

### 3）请求头：鉴权通常放这里

常见请求头包括：

- `Authorization`
- `Content-Type: application/json`

有些平台要求：

- `Authorization: Bearer 你的API_KEY`
- 或者使用自定义头字段

不要猜，**以文档为准**。前端联调最常见的问题，就是 Key 写错位置，或者少了 `Bearer ` 前缀。看起来只差几个字符，接口却会直接报错。

### 4）返回结构：先看最外层，再找答案文本

模型接口返回的数据通常不会直接给你一句完整答案，而是会包一层结构。你需要重点找：

- 回答内容在哪个字段
- 是否有错误码
- 是否有会话 ID
- 是否分块返回
- 是否是流式 chunk

例如：

```json
{
  "id": "xxx",
  "choices": [
    {
      "message": {
        "role": "assistant",
        "content": "你好，我是 AI。"
      }
    }
  ]
}
```

这只是帮助理解结构，不代表所有平台都一样。你的任务不是背格式，而是看文档，找到“最终展示给用户的文本”在哪个字段里。后面做 Markdown 渲染、消息列表或流式更新时，这个字段最关键。

### 一眼看懂的接口要点表

| 项目 | 你要关注什么 | 你最终要记下来什么 |
|---|---|---|
| 接口地址 | 请求发到哪里 | 完整 URL |
| 请求方式 | 用什么方法调用 | `POST` / `GET` |
| 请求头 | 怎么鉴权、怎么声明格式 | `Authorization`、`Content-Type` |
| 请求体 | 要提交什么内容 | `model`、`messages`、`stream` 等 |
| 返回结构 | 回答在哪个字段 | `content` 或对应文本字段 |
| 错误信息 | 出错时怎么看 | 错误码、错误消息 |

### 常见误区

- 只看请求体，不看返回体
- 以为接口成功就能直接渲染
- 不区分错误返回和正常返回
- 返回里有多层嵌套，却只取了第一层

| 项目 | 内容 |
|---|---|
| 接口地址 |  |
| 请求方式 |  |
| 请求头 |  |

**结果要求：**  
你能明确说出“我该往哪里发请求、怎么发、怎么拿结果”。

## 2.3 区分测试环境与正式环境的使用方式

很多人第一次接接口失败，不是代码错了，而是**环境没分清**。

### 为什么要区分测试环境和正式环境

测试环境通常用于：

- 联调
- 验证参数
- 低风险试错
- 开发期间的小规模测试

正式环境通常用于：

- 真正给用户使用
- 真实计费
- 稳定访问
- 部署上线

### 你要重点关注的差异

#### 1）接口地址可能不同

测试环境和正式环境的 URL 可能完全不一样。你必须确认当前代码请求的是哪个地址。

#### 2）Key 可能不同

有的平台会区分测试 Key 和正式 Key。不要把测试环境的凭证误用到正式环境。

#### 3）额度和限制不同

测试环境常见特点：

- 次数有限
- 并发较低
- 结果可能不稳定
- 适合调试，不适合长期在线使用

#### 4）模型版本可能不同

测试环境未必和正式环境提供同样的模型能力。  
如果你发现“本地能调通，线上不通”，先检查环境是否一致。

### 推荐方案：先测试，再上线

新手最稳的做法是：

1. 先用测试环境确认请求能成功
2. 再把同样的请求结构迁移到正式环境
3. 最后把 Key 和 URL 通过环境变量管理起来

这样能避免把问题混在一起：到底是页面写错了，还是接口地址错了，还是 Key 错了。

### 不推荐方案：把正式 Key 直接写进前端仓库

这个做法问题很多：

- 容易被看到
- 不方便更换
- 开发和上线混在一起，排错麻烦

更好的方式是：

- 本地开发时用 `.env`
- 构建时注入环境变量
- 真正上线时再切正式环境配置

### 本节练习

找出测试环境和正式环境的差异，至少记录以下内容：

- URL 是否不同
- Key 是否不同
- 是否有调用次数限制
- 是否支持流式输出

**结果要求：**  
你能判断当前项目该先接测试环境还是正式环境，并说出原因。

## 2.4 准备一份可直接复用的接口配置模板

这一小节的目标很实际：**不要每次都手动翻文档，做一份能直接复制的模板**。  
后面你做 Vue 或 React 页面时，只要替换几个变量就能发请求。

### 推荐的配置结构

你可以先准备一个 `apiConfig.js` 或 `.env` 风格的配置文件：

```js
export const API_CONFIG = {
  baseURL: 'https://example.com',
  chatPath: '/v1/chat/completions',
  apiKey: 'YOUR_API_KEY',
  model: 'your-model-name'
}
```

更安全的做法，是把 API Key 放到环境变量里：

```env
VITE_API_KEY=your_api_key
VITE_API_BASE_URL=https://example.com
VITE_API_MODEL=your-model-name
VITE_API_CHAT_PATH=/v1/chat/completions
```

代码里读取：

```js
const apiKey = import.meta.env.VITE_API_KEY
const baseURL = import.meta.env.VITE_API_BASE_URL
const model = import.meta.env.VITE_API_MODEL
const chatPath = import.meta.env.VITE_API_CHAT_PATH
```

如果你用 React，并且项目是 CRA 或 Vite，思路一样，只是环境变量前缀略有差别。你先记住原则：**Key 不硬编码，统一从环境变量或配置文件读取**。

### 发送请求时的最小模板

先准备一个最基础的 `fetch` 模板，后面再扩展成聊天、流式和错误处理版本：

```js
async function sendMessage(message) {
  const res = await fetch(`${baseURL}${chatPath}`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${apiKey}`
    },
    body: JSON.stringify({
      model,
      messages: [
        { role: 'user', content: message }
      ],
      stream: false
    })
  })

  if (!res.ok) {
    throw new Error(`请求失败：${res.status}`)
  }

  return await res.json()
}
```

如果你更习惯 `axios`，也可以先准备一个实例：

```js
import axios from 'axios'

export const apiClient = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL,
  headers: {
    'Content-Type': 'application/json',
    'Authorization': `Bearer ${import.meta.env.VITE_API_KEY}`
  }
})
```

后面页面里直接调用 `apiClient.post(...)` 就行，不需要每次重复写请求头。

### 这份模板里，哪些字段要替换

| 字段 | 是否替换 | 说明 |
|---|---|---|
| `baseURL` | 要替换 | 接口域名 |
| `chatPath` | 要替换 | 聊天接口路径 |
| `apiKey` | 要替换 | 你的访问凭证 |
| `model` | 要替换 | 模型名称 |
| `Content-Type` | 通常不替换 | 一般保持 `application/json` |
| `Authorization` 格式 | 按文档调整 | 可能是 Bearer，也可能是别的格式 |
| `messages` | 要替换 | 用户输入的消息内容 |
| `stream` | 按需求替换 | 是否开启流式输出 |

### 常见误区

- 把 Key 写死在代码里，部署时泄露
- 不做环境变量，导致本地和线上配置混乱
- 接口地址、模型名、请求头散落在多个文件里，维护困难

### 本节练习

建立一个自己的“接口配置文件”，包含：

- 基础地址
- 模型名
- Key 的读取方式
- 一个可调用的 `sendMessage` 函数

**结果要求：**  
你已经拥有一个能直接被页面调用的接口模板，不用每次重新查文档。

# 第3章 第3章 安全存放 API Key：别把密钥直接写进前端代码

## 开篇：先记住一句话

**API Key 不是普通配置，它更像“门禁卡”。**  
网页代码可以公开，但门禁卡不能公开。因为前端代码一旦发到浏览器里，用户、抓包工具、源码查看器都可能看到你写进去的内容。

很多新手第一次做 ChatGPT 网页应用时，会直接这样写：

```js
const API_KEY = "sk-xxxxxx";
```

看起来省事，但这是最危险的一步。项目一旦上线，这把钥匙就可能被别人拿走，轻则盗刷额度，重则账号被滥用、接口被封。

这一章只解决一件事：**怎么把 API Key 放对地方，并且让你本地开发时照样能用。**

---

## 一、先把底线说清楚：不要把 Key 直接写进前端源码

### 1）前端代码天然公开
前端代码最终会被浏览器下载到用户电脑上。只要它在前端执行环境里，就有机会被看到。更直接一点说，打开开发者工具或查看构建后的 JS 文件，都可能找到你的密钥。

### 2）泄露后的后果很直接
- 别人拿你的 Key 调接口，消耗你的额度
- 账号可能被滥用，触发风控
- 源码仓库、历史提交、构建产物都可能留下痕迹

### 3）判断标准很简单
**只要这个值不应该给普通用户看到，就不要放进前端源码。**

### 常见误区
- “我只是测试一下，先写死没关系”
- “我把文件名改掉就没人看见了”
- “项目很小，不会有人盯上”

这些做法都不安全，很多密钥泄露都从“临时写死”开始。

---

## 二、推荐方案：环境变量存放，前端只读取

思路很简单：**把敏感信息从源码里拿出去，放到环境变量中。**  
代码里只读取配置，不直接暴露具体值。

### 1）创建 `.env` 文件
在项目根目录新建 `.env`：

```env
VITE_API_KEY=你的密钥
VITE_API_BASE_URL=https://api.example.com
```

如果你用的是 Vite，通常需要带 `VITE_` 前缀，前端代码才能读取。不同框架规则不同，但思路一样：**敏感信息进环境变量，不进源码。**

### 2）在代码里读取
以 Vite 为例：

```js
const API_KEY = import.meta.env.VITE_API_KEY;
const API_BASE_URL = import.meta.env.VITE_API_BASE_URL;
```

Vue / React 项目都类似：先从环境变量拿值，再放进请求里。比如：

```js
fetch(`${API_BASE_URL}/chat`, {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Authorization: `Bearer ${API_KEY}`,
  },
  body: JSON.stringify({
    model: "xxx",
    messages: [{ role: "user", content: "你好" }],
  }),
});
```

这样改密钥时只需要改 `.env`，不用到处搜代码替换。

### 3）一定要加 `.gitignore`
避免把密钥提交进 Git 仓库：

```gitignore
.env
.env.local
```

很多人本地没问题，一上传仓库就泄露，问题通常就出在这里。

### 4）给团队协作留模板
建议提交 `.env.example`，只写字段名，不写真实值：

```env
VITE_API_KEY=
VITE_API_BASE_URL=
```

别人拿到项目后，复制一份为 `.env`，再自己填值。这样既方便协作，也避免真实密钥被写进仓库。

---

## 三、推荐方案和不推荐方案，对照着记

### 不推荐方案
```js
const API_KEY = "sk-你的真实密钥";
```

问题很直接：
- 代码一公开，Key 就公开
- 容易被提交到仓库
- 部署后也可能被打包进静态文件

### 推荐方案
```env
# .env
VITE_API_KEY=sk-你的真实密钥
```

```js
// 代码里读取
const API_KEY = import.meta.env.VITE_API_KEY;
```

好处是：
- 源码里不出现真实密钥
- 本地开发和线上部署都能统一管理
- 换 Key 的时候只改配置，不改业务代码

### 前端可见配置 vs 后端代理
简单区分：

- **前端可见配置**：接口地址、主题色、页面标题、非敏感开关
- **必须隐藏的敏感信息**：API Key、私有密钥、管理员 Token、永久凭证

如果是后者，**优先走后端代理**。

---

## 四、后端代理怎么理解：前端只碰你的接口，不碰真实 Key

如果你不想让 Key 出现在浏览器里，就不要让浏览器直接请求大模型平台，而是：

**浏览器 → 你的后端接口 → 大模型 API**

这样 Key 存在后端服务器环境变量中，前端只访问你自己的接口，不接触真实密钥。

### 什么时候用后端代理？
- 准备上线
- 需要更严格的安全控制
- 需要做用户鉴权、限流、日志审计

### 新手怎么选？
- **做练习 Demo**：先用环境变量方式跑通流程
- **准备上线**：优先后端代理，别把真实密钥暴露给浏览器

### 你现在先记住这条
**前端负责展示和交互，后端负责保管密钥。**

# 第4章 第4章 设计聊天页面：先做出能用的输入框、按钮和消息区

这一章先不碰复杂逻辑，先把**聊天页骨架**搭出来。新手最容易翻车的地方，往往不是接口，而是页面一开始没设计好，后面加功能时布局全乱，返工很重。更稳妥的做法是：**先把标题区、消息列表区、输入区、发送按钮一次摆好**，让页面先像一个真正的聊天应用，再往里接 API、流式输出和历史记录。

你可以把这一步理解成搭积木：先搭壳，后填内容。壳先做好，下一章接真实接口时就不会乱。

---

## 一、先定页面结构：从上到下分四块

聊天页面不用一开始就做复杂，先固定成最小可用结构就行：

1. **标题区**：显示应用名、简短说明、当前状态  
2. **消息列表区**：展示用户和 AI 的对话内容  
3. **输入区**：输入问题，支持多行  
4. **发送按钮**：提交消息，进入请求流程  

这个顺序很重要。先有标题，用户知道这是啥；再有消息区，能看见对话；最后是输入和按钮，完成交互闭环。

### 先记住一个判断标准

如果你打开页面，能一眼看出：

- 这是一个聊天工具；
- 你可以输入内容；
- 你可以发送消息；
- 发出去后消息会显示在列表里；

那这个页面骨架就合格了。

### 常见误区

- 一上来就写复杂样式，结果接口还没接，布局已经乱了；
- 输入框只做单行，后面加回车发送会很别扭；
- 没有消息列表区，无法展示对话历史；
- 按钮没有禁用状态，空输入也能点。

---

## 二、先把组件拆开，后面才好加功能

这一节不是为了“做漂亮”，而是为了“做得稳、做得快、后面好改”。建议最少拆成这四个部分：

- `ChatPage`：整个聊天页面容器
- `MessageList`：消息列表
- `MessageItem`：单条消息
- `ChatInput`：输入区 + 发送按钮

这样后面要加流式输出、Markdown 渲染、历史保存时，不用整页重写。

### Vue 版模板思路

```vue
<template>
  <div class="chat-page">
    <header class="chat-header">
      <h1>AI 聊天助手</h1>
      <p>输入问题，立即开始对话</p>
    </header>

    <main class="chat-main">
      <section class="message-list">
        <div
          v-for="(msg, index) in messages"
          :key="index"
          class="message-item"
          :class="msg.role"
        >
          {{ msg.content }}
        </div>
      </section>

      <section class="chat-input-area">
        <textarea
          v-model="input"
          placeholder="请输入你的问题…"
          rows="4"
        ></textarea>
        <button :disabled="!input.trim() || loading" @click="sendMessage">
          {{ loading ? '发送中...' : '发送' }}
        </button>
      </section>
    </main>
  </div>
</template>
```

      </header>

      <main className="chat-main">
        <section className="message-list">
          {messages.map((msg, index) => (
            <div key={index} className={`message-item ${msg.role}`}>
              {msg.content}
            </div>
          ))}
        </section>

        <section className="chat-input-area">
          <textarea
            value={input}
            onChange={(e) => setInput(e.target.value)}
            placeholder="请输入你的问题…"
            rows={4}
          />
          <button disabled={!input.trim() || loading} onClick={sendMessage}>
            {loading ? '发送中...' : '发送'}
          </button>
        </section>
      </main>
    </div>
  );
}
```

先做最小版本就够了：容器、标题、消息列表、文本框、按钮。结构先对，后面加功能才轻松。

## 三、输入框怎么设计：多行输入、回车发送、按钮禁用

聊天页里的输入框不是普通表单，至少要处理三个点：**多行输入、回车发送、按钮禁用**。

### 1）多行输入

AI 对话里用户经常输入长问题，所以优先用 `textarea`，不要一开始就用单行 `input`。它更适合聊天场景，也方便后面加“Shift + Enter 换行”。

### 2）回车发送

建议采用常见规则：

- **Enter**：发送
- **Shift + Enter**：换行

这样既方便输入长文本，也符合聊天产品习惯。

### 3）按钮禁用状态

按钮至少在以下情况禁用：

- 输入为空
- 正在请求中
- 发送逻辑未准备好

判断可以直接写成：

```js
const canSend = input.trim().length > 0 && !loading;
```

这样能避免空消息发送、重复点击、接口未返回又触发下一次请求。

### 事件处理建议

- `textarea` 监听 `keydown`；
- 如果按下 `Enter` 且不是 `Shift + Enter`，阻止默认换行并发送；
- 发送成功后清空输入框；
- 发送失败时保留输入内容，方便重试。

- 用户消息右对齐
- AI 消息左对齐

## 六、可直接改造的聊天页模板

下面这份模板可以直接改。你只要替换到项目页面里，再补上发送逻辑，就能继续往下做。

```vue
<template>
  <div class="chat-page">
    <header class="chat-header">
      <h1>AI 聊天助手</h1>
      <p>支持输入、发送、消息展示和后续流式输出</p>
    </header>

    <main class="chat-main">
      <section class="message-list">
        <div
          v-for="(msg, index) in messages"
          :key="index"
          class="message-item"
          :class="msg.role"
        >
          {{ msg.content }}
        </div>
      </section>

      <section class="chat-input-area">
        <textarea
          v-model="input"
          placeholder="请输入你的问题，Enter 发送，Shift + Enter 换行"
          rows="4"
          @keydown="handleKeydown"
        ></textarea>

        <button :disabled="!canSend" @click="sendMessage">
          {{ loading ? '发送中...' : '发送' }}
        </button>
      </section>
    </main>
  </div>
</template>

<script setup>
import { computed, ref } from 'vue';

const input = ref('');
const loading = ref(false);
const messages = ref([
  { role: 'assistant', content: '你好，我是 AI 助手。你可以先问我一个简单问题。' }
]);

const canSend = computed(() => input.value.trim().length > 0 && !loading.value);

function handleKeydown(e) {
  if (e.key === 'Enter' && !e.shiftKey) {
    e.preventDefault();
    if (canSend.value) sendMessage();
  }
}

function sendMessage() {
  if (!canSend.value) return;
  messages.value.push({ role: 'user', content: input.value });
  input.value = '';
  loading.value = true;

  // 下一章在这里接 API 请求
  setTimeout(() => {
    messages.value.push({ role: 'assistant', content: '这里是占位回复，后面替换成模型返回结果。' });
    loading.value = false;
  }, 800);
}
</script>
```

# 第5章 第5章 发起第一次请求：用 fetch 或 axios 把消息发给模型

## 开篇引入：先别急着做花活，先把“消息送出去”

到这一步，你已经有了输入框、发送按钮和消息区域。接下来最重要的，不是动画，也不是复杂气泡样式，而是**让前端真的把用户消息发给模型服务，并把返回结果显示出来**。

本章只做一件事：把“用户输入 → 请求模型 → 拿到回复 → 显示到页面”这条最小闭环跑通。先别管流式输出、上下文记忆、复杂鉴权，这一章的目标很明确：**先发出第一条成功请求**。只要这个闭环建立起来，后面再加流式、Markdown、历史记录都会顺很多。

换句话说，这一章不是让你一下子理解所有原理，而是让你**真的把第一条消息送出去，并把结果拿回来**。

## 一、先把请求要素整理清楚：你到底要发什么？

前端调用大模型 API，最少要准备四样东西：

- **用户输入内容**：输入框里的文字
- **请求地址**：接口 URL
- **请求头**：通常包括 `Content-Type` 和鉴权信息
- **请求体**：真正传给模型的 JSON 数据

你可以把它理解成一次“发快递”：

- 输入内容 = 包裹
- 请求地址 = 收件地址
- 请求头 = 快递单和身份信息
- 请求体 = 包裹里的具体东西

### 1.1 最小请求体长什么样

不同平台字段名可能不同，但常见结构大概是这样：

```js
{
  model: "gpt-4o-mini",
  messages: [
    { role: "user", content: "你好，帮我写一个自我介绍" }
  ],
  temperature: 0.7
}
```

如果后面要做多轮对话，`messages` 就会不断追加历史消息。现在先不用复杂化，先发一条用户消息即可。

### 1.2 发送前先做最简单校验

点击发送后，先做两件事：

- 去掉前后空格
- 判断是否为空

```js
const content = inputValue.trim();
if (!content) {
  setError("请输入内容后再发送");
  return;
}
```

这一步很小，但能避免很多低级问题，比如空字符串、只有空格、误点发送却没有有效请求。

### 1.3 前端要准备哪些状态

至少准备这几个状态：

- `inputValue`：输入框内容
- `messages`：对话列表
- `loading`：是否正在请求
- `error`：错误提示

记住一句话：

> 凡是会影响页面显示的内容，基本都应该放在状态里。

这样请求完成后，页面才能自动刷新，不需要手动改 DOM。

#### 本章练习
- 把输入框内容绑定到状态
- 点击发送时先输出 `trim()` 后的内容
- 为空时给出提示，不发请求

#### 本章结果
你会得到一个可检查输入的发送入口，为后面的请求打基础。

---

## 二、先用 fetch 跑通第一次请求：理解最基础的发送和接收流程

如果先不引入额外库，`fetch` 是最直接的选择。它适合先理解浏览器怎么发请求。

### 2.1 fetch 最小可运行模板

```js
async function sendMessageByFetch(userText) {
  setLoading(true);
  setError("");

  try {
    const response = await fetch("https://api.example.com/v1/chat/completions", {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "Authorization": `Bearer ${import.meta.env.VITE_API_KEY}`
      },
      body: JSON.stringify({
        model: "gpt-4o-mini",
        messages: [
          { role: "user", content: userText }
        ],
        temperature: 0.7
      })
    });

    if (!response.ok) {
      throw new Error(`请求失败：${response.status}`);
    }

    const data = await response.json();
    return data?.choices?.[0]?.message?.content || "没有返回内容";
  } finally {
    setLoading(false);
  }
}
```

### 2.2 你先看懂这 4 件事就够了

1. `fetch(url, options)`：发请求  
2. `headers`：告诉服务端我发的是什么格式，以及我是谁  
3. `body`：真正要传的内容  
4. `response.json()`：把返回结果转成 JS 对象

最容易出错的是 `body`。不要直接把对象塞进去，通常要先 `JSON.stringify()`。

### 2.3 fetch 常见误区

- 直接把对象塞进 body，不行，要先 `JSON.stringify()`
- 没判断 `response.ok`，接口报错时不一定会直接 throw
- 把 API Key 写死在代码里，不要这么做
- 只看控制台，不看 Network，定位问题会很慢

### 2.4 一次完整调用的顺序

你可以按这个顺序理解：

- 点击发送按钮
- 读取输入框内容
- 设置 `loading = true`
- 发 `fetch` 请求
- 拿到返回值
- 更新消息列表
- 关闭 `loading`
- 如果报错，显示错误信息

第一次没成功时，优先看：

- 请求地址是否正确
- 请求头有没有带鉴权信息
- 请求体字段是否符合要求
- 返回值结构是不是你预期的

#### 本章练习
- 用 `fetch` 发送一条固定文本到接口
- 打印返回的原始 JSON
- 再从 JSON 中取出模型回复内容

#### 本章结果
你能用最基础的浏览器能力完成一次模型请求，理解“发送—接收”的基本链路。

## 三、再用 axios 写一遍：按你的习惯选更顺手的方式

如果你觉得 `fetch` 太原生，想写得更顺手一点，`axios` 很适合。它的优点很直接：

- JSON 处理更省心
- 错误对象更好读
- 更贴近常见工程写法

### 3.1 先安装 axios

```bash
npm install axios
```

### 3.2 axios 最小请求模板

```js
import axios from "axios";

async function sendMessageByAxios(userText) {
  setLoading(true);
  setError("");

  try {
    const { data } = await axios.post(
      "https://api.example.com/v1/chat/completions",
      {
        model: "gpt-4o-mini",
        messages: [
          { role: "user", content: userText }
        ],
        temperature: 0.7
      },
      {
        headers: {
          "Authorization": `Bearer ${import.meta.env.VITE_API_KEY}`,
          "Content-Type": "application/json"
        }
      }
    );

    return data?.choices?.[0]?.message?.content || "没有返回内容";
  } catch (err) {
    const msg = err?.response?.data?.error?.message || err.message || "请求失败";
    throw new Error(msg);
  } finally {
    setLoading(false);
  }
}
```

### 3.3 fetch 和 axios 怎么选

- **想理解浏览器原生能力**：先用 `fetch`
- **想快速开发、少写样板代码**：用 `axios`

两者都能完成任务。你现在最重要的不是选边站，而是先把请求跑通。

### 3.4 二者最重要的差别

- `fetch`：遇到 4xx/5xx 不一定抛异常，要手动判断
- `axios`：状态码异常通常会进入 `catch`，更省心

如果你想少踩坑，axios 往往更友好；如果你想看懂底层流程，fetch 更适合入门。

#### 本章练习
- 用 axios 再写一遍同样的请求
- 对比 fetch 和 axios 的错误处理
- 故意传错 API 地址，观察错误信息

#### 本章结果
你可以按自己的习惯选择请求方式，并知道如何拿到模型回复。

## 四、把请求结果渲染到页面上：真正形成最小可用聊天闭环

真正像聊天应用，不能只把回复打印在控制台里，而是要显示到页面上。

### 4.1 先把消息列表结构定下来

最小数据结构可以这样设计：

```js
const [messages, setMessages] = useState([
  { role: "assistant", content: "你好，我是你的 AI 助手" }
]);
```

发送时的更新逻辑可以这样写：

```js
async function handleSend() {
  const content = inputValue.trim();
  if (!content) return;

  const userMsg = { role: "user", content };
  setMessages(prev => [...prev, userMsg]);
  setInputValue("");
  setLoading(true);

  try {
    const reply = await sendMessageByFetch(content);
    const aiMsg = { role: "assistant", content: reply };
    setMessages(prev => [...prev, aiMsg]);
  } catch (err) {
    setError(err.message || "请求失败");
  } finally {
    setLoading(false);
  }
}
```

一个实用技巧：**先把用户消息追加到列表里，再请求 AI 回复**。这样页面响应更快，也更像真实聊天软件。

### 4.2 页面渲染最小写法

```jsx
<div className="chat-box">
  {messages.map((msg, index) => (
    <div key={index} className={`msg ${msg.role}`}>
      {msg.content}
    </div>
  ))}

  {loading && <div className="msg assistant">AI 正在思考中...</div>}

  {error && <div className="error">{error}</div>}
</div>
```

后面可以继续优化：

- 用户消息靠右，助手消息靠左
- 不同颜色区分角色
- loading 时显示“正在输入...”

但这一章先别复杂化，先保证能跑起来。

### 4.3 基础 UI 美化：先把能看清楚做好

最小 Demo 也建议做一点基础美化，不然调试时很难看清状态：

```css
.chat-box {
  padding: 16px;
  max-height: 500px;
  overflow-y: auto;
  background: #f8f8f8;
}

.msg {
  margin-bottom: 12px;
  padding: 10px 12px;
  border-radius: 8px;

  background: #dff4ff;
  text-align: right;

### 4.4 这一步的判断标准

如果你做对了，页面上应该出现这些变化：

- 输入一段话，点击发送

#### 本章练习
- 让消息列表支持用户消息和助手消息两种角色

## 五、API Key 的安全存放：最少也要做到“别直接写死”

这一章是第一次真正发请求，API Key 也会第一次进入代码视野。这里必须先说清楚：**不要把 Key 直接写进源码并提交到仓库**。

### 5.1 推荐方案：放到环境变量里

如果你用的是 Vite，一般这样写：

```bash
VITE_API_KEY=你的key
```

然后在代码里读取：

```js
const apiKey = import.meta.env.VITE_API_KEY;
```

如果你用 React、Vue CLI 或其他脚手架，读取方式会不同，但思路一样：**把敏感信息放在环境变量里，而不是写死在组件代码里。**

### 5.2 不推荐方案：直接在前端请求里裸露 Key

不推荐这样写：

```js
headers: {
  Authorization: "Bearer sk-xxxxx"
}
```

原因很简单：

- 容易被打包后直接看到
- 容易被提交到代码仓库
- 线上被别人复制拿去乱用

### 5.3 更稳的做法：前端走后端代理

正式项目里更推荐：

- 前端把用户输入发给自己的后端
- 后端再带着 Key 去请求模型
- 后端把结果返回给前端

这一章为了让你快速跑通 Demo，可以先用环境变量；正式项目里更推荐后端代理来保护 Key。

#### 本章练习
- 把代码里的 Key 改成环境变量读取
- 检查项目里有没有把 Key 写死在源码中
- 记录 Demo 用前端直连，正式项目走后端代理

#### 本章结果
你能区分“演示可用”和“正式可用”两种做法，避免把 Key 裸露出去。

## 六、基础鉴权怎么做：Demo 能跑，正式项目别乱来

很多新手会问：前端是不是只要拿到 Key 就能直接调接口？  
答案是：**Demo 可以这样做，但正式项目不建议这样做。**

### 6.1 推荐和不推荐，简单对照

| 场景 | 推荐方式 | 说明 |
|---|---|---|
| 本地学习 Demo | 前端读环境变量，先跑通流程 | 方便新手快速上手 |
| 正式线上项目 | 前端请求自己的后端，再由后端调用模型接口 | 更安全，Key 不暴露 |
| 团队协作项目 | 统一通过后端做鉴权和限流 | 便于管理和排查问题 |

### 6.2 前端基础鉴权能做什么

前端本身不适合承担真正的密钥保护，但至少可以做一些基础处理：

- 登录后才显示聊天入口
- 每次请求带上自己的用户 token
- 请求前检查是否登录
- 出错时提示“请先登录”或“鉴权失败”

注意，这些只能算**基础鉴权**，真正敏感的 Key 还是应该放在后端。

#### 本章练习
- 给发送按钮加一个登录态判断
- 未登录时禁止发送
- 在请求头里保留你自己的用户 token 位置

#### 本章结果
你会知道前端能做什么、不能做什么，避免把安全问题理解错。

## 七、常见报错排查：为什么请求发出去了却没结果？

如果接口没成功，优先看这四项：

1. **API 地址写错了**
2. **API Key 没读到**
3. **请求体字段不符合接口要求**
4. **浏览器控制台有跨域或网络错误**

这四个问题，几乎覆盖了新手阶段大多数“代码没语法错，但就是不返回”的情况。

### 7.1 快速排查清单

按这个顺序查：

- 控制台有没有报错
- Network 里请求有没有发出去
- `status` 是多少
- 返回体里有没有错误信息
- `.env` 是否在修改后重新启动项目

特别提醒：如果你改了环境变量，很多前端项目需要**重启开发服务器**才会生效。只改 `.env` 不重启，页面里读到的可能还是旧值。

### 7.2 新手最容易忽略的点

- `.env` 变量名前缀不对，比如 Vite 要用 `VITE_`
- 修改环境变量后没重启开发服务器
- 把 `undefined` 当成 API Key 发送了
- 请求体缺少必填字段
- 接口地址写错，环境也配错

如果一直 401，优先检查 Key；如果是 400，优先检查请求体字段；如果是网络错误，优先检查地址和跨域。

#### 本章练习
- 故意把 API 地址写错，观察报错信息
- 故意去掉 Authorization 头，观察返回结果
- 打开浏览器 Network 面板，查看请求记录和状态码

#### 本章结果
你能快速定位“请求没成功”的常见原因，不再只盯着代码发呆。

# 第6章 第6章 渲染消息列表：把用户消息和 AI 回复做成对话形式

这一章要解决的，不是“能不能发请求”，而是“怎么让用户真的像在和 AI 聊天”。

单次请求只能看到一段回答，真正像 ChatGPT 的网页应用，必须把每次输入和回复累积成消息列表，并用不同样式展示出来。做完这一章后，页面会从“一个输入框 + 一个按钮”升级成“可持续对话的聊天界面”。后面的流式输出、Markdown 渲染、对话历史保存，底层都依赖这套消息结构。

## 6.1 先定数据结构：角色、内容、时间、状态

先别急着写样式，先把数据结构定好。聊天页面最怕一开始随便存，后面要加流式输出、失败重试、历史记录时全部乱掉。

### 推荐的消息结构

```js
{
  id: 'msg_001',
  role: 'user',      // user | assistant | system
  content: '帮我写一个登录页',
  time: Date.now(),
  status: 'done'     // sending | done | error
}
```

### 这四个字段分别干什么

- **role**：区分是谁说的话，常用 `user` 和 `assistant`
- **content**：消息正文，流式输出时就往这里追加
- **time**：用于显示时间、排序、持久化
- **status**：用于展示“发送中”“已完成”“失败”

后面如果要做“重新生成”“复制消息”“点击重试”，这些字段都会用上。

### 推荐做法和不推荐做法

| 做法 | 推荐吗 | 说明 |
|---|---|---|
| 只存字符串数组 | 不推荐 | 后面没法区分角色和状态 |
| 只用一个 `text` 字段 | 不推荐 | 扩展时很痛苦 |
| 用对象数组保存消息 | 推荐 | 最适合聊天列表、流式输出、历史保存 |

### 可直接改造的模板

```js
const messages = ref([
  {
    id: 'msg_001',
    role: 'assistant',
    content: '你好，我可以帮你写前端页面。',
    time: Date.now(),
    status: 'done'
  }
])
```

### 本章练习

把当前的聊天数据从“纯文本数组”改成上面的消息对象数组。

### 本章结果

你会得到一个可以支撑多轮对话的基础数据模型。

## 6.2 区分用户消息和 AI 消息：左右气泡直接做出来

聊天感的核心，就是左右不同、颜色不同、气泡不同。用户和 AI 必须一眼分开，不然页面会像普通留言板。

### 页面布局建议

- 用户消息：右侧、蓝色或深色气泡、文字靠右
- AI 消息：左侧、浅色气泡、文字靠左
- 时间：放在气泡下方，小字灰色
- 状态：发送中显示“正在思考…”，失败显示“发送失败，可重试”

### 可直接改造的模板

```html
<div class="chat-list">
  <div
    class="msg"
    :class="msg.role === 'user' ? 'msg-user' : 'msg-ai'"
    v-for="msg in messages"
    :key="msg.id"
  >
    <div class="bubble">
      <div class="content">{{ msg.content }}</div>
      <div class="meta">
        <span>{{ formatTime(msg.time) }}</span>
        <span v-if="msg.status === 'sending'">发送中...</span>
        <span v-if="msg.status === 'error'">发送失败</span>
      </div>
    </div>
  </div>
</div>
```

```

- 气泡不要太宽，手机端建议最多占屏幕 70%~80%
- 用户和 AI 的圆角做出差异，视觉会更自然

如果你闭上眼睛看页面，仍能立刻分清：

- 谁发的
- 哪条是最新的

那就说明样式已经达标。

## 6.3 处理空状态、首条消息和自动滚动到底部

新手最容易忽略的是“没有消息时怎么办”。实际上，空状态和自动滚动直接影响体验。

### 1）空状态怎么做

当 `messages.length === 0` 时，不要只显示空白页。可以给一个简单引导：

```html
<div v-if="messages.length === 0" class="empty">
  <h3>开始你的第一轮对话</h3>
  <p>试着输入：帮我写一个 Vue 登录页</p>
</div>
```

空状态的作用很直接：

- 告诉用户这里可以用
- 帮用户快速发出第一条消息

你也可以放几个快捷提问按钮，比如“写一个待办事项页面”“帮我改一下代码结构”，降低新手的使用门槛。

### 2）首条消息怎么处理

首条消息通常是用户消息，发出去后立刻插入列表。推荐流程：

1. 用户点击发送
2. 先把用户消息 push 到数组
3. 再插入一条 AI 占位消息，如“正在思考…”
4. 请求返回后替换占位内容

这样用户不会感觉页面卡住，尤其在网络慢的时候，这个“先插入、后请求”的顺序很重要。

### 3）消息如何自动滚动到底部

聊天界面必须让最新消息始终可见。做法很简单：每次 `messages` 更新后，把底部锚点滚动出来。

```js
const listRef = ref(null)

watch(
  () => messages.value.length,
  () => {
    nextTick(() => {
      listRef.value?.scrollTo({ top: listRef.value.scrollHeight, behavior: 'smooth' })
    })
  }
)
```

如果是流式输出，建议不仅在 `length` 改变时滚动，还要在 `content` 更新时也触发一次，否则文字会一边生成一边跑出可视区。

### 常见误区

- 只在首次进入时滚动一次，后面消息被挡住
- 流式输出时没持续滚动，文字卡在屏幕外
- 空状态占太大空间，导致输入框跑得很下面

### 本章练习

做一个空状态页，并让新消息出现后自动滚到最底部。

### 本章结果

用户一发消息，聊天体验就自然起来了。

## 6.4 把列表抽成可复用组件，后面直接套用

这一章不只是“把列表做出来”，还要把它做成以后能反复用的模块。否则你每换一个项目都要重写一次。

### 组件拆分建议

你可以拆成三个部分：

- **MessageList**：只负责展示列表
- **MessageItem**：只负责单条气泡
- **ChatInput**：只负责输入和发送

这样做的好处很直接：

- 样式更好维护
- 状态更容易管理
- 后面加 Markdown、图片、引用块也方便

### 一个实用模板

```html
<MessageList :messages="messages" />
<ChatInput @send="handleSend" />
```

```js
// MessageList 接收 messages
props: {
  messages: { type: Array, default: () => [] }
}
```

### Vue / React 都能套的思路

- **Vue**：用 `props` 接收 `messages`，用 `v-for` 渲染
- **React**：用 `props.messages.map(...)` 渲染
- 两边都尽量让组件只负责展示，不要把请求逻辑塞进去

### 组件里要保留的扩展点

- 是否显示时间
- 是否显示头像
- 是否显示失败重试按钮
- 是否支持 Markdown 渲染
- 是否支持流式输出中的“打字中”光标

这里要注意：**不要把展示组件写死**。今天你可能只想显示纯文本，明天就可能要支持代码块、列表、链接。提前留好扩展口，后面会省很多事。

### 模板复用的关键原则

1. 展示和业务分离
2. 数据结构先统一
3. 样式做成类名可切换
4. 状态字段保留扩展空间

### 本章练习

把聊天列表抽成独立组件，主页面只保留数据和发送逻辑。

### 本章结果

你会得到一个可复用的对话列表模板，后面做“历史记录页”“多会话页”都能直接拿来改。

# 第7章 第7章 做出流式输出：让 AI 回复一边生成一边显示

第一次把大模型接到前端时，很多人会遇到同一个问题：点了发送，页面卡几秒，然后一次性吐出一大段答案。虽然能用，但体验不像 ChatGPT。  
这一章我们把“等整段返回”改成“边生成边显示”，让聊天页立刻更像一个真正的产品。

---

## 一、先看效果：流式输出到底长什么样

流式输出最直观的效果是：**用户一点击发送，AI 回复气泡马上出现，文字一段段往外冒，最后完整收尾**。

你可以把它理解为三种状态：

- **等待中**：还没发出请求
- **生成中**：AI 正在一段段返回内容
- **结束后**：回复完整显示，按钮恢复可用

和一次性返回相比，流式输出提升的不是计算速度，而是**反馈速度**。用户会立刻知道：系统正在工作。

### 页面应该出现的变化

1. 用户发送消息  
2. 页面先插入一条空的 AI 消息，或显示“正在生成…”  
3. 回复内容逐段追加  
4. 生成结束后，状态恢复正常  

做对之后，页面会很像真实 ChatGPT：**不是等结果，而是看结果生成**。

---

## 二、先准备最小可运行状态

这一章先用 `fetch` 来做，因为它最适合读取流式响应。新手阶段先把这条路跑通，再考虑换成 axios。

```js
const [messages, setMessages] = useState([]);
const [input, setInput] = useState('');
const [loading, setLoading] = useState(false);
const [error, setError] = useState('');
const controllerRef = useRef(null);
```

这几个状态就够支撑一个最小聊天页：

- `messages`：聊天记录
- `input`：输入框内容
- `loading`：是否正在生成
- `error`：错误提示
- `controllerRef`：停止生成用

---

## 三、用 fetch 读取流，并逐段追加到最后一条消息

核心思路只有一句：**先插入一条空的 assistant 消息，然后每读到一段流，就更新它的内容**。

### 最小实现模板

```js
async function handleSend() {
  if (!input.trim() || loading) return;

  const userText = input;
  setInput('');
  setError('');
  setLoading(true);

  const userMsg = { role: 'user', content: userText };
  const aiMsg = { role: 'assistant', content: '' };

  setMessages(prev => [...prev, userMsg, aiMsg]);

  const controller = new AbortController();
  controllerRef.current = controller;

  try {
    const res = await fetch('/api/chat', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      signal: controller.signal,
      body: JSON.stringify({
        messages: [...messages, userMsg],
        stream: true
      })
    });

    if (!res.ok) throw new Error(`请求失败：${res.status}`);
    if (!res.body) throw new Error('当前浏览器不支持流式响应');

    const reader = res.body.getReader();
    const decoder = new TextDecoder('utf-8');
    let done = false;
    let aiText = '';

    while (!done) {
      const { value, done: finished } = await reader.read();
      done = finished;

      if (value) {
        const chunkText = decoder.decode(value, { stream: true });
        aiText += chunkText;

        setMessages(prev => {
          const copy = [...prev];
          copy[copy.length - 1] = {
            role: 'assistant',
            content: aiText
          };
          return copy;
        });
      }
    }
  } catch (err) {
    if (err.name === 'AbortError') {
      setError('已停止生成');
    } else {
      setError(err.message || '发送失败');
    }
  } finally {
    controllerRef.current = null;
    setLoading(false);
  }
}
```

### 这段代码最重要的三步

- **先加用户消息**
- **再加一个空的 AI 消息**
- **每次读到新数据，都覆盖最后一条 AI 消息**

这就是流式更新的基本套路。  
新手最容易犯的错，是每来一段就新建一条 assistant 消息。那样消息列表会乱，后面做 Markdown、历史保存也会更麻烦。

## 四、把“生成中、停止中、结束后”状态做清楚

### 1）生成中：按钮置灰，输入框暂时不可重复提交

```jsx

```jsx

## 五、逐段更新和逐字更新，怎么选

流式展示常见有两种方式：

### 1）逐段更新：最推荐新手先做

后端返回一小段，前端就追加一小段。  
优点是稳定、简单、最像真实流式接口。

### 2）逐字更新：更像“打字效果”

如果后端一次性返回完整文本，你也可以在前端模拟逐字显示：

```js
function typeWriter(text, onUpdate, onDone) {
  let i = 0;
  const timer = setInterval(() => {
    i += 1;
    onUpdate(text.slice(0, i));
    if (i >= text.length) {
      clearInterval(timer);
      onDone && onDone();
    }
  }, 20);
}
```

这个方案适合：

- 接口暂时不支持真正流式
- 想先做一个“像聊天产品”的效果
- 想在 demo 阶段快速出成果

### 什么时候用哪种

- **真实接流式接口**：优先用逐段更新
- **演示或补效果**：可以用逐字更新

## 一、先接入 Markdown 渲染组件或库：让富文本有地方“落地”

### 你要解决的问题

AI 返回的内容通常不是纯文本，而是 Markdown。前端如果直接当字符串显示，格式会全部丢失：

- 标题不会变大
- 列表不会换行
- 代码块不会高亮
- 链接不会变成可点击内容

所以不能再直接 `{{ content }}` 或 `{content}` 了事，而要先解析 Markdown，再渲染。

### 标准流程

1. 把 AI 回复字符串交给 Markdown 解析器
2. 解析成 HTML 或组件
3. 再补样式

### React 参考模板

先安装依赖：

```bash
npm i react-markdown remark-gfm rehype-highlight highlight.js
```

基础组件：

```jsx
import ReactMarkdown from "react-markdown";
import remarkGfm from "remark-gfm";

export default function MessageContent({ content }) {
  return <ReactMarkdown remarkPlugins={[remarkGfm]}>{content}</ReactMarkdown>;
}
```

### Vue 参考模板

先安装依赖：

```bash
npm i markdown-it dompurify
```

封装渲染方法：

```js
import MarkdownIt from "markdown-it";

const md = new MarkdownIt({ breaks: true, linkify: true });

export function renderMarkdown(text) {
  return md.render(text);
}
```

页面里渲染：

```vue
<div v-html="safeHtml"></div>
```

把当前消息列表里的 `content` 改成 Markdown 渲染，先让最基础的格式正常显示。

### 结果

你会立刻看到变化：

- `# 标题` 变成标题
- `- 列表` 正常分行
- `**加粗**` 不再是原始字符

## 二、先看渲染前后差异，再处理常见富文本元素

### 渲染前

AI 原始输出通常长这样：

```md
**推荐步骤**
- 第一步：安装依赖
- 第二步：接入接口
- 第三步：测试结果

> 这是一个引用

```js
console.log("hello");
```

访问 [官网](https://example.com)
```

如果直接显示字符串，用户看到的就是一堆符号，重点也不容易抓住。

### 渲染后应该变成什么样

- **加粗** 会被突出显示
- 列表自动换行并缩进
- 引用有左侧样式
- 代码块单独成段
- 链接可以点击跳转

### 实战处理建议

按优先级处理：

1. **列表、引用、加粗、链接**：交给 Markdown 库标准处理
2. **代码块**：单独加样式，最好支持高亮
3. **链接**：建议新窗口打开
4. **长代码块**：必须支持横向滚动

### React 示例：代码块自定义

```jsx
import ReactMarkdown from "react-markdown";
import remarkGfm from "remark-gfm";

function CodeBlock({ children }) {
  return <pre className="code-block">{children}</pre>;
}

export default function MessageContent({ content }) {
  return (
    <ReactMarkdown
      remarkPlugins={[remarkGfm]}
      components={{
        code({ inline, children }) {
          return inline ? (
            <code className="inline-code">{children}</code>
          ) : (
            <CodeBlock>{children}</CodeBlock>
          );
        },
        a({ href, children }) {
          return (
            <a href={href} target="_blank" rel="noreferrer">
              {children}
            </a>
          );
        },
      }}
    >
      {content}
    </ReactMarkdown>
  );
}
```

### 常见误区

- 只渲染 Markdown，却不给代码块加样式，结果一大片灰底看不清
- 链接不加 `target="_blank"`，用户点出去回不来
- 长代码块不加滚动，页面直接被撑坏
- 以为所有内容都该“自动美化”，结果把结构搞乱

### 检查清单

- [ ] 列表有缩进
- [ ] 引用有左边框
- [ ] 代码块可横向滚动
- [ ] 外链新窗口打开
- [ ] 加粗和斜体能正确显示

这五项都通过，说明你的 Markdown 基础渲染已经合格。

## 三、怎么简单处理 XSS 与安全渲染边界？

### 你要解决的问题

`v-html`、`dangerouslySetInnerHTML` 很方便，但本质上是把 HTML 直接塞进页面。如果内容不干净，就可能带来 XSS 风险。

AI 输出大多是正常文本，但不能默认它永远安全。尤其是把用户输入和模型输出混合渲染时，更要留心。

### 最稳妥的原则

记住三条就够了：

- **优先用 Markdown 解析成组件**
- **不要直接信任模型输出的 HTML**
- **必须渲染 HTML 时先净化**

### Vue 场景

如果要用 `v-html`，建议先净化再渲染：

```bash
npm i dompurify markdown-it
```

```js
import DOMPurify from "dompurify";
import MarkdownIt from "markdown-it";

const md = new MarkdownIt({ linkify: true, breaks: true });

export function renderSafeMarkdown(text) {
  const html = md.render(text);
  return DOMPurify.sanitize(html);
}
```

### React 场景

React 更推荐直接用 `react-markdown` 这种组件化方式，天然比拼接 HTML 更稳。如果真要插入 HTML，也要先净化。

### 安全边界怎么判断

一句话就够了：

**模型输出是内容，不是可信代码。**

所以：

- 链接可以显示，但尽量只允许 `http/https`
- 图片、脚本、内联事件不要随便放开
- 用户输入和模型输出都不要直接当安全文本

### 推荐方案和不推荐方案

| 场景 | 推荐做法 | 不推荐做法 |
| --- | --- | --- |
| React 渲染 AI 回复 | `react-markdown + remark-gfm` | 直接拼接 HTML 再塞进页面 |
| Vue 渲染 AI 回复 | `markdown-it + DOMPurify` | 直接 `v-html="content"` |
| 链接处理 | `target="_blank" rel="noreferrer"` | 默认当前页跳转 |
| 富文本安全 | 先解析，再净化 | 相信模型输出天然安全 |

### 练习

给你的 Markdown 渲染层加入净化处理，测试：

- `<script>alert(1)</script>`
- 奇怪协议的链接
- 非法 HTML 标签

### 结果

你不仅能显示富文本，还建立了最基本的安全意识，这对上线和公开演示都很重要。

# 第9章 第9章 保存对话历史：刷新页面后也能继续聊

## 一、先用 localStorage 做最小可用方案

入门项目里，最稳妥的方案就是用 `localStorage`。它不需要后端和数据库，先把功能跑通最重要。

### 适合用它的场景
- 只保存当前浏览器里的聊天记录
- 想快速做出可演示效果
- 还没接入账号体系和云端同步

### 不适合只靠它的场景
- 需要多设备同步
- 需要长期保存或团队共享
- 对隐私和数据管理要求更高

### 建议保存的字段
- `role`：消息角色，如 `user`、`assistant`
- `content`：消息正文
- `createdAt`：可选，记录时间
- `id`：可选，方便渲染和更新

### 可直接套用的存储模板

```js
const STORAGE_KEY = "ai_chat_history_v1";

export function saveChatHistory(messages) {
  localStorage.setItem(STORAGE_KEY, JSON.stringify(messages));
}

export function loadChatHistory() {
  const raw = localStorage.getItem(STORAGE_KEY);
  if (!raw) return [];
  try {
    const data = JSON.parse(raw);
    return Array.isArray(data) ? data : [];
  } catch {
    return [];
  }
}

export function clearChatHistory() {
  localStorage.removeItem(STORAGE_KEY);
}
```

### 记住一个原则
**每次消息列表变化，就同步到本地。**  
不要等到最后再存，用户随时可能关闭页面。

## 二、页面初始化时恢复历史消息

保存只是第一步，真正有用的是：**页面加载时自动把历史记录读回来**。

### 实现步骤
1. 页面首次打开
2. 从 `localStorage` 读取历史消息
3. 放入消息列表状态
4. 直接渲染历史内容

如果消息只存在 `useState` 或 `ref` 里，刷新后当然会丢。想“接着聊”，就必须在页面启动时恢复一次。

### React 示例

```jsx
import { useEffect, useState } from "react";
import { loadChatHistory, saveChatHistory } from "./chatStorage";

export default function ChatPage() {
  const [messages, setMessages] = useState([]);

  useEffect(() => {
    setMessages(loadChatHistory());
  }, []);

  useEffect(() => {
    saveChatHistory(messages);
  }, [messages]);

  return (
    <div>
      {messages.map((msg, index) => (
        <div key={index}>
          <b>{msg.role}：</b>
          <span>{msg.content}</span>
        </div>
      ))}
    </div>
  );
}
```

### Vue 示例

```vue
<script setup>
import { ref, onMounted, watch } from "vue";
import { loadChatHistory, saveChatHistory } from "./chatStorage";

const messages = ref([]);

onMounted(() => {
  messages.value = loadChatHistory();
});

watch(
  messages,
  (val) => {
    saveChatHistory(val);
  },
  { deep: true }
);
</script>
```

### 这里有个小坑
如果你一进页面就把空数组写回本地，很容易把旧记录覆盖掉。  
所以建议：**先读，再渲染，再监听变化保存。**

### 检查标准
刷新页面后还能看到上次最后几轮对话，说明这一步成功了。

## 三、什么时候更新存储内容

这个点很关键。新手常见做法是“点发送才存一次”，这样看起来能用，但很容易漏数据。

### 推荐更新时机
- 页面初始化：读取历史
- 每次消息列表变化：保存历史
- 点击清空会话：删除历史
- 完成一轮流式输出后：保存完整助手回复

### 不推荐的做法
- 只保存最后一条消息
- 等接口全部结束后才统一保存
- 把输入框内容和消息列表混在一起存

### 简单原则
**消息列表就是事实来源。**  
谁进了列表，谁就该被保存；谁被删除，谁就不该再出现。

如果你做了流式输出，建议在助手回复拼完整后再落盘，这样刷新后恢复的是完整内容，不会出现半句半句的碎片。

## 四、支持清空会话和重新开始

一个能用的聊天应用，必须允许用户“重新来过”。否则一旦聊乱了、上下文过长了，用户很难整理。

### 建议提供两个按钮
- **清空会话**：删除历史消息并清空本地存储
- **重新开始**：本质一样，但文案更友好

### 操作步骤
1. 点击按钮
2. 将消息列表置空
3. 删除本地存储记录
4. 清空输入框
5. 如果有流式输出，顺手中断当前请求

### 可复制代码

```js
function handleClearChat() {
  setMessages([]);
  setInput("");
  clearChatHistory();
  // 如果你有 AbortController，这里也可以取消请求
}
```

### 为什么要清空上下文
当聊天记录越来越长时：
- 请求体会越来越大
- 大模型上下文更容易超限
- 用户也更容易混乱

所以“清空会话”不是装饰按钮，而是实用功能。建议放在输入框旁边，用户一眼就能找到。

---

## 五、多轮上下文怎么组织

很多新手以为聊天就是“用户说一句，发给模型一句”。实际上，多轮对话要把**上下文一起带上**。

### 最基础的消息组织方式

```js
const payload = {
  messages: [
    { role: "system", content: "你是一个简洁的助手" },
    ...messages.slice(-20)
  ]
};
```

### 这样做的目的
模型需要知道：
- 用户前面问过什么
- 助手之前怎么回答
- 当前问题是不是延续上一个话题

### 实战建议
- 把 `messages` 作为唯一事实来源
- 每次新消息都先追加到列表
- 调接口时直接用完整消息数组
- 只保留最近若干轮，避免请求过长

### 更推荐的方案
- **前端负责展示、暂存、恢复**
- **后端代理负责真正发请求**
- **历史消息只保存用户和助手内容**
- **system 提示词由后端统一注入**

### 不推荐的做法
- 把 API Key 直接写在前端
- 把系统提示词、用户输入、调试信息全混在一起
- 无限追加历史，不做裁剪

这一步先做到“能稳定续聊”就够了，后面再慢慢优化裁剪策略。

## 六、一份可直接套用的历史存储模板

下面这份模板可以直接改造。你只需要把它接到发送逻辑里。

```js
const STORAGE_KEY = "ai_chat_history_v1";

export function loadChatHistory() {
  const raw = localStorage.getItem(STORAGE_KEY);
  if (!raw) return [];
  try {
    const data = JSON.parse(raw);
    return Array.isArray(data) ? data : [];
  } catch {
    return [];
  }
}

export function saveChatHistory(messages) {
  localStorage.setItem(STORAGE_KEY, JSON.stringify(messages));
}

export function clearChatHistory() {
  localStorage.removeItem(STORAGE_KEY);
}

export function createUserMessage(content) {
  return {
    role: "user",
    content,
    createdAt: Date.now()
  };
}

export function createAssistantMessage(content) {
  return {
    role: "assistant",
    content,
    createdAt: Date.now()
  };
}
```

### 这些字段怎么扩展
你后面还可以加：
- `id`：用于列表渲染和局部更新
- `status`：比如 `streaming`、`done`
- `error`：保存失败状态
- `model`：记录使用了哪个模型

### 推荐接入方式
- 页面加载时 `loadChatHistory()`
- 新消息进入列表后自动 `saveChatHistory(messages)`
- 点击清空按钮时 `clearChatHistory()`

# 第10章 第10章 做好加载状态、错误提示和基础鉴权

很多 AI 聊天网页“能发请求、能回消息”，但一到真实使用就露馅：用户不知道有没有在请求，失败了没有提示，按钮一顿连点会重复发，多人访问时接口还可能被乱刷。  
这一章只做一件事：把“看起来能用”补成“真的可用”。

---

## 10.1 先把状态拆开：发送中、生成中、失败、可重试

先别急着写 UI，先把状态理清楚。一个可用的聊天页，至少要有这几种状态：

- **空闲**：输入框可编辑，发送按钮可点
- **发送中**：请求已发出，还没拿到模型响应
- **生成中**：流式输出正在持续返回
- **失败**：请求中断、超时、鉴权失败、服务异常
- **可重试**：保留上次输入，一键再发

很多新手只写一个 `loading`，后面做流式输出、错误提示、按钮禁用时就会乱。建议一开始就拆开。

### 推荐状态写法

```js
const [isSending, setIsSending] = useState(false);
const [isStreaming, setIsStreaming] = useState(false);
const [errorMsg, setErrorMsg] = useState('');
const [retryPayload, setRetryPayload] = useState(null);
```

如果你更喜欢一个状态变量，也可以这样：

```js
const [status, setStatus] = useState('idle'); // idle | sending | streaming | error
```

但对新手来说，几个布尔值更直观，也更容易排错。

### 状态切换规则

1. 用户点击发送：`isSending = true`
2. 请求接通：`isSending = false, isStreaming = true`
3. 流式输出完成：`isStreaming = false`
4. 任一步失败：`errorMsg = xxx, isSending = false, isStreaming = false`
5. 用户点重试：复用 `retryPayload`

### 页面反馈要同步

- `isSending` 时，按钮显示“发送中…”
- `isStreaming` 时，回复区显示“AI 正在生成…”
- `errorMsg` 存在时，显示红色提示条
- `retryPayload` 存在时，提供“重试”按钮

### 你要看到的结果

- 点击后立刻有反馈
- 流式回复时界面明确显示“正在生成”
- 出错后能继续操作，不会卡死

---

## 10.2 发送按钮要“锁住”：防重复提交和连点

聊天发送不是搜索框，重点不是防抖，而是：**同一时刻只允许发一次请求**。

### 先做重复提交拦截

```js
const handleSend = async () => {
  if (isSending || isStreaming) return;

  setErrorMsg('');
  setIsSending(true);

  try {
    await sendMessage();
  } catch (err) {
    setErrorMsg(getFriendlyErrorMessage(err));
    setRetryPayload({
      prompt: inputValue,
      messages: [...messages]
    });
  } finally {
    setIsSending(false);
  }
};
```

### 再做按钮联动

```jsx
<button disabled={isSending || isStreaming} onClick={handleSend}>
  {isSending ? '发送中...' : isStreaming ? '生成中...' : '发送'}
</button>
```

- `isSending === true`：按钮禁用
- `isStreaming === true`：按钮禁用
- 有错误时：显示“重试”按钮

### 重试入口怎么放

失败后不要让用户重新打一遍。把上一次请求内容保存下来：

```js
setRetryPayload({
  prompt: inputValue,
  messages: [...messages]
});
```

重试时直接复用：

```js
const handleRetry = () => {
  if (!retryPayload) return;
  setInputValue(retryPayload.prompt);
  handleSend();
};
```

如果担心重试时输入框内容被清空，可以等请求成功后再清空输入。

### 你要看到的结果

- 连点不会发出多次请求
- 按钮状态和请求状态一致
- 失败后可以一键重试

---

## 10.3 错误提示要让用户知道“发生了什么”和“下一步怎么做”

错误提示不要直接把后端报错原样丢给用户。用户不关心 `401`、`500`、`ECONNRESET` 的细节，他们只想知道：**还能不能继续用，下一步该怎么做**。

### 错误提示建议分三类

#### 1）鉴权失败
- “登录已过期，请重新进入页面”
- “接口权限不足，请检查 API Key 或访问令牌”

#### 2）网络失败
- “网络不稳定，请检查连接后重试”
- “请求超时，模型可能响应较慢”

#### 3）服务失败
- “服务暂时不可用，请稍后再试”
- “模型返回异常，建议重试或切换模型”

### 常见失败原因，优先排这几个

- API Key 填错或失效
- 请求地址写错
- CORS 跨域没配好
- 后端限流，短时间请求过多
- 网络断开或浏览器拦截
- 流式响应中途被关闭

### 统一错误文案转换

```js
function getFriendlyErrorMessage(err) {
  const msg = String(err?.message || err);

  if (!navigator.onLine) return '当前网络不可用，请检查后重试';
  if (msg.includes('401')) return '鉴权失败，请检查登录状态或 API Key';
  if (msg.includes('429')) return '请求过于频繁，请稍后再试';
  if (msg.includes('500')) return '服务端异常，请稍后重试';
  if (msg.toLowerCase().includes('timeout')) return '请求超时，请稍后重试';

  return '请求失败，请稍后重试';
}
```

如果你用的是 `fetch`，记得在 `!res.ok` 时主动抛错：

```js
const res = await fetch('/api/chat', { method: 'POST' });
if (!res.ok) {
  throw new Error(`HTTP ${res.status}`);
}
```

### 错误提示应该长什么样

```jsx
{errorMsg && <div className="error-tip">{errorMsg}</div>}
```

再加一个重试按钮：

```jsx
{errorMsg && retryPayload && (
  <button onClick={handleRetry}>重试</button>
)}
```

### 你要看到的结果

- 页面不会只吐出技术报错
- 用户能看懂提示
- 用户知道下一步是检查网络、重新登录，还是直接重试

---

## 10.4 基础鉴权怎么做：推荐方案和不推荐方案

如果 AI 聊天页直接暴露在公网，最怕两件事：**别人拿你的接口乱刷**，以及**API Key 被前端偷走**。所以哪怕是入门项目，也要有基础鉴权。

### 推荐做法：前端只拿登录态，密钥放后端

这是最稳的方式：

- 前端只负责收集用户输入
- 后端代理调用大模型 API
- API Key 放在服务端环境变量里
- 前端拿到的是短期 token、session 或访问码结果

### 一个最简访问码方案

适合个人演示、课程作业、内部工具。

#### 前端登录

```js
async function login(passcode) {
  const res = await fetch('/api/login', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ passcode })
  });

  if (!res.ok) throw new Error('login failed');
  return await res.json();
}
```

后端校验通过后返回短期 token，前端再带到后续请求里：

```js
await fetch('/api/chat', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    Authorization: `Bearer ${token}`
  },
  body: JSON.stringify({ messages })
});
```

### 不推荐做法

- 把真实 API Key 直接写在前端代码里
- 让浏览器直接请求第三方大模型接口
- 用一个全局固定密码长期裸奔在页面里
- 不做任何限流，页面公开后任人刷

### 可以顺手加的限制

- **限制频率**：同一用户 1 分钟最多发 10 次
- **限制长度**：单条消息最多 1000 字
- **限制来源**：只允许自己的域名调用
- **限制会话**：登录态过期后重新验证

### 你要做到的结果

- 普通用户不能无限刷接口
- 页面被分享后，不至于直接裸奔
- API Key 不会出现在浏览器源码里

# 第11章 第11章 常见报错排查：接口失败、跨域、环境变量和流式问题怎么修

做 AI 聊天网页应用，最常见的卡点不是页面，而是“代码看起来没错，为什么就是不出结果”。这时别乱改，先按顺序排查：**先看现象，再看状态码；先查网络，再查代码；先看前端，再看后端。**

本章只抓一条主线：**把报错分层定位**。接口错看状态码，跨域错看代理，变量没读到看环境配置，流式不完整看读取逻辑。这样排查最快。

---

## 11.1 先看接口状态码：401、403、404、429、500 怎么判断？

排查接口问题，第一步永远是打开浏览器开发者工具，看 **Network** 和返回码。不要先改 UI，也不要凭感觉猜。

### 1）401：没带 Key、Key 不对、鉴权失败

401 通常就是**身份校验没通过**。常见表现：

- 返回 `Unauthorized`
- 请求发出去了，但没有结果
- 后端日志提示鉴权失败
- 页面只显示“请求失败”

排查顺序：

1. 看请求头里有没有 `Authorization`
2. 看 `Bearer ` 后面是不是空的
3. 确认 Key 有没有复制错、是否带空格
4. 检查环境变量是否真的读到了

**可复制模板：**

```js
fetch('/api/chat', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    Authorization: `Bearer ${import.meta.env.VITE_API_KEY}`
  },
  body: JSON.stringify({ message: input })
})
```

如果 `import.meta.env.VITE_API_KEY` 是 `undefined`，先查 `.env` 和启动方式，不要先怀疑接口。

---

### 2）403：有身份，但没权限

403 说明不是“完全没身份”，而是**权限不足**。常见原因：

- Key 没权限调用这个模型
- 账号额度不足
- 访问了受限接口
- 请求来源不符合平台要求

处理顺序：

1. 确认模型名是否可用
2. 看账户额度是否够
3. 检查接口地址是否正确
4. 如果走代理，确认后端没有额外限制

---

### 3）404：地址写错了

404 通常不是功能问题，而是**路径错了**。

重点检查：

- 域名是否少写一段
- 接口路径是否多了或少了 `/v1`
- 代理地址是否配置正确
- 开发环境端口是否对应

如果是前端请求自己的后端，先确认：

```js
fetch('/api/chat')
```

这个地址是否真能打到后端。很多时候不是模型有问题，而是请求根本没到接口。

---

### 4）429：请求太频繁

429 表示**触发限流了**。聊天页里用户连续点发送、流式还没结束又发下一条，都很容易触发。

解决办法：

- 请求中禁用发送按钮
- 流式没结束时不允许再次提交
- 必要时加节流

**推荐写法：**

```js
if (loading) return
setLoading(true)
```

这个判断能挡住很多重复请求，也能减少 429。

---

### 5）500：服务端出错

500 一般说明：**请求已经到后端，但后端处理失败。**

常见原因：

- 参数格式不对
- 模型不支持某个字段
- 代理代码崩了
- 服务端内部异常

排查时先用最小请求测试：

- 只传最基础的 `message`
- 暂时去掉复杂参数
- 看后端日志里的具体报错

---

## 11.2 跨域、代理、环境变量读取失败怎么修？

这三类问题很常一起出现：本地能跑，接口却不通；一部署就炸。按顺序查就行。

### 1）跨域：不是接口没回，而是浏览器拦了

如果控制台出现 `CORS policy` 报错，说明问题不是接口不存在，而是**浏览器不允许你直接请求**。

最稳妥的做法是：

- 前端只请求自己的后端
- 由后端去请求大模型接口
- 不要把真实 API Key 暴露在浏览器里

所以更推荐：**前端请求自己的 `/api/chat`，后端去代理第三方接口。**

---

### 2）代理：让前端只打自己的接口

推荐写成：

```js
fetch('/api/chat', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ message })
})
```

由后端代理请求大模型服务。

好处很直接：

- 避免跨域
- 隐藏 API Key
- 统一做错误处理
- 调试日志更清晰

如果你现在还在前端直接请求第三方地址，建议尽快改成代理模式，后面部署也更省事。

---

### 3）环境变量读取失败

环境变量最常见的问题是“看起来写对了，其实没读到”。常见坑：

- 文件名写错
- 前缀写错
- 改了 `.env` 没重启
- 前端和后端变量混用了
- 大小写不一致

**检查清单：**

- Vite 通常用 `VITE_` 前缀
- Next.js 前端公开变量通常用 `NEXT_PUBLIC_`
- `.env` 改完要重启开发服务器
- 变量名要完全一致

**例子：**

```env
VITE_API_BASE_URL=https://your-domain.com
VITE_API_KEY=xxx
```

```js
console.log(import.meta.env.VITE_API_BASE_URL)
```

如果输出 `undefined`，按这个顺序查：

1. `.env` 是否在项目根目录
2. 是否重启了 `npm run dev`
3. 前缀是否正确
4. 变量名有没有拼错

---

## 11.3 流式输出中断、乱码、空响应和解析失败怎么查？

流式输出体验最好，但也最容易出问题。常见情况是：只出一半、中文乱码、页面没字、解析失败。

### 1）中断：只输出一半就停了

一般是这些原因：

- 请求被取消了
- 后端流处理提前结束
- 前端读取流时抛异常
- 网络中断或超时

排查顺序：

1. 看后端日志有没有异常
2. 检查 `reader.read()` 循环是否完整
3. 看代码里有没有中途 `return`
4. 检查超时时间是否太短

很多时候不是模型没返回，而是读取流的过程出错了。

---

### 2）乱码：中文被拆坏了

流式传输时如果按字节乱拼，中文容易乱码。正确做法是用 `TextDecoder`。

**前端读取流的基本写法：**

```js
const reader = response.body.getReader()
const decoder = new TextDecoder('utf-8')
let result = ''

while (true) {
  const { done, value } = await reader.read()
  if (done) break
  result += decoder.decode(value, { stream: true })
}

result += decoder.decode()
```

重点是：**让解码器处理分段字符**，不要手动乱拆。

---

### 3）空响应：接口成功，但页面没字

空响应常见原因：

- 后端返回了，但前端没更新状态
- 读取字段写错了
- 解析格式和返回格式不一致
- 把纯文本当 JSON 解析了

排查方法：

- 先 `console.log` 原始响应
- 确认后端返回的是纯文本、SSE 还是 JSON
- 按对应格式处理，不要混着写

原则很简单：**先确认后端返回什么，再决定前端怎么读。**

---

### 4）解析失败

如果用的是 SSE 或分段 JSON，常见坑有：

- 以为每一段都是完整 JSON
- 没处理换行分隔
- 没过滤空行
- 直接对半截字符串 `JSON.parse`

处理方式：

- 先确认返回格式
- 再写对应解析器
- 不要把“看起来像 JSON”的内容当完整 JSON

不确定格式时，先打印原始文本，再决定怎么解析。

---

## 11.4 推荐的排错顺序：先查哪一步，再查哪一步

很多新手不是不会修，而是**修错了地方**。固定顺序最省时间。

### 推荐排错顺序

1. 先看浏览器控制台
2. 再看 Network 请求状态码
3. 再看请求头和请求体
4. 再看后端日志
5. 最后检查环境变量和代理

前面的信息最直接，后面的信息更接近根因。别一上来就盯着 `.env` 改。

### 常见错误到解决办法对照表

| 错误表现 | 优先检查 | 常见原因 | 处理办法 |
|---|---|---|---|
| 401 | 请求头、Key | 没带 `Authorization`、Key 为空 | 检查环境变量和 Bearer 前缀 |
| 403 | 权限、额度 | 模型没权限、额度不足 | 换可用模型或补额度 |
| 404 | 路径 | 接口地址写错 | 核对 `/api/chat`、`/v1`、域名 |
| 429 | 请求频率 | 连点发送、重复提交 | 加 `loading` 锁，禁用按钮 |
| 500 | 后端日志 | 代理报错、参数错误 | 用最小请求测试 |
| CORS | 代理配置 | 前端直连第三方 | 改成前端请求自家后端 |
| `undefined` | `.env` | 前缀错、没重启 | 重启开发服务并检查命名 |
| 流式中断 | 读取逻辑 | `reader.read()` 处理不完整 | 检查循环和超时 |
| 中文乱码 | 编码 | 没用 `TextDecoder` | 按 UTF-8 分段解码 |
| 页面空白 | 状态更新 | 没把结果写回 state | 打印响应并确认字段 |

### 检查清单

- [ ] API 地址是否正确
- [ ] Key 是否存在，是否真的读到了
- [ ] 请求头是否带了 `Authorization`
- [ ] 是否有跨域报错
- [ ] 后端代理是否启动
- [ ] 模型名是否可用
- [ ] 流式读取逻辑是否正确
- [ ] 中文是否被错误拆包
- [ ] `.env` 是否改完后重启
- [ ] 发送按钮是否重复提交
- [ ] 后端日志是否有 500 细节

你可以直接把这份清单放到项目里，当作自己的排查文档。

## 一、发布前先做一轮 UI 和交互微调

**这一节要回答的问题：怎么让你的页面从“能跑”变成“看起来像个产品”？**

先别急着加新功能。对新手来说，最有效的提升通常不是继续写业务，而是把已有页面整理得更顺手、更稳定。

### 1. 页面布局先稳住

聊天页最推荐的结构，还是“居中卡片 + 自适应宽度”：

- 外层容器限制最大宽度，比如 `max-width: 900px`
- 页面居中显示，左右留白舒服
- 聊天区域固定可视高度，比如 `70vh`
- 消息列表内部滚动，避免整个页面越聊越长
- 输入框和发送按钮固定在底部，保证操作连续

这样做的好处很直接：页面不会散，用户一眼就知道哪里看消息、哪里输入、哪里发送。

### 2. 按钮和状态要有反馈

用户最怕的不是慢，而是“我点了，为什么没反应”。所以按钮一定要做出状态变化：

- **普通态**：颜色清晰、大小合适、看起来能点
- **加载态**：禁用按钮，显示“生成中…”或“思考中…”

还可以加一些轻量反馈：

- 悬停时颜色变深
- 禁用状态降低透明度
- 发送成功后自动清空输入框
- 回车发送和按钮点击不要冲突

### 3. 消息气泡要区分角色

消息列表最好清楚地区分用户和助手，否则整页会很乱。常见做法是：

- 用户消息：靠右、浅蓝背景
- 助手消息：靠左、浅灰背景
- 错误消息：单独用红色提示，避免和正常消息混在一起

如果已经做了 Markdown 渲染，助手消息里的代码块、列表、引用也要注意排版，避免把气泡撑坏。

### 4. 响应式一定要检查

桌面端正常，不代表手机端没问题。至少检查这些点：

- 小屏幕下消息是否自动换行
- 输入区会不会被挤压
- 按钮是否足够大，方便点击
- 页面有没有横向滚动条
- 长消息、长代码块会不会撑破布局

## 二、上线前整理检查清单，别把半成品直接发出去

**这一节要回答的问题：上线前到底要检查什么，避免部署后返工？**

很多人一到部署就急着点按钮，结果上线后才发现：Key 没配、样式丢了、路由 404、历史记录没保存。其实这些问题，大多能在本地提前排掉。

### 1. 先检查核心功能

别先看“好不好看”，先看“能不能用”：

- 能不能正常输入并发送消息
- 能不能拿到模型回复
- 流式输出是否完整显示
- 历史对话是否还在
- Markdown 是否正常渲染
- 错误提示是否能出现

只要有一项不稳定，上线后用户第一时间就会碰到。

### 2. 再检查配置和环境变量

这一部分尤其容易出问题：

- API Key 是否没有写死在前端代码里
- 环境变量名是否一致
- 本地 `.env` 和线上环境变量是否都配置好了
- 是否已经把 `.env` 加进 `.gitignore`

如果你前面是通过后端代理调用模型接口，还要确认代理地址在本地和线上都可用。

### 3. 安全边界要想清楚

上线前最重要的一条就是：**不要把敏感密钥暴露给浏览器**。

推荐方案：

- **推荐**：前端请求你自己的后端接口，Key 放后端环境变量里
- **不推荐**：把真正敏感的 Key 直接写进前端代码再部署

简单判断标准：

- 纯前端静态站，不要放敏感 Key
- 前后端分离时，前端只拿到自己的接口地址，不直接接触模型 Key

### 4. 先本地跑一遍生产构建

本地开发能跑，不代表生产构建能过。部署前至少跑一遍：

```bash
npm run build
npm run preview
```

重点看：

- 构建是否成功
- 有没有明显报错或警告
- 刷新页面会不会 404
- 静态资源路径是否正确
- 路由在生产环境是否正常

### 本章练习：发布前自检

按下面清单逐项勾选：

- [ ] 输入发送正常
- [ ] 流式输出正常
- [ ] Markdown 渲染正常
- [ ] 历史保存正常
- [ ] 错误提示正常
- [ ] `.env` 已配置
- [ ] `.gitignore` 已生效
- [ ] `npm run build` 成功

### 本章结果

你能在上线前提前发现大部分低级错误，减少部署后返工。

## 三、部署到 Vercel 或 Netlify，并配置环境变量

**这一节要回答的问题：怎么把项目真正发布到公网？**

如果你已经把项目做成前端应用，部署并不复杂。对新手来说，最常用、最省事的就是 Vercel 和 Netlify。

### 1. 部署到 Vercel

适合 React / Vite / Next.js 项目，流程很直接：

1. 把代码推到 GitHub
2. 打开 Vercel，导入仓库
3. 选择框架类型
4. 填好构建命令和输出目录  
   - Vite 通常是 `npm run build`
   - 输出目录通常是 `dist`
5. 配置环境变量
6. 点击 Deploy

如果配置正常，Vercel 会自动构建并生成公网地址。

### 2. 部署到 Netlify

Netlify 也很适合静态前端部署，步骤也接近：

1. 连接 GitHub 仓库
2. 设置 build command 和 publish directory
3. 添加环境变量
4. 发布上线

如果你的项目只是前端页面加一个自己的后端接口，这两种平台都很好用。

### 3. 环境变量怎么配

如果项目依赖 `API_KEY` 或其他密钥，一定要在部署平台的环境变量面板里单独配置：

- 变量名：例如 `VITE_API_KEY` 或 `OPENAI_API_KEY`
- 变量值：你的真实密钥
- 作用范围：生产环境和预览环境按需配置

注意，如果你在 Vite 里使用前端环境变量，通常要以 `VITE_` 开头。名字不对，代码里就读不到。

### 4. 推荐的请求链路

```text
前端页面
  -> 请求你自己的后端接口
    -> 后端读取环境变量里的模型 Key
      -> 调用大模型 API
        -> 把结果返回给前端
```

这样虽然多了一层，但更安全，也更适合后面继续扩展。

**练习：** 任选 Vercel 或 Netlify，完成一次真实部署。  
**结果：** 你得到一个可以分享给别人访问的公开链接。

## 四、上线后做一次完整验证：访问、请求、历史保存都要测

**这一节要回答的问题：发布成功后，怎么确认它真的能用？**

上线不是点完 Deploy 就结束了，还要做一次完整回归验证。不要只看“页面打开了”，要把整个使用流程从头走一遍。

### 1. 先看页面能不能打开

打开公网地址，先检查基础展示：

- 首页是否正常加载
- 样式是否丢失
- 图片、图标、字体是否正常
- 手机浏览器是否能访问

如果页面空白，先看控制台和网络请求，通常能很快定位问题。

### 2. 再测聊天请求

输入一段简单内容，比如“你好，简单介绍一下你自己”，然后看：

- 是否能发出请求
- 是否有加载状态
- 是否能收到回复
- 流式输出是否一段段出现
- 消息是否能正确追加到列表里

如果你做的是流式输出，还要确认文字不是一次性全出来，而是按增量显示。

### 3. 再测历史保存

刷新页面后验证：

- 历史消息是否保留
- 是否还按顺序显示
- 是否会重复加载
- 本地存储是否真的读写正常

如果你是把对话保存到 `localStorage`，最常见的问题就是 key 名写错，或者读取时没有做空值判断。

### 4. 再测错误处理

故意制造一个问题，看看页面会不会“体面地失败”：

- 断网
- 输入空内容
- 配错环境变量
- 暂时把接口地址改错

你要观察的是：页面有没有明确提示，而不是直接白屏或者卡住不动。

### 5. 记录上线后的第一个问题

上线后几乎都会遇到小问题，常见的有：

- CORS 跨域
- 环境变量没生效
- API 返回格式和本地不一样
- 某些浏览器对流式响应兼容不好

遇到问题不要慌，先看浏览器控制台和 Network 面板，再看部署平台日志。通常不是大问题，只是某个配置漏了。

### 本章练习：做一次上线回归测试

按照“打开页面 → 发消息 → 看流式输出 → 刷新页面 → 查历史 → 故意报错”的顺序完整走一遍。

你能确认这个 AI 聊天网页不仅“部署成功”，而且“真的能用”。
