# 第1章：React 之后，为什么要学 Next.js

## 开篇引入：React 会了，为什么还要学 Next.js？

很多同学学完 React 后会想：组件、状态、交互都掌握了，接下来是不是继续深挖 React 就行？

我的建议是：先别只盯着“前端页面”，先看你接下来要做的到底是什么。

如果你做的是交互很强的后台系统、管理台、单页工具，React 往往已经够用。  
但如果你要做的是内容站、官网站、博客、产品介绍页、营销落地页、SEO 站点，事情就不一样了——这类项目不只是“把页面做出来”，还要考虑：

- 页面能不能更快打开
- 搜索引擎能不能抓到内容
- 路由怎么组织更省事
- 数据怎么获取，静态内容怎么发，动态内容怎么更新
- 站点怎么部署更顺
- 分享出去时标题、描述、图片是不是对的

这时候，Next.js 的价值就出来了。你可以把 React 理解成“做界面”的能力，而 Next.js 更像是“把站点完整做起来”的框架。它不是替代 React，而是把 React 做站点时常缺的那一截补上。

**实用建议：**  
如果你现在做的是纯内部系统，用户不靠搜索引擎进入，页面逻辑比内容分发更重要，那先把 React 学扎实，不必一上来就把 Next.js 搞重。学习工具要跟场景走，不要为了“看起来高级”提前增加复杂度。

---

## React 和 Next.js 的边界：一个负责页面，一个负责站点

这块最容易说虚，我直接给结论。

React 的强项很明确：组件化、状态管理、交互处理、UI 组合。  
它更像是“把一个页面写出来”的能力。

Next.js 则是在 React 的基础上，继续补齐站点开发里常见的那些事：

- 多页面导航
- 首屏加载优化
- 搜索引擎友好
- 服务端渲染或静态生成
- 接口能力
- 图片优化
- 更顺手的部署方式

所以你可以记成一句话：

**React 解决“页面怎么写”，Next.js 解决“站点怎么跑起来、怎么更适合上线”。**

这也是为什么很多人学完 React 后，真正开始做官网站、内容站、SEO 站点时，会明显感觉“光会 React 不够用了”。

**实用建议：**  
如果你已经在项目里反复碰到“要不要服务端渲染”“路由越写越乱”“SEO 没法做”“图片加载不够优雅”这些问题，那就说明你已经到了该认识 Next.js 的阶段。

---

## 为什么内容站、官网站、SEO 站点更适合 Next.js？

这类项目和普通后台最大的差别，是它们很看重“被看见”。

比如：

- 官网要让搜索引擎收录
- 内容站要让文章页尽快被索引
- 落地页要兼顾打开速度和分享效果
- 产品页要在社交平台预览时有正确标题和描述

这些需求都和页面渲染策略、SEO 基础直接相关。Next.js 更适合这类项目，不是因为它“更潮”，而是因为它默认就把这些事情当成重点来设计。

举个简单例子：  
一个文章页，如果完全依赖浏览器执行 JavaScript 才把内容渲染出来，用户可能还能看见，但搜索引擎、爬虫、分享卡片预览、首屏体验就未必理想。  
而 Next.js 可以根据场景选择服务端渲染、静态生成，或者混合使用，让页面在“可访问、可收录、可传播”这件事上更稳。

所以内容站、官网站、SEO 站点常常会优先考虑 Next.js，因为它更贴近这类站点的实际需求。

**实用建议：**  
如果你的页面核心价值是“内容被访问、被搜索到、被传播”，那 Next.js 往往比纯 React 更合适。反过来，如果页面只是公司内部操作台，SEO 完全不重要，那 Next.js 的一些能力就未必是刚需。

---

## Next.js 核心能解决什么问题？

### 1. 路由：不用自己从头搭页面组织

React 本身不负责应用级路由，你通常还得额外选路由方案。  
Next.js 把路由体系直接整合进来了，页面文件本身就能对应访问路径。这样做的好处是：

- 页面结构更清晰
- 项目更容易维护
- 从“页面”到“路由”的映射更直观
- 新成员接手时，不用先研究一堆路由配置

对做站点来说，这比自己手工拼路由配置更省心。

### 2. 渲染：按内容类型选策略

Next.js 很重要的一点，是它不是只给你一种渲染方式，而是让你能按场景选择。

- 静态内容：适合提前生成，访问快
- 动态内容：适合实时请求，数据更灵活
- 需要 SEO 的页面：更适合让页面在服务端就具备可读内容

这就是页面渲染策略。真正上项目时，关键不是背术语，而是知道“这页应该怎么出”。

比如首页、文章页、产品介绍页，通常更适合让内容尽早可见；而登录后个人中心、实时数据面板，则更适合动态获取。Next.js 的价值就在于：它允许你按页面类型做不同选择，而不是一刀切。

### 3. 接口：前后端边界更灵活

Next.js 提供接口能力，可以在同一个项目里处理一些轻量后端逻辑。比如：

- 提交表单
- 获取简单数据
- 做登录校验
- 处理一些站点内的小接口

这对小型站点尤其方便。你不一定非要单独起一个后端项目，前后端可以先在一个仓库里完成闭环。

### 4. SEO：把基础工作做规范

做 SEO 不是玄学，基础就几件事：

- 页面标题要清楚
- 描述要准确
- 内容要尽量可被爬虫直接读取
- 页面层级要合理
- 站点结构要清晰

Next.js 在这些方面更顺手，因为它更适合“先把可见内容输出，再让交互慢慢增强”的思路。

### 5. 部署友好：更接近上线场景

Next.js 更适合站点型部署。你不需要每次都把所有东西当成纯前端静态包去想，而可以根据页面类型决定怎么部署、怎么更新、怎么加接口。

**实用建议：**  
如果你已经能明确说出“这个页面应该静态，这个页面要动态，这个页面得让搜索引擎尽快看到内容”，那你就已经进入 Next.js 的使用语境了。反过来，如果你还没想清楚这些，只是因为“别人都在用”，那先别急着上。

---

## 什么时候先别学 Next.js？

这个问题我单独拎出来讲，避免你一上来就把项目做重。

### 先别急着上 Next.js 的场景

- 只是做纯交互页面
- 单页小工具，逻辑简单
- 内部后台原型，先验证流程
- 页面不需要 SEO，也不关心分享卡片
- 项目周期短，没必要引入更多约定

这类场景里，React 已经能把事情干漂亮了。你如果为了“顺手学一下 Next.js”，结果把路由、渲染、部署一起抬上来，反而会拖慢开发。

### 适合开始学 Next.js 的信号

- 你开始做网站，而不是只做页面
- 页面需要被搜索、被收录、被分享
- 首页、文章页、产品页这类内容页变多了
- 你开始关心首屏速度和 SEO
- 项目里开始出现接口、权限、布局、数据获取这些站点级问题

**实用建议：**  
判断标准很简单：  
**如果你主要是在“做应用”，React 就够用；如果你主要是在“做站点”，Next.js 更合适。**  
别被技术名词带跑，先问自己三个问题：这东西要不要 SEO？首屏速度重不重要？内容是不是页面的核心价值？如果答案大多是“要”，那 Next.js 值得上；如果答案大多是“不要”，那先别把系统做重。

---

## 学 Next.js 的收益和代价：别只看收益，也要看复杂度

学 Next.js 的收益很实在：你会从“会写组件”进阶到“会做站点”。这意味着你开始理解：

- 页面如何组织
- 内容如何渲染
- SEO 如何落地
- 动态与静态内容如何分工
- 接口如何与页面协作
- 项目如何更接近真实上线

但代价也要看清楚：  
Next.js 不是零成本，它会引入更多概念，比如渲染方式、数据获取、路由约定、服务端能力、部署思路。对新手来说，信息量会明显比纯 React 大。

所以我的建议是：

- 需要站点能力时，再学 Next.js
- 只是做普通前端交互页面时，先别提前加复杂度
- 先把 React 的组件、状态、通信、页面组织练熟，再来接 Next.js，会顺很多

---

## 结尾小结：先判断需求，再决定学什么

这一章最想帮你建立的，不是“Next.js 很强”这种空话，而是一个判断框架：

1. React 擅长做页面交互和组件组合  
2. Next.js 擅长把“做站点”补完整  
3. 内容站、官网站、SEO 站点更适合 Next.js  
4. 路由、渲染、接口、SEO、部署，是 Next.js 的核心价值  
5. 不是所有项目都该上 Next.js，先判断需不需要复杂度

如果你下一步要做的是一个真正面向用户、面向搜索、面向上线的站点，那么 Next.js 值得学，而且应该尽早学。  
如果你现在还在练 React、做小页面、做内部工具，那也不用焦虑，先把 React 的基础打牢，再来接 Next.js，会更稳。

# 第2章：Next.js 的应用场景与整体开发思路

## 开篇引入：为什么 React 之后还要学 Next.js？

很多同学学完 React 之后都会问：页面我已经会写了，为什么还要学 Next.js？

因为 React 更像“把界面搭出来”，你会写组件、会处理状态、会做交互；而 Next.js 更像“把页面变成一个真正可上线、可访问、可收录的网站”。简单说，React 解决页面表达，Next.js 解决站点交付。

如果你做的是内部管理系统，页面少、用户固定、SEO 不重要，那 React 配合常规前端方案通常就够了。但如果你要做内容站、官网站、营销页、文档站，或者希望页面更快、更容易被搜索引擎理解，Next.js 的价值就很明显。

可以先记住一句话：**React 让你会做页面，Next.js 让你会做网站。**

**实用建议：**  
如果项目只是内部系统，页面不多，用户也不靠搜索引擎进来，先把 React、接口请求、状态管理这些基础打扎实，不必急着上 Next.js。框架不是越高级越好，适合业务才最值钱。

---

## 一、Next.js 适合哪些业务场景？

### 1. 内容站：文章多、更新频繁、需要收录

内容站最典型的需求就是“多页面、强内容、重搜索”，比如博客、资讯站、教程站。这类站点通常页面数量多，而且希望搜索引擎能稳定抓到内容。

Next.js 很适合这种场景，因为它能结合静态生成、服务端渲染等方式，让内容既快又利于 SEO。比如文章详情页内容相对稳定，适合提前生成；文章列表页如果经常更新，也可以按合适节奏刷新。

**适合的特征：**
- 页面以文字内容为主
- 需要搜索引擎收录
- 页面层级清晰
- 内容更新有规律

### 2. 官网站和营销页：强调首屏、转化和分享

官网站、活动页、产品落地页，最在意的是首屏速度、内容展示和转化路径。用户常常从搜索、社交平台或广告直接进来，这时候页面打开快不快、标题和摘要对不对，都会影响效果。

Next.js 的优势很直接：可以把首屏内容提前准备好，配合 SEO 配置和图片优化，让页面既更快，也更适合转化。比如产品官网首页的卖点、按钮入口、核心介绍，最好一进来就能看到，而不是等客户端慢慢请求完再显示。

### 3. 文档站：结构稳定、访问频繁、目录清晰

文档站通常目录明确，内容更新可控，比如产品文档、API 文档、开发指南等，都很适合用 Next.js 构建。原因很简单：页面结构规律，适合布局复用，也适合按内容颗粒度做静态化。

文档站还特别看重“找得到”和“翻得快”。用户不只是要页面打开快，还要能快速找到目录、章节和相关链接。Next.js 做这类结构化内容会很顺手。

### 4. SEO 站点：不是“能打开”就够了

如果业务依赖自然搜索流量，比如关键词流量站、品牌词落地页、知识型站点，就不能只考虑“页面能渲染”，还要考虑：
- 页面标题和描述
- URL 结构是否清晰
- 内容是否容易被抓取
- 图片和资源是否影响加载

这类站点里，Next.js 的渲染策略和元信息配置就很重要。你不是只在做页面，而是在做一个能被搜索引擎正确理解的站点。

**实用建议：**  
如果项目内容少、只给内部员工用、SEO 完全不重要，别一上来就强行 Next.js。很多项目后期复杂，不是需求真的复杂，而是起步时架构想太多。

---

## 二、前端页面开发和站点开发，有什么区别？

很多人从 React 过来，习惯先把页面做出来。这没错，但站点开发比页面开发多了几层事情。

### 1. 不只是写 UI，还要考虑索引

页面开发关注视觉和交互；站点开发还要考虑搜索引擎能不能读懂你的内容。  
同样是一篇文章：

- 纯前端渲染：用户进来后才请求数据，内容晚一点才出来
- Next.js：可以提前把内容准备好，搜索引擎和用户都更容易拿到完整页面

这也是很多内容类站点不太愿意只用纯 SPA 的原因。不是 SPA 不行，而是在“首屏可见内容”和“被搜索引擎理解”这两件事上，站点框架更顺手。

### 2. 不只是能访问，还要考虑部署和效率

站点上线后，用户访问路径、缓存策略、静态资源加载、首屏速度，都会影响体验。Next.js 的核心价值之一，就是把页面、数据和部署策略串起来。

你可以把它理解成：React 负责组件表达，Next.js 负责页面交付。交付这件事，真正难的地方就在于“怎么更快、怎么更稳、怎么更容易被发现”。

### 3. 不只是单页，而是整站结构

页面开发常常是一个组件页一个组件页地做；站点开发则更关注：
- 首页、列表页、详情页怎么组织
- 公共头部、导航、底部如何复用
- 数据从哪里来
- 页面是否需要登录
- 哪些内容要静态化，哪些内容要动态获取

所以 Next.js 不只是一个前端框架，更像一个站点开发框架。它希望你从“组件思维”过渡到“页面结构思维”，再过渡到“内容交付思维”。

**实用建议：**  
如果你已经开始频繁思考“这个页面是不是应该预先生成”“这个数据要不要给搜索引擎看到”，那你其实已经进入站点开发阶段了。这个时候再看 Next.js，会比纯学 API 顺很多。

---

## 三、Next.js 项目的典型组成是什么？

### 1. 页面：站点的入口

页面就是用户能访问的具体内容，比如首页、列表页、详情页、关于页。  
在 Next.js 里，页面和路由关系很紧，通常你创建页面，也就顺手定义了访问路径。

这对 React 开发者很友好，因为你不需要先搭一堆路由配置再映射页面，很多时候就是“文件在哪，页面在哪”。项目结构更直观，也更贴近真实站点的组织方式。

### 2. 布局：让站点保持统一

布局负责把多个页面共用的结构抽出来，比如：
- 顶部导航
- 侧边栏
- 页脚
- 公共容器样式

布局做好了，站点会统一很多，维护也轻松。比如内容站里的首页、文章页、分类页通常都需要同样的头部和底部，放进布局里统一管理，改一次就能全站生效。

### 3. 数据：内容从哪来

Next.js 项目不只是静态页面，很多页面都要从数据库、接口、CMS 或文件中拿数据。数据处理方式决定了页面是静态的、动态的，还是二者混合。

如果你只是把页面当“展示壳子”，就会忽略站点真正的核心——内容本身。站点开发最关键的不是组件多漂亮，而是数据怎么流进来，页面怎么把它展示出去。

### 4. 接口：站点自己的能力

很多站点不只是“展示内容”，还要有自己的接口能力，比如：
- 提交表单
- 登录验证
- 获取列表
- 管理后台的数据操作

Next.js 可以把前后端边界压得更近一些，让你在一个项目里完成常见站点能力。对小中型项目来说，这种方式很实用：前端开发者不必一开始就切到另一套后端工程里，效率会更高。

### 5. 静态资源：图片、图标、字体、封面图

站点开发里，静态资源不是配角。图片加载速度、尺寸控制、格式优化，都会影响体验和 SEO。尤其是内容站和官网站，封面图、配图、Logo、分享图都很关键。

**实用建议：**  
先把“页面、布局、数据、资源”这四件事想清楚，再决定要不要上更复杂的架构。很多项目不是技术不够，而是结构没理顺。结构一乱，后面写再多代码都难维护。

---

## 四、静态内容、动态内容、混合方案怎么选？

这是 Next.js 里最值得先想清楚的一点。不要先问“哪种渲染最好”，先问“这个页面到底是什么类型”。

### 简单判断表

| 页面类型 | 更适合的方案 | 典型例子 |
|---|---|---|
| 内容稳定、变化少 | 静态生成优先 | 关于我们、帮助文档、产品介绍 |
| 实时变化、用户相关 | 动态渲染优先 | 用户中心、订单页、消息列表 |
| 一部分稳定、一部分变化 | 混合方案 | 首页、文章列表、详情页 |

### 1. 静态内容：适合稳定页面

如果页面内容变化少，比如公司简介、帮助文档、固定活动页，就适合偏静态处理。好处很明显：访问快、部署简单、稳定性高。

比如“关于我们”这种页面，今天和明天内容基本一样，就没必要每次请求都重新生成。提前准备好，用户访问时直接拿结果，简单又高效。

### 2. 动态内容：适合实时变化和个性化

比如用户中心、消息列表、订单页、登录后首页，这些页面通常要根据用户状态、权限、实时数据来展示。这类内容不适合完全静态化，因为每个用户看到的东西可能都不一样。

动态内容的重点不是“能不能做”，而是“有没有必要实时算”。如果每次都重新生成，反而会增加成本，甚至拖慢体验。

### 3. 混合方案：真实项目里的常态

真实项目里，大多数页面都是混合的：
- 首页偏静态
- 列表页按周期更新
- 详情页内容较稳定
- 用户中心动态加载

这也是 Next.js 常被喜欢的原因：它不是逼你站队，而是让你按页面类型选择合适的渲染方式。你可以对不同页面用不同策略，不用所有页面一刀切。

**实用建议：**  
判断一个页面用什么方案，主要看四件事：  
1. 内容是否经常变  
2. 是否依赖登录态  
3. 是否需要搜索引擎收录  
4. 是否希望首屏更快  
这四个问题，基本就能帮你定方向。

---

## 五、别为了“全栈”而全栈

Next.js 确实让前端开发者更容易接触接口、服务端逻辑和部署流程，但不代表每个项目都要把所有能力用满。

### 常见误区

1. **一上来就强行做复杂架构**  
   本来是一个简单官网，非要拆成一堆服务，结果开发成本飙升。

2. **把 Next.js 当成必须全能**  
   不是所有项目都需要 SSR、API Routes、登录系统、复杂权限。

3. **只看技术新鲜，不看业务价值**  
   如果页面不需要收录，也不需要复杂交互，纯 React SPA 可能更简单直接。

### 一个更落地的例子

比如你做一个公司官网，需求其实很朴素：  
- 首页展示公司介绍  
- 产品页展示功能和价格  
- 联系页提交表单  
- 文章页用于发布更新  

这种项目用 Next.js 很合适，因为页面结构清楚，内容也有收录需求。  
但如果你做的是一个内部报表系统，页面主要给员工登录后查看数据，而且所有数据都来自后台接口，那你先用 React + 现成前端方案，往往更轻。这个项目为了“全栈”去上 Next.js，收益未必大，反而会增加理解成本。

### 什么时候适合用 Next.js？

- 做内容站、官网站、文档站
- 需要 SEO 和首屏表现
- 页面数量多，结构清晰
- 希望前后端能力在一个项目里协同

### 什么时候先别上复杂度？

- 只是内部系统
- 页面少、生命周期短
- SEO 完全不重要
- 团队对服务端逻辑还不熟

**经验建议：**  
技术选型的原则不是“能不能做”，而是“值不值得做”。Next.js 很强，但强不等于每次都要上。先看业务，再看框架。

---

## 结尾小结：先看业务，再看框架

这一章最想让你记住的一句话是：**React 解决页面表达，Next.js 解决站点交付。**

当你的项目开始考虑收录、首屏、部署、接口、内容组织时，Next.js 的价值就出来了。它适合内容站、官网站、营销页、文档站和 SEO 站点，也适合需要页面、布局、数据、接口协同的实际业务。

**适用场景：**  
内容站、官网站、营销页、文档站、SEO 站点，以及需要静态与动态混合处理的真实业务。

**不适合场景：**  
纯内部系统、页面少且生命周期短的项目、完全不需要搜索引擎收录的应用。如果你的需求很简单，先把 React 和常规前端方案用熟，别急着加复杂度。

**下一步怎么学：**  
接下来学 Next.js，不要急着背概念，先带着这几个问题去看每一个页面：  
- 这个页面是静态还是动态？  
- 它要不要被搜索引擎收录？  
- 它和哪些页面共享布局？  
- 它的数据从哪里来？  
- 我现在真的需要这么复杂吗？

把这些问题想明白，你学 Next.js 就不会飘，后面的创建项目、路由、数据获取、SSR/SSG、SEO 配置，也都会顺很多。

# 第3章：创建 Next.js 项目与开发环境搭建

## 开篇引入：为什么先把项目跑起来，再谈高级玩法

学 Next.js，很多人一上来就盯着 SSR、SSG、SEO、路由这些“看起来很高级”的词。老赵提醒你一句：**先把项目搭起来，知道目录长什么样、命令怎么跑、页面怎么改，后面这些东西才有落脚点**。

Next.js 不是单纯的 React 补丁，它更像是给 React 补齐了一整套站点开发能力：路由、渲染、构建、接口、图片优化、SEO 配置，甚至简单全栈能力都能一起做。你学它，不是为了炫技，而是为了更快做出能上线的内容站、官网站、活动页和 SEO 站点。

但也别上头：**不是所有项目都必须上 Next.js**。如果你只是做一个纯交互小工具、内部系统，SEO 和服务端能力都用不上，先用 React + Vite 往往更轻松。可一旦项目开始关心首屏、搜索收录、页面分享、内容组织和服务端能力，Next.js 的价值就会很明显。

这一章的任务很明确：**把 Next.js 项目真正跑起来，并建立正确的目录认知和开发习惯**。这一步没打牢，后面在组件放哪、页面怎么拆、配置怎么改这些问题上都会反复踩坑。

---

## 一、使用 create-next-app 创建项目：先把起点选对

### 1.1 为什么推荐从 create-next-app 开始

对新手来说，最稳妥的方式就是用官方脚手架创建项目。它会把基础骨架、构建配置、开发服务器、类型检查和常用约定一次配好。你不用先纠结 Webpack、Vite、Babel 这些底层工具链，先把“能开发”建立起来，再慢慢理解“为什么这样设计”。

对 React 开发者来说，这一步的意义尤其大：

- 不再只是写组件，而是进入“页面 + 路由 + 数据 + 站点能力”的开发模式
- 开始接触服务端渲染、静态生成和接口能力
- 会发现项目结构和纯前端 SPA 不一样，思路也要跟着调整

简单说，React 让你学会“怎么把界面写出来”，Next.js 则让你继续学会“怎么把站点做出来”。这不是重复，而是能力升级。

### 1.2 创建项目时常见配置项怎么选

创建时常见选择包括 TypeScript、ESLint、App Router、样式方案。老赵建议这样判断：

- **TypeScript**：默认推荐。只要准备认真做项目，就直接选。页面参数、接口返回值、组件 props 会越来越多，类型系统能帮你少踩坑。
- **ESLint**：默认推荐。它能尽早发现不规范写法，适合项目迭代和多人协作。
- **App Router**：新项目优先用。后面页面、布局、路由和数据获取的学习都会围绕它展开。
- **样式方案**：先选一个简单稳定的，不要一开始就堆复杂工具。纯 CSS、CSS Modules、Tailwind 都可以，前提是你会用、团队能接受。

经验判断很简单：**如果你只是先做原型，可以从简；如果项目准备继续迭代，TypeScript 和 ESLint 尽量别省。**

### 1.3 创建后第一件事不是写业务，而是看结构

很多人项目一打开就开始写首页，写着写着就不知道组件该放哪、公共逻辑怎么收。正确做法是：**先看目录，再动手**。因为 Next.js 的目录结构本身就是使用说明书的一部分。

你至少要先知道三件事：

1. 哪个目录对应页面入口  
2. 哪个目录负责布局包裹  
3. 静态资源和配置文件分别放在哪里  

页面是页面，布局是布局，工具函数是工具函数，别混成一锅粥。

**实用建议**：  
如果你只是练手，优先用脚手架默认配置，不要一开始加一堆自定义别名、复杂主题系统、状态管理和请求封装。先把“项目能跑、页面能改、路由能通”这三件事做好。

---

## 二、项目目录结构怎么看：先认识哪些文件，哪些可以先放一放

### 2.1 先认识的部分：页面、布局、静态资源

Next.js 项目里，最先要搞明白的是这些东西：

- **页面入口**：决定一个 URL 对应什么页面
- **布局文件**：决定一组页面共享什么外壳
- **公共资源目录**：图片、图标、静态文件放在哪里
- **配置文件**：构建、路径别名、环境变量相关配置

最容易忽略的是“布局”。很多 React 开发者习惯把导航栏、页脚、头部信息写在每个页面里，页面一多，重复代码就会越来越明显。Next.js 的目录设计就是在告诉你：**公共外壳应该单独抽出来，页面只负责内容变化部分**。

比如官网里的首页、关于我们、联系我们、帮助中心，通常都共用一套顶部导航和底部信息，这些内容就该交给布局来处理，而不是每个页面复制一遍。

### 2.2 先不用深挖的部分：别把时间耗在底层实现

新手常见问题是，刚进项目就开始研究所有配置文件的每个字段，或者到处改底层构建参数。这个阶段没必要。因为：

1. 你还没有业务场景，改配置没有目标  
2. 配置越多，出错点越多，反而影响建立正反馈  

老赵建议你分层看目录：

- 第一层：页面、布局、静态资源
- 第二层：组件、工具函数、样式
- 第三层：接口、环境变量、路由参数
- 第四层：构建和部署相关配置

先从第一层开始，后面的内容会顺很多。Next.js 的学习不是“先吃最难的”，而是“先知道项目如何组织，再逐步加能力”。

### 2.3 一个好习惯：按功能划分，而不是按零碎文件堆放

建议从一开始就形成这样的目录思路：

- 页面放页面目录里
- 通用组件放 `components`
- 业务组件按模块分组
- 工具函数放 `utils` 或 `lib`
- 样式尽量跟组件或页面保持关联

**常见误区**：为了“整洁”，把所有文件分得过细，最后自己都找不到。真正的整洁不是目录层级多，而是**每个文件放得合理、边界清楚、查找成本低**。

如果现在还拿不准，可以先按“页面级”“组件级”“工具级”三类去收纳，等项目复杂起来再慢慢细分。别一开始就过度设计，文件太散只会让你后面维护更累。

**实用建议**：  
如果某个目录里连续放了 5 个以上“看不懂用途的小文件”，先停一下，说明你可能拆得太细了。先合并，再慢慢拆。

---

## 三、开发环境与启动命令：怎么进入稳定的开发节奏

### 3.1 本地开发最重要的是三个状态

项目跑起来后，你要关注三个状态：

- 开发服务器能否稳定启动
- 修改文件后是否热更新正常
- 报错时能否快速定位问题

Next.js 的开发体验通常比较顺手，改页面文件后能及时看到变化，这对内容页、官网页尤其重要。你会很快形成一种节奏：改代码、看效果、再调整。

但别把“开发顺畅”理解成“上线也一定顺畅”。开发模式和生产模式不是一回事。很多问题在开发环境看不出来，到构建或部署时才暴露。所以后面要养成习惯：不只在本地能打开就结束，还要看一次打包是否正常。

### 3.2 常见启动命令要知道什么

你不需要死记命令，但要知道各自用途：

- 开发模式：用于日常编码和调试
- 构建模式：用于检查项目能否正常打包
- 生产启动：用于模拟上线后的运行状态

很多新手只会跑开发模式，结果上线前才发现构建失败。老赵的建议是：**写到一定阶段，至少跑一次构建**。这不是走形式，而是提前发现隐藏问题，比如类型错误、导入错误、环境变量缺失、动态路由处理不当等。

### 3.3 调试时先看什么，不要一上来就乱查

基础调试按这个顺序来：

1. 看终端报错  
2. 看浏览器控制台  
3. 看页面是路由问题还是渲染问题  
4. 看数据是否为空、参数是否传错  
5. 再查组件内部逻辑  

很多问题不是“组件写错了”，而是你对页面、布局、路由参数、服务端数据的理解还不够统一。比如页面没内容，先别急着怀疑样式，先判断是不是路径不对、参数没传、数据没拿到。很多时候问题根本不在 UI，而在“数据从哪里来、页面什么时候渲染”这两个地方。

**实用建议**：  
遇到问题先判断它属于哪一层：路由层、渲染层、数据层还是样式层。层次判断对了，排错速度会快很多。

---

## 四、TypeScript、ESLint、样式方案：默认推荐，但别过早折腾

### 4.1 TypeScript：建议直接上，但别把它当负担

如果你已经会 React，Next.js 项目里上 TypeScript 通常是划算的。它能帮你明确：

- 页面参数长什么样
- 接口返回值是什么结构
- 组件 props 是否传对
- 数据为空时怎么处理

但 TypeScript 不是让你把代码写得“很学术”，而是帮助你少犯低级错误。新手常见的问题是过度追求类型完美，结果一页代码还没写完，类型先绕晕了。

正确姿势是：先把业务写通，再逐步补类型。页面能跑、数据能展示、交互能完成，然后再回头把关键接口和关键 props 的类型补齐，这样效率更高，也更符合实战节奏。

**建议原则**：  
先保证核心功能能跑，再逐步补类型。不要为了类型而拖慢业务进度。

### 4.2 ESLint：它是开发习惯，不是束缚

ESLint 的作用不是“限制你写代码”，而是让团队和项目保持基本一致性。比如命名风格、未使用变量、潜在错误、导入顺序等，这些东西手工检查太浪费时间。

新手常见误区是：一遇到 lint 报错就全部关闭。这不是解决问题，是把问题推迟。正确做法是理解规则的目的，必要时局部调整，而不是一刀切。

如果你做的是内容站、官网站这类项目，代码量不会像大型后台那样爆炸，但规范性依然重要。因为这类项目经常会迭代文案、页面、栏目和活动页，规范越稳，后续改起来越安全。

### 4.3 样式方案：先求稳，再求花

样式怎么选，没有绝对答案，但有一个实战原则：**先选你能持续维护的方案**。

常见思路：

- 纯 CSS / CSS Modules：适合基础清晰、局部样式明确的项目
- Tailwind：适合快速搭页面、减少来回切文件
- 组件库：适合后台、管理界面或快速出效果

如果你是做内容站、官网站、SEO 站点，页面结构通常比较明确，样式不必一开始就搞得很复杂。**别为了“工程化”而工程化**，小项目最怕复杂度先行。

一个实际经验是：如果目标是先验证内容和页面效果，那么样式只要足够清晰、足够一致就够了。先把页面做出来，比追求一套“看上去很强”的样式体系更重要。

**实用建议**：  
样式方案选完后，保持至少一段时间不乱换。频繁切换方案，只会让你在学习 Next.js 的过程中不断被样式工具分心。

---

## 五、新手先做什么，先别做什么：把配置焦虑压下去

### 5.1 先做什么

刚开始接触 Next.js，不要想着一下子把所有东西都补齐。你先做这几件事就够了：

- 用 `create-next-app` 创建项目
- 跑起来开发服务器
- 打开一个页面，确认热更新正常
- 认识页面目录和布局目录
- 用一个简单组件拆分页面内容
- 跑一次构建，看看有没有基础错误

这几步做完，你就已经从“看教程的人”变成“真正能启动项目的人”了。很多人卡住不是因为技术难，而是因为起点没跑顺。

### 5.2 先别做什么

以下这些事情，建议先压一压：

- 不要急着改一堆底层构建配置
- 不要一上来引入复杂的全局状态管理
- 不要先做一套过度完整的请求封装
- 不要把权限、主题、国际化、低代码化全都提前加进来
- 不要为了“像大项目”而强行堆复杂目录

这些功能不是不能做，而是**要在确实需要时再做**。如果项目还没跑通，先把复杂度压住，别让自己在配置和抽象里打转。

### 5.3 何时适合用 Next.js，何时先别上复杂度

这点老赵再给你掰开说一下：

- **适合用 Next.js**：官网、内容站、产品介绍页、SEO 站点、需要首屏和收录的项目、需要服务端接口配合的站点
- **先别急着上 Next.js**：纯客户端交互工具、内部系统、小型活动页、需求还在频繁变化的原型项目

判断标准不是“框架强不强”，而是“它是否解决你现在的问题”。  
如果你现在最重要的是快速做页面验证，React + Vite 可能更省心；如果你要开始做站点分发、搜索收录、页面渲染和接口联动，Next.js 的价值就很大了。

**实用建议**：  
技术选型别跟风。你要看项目目标，不是看别人用了什么。

# 第4章：页面、布局与组件组织方式

## 开篇引入：先把站点骨架搭起来，再谈功能

很多同学学 React 时，习惯是“先写页面，再往里塞组件”。做小 Demo、活动页、临时展示页，这么干很快，也没问题。

但到了 Next.js，这个习惯要升级。因为 Next.js 不只是“能写页面”，它更像一套站点工程方案：**页面怎么分、布局怎么复用、导航和头尾放哪、列表页和详情页怎么组织**，这些都会直接影响后面的路由、数据获取、SEO 和权限能力。

老赵先给你一个最直接的判断：

- 只做一个很小的交互页、纯展示 Demo，React + Vite 往往就够了。
- 做官网、内容站、文档站、营销页、带列表和详情的业务站，Next.js 的页面和布局机制会省很多事。
- 如果一开始把所有东西都塞进一个页面，后面大概率会遇到路由乱、头尾重复、列表详情混在一起、维护困难的问题。

所以这章先不讲接口，不讲 SEO，先把**页面、布局与组件组织方式**讲清楚。骨架搭对了，后面的内容才好展开。

---

## 一、页面文件、布局文件、公共头尾如何组织

### 1. 页面文件：对应“用户能访问的一个地址”

在 Next.js 里，页面文件本质上对应站点上的一个可访问路径：

- `/` 首页
- `/posts` 文章列表页
- `/posts/123` 文章详情页
- `/about` 关于页

也就是说，**页面文件负责“这个地址展示什么”**，它更像页面入口，而不是一个可复用 UI 零件。

这个理解很重要。很多 React 开发者刚上 Next.js 时，会下意识把页面当成“大组件”来写，结果把数据请求、展示逻辑、公共结构全塞在一起。页面当然能这么写，但站点一大，就很容易乱。

### 2. 布局文件：负责“这一组页面共享什么壳子”

布局的作用很简单：**把多个页面共同的部分抽出来**。比如：

- 顶部导航
- 底部版权
- 侧边栏
- 内容区外壳
- 登录态提示栏
- 统一标题、Meta、容器宽度

很多初学者每个页面都复制一份 Header/Footer，短期看没问题，后面改一次导航，十几个页面全得改，漏一个就是 bug。

布局的价值就是：**把稳定不变的壳收起来，把经常变化的内容放出来。**

实际开发里，可以把布局理解成“站点的壳”，页面内容是“壳里面换的内容”。这样导航、页脚、整体宽度、背景色、统一风格，都能集中管理。

### 3. 公共头尾：不要散落在每个页面里

公共结构的组织原则，老赵建议记一句：

> **公共结构进布局，页面差异进页面，复用片段进组件。**

常见组织方式是：

- `layout`：全站通用壳，比如 Header、Footer、主内容区域
- `page`：具体页面内容
- `components`：按钮、卡片、搜索框、文章摘要、分页器这类复用块

好处很直接：

1. 页面更清楚  
2. 修改头尾更方便  
3. 结构更像一个站点，而不是一堆孤立页面  

尤其是后面做不同区域站点时，这种结构会继续发挥作用。比如博客区和后台区通常不是同一套壳，布局分开后维护会轻松很多。

### 4. 一个简单的判断标准

碰到一个 UI 片段时，问自己三个问题：

- 它是不是所有页面都要用？
- 它是不是只属于某一类页面？
- 它是不是一个可独立复用的小块？

通常结论是：

- **所有页面都用**：放布局
- **某一类页面共享**：放分组布局
- **多个地方都会用**：放组件

这个判断不复杂，但很管用。按这个思路整理项目，结构一般不会失控。

### 实用建议

- 别把 Header/Footer 直接复制到每个页面里。
- 先把站点壳子想清楚，再写具体内容。
- 小项目布局可以先简单，别一开始就拆太碎。
- 先保证结构清楚，再考虑进一步抽象。

---

## 二、嵌套路由场景下的布局复用思路

### 1. 什么叫嵌套路由下的布局复用

很多站点不是“首页 + 一堆单页”这么简单，更常见的是：

- `/docs/*` 下是一套文档布局
- `/dashboard/*` 下是一套后台布局
- `/blog/*` 下是一套内容布局

这时就不能只靠一个全站布局，而要有**分层布局**的思路。

比如：

- 全站都有顶栏和底栏
- 博客区有文章目录
- 后台区有侧边栏菜单
- 文档区有左侧导航和右侧正文

这就是典型的嵌套路由布局复用：**不同路径共享不同层级的壳子**。

### 2. 复用的核心不是“套娃”，而是“分层”

别把布局写成一层套一层，最后容易绕。更好的方式是按“层级职责”来分：

- 第一层：全站通用壳
- 第二层：某个业务域的壳
- 第三层：单页内容

例如一个内容站可以理解成：

- 全站：顶部导航、底部版权
- 文章区：分类栏、推荐位、搜索框
- 单篇文章页：文章正文、作者信息、相关推荐

布局不是为了炫技，而是为了让不同页面共享不同的骨架。更实在地说，它的职责就是把**重复且稳定的结构固定下来**，让页面只关心自己的内容。

### 3. 什么时候该做嵌套布局

不是所有项目都值得上复杂的嵌套布局。可以这样判断：

适合做嵌套布局：

- 页面数量多
- 页面类型明显分组
- 同一类页面需要共享左侧菜单、导航或筛选器
- 后面还会持续扩展

不太适合：

- 只有两三个静态页
- 页面结构高度相似但改动很少
- 还不确定站点会不会继续长大

布局层级不是越多越好，而是要和业务规模匹配。小站点保持轻量，大站点再逐步分层，这才稳。

### 4. 实战里怎么想

比如做技术文档站，常见布局可能是：

- 顶部导航：切换站点入口
- 左侧目录：定位当前章节
- 中间正文：阅读内容
- 右侧辅助信息：版本说明、相关链接

这时文档页就不该和普通介绍页用同一套布局。因为阅读场景不同，用户关注点也不同。布局不是为了好看，而是为了让用户更容易完成任务。

### 实用建议

- 先按业务域分组，再考虑层级布局。
- 别为了“看起来专业”强行上三四层布局。
- 目标是减少重复，不是制造抽象。
- 如果某个布局只服务两三个页面，先别拆太复杂。

---

## 三、页面与组件的职责边界：什么放页面，什么放组件

### 1. 页面负责“编排”，组件负责“表达”

很多项目乱，不是代码少，而是**职责边界乱了**。

可以这么理解：

- **页面**：负责组织这一屏有哪些模块，模块顺序是什么，数据从哪来，和路由参数怎么对应。
- **组件**：负责一个明确的小功能或 UI 片段，比如文章卡片、分页按钮、搜索输入框。

页面像导演，组件像演员。导演不该亲自演每个角色，演员也不该决定整场戏怎么排。

### 2. 什么应该放页面里

页面里适合放这些内容：

- 路由参数相关逻辑
- 页面级数据获取
- 页面级状态，如筛选条件、分页页码
- 页面整体结构编排
- 和该地址强相关的文案、标题、SEO 信息

简单说，**只属于当前 URL 的东西**，优先放页面。

比如文章详情页里，当前是哪篇文章、是否展示相关推荐、标题怎么拼、面包屑怎么走，这些都更适合放在页面层处理。它们跟路由关系强，放进组件里反而会让组件变得很“聪明”，不好维护。

### 3. 什么应该放组件里

组件里适合放这些内容：

- 按钮、输入框、弹窗、标签
- 卡片、列表项、头像、评分
- 公共导航、页脚、搜索栏
- 纯展示型的可复用模块

组件的原则是：**输入明确、输出稳定、尽量少知道外部上下文**。

换句话说，组件最好是“拿数据来就能渲染，别到处猜上下文”。这样它才能在不同页面里自由复用。

### 4. 常见误区：把页面写成一坨，或者拆得太碎

#### 误区一：页面写成一坨

典型表现：

- 页面里有几十行甚至几百行 JSX
- 数据请求、筛选逻辑、渲染逻辑混在一起
- 想改一个小模块，就得在大文件里翻半天

这种写法短期快，长期很痛苦。你一开始可能觉得“先跑起来再说”，但站点一长，排查和修改都会变慢。

#### 误区二：过度抽象

另一种极端是：

- 一个小卡片拆成五六个文件
- 组件名很抽象，看不出用途
- 为了“复用”硬拆，结果阅读成本暴涨

这也不对。不是拆得越细越好，而是**拆到职责清楚就够了**。如果一个组件只会在一个地方出现，而且逻辑简单，完全可以先放在页面里，没必要强行抽出来。

### 5. 一个更具体的拆分原则

老赵给你一个更落地的判断法：

1. **先按页面功能切块**：先看页面上有哪些明显区域，比如头部、筛选区、列表区、分页区。  
2. **再看是否存在重复**：如果这个块在别的页面也会出现，优先抽成组件。  
3. **最后看职责是否单一**：一个组件最好只做一件事，别又管展示、又管交互、又管数据。  

也就是说，拆分顺序不是先想“我要造多少组件”，而是先把页面结构理顺。**先可读，再复用。**

### 6. 什么时候先别拆太细

如果你遇到下面这些情况，说明可以先简单点：

- 这是一个只有一两个页面的小站点
- 模块还没重复出现
- 功能还在试阶段，经常改
- 团队人少，先要快速验证需求

这时候最重要的是把页面跑通，把信息呈现清楚。等模块开始重复、需求稳定下来，再抽组件更合适。

### 实用建议

- 页面别复杂到自己一眼看不懂。
- 组件命名尽量具体，别搞“Container”“Wrapper”“Panel”这种看不出干嘛的名字。
- 不确定要不要拆时，先放在页面里，等第二次出现再抽。
- 组件越通用，越要谨慎设计输入输出，别让它变成“万能组件”。

## 四、站点级结构设计：导航、首页、列表页、详情页、专题页

### 1. 先从“站点信息架构”想，而不是从页面碎片想

做站点不是做单页，最怕一上来就写一个个孤立页面。应该先站在“访客会怎么走”的角度，想站点结构。

常见内容站或官网站，通常会有这些核心页面：

- **导航**：告诉用户站点有哪些主要入口
- **首页**：展示核心内容、重点产品或主线信息
- **列表页**：承载分类、筛选、分页
- **详情页**：承载某一篇内容、某一个产品、某一个案例
- **专题页**：围绕一个主题聚合多个内容

这五类页面基本能覆盖大多数官网、内容站和 SEO 站点。

### 2. 一个站点结构示意

如果你做的是内容型站点，可以先按下面这种方式想：

- `/`：首页，放核心入口、精选内容、站点定位
- `/articles`：列表页，放分类、搜索、分页、文章摘要
- `/articles/[slug]`：详情页，放完整正文、作者信息、相关推荐
- `/topics/[slug]`：专题页，放围绕主题聚合的一组内容
- `/about`：关于页，放站点介绍、团队信息、联系入口

这个结构不一定是标准答案，但它很实用。因为它把“入口、浏览、阅读、聚合、说明”这几件事分开了，用户路径会比较顺。

### 3. 每类页面的职责要分清

#### 导航
导航不是装饰，它是站点结构的一部分。它负责告诉用户：

- 我在哪
- 还能去哪里

如果导航乱，用户就像进了没门牌号的楼里，找不到下一步。导航清楚了，站点整体可用性会直接提升。

#### 首页
首页不是“什么都放一点”，而是站点入口总览。适合放：

- 核心卖点
- 热门内容
- 推荐入口
- 明确的行动按钮

首页最忌讳信息堆砌。好的首页不是展示越多越好，而是让用户一眼知道这个站点能提供什么。

#### 列表页
列表页最重要的是“组织信息”：

- 分类
- 标签
- 搜索
- 分页
- 排序

它的重点不是讲完整内容，而是帮助用户快速筛选、快速进入详情。它像一个“内容中转站”。

#### 详情页
详情页承载完整内容：

- 标题
- 正文
- 作者
- 发布时间
- 推荐阅读
- 上下篇

列表页和详情页的职责一定要分开。列表负责入口，详情负责内容。很多项目后面不好维护，就是因为一开始把这两个职责混在一起了。

#### 专题页
专题页适合做内容聚合，比如：

- 某个主题的系列文章
- 某个产品线的介绍页
- 某次活动的落地页

专题页很适合做 SEO，也很适合做运营承接页。它通常比普通列表页更聚焦，用户也更容易看明白价值。

### 4. 一个实战结构思路

如果你在做技术内容站，可以这样组织：

- `/`：首页，展示精选文章、栏目入口、搜索框
- `/articles`：文章列表页，支持分类和分页
- `/articles/[slug]`：文章详情页
- `/topics/[slug]`：专题页，聚合相关文章
- `/about`：关于页

这种结构的好处是：

- 用户路径清晰
- 后续 SEO 好做
- 页面类型明显，布局和组件都容易复用

更重要的是，它天然适合后续扩展。以后想加作者页、标签页、搜索页，也能自然长出来。

### 实用建议

- 先画站点地图，再开始写代码。
- 不要让首页承担所有内容职责。
- 列表页和详情页要尽早分开，否则后面会越来越乱。
- 从一开始就想清楚“用户从哪来、要去哪里”，结构会更顺。

---

## 五、组件拆分经验：别把页面写成一坨，也别过度抽象

### 1. 拆组件的目标是什么

拆组件不是为了“优雅”，而是为了：

- 更容易读
- 更容易改
- 更容易复用
- 更容易测试和替换

如果一个组件拆出来之后，反而让理解成本更高，那它就没真正带来收益。

所以老赵常说，组件拆分不能只看代码层面，还要看团队协作和后期维护。你今天省下来的 10 分钟，可能会在下周的改版里加倍还回来。

### 2. 老赵常用的拆分原则

#### 原则一：按变化点拆
哪些地方最可能变动，就优先独立出来。比如：

- 文章卡片样式以后可能改
- 搜索栏逻辑以后可能升级
- 列表分页可能换实现

这些地方一旦改动频繁，单独抽出来会更省心。

#### 原则二：按复用频率拆
一个东西会在多个页面出现，就值得抽成组件。比如：

- Header
- Footer
- Card
- Pagination

复用频率越高，越值得早一点整理出来。

#### 原则三：按职责边界拆
一个组件只做一件事，别什么都干。比如：

- `ArticleCard` 只负责展示文章摘要
- `ArticleList` 负责渲染一组卡片
- `ArticlePage` 负责组织页面结构

职责边界越清楚，后面越不容易互相影响。

### 3. 怎么判断是不是拆过头了

出现这些信号，通常说明你拆多了：

- 文件名看不出功能
- 一个页面要跳来跳去看十几个组件
- 修改一个文案要改多个文件
- 组件之间传来传去的 props 特别多

这时候要反向合并，回到“够用就好”。

老赵提醒你一句：**拆分的目的不是把文件数量做大，而是把复杂度分散到合理的位置。** 如果拆完更难维护，那说明这次拆分没做好。

### 4. 组件拆分的经验总结

你可以记住这句：

> **先保证页面结构清楚，再保证组件复用合理。**

别为了提前准备未来，牺牲当前可读性。很多项目真正的问题，不是复用太少，而是抽象太早。

尤其是做站点的时候，先把“首页、列表页、详情页”这些核心页面跑通，组件抽象可以慢慢补。不要一开始就把所有可能复用的东西都预判出来，结果把自己绕进去。

### 实用建议

- 小项目：组件少一点，结构清楚最重要。
- 中大型项目：公共组件、业务组件、页面组件要分层。
- 如果还在犹豫要不要抽象，先别抽，等重复出现再说。
- 先把站点做出来，再把结构优化好，这个顺序别反过来。

---

## 结尾小结：先做对结构，再谈精细拆分

这一章你真正要记住的，不是某个文件名，而是**站点组织思维**。

Next.js 的页面、布局、组件，本质上是在帮你把站点拆成三层：

- **页面**：解决“哪个地址显示什么”
- **布局**：解决“这一组页面共用什么壳”
- **组件**：解决“哪些 UI 片段可以复用”

再往下看，站点通常会自然长成首页、列表页、详情页、专题页这些结构。你如果一开始就把这些边界想清楚，后面接数据、做 SEO、处理渲染策略，都会顺很多。

最后给你一个更实在的判断口诀：

- **小站点、验证期项目**：先简单做，页面和组件别拆太碎。
- **页面类型开始分组、公共结构开始重复**：引入布局和公共组件。
- **内容规模变大、后台和前台分离、不同区域壳子不同**：再考虑嵌套布局和更细的组织方式。

也就是说，结构不是一步到位搭出来的，而是跟着站点长出来的。你要做的是先搭对骨架，再慢慢长肌肉。

下一章，我们继续讲 Next.js 里的路由与参数，看看这些页面骨架是怎么和 URL 真正连起来的。

# 第5章：路由、动态参数与页面跳转

## 开篇：为什么学到这里，路由就变成了“站点骨架”

前面你已经知道，Next.js 不只是“会写页面的 React”，它更像一套站点工程方案，把页面、路由、数据获取、SEO 和接口能力串起来。

而路由，就是这套方案的骨架。

在 React 里你也能用 React Router，但一旦项目变成内容站、官网站、SEO 站点，路由组织、动态参数、404 兜底这些问题就会一下变多。Next.js 的思路很直接：**把路由交给文件系统管理**。你建一个文件，基本就等于多了一条路由，页面结构和 URL 结构天然对齐。

这也是 React 之后为什么值得学 Next.js 的一个现实原因：**当页面从单页组件走向站点结构时，Next.js 能帮你少踩很多组织和工程化的坑。**

但也别上头。  
如果你只是一个很小的后台页、单页工具站，路由结构并不复杂，未必一开始就要引入这整套机制。**先解决问题，再引入复杂度**，这是老赵一直强调的原则。

---

## 一、文件系统路由：看文件就知道站点长什么样

### 1. 目录就是路由

在 Next.js 里，页面路由通常来自目录结构：

- `app/page.tsx`：首页
- `app/about/page.tsx`：`/about`
- `app/blog/page.tsx`：`/blog`

文件夹代表路径层级，页面文件代表可访问页面。这样最大的好处是：**页面结构和 URL 结构一致**，回头看项目时，直接看文件树就能知道站点大概长什么样。

这对内容站、博客站、官网站尤其友好：首页、列表页、详情页、分类页、标签页，都能清晰表达出来。

### 2. 常见目录职责

实际项目里常见这些文件：

- `page.tsx`：页面入口
- `layout.tsx`：布局
- `loading.tsx`：加载中状态
- `error.tsx`：错误页
- `not-found.tsx`：404 页

也就是说，Next.js 不只是帮你“找页面”，还把页面体验的配套能力一起考虑进来了：没加载完怎么办、出错怎么办、找不到怎么办。

### 3. App Router 和 Pages Router 的区别

Next.js 有两套路由体系：

- **Pages Router**：基于 `pages/` 目录，老一些，但很多项目还在用
- **App Router**：基于 `app/` 目录，是新方向，更强调布局嵌套、服务端组件和流式渲染

如果你是现在开始学，建议重点放在 **App Router** 上；如果你接手的是旧项目，也要知道 `pages/` 体系依然常见。

### 4. 这套机制适合什么场景

特别适合：

- 内容站
- 文档站
- 官网站
- 博客站
- 带详情页的业务展示站

因为这类站点天然就是“首页 + 列表 + 详情 + 专题/关于/联系”这种结构。文件系统路由几乎就是为它们准备的。

如果项目只是“首页 + 登录页 + 几个后台页”，当然也能用，但要先判断：Next.js 带来的站点能力，值不值得你付出更多工程复杂度。

### 实用建议

- 小项目先按页面结构建目录，不要急着拆太细。
- 目录命名尽量语义化。
- 页面少时保持简单，页面多了再做分组和布局拆分。
- 临时活动页或内部工具页，别把目录设计得过度复杂。
- 新项目优先学 App Router，老项目先确认自己用的是哪套体系。

---

## 二、动态路由、可选参数与嵌套路由：让页面地址“活”起来

### 1. 动态路由解决什么问题

静态路由适合固定页面，比如：

- `/about`
- `/pricing`

但文章详情页、商品详情页、用户主页这类页面数量是动态变化的，不可能每个 ID 都建一个文件，这时就要用动态路由。

例如：

- `/blog/1`
- `/blog/hello-nextjs`

页面结构一样，只是参数不同。

### 2. 最小案例：文章详情页怎么设计

最典型的是文章详情页：

- 列表页：`/posts`
- 详情页：`/posts/[slug]`

这里的 `slug` 是动态参数。比如文章“Next.js 入门”可以映射成 `/posts/nextjs-intro`。

这样做的好处是：

1. 地址可读
2. 分享方便
3. SEO 更友好

如果你的业务更依赖数据库主键，也可以用 `/posts/[id]`。不是 `slug` 一定比 `id` 高级，而是看业务需要。

### 3. 常见写法思路

动态段通常这样写：

- `[id]`：单个动态参数
- `[slug]`：语义化标识
- `[...slug]`：捕获多个层级
- `[[...slug]]`：可选的多段参数

核心只要记住：**动态路由就是把 URL 中变化的部分抽出来，交给页面处理。**

参数命名要贴近业务对象，别乱写 `pid`、`dataId` 之类的缩写，不然维护会很难受。

### 4. 什么情况下别乱用动态参数

不要为了“统一”把所有页面都做成动态的。  
比如固定页：

- `/about`
- `/contact`
- `/pricing`

硬写成 `/[pageName]`，看起来整齐，实际上会让页面职责、SEO 目标、布局差异都变模糊。

动态路由是为真实变化服务的，不是为了显得高级。

### 5. 嵌套路由适合什么

嵌套路由适合页面之间有层级关系的场景，比如：

- `/docs`
- `/docs/guide`
- `/docs/api`
- `/blog/category/frontend`

这类结构上层一致、下层变化，天然适合用嵌套路由来组织页面和布局。

### 6. 可选参数别乱用

可选参数会让路由更灵活，但也容易把结构搞模糊。  
如果一个路由既能接 `id`，又能接多层参数，还能空着不传，没有明确需求时，往往就是在给自己挖坑。

### 常见误区

- 为了“未来可能用到”提前设计太多参数位
- 一个页面兼容多种 URL 形态
- 参数命名不统一

### 实用建议

- 先判断页面是固定内容还是动态内容。
- 动态路由只给真正会变的资源用。
- 单参数能解决的，就别上多段参数。
- URL 设计从用户和内容结构出发，不从技术炫技出发。
- 详情页优先考虑 `slug` 或 `id`，别把参数设计得太花。

---

## 三、列表页到详情页：最典型的路由设计路径

### 1. 这是一条最常见的站点路径

在内容站、产品站、资讯站里，最常见的链路就是：

- 用户先看到列表页
- 点击某一项
- 进入详情页
- 详情页根据参数加载对应内容

这个链路做顺了，网站才像一个成熟站点。

### 2. 一个好用的典型路径设计

最朴素、也最实用的设计通常是：

- 列表页：`/posts`
- 详情页：`/posts/[slug]`
- 搜索页：`/posts?keyword=nextjs`
- 分类页：`/posts/category/frontend`

这套路径一眼就能看懂，核心就是先把主链路做顺，再考虑扩展。

### 3. 路径参数和查询参数怎么选

这个地方很关键，很多新手会混。

#### 路径参数
像 `/posts/nextjs-intro`、`/product/1001`，表示的是一个明确资源，语义是“我访问的是哪一个对象”。

适合：

- 文章详情
- 商品详情
- 用户主页
- 专题页

#### 查询参数
像 `?keyword=react&page=2&sort=hot`，更多是在描述“如何筛选、如何查看”。

适合：

- 搜索
- 分页
- 排序
- 筛选条件

简单理解：

- 路径参数更像“我是谁”
- 查询参数更像“我怎么筛选、怎么查看”

### 4. 页面跳转的思路

Next.js 里页面跳转一般有两类：

- **声明式跳转**：适合列表项、按钮、导航菜单
- **编程式跳转**：适合登录成功、表单提交后、条件满足后自动跳转

大多数列表、卡片、标题都可以直接做成可点击链接。这样更自然，也更利于 SEO 和可访问性。

### 5. Link 和 useRouter 分别适合什么

- `Link`：适合页面之间自然跳转
- `useRouter`：适合程序触发的跳转

比如：

- 菜单、列表标题、相关推荐：优先用 `Link`
- 登录成功后跳首页：用 `useRouter`
- 表单提交完成后跳详情页：用 `useRouter`

判断标准很简单：

> 如果这个跳转本质上是“一个页面链接到另一个页面”，优先用 `Link`。  
> 如果它本质上是“某个动作完成后再决定去哪里”，再考虑 `useRouter`。

不要用点击事件代替链接来做所有跳转，那样会丢掉右键新开、复制链接、预加载等原生能力。

### 6. 详情页如何获取参数

详情页拿到参数后，通常做两件事：

1. 解析参数
2. 根据参数拿数据

比如文章详情页拿到 `slug`，再去查对应文章。如果查不到，就进入 404 或错误状态。

真实站点里，乱输地址、过期链接、爬虫访问都会出现，所以不能假设用户输入的 URL 都合法。

### 实用建议

- 列表项优先用链接，不要全靠 `onClick`。
- 资源定位用路径参数，筛选条件用查询参数。
- 详情页一定要考虑参数不存在或内容已删除。
- 跳转后页面标题、面包屑、返回路径最好能呼应当前位置。
- 能直连的地方用 `Link`，需要业务判断的地方再用 `useRouter`。

---

## 四、基础体验兜底：404、loading、错误页要放在一组里看

### 1. 不要只盯着“能跳”，还要盯着“出事怎么办”

很多人写路由时，只管“点了能跳”，但站点上线后，问题往往出在边角：

- 内容加载慢怎么办？
- 页面请求失败怎么办？
- 访问不存在的地址怎么办？
- 动态参数对不上怎么办？

这些地方决定了站点是否“像样”。

### 2. 一个完整流程案例：不存在页面、加载中、接口失败

拿文章详情页举个例子。

#### 第一步：访问不存在的文章地址
用户访问 `/posts/not-exist`，系统根据 `slug` 去找文章，结果查不到。

这时不要白屏，也不要把一堆报错甩给用户，而是进入 **not-found**，明确告诉用户：

- 这篇文章不存在
- 可能被删除了
- 可以返回列表页继续看

#### 第二步：页面正在请求中
如果数据是异步获取的，打开详情页时可能还在加载。

这时可以展示 loading 状态，比如骨架屏、标题占位、正文占位。用户看到的是“正在加载”，不是“页面坏了”。

#### 第三步：接口失败
如果是接口临时报错，比如网络波动、服务异常，那就应该进入 **error** 兜底，提示：

- 数据加载失败
- 请稍后重试
- 返回上一页或回首页

### 3. 404 页面：不存在就明确告诉用户

404 页不是摆设。它要做的是：

- 明确告诉用户页面不存在
- 给用户返回首页、返回列表、继续浏览的路径
- 避免一片空白

好的 404 页不是只写 `Not Found`，而是要有行动出口，比如回首页、看热门内容、回文章列表、搜索站内内容。

### 4. loading 页面：让用户知道你在干活

页面数据还没准备好时，加载状态很重要，尤其是动态详情页、筛选列表页、权限判断页。

重点不是炫动画，而是：

- 告诉用户系统没有卡死
- 给到明确等待反馈
- 减少页面空白感

简单的骨架屏、灰块占位、局部加载提示就够了。

### 5. 错误页：别让一个请求拖垮整页

错误页的价值在于隔离问题。  
有时候只是某个模块接口报错，不应该把整个站点炸掉。比如详情页正文能出来，但相关推荐挂了，正文仍然可以读，这种“能活着就先活着”的思路，很适合内容站和资讯站。

### 常见误区

- 只给首页做了漂亮 UI，错误状态完全没设计
- 以为线上不会出错
- 所有错误都只会让用户看到白板
- 把“页面不存在”和“接口失败”混为一谈

### 实用建议

- 404 页一定要带返回按钮或推荐内容。
- loading 状态尽量和页面风格一致。
- 错误页要区分“页面不存在”和“请求失败”。
- 上线前至少手动测：不存在路径、慢接口、接口报错三种情况。
- 详情页异常处理最好和数据获取一起设计，不要最后补。

## 五、路由设计建议：先简单，再扩展，别一开始就设计过度

### 1. 跟着内容走，别跟着想象走

很多项目一开始就喜欢画很复杂的 URL 结构图，想把未来三年的页面都规划完，结果项目还没做完，路由先复杂了。

老赵建议你记住一句话：

> **路由不是拿来展示架构能力的，是拿来服务内容和用户路径的。**

先看内容怎么分：

- 是文章？
- 是商品？
- 是分类？
- 是专题？
- 是后台管理？

内容结构清楚了，路由自然就清楚了。

### 2. 先简单的标准是什么

如果你还在做 MVP、验证产品、快速搭建官网，路由设计先满足这几个要求就够了：

- 路径好读
- 规则统一
- 参数少而明确
- 页面职责清楚
- 后期能平滑扩展

简单不是偷懒，而是把精力花在内容、交互、数据和 SEO 上。

### 3. 什么情况下再扩展复杂度

当你遇到这些情况，再考虑更复杂的路由设计：

- 页面层级明显增多
- 同类页面需要统一布局
- 内容要按专题、分类、标签细分
- 需要权限分区、后台分区、站点分区
- SEO 和页面模板差异开始明显

这时候路由复杂度上来，是有业务理由的，不是为了“看起来高级”。

### 4. 一个简单判断法

你可以问自己三个问题：

1. 这个路由是不是用户能看懂？
2. 这个参数是不是必须存在？
3. 这个结构是不是未来真的会用到？

如果两个问题答不上来，那就先别设计过度。

### 实战中的经验总结

- 简单站点先用简单路由，别一上来就“框架化”
- 动态路由是为了处理真实变化，不是为了显得高级
- 页面跳转要服务用户路径，而不是只服务代码逻辑
- 404、loading、错误页这些细节，往往比你想象中更影响站点质感

---

## 结尾：这一章你真正该带走什么

这一章讲的不是“怎么写几个路径”，而是 Next.js 路由背后的站点思维。

你应该记住这几条：

- **文件系统路由**让页面组织和 URL 结构保持一致
- **动态路由**解决列表页、详情页这类变化内容
- **参数传递**要区分资源定位和筛选条件
- **Link 和 useRouter** 各有适用场景，别用点击事件硬替代链接
- **404、loading、错误页**是站点体验的一部分，不是附加品
- **App Router 和 Pages Router** 都要认识，但新项目优先学 App Router
- **路由设计要先简单后扩展**，别为了将来可能出现的需求提前堆复杂度

如果你已经能把一个列表页、详情页、404 页串成一套完整的访问链路，那你对 Next.js 路由就不是停留在“会写”，而是开始进入“会设计”。

# 第6章：数据获取、静态内容与动态内容处理

## 开篇：页面能不能“先有内容”，决定了站点好不好做

讲到 Next.js，很多人先关心路由、组件、样式，真到做站点时才发现，最麻烦的往往不是页面怎么写，而是**数据从哪里来、什么时候来、要不要每次都来**。

如果你做的是内容站、官网站、博客站，页面里的大部分内容通常不需要用户一打开就临时请求一遍。文章标题、正文、产品介绍、FAQ，这些内容变化不频繁。Next.js 的价值就在于：**把数据获取和页面生成结合起来，尽量让页面先准备好，而不是用户来了再拼装**。

这就是 React 做纯前端页面和 Next.js 做站点开发之间最关键的差别。React 更像“先搭壳，内容后补”；Next.js 更像“壳和内容一起提前准备”。对内容站来说，这会直接影响加载速度、SEO、运维成本和体验。

到了站点开发阶段，**数据获取不是代码细节，而是页面策略**。你怎么拿数据，决定了页面是快、稳，还是重、慢。

---

## 一、页面渲染前后的数据获取思路：先准备，还是后请求？

### 1.1 页面渲染前获取数据，适合“结果相对固定”的内容

渲染前获取数据，就是页面生成前先把数据拿到，再输出完整页面。你可以理解为：**页面不是空壳，而是带着内容出生的**。

这种方式适合：

- 首页推荐内容
- 文章详情页
- 产品介绍页
- 帮助中心、FAQ
- 落地页、官网页

优点很直接：

- 首屏更完整
- 搜索引擎更容易抓取正文和标题
- 不用等前端补数据，体验更稳
- 很适合展示型页面

这类页面最怕“先出骨架，正文晚点才填上”。用户会觉得虚，搜索引擎也不够友好。

### 1.2 页面渲染后再获取数据，适合“强交互、强实时”的内容

另一种思路是页面先渲染基础结构，浏览器加载后再发请求。它更像传统单页应用，适合：

- 登录后的个人中心
- 实时消息列表
- 后台管理页
- 依赖用户状态的内容区
- 库存、订单状态、通知流这类实时数据

优点是交互灵活；缺点是首屏内容可能不完整，SEO 也一般。

所以这两种方式不是谁更高级，而是服务目标不同：一个偏“展示”，一个偏“操作”；一个讲“先给内容”，一个讲“先给框架”。

### 1.3 先判断“内容是给谁看的”

最实用的判断法很简单：

- **给搜索引擎和访客看的内容**：尽量前置获取
- **给登录用户操作看的内容**：可以后置获取
- **给实时变化看的内容**：偏动态
- **给长期展示看的内容**：偏静态

别一上来就问“用什么技术”，先问：**这页到底是谁在看，它要多快变化？**

比如文章详情页是给所有人看的，应该让内容尽早出现；而“我的订单”只给登录用户看，没必要硬做成公共可抓取页面。

### 实用建议

如果你做的是官网、博客、内容站，先把“页面内容提前准备好”当默认策略。不要把所有请求都放到浏览器里做，那样得到的往往是一个“能跑但不适合站点”的前端。

## 二、静态内容适合什么，动态内容适合什么？

### 2.1 静态内容：不常变、适合复用、适合被收录

静态内容不是“死内容”，而是指**变化频率低、可以提前生成、重复访问成本低**的内容。

典型包括：

- 公司介绍
- 产品页
- 服务页
- 博客文章
- 课程介绍
- 帮助文档

静态内容的好处是：

- 加载快
- 成本低
- 稳定性高
- SEO 友好

内容站里，大多数页面都应该优先考虑静态化。因为它们本质上不是“频繁操作”，而是“长期展示”。

### 2.2 动态内容：变化快、个性强、依赖用户状态

动态内容通常有这些特征：

- 每个用户看到的不一样
- 数据更新频繁
- 内容依赖登录状态
- 需要即时反馈

例如：

- 个人中心
- 我的订单
- 收藏列表
- 管理后台
- 消息通知
- 实时统计面板

这类内容如果硬做成静态，维护会很痛苦；但如果把所有页面都动态化，又会牺牲首屏和 SEO。所以关键不是“静态好还是动态好”，而是**该静态的静态，该动态的动态**。

### 2.3 一个简单原则：展示内容静态化，操作内容动态化

可以粗暴分成两类：

- **展示型页面**：首页、文章页、产品页、落地页
- **操作型页面**：个人中心、后台页、任务页

前者优先静态或半静态，后者优先动态或客户端获取。这个划分虽然朴素，但在实际项目里特别管用。

你可以记成一句话：

- 页面是“给别人看”的，越早准备越好
- 页面是“给自己用”的，越灵活越好

### 常见误区

1. **所有页面都做动态**  
   结果是慢、贵、SEO 一般。

2. **所有页面都死静态**  
   结果是登录态、用户态、实时数据都不好处理。

3. **把“能更新”误解成“必须动态”**  
   很多页面不是不能更新，而是不需要每次访问都重新算一遍。

### 实用建议

如果一个页面一天才改一两次，优先考虑静态化；如果内容每分钟都变，再认真考虑动态方案。不要为“可能会变”提前引入复杂度。

## 三、列表页、详情页、首页、个人中心：不同页面，数据策略不一样

### 3.1 首页：优先“快”和“稳”，兼顾少量动态

首页是门面，通常要兼顾：

- 首屏速度
- 内容完整度
- 搜索引擎可读性
- 少量个性化推荐

内容站首页通常建议：

- 主体内容静态化
- 热门模块定时更新
- 登录后区域再做个性化展示

首页别做得太重。首页一慢，整个站的第一印象就差了。官网或内容站的首页重点不是把功能塞满，而是让用户迅速知道：你是谁、你能提供什么、该往哪点。

### 3.2 列表页：适合按分类或分页生成

列表页常见于文章分类、产品列表、资源列表，特点是：

- 内容多
- 结构统一
- 更新有批次性
- 很适合缓存

常见做法：

- 分类列表按页生成
- 热门分类优先缓存
- 新增内容定时刷新
- 搜索结果页再动态处理

列表页很适合做“半静态”。只要内容结构稳定，它就是很好的静态候选。分页列表尤其如此，第一页最重要，后面的页可以更偏缓存和复用。

### 3.3 详情页：最适合静态化的页面之一

详情页通常是文章详情、商品详情、案例详情，有两个特点：**访问量大、重复展示多**。它往往也是 SEO 的重点，所以应尽量让内容可被完整抓取。

建议：

- 内容不常变时优先静态化
- 更新后再触发重新生成
- 评论、点赞等互动区可以后置动态加载

详情页不是“完全不能动态”，而是**正文尽量稳定，互动区可以动态**。比如文章正文静态化，评论、收藏、相关推荐再异步加载，这样既保住收录，也保留互动能力。

### 3.4 个人中心：典型动态页面

个人中心的内容通常与用户有关：

- 我的资料
- 我的订单
- 我的收藏
- 我的阅读记录

这类页面很难做成通用静态页，因为每个用户都不同。更适合登录后按需请求，或者基础框架静态化、用户数据动态加载。

个人中心要的是准确性和权限控制，不是搜索收录。

### 实用建议

设计页面时先问一句：**这个页面是公共展示，还是私有操作？**

- 公共展示：优先静态或预渲染
- 私有操作：优先动态或登录后请求

这个判断能帮你少走很多弯路。

## 四、缓存、更新频率与内容时效性：怎么判断该不该“提前生成”？

### 4.1 判断核心不是技术，而是时效性

本质只看三件事：

1. 内容多久变一次
2. 变了之后影响多大
3. 用户能不能接受短时间不一致

如果改动后允许几分钟甚至几十分钟再生效，就适合缓存或静态化；如果一变就必须立刻看到，就偏动态。

做站点开发，不能只盯着“技术酷不酷”，而要先看业务能不能接受延迟。大多数内容站其实都能接受一定延迟，尤其是文章、产品、公告。

### 4.2 一个简单的判断流程

你可以按下面几个问题顺着想：

1. 这是公共页面还是私有页面？
2. 这是展示内容还是操作内容？
3. 内容多久更新一次？
4. 更新晚一点，用户能不能接受？
5. 这页是否需要尽量被搜索引擎收录？

如果答案偏向“公共、展示、低频更新、可接受延迟、需要收录”，那就优先静态化；如果答案偏向“私有、操作、高频变化、不能延迟”，那就优先动态获取。

### 4.3 缓存不是“偷懒”，而是控制复杂度

缓存的意义不是“让数据不更新”，而是**让你在合适的时机更新**。

你可以把缓存理解为三个问题：

- 多久更新一次？
- 谁来更新？
- 更新后谁受影响？

这三个问题想清楚了，缓存就不是负担，反而是减轻系统压力的好办法。

### 常见误区

- 认为“缓存一旦过期就不准”
- 认为“动态一定比静态更真实”
- 认为“越实时越好”

实际上，大多数内容站并不需要秒级实时。用户更在意的是：打开快、内容全、搜索能搜到、页面别乱跳。

### 实用建议

对于内容站，先把“更新频率”和“用户容忍度”列出来，再决定数据处理方式。不要反过来：先选技术，再硬套业务。

---

## 五、经验建议：内容不常变就尽量静态化，常变化再走动态

### 5.1 先从最简单、最稳的方案开始

能静态就别动态，能少请求就别多请求。

原因很简单：

- 静态方案通常更快
- 维护成本更低
- SEO 更友好
- 出问题的点更少

刚做站点时，不要把每个页面都做得很“智能”。你需要的是稳定上线，而不是架构炫技。真正成熟的做法，是把复杂度用在刀刃上：该静态的静态，该交互的交互，该实时的实时。

### 5.2 哪些场景适合先上 Next.js 的数据能力？

如果你满足下面任意几条，就很适合认真用 Next.js 的数据能力：

- 做内容站、博客站、官网站
- 页面需要被搜索引擎收录
- 大部分页面内容变化不频繁
- 有文章、产品、案例、帮助中心这类详情页
- 需要首页和列表页做统一的数据处理

这时 Next.js 的优势不是“多一个框架”，而是帮你把站点开发的关键问题一次考虑进去：怎么拿数据、怎么生成页面、怎么兼顾展示和收录。

### 5.3 哪些场景可以先别急着上复杂度？

如果你现在是下面这些情况，先别急着把 Next.js 数据机制用满：

- 纯内部工具，不需要 SEO
- 页面大多是表单和操作，不是内容展示
- 业务还很小，数据源也简单
- 先验证需求，再考虑性能和收录

这时候更重要的是把功能做对，而不是一开始就搞太多处理策略。很多项目死在“过早复杂化”。

你要记住：**框架不是为了让你看起来更专业，而是为了让项目更适合业务。**

### 5.4 本章的操作清单

你可以按这个顺序给项目做判断：

1. 先列页面类型：首页、列表、详情、登录后页面
2. 再列内容属性：公共还是私有、静态还是实时
3. 再看更新频率：小时级、天级、分钟级还是秒级
4. 再决定策略：静态、动态、缓存、定时刷新
5. 最后再考虑实现细节

这个顺序一旦理顺，后面做 SEO、图片优化、API Routes 和登录权限都会轻松很多。

---

## 小结：先把“内容怎么活”想明白，再谈“页面怎么写”

这一章讲的其实就一件事：**Next.js 的数据获取，不是单纯把请求搬到服务端，而是围绕内容类型、更新频率、页面角色来决定怎么处理。**

你要记住几个最实用的结论：

- 展示型页面，优先静态化或预渲染
- 操作型页面，优先动态获取
- 列表页和详情页是内容站核心，通常更适合静态化
- 首页要快，个人中心要准，不能用同一套思路硬套
- 缓存和静态化不是偷懒，而是站点设计的一部分
- 内容不常变就尽量静态化，常变化再走动态

如果你后面要做 SEO、图片优化、API Routes 和登录权限，这一章就是地基。地基打稳了，后面的章节才不会东一榔头西一棒子。

**行动建议：**  
拿你正在做的一个页面，写下它的“内容来源、更新频率、是否公开、是否需要收录”四项信息，然后判断它应该静态、动态，还是静态加局部动态。只要你能把这一步做对，Next.js 的数据获取思路就算真正入门了。

# 第7章：SSR、SSG 与渲染策略怎么选

## 开篇：别先问“哪个最强”，先问“这个页面到底想干什么”

讲到 Next.js，很多人最容易卡在渲染策略上：SSR、SSG、ISR 这些词一出来，脑子就乱了。其实不用先背定义，你先把它们当成“页面什么时候生成、谁来生成、要不要现做”的交付方式就行。

这一步为什么重要？因为 React 解决的是“怎么写界面”，而 Next.js 还要继续解决一层更现实的问题：**页面怎么交付、怎么被访问、怎么被搜索引擎看见、怎么尽快打开**。这也是 React 之后为什么要学 Next.js 的核心原因之一。你不是只在写组件了，你是在做一个真正能上线、能收录、能扩展的站点。

所以这一章别急着背概念，先把场景和选择思路搞明白。后面你做内容站、官网站、活动页，甚至后台页，都会用到这套判断法。

---

## 一、先把三个词说清楚：SSR、SSG、ISR 分别是什么

### 1. SSR：请求来了，服务器现场渲染

SSR 就是：**用户一请求，服务器根据当前请求现场生成 HTML，再返回给浏览器**。

最典型的场景：

- 登录后的个人中心
- 订单详情页
- 根据权限展示不同内容的页面
- 实时价格、实时库存
- 强动态后台页

它的好处很直接：

- 内容是当前最新的
- 页面更容易被搜索引擎直接读取
- 适合跟用户身份、请求参数强相关的页面

它的代价也要知道：

- 每次请求都要服务端计算
- 服务端压力更大
- 缓存和鉴权处理更复杂
- 逻辑复杂时，排错和部署都更麻烦

你可以把 SSR 理解成“现炒现卖”，新鲜，但厨房压力也大。

### 2. SSG：提前生成好，用户来了直接拿成品

SSG 就是：**在构建阶段把页面提前生成好 HTML，用户访问时直接拿现成页面**。

最典型的场景：

- 官网首页
- 产品介绍页
- 博客文章页
- 文档页
- 内容稳定的活动落地页

它的优点很实在：

- 打开快
- CDN 分发方便
- 搜索引擎容易抓取
- 服务端压力小
- 页面结构稳定，维护轻松

它的缺点也很明确：

- 内容更新后通常要重新构建
- 不适合强实时页面
- 页面越多，构建时间越可能变长
- 如果更新很频繁，发布流程会别扭

所以，SSG 不是“老旧的静态页”，它其实是内容站、官网站特别常用的一种交付方式。

### 3. ISR：先静态，过一段时间再更新

ISR 可以理解成：**页面先静态生成，但允许过一段时间自动重新生成**。它是 SSG 的增强版，兼顾“快”和“能更新”。

典型场景：

- 内容站文章页
- 商品详情页
- 资讯详情页
- 带推荐模块的内容页
- 基础信息稳定、局部会变化的页面

它的优势很明显：

- 首屏仍然快
- 不需要每次全站重建
- 比纯 SSG 更灵活
- 对内容站和商品站都比较友好

但它也不是万能药：

- 不适合必须秒级更新的场景
- 需要理解缓存和重新生成的节奏
- 要提前设计内容更新策略

### 4. 一个最实用的记法

你可以先这样记：

- **SSR：每次都现做**
- **SSG：提前做好**
- **ISR：先做好，过一会儿再更新**

这个记法足够你先做方向判断。真正难的不是名词，而是你能不能把页面类型、更新频率、SEO 需求和团队成本连起来看。

**实用建议：**  
第一次做站点，别一上来就全站 SSR，也别迷信“全站静态一定最优”。先按页面性质分：内容型页面优先静态，用户态页面优先服务端，更新不频繁但又要保持新鲜的内容页考虑 ISR。

---

## 二、不同页面类型怎么选：把首页、内容页、活动页、后台页分开看

真实项目里，你做的不是一个页面，而是一组页面。不同页面的目标不同，策略就不能一刀切。

| 页面类型 | 优先策略 | 适用原因 | 不太适合的情况 |
| --- | --- | --- | --- |
| 首页 | SSG / ISR | 需要快、要收录、内容相对稳定 | 强依赖登录态或实时数据时 |
| 内容页 | SSG / ISR | SEO 重要，正文稳定，访问量大 | 内容强实时、每人看到不同内容时 |
| 活动页 | SSG 为主，局部动态补充 | 打开快、转化路径短、文案稳定 | 活动规则频繁变化、实时人数很关键时 |
| 后台页 | SSR / 客户端渲染 | 登录态强、交互多、SEO 不重要 | 为了“看起来高级”硬做静态时 |

### 1. 首页：大多数情况下优先 SSG，必要时配合 ISR

首页通常是站点门面，特点很明确：

- 要打开快
- 要让搜索引擎快速理解站点主题
- 展示信息多，但变化不一定频繁
- 往往承载品牌、导流和核心入口

所以，官网首页、内容站首页、品牌首页，通常优先考虑 **SSG**。如果首页有推荐内容、最新文章、热门产品这些会变化的模块，可以再考虑 **ISR**，或者把变化部分单独动态加载。

什么时候用 SSR？

- 首页内容和用户身份强相关
- 要展示实时价格、实时状态
- 需要根据地区、语言、登录态动态变化

但多数站点首页并不需要这么复杂。更稳的做法是：**主体静态化，少量变化区域动态处理**。

### 2. 内容页：优先 SSG 或 ISR

内容页是 Next.js 很舒服的场景，比如文章详情、教程详情、帮助文档、案例页。

原因很简单：

- 内容通常不是每秒都变
- 非常看重 SEO
- 访问量可能不小，但更新不频繁
- 结构可以标准化，便于批量生成

如果内容长期稳定，SSG 足够好。  
如果是新闻、资讯、商品详情这类会更新的内容，ISR 更实用。

简单判断：

- 文章发布后很少改：SSG
- 文章会改标题、摘要、正文：ISR
- 详情页涉及库存、价格、状态：可能要 SSR，或者 SSR + 客户端刷新
- 文档页面更新不频繁：SSG 很合适

内容页最容易踩的坑，是为了省事全走客户端请求，结果正文晚半拍才出来，SEO 和首屏都不理想。做内容站，静态化和增量更新通常更自然。

### 3. 活动页：看性质，常见是 SSG + 少量动态

活动页、营销页、落地页最重要的是：

- 打开快
- 转化路径短
- SEO 能收录
- 视觉和文案稳定

如果活动内容固定，直接 SSG 就很好。  
如果有倒计时、剩余名额、实时报名人数，可以把核心文案静态化，动态部分单独拉取。

别为了一个报名按钮把整页都做 SSR。很多时候，**大部分内容静态，只有少量模块实时更新**，才是更稳的设计。

### 4. 后台页：大多不需要 SSG，优先 SSR 或客户端渲染

后台页、管理页、控制台，和内容站完全不是一类问题。它们通常：

- 登录态强依赖
- 数据频繁变化
- SEO 没意义
- 交互复杂
- 表格、筛选、弹窗、批量操作很多

所以后台页一般不追求静态生成，更多是：

- SSR：先保证登录态和初始数据
- 客户端渲染：表格、筛选、交互、实时操作在浏览器完成

Next.js 可以用来统一路由、布局和接口调用，但后台不是为了 SEO 才存在的。

**实用建议：**  
内容站、官网站、文章站，优先从 SSG/ISR 开始；后台管理系统，不要为了“听起来高级”强行全站 SSR。先看页面性质，再选渲染策略。

---

## 三、首屏速度、SEO、实时性、维护成本，怎么一起权衡

很多项目不是不会做，而是每个目标都想要，最后什么都没做好。判断渲染策略，不能只看某一个指标。

### 1. 首屏速度：越少临时计算，通常越快

首屏速度主要看：

- 服务端是否临时渲染
- 页面 JS 体积
- 网络请求多少
- 图片是否优化
- 是否走缓存/CDN
- 首屏是否要等多个接口返回

通常来说：

- SSG 首屏快
- ISR 也快
- SSR 通常比静态慢一些，但可以通过缓存优化
- 纯客户端渲染首屏往往最吃亏

但别把“SSR”理解成“自动变快”。它只是一个策略，还得配合页面体积、缓存、图片优化一起看。

### 2. SEO：搜索引擎更喜欢直接看到正文

SEO 的基础逻辑很简单：  
**爬虫要尽量在初次响应里读到有效内容，而不是等 JS 跑完后才拼出来。**

所以：

- SSG 很适合 SEO
- SSR 也适合 SEO
- 纯客户端渲染对 SEO 不友好

但 SEO 不只是“能收录”，还包括：

- title 是否清楚
- description 是否合理
- 标题层级是否规范
- 内容是否完整
- 图片是否有 alt
- 页面是否响应快
- URL 是否清晰、参数是否可控

Next.js 解决的是“更容易被看见”，但内容组织也要做好。

### 3. 实时性：越实时，越偏向 SSR 或动态加载

如果页面显示的是：

- 登录状态
- 当前订单
- 实时库存
- 用户消息
- 审批状态
- 当前用户可见内容

那就不能太依赖静态化。因为静态页本质上有“生成时刻”，不是实时数据库镜像。

常见做法是：

- 页面主体 SSR
- 局部信息客户端请求刷新
- 重要数据由服务端实时返回
- 不重要的展示内容静态化
- 页面骨架先出来，再补充局部数据

关键不是“要不要 SSR”，而是“哪些部分必须实时，哪些部分可以延后”。

### 4. 维护成本：不是越高级越好，而是越适合越省事

维护成本才是后期最贵的东西。

- SSR 需要更重的服务端考虑
- SSG 需要构建流程和内容更新机制
- ISR 需要理解缓存失效和重建节奏
- 纯客户端渲染虽然简单，但 SEO 和首屏可能吃亏

如果团队小、需求稳、内容为主，别把策略搞得过于复杂。  
**先用最少复杂度满足需求，再逐步升级。**

尤其是小型官网、公司介绍站、个人博客站，很多时候没必要把架构做得像大型平台。能静态就静态，能局部动态就局部动态，别为了“技术完整性”把发布流程搞得很重。

**实用建议：**  
做决策时，别只问“哪个性能最好”，要问“哪个策略能以最小成本满足当前业务”。很多站点不是死在技术不够先进，而是死在引入了不必要的复杂度。

---

## 四、什么时候优先静态生成？什么时候必须服务端渲染？

这个问题最值得记。你可以直接拿下面这套判断标准去评审需求、拆页面、做方案。

### 1. 优先静态生成的情况

满足这些特征时，优先 SSG 或 ISR：

- 内容大体稳定
- 希望页面打开快
- 需要 SEO
- 页面访问量大但更新不频繁
- 内容可以按时间批量更新
- 页面不依赖当前登录用户的个性化信息

典型页面：

- 首页
- 关于我们
- 产品介绍
- 博客文章
- 文档页
- 活动落地页

一句话：**能提前做的，就别现场赶工。**

### 2. 必须服务端渲染的情况

这些场景优先 SSR：

- 数据必须按请求实时生成
- 页面依赖登录态或权限
- 内容因用户不同而变化明显
- 不能接受缓存延迟
- 数据变化很频繁
- 页面需要根据请求参数实时筛选

典型页面：

- 用户中心
- 订单详情
- 权限相关页面
- 动态筛选结果页
- 实时数据面板

一句话：**如果每个人看到的都不一样，而且必须准，那就让服务器现场算。**

### 3. 介于两者之间怎么办？

这就是 ISR 的价值。  
如果内容不是绝对实时，但又不能一直不更新，就用 ISR：

- 保证首屏快
- 通过重新生成保持内容不过期
- 适合内容站和商品站
- 适合“稳定为主，偶尔变化”的业务

很多项目的最佳方案不是“纯 SSR”或“纯 SSG”，而是混合策略：

- 首页 SSG
- 文章页 ISR
- 登录后个人页 SSR
- 后台管理页客户端渲染为主

这才是 Next.js 真正的优势：**按页面选策略，而不是一把梭。**

**实用建议：**  
做技术方案时，先把页面按“公开内容、用户内容、实时内容”分层。公开内容优先静态，用户内容优先服务端，实时内容单独拉接口。很多系统根本不需要全站同一种渲染方式。

---

## 五、实战里最常用的选择顺序：先内容，再收录，再实时性，最后看成本

如果你不想每次都纠结，可以按这个顺序来判断：

### 第一步：先看内容是否常变

- 常变：偏 SSR
- 不常变：偏 SSG
- 偶尔变：考虑 ISR

先把“内容变化频率”判断出来，方向就出来一半了。

### 第二步：再看是否要搜索引擎收录

- 要收录：优先 SSR / SSG / ISR
- 不需要收录：可以更偏客户端渲染
- 收录重要但内容也动态：考虑混合方案

比如：

- 文章详情：不常变 + 要收录 = SSG / ISR
- 用户订单页：常变 + 不需要收录 = SSR
- 后台报表页：常变 + 不需要收录 = SSR 或客户端渲染
- 官网首页：不常变 + 要收录 = SSG

### 第三步：再看是否需要实时性

有些页面虽然不常变，但某些字段要实时，比如：

- 活动页剩余名额
- 商品页库存
- 新闻页最新推荐
- 门店页营业状态

这时不要把整个页面都做成 SSR，通常只要把实时部分拆出来动态获取即可。主内容静态化，局部模块单独更新，往往更合理。

### 第四步：最后看团队成本

如果团队小、需求稳、内容为主，别搞得太复杂。  
如果团队成熟、站点规模大、内容更新快，可以引入更细的缓存和重建策略。

**常见误区：**

1. 看到 Next.js 就默认所有页面都要 SSR  
2. 为了 SEO 盲目把后台也做成服务端优先  
3. 内容页不做静态化，导致服务端压力大  
4. 只盯着渲染方式，忽略图片、标题、结构化信息这些 SEO 基础  
5. 过早引入复杂缓存和重建机制，结果维护成本飙升

**实用建议：**  
先按页面分类，再定策略；先满足业务，再优化实现。别让技术选择反过来绑架产品节奏。

---

## 本章小结：策略不是背出来的，是按场景选出来的

这一章你只要抓住四件事就够了：

1. **SSR、SSG、ISR 不是互相替代的口号，而是不同页面的不同交付方式。**
2. **首页、内容页、活动页、后台页，各自目标不一样，所以渲染策略也不一样。**
3. **判断顺序很朴素：先看内容是否常变，再看是否要搜索引擎收录，最后看是否需要实时性和团队成本。**
4. **Next.js 的价值，不是逼你全站高级化，而是让你按页面选最合适的渲染方式。**

记不住所有术语，就记这句：

> **能提前做的，优先静态；必须实时的，服务端现做；介于中间的，用 ISR 过渡。**

如果你再想多记一句，那就记：

> **先看内容是否常变，再看是否要收录；静态优先，实时兜底，别一上来就上复杂度。**

下一章我们会继续往下走，结合 SEO 配置和图片优化，把一个站点真正搭完整。到那一步，你会更清楚：Next.js 不只是“一个 React 框架”，它是把页面、数据、收录、性能和交付方式串起来的一套站点开发方案。

# 第8章：SEO 基础与 Next.js 的页面优化

## 开篇引入：为什么做站点开发，SEO 不能“后面再说”

很多 React 开发者做页面时，先盯着组件拆分、状态管理和交互实现，这些都没错。但只要你做的是内容站、官网站、博客、落地页或产品介绍页，SEO 就不是“有空再补”的事，而是站点能不能被找到、被理解的基础能力。

**React 更擅长把页面做出来，Next.js 更擅长把页面做给搜索引擎和用户一起看懂。** 这也是很多人学完 React 后继续学 Next.js 的原因：不是为了炫技，而是为了把前端页面升级成可运营、可收录、可传播的站点。

这一章只讲能落地的部分：页面元信息怎么配、渲染策略怎么选、内容站和官网站到底该检查什么。我们不讲玄学，只讲上线前能直接照着做的动作。

---

## 一、SEO 到底在看什么：先把最基础的动作做对

### 1.1 标题、描述、结构、可抓取性

SEO 先不是研究“怎么涨排名”，而是先看搜索引擎能不能读懂你的页面。

最基础的几个点是：

- **title**：页面最核心的识别信息，决定搜索结果里用户先看到什么。
- **description**：页面摘要，主要影响点击率。
- **结构化信息**：标题层级、列表、正文、FAQ、面包屑等，让内容更容易被理解。
- **可抓取性**：页面内容能不能被稳定访问到，不依赖复杂脚本才看得见。

你可以把它理解成一句话：**页面要先像个正常网页，再谈优化。**

### 1.2 站点型项目为什么更在意这些

如果是纯后台系统，SEO 不是核心目标，能正常登录和操作就行。  
但如果你做的是：

- 公司官网
- 产品介绍页
- 知识库
- 博客 / 专栏
- 活动落地页
- 文档站

那搜索引擎就是重要流量入口。页面如果只有一堆 JS 才渲染出内容，或者标题描述都空着，搜索引擎就很难高效理解页面价值。

站点型项目和普通管理后台最大的区别，不是页面好不好看，而是**页面有没有传播属性**。一个页面如果会被搜索、会被分享、会被收藏，就不能只按内部系统的思路来做。你得从一开始就考虑：别人点开这个链接时，能不能快速知道这页在讲什么。

### 1.3 一个简单判断：页面是给谁看的？

赵老师给你一个很实用的判断：

- **内容本来就要被搜索和分享**：优先考虑 SEO
- **页面主要靠登录后使用**：SEO 优先级低
- **内容长期不变或变化慢**：适合做静态优化
- **内容实时变化强**：考虑服务端渲染或按需渲染

别把所有项目都当 SEO 项目做，复杂度会把自己拖死。  
如果你做的是内部系统，标题写得再漂亮，搜索引擎也不会给你带来多少价值；但如果你做的是面向公众的产品页，标题、描述、首屏内容，甚至 URL 结构，都会直接影响流量和转化。

---

## 二、页面元信息配置：title、description、OG、canonical 怎么配

### 2.1 title 和 description：最先要做的两件事

这是最基础，也最容易被忽略的。

#### title 的写法建议
一个好标题通常要包含：

- 页面主题
- 站点或品牌名
- 必要时加上场景词

例如：

- `Next.js 实战教程：从 React 页面到 SEO 站点 | 全栈老赵`
- `产品定价页 - XX 官网`
- `如何用 Next.js 做博客首页`

不要写成：

- `首页`
- `文章`
- `无标题`
- `Welcome`

标题的原则不是越长越好，而是越准确越好。它要让人一眼知道：这页是谁、讲什么、适合什么场景。

#### description 的写法建议
description 不是堆关键词，而是用一两句话告诉用户：

- 这个页面讲什么
- 能解决什么问题
- 有什么特点

比如：

> 本文讲解 Next.js 中 SEO 基础配置、title 与 description 的写法，以及静态生成和服务端渲染如何影响页面收录。

这种描述比“Next.js, SEO, React, 网站优化”有效得多。

你可以把 description 理解成“搜索结果里的广告语”，但这个广告语不能夸张，必须贴近正文内容。否则用户点进来发现不匹配，跳出率高，反而不利于站点长期表现。

### 2.2 OG 信息：让分享链接看起来更像样

OG（Open Graph）信息主要用于社交分享预览。  
你在微信、微博、Slack、X 等平台分享链接时，看到的标题、摘要、封面，很多都来自这部分配置。

常见字段包括：

- `og:title`
- `og:description`
- `og:image`
- `og:url`

如果你做官网站或内容站，OG 信息很值得配。因为用户不只在搜索引擎里见到你，很多流量来自转发、收藏和二次传播。

Next.js 的好处在于，你可以把这些元信息和内容自然绑定起来。比如文章详情页直接用文章标题、摘要、封面图生成 OG 信息；产品页则用产品名、简介和品牌图。这样一来，链接发出去的第一眼印象就比较完整。

### 2.3 canonical：避免重复页面抢权重

canonical 的作用很简单：告诉搜索引擎“这个页面的标准地址是哪一个”。

常见场景：

- 同一内容有多个 URL 版本
- 带参数的列表页
- 同内容的分页或筛选页
- http/https、www/非 www 的统一

如果不处理，搜索引擎可能把相似页面当成重复内容，分散权重。

比如一个文章页可能同时存在：

- `/post/nextjs-seo`
- `/post/nextjs-seo?ref=home`
- `/article/nextjs-seo`

你本来想让一个页面聚合权重，结果被拆散了。canonical 的意义，就是告诉搜索引擎：别分心，真正要算的是这一页。

### 2.4 这几个动作怎么排优先级

先记住一句话：**SEO 的元信息配置，不是为了讨好搜索引擎，而是为了让页面身份明确。**

建议优先级如下：

1. 每个页面都有唯一 title
2. 核心页面补 description
3. 需要分享的页面补 OG
4. 存在重复 URL 的页面补 canonical

如果这四步都没做好，谈别的 SEO 优化意义不大。

---

## 三、静态生成和服务端渲染：对 SEO 的影响到底有什么不同

### 3.1 静态生成（SSG）：内容稳定的页面优先用它

静态生成的核心思想是：**在构建时把页面提前生成好。**

适合：

- 博客文章
- 文档页
- 产品介绍页
- 落地页
- 不常变化的内容页

优点很直接：

- 首屏快
- 访问稳定
- 搜索引擎容易抓取
- 部署简单，成本低

如果页面内容变化不频繁，SSG 往往是 SEO 友好又省心的方案。尤其是内容站，文章和专题页通常是“写一次、改得少、传播久”。页面在构建时就已经把正文、标题、摘要、图片、链接准备好，搜索引擎来抓的时候，拿到的就是完整结果，不需要等太多脚本执行。

### 3.2 服务端渲染（SSR）：实时内容更适合它

服务端渲染的核心思想是：**每次请求时在服务端生成 HTML。**

适合：

- 首页内容经常变
- 搜索结果页
- 个性化内容页
- 依赖实时数据的页面

SSR 的好处是搜索引擎拿到的是完整 HTML，内容可直接读到。  
但它也有代价：服务端压力更大，响应链路更长，开发时要更注意缓存和性能。

比如首页每天都要展示最新活动、最新推荐、最新文章，这类页面就适合 SSR 或混合策略。因为如果全静态化，更新不及时；如果全靠客户端请求，首屏内容可能不完整，SEO 和体验都会受影响。

### 3.3 这两种方案怎么选，别只看“谁更高级”

很多人会问：是不是 SSR 就一定比 SSG 更利于 SEO？

不是这么简单。

从 SEO 角度看，重点不是哪种更高级，而是：

- 搜索引擎能否快速拿到主要内容
- 页面初始 HTML 是否完整
- 内容是否稳定
- 响应速度是否足够好

对大多数内容站和官网站来说，**SSG + 局部动态内容** 往往是很舒服的方案。  
对需要强时效的页面，SSR 更合适。  
Next.js 的价值就在于：你不用把全站绑死在一种渲染方式上，而是可以按页面选择策略。内容页静态化，数据页服务端化，登录后页面再做权限控制，整个站点会更灵活。

### 3.4 什么时候别急着上复杂渲染

如果你做的是一个简单的产品介绍页、活动页，内容不多、不实时变化，那就别一上来纠结各种高级渲染组合。

先把这几个点做对：

- 页面可访问
- title/description 完整
- 内容结构清晰
- 图片有 alt
- 首屏性能好

很多站点 SEO 其实不是输在“没用 SSR”，而是输在“页面自己都没写明白”。

赵老师常说一句话：**先把该有的 HTML 写好，再考虑渲染花活。**  
如果页面内容本身就很少、更新又不频繁，强行上复杂策略，只会增加心智负担，不一定带来收益。

---

## 四、内容站和官网站，上线前要检查什么

### 4.1 内容站的 SEO 检查清单

内容站最核心的目标是：**让文章被收录、被理解、被推荐。**

上线前先过一遍这些点：

- 每篇文章有独立 title 和 description
- 文章主标题唯一，通常用 H1
- 文章结构清楚，H2/H3 层级合理
- 正文内容原创且有信息密度
- 图片有 alt
- 有相关文章或目录导航
- 详情页有 canonical
- 列表页可分页、可抓取
- sitemap 可提交
- robots 配置合理

内容站最大的坑不是技术，而是内容一团乱。比如一篇文章没有层级，所有小标题都像平铺叙述，搜索引擎就很难判断重点。

你可以把内容页当成一篇“结构化说明书”来写：开头先告诉用户这篇讲什么，中间分层拆开，最后给结论和行动建议。这样用户看得舒服，搜索引擎也更容易理解。

### 4.2 官网站的 SEO 检查清单

官网站更看重品牌展示和转化。重点通常是：

- 首页 title 和 description 精准
- 产品页、功能页、方案页各自独立
- 每个核心页面都能说明“你是谁、你做什么、用户为什么要看你”
- 分享卡片统一而清晰
- 行动按钮明确
- 图片和首屏内容加载快

官网站不是文章站，它更强调“少而准”。页面不一定要长，但要让搜索引擎和用户第一眼就知道你在干什么。

官网最常见的问题有两个：标题太泛，内容太空。比如首页只写“欢迎来到我们的平台”，这就跟没写一样。官网页应该直接说明业务范围、核心价值和下一步动作，别让用户猜。

### 4.3 一个通用的上线前检查表

你可以按这个顺序过一遍：

1. 是否有唯一 title？
2. description 是否准确概括内容？
3. 页面是否有清晰 H1？
4. 正文是否能直接读取？
5. 图片是否有 alt？
6. 是否需要 canonical？
7. 是否有 OG 信息？
8. 页面是否足够快？
9. 是否有内部链接帮助跳转？
10. URL 是否简洁、可读？

再补一条：页面是否真的回答了用户的问题。因为 SEO 的底层逻辑不是“页面像 SEO”，而是“内容真的有价值”。

---

## 五、经验建议：把 SEO 当站点工程，不要当关键词填空题

### 5.1 不要把 SEO 做成关键词重复

以前有些人做 SEO，喜欢在页面里反复塞同一个词。结果搜索引擎未必喜欢，用户一定不喜欢。

正确做法是：

- 页面主题明确
- 标题自然
- 正文回答用户真实问题
- 结构清楚
- 语义完整

你写的是“讲清楚问题”，不是“重复一个词”。

搜索引擎现在更重视上下文和语义，不是看你把某个词重复了多少遍，而是看整篇内容是否围绕一个主题展开，信息是否完整，是否能帮助用户快速找到答案。

### 5.2 内容、结构、技术三者要一起看

SEO 不只是前端配个 meta 标签，它其实是三件事一起作用：

- **内容**：你写了什么，是否有价值
- **结构**：标题层级、列表、段落是否清楚
- **技术**：是否能抓取、是否快、是否有正确元信息

Next.js 的优势在于，它能把这三件事更自然地结合起来。你可以用组件化方式管理页面，同时又能在服务端或构建期把最关键的内容直接输出给搜索引擎。

这也是为什么很多内容站和官网站从纯 React 迁到 Next.js 后，页面维护反而更轻松了。不是因为 Next.js 魔法多，而是因为它把“页面如何展示”和“页面如何被理解”放在了一起考虑。

### 5.3 什么时候适合用 Next.js 做 SEO 站点

适合上 Next.js 的典型情况：

- 你要做内容站、博客、官网、文档站
- 页面需要被搜索引擎收录
- 你希望每个页面都有独立元信息
- 你需要静态生成和服务端渲染的灵活切换
- 后面还可能接接口、登录、简单权限

什么时候先别急：

- 只是做纯后台系统
- 页面只给登录用户看，不靠搜索流量
- 项目规模很小，短期内不需要站点化能力
- 团队还没准备好处理渲染、部署和数据获取的复杂度

赵老师的建议很直接：**能用普通 React 解决的小项目，就先别把 Next.js 当必选项。**  
但只要你开始面对“要被收录、要被分享、要有站点感”的需求，Next.js 的价值就会明显起来。

## 本章小结：SEO 不是玄学，是让页面更像一个好站点

这一章我们要记住的不是某个 meta 字段，而是一个完整思路：

- SEO 的本质，是让页面可读、可抓取、可理解
- title、description、OG、canonical 是基础配置
- SSG 和 SSR 会影响页面抓取方式和加载表现
- 内容站和官网站要分别看重点
- SEO 不是堆关键词，而是把内容、结构和技术做扎实

### 行动建议

如果你现在手上有一个 Next.js 项目，建议立刻做这 5 件事：

1. 给每个核心页面补上独立 title 和 description  
2. 给需要分享的页面加 OG 信息  
3. 检查是否存在重复 URL，必要时加 canonical  
4. 把内容页的标题层级理顺，至少做到 H1 + H2 结构清晰  
5. 重新判断页面该用 SSG 还是 SSR，不要一把梭全站同一种方式  

SEO 这件事，越早做越省事。  
等站点做大了再补，通常都是返工式优化。  
而 Next.js 的优势，就是让你从一开始就能把“页面开发”往“站点开发”上带。

# 第9章：图片优化、静态资源与站点体验提升

做 Next.js 站点，很多人前面把页面、接口、SEO 都搞定了，最后才发现：**站点不慢，但就是不够顺。** 首屏等得久、图片一张张跳出来、封面先糊后清、字体加载时页面抖一下，这些问题单看不大，放在一起就很影响体验。

这一章专讲一件很实在的事：**怎么把图片、静态资源、字体和封面图处理好，让站点更专业、更顺滑。** Next.js 的价值不只是“能做页面”，它还把很多站点级优化能力直接放进了框架里，让你少造很多轮子。

---

## 一、为什么图片优化在站点里特别重要？

先说结论：**图片通常是站点里最容易拖慢体验的资源之一。**

尤其是内容站、官网站、博客、产品页，这类站点往往有几个特点：

1. 首页和列表页图片多；
2. 封面图、Banner 图、产品图占比大；
3. 用户先看图，再看字；
4. 图片没加载好，页面就显得“空”“卡”“跳”。

### 1.1 体积大，直接影响加载速度

很多前端同学习惯直接把图片丢进页面，能显示就行。问题是，一张原图可能几 MB，网络稍慢，首屏就被拖住了。站点体验不是“能不能显示”，而是“**多久能让用户看到关键内容**”。

比如文章站首页第一屏有标题、摘要、封面图，结果封面图体积过大，文字先出来，图半天不显示，用户就会觉得页面卡住了。更糟的是，图一补上来，版面还会被顶开，阅读节奏直接乱掉。

### 1.2 首屏不稳，用户会觉得站点不专业

如果图片尺寸不固定，加载完成前布局会抖动，文字位置、卡片高度都会变。内容站里这类问题特别常见：一开始整整齐齐，图片一加载，整个页面上下蹦。

所以图片优化不只是为了快，还为了稳。你要让浏览器尽量提前知道图片占多少空间，别让它边加载边挪位置。对用户来说，稳定的页面比“看起来很炫但一直抖”舒服得多。

### 1.3 图片不是单独的问题，而是页面链路的一部分

很多人以为性能优化就是“把图片压小点”，其实不是。图片慢，往往还伴随着：

- CSS 和字体加载顺序不合理；
- 首屏渲染依赖太多客户端请求；
- 图片懒加载策略不当；
- 大图被误用在小图位置；
- 页面整体资源没有分级。

也就是说，你不能只盯着某一张图，而要看整条链路。一个站点顺不顺，关键在于**先让用户看到最重要的东西**，而不是“所有东西都准备好了再一起出现”。

**实用建议：**  
如果你做的是官网、内容站、SEO 站点，图片优化要提前考虑。  
**何时适合重点做图片优化？** 当页面以图文内容为主、首屏依赖视觉呈现、移动端访问占比较高时。  
**何时先别过度复杂？** 如果是内部管理后台、纯表单系统、图片极少，就不必一上来做很重的图片处理方案。

---

## 二、图片组件与常见优化策略，怎么用才靠谱？

Next.js 的一个实用点，就是它把图片处理做得比较体系化。你不用再把“图片显示”和“图片优化”完全拆开。

### 2.1 先管尺寸，不要让图片“裸奔”

最常见的错误是：图片直接塞进页面，不指定合适尺寸，或者图片分辨率远大于展示区域。

正确思路是：

- 先看图片在页面里的实际展示尺寸；
- 再决定传什么分辨率的资源；
- 避免拿 2000px 宽的大图硬塞给 300px 的卡片封面。

核心不是“图片越小越好”，而是**资源要匹配使用场景**。列表页里的封面图只是缩略图，就不必加载详情页那种大图规格；详情页里如果用户要认真看图，再提供更高质量的资源才合理。

### 2.2 懒加载要用在合适的位置

懒加载适合首屏之外的图片，比如：

- 文章正文中的后续图片；
- 列表页下方的更多内容；
- 长页面里的补充图。

但不要把首屏主视觉也懒加载得太狠。  
如果首屏 Banner、站点封面图、关键产品图都延迟明显，用户会觉得页面空。

判断很简单：

- **首屏关键视觉**：尽量优先加载；
- **非首屏内容**：可以懒加载；
- **纯装饰图**：更适合延后。

### 2.3 格式选择不是越新越好

图片格式要看内容类型：

- 照片类图片：控制压缩和清晰度；
- 简单图标：更适合矢量图形；
- 透明背景图：注意格式支持和压缩效果；
- 大面积封面图：控制体积和宽高比。

别一味追新格式。站点目标不是“技术看起来先进”，而是**打开更快、看起来更稳**。很多时候，合适的压缩、裁剪和宽高比，比换一种更高级的格式更有价值。

### 2.4 封面图要特别小心

封面图是内容站和官网站最常见的性能刺客。原因很简单：它出现频率高，而且常常被当成视觉重点，结果就用上了过大的原图。

建议记住三点：

1. 封面图优先做裁剪和压缩；
2. 列表页封面图和详情页大图不要混用同一份超大资源；
3. 保证宽高比稳定，避免布局跳动。

封面图可以理解成“内容的门牌”。门牌清楚、统一、加载快，用户才愿意继续往下看。  
如果封面尺寸乱、加载慢、比例不一致，站点就会显得很散。

**实用建议：**  
先列出“首屏必须显示的图片”和“首屏后才显示的图片”，分开处理。  
**何时适合强调图片优化？** 列表页、文章详情页、首页 Banner、多图展示页。  
**何时别过度折腾？** 图片少、只是辅助展示时，先把布局、文案和加载顺序做好，收益更大。

---

## 三、静态资源怎么管理，才不乱？

站点做大以后，资源会越来越多：logo、图标、封面图、默认头像、背景图、字体文件……没有一套清晰方式，很快就会变成“图片仓库”。

### 3.1 公共资源和内容资源要分开管

常见资源通常可以分成两类：

- **固定公共资源**：logo、favicon、默认头像、站点品牌图；
- **页面内容资源**：文章封面、活动海报、产品展示图。

前者适合统一位置管理，方便全站引用；后者适合按业务场景组织，避免混乱。  
这样做的好处是，品牌图换一次，全站一起生效；文章封面更新，也不会影响别的模块。

### 3.2 引用方式要统一，别到处写死路径

静态资源引用不要到处写死路径。建议至少做到：

- 同类资源放在同一目录；
- 命名有规则；
- 页面中引用方式一致；
- 不要出现“这张图只在某个组件里能找到”的情况。

你今天在首页用了一个 logo，明天在文章页又手工写了另一种引用方式，后面一改目录，半个站点都可能出问题。统一管理不是为了好看，而是为了降低维护成本。

### 3.3 目录别太乱，也别分得太细

资源管理要讲平衡：

- 太集中：目录混乱，找图困难；
- 太分散：重复资源多，维护成本高。

比较实用的做法是按用途分层，例如：

- `common`：站点级公共图；
- `home`：首页资源；
- `article`：文章相关图片；
- `icon`：图标类资源。

如果是团队协作，再继续细分，但前提是别把目录搞成迷宫。资源管理最重要的原则不是“分得越细越专业”，而是**后面的人能不能快速找到、替换和复用**。

**实用建议：**  
项目小，先把目录分清楚；多人协作，尽快建立命名规则和资源分类规范。  
**何时适合做严格管理？** 当你开始有多个页面、多个作者、多个图源时。  
**何时不必过度设计？** 小型 Demo 或一次性活动页，不需要先搞一套“企业级资源中心”。

---

## 四、字体、图标、封面图，这三类资源怎么处理更合理？

这三类资源看着普通，其实最容易影响“高级感”和“体验感”。

### 4.1 字体：别为了好看，把加载搞崩

很多站点喜欢自定义字体，但字体文件太大，页面就容易出现：

- 首屏文字延迟；
- 字体切换闪动；
- 页面布局轻微抖动。

建议：

1. 只选必要的字重；
2. 不要一次引入太多款；
3. 中文站点尤其要控制体积；
4. 如果只是普通内容页，系统默认字体先用着就行。

记住一个经验：**字体是加分项，不是基础项。**  
如果站点的核心目标是让用户快速读内容、快速搜到内容，那么字体优先级一定低于首屏加载速度和正文可读性。

### 4.2 图标：优先考虑轻量和统一

图标最怕两件事：格式乱，风格乱。  
比如导航栏一个风格，按钮又一个风格，列表图标再一个风格，整个站点会显得不专业。

建议：

- 图标尽量统一来源；
- 用轻量方式管理；
- 尺寸和线条风格保持一致；
- 少量图标不用搞得太复杂。

如果页面只有几个常用图标，统一处理就够了。不要为了少量图标引入一堆复杂方案，那是典型的“为了优化而优化”。

### 4.3 封面图：既要好看，也要稳

封面图在内容站里很关键，既是点击入口，也是站点门面。  
处理封面图时，最重要的不是“最大化清晰度”，而是：

- 展示区域匹配；
- 宽高比稳定；
- 压缩合理；
- 对列表和详情页分别优化。

封面图可以理解成“内容的门牌”。门牌清楚、统一、加载快，用户才愿意继续往下看。  
如果列表页和详情页共用一套超大封面图，短期看省事，长期看就是把性能压力全压在用户网络上。

**实用建议：**  
先从“用户能马上看到什么”出发，再决定资源规格。  
**何时适合自定义字体和复杂图标系统？** 品牌站、官网站、面向外部用户的产品站。  
**何时先别折腾？** 个人博客、小型内容站、原型验证阶段，先把性能和内容组织做好更划算。

---

## 五、性能优化别只盯着图片，还要看整个加载链路

这一点很关键。很多人优化图片后，发现页面还是慢，就开始怀疑是不是 Next.js 不够快。其实大多数时候，问题不在图片本身，而在整个链路。

### 5.1 先看首屏有没有“多余等待”

检查一下：

- 首屏是不是加载了太多非关键资源；
- 首屏是不是依赖过多客户端请求；
- 页面是不是先渲染壳子，再慢慢补内容；
- 是否有某些资源阻塞了关键内容显示。

很多“慢”的站点，不是单个资源太大，而是首屏要等太多东西。  
用户其实不在乎内部怎么分层，他只关心：打开以后，能不能马上看到标题、正文和关键图片。

### 5.2 先决定“先显示什么”

一个站点是否体验好，核心在于：**用户打开后，第一眼先看到什么。**

你至少要保证：

1. 先出标题和核心文案；
2. 再出关键图片；
3. 最后补充次要内容。

不要把所有视觉元素都当成“必须同步完成”。那样首屏会很重。  
内容站先让文字可读；官网站先让主视觉和核心卖点出现；产品页先让用户知道这是什么，再补充细节。

### 5.3 优化要做组合拳

真正有效的优化通常是组合出来的：

- 图片做压缩和尺寸匹配；
- 首屏资源优先加载；
- 非首屏资源延后；
- 字体和图标轻量化；
- 页面结构清晰，不要层层套娃。

**常见误区：**

- 以为压缩了图片就万事大吉；
- 以为某个组件慢，只需要换一张更小的图；
- 以为“页面白屏”都是图片造成的。

站点优化不是只改一个点，而是把**内容、图片、字体、结构、加载顺序**一起看。你把这些串起来，页面不一定花哨，但会很专业。

**实用建议：**  
可以把性能优化拆成三问：

1. 用户最先要看到什么？
2. 这些内容是不是被别的资源挡住了？
3. 有没有不必要的资源在首屏抢队列？

**何时适合做系统性优化？** 当站点内容多、用户访问量上来、移动端占比高时，收益会很明显。  
**何时不必一开始就重优化？** 如果还在做功能验证，先把业务闭环做通，不要为了优化拖慢开发节奏。

---

## 六、站点体验优化 Checklist

这一小节给你一个能直接照着做的清单。做站点时，别总停留在“感觉好像优化了”，要能落到检查动作上。

### 6.1 图片检查

- 首屏图片是否过大；
- 列表页封面是否统一尺寸；
- 详情页大图是否和缩略图共用同一份原图；
- 非首屏图片是否合理懒加载；
- 图片是否有稳定宽高比，避免布局抖动。

### 6.2 静态资源检查

- logo、favicon、默认头像是否统一管理；
- 图片、图标、背景图是否按用途分目录；
- 引用路径是否统一；
- 是否存在重复资源和临时散图。

### 6.3 字体与图标检查

- 字体是否引入过多字重；
- 是否在普通内容页过度追求自定义字体；
- 图标风格是否统一；
- 是否为了几个图标引入过重方案。

### 6.4 页面链路检查

- 首屏是否被非关键资源拖慢；
- 关键内容是否先出现；
- 是否先白屏再补内容；
- 页面结构是否清晰，避免资源互相抢占。

这个清单不复杂，但很实用。你每做完一个页面，就按这几条过一遍，基本能抓住八九成常见问题。

---

## 本章小结：别只压图片，要把体验当成一条链路来做

这一章讲的不是“把图片压到极致”，而是建立一个更靠谱的站点优化思路：

- 图片影响首屏、加载速度和页面稳定性；
- Next.js 的图片与资源处理能力，适合做站点级优化；
- 静态资源要分层管理，别让项目变成图片堆；
- 字体、图标、封面图都要兼顾美观和性能；
- 性能优化不是单点动作，而是整个加载链路的协调。

最后给你一个很实用的判断：

**如果你的站点是内容站、官网站、SEO 站点，图片和静态资源优化值得尽早做。**  
**如果你只是做后台、工具页、内部系统，先把功能和数据流跑顺，不必过早引入复杂的资源优化策略。**

下一章，我们会继续往前走，进入 **API Routes、接口能力和简单登录权限**，把这个站点从“会展示”推进到“能交互、能管理”的阶段。

# 第10章：API Routes 与站点接口能力

## 开篇引入：为什么做站点，最后还是绕不开接口

很多同学学 React 时，习惯了“页面归页面，接口归接口”：前端管展示，后端管数据，两个仓库、两套部署、两边联调。这样当然没问题，成熟团队里也很常见。  
但一旦你开始做内容站、官网站、活动页、轻量后台，就会碰到一个现实问题：**每个小需求都值得单独起一个后端项目吗？**

比如联系表单、文章列表、首页推荐位、简单登录校验，这些东西如果都要单独拆后端，项目很快就会变重。  
这就是 Next.js 的优势：它不只负责渲染页面，还能在同一个项目里提供接口能力，让一些轻量业务逻辑、表单提交、内容查询、简单聚合直接在站点内完成。

但老赵提醒你：**能提供接口，不代表什么都该塞进去。**  
这一章就讲清楚：API Routes 能干什么、适合什么、怎么用、什么时候别硬上。

---

## 一、API Routes 是什么，适合做什么？

在这里，API Routes 指的是：**在 Next.js 项目内部定义接口，由这个项目直接对外提供 HTTP 能力**。你可以把它理解成站点自带的小后端，目标不是大而全，而是够用、直接、好维护。

### 1. 它解决什么问题？

API Routes 很适合这些场景：

- 表单提交：留言、报名、反馈
- 内容读取：文章列表、分类数据、配置数据
- 简单聚合：合并多个来源的数据后返回
- 轻量业务逻辑：参数校验、摘要生成、基础权限判断
- 站点内部统一数据出口

核心价值不是“技术上能不能做”，而是**减少站点型项目的复杂度**：

- 页面和接口在同一个仓库里，修改更同步
- 数据结构更容易统一
- 部署只需要一个应用
- 对个人开发者和小团队很友好

### 2. 它不适合什么？

也要看清边界：

- 复杂业务系统，权限链路很长
- 大量数据库读写
- 需要独立扩容的服务
- 多端复用的统一后端
- 已有成熟微服务体系的企业项目

如果你本来就有独立后端，Next.js 只是前端壳子，那就别为了“全栈感”硬把核心业务搬进去。**API Routes 不是重造后端，而是让轻量站点少依赖一个后端项目。**

### 实用建议

做官网、内容站、落地页、轻量管理台时，优先考虑 Next.js 内置接口通常是合理的。  
如果是电商中台、复杂 CMS、多角色审批系统、高并发业务接口，那就别贪图方便，独立后端更稳。

---

## 二、API Routes 怎么用：基本方式与最小思路

### 1. 基本使用方式

API Routes 的核心就一句话：**定义一个接口文件，接收请求，处理逻辑，返回结果**。把它当普通 HTTP 接口就行：

1. 前端发起请求  
2. 服务端读取参数  
3. 校验并处理业务  
4. 返回 JSON 数据  

常见返回形式可以统一成：

- 成功：`{ code: 0, data: ... }`
- 失败：`{ code: 1, message: 'xxx' }`

站点型项目里，别把事情搞复杂，**统一格式、可读、好调试**最重要。

### 2. 一个典型流程

比如留言表单：

- 用户填写姓名、邮箱、留言内容
- 前端提交到 `/api/contact`
- 接口校验字段是否为空
- 通过后写入数据库、发邮件或先落日志
- 返回提交成功

这类逻辑短、链路短、耦合低，非常适合放在 API Routes 里。

再比如文章列表接口：

- 前端请求 `/api/posts`
- 后端读取内容源
- 做分页、筛选、排序
- 返回前端直接渲染

这种场景如果单独起后端，很多时候就是“为了接口而接口”。

### 3. 常见误区

很多人会犯两个错：

- 把所有逻辑都写进接口，结果接口越来越胖
- 把接口当成页面数据的万能入口，所有数据都先走一遍 API，反而多绕一圈

要记住：如果页面可以直接在服务端拿到数据，不一定非要先请求自己的 API。  
有些场景直接在页面层做数据获取更自然，API Routes 更适合作为“对外能力”和“复用入口”。

### 4. 最小可执行思路

写接口时，先问这五个问题：

- 输入是什么？
- 必填项有哪些？
- 错误时怎么返回？
- 成功时返回什么结构？
- 前端拿到以后怎么用？

只要这五件事清楚，接口就不会乱。

### 实用建议

先从最简单的三个接口练起：

- 一个表单提交接口
- 一个内容列表接口
- 一个详情查询接口

别一上来设计十几个接口，最后自己都记不住。站点开发讲究的是“够用且清晰”。

---

## 三、前后端同仓开发的优势：为什么少一个项目真的省事？

### 1. 少一个项目，少很多沟通成本

传统前后端分离没问题，但小型站点里常常有这些烦恼：

- 前端等后端接口
- 后端等前端字段确认
- 联调时字段名不一致
- 部署时两个项目分别处理
- 跨域、环境变量、域名配置层层增加

Next.js 的 API Routes 把这件事简化了：**页面和接口在同一个仓库里，需求改动更容易同步。**

### 2. 同仓开发的实际好处

#### 第一，开发速度快
改页面时顺手改接口，不需要来回切项目。比如表单字段从“手机号”改成“邮箱”，页面和接口可以一起改，效率很高。

#### 第二，接口和页面天然一致
字段定义、错误提示、数据展示都在一个代码库里维护，沟通成本低。对官网、活动页、内容站这种本来就不复杂的项目，没必要拆得太碎。

#### 第三，部署简单
很多站点最终只需要部署一个应用。少一套服务，也就少一套监控、日志和发布流程。

#### 第四，适合个人和小团队
一个人做项目时，最怕的是“看着像全栈，实际上在维护两个半吊子系统”。Next.js 同仓开发很适合先把业务跑起来。

### 3. 但同仓不是无成本

同仓开发虽然方便，也要守住边界：

- 代码分层要清楚
- 前端和接口逻辑要分开
- 公共逻辑单独抽出来
- 不要因为“都在一个项目”就乱写

正确姿势是：**页面归页面，接口归接口。**

### 实用建议

个人开发者、内容创作者、独立站点开发者，用 Next.js 同仓开发很值。  
如果是中大型团队，后端已有成熟规范，那就把 Next.js 当成前端层和少量 BFF 层，不要把它当成全部后端。

---

## 四、常见接口场景：哪些业务最适合放进 Next.js？

### 1. 表单提交：最典型也最常见

站点项目里最常见的接口就是表单，比如：

- 联系我们
- 用户反馈
- 加入内测
- 预约报名
- 下载资料申请

这类接口的特点是：

- 结构简单
- 交互明确
- 成功失败容易表达
- 不需要特别复杂的后端体系

重点不在功能多强，而在：

- 字段校验是否完整
- 重复提交如何处理
- 错误提示是否明确
- 是否要加基础防刷

哪怕只是留言表单，也要考虑姓名为空、邮箱格式不对、内容太短这些边界条件，接口层要做一次兜底，不能只靠前端限制。

### 2. 内容查询：站点里经常用

内容站、官网站常常需要：

- 文章列表
- 分类列表
- Banner 配置
- 页面元数据
- 推荐内容

如果这些数据来自 CMS、数据库或外部服务，Next.js 可以做一层轻量查询聚合。好处是前端不用关心多个来源，统一从你的站点接口拿结果。

### 3. 简单聚合：把零散数据整理好再给前端

很多站点页面不是“一个接口返回一个完整页面”，而是要把多个数据源拼起来。  
这时候 API Routes 很合适，因为它可以在服务端先做整理。

比如：

- 读取文章列表
- 读取分类列表
- 读取推荐配置
- 合并成首页需要的数据结构

这样前端就不用写一堆拼装逻辑。对内容站来说，这种“统一出口”很实用。

### 4. 轻量业务逻辑：别小看这些小功能

比如：

- 计算文章摘要
- 根据参数生成标签
- 按条件过滤内容
- 读取配置后返回页面

这些逻辑放在接口里很自然，也容易维护。像“把 Markdown 内容转成摘要”这种能力，完全没必要拆成单独服务。

### 实用建议

判断一个场景适不适合放到 Next.js，问自己三个问题：

1. 这个功能是否轻量？  
2. 是否和站点页面强相关？  
3. 是否需要独立后端能力？  

如果前两个答案是“是”，大概率适合。  
如果已经涉及复杂权限、支付、订单、长期任务，那就该停一停了。

---

## 五、接口设计与前端调用：怎么写才不乱？

### 1. 接口设计先统一，再开发

一个站点项目最怕接口风格乱。建议提前统一：

- URL 命名风格
- 返回格式
- 成功失败编码
- 错误信息字段
- 分页参数命名

比如统一成：

- `GET /api/posts`
- `GET /api/posts?id=xxx`
- `POST /api/contact`

返回格式统一成：

- `code`
- `message`
- `data`

这样前端调用时就不会到处猜。

### 2. 前端调用时注意什么？

前端调用接口，别只想着“能拿到数据就行”。至少注意这几点：

#### 参数校验
请求前先检查必填项，别把明显错误的请求发出去。

#### 异常处理
网络失败、超时、返回错误，都要给用户明确提示，不要点了提交像没反应一样。

#### 加载状态
提交表单、加载列表时，要有 loading 反馈。这不是细节，这是体验。

#### 数据结构稳定
接口一旦对外，就尽量保持字段稳定。今天叫 `title`，明天叫 `name`，前端就会很难受。

### 3. 基本注意事项清单

做站点接口时，老赵建议你记住这份清单：

- 先定接口边界，再写代码
- 参数在服务端再校验一次
- 返回值尽量统一
- 错误信息要能看懂
- 别把敏感信息直接回传给前端
- 接口失败时，前端一定要有兜底提示
- 别依赖“用户一定会按正确方式操作”

### 4. 常见误区

- 接口只顾返回成功，不管失败怎么提示
- 前端直接假设接口一定成功
- 返回结构每个接口都不一样
- 页面和接口耦合过深，后期很难改

这些坑，项目小的时候不明显，项目一多就会很难受。  
所以站点开发不要追求“花样多”，要追求“统一”和“稳定”。

### 实用建议

接口设计越简单越好，但一定要统一。  
对站点型项目来说，**一致性比花哨更重要**。你不是在设计一个炫技平台，而是在做一个能长期维护的站点。

---

## 六、使用建议：什么时候该用 Next.js，什么时候先别上复杂度？

这部分很关键。老赵最怕大家形成一个误解：**“Next.js 很强，所以所有项目都要上。”** 不对。

### 1. 适合用 Next.js 的情况

- 要做内容站、官网站、SEO 站点
- 希望页面和接口放在一起
- 要快速做出能上线的完整站点
- 需要 SSR、SSG、接口、SEO 配合
- 是个人开发者或小团队，希望减少协作成本

### 2. 暂时别上复杂度的情况

- 只是一个纯前端展示页，没什么数据交互
- 后端系统已经很成熟，你只负责前端消费
- 业务复杂到需要独立后端架构
- 团队已经有明确的前后端分工和接口规范
- 当前目标只是练组件、练交互，不是做完整站点

### 3. 一个很实在的判断法

你可以问自己：

- 这个项目是否需要 SEO？
- 是否需要服务端渲染或静态生成？
- 是否需要轻量接口能力？
- 是否希望部署更简单？
- 是否希望前端和接口统一管理？

如果这些答案大多是“是”，Next.js 值得上。  
如果只是“想试试”“听说很火”，那就先别急。工具的价值在于解决问题，不在于显得先进。

### 4. 老赵的经验判断

很多人做项目时，一上来就想把架构搞得很完整，结果还没开始写页面，先把接口、登录、权限、数据库、缓存全想一遍。  
这种做法的风险就是：**复杂度先上来了，产品却还没跑起来。**

更稳的路线是：

1. 先把页面和内容结构搭好  
2. 再判断哪些数据必须服务端处理  
3. 再决定是否使用 Next.js 的接口能力  
4. 最后才考虑登录、权限、缓存这些增强项  

这样你会更接近真实项目的节奏。

### 实用建议

**先解决问题，再选择框架复杂度。**  
做站点时，最稳的路线通常是：

1. 先明确页面和内容结构  
2. 再判断是否需要 SEO  
3. 再决定是否使用 Next.js 的服务端能力  
4. 最后才考虑接口是否内置  

这个顺序很重要，别反过来。

---

## 结尾小结：把 Next.js 的接口能力用在刀刃上

这一章你要记住的核心就三句话：

1. **Next.js 不只是页面框架，它还能提供站点接口能力。**  
2. **API Routes 很适合轻量表单、内容查询和简单聚合。**  
3. **复杂后端别硬塞进 Next.js，合适的复杂度才是好架构。**

对于内容站、官网站、SEO 站点来说，API Routes 的价值不是替代一切后端，而是让你在一个项目里更快完成页面、数据和接口的闭环。你少搭一个项目，少处理一层跨域和部署，很多事情就顺手了。

但老赵还是那句话：**工具是为业务服务的，不是为了显得全栈而全栈。**  
简单场景用 Next.js 的接口能力，复杂系统就老老实实拆分。这样你写出来的站点，才会既快，又稳，还能维护。

# 第11章：登录、简单权限与内容管理基础

## 开篇引入：为什么站点做到这一步，就该谈登录和权限了？

前面我们已经把 Next.js 的页面、路由、数据获取、SEO、图片优化这些能力搭起来了。到了这里，很多站点都会碰到一个现实问题：**内容不再只是“给所有人看”，而是要区分谁能看、谁能改、谁能发、谁能管理**。

这就是登录和权限的价值。

如果你做的是内容站、官网后台、知识库、活动站，或者轻量 CMS，前面那些能力解决的是“站点能不能跑起来”，这一章解决的是“站点能不能真正用起来”。不过老赵先提醒一句：**权限系统不是越复杂越好**。很多项目一上来就想做 OAuth、SSO、RBAC、细粒度策略，结果网站还没上线，认证系统先把自己绕晕了。对大多数 Next.js 站点来说，先做一个够用的登录和基础权限，往往就能解决 80% 的问题。

这一章我们按实战思路来：先搞清楚登录怎么做，再搞清楚谁能访问什么，最后把内容发布和编辑的基础流程串起来。

---

## 一、登录功能的基本思路：会话、Cookie、Token 到底怎么选？

### 1. 先回答“登录状态怎么保存”

登录的本质很简单：用户验证成功后，系统要记住“这个人是谁”。  
在 Web 里，常见思路主要有三种：

- **会话（Session）**
- **Cookie 保存标识**
- **Token（常见是 JWT）**

没有绝对优劣，关键看你的站点需要什么。

### 2. 会话（Session）：适合服务端控制强的场景

会话的思路是：用户登录后，服务端保存登录状态，浏览器只拿一个会话标识。

**优点：**
- 服务端可随时注销、踢人、失效控制
- 权限变更更容易立即生效
- 做后台管理、内容审核比较顺手

**缺点：**
- 服务端要保存状态，部署和扩展时要考虑存储
- 多实例环境下要共享会话或统一方案

**适合：**
- 内容管理后台
- 管理员登录
- 以服务端控制为主的站点

如果你做的是小型内容站，登录人数不多，管理功能比较明确，session 往往比你想象中更稳。别一上来就觉得“JWT 更现代，所以更适合”，这个思路不对。**认证方案不是看流行不流行，而是看你后面维护起来累不累。**

### 3. Cookie：不是登录方案本身，而是承载状态的常用方式

很多人会把 Cookie 当成登录方案，其实更准确地说，**Cookie 是保存状态的容器**。  
你可以把 session id 放进 Cookie，也可以把 token 放进 Cookie。

在 Next.js 里，Cookie 很常见，因为：

- 服务端渲染时可以直接读 Cookie
- 中间件可以做访问拦截
- 页面请求接口时浏览器会自动带上 Cookie

**实战建议：**
- 如果你想让 SSR 页面首屏就知道当前用户是谁，Cookie 很方便
- 如果是管理后台，Cookie + 服务端校验通常够用
- 重要信息别直接明文塞进 Cookie，至少要用服务端可识别、可失效的标识

你可以把 Cookie 理解成“门禁卡”，真正决定你能不能进门的，还是服务端那套校验逻辑。

### 4. Token：适合前后端分离意识更强的场景，但别神化

Token 常见于 JWT 方案，用户登录后拿到 token，之后每次请求带上它。

**优点：**
- 客户端和接口调用比较直接
- 适合移动端、多客户端统一认证

**缺点：**
- 失效控制不够自然
- 管理不好时，安全性容易出问题
- 某些场景下比 session 更麻烦

**老赵建议：**
对于大多数 Next.js 站点，尤其是内容站和轻量后台，**优先考虑“Cookie 承载会话”或“Cookie 承载受控 token”**。不要一上来就把认证系统设计成分布式大工程。你现在需要的是“能稳定用”，不是“看起来很高级”。

### 5. 一个实战判断：你到底需不需要独立登录系统？

如果你的站点只是：

- 公开内容阅读
- 少量后台编辑
- 管理员自己操作

那完全可以先用简单登录方案。  
如果你需要：

- 多端统一登录
- 第三方账号接入
- 企业级单点登录

那再考虑更完整的认证体系。**不要一开始就把简单网站做成统一身份中心。**

---

## 二、简单权限控制：游客、登录用户、管理员到底怎么区分？

### 1. 先把最常见的三层分清楚

对于大多数站点，权限分层其实可以很朴素：

- **游客**：没登录的人
- **登录用户**：已验证身份，但没有管理能力
- **管理员**：能发布、编辑、删除内容，或管理其他用户

这三层已经能覆盖很多业务了。

### 2. 三层权限的访问差异怎么设计？

从“页面”和“操作”两个维度看最清楚。

#### 游客能做什么
- 浏览公开内容
- 搜索内容
- 查看详情页
- 看到登录入口

#### 登录用户能做什么
- 查看个人信息
- 收藏、评论、提交表单
- 访问需要身份的页面
- 修改自己允许修改的内容

#### 管理员能做什么
- 进入内容管理后台
- 新建、编辑、删除内容
- 审核用户提交
- 管理分类、标签、权限

### 3. 权限控制不是“把按钮藏起来”就完了

很多初学者会误解：前端把删除按钮隐藏掉，不就算权限控制了吗？

不算。

**前端隐藏只是展示控制，真正的权限控制必须在服务端完成。**  
因为任何人都可以绕过前端直接请求接口。  
所以正确做法是：

- 前端：控制用户看到什么
- 服务端：控制用户能不能真正执行

如果你只是把按钮藏了，接口却没拦住，那权限系统等于没做。

### 4. 常见误区

- 把“登录”和“管理员”混为一谈：登录了不代表有管理权限
- 所有页面都做成登录后才能看：内容站很多内容应该公开，别为了“安全”牺牲访问体验和 SEO
- 权限只在页面层判断：接口层不校验，迟早出问题

### 5. 一个简单但好用的判断标准

你可以问自己一句：**这个动作是不是会影响数据、内容，或者其他用户的体验？**

如果会，就必须加权限判断。  
如果只是普通浏览，尽量保持开放。  
这也是做站点时很重要的取舍：**不是所有东西都要锁起来，公开内容的可访问性本身就是产品的一部分。**

---

## 三、内容发布、编辑、查看的基础权限设计：内容系统最核心的规则是什么？

### 1. 内容管理不难，难的是把“谁能对什么做什么”讲清楚

如果你的站点有文章、产品、案例、活动页等内容，那么最基础的权限模型一般就是：

- **查看**：公开内容谁都能看
- **编辑**：只有作者或管理员能改
- **发布**：管理员或审核通过的人才能发
- **删除/下线**：通常只有管理员能做

这几个动作一旦定清楚，系统就不会乱。

### 2. 推荐一个够用的内容权限模型

可以先按下面这个模型做：

- 内容状态：`草稿`、`已发布`、`已下线`
- 内容归属：`作者ID`
- 操作权限：
  - 游客：只能看 `已发布`
  - 登录用户：可看自己草稿，或参与提交
  - 作者：可编辑自己创建的内容
  - 管理员：可编辑所有内容、审核发布、下线内容

这个模型简单、清晰，也很适合 Next.js 站点做第一版。

### 3. 为什么要先做“基础版”？

因为内容系统的复杂度会随着业务慢慢长出来。  
一开始就做：

- 多角色多权限矩阵
- 资源级授权
- 审批流
- 操作审计
- 多租户隔离

这些不是不能做，而是**没必要在项目初期就全上**。  
先把“草稿—发布—下线”跑通，能真正支撑内容生产，这比空想一套大而全的模型更重要。

### 4. 实际项目里最容易忽略的两个点

#### 第一，草稿能不能被搜索引擎抓到？
一般不行。草稿应该只对作者和管理员可见，公开检索只服务已发布内容。这样既安全，也更符合 SEO 的预期。

#### 第二，内容修改后怎么生效？
如果页面有静态生成、缓存或增量更新，内容发布后要考虑刷新页面、重新生成静态页或者失效缓存。  
也就是说，权限和内容状态不是孤立的，它还会影响渲染策略和发布流程。

### 5. 页面访问控制示例：游客、登录用户、管理员怎么落地？

你可以这样理解一个后台内容页：

- `/admin/articles`：管理员能进，游客直接跳登录页
- `/admin/articles/new`：管理员能新建，普通登录用户看不到入口
- `/admin/articles/123/edit`：作者或管理员能编辑
- `/articles/draft/123`：只有作者和管理员能看，普通用户访问应返回 404 或跳转

这里有个小经验：**对不该暴露的资源，很多时候返回 404 比直接提示“没权限”更稳妥**，既减少信息暴露，也让页面体验更自然。

---

## 四、服务端校验和前端展示控制：两手都要抓，但职责不一样

### 1. 前端负责体验，服务端负责安全

这是权限系统里最容易搞错的一点。

#### 前端做什么
- 判断当前用户是否已登录
- 根据角色显示不同菜单、按钮、入口
- 对“没有权限”的用户给出友好提示
- 减少用户误操作

#### 服务端做什么
- 校验用户身份是否合法
- 校验是否有权限访问接口
- 校验是否能修改指定资源
- 拒绝非法请求

一句话总结：**前端是给人看的，服务端是给系统守门的。**

### 2. 在 Next.js 里怎么配合？

Next.js 的好处就在这里：它既能做页面，也能做服务端逻辑。  
所以你可以在这些位置做校验：

- **页面层**：进入页面前判断登录状态
- **中间件**：对后台路由做统一拦截
- **API Routes**：对接口请求做身份和权限校验
- **服务端渲染逻辑**：根据用户信息返回不同内容

这也是为什么说 Next.js 比单纯的 React 更适合做“站点”。因为站点不只是页面，还包括访问控制、数据处理和服务端协作。

### 3. 一个常见的实现顺序

你可以这样设计：

1. 用户登录后，服务端写入 Cookie
2. 访问后台页面时，中间件或服务端先检查 Cookie
3. 有效则放行，无效则跳转登录页
4. 用户点击“保存文章”时，请求 API Routes
5. 接口再次校验用户身份和角色
6. 通过才允许写数据库

这个流程看起来多了一层，但其实非常必要。  
因为**页面能进去，不等于操作就能成功**。

### 4. 为什么要重复校验？

因为浏览器里的一切都不可信。  
页面可以被篡改，按钮可以被伪造，接口也可以被直接请求。  
所以你必须接受一个事实：**真正的安全边界在服务端，不在前端。**

### 5. 前后端配合的一个实操原则

可以记住这句：**“前端管显示，后端管结果。”**

具体落地时：
- 前端负责把管理员菜单展示出来
- 后端负责判断这个管理员有没有权限删文章
- 前端负责把“草稿”标签展示出来
- 后端负责决定这篇草稿能不能被公开访问

这样分工清楚，后面维护起来才不乱。

---

## 五、实践建议：权限先做够用版，不要一上来搞复杂认证系统

### 1. 什么时候适合用 Next.js 来做登录和权限？

如果你的站点满足下面这些情况，Next.js 很合适：

- 需要页面首屏就知道用户身份
- 有内容发布、编辑、管理需求
- 有公开页和后台页混合场景
- 希望前后端逻辑在一个项目里完成
- 想减少接口对接和部署分离的复杂度

这时候 Next.js 的服务端能力会很顺手：页面渲染、Cookie 读取、路由拦截、API Routes 都能配合起来。

### 2. 什么时候先别把复杂度抬太高？

如果你的项目只是：

- 一个纯展示型官网
- 没有登录需求
- 没有后台管理
- 内容更新频率很低
- 业务非常简单

那就先不要急着上登录系统、权限矩阵、后台编辑器。  
很多时候，**静态页面 + 基础表单 + 简单管理后台**就够了。

### 3. 一个够用版权限系统的检查清单

你可以按这个清单落地：

- [ ] 是否明确区分游客、登录用户、管理员
- [ ] 是否所有敏感接口都做了服务端校验
- [ ] 是否公开内容不被误拦截
- [ ] 是否能控制草稿、发布、下线状态
- [ ] 是否能限制用户只能编辑自己的内容
- [ ] 是否前端仅负责展示，后端负责最终判定
- [ ] 是否避免了一开始就引入过重的认证系统

### 4. 老赵的经验话

权限这件事，最怕两个极端：

- 一个极端是啥都不做，结果上线后全靠人肉
- 另一个极端是过度设计，项目还没跑起来，规则先把自己困住

正确姿势是：**先做能支撑业务闭环的最小权限集**。  
等内容量上来了、团队人数多了、管理流程复杂了，再逐步增强。

### 5. 你可以怎么开始

如果你现在正在做一个 Next.js 站点，建议先从这三步入手：

1. 做一个最基础的登录入口
2. 给后台路由加访问拦截
3. 把“草稿、发布、下线”三个状态跑通

这三步不花哨，但非常实用。等这些基础跑稳了，再去补更细的角色、更复杂的审批、更完整的审计记录，顺序就对了。

---

## 结尾小结：这一章你该带走什么？

这一章其实只想讲清一个核心：**Next.js 不只是用来做页面，它也能承担站点里的用户登录、基础权限和内容管理入口**。  
但前提是你要把问题拆开：

- 登录状态怎么保存：会话、Cookie、Token 各有适用场景
- 谁能访问什么：游客、登录用户、管理员分层处理
- 内容怎么流转：草稿、发布、下线先跑通基础流程
- 哪些逻辑放前端，哪些必须放服务端：展示控制和安全校验分工明确

如果你现在正在做一个内容站、官网后台或轻量 CMS，建议你先完成这三件事：

1. **搭一个最小登录链路**
2. **把后台路由拦截做好**
3. **把内容的查看、编辑、发布权限分清楚**

记住一句老赵式判断：  
**能用最小复杂度解决问题，就先别把系统做成认证框架演示场。**  
Next.js 的价值，是让你把站点能力做扎实，而不是把每个功能都做得很“重”。

# 第12章：完整站点实战——搭建一个可发布的内容站

## 开篇引入：为什么学到这里，必须做一个“能上线”的站点

前面我们讲了页面、路由、数据获取、SSR/SSG、SEO、图片优化、API Routes、登录。到了这一章，就不能再把它们当零散知识点看了，得把它们串成一个真正能发布的内容站。

很多人学 Next.js 时，概念都懂，一到真做站点就卡住：  
- 首页该静态还是动态？  
- 列表页要不要做 SEO？  
- 详情页更新频繁，还能不能用 SSG？  
- 登录和后台入口放哪儿？  
- 搜索页是不是应该走客户端渲染？  

这些问题单看都不难，放到真实项目里就得一起判断。  
本章我们做一个“可发布的内容站”——有首页、列表页、详情页、搜索、登录、后台入口，能展示内容，也能做基础管理。重点不是堆功能，而是理解：**Next.js 为什么适合内容站、官网站和 SEO 站点，以及什么时候别一上来就上复杂度。**

---

## 一、项目目标与功能拆解：先想清楚这个站要解决什么问题

### 1.1 站点目标：不是做页面，而是做可访问、可收录、可维护的内容站

一个内容站，核心目标就三个：

1. **让用户看得到内容**：首页能看，列表页能筛，详情页能读。  
2. **让搜索引擎收得到内容**：标题、描述、正文结构、首屏信息要清楚。  
3. **让后续维护做得动**：内容更新、登录控制、后台入口、接口调用要有闭环。  

所以这类站点很适合 Next.js。React 更像“做页面的工具”，Next.js 则是“把页面做成站点的工具”，自带路由、服务端渲染、静态生成、接口能力、图片优化和元信息管理，正好覆盖内容站常用能力。

### 1.2 功能拆解：按访问路径拆，不按技术名词拆

建议先拆成五块：

- **首页**：展示站点概览、推荐内容、入口导航  
- **列表页**：按分类、标签、时间展示文章  
- **详情页**：文章正文、作者信息、相关推荐  
- **搜索页**：按关键词查内容  
- **登录 + 后台入口**：登录后进入内容管理或内部预览  

经验上，**先按用户访问路径拆，不要按技术栈拆**。先想用户先看什么、再点什么、哪里需要跳转、哪里需要权限，这样结构才不会乱。

### 1.3 站点页面清单：先列完整，再开始写

这个项目建议最少包含以下页面：

- `/`：首页  
- `/articles`：文章列表页  
- `/articles/[slug]`：文章详情页  
- `/search`：搜索页  
- `/login`：登录页  
- `/admin`：后台入口页  
- `/admin/articles`：文章管理页  
- `/admin/articles/new`：新建文章页（可选）  

页面一旦列清楚，后面路由、数据流、权限边界就都清楚了。

### 实用建议

- 第一版只保留“能看、能搜、能登录、能进后台”
- 后台先做简单管理页，不必立刻做完整 CMS
- 内容少、更新不频繁，优先考虑静态生成
- 内容更新很快，再考虑更强的动态渲染和刷新机制

## 二、站点结构设计与页面路由规划：把 URL 设计成一张清晰地图

### 2.1 路由清单：页面和路径先对齐

一个清晰的结构可以这样规划：

- `/`：首页
- `/articles`：文章列表页
- `/articles/[slug]`：文章详情页
- `/search`：搜索页
- `/login`：登录页
- `/admin`：后台入口
- `/admin/articles`：内容管理页

这个结构直观，用户看 URL 知道自己在哪，开发者看目录也知道页面职责。

### 2.2 路由规划原则：固定页、列表页、详情页分开处理

核心思路很简单：

- **固定页**：首页、登录页、后台入口页，结构稳定  
- **列表页**：依赖筛选条件、分页参数  
- **详情页**：依赖 slug 或 id  
- **搜索页**：依赖 query 参数  

分清后，页面职责就不会混在一起：  
首页负责引导访问，列表页负责组织内容，详情页负责承载正文，搜索页负责快速找内容，登录页负责身份入口。

### 2.3 动态参数与查询参数：职责不同，别混着用

初学者常把 `slug`、`id`、`?keyword=` 混在一起，其实职责不同：

- **动态路由参数**：适合内容实体，如 `/articles/nextjs-guide`
- **查询参数**：适合筛选、搜索、分页，如 `/articles?page=2&tag=seo`
- **登录状态**：不是 URL 决定的，而是身份状态决定的

路由设计清楚了，后面的数据获取、SEO、缓存策略才好做。

### 实用建议

- 文章详情页尽量用稳定的 slug
- 搜索和筛选优先用 query 参数
- 站点早期不要拆太细，先保证结构清楚
- 内容导航复杂时，先画信息架构图再写代码

---

## 三、页面数据流：首页、列表页、详情页、搜索页怎么联动

### 3.1 首页不是“摆门面”，它要负责分发流量

首页一般承担三个任务：

1. 展示站点定位和主导航  
2. 推荐几篇重点内容  
3. 把用户引导到列表页、详情页、搜索页  

所以首页的数据通常比较轻，常见做法是读取推荐文章、热门分类、最新更新等内容。首页要做到两点：**加载快**、**入口清楚**。

### 3.2 列表页负责组织内容，详情页负责承载正文

列表页最重要的是“可浏览”，详情页最重要的是“可阅读”。

- 列表页展示标题、摘要、标签、更新时间
- 详情页展示标题、正文、作者、发布时间、相关推荐

这两个页面的数据流要分开。列表页拿集合数据，详情页拿单篇内容数据。不要为了省事把详情页硬塞成列表页的一部分，那样 SEO 和维护都会别扭。

### 3.3 搜索页的特点：用户输入驱动，适合动态处理

搜索页是典型的“用户输入驱动”页面。用户输入关键词后，页面再请求结果，所以搜索页一般不必强行静态化。这里重点不是首屏收录，而是**响应快、反馈清楚、结果可筛选**。

### 3.4 数据流建议：别让页面直接到处乱拉接口

建议把数据流整理成四层：

- **页面层**：负责展示和交互  
- **服务层**：负责组织请求  
- **接口层**：负责读写数据  
- **内容源**：数据库、CMS 或外部内容接口  

这样后面要换数据源，不用把整个页面推倒重来。

### 实用建议

- 首页、列表页、详情页的数据结构尽量统一
- 搜索页不要做过重的首屏逻辑
- 页面不要直接散落多个接口请求，尽量收拢到统一服务层
- 内容字段先定好：标题、摘要、正文、标签、时间、作者

## 四、数据获取、渲染策略、SEO 配置的组合应用：不同页面该怎么渲染？

### 4.1 先回答关键问题：哪些页面该静态，哪些页面该动态？

这就是 Next.js 最值得学的地方之一，不是“会写页面”就够了，而是要会判断页面怎么生成。

本章这个站点里，可以这样分：

#### 首页
- 内容更新不算特别频繁
- 需要 SEO
- 适合 **SSG** 或带更新机制的静态方案

#### 列表页
- 公开文章列表适合 **SSG + 定期更新**
- 如果筛选条件很多，可局部动态化

#### 详情页
- 文章类内容非常适合 **SSG**
- 如果更新频繁，也可以用 **SSR** 或增量更新思路

#### 搜索页
- 典型动态页面，适合 **客户端请求 + 动态渲染**
- 结果依赖用户输入，不必强行静态化

#### 登录页、后台页
- 对 SEO 没要求
- 更关注交互和权限，通常动态处理即可

### 4.2 渲染策略不是“选一个就完了”，而是“按页面组合”

理解 SSR/SSG，别只问“哪个更好”，更准确的问题是：**不同页面分别适合哪种策略？**

判断标准很实用：

- **内容是否公开**：公开内容更适合 SEO
- **内容是否稳定**：稳定内容更适合静态生成
- **是否依赖用户态**：依赖登录态的内容更适合动态渲染
- **是否强实时**：强实时内容不要硬做静态

### 4.3 SEO 配置：不是堆关键词，而是让页面“说人话”

内容站做 SEO，重点是基础做到位：

- 每个页面有合适标题
- 描述清楚页面主题
- 详情页有语义化结构
- 图片有合理 alt
- URL 简洁可读
- 站点内部链接清晰

Next.js 的好处是可以把页面元信息放在页面层管理，而不是后补。内容站最怕页面做出来了，但标题全一样、描述全空、详情页像纯前端壳子。

### 4.4 常见误区：为了 SEO 过度追求“全站 SSR”

一听 SEO 就把所有页面改成 SSR，其实没必要。

- 静态内容多的页面，SSG 更省事、更快
- 不需要实时变化的详情页，没必要每次请求都渲染
- 搜索页和登录页，强行做 SEO 价值不大

记住：**SEO 不是让所有页面都服务搜索引擎，而是让值得被收录的页面更容易被理解。**

### 实用建议

- 首页、列表页、详情页优先考虑 SEO
- 搜索页、登录页别在 SEO 上浪费太多精力
- 页面标题、描述、正文首屏内容要一致
- 公开内容和用户态内容分开思考，别混着渲染

## 五、接口、登录、简单权限与内容展示的联动实现：让站点真正“可用”

### 5.1 API Routes 的作用：前端站点里留一个“轻后端口子”

Next.js 的接口能力很适合这类项目早期阶段。因为你不一定一开始就有完整后端，但又需要一些能力：

- 登录校验
- 内容列表获取
- 详情页数据拉取
- 简单后台操作

这时候，API Routes 就能作为站点内部的轻接口层，承接前端和后端之间的请求。

### 5.2 登录与简单权限：先做“够用”，不要一上来做复杂权限系统

本章这个站点里，登录和权限建议只做最小闭环：

1. 用户在 `/login` 输入账号密码  
2. 接口校验成功后返回登录态  
3. 前端保存登录信息  
4. 访问 `/admin` 时检查是否登录  
5. 未登录则跳回登录页  

这就够了。不要一开始就设计多角色、多级审批、细粒度资源授权，那是下一阶段的事。

### 5.3 权限判断要放在哪儿？

建议这样理解：

- **前端**负责展示和交互控制，比如是否显示后台入口
- **接口层**负责真实校验，不能只靠前端隐藏
- **页面层**负责访问拦截和体验引导

权限不是一个点，而是一条线。

### 5.4 内容展示与接口联动：把“发布链路”跑通

一个内容站真正可用，不只是能看文章，还要能让内容流转起来。比如：

- 首页读取推荐内容接口
- 列表页读取文章集合接口
- 详情页读取文章详情接口
- 后台页读取用户权限和管理数据
- 登录接口返回身份状态
- 新建文章后刷新列表和详情相关缓存

这时 Next.js 的优势就出来了：页面、接口、渲染、跳转放在同一个项目里协同处理，少很多跨仓库、跨服务的沟通成本。

### 实用建议

- 登录校验一定要服务端参与，别只靠前端判断
- 站点早期接口可以简单，但返回结构要稳定
- 后台功能先做“可进入、可查看、可更新基础内容”
- 权限从“页面可见性”开始，不必一口气做到企业级

## 六、发布流程与验收要点：站点不是写完就完了

### 6.1 发布流程：从内容到上线要有一条线

一个内容站的基本发布流程可以这样走：

1. 编辑或录入内容  
2. 保存到内容源或接口层  
3. 生成或更新列表页、详情页数据  
4. 页面按约定渲染策略输出  
5. 部署到线上环境  
6. 验证首页、列表、详情、搜索、登录和后台入口是否正常  

如果你做的是 SSG 或带缓存更新的方案，发布后还要确认内容刷新是否生效。别上线了还停留在旧内容。

### 6.2 验收要点：别只看“能打开”，还要看“是否像个站”

上线前建议逐项确认：

- 首页是否能正常访问和收录
- 列表页分页是否清晰
- 详情页标题、描述、正文是否合理
- 搜索页是否响应快、交互顺
- 登录态是否真实有效
- 后台入口是否有基本保护
- 图片是否优化，首屏是否过重
- 哪些页面用了静态，哪些页面用了动态，是否符合业务
- 刷新页面后，权限和内容是否还保持一致

### 6.3 复盘重点：哪些地方值得用 Next.js，哪些地方不必复杂化

这个项目里，Next.js 最适合做这些事情：

- **内容站主页和详情页**：公开内容，适合 SEO  
- **文章列表和分类页**：需要结构化展示和可收录  
- **接口聚合**：减少前后端分离早期的沟通复杂度  
- **图片处理**：减少页面体积，提高加载体验  
- **登录入口和后台基础页**：同一个项目内完成访问控制和内容管理入口  

换句话说，凡是“要发布、要收录、要稳定展示”的内容，Next.js 都很顺手。

也要讲清楚，哪些地方别上来就搞复杂：

- 内容量很小、只是内部展示页时，不一定非要上完整 Next.js 站点
- 搜索逻辑如果很简单，不必做复杂缓存和索引
- 后台管理如果只是少量文章维护，不必马上引入完整 CMS
- 登录如果只是内部入口，不需要一开始就做多角色体系

判断标准很简单：  
**如果你只是做纯静态展示页，React 加静态托管可能就够了；如果你要做内容发布、SEO、路由、接口、登录这些完整站点能力，Next.js 才真正体现价值。**

### 实用建议

- 站点上线前先检查“访问路径”是否完整
- 不要只测功能，还要测首屏、SEO、图片、登录状态
- 后期内容增长快，再逐步增强缓存和增量更新
- 先把“能发布”做出来，再考虑“做大做强”

## 结尾小结：先把站点跑起来，再谈高级架构

这一章，我们用一个可发布的内容站，把前面学过的 Next.js 能力串成了完整闭环：

- 用站点目标拆功能
- 用路由规划组织页面
- 用数据流明确首页、列表页、详情页和搜索页的关系
- 用渲染策略区分静态和动态内容
- 用 SEO 配置让内容更容易被理解和收录
- 用 API Routes、登录和简单权限让站点真正可用
- 用发布流程和验收要点把项目落到线上
- 最后复盘哪些地方值得用 Next.js，哪些地方不必提前增加复杂度

你要记住，学 Next.js 不是为了多记几个名词，而是为了把 React 页面推进到**可发布、可维护、可增长的站点**。

### 最后给你一个判断口诀

- **内容公开、需要收录、结构清晰**：Next.js 很合适  
- **页面简单、没 SEO 压力、只是内部展示**：先别上复杂度  
- **有路由、有接口、有登录、有页面层次**：Next.js 的价值就出来了  

如果你能把这一章做完，基本就从“会写 React 页面”迈到了“能做站点”的层级。
