# 第1章 先把话说明白：Vue3 组件到底是个啥

## 开篇：别急着写代码，先把“组件”想明白

很多人学 Vue3，`ref`、`computed`、`v-for` 都会写，可一到真做页面就开始乱。原因很简单：页面一复杂，光会语法不够，还得会拆。

而拆的前提，是先搞清楚：**组件到底是什么**。

老赵先给你一句直白的：  
**组件不是一个 Vue 文件这么简单，它是把 UI、状态、事件和职责打包到一起的一个小单元。**

你可以把它理解成一个能独立工作的零件。页面是机器，组件是按钮、齿轮、电路板。好的页面，不是把所有逻辑堆进一个大文件里，而是按职责拆开，谁干谁的活，别越界。

这里先埋一个后面会一直用到的概念：**组件边界**。  
边界说白了就是“这块东西管到哪儿为止”。边界清楚，组件才好维护、好复用；边界一糊，页面迟早变成一锅粥。

## 一、组件是什么：UI、状态、事件、职责的组合

### 1.1 一个组件最少要回答四件事

一个组件至少要看这四层：

- **UI**：长什么样
- **状态**：内部管哪些数据
- **事件**：怎么响应用户操作
- **职责**：负责哪块业务，边界在哪

比如一个按钮组件，不只是“一个按钮样式”，它还可能负责禁用、loading、类型、尺寸等展示和交互。

所以组件不是页面切片，而是**职责单元**。页面上挨得近，不代表职责就该绑在一起。

### 1.2 组件的价值：复用、维护、隔离

组件化主要解决三件事：

1. **复用**：同样的按钮、弹窗、表单项不用重复写  
2. **维护**：需求变了，只改对应组件  
3. **隔离**：把复杂页面拆小，降低理解成本

说白了，组件化就像收纳盒：东西没少，但每样都有位置，找得到、改得动、还能重复用。

### 1.3 组件边界先怎么理解：不是“能不能放一起”，而是“该不该放一起”

拆组件时，很多人容易走两个极端：

- **拆太大**：一个组件把页面标题、筛选区、列表、弹窗、请求、校验全包了
- **拆太碎**：一个按钮也拆，图标也拆，最后传参像走迷宫

真正好用的边界，是让组件做到这三件事：

- 能独立看懂
- 能独立复用
- 能独立改动而不牵连全局

### 可复用的组件案例：基础按钮组件

一个基础按钮组件可以先抽成：

- `type`
- `size`
- `disabled`
- `loading`
- `click` 事件

它的职责很单纯：**统一按钮外观和交互**。  
页面只告诉它是什么按钮、是否提交中、点击后通知谁，别让按钮去管接口、跳转这些业务事。

这个按钮之所以适合作为可复用组件，不只是因为“很多地方都会用”，更因为它满足了几个复用条件：

- 输入稳定，参数少
- 输出明确，核心就是点击事件
- 业务耦合低，不依赖某个页面的特殊逻辑
- 文档很好写，别人一看就知道怎么用

这才叫能复用，不是硬抽象出来的“伪通用”。

### 老赵常见踩坑提醒

**别把组件理解成“一个 Vue 文件就叫组件”，更别做成万能按钮。**  
按钮就是按钮，别让它顺手干请求、开弹窗、提交流程这种活。职责一乱，后面全乱。

## 二、组件边界怎么判断：一个组件到底管多少事

### 2.1 先问自己：这个组件的核心职责是什么？

判断边界，先问三个问题：

- 它主要展示什么？
- 它主要处理什么交互？
- 它主要服务哪段业务？

如果一个组件回答的问题越来越多，它就可能越界了。比如“用户信息卡片”如果只展示头像、昵称、角色，边界清楚；但如果又要编辑、校验、上传、提交，它就从卡片变成了复杂业务容器。

### 2.2 一个真实一点的拆分示例：订单列表页怎么拆

一个订单列表页通常有：

- 顶部标题和操作按钮
- 筛选条件
- 表格
- 分页
- 行内操作
- 详情或确认弹窗

正确的拆法不是把整页塞进一个组件，也不是把每个小标签都拆出去，而是按职责分层：

- **页面层**：负责拉数据、组合模块、管理页面状态
- **筛选区组件**：负责收集筛选条件并触发查询
- **表格区组件**：负责展示订单数据和行内操作
- **分页组件**：负责页码切换
- **弹窗组件**：负责确认、查看详情等独立交互

这样拆完，每块都知道自己在干嘛。页面层像总指挥，子组件像各自岗位上的人，谁也别越权。

### 2.3 错误拆法 → 问题暴露 → 重新划边界

#### 错误拆法
很多人会这么做：

- `OrderPage.vue` 一个文件写完所有内容
- `OrderTable.vue` 除了表格，还负责请求、筛选、弹窗
- `OrderFilter.vue` 不只负责筛选，还顺手改列表状态
- `ConfirmDialog.vue` 直接调用接口，提交完自己关闭

#### 问题暴露
开始好像省事，后面马上出问题：

- 页面一长，看不懂
- 表格改一下，筛选区也被牵连
- 弹窗复用不了，因为业务写死了
- 出 bug 不知道谁负责
- 组件之间互相咬死，改一个地方牵一片

#### 重新划边界
正确方式是把职责切开：

- 页面层拉列表、维护筛选条件和分页状态
- 筛选组件只负责收集条件并 emit 出去
- 表格组件只负责展示数据和抛出行内操作事件
- 弹窗组件只负责显示确认内容和交互结果
- 真正的接口请求留在页面层或业务容器层处理

这样一改，组件边界就清楚了：  
**谁负责显示，谁负责交互，谁负责业务决策，分开。**

### 2.4 组件边界的判断标准

#### 1）变化点是否一致
变化节奏不同的部分，通常不该放一起。

#### 2）职责是否单一
一个组件最好只做一类事。列表负责展示和基础交互，别顺手把审批逻辑也背了。

#### 3）是否能独立描述
如果一句话讲不清它干嘛，边界多半不清。

### 2.5 什么时候该拆组件

出现这些信号，基本就该拆了：

- 模板太长，看不清
- `watch`、`computed`、方法太多
- 某块 UI 其他地方也会用
- 局部改动会牵连整页
- 一个组件同时管展示、数据、请求、校验、弹窗

### 2.6 组件边界不是越小越好

拆分不是越碎越好。太碎会导致文件太多、props 传来传去、阅读成本暴涨。  
目标不是“最小”，而是**刚刚好**：能独立理解、独立复用、独立维护。

### 可复用的组件案例：按钮组

把“确定 / 取消 / 重置”做成按钮组组件：

- 统一排列和间距
- 可按 props 控制显示
- 对外只暴露点击事件

它只管按钮区，不管业务结果，边界清楚，复用也稳。

### 老赵常见踩坑提醒

**最常见的坑，就是顺手把别的职责也带进去。**  
今天按钮管埋点，明天管跳转，后天管权限，最后它就不是按钮，是个小型业务系统。

## 三、从页面到组件：组件化拆分的基本思路

### 3.1 先从页面骨架开始拆

老赵建议：**先看页面骨架，再看重复局部，再看交互独立性。**

一般顺序是：

1. 识别页面大块区域
2. 找可复用模块
3. 找独立交互块
4. 决定哪些逻辑留在页面层，哪些下放到子组件

比如列表页通常有：

- 筛选区
- 表格区
- 分页区
- 新增弹窗

这些就很适合先按职责拆开，再考虑通信。

### 3.2 一个实用拆分法：三层法

#### 页面层
负责业务编排：拉数据、管整体状态、组合子组件。

#### 业务组件层
负责某一块业务：用户列表、商品筛选、订单摘要。

#### 基础组件层
负责纯 UI 和通用交互：按钮、输入框、弹窗、标签。

三层分开，维护顺很多。基础组件写“怎么用”，业务组件写“适用场景”，页面层写“如何组合”，文档也更好写。

### 3.3 拆分时要先想“谁来持有状态”

组件拆出去之后，**状态放哪儿**很关键。一般来说：

- **页面层**：页面级状态，比如列表数据、筛选条件、接口结果
- **子组件**：局部状态，比如按钮 loading、输入框临时内容
- **共享状态**：再考虑父子通信或状态提升

这就引出一个非常重要的思路：**受控/非受控**。

- **受控**：状态由外部控制
- **非受控**：状态由组件内部自己管理

表单、弹窗、分页里，这个思路特别常见。你先搞明白谁控制谁，很多组件设计问题就通了。

### 可复用的组件案例：搜索栏组件

把“输入框 + 搜索按钮 + 重置按钮”抽成搜索栏组件：

- 页面决定搜索哪些字段
- 组件负责展示和交互
- 搜索条件通过事件向外发出

这样页面层只管拿条件请求接口，搜索栏本身就能复用到多个列表页。它的边界也清楚：收集筛选条件，不负责接口请求。

### 老赵常见踩坑提醒

**别一上来就想着“这个页面要抽几个组件”，先看职责，再看复用。**  
很多时候不是拆不出来，而是你没分清页面逻辑和组件逻辑。

## 四、可复用组件和一次性组件的区别

### 4.1 不是什么都值得抽象

老赵先泼点冷水：**组件复用是能力，不是信仰。**  
有些东西就是一次性的，硬抽出来反而更复杂。

### 4.2 两类组件怎么区分

#### 可复用组件
通常具备这些特征：

- 多处会用
- 逻辑相对稳定
- 输入输出明确
- 和具体页面耦合低

比如按钮、弹窗、分页器、标准表单项、通用选择器。

#### 一次性组件
通常是：

- 只在当前页面用
- 业务强绑定
- 改动频繁
- 抽象后反而难懂

比如某个活动页的海报块、某个报表页的特殊图表块。

### 4.3 怎么判断要不要复用

可以简单问四个问题：

- 会不会出现第二次使用
- 输入输出是否稳定
- 业务变化会不会让它持续扩张
- 能不能写出简单文档让别人直接用

大部分答案都是“是”，才值得抽。

### 4.4 复用不是“通用化”

复用最怕为了“通用”把组件做成复杂配置怪兽。  
记住：**可复用，不等于尽可能通用。**

好的复用是在“足够通用”和“足够简单”之间找平衡。能少一个配置项就少一个，能让使用方一眼看懂就别写成迷宫。

### 可复用的组件案例：确认按钮区

很多页面都需要“确认 + 取消”的操作区，可以抽成组件：

- `confirmText`
- `cancelText`
- `loading`
- `showCancel`
- `confirm`、`cancel` 事件

这样每个页面只管传配置，不用重复写按钮排版和交互逻辑。

### 老赵常见踩坑提醒

**最常见的坑，就是把一次性需求硬抽象成通用组件，结果配置项比业务代码还多。**  
组件一旦“太聪明”，后面谁都不敢改。

## 五、组件案例：一个基础按钮组件的完整拆分思路

### 5.1 先定义它的职责

按钮组件职责很简单：

- 展示按钮样式
- 响应点击
- 支持基础状态控制

别让它做别的。如果按钮要承接的业务越来越多，就该考虑拆成“按钮外壳 + 业务控制层”，而不是继续往里塞。

### 5.2 先决定输入和输出

按钮是典型的“外部控制 + 内部呈现”组件。

#### 输入（props）
- `type`：默认、主按钮、危险按钮
- `size`：小、中、大
- `disabled`：是否禁用
- `loading`：是否加载中
- `icon`：是否带图标

#### 输出（emit）
- `click`：用户点击时通知外部

核心就一句：**按钮不决定业务结果，只负责把点击事件交出去。**

这样页面层就能统一处理校验、请求、跳转等流程，而按钮只负责交互表现。

### 5.3 受控/非受控思路怎么用

按钮里的 `loading`、`disabled` 通常更适合受控：外部决定是否在提交中、是否可点击。  
这样按钮不会偷偷改业务状态，因为它不是业务决策者，只是执行层。

像 hover 样式、图标展示这类纯展示细节，则可以交给组件内部自己管理。  
这就是受控和非受控的区别：**能外部管的尽量外部管，纯展示细节再交给内部。**

### 5.4 一个可复用按钮的设计检查清单

- 是否只做按钮该做的事
- 是否通过 props 接收外部控制
- 是否通过 emit 向外抛事件
- 是否样式可配置但不过度复杂
- 是否能在不同页面复用
- 是否有清楚的使用说明

### 5.5 如何给按钮写简单文档

组件文档不用写成论文，最起码有这几项：

- 组件用途
- props 列表和默认值
- 事件说明
- 示例代码
- 注意事项

比如按钮文档可以写成：

- 用途：统一项目按钮样式与交互
- props：`type`、`size`、`disabled`、`loading`
- 事件：`click`
- 场景：提交、确认、取消、重置

这就够业务同学快速上手了。文档的作用，就是让别人知道“能不能直接用、会不会用错”。

### 5.6 一个更实在的重构对照：从页面按钮到组件按钮

#### 错误做法
有些页面会直接写一堆按钮：

- 样式写死在页面里
- `loading` 在页面到处传
- 点击后在按钮内部直接调接口

结果就是同类按钮每页一份，改文案、改状态、改样式都要翻页面。

#### 重构后
把按钮抽成组件以后：

- 页面只传 `type`、`loading`、`disabled`
- 点击行为统一通过 `emit` 抛出去
- 接口请求放在页面层或业务层
- 按钮只负责“长什么样、什么时候能点”

这时候它就从一次性页面片段变成了真正可复用的基础组件。

### 老赵常见踩坑提醒

**按钮组件最忌讳既管样式，又管业务，还管接口请求。**  
按钮只是发出“我被点了”这个信号，不要把请求逻辑塞进去，不然它很快就变成黑盒。

## 六、老赵总结：先把组件边界站稳，再谈复用和抽象

这一章你先记住三句话：

1. **组件是 UI、状态、事件、职责的组合**
2. **组件边界不是按页面切，而是按职责切**
3. **复用不是越通用越好，而是越稳定、越清楚越好**

后面你会学到 `props / emit`、`slot`、受控/非受控、表单、弹窗、列表、分页这些内容，但底层逻辑都绕不开今天这件事：**先把组件边界定清楚。**

### 这一章的行动建议

你可以马上做三件事：

1. 找一个项目页面，标出页面职责和可拆组件  
2. 选一个基础按钮或输入框，试着写出它的 props、emit 和简单文档  
3. 看看有没有“万能组件”倾向，问自己：它是不是承担了太多职责？

老赵最后送你一句话：  
**组件化不是把代码拆碎，而是把职责理顺。职责一顺，复用就顺；复用一顺，维护就轻松。**

### 老赵常见踩坑提醒

**千万别把组件做成万能黑盒。**  
你今天图省事，把所有东西都往一个组件里塞，明天维护的时候就会发现：谁都不敢改，谁都改不动，最后连你自己都不想看。

# 第2章 单文件组件 SFC：写规范，后面才好复用

如果你已经会写 Vue3 组件，这一章就不讲“怎么跑起来”，而是讲更重要的事：**怎么把组件写得像组件，而不是一坨临时拼出来的页面代码**。

SFC，也就是单文件组件，最大的价值不只是把 `template`、`script`、`style` 放在一个文件里，而是它天然适合收拢一个组件的**边界、结构和职责**。现在写得随意，后面复用、维护、协作都会很痛；现在写得规范，后面才好抽成业务组件，甚至沉淀成组件库。

老赵先说句大白话：**SFC 不是为了炫技，是为了让别人和未来的自己都能看懂。**

## 一、SFC 的基本结构：`template`、`script`、`style` 怎么配合？

### 1. SFC 本质上是在做“职责分区”

一个标准的单文件组件，通常由三块组成：

- `template`：管结构和展示
- `script`：管数据、逻辑、交互
- `style`：管样式、视觉呈现

你可以把它理解成一个小工厂：

- `template` 是车间布局
- `script` 是生产流程
- `style` 是外观包装

核心判断标准很简单：

- 模板里尽量只放展示和少量表达式
- 逻辑集中到 `script`
- 样式尽量局部化，别影响别的组件

如果模板负责“想”，脚本负责“看”，样式负责“跑偏”，那这个组件基本就乱了。

### 2. 模板里别堆太多判断

很多人喜欢在模板里写一堆三元表达式、嵌套 `v-if`、字符串拼接。短期看着省事，长期就是维护灾难。

更稳的做法是：

- 复杂判断提前放进计算属性
- 重复逻辑抽成方法或组合式函数
- 模板只负责根据结果渲染

比如状态颜色，不要直接在模板里写长串判断，改成在脚本里做映射，模板只绑定结果。这样更清楚，也更好改。

### 3. 样式要服务组件，不要服务情绪

组件样式最怕两件事：

- 写得太泛，误伤全局
- 写得太死，后面改一点都难

建议优先考虑：

- 作用域样式
- 相对统一的命名方式
- 预留基础状态类名，比如 `is-active`、`is-disabled`

样式和组件绑定得越紧，越不容易和别的页面撞车。

#### 可复用组件案例：基础按钮骨架

按钮组件别一开始就做成“大而全”，先把结构分清：

- `template`：按钮内容、图标、加载态
- `script`：点击事件、禁用逻辑
- `style`：尺寸、颜色、状态

这种按钮一旦结构清楚，后面加 `type`、`size`、`loading` 都不会乱。它不只能服务页面按钮，也能服务弹窗确认按钮、表单提交按钮、列表操作按钮。

### 老赵常见踩坑提醒

**模板里啥都写，最后自己都看不懂。**  
尤其把复杂判断、数组处理、字符串拼接全塞进 `template`，短期省事，长期一定把维护成本拉爆。

## 二、组件命名、文件命名和目录组织：怎么才算规范？

### 1. 命名不是形式主义，是为了协作不费劲

组件一多，最怕的不是写不出来，而是**找不到、分不清、改不动**。所以命名要稳定。

建议保持：

- 组件名语义明确
- 文件名和组件名一致
- 目录按业务域或组件类型组织

比如：

- `BaseButton.vue`
- `InfoCard.vue`
- `UserTable.vue`

不要出现 `index.vue`、`new.vue`、`test2.vue`、`最终版.vue` 这种名字。你现在看着无所谓，等项目里堆出一堆 `index.vue`，就知道什么叫认知污染了。

### 2. 目录组织要和复用目标一致

简单判断一下：

- **页面级组件**：只服务当前页面
- **基础组件**：按钮、输入框、卡片这类通用 UI
- **业务组件**：订单列表、用户弹窗、筛选面板这类场景组件

这不是为了好看，而是为了明确组件边界。基础组件尽量少带业务味道，业务组件允许更贴近场景，但也别太散。

### 3. 名字要能表达边界

组件命名其实是在告诉别人：这个组件管什么，不管什么。

比如“Card”太泛，最好进一步说明：

- `UserCard`
- `ProductCard`
- `StatCard`

名字越具体，误用越少；名字越抽象，越容易沦为万能盒子。

#### 可复用组件案例：信息卡片命名规范

假设你做一个“信息卡片”组件，建议命名为 `InfoCard.vue`，如果它专门展示用户数据，就改成 `UserInfoCard.vue`。这样文件好找，文档也好写。

比如：

- `InfoCard`：通用信息展示
- `UserInfoCard`：用户资料展示
- `StatCard`：数据统计展示

名字定准了，组件边界也就顺了。

### 老赵常见踩坑提醒

**组件名字太抽象，最后自己都分不清是干嘛的。**  
一个叫 `Panel.vue` 的组件，可能是容器、卡片、弹层、布局块，谁看谁迷糊。命名尽量具体，别靠脑补。

## 三、逻辑、样式、状态该放哪里？别乱塞

### 1. 先分清“静态展示”和“交互状态”

组件里最常见的混乱，就是把状态、样式、逻辑揉成一团。先问自己三个问题：

- 这是纯展示的吗？
- 这是会变化的状态吗？
- 这是与用户交互相关的吗？

比如一个用户卡片：

- 用户头像、昵称、描述是展示内容
- 是否选中、是否高亮是状态
- 点击卡片查看详情是交互

先把这三块分开，组件就不容易写乱。

### 2. 逻辑放 `script`，状态放最靠近使用处

状态管理尽量遵循一个原则：**就近管理**。

- 局部状态：放组件内部
- 需要外部控制的状态：通过 `props` 接收
- 需要对外通知的行为：通过 `emit` 发出

这就是后面复用组件最重要的基础。把本该父组件控制的状态藏进子组件里，组件一旦复用，立刻就会变得不好控。

### 3. 不要把业务判断写成视图污染

比如一个卡片组件，你只需要知道“是否高亮”“是否显示角标”“是否展示副标题”。至于数据怎么来的、是否超管、是否 VIP，最好在上层处理后传入组件。

这样组件边界才清楚：

- 组件负责展示
- 父组件负责业务决策

组件不要替业务做主，只负责把业务结果展示好。

#### 可复用组件案例：状态清晰的 Card 信息卡片

这个卡片可以接收：

- `title`
- `desc`
- `cover`
- `highlight`

组件内部只处理展示，不参与复杂业务判断。这样它能复用到用户卡片、商品卡片、文章卡片上。后续扩展时，也优先通过插槽补充，而不是继续往里塞业务判断。

### 老赵常见踩坑提醒

**状态到处飞，最后谁改的都不知道。**  
尤其一个状态一会儿放 `data`，一会儿放 `computed`，一会儿又在模板里临时算，调试起来很痛。状态要有唯一来源，别左右横跳。

## 四、组合式 API 在组件里的基本摆法：怎么写才顺手？

### 1. 组合式 API 的价值，是让逻辑更容易拆

组合式 API 不是为了写得“高级”，而是为了按功能组织逻辑。一个规范组件，通常这样摆：

1. 导入依赖
2. 定义 `props` 和 `emit`
3. 定义响应式状态
4. 定义计算属性
5. 定义事件方法
6. 返回给模板使用

这样读代码时，你能很快看清这个组件“收什么、算什么、发什么”。

### 2. 推荐的组织顺序

比较稳的顺序是：

- 先定义输入：`props`
- 再定义输出：`emit`
- 再定义内部状态：`ref`、`reactive`
- 再定义派生状态：`computed`
- 再定义交互方法：`handleXxx`

按这个顺序写，逻辑会清楚很多。尤其做可复用组件时，先看输入输出，心里才有底。

### 3. 组件内部逻辑要围绕职责聚合

不要把方法随便堆在一起。比如卡片组件里，可能只需要：

- `handleClick`
- `handleClose`

那就没必要写成十几个函数。函数多，不代表组件强，只代表职责开始散了。

如果一个组件内部方法越来越多，通常说明它已经超出边界了。这个时候该考虑拆组件，或者把部分逻辑提到组合式函数里。

#### 可复用组件案例：可点击卡片

一个 `ClickableCard` 可以支持：

- 点击卡片跳转
- 禁用态
- 选中态

它内部用 `props` 控制状态，用 `emit` 通知点击事件，逻辑就很清楚。父组件决定跳到哪里，子组件只负责“被点击”和“被展示”。

### 老赵常见踩坑提醒

**组合式 API 写成变量大杂烩。**  
`ref`、`computed`、方法全乱排，自己写完都不知道哪个是输入、哪个是输出。建议按“输入—状态—派生—动作”来排，脑子会轻很多。

## 五、一个规范的 Card 信息卡片组件：怎么做才算能复用？

### 1. 先回答一个问题：它的边界是什么？

Card 不是“什么都能放”的盒子。一个可复用的 Card，边界应该明确：

- 负责展示信息块
- 不负责业务数据获取
- 不负责路由跳转决策
- 不负责复杂权限判断

也就是说，它只做“展示容器 + 基础交互”。

如果你把 Card 做成“能展示、能编辑、能删除、能跳转、能校验、还能发请求”，它最后一定不好复用。边界失控，复用就会变负担。

### 2. 设计一个可复用的卡片接口

可以先从这些参数开始：

- `title`：标题
- `desc`：描述
- `cover`：封面
- `extra`：右侧补充信息
- `clickable`：是否可点击

如果需要更灵活，就给它留插槽：

- 标题区插槽
- 内容区插槽
- 底部操作区插槽

这样稳定部分由 props 控制，可变部分由 slot 接管，扩展性就有了。

### 3. 通用和可定制要平衡

好组件不是把所有功能写死，而是给可变部分留接口，给稳定部分定规则。

- 稳定的：边距、基础结构、默认样式
- 可变的：内容、状态、部分交互

这也是受控/非受控思路的影子：关键状态交给外部控制，小状态留在组件内部。别把所有东西都做成“全自动”，那样反而难接入业务。

#### 可复用组件案例：InfoCard

`InfoCard` 可以支持：

- 标题
- 描述
- 右上角操作
- 点击高亮
- 内容自定义

它能在用户页、商品页、统计页反复使用。到这一步，它就不是“一个卡片”，而是一个可扩展的信息展示容器。

### 老赵常见踩坑提醒

**卡片一做就想支持所有场景，最后谁都不好用。**  
组件不是功能越多越好，而是边界越清楚越好。先做 80% 场景，再通过插槽和配置补足剩余 20%。

## 六、老赵常见踩坑提醒：别让模板把你自己埋了

这一节单独拎出来，因为这是最常见的翻车点。

### 1. 常见封装陷阱

- 把复杂逻辑塞模板
- 组件内部直接改外部传入的数据
- 样式命名混乱，互相污染
- props 设计过多，最后成了参数黑洞
- 组件职责不清，既像展示组件，又像业务页面

### 2. 怎么避免

记住一个很实用的判断：

> 一个组件如果改动需求时总是牵一发动全身，八成是边界没画好。

所以要坚持：

- 输入明确：`props`
- 输出明确：`emit`
- 结构清晰：`template`
- 逻辑集中：`script`
- 样式隔离：`style`

还有一点很重要：别把“能用”当成“可复用”。能跑只是第一步，可复用才是组件设计的真正目标。

### 3. 给组件写简单文档，越早越省事

哪怕还没做组件库，也建议给常用组件写个最简文档，内容不用花哨，但要实用：

- 组件用途
- 适用场景
- `props` 说明
- 事件说明
- 插槽说明
- 示例代码
- 注意事项

这份文档的价值很大：**它逼你把组件边界想清楚。**

文档不一定要正式，放在 README、注释里、设计稿旁边都行。关键是让后面的人能快速知道：怎么用、什么时候该用、什么情况下别用。

#### 可复用组件案例：Card 简单文档模板

给 `InfoCard` 写一个小文档就够用：

- 用途：展示一块信息区域
- 场景：用户卡片、商品卡片、统计卡片
- Props：`title`、`desc`、`clickable`
- Slots：`header`、`default`、`footer`
- 事件：`click`
- 注意：不要把业务逻辑写进组件内部

这类简单文档看似不起眼，但到团队协作时，能省很多解释成本。

### 老赵常见踩坑提醒

**不写文档，三天后连自己都不敢改。**  
尤其是可复用组件，哪怕只是几行说明，也比空着强。你不写，最后就会变成“只有作者敢碰”的组件。

你要记住这几个关键词：

- **组件边界**：这个组件管什么、不管什么
- **受控/非受控思路**：哪些状态交给父组件，哪些留在组件内部

# 第3章 props 和 emit：把输入输出这点事讲透

做 Vue3 组件开发，最先绕不过去的就是两件事：**数据怎么进来**，**事件怎么出去**。  
很多组件写乱了，不是业务复杂，而是 **props 和 emit 没设计明白**。

老赵先把话挑明：一个组件要想好复用，第一件事不是“功能做多”，而是先想清楚——**组件边界在哪里，哪些东西外面传进来，哪些东西组件自己决定，哪些变化要通知外面**。这就是 props 和 emit 的基本功。

你可以把组件理解成一个小店铺：props 是顾客交来的需求单，emit 是处理完之后给顾客的反馈单。需求单写乱了，店员懵；反馈单发乱了，外面也不知道发生了什么。组件开发也是一样。

## 一、props 的作用、类型、默认值和校验：组件到底该接什么输入？

### 1. props 的作用是什么

props 是组件对外暴露的输入口，父组件传数据，子组件负责接收和使用。你也可以把它理解成组件参数：参数清楚，组件就清楚；参数混乱，组件就会变成一锅粥。

设计 props 时先问四个问题：

- 这个值是不是必须传？
- 默认值是什么？
- 允许什么类型？
- 它是不是组件边界内真正需要的输入？

核心原则只有一句：**props 只接组件真正需要的东西**。  
页面临时逻辑别硬塞进来，真正会决定组件行为的，才应该做成 props。

### 2. props 的类型、默认值和校验

Vue3 里定义 props，尽量把规则写清楚。比如一个 Switch 组件常见的输入有：

- `modelValue`：当前状态
- `disabled`：是否禁用
- `size`：尺寸
- `activeText` / `inactiveText`：文案

一般来说：

- `modelValue` 是核心输入
- `disabled`、`size` 是常规配置
- 文案是增强展示能力

写 props 时，尽量做到类型明确、默认值明确、必要性明确。比如 `disabled` 默认是 `false`，不传也能用；`modelValue` 往往是受控核心值，必须和外部状态对应。规则不清，后面排 bug 的还是你自己。

### 3. 为什么 props 不是越多越好

很多人喜欢给组件塞一堆 props，觉得“可配置性强”。老赵提醒你：**配置项多，不等于复用性强**。真正的复用，是配置围绕一个明确场景展开，而不是把所有可能都提前塞进去。

判断一个 props 是否该存在，就问一句：

> 这是不是组件边界内的核心输入？

如果不是，大概率应该交给业务层处理，而不是塞进组件里。按钮组件你非要加“请求成功后跳哪一页”这种 props，就已经越界了。组件边界一乱，后面维护会很痛苦。

### 可复用组件案例：基础 Switch 的 props 设计

一个可复用 Switch 通常只需要少量核心 props：

- `modelValue`: 开关状态
- `disabled`: 是否禁用
- `activeText`: 开启文案
- `inactiveText`: 关闭文案

这样设计的好处是输入简单、边界清晰、职责单一，后续扩展样式也容易。若要扩展，也优先加和开关强相关的能力，比如 `loading`、`activeColor`、`inactiveColor`，别把页面逻辑塞进来。

### 老赵常见踩坑提醒

**别把 props 当成随便塞配置的口袋。**  
props 不是越多越高级，很多组件难维护，就是因为开发时“什么都想支持”，最后边界越来越模糊。记住：**组件只接它真正负责的输入。**

## 二、emit 的作用、事件命名和参数传递：组件怎么把变化告诉外面？

### 1. emit 是干什么的

如果说 props 是“进来”，那 emit 就是“出去”。组件内部发生点击、切换、确认、取消，就通过 emit 通知父组件。

emit 解决的是：

- 子组件如何向父组件汇报状态变化
- 如何把用户动作暴露出去
- 组件如何保持内部逻辑和外部业务分离

说白了，emit 就是组件的汇报机制。子组件别自己把会影响外部业务的变化都决定了，必须告诉父组件。

### 2. 事件命名要统一、明确

事件名最好有规律，别今天 `change`，明天 `switchChange`，后天又来个 `toggle-state`。

常见建议：

- 用语义清晰的事件名：`change`、`update:modelValue`、`confirm`、`cancel`
- 双向绑定尽量遵循 `update:xxx`
- 事件名要和组件行为对得上

比如 Switch 组件里：

- 状态变化用 `update:modelValue`
- 单独通知业务变化用 `change`

`update:modelValue` 适合配合 `v-model`，`change` 适合“状态变了，你可以顺手做业务”。

### 3. 参数传递怎么设计

emit 可以带参数，常见有：

- 当前值，比如 `true / false`
- 触发来源，比如点击还是程序更新
- 业务补充信息，比如 id、索引

但别贪多。事件传参的目标是让外部知道“发生了什么”，不是把内部状态一股脑倒出去。优先传结果，少传过程细节。

### 可复用组件案例：Switch 的事件设计

Switch 可以这样设计：

- 用户切换时，emit `update:modelValue`
- 状态变化后，再 emit `change`

这样父组件既可以接 `v-model`，也可以监听变化做联动处理。表单里用来同步值，页面里用来触发业务，接口简洁但用途不单一，这才是好设计。

### 老赵常见踩坑提醒

**别把 emit 当成 props 的反向镜像，乱发一通。**  
事件太多、命名太散，会让组件对外接口失控。emit 不是“能发就发”，而是“该发才发”。

## 三、受控组件与非受控组件：这两个思路到底怎么选？

### 1. 什么是受控组件

**受控组件**就是：组件的核心状态由父组件控制，子组件只负责展示和发事件。

典型特征：

- 数据从外部传进来
- 子组件不自己偷偷改
- 每次变化都通知父组件
- 父组件决定最终状态

开关、输入框、分页当前页，这些都很适合受控设计，因为它们通常会影响表单提交、列表筛选、业务流程，状态必须可追踪、可统一管理。

### 2. 什么是非受控组件

**非受控组件**就是：组件内部自己维护状态，外部只传初始值或少量配置。

适合场景通常是：

- 很简单的本地交互
- 外部不需要精确接管状态
- 组件生命周期短、业务约束少

比如轻量提示、内部自管理的折叠面板，可能更偏非受控。

### 3. 怎么判断该受控还是非受控

判断标准很直接：

- 业务是否要求外部随时掌控状态？
- 状态变化是否会影响其他模块？
- 是否需要和表单、路由、权限联动？
- 是否存在“外部改了，组件也必须跟着变”的场景？

如果大多是“是”，优先受控。  
如果只是组件自己玩自己的，非受控也行。

简单说：**越是业务核心状态，越要受控；越是局部、临时、轻量的状态，越可以非受控。**

### 4. 受控与非受控的对比怎么落地

你可以这样判断：

- 值要参与提交、校验、回显，选受控
- 值只是自己展示，不影响外部流程，选非受控
- 两者都想要时，先把“默认受控”作为主方案，再考虑内部兜底

业务里最常见的矛盾，就是“组件内部想自己管，页面又想随时接管”。这时候别糊涂，**最终状态的裁判只能有一个**。

### 可复用组件案例：Switch 的两种实现方式

同一个 Switch，实际上可以做成两种模式：

#### 1）受控模式
外部传入 `modelValue`，内部只负责发 `update:modelValue`。

```vue
<template>
  <button :class="{ on: modelValue, disabled }" @click="toggle">
    {{ modelValue ? activeText : inactiveText }}
  </button>
</template>

<script setup>
const props = defineProps({
  modelValue: { type: Boolean, default: false },
  disabled: { type: Boolean, default: false },
  activeText: { type: String, default: '开' },
  inactiveText: { type: String, default: '关' }
})

const emit = defineEmits(['update:modelValue', 'change'])

function toggle() {
  if (props.disabled) return
  const next = !props.modelValue
  emit('update:modelValue', next)
  emit('change', next)
}
</script>
```

这个版本适合表单、筛选、设置页。因为状态必须由外部统一管理，组件只是执行动作。

#### 2）非受控模式
组件内部自己维护状态，外部只传一个初始值。

```vue
<template>
  <button :class="{ on: innerValue, disabled }" @click="toggle">
    {{ innerValue ? activeText : inactiveText }}
  </button>
</template>

<script setup>
import { ref, watch } from 'vue'

const props = defineProps({
  defaultValue: { type: Boolean, default: false },
  disabled: { type: Boolean, default: false },
  activeText: { type: String, default: '开' },
  inactiveText: { type: String, default: '关' }
})

const emit = defineEmits(['change'])
const innerValue = ref(props.defaultValue)

watch(
  () => props.defaultValue,
  (val) => {
    innerValue.value = val
  }
)

function toggle() {
  if (props.disabled) return
  innerValue.value = !innerValue.value
  emit('change', innerValue.value)
}
</script>
```

这个版本适合本地展示、独立交互、外部不关心最终状态的场景。

#### 3）两者怎么选
老赵建议你记住一句话：

- **业务核心状态，用受控**
- **局部临时状态，用非受控**
- **如果两者都要，优先把受控模式做好，再补默认值兜底**

这就是组件设计里的业务决策，不是 API 选择题。

### 老赵常见踩坑提醒

**别以为非受控更省事，很多后期 bug 都是状态没统一导致的。**  
一个组件一会儿自己改状态，一会儿又听外部指令，最后谁说了算都不清楚。状态管理最怕“既要又要还要”。

## 四、直接改 props 会怎样翻车：一个最常见、也最容易忽略的坑

### 1. 错误实现长什么样

很多初学者会在组件内部直接改 props。看起来好像能跑，实际上是在给自己埋雷。

```vue
<script setup>
const props = defineProps({
  modelValue: Boolean
})

function toggle() {
  // 错误示范：直接改 props
  props.modelValue = !props.modelValue
}
</script>
```

这个写法问题很大：

- props 是父组件传下来的，只读约定明确
- 子组件直接改，表面变了，外部数据可能没变
- 组件内外状态就开始不同步

你这边看着开了，父组件那边还以为是关的，用户一刷新或者一切换，状态立马对不上。

### 2. 为什么会翻车

因为 Vue 组件的数据流本来就应该是：

- 父组件传值给子组件
- 子组件通过 emit 把变化告诉父组件
- 父组件更新自己的状态，再传回来

你直接改 props，相当于绕过了这个流程。结果就是：

- 组件内部状态和外部状态不一致
- 调试时很难发现问题根源
- 一旦有重置、回显、校验、联动，bug 特别顽固

### 3. 正确写法是什么

正确做法不是“偷偷改”，而是：

1. 先计算出新值
2. 用 emit 发给父组件
3. 由父组件更新 `v-model` 或状态
4. 组件重新接收新 props

```vue
<script setup>
const props = defineProps({
  modelValue: Boolean
})

const emit = defineEmits(['update:modelValue', 'change'])

function toggle() {
  const next = !props.modelValue
  emit('update:modelValue', next)
  emit('change', next)
}
</script>
```

这才是受控组件的标准路径。你不是在改数据，而是在申请修改。

### 可复用组件案例：Switch 的安全切换逻辑

把 Switch 做成受控组件后，它能稳定适配：

- 表单开关
- 用户设置
- 筛选条件
- 列表状态切换

因为它不抢控制权，所以别的业务接进来也不容易翻车。

### 老赵常见踩坑提醒

**别直接改 props，别把双向绑定玩乱。**  
双向绑定不是“我想怎么改就怎么改”，而是“父子协商后同步状态”。你一旦绕过 emit，后面状态不同步就是迟早的事。

## 五、父子组件之间的数据流设计：输入输出到底怎么走才顺？

### 1. 父子数据流的基本原则

在 Vue 组件设计里，最舒服的数据流通常是：

- 父组件提供数据
- 子组件负责展示和触发动作
- 子组件通过 emit 把变化告诉父组件
- 父组件决定是否更新状态

本质上就是：**单向输入，事件输出**。这样关系清楚，不容易互相缠死。

### 2. 组件边界要先定好

组件边界是老赵最强调的点。你得先知道：

- 哪些数据属于组件内部
- 哪些数据属于外部业务
- 哪些状态只是展示，不该让外部操心
- 哪些状态必须交给父组件统一管理

边界一乱，props 和 emit 也会跟着乱。

比如搜索框组件，如果把“查询接口地址”也塞进去，它就不再是搜索框，而是半个页面组件。真正可复用的搜索框，只管输入、清空、触发搜索；接口地址、查询条件拼装，应该交给页面层。

### 3. 什么时候该把状态抬高

如果一个状态会被多个组件共享，或者会影响表单提交、列表筛选、弹窗流程，那就该考虑交给父组件或更上层管理。

简单说：

- 单组件内能解决的，别上升
- 会影响业务流程的，尽量受控

这也是可复用业务组件的核心原则。你不是在写“什么都能管”的万能组件，而是在写“职责明确、边界稳定”的组件。

### 4. 反例：把页面逻辑塞进基础组件会怎样

老赵见过最常见的坑，就是把接口请求、路由跳转、权限判断这些页面逻辑，直接塞进基础组件里。

比如一个输入框组件，除了输入和清空，还负责：

- 调接口搜数据
- 判断权限
- 控制路由跳转

看起来一组件全包，实际上以后别的页面根本没法复用。因为别的页面不需要它的业务逻辑，只需要它的输入能力。**基础组件一旦混入页面职责，边界就崩了。**

### 可复用组件案例：Switch 在表单中的接入

在表单里，Switch 最好不要自己决定最终值。它只负责：

- 展示当前状态
- 响应点击
- 向外发出变化

真正保存、校验、提交，交给表单层处理。这样后面做重置、回显、校验时，逻辑都顺着走，不会出现“组件内部关了，表单数据还开着”的怪事。

### 老赵常见踩坑提醒

**别让子组件偷偷改父组件数据，也别让父组件到处扒子组件内部状态。**  
这种双向乱流，一开始看着省代码，后面一定难维护。数据流越清楚，组件越好用；数据流越乱，bug 越像野草。

## 六、一个可复用组件的基础文档怎么写：让别人接得上、用得稳

### 1. 为什么要写简单文档

可复用组件不是你一个人用。只要组件准备给团队、给后续项目、给自己两个月后再看，就最好补一份最基础的文档。

文档不用长，但要完整回答几个问题：

- 这个组件是干什么的？
- 需要传什么 props？
- 会发什么事件？
- 支持哪些插槽或特殊配置？
- 受控还是非受控？
- 最小示例怎么写？

### 2. 一个最小模板长什么样

你可以先按这个结构写：

#### 组件名称
比如：`Switch`

#### 组件用途
用于表示开关状态，支持受控模式，适合表单、筛选、设置项。

#### Props
- `modelValue`：当前值，Boolean，默认 `false`
- `disabled`：是否禁用，Boolean，默认 `false`
- `activeText`：开启时文案，String，默认 `开`
- `inactiveText`：关闭时文案，String，默认 `关`

#### Events
- `update:modelValue`：切换状态时触发
- `change`：状态变化后触发

#### 使用示例
```vue
<template>
  <Switch v-model="open" activeText="启用" inactiveText="停用" />
</template>
```

#### 注意事项
- 不要直接修改 `modelValue`
- 表单场景优先使用受控模式
- 如果要做默认值初始化，建议在父组件统一处理

### 3. 文档写得好，复用才真能落地

很多组件不是不能复用，而是没人敢接。原因很简单：接口不清、行为不明、边界不稳。  
你把文档写清楚，别人一看就知道：

- 这个组件怎么用
- 哪些值该传
- 哪些别乱改
- 出问题先看哪里

这其实就是组件工程化的起点。

### 可复用组件案例：Switch 的基础文档

一个好的 Switch 文档，至少应该让人一眼看出：

- 它支持 `v-model`
- 它有哪些文案和禁用配置
- 它发什么事件
- 它适合什么场景

文档不求花哨，但求别人能直接抄示例跑起来。

### 老赵常见踩坑提醒

**别只写代码不写说明。**  
你自己写的时候当然懂，过两天别人接手、或者你自己回头再看，没文档就等着翻源码。可复用组件越多，文档越不能省。

## 七、结尾小结：写好 props 和 emit，组件才算真正“能用”

这一章讲下来，核心其实就一句话：

> 组件设计，不是先想“我能写出多少功能”，而是先想“输入是什么、输出是什么、边界在哪里”。

你可以把这章的方法记成一个检查清单：

- props 是否明确了组件输入？
- 默认值和类型是否写清楚？
- emit 是否表达了真实行为？
- 事件名是否统一？
- 组件是受控还是非受控？
- 数据流是否单向清楚？
- 组件边界是否稳定？
- 有没有简单文档说明用法？

老赵最后送你一句实在话：**写组件，别急着堆功能，先把输入输出理顺。**  
输入输出清楚了，组件就不会乱；组件不乱，复用才有意义；复用有意义，业务组件才真能长期维护。

下一章，我们继续把 slot 插槽讲透。你会发现，**props 负责“给什么”，slot 负责“放什么”**，这俩搭配起来，组件才真正开始有弹性。

# 第4章 slot 插槽：把组件留出入口，才有复用空间

## 开篇引入：为什么一个好组件，先要学会“留口子”

老赵先说个实在的：**组件不是越封死越好，很多高复用组件的价值，就在于它愿意给外部留入口。** 这个入口，在 Vue3 里最常见的就是 `slot`。

你可以把组件理解成一个盒子：

- 有些盒子里面东西固定，拿来就用；
- 有些盒子只负责提供结构，里面放什么由外部决定。

前者适合纯展示、纯逻辑组件；后者就特别适合插槽。尤其在做**容器组件、布局组件、提示组件**时，slot 往往比一堆 `props` 更自然，也更能守住组件边界。

这一章我们就把这件事讲透：**slot 是什么，什么时候该用，什么时候别硬上，以及怎么用它做一个真正可复用的 Panel 组件。** 另外，咱们还要补一块很重要的内容：**插槽和组件边界到底是什么关系，怎么判断该不该开放入口。** 这部分搞明白了，后面你做弹窗、列表、表格、分页时，心里就会稳很多。

---

## 1. slot 是什么，适合解决什么问题？

### 1.1 slot 的本质：让父组件把内容“塞进来”

`slot` 就是组件预留的内容出口。子组件先搭好结构，父组件再决定某一块区域里放什么内容。

最简单的默认插槽：

```vue
<!-- Panel.vue -->
<template>
  <div class="panel">
    <div class="panel-header">标题区</div>
    <div class="panel-body">
      <slot />
    </div>
  </div>
</template>
```

父组件使用：

```vue
<Panel>
  <p>这里是我想放进去的内容</p>
</Panel>
```

`Panel` 负责容器结构，真正内容由外部决定。  
这就是插槽最核心的价值：**把“结构”和“内容”解耦。**

所以组件边界也会更清楚：

- 子组件负责外壳、样式、布局规则；
- 父组件负责业务内容、内容顺序和具体表达。

这对高复用业务组件特别重要。很多时候我们写的不是“某个页面专用组件”，而是“未来多个页面都可能复用的组件”。这时候，内容如果写死，复用性就差；内容如果全靠 `props` 拼，又容易变成一堆配置参数。slot 正好夹在中间，既开放又克制。

### 1.2 slot 适合解决什么问题？

slot 主要解决两类痛点：

1. **内容不固定，但结构固定**  
   比如卡片、面板、弹窗、提示框、布局区块。

2. **子组件不想知道父组件的业务内容**  
   组件越通用，越不能把业务文案、业务表单、业务列表写死在内部。

这就是高复用组件的关键：**不是写一个能跑的组件，而是写一个别人愿意反复用的组件。**

### 1.3 真实业务场景：为什么这里用插槽比把内容写死更合理？

老赵给你举个常见后台场景：**用户详情页的资料面板**。

这个面板外层样式基本固定：

- 有标题栏；
- 有统一边框和间距；
- 有底部操作区；
- 中间是主体内容。

但不同页面里，主体内容可能完全不同：

- A 页面是基础信息 + 标签；
- B 页面是表单编辑；
- C 页面是审批记录；
- D 页面是图文说明。

如果你把内容写死在组件里，那它只能服务一种页面。  
如果你用很多 `props` 去拼，最后就会变成一堆配置项，组件越写越像“接口大全”。  
这时候用插槽更合理：**外壳固定，内容开放。**

也就是说，`slot` 不是为了“看起来高级”，而是为了让组件边界更清楚：  
**面板负责壳，业务页面负责内容。** 这才是高复用业务组件该有的样子。

### 1.4 可复用组件案例：最基础的内容容器

```vue
<!-- BaseBox.vue -->
<template>
  <section class="base-box">
    <slot />
  </section>
</template>
```

这个组件很简单，但已经具备复用雏形：

- 不绑定具体业务；
- 不强制内部布局；
- 只提供一个稳定容器。

使用时可以放文字、图片、表单、列表，甚至另一个组件：

```vue
<BaseBox>
  <UserCard />
</BaseBox>
```

它体现的就是：**只提供边界，不替外部决定内容。**

### 老赵常见踩坑提醒

**slot 不是“随便塞东西”的万能口袋。**  
如果组件职责很明确，比如只是“确认删除按钮”，你还硬开 slot，让别人传一堆内容进去，最后就会变成四不像。  
记住：**能用 slot，不代表应该用 slot。**

---

## 2. 插槽使用场景：容器组件、布局组件、提示组件

### 2.1 容器组件：只负责包裹，不负责内容

容器组件最适合 slot。比如 Panel、Card、Box、CardSection 这一类。它们通常有：

- 稳定的视觉结构；
- 经常变化的内容；
- 希望外部自由组合。

典型场景：

- 页面内容卡片；
- 搜索区包裹；
- 业务模块块状容器；
- 左右布局里的内容盒子。

判断一个组件是不是容器组件，先看它有没有“外壳感”：

- 有边框、有阴影、有间距；
- 结构固定；
- 里面放什么都不影响外观逻辑。

这种就很适合 slot。

### 2.2 布局组件：结构强，内容弱

布局组件往往有多个区域，比如顶部、侧边、主体、底部。  
这时 slot 比单纯 `props` 更合适，因为每个区域放什么，外部更清楚。

```vue
<Layout>
  <template #header>顶部导航</template>
  <template #default>主内容</template>
  <template #footer>底部信息</template>
</Layout>
```

布局组件的重点不是“我里面写死什么”，而是“我给你几个稳定位置，你自己填”。  
它特别适合页面骨架、后台系统布局、详情页结构。

### 2.3 提示组件：结构统一，内容可变

像公告条、温馨提示、说明块、错误提示区，也很适合 slot。因为提示组件通常有统一视觉风格，但内容来自不同页面、不同业务。比如内容里可能有：

- 超链接
- 加粗
- 换行
- 操作按钮

这时 slot 比传字符串更灵活。

### 2.4 可复用组件案例：提示框 NoticeBox

```vue
<!-- NoticeBox.vue -->
<template>
  <div class="notice-box">
    <div class="notice-icon">i</div>
    <div class="notice-content">
      <slot />
    </div>
  </div>
</template>
```

使用方式：

```vue
<NoticeBox>
  请先完成实名认证，再进行后续操作。
</NoticeBox>
```

未来如果要扩展成带按钮、带链接、带多段文字，这种结构也很好扩展，组件内部逻辑不用大改。

### 老赵常见踩坑提醒

**提示组件最容易被写成“文字写死的样板间”。**  
一旦业务变化，文案、按钮、链接都变了，你就得改组件源码。  
本来该开放的入口没留，最后只能复制粘贴到处散。

---

## 3. 什么时候该用插槽，什么时候别硬上？

### 3.1 适合用插槽的判断标准

老赵给你一个很实用的判断法：只要满足下面任意两条，就可以考虑 slot。

- 内容不确定
- 内容可能很复杂
- 需要保留外部结构自由度
- 组件主要职责是提供容器或布局
- 未来很可能有扩展需求

比如 Card、Panel、Modal、Empty、Notice 这类，slot 往往比 `props` 更顺手。

### 3.2 不适合硬上插槽的场景

有些组件不该为了“可复用”而过度开放。

#### 1）内容非常固定

比如“退出登录确认按钮”，它就是一个小功能组件。  
这时候强行上 slot，只会把它变成一个没有边界的空壳。

#### 2）只需要简单文本

比如“网络异常，请稍后重试”，直接用 `props` 传文案就够了。别为了几个字引入 slot。

#### 3）组件业务规则非常明确

例如表单项校验、分页页码切换、固定权限提示。  
这类组件核心是逻辑稳定，内容开放反而容易破坏一致性。

### 3.3 判断清单：什么时候该用，什么时候不该用

#### 适合用插槽
- 内容是可变的
- 内容是富结构的
- 组件负责的是外壳或布局
- 外部需要自定义内容顺序
- 组件会被多个页面复用

#### 不该硬上插槽
- 内容固定且简单
- 只是一个明确动作按钮
- 开放后会破坏交互规则
- 为了“看起来灵活”而增加复杂度
- 组件本身就不打算复用太多场景

### 3.4 可复用组件案例：简单说明块 ExplainBox

```vue
<!-- ExplainBox.vue -->
<template>
  <div class="explain-box">
    <slot />
  </div>
</template>
```

这个组件适合承载说明内容、使用帮助、规则提醒。  
如果只是单纯文本，直接用；如果需要富内容，也能自然扩展。

适用场景：

- 表单填写说明
- 操作步骤提示
- 导入导出规则
- 页面功能介绍

### 老赵常见踩坑提醒

**别一上来就想“以后可能复杂，所以我先全开放”。**  
这是典型过度设计。今天留十个 slot，明天发现只有一个在用，剩下九个全是摆设，维护成本反而更高。

---

## 4. 插槽与组件边界的关系：入口开放，不等于职责无限扩张

### 4.1 插槽不是开放越多越好，而是边界更清楚

组件边界的本质是：**哪些事情组件自己负责，哪些事情交给外部决定。**

- 组件自己负责：结构、样式骨架、交互规则、基础状态
- 外部决定：具体内容、业务文案、复杂渲染、个性化区域

slot 只是边界的一种表达方式。它不是让组件更松散，而是让职责划分更明确。

你可以把它理解成：组件不是把门拆了，而是在门上留了几个合适的窗户。

### 4.2 什么时候边界该收，什么时候该放

#### 收紧边界
当组件核心规则不能乱改时，要收边界。  
比如按钮禁用状态、弹窗关闭逻辑、分页跳转逻辑。

#### 放开边界
当只是展示层面的差异时，可以放开边界。  
比如标题内容、正文内容、底部说明、空状态文案。

所以，slot 的真正作用不是“让一切都可定制”，而是**让最该变化的部分变化，最不该变化的部分稳定。**

### 4.3 真实业务里的边界感：别让插槽把组件带跑偏

比如一个“审批提示条”组件，真正应该固定的是：

- 视觉风格
- 提示语气
- 状态颜色
- 统一的图标位置

而应该交给外部变化的是：

- 具体说明文案
- 补充链接
- 操作按钮文案

如果你把整块结构都交给外部塞内容，那这个组件就不再是“提示条”，而只是一个空容器。  
这时候复用不是增强了，而是边界被冲垮了。  
**入口可以开，但职责不能散。**

### 4.4 可复用组件案例：业务公告容器

```vue
<!-- BusinessBanner.vue -->
<template>
  <div class="business-banner">
    <strong>系统公告</strong>
    <div class="business-banner__body">
      <slot />
    </div>
  </div>
</template>
```

它把“公告样式”固定住，把“公告内容”交出去。  
后面要换文案、换链接、换排版，都不用动组件结构。

### 老赵常见踩坑提醒

**有些人把 slot 当成“我不想想内容怎么设计”的借口。**  
结果组件内部什么都不管，样式也靠外面补，最后谁用谁痛苦。  
记住：**开放入口，不等于放弃设计。**

## 5. 组件案例：一个可复用的 Panel 容器组件

### 5.1 组件目标

这个 Panel 要做到：

- 有统一外壳；
- 标题可选；
- 内容可插入；
- 支持底部操作区；
- 结构稳定，使用简单。

这类组件在后台项目里特别常见，基本每个页面都能碰到。

### 5.2 组件实现

```vue
<!-- Panel.vue -->
<template>
  <section class="panel">
    <header v-if="$slots.header" class="panel__header">
      <slot name="header" />
    </header>

    <main class="panel__body">
      <slot />
    </main>

    <footer v-if="$slots.footer" class="panel__footer">
      <slot name="footer" />
    </footer>
  </section>
</template>

<style scoped>
.panel {
  border: 1px solid #e5e7eb;
  border-radius: 8px;
  background: #fff;
  overflow: hidden;
}
.panel__header,
.panel__footer {
  padding: 12px 16px;
  background: #f9fafb;
}
.panel__body {
  padding: 16px;
}
</style>
```

这里两个细节很关键：

1. `v-if="$slots.header"` 和 `v-if="$slots.footer"`  
   插槽有内容时才渲染对应区域，避免空壳结构。

2. `default`、`header`、`footer` 三个区域分工明确  
   这就是典型的组件边界设计。

### 5.3 使用方式

```vue
<Panel>
  <template #header>
    用户信息
  </template>

  <UserProfile />

  <template #footer>
    <button>保存</button>
  </template>
</Panel>
```

这个组件好就好在：

- 结构清楚；
- 使用方知道哪里放标题、哪里放正文、哪里放操作；
- 未来样式调整，只改 Panel 内部；
- 外部业务内容完全独立。

也就是说，`Panel` 管壳子，`UserProfile` 管内容，按钮区管动作。各管各的，才不会打架。

### 5.4 这个 Panel 的复用价值在哪里？

它不是“功能很多”，而是“职责稳定”。  
这类组件最适合沉淀到项目基础层，因为很多页面都会用到：

- 详情页信息块
- 设置页分组
- Dashboard 卡片
- 列表区包裹

真正的高复用，不是通吃所有场景，而是稳定覆盖一类场景。

### 5.5 如何给这种组件写简单文档？

可复用组件如果没有简单说明，最后就会变成“只有作者敢用”。

建议最少写清这几项：

- **组件用途**：用于承载标题、内容和底部操作的容器
- **插槽说明**：
  - `default`：正文内容
  - `header`：标题区
  - `footer`：底部操作区
- **使用示例**：给出最常见的用法
- **注意事项**：不要在 header/footer 放太重的业务逻辑

再补一句适用场景也很有用：

- 适合详情块、卡片区、设置区；
- 不适合复杂强交互的大型页面壳。

### 老赵常见踩坑提醒

**Panel 最容易被写成“啥都能塞，啥都不管”的万能框。**  
一旦大家开始往里塞复杂表单、巨型列表、各种条件渲染，组件边界就塌了。  
记住：**容器组件是容器，不是业务大杂烩。**

## 6. 结尾小结：slot 的核心，不是开放，而是克制地开放

这一章你要真正记住的，不是 slot 的语法，而是它背后的设计思路。

### 老赵给你收个口：

1. **slot 解决的是“内容不固定，但结构固定”的问题。**
2. **适合容器组件、布局组件、提示组件。**
3. **是否使用插槽，先看组件边界，再看复用需求。**
4. **不要为了复用而过度开放，也不要为了省事把内容写死。**
5. **高复用组件不是功能堆出来的，是边界设计出来的。**
6. **写组件文档别整太复杂，至少说清用途、插槽、示例和注意事项。**

### 你可以立刻去做的事

拿你项目里的一个卡片、公告条、说明框、Panel，问自己三个问题：

- 这个组件里哪些内容是固定的？
- 哪些内容应该由外部决定？
- 我是不是可以用默认插槽，先把结构和内容分开？

如果这三个问题能答明白，slot 这一章就算真正入门了。

### 老赵常见踩坑提醒

**插槽不是万能填空题，更不是“我懒得设计”的借口。**  
真正成熟的组件设计，不是把入口开满，而是知道该在哪里开口、开多大口、留给谁用。  
这才是 Vue3 组件复用的第一层功夫。

# 第5章 具名插槽与作用域插槽：让复杂内容也能好好装进去

## 开篇引入：为什么复杂组件一定会走到插槽这一步

前面讲默认插槽，解决的是“把一坨内容塞进去”。但一到表格、弹窗、卡片列表、筛选面板这种业务组件，你很快就会发现：**一个位置不够用，子组件还得把内部数据往外抛**。这时候，具名插槽和作用域插槽就必须上场了。

老赵先把话说透：**插槽不是炫技，是为了把组件边界划清楚。**  
父组件负责业务定制，子组件负责结构和能力，插槽就是两边的接口。接口设计得好，组件就能复用；接口一乱，组件就会变成“什么都能传，最后什么都不好维护”。

你可以把它理解成：子组件像装修好的房子，插槽就是预留的门、窗、柜位；父组件负责把自己的业务内容放进去。

本章就拿最典型的场景来说：**一个可定制的 Table 表格壳子组件**。它最适合讲清楚具名插槽、作用域插槽、业务定制能力，以及插槽 API 怎么设计才不把自己绕进去。

---

## 一、具名插槽：多个内容区域怎么组织才不乱？

### 1.1 具名插槽解决的是什么问题？

默认插槽只有一个入口，适合整块内容替换。但很多复杂组件不是一个洞，而是多个区域都要给外部定制，比如：

- 表格工具栏
- 表头操作区
- 每行操作列
- 底部分页
- 弹窗标题、内容、底部按钮

如果还用默认插槽硬塞，代码很快就乱：父组件像拼作文，子组件也不知道每块内容该放哪。

**具名插槽的作用就是：给不同区域起名字，让内容各回各家。**

### 1.2 适合哪些场景？

判断很简单：

- 组件内部有多个可替换区域
- 不同区域职责不一样
- 你希望父组件按位置精准注入内容
- 你不想让父组件整块接管子组件结构

典型场景：`Table` 的 `toolbar/body/footer/empty`，`Modal` 的 `title/body/footer`，`FormPanel` 的 `prepend/append/tips`。

### 1.3 基本写法

子组件先把坑位摆好：

```vue
<template>
  <div class="table-shell">
    <div class="table-toolbar">
      <slot name="toolbar" />
    </div>

    <div class="table-body">
      <slot />
    </div>

    <div class="table-footer">
      <slot name="footer" />
    </div>
  </div>
</template>
```

父组件按名字投放内容：

```vue
<TableShell>
  <template #toolbar>
    <button>新增</button>
    <button>导出</button>
  </template>

  <template #default>
    <div>表格主体内容</div>
  </template>

  <template #footer>
    <div>分页区域</div>
  </template>
</TableShell>
```

好处很直接：父组件一眼能看懂，子组件结构也清楚。

### 1.4 可复用组件案例：表格壳子的区域划分

一个表格壳子，最常见的区域就是：

- 顶部工具栏：搜索、筛选、操作按钮
- 中间表格主体：数据展示
- 底部分页：翻页、条数选择
- 空状态：无数据展示

把这些区域拆成具名插槽，表格就只负责壳子和布局，业务内容按区域填进去，复用起来会舒服很多。

### 1.5 老赵常见踩坑提醒

**坑：具名插槽命名太随意。**  
今天叫 `top`，明天叫 `header`，后天又改成 `toolbar`，父组件全跟着改。  
建议一开始就按“区域职责”命名，并保持长期一致。组件 API 最怕的不是功能少，而是名字乱。

---

## 二、作用域插槽：子组件怎么把数据优雅地交给外部？

### 2.1 解决的是什么问题？

具名插槽只解决“放哪里”，但很多时候父组件还想知道子组件内部状态，比如当前行数据、当前页码、某个状态字段。光有位置还不够，**还得把子组件的数据暴露给外部使用**。这就是作用域插槽的价值。

一句话：**作用域插槽 = 子组件提供数据，父组件决定怎么渲染。**

### 2.2 典型场景

- 表格每行的操作按钮依赖当前行数据
- 列表卡片渲染依赖 item
- 弹窗底部按钮依赖校验状态
- 分页组件向外暴露当前页、总数、切换方法

这些场景里，父组件不是单纯“放内容”，而是要基于子组件提供的数据做定制。

### 2.3 写法

子组件：

```vue
<template>
  <div v-for="(row, index) in data" :key="row.id">
    <slot name="row-actions" :row="row" :index="index" />
  </div>
</template>
```

父组件：

```vue
<TableShell :data="list">
  <template #row-actions="{ row, index }">
    <button @click="edit(row)">编辑</button>
    <button @click="remove(row.id)">删除 {{ index }}</button>
  </template>
</TableShell>
```

父组件拿到 `row` 和 `index`，就能按业务定制按钮、文案和逻辑。子组件不关心“编辑按钮什么时候出现”，只负责把数据传出来。

### 2.4 判断标准

适合用作用域插槽的情况：

- 子组件内部有一份数据，但不想把渲染写死
- 父组件需要基于子组件状态做个性化展示
- 某块 UI 看起来固定，实际上内容和行为都高度业务化

不适合滥用的情况：

- 只是想传几个普通配置项
- 只是想让父组件拿到一两个静态值
- 本来用 `props` 就能解决，却偏要搞插槽

老赵提醒一句：**作用域插槽不是“更高级的 props”，它是“把渲染权交出去”。**  
如果只是传值，优先考虑 `props`；如果是把某块 UI 的表现方式也交给父组件，那才用作用域插槽。

### 2.5 可复用组件案例：行操作区

表格里最实用的就是“行操作区”：

```vue
<template #row-actions="{ row }">
  <button v-if="row.status === 'draft'">发布</button>
  <button>编辑</button>
  <button>删除</button>
</template>
```

子组件只负责把 `row` 暴露出来，至于展示什么按钮、是否禁用，都交给父组件。  
这就是高复用组件的味道：**结构固定，业务灵活。**

### 2.6 老赵常见踩坑提醒

**坑：插槽参数传太多，最后连自己都不会用了。**  
一开始你可能觉得“多传点方便”，于是塞进来 `row`、`index`、`selected`、`hovered`、`toggle`、`meta`……  
结果父组件每次都要解构一大坨，子组件也不知道哪些参数是核心。  
老赵建议：**作用域插槽只暴露当前插槽真正需要的最小数据集。**

---

## 三、插槽与业务定制能力：为什么有些组件天生更好复用？

### 3.1 插槽本质上在增强什么能力？

插槽不是语法糖，而是在增强组件的**业务定制能力**。  
组件越通用，越要把“结构”和“内容”分开：

- 结构由组件提供
- 业务内容由外部注入

这样组件就不会被某个项目的具体需求锁死。

### 3.2 组件边界怎么借助插槽来划分？

这里最关键的是**组件边界**。

你可以这样理解：

- 子组件边界内：样式、布局、通用交互、通用状态
- 子组件边界外：具体文案、业务按钮、特殊逻辑、定制渲染

当一个组件开始“什么都想管”，说明边界已经模糊了。  
插槽的作用就是把边界重新划回来。

比如列表组件可以负责卡片排列、loading、空状态、分页，但每张卡片长什么样、按钮显示什么，最好交给插槽。这样组件不会被业务细节拖垮。

### 3.3 可复用组件案例：通用列表壳子

一个通用列表组件可以固定：

- 列表容器
- 空状态
- 分页位置
- 加载状态

同时开放：

- `header`
- `item`
- `empty`
- `footer`

这样不同业务都能复用，只改内容，不改骨架，特别适合后台管理系统。

### 3.4 老赵常见踩坑提醒

**坑：为了“通用”，把组件做成大杂烩。**  
看起来什么都支持，实际上每个业务都得传一堆插槽，维护成本直线上升。  
真正的高复用不是“功能最多”，而是“边界最清晰”。

---

## 四、插槽 API 设计：怎么设计才更好用？

### 4.1 一个好插槽 API 的标准

老赵给你一个实用标准：

1. 名字一看就懂
2. 数量尽量少
3. 默认行为要合理
4. 暴露数据要克制
5. 文档要写清楚每个插槽放什么

如果一个组件的插槽 API 连自己团队的人都要猜，那基本就是设计失败。

### 4.2 设计步骤

#### 第一步：先想区域，不要先想字段
先从组件结构出发，问自己：有哪些天然区域？哪些地方需要外部定制？

#### 第二步：先设计默认值
不是所有地方都要插槽。能默认渲染的，尽量默认渲染，插槽留给真正变化大的部分。

#### 第三步：插槽参数只暴露必要信息
比如表格行操作区，只给 `row` 就够了，别一口气把整张表的上下文全塞进去。

#### 第四步：补一份简单文档
最少写清楚：

- 有哪些插槽
- 每个插槽的位置和用途
- 插槽能拿到什么参数
- 有没有默认内容

### 4.3 可复用组件案例：Table 插槽说明文档

可以这样写：

- `toolbar`：表格顶部工具栏
- `body`：表格主体区域，默认渲染表格
- `row-actions`：每行操作区，参数 `{ row, index }`
- `empty`：空状态展示
- `footer`：底部区域

补文档这件事别嫌麻烦，真正落地时，它决定了别人能不能五分钟接上这个组件。  
简单文档不是写给老板看的，是写给未来的你、队友、接手人看的。

### 4.4 老赵常见踩坑提醒

**坑：只写实现，不写文档。**  
组件自己能跑，不代表别人能用。  
可复用组件最怕“作者离职，组件失语”。简单文档一定要配上，不然再漂亮的插槽设计也会变成半成品。

---

## 五、组件案例：一个可定制的 Table 表格壳子组件

### 5.1 需求拆解

我们要做的不是完整数据表格，而是一个**表格壳子**，它负责：

- 统一外框和布局
- 提供顶部工具栏
- 提供表格主体区域
- 提供底部分页或附加信息
- 允许外部定制每行操作区和空状态

这类组件最适合做成“结构稳定、内容可插拔”的模式。

### 5.2 组件结构示意

```vue
<template>
  <div class="table-shell">
    <div class="table-shell__header">
      <slot name="toolbar" />
    </div>

    <div class="table-shell__body">
      <slot name="body">
        <table>
          <thead>
            <tr>
              <th>名称</th>
              <th>状态</th>
              <th>操作</th>
            </tr>
          </thead>
          <tbody>
            <tr v-for="(row, index) in data" :key="row.id">
              <td>{{ row.name }}</td>
              <td>{{ row.status }}</td>
              <td>
                <slot name="row-actions" :row="row" :index="index" />
              </td>
            </tr>
          </tbody>
        </table>
      </slot>
    </div>

    <div class="table-shell__footer">
      <slot name="footer" />
    </div>

    <div class="table-shell__empty" v-if="!data.length">
      <slot name="empty">暂无数据</slot>
    </div>
  </div>
</template>
```

这个设计的好处是：

- 默认有一个可用表格
- 外部可以替换 `body`
- 外部可以单独定制 `toolbar` 和 `footer`
- 行操作通过作用域插槽完成
- 空状态也可以交给外部统一定制

### 5.3 业务场景里的用法

比如商品列表页，顶部放筛选和新增按钮，主体显示商品表格，每行操作根据状态变化：

```vue
<TableShell :data="list">
  <template #toolbar>
    <button @click="create">新增商品</button>
    <button @click="exportList">导出</button>
  </template>

  <template #row-actions="{ row }">
    <button v-if="row.status === 'draft'">上架</button>
    <button @click="edit(row)">编辑</button>
    <button @click="remove(row.id)">删除</button>
  </template>

  <template #footer>
    <Pagination :total="total" />
  </template>
</TableShell>
```

这就是典型的业务型高复用组件：骨架统一，内容灵活。

### 5.4 为什么它可复用？

因为它只锁定了“表格壳子”的职责，没有把业务字段、按钮逻辑、搜索条件写死。  
不同页面只需要换工具栏按钮、行操作内容、空状态、分页内容，组件骨架不动，业务内容随项目变化，这才叫复用。

### 5.5 老赵常见踩坑提醒

**坑：把数据请求、分页逻辑、筛选逻辑全塞进表格组件里。**  
这样一来，表格就不再是表格壳子，而成了“超级业务容器”。  
正确做法是：**表格负责展示和插槽，数据和业务流程尽量交给外层。**

---

## 六、作用域插槽的进阶场景：把“展示权”交出去，但别把“控制权”也丢了

### 6.1 典型业务场景：列表卡片的自定义展示

除了表格，列表卡片也特别适合作用域插槽。比如商品卡片组件内部已经拿到了 `item`、`selected`、`loading` 这些状态，但每个业务页面想展示的内容不一样。

这时组件可以把当前项暴露出去：

```vue
<ListShell :items="items">
  <template #item="{ item, index }">
    <div class="card">
      <h3>{{ index + 1 }}. {{ item.name }}</h3>
      <p>价格：{{ item.price }}</p>
      <button @click="buy(item)">购买</button>
    </div>
  </template>
</ListShell>
```

子组件负责列表的骨架、滚动、分页、空状态，父组件负责每张卡片怎么长相。  
这就很适合后台系统、内容平台、商品管理这些场景。

### 6.2 “展示权”和“控制权”的边界

老赵要提醒你：  
作用域插槽能把“展示权”交给外部，但**控制权不要轻易交出去**。

比如分页组件可以暴露当前页和切页方法，但它自己的页码边界校验、切换节流、异常处理，最好还是在内部完成。  
不然父组件一接管，组件就很快变成“大家都能改，最后谁都不敢改”。

### 6.3 可复用组件案例：状态驱动的列表项渲染

一个不错的模式是：

- 子组件负责统一状态：loading / empty / normal
- 父组件只定制 item 插槽
- 子组件提供 `item`、`index`、`active` 等最小参数

这样既保留灵活度，又不把组件 API 搞得太散。

### 6.4 老赵常见踩坑提醒

**坑：把插槽当成万能后门，什么逻辑都往里塞。**  
结果表面上可扩展，实际上 API 越长越难懂。  
记住一句话：**插槽适合定制渲染，不适合接管整个业务流程。**

---

## 七、本章小结：会用插槽，不等于会设计插槽

具名插槽解决的是**多个内容区域的组织问题**，作用域插槽解决的是**子组件向外暴露数据的问题**。  
真正做复杂组件时，你要关心的不是“能不能塞”，而是：

- 组件边界清不清楚
- 父子职责分得明不明白
- 插槽 API 好不好用
- 暴露的数据是否克制
- 有没有简单文档能让别人快速接手

对于表格、列表、弹窗这类高复用场景，插槽往往不是装饰，而是组件可复用的关键。  
你只要记住一个原则：**结构交给子组件，变化交给父组件。**

### 老赵总结

- 具名插槽管的是“放哪儿”
- 作用域插槽管的是“怎么渲染”
- 插槽 API 管的是“好不好接”
- 简单文档管的是“别人能不能用”

### 行动建议

1. 拿你项目里一个最常见的表格组件，先找出 `toolbar`、`body`、`footer` 三个区域。
2. 把每行操作区改造成作用域插槽，只暴露 `row` 和 `index`。
3. 给这个组件补一份最简单的使用说明：有哪些插槽、分别干什么、参数是什么。
4. 回头检查一下：有没有哪个插槽参数，其实根本不该暴露。

老赵最后再送你一句：  
**组件复用不是把功能都堆上去，而是把边界划清楚，把接口设计顺。**

# 第6章 组件通信模式：别只会父传子和子传父

## 开篇引入：组件通信，本质上是在管“谁该知道谁”

老赵先把话挑明：**组件通信不是越多越好，而是越清楚越好。**  
很多同学一上来就把状态往顶层抬，事件一路往上抛，页面一大，链路就乱：A 改 B，B 影响 C，C 又反过来牵动 A，最后谁都说不清数据从哪来、往哪去。

所以这一章先想明白两件事：

1. **组件边界**：这个数据该归谁管？
2. **通信模式**：该用 `props/emit`，还是 `provide/inject`，还是事件总线，还是状态共享？

记住老赵这句总结：  
**通信不是为了写得热闹，是为了让组件关系可读、可控、可维护。**

---

## 一、父子通信、兄弟通信、跨层通信：先分清“谁和谁说话”

### 1. 父子通信：最基础，也最常用

父子通信就是两种方向：

- **父传子**：通过 `props` 传数据
- **子传父**：通过 `emit` 发事件

它适合**边界清晰、关系直接、局部状态明确**的场景。

#### 典型例子
- 父组件传列表数据给子组件展示
- 子组件点击按钮后通知父组件关闭弹窗
- 表单项把输入结果交给表单容器

#### 判断标准
如果这件事只需要“上一级知道”，那就别搞复杂。  
谁是状态主人，谁就负责维护，其他人只通过 `props/emit` 沟通。

### 2. 兄弟通信：不要互相硬找，找共同上级

兄弟组件不要直接乱拉手。更稳妥的方式是：

- 通过**共同父组件**中转
- 通过**状态共享**统一管理
- 在局部复杂时用 `provide/inject` 做层级穿透

比如筛选页里，左侧条件变了，右侧列表和底部统计都要变。  
这时候不要让左边直接找右边，应该：

- 筛选栏只负责发出“条件变化”
- 页面容器统一接住条件
- 列表和统计区只读容器下发的数据

兄弟组件不互相认识，但业务照样跑通，这就是边界清楚。

### 3. 跨层通信：别让中间层被迫“传话”

跨层通信最容易把结构搞脏。比如深层弹窗要知道页面主题，子孙组件要更新顶层表单状态。  
这时别一层层 `emit` 上去，先判断：

- 这个状态是不是本来就应该跨层共享？
- 中间层是不是只是布局容器？
- 是否应该提升到共享状态，而不是一路往上抛？

#### 错误案例：通信链路打结
A 传给 B，B 传给 C，C 再回给 D，D 又同步回 A。  
看着像数据流，其实是接力赛。问题不是“改不动”，而是“谁改了都不知道”。

### 可复用组件案例：树形菜单的选中通知

树组件里，叶子节点点击后通知根节点更新选中状态，常见做法有两种：

- 层层 `emit`
- 用 `provide/inject` 共享树上下文

如果层级多、节点多，`provide/inject` 更顺；如果只两三层，直接父子通信更直观。

### 老赵常见踩坑提醒
**别把兄弟通信写成兄弟互相 import 对方组件实例。**  
那不是通信，是耦合。组件之间应该通过数据流协作，不是互相偷看内部状态。

---

## 二、provide/inject、事件总线、状态共享：分别适合什么场景？

### 1. provide/inject：适合“祖孙链路清晰”的跨层传递

`provide/inject` 的优势是：中间层不用层层传参，深层组件也能拿到上下文。

#### 适合场景
- 表单组件库：父级表单向子项提供校验上下文
- 树组件：父节点向后代提供树实例信息
- 弹窗容器：向内部内容区提供关闭方法、状态、配置
- 复杂布局里，某个模块要给很多后代共享同一份业务上下文

#### 什么时候更省事
当中间层只是“过路”的，不承载业务逻辑，`provide/inject` 会特别省事。  
比如表单容器提供当前表单值、校验方法、字段注册/注销能力，子组件就不用接一长串 `props`，也不用把事件层层往上抛。

#### 不适合什么
- 把它当全局状态工具
- 把业务大对象随便塞进去
- 需要强响应追踪却没设计好数据结构
- 本来清晰的父子关系，硬改成隐式共享

老赵建议你记住一句：  
**provide/inject 适合“传上下文”，不适合“乱扔全家桶”。**

### 2. 事件总线：适合轻量、短链路、临时事件

事件总线的本质是“谁都能发，谁都能收”，自由，但也最容易乱。

#### 适合场景
- 小型后台里，局部模块需要广播通知
- “刷新一下”“关闭一下”“提醒一下”这类轻量事件
- 不值得上状态管理，但又确实要跨组件通知

#### 风险
- 事件名越来越多
- 监听器不清理导致泄漏
- 事件流向不可见，排查困难
- 组件卸载了，事件还在飞

所以事件总线只适合局部、临时、轻量通知。要是事件多到得写表格文档了，说明路可能走歪了。

### 3. 状态共享：适合“多个组件共同关心同一份状态”

当一个状态已经不是某个组件私有，而是多个组件共同关注，就该考虑状态共享。

#### 适合场景
- 登录信息
- 主题、语言、权限
- 列表筛选条件、分页信息
- 多个区域共同使用的弹窗可见状态

#### 判断标准
只要你发现“这个状态好像谁都在改，谁都在读”，它就大概率不适合放在单个组件里了。  
这时候最怕什么？不是代码多，而是大家都在改同一个地方，最后互相覆盖。

### 可复用组件案例：表单上下文组件

做一个表单容器 `FormProvider`，通过 `provide` 向内部表单项暴露：

- 当前表单值
- 校验方法
- 注册/注销字段方法

这样表单项不用一层层收 `props`，也不用把事件往外抛，后面要加重置、批量校验、错误聚焦，也能统一处理。

### 老赵常见踩坑提醒
**通信方式不是越高级越好。**  
能直连就直连，能局部就局部，别把代码写成迷宫。

---

## 三、组件边界与受控/非受控：先定谁负责，再决定怎么说

### 1. 组件边界是什么

组件边界就是：

- 这个组件负责什么
- 不负责什么
- 谁拥有数据
- 谁只是展示或触发

边界没定好，通信一定乱。

#### 例子
一个弹窗到底是：

- 只负责展示和关闭？
- 还是顺便拉接口？
- 还是顺便处理表单提交？

如果都塞进去，短期省事，长期就是一个组件三种人格。

#### 边界判断小技巧
问自己三个问题：

- 这个数据是不是这个组件的“私产”？
- 这个动作是不是它的“本职工作”？
- 别的地方是不是只需要知道结果，不需要参与过程？

### 2. 受控 / 非受控思路怎么配通信

这是组件设计里很关键的一点。

#### 受控思路
组件内部状态由外部控制，比如弹窗显示与否由父组件决定，输入值由外部表单系统决定。  
优点是可预测、易管理；缺点是更规范，也更啰嗦。

#### 非受控思路
组件内部自己维护状态，比如简单输入框自己记录临时输入，轻量下拉面板自己控制展开收起。  
优点是简单；缺点是外部介入时要设计同步机制。

#### 怎么选
- **核心业务状态**：优先受控
- **纯局部 UI 状态**：可以非受控
- **可配置组件**：最好兼容两种模式

老赵的经验是：能受控就尽量受控，因为业务组件最怕“内部自己演，外部还要跟着猜”。但像展开态、提示气泡显隐这类局部状态，非受控反而更自然。

### 3. 通信方式要和边界匹配

边界清楚，通信就清楚。  
比如：

- 展示型组件：`props` 为主，`emit` 为辅
- 容器型组件：协调更多子组件通信
- 业务聚合组件：常常需要状态共享或上下文注入

### 可复用组件案例：可控弹窗容器

一个弹窗组件可以设计成：

- `visible` 由外部传入，作为受控模式
- 内部提供 `open()` / `close()` 触发事件
- 内容区通过 slot 注入
- 关闭事件通过 `emit('update:visible')` 同步给父组件

这样边界很清楚：**弹窗负责展示和行为，业务数据由外层掌控。**  
后面复用到“确认删除”“编辑详情”“选择商品”这些场景，只要换内容区，不用重写壳子。

### 老赵常见踩坑提醒
**边界不清，通信必炸。**  
最常见的错法就是：组件既想当 UI，又想当数据中心，还想替父组件做决定。最后它不是组件，是宇宙中心。

---

## 四、复杂页面里如何避免通信打结

### 1. 先画数据流，再写代码

复杂页面里，老赵建议先做一件笨但管用的事：  
**把谁依赖谁、谁修改谁、谁监听谁画出来。**

至少看清：

- 数据从哪来
- 谁改它
- 哪些组件只读
- 哪些组件会触发变化

很多通信灾难，不是 Vue 不行，是一开始就没想清楚数据流。

### 2. 少做“中间转发员”

如果一个事件要经过 4 层组件转发，那就说明设计有问题。你要么：

- 提升状态位置
- 提供上下文
- 用局部状态共享
- 重新拆分组件边界

中间层如果只是布局壳，就别让它承担业务转发；中间层如果确实承接业务，就要把职责写清楚，不然每层都像客服转接。

### 3. 让通信“单向可追踪”

理想状态是：

- 数据流向尽量单向
- 事件命名清楚
- 状态归属明确
- 变更入口尽量少

#### 检查清单
- 这个状态是不是只有一个主人？
- 组件是不是只做自己该做的事？
- 有没有重复同步逻辑？
- 有没有“改了 A，忘了改 B”的情况？

### 可复用组件案例：筛选面板 + 列表联动

做页面筛选区和列表区联动时：

- 筛选面板只负责收集条件并发出查询事件
- 列表组件只负责展示数据
- 页面容器负责承接条件、请求数据、下发结果

这样兄弟组件不直接通信，页面逻辑就稳了。后面加“重置筛选”“批量导出”“分页切换”，也能在容器层统一调度。

### 老赵常见踩坑提醒
**不要把所有逻辑都塞进页面组件，最后页面组件胖得像总经理。**  
页面应该协调，组件应该专注。协调和实现是两回事。

---

## 五、组件案例：一个弹窗控制器组件的通信设计

### 1. 需求拆解

假设有一个业务弹窗，需要：

- 外部可以打开、关闭
- 内部点击确认后要通知外层
- 弹窗里可能放表单、列表、说明文案
- 某些深层按钮需要触发关闭
- 业务确认后，外层还要决定是否刷新列表、是否保留当前筛选

### 2. 通信设计

#### 父组件负责
- 控制弹窗是否显示
- 接收确认结果
- 管理业务数据
- 决定后续是否刷新页面状态

#### 弹窗组件负责
- 显示/隐藏
- 提供关闭事件
- 向内部内容 slot 暴露上下文
- 把确认、取消这类动作标准化

#### 深层内容负责
- 通过注入或 emit 触发关闭
- 把表单提交结果交给弹窗外层
- 不直接操心“提交后刷新列表”这种页面级事务

### 3. 一个更完整的通信链路

这个场景里，建议把通信拆成三条线：

- **状态来源**：`visible`、标题、尺寸、是否遮罩关闭，都由父组件控制
- **触发方式**：打开弹窗用父组件方法或状态切换，内部按钮通过 `emit` 发出操作信号
- **回调路径**：确认结果先回父组件，父组件再决定是更新列表、关闭弹窗，还是继续下一步流程

这样设计的好处是：

- 弹窗壳可以复用
- 内容区可以替换
- 外层业务逻辑不会被锁死
- 深层按钮不需要知道页面全貌

### 4. 简单文档怎么写

给这个弹窗组件写最小文档，至少说明：

- **组件用途**：用于展示业务弹窗
- **受控方式**：通过 `visible` 控制显示隐藏
- **事件**：`confirm`、`cancel`、`update:visible`
- **插槽**：默认内容区、头部、底部
- **使用示例**：至少给一个打开和提交示例
- **注意事项**：不要父子双方同时改显示状态，避免不同步

这就是简单文档，不用花哨，但得让别人接手不迷路。  
老赵补一句：**可复用组件不是你会用就行，别人看说明也得能上手。**

### 可复用组件案例
**弹窗控制器组件**：受控显示 + slot 内容注入 + 事件向外通知。  
这是一个典型的“高复用业务组件”雏形。

### 老赵常见踩坑提醒
**弹窗最怕外面也管、里面也管。**  
一边父组件控制 `visible`，一边子组件自己偷偷改状态，最后两边不同步，关也关不掉，开也开不准。

---

## 结尾小结：通信选型，不靠感觉，靠边界

这一章你要真正记住的是：

1. **先看组件边界，再选通信方式**
2. **父子通信最基础，兄弟通信找上级，跨层通信别硬传**
3. **`provide/inject`、事件总线、状态共享各有适用场景**
4. **受控/非受控思路决定组件是谁说了算**
5. **复杂页面要先梳理数据流，避免通信打结**
6. **可复用业务组件一定要有清晰文档，别让别人猜**

最后给你一个行动建议：

> 下次写组件前，先问自己三句：  
> **这个状态归谁？谁需要知道它？谁来修改它？**  
> 这三句想明白了，通信方式基本就不会选歪。

### 赵老师收尾一句
**通信方式越多，不代表你越高级；通信链路越清楚，才代表你真会做组件。**

# 第7章 组件封装原则：怎么封才不容易翻车

## 开篇：封装不是“把代码包起来”这么简单

很多人做组件封装，第一反应就是：先做一个能用的。这个思路不算错，但只停在“能用”上，往往很快就会变成“难维护、不可复用”。

在 Vue3 里，真正靠谱的封装，不是把代码塞进一个 `.vue` 文件，而是先想清楚：这个组件给谁用、解决什么问题、会不会被多个页面反复调用。**组件边界**没定好，后面再怎么加 props、加事件、加样式，都会越封越乱。

说白了，封装组件不是写页面里的一个零件，而是在设计一个**可长期复用的接口**。这个接口要稳定、好懂、可扩展，还不能把内部实现全暴露出去。否则今天改个样式，明天改个交互，整个项目都跟着抖。

### 封装前先判断：值不值得封

老赵建议你先别急着写，先做个很现实的判断：

- 这个东西是不是只在当前页面用一次？
- 后面会不会有第二个、第三个页面也要用？
- 它是不是某个业务线里高频出现的公共能力？

如果只是一次性页面，强行抽成组件，往往会把简单问题搞复杂。  
如果它本来就是高频复用项，那就值得认真封装，甚至提前考虑文档和扩展点。

### 可复用组件案例

比如 `FormItem`，它不负责“把所有表单都包住”，只负责统一：

- label 展示
- 错误提示
- 帮助文案
- 输入区域布局

它只管表单项这块边界，具体是输入框、选择器还是日期组件，都交给外部决定，这样才有复用价值。

### 老赵常见踩坑提醒

**别把“我觉得需要”当成“别人真的需要”。**  
很多组件翻车，不是写不出来，而是封装前没想清使用场景，最后 API 越堆越多，自己都记不住怎么用了。

---

## 一、封装前先想清楚：目标用户是谁、要解决什么问题？

封装之前，先问两个问题，别上来就写。

### 1. 谁会用这个组件？

- 只有当前页面自己用？
- 同一个业务线多个页面会用？
- 以后会不会进组件库，给更多项目用？

这几个答案，决定了你的封装要多“通用”。如果只是临时页面用一下，可以偏业务化；如果会被多个页面复用，就要克制：少写硬编码，少依赖页面上下文，多留配置入口。

### 2. 它到底解决什么问题？

常见目标就几类：

- 减少模板重复
- 统一交互和样式
- 屏蔽复杂逻辑
- 让业务方只关注配置

如果这些目标搅在一起，很容易封成一个“大杂烩”。看起来很强，实际一改就崩。

### 判断标准

如果一个组件的使用者只能是你自己，可以适当偏业务；  
如果它会被多个页面复用，就要尽量把**稳定能力**暴露出来，把**变化部分**交给外部传入。

这里最关键的是：**组件边界要先定好**。边界不清，后面的封装动作都会跑偏。

### 可复用组件案例

继续拿 `FormItem` 举例。它的目标不是管理整个表单，而是：

- 统一 label 和内容区布局
- 统一错误提示和辅助文案
- 让不同输入控件都能接入

这样它就能复用到输入框、下拉框、日期选择器、开关等场景。

### 老赵常见踩坑提醒

**别一上来就想着把所有未来需求都支持了。**  
真正高频的能力，通常也就那几项。先把核心场景做好，比堆一堆看起来很厉害的配置更重要。

---

## 二、组件边界怎么划，避免职责过重？

组件边界，说白了就是：**这个组件管到哪一步，另一个组件从哪一步接手**。

一个好组件，通常只负责一类事情：

- 展示
- 交互
- 状态管理
- 数据组织

但不要把这四类全包了。否则组件就会变成“啥都能干，啥都干不精”，维护起来很累。

### 怎么划边界更稳

一句话判断：  
**组件内部做稳定的事，组件外部做变化的事。**

稳定的事，比如：

- label 怎么排版
- 错误提示放哪里
- 默认边框和间距怎么统一

变化的事，比如：

- 具体输入控件是什么
- 字段校验规则怎么写
- 这个字段在不同页面要不要显示

这些变化项，尽量通过 props、slot、事件交给外部。

### 常见封装陷阱

1. **职责过重**：一个组件既管 UI，又管请求，还管路由跳转。  
2. **边界模糊**：外部能控制的东西，组件内部又偷偷写死。  
3. **过度耦合**：子组件必须依赖父组件特定的数据结构才能活。  
4. **文档没写清**：别人根本不知道该传什么、不该传什么，只能翻源码猜。

这类问题一旦出现，组件就很难真正复用，因为它不再是通用零件，而像某个页面的附属器官。

### 可复用组件案例

`FormItem` 很适合做边界清晰的容器：

- `label`：左侧标题
- `required`：是否显示必填标记
- `error`：错误文案
- `help`：辅助说明
- 默认插槽：放具体表单控件

它只管“这一项怎么长”，不管“这一项具体输入什么”。

### 老赵常见踩坑提醒

**别让一个组件替你做三个组件的活。**  
职责越多，维护成本越高。后面改一个地方，页面跟着连锁反应，这种组件就是典型的“翻车预备役”。

---

## 三、受控 / 非受控思路在封装中的取舍

这个点很关键，很多组件设计翻车，根子就在这里。

### 什么是受控

**受控**就是组件状态主要由外部控制。比如父组件传入 `value` 或 `modelValue`，再通过 `update:modelValue` 接管更新逻辑。

好处是：

- 状态来源明确
- 父子同步方便
- 适合复杂联动场景

### 什么是非受控

**非受控**就是组件自己维护内部状态，外部只给初始值或少量配置。

好处是：

- 用起来简单
- 组件内部更独立
- 适合轻量交互

### 怎么取舍

判断标准很实用：

- 如果值需要和父层强同步，优先受控
- 如果只是局部交互，优先非受控
- 如果两者都要支持，就设计成“外部可控，内部兜底”

重点是，**不要在一个组件里同时放两套抢控制权的逻辑**。否则最后谁说了算都不清楚。

### 放到 FormItem 里怎么理解

严格说，`FormItem` 本身更像“容器”，真正受控/非受控的通常是它里面的输入控件。但在业务里，`FormItem` 经常要配合校验、提示、聚焦、重置这些动作，所以它的设计思路也要跟状态管理对齐：

- 表单值由父层统一管理时，`FormItem` 只负责展示和承接状态
- 某些轻量字段只需要局部使用时，可以让内部控件先自己维护，最后再统一提交
- 如果要两种模式都支持，最好明确：`value` 存在时走受控，不传时走内部兜底

这个约定一旦写清，后面别人接入时就不会乱。

### 可复用组件案例

`FormItem` 的典型做法是：外部传入校验状态、错误信息和布局配置，内部只负责把输入区域展示出来。这样它不会绑死在某一种输入模式上，复用空间更大。

### 老赵常见踩坑提醒

**别把受控和非受控混着写。**  
同一个值既能外部改、又能内部改，还没有优先级约定，排查问题会非常痛苦。

---

## 四、API 设计原则：少而稳、明确、可预测

组件 API 设计，最怕两件事：**多** 和 **飘**。

### 1. 少而稳

先提供最核心的能力，不要一开始就把所有未来需求都塞进去。  
API 少一点，记忆成本低，文档也好写，测试更简单。

### 2. 明确

命名要让人一眼看懂：

- `label` 就是标签
- `required` 就是必填
- `errorMessage` 就是错误信息

别用那种看起来高级、其实很绕的命名。

### 3. 可预测

用户看到 props、事件、插槽，就能大概判断组件怎么工作，这才叫可预测。  
比如看到 `default` 插槽，大家会知道这里放主要内容；看到 `error` prop，就知道它应该控制错误展示。

### 简单文档怎么写

可复用组件最好配一份简单文档，至少写清楚：

- 组件用途
- props 列表
- events 说明
- slots 说明
- 使用示例
- 注意事项

老赵建议你直接固定成一个模板：

```md
## 组件名
## 适用场景
## Props
## Emits
## Slots
## 示例
## 注意事项
```

这样后面无论是 `FormItem`、弹窗还是分页组件，文档都能套一个统一格式。

### 可复用组件案例

`FormItem` 的简单文档可以这样写：

- `label`：左侧标题
- `required`：是否显示必填标记
- 默认插槽：放输入控件
- `error`：外部传入错误文案
- `help`：辅助说明

几条就够，但已经能让别人快速上手。

### 老赵常见踩坑提醒

**别追求“参数越多越专业”。**  
参数一多，组件就不再是工具，而变成测试题。真正好用的组件，往往就是少数几个稳定 API。

---

## 五、组件案例：一个可配置的 FormItem 表单项组件

下面用 `FormItem` 把前面的原则串起来。

### 设计思路

它主要解决三件事：

- 统一表单项外观
- 统一提示信息
- 保留对不同控件的适配能力

### 典型结构

- `label`：左侧标签
- 默认插槽：右侧内容区域
- `error`：错误提示
- `help`：辅助文案

### 使用方式示意

```vue
<FormItem label="用户名" required error="用户名不能为空">
  <input v-model="form.username" />
</FormItem>
```

这个设计的好处很明显：

- `FormItem` 不关心你放的是输入框还是选择器
- 外部可以自由组合控件
- 组件边界清楚，复用性高

如果后面要扩展，也应该先扩展稳定能力，比如：

- 是否禁用
- 是否拉齐宽度
- 错误提示显示位置
- label 宽度是否固定

但前提始终是：**先把最核心的部分做好，再考虑扩展。**

### 业务实战里怎么分工

在真实项目里，`FormItem` 往往要和表单校验联动。老赵建议你把职责分开：

- **输入**：交给具体控件，比如 `Input`、`Select`
- **校验**：交给表单规则或表单容器
- **提示**：交给 `FormItem`
- **布局**：也交给 `FormItem`

也就是说，`FormItem` 不是“万能表单盒子”，而是“表单项边框和信息展示层”。这样职责最清楚，后期改版也不会互相打架。

### 老赵常见踩坑提醒

**别在 `FormItem` 里把所有表单逻辑都内置进去。**  
它应该是“表单项容器”，不是“整套表单解决方案”。一旦边界失控，后面加一个需求就会牵一串代码。

---

## 结尾：先稳住边界，再谈高级封装

这一章其实就想讲明白一件事：**组件封装不是炫技，是控制复杂度。**

你在封装前要先想清楚目标用户和问题场景；封装时要守住组件边界；设计时要权衡受控/非受控；API 要少而稳、明确、可预测；最后还要补一份简单文档，让别人知道怎么用、哪里能扩、哪里别乱碰。

最后给你一个赵老师式检查清单：

- 这个组件到底给谁用？
- 它解决的是不是一个清晰的问题？
- 边界有没有画清楚？
- 受控和非受控有没有混乱？
- API 有没有过多、过飘、过难记？
- 有没有一份简单文档，能让别人快速上手？

只要这几条你能答上来，组件就已经从“能用”迈向“好维护、可复用”了。下一步，我们就可以把这些原则真正落到表单、弹窗、列表、分页这些高频业务组件里。

**老赵总结：**别一上来就追求大而全，最后谁都不好用。组件封装这事，先守住边界，再把核心能力打磨稳，能少一点就少一点，能清楚一点就清楚一点。真正靠谱的封装，不是把东西塞满，而是让别人用起来不费劲、以后改起来也不翻车。

# 第8章 表单组件实战：从输入框到整套表单能力

表单看着简单，真做起来最容易翻车。  
一旦需求复杂起来：要校验、要联动、要重置、要默认值、要禁用、要异步提交，还要按权限隐藏字段，表单就不再是页面里的一块，而是一个小型状态系统。

老赵先给你一句结论：**表单组件不是把输入框堆起来，而是把值、校验、状态、提交这四件事组织好。**  
这四件事没想清，后面复用越多，返工越狠。

这一章我们拿最常见的业务场景——`SearchForm` 查询表单——把输入框、表单项、联动、重置、回填和文档化使用串起来讲清楚。你会发现，表单做得好不好，直接决定一个组件能不能从“能跑”变成“能复用”。

---

## 一、表单组件的核心需求：值、校验、状态、提交

表单真正要解决的，不只是“能输入”，而是“输入之后怎么可靠流转”。

### 1. 值：谁来保存，谁来驱动

表单里最基础的是值，比如姓名、手机号、城市、日期区间，这些值必须有明确归属：

- 是组件内部自己记着？
- 还是交给外部页面统一管理？
- 还是两者都支持？

这就引出两个关键词：**受控** 和 **非受控**。

- **受控**：值由外部传入，组件只负责展示和触发事件。
- **非受控**：值由组件内部维护，外部只在需要时读取。

高复用业务组件通常建议**优先支持受控，同时兼容非受控**。这样既能满足简单场景，也能应对复杂联动。比如搜索表单里，父页面可能要把查询条件同步到路由参数；而一个简单弹窗里的小表单，可能只需要组件先自己记住值，等点击确认再提交。

### 2. 校验：不要等提交才发现问题

表单校验不是最后补一刀，而是体验的一部分。常见校验包括：

- 必填
- 格式校验
- 长度限制
- 范围限制
- 联动校验，比如“开始时间不能晚于结束时间”

一个好表单至少要明确：

- 校验什么时候触发：输入时、失焦时、提交时
- 校验结果怎么展示：红字提示、边框高亮、气泡提示
- 校验失败后是否阻止提交

还要考虑**回填后的校验状态**。很多表单不是用户手动填错，而是接口回填的数据本身就不合法，组件要能给出明确反馈。

### 3. 状态：不只是值，还要管当前处于什么情况

表单状态一般包括：

- 是否编辑中
- 是否有错误
- 是否提交中
- 是否禁用
- 是否已被修改
- 是否需要重置

很多项目里，表单写乱不是因为字段多，而是因为状态乱。尤其是把“值”“错误信息”“加载状态”全塞进一个大对象里，后面任何变化都可能牵一发动全身。

### 4. 提交：表单出口必须清晰

提交是表单的出口。一个好组件应该让外部明确知道：

- 何时触发提交
- 提交参数是什么
- 校验不过怎么办
- 提交成功后是否重置
- 提交失败如何反馈

判断标准很简单：**如果一个表单提交逻辑要在页面里写很多重复代码，那这个表单组件就还没抽对。**

### 可复用组件案例：基础 `BaseField`

可以先从单个字段组件做起，比如统一封装输入框：

- 支持 `modelValue`
- 支持 `disabled`、`placeholder`
- 支持 `error`
- 支持 `blur`、`change` 事件

它的价值不在于“像个输入框”，而在于把输入、提示、状态、事件统一起来，为后面的登录表单、搜索表单、编辑表单打底。

### 老赵常见踩坑提醒

**踩坑点：把字段值和表单状态混在一起。**  
比如 `form = { name: '', nameError: '', loading: false, dirty: false }` 全塞一个对象里，看着省事，后面联动一多就开始灾难。  
老赵建议：**值、校验、状态尽量分层管理，别让一个对象背所有锅。**

## 二、输入类组件如何设计受控与非受控模式

输入类组件是表单的基本盘。输入框都没设计好，后面的搜索表单、筛选表单、编辑表单都会受影响。

### 1. 受控模式：外部统一管理，适合复杂场景

受控模式的核心是：**组件只接收值，变化时通知外部，自己不偷偷改值。**

适合这些场景：

- 多字段联动
- 需要外部统一重置
- 要和路由参数、接口数据同步
- 需要精确控制每次变更

典型设计是：

- `modelValue` 作为输入值
- `update:modelValue` 作为更新事件
- 组件内部只负责把用户输入转出去

好处很直接：**状态来源唯一，排查问题简单。**

### 2. 非受控模式：组件内部自管，适合轻量场景

非受控模式就是组件内部自己维护值，外部不必每次都接管。

适合这些场景：

- 临时表单
- 简单搜索栏
- 低耦合输入组件
- 只关心最终结果，不关心每次变化

比如“搜索关键字输入框”，组件内部先存着，用户点搜索时再一次性提交，这就是典型的非受控思路。

### 3. 最实用的方式：两种都支持

真正好用的组件，通常不是二选一，而是**默认可控，必要时可自管**。  
可以理解成：

- 外部传 `modelValue`，它就是受控
- 外部不传，组件内部初始化默认值，自行维护

但要注意一个原则：  
**不要让组件在受控与非受控之间反复横跳。**  
不然就会出现“外部改了内部没同步”“内部改了外部又覆盖”的经典问题。

### 4. 一个更贴近业务的判断标准

你可以这样判断：

- 这个字段会不会被父组件重置？
- 会不会和别的字段联动？
- 会不会被接口回填？
- 会不会被路由参数控制？
- 会不会需要外部统一校验结果？

只要有两条以上是“会”，那就优先用受控模式。  
这也是表单组件里最容易忽略的一点：**不是技术上能不能做，而是后面改起来会不会痛。**

### 可复用组件案例：`BaseInput`

一个高复用输入组件至少应支持：

- `modelValue`
- `defaultValue`
- `disabled`
- `readonly`
- `clearable`
- `placeholder`
- `errorMessage`

并向外暴露：

- `update:modelValue`
- `focus`
- `blur`
- `enter`

如果再往前一步，可以补上清空按钮、前后缀插槽、字数统计等能力，但别一口气加太满。输入框的核心不是功能多，而是**边界稳、行为一致**。

### 老赵常见踩坑提醒

**踩坑点：受控组件里偷偷维护内部状态，又忘了同步外部值。**  
这种问题最隐蔽：开发时看起来正常，一旦父组件异步回填数据，输入框就开始“记仇”。  
老赵提醒你：**受控就老老实实受控，别一边听外部指挥，一边自己另起炉灶。**

## 三、表单联动和表单项组合的常见做法

表单一进入业务场景，就很少是单个字段孤立工作，更多是字段之间互相影响。

### 1. 联动的本质：谁影响谁，要提前说清楚

常见联动包括：

- 选择“类型”后，后面字段显示/隐藏
- 选择“国家”后，城市列表变化
- 勾选某项后，另一项自动启用
- 日期区间联动校验
- 输入关键字后自动补全或过滤

联动能不能做好，核心不在技术，而在**组件边界**。

你得先判断：

- 这个联动应该由字段组件自己管吗？
- 还是应该由表单容器统一管？
- 是纯展示联动，还是数据也要联动？

### 2. 常见做法：表单容器统一编排，字段组件专注表达

老赵建议一个基本原则：

- **字段组件负责单点输入**
- **表单容器负责联动逻辑**
- **校验规则尽量靠近数据结构**
- **复杂条件用配置驱动，不要全写死在模板里**

这样后面新增字段、删除字段、调整顺序，都不会把联动逻辑搅成一锅粥。

### 3. 表单项组合：不是越抽越好

很多人一上来就想搞“万能表单项组件”，最后结果是：

- 所有字段都能塞进去
- 所有场景都要传一堆配置
- 最后谁都看不懂

合理的做法是分层：

- 基础输入组件：`BaseInput`、`BaseSelect`
- 表单项包装组件：统一 label、错误提示、布局
- 业务表单组件：负责组合字段与联动

**组件边界要清楚：输入组件别管业务，业务组件别吞掉基础能力。**

### 可复用组件案例：`FormItem`

一个可复用的 `FormItem` 可以统一处理：

- label 对齐
- 必填标识
- 错误提示
- 帮助文案
- 插槽放入任意输入组件

它像一个连接器：不直接决定填什么，只负责把标签、提示、内容区组织起来。后面接输入框、选择器、日期组件，布局都能保持一致。

### 老赵常见踩坑提醒

**踩坑点：把联动逻辑写进每个字段组件里。**  
今天字段 A 控字段 B，明天字段 C 又控字段 D，最后每个组件都知道别人的事。  
老赵一句话：**字段只管自己，联动放到上层统一编排。**

## 四、`SearchForm` 场景：查询条件、重置、回填、展开收起怎么组织

这一节是本章重点。很多人会写一个“能用的查询表单”，但离“可复用的业务组件”还差一口气，差的就是这几个细节：**回填、重置、展开、联动、文档化。**

### 1. 查询表单真正会遇到什么

一个后台列表页里的 `SearchForm`，通常会遇到这些需求：

- 页面初次加载时，要回填路由参数或缓存条件
- 点击“查询”时，统一提交当前条件
- 点击“重置”时，恢复默认值
- 条件太多时，要支持展开/收起
- 某些字段变化后，另一些字段要联动清空或重算
- 甚至要支持“进入页面自动查询一次”

你看，表单并不只是收集值，而是在做一套状态编排。

### 2. 一个可落地的组织方式

比较稳的做法是把 `SearchForm` 拆成三层：

- **数据层**：表单模型，保存当前筛选条件
- **渲染层**：根据配置渲染字段和插槽
- **动作层**：查询、重置、展开、收起

这样每一层职责清楚，不容易互相打架。

比如：

- 父组件负责提供默认查询条件和字段配置
- `SearchForm` 负责显示、编辑和收集
- 用户点击查询按钮时，`SearchForm` 把完整条件抛给父组件
- 父组件拿到条件去请求接口

这个模式的好处是：**表单只管“怎么收集”，页面只管“拿去做什么”。**

### 3. 回填要怎么做才不乱

查询表单最常见的问题就是“回填”。

比如：

- 用户从列表页切到详情页，再回来时要保留筛选条件
- 路由 query 带了初始筛选项
- 页面刷新后希望恢复上次搜索条件

这时候要先明确一件事：**回填数据是不是表单的最终真相。**

如果是，那就应该让表单支持受控输入，父组件统一提供初始值或当前值。  
如果不是，只是临时展示，那也要在组件初始化时把默认值和外部值合并清楚，避免“重置以后回不到原点”。

### 4. 重置不是清空，而是回到初始状态

很多人把“重置”理解成全部置空，这其实不对。  
业务里真正想要的是：**回到默认值**。

例如：

- 默认状态下，`status` 可能是“全部”
- `pageSize` 可能是 20
- 日期范围可能默认取最近七天

所以重置时应该恢复到“组件定义的初始值”，而不是机械清空。  
这个点很重要，因为它直接影响用户体验，也影响后续接口参数是否正确。

### 5. 展开/收起要和字段值解耦

搜索表单常常会有“高级筛选”区域。  
这里的原则是：

- 展开/收起只影响布局，不影响已输入的值
- 隐藏字段也要保留数据，除非业务明确要求清空
- 切换展开状态时，不要让表单重新初始化

不然就会出现一个很烦人的问题：  
用户刚填完高级条件，一点收起，值没了。

### 可复用组件案例：`SearchForm`

这是一个很典型的可复用业务组件。  
它可以支持：

- `modelValue`：表单当前值
- `fields`：字段配置数组
- `submit`：点击查询时触发
- `reset`：点击重置时触发
- `expand`：展开/收起状态切换
- `slots`：自定义操作区、扩展区

它的价值不是“长得像个搜索框”，而是把列表页里最重复的一套筛选逻辑统一收口。后面换页面，只要改字段配置和少量插槽，基本就能复用。

### 老赵常见踩坑提醒

**踩坑点：查询表单一复杂就开始手写一堆局部状态。**  
今天一个字段一个 `ref`，明天一个按钮一个 `ref`，重置时还要挨个清。  
老赵建议：**查询表单尽量围绕一个统一的表单模型管理，不要散成满天星。**

## 五、错误示例：状态乱绑，表单为什么会失控

这一段很重要，因为很多表单不是“设计不够”，而是“起手式就错了”。

### 1. 一个容易出问题的写法

比如你可能会写成这样：

```vue
<template>
  <div>
    <input v-model="keyword" />
    <select v-model="status"></select>
    <button @click="search">查询</button>
    <button @click="reset">重置</button>
  </div>
</template>

<script setup>
import { ref } from 'vue'

const keyword = ref('')
const status = ref('')
const loading = ref(false)
const keywordError = ref('')
const statusError = ref('')

function search() {
  loading.value = true
  // 请求接口...
}

function reset() {
  keyword.value = ''
  status.value = ''
  keywordError.value = ''
  statusError.value = ''
  loading.value = false
}
</script>
```

这个写法短期能跑，但一旦加上：

- 默认值回填
- 条件展开
- 多字段联动
- 路由同步
- 权限字段隐藏
- 接口回显

你会发现它开始变得不可收拾。因为每一个字段、错误、状态都各自为政，重置要改一堆地方，后面再加新字段更是雪上加霜。

### 2. 重构思路：把“值”统一，把“状态”分层

更稳的方式是：

- 用一个统一的 `formModel` 保存值
- 用单独的 `uiState` 管理展开、加载等状态
- 用规则配置管理校验
- 用事件向外暴露查询和重置

比如把模型收拢成：

```js
const formModel = reactive({
  keyword: '',
  status: '',
  dateRange: []
})

const uiState = reactive({
  loading: false,
  expanded: false
})
```

这样值和状态各管各的，后面新增字段只是在 `formModel` 里补一项，不需要满地找 `ref`。

### 3. 重构后的好处

- 重置逻辑集中
- 回填逻辑集中
- 提交参数更清晰
- 后续加字段更容易
- 联动规则更容易维护

这就是表单组件为什么强调“边界”和“分层”。  
不是为了看起来高级，是为了让你半年后还能改得动。

### 可复用组件案例：`SearchForm` 重构版思路

可以把错误示例重构成一个表单容器：

- `formModel` 统一承接字段值
- `fieldConfig` 负责渲染结构
- `emit('submit', cloneDeep(formModel))` 提交完整条件
- `emit('reset')` 时恢复初始模型
- `expanded` 只管展示，不碰值

这样你的查询表单就从“临时拼装”变成了“可维护组件”。

### 老赵常见踩坑提醒

**踩坑点：字段越多，状态越散，最后自己都不敢改。**  
老赵的经验很直接：**表单复杂了，第一件事不是加功能，而是先收口状态。**

## 六、如何给表单组件写简单文档，方便接手和复用

组件能不能复用，不只看代码，还看别人敢不敢用。  
而“敢不敢用”，很大程度取决于文档清不清楚。

### 1. 简单文档不需要花哨，但一定要完整

一个好用的表单组件文档，至少要回答：

- 这个组件干什么用
- 适合什么场景
- 支持哪些 props
- 会发出哪些事件
- 插槽怎么放
- 默认行为是什么
- 受控还是非受控
- 校验怎么接
- 如何重置、如何提交

### 2. 文档写法：少讲概念，多给例子

别写空话，比如“本组件用于提供高性能表单输入能力”。  
听着高级，接手的人用不上。

更实用的写法是：

- 一句话说明用途
- 列出核心参数
- 给一个最小可运行示例
- 给一个复杂联动示例
- 说明常见限制

### 3. 推荐一个统一的文档模板

你可以直接按这个结构写，后面每个可复用表单组件都能套：

#### 组件名称
`SearchForm`

#### 组件用途
用于列表页查询、条件筛选、后台搜索等场景。

#### Props
- `modelValue`：表单值
- `fields`：字段配置
- `loading`：是否提交中
- `expandLimit`：默认展示字段数量

#### Events
- `submit`：点击查询触发
- `reset`：点击重置触发
- `update:modelValue`：表单值变化时触发

#### Slots
- `actions`：自定义按钮区
- `extra`：扩展条件区
- `field-{name}`：自定义某个字段的渲染

#### 受控/非受控说明
- 推荐受控使用
- 父组件负责传入初始值和接收提交结果
- 非受控适合简单临时查询，但不建议在复杂页面里长期使用

#### 示例代码
```vue
<SearchForm
  v-model="query"
  :fields="fields"
  @submit="handleSearch"
  @reset="handleReset"
/>
```

#### 注意事项
- 重置会恢复默认值，不是简单清空
- 展开/收起不影响已输入的数据
- 隐藏字段默认保留值，除非业务要求主动清除
- 若字段有联动，建议由父组件统一处理

### 4. 文档的真正作用

文档不是装样子，它的作用是：

- 降低接手成本
- 降低误用概率
- 提高复用率
- 让组件边界更清楚

尤其是表单这种高状态组件，文档写不清楚，别人一用就容易误解“哪个值归谁管”“重置会不会清空”“提交时带哪些字段”。

### 可复用组件案例：`SearchForm` 文档模板

如果你只想先做一页文档，那就先把 `SearchForm` 写清楚。  
这个模板可以直接成为团队以后所有表单组件的基础版本。

### 老赵常见踩坑提醒

**踩坑点：组件做出来了，结果没人知道怎么用。**  
代码再优雅，没文档也会变成“只有作者会用的组件”。  
老赵建议：**组件一旦要复用，就必须配最简文档，哪怕只有一页。**

---

## 七、结尾：表单组件要做成“能接手、能扩展、能复用”

这章你要真正记住的，不是某个 API，而是表单组件的设计逻辑：

1. **值要统一管理**
2. **校验要有明确触发点**
3. **状态要分层，不要乱绑**
4. **提交要清晰，重置要可控**
5. **组件边界要明确**
6. **受控/非受控思路要先想清**
7. **联动放在合适层级，不要把组件写成八爪鱼**
8. **复用组件必须配简单文档**
9. **查询表单要把回填、展开、重置一起设计进去**

老赵最后送你一句实战经验：  
**表单不是把字段做出来就完事了，真正值钱的是把“能改、能扩、能接手”也一起做出来。**

### 本章行动建议

- 先拿一个最简单的输入组件，练习受控/非受控两种写法
- 再做一个 `FormItem`，统一 label 和错误提示
- 接着封装一个 `SearchForm`，把查询、重置、展开、回填一次性练完整
- 给 `SearchForm` 补一页最简文档，按“用途、Props、Events、Slots、示例、注意事项”六项写
- 写完后自己模拟一次“别人接手”，看看不问你能不能上手

**老赵总结：表单组件最怕的不是复杂，最怕的是一开始没想清边界。边界一乱，后面所有复用都是给自己挖坑。**

# 第9章 弹窗组件实战：交互复杂的地方最考验封装

弹窗看着简单，不就是“点一下弹出来，再点一下关掉”吗？但真到业务里，它往往是最容易做乱的地方：标题要配，内容要变，按钮要控，关闭还可能牵着接口、表单、列表刷新一起跑。一个弹窗没封好，后面一串“确认删除”“表单编辑”“选择用户”“批量操作”都会被拖累。

这一章咱们就拿弹窗来练手，讲清楚一件事：**怎么把一个交互复杂、变化很多的东西，封装成可复用的业务组件。**

---

## 一、弹窗组件的核心构成到底是什么？

先别急着写代码，先拆结构。一个弹窗通常就四块：

1. **显示控制**：什么时候弹、什么时候关  
2. **标题区**：告诉用户这是干嘛的  
3. **内容区**：承载真正的业务信息或表单  
4. **操作区**：确认、取消、关闭等动作  

弹窗的边界要清楚：**弹窗负责壳子，业务内容负责内容，业务动作负责结果。**

### 组件边界怎么判断？

老赵给你一个简单标准：

- **弹窗该管的**：遮罩、居中、动画、关闭、按钮区、基础布局
- **弹窗不该管的**：具体表单字段、接口调用、列表刷新、权限判断、复杂校验

一句话：**弹窗是容器，不是业务本体。**  
边界不清，弹窗就会变成“第二个页面”，后面维护非常痛苦。

### 可复用组件案例：基础弹窗壳

最小弹窗一般只保留：

- `title`
- `visible` / `modelValue`
- `close`
- `confirm`
- `cancel`
- `default slot`

这就是后面所有高级封装的底座。无论是删除确认、表单编辑，还是复杂选择器，本质都在这层壳里换内容、换动作。

### 老赵常见踩坑提醒

**最常见的坑就是把业务内容写进弹窗内部。**  
今天一个删除确认，明天一个编辑用户，后天又来选择商品，最后组件里全是 `if/else`。记住，弹窗只负责“容器能力”，不要把业务逻辑焊死在里面。

---

## 二、受控弹窗与内部状态弹窗，区别到底在哪？

弹窗封装里最核心的问题之一就是：**谁来控制它的显示隐藏？**

### 1）受控弹窗：外部说了算

受控弹窗指的是弹窗显隐由父组件控制，比如父组件传入 `modelValue`，再通过 `update:modelValue` 通知更新。

优点很明显：

- 状态来源清晰
- 父组件统一管理
- 适合复杂业务流程
- 方便和表单、列表、路由联动

适合的场景包括：

- 编辑弹窗
- 删除确认弹窗
- 选择器弹窗
- 关闭后要刷新数据的弹窗

这种模式最贴近实际业务：页面状态由页面掌控，弹窗只是展示层。

### 2）内部状态弹窗：组件自己管自己

内部状态弹窗就是组件自己维护开关，点按钮打开，点取消关闭。优点是简单直接，代码少。

适合：

- 简单提示
- 本地独立展示
- 不需要外部精细控制的轻量交互

### 3）怎么选？

老赵建议你这么判断：

- **弹窗结果会影响外部状态，优先受控**
- **只是临时展示，才考虑内部状态**

### 4）对比一下，差别就更清楚了

#### 受控弹窗示意

```vue
<ConfirmDialog
  v-model="dialogVisible"
  title="确认删除"
  @confirm="handleDelete"
/>
```

父组件负责什么时候开、什么时候关，弹窗只负责把交互动作抛出来。  
这类模式特别适合“点确认后要调接口、成功后刷新列表”的场景。

#### 内部状态弹窗示意

```vue
<ConfirmDialog title="温馨提示" />
```

组件内部自己管开关，父组件不关心状态流转，只把它当一个独立弹层来用。  
这种写法适合“临时说明”“轻提示”“不影响外部业务”的场景。

### 5）什么时候别偷懒用内部态？

如果弹窗一关就要：

- 刷新列表
- 重置表单
- 记录操作日志
- 联动其他组件状态

那就别图省事用内部态。**业务结果要回到父组件里收口，受控模式才稳。**

### 可复用组件案例：双模式弹窗思路

可以设计成：

- 传了 `modelValue` 就走受控模式
- 没传就组件内部自己维护开关

但这种双模式最容易让人迷糊，团队水平一般时不建议乱用。**组件不是用来炫技的，先让人看得懂，再谈高级封装。**

### 老赵常见踩坑提醒

**受控和非受控混着用，最后谁都不知道状态是谁在改。**  
父组件关了，子组件又自己打开；子组件关了，父组件状态没同步，弹窗看着就像“抽风”。记住：**一个弹窗最好只认一个状态源。**

---

## 三、把 ConfirmDialog 拆细一点，才能真正复用

咱们这一章的主角是 **ConfirmDialog 确认弹窗**。这个组件看着小，但最适合讲封装，因为它能把“显示控制、标题、内容、按钮区、关闭行为”这几件事拆得很清楚。

### 1）显示控制怎么设计？

建议优先用 `modelValue` 做受控显示。  
原因很简单：确认弹窗几乎都和外部业务状态相关，特别是删除、提交、发布、审批这种动作，弹窗打开和关闭都不该脱离业务上下文。

组件内部只负责：

- 接收是否显示
- 发出关闭请求
- 必要时控制 loading

**不要在组件里偷偷改外部业务状态。**

### 2）标题怎么设计？

标题最好支持两种方式：

- 默认标题文字 props 传入
- 需要复杂内容时用具名插槽覆盖

大多数确认弹窗只需要一句话标题，比如：

- “确认删除这条数据吗？”
- “确认提交当前表单吗？”
- “确认执行批量操作吗？”

如果标题里要带用户名、订单号、风险等级，那就交给插槽，别硬塞成一串字符串。

### 3）内容区怎么设计？

内容区是弹窗最该开放的地方。  
对于确认弹窗，默认内容通常是一段提示文案；但到了业务里，内容可能变成：

- 简单确认文案
- 风险说明
- 额外表单项
- 只读详情
- 二次确认复选框

所以内容区建议优先用默认插槽，必要时再配合具名插槽拆分头部和底部。

### 4）按钮区怎么设计？

按钮区是弹窗的“动作出口”，但不是给业务随意改写的地方。  
建议只开放这些常用能力：

- 确认按钮文案
- 取消按钮文案
- 是否显示取消按钮
- confirm 的 loading 状态
- 点击遮罩是否允许关闭

这样能覆盖大部分业务，同时不会把按钮区做成“自由发挥区”。

### 5）关闭行为怎么设计？

关闭不是一个简单动作，通常有三种情况：

- 点取消关闭
- 点右上角关闭
- 点确认后，业务成功再关闭

所以 ConfirmDialog 里最好把“关闭”与“确认”分开处理：

- **取消/关闭**：退出即可，不改业务结果
- **确认**：只表达意图，真正业务动作由父组件处理
- **成功后关闭**：由父组件明确控制

这样一来，组件职责就清楚了。

### 可复用组件案例：ConfirmDialog 的推荐结构

你可以把它拆成这几部分：

- `props`
  - `modelValue`
  - `title`
  - `confirmText`
  - `cancelText`
  - `confirmLoading`
  - `closeOnMask`
- `emits`
  - `update:modelValue`
  - `confirm`
  - `cancel`
  - `close`
- `slots`
  - `default`：正文内容
  - `title`：自定义标题
  - `footer`：自定义操作区

这个结构不花哨，但很稳。对业务来说够用，对维护来说也清爽。

### 老赵常见踩坑提醒

**确认按钮一点，先关弹窗再发请求，很容易把用户搞懵。**  
接口慢的时候，用户会以为没点上，连点两次，结果重复提交。正确做法是：确认后进入 loading，或者等业务明确成功后再关闭，逻辑别含糊。

---

## 四、如何用插槽承载不同业务内容？

弹窗真正可复用的关键，不是标题和按钮，而是**内容注入能力**。这时候插槽就特别好用。

### 1）默认插槽：承载主体内容

默认插槽最适合放：

- 确认提示文案
- 表单
- 详情信息
- 自定义说明

这样弹窗组件只管框架，业务内容由调用方塞进来。

### 2）为什么弹窗特别适合插槽？

因为弹窗的壳子基本稳定，但内容千变万化。你总不能每种业务都单独写一个弹窗，那维护成本会很高。

插槽的价值就在这里：

- **结构稳定**
- **内容可变**
- **复用度高**

### 3）插槽使用场景

特别适合弹窗插槽的场景有：

- 删除确认：放提示文本
- 表单编辑：放完整表单
- 批量操作：放风险说明和选项
- 复杂配置：放多个子组件组合

经验很简单：**凡是“内容差异大、壳子相似”的地方，优先想插槽。**  
弹窗、卡片、面板、抽屉都很适合这个思路。

### 可复用组件案例：带默认插槽的确认弹窗

弹窗只提供标题栏、内容容器、底部按钮，内容交给父组件传入。  
这样同一个弹窗可以同时服务“危险操作确认”“补充说明”“简易表单”等多种业务。

它真正的价值不是长得多漂亮，而是以后新增业务时，不用重写弹窗，只要换插槽内容。

### 老赵常见踩坑提醒

**别把插槽当万能口袋，啥都往里扔。**  
插槽是解耦，不是放飞自我。你得先想清楚哪部分是壳、哪部分是内容，不然组件看起来灵活，实际很难维护。

---

## 五、一个反例：弹窗逻辑和业务逻辑缠在一起，后面必定难维护

这个坑太常见了，老赵得专门拎出来说。

### 反例长什么样？

很多人一开始写弹窗，会这么干：

- 弹窗组件里直接写表单字段
- 点击确认后直接调用接口
- 接口成功后直接刷新列表
- 删除、编辑、提交全塞进一个组件
- 甚至把权限判断也写进弹窗内部

结果就是：

- 弹窗看着像通用组件，实际只服务某一个页面
- 其他业务想复用，发现参数越来越多
- 后期修改一个按钮文案，要把业务流程也翻一遍
- 出问题时根本不知道是 UI 错了还是业务错了

### 拆开以后会更清爽

正确的拆法是：

#### 弹窗组件负责
- 显示与隐藏
- 标题、内容、按钮
- 基础交互事件
- loading 和关闭状态

#### 业务页面负责
- 调接口
- 校验数据
- 决定关闭时机
- 刷新列表
- 处理失败提示

比如“删除用户”这个场景：

- 弹窗只是显示“确认删除吗？”
- 用户点确认后，弹窗抛出 `confirm`
- 父组件收到后发删除接口
- 接口成功再关弹窗并刷新数据

这样一拆，逻辑就顺了。弹窗可复用，业务也好维护。

### 可复用组件案例：从“页面专属弹窗”重构成 ConfirmDialog

原来写法是一个页面一个弹窗，代码散落在业务里。  
重构之后：

- 页面只管业务动作
- ConfirmDialog 只管交互壳
- 内容用插槽注入
- 确认行为通过事件上抛

这就是从“能跑”到“能复用”的关键一步。

### 老赵常见踩坑提醒

**弹窗逻辑和业务逻辑一缠，后面不是难改，是根本不敢改。**  
你以为省了几行代码，实际上是把未来的维护成本全提前预支了。

---

## 六、弹窗组件有哪些常见扩展点？边界又该怎么控制？

弹窗一旦复用，需求就会不断冒出来：能不能全屏？能不能点遮罩关闭？能不能隐藏取消按钮？能不能按回车确认？

这时候就要提前考虑扩展点，但不能无限扩。

### 1）常见扩展点

常见可配置项包括：

- 标题文本
- 宽度
- 是否显示关闭按钮
- 是否允许遮罩关闭
- 是否显示底部操作区
- 确认/取消文案
- 确认和取消回调
- loading 状态

这些配置足够覆盖大部分通用场景。

### 2）边界控制原则

#### 第一条：只开放高频通用项
低频需求别一开始就参数化，不然组件会越做越胖。

#### 第二条：业务差异交给插槽和事件
能用插槽解决的，不要硬加配置；能让父组件处理的，不要在内部写死。

#### 第三条：状态变更要单向清晰
确认后是直接关闭，还是等接口成功再关，必须明确，别到处散。

这其实就是在控制组件边界。边界清楚，组件才不会变成“啥都管一点，啥都管不好”的四不像。

### 可复用组件案例：ConfirmDialog 的扩展能力

一个成熟的确认弹窗通常会支持：

- 自定义标题
- 自定义确认/取消文案
- 自定义内容插槽
- 关闭前拦截
- 确认 loading
- 遮罩是否关闭

这已经能覆盖大量业务了。别一上来就把语音播报、倒计时、多语言全塞进去，先把最常见的场景做稳。

### 老赵常见踩坑提醒

**最危险的不是功能少，而是扩展点乱加。**  
参数一多，组件就变成“配置怪兽”，看着灵活，实际上没人敢改。记住，封装不是把所有需求塞进去，而是把80%的通用需求做稳。

---

## 七、如何写一份简单但好用的组件文档？

一个可复用组件，不能只给代码，至少要写清楚怎么用。弹窗这种组件尤其如此，因为它既有受控状态，又有事件，又有插槽，还可能有关闭前拦截。

### 一个简单文档模板就够了

你可以按下面这个模板写：

#### 1）组件用途
一句话说明组件是干什么的。  
比如：`ConfirmDialog` 用于展示确认类交互，支持自定义标题、内容和操作按钮。

#### 2）props 列表
写清楚每个参数的含义，比如：

- `modelValue`：是否显示
- `title`：弹窗标题
- `confirmText`：确认按钮文案
- `cancelText`：取消按钮文案
- `confirmLoading`：确认按钮加载状态

#### 3）events 列表
告诉使用者什么时候会触发事件：

- `update:modelValue`
- `confirm`
- `cancel`
- `close`

#### 4）slots 列表
说明哪些内容可以自己传：

- `default`：弹窗主体内容
- `title`：自定义标题
- `footer`：自定义底部按钮区

#### 5）使用示例
给一个最小可运行示例，别只写接口列表，不写例子。  
业务同学最怕的就是“看懂了名字，不知道怎么接”。

#### 6）注意事项
写清楚：

- 这是受控还是非受控
- 确认后是否自动关闭
- loading 期间是否禁止重复点击
- 遮罩关闭是否默认开启

这份文档不用长，但一定要完整。**文档不是摆设，是让组件真正能被团队复用的前提。**

### 可复用组件案例：ConfirmDialog 文档页

如果你把上面这些内容整理成一个 Markdown 文档，基本就能让同事快速上手。  
这比单纯丢一个 `.vue` 文件靠谱得多，因为别人一看就知道这组件的边界、能力和限制。

### 老赵常见踩坑提醒

**组件写完不写文档，等于把复用门槛全交给别人猜。**  
你自己当然知道怎么用，但同事不知道。结果大家宁愿复制一份新写，也不敢直接复用，你这封装就白做了。

---

## 结尾小结：弹窗封装，拼的是边界感

这一章你要真正记住的，不是某个 UI 写法，而是弹窗封装的思路：

- **先划组件边界**：弹窗管壳子，业务管内容
- **再定状态模式**：优先搞清受控还是非受控
- **再用插槽承载变化**：内容多变，结构稳定
- **再控制扩展点**：别把组件做成配置黑洞
- **最后补文档**：让别人知道怎么用、怎么改、怎么扩

如果你能把一个 `ConfirmDialog` 做明白，后面很多复杂组件其实都能套这个思路去拆。

### 赵老师最后给你一句话

**弹窗不是“弹出来的页面”，而是“有边界的交互容器”。**  
弹窗控制权别乱抢，业务逻辑别和展示逻辑拧成一团。边界清楚了，组件才好复用；状态清楚了，代码才好维护；文档清楚了，团队才敢扩。  
这一套吃透了，后面做表单弹窗、抽屉弹窗、详情弹窗，都会顺很多。

# 第10章 列表组件实战：把展示型组件做得既灵活又统一

## 开篇引入：列表看起来简单，其实最容易“长歪”

很多人第一次写列表组件，都会觉得：不就是 `v-for` 循环一把吗？  
真到项目里你就会发现，列表最难的从来不是“能不能显示”，而是**展示结构、状态管理、内容定制、数据联动**能不能同时做好。

一个业务列表通常会碰到这些事：

- 头像、标题、标签、摘要混着来；
- 操作按钮、批量选择、展开收起都要有；
- 空状态、加载中、错误态不能缺；
- 筛选、分页、刷新要联动；
- 还要处理请求乱序、页码越界、切换筛选后数据不同步。

所以老赵先把话说透：**列表组件不是循环模板，而是“展示壳 + 状态处理 + 内容定制 + 数据联动”的组合体。**

这章我们就围绕一个可复用的 `DataList` 组件，讲清楚列表组件怎么设计、怎么拆、怎么抽象，以及怎么和分页筛选联动。

---

## 一、列表组件的通用结构：数据、渲染、状态、操作怎么拆？

### 1. 列表组件到底负责什么？

一个合格的列表组件，至少要管四件事：

- **数据**：展示哪组数据；
- **渲染**：每一项怎么画；
- **状态**：空、加载、错误、正常；
- **操作**：刷新、点击、选择、删除、编辑等事件。

它本质上不是“显示数组”，而是“围绕数据状态输出统一 UI”。

这里要特别注意：**列表组件不是页面**。  
页面负责路由、接口、权限、筛选、分页参数；列表组件只负责把一组数据稳定地展示出来。边界一乱，组件就会从展示壳变成业务大杂烩。

### 2. 组件边界怎么定？

列表组件最重要的一点，就是先定好**组件边界**：

- **组件内处理**：空状态、加载中、错误提示、基础布局；
- **外部传入**：数据、字段展示规则、按钮动作、业务文案；
- **不要塞进组件里**：具体 API 请求、复杂权限判断、页面跳转；
- **谨慎放进组件里**：只适合单一业务的复杂规则。

拿不准时就问自己一句：**这个能力是不是大多数列表场景都通用？**  
如果不是，通常就不该放进组件里。

### 3. 受控/非受控思路怎么用在列表里？

列表也能套用**受控/非受控**思路：

- **受控**：数据、加载状态、选中项由父组件控制，列表只负责展示和发事件；
- **非受控**：列表内部维护少量局部状态，比如折叠展开、局部高亮、内部排序开关。

跨页面复用的展示型列表，老赵建议优先走**受控**：  
**外部控制数据，内部控制展示细节。**  
比如“显示哪批数据”“是否加载中”“是否错误”，交给父组件；“边框、间距、hover 样式”，交给列表组件自己管。

### 4. 可复用组件案例：基础 DataList 结构

```vue
<template>
  <div class="data-list">
    <div class="data-list__header" v-if="$slots.header">
      <slot name="header" />
    </div>

    <div v-if="loading" class="data-list__state">加载中...</div>
    <div v-else-if="error" class="data-list__state">加载失败：{{ error }}</div>
    <div v-else-if="!data.length" class="data-list__state">暂无数据</div>

    <div v-else class="data-list__body">
      <slot
        v-for="(item, index) in data"
        :key="item.id ?? index"
        name="item"
        :item="item"
        :index="index"
      />
    </div>

    <div class="data-list__footer" v-if="$slots.footer">
      <slot name="footer" />
    </div>
  </div>
</template>
```

这个骨架的价值在于，它把列表拆成了：**头部、主体、底部、状态区**。后面的扩展都围绕这个骨架来做。

### 老赵常见踩坑提醒

**别把列表组件写成“万能容器”。**  
一旦把 API 请求、分页逻辑、权限按钮、搜索筛选都塞进去，组件就会越来越胖，最后谁都不敢改。

---

## 二、如何拆分列表的头部、主体和底部区域？

### 1. 为什么要分头部、主体、底部？

列表在业务里最常见的结构就是：

- **头部**：标题、筛选、搜索、批量操作；
- **主体**：列表项内容；
- **底部**：分页、合计、更多操作。

拆开不是为了好看，而是为了职责清晰。头部负责说明和控制，主体负责内容输出，底部负责收口。结构稳了，业务变化才好接。

### 2. 头部怎么设计？

头部通常放：

- 标题；
- 搜索框；
- 筛选条件；
- 批量按钮。

建议直接开放具名插槽：

```vue
<slot name="header" />
```

因为头部变化最大，写死模板后面只会越来越多 `v-if`。很多页面是“标题 + 搜索”，有些是“筛选器 + 新建按钮”，还有的是“说明文字 + 批量操作”。这部分最适合交给插槽。

### 3. 主体怎么设计？

主体是核心，但不要把每项内容固定死。  
正确做法是：**组件负责遍历，外部负责每一项长什么样。**  
也就是把 `item` 和 `index` 暴露出去，具体渲染交给插槽。

### 4. 底部怎么设计？

底部常见内容有：

- 分页器；
- 合计信息；
- 追加说明；
- 批量操作提示。

底部也建议开放插槽，别把分页写死。因为有的页面不分页，有的是“加载更多”，还有的是无限滚动。默认绑死分页，迁移场景会很别扭。

### 5. 可复用组件案例：三段式 DataList

记住这个公式：

> **头部插槽 + 主体项插槽 + 底部插槽 + 状态统一处理**

这就是一个能落地的列表骨架。它不是炫技，而是让列表像搭积木，而不是写死模板。

### 老赵常见踩坑提醒

**不要把“分页”默认写进列表底部。**  
很多项目不是分页列表，而是卡片流、消息流、日志流。你一写死，后面改成加载更多就很痛苦。

---

## 三、列表项的内容定制与插槽设计，怎么既灵活又不乱？

### 1. 为什么列表项一定要用插槽？

因为列表项变化太大了。

有的要标题 + 副标题，有的要头像 + 标签，有的要缩略图 + 详情，有的还要操作区。你如果用 props 一个个拼，最后一定会越来越臃肿。  
所以列表项最适合的方式就是：**把渲染权交给插槽。**

### 2. 具名插槽怎么配合列表项？

常见做法是给列表项一个 `item` 插槽：

```vue
<slot name="item" :item="item" :index="index" />
```

外部这样用：

```vue
<DataList :data="users">
  <template #item="{ item, index }">
    <div class="user-card">
      <strong>{{ index + 1 }}. {{ item.name }}</strong>
      <span>{{ item.role }}</span>
    </div>
  </template>
</DataList>
```

`DataList` 不关心用户卡片怎么长，只负责统一壳子。

### 3. 作用域插槽的价值在哪里？

作用域插槽的本质就是：**组件把数据抛出去，外部决定怎么画。**  
对列表这种展示型组件来说，这很重要：既保留统一结构，又能按业务定制，还能减少 props 层层传递。

### 4. 插槽使用场景怎么判断？

老赵给你一个简单判断：

- **结构固定、内容变化大**：用插槽；
- **内容固定、参数变化小**：用 props；
- **既要统一结构，又要高度定制**：插槽 + 少量 props 一起用。

列表组件特别适合这个判断法，因为它天然就是“结构稳定、内容变化大”。

### 5. 可复用组件案例：带 item 插槽的列表

```vue
<DataList :data="products">
  <template #item="{ item }">
    <div class="product-row">
      <img :src="item.cover" class="cover" />
      <div class="info">
        <h4>{{ item.title }}</h4>
        <p>{{ item.desc }}</p>
      </div>
    </div>
  </template>
</DataList>
```

好处很直接：**列表骨架统一，内容展示自由。**

### 老赵常见踩坑提醒

**别为了“通用”把所有字段都做成 props。**  
一旦 props 越来越多，十有八九说明你该用插槽了，而不是继续加属性。

---

## 四、空数据、加载中、错误态，怎么统一处理才不乱？

### 1. 为什么这些状态一定要统一处理？

列表页面最烦的不是有数据，而是“没数据的时候长什么样”。  
如果每个页面自己写一套空状态、加载状态、错误状态，那体验不统一，维护也麻烦。

更糟的是，状态散落在各处：一个页面写 `loading`，一个写 `isLoading`，空态再单独放一个 `Empty` 组件，后面找问题会很累。

### 2. 统一状态的设计原则

建议列表组件内部统一状态顺序：

1. `loading`
2. `error`
3. `empty`
4. 正常渲染

顺序别乱。加载中和错误态优先级更高，不能让空状态抢戏。

### 3. 状态区也要可定制

不同业务空态文案不一样：

- 商品列表：暂无商品；
- 订单列表：暂无订单；
- 消息列表：暂无消息。

所以状态别写死，建议提供插槽或文案 props：

```vue
<slot name="loading">加载中...</slot>
<slot name="error" :error="error">加载失败</slot>
<slot name="empty">暂无数据</slot>
```

这样既统一，又灵活。

### 4. 可复用组件案例：统一状态的 DataList

```vue
<div v-if="loading" class="state">
  <slot name="loading">加载中...</slot>
</div>
<div v-else-if="error" class="state">
  <slot name="error" :error="error">加载失败</slot>
</div>
<div v-else-if="!data.length" class="state">
  <slot name="empty">暂无数据</slot>
</div>
```

这套结构很适合做成通用展示组件。

### 老赵常见踩坑提醒

**别把空状态当成“后补内容”随手写在页面里。**  
空状态不是装饰，它是列表体验的一部分。统一处理，后面维护才轻松。

---

## 五、列表和分页、筛选怎么联动，数据流才不会打架？

### 1. 真正的列表，通常不是单独存在的

到业务里，列表很少是孤立组件。更常见的是：

- 上面有筛选条件；
- 中间是列表；
- 下面是分页；
- 旁边还有搜索、刷新、批量操作。

这时候最重要的不是“能不能显示”，而是**数据流怎么走**。  
老赵建议你把它想成一条线：

> 筛选变化 → 请求数据 → 更新 loading → 返回数据/错误 → 列表展示 → 分页同步

这条线要顺，页面才不乱。

### 2. 筛选和分页为什么要联动？

因为筛选条件一变，页码通常应该回到第一页。  
这是特别容易漏掉的地方。

比如你当前在第 5 页，突然改了“状态=已完成”，如果页码不归零，有可能直接查不到数据。用户会以为系统坏了，其实只是页码没重置。

所以比较合理的规则是：

- **筛选变化时，页码回到 1**
- **页大小变化时，页码回到 1**
- **刷新时，保留筛选，重新拉取数据**
- **切换排序时，按规则决定是否回到第一页**

### 3. 异步竞态和请求乱序怎么处理？

这是列表组件里很实战的一块。  
你点了筛选 A，接口还没回来，又立刻点筛选 B。结果 A 比 B 更晚返回，把 B 的结果覆盖，这就是典型的**请求乱序**。

#### 方案一：请求序号法

每次发请求时记录一个递增编号，只接收最后一次请求的结果。

```js
let requestSeq = 0

async function fetchList(params) {
  const currentSeq = ++requestSeq
  loading.value = true

  try {
    const res = await api.getList(params)
    if (currentSeq !== requestSeq) return
    data.value = res.list
  } catch (err) {
    if (currentSeq !== requestSeq) return
    error.value = err.message || '加载失败'
  } finally {
    if (currentSeq === requestSeq) loading.value = false
  }
}
```

#### 方案二：AbortController 取消上一次请求

如果请求层支持取消，那就更干净。新请求发起前先取消旧请求，避免旧结果覆盖新结果。

这两种方式本质上都在解决同一个问题：**只让最新状态生效。**

### 4. 页码越界也要兜底

还有一个常见边界：删除一条数据后，当前页可能空了；或者筛选后总页数变少，当前页码超出范围。

这时页面层或列表联动层应该兜底：

- 当前页空了，自动回退到上一页；
- 新总页数小于当前页，修正页码；
- 页码变化后重新请求，保证界面和数据一致。

### 5. 可复用组件案例：DataList + Pagination 的联动模板

```vue
<DataList :data="list" :loading="loading" :error="error">
  <template #header>
    <FilterBar
      :model-value="filters"
      @change="handleFilterChange"
      @refresh="handleRefresh"
    />
  </template>

  <template #item="{ item }">
    <ListCard :item="item" />
  </template>

  <template #footer>
    <Pagination
      :current="page"
      :page-size="pageSize"
      :total="total"
      @change="handlePageChange"
      @page-size-change="handlePageSizeChange"
    />
  </template>
</DataList>
```

这里的职责很清楚：

- `FilterBar` 负责筛选；
- `DataList` 负责统一展示；
- `Pagination` 负责分页；
- 页面层负责请求和数据流控制。

### 老赵常见踩坑提醒

**别让列表和分页互相“偷控制权”。**  
页面改页码，列表自己又偷偷翻页；筛选变了，分页不重置。看起来是小毛病，排查起来很费劲。

## 六、一个完整的可复用 DataList 组件，应该长什么样？

### 1. 组件接口设计

建议 `DataList` 至少支持这些输入：

- `data`：列表数据；
- `loading`：加载状态；
- `error`：错误信息；
- `emptyText`：空状态文案；
- `rowKey`：主键字段；
- `bordered`：是否边框样式。

### 2. 简化代码结构

```vue
<script setup>
defineProps({
  data: { type: Array, default: () => [] },
  loading: Boolean,
  error: [String, Boolean],
  emptyText: { type: String, default: '暂无数据' },
  rowKey: { type: String, default: 'id' },
  bordered: Boolean
})
</script>

<template>
  <div class="data-list" :class="{ 'data-list--bordered': bordered }">
    <slot name="header" />

    <div v-if="loading" class="data-list__state">
      <slot name="loading">加载中...</slot>
    </div>

    <div v-else-if="error" class="data-list__state">
      <slot name="error" :error="error">加载失败</slot>
    </div>

    <div v-else-if="!data.length" class="data-list__state">
      <slot name="empty">{{ emptyText }}</slot>
    </div>

    <div v-else class="data-list__body">
      <slot
        v-for="(item, index) in data"
        :key="item[rowKey] ?? index"
        name="item"
        :item="item"
        :index="index"
      />
    </div>

    <slot name="footer" />
  </div>
</template>
```

### 3. 为什么这个组件值得复用？

因为它把最容易重复的部分都收起来了：

- 状态处理统一；
- 结构统一；
- 内容渲染开放；
- 业务定制走插槽；
- 主键字段可配置，避免硬编码。

这就是可复用业务组件的典型思路：**把变化最大的地方交给外部，把变化最少的地方收进来。**

### 4. 这个组件的边界

它只负责**展示和状态切换**，不负责：

- 请求数据；
- 翻页逻辑；
- 搜索过滤；
- 权限判断；
- 路由跳转。

边界清楚，组件才不会膨胀成列表大杂烩。

### 5. 如何给它写简单文档？

可复用组件最好配一个简短说明，别写虚话。老赵建议直接按这个模板来：

#### DataList 组件说明

- **用途**：用于展示标准化列表内容，支持空态、加载中、错误态；
- **Props**：`data`、`loading`、`error`、`emptyText`、`rowKey`、`bordered`
- **插槽**：
  - `header`：列表头部
  - `item`：列表项内容
  - `footer`：列表底部
  - `empty`：空状态
  - `loading`：加载中
  - `error`：错误态
- **数据流**：父组件负责请求、筛选、分页；`DataList` 只负责展示
- **适用场景**：商品列表、用户列表、消息列表、日志列表等
- **注意事项**：列表项需要复杂交互时，优先用 `item` 插槽，不要继续堆 props

这就是简单但实用的组件文档写法。

### 老赵常见踩坑提醒

**别把文档写成“自我感动说明书”。**  
真正有用的文档，是告诉别人：这个组件干什么、不干什么、怎么用、有哪些插槽和边界。

---

## 七、列表组件怎么复用与抽象？什么时候该抽，什么时候别抽？

### 1. 复用不是越抽越好

很多人学会抽象后，马上想把所有列表都抽成一个公共组件。老赵提醒你：**抽象不是目的，减少重复才是目的。**  
如果一个组件为了兼容太多场景，最后长成参数怪兽，那它不是复用，是折磨。

### 2. 哪些地方适合抽象？

适合抽象的通常是：

- 统一状态；
- 通用外壳；
- 标准化布局；
- 重复的列表结构；
- 多页面共用的空态和加载态。

### 3. 哪些地方不适合抽象？

不适合抽象的通常是：

- 每个业务差别很大的操作区；
- 复杂表头；
- 特殊交互；
- 强业务绑定逻辑；
- 只在单个页面出现的临时规则。

如果一个列表组件为了兼容十个项目塞进二十个 props，它已经失去意义了。

### 4. 抽象的判断标准

老赵给你一个实用标准：

- **至少重复 2-3 次，再考虑抽象**；
- **抽象后接口要简单**；
- **业务差异通过插槽/少量 props 解决**；
- **组件职责必须能一句话说清楚**；
- **页面层保留业务判断，组件层保留展示能力**。

### 5. 可复用组件案例：从页面列表抽出 DataList

比如用户列表页、订单列表页、文章列表页，如果都存在“数据 + 状态 + item 渲染”的共性，就适合抽出 `DataList`。  
而“订单列表特有的筛选器”“文章列表特有的标签统计”，保留在页面层。

这个抽象方式最稳：**壳子归组件，业务归页面。**

### 老赵常见踩坑提醒

**不要为了复用，把业务页面抽成四不像。**  
抽象过头，最后你会发现：新项目接不进去，老项目改不动。

---

## 八、结尾小结：列表组件真正要追求的，是统一骨架下的灵活表达

这章其实只讲了一件事：**列表组件不是简单循环，而是一个要兼顾结构、状态、定制能力和数据联动的展示型组件。**

你做列表组件时，记住这几个关键词就够了：

- **组件边界清楚**：展示归展示，业务归业务；
- **受控优先**：数据、筛选、分页尽量由外部掌控；
- **插槽是主力**：尤其是 `item`、`header`、`footer`；
- **状态统一处理**：空、加载、错误别散落在各页面；
- **联动要顺**：筛选改了，页码要回一页；请求乱序，要防覆盖；
- **抽象要克制**：能复用，不代表要全能。

### 赵老师最后给你的行动建议

下次你在项目里写列表，不妨先问自己五个问题：

1. 这个列表的**骨架**能不能统一？
2. 哪些内容应该交给**插槽**？
3. 空状态、加载中、错误态是不是已经统一？
4. 筛选、分页、刷新之间的数据流是不是顺的？
5. 这个组件的**边界**是不是清楚，没把业务逻辑塞进去？

如果这五个问题你都答得上来，那你写出来的列表组件，基本就不是“能用”，而是“真能复用”。这才是组件开发进阶该有的样子。

### 老赵常见踩坑提醒

**别为了通用，把列表做成谁都不会用的拼装机。**  
真正好的列表组件，不是把所有可能都塞进去，而是把常用的骨架搭稳，把变化交给插槽，把边界守住。这样才叫灵活，才叫统一，才叫能长期维护。

# 第11章 分页组件实战：小组件也要有大讲究

## 开篇引入：分页这种“小组件”，最容易把人坑到怀疑人生

很多人写分页，第一反应都是：**不就是几个页码按钮吗？** 真上手才知道，这东西看着小，坑不少：上一页、下一页、每页条数、总数变化、当前页越界、和列表联动、受控还是非受控……状态一乱，页面立刻“抽风”。

所以这一章不只是做一个能用的分页，而是把它当成一个**高频基础业务组件**来设计：

- 组件边界怎么划
- 哪些状态交给外部，哪些自己管
- API 怎么设计得稳定清晰
- 怎么和列表联动不打架
- 怎么写成别人一看就会用的组件
- 顺手补一份简单文档，方便协作

老赵先给你一句结论：**分页越简单，越要讲究边界和状态设计。** 因为它到处都要用，今天你随便写，明天整个项目都可能跟着受罪。

---

## 一、分页组件的基础能力：到底要解决什么问题？

分页的职责其实就四件事：

1. 展示当前页码
2. 展示总数和页大小
3. 支持切换页码
4. 在变化时通知外部

基础版分页至少要表达这些信息：

- 当前页：`currentPage`
- 每页条数：`pageSize`
- 总条数：`total`
- 页码变化事件：`change`
- 页大小变化事件：`page-size-change`

### 1.1 分页的本质不是“翻页按钮”，而是“数据范围切换”

分页不是为了好看，而是告诉列表：**我现在要哪一段数据**。

比如：

- 第 1 页，每页 10 条：取 `0~9`
- 第 2 页，每页 10 条：取 `10~19`
- 第 3 页，每页 20 条：取 `40~59`

所以分页组件真正输出的，不是按钮，而是**当前数据窗口**。这个思路清楚了，API 设计就不会跑偏。

### 1.2 一个合格的分页组件，最少要支持哪些能力？

建议至少支持：

- 首页 / 尾页
- 上一页 / 下一页
- 页码列表
- 当前页高亮
- 每页条数切换
- 总数展示
- 禁用态
- 当前页越界修正

### 1.3 组件边界先想清楚

老赵建议你记住一句话：**分页只管“翻页”，不管“查数据”。**  
查数据、筛选条件、加载状态、请求异常，都属于父组件或页面层。分页最多负责“我变了”的通知。

### 组件案例：基础分页信息结构

```vue
<Pagination
  :current-page="currentPage"
  :page-size="pageSize"
  :total="total"
  @change="handlePageChange"
  @page-size-change="handlePageSizeChange"
/>
```

### 老赵常见踩坑提醒

**最常见的坑，不是不会写按钮，而是把“显示状态”和“数据状态”混成一锅粥。**  
比如列表变了，分页没同步；总数变了，当前页还停在不存在的页码；页大小变了，当前页不重置，结果请求空白页。  
一句话：**分页不是摆设，它和数据范围是一体的。**

---

## 二、受控分页和内部态分页：状态到底放哪儿才不乱？

这里是分页设计的核心。你得先回答：**当前页到底谁说了算？**

### 2.1 受控分页：外部管状态，组件只负责显示和通知

受控模式就是：父组件持有 `currentPage`、`pageSize`、`total`，分页组件只负责：

- 展示当前值
- 用户操作时触发事件
- 不自己改外部状态

适合：

- 列表数据由接口控制
- 页面状态要和路由、筛选表单联动
- 需要统一管理分页逻辑

```vue
<Pagination
  :current-page="page.current"
  :page-size="page.size"
  :total="page.total"
  @change="page.current = $event"
/>
```

### 2.2 内部态分页：组件自己维护当前页

内部态分页是组件自己存当前页，点击时自己切换，同时通知外部。

适合：

- 纯展示型分页
- 简单场景
- 业务方不想管太多状态

但老赵提醒你：**内部态分页用起来爽，维护起来未必爽。** 它很容易和外部状态脱节。

### 2.3 怎么选？看两个标准

#### 标准一：分页状态是否影响接口请求？
会影响，优先受控。因为接口数据是外部来的，外部必须能掌控分页状态。

#### 标准二：分页是否需要和筛选条件联动？
会联动，也优先受控。比如搜索条件一变，分页通常要回到第一页，这不是组件内部能随便决定的。

### 2.4 一个可复用的判断方法

- 页面级业务：优先受控
- 局部展示：可以考虑非受控
- 会和接口打交道：尽量受控
- 会和搜索表单联动：尽量受控

### 2.5 两种模式的适用场景对照

| 场景 | 推荐模式 | 原因 |
| --- | --- | --- |
| 商品列表、用户列表、订单列表 | 受控 | 需要和接口请求联动 |
| 弹层内的小型数据翻页 | 受控或内部态都可 | 取决于是否要回传父级 |
| 本地数组分页展示 | 内部态 | 数据不依赖接口 |
| 搜索条件频繁变化的页面 | 受控 | 方便统一重置页码 |

### 组件案例：受控分页推荐写法

```vue
<Pagination
  :current-page="currentPage"
  :page-size="pageSize"
  :total="total"
  @change="onPageChange"
  @page-size-change="onPageSizeChange"
/>
```

```js
const currentPage = ref(1)
const pageSize = ref(10)
const total = ref(0)

function onPageChange(page) {
  currentPage.value = page
  fetchList()
}

function onPageSizeChange(size) {
  pageSize.value = size
  currentPage.value = 1
  fetchList()
}
```

### 老赵常见踩坑提醒

**别把受控和非受控混着用。**  
最典型的问题就是：外部传了 `currentPage`，组件内部又自己改一份 `innerCurrentPage`，最后两个值不同步。UI 变了，接口没变；接口变了，UI 又回去了。  
老赵一句话：**一个状态，只能有一个真正的主人。**

## 三、分页与列表联动：为什么很多项目分页一联动就出 bug？

分页单独看很简单，真正麻烦的是和列表联动。分页不是一个独立摆件，它通常服务于表格、卡片列表、搜索结果页，所以联动流程一定要理顺。

### 3.1 正确思路

不是“点分页，列表自己刷新”，而是：

1. 分页触发变化事件
2. 父组件更新分页状态
3. 父组件重新请求列表
4. 返回结果后更新列表和总数

分页只负责第 1 步，后面交给父组件。

### 3.2 页码变化、页大小变化、重新请求数据分别怎么处理？

#### 页码变化
本质是“在当前查询条件下切换数据窗口”。

处理方式：

- 更新 `currentPage`
- 保持 `pageSize` 不变
- 重新请求列表

#### 页大小变化
本质是“同一套条件下，数据窗口大小变化了”。

处理方式：

- 更新 `pageSize`
- **把 `currentPage` 重置为 1**
- 重新请求列表

为什么要回第一页？因为页大小变了，原来的页码对应关系已经变了，继续停在老页码上，很容易查出空数据或越界。

#### 重新请求数据
通常发生在这些场景：

- 搜索条件变化
- 排序条件变化
- 路由参数变化
- 外部手动刷新

处理方式：

- 保持最新查询条件
- 如果条件变动影响数据范围，`currentPage` 先归 1
- 再发起请求

### 3.3 搜索条件和分页联动时，最容易出什么问题？

三个高频坑：

- 搜索条件变了，当前页没重置
- 页大小变了，当前页还沿用旧值
- 列表请求慢，旧请求回来覆盖新请求

所以要养成习惯：

- **筛选条件变化 -> currentPage 置 1**
- **pageSize 变化 -> currentPage 置 1**
- **请求结果返回时，以最新条件为准**

### 3.4 一个实战中的联动方式

```vue
<SearchForm @submit="handleSearch" />
<Table :data="list" />
<Pagination
  :current-page="query.page"
  :page-size="query.pageSize"
  :total="total"
  @change="handlePageChange"
  @page-size-change="handlePageSizeChange"
/>
```

```js
const query = reactive({
  keyword: '',
  page: 1,
  pageSize: 10
})

function handleSearch(form) {
  query.keyword = form.keyword
  query.page = 1
  fetchList()
}

function handlePageChange(page) {
  query.page = page
  fetchList()
}

function handlePageSizeChange(size) {
  query.pageSize = size
  query.page = 1
  fetchList()
}

async function fetchList() {
  const params = {
    keyword: query.keyword,
    page: query.page,
    pageSize: query.pageSize
  }

  const res = await apiGetList(params)
  list.value = res.list
  total.value = res.total

  const maxPage = Math.max(1, Math.ceil(total.value / query.pageSize))
  if (query.page > maxPage) {
    query.page = maxPage
    return fetchList()
  }
}
```

### 3.5 页码越界、总数变化怎么办？

#### 场景一：删除了一条数据，总数变少
原来在第 5 页，删完后总页数变成 4 页，此时当前页 5 就越界了。

处理方式：

- 计算最新最大页码 `maxPage`
- 如果 `currentPage > maxPage`，把 `currentPage` 改成 `maxPage`
- 重新请求

#### 场景二：筛选条件变了，总数大幅下降
比如原来 100 条，筛选后只剩 12 条。当前页如果还是 10，就不合理。

处理方式：

- 直接重置 `currentPage = 1`
- 重新请求列表

#### 场景三：页大小切换后页码超范围
比如在第 8 页，每页 10 条，切到每页 50 条后只剩 2 页。

处理方式：

- 页大小切换时先回首页
- 再请求新数据

### 3.6 组件边界在这里特别重要

分页不该知道搜索框里填了什么，表格也不该知道第几页怎么来的。  
这就是组件边界：**每个组件只负责自己那一小块职责，别越界。**

### 组件案例：列表联动分页的父组件结构

分页纯、列表清楚、后期改接口或筛选条件，都不容易把分页改炸。

### 老赵常见踩坑提醒

**分页联动最怕请求顺序乱套。**  
你点了第 3 页，接口还没回来又点了第 4 页，结果第 3 页数据比第 4 页先返回，页面就显示错了。业务一复杂，别只顾改 UI，**请求取消、请求标记、结果校验**也要考虑。

## 四、分页组件 API 怎么设计才稳定清晰？

分页是高频基础组件，API 一定要克制。不是功能越多越好，而是**表达越清晰越好**。

### 4.1 推荐的 API 设计原则

#### 原则一：命名统一
建议统一用：

- `currentPage`
- `pageSize`
- `total`

事件统一用：

- `change`
- `page-size-change`

别今天 `pageChange`，明天 `onPageChange`，后天又来个 `update:currentPage` 还不统一，大家用起来像猜谜。

#### 原则二：默认值明确
建议默认：

- `currentPage = 1`
- `pageSize = 10`
- `total = 0`

#### 原则三：能力分层
基础版分页只做分页，别把筛选、排序、跳页输入框全揉进去。需要“跳页输入”“页大小下拉”“总数显示”，可以作为可选能力，但别一上来做成万能盒子。

### 4.2 简单文档怎么写？

可复用组件一定要写简单文档，哪怕只有一页，也比没有强。最少包含：

- 组件用途
- Props 列表
- Events 列表
- 示例代码
- 注意事项

例如：

#### `Pagination` 组件说明

- 用途：用于列表分页展示与切换
- Props：
  - `currentPage`：当前页码
  - `pageSize`：每页条数
  - `total`：总条数
- Events：
  - `change`：页码变化
  - `page-size-change`：每页条数变化
- 说明：
  - 受控模式下由父组件维护状态
  - 切换页大小时建议重置页码为 1
  - 当 `total` 变化导致页码越界时，建议由父组件修正

### 4.3 文档不是形式，是复用成本控制

当组件要被第二个人、第三个人用时，文档就是最便宜的沟通成本。你不用每次都口头解释“默认值是什么”“什么时候触发事件”“页大小变化后要不要重置页码”。

### 4.4 一份更像样的简单文档模板

```md
## Pagination

### 用途
用于列表分页展示与切换。

### Props
- `currentPage: number` 当前页码，默认 `1`
- `pageSize: number` 每页条数，默认 `10`
- `total: number` 总条数，默认 `0`

### Events
- `change(page)`：页码变化时触发
- `page-size-change(size)`：每页条数变化时触发

### 默认行为
- 点击上一页/下一页时，只触发事件，不直接请求数据
- 切换页大小后，建议业务层将页码重置为 `1`
- 当总数变化导致页码越界时，业务层应修正当前页

### 示例
```vue
<Pagination
  :current-page="page"
  :page-size="size"
  :total="total"
  @change="page = $event"
/>
```

### 注意事项
- 建议在页面级业务中使用受控模式
- 不要在组件内部偷偷维护另一份分页状态
- 分页只负责状态通知，不负责数据请求
```

### 组件案例：最小文档模板

这个模板不花哨，但很实用。很多协作问题不是代码写不出来，而是别人不知道怎么用。

### 老赵常见踩坑提醒

**API 最怕“看着灵活，实际上没人知道怎么用”。**  
如果一个分页组件要同时支持十几种参数，还得猜优先级，那就不是组件，是考试题。  
老赵建议：**先稳定核心 API，再慢慢加扩展能力。**

## 五、组件案例：一个可复用的 Pagination 分页组件

下面给你一个思路完整、不过度花哨的可复用分页组件。

### 5.1 设计目标

满足这些需求：

- 支持受控使用
- 支持基本页码切换
- 支持页大小切换
- 支持总数展示
- 对外只抛必要事件
- 页码越界时能被业务层修正

### 5.2 组件结构示意

```vue
<script setup>
const props = defineProps({
  currentPage: { type: Number, default: 1 },
  pageSize: { type: Number, default: 10 },
  total: { type: Number, default: 0 },
  disabled: { type: Boolean, default: false }
})

const emit = defineEmits(['change', 'page-size-change'])

function maxPage() {
  return Math.max(1, Math.ceil(props.total / props.pageSize))
}

function goPrev() {
  if (!props.disabled && props.currentPage > 1) {
    emit('change', props.currentPage - 1)
  }
}

function goNext() {
  if (!props.disabled && props.currentPage < maxPage()) {
    emit('change', props.currentPage + 1)
  }
}

function changePage(page) {
  if (!props.disabled && page !== props.currentPage) emit('change', page)
}

function changeSize(size) {
  if (!props.disabled && size !== props.pageSize) {
    emit('page-size-change', size)
  }
}
</script>

<template>
  <div class="pagination">
    <button :disabled="disabled || currentPage <= 1" @click="goPrev">上一页</button>

    <button
      v-for="page in maxPage()"
      :key="page"
      :class="{ active: page === currentPage }"
      :disabled="disabled"
      @click="changePage(page)"
    >
      {{ page }}
    </button>

    <button
      :disabled="disabled || currentPage >= maxPage()"
      @click="goNext"
    >
      下一页
    </button>

    <select :disabled="disabled" :value="pageSize" @change="changeSize(Number($event.target.value))">
      <option :value="10">10 / 页</option>
      <option :value="20">20 / 页</option>
      <option :value="50">50 / 页</option>
    </select>

    <span>共 {{ total }} 条</span>
  </div>
</template>
```

### 5.3 这个组件的可复用点在哪？

- **受控**：当前页和页大小由外部传入
- **纯粹**：不负责请求数据
- **清晰**：只做分页相关事情
- **易扩展**：后续可加“跳页”“省略号”“页大小切换”

### 5.4 如果要增强一点，怎么做？

可以继续加：

- `showSizeChanger`
- `showQuickJumper`
- `disabled`
- `layout`

但老赵建议你记住：**扩展要建立在稳定核心之上，不要先把自己绕晕。**

### 5.5 进一步优化的小方向

更像真实业务的话，还可以考虑：

- 总页数过多时显示省略号
- 当前页越界时自动修正
- 页大小变化后是否自动回到第一页
- `total = 0` 时如何展示空状态

这些都属于边界处理，看着小，实际特别影响体验。

### 5.6 一个更贴近业务的重构建议

如果分页用在多个列表页里，建议把“请求列表”封装成统一的业务层函数，分页只负责发事件，页面负责把这些事件转成查询参数更新。这样做的好处是：

- 页码变化逻辑统一
- 页大小切换逻辑统一
- 越界修正统一
- 后面改接口字段时只改一处

这就是**如何写可复用业务组件**的关键：  
不是把功能都塞进组件里，而是把职责边界切开，让组件、页面、请求层各干各的。

### 老赵常见踩坑提醒

**分页按钮数量和总页数一定要算准。**  
总数为 0 时怎么显示？页码太多时要不要省略？当前页超出最大页怎么办？  
这些边界不先处理，组件在小数据时正常，大数据时就开始胡来。

---

## 六、老赵总结：分页看着简单，真要做好全是细节

分页组件是典型的“小组件大讲究”。你要做好的，不只是几个按钮，而是：

- **组件边界清楚**
- **状态归属明确**
- **受控/非受控思路分明**
- **和列表联动稳定**
- **页码越界能兜住**
- **页大小切换知道回首页**
- **API 简洁统一**
- **文档能让别人一眼会用**

### 这一章你最该带走的行动建议

1. 先把分页当成“数据范围控制器”，不要只当 UI 按钮组
2. 优先做受控分页，减少状态打架
3. 分页和列表联动时，记得重置页码和处理异步顺序
4. 页大小变化后，默认回到第一页，这几乎是业务组件的标配
5. 当总数变化导致当前页越界时，必须修正当前页
6. 给组件补一份简单文档，后面维护会轻松很多

最后老赵送你一句实战经验：  
**分页不是难在实现，而是难在边界。**  
边界想清楚了，这个小组件就能在项目里稳稳当当地跑很多年。

# 第12章 组件复用与抽象：从单个组件走向一套组件方法论

## 开篇引入：复用，不是把代码搬来搬去

前面我们聊了单文件组件、`props/emit`、`slot` 和组件通信。到了这一章，咱们再往前走一步：**不只是写出一个能用的组件，而是写出一套能持续演进、能被别人接着用的组件方法论**。

很多人一说“组件复用”，第一反应就是复制一份改改，或者硬做一个参数特别多的万能组件。老赵先给你结论：**复用不是复制粘贴，也不是硬凑一个万能父组件。** 真正的复用，是先看清组件边界，再提炼稳定能力，最后把变化留出出口。

这一章就围绕三个问题展开：**什么时候该抽象，怎么抽象，抽到什么程度才合适。**  
你把这一章吃透，后面做表单、弹窗、列表、分页，就不会只停在“能写出来”，而是会开始考虑“怎么让它稳定地被复用”。

---

## 一、什么时候该抽象，什么时候不该抽象？

### 1. 先问三个问题，再决定要不要抽象

不是所有相似组件都值得抽。老赵建议先问三个问题：

1. **核心职责是不是一致？**  
   比如都是“弹出一个层，让用户确认或填写信息”，职责就接近。

2. **变化点是不是稳定？**  
   如果只是标题、文案、内容区不同，这种变化点比较稳，适合抽。

3. **未来是否还会重复出现？**  
   如果只是一次性需求，抽象成本往往大于收益。

这三个问题，本质上是在判断这个组件有没有“可复用的骨架”。职责都不一致，那你抽出来的多半不是方法论，而是一个杂物袋。

### 2. 不该抽象的典型情况

有些组件看着像，实际上不该硬抽：

- 只是样式像，业务逻辑完全不同；
- 未来需求还不明确，今天抽完明天就推翻；
- 内部已经很复杂，再抽一层只会更难读。

这里要记住一个关键点：**组件边界**。边界清晰的组件，职责单一，外部只通过少量 API 交互；边界模糊的组件，什么都管，最后谁都不好维护。

### 可复用的组件案例：判断是否值得抽象的“业务相似度清单”

你可以给候选组件做一个简单清单：

- 是否有相同的核心动作？
- 是否只有内容区不同？
- 是否能通过 `props` / `slot` 解决差异？
- 是否会在多个页面重复出现？
- 是否能在不破坏现有页面的前提下复用？

大部分答案是“是”，才值得抽象。否则就先别急，继续观察业务变化。

### 老赵常见踩坑提醒

**别因为“长得像”就急着抽。** 外观像，不代表职责像；接口像，不代表维护成本低。

---

## 二、从相似组件中提炼公共能力的方法

### 1. 先找稳定部分，再找变化部分

抽象最怕一上来就写组件框架。正确做法是先拆：

- **稳定部分**：遮罩、关闭逻辑、基础布局、底部按钮区；
- **变化部分**：标题、内容、按钮文案、表单字段、确认行为。

也就是说，把“大家都一样的东西”放进组件，把“各家不一样的东西”留给外部传进来。这就是组件复用能不能站住的关键。

### 2. 公共能力通常从这几类里提炼

常见的公共能力有：

- **展示能力**：标题、宽度、是否显示遮罩；
- **交互能力**：打开、关闭、确认、取消；
- **内容承载能力**：`slot` 插槽承载不同内容；
- **状态能力**：是否可见、是否加载中、是否禁用；
- **校验能力**：确认前是否需要校验表单。

最常见的做法，是把组件骨架固定住，再用 `props` 和 `slot` 交给外部定制细节。这样外部自由，内部稳定。

### 3. 用“最小可用版本”开始

不要一开始就想着“以后什么都要支持”。先做一个最小版本：

- 能显示和隐藏；
- 支持标题；
- 支持默认 `footer`；
- 内容区通过 `slot` 自定义。

等真实业务跑起来，再补能力。**先复用已发生的需求，再抽象未来可能的需求。**

### 可复用的组件案例：抽象弹窗时的公共能力

比如多个业务弹窗都有这些共性：

- 都有遮罩层；
- 都有标题栏；
- 都能关闭；
- 都有确认/取消按钮。

那就可以先抽一个 `BaseModal`，把这些公共能力收进去，内容区留给具名插槽或默认插槽。它不负责业务，它只负责“一个标准弹窗该有的样子”。

### 老赵常见踩坑提醒

**别把“抽象能力”当成“提前预言未来”。** 你现在看不到的需求，不代表一定要先设计好。抽象的目的，是降低重复成本，不是制造设计负担。

---

## 三、从多个业务弹窗抽出通用 Modal 基座：先相似，后抽象

### 1. 先不要急着统一，先把相似点跑出来

假设项目里已经有三个弹窗：

- 删除确认弹窗；
- 编辑用户信息弹窗；
- 订单备注弹窗。

一开始千万别上来就写 `Modal` 基座，先把这三个弹窗分别跑通。你会发现，它们虽然内容不同，但都有共同骨架：

- 需要遮罩；
- 需要标题；
- 需要关闭按钮；
- 需要底部确认/取消；
- 需要一个中间内容区。

这时候再看，抽象就不是拍脑袋，而是“先相似，后抽象”。

### 2. `BaseModal` 应该抽什么，不应该抽什么

适合抽出来的，是弹窗的通用壳子：

- 显示与隐藏；
- 宽度、标题、遮罩；
- 关闭行为；
- 底部区域；
- 过渡动画；
- 统一的视觉结构。

不适合抽出来的，是具体业务逻辑：

- 提交用户表单；
- 删除某条记录；
- 订单备注校验；
- 详情页里的字段展示。

这些逻辑一旦放进基座，`BaseModal` 就会从“壳子”变成“业务垃圾桶”。

### 3. 一个更稳的写法：内容交给插槽，行为交给事件

`BaseModal` 可以这样设计：

- `modelValue`：控制显示隐藏，采用受控思路；
- `title`：弹窗标题；
- `width`：弹窗宽度；
- `loading`：确认时的加载状态；
- 默认插槽：放主体内容；
- `footer` 插槽：自定义底部按钮；
- `confirm` / `cancel`：对外抛出行为事件。

这样做的好处很明显：**组件边界清楚。** 组件只管弹窗壳，业务怎么做交给外面。

### 4. 受控 / 非受控思路，在这里怎么选

对于弹窗这种组件，老赵一般建议优先用**受控**：

- 父组件决定弹不弹；
- 子组件只负责展示和发事件；
- 状态来源统一，不容易乱。

非受控不是不能用，但要小心。比如内部提示弹层，组件自己开关也行；可一旦弹窗和页面状态强相关，最好还是让父组件掌控。否则很容易出现页面都切走了，弹窗还在；或者父组件想关，子组件又自己打开了。

### 可复用的组件案例：`BaseModal`

一个好用的 `BaseModal`，不是功能最多，而是：

- 骨架稳定；
- 内容可变；
- 行为一致；
- 外部接入简单。

### 老赵常见踩坑提醒

**别把所有弹窗都塞进一个万能 `Modal`。** 该统一的是骨架，不该统一的是业务。越想“一把梭”，越容易把组件边界搞糊。

---

## 四、如何避免抽象过度和抽象不足？

### 1. 抽象过度：一个组件背着十个职责

抽象过度的常见表现是：

- `props` 一大堆；
- 配置项特别多；
- 内部很多 `if/else`；
- 外部使用时要记住一堆规则。

这种组件看起来“统一”，实际上难用得很。它什么都能做，但每次用都像在调一台复杂机器。**如果一个组件的使用文档比业务说明还长，大概率就是抽过头了。**

### 2. 抽象不足：每个页面都在重复写

抽象不足也很常见：

- 三个页面写三套差不多的弹窗；
- 同一套表单校验逻辑散落多个文件；
- 列表的空态、分页、查询条件每个地方都重新组织。

短期看不出来，长期维护成本很高。改一个地方，容易漏两个地方；多人协作时，代码风格也会越来越散。

### 3. 怎么平衡：用“变化频率”决定抽象程度

老赵建议看两个维度：

- **使用频率高不高**：越常用，越值得抽；
- **变化频率高不高**：变化太快的部分，不要过度固化。

高频、稳定的能力适合抽象；低频、变化大的业务逻辑，留在页面里。  
记住一句话：**稳定的交给组件，变化大的留给页面。**

### 可复用的组件案例：弹窗中的“固定骨架 + 变化内容”

比如：

- 骨架固定：标题栏、底部按钮、关闭逻辑；
- 变化内容：表单、说明文字、详情信息。

这样既避免重复写弹窗壳子，又不会把所有业务逻辑塞进一个万能弹窗。页面只关心“放什么内容、确认后做什么”，组件只负责“怎么把弹窗撑起来”。

### 老赵常见踩坑提醒

**别让一个组件变成“巨无霸配置中心”。** 配置项越多，不代表越高级，很多时候只是说明这个组件已经失去边界了。

---

## 五、组件复用中的命名、结构和 API 稳定性

### 1. 命名要让人一眼知道它干什么

好的命名是降低理解成本，不是炫技。比如：

- `BaseModal`：基础弹窗骨架；
- `ConfirmModal`：确认类弹窗；
- `FormDialog`：带表单的弹窗；
- `PaginationBar`：分页条。

命名最好同时体现两件事：**它是什么、它解决什么场景**。别起那种作者知道、别人猜半天的名字。

### 2. 结构要稳定，别今天一版明天一版

组件进入复用阶段后，结构就不能太飘。建议保持这几个区域稳定：

- 顶部：标题、关闭；
- 中间：内容；
- 底部：操作按钮。

结构稳定，外部使用者心里有数，后面扩展功能也不容易把页面改得面目全非。

### 3. API 稳定性比“功能多”更重要

API 稳定，意味着：

- `props` 命名清楚；
- `emit` 事件语义明确；
- `slot` 职责边界清楚；
- 默认行为符合直觉。

尤其要注意**受控/非受控思路**：像弹窗、开关、分页这类组件，通常更适合受控模式，也就是由父组件掌控状态。这样组件只做展示和事件输出，职责更干净。

### 4. 简单文档也要写，而且要有统一模板

可复用组件最怕“只有作者会用”。所以文档别散着写，最好统一成一个小模板：

- **组件用途**：这个组件是干什么的；
- **适用场景**：在哪些页面会用到；
- **Props**：支持哪些参数，默认值是什么；
- **Events**：会抛出哪些事件；
- **Slots**：哪些区域可以自定义；
- **示例代码**：给一个最常见的用法；
- **注意事项**：哪些地方不要乱传值、乱改状态。

哪怕只有几十行，也比“看源码猜”强太多。你连文档都写不出来，通常说明组件边界也还没想明白。

### 可复用的组件案例：`BaseModal` 的简单文档写法

可以这样写：

- **用途**：提供统一的弹窗骨架；
- **props**：`modelValue`、`title`、`width`、`showFooter`；
- **events**：`update:modelValue`、`confirm`、`cancel`；
- **slots**：默认内容区、`footer` 插槽；
- **适用场景**：确认、编辑、说明类弹窗。

文档不需要花哨，但一定要清楚。清楚了，别人就能接着用。

### 老赵常见踩坑提醒

**组件复用最怕 API 朝令夕改。** 你自己改得爽，使用方会很痛苦。稳定的 API，才是组件能活下去的前提。

---

## 六、回收前文：表单、弹窗、列表、分页的共性抽象点

前面几章其实已经埋了很多抽象线索，这里我们顺手收一下。

### 1. 表单组件的抽象点

表单最容易抽的是：

- 字段布局；
- 校验规则；
- 提交行为；
- 重置行为；
- 错误提示展示。

但表单最容易抽过头的地方也在这：**业务字段变化太快。**  
所以表单组件适合抽“通用壳子”和“校验流程”，字段配置则要保留一定灵活度。

### 2. 列表和分页的抽象点

列表和分页常常一起出现，它们的共性是：

- 查询条件；
- 表格展示；
- 空态处理；
- 分页切换；
- 加载状态。

这里很适合抽出一个列表基座，再把具体列配置、操作按钮、请求逻辑留在页面层。分页也一样，分页条只管翻页，不要顺手把接口请求、筛选条件、排序逻辑全揽进来。

### 3. 这几类组件的共同原则

不管是表单、弹窗、列表还是分页，抽象时都要记住三件事：

- **边界清楚**：组件管什么，不管什么；
- **状态清楚**：受控还是非受控，先定好；
- **出口清楚**：通过 `props`、`emit`、`slot` 把变化留出去。

这就是你以后做高复用业务组件时最实用的底层逻辑。

### 可复用的组件案例：列表 + 分页的基础组合

你可以把列表和分页拆成两个组件：

- `BaseTable`：负责展示数据和基础操作；
- `PaginationBar`：负责翻页、页大小切换、页码展示。

页面层负责请求和条件筛选。这样一来，列表、分页、查询这几个部分都不会互相黏死，后面换接口、换字段也更稳。

### 老赵常见踩坑提醒

**别把请求逻辑、展示逻辑、交互逻辑全绑死在一个组件里。** 一绑死，复用就没了，维护也会越来越难。

---

## 七、组件复用的终点，不是“抽出来”，而是“持续演进”

很多人以为抽象完就结束了，其实不是。组件真正难的是后面三件事：

1. **有人持续在用**；
2. **有人愿意补文档**；
3. **有人敢于在不破坏老用法的前提下升级它**。

所以复用不是一次性动作，而是一个持续演进的过程。你今天抽出 `BaseModal`，明天可能会发现需要支持键盘关闭、加载态、异步确认、插槽扩展；这都正常。关键是别把组件改成“想起什么加什么”，而是每次升级都先想清楚：**这次加的是骨架能力，还是业务特例。**

### 可复用的组件案例：版本演进时的接口保护

比如 `BaseModal` 新增一个 `loading` 属性，你最好保持原有 `modelValue`、`title`、`confirm`、`cancel` 的行为不变。能加不改，尽量别改；必须改，也要给使用方足够的迁移空间。

### 老赵常见踩坑提醒

**别把升级做成重写。** 真正成熟的组件，都是在保持老 API 尽量稳定的前提下一点点长出来的。

---

## 结尾小结：抽象的本质，是让组件更像工具，不像作品

这章讲的是从“写一个组件”走向“建立一套组件方法论”。核心思路其实很朴素：

- **先判断值不值得抽象**；
- **再找稳定能力和变化点**；
- **用 `props`、`emit`、`slot` 组织边界**；
- **控制抽象粒度，别过度也别不足**；
- **保持命名、结构、API 的稳定性**；
- **最后补上简单文档，让别人能接着用**。

你可以把它记成一句老赵式总结：

> **组件复用不是把功能堆一起，而是把“该稳定的稳定下来，把该变化的留出去”。**

如果你接下来要做自己的业务组件库，建议先从一个 `BaseModal`、一个表单基座、一个分页条开始练手。先让一个组件真正被多个页面用起来，再谈抽象第二个、第三个。因为复用这件事，靠的不是想象力，靠的是一次次真实使用后的修正。

### 行动建议

- 先挑一个项目里重复最多的组件，画出它的稳定部分和变化部分；
- 给它补一份最简文档，至少说明用途、`props`、`events`、`slots`；
- 观察三次真实使用，再决定要不要继续抽象；
- 每次扩展功能前，先问自己一句：这是在增强组件，还是在污染边界。

### 老赵常见踩坑提醒

**复用不是复制粘贴，也不是硬凑一个万能父组件。** 真正靠谱的复用，是基于清晰边界、稳定 API 和真实业务反馈不断演进出来的。

# 第13章 组件库初步思路：把经验沉淀成可交付资产

## 开篇引入：为什么你迟早要碰组件库

前面我们讲的是单个组件怎么做：按钮怎么封装、弹窗怎么抽、表单怎么控、列表怎么复用。做到这一步，你已经不是只会写组件了，而是在具备“沉淀组件资产”的能力。

组件库说白了，就是把一批稳定、可复用、可维护的组件，按统一规范组织起来，让团队里的人拿来就能用、用起来不别扭、后面改起来也不心虚。

老赵先给你一句实在话：**组件库不是从零造轮子，而是把你已经验证过的轮子收进仓库，顺手把说明书也写好。**

---

## 一、组件库的最小可行形态：目录、规范、版本意识

很多人一提组件库，就想着按需加载、主题系统、国际化。先别急，先把最小可行形态做出来。

### 1）目录要清楚

一个初步的组件库，至少要结构明确：

```bash
src/
  components/
    BaseButton/
    BaseModal/
    BaseForm/
  styles/
  utils/
  docs/
  index.ts
```

这样做的核心是：**组件边界清楚**。按钮就是按钮，弹窗就是弹窗，别把业务页面逻辑塞进去。一个组件一个目录，放组件文件、样式、文档和示例，后面接手的人一眼就知道从哪看。

### 2）规范要统一

统一的不只是命名，还有：

- props 命名
- 事件命名
- 插槽命名
- 样式前缀
- 默认值和受控/非受控思路

比如按钮统一叫 `BaseButton`，事件尽量统一风格，别今天一个 `change`，明天一个 `confirmClick`。规范统一的意义不在“看起来高级”，而在于后续扩展和维护不会乱。

### 3）版本要有意识

组件库一旦被多个地方引用，改动就不再是改一个文件，而是在影响一批调用方。所以要分清：这是修 bug、增能力，还是破坏旧用法。哪怕暂时不正式发包，也要先建立版本意识。

### 可复用的组件案例

把基础按钮整理成 `BaseButton`：

- `type`
- `disabled`
- `loading`
- 默认插槽放按钮内容

它不关心你是“保存”“删除”还是“提交”，只负责动作入口，足够稳定，也容易复用。

### 老赵常见踩坑提醒

**别把目录当成组件库。**  
目录再漂亮，组件边界不清、规范不统一、升级没章法，还是没法真正交付。

---

## 二、组件库和业务组件是什么关系：怎么平衡通用与定制

这个问题很关键。很多人一上来就想把所有业务都抽成通用组件，老赵劝你别这么干。

### 1）业务组件不是敌人

业务组件是为当前场景服务的，比如“订单筛选表单”“用户信息弹窗”“商品列表卡片”。它们可能带一点通用能力，但核心还是业务。硬塞进通用库，最后往往变成“看着通用，实际上谁都不敢复用”。

### 2）通用组件只做稳定的公共能力

比如：

- 按钮负责交互和视觉态
- 弹窗负责展示、关闭、确认
- 表单负责收集、校验、提交触发

这类组件职责稳定，才值得进入组件库。

### 3）平衡通用和定制的判断标准

问自己三个问题：

- 这个能力是不是会在多个页面重复出现？
- 这个 API 能不能稳定？
- 这个抽象会不会把业务细节抹平得太狠？

如果答案都比较正面，再沉淀到组件库；否则先放在业务层更稳。

### 可复用的组件案例

`BaseModal` 可以提供：

- `visible`
- `title`
- `confirmText`
- `cancelText`
- `footer` 插槽

而“订单审核弹窗”这种就放业务层，基于 `BaseModal` 组合，不要硬塞进通用组件里。

### 老赵常见踩坑提醒

**别为了“通用”把组件做成四不像。**  
API 太大、功能太杂，最后谁都不敢用，组件库反而成了负担。

---

## 三、组件文档怎么写才够用：示例、参数、事件、插槽

组件库能不能用起来，文档很重要。老赵的原则是：不用写成百科全书，但一定要让人“看完就会用”。

### 1）文档最少要包含什么

一个够用的组件文档，至少包括：

- 功能说明：解决什么问题
- 基础示例：最简单怎么用
- 参数说明：props 有哪些，默认值是什么
- 事件说明：触发什么事件，参数是什么
- 插槽说明：哪里可以自定义内容
- 受控方式：这个组件是外部控制，还是内部自管

### 2）示例优先于理论

先给代码，再讲参数：

```vue
<BaseButton type="primary" :loading="saving" @click="handleSave">
  保存
</BaseButton>
```

组件库用户通常不是来学原理的，是来解决问题的。先看用法，再看说明，效率最高。

### 3）写文档时别漏掉“边界说明”

比如弹窗到底是受控还是非受控，表单提交后是否自动重置，按钮点击是否只负责抛事件，这些都要写清楚。否则调用方一改状态，组件表现和预期不一致，最后就会开始互相甩锅。

### 一个统一的简单文档模板

你可以给每个组件都套这个模板：

```md
## 组件名
### 用途
这个组件解决什么问题。

### 基础用法
贴一段最小示例。

### Props
- `name`：说明，默认值，是否必填

### Events
- `change`：触发时机，参数说明

### Slots
- `default`：放什么内容
- `footer`：适用场景

### 受控方式
由外部控制什么状态，内部维护什么状态。

### 注意事项
写清楚常见限制、边界和坑。
```

### 可复用的组件案例

给 `BaseForm` 写一页简单文档：

- 基础示例：如何传 `model`、`rules`
- 参数：`labelWidth`、`inline`、`disabled`
- 事件：`submit`、`reset`
- 插槽：`footer`、`extra`
- 受控方式：表单值通常由外部传入，提交由组件抛事件

够用了，别把文档写成开发者自嗨笔记。

### 老赵常见踩坑提醒

**别把文档写成“我自己能看懂就行”。**  
用户最关心的是：怎么用、能传啥、会触发啥、哪里能改。

---

## 四、组件发布与维护：先能交付，再谈优雅

组件库不是写完就结束，后面还有维护。

### 1）发布前先做基本检查

至少确认：

- 默认样式不会乱跑
- 组件命名统一
- props 默认值合理
- 受控/非受控行为清楚
- 插槽没传内容时也能正常展示

这里尤其要注意受控/非受控思路。比如弹窗是外部 `visible` 控制，还是组件内部自己管理状态，最好在设计阶段说清楚，不然调用方很容易出现“我改了值，为什么没反应”。

### 2）维护时要有变更意识

一个组件改动，至少要判断：

- 是内部优化，外部无感
- 是新增能力，旧用法不受影响
- 还是要改 API，需要通知使用方

组件库最怕“我就改了一点点”，但这“一点点”碰到公共接口，可能就会影响很多页面。

### 3）先把版本和目录稳定下来

哪怕你现在还没正式发布，也建议先约定：

- 哪些组件属于基础库
- 哪些组件只是业务模板
- 哪些改动需要回归验证
- 哪些改动要同步更新文档

这一步看起来朴素，但它决定了组件库是不是能长期维护。

### 可复用的组件案例

把 `BaseButton`、`BaseModal`、`BaseForm` 统一导出：

```ts
export { default as BaseButton } from './components/BaseButton'
export { default as BaseModal } from './components/BaseModal'
export { default as BaseForm } from './components/BaseForm'
```

先把“能导出、能安装、能使用”做扎实，再谈更复杂的工程化能力。

### 老赵常见踩坑提醒

**别一边改组件，一边顺手改业务页面验证效果。**  
组件库改动要有明确验证路径，不然你根本不知道问题出在组件里，还是调用方里。

---

## 五、实战案例：把按钮、弹窗、表单整理成一个小型组件集合

这一节把前面的能力串起来。

### 1）按钮：只负责动作入口

`BaseButton` 只管：

- 展示
- 状态
- 点击事件
- `loading` / `disabled`

它不关心你点完后是保存、删除还是提交审批。按钮最重要的是稳定，不要把额外逻辑塞进去。

### 2）弹窗：只负责承载交互

`BaseModal` 负责：

- 显示隐藏
- 标题
- 内容区
- 确认/取消
- 底部插槽

业务内容放进默认插槽，弹窗本身保持稳定。这样你可以塞入不同表单、说明或确认文案，复用性就出来了。

### 3）表单：只负责收集和触发

`BaseForm` 负责：

- 表单布局
- 统一字段样式
- 提交与重置
- 校验触发

真正的业务字段配置由调用方决定，这样表单不会被某个页面绑死。

这三个组件放在一起，就是一个典型的小型组件集合。它不大，但足够说明一个道理：**高复用业务组件，不是堆功能，而是把职责切清楚。**

### 可复用的组件案例

“新增用户”场景可以这样组合：

- 按钮打开弹窗
- 弹窗里放表单
- 表单提交后关闭弹窗

单个组件不复杂，组合起来却能解决一类业务问题，这才是组件库真正的价值。

### 老赵常见踩坑提醒

**别把业务联动硬写进基础组件。**  
比如“弹窗里必须有表单”“按钮点击后必须发请求”，这些都不是基础组件该背的锅。

---

## 结尾小结：先沉淀能落地的，再追求更大的平台化

今天这章就一句话：**组件库不是宏大的工程计划，而是把稳定、可复用的组件和规范，整理成能交付的资产。**

你可以先做这几件事：

1. 选出真正稳定的基础组件
2. 给它们统一目录和命名
3. 写清楚示例、参数、事件、插槽
4. 明确受控/非受控边界
5. 保持版本和变更意识
6. 给每个组件配一份简单文档模板

这里再补一句更现实的话：**先做能落地的小集合，再谈组件库演进。**  
别一开始就想着通用平台、设计系统、主题切换、低代码联动。那些都可以往后放。你先把按钮、弹窗、表单这些真正能复用的东西稳稳做出来，把文档写明白，把边界划清楚，组件库就已经有雏形了。

赵老师最后送你一句：**先把能落地的部分做稳，再慢慢往组件库走。**  
别急着造大轮子，先把手里的小轮子打磨顺了，车才跑得起来。
