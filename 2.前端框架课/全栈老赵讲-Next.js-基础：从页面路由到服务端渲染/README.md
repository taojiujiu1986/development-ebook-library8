# 第1章：先别急着上框架，Next.js 到底为什么这么火

如果你已经会 React，那大概率也遇到过这些问题：组件能拆、状态能管、页面也能写，但项目一大，路由怎么组织、首屏怎么更快、SEO 怎么处理、接口要不要单独起后端，都会开始变麻烦。

这时候，很多人会听到一个名字：**Next.js**。

它火，不是因为“新”，而是因为它正好补上了 React 项目落地时最常见的那些坑。先别急着学代码，这一章先把“为什么要用它”讲明白。你只有知道它解决什么问题，后面学路由、布局、数据获取、SSR、SSG 才不会学成零散知识。

---

## 一、React 做前端时，最常见的几个痛点是什么？

### 1. 路由要自己搭，页面组织容易乱

React 本身更像 UI 库，负责把界面搭起来，但**页面怎么分、URL 怎么管、怎么跳转**，它并没有默认方案。你当然可以接 React Router，再自己定目录结构，但项目一大，很容易变成：

- 页面和组件混在一起
- 路由配置越写越长
- 目录命名各写各的
- 多人协作风格不统一

不是不能做，而是要自己从零建立规则。小项目看不出问题，页面一多、需求一改，维护成本就会上来。

### 2. SEO 和首屏性能，经常让人头疼

如果你做的是后台系统，SEO 可能没那么重要；但如果你做的是官网、博客、内容站、电商详情页、营销落地页，那搜索引擎能不能抓到内容、首屏快不快，就很关键了。纯前端渲染通常要等 JS 下载和执行后内容才出来，用户体验还行，但**搜索引擎和首屏速度**可能吃亏。

### 3. 前后端边界太硬，效率未必高

很多项目最后会变成：

- 前端单独一个项目
- 后端再一个项目
- 接口文档来回对
- 本地开发要联调
- 部署也分两套

这套方式当然可以，但对于官网、内容站、小型电商这类项目，复杂度可能偏高。你本来只是想把页面和少量接口做好，结果工程先重了。

### 4. 工程组织问题，迟早会找上门

当页面、组件、接口、静态资源全堆在一起时，常见结果就是：

- 找文件像翻仓库
- 新人接手成本高
- 复用逻辑散落各处
- 业务一改，很多地方都得跟着动

真正难的往往不是“能不能写页面”，而是“能不能长期、稳定、协作地写下去”。

## 二、Next.js 的核心定位：它不是替代 React，而是 React 之上的全栈框架

先记住一句最重要的话：

> **Next.js 不是另起炉灶，它是建立在 React 之上的框架。**

你不是学了 Next.js 就把 React 扔了，而是把 React 放进一个更完整的开发体系里。

### Next.js 主要补了什么？

#### 1. 约定式路由
不需要把路由一条条手写出来，它通过目录结构帮你约定页面怎么生成、怎么访问。

#### 2. 多种渲染模式
它提供 SSR、SSG、CSR 等方式，让你按场景选择。

#### 3. 接口能力
你可以在项目里直接写一些轻量接口逻辑，让前后端结合更紧凑。

所以，Next.js 的定位不是“更高级的 React 写法”，而是**面向真实业务的 React 应用框架**。它特别适合那些既要做页面，又要考虑性能、SEO、接口协作和工程组织的项目。

---

## 三、Next.js 为什么特别适合内容型站点、官网、博客、电商？

### 1. 内容型站点最在意什么？

内容型站点通常不太追求复杂交互，而更在意：

- 页面能不能被搜索引擎更好地收录
- 首屏能不能快一点
- 页面结构能不能稳定
- 内容更新后能不能方便发布

这类站点包括技术博客、公司官网、产品介绍页、文档站、新闻资讯站。Next.js 的优势在于它能更灵活地选择渲染方式：文章详情页可以预先生成，列表页按需更新，用户登录后的个人区域再用客户端交互，组合起来很顺。

### 2. 官网和营销页，拼的就是“快”和“稳”

官网、活动页、落地页，目标通常就是：

- 打开快
- 内容清楚
- 搜索可见
- 结构稳定

这类页面不需要太重的状态管理，但对**首屏和 SEO**很敏感。Next.js 很合适，因为它能把“页面性能”和“内容可见性”放在更高优先级。

### 3. 电商站点为什么也常用它？

电商网站通常是混合体：

- 商品列表要快
- 商品详情页要能被搜索到
- 购物车、收藏、登录要有强交互
- 后台管理和前台展示要求不同

这意味着它不适合只靠单一渲染模式硬撑。Next.js 的价值就在于：**你可以按页面类型选择方案**。首页和类目页重曝光，详情页重 SEO，购物车和个人中心重交互，同一个项目里不同页面需求完全不同，Next.js 正适合这种混合场景。

## 四、Next.js 带来的开发收益，到底体现在哪？

### 1. 约定式路由，少写配置，页面组织更清晰

你看到一个页面文件，基本就能知道它对应什么 URL。好处很直接：

- 新人更容易上手
- 页面和路由关系直观
- 目录结构本身就是文档
- 不用把所有路由堆在一个配置文件里

这对中大型项目很友好，因为**页面组织清晰了，协作成本就低了**。

### 2. 渲染能力更灵活，不必死守一种模式

React 项目里，很多团队容易把所有页面都按一种思路做，但现实是：

- 首页希望快，适合预渲染
- 详情页要兼顾 SEO，适合服务器端生成
- 交互强的面板，客户端渲染更顺手

Next.js 让你按场景选，而不是逼你统一模板。**渲染模式不是教条，而是工具箱**。

### 3. 接口能力更近，前后端结合更自然

不是每个功能都值得单独起一套完整后端服务。像表单提交、简单数据聚合、页面轻接口、外部服务中转这类逻辑，用 Next.js 里更贴近页面的接口方式会很顺手。它不是取代后端，而是把前后端协作距离缩短一点。

### 4. SEO 和内容呈现更容易做对

做内容型站点时，很多 SEO 基础能力不能忽视：

- 页面标题是否独立
- 描述信息是否可控
- 内容是否能直接输出给搜索引擎
- 页面链接结构是否清晰

Next.js 的价值不是“自动 SEO”，而是**更容易写出搜索引擎能看懂的页面**。

## 五、渲染模式怎么理解：别把 SSR、SSG、CSR 当成背口诀

虽然后面会专门讲，但这里先打个底，因为它直接关系到“为什么 Next.js 火”。

### 1. SSR：每次请求时现做
SSR 的意思是页面在服务器上先渲染好，再发给浏览器。好处是首屏和内容可见性通常不错，适合内容经常变化、又比较看重 SEO 的页面。

### 2. SSG：提前做好，发出去就能用
SSG 是在构建阶段就把页面生成好。好处是快、稳、成本低，特别适合博客文章、文档页、产品介绍页这种变化不那么频繁的内容。

### 3. CSR：浏览器自己跑起来再渲染
CSR 就是 React 里最熟的那套，交互灵活，适合后台系统、复杂表单、强交互页面。

Next.js 受欢迎，一个很重要的原因就是：**它不是逼你只选一种，而是让你按页面类型来选。**

## 六、什么时候该用 Next.js，什么时候别乱上？

### 适合用 Next.js 的场景

如果你符合下面几条，Next.js 通常值得考虑：

- 你做的是官网、博客、内容站、文档站
- 你很在意 SEO
- 你希望首屏更快
- 你的页面既有展示，又有一定交互
- 你想把前后端协作做得紧凑一些
- 你希望项目目录和路由组织更规整

简单说：**页面驱动型、内容驱动型、需要兼顾展示和性能的项目**，Next.js 很合适。

### 别乱上的场景

但如果你遇到的是下面这些情况，就别盲目跟风：

- 纯后台管理系统，SEO 不重要
- 业务特别简单，页面就那么几页
- 你已经有一套成熟前端架构，团队配合很好
- 你的后端和前端必须严格分离，且已有稳定部署链路
- 团队对 React 还没熟，基础工程规范都没建立好

这时候硬上 Next.js，不一定更快，反而可能把复杂度提前引进来。框架的价值是解决问题，不是让项目看起来更高级。

### 老赵给你的判断标准

可以用这三个问题快速判断：

1. **这个项目是不是内容或页面展示占主导？**  
   是，Next.js 更有价值。

2. **这个项目是否对 SEO 和首屏有要求？**  
   是，Next.js 很合适。

3. **这个项目是否需要前后端结合，但又不想把工程切得太碎？**  
   是，Next.js 值得考虑。

如果三个答案里有两个以上是“是”，就可以认真看 Next.js 了；如果全都不是，那别为了“流行”而流行。

## 七、一个很现实的案例：博客站为什么常常是 Next.js 的练兵场？

一个博客站通常有这些页面：

- 首页：文章列表
- 分类页：按标签或专题聚合
- 文章详情页：核心内容展示
- 关于页：静态内容
- 站内搜索：少量交互
- 管理或发布接口：轻量数据处理

这类站点有三个特点：

### 1. 内容比交互更重要
文章内容本身就是核心资产，所以页面要尽量让内容可见、结构清楚。

### 2. SEO 很重要
文章如果能被搜索到，就会带来持续流量，这类页面特别适合更友好的渲染策略。

### 3. 页面类型非常清晰
首页、详情页、标签页、关于页，天然适合按目录来组织，这也是 Next.js 约定式路由舒服的地方。

所以博客站经常被拿来做 Next.js 入门项目，不是因为它简单，而是因为它**把 Next.js 的优势展示得很完整**：路由、渲染、接口、静态资源、SEO，都能串起来，而且足够贴近真实业务。

## 八、老赵式总结：别为了“火”去上框架，要为了“合适”去选框架

这一章你只需要记住一句话：

> **Next.js 的核心价值，不是把 React 换掉，而是让 React 更适合做真实业务里的页面型项目。**

它之所以火，是因为它正好解决了 React 落地时最常见的几个麻烦：

- 路由怎么组织
- 页面怎么生成
- 首屏怎么更快
- SEO 怎么更好
- 前后端怎么更顺手地结合

但老赵也要提醒你：**别看到大家都在用，就觉得自己也必须上。**

### 什么时候该用 Next.js？
- 内容型站点
- 官网
- 博客
- 电商详情页
- 需要 SEO、首屏和页面组织的项目

### 什么时候别乱上？
- 纯后台系统
- 小而简单的前端项目
- 团队还没建立好 React 基础工程规范
- 现有架构已经很稳，不需要为了技术栈而折腾

换句话说，**Next.js 不是万能药，但它在“页面多、内容多、还想兼顾性能和 SEO”的场景里，确实很顺手。**  
下一章开始，我们就不再停留在“为什么”，而是直接上手：**创建一个 Next.js 项目，先把目录结构和页面路由跑起来**。

# 第2章：页面路由怎么来的，Next.js 为什么不用你手动配太多

## 开篇引入：为什么老赵总说“先把路由搞顺，后面就顺了”

如果你已经会 React，组件拆分、状态管理、数据传递这些基本都不陌生。但一到真实项目，很多人还是会卡在几个很实际的问题上：

- 首页放哪？
- 列表页怎么进详情页？
- 详情页的 `id` 从哪来？
- 为什么还得自己配一堆路由？

Next.js 受欢迎，很大一部分原因就在这：**它把页面路由尽量变成了文件和目录的事情**。你不用先写一张大路由表，再一个个挂页面；很多时候，只要把文件放对位置，路由就自然出来了。

老赵最怕的，不是功能多，而是页面系统被路由配置绕晕。Next.js 的页面路由，本质上就是减少重复劳动。尤其是博客、文档站、营销页、内容站、后台这类结构清楚的项目，这种“文件即路由”的方式特别省心。

当然，它不是魔法，只是把常见页面组织方式变成了默认规范。你先把这套东西弄明白，后面学布局、数据获取、SSR/SSG/CSR，都会顺很多。

### 老赵式总结

路由不是越复杂越高级，**能把页面结构清楚地表达出来才是本事**。Next.js 的文件路由适合页面型项目，它帮你少写很多重复配置。  
**什么时候该用 Next.js？** 页面多、层级清晰、要 SEO 的场景。  
**什么时候别乱上？** 只是一个很轻的内部工具页，页面跳转很少，直接 React 也许更轻。

## 一、页面路由的基本概念和文件映射规则

### 1. 什么叫“文件即路由”

在 Next.js 里，页面通常对应一个文件。把页面文件放进约定目录后，框架会自动把它映射成 URL。

最直白的例子是：

- `pages/index.tsx` → `/`
- `pages/about.tsx` → `/about`
- `pages/posts/list.tsx` → `/posts/list`

你可以直接把它理解成：**目录结构就是网站地址结构**。这和很多传统 SPA 里“先写路由配置，再写页面组件”相比，更直接。

好处不只是少写几行配置，更重要的是，页面结构一眼能看出来。打开目录，你基本就知道这个站点长什么样。对团队协作来说，这种可读性很值钱。

### 2. 为什么这种方式适合页面项目

页面项目有个典型特点：结构比业务逻辑更稳定。  
比如一个内容站，通常就是：

- 首页
- 分类页
- 列表页
- 详情页
- 关于页
- 联系页

这种结构天然适合文件路由。页面多了之后，你更能体会到它的省心：不用手工注册，不用到处找配置。

老赵以前见过不少项目，页面不多，但路由写得像迷宫。Next.js 的文件路由，就是把这种“人肉配路由”的成本降下来。

### 3. 初学时最该记住的判断标准

先记一句：

> **页面越像固定层级结构，Next.js 越省心。**

如果你的应用是：

- 内容展示为主
- 页面跳转清晰
- SEO 有要求
- 页面数量中等偏多

那文件路由会很舒服。

但如果你的应用是：

- 单页交互极强
- 页面结构几乎不变
- 所有状态都围绕一个大画布变化

那你未必需要特别重的页面路由体系，盲目上 Next.js 也不一定划算。

### 老赵式总结

页面路由的关键，不是“配置得多”，而是“结构清楚”。  
**Next.js 适合什么？** 页面多、层级清晰、要 SEO 的项目。  
**别乱上什么？** 很简单的内部工具页，跳转极少，没必要硬上完整页面体系。

## 二、如何创建首页、列表页、详情页等基础页面

### 1. 首页怎么做

首页通常是站点入口，最常见的做法就是在根目录放一个页面文件，让它成为首页。

首页一般承担三件事：

1. 站点门面
2. 导航中心
3. 重要内容入口

首页别把所有信息都塞进去，尤其是内容型站点。它更像“目录 + 推荐位”，负责把用户导向合适内容。比如文章站可以放：

- 最新文章
- 热门分类
- 推荐专题
- 网站简介

### 2. 列表页怎么组织

列表页负责聚合内容，比如：

- 文章列表
- 产品列表
- 新闻列表
- 分类列表

它的核心任务不是讲细节，而是把内容分组、排序、筛选、分页做清楚。一个实用结构通常是：

- 顶部：分类/筛选条件
- 中部：列表内容
- 底部：分页

这样后面做数据请求和 URL 参数时会很顺。

例如文章列表页可以支持：

- `/posts`
- `/posts?category=frontend`
- `/posts?page=2`

这种地址结构就很像一个真正的网站。

### 3. 详情页怎么设计

详情页最容易和路由参数结合。比如：

- `/posts/1001`
- `/posts/1002`
- `/products/abc123`

这些页面本质上是同一个模板，只是数据不同。Next.js 的动态路由就是专门解决这个问题的。

详情页最关键的不是“怎么把标题显示出来”，而是“怎么根据 URL 找到正确的数据”。也就是说，路由不仅负责跳转，还承担了**页面与数据的对应关系**。

### 4. 页面创建的实际步骤

你可以按这个顺序来：

1. 先想清楚站点有哪些固定页面
2. 再按 URL 结构设计目录
3. 给每个页面写最小可用内容
4. 最后把导航串起来

老赵建议第一版别追求花哨，先把：

- 首页
- 列表页
- 详情页
- 关于页

这几个基础页面跑通，页面骨架就立住了。

### 老赵式总结

页面创建别一上来就想“高大上”。**先把首页、列表页、详情页这三类页面的职责分清楚**，项目就稳了。  
**Next.js 适合什么？** 典型站点骨架，尤其是内容站。  
**别乱上什么？** 别为了几个页面就堆一套复杂状态管理和手工路由配置，真没必要。

---

## 三、Link 组件与页面跳转方式：别再用“硬跳转思维”了

### 1. 为什么不建议随便用普通 `<a>`

在 Next.js 里，站内页面跳转通常推荐用 `Link` 组件。原因很简单：它更符合框架的导航机制，能更好支持预取和客户端跳转。

普通链接不是不能用，但对于站内页面切换，`Link` 往往更顺手。尤其是列表页跳详情页这种高频跳转，体验会更好。

### 2. Link 的核心价值

你可以把 `Link` 理解成“Next.js 认可的站内导航方式”。它的价值主要有三个：

- 跳转体验更流畅
- 更适合站内页面切换
- 和路由系统配合更自然

对于内容型站点，用户的浏览路径往往是：首页 → 列表 → 详情 → 相关文章，这种路径天然适合用 `Link` 串起来。

### 3. 一个常见的导航结构

内容型站点通常会有这样的导航：

- 首页
- 文章列表
- 分类页
- 关于页

建议你做到两点：

1. 导航数据集中维护
2. 页面路径命名保持统一

这样以后改链接，不会满项目找。

比如文章列表统一放在 `/posts`，详情页统一放在 `/posts/[id]`，那么导航、面包屑、相关推荐都能围绕这个规律设计，站点会非常整齐。

### 4. 常见误区

很多人刚上手会犯两个错误：

- 站内跳转全写普通标签，不考虑框架能力
- 页面路径命名很随意，今天叫 `detail`，明天叫 `articlePage`

还有一个常见问题：页面里到处硬编码 URL。今天写死 `/posts/1`，明天又写死 `/posts/2`，后面改路由结构时就得全手改。更稳妥的方式，是把路径生成逻辑集中处理。

### 老赵式总结

`Link` 不是装饰，它是你和 Next.js 路由系统协作的入口。  
**该用 Next.js 吗？** 只要你的项目有稳定的站内跳转，它就挺合适。  
**别乱上吗？** 如果页面之间几乎没有跳转，或者只是极少量页面，没必要为了“框架感”而框架化。

---

## 四、路由参数的基础使用：详情页为什么能“一页管一类内容”

### 1. 什么是路由参数

路由参数，就是 URL 里带着可变信息。  
比如文章详情页需要知道当前是哪篇文章：

- `/posts/1001`
- `/posts/1002`

这个 `1001`、`1002` 就是参数的一种典型形式。

如果你做过 React 组件传参，会发现它们本质很像：都是把“当前应该展示什么”传进去，只不过路由参数是通过 URL 表达的。

### 2. 动态路由的核心思路

动态路由不是给每个页面都新建文件，而是用一个模板接住一类路径。  
这特别适合：

- 文章详情
- 商品详情
- 用户主页
- 分类列表

因为这些页面通常结构类似，只是数据不同。

你可以把它理解成：**页面模板只有一个，页面内容根据参数变化**。这样做的好处很明显：

- 文件数量不会爆炸
- 逻辑复用更容易
- URL 结构更统一

### 3. 参数从哪来，怎么用

参数通常来自两处：

- URL 本身
- 页面跳转时传入的路径信息

实际开发里，你一般会这样处理：

1. 拿到路径参数
2. 根据参数请求数据
3. 再把数据渲染出来

比如用户从文章列表点进来，你拿到文章 `id` 后，就去请求标题、正文、作者、发布时间，再渲染到详情页里。页面结构不变，换的是数据。

### 4. 传参时要注意什么

有三个老问题要提前考虑：

- 参数不存在怎么办？
- 参数非法怎么办？
- 参数对应的数据为空怎么办？

内容站最常见的问题之一，就是用户点进去一个链接，结果文章已删除或 ID 不存在。这时你要考虑：

- 提示页面不存在
- 跳回列表页
- 给出推荐内容

别小看这一步，项目上线后这类问题很常见。

### 老赵式总结

路由参数的本质就是：**一个页面模板，服务一类数据**。  
**Next.js 适合吗？** 特别适合详情页、分类页这种 URL 规律明显的页面。  
**别乱上吗？** 如果页面没有参数变化，硬搞动态路由只会让结构变复杂。

---

## 五、页面组织方式与目录命名习惯：项目乱不乱，八成看这里

### 1. 目录不是摆设，是项目骨架

很多人写项目，代码能跑，但过两周自己都找不到文件了。  
Next.js 的好处之一，就是它天然鼓励你把页面结构和目录结构对应起来。只要命名和分层有意识，项目会清楚很多。

页面组织得好，后面扩展时会省很多事。比如要加一个专题页，如果原来的目录本来就是按内容类型分层的，加入进去很自然；如果原来乱成一团，就只能边改边拆。

### 2. 老赵建议的组织原则

一个实用原则是：

- **页面归页面**
- **组件归组件**
- **数据归数据**
- **公共逻辑归公共逻辑**

不要把所有东西都堆进页面文件里。页面文件应该像“总控台”，负责拼装，不负责包办一切。

比如列表页里的分页器、筛选栏、文章卡片，都可以拆成组件。这样一来：

- 页面更清爽
- 组件更容易复用
- 调试更容易定位问题

### 3. 页面命名的建议

建议保持这些习惯：

- 页面文件名语义明确
- 目录层级不要过深
- 同类页面放在一起
- 公共组件统一放到共享目录

比如：

- `pages/posts/index.tsx` 表示文章列表
- `pages/posts/[id].tsx` 表示文章详情
- `components/Layout.tsx` 表示布局组件

这种命名方式一眼就懂，不容易踩坑。

### 4. 内容型站点特别适合这种组织方式

内容型站点最怕的不是功能少，而是内容一多，页面路径和组件复用开始失控。

Next.js 这种“页面结构清晰、目录即结构”的方式，特别适合文章站、教程站、案例站、帮助中心这类项目。它的价值不是“酷”，而是“稳”。

### 页面组织速记表

| 目标 | 建议做法 |
| --- | --- |
| 首页 | 放站点入口和导流内容 |
| 列表页 | 按内容类型或分类组织 |
| 详情页 | 用动态路由接住一类内容 |
| 公共区域 | 抽成可复用组件 |
| 导航 | 集中维护，保持命名统一 |

### 老赵式总结

目录命名不是形式主义，它决定你后面能不能轻松维护。  
**什么时候该用 Next.js？** 当你希望页面结构、导航结构、目录结构统一时，它很舒服。  
**什么时候别乱上？** 如果团队连命名规范都没准备好，先别急着上复杂框架，项目越大越容易乱。

## 六、从页面路由想到下一步：动态路由和数据获取怎么接上

本章你已经把“页面怎么映射成路由”这件事搞明白了。接下来真正要往前走一步的，就是动态路由和数据获取。

为什么要单独讲下一步？因为你会发现：

- 固定页面解决的是“站点骨架”
- 动态路由解决的是“同一模板承载不同内容”
- 数据获取解决的是“页面内容从哪来”

这三件事是连着的。  
比如文章详情页，先靠路由拿到 `id`，再根据 `id` 请求文章内容，最后把数据渲染出来。你只要把这个链路理顺，后面的 SSR、SSG、CSR 也就有了落脚点。

所以你现在不用急着把所有路由细节都背下来，先记住一个最核心的判断：

> **文件路由解决的是结构，动态路由解决的是变化。**

前者让项目清楚，后者让页面灵活。两者合在一起，才是 Next.js 路由系统最有价值的地方。

### 老赵式总结

路由讲到这儿，核心其实就一句：**先把页面骨架搭顺，再谈内容怎么变。**  
**Next.js 适合什么？** 页面结构清楚、内容按类型变化的项目，尤其是内容站和产品站。  
**别乱上什么？** 只有几个静态页、还没想清楚页面层级的项目，别急着把路由设计得太重。  
下一章我们就接着讲动态路由，看看它怎么把“一个页面模板”变成“能装一类内容”的实战能力。

# 第3章：动态路由、传参与页面组织，内容站点最常用的那一套

## 开篇引入：为什么内容站点一上来就绕不开动态路由

如果你做博客、资讯站、商品详情页、用户主页、知识库文章页，很快就会发现：  
**这些页面结构差不多，但内容不一样。**

比如：

- `/posts/1`
- `/posts/2`
- `/posts/3`

页面骨架基本一致，差别只在内容。要是每篇文章都单独写一个页面，项目还没做完，人先累了。

这就是 Next.js 动态路由最顺手的地方：**用一套页面模板，承载一批“结构相同、数据不同”的页面。**

对内容型站点来说，这几乎是刚需。因为它的特点不是“页面少”，而是“页面类型少、页面实例多”。Next.js 的路由系统，正是为这种场景准备的。

老赵先把话放这：**动态页面多、内容更新频繁、列表页要跳详情页、还想兼顾 SEO，这种场景下 Next.js 很顺手。**  
但如果你做的是纯后台管理系统，页面都是固定表单，或者只是几个一次性静态页，那就别把 Next.js 当万能钥匙。

## 一、动态路由的使用场景：文章、商品、用户详情页

### 1. 什么叫动态路由

静态路由是路径固定：

- `/about`
- `/contact`
- `/dashboard`

动态路由则是在路径里留一个变量位，比如：

- `/posts/[id]`
- `/products/[slug]`
- `/users/[username]`

这里的 `[id]`、`[slug]`、`[username]` 本质上就是占位符，意思是：这一段不是写死的，而是根据实际数据变化。

比如文章列表页里有一篇文章 ID 是 `42`，点进去就是 `/posts/42`；另一篇是 `99`，就变成 `/posts/99`。

### 2. 为什么内容站特别需要它

内容站常见页面模型很固定：

- 列表页：展示很多条内容
- 详情页：展示某一条内容
- 分类页：展示某一类内容
- 作者页：展示某一个作者的内容

它们的共性是：**URL 里通常都带标识符，页面内容要根据这个标识符取数据。**

不用动态路由，就会有两个麻烦：

1. 页面文件爆炸，维护成本高  
2. 页面和数据耦合乱，不利于扩展

### 3. 动态路由适合什么，不适合什么

**适合：**

- 文章详情页
- 商品详情页
- 用户主页
- 课程详情页
- 活动页、专题页

**不太适合硬上：**

- 固定页面极少的简单官网
- 完全依赖后台配置、前端只是壳子的小项目
- 页面很少、且未来不会增长的超轻量项目

老赵的判断很直接：**只要页面“结构重复、内容变化”，动态路由就值得用。**

#### 老赵式总结
动态路由不是炫技，它是内容型站点的基本功。  
**内容多、详情页多、列表到详情跳转多**，Next.js 会明显比手写一堆页面省心。  
但如果只是几个固定页面，别为了“听起来先进”乱上，复杂度会上来，收益未必够。

## 二、路径参数、查询参数与页面数据的关系

这一节老赵给你拆开讲，不混着来。很多人写着写着就把路径参数、查询参数和页面状态搅成一锅粥，后面排查问题特别费劲。

### 1. 路径参数是什么

路径参数通常是 URL 结构的一部分，比如：

- `/posts/42`
- `/users/tom`

这里的 `42`、`tom` 就是路径参数。它表达的是：**这个页面具体是谁。**

在内容站里，它通常用于定位资源本身。

### 2. 查询参数是什么

查询参数是 URL 后面 `?` 之后的部分，比如：

- `/posts?category=react`
- `/products?sort=price&page=2`

它更像筛选条件或附加状态。  
路径参数决定“你是谁”，查询参数决定“你想怎么查看我”。

### 3. 路径参数和页面数据的关系

可以简单记：

- **路径参数**：决定取哪条主数据
- **查询参数**：决定如何过滤、排序、分页、切换视图

比如：

- `/posts/42`：取 ID 为 42 的文章
- `/posts/42?preview=true`：可能是预览态
- `/posts?category=nextjs&page=2`：文章列表按分类和页码加载

这说明：**URL 不只是地址，它还是数据请求的输入。**

### 4. 一个常见误区

很多人把所有东西都塞进查询参数里，比如：

- `/posts?id=42`

这也能用，但在内容站里通常不如 `/posts/42` 直观。前者更像列表条件，后者更像资源定位。

老赵建议你这样记：

- **资源本身**放路径里
- **筛选和状态**放查询里

### 5. 什么时候必须用路径参数，什么时候查询参数就够了

如果页面内容本身就是“某一个具体对象”，比如文章详情、商品详情、用户主页，优先用路径参数。  
如果页面是在“同一类内容里切换视图”，比如筛选分类、搜索关键词、分页、排序，就更适合查询参数。

举个例子：

- `/posts/42`：这是文章 42 的详情页
- `/posts?tag=react&page=2`：这是文章列表的第二页，筛了 react 标签

两者一眼就能看出用途不同。这样做不仅用户看得懂，后面你做分享链接、返回列表、SEO 处理也更顺。

#### 老赵式总结
路径参数和查询参数不是谁高级谁低级，而是职责不同。  
**详情页用路径参数，筛选、排序、分页用查询参数**，这是内容站最顺的做法。  
URL 一乱，后面的数据获取和 SEO 也会跟着乱。

---

## 三、路由传参的几种常见方式：怎么把数据送到页面里

### 1. 通过路径直接传参

这是最常见的方式。列表页点进详情页，本质就是把内容 ID 或 slug 带到 URL 里。

比如文章卡片点击后跳到 `/posts/42`。

好处很明确：

- URL 清晰
- 可分享
- 可刷新
- 适合 SEO

### 2. 通过查询参数传参

适合列表页的筛选、分页、排序、搜索：

- `/posts?keyword=react`
- `/posts?page=3`
- `/posts?tag=frontend`

优点是状态表达清楚，而且不会污染路径结构。用户复制链接给别人，对方打开后也能看到同样的筛选状态。

### 3. 通过页面跳转时携带状态

有些场景会想在跳转时带一点临时状态，比如：

- 从某个分类页跳到详情页时保留来源分类
- 从列表页回退时恢复分页位置
- 从专题页进入详情页后，返回还能回到专题页

这类信息通常不适合做主业务数据，更适合做辅助状态。可以放查询参数里，也可以用别的状态方案处理，但原则是：

> **页面必须能靠 URL 自己站得住。**

否则刷新一下就失忆，体验会很差。

### 4. 传参的判断标准

问自己三个问题：

1. 这是不是页面定位所必需的信息？
2. 刷新后还要不要保留？
3. 复制链接给别人后，是否应该保留？

如果答案是“要”，它大概率就应该进 URL。  
如果只是临时 UI 状态，比如弹窗开关、输入框草稿，那就别硬塞进路由。

### 5. 路由传参和页面数据请求怎么配合

在 Next.js 里，路由参数通常不是单纯“拿来看的”，它会直接参与数据请求。  
比如详情页拿到 `id=42` 之后，再去请求：

- 文章正文
- 作者信息
- 相关文章
- 标签列表

列表页拿到 `page=2&tag=react` 之后，再去请求对应的数据集合。

也就是说，**路由参数不是路由参数本身，它还是接口参数的一部分。**  
这就是前后端结合的味道：URL 负责表达意图，数据层负责把内容填出来。

#### 老赵式总结
路由传参的核心就一句：**该进 URL 的进 URL，不该进 URL 的别硬塞。**  
内容站尤其如此，因为列表页、详情页、筛选页，本来就是靠 URL 组织起来的。  
Next.js 顺手的地方就在这：页面跳转、参数传递、数据加载能串成一条线。

## 四、列表页到详情页的完整页面流转：内容站最典型的链路

### 1. 先有列表，再进详情

内容型站点最经典的流程是：

1. 访问列表页
2. 获取文章、商品或用户列表
3. 用户点击某一项
4. 跳转到动态详情页
5. 根据路径参数请求详情数据
6. 渲染详情内容

这条链路不复杂，但它把很多基础能力串起来了：

- 路由设计
- 数据请求
- 参数传递
- 页面组织
- SEO 友好性

### 2. 一个文章站的简化思路

假设有两个页面：

- `/posts`：文章列表
- `/posts/[id]`：文章详情

列表页负责展示标题、摘要、发布时间；详情页负责展示正文、作者、标签、相关推荐。

你会发现：

- 列表页适合快速浏览
- 详情页适合完整阅读
- 路由结构天然反映内容层级

这就是 Next.js 做内容站自然的原因：**页面结构和内容结构是对齐的。**

### 3. 实战中的组织方式

建议把“页面职责”分开：

- 列表页：筛选、分页、入口展示
- 详情页：展示具体内容
- 公共组件：卡片、标签、分页器、作者信息、侧边栏

不要把所有逻辑都堆在页面文件里。页面文件应该偏“组合”，业务逻辑和 UI 细节尽量拆出去。

### 4. 从列表页到详情页，最好把什么一起带上

很多时候你不是只想“跳过去”，你还想保留一些上下文，比如：

- 当前页码
- 当前分类
- 搜索关键词
- 来源专题页

这些信息可以通过查询参数保留，也可以通过浏览器历史记录配合返回逻辑处理。  
但老赵提醒你：**别把“返回体验”建立在隐藏状态上，页面本身能读懂才是王道。**

### 5. 常见坑

- 列表页字段不够，详情页还得再请求
- 路由参数和后端接口参数没对齐
- 详情页刷新后依赖前一页状态，导致空白
- SEO 需要的标题、摘要没有随页面内容变化

这些问题大多不是框架不行，而是页面组织没想清楚。

#### 老赵式总结
列表页到详情页，是内容站最核心的一条业务链。  
**你把这条链路跑通了，Next.js 的价值就基本摸到了。**  
如果连“列表—详情—返回列表”都组织不好，别急着谈架构，先把页面和数据关系理顺。

---

## 五、内容型站点常见页面结构设计：别把页面写成一锅粥

### 1. 典型页面结构

内容站通常不只是“首页 + 详情页”，常见结构还有：

- 首页：推荐内容、热门分类、最新文章
- 列表页：分类文章列表、搜索结果页
- 详情页：正文、作者、标签、相关推荐
- 归档页：按时间聚合
- 标签页：按主题聚合
- 关于页：固定信息

这些页面本质上都围绕“内容组织”展开，所以重点不是页面有多少，而是内容关系怎么排。

### 2. 页面组织建议

老赵建议按“内容层级”来组织，而不是按“写到哪儿算哪儿”。

比如：

- `posts/`
  - 列表页
  - 详情页
- `tags/`
  - 标签列表页
  - 标签详情页
- `authors/`
  - 作者列表页
  - 作者详情页

这种组织方式的好处是：

- 一眼看出功能边界
- 动态路由好管理
- 扩展新内容类型时不乱

### 3. 组件复用怎么做

内容站常见复用组件包括：

- 内容卡片
- 面包屑导航
- 标签组件
- 文章目录
- 作者信息卡
- 分页器
- 相关推荐模块

注意：**复用的是表现形式，不是业务职责。**  
别为了复用把一个巨型组件写得谁都能传、谁都能配，那样看起来灵活，实际上维护很痛苦。

### 4. 页面、组件、数据层怎么分工

记住这句很管用：

> 页面负责路由和组合，组件负责展示，数据层负责取数。

页面文件处理“我是谁、我要展示什么”；  
组件处理“我长什么样、怎么复用”；  
数据层处理“内容从哪来、怎么传过去”。

这套分工在 Next.js 里尤其重要，因为它既要考虑前端组件，也要考虑页面路径和数据来源。

### 5. 一个更贴近实战的结构判断

如果你的站点是内容型的，页面层级通常会很清楚：  
首页管入口，列表页管聚合，详情页管内容，专题页管组合。  
这时 Next.js 很适合做结构化页面。

如果你的页面大多是单独的展示页，而且不会增长，不需要列表、详情、专题这种内容层级，那就没必要把页面组织得过于复杂，普通静态方案反而更轻。

#### 老赵式总结
内容型站点最怕“页面越做越散，组件越拼越乱”。  
Next.js 的优势不只是路由，还在于它能让你把**内容层级、页面层级、组件层级**对齐。  
如果是页面重复、内容变化、结构清晰的站点，Next.js 很合适；  
如果只是临时活动页、单页展示页，别为了组织而组织。

---

## 六、什么时候只是普通静态页面，不一定非要上复杂路由方案

这一小节老赵特意补给你，因为很多人一学会动态路由，就容易见啥都想套进去。

### 1. 哪些场景其实很简单

比如：

- 公司介绍页
- 产品介绍页
- 招聘页
- 一次性的活动落地页
- 少量固定导航页面

这类页面往往内容稳定，数量不多，变化也不频繁。  
如果没有列表到详情的跳转，没有大量参数传递，也没有复杂内容聚合，那完全可以先用更简单的方案。

### 2. 别乱上复杂方案的原因

复杂路由、动态渲染、数据预取这些能力，本质上是为“规模化内容管理”服务的。  
如果你的项目根本不吃这套，硬上只会带来：

- 目录结构变深
- 心智负担变重
- 数据流更绕
- 维护成本上升

老赵见过不少项目，页面就三五个，结果路由分层写得像大型门户，最后自己都找不到入口了。

### 3. 一个实用判断

你可以问自己：

- 未来会不会有大量详情页？
- 会不会有列表、筛选、分页、专题？
- 页面会不会随着内容不断增加？
- 是否需要 SEO 和分享链接稳定可读？

如果这些答案大多是否定的，那就别为了“看起来专业”强行上复杂路由结构。

#### 老赵式总结
**动态路由不是必选项，它是解决“页面规模化”的工具。**  
页面少、结构固定、没有内容增长压力时，简单方案往往更合适。  
会用 Next.js 不等于必须用 Next.js，能判断场景，才算真懂。

---

## 七、老赵式判断：动态页面多的时候 Next.js 为什么特别顺手

这一部分老赵给你一个实用结论，不讲虚的。

### 1. Next.js 顺手的原因

当动态页面很多时，Next.js 的优势通常体现在这几件事上：

- 路由文件即页面结构，省去手写路由配置
- 动态路由天然支持内容详情页
- 列表页到详情页的数据流很自然
- 可根据场景选择 SSR / SSG
- 对 SEO 和内容分发更友好
- API Routes 能把简单前后端联动收进一个项目里

也就是说，它很适合做“前台内容展示 + 基础服务接口”的组合。

### 2. 什么时候该用 Next.js

比较适合：

- 内容站、博客、媒体站
- 文档站、知识库
- 电商详情页、类目页
- 需要 SEO 的营销站
- 前后端结合、页面以读取数据为主的项目

### 3. 什么时候别乱上

不太建议一开始就上：

- 纯后台系统，几乎不需要 SEO
- 页面很少、生命周期短的小活动
- 团队对 React 还不熟，先把状态管理和组件拆分练稳更重要
- 项目只需要非常简单的静态页面

### 4. 最后给你一个判断句

如果你的项目满足下面三条中的两条以上，Next.js 大概率值得考虑：

- 有很多详情页或列表页
- 需要内容更新和页面复用
- 希望页面能被搜索引擎更好收录
- 想把前后端放在一个统一的开发节奏里

#### 老赵式总结
动态页面一多，手写 React 单页应用的页面管理成本会迅速上升。  
这时候 Next.js 的价值不是“更高级”，而是**更贴近内容站的真实需求**。  
但反过来说，如果不需要路由分层、不需要 SEO、不需要内容聚合，那就别为了用框架而用框架。

---

## 结尾小结：把动态路由和页面组织真正用起来

这一章你只要抓住一件事：  
**Next.js 的动态路由，本质上是为“内容型页面规模化”服务的。**

你要重点记住：

- 文章、商品、用户详情页，都是动态路由的典型场景
- 路径参数负责定位资源，查询参数负责筛选和状态
- 路由传参的核心是让页面能独立工作、能刷新、能分享
- 列表页到详情页，是内容站最典型的页面流转
- 页面组织要跟内容层级对齐，别写成一锅粥
- 动态页面多、SEO 重要、前后端结合需求强时，Next.js 特别顺手
- 如果只是少量静态页面，就别把路由系统搞得太复杂

### 行动建议

如果你手里正好有个小项目，老赵建议你立刻做三件事：

1. 选一个列表页和一个详情页场景，先把动态路由跑通  
2. 把路径参数、查询参数分清楚，别混着用  
3. 重新审视页面组织：哪些是页面，哪些是组件，哪些该由数据层负责  

先把这条链路做顺了，你后面再学数据获取、SSR、SSG、API Routes，就不会飘。

**老赵最后一句：Next.js 不是拿来装门面的，它是拿来把“内容怎么组织、页面怎么生成、数据怎么传递”这三件事做顺的。**  
动态页面多的时候，它确实香；但如果你的项目不吃这套，就别硬上。

# 第4章：组件与布局怎么组织，别让项目越写越乱

## 开篇引入：页面能跑不算本事，结构清楚才算真会写

很多人刚接触 Next.js，最容易犯的错不是“不会写”，而是“写得太顺手”。首页写在 `pages/index.tsx`，第二个页面也顺手塞进去，Header 复制一份，Footer 再复制一份，Sidebar 临时拼一下。短期看没问题，页面能跑、功能也能出；可项目一大，页面互相抄、互相改，最后谁都不敢动。

这就是前端项目最常见的隐形灾难：**代码能运行，结构却失控。**

Next.js 的价值，不只是路由、SSR、SSG，更在于它天然鼓励你把**页面、组件、布局**分开思考。React 里也能这么做，但 Next.js 自带路由和页面组织能力，更适合顺手把结构理顺。你写的不只是一个页面，而是一套可维护的站点。

这章老赵就带你把这件事讲透：**页面组件、通用组件、布局组件怎么分，公共区域怎么抽，组件拆多细合适，Next.js 项目怎么组织才不乱。**

---

## 一、页面组件、通用组件、布局组件的区别

### 1. 页面组件：路由入口，不是万能容器

在 Next.js 里，页面组件通常直接对应一个路由。你可以把它理解成“用户访问某个地址时看到的整页内容”。比如：

- `pages/index.tsx` 对应首页
- `pages/about.tsx` 对应关于页
- `pages/posts/[id].tsx` 对应文章详情页

页面组件的职责，是**组织这一页需要哪些模块**，而不是把所有东西自己写完。它更像导演，负责安排演员出场，而不是自己演所有角色。

页面组件适合放：

- 当前页面特有的数据请求逻辑
- 页面级组合结构
- 少量页面状态
- 和路由参数直接相关的逻辑

不适合放：

- 重复很多次的 UI 细节
- 所有页面都要用的头部、底部、侧边栏
- 复杂但可复用的交互模块

简单说，页面组件应该“懂业务”，但不要“包打天下”。如果一个页面文件里塞了几百行 JSX，还混着列表、弹窗、表单、请求、校验，那基本就是页面写成了“临时总包现场”。

### 2. 通用组件：可复用的功能单元

通用组件就是多个页面都能用的部件，比如：

- `Button`
- `Card`
- `EmptyState`
- `Pagination`
- `ArticleList`
- `SearchBar`

它们通常输入明确、输出稳定。外部传什么 props，它就按规则渲染什么，不太依赖具体页面环境。

通用组件的好处很直接：

- 减少重复代码
- 统一视觉风格
- 后续改版更轻松
- 降低页面耦合

但别误会，**能复用不等于必须抽**。有些人喜欢把所有东西都拆成组件，最后一个按钮也拆、一个提示也拆，目录看着很“架构”，实际开发却像在文件夹里迷路。

老赵看组件抽象，只看两个词：**必要性**和**稳定性**。一个东西今天变、明天也变，就别急着抽到最底层去。

### 3. 布局组件：负责页面骨架

布局组件不是具体内容，而是**页面的公共骨架**。比如常见网站结构：

- 顶部 Header
- 左侧 Sidebar
- 中间内容区
- 底部 Footer

这些区域通常属于站点级公共部分，不属于某个单页。布局组件的职责，就是把这些公共区域包起来，让页面内容作为变化部分插进去。

在 Next.js 里，布局思想很重要，因为它和路由天然配合。布局处理好，页面切换时结构稳定，维护也会轻松很多。

#### 老赵式判断

- **页面组件**：负责这一页“讲什么”
- **通用组件**：负责一类“零件怎么长”
- **布局组件**：负责整个页面“外壳怎么搭”

---

## 二、Header、Footer、Sidebar 等公共区域怎么抽象

### 1. 先问一句：它是不是跨页面稳定存在的东西

抽公共区域，最怕一上来就写组件，结果某个页面根本不用。老赵的建议很简单：先看它是不是满足两个条件：

1. 多个页面都要用
2. 结构和职责相对稳定

像 Header、Footer、Sidebar 这种，一般都适合抽出来。它们通常承载站点导航、联系方式、版权信息、栏目入口，和页面主体内容关系不大。

但如果只是某个活动页临时出现一次，比如促销横幅、一次性的浮层，那就没必要过度抽象。先放页面里，等真的复用起来再拆。

### 2. 抽象时控制粒度

比如 Header 里有 Logo、主导航、搜索框、头像、登录按钮，别一开始就全拆成独立文件。更稳的做法是：

- 先抽一个 `Header`
- 再把明显独立、复用价值高的部分拆成子组件，比如 `NavMenu`、`SearchBox`
- 那些只在 Header 内部使用、又不复杂的细节，先留在 Header 里

也就是说，抽象不是越碎越好，而是**足够复用、足够清晰就行**。

### 3. 一个简单的组织示意

```bash
components/
  layout/
    Header.tsx
    Footer.tsx
    Sidebar.tsx
    Layout.tsx
  ui/
    Button.tsx
    Card.tsx
    Badge.tsx
```

这里的思路很清楚：

- `layout/` 放结构型组件
- `ui/` 放基础通用组件
- 页面文件只负责组合，不负责堆细节

项目再大一点，还可以按业务继续分：

```bash
components/
  article/
    ArticleCard.tsx
    ArticleMeta.tsx
    ArticleTagList.tsx
```

这样一眼就知道这批组件是干什么的。

### 4. 常见误区

**误区一：公共区域直接复制粘贴**  
改一个地方要改多个页面，维护成本越来越高。

**误区二：为了“未来可能复用”过度拆分**  
目录先复杂了，项目本身没变清楚。

**误区三：拆得太碎**  
查找成本变高，打开一个页面得跳好几个目录才能看清结构。

---

## 三、布局复用与页面嵌套，怎么组织才顺手

### 1. 页面不是孤岛，布局才是连接点

Next.js 里很多页面都不是完全独立的。比如：

- 首页、文章列表页、文章详情页，共用同一个 Header 和 Footer
- 登录页、注册页，可能需要简化布局
- 后台页面，通常需要侧边栏布局

布局复用的核心思路是：**把页面内容作为变化部分，把外壳作为稳定部分。**

### 2. 常见做法：外层布局包页面内容

你可以把页面想成内容块，把布局想成容器。常见做法是：

- `Layout` 负责 Header/Footer/Sidebar
- 页面组件只返回主体内容
- 页面通过组合被 Layout 包住

例如：

```tsx
export default function HomePage() {
  return (
    <Layout>
      <main>
        <h1>首页</h1>
        <ArticleList />
      </main>
    </Layout>
  );
}
```

好处很直接：

- 页面切换时，公共结构统一
- 每个页面只专注自己的主体内容
- 代码阅读更顺：先看页面，再看布局

### 3. 页面嵌套的思路

如果站点区域差异明显，可以进一步做分层布局：

- `SiteLayout`：前台页面
- `DashboardLayout`：后台页面
- `AuthLayout`：登录注册页

这样就不会把所有页面硬塞进一个 Layout 里。不同场景用不同外壳，结构更稳。

比如内容站点可以这样理解：

- 前台文章页：顶部导航 + 搜索框 + 主内容 + 推荐栏
- 后台编辑页：侧边菜单 + 表单区 + 保存按钮
- 登录页：只保留最少干扰元素

布局是为了让页面有明确边界，不是为了炫技。

### 4. 老赵提醒：别让布局抢戏

布局是服务页面的，不是来喧宾夺主的。很多人写布局时，喜欢把业务逻辑塞进去，比如：

- 在 Layout 里请求页面数据
- 在 Layout 里判断各种页面状态
- 在 Layout 里写一堆和某个页面强相关的条件渲染

这样布局会越来越臃肿。布局最好保持**稳定、通用、少逻辑**。页面级业务，尽量放回页面本身或者页面专属组件里。

---

## 四、组件拆分的粒度怎么拿捏

### 1. 拆分的目标不是优雅，而是可维护

组件拆分不是为了看起来高级，而是为了后面的人好改、好找、好复用。判断拆不拆，老赵给你一个实用标准：

- 是否会在多个地方用到？
- 是否足够独立？
- 是否会让当前文件明显变复杂？
- 是否方便测试和修改？

如果大多数答案都是否定的，那就先别拆。

### 2. 适合拆的场景

**适合拆：**

- 一个组件在多个页面出现
- 一个模块职责单一
- 一个局部交互逻辑明显独立
- 视觉样式和行为都比较稳定

比如文章卡片、分页器、筛选栏，就很适合拆。因为首页列表、分类页、搜索结果页，往往都会用到同样的结构。

### 3. 不适合拆的场景

**不适合拆：**

- 只在一个页面用一次
- 逻辑很短，拆出去还要来回跳文件
- 只是为了“未来可能复用”，但现在没证据
- 拆完后 props 来回传，比原来更绕

老赵常说一句话：**没到一定规模之前，过度抽象就是提前制造负担。**

### 4. 一个实用拆分顺序

你可以按这个步骤来：

1. 先把页面写通
2. 找重复片段
3. 看重复片段是不是同类功能
4. 再决定抽成通用组件还是局部子组件
5. 最后把布局和页面骨架独立出来

这个顺序很重要。先跑通，再整理，比一开始就追求完美结构更稳。

---

## 五、与 React 项目相比，Next.js 的页面组织习惯有什么不同

### 1. React 项目更自由，Next.js 更有约束

在纯 React 项目里，路由通常要自己配，页面结构也更自由。你可以把所有页面都放一个目录，也可以按业务拆。自由是自由，但也容易乱。

Next.js 不一样，它本身就带页面路由，目录结构和路由路径通常直接对应。所以它更强调：

- 页面文件怎么放
- 路由怎么对应
- 布局怎么复用
- 数据怎么按页面组织

### 2. Next.js 更适合内容驱动型组织

如果项目是官网、博客、文档站、内容型站点、带 SEO 的营销页面，那 Next.js 的组织方式会很顺手。因为这类站点通常结构稳定，页面共享布局明显，也很适合按页面分层组织内容。

比如文章站点里，你可以自然拆成：

- 首页
- 分类页
- 标签页
- 文章详情页
- 作者页

它们的页面结构不同，但公共区域很一致：头部、导航、列表、侧边栏、底部信息。

### 3. React 思维要保留，Next.js 思维要补上

你已经有 React 基础，所以组件化思维不用重学。要补的是：

- 页面就是路由入口
- 布局是公共骨架
- 数据请求常常和页面场景绑定
- 目录结构本身就是一种设计语言

换句话说，在 Next.js 里，**目录不是单纯存文件，而是在表达产品结构。**

---

## 六、实战小案例：做一个内容型博客站的页面组织

下面用一个典型案例串起来：一个 SEO 友好的博客站。

### 1. 页面规划

站点包含这些页面：

- 首页：展示最新文章和推荐栏目
- 分类页：展示某类文章列表
- 文章详情页：展示正文、作者、相关推荐
- 关于页：站点介绍
- 搜索结果页：根据关键词展示文章

这个站点页面不复杂，但结构很清楚，很适合练布局和组件组织。

### 2. 组件与布局拆法

#### 布局组件

- `SiteLayout`
  - `Header`
  - `Sidebar`
  - `Footer`

#### 通用组件

- `ArticleCard`
- `ArticleList`
- `TagList`
- `Pagination`
- `SearchBar`

#### 页面组件

- `pages/index.tsx`
- `pages/category/[slug].tsx`
- `pages/posts/[id].tsx`
- `pages/about.tsx`
- `pages/search.tsx`

### 3. 组织思路

首页和分类页都要用文章列表，那就复用 `ArticleList`。  
文章详情页要正文和相关推荐，那就把正文展示和推荐区域拆成页面内部子组件。  
Header、Footer、Sidebar 统一放在 `SiteLayout` 里。

这样一来：

- 页面只管业务内容
- 组件只管可复用零件
- 布局只管统一外观
- 改版时影响范围清楚

以后要加热门标签、作者专区、专题栏目，也能平滑扩展，不会一下把首页写成一团。

### 4. 这个案例为什么适合 Next.js

因为这是典型的内容型站点，天然需要：

- 清晰的页面组织
- 可复用布局
- 页面级数据获取
- 较好的 SEO 表现

用纯前端单页应用也能做，但在首屏展示、搜索引擎收录、内容页组织上，Next.js 往往更省心。尤其是文章详情页、分类页这种“内容先于交互”的页面，Next.js 的路由和布局体系优势很明显。

---

## 老赵式总结：别为了复用而硬拆组件

这一章你记住一个核心就行：**组件拆分不是越多越好，布局抽象也不是越早越好。**

老赵给你的实战判断是：

- **页面组件**：负责路由入口和页面组合
- **通用组件**：负责高复用、职责单一的小部件
- **布局组件**：负责公共骨架和页面包裹
- **拆分粒度**：先写通，再按重复和职责去拆

尤其在 Next.js 里，页面组织和路由是连着的，结构一乱，后面数据获取、SEO、部署都会跟着乱。所以别一上来就追求“架构感”，先把项目写得清楚、改得动、找得到，才是真本事。

最后给你一句老赵的使用判断：

- **适合用 Next.js**：内容型站点、官网、博客、文档站、需要 SEO、页面结构稳定、前后端结合明显的项目
- **别乱上 Next.js**：纯后台工具、超重交互应用、SEO 不重要、页面几乎全靠客户端状态驱动的项目

说白了，Next.js 不是“更高级的 React”，它是**更适合某些场景的 React 组织方式**。场景对了，它很香；场景不对，上了反而增加复杂度。

# 第5章：数据从哪来，Next.js 的数据获取方式一次讲透

## 开篇引入：页面能写出来，不代表数据能拿对

前面咱们把 Next.js 的路由、页面组织这些“骨架”搭好了。接下来真正关键的，就是：**页面内容从哪来？**

很多人刚上 Next.js，会想：“这不就是 React 再加个路由吗？那我直接在组件里 `fetch` 不就完了？”

这话只对一半。因为在 Next.js 里，数据不只有一种拿法：可以在页面层拿，也可以在组件层拿；可以在服务端拿，也可以在浏览器里拿；可以在构建时拿，也可以在用户访问时拿。**拿数据的位置不同，首屏、SEO、交互体验和缓存策略都会变。**

所以这一章，老赵就把“数据从哪来、在哪拿、怎么传、什么时候拿”一次讲清楚。你学完之后，至少能回答三个实战问题：

1. 这个页面的数据该放在哪里拿？
2. 这个接口请求该服务端发，还是客户端发？
3. 列表页、详情页、搜索页，分别怎么组织数据流？

---

## 一、先把总关系捋明白：页面层、组件层、服务端、客户端各管什么

你可以把 Next.js 的数据获取理解成一个四层关系：

- **页面层**：决定这个页面先显示什么
- **组件层**：决定某个局部模块怎么补充内容
- **服务端**：负责首屏、SEO、稳定内容
- **客户端**：负责交互、局部刷新、用户操作后的补充请求

它们不是互相替代，而是各有分工。

比如一个文章详情页：

- 页面层先根据路由参数找到文章
- 服务端先把文章正文渲染出来
- 组件层再去拉相关推荐、评论区
- 客户端负责点赞、展开评论、切换标签这些交互

真正成熟的页面，不是“只用一种方式拿数据”，而是**按场景组合使用**。这就是 Next.js 的思路：不是给你一个万能按钮，而是给你一套可以组合的方案。

---

## 二、前端拉数据：先搞清楚“谁来发请求”

### 1. 三个最常见的位置

在 Next.js 里，拉数据最常见的位置，基本就这三个：

- **页面层**：页面一进来就把数据准备好
- **组件层**：某个局部组件自己负责拉数据
- **服务端层**：页面渲染前，在服务端先把数据拿到

你可以把它理解成三种责任范围：

- 页面层：管整页骨架和主数据
- 组件层：管局部模块，比如评论、推荐、头像
- 服务端层：管首屏和需要提前准备好的内容

老赵先强调一句：**Next.js 的厉害，不是“能不能请求”，而是“请求放在哪一层最合适”。** 这才是前后端结合的核心。

### 2. 前端拉数据的常见方式

不管在哪层，发请求的方法本质都差不多：

- `fetch`
- `axios`
- 封装好的请求函数
- 配合状态管理或数据请求库

关键不是“用什么工具”，而是**请求应该在哪个时机发**。

比如：

- 首页文章列表：适合页面加载前就拿好
- 登录后个人消息：可以等页面进来后再拿
- 点击展开的评论区：适合组件显示时再请求

同一个接口，放在不同位置，页面体验可能完全不一样。

### 3. 常见误区

很多初学者会把所有请求都写进组件里，结果页面一打开先空白，等 JS 执行完再补内容。这样会带来几个问题：

- 首屏慢
- SEO 差
- 页面闪一下
- 逻辑分散，不好维护

还有一种情况更常见：一个页面上多个子组件都各自请求同类数据，接口重复打，状态互相抢，排查问题时还不知道谁先谁后。

所以老赵先给你一句话：

> **能在页面层解决的主数据，别一股脑塞进子组件里。**

---

## 三、页面级数据获取：先定页面，再定数据

### 1. 什么叫页面级数据获取

页面级数据获取，意思就是：**这个页面要展示什么内容，尽量先在页面入口处把数据组织好，再往下传给子组件。**

这样有两个好处：

- 页面结构清楚
- 数据流向简单

比如博客详情页，页面上有：

- 文章标题
- 作者信息
- 正文
- 标签
- 推荐阅读
- 评论区

这里最核心的是文章本体。页面层应该先把文章详情拿到，再传给标题、正文、标签这些子组件。评论区要不要单独拿，看业务。

这个思路特别适合内容型页面，因为内容型页面最怕数据散，一个页面像拼乐高，哪块数据谁拿的都说不清。

### 2. 页面层拿数据的判断标准

如果满足下面任意几条，优先考虑页面层：

- 这份数据决定页面主体内容
- 页面首屏必须展示
- 希望对搜索引擎更友好
- 数据结构较稳定
- 子组件都要复用同一份数据

反过来，如果是用户操作后才出现的内容，比如弹窗、下拉加载、局部筛选，那就不一定非要页面层先拿。

老赵给你个很实用的判断：  
**只要这个数据没它页面就不像页面，那它就该更靠近页面层。**

### 3. 页面层和组件层的分工

一个稳妥的思路是：

- **页面层负责调度**
- **组件层负责展示**
- **数据层负责请求**

也就是说，页面先拿到总数据，再拆给不同组件。这样不会出现每个组件都自己去后端问一遍，避免重复请求和状态打架。

你可以把页面层想象成项目经理，组件层是执行者，接口请求是采购。项目经理先把货拿回来，再分给不同工位，别每个工位自己去市场买一遍。

---

## 四、服务端和客户端取数据：不是谁更高级，而是谁更合适

### 1. 服务端取数据：先算好，再给用户看

服务端取数据的特点是：

- 用户请求页面时，服务器先拿数据
- 再把带数据的 HTML 返回给浏览器
- 首屏通常更完整
- 对 SEO 更友好

这种方式特别适合：

- 内容型页面
- 详情页
- 文章页
- 商品页
- 需要被搜索引擎抓取的页面

你可以理解成：**先把饭做好端上来，用户一坐下就能吃。**

这类页面最大的优势就是“打开即有内容”。对于资讯、博客、商品介绍这类站点，服务端拿数据很自然，也更符合用户预期。

### 2. 客户端取数据：页面先出来，数据后补上

客户端取数据的特点是：

- 页面先渲染一个基础壳子
- 浏览器加载完成后再发请求
- 适合交互强、数据频繁变化的场景

常见场景：

- 登录后个人中心
- 实时筛选
- 不需要 SEO 的后台页面
- 用户点击后加载更多内容

它的好处是交互灵活，坏处是首屏可能没内容，或者内容迟一点才出现。

所以你会发现，客户端请求不是“低级”，它只是适合另一类场景。后台系统本来就不太需要被搜索引擎收录，那就没必要为了首屏 HTML 漂亮，强行上服务端渲染。

### 3. 两者怎么选

老赵给你一个简单判断：

- **要首屏、要 SEO、要稳定内容**：优先服务端
- **要交互、要动态更新、SEO 不重要**：优先客户端

别一上来就觉得“客户端更现代”，也别觉得“服务端一定更高级”。在 Next.js 里，**选择正确比追求高级更重要。**

---

## 五、页面间传参与页面内取数：从列表页到详情页怎么串起来

### 1. 传参不是只传 id

很多人一说传参就只会想到 `id`。其实在 Next.js 里，传参远不止这个。

常见参数类型包括：

- 路由参数：`/posts/123`
- 查询参数：`?keyword=nextjs&page=2`
- 请求体参数：提交表单时的内容
- Header 参数：鉴权信息、语言信息等

不同参数负责不同事情：

- **路由参数**：识别资源是谁
- **查询参数**：描述筛选条件
- **请求体**：提交数据
- **Header**：附带上下文信息

你可以把它理解成：路由参数是“找人”，查询参数是“附加条件”，请求体是“正式提交”，Header 是“随身证件”。

### 2. 传参的常见方式

在页面之间传参，常见方式有：

- 通过 URL 传参
- 通过动态路由拿参数
- 通过接口请求时带参数
- 通过状态管理临时保存

但老赵提醒你一句：  
**能放 URL 的，尽量放 URL。**

因为 URL 天然可访问、可分享、可刷新。比如文章详情、商品列表、搜索结果，都非常适合用 URL 传递关键信息。

### 3. 一个完整步骤案例：列表页跳详情页，再根据参数取数

这个案例最能把“传参”和“取数”串起来。

假设你有一个文章列表页：

1. 列表页请求文章列表
2. 每条文章渲染标题、摘要、封面
3. 每条卡片链接到 `/posts/[slug]`
4. 用户点击后进入详情页
5. 详情页从路由里拿到 `slug`
6. 页面根据 `slug` 请求文章详情
7. 正文加载后，再请求评论和相关推荐
8. 如果请求失败，展示错误状态或兜底文案
9. 如果正在加载，先展示骨架屏或者占位内容

这个流程里，前一页负责“给入口”，后一页负责“按入口找数据”。  
这就是典型的页面间数据流。

如果你把列表页和详情页的数据组织清楚了，后面做商城、课程站、博客站，思路都差不多。

---

## 六、数据获取方式怎么配：SSR、SSG、CSR 的区别

### 1. SSR：请求时拿数据，适合变化频繁或强 SEO 页面

SSR 可以简单理解成：**用户每访问一次，服务器就按当前请求准备一次内容。**

适合：

- 新闻
- 文章详情
- 商品详情
- 个性化内容
- 需要实时状态的页面

优点是内容新、SEO 好。  
缺点是服务器压力相对大一些。

如果你做的是内容站或者官网页面，SSR 很多时候都很顺手。尤其是页面内容会更新，但又不想让用户看到过时内容的时候，SSR 很合适。

### 2. SSG：构建时拿数据，适合稳定内容

SSG 可以理解成：**在构建阶段先把页面做好，访问时直接发成品。**

适合：

- 文档站
- 博客
- 落地页
- 内容比较稳定的专题页

优点是快、稳、便宜。  
缺点是内容更新不如 SSR 灵活。

比如公司介绍页、产品介绍页、帮助中心，这类内容改动没那么频繁，就很适合 SSG。构建一次，访问效率高，部署后也省心。

### 3. CSR：浏览器里拿数据，适合交互型页面

CSR 就是大家熟悉的前端模式：  
**页面先渲染壳子，再在浏览器里加载数据。**

适合：

- 后台管理系统
- 用户中心
- 交互非常复杂的应用
- SEO 不重要的内部页面

优点是交互灵活。  
缺点是首屏内容可能不够完整。

### 4. 为什么实际项目里经常混用

很多人以为一个项目只能选一种渲染方式，其实不是。真实项目里很常见的是混用：

- 首页用 SSR，保证首屏和 SEO
- 文章详情用 SSG，保证性能和稳定访问
- 评论区用 CSR，保证交互体验
- 后台管理页全 CSR，简单直接

这才是 Next.js 的正常打开方式。  
你不用被“必须选一个”绑住，关键是看页面职责。

### 5. 选择口诀

老赵给你一个特别实用的判断：

- **内容稳定、追求速度**：SSG
- **内容变化快、追求首屏和 SEO**：SSR
- **强交互、SEO 不关键**：CSR

别把三种模式当成死教条，实际项目里经常是混着用的。比如首页 SSR，详情页 SSG，后台页面 CSR，这很正常。

你真正要学会的不是背定义，而是看到页面就能判断：这个页面是给谁看、看什么、要不要被搜到、要不要马上完整呈现。

---

## 七、什么时候不该在组件里请求：别让局部组件把页面拖慢

### 1. 组件里请求也有边界

组件层请求不是不能用，而是要用对地方。

适合组件层请求的情况：

- 评论区加载
- 推荐阅读
- 懒加载模块
- 用户展开后才需要的内容
- 与主内容弱相关的附加信息

不适合组件层请求的情况：

- 页面主内容
- 首屏必须显示的信息
- 多个子组件都依赖的公共数据
- 需要参与 SEO 的内容

### 2. 一个反例：子组件各自请求同一份文章信息

比如详情页里，标题组件请求一次文章信息，正文组件又请求一次，作者组件再请求一次。看起来每个组件都很独立，实际上：

- 请求重复
- 状态分散
- 页面加载变慢
- 出错难排查

这时候就应该把文章详情放到页面层统一拿，再传给子组件。

### 3. 组件内请求的正确姿势

如果确实需要在组件里请求，建议满足这几个条件：

- 数据是局部的
- 请求有明确触发点
- 有加载态和错误态
- 不影响主页面首屏
- 不会和其他组件重复抢数据

这样组件才是“自己负责自己”，而不是“顺手把整个页面拖下水”。

---

## 八、一个小型实战：内容型站点的文章列表 + 详情页

咱们把前面讲的串起来，做一个内容型站点的思路。

### 1. 文章列表页

需求：

- 展示文章标题、摘要、发布时间
- 支持分类筛选
- 支持分页

数据流：

- 页面层根据分类和页码请求文章列表
- 文章卡片组件只负责展示
- 筛选条件放到 URL 里，方便刷新和分享

适合理由：

- 列表页是内容型站点入口
- 页面需要可被搜索引擎抓取
- 适合使用更偏 SSR 或 SSG 的方式

这里要注意，列表页不是“看起来像列表”就够了，而要做成真正能被访问、能被搜索、能继续导航的入口页。

### 2. 文章详情页

需求：

- 展示文章正文
- 展示作者、发布时间、标签
- 下方补充相关推荐

数据流：

- 路由参数决定文章唯一标识
- 页面层请求文章详情
- 相关推荐可交给子组件或者后续请求

适合理由：

- 详情页天然和 SEO 强相关
- 首屏内容要完整
- 路由和数据一一对应

如果你做的是博客、专栏、知识库，这一套几乎就是标准答案。

### 3. 搜索页

需求：

- 输入关键词搜索文章
- 支持排序
- 支持分页

数据流：

- 关键词、排序、页码全部写入 URL
- 页面读取参数后请求接口
- 参数变更就重新请求

这个案例里，你会发现 Next.js 的价值很明显：  
**页面组织、路由参数、服务端渲染、SEO 友好，这些东西合在一起，就很适合内容型站点。**

---

## 九、老赵式总结：这一章到底要怎么记

这一章你最该记住的，不是某个请求写法，而是数据获取的判断思路。

### 你要形成的心法

- 页面主内容，优先页面层组织
- 强 SEO 页面，优先服务端或构建时准备
- 交互型局部数据，放组件层更合适
- 搜索条件、列表筛选，尽量体现在 URL 里
- 主数据和路由参数要绑紧

### 什么时候该用 Next.js

Next.js 特别适合这些场景：

1. **内容型站点**：博客、专栏、资讯、文档、知识库
2. **需要 SEO 的官网或落地页**：首页、产品页、活动页
3. **页面组织清晰、路由明确的前后端结合项目**：列表页、详情页、搜索页一套走通

这些场景里，Next.js 的路由、服务端渲染、静态生成、接口能力配合起来，确实很顺手。

### 什么时候别乱上

但老赵也要提醒一句：**不是所有项目都要上 Next.js。**

如果你做的是：

1. **纯后台系统**，SEO 不重要，主要是登录后操作
2. **强交互、重实时、状态很复杂的前端应用**
3. **团队只需要一个轻量 React SPA，不想引入太多框架约束**

那你别为了“听起来高级”就硬上 Next.js。此时纯 React + 合适的状态管理和请求方案，往往更轻、更直接。

### 最后一句

Next.js 之所以在内容站、博客、商品详情、落地页这些场景里特别吃香，不是因为它“会发请求”，而是因为它把**路由、渲染、数据获取**这几件事连成了一套。  
你一旦理解了数据应该从哪来、在哪拿、怎么传，Next.js 的很多能力就通了。

下一章，咱们就继续把“渲染模式”和“页面实际交付效果”彻底讲清楚。

# 第6章：SSR、SSG、CSR 怎么选，不是背概念，是看场景

如果你已经会 React，再看 Next.js，最容易绕晕的就是这三个词：**SSR、SSG、CSR**。很多人能背出“服务端渲染、静态生成、客户端渲染”，一到真实项目里还是会问：

- 这个页面到底该放哪种渲染？
- 首页要不要 SSR？
- 文章详情页是不是一定要 SSG？
- 后台管理系统是不是全 CSR 最省事？
- 为什么同一个项目里，居然能混着用好几种方式？

老赵先给你一个结论：**别背概念，先看场景。看页面类型，看你更在意首屏、SEO，还是实时性。** 这三个维度一弄清楚，渲染模式就不神秘了。

---

## 一、SSR、SSG、CSR 到底分别是什么？

先把概念说清楚，但不抠教科书定义。

### 1. SSR：请求来了，服务器先把页面画好

SSR 指的是：**请求来了以后，服务器先根据数据生成 HTML，再返回给浏览器**。浏览器拿到的不是空白页，而是已经有内容的页面，随后再由前端 JavaScript 接管交互。

你可以理解成：

- 用户打开页面，先看到内容；
- 然后 JS 再补交互；
- 不用等脚本全跑完才显示。

**优点：**
- 首屏通常更快看到内容
- 对 SEO 友好
- 适合内容变化频繁、又需要被搜索引擎抓取的页面

**缺点：**
- 每次请求都要服务器参与渲染
- 服务端压力更大
- 缓存和架构要更认真设计

### 2. SSG：提前把页面烘焙成静态文件

SSG 指的是：**在构建阶段就把页面生成好**，部署后用户访问时直接拿到静态 HTML。

就像菜单提前印好，顾客来了直接拿，不用每次现写。

**优点：**
- 访问速度快
- 部署简单
- 成本低
- SEO 也很好

**缺点：**
- 内容更新不够实时
- 数据变了通常要重新构建或做增量更新
- 不适合高频变化页面

### 3. CSR：浏览器自己把页面拼出来

CSR 指的是：**服务器先返回基础 HTML，真正页面内容主要靠浏览器端 JavaScript 去请求数据并渲染**。这是很多传统单页应用最常见的方式。

**优点：**
- 前端交互灵活
- 适合复杂后台、操作型系统
- 前后端分工清晰

**缺点：**
- 首屏容易慢，尤其是 JS 包大时
- SEO 天然不占优
- 用户得先等脚本跑起来

### 4. 一句话分辨三者

简单记：

- **SSR：请求时生成**
- **SSG：构建时生成**
- **CSR：浏览器里生成**

这个记法不花哨，但很实用。

---

## 二、别只看概念，先看首屏、SEO 和实时性

渲染模式不是“谁更高级”，而是**你更看重什么**。老赵建议你每次选型都先问自己三件事。

### 1. 首屏性能：用户第一眼看到什么

首屏性能本质上就是：**用户打开页面后，多久能看到有意义的内容**。

- SSR：通常不错，因为 HTML 里已经有内容
- SSG：通常最好，因为直接返回静态文件
- CSR：最容易吃亏，因为要先下载 JS，再请求数据，再渲染

别误会，CSR 不一定慢到不能用。它的问题通常是**内容出现得晚**，不是最终体验一定差。比如内部系统、登录后后台，用户本来就不是来抢那一秒的。

### 2. SEO：搜索引擎能不能看懂

SEO 场景里，内容能不能被抓取很关键。

- SSR 和 SSG 天然更友好
- CSR 不是不能做 SEO，但通常要额外处理
- 如果你做的是公开内容页、文章页、商品页、活动页，SEO 往往不能忽略

老赵给你一个简单判断：

> 只要页面希望被搜索引擎收录，或者希望别人分享链接时预览信息完整，就尽量不要做成纯 CSR。

### 3. 实时性：数据变了要不要立刻体现

这个点很多人容易忽略。

- SSR：请求时拿最新数据，实时性较强
- SSG：默认是构建时数据，实时性最弱
- CSR：浏览器端拉最新数据，实时性也可以很强

但实时性强，不代表就一定适合 CSR。你还得同时考虑首屏和 SEO。很多时候，最佳答案不是单选，而是**混合策略**。

### 4. 一个实用判断模型

用这三问来判断：

1. **这个页面要不要被搜索引擎收录？**
2. **用户打开时，是不是特别在意第一屏速度？**
3. **这个页面内容更新频率高不高？**

粗略结论：

- **SEO 强 + 内容稳定**：优先 SSG
- **SEO 强 + 内容经常变**：优先 SSR
- **内部系统 + 强交互 + 不太在乎 SEO**：优先 CSR

---

## 三、内容型站点、后台系统、活动页，分别怎么选？

这部分最实战。别只记概念，要能落到页面类型上。

### 1. 内容型站点：文章、资讯、知识库、博客

这类站点最像 Next.js 的舒适区。

**典型特点：**
- 内容以阅读为主
- 页面需要被搜索引擎收录
- 大量页面结构相似
- 更新频率中低，或者可以分批更新

**推荐策略：**
- 文章详情页：SSG 或 SSR
- 文章列表页：SSG + 增量更新，或者 SSR
- 首页：内容不常变就用 SSG；热点变化快就考虑 SSR

**为什么适合 Next.js？**
- 路由组织清晰
- 页面天然适合 SEO
- 组件复用方便
- 能把内容页、推荐位、标签页拆得很细

### 2. 后台系统：管理台、表单系统、工作流页面

后台系统是另一种画风。

**典型特点：**
- 登录后使用
- 强交互
- 权限复杂
- SEO 基本不重要
- 重点是功能效率和开发效率

**推荐策略：**
- 大部分页面可用 CSR
- 某些页面需要首屏预填数据时，可局部 SSR
- 很多后台没必要为了“看起来高级”硬上 SSR

**为什么 CSR 常常更合适？**
- 用户进后台前就已经登录
- 页面更多是“操作”，不是“传播”
- 状态管理、表单、筛选、分页会很多
- 纯前端渲染更顺手

### 3. 活动页：营销页、落地页、专题页

活动页讲究的是：**打开快、展示准、转化高**。

**推荐策略：**
- 内容固定的活动页：SSG 很合适
- 临时促销但要快速更新：SSR 或 SSG + 重新构建
- 价格、库存、名额变化频繁：考虑 SSR 或接口补数据，别死靠静态页

**为什么活动页常喜欢 SSG？**
- 页面稳定
- 访问压力大时，静态页抗压强
- 适合快速加载和 SEO 收录

---

## 四、为什么同一个项目里，页面可以用不同渲染方式？

这点是 Next.js 很有价值的地方：**不是整个项目只能选一种渲染模式**。

你完全可以这样分工：

- 首页：SSG 或 SSR
- 文章详情页：SSG
- 搜索结果页：SSR
- 用户中心：CSR
- 后台管理页：CSR
- 活动专题页：SSG

这才是前后端结合开发真正的威力：**不同页面按不同目标、不同成本去选方案**。

### 1. 页面组织方式要按业务切，不要按技术炫技切

很多新手喜欢问：“我项目到底是 SSR 还是 CSR？”  
老赵通常会说：**你先别问项目，先问页面。**

因为真实业务里，不同页面目标根本不一样：

- 文章页：要收录
- 搜索页：要实时
- 仪表盘：要交互
- 个人中心：要权限
- 落地页：要转化

### 2. 一个简单的页面分层思路

可以这样规划：

- **公开内容页**：优先 SSG/SSR
- **登录后业务页**：优先 CSR
- **高频变动但需要曝光的页面**：SSR
- **稳定、重复访问高的页面**：SSG

这样团队不会被“全站统一渲染模式”绑死。

---

## 五、渲染模式选择时，最常见的几个误区

这节很关键，因为很多项目不是技术不行，而是选型一开始就歪了。

### 误区 1：SSR 一定比 CSR 高级

不是。

SSR 在 SEO 和首屏上有优势，但不代表默认更好。后台系统、内部工具、强交互表单，用 SSR 往往只会增加复杂度。

### 误区 2：做 Next.js 就必须全站 SSR

也不是。

Next.js 强就强在灵活，不是强迫你全站一种模式。一个项目里混用多种策略很正常。

### 误区 3：SSG 就意味着不能更新

也不完全对。

SSG 强调的是“构建时生成”，但你可以通过重新构建、定时发布、增量更新让内容变化。关键是它不是秒级实时。

### 误区 4：CSR 没 SEO，所以不能做内容站

这个说法太绝对。

更准确地说：**如果你想让内容站更适合搜索和分享，SSR/SSG 往往更省心**。CSR 不是完全不能做，但通常不是最优解。

### 误区 5：一个项目只能选一种渲染方式

这是最容易把自己困住的想法。真实项目里，页面差异很大，**混用才是常态**。

### 误区 6：听起来高级就默认选 SSR

这个最要命。很多团队一听“服务端渲染”就上头，觉得只要 SSR 就稳了。结果页面本来是登录后台、内部工具，或者只是一个很简单的管理页，非要上 SSR，最后得到的不是更好的体验，而是更复杂的代码、更高的服务器压力，甚至更难维护的缓存逻辑。

老赵的判断是：**SSR 不是身份象征，它只是一个工具。**

---

## 六、一个内容型站点案例：技术博客该怎么选？

咱们拿一个很常见的场景串一下。

假设你要做一个技术博客站点，有这些页面：

- 首页：展示最新文章、热门标签
- 文章列表页：按分类、标签筛选
- 文章详情页：长文阅读
- 搜索页：按关键字检索
- 登录后的草稿管理页：编辑文章、发布文章

### 1. 首页

如果博客更新频率不算特别高，首页可以用 **SSG**。这样访问快，分享出去预览也完整，还能吃到 SEO 的好处。

如果首页内容高度动态，比如要展示实时推荐、热榜、最近更新，而且变化很快，那就考虑 **SSR**。

### 2. 文章列表页

列表页通常也很适合 **SSG** 或 **SSR**。

- 分类稳定、内容变化不频繁：SSG
- 文章上新快、筛选条件多、要尽量最新：SSR

### 3. 文章详情页

这是内容型站点最核心的 SEO 页面，通常优先考虑 **SSG**。

原因很直接：
- 内容稳定
- 访问量可能高
- 适合被搜索引擎抓取
- 适合缓存和分发

### 4. 搜索页

搜索页更偏实时，通常更适合 **SSR** 或 **CSR + 接口请求**。

如果你希望搜索结果首屏就能被抓到，SSR 更稳。  
如果搜索是登录后内部使用，CSR 也完全合理。

### 5. 草稿管理页

这个页面就是典型 **CSR** 场景。编辑、保存、预览、发布，全是交互，不需要 SEO。你没必要为了它折腾服务端渲染。

### 6. 这个案例说明了什么？

同一个站点里，不同页面的选择完全不同。  
这也是 Next.js 的价值：**把“内容型站点”和“应用型页面”放在一个技术体系里统一管理**。

## 七、渲染模式选择清单：你上线前可以这样判断

上线前别拍脑袋，按这个清单过一遍：

### 如果页面满足以下条件，优先考虑 SSG
- 内容变化不频繁
- 需要 SEO
- 访问量可能大
- 允许构建时生成

### 如果页面满足以下条件，优先考虑 SSR
- 需要 SEO
- 数据变化频繁
- 希望打开时就拿到最新内容
- 页面内容依赖请求参数或用户状态

### 如果页面满足以下条件，优先考虑 CSR
- 主要是登录后使用
- 强交互、强状态管理
- SEO 不重要
- 页面逻辑更像工具而不是内容展示

这三组条件不是死规则，但足够帮你做第一轮判断。只要你能先把页面分型，后面再做细化就不难了。

## 八、老赵式总结：别把 SSR 当万能药

SSR、SSG、CSR 这三个东西，不是让你考试背名词的，是让你**根据业务做判断**的。

你真正要记住的是：

- **SSG** 适合稳定内容和 SEO，像博客、文章、专题页；
- **SSR** 适合要收录、又要尽量实时的页面；
- **CSR** 适合后台系统、登录后应用、强交互场景。

别一听“服务端渲染”就兴奋，觉得它天然比客户端渲染高级；也别一看“静态生成”就觉得只能做静态博客。真正专业的做法是：**按页面选方案，而不是按名词站队**。

再把这句话记牢一点：

> 性能、SEO、实时性，这三样你不可能每次都全拿满，通常得看你这次更想保哪一个。

所以什么时候该用 Next.js？

- 你要做内容站、营销页、需要 SEO 的页面；
- 你希望同一个项目里兼顾内容展示和应用交互；
- 你想把路由、渲染、接口、静态资源统一在一个体系里管理。

什么时候别乱上 Next.js？

- 你只是做一个非常简单的内部小工具；
- 项目根本不需要 SEO，也不需要复杂页面组织；
- 你为了“听起来先进”硬把一个纯 CSR 的后台包装成 SSR，结果只会增加复杂度。

**一句话结尾：Next.js 不是越多 SSR 越好，而是越会选，越省力。**  
这才是前后端结合开发真正该有的样子。

# 第7章：API Routes 让前后端靠得更近，但别把它想得太神

## 开篇引入：为什么很多人一上 Next.js，就想先写个接口？

学 React 久了，你大概率会遇到一个现实问题：页面会写了，数据一接就得找后端，或者自己再搭一层服务。Next.js 让很多人觉得顺手，原因很直接——**它不只是前端框架，还自带一点“后端能力”**。

这里说的就是 API Routes。你可以把它理解成：**在同一个 Next.js 项目里，顺手写几个轻量接口**，比如表单提交、列表查询、简单中转代理，或者把敏感参数包起来，不直接暴露给浏览器。

它的确方便：页面、接口、仓库都在一起，联调省事，特别适合小团队、个人项目、内容站、活动页这类需求。

但老赵先把话说在前面：**API Routes 很方便，不等于它能替代真正的后端。**

你得先知道它擅长什么、不擅长什么，不然很容易把一个轻巧的页面项目，写成“前端里套了个小后端”，最后维护起来反而更乱。  
所以这一章不是教你“Next.js 也能做后端，真香”，而是教你：**什么时候用得顺，什么时候别硬上。**

---

## 一、API Routes 的作用与使用场景：它到底解决什么问题？

### 1.1 它的核心作用是什么？

API Routes 的核心作用就一句话：**让你在 Next.js 项目里定义服务端接口**。这些接口既可以给页面用，也可以给外部请求用。对开发者来说，它像项目内部自带的一个“迷你后端入口”。

它主要解决页面不方便直接做的事：

- 接收参数
- 做校验
- 调第三方接口
- 返回统一格式的数据
- 隐藏敏感信息

常见价值主要有三类：

#### 1）减少前后端分离时的协调成本
有些小项目不值得单独起一套后端服务，比如活动页、内容站、产品介绍站、内部工具页。前端自己写个接口就能跑起来，没必要为了几条数据再搭一整套服务。

#### 2）做数据中转
有些外部接口浏览器不能直接请求，比如需要隐藏密钥、统一鉴权、做参数清洗或跨域代理。这时 API Routes 很适合当中间层：前端先打到自己项目里的接口，再由它去转发或加工数据。

#### 3）承载轻量业务逻辑
比如表单校验、参数拼装、埋点记录、接口聚合。这些逻辑放在 API Routes 里，通常比散落在前端组件里更清楚：页面管展示，接口管处理，职责分明。

### 1.2 什么场景适合用？

老赵给你一个直接的判断：

#### 适合用 API Routes 的场景
- 小型网站或原型项目
- 内容型站点
- 快速上线的活动页
- 简单表单提交
- 轻量数据代理
- 暂时不想单独维护后端项目

#### 不太适合的场景
- 复杂权限系统
- 高并发业务
- 大量数据库操作
- 复杂事务处理
- 需要完整后端架构的系统

简单说：**它适合“顺手干点服务端小活”，不适合“接管整个后端”。**

### 老赵式总结
API Routes 的价值在于“省事”，不是“万能”。

**什么时候该用 Next.js 的内置接口？** 当你只是想快速做页面 + 轻量接口，项目规模不大，逻辑也不复杂。  
**什么时候别乱上？** 当你已经明确这是一个正经业务后端，未来要多人协作、要拆服务、要做复杂治理，那就老老实实接独立后端。

---

## 二、如何在 Next.js 项目里写简单接口：最小可用方案是什么？

### 2.1 API Routes 的基本位置

在 Next.js 里，你通常会在特定目录下创建接口文件。不同版本目录会有差异，但原则一样：**页面归页面，接口归接口**，不要把业务逻辑全塞进组件里。

一个简单接口通常只做三件事：

1. 接收请求  
2. 读取参数  
3. 返回 JSON 数据  

先把“接口能跑起来”这件事做好，比一上来堆复杂逻辑更重要。

### 2.2 一个最简单的接口长什么样？

你可以把它想成一个“服务端函数”：前端来请求，它就返回结果。比如做“获取文章列表”的接口，大概就是：

- 判断请求方法
- 如果是 GET，就返回文章列表
- 如果不是 GET，就返回错误

关键不是代码长什么样，而是职责要清楚：

- **它不是页面**
- **它不是组件**
- **它是一个服务端接口**

这个认知很关键。因为一旦把它当普通函数写，就容易忘了它面对的是网络请求，而不是本地调用。

### 2.3 写接口时要注意什么？

#### 1）先定输入，再定输出
接口最怕“随便写”。你至少要先想清楚：

- 前端传什么参数？
- 接口返回什么字段？
- 出错时怎么返回？

比如一个搜索接口：

- 输入：`keyword`
- 输出：`list`、`total`
- 错误：`message`

先把这些定下来，前后端配合就会顺很多，不然字段名一会儿一个样，大家都在猜。

#### 2）尽量保持返回结构统一
别今天返回 `{ data }`，明天返回 `{ list }`，后天又变成 `{ result }`。  
前端调用会很痛苦，项目一大，维护成本更高。

建议至少保持统一风格，比如：

- 成功：`{ success: true, data: ... }`
- 失败：`{ success: false, message: ... }`

#### 3）别把敏感逻辑写到前端
如果涉及密钥、Token、内部地址、私有配置，都应该放在服务端处理。API Routes 正好能帮你挡一层，前端只拿结果，不碰核心秘密。

### 老赵式总结
写简单接口，不是为了炫技，而是为了让项目更顺。

**适合用 Next.js 写接口的情况**：页面和接口绑定紧密，逻辑轻，开发节奏快。  
**别乱上 API Routes 的情况**：你还没想清楚边界，就先把数据库、权限、消息队列逻辑往里面塞，这不是“前后端靠近”，这是“把锅都扣到一个项目里”。

---

## 三、前端调用自定义接口的常见方式：页面怎么把接口用起来？

### 3.1 最常见的调用模式

在前端里调用 API Routes，本质就是发请求。常见方式有：

- 页面加载时请求
- 用户点击按钮后请求
- 表单提交后请求
- 路由切换时请求

你可以把它理解为：**组件负责交互，接口负责数据。**

对 React 开发者来说，这不陌生。区别只是，在 Next.js 里，你多了一个选择：有些数据可以先在服务端拿，有些再交给客户端处理。接口不是必须每次都在浏览器里打，页面组织方式可以更灵活。

### 3.2 页面里怎么组织请求逻辑？

#### 方式一：在页面组件里直接请求
适合简单场景。比如首页加载时请求文章列表，逻辑简单，写在页面里也没问题。

#### 方式二：封装成独立函数
把请求逻辑抽出去，比如：

- `fetchArticles()`
- `submitForm()`
- `loadProfile()`

这样页面组件会更干净，职责也更清楚。

#### 方式三：继续封装成统一请求层
项目再大一点，可以统一做请求封装、错误处理、token 注入、响应拦截。以后改接口地址或鉴权方式，只改一处，不用全项目搜字符串。

### 3.3 前端调用接口时最容易踩的坑

#### 坑 1：接口地址写死
上线后路径一变，前端全挂。最好统一请求方式，别到处硬编码，尤其是开发、测试、生产环境路径不同的时候。

#### 坑 2：忘记处理加载状态和错误状态
很多人只写“成功后渲染”，没写 loading、error、empty。结果接口一慢，页面像卡死一样，用户根本不知道发生了什么。

#### 坑 3：过度依赖客户端请求
如果一个内容页本来更适合服务端渲染，你却非要先渲空壳，再在浏览器里请求数据，那 SEO 和首屏体验都可能吃亏。  
有些页面就是应该早点把内容给到搜索引擎和用户，别为了“统一写法”把体验搞差了。

### 老赵式总结
前端调用自定义接口，核心不是“会不会发请求”，而是**知道什么时候在页面里发，什么时候在服务端先拿**。

**适合 Next.js 的地方**，在于你可以把页面和数据获取方式一起设计。  
**别乱上 Next.js 的套路**，是把所有数据都拖到浏览器里再处理，最后又慢又乱，还浪费了它的服务端能力。

---

## 四、表单提交、查询接口、代理请求：三种最常见的接口思路

### 4.1 表单提交：最典型的“前端到接口”

表单提交是 API Routes 最常见的场景之一，比如联系我们、留言板、邮箱订阅、活动报名。

典型流程是：

1. 用户填写表单
2. 前端做基础校验
3. 提交给 Next.js 接口
4. 接口二次校验
5. 返回成功或失败

老赵提醒你：**前端校验只是体验，后端校验才是底线。**  
只要请求是网络传来的，参数就可能被改，接口必须再检查一次。

实际做的时候，建议你按这个顺序来：

- 先在页面里收集表单数据
- 再检查必填项、格式、长度
- 然后请求 API Routes
- 接口里再次校验字段是否合法
- 最后把结果返回给页面提示用户

这样一来，用户体验和安全性都能兼顾。

### 4.2 查询接口：给页面提供数据

查询接口就是最常见的 GET 场景。比如做一个内容站：

- 首页展示最新文章
- 分类页展示某个分类下的内容
- 详情页展示单篇文章

前端可以通过接口拿数据，再渲染页面。

这里有个关键点：  
**如果是内容型站点，很多查询接口更适合配合 SSG 或 SSR 使用，而不是纯 CSR。**

也就是说，API Routes 只是拿数据的入口，真正怎么渲染，还是要看场景。页面要不要提前生成、要不要服务端先渲染，不是接口说了算，而是业务目标说了算。

### 4.3 代理请求：最像“中间人”的用法

代理请求特别适合这些情况：

- 第三方 API 有跨域限制
- 不想把密钥暴露给浏览器
- 想统一做鉴权
- 想在返回前改造数据格式

简单说，API Routes 可以当“翻译官”：

前端只跟你说一句话，你去帮它跟外部系统沟通，再把结果整理后返回。

这个场景很实用，因为很多项目真正难的，不是“拿到数据”，而是“安全地拿到数据”。如果页面直连第三方接口，很多细节会变得很麻烦。

### 老赵式总结
表单提交、查询接口、代理请求，看起来都是请求，本质却不同。

- **表单提交**重在验证和安全
- **查询接口**重在页面数据组织
- **代理请求**重在保护敏感信息和统一接口

**什么时候该用 Next.js？** 你需要一个项目里就能解决这些轻量服务端问题。  
**什么时候别乱上？** 如果你已经有成熟后端服务，Next.js 就别重复造一套接口层，免得两边职责打架。

---

## 五、API Routes 和真正后端服务的边界：别把“能写”误解成“该负责”

### 5.1 它能做什么

API Routes 适合做：

- 轻量接口
- 数据代理
- 表单处理
- 简单业务判断
- 少量读写数据

这些事情它做起来顺手，而且和页面开发配合紧密，特别适合快速迭代。

### 5.2 它不该硬扛什么

别把这些都塞进去：

- 大量业务规则
- 复杂权限模型
- 多系统联动
- 长事务处理
- 消息消费、任务调度
- 复杂数据库结构管理

这些内容一旦增长，Next.js 内置接口就会显得有点顶不住。不是它完全不能做，而是这样会让项目职责越来越模糊，后面维护特别累。

### 5.3 怎么判断边界是否越线？

你可以用这几个问题判断：

#### 问题 1：这个逻辑是不是页面专属？
是的话，API Routes 很合适。

#### 问题 2：这个逻辑是不是多个端都会用？
如果是，最好独立成后端服务。

#### 问题 3：这个逻辑会不会越来越复杂？
如果会，早点拆分，别等到后面重构。

#### 问题 4：这个接口是不是只为前端服务？
如果接口完全是为了页面，那放在 Next.js 里通常很自然。

### 老赵式总结
API Routes 不是后端的替代品，它更像是“前端项目里的服务端补丁”。

**适合 Next.js 的边界**：页面相关、轻逻辑、快速交付。  
**不适合乱上的边界**：核心业务、复杂系统、长期演进的后端能力。

老赵的经验是：**先轻后重，先快后稳**，别一上来就把小项目按大系统设计。

---

## 六、基础部署思路：接口上线时要考虑什么？

Next.js 项目里有 API Routes，部署时要多想一步：**页面和接口是一起发布的。**

这意味着你需要关注：

- 环境变量是否配置正确
- 接口是否依赖运行时能力
- 数据源是否可访问
- 线上域名和请求路径是否匹配

### 6.1 基础检查清单

上线前至少检查这几项：

- 接口是否能在生产环境正常返回
- 是否使用了正确的环境变量
- 是否有敏感信息泄露
- 请求路径是否与前端一致
- 错误信息是否过于详细

这些看起来基础，但真出问题时，往往就是这些地方没处理好。

### 6.2 一个容易忽略的问题：部署和存储

如果接口依赖本地文件系统、临时文件或本地状态，要小心。很多部署环境并不适合长期依赖本地持久化。

所以涉及上传、存储、后台任务时，要提前规划，别把 API Routes 当万能盘。它能处理请求，但不代表适合承载所有运行时数据。

### 老赵式总结
部署不是“点一下上线”就完事。

**Next.js 适合什么部署思路？** 页面和轻接口一体化，快速交付，适合中小项目。  
**什么时候别乱上？** 当接口明显依赖复杂环境、异步任务、持久存储时，就别硬塞在项目里，后面会很难维护。

---

## 七、一个完整案例：内容型站点的留言与投稿接口

为了把前面这些东西串起来，老赵给你一个更贴近实际的场景：**做一个内容型站点，比如技术博客、专栏站、活动资讯站。**

这个站点通常会有几个典型需求：

- 文章列表和详情页要能被搜索引擎抓到
- 用户能留言
- 读者可以投稿或订阅
- 管理端不想单独再开一个很重的后端

这时候，API Routes 就很适合做一些轻量支撑。

### 7.1 留言功能怎么做？

留言页的流程可以这样设计：

1. 用户在文章详情页填写留言
2. 前端先做基础校验，比如昵称、内容不能为空
3. 提交到 `/api/comment`
4. API Routes 再检查一次参数
5. 通过后写入数据库或转发到消息服务
6. 返回成功信息，前端刷新留言列表

这个场景里，API Routes 的价值很明显：  
页面负责内容展示，接口负责收口处理，逻辑不会散在组件里。

### 7.2 投稿或订阅怎么做？

如果用户要投稿，你可能还会收到：

- 标题
- 作者信息
- 正文内容
- 联系方式

这些信息不适合直接暴露到前端更深层的处理链路里。用 API Routes 做一个入口，能帮助你先做：

- 字段过滤
- 内容长度检查
- 简单反垃圾
- 转发到邮件或外部服务
- 记录提交日志

如果只是轻量站点，这已经够用了。

### 7.3 这个案例为什么和 SEO 有关系？

因为内容型站点最重要的不是“能不能点”，而是“能不能被看到”。  
文章页面、分类页面、详情页，如果能结合 SSR 或 SSG 提前把内容准备好，搜索引擎和用户体验都会更好。

而 API Routes 在这里扮演的是辅助角色：  
它负责提交、代理、补充数据，不抢页面渲染的主线。

这就对了。  
**页面的事交给页面，接口的事交给接口。**

### 7.4 这个项目的边界怎么定？

如果你的网站只是：

- 内容展示
- 留言提交
- 简单投稿
- 订阅表单
- 少量后台数据操作

那 Next.js + API Routes 很舒服。

但如果你后面要做：

- 复杂会员体系
- 多角色权限
- 订单与支付
- 大规模异步任务
- 多端共用同一套业务能力

那就别把全部东西都塞在 Next.js 里面。该接独立后端就接独立后端，该上网关就上网关，别为了省一步，把后面十步都坑了。

### 老赵式总结
内容型站点是 API Routes 很典型的落地场景，但它的定位永远是“辅助”。

**适合 Next.js 的情况**：内容站、博客、活动页、轻量后台，想快速把页面和接口跑通。  
**别乱上的情况**：业务越来越重、接口越来越多、多人协作开始复杂，这时候就该拆边界了。

---

## 结尾小结：API Routes 是加分项，不是护身符

这一章你只要记住一句话：**API Routes 让 Next.js 更像一个完整应用框架，但它不是让你放弃后端设计的理由。**

它最适合的任务是：

- 给页面提供轻量接口
- 做数据代理
- 处理表单提交
- 封装敏感逻辑
- 让前后端协作更顺滑

它最不适合的任务是：

- 替代完整后端
- 承担复杂业务核心
- 充当长期扩张的服务中枢

如果你做的是内容型站点、营销页、轻量后台、活动页面，Next.js 的 API Routes 往往很好用。  
如果你做的是业务复杂、多人协作、后端逻辑很重的系统，那就别为了“全栈感”硬上，分工清楚反而更稳。

## 老赵最后一句话

**Next.js 适合把页面和轻量接口绑得更近，但不适合把所有后端问题都揽过来。**  
会用的人，拿它提效；不会用的人，容易把项目写成一锅粥。  
所以真正成熟的判断不是“能不能用”，而是——**这事是不是值得让 Next.js 来管。**

# 第8章：图片、静态资源和基础性能优化，细节决定体验

## 开篇引入：页面看着慢，很多时候不是代码慢，而是资源太“实在”

老赵先说句大实话：很多 Next.js 页面跑得不舒服，问题未必出在业务逻辑，而是出在图片、静态资源和加载方式上。页面写得再漂亮，首屏一进来先卡两秒，文章配图一张比一张大，Logo 还用原始尺寸，体验很快就塌了。

Next.js 的价值，不只是“能做服务端渲染”，还在于它把前端工程里容易被忽略的细节也接了过来：图片优化、静态资源管理、按需加载、首屏策略和基础性能意识。尤其是内容型站点、博客、资讯页、电商详情页，这些页面往往不是计算最重，而是资源最杂。谁能把资源处理好，谁的体验就更稳。

这一章老赵不讲虚的，就围绕一个问题展开：**怎么让页面既好看，又不拖沓。**

---

## 一、图片资源的引入、优化与加载思路：图片不是“放进去就完事”

### 1. 图片为什么是性能大头

很多人做页面时先盯 JS 体积，最后真正拖慢体验的却往往是图片。原因很简单：

- 图片体积大
- 数量多
- 尺寸常常不受控
- 首屏图片会直接影响感知
- 内容型站点本来就依赖封面图、正文图、头图

尤其在文章页、专题页、商品页，图片不是装饰，而是内容本身。不能简单理解成“放个 `<img>` 就完了”。

老赵常见一种情况：开发时本地网络快，看不出问题；一上线到手机端，首屏内容还没出来，大图先一张张加载，页面就开始跳。做图片，不能只盯着“显示出来”，还得盯着“什么时候显示、显示多大、会不会拖慢别的内容”。

### 2. 在 Next.js 里，优先考虑什么

Next.js 提供了更方便的图片处理思路，核心不是让你少写几行代码，而是帮你把常见问题提前处理掉：

- 自动处理响应式尺寸
- 可以按场景控制加载策略
- 减少不必要的首屏浪费
- 提供基础优化能力，改善体验

如果你做的是内容型站点，尤其适合把文章封面图、列表卡片图、Banner 图纳入统一规则，而不是每个页面各写各的。

老赵建议先养成一个习惯：**先判断这张图是什么角色。**  
它是首页主视觉？列表缩略图？正文配图？还是补充说明图？  
不同角色，对应不同策略，别把所有图都当主角。

### 3. 图片加载的基本判断标准

老赵给你一个实用判断：

- **首屏主视觉图**：保证清晰和加载速度，不能太大也不能糊
- **列表中的缩略图**：尺寸统一，尽量小而准
- **正文配图**：按实际展示宽度控制，不要原图硬怼
- **非首屏图片**：可以延后加载，别一上来全塞进浏览器

核心思路就一句：**先让用户看到内容，再让用户看到细节。**

### 4. 常见误区

- 图片越大越清晰  
  错。真正该做的是“合适尺寸 + 合适格式 + 合适展示区域”。

- 全站用同一张超大图缩小显示  
  看起来一样，体验却很差，移动端尤其明显。

- 只管视觉，不管体积  
  页面好看不难，难的是又快又稳。

很多团队会花时间优化组件和接口，最后一看首页，最重的居然是那张 2MB 的 Banner 图。这个时候就知道，性能优化不能只看代码，资源也得管。

### 5. 可执行建议

现在就能做三件事：

1. 找出首页和详情页最重的三张图  
2. 看它们是否真的需要原始尺寸  
3. 把非首屏图片改成延后加载思路

这三步通常就能看出明显变化。

---

## 二、静态文件的存放与访问方式：资源要放对地方，别让项目目录乱成一锅粥

### 1. 静态资源到底指什么

静态资源通常包括：

- 图片
- 图标
- 字体
- 下载文件
- 固定不变的公共资源

它们的特点是：**不需要每次请求都现算，内容相对固定。**

它们不像接口数据那样每次都要查数据库，也不像页面逻辑那样每次都要重新计算。正因为这样，静态资源最怕的不是没有，而是乱。

### 2. Next.js 里静态资源怎么放

通常做法是把公开访问的静态文件放到约定位置，让它能直接访问。好处很直接：

- 路径清晰
- 访问稳定
- 不需要额外写接口
- 适合全站复用

比如 Logo、favicon、页面背景图、活动海报这类资源，应该统一管理，而不是散落在各个组件目录里。

老赵的经验是：**凡是会被多个页面复用的资源，就不要放得太“私房”。** 资源一旦散开，后面改一个 Logo、换一次品牌图，你就得翻遍项目。小项目还好，大一点能把人找崩溃。

### 3. 文件组织方式建议

老赵建议至少按这几类管理：

- **公共静态资源**：Logo、icon、favicon、站点默认图
- **内容资源**：文章封面、活动图、专题图
- **本地调试资源**：开发阶段临时图片，上线前清理
- **字体和下载类资源**：单独放，别和业务图片混在一起

如果你做的是内容站，建议再细一点：首页资源、文章资源、活动资源、品牌资源，最好有基本分层。不是为了显得专业，而是为了后面好维护。

### 4. 常见误区

- 把所有图片都塞到组件目录里，后面找都找不到
- 资源命名太随意，`img1.png`、`final-final-new.png` 这种最容易埋雷
- 同一张图多处重复上传，增加体积和维护成本

老赵见过最典型的问题就是：一个项目里有三四个“logo 最终版”，最后谁也说不清线上到底在用哪个。别笑，这种事在团队里很常见。

### 5. 实操建议

一个好习惯是：**资源文件按“业务域”或“用途”分类，而不是按“心情”分类。**  
比如文章相关图片放一组，首页视觉资源放一组，公共图标放一组。后期替换、排查、清理都会轻松很多。

如果项目已经启动，老赵建议趁早整理一次资源目录。看着不起眼，但它直接决定你后面是优雅维护，还是边改边骂。

---

## 三、首屏体验和资源体积的基础意识：别让用户等你“慢慢准备”

### 1. 首屏为什么重要

用户打开页面时，不会想“我先等等你加载完”。他只会判断：这个网站快不快、值不值得看、是不是卡了。

所以首屏体验不是性能指标的附属品，而是第一印象。尤其是内容型站点，首页、栏目页、文章页通常就是入口，首屏决定了大部分感受。

Next.js 很适合做这类页面，一个重要原因就是它能把首屏展示和后续资源加载拆开考虑：先把最关键的内容亮出来，而不是一股脑全端上来。

### 2. 资源体积的三个基本意识

老赵建议你先建立三个最朴素的意识：

#### 1）能小就别大
图片、脚本、字体、背景图，凡是能控制体积的，都别放飞。

#### 2）能少就别多
首屏不需要的资源别急着加载，不是所有内容都必须第一时间出现。

#### 3）能晚就别早
非关键资源，优先让核心内容先出来。

这三条看着简单，实际上很管用。很多性能优化不是靠高级技巧，而是靠顺序判断。

### 3. 先保核心信息，再追求丰富效果

一个页面最重要的不是“东西很多”，而是用户能不能迅速看到：

- 标题
- 主内容
- 关键按钮
- 当前页面主体信息

图片再漂亮，如果把正文和结构压得太慢，那就是本末倒置。内容型站点尤其如此，用户来这里多半是看文章、列表、专题，不是欣赏复杂特效。

### 4. 可执行建议

你可以拿首页做个检查：

- 首屏有没有不必要的大图
- 有没有一进来就加载一堆非关键资源
- 标题和正文是不是比图片更晚出现
- 是否把所有元素都当成“必须立即显示”

如果首屏里有太多“其实可以晚点再来”的内容，就该收一收了。

---

## 四、懒加载、尺寸控制与基础优化习惯：优化不是玄学，是习惯

### 1. 懒加载适合什么场景

懒加载的核心思想很简单：**先加载用户马上要看到的，再加载后面才可能看到的。**

适合懒加载的通常有：

- 长列表中的图片
- 文章正文中靠后的配图
- 评论区头像
- 页面底部推荐内容图

不适合一股脑懒加载的：

- 首屏核心视觉图
- 关键内容图标
- 会影响页面理解的主图

这个判断很关键。懒加载不是“能懒就懒”，而是“该懒的才懒”。首屏主图如果也懒加载，用户看到的就是空壳子，体验反而更差。

### 2. 尺寸控制为什么重要

很多性能问题不是图片太大，而是展示尺寸和实际文件尺寸差太多。页面展示 300px 宽，你传了一个 3000px 的原图，那就是浪费。

尺寸控制的目标是：

- 让图片接近实际展示尺寸
- 避免浏览器多做无意义缩放
- 降低网络传输压力

这个道理放到字体、背景图、图标上也一样。不是所有资源都要最好最全，要按场景给合适的尺寸。你给多了，浏览器不感谢你，只会拖慢页面。

### 3. 基础优化习惯清单

老赵建议你养成这套习惯：

- 上传前先压缩
- 统一图片命名规则
- 给图片设置合理尺寸
- 首屏图优先加载
- 非核心图延后处理
- 页面中重复使用的图尽量复用
- 上线前检查大图是否误入

不用一开始就追求复杂优化，先把这些基本动作做扎实，效果通常就已经够用。

### 4. 常见误区

- 只优化代码，不优化资源
- 只关心本地开发速度，不关心线上体验
- 觉得“图片就那样，没必要管”

很多内容站上线后，最先被吐槽的就是“图太大、页面慢、滑起来卡”。

老赵的看法很直接：你可以暂时不做特别复杂的工程化优化，但基础资源管理一定不能松。因为这类问题不是“有没有”，而是“迟早会不会被用户感知到”。

---

## 五、内容型站点里图片资源的常见处理方式：这类站点最怕“图乱、图重、图慢”

### 1. 内容型站点的图片特点

内容型站点，比如博客、资讯、专栏、教程站、知识库，图片通常承担三类任务：

- 说明内容
- 增强点击
- 提升排版视觉

这类站点对图片的要求不是“越炫越好”，而是“稳定、统一、够用”。

老赵很爱拿内容站做例子，因为它特别能体现 Next.js 的价值：页面要有 SEO 友好性，要能快速首屏展示，还要兼顾图文混排。图片管理做得好，整个站点就会很顺。

### 2. 常见处理方式

#### 方式一：统一封面图比例
文章列表页最怕每张封面比例不同，版面会乱。建议统一成固定比例，比如 16:9 或 4:3，至少在视觉上保持稳定。

#### 方式二：正文图限制最大宽度
正文里的图片不应该横着把整页撑爆，通常控制在内容容器宽度以内，保证阅读节奏。

#### 方式三：大图做缩略图，小图做预览图
列表页用缩略图，详情页再加载较清晰版本，这样更省流量，也更快。

#### 方式四：为内容图建立统一规范
包括：

- 图片比例
- 文件大小范围
- 文件命名
- 备选图策略
- 无图时的占位方案

这些规范看起来像运营细则，实际上对开发很重要。内容图来源不统一时，前端就会经常补锅。与其后面到处兜底，不如一开始就把标准定住。

### 3. 一个典型案例

比如你做一个“前端学习博客”：

- 首页文章卡片显示统一封面图
- 列表页只加载缩略图
- 文章详情页正文图按需加载
- 没有封面图时显示默认占位图
- 站点 Logo 和分享图统一管理

这样页面既整齐，性能也不会太差。更重要的是，后续内容维护的人知道怎么上传图，不会把站点搞乱。

这类案例最能体现 Next.js 的实用价值：它不是单纯一个“页面框架”，而是一整套面向内容展示的开发思路。你能把图片、路由、数据、SEO 一起考虑，站点就会更像一个成品。

---

## 六、这一章到底该怎么落地：先管住最重的资源，再谈更细的优化

如果把前面这些内容收成一句话，那就是：**先解决用户最容易感知到的慢，再去折腾更深的性能优化。**

老赵建议你在项目里按这个顺序做：

1. 先找首屏最重的图片和资源  
2. 再整理静态文件目录  
3. 然后统一内容图规范  
4. 最后再看哪些资源可以懒加载、延后加载或压缩

别一上来就追求“极致优化”，很多时候你把目录、尺寸、加载顺序这三件事做好，页面体验就已经明显改善了。

如果项目是内部管理后台、工具类页面，图片少、访问量低、内容也不复杂，那这章的很多做法可以简化处理，不用过度设计。  
但如果你做的是博客、资讯站、专题页、营销落地页、商品详情页，或者任何一个靠内容和图片吃饭的项目，那这章的内容就非常值钱。因为这类站点一旦资源没管住，SEO、转化和体验都会一起受影响。

---

## 七、老赵式总结：别让大图拖垮一个本来挺好的页面

这一章你要记住的，不是某个 API 怎么写，而是一个判断：**图片和静态资源不是装饰品，它们是体验的一部分。**

老赵给你收个口：

1. **图片先看场景，再看好不好看。**  
   首屏图、列表图、正文图，处理方式不一样。

2. **静态资源要统一管理。**  
   别把项目弄成“谁上传谁负责”，最后连自己都找不到文件在哪。

3. **性能优化先从资源入手。**  
   很多页面慢，不是逻辑慢，是资源太重、太多、太早加载。

4. **内容型站点尤其要重视图片规范。**  
   因为它本来就是图文混排的场景，图片一乱，整个站点气质就没了。

5. **别乱上复杂方案。**  
   如果你的页面只是一个内部管理后台、低频使用的小工具，图片又少、访问量也不高，那没必要过度优化。  
   但如果你做的是博客、资讯站、专题站、营销页，Next.js 这套图片、静态资源和基础优化能力就很值。

### 行动建议

本章结束后，你可以马上做三件事：

- 检查项目里最大的一批图片，看看有没有明显超尺寸
- 梳理静态资源目录，统一命名和分类
- 找一个内容页做一次首屏优化，优先处理最重的那张图

**老赵最后一句话：页面体验很多时候不是“代码写得对不对”，而是“资源有没有被你认真对待”。别让大图拖垮一个本来挺好的页面。**

# 第9章：SEO 基础怎么做，内容型站点为什么离不开 Next.js

## 开篇引入：SEO 不是玄学，它本质上是在回答“搜索引擎能不能看懂你”

前面我们讲了 Next.js 的页面、路由、渲染和数据获取。到这一章，要把这些能力和一个很现实的问题连起来：**你的页面能不能被搜到、看懂、收录。**

从开发者视角看，SEO 主要就三件事：

- **标题**：搜索结果里显示什么
- **描述**：搜索结果里给用户看的简介
- **可抓取内容**：搜索引擎能不能顺利拿到正文

这三件事没做好，内容再好也可能没人看到。尤其是内容型站点、博客、官网、专题页，流量很多时候不是靠直接访问，而是靠搜索来的。

**老赵先说结论：如果你做的是内部系统、登录后才能看的后台，那就别为了“听起来高级”硬上 SEO 思路。**

---

## 一、SEO 的基本概念：你至少要让搜索引擎看到什么？

### 1. 标题和描述：别让搜索结果像一张白纸

页面最基础的 SEO 信息，就是标题和描述。标题像门牌号，描述像简介。

比如一篇文章页，如果标题只是“详情页”，搜索结果就没辨识度。更合理的是：

- 标题：`Next.js 入门：从页面路由到服务端渲染`
- 描述：`本文讲解 Next.js 的基础路由、数据获取方式和渲染模式选择，适合已经掌握 React 的开发者`

这不是为了堆关键词，而是为了**让页面内容更明确**，方便用户和搜索引擎判断值不值得点。

### 2. 可抓取内容：别把正文全藏在前端

如果正文主要靠客户端运行后再请求数据渲染，搜索引擎可能抓取不稳定，甚至抓到空壳。内容页、文章页、专题页尤其要注意，正文本来就是核心资产，不能含糊。

所以 SEO 的本质不是“加几个词”，而是：

- 页面结构清楚
- 内容能直接输出
- 元信息完整
- 重要文本不要全靠交互后才出现

### 3. 基础可访问性：不只是给机器人看，也是给人看

SEO 和可访问性经常是一回事的两面。比如：

- 正确使用标题层级
- 图片有合适的 `alt`
- 链接文本清楚
- 页面结构语义明确

这些做法既方便搜索引擎理解页面，也让真实用户更容易浏览。说白了，你把页面做得像“一个正常能读的网页”，SEO 往往不会太差。

**老赵式总结：SEO 不是偷偷塞词，而是把标题、正文、结构、图片这些东西摆清楚。内容站最怕的不是没技术，而是内容明明有，搜索引擎却看不见。**

---

## 二、为什么内容型站点、博客、官网都重视 SEO？

### 1. 内容型站点靠“长期流量”活着

内容型站点和博客的特点是：文章不是一次性用完就扔，而是能长期带来访问。比如教程、产品说明、行业专题，可能上线几个月后还在持续被搜到。

这类站点更关心的是：

- 搜索结果能不能稳定展示
- 新内容能不能尽快被收录
- 专题页能不能形成内容聚合

内容站的思路和普通活动页不一样。活动页讲究短期转化，内容站更像“慢慢养资产”，每篇文章都可能成为未来入口。

### 2. 官网更需要“被准确理解”

官网常见目标不是纯展示，而是承接咨询、注册、下载、预约。用户搜索时，往往带着明确意图：

- 这家公司做什么？
- 这个产品怎么用？
- 有没有价格页、文档页、案例页？

如果标题、描述、正文结构不清楚，搜索引擎很难判断你到底提供什么。网站里明明有“产品介绍”“解决方案”“帮助文档”，结果页面标题全一样，那搜索引擎只能猜。

### 3. 博客和专题页适合做内容分发

博客页承接单篇文章流量，专题页把多个文章聚合起来，形成主题入口。比如：

- 文章列表页：展示最新内容、分类内容
- 文章详情页：承载具体知识点
- 专题页：把“Next.js 基础”“部署指南”这类内容聚在一起

这种结构既适合搜索引擎，也方便用户顺着路径继续看下去。用户今天搜到一篇文章，明天可能就顺着专题页继续读，这就是内容站最宝贵的长尾效果。

**老赵式总结：内容站、博客、官网重视 SEO，不是因为讲究，而是因为它们的价值本来就建立在“被找到”这件事上。要是你的网站不靠搜索吃饭，别把 SEO 当成必须项。**

---

## 三、Next.js 在 SEO 上为什么天然占优？

### 1. 它更容易先输出页面内容

Next.js 的核心优势之一，就是可以让页面在服务端先生成可见内容，或者在构建时提前生成静态页面。这样搜索引擎访问时，拿到的不是一张空壳，而是已经有正文的页面。

这对内容页特别友好。搜索引擎最怕的就是页面打开了，但正文还要等 JavaScript 跑完。对用户也是一样，先看到标题和正文，再慢慢补交互，体验通常更稳。

### 2. 路由和页面组织更适合内容站

Next.js 的文件式路由很适合内容型站点组织页面：

- `pages/articles/index.js`：文章列表页
- `pages/articles/[id].js`：文章详情页
- `pages/topics/[slug].js`：专题页

这种结构一眼就知道每个页面干什么，也方便给不同页面设置不同的标题、描述和数据来源。做内容站时，你不会想把所有内容塞进一个大页面里靠前端切换，那样后面维护和优化都会很痛苦。

### 3. 元信息管理更自然

你可以给每个页面设置自己的标题、描述、OG 信息，让每一页都像独立内容单元，而不是一个大壳子里动态换字。对 SEO 来说，这非常关键。

比如文章详情页用文章标题，专题页用专题名和说明，列表页则写清栏目属性。每页都有自己的“名片”，搜索引擎才知道它们分别是什么。

### 4. 图片、静态资源和性能也会间接影响 SEO

页面打开慢，用户会走，搜索引擎体验也差。Next.js 在图片处理、静态资源管理上更顺手，至少能少踩几个常见坑。内容站尤其要注意：首屏慢、图片乱、资源拖沓，都会影响整体体验。

**老赵式总结：Next.js 的 SEO 优势，不是因为它有个“SEO 按钮”，而是它在页面输出、路由组织、静态生成这些地方，天然更适合内容站。**

---

## 四、页面元信息、结构化内容和基础可访问性，具体怎么做？

### 1. 页面元信息：每页都要“名片清晰”

最基本的做法是让每个页面有独立标题和描述，不要全站一个标题走天下。文章页、列表页、专题页，应该各写各的。

简单判断标准：

- 列表页强调“主题 + 分类 + 更新”
- 详情页强调“文章标题 + 核心主题”
- 专题页强调“专题名 + 内容范围”

开发时先别急着填内容，先想清楚它在搜索结果里应该怎么被介绍。

### 2. 结构化内容：让页面像文章，而不是像一坨 div

内容页至少要做到：

- 一个清晰的主标题
- 段落分明
- 小标题层次合理
- 相关内容分区明确
- 文末有相关推荐或下一篇入口

搜索引擎更容易理解这种结构，用户也更容易扫读。尤其教程类文章，层次清楚非常重要。

### 3. 图片与文字要配合

文章里用了封面图、配图，要注意：

- 图片有描述性 `alt`
- 不要把关键信息只放在图片里
- 图片大小尽量合理，避免拖慢首屏

图文并茂没问题，但图是辅助理解，不是代替正文。

### 4. 基础可访问性别忽略

按钮、链接、表单都要语义清楚。你把页面做得像“能被正常阅读的网页”，SEO 往往不会太差。

**老赵式总结：SEO 不是单点优化，得连着页面结构一起做。标题、正文、图片、链接，像一套配合好的桌面，别只顾摆花瓶。**

---

## 五、内容型站点案例：文章列表页、文章详情页、专题页怎么配合？

我们拿一个“Next.js 学习博客”来举例，顺着看就很清楚了。

### 1. 文章列表页：承接主题流量

列表页主要职责是聚合内容，比如“Next.js 基础文章”“部署文章”“性能优化文章”。

做法上要注意：

- 页面标题写清楚分类
- 描述说明这个栏目提供什么
- 列表项用真实文章标题，不要全叫“文章1、文章2”
- 加分页或加载更多，保证内容可持续扩展

列表页不是摆设页，它是用户进入专题内容前的导航入口。很多时候，一个好的列表页比单篇文章更容易把用户留住。

### 2. 文章详情页：承载搜索主流量

详情页是最容易被搜索到的页面。它应该包含：

- 文章标题
- 简洁摘要
- 正文内容
- 作者、日期、分类
- 相关文章推荐

如果文章是“Next.js 中的 SSR 怎么理解”，页面就该围绕这个问题展开，而不是一上来先塞一堆无关内容。内容站最怕标题党式结构，标题说一套，正文跑偏另一套，用户和搜索引擎都会不舒服。

### 3. 专题页：把零散内容串成路径

专题页适合做内容聚合，比如“Next.js 从入门到实战”专题。它可以把相关文章串起来，形成学习路径：

1. 为什么流行  
2. 页面路由与动态路由  
3. 数据获取  
4. SSR/SSG/CSR  
5. SEO 与部署  

专题页的价值在于：**它既有搜索价值，也有导航价值。** 搜索进来的是单篇内容，但留下来的往往是整条内容路径。

**老赵式总结：内容站不是堆文章，而是把文章组织成体系。列表页负责聚合，详情页负责深度，专题页负责串联，这才像一个能长期吃搜索流量的站。**

---

## 六、什么时候该用 Next.js，什么时候别乱上？

这是老赵最想提醒你的地方。

### 适合用 Next.js 的场景

- 内容型站点、博客、官网、文档站
- 需要 SEO 和搜索收录
- 页面数量多，且路由层次清晰
- 既要前端体验，又想兼顾服务端输出
- 想把页面、数据接口、静态资源组织在一个体系里

### 不建议硬上 Next.js 的场景

- 纯内部后台，基本不需要搜索引擎
- 页面特别简单，一个静态壳就够
- 团队完全不需要服务端能力，却硬要为“技术先进”增加复杂度
- 项目生命周期很短，没必要引入一整套页面渲染和路由约定

一句话：**Next.js 适合“内容要被看见”的项目，不适合“为了用而用”的项目。**

**老赵式总结：别把 SEO 当借口，也别把 Next.js 当装饰。你的网站如果不需要被搜索引擎看到，就没必要为了 SEO 把架子搭得太重；反过来，如果你做的是内容站、博客、官网，那 Next.js 确实很值。关键是场景，不是面子。**

---

## 结尾小结：先把“能不能被看见”想明白，再谈花活

这一章你只要记住一件事：**SEO 不是后期补丁，而是页面结构、渲染方式和内容组织方式的结果。**

对内容型站点来说，Next.js 的价值很直接：

- 更容易输出可抓取内容
- 更方便组织页面和路由
- 更适合做文章页、专题页、官网页
- 更容易兼顾性能、体验和收录

如果你正在做博客、内容站、产品官网，Next.js 很值得上；如果你的项目根本不需要搜索引擎参与，那就别把 SEO 和 Next.js 过度神化。

**最后给你一个行动建议：**  
下次你做页面时，先别急着写组件，先问自己三个问题：

1. 这个页面谁会搜到？
2. 搜索引擎看到的标题和描述是什么？
3. 正文内容是不是一打开就能看见？

这三个问题想明白了，你的 Next.js 页面，才算真的开始像一个能上线的内容产品。

# 第10章：做一个内容型小项目，把路由、数据、渲染和 SEO 串起来

## 开篇引入：为什么要做这个小项目

前面我们已经把 Next.js 的几个关键点拆开讲了：路由怎么走、动态路由怎么配、页面怎么组织、SSR、SSG、CSR 怎么选、API Routes 怎么接、图片和静态资源怎么管。  
但很多人学到最后还是会卡住：**每个知识点都懂一点，真落地时却不知道怎么串起来**。

所以这一章，老赵不空谈，咱们直接做一个**内容型小项目**：一个简单的文章站点。它不复杂，但足够完整，能把 Next.js 的核心能力串成一条线。

这个项目我们设定成三类页面：

- **列表页**：展示文章摘要、封面、发布时间
- **详情页**：展示文章正文、作者、推荐阅读
- **专题页**：按主题聚合内容，比如“前端工程化”“React 进阶”

你会发现，这种项目很像真实业务里的内容站、博客站、知识库、营销页，特别适合 Next.js。因为它天然有 SEO 需求，也天然适合页面级路由和服务端能力。

## 一、项目目标与页面结构设计：列表页、详情页、专题页怎么拆

### 1.1 先想清楚页面职责

做页面，不是先写代码，而是先回答：**这个页面给谁看、看什么、要不要被搜索引擎收录**。

我们这个内容型站点可以这样拆：

- `/posts`：文章列表页
- `/posts/[slug]`：文章详情页
- `/topics/[slug]`：专题页
- `/about`：关于页
- `/search`：搜索页

### 1.2 内容型站点的特点

内容型站点跟工具型后台不一样，它通常有几个特征：

1. 页面以内容展示为主
2. 很多页面是固定结构 + 动态内容
3. SEO 很重要
4. 访问量可能主要来自搜索
5. 页面更新频率不一定高，但每一页都希望被完整抓取

这正是 Next.js 擅长的地方：它把“路由 + 服务端 + 构建 + SEO”这些底座都搭好了。

### 1.3 页面结构怎么设计更合理

建议按“信息层级”组织：

- **列表页**负责发现内容
- **详情页**负责消费内容
- **专题页**负责聚合内容
- **搜索页**负责精准找到内容

这样拆的好处是：每个页面职责清楚，后续路由、数据请求、渲染模式也更好选。

**老赵提醒：**  
页面设计别追求一步到位，先把最核心的链路跑通：列表 → 详情 → 返回专题/列表。链路顺了，项目就活了。

### 老赵式总结

内容型站点第一步，不是写接口，也不是堆组件，而是先把页面职责分清楚。  
**什么时候该用 Next.js？** 当项目有明显页面层级、内容展示和 SEO 诉求时，Next.js 很合适。  
**什么时候别乱上？** 如果只是一个单页小工具，页面少、逻辑轻、搜索也不重要，就别为了“像大项目”硬上 Next.js。

---

## 二、路由设计、动态路由与页面组织方案：文件怎么摆，URL 怎么定

### 2.1 Next.js 的路由系统为什么省心

Next.js 的爽点之一，就是**文件即路由**。  
你创建什么页面文件，基本就对应什么 URL，这让页面组织很直观。

例如：

```bash
pages/
  posts/
    index.tsx
    [slug].tsx
  topics/
    [slug].tsx
  about.tsx
  search.tsx
```

对应关系很清楚：

- `pages/posts/index.tsx` → `/posts`
- `pages/posts/[slug].tsx` → `/posts/xxx`
- `pages/topics/[slug].tsx` → `/topics/xxx`

这种映射方式最大的好处，就是少一层配置，多一层可读性。页面放哪、路由是什么，一眼就能看懂。

### 2.2 动态路由解决什么问题

文章详情页、专题页这种页面，内容不是固定死的，而是根据参数变化。  
这时候就要用**动态路由**。

比如：

- `/posts/nextjs-basic`
- `/posts/ssg-vs-ssr`
- `/topics/frontend-engineering`

这里的 `slug` 就是内容标识，通常来自数据库、CMS、接口返回值或者本地 mock 数据。

动态路由的价值不只是“能传参”，更重要的是它能让 URL 变得**有语义**。  
比起 `/posts?id=123`，`/posts/nextjs-basic` 更适合分享、收藏和搜索引擎理解。

### 2.3 页面组织的建议

做内容型站点时，建议把“页面”和“数据来源”分开：

- `pages/`：页面路由入口
- `components/`：通用组件，比如文章卡片、标签、分页
- `lib/`：数据请求、格式化、接口封装
- `data/`：本地演示数据或 mock 数据
- `styles/`：样式

这种组织方式的好处是：**页面薄、组件厚、数据层独立**。  
以后页面变多，你不会写成一锅粥。

比如文章卡片是一个通用组件，列表页用它，专题页也能用它。  
文章请求方法放到 `lib/posts.ts`，以后改成接真实后端接口时，页面层基本不用大动。

### 2.4 常见误区

- 页面和组件混着放，最后谁都找不到谁
- 动态路由只知道写 `[id]`，不知道参数从哪来
- URL 设计和业务命名混乱，后期改起来很痛苦

**老赵提醒：**  
路由不是越炫越好，URL 最重要的是“人能看懂、搜索引擎能理解、后期能维护”。别把路由搞成谜语。

### 老赵式总结

路由这块，别只记 `[slug]` 这种语法，要真正理解：**页面怎么拆，URL 怎么定，数据怎么跟路由对上**。  
**什么时候该用 Next.js？** 当页面是典型的“一个 URL 对应一个内容单元”时，Next.js 的文件式路由特别顺手。  
**什么时候别乱上？** 如果应用几乎没有页面级跳转，所有东西都在一个壳里切来切去，那 Next.js 的优势就没那么明显。

---

## 三、数据获取、传参和接口调用的串联：内容从哪来，怎么传过去

### 3.1 文章列表页的数据怎么拿

列表页通常要拿这些信息：

- 标题
- 摘要
- 封面图
- 发布时间
- 标签或专题

如果是内容型站点，列表页一般优先考虑**静态生成**或者**服务端渲染**，因为它主要是展示页面，而不是高频交互页面。

核心思路很简单：用户打开页面时，希望马上看到内容，而不是先空着等请求回来。  
所以内容站更适合“先把内容准备好，再给用户看”。

### 3.2 详情页的数据怎么传

详情页通常有一个核心参数：`slug`。

流程一般是：

1. 用户点列表页里的文章卡片
2. 跳转到 `/posts/[slug]`
3. 页面拿到 `slug`
4. 根据 `slug` 请求文章详情
5. 渲染标题、正文、作者信息、推荐阅读

如果你用接口，slug 可以作为路径参数：

```text
GET /api/posts/nextjs-basic
```

如果你是本地数据，也可以先在服务端查到对应内容再渲染。

这里要注意：**参数不是为了传着好看，是为了让页面能准确定位内容**。  
这也是为什么内容站非常适合动态路由。

### 3.3 专题页怎么串联内容

专题页一般是“聚合型页面”，它的任务不是输出一篇内容，而是输出一组相关内容。

例如 `/topics/frontend-engineering` 页面可能展示：

- 专题介绍
- 相关文章列表
- 热门文章
- 相关标签

这里的重点是**传参和聚合逻辑**。  
专题页既可以根据 `slug` 查专题信息，也可以根据专题 ID 再查文章列表。

现实里，专题页很像一个“内容导航页”：它不负责讲完一个知识点，而是负责把一类内容串起来。  
这也是它很适合 SEO 的原因之一——聚合页面常常能承载更多关键词和内部链接。

### 3.4 数据请求的基本判断

你要问自己三个问题：

1. 这个数据是不是页面首次加载就必须有？
2. 这个数据会不会影响 SEO？
3. 这个页面内容更新频率高不高？

这三个问题会直接影响你后面选 SSR、SSG 还是 CSR。

**老赵提醒：**  
很多人一上来就 `useEffect` 请求接口，这在后台系统里有时没问题，但在内容型站点里，可能直接把 SEO 和首屏体验弄丢了。

### 老赵式总结

数据获取不是“会不会请求接口”这么简单，而是要和页面职责、渲染方式一起考虑。  
**什么时候该用 Next.js？** 当页面内容需要首屏就呈现，并且要兼顾搜索收录时，Next.js 的数据组织很有价值。  
**什么时候别乱上？** 如果数据只是用户点按钮后才看，SEO 又不重要，那就别把流程搞得太重。

---

## 四、渲染模式在不同页面中的落地选择：SSR、SSG、CSR 怎么选

### 4.1 三种模式别背概念，要看场景

#### SSG：静态生成
适合：

- 文章详情页
- 专题页
- 不常变的营销页面
- 需要 SEO 的内容页

优点：

- 速度快
- SEO 友好
- 部署简单

缺点：

- 数据更新后需要重新构建或增量更新
- 不适合内容每分钟都变的场景

#### SSR：服务端渲染
适合：

- 首页需要实时内容
- 内容更新比较频繁
- 需要根据请求动态生成页面

优点：

- 每次请求拿到最新数据
- SEO 也不错

缺点：

- 服务端压力更大
- 响应速度受后端和网络影响

#### CSR：客户端渲染
适合：

- 交互复杂、SEO 不重要的页面
- 登录后个人中心
- 筛选器很多的后台界面

优点：

- 交互灵活
- 前后端分工清楚

缺点：

- 首屏内容可能慢
- SEO 弱

### 4.2 在本项目里的推荐选择

我们这个内容型小项目可以这样配：

- **文章列表页**：SSG 或 SSR
- **文章详情页**：SSG 优先，内容更新频繁再考虑 SSR
- **专题页**：SSG
- **搜索页**：CSR
- **关于页**：SSG

这样搭配，基本就符合“内容优先、交互次之”的思路。  
尤其是详情页和专题页，它们往往是搜索入口页，越早拿到内容越好。

### 4.3 做完项目后再回头看，结论会更清楚

你把一个内容站真的做一遍，就会发现渲染模式不是玄学，而是取舍：

- 文章和专题，重点是收录和首屏，SSG 最顺手
- 搜索和筛选，重点是交互，CSR 更自然
- 少数实时更新的内容，SSR 才更稳

这也是 Next.js 的强项：**同一个项目里，不同页面可以有不同渲染策略**。  
你不用整站一个模式梭到底，灵活得多。

### 4.4 常见误区

- 不是所有页面都要 SSR
- 不是一有接口就必须客户端请求
- 不是 Next.js 就一定比纯 React 更快
- 不要为了“听起来高级”而乱选渲染方式

**老赵提醒：**  
渲染模式选错，比没选还麻烦。内容站上来就 CSR，等于自己把搜索引擎入口堵了一半；后台系统硬上 SSG，又容易把更新流程搞复杂。别乱上，先看场景。

### 老赵式总结

SSR、SSG、CSR 不是谁比谁高级，而是谁更适合当前页面。  
**什么时候该用 Next.js？** 当项目里需要同时处理内容展示、SEO、首屏速度和局部交互时，Next.js 可以让你灵活选渲染方式。  
**什么时候别乱上？** 如果压根不需要这些能力，只是一个简单交互页，那就别把问题复杂化。

---

## 五、API Routes、图片与静态资源在项目中的实际应用：把前后端这层也串起来

### 5.1 API Routes 适合做什么

在这个小项目里，API Routes 很适合承担三类任务：

- 返回文章列表
- 返回文章详情
- 返回专题聚合数据

比如你可以有这些接口：

- `/api/posts`
- `/api/posts/[slug]`
- `/api/topics/[slug]`

它的好处是，前端页面和数据接口能在一个项目里先跑通。  
对练手来说，这特别省事；对小团队来说，也能减少一开始的上下文切换。

### 5.2 为什么内容站适合先用 API Routes 做原型

内容站最怕的不是“没有接口”，而是“页面、接口、数据结构三边都没对齐”。  
先用 API Routes 跑通原型，你能快速验证：

- 路由设计对不对
- slug 是否好用
- 列表和详情的数据字段是否统一
- 页面加载顺序是否合理

等整个链路稳定了，再把接口迁到真正的后端也不迟。

### 5.3 图片和静态资源别拖后腿

内容型站点里，图片和静态资源出现得特别频繁：

- 文章封面
- 作者头像
- 专题头图
- 站点 logo
- 分享卡片图

这时候要注意两点：

1. 图片要统一尺寸和策略，别让大图把首屏拖慢
2. 静态资源要集中管理，别散落在各处不好维护

如果资源太散，后面改版会特别痛苦。  
老赵见过不少项目，功能做得挺全，但 logo、封面、默认图东一张西一张，最后维护起来跟捡拼图一样。

### 5.4 API、资源和页面之间的关系

你可以把它理解成三层：

- **页面层**：负责展示和路由
- **接口层**：负责取数据
- **资源层**：负责图片、图标、静态资产

这三层分清楚了，项目就不会乱。  
内容站不是页面越多越好，而是结构越清楚越好。

### 老赵式总结

API Routes 和静态资源处理，都是在帮你把“内容站的基本功”打扎实。  
**什么时候该用 Next.js？** 当你希望前端页面、接口原型、页面路由在一个项目里快速闭环时，Next.js 很省心。  
**什么时候别乱上？** 如果后端接口已经很成熟，前端只是纯展示，而且没有页面级路由和 SEO 压力，那就别为了“全家桶”增加复杂度。

---

## 六、SEO 落地检查：这个项目到底有没有内容站的样子

### 6.1 SEO 不是最后一层装饰

做完这个项目，你要检查的不是“页面能不能打开”，而是“页面像不像一个能被搜索到的内容站”。

重点看这些：

- 标题是否准确
- 描述是否清晰
- URL 是否语义化
- 文章正文是否直接可见
- 图片是否有 alt
- 内链是否合理

### 6.2 一个内容站最容易漏掉的地方

很多人项目做到最后，页面是有了，数据也出来了，但还是不像内容站。原因往往很简单：

- 列表页没有摘要，只有标题
- 详情页内容包得太深
- 头图没有处理
- 页面标题全是“详情页”
- 专题页只是列表堆砌，没有聚合价值

这些问题不是大 bug，但会直接影响用户感受和搜索引擎理解。

### 6.3 做完以后学到了什么

这个小项目做完，你应该能明确几件事：

1. Next.js 不是只会“比 React 多一个框架名”
2. 路由、数据、渲染、SEO 是连在一起的
3. 内容型站点非常适合 Next.js 的页面级组织方式
4. 同一套项目里可以同时使用 SSG、SSR、CSR
5. 页面设计先于编码，URL 设计先于接口堆砌

### 老赵式总结

SEO 这事，别等上线前才想起来补。它从页面组织、渲染模式、资源管理开始就得一起考虑。  
**什么时候该用 Next.js？** 当你的项目确实要面向搜索、面向内容曝光、面向页面级访问时，Next.js 很值。  
**什么时候别乱上？** 如果页面不需要被检索，也不讲首屏内容，那就别把 SEO 和 Next.js 一起硬绑，能省就省。

---

## 七、项目收尾复盘：这套方案到底值不值

把这个内容型小项目做完后，老赵建议你别急着继续加功能，先回头复盘四件事：

### 7.1 页面结构是否清楚

- 列表页、详情页、专题页职责是不是分开了？
- 有没有哪个页面被你写成了“大杂烩”？
- URL 是否一眼能看懂？

### 7.2 数据链路是否完整

- 列表到详情的 `slug` 是否打通？
- 专题页聚合逻辑是否明确？
- API 和页面字段是否统一？

### 7.3 渲染选择是否合理

- 内容页是不是优先用了 SSG？
- 搜索页是不是交给了 CSR？
- 是否有页面被你为了“保险”乱上了 SSR？

### 7.4 SEO 和资源处理是否到位

- 标题、描述、图片、静态资源有没有做基本整理？
- 页面是不是具备内容站该有的样子？

这四项如果都过关，说明你不仅“写出了一个项目”，而且真的把 Next.js 的关键能力串起来了。

### 老赵式总结

这一章真正想让你记住的，不是某一个 API，而是整套判断方式：**页面怎么分、数据怎么来、渲染怎么选、SEO 怎么落地。**  
**什么时候该用 Next.js？** 当你做的是内容型站点、营销站、知识库、文章系统，或者任何“页面有层级、内容要收录、首屏要稳定”的项目，Next.js 很合适。  
**什么时候别乱上？** 当项目只是一个简单工具、纯交互表单、页面很少、SEO 没意义，别为了框架而框架。能用更轻的方案解决，就别给自己加戏。

学 Next.js，核心不是记一堆名词，而是学会判断：**这个页面该怎么组织，这个数据该怎么来，这个渲染该怎么选。**  
你把这套思路跑通了，Next.js 才算真正开始用起来。

# 第11章：部署、复盘与选型建议，学完之后怎么真正上手

学到这里，Next.js 的核心能力你基本已经摸清了：路由怎么组织、页面怎么渲染、数据怎么拿、接口怎么写、图片怎么处理、SEO 怎么照顾。  
但真正把技术落到项目里，最后一步不是“会写”，而是“能上线、能维护、能判断值不值得用”。

这一章，我们把前面学过的东西收个口：**怎么部署、上线前看什么、上线后查什么，以及什么项目适合 Next.js，什么场景别硬上。** 这才是全栈开发里最值钱的判断力。

## 一、基础部署思路：先想清楚你把代码跑到哪里

Next.js 的部署不用一开始就想太复杂，先抓住一个朴素逻辑：

1. 本地开发用 `next dev`
2. 正式上线前执行构建
3. 把构建产物放到服务器或平台上运行
4. 验证路由、接口、静态资源和 SEO 是否正常

### 1. 构建到底在干什么

构建这一步，本质上是把开发阶段的代码整理成可上线的产物。它会检查编译、生成生产环境资源，并准备好服务端渲染、静态页面和接口路由。

所以，**构建能不能通过，基本就是一次上线前体检。**  
如果构建不过，先修问题，别急着发版。

对于内容站、官网、文章详情页这类项目，构建通过还不够，还要看页面是否能正确预渲染，静态资源路径有没有问题，动态路由有没有漏页。因为这类站点上线后，首屏就是门面，首屏一翻车，体验立刻掉档。

### 2. 发布流程怎么理解

不管是传统服务器还是托管平台，流程都差不多：

- 拉取最新代码
- 安装依赖
- 配置环境变量
- 执行构建
- 启动生产服务
- 访问站点验收

展示类项目重点看首屏、收录和图片样式；业务类项目重点看登录、接口和数据流转。

### 3. 环境变量、构建产物和运行环境要对齐

上线翻车，很多时候不是业务代码错了，而是**环境变量、构建方式、运行环境**没对齐。

开发和生产环境通常不是一套配置，比如：

- 本地接口地址
- 线上接口地址
- 第三方登录密钥
- 数据库连接信息

这些都不要写死在代码里，要交给环境变量管理。上线前最重要的是确认：**线上变量已经配齐，而且名字和代码读取一致。**

常见错误包括：

- 本地能跑，线上接口全挂了
- 某些变量只在开发环境配置了，生产环境漏了
- 把敏感信息直接写进前端代码

如果是内容管理站点，还可能有 CMS 或后端接口环境，这时别只看首页，列表页、详情页、管理接口都要确认数据源正确。

### 4. 发布流程别跳步

建议固定一个简单流程：

- 本地跑通核心页面
- 执行构建命令
- 预览生产效果
- 检查环境变量
- 验证接口和资源
- 再正式发布

这套流程看起来朴素，但能挡住一大半低级错误。

### 老赵提醒

部署不是“最后点一下发布”这么简单。你得先判断项目是偏静态、偏内容，还是偏交互、偏接口。**Next.js 很适合把这些能力揉在一起，但如果只是纯展示页，别为了技术先进硬上复杂方案。**

---

## 二、上线后常见检查项：别只看首页打开了没有

网站上线后，最怕的不是“打不开”，而是“看起来能打开，实际上暗伤一堆”。

### 1. 路由是否正常

先检查这些点：

- 首页能不能打开
- 子页面能不能直接访问
- 动态路由是否正确
- 刷新后会不会 404
- 页面跳转是否符合预期

Next.js 的路由很方便，但上线后还是要看生产环境是否按预期工作。动态路由尤其容易在部署后因为路径配置、重写规则或服务器设置出问题。

比如文章站里 `/posts/hello-nextjs` 这种详情页，用户刷新后必须还能直接访问。否则搜索引擎和用户体验都会受影响。

### 2. 静态资源和图片是否正常

继续看：

- 图片能不能加载
- CSS、JS 是否正常引用
- `public` 目录资源能不能访问
- 相对路径有没有写错

如果页面能开，图片裂了或者样式丢了，体验会立刻变差。内容型站点尤其明显，图文页资源一挂，整个页面观感就废了。

Next.js 的图片处理能力很好，但上线时依然要检查：图片有没有压缩，远程域名有没有放行，静态资源路径是否在生产环境正确解析。

### 3. SEO 有没有问题

如果是内容站、文章站、官网、产品介绍页，就一定要看 SEO：

- 页面标题是否正确
- 描述信息是否完整
- 重要内容有没有首屏输出
- 页面是否更容易被搜索引擎理解

Next.js 常被用在内容型站点里，很大原因就是它在 SEO 和渲染模式上更灵活。但前提是你真的把基础项做对。标题乱写、内容全靠接口后渲染、首屏空白，这些问题照样拖后腿。

### 4. 接口是否可用

如果项目里有 API Routes，或者前端要请求后端接口，上线后务必检查：

- 接口返回是否正常
- 跨域是否处理好
- 登录态是否失效
- 参数传递是否正确
- 错误提示是否友好

不要只测成功路径，失败路径也要看。API Routes 很适合做轻量接口，比如表单提交、简单聚合数据、转发请求，但上线后仍要确认生产环境配置正确。

### 老赵提醒

上线检查不是“看一眼就行”，而是按清单扫一遍。**Next.js 适合做完整站点，但也正因为它覆盖面广，你更不能只盯着一个页面。**

---

## 三、什么项目适合 Next.js：别盲目上，先看场景

这是最关键的一问：**什么时候该用 Next.js？**

### 适合用 Next.js 的项目

通常这几类项目很合适：

- 内容型站点：博客、文档站、媒体站、专题页
- 需要 SEO 的官网：企业站、产品介绍页、活动落地页
- 需要前后端结合的项目：前台页面加接口、页面加登录、页面加数据管理
- 既要首屏性能，又要后续交互的业务站点
- 想统一页面、接口、资源、渲染方案的中小团队项目

它们的共同点是：**页面不仅要能交互，还要能被更好地展示、收录和维护。**

### 适合 Next.js 的一个典型案例

比如你要做一个“产品知识库 + 文章中心”网站：

- 首页展示热门文章和产品入口
- 文章详情页要求 SEO 好
- 后台接口负责文章列表和标签数据
- 图片很多，不能乱糊
- 用户要能从列表页跳到详情页

这类项目用 Next.js 很顺手：页面路由负责结构，动态路由负责详情页，数据获取负责列表和内容，API Routes 处理轻量接口，SEO 也能顺便做好。

### 老赵提醒

如果项目天然就是“内容驱动 + 页面多 + 需要收录”，Next.js 往往很合适。**这时候用它，不是装技术范儿，而是确实省心。**

---

## 四、什么场景别乱上 Next.js：工具合适，别拿来拧螺丝

那什么时候别乱上？

### 不太适合的场景

- 只是一个极简单页展示
- 纯后台管理系统，几乎不关心 SEO
- 业务逻辑完全由现成后端页面承担，前端只是薄薄一层
- 团队对 React 都还没熟，先要把基础交互跑稳
- 项目节奏特别快，但团队又没有时间统一约定路由和数据模式

不是说这些场景不能用，而是**不一定值得上完整的 Next.js 套路。**

### 为什么要克制

引入 Next.js 后，你得到的不只是更强的页面能力，还有：

- 路由组织
- 渲染模式选择
- 数据获取策略
- 环境变量管理
- 部署和构建流程
- SEO 和资源处理

这些都能帮你，但也都要维护。项目很小、目标单一时，反而显得重。

比如公司内部管理台，核心就是表格、筛选、编辑、提交，几乎不考虑搜索引擎收录。这个时候要先看团队熟悉什么、后端接口是否现成、部署方式是否简单。能不能用 Next.js 不是重点，**值不值得为它增加一整套生产心智**，才是重点。

### 老赵提醒

技术选型不是“越强越好”，而是“刚刚好最好”。**Next.js 很强，但别把每个项目都当内容站、官网或者全栈平台来做。**

---

## 五、学完以后怎么判断值不值：给自己一个落地决策法

如果你现在手上刚好有个新项目，不妨按这个顺序问自己：

1. 这个项目需要 SEO 吗？
2. 这个项目是不是页面和数据都比较多？
3. 我们是不是希望前后端在同一个项目里更顺地协作？
4. 上线后是否需要稳定处理路由、资源和接口？
5. 团队有没有能力把构建、部署、环境变量这些东西一起管起来？

如果前面三四个答案里有两个以上是“是”，那 Next.js 大概率值得考虑。  
如果答案大多是否，或者只是为了“听起来先进”，那就先别上，免得给自己加戏。

### 一个真实点的决策场景

比如你要做一个公司官网加博客系统：

- 官网页面要有 SEO
- 博客文章要能被搜索引擎收录
- 还要接一个简单的表单接口
- 未来可能要加活动页和详情页

这时候 Next.js 就很顺手，因为它能把页面、路由、渲染、接口和资源管理放在一套体系里。

但如果你只是做一个内部审批台：

- 主要是登录后操作
- 页面都是表格和表单
- 不需要收录
- 后端接口已经很完整

那你就得想清楚：Next.js 能用，但可能不是最省的。也许一个更轻的前端方案，或者沿用团队现有栈，会更稳。

---

## 六、全书老赵式总总结：什么时候该用，什么时候别乱上

学完这一整本，你可以记住一句话：

**Next.js 适合用在“页面多、内容多、要 SEO、要首屏体验、还想顺手把前后端衔起来”的项目里。**

它的核心价值不只是“React 的增强版”，而是把：

- 路由
- 渲染
- 数据获取
- API 接口
- 静态资源
- SEO
- 部署

这些原本分散的事情，尽量收进一套体系里。

但你也要知道，**如果项目很轻、很简单、纯管理后台、纯静态展示，或者团队还没准备好维护这套复杂度，就别急着上。**

### 你可以用这个判断法

问自己三个问题：

1. 这个项目需要 SEO 吗？
2. 这个项目是不是页面和数据都比较多？
3. 我们是不是希望前后端在同一个项目里更顺地协作？

如果三个问题里有两个以上答案是“是”，那 Next.js 大概率值得考虑。  
如果都是否，或者只是为了“听起来先进”，那就先别上，免得给自己加戏。

到这里，Next.js 的基础知识就真正闭环了。你不只是知道它能做什么，还应该知道：

- 上线前要检查什么
- 环境变量怎么管
- 构建和发布怎么理解
- 路由、资源、SEO、接口怎么验收
- 什么项目适合它，什么项目不适合它

真正成熟的开发者，不是见什么都上新框架，而是能清楚地说：**这个场景，用 Next.js 刚好；那个场景，别折腾。**

不是一套炫技方案，而是一套能落地的判断。
