# 第1章：项目初始化与 CRA 基础搭建

## 开篇引入：先把项目跑起来，再谈“写得漂亮”

很多同学学 React 的时候，前面都挺顺：会写组件、会写 JSX、会用 `useState`，感觉自己已经“懂 React”了。可一到真正做项目，就会卡在最基础的地方：项目怎么建、目录怎么分、入口文件在哪、开发命令怎么跑、出错了去哪看。

这章老赵不急着带你写功能，先做一件最重要的事：**把一个基于 CRA 的 React 项目从零跑起来，并建立起对整个工程的第一印象。**  
因为真实项目里，代码能力只是其中一部分，工程能力、组织能力、排错能力，才是你从“会写组件”走向“会做项目”的关键台阶。

本书后面会围绕**同一个核心项目**展开。你可以把它理解成一个“内容管理类”的前端应用：有首页、有列表页、有详情页、有表单页，能做数据展示、搜索筛选、新增编辑、路由切换、状态反馈和最终打包上线。  
后面每一章，都是在这一个项目上继续往前搭，不会今天一个任务管理，明天一个文章列表，后天又换成商品管理。**主线只保留一个，咱们就顺着它一路做到底。**

### 本书统一开发路线图

为了让你一开始就有全局感，老赵先把后面的路子给你画清楚：

1. **项目初始化**：用 CRA 把工程跑起来，搞定基础目录和开发环境  
2. **页面布局**：先搭出页面骨架，让项目“长得像个产品”  
3. **组件拆分**：把页面拆成可复用组件，建立 React 组件设计思维  
4. **数据请求**：接入接口，开始让页面有真实数据  
5. **状态管理基础**：用 `useState` 管住页面状态，搞清楚数据怎么流  
6. **表单与交互**：做搜索、筛选、提交、编辑这些常用动作  
7. **路由组织**：用基础路由把多个页面串起来  
8. **异步处理**：处理加载中、失败、重试这些真实场景  
9. **常见问题**：把开发过程中最容易踩的坑收拾干净  
10. **打包与上线**：完成构建、部署思路和发布前检查

你先不用急着把这些都学完，先记住一件事：**这本书不是零散知识点堆叠，而是围着一个完整项目一步步搭出来。**

## 一、项目目标与最终成品预览：我们到底要做什么？

### 1.1 先明确项目边界，别一上来就乱写

做项目最怕的不是不会写，而是一开始没有目标。没有目标就会导致页面越做越多、组件越拆越碎、状态到处乱放，最后自己都不知道项目在干嘛。

所以初始化阶段先把项目目标说清楚：

- 这个项目要解决什么问题
- 核心页面有哪些
- 每个页面展示什么信息
- 用户会做哪些操作
- 哪些数据来自接口，哪些是本地状态

简单说，就是**先设计项目轮廓，再动手敲代码**。这样后面每写一个组件、每加一个接口、每做一个交互，你都知道它在整个项目里扮演什么角色。

### 1.2 按本书语境的项目成品预览

为了让后面章节有统一落点，我们把这个 CRA 项目设定成一个典型的前端实战应用，它至少要具备这些能力：

- **首页**：展示概览信息、入口导航、基础布局
- **列表页**：展示数据列表，支持筛选、搜索、分页或加载更多
- **详情页**：查看单条数据的完整信息
- **表单页**：新增或编辑数据
- **通用交互**：加载中、空状态、错误提示、按钮反馈
- **路由切换**：不同页面之间自由跳转
- **请求能力**：从后端接口获取真实数据
- **部署能力**：开发完成后能正常打包上线

你先不用纠结项目具体叫啥，关键是：**它要足够完整，能把 React 的基础能力串起来。**  
后面你会发现，组件、状态、请求、路由、异步处理，这些概念单独看都不难，难的是放进真实项目后怎么组织顺。

### 1.3 一个实战判断标准

如果你现在写的只是单个组件示例，那叫练习；如果你能从项目初始化一路做到页面、请求、状态、路由、部署，那才叫项目实战。

判断标准很简单：

- 有没有明确目录结构
- 有没有统一入口
- 有没有真实页面流转
- 有没有接口与数据流
- 有没有最终打包产物

这几项能串起来，你的 React 学习就已经从“语法层”迈进“工程层”了。

## 二、CRA 项目初始化流程：怎么把开发环境跑通？

### 2.1 CRA 在本书里的角色

CRA 可以理解成一套“开箱即用”的 React 项目脚手架。它的价值不是帮你写业务，而是帮你快速把工程骨架搭起来，让你把精力放在页面和逻辑上。

在本书语境里，CRA 的作用主要有三点：

1. 快速创建 React 工程
2. 提供本地开发环境
3. 提供打包构建流程

对初学者来说，CRA 最大的好处就是省心。你不用一上来就折腾 webpack、Babel、入口配置，而是先把 React 项目跑通，尽快进入“做页面、做功能”的状态。

### 2.2 初始化步骤

常见初始化流程如下：

```bash
npx create-react-app my-react-project
cd my-react-project
npm start
```

如果你用的是 `yarn` 或 `pnpm`，命令会略有差异，但思路一致：

- 创建项目
- 进入项目目录
- 启动开发服务

启动后，浏览器通常会打开本地开发地址。如果看到 React 默认页面，说明第一步成功了：**工程已经活了。**

老赵提醒一句：第一次初始化别急着删文件、改结构，先确保项目从默认状态能稳定启动。先确认“发动机正常”，再考虑“怎么改装”。

### 2.3 常用脚本命令先记住

CRA 项目最常用的命令，至少要熟：

```bash
npm start
npm run build
npm test
npm run eject
```

重点先知道它们分别干什么：

- `start`：启动开发环境，边写边看效果
- `build`：打包生产环境代码
- `test`：跑测试相关流程
- `eject`：暴露底层配置，通常不建议轻易用

其中最重要的是 `start` 和 `build`。前者服务开发阶段，后者服务上线前检查。很多人开发时只会 `npm start`，到最后打包才发现问题，这就属于平时没练，临场才慌。

### 2.4 初始化阶段的判断标准

一个初始化成功的项目，至少满足：

- 能正常安装依赖
- 能正常启动开发服务器
- 浏览器能打开默认页面
- 修改文件后能热更新
- 没有基础报错信息

如果这几个点没过，后面的组件、状态、请求都别急着写。先修环境，后做业务，这是老规矩。

## 三、CRA 项目结构拆解：文件都该放哪？

### 3.1 先认识 `public` 和 `src`

CRA 创建好项目后，最核心的两个目录就是：

- `public`
- `src`

你可以把它们理解成两个不同的职责区域。

#### `public`
放的是静态入口壳子和不经过打包处理的资源，常见文件包括：

- `index.html`
- 图标类资源
- 一些静态文件

这里面最关键的是 `index.html`。它通常只提供一个 HTML 骨架和一个挂载点，React 应用就是从这里“接”进去的。你可以把它理解成门面和底座，页面真正的内容并不是写在这里，而是等着 `src` 里的 React 代码渲染上来。

#### `src`
放的是我们真正写 React 代码的地方，通常包括：

- 组件
- 页面
- 样式
- 请求封装
- 工具函数
- 路由配置

简单理解：`public` 更像项目外壳，`src` 更像项目大脑。真正的业务开发，基本都在 `src` 里展开。

### 3.2 入口文件是怎么串起来的？

CRA 项目里最关键的概念之一，就是入口文件链路。React 应用不是凭空出现的，而是从 HTML 里的挂载点开始，再由入口文件把组件渲染进去。

常见链路是：

- `public/index.html` 提供页面挂载容器
- `src/index.js` 或 `src/index.jsx` 负责入口渲染
- `src/App.js` 是应用根组件
- 其他页面和组件由根组件继续组织

你不必一上来把底层细节都背熟，但必须知道：**项目入口、根组件、页面组件之间，是一条自上而下的装配链。**  
这条链路一旦清晰，后面做页面布局、路由、数据请求时，脑子里就不会乱。

### 3.3 推荐的基础目录规划

为了后面章节好展开，老赵建议你从第一天开始就有目录意识。一个常见而且好维护的结构可以参考：

```text
src/
  assets/
  components/
  pages/
  services/
  utils/
  styles/
  App.js
  index.js
```

各目录职责大致如下：

- `assets`：图片、字体、图标等静态资源
- `components`：可复用组件
- `pages`：页面级组件
- `services`：接口请求相关
- `utils`：通用工具函数
- `styles`：全局样式或公共样式

如果后面要做请求封装，就放进 `services`；如果要做日期格式化、数据处理，就放进 `utils`。职责清楚，后面改起来省劲。

### 3.4 目录结构背后的原则

目录不是越多越好，关键是**职责清晰**。  
如果所有文件都堆在 `src` 根目录里，后面一定会乱；如果一开始就按职责分区，后面加路由、加请求、加状态时就很顺。

老赵的建议是：**先小而清，再逐步扩展。**  
不要为了显得“专业”硬拆一堆目录，结果自己都不知道文件该往哪放。

## 四、基础开发规范：怎么让项目越做越顺？

### 4.1 文件命名要统一

项目一开始就要统一命名习惯，不然后面协作和维护会很痛苦。

建议遵循这些基本原则：

- 组件文件名用大驼峰：`Header.js`、`UserList.js`
- 页面文件名尽量清晰：`HomePage.js`、`DetailPage.js`
- 工具函数和请求文件命名语义明确：`request.js`、`formatDate.js`
- 不要随便起 `test1.js`、`new2.js` 这种名字

命名这件事看起来小，其实特别影响项目寿命。文件名清楚的项目，哪怕隔几周再回来接着写，你也能快速找到东西。

### 4.2 组件设计先从“职责单一”开始

初始化阶段，很多人喜欢把所有东西写进一个大页面里。短期看着快，长期看着乱。

老赵建议你记住一句话：

> 一个组件只负责一件事，页面负责组合，组件负责复用。

比如：

- 页面组件负责组织结构
- 列表组件负责渲染列表
- 搜索框组件负责搜索交互
- 按钮组件负责通用按钮行为

这样后面做父子通信、状态传递时也更清楚。组件设计一旦合理，很多后续问题都会自然变简单。

### 4.3 样式和资源管理要趁早规范

刚开始写项目的时候，样式最容易乱。建议至少建立以下意识：

- 全局样式和局部样式分开
- 页面样式尽量跟页面走
- 公共样式抽离出来，不要重复写
- 图片和图标统一放资源目录

如果一开始就没有边界，后面页面一多，样式冲突、类名重名、布局混乱这些问题就会一起冒出来。项目不是“能跑就行”，而是“能持续改”。

### 4.4 一个实用的检查清单

初始化时，你可以拿这份清单自检：

- [ ] 项目能启动
- [ ] 目录职责清楚
- [ ] 文件命名统一
- [ ] 页面和组件分层明确
- [ ] 资源文件有固定位置
- [ ] 入口链路清晰
- [ ] 后续功能有可扩展空间

这份清单不用写进代码里，但要写进脑子里。以后你每开一个新项目，都可以拿它过一遍。

## 五、可复制的代码思路：照着搭，先把骨架立住

老赵一直强调，学项目实战，别只听概念，得有能直接照着做的步骤。第 1 章最适合把“基础模板”搭出来，后面所有章节都能在这套骨架上继续扩展。

### 5.1 初始化命令清单

你可以先按这个顺序来：

```bash
npx create-react-app my-react-project
cd my-react-project
npm start
```

如果你的团队或个人习惯使用其他包管理器，也可以保持一致，但不要一会儿 npm、一会儿 yarn、一会儿 pnpm，环境越统一，越少出幺蛾子。

### 5.2 基础目录创建顺序

项目启动后，先别急着写业务，建议先把 `src` 里的骨架补上：

```text
src/
  assets/
  components/
  pages/
  services/
  utils/
  styles/
```

然后按职责把第一批文件放进去：

- `src/index.js`
- `src/App.js`
- `src/pages/HomePage.js`
- `src/components/` 下的通用组件
- `src/services/request.js`
- `src/styles/global.css`

### 5.3 一个最小可用的开发模板

你可以先把项目理解成三层：

- **入口层**：`index.js` 负责挂载应用
- **根层**：`App.js` 负责组织全局结构
- **页面层**：`pages/` 里放具体页面

后面无论是布局、组件拆分、请求封装，还是路由和状态管理，基本都围绕这三层往下长。先把这三层拎清楚，项目就不会散。

## 六、初始化阶段的排坑经验：别让小问题拖慢大节奏

### 6.1 依赖安装报错怎么办？

刚装 CRA 项目时，依赖问题非常常见，尤其是：

- 网络不稳定
- Node 版本不匹配
- 包管理器缓存异常
- 镜像源设置有问题

遇到这类问题，先别急着重装十次。你可以按这个顺序排：

1. 看报错信息，确认是安装失败还是启动失败
2. 检查 Node.js 版本是否符合项目要求
3. 清理缓存后重试
4. 删除 `node_modules` 和锁文件后重新安装
5. 检查网络和镜像源

排错的核心不是“手快”，而是“定位准”。很多时候你以为是 React 的问题，其实只是某个依赖没装上。

### 6.2 启动报错先看哪？

启动报错时，优先看三处：

- 命令行输出
- 浏览器控制台
- 代码里最近改动的文件

很多时候问题不是项目本身坏了，而是你改了某个文件，引入了语法错误、导入错误、路径错误。  
所以排错不要凭感觉，要先定位。

老赵经验里有一句很实用的话：**报错不怕，怕的是看不懂报错就开始乱改。**

### 6.3 环境差异要提前有心理准备

同一个项目，在不同电脑上可能表现不一样，常见原因有：

- Node 版本不同
- npm/yarn/pnpm 使用不同
- 系统权限不同
- 编辑器自动修复规则不同

因此，项目初始化阶段最好统一环境基线。哪怕你一个人做项目，也建议尽量保持版本稳定，不要今天一个环境，明天另一个环境。

### 6.4 初始化阶段的常见误区

最典型的误区有三个：

#### 误区一：项目还没跑通就急着写业务
这会导致问题叠加，最后不知道是环境错了还是代码错了。

#### 误区二：不看目录结构，直接往里塞文件
结果后面功能多了，根本找不到入口。

#### 误区三：报错后只会重启
重启不是排错，重启只是碰运气。

真正靠谱的做法，是先判断问题类型，再逐步缩小范围。项目越往后走，这种能力越重要。

## 七、老赵经验总结：先把工程跑顺，再谈功能开发

这一章你最该记住的一句话，就是：

> **先把工程跑顺，再谈功能开发。**

为什么这么说？

因为项目实战不是比谁一开始写得快，而是比谁能稳定地把项目做完。一个真正能落地的 React 项目，从来不是靠“某个组件写得很炫”完成的，而是靠这些基本动作串起来的：

- 初始化工程
- 搞清目录结构
- 统一开发规范
- 跑通开发环境
- 提前预判排坑点
- 给后续页面、组件、请求、状态留空间

### 7.1 本章的行动建议

你现在就可以做三件事：

1. 用 CRA 创建一个新项目并成功启动
2. 按本章建议整理 `src` 目录骨架
3. 观察默认项目结构，尝试说清楚每个目录和文件的职责

别小看这三步。你能把它们做顺，后面的页面布局、组件拆分、数据请求，才有真正的落脚点。

### 7.2 为后续章节埋下的伏笔

这章只是起点，后面我们会继续把这个项目往下搭：

- 下一章做页面布局，让项目真正有“样子”
- 再往后拆组件，建立 React 组件设计思维
- 接着做数据请求、状态管理、表单交互
- 然后接入路由、处理异步、排查常见问题
- 最后完成打包和上线

你会发现，真正的项目能力不是“知道很多概念”，而是**能把这些概念顺着一个项目串起来**。  
这就是本书要带你完成的转变。

# 第2章：页面布局与项目骨架搭建

## 开篇引入：先把“房子骨架”搭起来

上一章我们已经把 CRA 项目跑起来了，开发环境和基础依赖都就位了。接下来很多同学会急着写功能，但在真实项目里，**最先要做的不是请求，也不是交互，而是先把页面骨架搭稳**。

你可以把它理解成盖房子：先定客厅、卧室、厨房的位置，再决定门窗怎么开，最后才往里摆家具。React 项目也是一样，**页面布局不是为了先好看，而是为了让后面的组件、状态、请求、路由都能顺着结构落地。**

这一章我们围绕同一个核心项目——**任务管理系统**——来搭页面骨架。后面你会看到，头部、侧边栏、主内容区、列表区，都会对应真实业务区域。先别管数据，先把页面“站稳”，后面会轻松很多。

## 一、页面整体结构怎么拆？先定区域，再谈细节

### 1.1 为什么要先拆结构

很多人一上来就纠结按钮放哪、卡片怎么美化，结果页面越写越乱，最后连组件该放哪都说不清。原因很简单：**太早关注细节装饰，却没先解决结构组织。**

真实项目里，布局是页面逻辑的地基。更稳的做法是：**先按业务区域切页面，再按区域填内容。**

对于任务管理系统，我们可以先把页面抽成三层：

1. **全局框架层**：头部、侧边栏、内容区，负责公共外壳。
2. **页面业务层**：任务列表页、详情页、编辑页，负责具体业务差异。
3. **页面内容层**：筛选区、表格区、统计区、空状态区，承接交互和数据展示。

先想清楚页面有哪些功能区域，它们之间是什么关系，再动手写代码。

### 1.2 一个可复制的结构思路

```jsx
<div className="app-shell">
  <header className="app-header">顶部导航</header>
  <div className="app-body">
    <aside className="app-sider">任务分类菜单</aside>
    <main className="app-main">
      <section className="page-toolbar">筛选区</section>
      <section className="page-content">主内容区</section>
    </main>
  </div>
</div>
```

这段结构先不管好不好看，重点是**角色分清楚**：头部、侧边栏、主内容、工具栏各归各位。角色分开了，样式、状态、数据、路由都容易接。

如果一开始把所有内容塞进一个容器里，后面常见问题就是：

- 想改头部，结果动到了列表区
- 想加筛选栏，结果把主内容挤乱
- 想接路由，发现侧边栏和主区域没有边界

所以，先分区，再填充，这是最稳的起点。

### 1.3 判断标准：结构是否拆对了

你可以用这几个标准检查：

- 顶部是否独立成块，方便后面放用户信息、退出按钮
- 侧边栏是否和主内容区分开，方便后面接路由
- 主内容区是否能容纳筛选、表格、详情等不同内容
- 页面是否能在不改整体结构的情况下替换内部业务

还有一个很实用的方法：把“任务列表页”换成“任务详情页”，看页面结构能不能继续用。能继续用，说明抽象得不错；不能继续用，说明骨架还不够灵活。

## 二、静态布局怎么做？先框架，后内容

### 2.1 为什么先做静态布局

布局阶段最忌讳一边做数据一边改结构，这样最容易返工。今天为了一个按钮改页面，明天为了一个表格字段推翻整体，最后页面还没进入业务，代码已经乱了。

更稳的顺序是：

1. 先把页面框架用静态内容搭出来  
2. 再替换成真实组件  
3. 最后再接请求和交互

静态布局的作用，就是先确认页面比例、区域关系和视觉层级。骨架稳了，再做功能就不会拧巴。

### 2.2 静态布局的操作步骤

#### 第一步：先用假数据和占位文本

先写顶部项目名、用户信息、侧边栏菜单、主区域标题和内容块，不用马上绑接口，先把位置摆对。

#### 第二步：先做页面比例

先确认：

- 头部高度
- 侧边栏宽度
- 主内容区是否自适应
- 页面内容是否能滚动

这些决定页面骨架是否正常。比例不合理，后面再美化也救不回来。

#### 第三步：再补业务模块

列表区先放一个假的表格盒子，表单区先放几个输入框样式，后面再替换成真正组件。关键是：**先让页面在结构上成立，再让它在业务上成立。**

### 2.3 一个典型的静态布局示例

```jsx
function HomePage() {
  return (
    <div className="page">
      <div className="page-header">
        <h1>任务管理系统</h1>
        <div className="user-info">欢迎，老赵</div>
      </div>

      <div className="page-layout">
        <div className="sidebar">
          <div className="menu-item active">任务列表</div>
          <div className="menu-item">新增任务</div>
          <div className="menu-item">系统设置</div>
        </div>

        <div className="content">
          <div className="toolbar">这里放筛选条件</div>
          <div className="list-panel">这里放列表内容</div>
        </div>
      </div>
    </div>
  );
}
```

虽然还没接数据，但项目雏形已经出来了。很多项目真正的第一步，就是先把这个“可以开发”的状态搭起来。

### 2.4 常见误区

这一阶段常见坑有四个：

- 一上来就做复杂样式，结果结构混乱
- 没有统一主内容区宽度，页面东一块西一块
- 所有内容都堆在一个组件里，后面难拆
- 只顾着“像”，不关心“后面能不能接功能”

老赵提醒你一句：**布局阶段不是做 PPT，它是给项目定骨架。**

## 三、公共样式怎么管？别让页面各写各的

### 3.1 公共样式的目标是什么

页面一多，样式最容易失控。今天一个页面一套宽度，明天另一个页面又一套间距，最后整个项目像拼贴画。

所以在布局阶段就要建立最基础的样式规则：

- 全局宽度统一
- 基础间距统一
- 字体大小统一
- 主色和辅助色统一
- 常用容器样式统一

这不是为了好看，而是为了后面组件复用时不互相打架。

### 3.2 建议先定的几个基础变量

```css
:root {
  --primary-color: #1677ff;
  --text-color: #1f2937;
  --muted-color: #6b7280;
  --border-color: #e5e7eb;
  --page-bg: #f5f7fb;
}

.page {
  min-height: 100vh;
  background: var(--page-bg);
  color: var(--text-color);
}

.page-header {
  height: 64px;
  padding: 0 24px;
  display: flex;
  align-items: center;
  justify-content: space-between;
  background: #fff;
  border-bottom: 1px solid var(--border-color);
}
```

这种写法的好处很直接：以后改主题色只改一处，改页面底色也不用一个个找文件。

### 3.3 响应基础怎么考虑

这个阶段不必追求全端适配，但至少要有基本弹性：

- 主内容区尽量使用 `flex`
- 避免写死过多绝对宽度
- 列表区域可设置横向滚动或最小宽度
- 栅格区域保留基础换行能力

后台页面最容易出问题的往往不是头部，而是列表表格。提前给内容区留弹性，后面即使数据列多，也不会把页面撑爆。

## 四、项目资源怎么组织？别把东西全扔一起

### 4.1 为什么资源组织重要

项目做大后，图片、图标、样式、公共组件都会越来越多。你一开始不整理，后面找一个文件都费劲，改个图标都要翻半天目录。

所以在 CRA 项目里，布局阶段就要开始建立资源组织习惯。项目越小越该整理，因为成本最低。

### 4.2 推荐的目录思路

```bash
src/
  assets/
    images/
    icons/
  components/
    Layout/
    PageTitle/
    EmptyState/
  pages/
    TaskList/
    TaskDetail/
    TaskEdit/
  styles/
    global.css
    variables.css
```

这样分的好处很明显：

- `assets` 放静态资源
- `components` 放复用组件
- `pages` 放页面级内容
- `styles` 放公共样式

### 4.3 布局阶段先抽哪些资源

建议先抽这几类：

- 页面公共头部
- 页面标题区域
- 空状态提示
- 通用卡片容器
- 通用按钮区

如果一个模块在两个页面以上会复用，就值得提前抽出来。反过来，如果只是当前页面临时使用，先留在页面里也没问题，别为了“模块化”而模块化。

## 五、代码怎么拆才合理？哪些先写页面，哪些抽公共模块

### 5.1 布局阶段的拆分原则

这个阶段最重要的不是“拆得多”，而是“拆得对”。

记住一句话：

**页面里放变化大的，公共组件里放稳定复用的。**

页面级内容通常和当前业务强相关，比如筛选条件、标题、说明文案，先留在页面里。  
而那些多个页面重复出现的结构，比如标题栏、卡片容器、空状态提示，适合抽成公共组件。

### 5.2 建议留在页面里的内容

以下内容通常先留在页面文件中：

- 只属于当前页面的布局结构
- 本页面特有的标题和说明
- 当前页面专属的筛选条件
- 临时静态占位内容

这些东西变化快，先别急着抽。抽早了，后面还要反复改接口、改样式、改文案，反而增加维护成本。

### 5.3 建议提前抽公共模块的内容

这些内容更适合抽成组件：

- `PageHeader`：页面标题区
- `Card`：通用卡片容器
- `EmptyState`：无数据提示
- `SidebarMenu`：侧边栏菜单
- `Layout`：整体布局框架

这些组件的特点是结构稳定、复用概率高。尤其是 `Layout`，它会成为整个项目最基础的一层壳，后面很多页面都要挂在它下面。

### 5.4 一个实战拆分方式

任务管理页可以这样分：

- `Layout` 负责头部、侧边栏、主区域
- `TaskListPage` 负责任务列表页整体内容
- `FilterBar` 负责筛选条件
- `TaskTable` 负责列表展示
- `EmptyState` 负责无数据提示

这样拆之后，后面接 `useState`、`useEffect`、请求数据时，结构会非常顺，因为每个模块职责清楚，状态和数据归属也更明确。

### 5.5 可复制的代码思路

可以按这个顺序来搭：

1. 先写 `Layout`，把头部、侧边栏、主内容区定下来  
2. 再写 `TaskListPage`，把页面标题、筛选区、列表区摆出来  
3. 接着抽 `PageHeader`、`Card`、`EmptyState` 这类公共模块  
4. 最后补样式和占位内容，确认结构能复用

```jsx
function Layout({ children }) {
  return (
    <div className="app-shell">
      <header className="app-header">任务管理系统</header>
      <div className="app-body">
        <aside className="app-sider">任务分类菜单</aside>
        <main className="app-main">{children}</main>
      </div>
    </div>
  );
}

function TaskListPage() {
  return (
    <>
      <div className="page-toolbar">筛选条件</div>
      <div className="page-content">任务列表内容</div>
    </>
  );
}
```

这种写法先把“壳”和“内容”分开了，后面无论接组件、状态还是接口，都比较顺手。

### 5.6 常见误区

- 页面还没定型就疯狂拆组件，反复改文件
- 所有内容都放页面里，最后变成巨型文件
- 公共组件抽得太早，结果根本没复用场景
- 只看代码规整，不看业务是否顺手

组件拆分不是越碎越好，关键是让结构和业务对得上。拆得合理，后面做状态管理、父子组件通信、请求封装都会轻松很多。

## 六、布局阶段怎么为后面章节铺路？

这一章不只是把页面做出来，更重要的是给后面章节打地基。

### 6.1 为组件拆分铺路

你已经把页面区域分清楚了，后面做组件拆分时，就能顺着区域拆，不会东一块西一块。头部做成独立组件，侧边栏做成导航组件，主内容区再按功能拆成筛选、列表、详情几个模块。

### 6.2 为状态管理铺路

侧边栏菜单高亮、筛选条件、展开收起这些状态，后面都可以挂到对应的小组件里。布局清楚，状态就好放；布局混乱，状态也会乱。

### 6.3 为请求和路由铺路

任务列表页、任务详情页、任务编辑页后面会通过路由串起来。你现在把主内容区和导航区拆开，路由就能自然挂在主区域上；如果结构没拆开，后面组织路由会很别扭。

## 七、老赵经验总结：布局不是为了好看，而是为了后面组件和数据能落地

这一节我只提醒你一句：**布局阶段真正的价值，不是页面看起来像样了，而是后面的功能能顺着骨架长出来。**

做布局时，脑子里要提前想三件事：

1. **这个区域后面是不是会接数据**  
   会接数据的地方，最好单独成块，别混在大容器里。比如表格区、统计区、列表区，这些都应该独立出来。

2. **这个区域后面是不是会有交互**  
   会搜索、会切换、会展开的模块，早点拆开。因为它们后面大概率会挂 `useState`、`useEffect`，甚至会有表单和异步请求。

3. **这个区域会不会在别的页面复用**  
   会复用的东西，早点做成公共组件。不要等到第三个页面也要用时，才回头重构。

### 老赵给你的实战提醒

- 先搭骨架，再填业务，不要反着来
- 先定结构，再定样式，不要一上来就抠颜色
- 先考虑未来接数据的入口，再决定组件怎么拆
- 页面越早有层次，后面 `useState`、`useEffect`、路由和请求越好接

如果这一步做得好，后面你会发现：组件好拆，状态好放，请求好挂，路由也好接。

# 第3章：组件拆分与 React 组件设计

## 开篇引入：为什么“把页面拆成组件”是项目能不能做下去的分水岭

前两章我们已经把项目跑起来，也把页面的静态骨架搭好了。到了这一步，很多人会以为接下来就是往里填功能。真做项目才会发现，页面一复杂，问题马上就来：代码堆在一个文件里，改一个按钮要顺手看一堆逻辑；列表、筛选、弹窗、分页混在一起，职责不清；过几天自己回来看，都得怀疑是不是别人写的。

所以这一章先不急着加功能，先做一件更重要的事：**把页面拆成合理的组件，建立清晰的 React 组件设计思路。**

我们拿一个典型的任务管理页来练手。它通常会有：

- 顶部搜索框
- 筛选按钮
- 新增按钮
- 主体列表
- 操作弹窗
- 空状态或提示区

这些内容不能简单拼在一起，得先看职责，再看复用，最后决定怎么拆。组件拆得好，后面的 `useState`、`useEffect`、请求、路由都会顺很多；拆乱了，后面每加一个功能都像在拆炸弹。

---

## 一、从页面到组件的拆分原则：先按职责拆，再按复用拆

### 1.1 先问一个问题：这个区域是“干什么的”？

组件拆分最怕一上来就想“这个能不能复用”。其实第一步不是想复用，而是想职责。

一个页面通常可以先按职责分成三类区域：

- **信息展示区**：列表、卡片、详情块
- **交互操作区**：搜索框、筛选器、按钮组
- **流程承载区**：弹窗、表单、确认框

先把大页面切成几个功能块，再看每个块内部要不要继续拆。比如任务管理页里，顶部区域负责筛选和搜索，中间区域负责展示任务列表，弹窗负责新增和编辑任务。不要一开始就把“新增按钮”“搜索输入框”“任务列表项”“操作按钮”全塞进一个组件里，短期省事，长期就是灾难。

### 1.2 拆分的判断标准

老赵建议你用这三条来判断。

#### 标准一：职责是否单一
一个组件最好只负责一件事。比如：

- `TaskSearchBar` 负责输入和触发搜索
- `TaskList` 负责渲染列表
- `TaskModal` 负责新增/编辑任务

如果一个组件既管输入框，又管列表，又管弹窗，那就明显超载了。

#### 标准二：是否存在明显复用
如果某一块内容会在多个地方用到，比如按钮、弹窗、分页器、标签，就值得抽出来做通用组件。但别为了“看起来能复用”就硬抽，得是真的会重复出现。

#### 标准三：是否容易维护
判断拆分好不好，不是看名字多高级，而是看以后改起来累不累。好的拆分，是你以后想改搜索区，就只看搜索区；想改列表项，就只看列表项。

### 1.3 推荐的拆分顺序

在本书这个项目里，老赵建议按这个顺序来：

1. 先搭页面整体结构  
2. 再按功能区拆模块  
3. 再看模块内部有没有可复用部分  
4. 最后再抽公共组件

比如任务管理页可以拆成：

- `TaskPage`：页面容器
- `TaskSearchBar`：搜索区
- `TaskToolbar`：按钮区
- `TaskList`：列表区
- `TaskModal`：弹窗区
- `BaseButton`、`BaseModal`：通用组件

这样拆，结构清楚，后面加功能也不容易乱。你一看文件名，大概就知道该去哪里找东西，团队协作时尤其省心。

### 可复制的代码思路

```jsx
function TaskPage() {
  return (
    <div className="task-page">
      <TaskSearchBar />
      <TaskToolbar />
      <TaskList />
      <TaskModal />
    </div>
  );
}
```

先别管逻辑复杂不复杂，先把页面变成“看得懂的结构”。

## 二、React 组件设计模板：容器组件、展示组件、通用组件怎么分？

### 2.1 为什么要分角色？

组件设计不是随便起名字，而是要让每个组件的身份清晰。  
本书里可以把组件大致分成三种：

- **容器组件**：负责状态、数据、事件处理
- **展示组件**：负责 UI 呈现，尽量少管业务
- **通用组件**：跨页面复用的基础组件

这样分，能把逻辑和 UI 分开，也能明显降低维护成本。

### 2.2 容器组件：负责“管事”

容器组件通常是页面级或模块级组件，比如：

- 拉取数据
- 维护筛选条件
- 控制弹窗显示
- 处理提交和删除

它像项目里的小主管，主要任务是协调各个子组件。一般页面最上层的组件，往往就承担容器职责。

比如 `TaskPage` 里可能会有这些状态：

- `keyword`：搜索关键字
- `list`：列表数据
- `selectedTask`：当前选中的任务
- `modalVisible`：弹窗是否打开

这些状态不适合散到各个子组件里，不然后面很难统一管理。

### 2.3 展示组件：负责“长得对、显示对”

展示组件更关注 UI 本身，比如列表项、标签、按钮样式、空状态。

展示组件的好处是：

- 更容易测试
- 更容易复用
- 不容易被业务逻辑污染

例如 `TaskList` 可以只接收：

- `data`
- `onEdit`
- `onDelete`

它不关心数据从哪来，只负责展示，并把用户动作抛出去。这样以后接口变了、数据结构变了，通常只改父组件，不用把列表组件一起翻修。

### 2.4 通用组件：负责“哪里都能用”

通用组件是项目里最值得积累的部分。比如：

- `BaseButton`
- `BaseModal`
- `BaseInput`
- `EmptyState`

它们一般有这些特点：

- 接口固定
- 风格统一
- 多处复用

但要注意，**通用不是越抽象越好**。如果一个组件只在一个页面用，而且未来大概率也不会复用，就没必要强行抽成公共组件。很多人喜欢把组件抽得特别“高级”，结果 props 一大堆，调用方反而看不懂，这就本末倒置了。

### 2.5 一个简单判断法

你可以这样问自己：

- 这是页面的业务核心吗？是的话，优先放容器组件
- 这是纯展示吗？是的话，优先做展示组件
- 这是项目级基础设施吗？是的话，考虑做通用组件

### 老赵经验总结

组件设计别一上来就追求“架构感”。先把职责分清楚，再谈优雅。很多项目不是写坏的，是一开始拆太猛，最后自己都接不住。

## 三、父子组件通信基础：props 传递、回调函数传参与事件上抛

### 3.1 为什么父子通信是组件化的核心？

组件拆开以后，马上就会遇到：数据谁来给？点击谁来处理？弹窗谁来开？

这就是父子组件通信要解决的事。

最常用的方式就两种：

- **父传子：props 传递数据**
- **子传父：回调函数传参，把事件上抛**

真实项目里 80% 的组件协作都绕不开它们。

### 3.2 父传子：让子组件拿到必要信息

比如父组件把搜索关键字、列表数据传给子组件：

```jsx
<TaskList data={list} />
<SearchBar value={keyword} />
```

核心思路是：**父组件掌握数据来源，子组件只负责使用。**

这样做的好处很直接：

- 数据流向清晰
- 组件职责明确
- 调试更容易

### 3.3 子传父：让父组件处理业务动作

子组件不应该自己决定“编辑谁”“删除谁”“提交什么”，它只负责把用户动作告诉父组件。

例如列表里点击编辑：

```jsx
function TaskList({ data, onEdit }) {
  return (
    <div>
      {data.map(item => (
        <div key={item.id}>
          <span>{item.title}</span>
          <button onClick={() => onEdit(item)}>编辑</button>
        </div>
      ))}
    </div>
  );
}
```

父组件接收后处理：

```jsx
<TaskList data={list} onEdit={handleEdit} />
```

这样一来，子组件只管触发事件，业务规则由父组件统一决定。比如点编辑后，父组件可以负责打开弹窗、把当前项塞进表单、切换编辑模式。这些动作不应该散落在子组件里，不然以后改交互会很麻烦。

### 3.4 事件上抛的实战场景

在真实项目里，子组件常常会把这些事件交给父组件：

- 搜索框提交关键字
- 列表项点击编辑/删除
- 弹窗提交表单
- 筛选条件变化

这套模式特别适合“页面容器 + 多个功能模块”的结构。你可以把子组件理解成“负责发信号的人”，父组件则是“负责做决定的人”。

### 3.5 一个常见误区

很多初学者会把状态往下塞，把逻辑往下压，最后每个子组件都变成一个小页面。结果就是：

- 状态分散
- 调试困难
- 组件耦合高

记住一句话：**数据尽量往上收，动作通过回调往上抛。**

页面才会保持“一个中心、多块协作”的结构，而不是四处开花、谁都能改、谁都不敢碰。

### 可复制的代码思路

```jsx
function TaskPage() {
  const [selected, setSelected] = useState(null);

  const handleEdit = (item) => {
    setSelected(item);
    setModalVisible(true);
  };

  return <TaskList data={list} onEdit={handleEdit} />;
}
```

推荐你记住这个数据流：

**子组件触发动作 → 回调函数上抛 → 父组件更新状态 → 父组件再把新状态传回子组件。**

这就是最基础、也最稳的 React 组件协作方式。

## 四、组件之间的协作关系：列表、搜索框、按钮、弹窗怎么联动？

### 4.1 组件不是孤岛，页面是协作系统

页面一旦组件化，就不只是“单个组件写得好不好”的问题，而是“组件之间怎么配合”的问题。

一个典型页面里的联动链路通常是：

1. 用户在搜索框输入关键字  
2. 点击搜索按钮  
3. 父组件更新筛选条件  
4. 触发列表刷新  
5. 列表重新渲染  
6. 点击新增按钮，弹窗打开  
7. 提交表单后更新列表  

这就是一个完整的协作链条。设计组件时，脑子里最好一直有这条链路，不然组件拆开了，操作还是乱。

### 4.2 用“状态归属”来协调组件

协作的关键，是先确定状态归谁管。

一般来说：

- 搜索条件、弹窗状态、选中项：交给页面容器
- 输入框当前值：可以由父组件控制，也可以局部管理
- 列表数据：通常由页面容器统一维护

这样做的结果是：组件虽然拆开了，但页面还是“一个脑子”。

页面容器负责统一调度，子组件负责局部执行。谁都别抢方向盘。

### 4.3 列表、搜索框、按钮、弹窗的推荐关系

#### 搜索框
- 负责接收输入
- 负责触发搜索动作
- 不直接请求接口

#### 按钮
- 负责触发某个动作
- 比如新增、刷新、清空
- 不自己改业务状态

#### 列表
- 负责展示数据
- 发出编辑、删除等动作
- 不直接决定弹窗逻辑

#### 弹窗
- 负责表单展示和提交
- 不直接决定列表数据怎么更新

这四类组件的边界如果混了，页面就容易变成“谁都管一点，最后没人管得住”。

### 4.4 一个实战组织方式

```jsx
function TaskPage() {
  const [keyword, setKeyword] = useState('');
  const [modalVisible, setModalVisible] = useState(false);

  return (
    <>
      <TaskSearchBar
        keyword={keyword}
        onKeywordChange={setKeyword}
        onSearch={() => fetchList(keyword)}
      />
      <TaskToolbar onAdd={() => setModalVisible(true)} />
      <TaskList onEdit={handleEdit} onDelete={handleDelete} />
      <TaskModal visible={modalVisible} onClose={() => setModalVisible(false)} />
    </>
  );
}
```

这里最重要的是：**每个组件知道自己该负责什么，不越界。**

如果搜索框开始负责打开弹窗，弹窗开始负责刷新列表，说明设计已经开始跑偏。协作的第一原则不是“谁能多做一点”，而是“谁该做什么”。

### 老赵经验总结

项目协作不是看谁功能多，而是看谁边界清楚。边界一乱，后面你会发现：弹窗管列表，列表管搜索，按钮管提交，最后谁都在管，谁也管不好。

## 五、组件复用与可维护性：抽公共组件、控制粒度、避免过度拆分

### 5.1 复用的目标不是“省代码”，而是“降低维护成本”

很多人一听复用，第一反应就是“我要把所有东西都抽出来”。别急。复用的本质不是少写几行，而是让项目更稳定、更好改。

如果公共组件抽得太早、太死板，反而会变成新麻烦。比如按钮组件本来只需要传文本和点击事件，你非要给它塞十几个配置项，最后每次用它都像在填问卷。

### 5.2 怎么判断该不该抽公共组件？

可以用三个问题判断：

1. 是否在两个及以上地方使用？  
2. 结构和行为是否基本一致？  
3. 抽出来后会不会让调用方更清楚？

如果三个问题里有两个答案偏否定，那就先别抽。先保留在当前页面里，等它真的成熟了再说。

### 5.3 控制组件粒度：不要拆得太碎

组件拆分还有个常见误区：以为越小越专业，结果拆成一堆只有十来行的小文件。

这种拆法的问题是：

- 跳文件太频繁
- 调试路径变长
- 业务理解成本上升

老赵建议你把粒度控制在“刚刚好”：

- 页面级组件：负责协调
- 功能模块组件：负责一个完整功能
- 通用组件：负责基础 UI 能力

组件拆分要服务于理解和维护，而不是服务于“文件数量好看”。

### 5.4 避免过度拆分的实战判断

如果一个子组件：

- 只在当前页面使用
- 逻辑极少
- 以后变化概率不高

那就可以先写在页面内部，没必要立刻独立成文件。这不是偷懒，这是控制复杂度。

一个项目最怕的不是组件少，而是组件多但没边界。先保证能跑、能看、能改，再考虑进一步抽象，这个顺序别反了。

### 5.5 推荐的检查清单

每次准备抽组件时，先问自己：

- 这个组件现在是否已经有明确职责？
- 它会不会和别的模块反复共用？
- 它的 props 接口是否容易理解？
- 以后修改它，会不会影响太多地方？

如果答不上来，就先别急着抽。老赵见过太多项目，前期拆得像教科书，后期维护起来像走迷宫。

### 可复制的代码思路

```jsx
function BaseButton({ type = 'button', children, onClick }) {
  return (
    <button type={type} onClick={onClick} className="base-button">
      {children}
    </button>
  );
}
```

公共组件尽量简单，别一开始就塞一堆业务参数。基础组件越干净，后面项目越稳。

## 六、可复制的组件拆分模板：文件命名、拆分顺序和 props 传递示例

这一节咱们把前面说的内容收成一个能直接照搬的模板。你以后做项目时，先按这个顺序走，基本不会太乱。

### 6.1 推荐的文件命名方式

老赵建议尽量按“页面名 + 功能名”的方式命名，清楚直观：

- `TaskPage.jsx`：页面容器
- `TaskSearchBar.jsx`：搜索区
- `TaskToolbar.jsx`：工具区
- `TaskList.jsx`：列表区
- `TaskModal.jsx`：弹窗区
- `BaseButton.jsx`：基础按钮

这样有两个好处：

- 一眼就能知道文件干什么
- 后期查找和维护成本低

### 6.2 推荐的拆分顺序

你可以照着这个顺序做：

1. 先写页面容器 `TaskPage`
2. 再拆出顶部交互区 `TaskSearchBar`、`TaskToolbar`
3. 再拆主体展示区 `TaskList`
4. 最后补弹窗 `TaskModal`
5. 只有多处复用时，再抽 `BaseButton`、`BaseModal`

注意，这个顺序很重要。不要一上来先搞公共组件，不然很容易为了复用而复用，最后页面主线还没理顺，组件就已经满天飞了。

### 6.3 一个完整的 props 传递示例

```jsx
function TaskPage() {
  const [keyword, setKeyword] = useState('');
  const [modalVisible, setModalVisible] = useState(false);
  const [selectedTask, setSelectedTask] = useState(null);

  const handleEdit = (task) => {
    setSelectedTask(task);
    setModalVisible(true);
  };

  const handleAdd = () => {
    setSelectedTask(null);
    setModalVisible(true);
  };

  return (
    <div className="task-page">
      <TaskSearchBar
        keyword={keyword}
        onKeywordChange={setKeyword}
        onSearch={() => console.log('search', keyword)}
      />
      <TaskToolbar onAdd={handleAdd} />
      <TaskList data={[]} onEdit={handleEdit} onDelete={(task) => console.log(task)} />
      <TaskModal
        visible={modalVisible}
        data={selectedTask}
        onClose={() => setModalVisible(false)}
      />
    </div>
  );
}
```

这个例子里，数据流非常清晰：

- 页面容器负责状态
- 子组件通过 props 接收数据
- 子组件通过回调把动作抛给父组件
- 父组件统一决定下一步怎么做

这就是最稳的组件化起手式。

### 老赵经验总结

组件拆分不是做数学题，不是越细越好，也不是越抽象越高级。你要盯住两个词：**边界** 和 **职责**。边界清楚了，职责明确了，项目就能越做越顺。

这一章我们做的事情，其实就一句话：**把一个静态页面，整理成边界清楚、职责明确、便于协作的 React 组件体系。**

你要记住这几个核心点：

- 组件拆分先看职责，再看复用

- 父子通信最常用的是 props 和回调函数上抛

如果这一步做顺了，后面学 `useState`、`useEffect`、请求封装、页面状态管理的时候，就会轻松很多。因为你已经有了一个真正能跑得动、改得动、看得懂的组件基础。

### 老赵经验总结

组件不是越碎越好，能把事情讲清楚、管得住，才是本事。一个好项目，靠的不是文件多，而是边界明。先让页面变得可控，再让功能变得可扩展，这才是从会写组件到会做项目真正跨过去的一步。

# 第4章：数据请求与请求封装实战

静态页面做到这一步，已经能“看”，但还不能“活”。真正让 React 项目往前走的，是**数据请求**：页面要从接口拿数据，列表要能刷新，详情页要按需加载，出错了也得给用户一个交代。  
这一章，老赵带你完成一个关键跨越：**从写死页面，到接入真实接口，再到把请求能力封装成可复用的工具层**。项目能不能做得稳，很多时候就看请求这块写得规不规矩。

先把思路摆正：**请求不是“点一下按钮就发出去”这么简单，它是一条完整链路**，包括接口准备、请求发送、结果处理、状态切换和页面展示。你把这条链路吃透了，后面状态管理、表单提交、路由详情页、异步处理，都会顺很多。

## 4.1 接口接入前的准备：先搞清楚你要拿什么数据

很多同学一上来就写 `axios.get()`，结果接口一改，页面全炸；字段一乱，组件又开始补丁式修修补补。老赵先提醒一句：**接接口之前，先把数据结构摸清楚**。

你不要把“发请求”理解成纯技术动作，它其实是**业务对齐**。你得先知道：这个页面要展示什么、接口会给什么、前端要怎么用。越早理清楚，后面返工越少。

### 你至少要确认三件事

#### 1）返回数据长什么样

比如列表接口可能返回：

```json
{
  "code": 0,
  "msg": "ok",
  "data": [
    { "id": 1, "title": "React 入门", "status": "published" }
  ]
}
```

你要确认的是：

- `code` 是不是成功标识
- 真正的数据在 `data` 还是别的字段里
- 失败时返回什么结构
- 字段是否稳定，是否有空值

这一步别偷懒。很多页面的问题，不是 React 写错了，而是你压根没搞清楚接口约定。字段一旦不稳定，组件就会跟着一起抖。

#### 2）页面真正需要哪些字段

别把接口返回的所有字段都塞进页面。页面只关心它需要的部分，比如列表页可能只要：

- `id`
- `title`
- `status`
- `createdAt`

详情页可能再多要：

- `content`
- `author`
- `tags`

这样能减少页面和接口的耦合。页面拿的数据越干净，组件越好写，后面重构也更轻松。

#### 3）请求什么时候发

不是所有数据都适合“页面一进来就请求”。你得先判断场景：

- 列表页：通常进入页面就请求
- 详情页：一般根据路由参数按需请求
- 搜索页：用户点击查询后再请求
- 表单编辑页：进入页面先请求详情，再回填表单

如果请求时机错了，页面就会出现空白、重复请求、无意义刷接口等问题。

### 接口接入前的检查清单

- 接口地址确认好了
- 请求方法确认好了：`GET / POST / PUT / DELETE`
- 参数名和字段名确认好了
- 返回结构确认好了
- 错误码规则确认好了
- 是否需要 token 或登录态确认好了

### 可复制的代码思路

先在页面旁边写清楚接口约定：

```js
// 列表接口：GET /api/articles
// 返回结构：{ code, msg, data }
// data: [{ id, title, status }]
// 页面需要：id, title, status
```

这一步看着笨，实际上很值钱。以后接口改了，你至少知道该从哪儿改起。

---

## 4.2 使用请求库发起数据请求：参数、响应和错误怎么处理

这部分就是把接口真正接进来。这里以常见请求库的思路来讲，重点不是某个库本身，而是**请求流程要清楚**。

### 一个完整请求要处理什么

一次请求至少包括三块：

1. **请求参数**
2. **响应数据处理**
3. **错误处理**

你不能只关心“能不能发出去”，还要关心“回来以后怎么处理”。成熟的请求写法，不是把接口调通就算完，而是把异常情况也考虑进去。

---

### 1）请求参数：别乱拼，先整理

比如列表接口需要分页和筛选：

```js
{
  page: 1,
  pageSize: 10,
  keyword: 'React'
}
```

建议先把参数整理成一个对象，再统一传给请求函数：

```js
const params = {
  page,
  pageSize,
  keyword,
};
```

这样好处很直接：

- 参数更清晰
- 改字段名更集中
- 调试时更容易打印

如果你直接在请求语句里拼一堆参数，后面想加筛选条件时就会很乱。

---

### 2）响应处理：不要直接把接口原样丢给组件

很多初学者喜欢这样写：

```js
const res = await request.get('/api/articles');
setList(res.data);
```

问题是：你把接口返回结构和组件状态绑死了。  
如果接口返回改成 `res.data.list`，你就得改一堆地方。

更稳的做法是：**在请求层就把返回值整理一遍**，让页面拿到的是统一格式。

```js
const result = await getArticleList(params);
// result 直接就是列表数据
setList(result);
```

页面只关心“我要什么数据”，不关心“接口原始结构是什么”。这就是请求封装真正的价值：**把变化挡在外面，把稳定留给页面**。

---

### 3）错误处理：别让页面悄悄挂掉

请求失败时，最怕的不是报错，而是**页面没有任何反馈**。  
你要区分几种情况：

- 网络错误
- 接口返回失败
- 参数不合法
- 超时
- 登录失效

基本写法可以这样组织：

```js
try {
  const result = await getArticleList(params);
  setList(result);
} catch (error) {
  setError('数据加载失败，请稍后重试');
}
```

这样页面至少知道出了问题，用户也能看到提示。  
如果你什么都不处理，用户看到的往往只是一个空白页。

### 常见误区

- 把所有错误都写成“服务器异常”
- 不做 loading 状态
- 在组件里重复写一模一样的请求处理逻辑
- 接口返回一改，页面就连锁报错

### 可复制的代码思路

```js
async function loadList() {
  setLoading(true);
  setError('');
  try {
    const data = await getArticleList({ page: 1, pageSize: 10 });
    setList(data);
  } catch (err) {
    setError('加载失败');
  } finally {
    setLoading(false);
  }
}
```

这套结构后面会反复用到，朴素，但稳定。

---

## 4.3 请求封装思路：为什么要统一 baseURL、拦截和返回值

如果每个页面都自己写请求配置，那项目做到中后期，基本就是“满地找牙”。  
所以老赵建议：**请求一定要封装**。

封装的目的不是装样子，而是把公共逻辑沉到一层里，页面只做业务。

### 1）统一 baseURL

同一个项目的接口，通常都有一个公共前缀：

```js
const baseURL = 'https://api.xxx.com';
```

统一配置后，页面里就不用每次手写完整地址。

好处很明显：

- 开发、测试、生产切换更方便
- 后期换域名，只改一处
- 请求代码更短

你可以把它理解成地基。地基打好了，后面接口换环境就不会满屋子改地址。

---

### 2）统一拦截

拦截就是把请求前、请求后统一处理一遍。

#### 请求前统一处理

比如：

- 自动带上 token
- 统一设置请求头
- 开启 loading

#### 请求后统一处理

比如：

- 根据 `code` 判断成功失败
- 把错误信息转成统一提示
- 登录失效时跳转登录页

示意：

```js
request.interceptors.response.use(
  (response) => {
    if (response.data.code === 0) {
      return response.data.data;
    }
    return Promise.reject(response.data.msg);
  },
  (error) => Promise.reject(error)
);
```

记住原则就行：**页面不要直接和底层响应结构打交道，封装层先消化一遍。**

---

### 3）统一返回值处理

如果有的接口返回 `res.data.data`，有的返回 `res.data.list`，页面会很痛苦。

所以封装层要尽量统一成一种风格：

- 成功：直接返回业务数据
- 失败：抛出统一错误

这样页面就能写成：

```js
const list = await getArticleList();
```

这就是“会做项目”和“会写代码”的差别：前者想的是整个项目的维护成本。

---

### 4）服务层 + 页面调用层：最推荐的请求结构

老赵建议你把请求分成两层：

- **服务层**：专门放接口函数
- **页面调用层**：专门处理页面状态和业务逻辑

这样结构最清爽，也最适合后续扩展。

```js
// services/request.js
import axios from 'axios';

const http = axios.create({
  baseURL: '/api',
  timeout: 10000,
});

http.interceptors.response.use(
  (response) => {
    const { code, msg, data } = response.data;
    if (code === 0) return data;
    return Promise.reject(new Error(msg || '请求失败'));
  },
  (error) => Promise.reject(error)
);

export default http;
```

```js
// services/article.js
import http from './request';

export function getArticleList(params) {
  return http.get('/articles', { params });
}

export function getArticleDetail(id) {
  return http.get(`/articles/${id}`);
}
```

```js
// pages/ArticleList.jsx
useEffect(() => {
  async function loadData() {
    setLoading(true);
    setError('');
    try {
      const data = await getArticleList({ page: 1, pageSize: 10 });
      setList(data);
    } catch (e) {
      setError(e.message || '加载失败');
    } finally {
      setLoading(false);
    }
  }

  loadData();
}, []);
```

这个模板你可以直接迁移到别的项目里。以后再加用户接口、评论接口、订单接口，也是一套思路。

---

## 4.4 列表数据与详情数据：到底怎么加载最合理

不同页面的数据加载方式不一样，不能一把梭。

### 1）页面进入即请求

适合列表页、首页推荐、仪表盘这类页面。

```js
useEffect(() => {
  loadList();
}, []);
```

特点：

- 页面一打开就拿数据
- 用户感知自然
- 常配合 loading 和空态

#### 适用场景

- 文章列表
- 商品列表
- 用户管理页

这种场景里，数据本来就是页面主体，用户进入后马上看到内容最合理。

---

### 2）按需请求

适合详情页、弹窗详情、懒加载区域。

比如文章详情页，需要从路由参数里拿 `id`，等 `id` 有了再请求：

```js
useEffect(() => {
  if (!id) return;
  loadDetail(id);
}, [id]);
```

特点：

- 不浪费请求
- 与用户行为绑定更紧
- 适合“打开时才加载”的页面

关键点是：**先判断参数存在，再发请求**。  
否则页面刚渲染时参数还没准备好，你就冲出去请求，容易出错。

---

### 3）条件请求

适合搜索、筛选、分页等场景。

比如用户点“查询”才发请求，而不是每敲一个字都请求一次：

```js
const handleSearch = () => {
  loadList({ keyword, status });
};
```

或者结合分页：

```js
loadList({ page, pageSize, keyword });
```

#### 判断标准

一句话判断：  
**这个数据是不是必须现在加载？如果不是，就别急着发。**

请求次数多了，不仅浪费资源，还会让页面状态难以控制。

### 列表页和详情页的区别，最好记牢

- **列表页**：重在“展示一批数据”，通常进入页面就请求
- **详情页**：重在“展示一个对象”，通常依赖路由参数按需请求
- **搜索页**：重在“用户触发后刷新结果”，通常条件请求
- **编辑页**：重在“先拿详情，再回填表单”，通常先详情后编辑

你以后做项目，会反复遇到这几种模式。先把这套脑子里的分类立住，后面就不会乱。

### 可复制的代码思路

```js
// 页面进入即请求
useEffect(() => {
  loadList();
}, []);

// 路由参数存在后按需请求
useEffect(() => {
  if (!id) return;
  loadDetail(id);
}, [id]);

// 用户点击后条件请求
const handleQuery = () => {
  loadList({ keyword, status, page: 1 });
};
```

---

## 4.5 加载态、空态和错误态：别让页面只会“转圈圈”

真实项目里，页面不是只有“成功展示”一种状态。  
你至少要准备三种基础状态：

- **加载态**
- **空态**
- **错误态**

这三种状态，是一个页面有没有产品感的分水岭。

### 1）加载态：告诉用户“我在干活”

```js
{loading ? <p>加载中...</p> : <List data={list} />}
```

更成熟一点的做法是：

- 列表加载时显示骨架屏或占位
- 按钮提交时禁用按钮，避免重复点击
- 详情页加载时显示“正在加载”

加载态的意义不只是“好看”，它是在告诉用户：页面没有卡死，系统正在处理。

---

### 2）空态：告诉用户“没数据，不是坏了”

空态不是错误。比如接口返回空列表：

```js
if (list.length === 0) {
  return <p>暂无数据</p>;
}
```

空态的价值在于：

- 让页面看起来完整
- 避免用户误以为页面卡死
- 提示下一步操作，比如“去创建第一条数据”

如果是可操作型页面，空态最好别只写“暂无数据”，可以顺手给个按钮，比如“去新增”。

---

### 3）错误态：告诉用户“刚才失败了”

如果接口报错，不要默默吞掉：

```js
if (error) {
  return <p>{error}</p>;
}
```

错误态最好能做到两点：

- 给出明确提示
- 提供重试入口

```js
<button onClick={loadList}>重试</button>
```

### 一个推荐的页面状态模型

可以把页面状态理解成这四个值之一：

- `idle`：未请求
- `loading`：请求中
- `success`：请求成功
- `error`：请求失败

页面渲染时按状态切换，比堆几个布尔值更清楚。项目越复杂，状态模型越重要。

### 可复制的代码思路

```js
if (loading) return <p>加载中...</p>;
if (error) return <p>{error}</p>;
if (!list.length) return <p>暂无数据</p>;
return <List data={list} />;
```

顺序别乱：先错误，再空态，再正常展示。这样你自己也更容易判断页面现在处于什么状态。

---

## 4.6 老赵经验总结：请求别散着写，封装好一层，后面改接口才不会满地找牙

这一章最重要的，不只是“会发请求”，而是**建立请求层的思维**。

老赵给你三个实用经验：

### 1）请求别散落在页面里

页面里写一次、另一个页面再写一次，看着不多，项目一大就乱。  
正确思路是：**业务接口集中管理，页面只负责调用**。

今天是文章列表，明天是文章详情，后天再来个编辑页。如果都各写各的，后面改字段、改地址、改鉴权，光定位问题都能绕晕。

### 2）返回值尽量统一

统一返回值，页面就轻松；返回值不统一，页面就天天写适配。  
你可以把“统一返回值”理解成给页面提供一个稳定接口。页面永远拿到的是同一种数据形状，组件代码才会干净。

### 3）状态一定要配齐

请求不是只有成功和失败，还包括加载、空态。  
页面有没有“像个产品”，往往就看这些状态有没有补上。

很多同学做出来的页面，数据一出来还挺像样，一旦没数据就只剩空白。这不是前端不会写，而是缺少项目意识。

### 老赵经验总结

**请求别散着写，封装好一层，后面改接口才不会满地找牙。**  
你现在可能觉得封装多写了几行代码，但等接口一调整，你就知道这几行代码有多值钱。

---

## 本章小结：把静态页面真正变成动态页面

这一章，你已经完成了从“页面能看”到“页面能活”的关键一步。  
你学到的，不只是请求怎么发，而是：

- 接口接入前要先确认数据结构和字段
- 请求要处理参数、响应和错误
- 请求层最好做统一封装
- 列表、详情、搜索要用不同加载策略
- 页面状态要覆盖 loading、空态、错误态

### 下一步行动建议

1. 先把当前项目里最核心的一个列表页接上接口  
2. 把请求写成独立的 `api` 层，不要直接塞进组件里  
3. 给页面补上 loading、空态、错误态  
4. 统一整理接口返回值，别让组件接原始响应  
5. 顺手把详情页的按需请求也一起做掉  

做到这一步，你的 React 项目就不再只是练习题，而是开始像一个真正的应用了。

# 第5章：useState 实战与页面状态管理基础

## 开篇引入：别把状态当“垃圾桶”，它是页面的发动机

前面我们已经把页面骨架、组件拆分和请求流程搭起来了。到了这一章，咱们正式进入 React 项目里最常见、也最容易写乱的部分：**状态管理**。

很多同学学会 `useState` 之后，第一反应就是“页面上啥都塞一个状态”，结果很快就会变成：

- 一个筛选条件一个状态
- 一个弹窗一个状态
- 一个按钮禁用一个状态
- 一个列表一个状态
- 一个表单字段一个状态

看着没毛病，实际一多就乱。改一处，别的地方跟着抖。  
所以这一章，老赵不只是带你回顾 `useState` 的基础用法，更重要的是教你：**在真实项目里，状态该怎么设计、怎么更新、怎么放位置，才能让页面稳定、好维护、好扩展。**

我们还是沿着前面那个完整项目来讲：一个带筛选、列表、分页、弹窗编辑的管理后台页面。这个页面几乎囊括了 React 项目里最常见的状态场景。你把这一章吃透了，后面做别的 CRUD 页面，很多套路都能直接复用。

---

## 一、useState 的基础用法回顾：够用就行，别一上来写复杂

`useState` 的核心就一句话：**用状态保存会变化的数据，然后让 UI 跟着状态走。**

### 1.1 字符串状态：输入框和关键词最常见

搜索关键词、备注文本、当前标签，一般都适合用字符串。

```jsx
import { useState } from 'react';

function ListPage() {
  const [keyword, setKeyword] = useState('');

  return (
    <div>
      <input
        value={keyword}
        onChange={(e) => setKeyword(e.target.value)}
        placeholder="请输入关键词"
      />
    </div>
  );
}
```

输入框的值交给 React 状态来管，页面展示什么，数据就是什么，逻辑很清楚。

### 1.2 布尔值状态：控制开关最合适

弹窗显示隐藏、加载中、是否选中，这些都很适合用布尔值。

```jsx
const [showModal, setShowModal] = useState(false);
const [loading, setLoading] = useState(false);
const [checked, setChecked] = useState(false);
```

常见写法就是：

```jsx
<button onClick={() => setShowModal(true)}>打开弹窗</button>

{showModal && <EditModal />}
```

真实项目里很多交互，本质上就是几个布尔状态在配合。

### 1.3 数组状态：列表和选中项集合都少不了

比如列表数据、已选中的 ID 列表、动态表单项，经常会用数组。

```jsx
const [list, setList] = useState([]);
const [selectedIds, setSelectedIds] = useState([]);
```

接口数据回来后直接塞进去：

```jsx
setList(response.data);
```

数组状态里最常见的两类信息是：

1. **展示数据**：接口返回的列表  
2. **交互数据**：批量选中项、动态项、勾选集合

这两类都像数组，但别混着理解。

### 1.4 对象状态：适合成组管理的数据

筛选条件、表单初始值、分页信息，通常更适合放在对象里。

```jsx
const [query, setQuery] = useState({
  keyword: '',
  status: 'all',
  page: 1,
  pageSize: 10,
});
```

对象状态的好处是：同一组业务信息放在一起，看起来更整齐，也更符合实际业务。

但注意，对象状态更新不能直接改属性，这个是重点。

---

## 二、列表页常见状态设计：先列清楚“会变什么”，再决定怎么存

真实项目里，一个列表页通常不只是“显示数据”这么简单，它还会带着一堆页面状态。老赵建议你先按职责列清楚，再动手写代码。

### 2.1 一个典型列表页会有哪些状态？

管理后台里，标准列表页通常会有这些状态：

- **筛选条件**：关键词、分类、状态、时间范围
- **选中项**：当前选中的行、批量操作的 ID 集合
- **分页信息**：当前页码、每页条数、总条数
- **弹窗开关**：新增弹窗、编辑弹窗、删除确认框
- **表单值**：弹窗里的输入内容、编辑前的数据回填

状态不是随便写的，它通常和页面功能一一对应。  
你画页面时，最好先想清楚：这个页面到底有哪些“会变的东西”，再决定用几个状态去接。

### 2.2 状态分别适合放在哪一层？

#### 放在组件内部更合适的状态
- 输入框当前值
- 弹窗是否打开
- 下拉框展开状态
- 局部按钮是否禁用

这些状态只服务于当前组件，没必要往上抬。

#### 放到父组件更合适的状态
- 列表筛选条件
- 列表数据
- 当前编辑项
- 分页信息
- 批量选中项

因为这些状态往往会被多个子组件使用，比如筛选栏、列表区、分页器、弹窗区都可能要读它们。

### 2.3 一个可复制的列表页状态模板

```jsx
const [list, setList] = useState([]);
const [loading, setLoading] = useState(false);
const [query, setQuery] = useState({
  keyword: '',
  status: 'all',
  page: 1,
  pageSize: 10,
});
const [selectedIds, setSelectedIds] = useState([]);
const [showModal, setShowModal] = useState(false);
const [currentRecord, setCurrentRecord] = useState(null);
```

这套结构在商品管理、用户管理、文章管理里都能直接复用。  
如果你现在还不知道怎么起状态，先别急着创新，先用这套模板跑通业务，再微调。

## 三、状态更新的实战细节：对象和数组不可变更新，必须写顺手

### 3.1 对象状态更新：别直接改属性

错误写法：

```jsx
query.keyword = 'React';
setQuery(query);
```

看着像改了，但 React 不一定会按你想的刷新。  
因为你改的是原对象引用，React 很难判断变化。

正确写法：

```jsx
setQuery({
  ...query,
  keyword: 'React',
});
```

这叫**不可变更新**。核心就是：  
**不要直接改原对象，而是复制一份新的对象，再改需要的字段。**

如果要改多个字段，也一样：

```jsx
setQuery({
  ...query,
  keyword: 'React',
  page: 1,
});
```

### 3.2 数组状态更新：增删改都要生成新数组

添加一个选中 ID：

```jsx
setSelectedIds([...selectedIds, id]);
```

删除一个选中 ID：

```jsx
setSelectedIds(selectedIds.filter((item) => item !== id));
```

更新列表中的某一项：

```jsx
setList(
  list.map((item) =>
    item.id === currentId ? { ...item, status: 'published' } : item
  )
);
```

记住一个原则：**数组更新尽量用 `map`、`filter`、展开运算符，少直接 `push`、`splice`。**

原地修改虽然方便，但容易让状态引用不变，导致更新不稳定。

### 3.3 什么时候用函数式更新更稳？

如果新状态依赖旧状态，比如计数器、勾选项切换、分页翻页，推荐函数式更新：

```jsx
setPage((prev) => prev + 1);
setSelectedIds((prev) => [...prev, id]);
```

这样能避免闭包里拿到旧值，尤其在异步场景里更稳。

## 四、页面状态管理基础：谁用谁管，谁共享谁提升

这一节是本章核心。你把这个判断吃透了，后面写页面会轻松很多。

### 4.1 判断标准：谁用谁管，谁共享谁提升

这是页面状态设计的核心。

#### 放组件内部的状态
适合只在当前组件内部使用的状态，比如：

- 输入框当前值
- 弹窗是否打开
- 某个下拉框展开状态
- 局部开关

#### 提升到父组件的状态
适合多个子组件都要用到的状态，比如：

- 列表筛选条件
- 当前选中的记录
- 列表刷新触发
- 全局弹窗控制
- 表单提交后的刷新信号

一句话：**一个状态谁要用，谁就应该能拿得到。**

### 4.2 父子组件通信里的状态提升怎么做？

父组件负责列表和筛选，子组件负责筛选栏，这种场景最常见。

父组件：

```jsx
function ArticlePage() {
  const [query, setQuery] = useState({ keyword: '' });

  return <SearchBar query={query} setQuery={setQuery} />;
}
```

子组件：

```jsx
function SearchBar({ query, setQuery }) {
  return (
    <input
      value={query.keyword}
      onChange={(e) =>
        setQuery({
          ...query,
          keyword: e.target.value,
        })
      }
    />
  );
}
```

这就是典型的父子组件通信：**父组件掌握状态，子组件负责展示和触发变化。**

这样做的好处很明显：数据来源统一，变更路径清楚，后面加“重置”“搜索”“分页联动”也顺手。

### 4.3 别把“能放子组件的状态”强行提到父组件

很多同学一学会“状态提升”，就把所有状态都往父组件堆。结果父组件越来越胖，子组件反而啥都不管。

老赵提醒你：**状态提升不是越高越好，而是只提升必要的共享状态。**

如果一个状态只在某个小组件里使用，就让它留在那个组件里，别硬提。  
比如小菜单的展开状态，完全没必要让父组件来管。

## 五、状态与 UI 的联动：状态怎么驱动渲染、筛选和交互？

### 5.1 状态变化会自动触发视图更新

```jsx
{loading ? <div>加载中...</div> : <List data={list} />}
```

当 `loading` 为 `true`，页面显示加载中；  
当 `loading` 为 `false`，列表展示出来。

这就是状态驱动视图。你可以把页面理解成一张“状态表”，每个状态变化，都会对应一部分 UI 变化。

### 5.2 筛选条件变化后，如何驱动请求和列表刷新？

常见套路是：

1. 用户修改筛选条件
2. 更新 `query`
3. 点击搜索或触发回调
4. 用最新 `query` 发起请求
5. 请求成功后更新 `list` 和 `total`

```jsx
const handleSearch = () => {
  const nextQuery = { ...query, page: 1 };
  setQuery(nextQuery);
  fetchList(nextQuery);
};
```

注意：如果你刚 `setQuery`，马上又用 `query` 请求，有时会拿到旧值。  
所以更稳的方式是直接组织一个新参数对象，再拿它去请求。

### 5.3 弹窗和表单值，如何和状态配合？

编辑弹窗打开时，需要把当前行数据回填进去：

```jsx
const handleEdit = (record) => {
  setCurrentRecord(record);
  setShowModal(true);
};
```

弹窗里根据 `currentRecord` 初始化表单值：

```jsx
<input
  value={currentRecord?.title || ''}
  onChange={(e) =>
    setCurrentRecord({
      ...currentRecord,
      title: e.target.value,
    })
  }
/>
```

实战里常见链路就是：

- 点击编辑
- 记录当前项数据
- 打开弹窗
- 回填表单
- 修改输入值
- 提交后关闭弹窗
- 刷新列表

这条链路看着长，其实本质上就是状态在串页面。

## 六、可复制的页面状态管理清单：写代码前先过一遍这个模板

### 6.1 页面状态判断清单

每次写页面前，先问自己这几个问题：

1. **这个值是不是页面必须记住的？**  
   是，就考虑用状态。

2. **它能不能从别的状态计算出来？**  
   能算出来，就别重复存。

3. **它是不是多个组件都要用？**  
   是，就考虑提升到父组件。

4. **它的变化会不会直接影响 UI？**  
   会，那它就是典型状态。

### 6.2 一个可直接套用的状态管理模板

```jsx
function ArticlePage() {
  const [list, setList] = useState([]);
  const [loading, setLoading] = useState(false);
  const [query, setQuery] = useState({
    keyword: '',
    status: 'all',
    page: 1,
    pageSize: 10,
  });
  const [selectedIds, setSelectedIds] = useState([]);
  const [showModal, setShowModal] = useState(false);
  const [currentRecord, setCurrentRecord] = useState(null);

  const fetchList = async (params = query) => {
    setLoading(true);
    // 请求成功后：
    // setList(res.data.list);
    // setLoading(false);
  };

  const handleSearch = () => {
    const nextQuery = { ...query, page: 1 };
    setQuery(nextQuery);
    fetchList(nextQuery);
  };

  return null;
}
```

这套模板的好处是：  
页面要管的事已经拆开了，后面接请求、分页、弹窗、编辑，都能围绕这几个状态继续扩展。

## 七、老赵经验总结：状态不是越多越好，能少就少，能复用就别重复存

这一章最重要的，不是记住多少 API，而是建立一个习惯：**先想清楚“这个状态为什么存在”，再决定“它该放哪里、怎么更新”。**

### 7.1 常见误区一：重复存同一个数据

比如列表数据已经在 `list` 里了，又单独存一个 `tableData`，本质就是重复存储。  
如果一个状态可以通过计算得到，就别额外存一份。

```jsx
const filteredList = list.filter((item) => item.status === query.status);
```

这种派生数据，能算出来就别再 `useState` 存。  
否则你就得多维护一份同步逻辑，时间久了很容易不一致。

### 7.2 常见误区二：所有状态都塞进一个大对象

一开始图省事，后面修改一个字段就得小心拷贝整个对象。  
如果某些状态职责完全不同，分开管理通常更清楚。

判断方法很简单：

- 同一组业务含义的，放一起
- 完全不同用途的，分开写

比如筛选条件放一起没问题，但弹窗开关、列表数据、加载状态就没必要硬塞进同一个对象里。

### 7.3 常见误区三：状态不分“展示用”还是“源数据”

比如筛选出来的结果列表，通常是接口返回的数据，属于源数据。  
而页面上显示的标签文案，很多时候是派生展示。

别把展示文本也塞成状态，不然同步成本会越来越高。  
真正该存的，往往是生成结果所需的原始条件。

### 7.4 老赵给你的最终提醒

**状态不是越多越好，能少就少，能复用就别重复存。**  
你写 React 页面时，真正厉害的地方不是“我能写多少个 `useState`”，而是“我能不能把状态放对位置、分对职责、用对更新方式”。

这才是从“会写组件”走向“会做项目”的关键一步。

# 第6章：表单与交互场景实战

如果说前面几章是在搭房子、铺地板，那这一章就开始装门、装锁、装开关了。  
表单和交互是 React 项目里最容易写乱的部分：输入框一多，状态一多，提交、校验、弹窗、重置、刷新全搅在一起，最后代码能跑，但你自己都不敢再改。

本章还是沿着前面的核心项目来练手，场景统一放在“内容管理页”里。这个页面里既有筛选搜索，也有新增编辑弹窗，还有提交、删除、重置这些常见操作。你会看到一整套交互链路是怎么串起来的：**页面结构怎么分、受控组件怎么写、提交前怎么整理数据、弹窗怎么回填、按钮怎么防重复点击**。学完后，你应该能从“会写几个 input”进阶到“能把一整套表单流程做完整”。

## 一、表单页面结构设计：先把流程分区，再写代码

表单页面最怕的不是写不出来，而是**逻辑没有分区**。  
一个页面里既有搜索区，又有编辑区，还要提交区、操作区、弹窗区，如果不先划分，后面状态和事件一定会乱。

### 1. 页面通常分成四块

一个比较稳的表单页面，建议拆成四个区域：

- **搜索区**：过滤列表，比如关键字、分类、状态
- **编辑区**：填写核心表单内容
- **提交区**：保存、重置、取消等主动作
- **操作区**：删除、批量操作、弹窗触发等辅助动作

这个分法不是为了好看，而是为了让页面逻辑天然分层。搜索区只负责筛选列表，编辑区只负责录入内容，弹窗只负责临时编辑，这几个区域的状态通常都不一样，硬塞在一起就容易互相干扰。

### 2. 结构设计的判断标准

一个区域如果有自己的交互目标，就值得单独成块。

比如：

- 搜索区只负责筛选，不负责保存
- 编辑区只负责录入，不负责列表渲染
- 弹窗只负责临时编辑，不抢主页面逻辑

这样做还有个好处：以后你想把“新增”做成弹窗，把“编辑”做成抽屉，改动范围也更可控。

### 3. 可复制的代码思路

```jsx
function ContentManagePage() {
  return (
    <div className="page">
      <SearchBar />
      <div className="content">
        <ContentForm />
        <ActionPanel />
      </div>
      <ConfirmDialog />
    </div>
  );
}
```

页面层先把区域摆出来，业务细节先别急着堆上去。这样你后面加字段、加按钮、加弹窗时，心里会稳很多，因为每个区域的职责已经定好了。

### 老赵经验总结

表单页面不是“把控件堆上去”就完事了。先定流程，再定区域，最后才是写输入框。结构先拆明白，后面写状态、写请求、写弹窗都会顺很多。

## 二、受控组件基础：输入框、下拉框、单选、多选和文本域怎么统一管理？

React 里做表单，核心思路通常就是**受控组件**。  
说白了，表单值不要散落在 DOM 里，而是放在 state 里统一管理。这样你才知道当前页面到底填了什么，也方便提交、重置和回填。

### 1. 输入框：最基础，也最容易写乱

```jsx
const [form, setForm] = useState({
  name: '',
  keyword: '',
});

<input
  value={form.name}
  onChange={(e) => setForm({ ...form, name: e.target.value })}
/>
```

判断一个输入框是不是受控，标准很简单：**value 来自 state，修改也通过 onChange 回写 state**。  
很多人一开始会写成“默认值 + 提交时再取值”，短期看着简单，长期就麻烦，因为校验、回填、清空、联动都很难统一处理。

### 2. 下拉框和单选：本质一样，都是“选中值”

```jsx
<select
  value={form.category}
  onChange={(e) => setForm({ ...form, category: e.target.value })}
>
  <option value="a">分类A</option>
  <option value="b">分类B</option>
</select>
```

```jsx
<label>
  <input
    type="radio"
    checked={form.gender === 'male'}
    onChange={() => setForm({ ...form, gender: 'male' })}
  />
  男
</label>
```

关键不是控件长什么样，而是你要记住：**表单值 = state 的一部分**。  
项目里常见的小坑是接口值和控件值类型不一致，比如接口返回数字，控件要字符串。这种情况要么回填时统一转换，要么提交前统一转换，别让类型在中间漂着。

### 3. 多选和文本域：特别注意数据类型

```jsx
<textarea
  value={form.remark}
  onChange={(e) => setForm({ ...form, remark: e.target.value })}
/>
```

多选一般会变成数组：

```jsx
const toggleTag = (tag) => {
  setForm((prev) => {
    const exists = prev.tags.includes(tag);
    return {
      ...prev,
      tags: exists ? prev.tags.filter((t) => t !== tag) : [...prev.tags, tag],
    };
  });
};
```

数组型字段最容易翻车，比如标签、兴趣、权限、附件列表。这类字段在 UI 上看着简单，但一到回填、移除、提交，就会暴露边界问题，所以先想清楚数据结构，再动手写组件。

### 4. 受控组件的常见误区

- 只写了 `value`，没写 `onChange`
- state 结构太散，每个字段一个 `useState`
- 输入框类型不同，但处理方式没有统一
- 表单值和接口字段名完全脱节，提交时又临时拼一遍

建议尽量采用一种统一方式：**一个 form state 管一组表单值，再用字段名映射控件**。

### 可复制的代码思路

```jsx
const [form, setForm] = useState({
  title: '',
  category: '',
  status: 'draft',
  tags: [],
  desc: '',
});

const updateField = (key, value) => {
  setForm((prev) => ({ ...prev, [key]: value }));
};
```

这样后面新增字段时，不需要为每个字段单独写一套状态逻辑。页面一大，统一入口就很重要。

### 老赵经验总结

表单一复杂，最容易犯的错就是“每个控件都单独管”。短期看着清楚，长期一定乱。老赵建议你先用一个统一的 form 对象兜住，再按字段拆方法，代码会稳很多。

## 三、提交与重置交互：校验、整理数据、恢复默认值怎么做？

表单真正有价值的地方，不是“能输入”，而是**能正确提交**。  
提交前后这段逻辑，往往决定你的项目是“能用”还是“像样”。

### 1. 提交前先做校验

校验不用一开始就搞得很复杂，但至少要有基础判断：

- 必填项不能为空
- 数字范围合法
- 选择项必须存在
- 文本长度不能超限

```jsx
const handleSubmit = async () => {
  if (!form.title.trim()) {
    alert('标题不能为空');
    return;
  }
  if (!form.category) {
    alert('请选择分类');
    return;
  }
};
```

重点不是 `alert` 多专业，而是先把“错误入口”拦住。真实项目里，校验可以是简单提示，也可以是表单级错误信息，但逻辑都一样：**不合法就别往下走**。

### 2. 提交前要整理数据

用户看到的表单结构，和后端需要的字段结构，往往不是一回事。  
所以提交前通常要做一次数据清洗：

- 去掉空格
- 字符串转数字
- 把数组拼接成接口需要的格式
- 删除页面临时字段

```jsx
const payload = {
  ...form,
  title: form.title.trim(),
  price: Number(form.price),
};
```

编辑页面还要注意“只提交业务字段，不提交临时 UI 字段”。比如 `confirmPassword`、`checkedAll`、`tempIndex` 这类字段，有些只是页面辅助状态，没必要发给后端。  
这一步很重要，因为它是前端从“界面数据”走向“业务数据”的桥梁。

### 3. 重置要恢复默认值

重置不是简单把所有值改空，而是恢复到你设定的默认状态。

```jsx
const defaultForm = {
  title: '',
  category: '',
  status: 'draft',
  tags: [],
  desc: '',
};

const [form, setForm] = useState(defaultForm);

const handleReset = () => {
  setForm(defaultForm);
};
```

如果是编辑场景，还要区分：

- **新增模式**：重置回初始值
- **编辑模式**：重置回当前记录的原始值

这个细节很多人会漏掉。比如编辑一条记录后，你点“重置”，到底是回到空表单，还是回到这条记录刚打开时的状态？业务一定要先定好。

### 4. 提交与重置的执行顺序

推荐顺序是：

1. 校验
2. 整理 payload
3. 发请求
4. 成功后提示
5. 刷新页面或列表
6. 必要时重置表单

这个顺序的意义在于：先保证数据合法，再让它进入请求层。别一上来就发接口，最后发现字段没处理好，又要回头补洞。

### 老赵经验总结

提交逻辑不要直接从按钮一路写到接口，先在中间加一层“数据整理”。你会发现代码更像样，也更容易调试。表单最怕的不是字段多，最怕的是提交前后没有边界。

---

## 四、弹窗与确认框交互：打开、关闭、回填、提交后刷新怎么串？

真实项目里，很多表单不是页面上直接填，而是藏在弹窗里。  
比如新增分类、编辑标签、删除确认，这些交互都绕不开弹窗。

### 1. 弹窗的核心状态只有三类

- 是否显示：`open`
- 当前数据：`currentItem`
- 是否提交中：`loading`

```jsx
const [open, setOpen] = useState(false);
const [currentItem, setCurrentItem] = useState(null);
const [loading, setLoading] = useState(false);
```

把弹窗当成一个独立的小流程来看，就会清楚很多：打开、填值、提交、关闭、清理，每一步都要有对应状态，不然很容易出现“弹窗关了但数据还在”的怪问题。

### 2. 打开弹窗时要不要回填？

如果是编辑场景，答案是要。  
回填一般发生在点击“编辑”按钮后：

```jsx
const handleEdit = (item) => {
  setCurrentItem(item);
  setForm({
    title: item.title,
    category: item.category,
    status: item.status,
    tags: item.tags || [],
    desc: item.desc || '',
  });
  setOpen(true);
};
```

回填时要注意两个问题：

1. 旧数据是否覆盖干净
2. 缺省值是否补齐

比如 `item.tags` 可能为空，`item.desc` 可能不存在，这时候要给默认值，避免组件渲染时出现 undefined。

### 3. 关闭弹窗时要不要清理状态？

要。最好关闭时顺手清理：

```jsx
const handleClose = () => {
  setOpen(false);
  setCurrentItem(null);
  setForm(defaultForm);
};
```

不清理的话，下次打开可能还残留上一次的输入内容。尤其是“新增”和“编辑”共用一个弹窗时，清理动作更重要。

### 4. 提交后的刷新逻辑

弹窗提交成功后，通常要做两件事：

- 关闭弹窗
- 刷新列表或重新拉取数据

```jsx
const handleSave = async () => {
  setLoading(true);
  try {
    await saveItem(form);
    setOpen(false);
    await loadList();
  } finally {
    setLoading(false);
  }
};
```

刷新列表很关键。不刷新，用户会觉得“我明明保存了，页面怎么没变”。前端交互最忌讳的就是“看起来没反应”，所以成功后一定要把反馈闭环做完整。

### 5. 确认框适合做什么

确认框适合做高风险操作，比如删除、取消发布、清空内容。  
它的逻辑一般更简单：

- 点击触发
- 用户确认
- 调用删除接口
- 成功后刷新列表

### 可复制的代码思路

```jsx
const handleDelete = async (id) => {
  const ok = window.confirm('确认删除吗？');
  if (!ok) return;
  await deleteItem(id);
  await loadList();
};
```

如果项目里对交互要求更高，可以把 `window.confirm` 换成自定义弹窗。但无论哪种方式，本质都一样：先确认，再执行，再刷新。

### 老赵经验总结

弹窗不要只看“显示和隐藏”，真正要管的是**打开时带什么，关闭时清什么，提交后怎么刷新**。这三个环节串对了，弹窗交互基本就稳了。

---

## 五、交互细节处理：怎么防重复提交、禁用按钮和给用户反馈？

页面能跑不代表体验好。  
表单交互里最值钱的，其实是这些细节。

### 1. 防重复提交

用户点得快、网络慢、接口抖，都会导致重复提交。  
解决办法很简单：提交期间按钮禁用。

```jsx
<button onClick={handleSubmit} disabled={loading}>
  {loading ? '提交中...' : '保存'}
</button>
```

这个逻辑看着小，但在真实项目里非常常见。很多重复请求不是后端的问题，而是前端没把入口锁住。尤其是保存、删除、批量操作这些按钮，一定要做好“提交中不可再点”。

### 2. 按钮禁用的判断标准

常见禁用条件有：

- 正在提交
- 必填项未填
- 当前状态不允许操作

```jsx
const canSubmit = form.title && form.category && !loading;
```

你也可以把这个判断拆出来，单独写成一个变量。这样 JSX 会清爽很多，后面排查问题也更方便。比如用户问“为什么按钮是灰的”，你直接看 `canSubmit` 就知道原因。

### 3. 提示信息要及时

前端的提示不是装饰，而是交互的一部分。  
用户需要知道：

- 哪一项错了
- 当前是不是在提交
- 成功了还是失败了
- 为什么按钮点了没反应

常用提示包括：

- 表单校验提示
- 成功提示
- 错误提示
- loading 状态提示

别怕提示多。真正让人难受的不是提示多，而是提示不明确。比如保存成功了没反馈，或者失败了只在控制台报错，用户根本不知道发生了什么，这就很不专业。

### 4. 反馈状态要尽量明确

一个好的页面，用户不需要猜。  
比如：

- 保存按钮变成“提交中...”
- 删除按钮旁边出现 loading
- 表单校验失败时直接定位到出错字段
- 提交完成后明确提示“已保存”

这些细节会让页面看起来很顺。其实不是代码高级，而是流程完整。

### 5. 交互细节的检查清单

做完表单后，建议自己过一遍：

- 输入框是否都受控
- 提交前是否校验
- 提交中是否禁用按钮
- 弹窗关闭后状态是否清理
- 保存成功后是否刷新列表
- 重置是否恢复默认值
- 编辑场景是否正确回填

这份清单很实用，基本能帮你查掉 80% 的表单问题。

### 老赵经验总结

很多同学做表单，只盯着“功能实现”，却忽略用户感受。其实前端交互做得像样，靠的不是多高级，而是细节到位。按钮有没有禁用，提示有没有及时，用户能不能知道下一步，这些都很重要。

---

## 六、把表单、组件和请求串成一条线

这一章最重要的，不是记住几个 input 的写法，而是理解一件事：  
**表单不是孤立的，它一定和组件、状态、请求连在一起。**

一个完整流程通常是这样的：

1. 页面初始化，拉取列表或详情
2. 点击新增 / 编辑，打开弹窗
3. 回填表单数据
4. 用户修改输入
5. 提交前校验和整理数据
6. 发请求保存
7. 成功后关闭弹窗
8. 刷新页面列表
9. 清理临时状态

你会发现，表单本质上就是一个小型业务流程。  
它不只是“输入 + 提交”，而是“状态流转 + 交互反馈 + 请求联动”。

### 可复制的代码思路

```jsx
const [form, setForm] = useState(defaultForm);
const [open, setOpen] = useState(false);
const [loading, setLoading] = useState(false);

const openCreate = () => {
  setForm(defaultForm);
  setOpen(true);
};

const openEdit = (item) => {
  setForm({
    title: item.title,
    category: item.category,
    status: item.status,
    tags: item.tags || [],
    desc: item.desc || '',
  });
  setOpen(true);
};

const submitForm = async () => {
  if (!form.title.trim()) return;
  setLoading(true);
  try {
    await saveItem({ ...form, title: form.title.trim() });
    setOpen(false);
    await loadList();
  } finally {
    setLoading(false);
  }
};
```

这个小流程已经把本章最核心的东西串起来了：**状态、组件、交互、请求、刷新**。后面做任何表单页面，都可以先照着这个骨架搭，再往里填业务细节。

## 七、老赵再补一刀：真实项目里表单最常见的坑

这一节不展开讲太虚的，老赵直接给你几个项目里最常见的坑，你做的时候可以直接对照排查。

### 1. 状态和字段名不统一

接口叫 `article_name`，页面里叫 `title`，最后提交时又临时映射一遍。  
这不是不行，但如果你页面很多，建议尽量统一命名，或者固定一个转换层，别让字段在组件里来回跑。

### 2. 新增和编辑混用一套逻辑，但默认值没区分

新增是空表单，编辑是回填表单。  
如果这两个场景没分开，最容易出现“编辑完再新增，表单残留上一次内容”的问题。

### 3. 提交成功了，但页面没刷新

这类问题最容易被忽略。  
用户看见成功提示了，却没看见列表变化，就会怀疑是不是没保存成功。所以保存后刷新列表、重新拉详情、更新本地状态，必须做一个闭环。

### 4. 表单校验只靠后端报错

后端校验当然要有，但前端也别完全躺平。  
能在前面拦住的错误，尽量前面就拦住。这样用户体验更好，接口压力也更小。

### 可复制的代码思路

```jsx
const submitForm = async () => {
  if (!form.title.trim()) {
    alert('请填写标题');
    return;
  }

  const payload = {
    ...form,
    title: form.title.trim(),
  };

  setLoading(true);
  try {
    await saveItem(payload);
    setOpen(false);
    await loadList();
  } catch (err) {
    alert('保存失败，请稍后再试');
  } finally {
    setLoading(false);
  }
};
```

这个模板不花哨，但很实用。真实项目里，大多数表单交互都能从这个骨架起步。

### 老赵经验总结

表单最怕逻辑散。  
交互先定流程，再写代码，效率最高。你先把“打开—编辑—提交—刷新—关闭”这条线画出来，再去补控件和样式，基本就不会写着写着迷路了。

---

## 本章小结：表单不是一堆控件，而是一条完整的业务链路

这一章我们把表单和交互的核心问题拆开讲了：  
**页面怎么分区、受控组件怎么写、提交和重置怎么做、弹窗怎么回填、细节怎么防翻车。**

你可以把本章记成一句话：

> 表单不是一堆控件，而是一条有状态、有流程、有反馈的业务链路。

接下来你做任何表单页面，都先问自己四个问题：

1. 这个页面有哪些区域？
2. 哪些字段需要统一管理？
3. 提交前要整理哪些数据？
4. 成功、失败、关闭、刷新分别怎么处理？

只要这四个问题想清楚，代码就不会乱。

### 老赵经验总结

表单最怕逻辑散。  
交互先定流程，再写代码，效率最高。你先把“打开—编辑—提交—刷新—关闭”这条线画出来，再去补控件和样式，基本就不会写着写着迷路了。

# 第7章：基础路由组织与页面切换

## 开篇引入：为什么一个项目做到后面，路由就必须上场？

前面我们已经把页面布局、组件拆分、数据请求这些基础活儿做得差不多了。项目一开始看着像一个页面，功能一多、入口一多，就会很快不够用：列表页要看详情，详情页要返回列表，新建页、编辑页、个人中心页也得各管各的。这个时候还把所有内容塞在一个大页面里，代码会越来越乱，后面维护也会很痛苦。

所以这一章，我们把单页内容扩展成“多页面项目”，把 React 的基础路由组织起来。你可以把路由理解成项目里的“交通规则”：谁去哪里、从哪里来、默认先去哪、出错了去哪，都要提前规划好。路由不只是跳页面，它真正解决的是**页面职责划分**和**页面关系管理**。

学完这一章，至少能做出这样一套结构：

- 首页负责展示列表和入口；
- 详情页负责查看单条数据；
- 编辑页负责修改数据；
- 404 页负责兜底；
- 左侧菜单、顶部导航、面包屑都能跟着路由联动。

换句话说，项目到这里，才算真正开始有“应用”的样子，而不是几个组件的拼接。

---

## 一、路由在项目中的作用：为什么不能只靠 `show`/`hide` 切页面？

### 1.1 多页面结构的意义是什么？

React 虽然是单页应用，但“单页”不是“只有一个内容区”。更准确地说，是**一个入口，多个视图**。页面之间切换不一定刷新浏览器，但业务上一定会有不同页面职责。

比如一个任务管理项目，通常会有这些页面：

- `/tasks`：任务列表页
- `/tasks/:id`：任务详情页
- `/tasks/create`：新建任务页
- `/tasks/:id/edit`：编辑任务页

每个页面职责都不同：

- 列表页：展示、筛选、进入详情；
- 详情页：查看信息、返回列表；
- 编辑页：修改数据、保存提交。

如果不用路由，而是在一个大组件里靠条件渲染切换，短期能跑，长期必乱。因为页面状态、标题、参数、返回逻辑都会混在一起。以后再加“导出”“审批”“归档”，这个大页面很容易变成一锅粥。

### 1.2 路由解决的核心问题

路由至少解决四件事：

1. **地址可读**：用户一看 URL 就知道自己在哪；
2. **页面可直达**：刷新后还能回到同一页面；
3. **职责可拆分**：每个页面负责自己的业务；
4. **导航可维护**：菜单、面包屑、返回路径可以统一管理。

你可以把路由理解成项目的“导航中心”。没有它，页面之间的跳转全靠手写判断；有了它，页面关系就会清晰很多，后面做权限控制、菜单同步、面包屑同步也更顺手。

### 1.3 常见误区

很多新手会把路由写成“页面开关”：

- `showList = true`
- `showDetail = false`
- `showEdit = false`

这不是路由，这是“手工切场景”。页面一多，条件判断会越来越碎；更麻烦的是，地址不变，刷新后状态直接丢掉。

**判断标准很简单：**  
如果你开始频繁写“显示哪个、不显示哪个”，而不是“当前路径是什么”，那说明项目该上路由了。

---

## 二、基础路由配置：路由表、路径映射、默认页面与 404 页面

### 2.1 路由表怎么组织更清楚？

做项目时，路由配置建议先按“页面级路由”来设计，而不是先想组件。最常见的方式就是先列路由表。

例如：

| 路径 | 页面 | 说明 |
| --- | --- | --- |
| `/` | 首页 | 默认入口 |
| `/tasks` | 任务列表 | 核心列表页 |
| `/tasks/create` | 新建任务 | 创建表单 |
| `/tasks/:id` | 任务详情 | 查看单条数据 |
| `/tasks/:id/edit` | 编辑任务 | 修改单条数据 |
| `*` | 404 | 兜底页 |

它有两个好处：

- 一眼看清项目有哪些页面；
- 后续新增页面时，不容易乱塞路径。

更重要的是，路由表会逼着你先思考“这个功能应该放在哪个页面里”。很多项目一开始乱，不是代码差，而是入口设计没想清楚。

### 2.2 路径映射的基本思路

基础路由里只要记住一个原则：**路径负责定位页面，组件负责呈现内容。**

```jsx
import { BrowserRouter, Routes, Route, Navigate } from 'react-router-dom';
import Layout from './layout/Layout';
import TaskList from './pages/TaskList';
import TaskCreate from './pages/TaskCreate';
import TaskDetail from './pages/TaskDetail';
import TaskEdit from './pages/TaskEdit';
import NotFound from './pages/NotFound';

function App() {
  return (
    <BrowserRouter>
      <Routes>
        <Route path="/" element={<Navigate to="/tasks" replace />} />
        <Route element={<Layout />}>
          <Route path="/tasks" element={<TaskList />} />
          <Route path="/tasks/create" element={<TaskCreate />} />
          <Route path="/tasks/:id" element={<TaskDetail />} />
          <Route path="/tasks/:id/edit" element={<TaskEdit />} />
        </Route>
        <Route path="*" element={<NotFound />} />
      </Routes>
    </BrowserRouter>
  );
}
```

这里要抓住几个点：

- `/` 默认重定向到 `/tasks`；
- `Layout` 包裹多个页面，表示这些页面共享统一外壳；
- `*` 是兜底页面，也就是 404；
- `:id` 是动态参数，后面会用到。

这种写法适合项目实战，因为它把页面入口统一收口了。以后新增页面，只要补进路由表，不需要到处改组件逻辑。

### 2.3 默认页面和 404 页面不能少

默认页面的作用是让用户“进来就有东西看”。  
404 页的作用是兜底，防止用户输入错误路径后页面空白。

**常见判断标准：**

- 用户访问 `/` 没内容，说明默认页没设计好；
- 用户访问错误路径白屏，说明兜底没做好。

404 页别写得太复杂，核心是告诉用户：

- 当前页面不存在；
- 可以返回首页或列表页；
- 不要让用户卡死。

它不是摆几个图标就结束了，而是要给用户一个明确去路，比如“返回任务列表”“回到首页”。

### 2.4 可复制的路由基础模板

如果你是第一次给 CRA 项目上路由，可以先照着这个最小结构搭：

```jsx
// src/constants/routes.js
export const ROUTES = {
  home: '/',
  taskList: '/tasks',
  taskCreate: '/tasks/create',
  taskDetail: (id) => `/tasks/${id}`,
  taskEdit: (id) => `/tasks/${id}/edit`,
};
```

```jsx
// src/App.jsx
import { BrowserRouter, Routes, Route, Navigate } from 'react-router-dom';
import { ROUTES } from './constants/routes';
import Layout from './layout/Layout';
import TaskList from './pages/TaskList';
import TaskCreate from './pages/TaskCreate';
import TaskDetail from './pages/TaskDetail';
import TaskEdit from './pages/TaskEdit';
import NotFound from './pages/NotFound';

export default function App() {
  return (
    <BrowserRouter>
      <Routes>
        <Route path={ROUTES.home} element={<Navigate to={ROUTES.taskList} replace />} />
        <Route element={<Layout />}>
          <Route path={ROUTES.taskList} element={<TaskList />} />
          <Route path={ROUTES.taskCreate} element={<TaskCreate />} />
          <Route path="/tasks/:id" element={<TaskDetail />} />
          <Route path="/tasks/:id/edit" element={<TaskEdit />} />
        </Route>
        <Route path="*" element={<NotFound />} />
      </Routes>
    </BrowserRouter>
  );
}
```

这套写法的好处很实在：

- 路径统一管理，少写魔法字符串；
- 页面跳转更稳定；
- 后面做权限、菜单高亮、返回路径时，能直接复用。

## 三、页面结构与路由结合：布局组件为什么要包裹页面？

### 3.1 什么叫“布局组件 + 页面组件”？

这是项目里最常见、也最值得学会的结构。

- **布局组件**：负责公共框架，比如顶部导航、侧边栏、页脚、内容区；
- **页面组件**：负责具体业务内容，比如列表、详情、表单。

这样做的好处很明显：

- 公共部分只写一次；
- 页面切换时，外壳不变，内容变化；
- 后续扩展菜单、权限、面包屑更方便。

如果前面已经做过页面布局，这一章就是把布局和路由串起来。这样项目就不是“每个页面都重新搭一遍壳”，而是共用一个稳定框架。

### 3.2 常见写法怎么落地？

在 React Router 里，`Layout` 组件通常配合 `Outlet` 使用。你可以理解成：`Layout` 是外壳，`Outlet` 是内容插槽。

```jsx
import { Outlet, NavLink } from 'react-router-dom';

function Layout() {
  return (
    <div className="app-layout">
      <header className="app-header">
        <h1>任务管理系统</h1>
      </header>

      <div className="app-body">
        <aside className="app-aside">
          <nav>
            <NavLink to="/tasks" end>
              任务列表
            </NavLink>
            <NavLink to="/tasks/create">
              新建任务
            </NavLink>
          </nav>
        </aside>

        <main className="app-content">
          <Outlet />
        </main>
      </div>
    </div>
  );
}
```

这个结构的关键是把“壳”和“内容”分离。你只需要在页面级组件里处理业务逻辑，不需要每个页面都重复写导航和框架。

### 3.3 页面职责怎么划分才不乱？

可以按这个规则切：

- **Layout**：只管外壳和通用导航；
- **ListPage**：只管列表、搜索、进入详情；
- **DetailPage**：只管单条记录展示；
- **EditPage**：只管编辑表单；
- **CreatePage**：只管创建逻辑；
- **NotFound**：只管兜底提示。

最容易犯的错，是把页面里的局部逻辑塞进 Layout 里。比如“列表加载中”“编辑表单提交中”这种状态，应该放在具体页面里，而不是放到布局组件里。布局越轻，项目越稳。

### 3.4 老赵提醒

很多人一开始就把布局组件写得很“全能”，最后变成第二个大杂烩。  
记住：**布局组件是框架，不是业务仓库**。业务逻辑越少越好，页面职责越清楚越省心。

---

## 四、带参数的页面切换：列表到详情、编辑到详情怎么传？

### 4.1 什么是带参数路由？

真实项目里最常见的场景就是：

- 从列表页点某条数据，进入详情页；
- 从详情页进入编辑页；
- 从编辑页保存后返回详情页。

这时就需要把“当前是哪条数据”带过去。基础路由里最常见的方式就是**路径参数**。

比如：

- `/tasks/1001`
- `/tasks/1001/edit`

这里的 `1001` 就是参数。

### 4.2 列表到详情的基础传参思路

列表页通常这样写：

```jsx
import { Link } from 'react-router-dom';

function TaskListItem({ task }) {
  return (
    <div>
      <h3>{task.title}</h3>
      <Link to={`/tasks/${task.id}`}>查看详情</Link>
      <Link to={`/tasks/${task.id}/edit`}>编辑</Link>
    </div>
  );
}
```

详情页再通过路由参数拿到 id：

```jsx
import { useParams } from 'react-router-dom';

function TaskDetail() {
  const { id } = useParams();

  return <div>当前任务ID：{id}</div>;
}
```

关键不是“怎么取到 id”，而是形成一套固定思路：

1. 列表页把 id 放进 URL；
2. 详情页从 URL 读取 id；
3. 详情页根据 id 请求数据；
4. 页面展示对应内容。

这个思路后面会贯穿整个项目。无论是订单、商品还是用户管理，本质都差不多：先定位，再读取，再展示。

### 4.3 编辑到详情怎么处理返回关系？

编辑页保存成功后，通常会跳回详情页或者列表页。

常见做法：

- 保存成功后跳回 `/tasks/:id`；
- 新建成功后跳回新数据的详情页；
- 也可以返回列表页，取决于业务。

要注意，**返回不是单纯 `back()` 就完事**。如果用户是从外部链接直接进来的，`back()` 可能没有上一页。更稳妥的方式是：

- 明确跳回某个业务页面；
- 保存时保留当前 id；
- 让跳转路径可预测。

这就是项目实战里常见的判断方式：**用户有没有可能不是按你设计的顺序进来**。只要有这个可能，就别把返回逻辑写得太随意。

### 4.4 常见误区

- 把参数写死在组件里；
- 详情页没有根据参数请求数据；
- 编辑后不知道该回到哪；
- 路径设计太随意，后面自己都看不懂。

**判断标准：**  
只要一个页面离开后仍然能准确回到同一条数据，说明参数传递是合格的。

---

## 五、路由与导航菜单联动：高亮、面包屑和返回路径怎么配？

### 5.1 为什么菜单要和路由联动？

项目做大后，用户不只靠按钮切页面，还会靠左侧菜单、顶部导航、面包屑来判断位置。  
如果菜单高亮跟不上路由，用户会很容易迷糊：我到底在哪？

所以路由和导航菜单必须联动，至少处理三件事：

- 当前菜单高亮；
- 面包屑路径展示；
- 返回按钮跳转正确。

这些看起来像“页面装饰”，其实是项目体验的一部分。页面切得再对，如果用户不知道自己在哪，也会觉得不好用。

### 5.2 高亮状态怎么做更自然？

基础思路就是：**当前路径等于菜单路径时，高亮当前项**。  
在 React Router 里可以直接用 `NavLink`，它会根据当前路由自动处理激活状态。

```jsx
import { NavLink } from 'react-router-dom';

<NavLink to="/tasks" end className={({ isActive }) => (isActive ? 'active' : '')}>
  任务列表
</NavLink>
```

这里的思路很简单：

- 当前在 `/tasks`，列表菜单高亮；
- 当前在 `/tasks/create`，新建页面按规则高亮；
- 当前在 `/tasks/1001/edit`，编辑页对应入口高亮。

如果菜单层级更深，也可以根据路径前缀判断，比如 `/tasks/*` 都归到任务管理菜单下。

### 5.3 面包屑的作用是什么？

面包屑不是装饰，它是在告诉用户“你是怎么走到这里的”。

例如：

- 首页 / 任务列表 / 任务详情
- 首页 / 任务列表 / 编辑任务

它的好处是：

- 层级清晰；
- 页面关系明确；
- 用户更容易返回上一级。

对于层级较多的项目，面包屑尤其重要。它能把页面关系展示出来，而不是让用户在页面里迷路。尤其详情页信息多、编辑页表单长时，面包屑能明显降低迷失感。

### 5.4 返回路径怎么设计才稳？

返回按钮建议不要只写“返回上一页”，而是根据业务场景设计：

- 详情页返回列表页；
- 编辑页保存后返回详情页；
- 新建页取消后返回列表页。

如果想更好维护，可以把返回路径统一配置成常量，避免散落在各处。

```jsx
const ROUTES = {
  taskList: '/tasks',
  taskCreate: '/tasks/create',
  taskDetail: (id) => `/tasks/${id}`,
  taskEdit: (id) => `/tasks/${id}/edit`,
};
```

这种写法后面会很好维护，因为你不会在项目里到处手写路径字符串。以后路径改了，只改一处就行，这就是项目化写法和临时拼凑写法的区别。

---

## 六、把路由串成一个完整链路：从列表、详情到返回再到编辑

这一节老赵专门补一句，因为很多书里讲路由，只讲“怎么配置”，不讲“怎么串起来”。但真实项目里，路由不是一条条孤立的地址，而是一条完整的页面链路。

一个最小可用的任务管理链路，通常应该是这样：

1. 用户打开 `/`，自动进入 `/tasks`；
2. 在任务列表页点击某条任务，进入 `/tasks/:id`；
3. 在详情页点击“编辑”，进入 `/tasks/:id/edit`；
4. 编辑完成后，保存成功跳回详情页；
5. 详情页提供“返回列表”按钮；
6. 任意错误路径进入 404 页；
7. 左侧菜单始终能反映当前页面。

你可以把这个过程理解成：**页面不是单独存在的，它们之间必须能互相接上。**

如果你愿意再往前走一步，还可以补一个返回状态的小设计。比如从列表进入详情时，记录当前筛选条件；从详情返回列表时，尽量回到原来的列表上下文。这个功能不是本章重点，但思路上要知道：**路由不只是去哪里，还包括从哪里回来。**

## 老赵经验总结：路由不是简单跳页，核心是把页面关系理顺

这一章最重要的，不是背几个路由 API，而是建立项目思维：  
**路由不是“点一下换个页面”这么简单，它是在帮你管理整个项目的页面关系。**

老赵给你几条很实用的经验：

1. **先画路由表，再写页面**  
   先知道项目有哪些页面，后面组件才不会乱长。

2. **页面职责要单一**  
   列表、详情、编辑、创建，别全塞一个组件里。

3. **布局和业务分开**  
   Layout 管外壳，页面管内容，这样结构才稳。

4. **参数一定要跟业务走**  
   详情页、编辑页都离不开参数，别把数据硬编码。

5. **菜单、面包屑、返回按钮要统一**  
   这些东西一旦散着写，后面你自己都不知道哪条路是对的。

6. **默认页和 404 页别偷懒**  
   一个项目从“能进”到“能用”，这两个页面是底线。

### 本章可复制的代码思路

如果你现在要落地这个章节，可以直接按下面步骤做：

1. 先确定核心页面：列表、详情、新建、编辑、404；
2. 在 CRA 项目里安装并配置基础路由；
3. 用 `Layout + Outlet` 搭出公共框架；
4. 用路由表统一管理路径；
5. 用 `useParams` 处理详情和编辑页参数；
6. 给菜单和面包屑加上路由联动；
7. 明确每个页面的返回路径和默认跳转；
8. 用 `NavLink` 做菜单高亮；
9. 把常用路径抽成 `ROUTES` 常量，减少硬编码。

### 行动建议

这章学完以后，别只看懂，要马上动手改前面的项目：

- 把“单页展示”拆成多个页面；
- 把列表页和详情页连起来；
- 给项目补上 404 页面；
- 把顶栏和侧栏接入路由；
- 统一整理一份路由常量；
- 检查每个页面的返回逻辑是不是清楚。

你会发现，一旦页面关系理顺了，后面的状态管理、请求封装、表单提交都会顺很多。项目终于从“能看”变成“像个项目”了。

# 第8章：useEffect 实战与异步处理入门

## 开篇引入：为什么你学会了 useEffect，项目还是会“莫名其妙出问题”？

很多同学刚学 React 的时候，都会觉得 `useEffect` 很简单：组件加载后执行一下，依赖变了再执行一下，最后记得清理就行。  
但一到真实项目里，问题就来了：

- 页面一进来就请求接口，结果请求发了两次；
- 组件切走了，老请求还在回包，页面状态却已经变了；
- loading 关了，数据却还没回来；
- 想监听窗口大小，结果忘了清理事件，越用越卡；
- 依赖数组写错，要么不刷新，要么疯狂重复执行。

所以这章老赵不跟你背概念，咱们直接放到项目里讲：**useEffect 到底负责什么、什么时候跑、怎么跑、怎么避免翻车**。  
你把这一章吃透，后面做列表页、详情页、搜索页、轮询、埋点、窗口监听这些功能，脑子里就会有一套稳定的判断方法。

更重要的是，这一章不是孤零零讲 Hook，而是紧扣咱们这个 CRA 项目里的页面流程来讲。你后面做列表页初始化、筛选刷新、页面离开清理、搜索联动请求，都会反复用到 `useEffect`。所以别把它当成一个语法点，要把它当成项目运行机制的一部分。

---

## 一、useEffect 的核心用途，到底是哪三件事？

你别把 `useEffect` 想得太神秘。真到项目里，它的核心用途其实就三块：

### 1. 首次加载时执行一次

最常见的就是页面刚进来要拉数据。  
比如文章列表、商品列表、用户列表，用户一打开页面，数据就应该自动出来，这时候就用 `useEffect(() => {}, [])`。

### 2. 依赖变化时重新执行

比如搜索词变了要重新请求，分页页码变了要重新请求，筛选条件变了也要重新请求。  
这类场景里，`useEffect` 就不是只跑一次了，而是“条件一变就再跑一遍”。

### 3. 清理副作用

比如定时器、事件监听、订阅回调，组件销毁时都要清掉。  
不清理的话，页面切走了，旧逻辑还在跑，轻则浪费资源，重则直接把页面搞乱。

你可以把它记成一句话：**首次加载、依赖变化、清理副作用，这就是 useEffect 的三板斧。**

### 可复制的代码思路

```jsx
import { useEffect } from 'react';

function Demo() {
  useEffect(() => {
    // 首次加载、依赖变化时要做的事

    return () => {
      // 清理副作用：定时器、事件、订阅
    };
  }, []);

  return <div>示例组件</div>;
}
```

这段模板你可以直接记住。后面不管是列表页、筛选页，还是轮询页、监听页，基本都能从这个骨架往上加。

---

## 二、页面进入即请求数据，应该怎么写才稳？

### 1. 典型场景：列表页一打开就加载数据

这是 useEffect 最常见的实战场景。  
比如“文章列表页”“商品列表页”“用户管理页”，一进页面就得请求接口，把数据渲染出来。

完整流程一般是：

1. 组件初始化；
2. 开始请求；
3. 请求中显示 loading；
4. 成功后渲染数据；
5. 失败后展示错误信息；
6. 没数据时给空状态。

这就是一个完整页面最基本的骨架。

### 2. 基础写法

```jsx
import { useEffect, useState } from 'react';

function ArticleList() {
  const [list, setList] = useState([]);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState('');

  useEffect(() => {
    const loadData = async () => {
      try {
        setLoading(true);
        setError('');
        const res = await fetch('/api/articles');
        const data = await res.json();
        setList(data);
      } catch (err) {
        setError('数据加载失败');
      } finally {
        setLoading(false);
      }
    };

    loadData();
  }, []);

  if (loading) return <div>加载中...</div>;
  if (error) return <div>{error}</div>;
  if (list.length === 0) return <div>暂无数据</div>;

  return (
    <ul>
      {list.map(item => (
        <li key={item.id}>{item.title}</li>
      ))}
    </ul>
  );
}
```

这段代码虽然简单，但把“请求”“状态”“渲染”分开了，逻辑很清楚。

### 3. 为什么这里一定要空依赖数组？

因为这个场景的目标是：**组件第一次进入页面时请求一次数据**。  
如果你不写 `[]`，那就可能在每次渲染后都执行，页面就会不断重复请求。

所以这里的依赖数组不是随便写的，它表达的是一个明确的业务意图：  
**只在首次挂载时触发。**

### 4. 不要在 useEffect 里直接写 async

更稳的方式是：**在 effect 里面定义异步函数，再调用它。**  
因为 `useEffect` 需要你返回清理函数，而 `async` 会让返回值变成 Promise，逻辑容易乱。

### 5. 页面状态切换模型

你可以把一个请求页面的状态拆成四段：

- `loading`：请求中
- `success`：请求成功且有数据
- `empty`：请求成功但没数据
- `error`：请求失败

这个模型后面做任何列表页都通用。  
老赵见过太多同学，页面一复杂就开始乱加状态，最后自己都忘了哪个状态该什么时候出现。你先把这四段捋顺，页面就稳了一大半。

---

## 三、依赖数组怎么判断？什么时候加，什么时候不加？

这是 useEffect 最容易翻车的地方。

### 1. 依赖数组的作用

依赖数组决定了：**这个 effect 什么时候重新执行。**

常见写法有三种：

```jsx
useEffect(() => {
  // 每次渲染后都执行
});
```

```jsx
useEffect(() => {
  // 仅首次执行
}, []);
```

```jsx
useEffect(() => {
  // 依赖变化时执行
}, [keyword, page]);
```

你可以把它理解成“触发条件列表”。条件不变，就不重新跑；条件变了，就重新执行。

### 2. 什么时候加依赖？

只要 effect 里面用到了外部的值，而且这个值变化后你希望重新执行副作用，通常就该加进依赖数组。

比如：

- 搜索词变了，重新请求列表；
- 页码变了，重新请求分页数据；
- 用户筛选条件变了，重新拉接口。

这类场景最常见，尤其是在列表页和筛选页里。

### 3. 什么时候不加？

有些情况下，你只想在组件首次进入时执行一次，比如：

- 首屏初始化请求；
- 页面统计埋点；
- 初始化定时器；
- 绑定一次窗口事件。

这时候用 `[]` 更合适。

### 4. 为什么会重复请求？

常见原因有几个：

#### 依赖写多了
比如把每次渲染都会变化的函数、对象、数组直接放进依赖里。

#### effect 里更新了依赖本身
比如请求完数据后，又修改了会触发 effect 的状态，结果形成循环。

#### 开发环境严格模式
有些开发环境下，React 会让 effect 执行得更“敏感”，帮助你发现副作用问题。  
所以看到“怎么跑了两次”，先检查逻辑和依赖，别先怀疑人生。

### 5. 老赵式判断法

你可以这样问自己：

- 这个副作用是不是只需要一次？
- 它是否依赖某个状态变化？
- 依赖项是不是稳定的？
- 重新执行会不会带来重复请求？
- 会不会形成循环更新？

老赵的经验是：**useEffect 不是“先写再看”，而是“先想清楚再写”。** 越是项目里，越不能靠猜。

## 四、异步加载过程中，页面状态怎么切换才像个真正的项目？

### 1. 真项目从来不是“请求一下就显示数据”

真实页面里，异步请求的体验一定要有层次：

- 还没开始：默认态
- 请求中：loading
- 请求成功：展示数据
- 请求失败：展示错误
- 没有数据：展示空状态

如果你只写“有数据就显示、没数据就不显示”，页面会显得很粗糙。用户会觉得这页面没反应，其实是状态管理没做好。

### 2. 推荐的状态拆分方式

```jsx
const [list, setList] = useState([]);
const [loading, setLoading] = useState(false);
const [error, setError] = useState('');
```

这三个状态基本够用：

- `list`：数据本身
- `loading`：请求状态
- `error`：失败信息

项目更复杂时，可以再加空状态、局部刷新、分页加载更多，但刚入门时先把这三个状态跑通就够了。

### 3. 典型渲染顺序

```jsx
if (loading) return <div>加载中...</div>;
if (error) return <div>{error}</div>;
if (list.length === 0) return <div>暂无内容</div>;
```

这个顺序很关键：

1. 先判断请求中；
2. 再判断错误；
3. 再判断空数据；
4. 最后才渲染正常内容。

别把空数据判断放在前面，不然请求还没回来，你就先给用户显示“暂无内容”，体验很怪。

### 4. 异步状态切换模板

```jsx
const loadData = async () => {
  try {
    setLoading(true);
    setError('');
    const res = await fetch('/api/articles');
    const data = await res.json();

    setList(Array.isArray(data) ? data : []);
  } catch (err) {
    setError('数据加载失败');
    setList([]);
  } finally {
    setLoading(false);
  }
};
```

这个模板的重点不是某个 API，而是状态流转逻辑：

- 开始时先进入 loading；
- 请求前清空错误；
- 成功后更新数据；
- 失败时把错误和数据状态收口；
- 最后统一关闭 loading。

这就是一个比较完整的异步状态闭环。

## 五、副作用怎么清理？怎么防止重复执行和资源泄漏？

### 1. 哪些场景必须清理？

常见需要清理的副作用有：

- 定时器；
- 事件监听；
- WebSocket 订阅；
- 手动注册的回调。

如果不清理，页面切走了，老任务还在跑，就容易出现：

- 内存泄漏；
- 重复执行；
- 回调打到已卸载组件上；
- 页面闪动或状态错乱。

很多项目前期跑得好好的，后面越改越慢、越点越卡，最后一查，往往就是清理逻辑没写完整。

### 2. 定时器清理示例

```jsx
useEffect(() => {
  const timer = setInterval(() => {
    console.log('轮询一次');
  }, 3000);

  return () => {
    clearInterval(timer);
  };
}, []);
```

这个写法在轮询、倒计时、自动刷新里都很常见。  
记住一句话：**开了什么，就要关什么。**

### 3. 事件监听清理示例

```jsx
useEffect(() => {
  const handleResize = () => {
    console.log(window.innerWidth);
  };

  window.addEventListener('resize', handleResize);

  return () => {
    window.removeEventListener('resize', handleResize);
  };
}, []);
```

这种写法在做响应式布局、监听滚动、窗口变化时都会用到。  
如果加了监听不清理，页面每次切换都会叠加一个监听器，后面就会越来越重。

### 4. 请求时机控制的思路

在真实项目里，尤其是搜索页、筛选页、切换 Tab 页时，不是所有变化都值得立刻请求。

你要考虑：

- 是不是用户输入停止后再请求更合理？
- 是不是切换条件时要防抖？
- 是不是只在条件完整时才请求？
- 是不是上一次请求还没完成，新请求又来了？

你要做的，不只是发请求，而是控制请求发出去的时机。

### 5. 防止老请求干扰新页面

有时用户很快切换页面，旧请求回来后还想改状态，这就危险了。  
常见处理方式是：

- 组件卸载后不再更新状态；
- 用标记判断当前请求是否有效；
- 在合适场景下做取消逻辑。

你不一定一上来就做得很复杂，但至少要知道：**请求发出去了，不代表请求回来时页面还在。**

## 六、把 useEffect 放回完整项目里，你应该怎么串联？

这章不是孤立知识点，它要服务整个 CRA 项目。

在前面的页面布局和组件拆分基础上，典型流程是这样的：

1. CRA 初始化项目，搭好基础目录；
2. 先搭列表页、搜索栏、筛选区、数据展示区；
3. 用 `useState` 管住本地状态；
4. 用 `useEffect` 在页面首次进入时请求列表数据；
5. 根据搜索词、分页、分类变化，控制是否重新请求；
6. 用 `loading / error / empty` 管住页面状态；
7. 进入详情页、返回列表页时，注意副作用清理；
8. 后续再把请求逻辑抽成统一封装，方便复用。

你会发现，`useEffect` 并不是一个单独知识点，它其实是**项目状态流转的发动机**。

如果说 `useState` 是在存数据，那 `useEffect` 就是在让数据流动起来。一个负责静态控制，一个负责动态驱动。把这两者结合起来，你的 React 项目才算真正开始像样。

### 可复制的异步处理步骤清单

你写 useEffect 前，先按这个顺序过一遍：

1. 先确认这件事是不是副作用；
2. 明确它是首次执行，还是依赖变化执行；
3. 先把 loading、error、empty 这几个状态准备好；
4. 在 effect 里只做一件事：触发异步流程；
5. 异步流程里统一处理成功、失败和兜底；
6. 该清理的清理，别让旧逻辑留尾巴；
7. 最后回头检查依赖数组，确认不会重复请求。

这套流程你可以直接复制到自己的项目里。  
别急着写代码，先把执行顺序想明白，后面会省很多坑。

## 老赵经验总结：useEffect 看着简单，真写项目最容易翻车，依赖关系一定先想清楚

老赵写项目这么多年，最想提醒你的一句话就是：

**useEffect 不是用来赶紧把代码写出来，而是用来明确副作用什么时候发生、什么时候结束。**

你写之前，先问四个问题：

1. 这个动作是不是副作用？
2. 它是只执行一次，还是依赖变化才执行？
3. 它有没有清理动作？
4. 它会不会造成重复请求或循环更新？

如果这四个问题你能答清楚，`useEffect` 基本就不会把你坑惨。

### 这一章你最该带走的实战方法

- 页面首次加载请求数据，用 `useEffect + []`；
- 依赖变化触发请求，用 `useEffect + [依赖]`；
- 用 `loading / error / empty` 管住异步状态；
- 定时器、事件监听一定记得清理；
- 请求逻辑不要写得太散，先想“时机”，再写“代码”。

### 行动建议

下一章你可以直接拿一个列表页练手：

- 打开页面自动请求；
- 切换关键词重新请求；
- 加上 loading 和错误提示；
- 再补一个空状态；
- 最后试着加一个定时刷新。

只要你把这一套跑通，`useEffect` 就不再是“看懂了但不会用”，而是能真正落到项目里的实战工具了。

## 一、组件渲染异常：为什么数据有了，页面却显示不对？

组件渲染异常是项目里最常见、也最容易让人上头的问题。React 里状态一变页面就跟着变，状态类型一旦不对，页面就可能直接报错。很多人看到白屏，第一反应是“React 有问题”，其实大多数时候是状态埋了雷。

### 1. 状态类型不对：数组、对象、字符串别混着来

很多人写列表页时喜欢把状态初始化成 `null`，等请求回来再赋值。理论上没错，但如果渲染阶段直接对它做 `map()`，就容易炸。还有一种更隐蔽：接口返回数组，你却按对象来用；或者字段没拿到，就直接读深层属性，页面一下就挂了。

**典型问题：**
- 列表状态初始值不是数组
- 对象字段未判空就直接读取
- 布尔状态被写成字符串 `"false"` / `"true"`

**可复制的代码思路：**
```jsx
const [list, setList] = useState([]);
const [detail, setDetail] = useState({});

return (
  <div>
    {list.length === 0 ? (
      <p>暂无数据</p>
    ) : (
      list.map(item => <div key={item.id}>{item.title}</div>)
    )}
  </div>
);
```

详情页则尽量给一个安全初值，再逐步渲染：

```jsx
<p>商品名称：{detail.name || '未获取到名称'}</p>
<p>商品描述：{detail.desc || '暂无描述'}</p>
```

**判断标准：**
- 列表用 `[]`
- 详情用 `{}`
- 访问深层字段前先做保护
- 不要把字符串 `"false"` 当布尔值用

### 2. key 使用不当：列表更新后页面乱了

`key` 是很多人写列表时最容易糊弄过去的地方。能跑不代表对，尤其在增删改之后，`key` 不稳定会导致输入框错位、列表状态串位，甚至你以为改的是第 1 条，结果页面改到了第 3 条。

**常见误区：**
- 直接用数组下标当 key
- key 不唯一
- 频繁变化的字段当 key

**正确思路：**
- 优先用后端返回的唯一 id
- 保证同一列表中的 key 稳定且唯一
- 列表会增删排序时，尽量别用下标

```jsx
{todos.map(todo => (
  <li key={todo.id}>{todo.title}</li>
))}
```

老赵提醒你一句：`key` 不是随便写个编号，它是让 React 判断“这是不是同一个元素”。判断错了，页面表现就会跟着错。

### 3. 条件渲染出错：不是没显示，而是逻辑写反了

条件渲染看起来简单，但最容易把逻辑写歪。比如：
- `loading` 和 `empty` 同时显示
- 把“没有数据”写成“有数据”
- 三元表达式嵌套太深，看不懂自己写了啥

真实项目里，页面状态通常就这几种：加载中、请求失败、空数据、正常显示。按优先级一层层判断，代码会清楚很多。

**建议做法：**
```jsx
if (loading) return <p>加载中...</p>;
if (error) return <p>请求失败</p>;
if (!list.length) return <p>暂无内容</p>;
return <ListView data={list} />;
```

这套写法朴素，但很稳。后面做列表页、详情页、搜索页都能直接用。

## 二、请求问题排查：为什么接口明明写了却拿不到数据？

数据请求出问题，八成不是 React 的锅，而是接口地址、参数、返回值结构或者跨域出了问题。这个时候别急着改页面，先把请求链路捋清楚。老赵见过太多人一遇到请求失败，就在组件里疯狂改 `useEffect`，最后发现只是 URL 拼错了一个字符。

### 1. 接口地址是否正确

最基础的问题，往往最容易忽略。尤其在 CRA 项目里，前端本地地址和后端接口地址常常不是一个域名，地址管理乱一点就会到处出问题。

**排查顺序：**
- 请求路径有没有写错
- 基础地址有没有配错
- 开发环境和生产环境是不是两个接口地址
- 路径前面有没有多一个 `/` 或少一个 `/api`

**建议：**
把接口地址统一放到请求封装里管理，避免在页面里到处写死。一旦接口变更，只改一处就行。

```js
// request.js
export const baseURL = process.env.REACT_APP_BASE_URL;
```

### 2. 跨域问题：前端能发出去，不代表后端肯接

开发时最常见的报错之一就是跨域。表面看是接口失败，实际上是浏览器拦住了。

**检查点：**
- 是否配置了代理
- 后端是否允许当前前端域名
- 请求方式是不是触发了预检
- 是否带了不必要的请求头

**实战建议：**
CRA 开发阶段可以通过 `proxy` 简化跨域调试；真正上线后再让后端或网关统一配置。别把开发环境代理当最终方案，不然一上线就容易露馅。

### 3. 参数格式不对：你传了，但传得不对

接口请求失败不一定是没传参数，而是传参格式不对。

**常见问题：**
- GET 请求把参数放到了 body
- POST 请求提交的是普通对象，但后端要 JSON
- 字段名和后端约定不一致
- 少传分页参数、状态参数、id 参数

**检查方法：**
- 打开浏览器 Network 面板
- 看请求参数到底有没有发出去
- 对照接口文档检查字段名和类型

分页接口通常会带 `page`、`pageSize`，漏一个，后端可能不会报错，但返回数据就不对。页面看起来像“没数据”，其实是请求参数从一开始就错了。

### 4. 返回值结构没处理好

请求成功不代表页面能显示。很多时候后端返回的是：

```js
{
  code: 200,
  message: "ok",
  data: { list: [] }
}
```

你却直接拿 `res.list`，当然找不到。实际项目里最常见的问题，不是接口没响应，而是把返回体和业务数据层搞混了。

**可复制的代码思路：**
```js
const res = await getList();
if (res.code === 200) {
  setList(res.data.list || []);
} else {
  setError(res.message || '请求失败');
}
```

### 5. 异常信息要看全，不要只看最后一行

报错信息里最值钱的不是“Failed”，而是前面的上下文。重点看：
- 请求发没发出去
- 服务器有没有响应
- 状态码是多少
- 响应体长什么样
- 控制台报错发生在哪一行

老赵经验是：先看 Network，再看 Console，最后回到代码。很多问题，只要把这三处串起来看，马上就露出来了。

## 三、状态与页面不同步：为什么数据变了，页面没跟着变？

React 项目里，状态和页面不同步，经常不是组件坏了，而是你对异步更新、依赖和旧值理解不够。这个坑很典型，尤其在你把 `useState` 和 `useEffect` 真正用进项目之后，会更明显。

### 1. `useState` 是异步更新的，别当场就想拿新值

`useState` 的更新不是同步立刻生效的。你刚 `setCount(count + 1)`，下一行打印出来的通常还是旧值，这是正常现象。

**常见误区：**
```js
setCount(count + 1);
console.log(count); // 这里通常还是旧值
```

**正确理解：**
- 状态更新是异步批处理的
- 页面会在下一次渲染时拿到新状态
- 不要把“刚设置完就立刻读到”当默认行为

如果你需要基于上一次状态继续计算，就用函数式写法更稳：

```js
setCount(prev => prev + 1);
```

### 2. `useEffect` 依赖遗漏：数据没刷新，问题常在这里

`useEffect` 很好用，但依赖数组写错，问题也大。

**典型场景：**
- 搜索条件变了，但列表没重新请求
- 路由参数变了，但详情页没更新
- 父组件传来的值变了，子组件还是旧数据

**检查清单：**
- 这个副作用依赖谁
- 谁变了就应该重新执行
- 依赖数组里是否漏了关键变量

```jsx
useEffect(() => {
  fetchData(keyword);
}, [keyword]);
```

如果 `keyword` 会变化，就必须放进去。很多页面“第一次能查出来，后面搜不动”，本质就是依赖没写对。

### 3. 旧值问题：你以为拿的是最新的，其实拿的是闭包里的旧值

这个坑在函数组件里特别常见。你在定时器、回调、异步函数里访问状态时，拿到的可能不是最新值。原因不复杂：函数执行时捕获了当时的状态，后面状态变了，不代表这个回调会自动更新。

**判断方式：**
- 是否在定时器里读状态
- 是否在异步请求完成后依赖旧状态
- 是否连续更新同一个状态，结果只生效一次

**实战建议：**
- 需要基于上一次状态更新时，使用函数式写法
- 需要在异步里使用最新值时，尽量通过参数传递，而不是直接依赖闭包变量

这个问题一开始感受不深，但一旦做分页、轮询、倒计时、联动筛选，马上就会遇到。

### 4. 父子组件通信没接好，页面就像“各说各话”

前面章节已经讲过父子组件通信，到了排坑阶段，这块也很容易出问题。典型表现就是：
- 父组件改了值，子组件没刷新
- 子组件触发了事件，父组件没收到
- 传了回调函数，但参数没按约定传
- 子组件拿到的是旧 props

**排查思路：**
- 先看 props 有没有传到位
- 再看回调函数有没有触发
- 最后看父组件是否真的把新状态传回去了

**可复制的代码思路：**
```jsx
function Parent() {
  const [keyword, setKeyword] = useState('');
  return <SearchBar value={keyword} onChange={setKeyword} />;
}

function SearchBar({ value, onChange }) {
  return (
    <input
      value={value}
      onChange={e => onChange(e.target.value)}
    />
  );
}
```

只要通信链路断一层，页面表现就会怪怪的。所以别只盯着子组件，父组件的数据源也要一起查。

---

## 四、路由跳转和刷新 404：为什么能点过去，刷新就没了？

做单页应用时，路由问题绕不开。特别是从列表页跳详情页，或者刷新深层路径时，问题就容易冒出来。表面上像“路由坏了”，实际往往是前端和服务器对路径的理解不一致。

### 1. 路径配置是否一致

先检查路径本身：
- 路由表里有没有这个路径
- 跳转时路径写对了没有
- 动态参数有没有匹配上
- 是否重复嵌套了路径前缀

如果做的是嵌套路由，父子路径一定要对齐。父路由是 `/admin`，子页面是 `/admin/user/list`，跳转时别再手动拼重复前缀，不然很容易出错。

### 2. 嵌套路由有没有正确挂载

很多页面是“父布局 + 子页面”的结构。如果父路由里没留子路由出口，页面就只剩框架没有内容。

**判断标准：**
- 父组件中是否有 `<Outlet />`
- 子路由是否写在正确层级
- 跳转路径是否匹配嵌套路由规则

老赵经验是：先把父子结构画清楚，再写路由。先有结构，再有路径，不然页面很容易“看着像在路由，实际谁都接不上”。

### 3. 刷新 404：不是路由错了，是服务器没接住

这是前端项目上线后特别常见的问题。开发环境里切页面没问题，但一刷新就 404，通常是：
- 服务器把这个地址当成真实文件路径找了
- 没有做前端路由回退配置
- 静态资源托管没配好

**项目部署思路里要记住：**
- 单页应用要让服务器把未知路径回退到 `index.html`
- 由前端路由接管页面展示
- 不要让服务器按传统多页应用那套理解路径

这个问题不解决，用户随便一刷新就黑屏，体验会很差。

---

## 五、样式与布局问题：页面不报错，但就是不好看，怎么办？

样式问题不一定报错，但会让项目“看起来没做完”。真实项目里，很多返工都卡在布局上。功能能跑只是及格，页面顺眼才像个项目。

### 1. 盒模型：宽度怎么算清楚了吗？

页面溢出、按钮挤歪、左右不对齐，很多时候就是盒模型没理顺。

**排查点：**
- 元素是否加了 padding 之后撑破宽度
- 是否忘了设置 `box-sizing: border-box`
- 父容器宽度是否固定得太死

如果布局里有很多卡片、列表、表单项，最好一开始就统一盒模型，别等最后再救火。

### 2. 层级问题：你看不见，不代表它不存在

有时候按钮点不到，不是逻辑问题，而是被别的元素盖住了。

**检查点：**
- `z-index` 是否生效
- 父级是否设置了定位上下文
- 是否有透明遮罩层挡住操作区

这种问题肉眼不容易看出来，得借助浏览器开发者工具看元素层级。页面能显示，不代表事件能正常触发。

### 3. 滚动区域：页面滚不动，或者只滚一半

复杂页面里，头部、侧边栏、内容区常常各管各的。如果滚动容器没设置清楚，就会出现：
- 整页滚动失效
- 某个区域滚动但内容被裁剪
- 列表过长时底部按钮被挤没

**建议：**
- 明确哪个区域负责滚动
- 避免多个容器同时设置滚动
- 高度计算要有依据，别全靠试

如果你做的是后台管理页，这点尤其要注意。布局一乱，整个项目的专业感就掉很多。

### 4. 兼容性检查：别只在自己电脑上看着顺眼

真实项目不是只给你自己的浏览器看的。至少要检查：
- 不同分辨率下是否错位
- 常见浏览器表现是否一致
- 文本溢出、按钮换行、图片缩放是否正常

老赵建议你每完成一个页面，都顺手切一下窗口尺寸，看看有没有溢出和错位。这个动作不费事，但能提前发现很多问题。

---

## 六、调试方法：别硬猜，按顺序定位

排错最怕的不是报错，而是乱猜。老赵给你一套很实用的排查顺序，基本适用于大多数 React 项目问题。

### 调试四步法
1. **先看现象**  
   是报错、白屏、数据不显示，还是样式错乱？

2. **再看数据流**  
   数据是没请求到、没传下来，还是传下来没渲染？

3. **再看组件边界**  
   问题是在父组件、子组件，还是通信链路？

4. **最后看环境配置**  
   路由、代理、部署、打包路径有没有问题？

### 常用检查清单
- 控制台是否有红色报错
- Network 里请求状态是否正常
- React 状态是否更新
- 路由是否匹配当前地址
- 样式是否被覆盖或遮挡
- 打包后路径是否正确

养成这套习惯后，不管项目多复杂，排错都会越来越快。别一遇到问题就慌，项目开发本来就是边做边调。

---

## 老赵经验总结

别怕报错，先看现象，再看数据流，八成问题都藏在最开始那一层。  
你做 React 项目，最重要的不是“会写出功能”，而是**出问题时知道从哪开始查**。

记住这几个原则：
- 组件渲染异常，先查状态类型和 `key`
- 请求失败，先查接口地址、跨域、参数和返回结构
- 页面不同步，先查 `useState` 异步更新和 `useEffect` 依赖
- 路由 404，先查路径和部署回退配置
- 样式乱掉，先查盒模型、层级和滚动区域
- 父子通信不通，先查 props 和回调有没有真正接上

最重要的一句放最后：**大多数问题都藏在最开始那一层**。  
你看到的是页面错了，真正的根因往往在状态、请求、路由、结构这些前置层。别急着改最后一层，先把前面的数据链路捋直，问题一般就没那么吓人了。

---

## 本章小结

这一章的核心，不是记住所有报错，而是建立一套稳定的排错思路。你在真实项目里遇到的问题，大多数都不是“新问题”，而是前面这些老坑换个形式再出现一次。

接下来做项目时，建议你养成一个习惯：  
**每次功能写完，顺手做一次“异常检查”**——空数据、慢请求、路由刷新、样式压缩、参数缺失、父子通信、`useEffect` 依赖，全都试一遍。  

这样你会越来越像一个真正做项目的人，而不是只会写组件的人。

# 第10章：打包、上线与项目部署思路

前面几章咱们把页面、组件、请求、状态和路由都搭起来了。到了这一章，重点就只剩一件事：**把开发环境里的项目，变成一个真正能交付、能访问、能维护的线上项目**。

很多同学最容易卡在这里。开发时 `npm start` 跑得好好的，一打包就报错；本地刷新没问题，线上一刷新就 404；接口在本地能通，部署后却全挂。别急，这不是你“不会”，而是**上线有自己的规则**。这一章老赵就带你把 CRA 项目的打包、部署、验证和回滚思路串起来，让你不只会写，还能稳稳交付。

---

## 一、打包前先做什么？别让低级问题拖后腿

**问题：上线前到底要检查哪些东西？**

打包不是一键执行完就结束，真正靠谱的做法，是先做一轮“上线体检”。老赵给你一个最实用的检查清单。别嫌琐碎，越是上线前的检查，越能帮你少踩坑。

### 1. 环境变量先分清楚

CRA 项目里，开发、测试、生产配置最好分开管理。接口地址、环境标识、功能开关这些东西，别直接写死在页面里。

先确认：

- 开发环境接口有没有忘记切到线上地址
- 环境变量名是否符合 CRA 读取规则
- `.env` 里有没有写进敏感信息
- 打包后是否真的读取到了生产配置

比如本地时可能这样写：

```js
const BASE_URL = 'http://localhost:3000';
```

这在开发时没问题，但上线后很容易翻车。更稳妥的方式是用环境变量：

```js
const BASE_URL = process.env.REACT_APP_API_BASE_URL;
```

这样开发、测试、生产各用各的地址，代码不用反复改，风险也小很多。

### 2. 接口地址要统一

如果项目里到处都是 `http://localhost:3000` 这种地址，上线时大概率出事。更稳的做法是把接口统一收进请求封装里，再按环境切换。

可复制的思路是：

```js
// request.js
const BASE_URL = process.env.REACT_APP_API_BASE_URL;

export function request(url, options = {}) {
  return fetch(`${BASE_URL}${url}`, options);
}
```

这样你只改环境配置，不改业务代码。后面登录、列表、表单提交、详情页请求都走这里，维护起来会轻松很多。

### 3. 静态资源要检查路径

图片、字体、图标、JSON 配置文件，这些资源在开发环境能显示，不代表上线后也正常。重点检查：

- 图片路径是不是写死了绝对路径
- 是否按 CRA 推荐方式引用资源
- 静态资源有没有被正确打进构建结果

很多新手会直接写：

```jsx
<img src="/images/logo.png" alt="logo" />
```

开发时也许没事，但部署路径一变，资源就可能找不到。更稳的方式是让构建工具来处理资源路径，别手动硬编码。

### 4. 代码清理别偷懒

上线前建议顺手清掉这些东西：

- 调试用 `console.log`
- 未使用的变量和组件
- 临时测试页面
- 失效接口地址
- 注释掉但没删的实验代码

别小看这些内容。`console.log` 太多，发布后控制台会很乱；测试页面没删，用户可能直接访问到；失效接口留着，后面排查问题时会把自己绕晕。

### 5. 上线前把清单过一遍

老赵建议你把打包前检查做成固定动作，别凭记忆。最少要包含这些项：

- 环境变量是否正确
- API 地址是否切到生产环境
- 静态资源路径是否正常
- 路由页面是否都能访问
- 代码里有没有残留调试信息
- 重要表单、列表、详情页是否都能跑通

**常见误区**：很多人觉得“打包成功就能上线”，其实打包成功只说明构建没炸，不代表业务链路都通。上线前一定要把环境、接口、资源和页面状态都过一遍。

### 可复制的代码思路

- 所有接口统一走请求封装
- 不在组件里写死生产地址
- 环境变量集中放到 `.env.*` 文件
- 静态资源尽量按构建流程引用
- 上线前执行一次“代码清理 + 路径检查 + 页面冒烟测试”

### 老赵经验总结

**上线前别图快，图快最容易出事故。**  
你越早把接口、资源、环境这些东西整理好，后面部署越省心。老赵做项目时最怕的不是代码多，而是“哪儿都改了一点，最后没人知道正式配置在哪”。

---

## 二、CRA 打包流程到底做了什么？

**问题：`npm run build` 之后发生了什么？**

CRA 的打包，本质上是把开发时的代码，转换成浏览器能高效加载的静态文件。执行构建命令后，通常会生成一个 `build` 目录。

### 1. `build` 目录是上线产物

这个目录里通常包含：

- 压缩后的 HTML
- JS 代码包
- CSS 文件
- 静态资源引用结果
- 其他构建产物

你可以把它理解成：**开发工程的成品包装**。真正上线时，部署的不是源码，而是这个目录里的文件。线上服务器看到的，也不是你平时写 React 的那些源码，而是经过打包优化后的最终交付物。

### 2. 构建会做哪些事

CRA 在构建阶段一般会完成这些工作：

- 合并和压缩代码
- 去掉开发调试内容
- 生成适合浏览器加载的资源文件
- 对文件名做哈希处理，方便缓存管理

所以你上线后常看到类似 `main.8f3a1c.js` 的文件名。它不是乱命名，而是为了让浏览器识别版本变化：文件名一变，浏览器就知道“这是新版本”，用户刷新后才有机会拿到最新代码。

### 3. 如何理解构建结果

打包后的文件有两个关键点：

- **入口文件**：浏览器先读 HTML，再加载 JS 和 CSS
- **静态资源引用**：路径必须正确，否则页面空白或资源 404

所以构建完成后，别只看终端里那句“成功”，最好手动打开 `build` 看看结构，知道哪些文件是核心、哪些是资源。至少要明确：`index.html` 是入口，JS/CSS 是页面逻辑和样式，其他资源是运行时辅助材料。

### 4. 线下先模拟线上，别直接硬上

老赵建议，构建完成后先在本地模拟一次静态部署，看看 `build` 目录能不能被正常访问。这样你能提前发现：

- 入口文件是否能加载
- 静态资源是否 404
- 路由页面是否刷新就挂
- 环境变量是否真的生效

这一步很关键。很多问题不是上线后才出现，而是你压根没提前试过。

### 可复制的代码思路

- 执行 `npm run build` 生成构建产物
- 打开 `build` 目录检查文件是否完整
- 确认入口 HTML 是否正确引用资源
- 观察文件名是否带哈希，便于缓存更新
- 用静态服务器在本地先模拟线上访问

**老赵提醒**：把“构建成功”当起点，不要当终点。真正重要的是：这个构建结果能不能稳定跑在服务器上。

---

## 三、上线前最容易出什么适配问题？

**问题：为什么本地没问题，上线后就各种 404、白屏、接口失败？**

这一节最值钱。很多项目不是写坏的，而是**部署环境和前端路由、资源路径、缓存机制没对齐**。

### 1. 路由刷新导致 404

如果你用的是 React Router，页面路径是前端控制的。开发环境里刷新没问题，是因为开发服务器帮你兜底了。

但上线后直接访问 `/user/list` 这种路由，服务器可能以为你要找一个真实文件，结果当然找不到，于是 404。

#### 解决思路

让服务器把所有非静态资源请求统一转发到 `index.html`，再由前端路由接管。你可以理解成：服务器先别判断这是不是某个真实页面，先把入口文件交给前端，剩下的由 React 自己处理。

### 2. 资源路径不对

如果项目部署在子路径下，比如 `https://example.com/app/`，资源引用就不能默认按根路径找，否则图片、JS、CSS 都可能加载失败。

#### 检查点

- 项目是不是部署在根目录
- CRA 的静态资源路径是否正确
- 是否用了适合当前部署路径的配置

很多白屏问题，不是代码逻辑炸了，而是入口 JS 根本没加载进来。你看到的是白屏，实际问题却是资源路径错了。

### 3. 缓存问题别忽视

构建时的文件名哈希，本来就是为了让浏览器识别新旧版本。但还要注意：

- HTML 不要被缓存太久
- JS/CSS 可以靠文件哈希做强缓存
- 发布新版本后，用户是否能及时拿到最新资源

这个地方很容易出现“我已经更新了，用户怎么还是老页面”的情况，通常就是缓存策略没配好。

### 4. 错误页面要准备

别让用户出问题时只看到空白。至少要考虑：

- 404 页面
- 网络异常提示
- 接口失败提示
- 服务器维护提示

这些看起来像细节，但上线体验全靠它们撑着。做真实项目，不能只想着“正常时怎么展示”，还得想“异常时用户怎么办”。

### 可复制的代码思路

- 前端路由统一交给 `index.html` 兜底
- 资源路径按部署位置调整
- HTML 和静态资源采用不同缓存策略
- 提前准备基础错误页和异常提示页
- 发布前模拟刷新、直达、深层路由访问

### 老赵经验总结

线上问题里，最常见的不是“功能没写”，而是“写的时候没想上线环境”。  
**你只要记住一句话：本地能跑，不代表线上能跑。**  
上线适配，才是前端项目从“练习”变成“交付”的分水岭。

## 四、项目怎么部署？静态服务器和 Nginx 要怎么理解？

**问题：打包后的项目到底怎么放到线上去？**

先说最基础的思路：CRA 项目打包后，本质上是静态文件，所以它适合部署到**静态服务器**上。服务器负责把文件发给浏览器，真正的页面逻辑还是浏览器执行。

### 1. 静态服务器的作用

静态服务器最核心的职责只有两个：

- 提供 HTML、JS、CSS、图片等文件
- 按规则处理前端路由和资源请求

只要这个逻辑通，React 项目就能跑起来。换句话说，前端部署的重点不是“服务器要会跑 React”，而是“服务器要会正确分发静态资源”。

### 2. Nginx 为什么常见

Nginx 在前端部署里很常见，原因很简单：

- 性能好
- 配置灵活
- 适合静态资源托管
- 能处理路由转发和反向代理

你不需要一上来就把 Nginx 学成专家，但至少要知道它在项目里的位置：**它是前端静态资源和浏览器之间的中间管家**。浏览器请求页面，Nginx 帮你把正确的文件送回去；接口请求过来，它也可以按规则转发给后端。

### 3. 常见配置方向

这里不展开服务器教程，只讲前端需要理解的方向：

- 把 `build` 目录内容映射到网站根目录
- 配置前端路由刷新时返回 `index.html`
- 让静态资源正确可访问
- 如有接口代理，把 API 请求转发到后端服务

你可以先记住一句话：  
**前端部署不是把代码扔上去就完事，而是要让“资源访问”和“路由访问”都按预期工作。**

### 4. 部署链路怎么走

老赵给你画一个简单链路：

1. 本地完成开发和测试
2. 执行 `npm run build`
3. 把 `build` 产物上传到服务器
4. 由静态服务器或 Nginx 托管这些文件
5. 浏览器访问域名
6. Nginx 返回入口文件和静态资源
7. 前端路由接管页面逻辑
8. API 请求再按配置转发到后端

这条链路看懂了，你就知道前端部署不是“神秘黑盒”，它就是文件分发和访问规则的组合。

### 可复制的部署思路

1. 本地执行 `npm run build`
2. 检查 `build` 目录是否完整
3. 把 `build` 内容上传到服务器对应目录
4. 配置静态资源访问
5. 配置前端路由刷新兜底
6. 配置接口代理或确认接口地址
7. 重载服务并验证访问

如果是团队协作，最好把这套流程写成部署说明文档，别靠口头传。口头传到后面，十有八九会漏步骤。

### 老赵经验总结

部署这件事，核心不是“把文件传上去”，而是“把访问规则配对好”。  
**静态资源能找到，前端路由能兜底，接口请求能通，这个项目才算真正上线。**

## 五、发布后怎么验证？别只看首页能不能打开

**问题：上线后怎么确认项目真的没问题？**

项目发布后，最怕的不是报错，而是“看起来能用，其实半残”。所以验证要分层做。

### 1. 页面访问验证

先确认基础页面：

- 首页能不能正常打开
- 二级路由能不能直接访问
- 刷新后是否还在
- 404 页面是否正确显示

建议别只点首页，一定要测试“直接输入地址访问深层路由”，再试刷新。因为这一步最容易暴露路由配置问题。

### 2. 请求连通验证

再看接口链路：

- 登录接口是否正常
- 列表接口是否返回数据
- 提交表单后是否有正确反馈
- 跨域或代理是否生效

如果项目里做了请求封装，就更要检查统一入口有没有在生产环境拿到正确的 baseURL。很多线上故障就是请求发出去了，但发到了错误地址，结果页面一直转圈或返回空数据。

### 3. 性能和资源验证

重点观察：

- 首屏加载是否明显变慢
- 图片是否过大
- 是否有重复请求
- 是否存在加载失败的静态资源

你不一定要一上来就做复杂优化，但至少要看得懂：页面卡是资源太大，还是请求太多，还是某些组件重复渲染导致的。会做项目的人，不能只会点功能，还得能看出项目哪里不顺。

### 4. 版本回滚思路

上线不是只考虑“成功”，还要考虑“出问题怎么办”。

一个简单的回滚思路是：

- 保留上一版构建产物
- 保留配置快照
- 新版本出问题时快速切回上一版
- 回滚后第一时间验证核心路径

别觉得回滚是“高级运维才要考虑的事”。实际上，任何认真交付的前端项目，都应该有最基本的版本恢复意识。

### 可复制的代码思路

- 发布后按“页面、请求、资源、缓存”四层验证
- 深层路由必须单独测试
- 接口失败要有明确提示
- 保留上一版构建包，必要时快速回退
- 验证通过后再通知业务方或团队切换正式入口

### 老赵经验总结

真正成熟的交付，不是“永远不出问题”，而是“出了问题能快速恢复”。  
项目上线不是终点，**它只是从开发环境走向真实环境的开始**。

## 六、这一章你要带走什么？

**问题：打包上线这件事，核心到底是什么？**

核心就一句话：**开发完成不算完，能稳稳上线，才算把项目真正做完。**

你要记住这套上线思维链：

- 先做上线前检查：环境变量、接口地址、资源路径、代码清理
- 再理解 CRA 打包结果：`build` 目录就是上线产物
- 然后处理上线适配：路由刷新、缓存、资源路径、错误页
- 接着选择合适的部署方式：静态服务器、Nginx、代理配置
- 最后做发布验证：访问、请求、性能、回滚

### 老赵经验总结

很多新手写项目，最容易把“代码写完”当成“项目做完”。其实不是。  
**会写组件，是基础；会把项目打包上线，才说明你真的理解了前端工程。**

你以后做项目，一定要养成这个习惯：  
不是只盯着开发过程，而是从一开始就想着“这东西最后怎么上线”。这样你写出来的代码，才更像一个真正能交付的项目。

### 可复制的部署检查单

上线前，你可以直接照着这份清单过一遍：

- [ ] `.env` 和环境变量已切到生产配置
- [ ] 请求封装里的接口地址已确认
- [ ] 静态资源路径已检查
- [ ] `console.log`、测试代码和临时页面已清理
- [ ] `npm run build` 执行成功
- [ ] `build` 目录内容完整可用
- [ ] 线上路由刷新不会 404
- [ ] 首页、列表页、详情页、表单页都能访问
- [ ] 核心接口连通正常
- [ ] 404 页面和错误提示已准备
- [ ] 新版本与上一版本都已留档
- [ ] 出问题时有回滚方案

### 行动建议

如果你手头有这个 CRA 项目，建议你现在就做三件事：

1. 手动检查一遍环境变量和接口地址  
2. 执行一次完整构建，观察 `build` 目录内容  
3. 模拟线上访问，重点测试刷新、静态资源和接口请求  

把这三步做完，你对“上线”这件事，就不再只是听说，而是真正走过一遍了。

# 第11章：结语 / 项目复盘：完整项目回顾与能力提升总结

## 开篇引入：别把这本书学成“零件收藏册”

前面十章，我们一直在做一件事：把一个基于 CRA 的 React 项目从零搭起来，再一点点补齐它该有的能力。你可能会发现，单看每一章都不难：会写组件、会用 `useState`、会发请求、会做路由，似乎都懂了。  
但真正到了项目里，难点从来不是“我知道这个 API”，而是“我知道在什么位置用它、为什么这么用、用完之后怎么和别的部分接起来”。

这也是很多人学完 React 后最容易踩的坑：知识点都认识，真到自己开新项目，还是不知道从哪下手。于是组件写了一堆，状态也有了，请求也发出去了，可页面就是乱，逻辑就是散，最后连自己两天前写的代码都看不懂。

所以这一章不再讲新技术点，而是把整条链路重新串起来：**从初始化到上线，每一步解决了什么问题；组件、状态、请求、路由和异步处理是怎么协同工作的；以及你学完这套方法后，怎么迁移到新项目里。**

## 一、从初始化到上线：每一步到底解决了什么问题？

如果把本书项目当成一条流水线，它大致是这样走的：

### 1. CRA 初始化：先把“地基”打稳

CRA 的作用，不只是让你少敲几行命令，而是帮你快速拿到一个能跑、能改、能扩展的前端骨架。  
这一阶段解决的是“项目从哪开始”的问题。

你会得到：

- 基础目录结构
- 开发服务器
- 构建命令
- 静态资源处理能力

最关键的不是“跑起来”，而是建立一个稳定起点。比如你知道 `src` 里放业务代码，`public` 放静态入口，组件、页面、请求、工具各自该待在哪儿。目录一清楚，后面功能再多也不会乱。

**判断标准**很简单：项目能不能启动，目录是否清晰，后续功能有没有地方放。

### 2. 页面布局：先把“骨架”搭出来

布局阶段的核心不是美化，而是把页面拆成合理区域，比如头部、筛选区、列表区、详情区、操作区。  
这一步解决的是“页面怎么组织”的问题。

实战里先别急着上细节样式，先把区域摆出来。比如一个列表页，先确认顶部有没有搜索条件，下面是不是表格或卡片列表，底部需不需要分页，右侧是否要留操作区。结构稳了，样式和功能才有落点。

### 3. 组件拆分：把“大页面”拆成“小零件”

真正的 React 项目，不是把所有 JSX 堆在一个文件里，而是根据职责拆组件。  
比如：

- `Header` 负责头部
- `SearchBar` 负责筛选
- `ItemList` 负责列表展示
- `Pagination` 负责翻页
- `Modal` 负责弹窗

这一步解决的是“代码怎么维护”的问题。

拆组件时有个实用判断：**一个部分如果有独立职责、独立状态、独立交互，就值得拆出来。**  
别为了拆而拆，也别图省事把所有逻辑塞进一个文件。前者容易过度设计，后者会让后期维护很痛苦。

## 二、状态、请求、路由和异步处理，是一条链，不是四张表

很多人学 React 时，容易把这些知识点拆开看。其实在项目里，它们是一条链。

### 1. 状态负责“记忆”

`useState` 的实战用法，不只是记住一个输入框的值，更重要的是让页面知道：

- 当前列表是什么
- 有没有加载中
- 当前选中了谁
- 弹窗是否打开
- 搜索条件是什么

状态明确了，页面逻辑就不会乱。你写代码时也会更清楚：这个值是谁改的、什么时候改的、改了以后影响哪里。

### 2. 请求负责“获取真实数据”

前端项目一旦接入接口，很多逻辑就从“本地演示”变成“真实协作”。  
这时候请求封装就很关键：统一 `baseURL`、统一错误处理、统一返回值处理，后面页面会轻松很多。

比如统一处理 token、统一打印错误、统一转换数据格式，页面里就不用到处写重复代码。页面只管“我要什么数据”，请求层负责“怎么去拿”。

### 3. `useEffect` 负责“把时机接上”

`useEffect` 的实战用法，核心不是“写一个副作用”，而是把页面什么时候该请求、什么时候该重新计算、什么时候该同步状态这件事接起来。  
它通常会配合首次加载、筛选条件变化、分页切换一起出现。

你可以把它理解成：页面一打开先拉一次数据，条件变了再拉一次数据，某个状态变化后顺手更新页面逻辑。  
这就是 `useEffect` 在项目里的位置——不是摆设，是时机控制器。

### 4. 路由负责“页面切换”

路由不是为了炫技，而是为了把业务拆成多个清晰入口。  
列表页、详情页、编辑页、登录页，都是典型场景。

有了路由之后，页面之间的关系就不是“点一下显示一下”那么粗糙，而是变成了更清晰的业务导航。用户看起来顺，开发也更好维护。

### 5. 异步处理负责“别让页面失控”

请求不是同步动作，加载、超时、失败、重复点击，都会让页面出问题。  
所以项目里必须考虑：

- 请求前显示 loading
- 请求中避免重复提交
- 失败后给出提示
- 请求结束后恢复页面状态

你可以把它理解成：组件是骨架，状态是神经，请求是血液，路由是通道，异步处理是刹车和方向盘。少了哪一个，项目都能跑，但跑不稳。

## 三、从基础语法到工程化思维，你到底提升了什么？

学完这套项目，你的提升不只是“会写更多代码”，而是思考方式变了。

### 1. 从“写功能”变成“拆问题”

以前可能是：这个按钮点一下就行。  
现在会先想：

- 按钮属于哪个组件？
- 触发后修改哪个状态？
- 是否需要请求接口？
- 请求回来后影响哪些区域？
- 失败怎么处理？

这就是工程化思维的起点。你开始关注“系统怎么协作”，而不是只盯着“这个按钮怎么点”。

### 2. 从“单文件思维”变成“模块协作”

以前很多人喜欢一个页面写到底。  
现在你会知道：页面负责组织，组件负责复用，状态负责联动，请求负责数据，路由负责跳转。每一层各管一摊，后期维护成本会低很多。

### 3. 从“能跑就行”变成“可扩展”

项目实战真正值钱的地方，不是当前功能能跑，而是后面还能接着长。  
比如今天做列表，明天加分页、筛选、详情、编辑，不需要推倒重来。  
这就是项目思维和练习题思维的区别：练习题只看结果，项目还要看后续。

## 四、后续扩展方向：如果项目继续做，应该怎么长？

本书的项目已经把基础链路打通了，但真实项目往往还会继续扩展。下面这些方向，都是很常见的升级点。

### 1. 列表分页与筛选

当数据变多后，单页展示肯定不够。  
你需要考虑：

- 当前页码
- 每页条数
- 总数
- 筛选条件变化后是否回到第一页

这里有个实用习惯：筛选条件一变，通常要把页码重置回第一页，不然用户可能还停在一个不合适的页数上。

### 2. 权限控制

不同角色看到的页面和按钮可能不同。  
这时路由守卫、按钮级权限、菜单级权限就会登场。  
虽然本书没有把权限做成重点，但你已经具备继续扩展的基础：有了路由和组件拆分，权限就能逐步接进去。

### 3. 缓存与优化

一些不常变的数据，可以缓存起来，减少重复请求。  
比如搜索条件、用户信息、字典数据等。  
这类优化不一定一开始就上，但你至少要知道它存在，不然项目一大就容易重复请求、重复渲染。

### 4. 复杂表单

一旦进入新增、编辑场景，表单会越来越复杂。  
你要考虑：

- 默认值初始化
- 联动字段
- 提交校验
- 异步回填

表单最常见的问题不是“不会写”，而是“状态太多，容易乱”。所以写复杂表单时，先画结构，再定状态，再接交互，通常会稳很多。

### 5. 更完整的状态方案

当页面间共享状态变多后，单靠局部状态会开始吃力。  
这时就要思考更完整的状态组织方式，但具体用哪种方案，要看项目规模，不要上来就为了高级而高级。

## 五、把本书的方法迁移到新项目：靠什么复用？

很多人看完一本书，最大的问题不是“没学会”，而是“下一个项目不会用了”。  
其实复用的关键，不是背代码，而是复用方法。

### 1. 模板化：先准备通用起手式

你可以把项目起步阶段整理成自己的模板：

- CRA 初始化步骤
- 常用目录结构
- 请求封装方式
- 常见布局组件
- `loading` / `error` / `empty` 状态写法

这样下次新项目来了，你不是从零找感觉，而是直接按自己的模板推进。

### 2. 组件化：把高频模块沉淀下来

像表格、弹窗、分页、搜索栏、确认框，这些都很适合沉淀为通用组件。  
下次新项目来，不是从头写，而是直接拿来改。  
组件一旦复用起来，你会明显感觉开发节奏快了很多。

### 3. 流程化：把开发顺序固定下来

一个好用的项目打法，通常顺序都差不多：

1. 初始化项目  
2. 搭页面结构  
3. 拆组件  
4. 接请求  
5. 管状态  
6. 做交互  
7. 补路由  
8. 处理异常  
9. 打包部署

```jsx
// 3. 页面组件基本套路
function Page() {
  const [loading, setLoading] = useState(false);
  const [list, setList] = useState([]);
  const [query, setQuery] = useState({ keyword: '', page: 1 });

  useEffect(() => {
    loadData();
  }, [query.page, query.keyword]);

  const loadData = async () => {
    setLoading(true);
    try {
      const res = await requestList(query);
      setList(res.data || []);
    } finally {
      setLoading(false);
    }
  };

  return <div>{/* 页面布局 + 组件组合 */}</div>;
}
```

```js
// 4. 请求封装基本套路
export function requestList(params) {
  return http.get('/list', { params });
}
```

这套模板的核心不是代码多，而是顺序清楚：**先搭骨架，再拆组件，再管状态，再接请求，再处理异常，最后补路由和上线。**

## 老赵经验总结：学会一套项目打法，比背一堆零散知识更值钱

React 基础语法当然要会，但真正拉开差距的，不是你知道多少 API，而是你有没有一套能落地的项目思路。

老赵一直觉得，学项目最怕两种状态：  
一种是只会看别人代码，自己一上手就懵；  
另一种是记住了一堆知识点，却不知道怎么串成一个能上线的产品。

所以你学完这本书，最重要的不是把每一章背下来，而是形成自己的习惯：

- 先看项目结构，再写功能
- 先拆组件，再补逻辑
- 先理状态，再接请求
- 先处理异常，再考虑优化
- 先完成闭环，再追求高级方案

这就是从“会写组件”到“会做项目”的真正跨越。  
你把这套打法学会了，后面换业务、换页面、换需求，心里都会更稳。
