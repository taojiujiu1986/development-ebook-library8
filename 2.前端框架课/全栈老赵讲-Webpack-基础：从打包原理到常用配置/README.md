# 第1章：Webpack 到底是干什么的，为什么前端工程化绕不开它

## 开篇引入：先把“Webpack 很复杂”这个印象放一放

很多人第一次听到 Webpack，脑子里会冒出打包、loader、plugin、配置文件这些词，听着就容易发怵。其实全栈老赵先给你一句实话：**Webpack 本质上就是一个前端资源组织和输出工具**。它负责把项目里的 JavaScript、CSS、图片、字体等资源按规则整理、转换，最后输出成浏览器能直接使用的构建结果。

前端项目一小，手写 `<script>`、`<link>` 还能凑合；项目一大，模块一多，资源类型一杂，人工管理就很容易乱。Webpack 的价值，就是把这些零散资源纳入同一条构建链路，让“开发时怎么写”和“上线时怎么交付”之间有一个明确、可控的转换过程。

所以你会发现，Webpack 之所以在前端工程化里绕不开，不是因为它多神秘，而是它正好解决了前端项目从开发到发布的一整套现实问题。理解它在做什么，后面的入口、出口、loader、plugin、代码分割这些概念，才会连成一条线。

---

## 一、Webpack 是什么：它到底在前端里扮演什么角色？

### 1.1 从“静态资源打包器”到“前端构建工具”

按本书的说法，Webpack 一开始可以理解成一个**静态资源打包器**：从一个入口开始，顺着依赖关系把相关文件找出来，经过处理后输出构建产物。

但在真实项目里，它早就不只是“打包”这么简单了。它还负责：

- 识别模块依赖
- 转换不同类型的资源
- 生成适合运行环境的输出文件
- 配合开发服务器提升调试体验
- 支持按需加载、缓存优化等能力

你可以把它理解成前端构建里的“总调度”：不直接写业务，但负责把业务代码变成能稳定运行、能顺利发布的产物。

### 1.2 为什么前端项目需要打包？

项目一大，常见问题就来了：

- 文件多，手动引入容易乱
- 模块依赖复杂，维护困难
- CSS、图片、字体分散在不同目录，发布不统一
- 一些语法或资源格式，浏览器不能直接识别

打包的意义，就是把这些资源组织起来。开发时按模块拆分，发布时再由构建工具统一收口。**开发阶段要方便，发布阶段要稳妥**，Webpack 正是连接这两件事的工具。

### 1.3 Webpack 解决了哪些问题？

Webpack 主要解决的不是“怎么写代码”，而是“怎么把代码交付出去”：

- **开发与发布分离**：开发时便于拆分，发布时便于整合
- **压缩与合并**：减少请求数量，降低体积
- **兼容与处理**：把浏览器不一定直接支持的资源先处理好
- **资源统一管理**：JS、CSS、图片、字体都能纳入一套流程

#### 老赵给你画重点
- Webpack 的核心角色：**从入口出发，按依赖关系组织资源并输出构建产物**
- 它不仅能打包 JS，也能处理 CSS、图片、字体等静态资源
- 它解决的是“项目如何构建和交付”的问题，不是代码编辑器替代品

#### 赵老师避坑提醒
别把 Webpack 理解成“写前端必须先学会的玄学工具”。它的本质很朴素：**入口进来，依赖找齐，资源处理，最后输出**。抓住这条线，很多配置就自然有意义了。

## 二、入口、出口、模式：Webpack 的基本骨架长什么样？

### 2.1 入口：从哪里开始找依赖？

入口就是 Webpack 开始分析的起点，也就是项目的起始文件。Webpack 会从入口出发，递归寻找它依赖的其他模块，再继续往下找，直到把整张依赖图摸清楚。

比如常见的 `src/index.js`，里面引入 `App.js`、`style.css`，`App.js` 再引入组件和工具函数。Webpack 不是“盲打包”，而是沿着 `import` 或 `require` 的关系一步步收集依赖。

### 2.2 出口：最终输出到哪里？

出口指的是打包完成后，构建产物放到哪里、叫什么名字。通常会是 `dist` 这样的目录。这个目录里的文件就是浏览器最终要加载的结果，也就是**构建产物**。

出口之所以重要，是因为上线不是把源码目录直接丢给服务器，而是要把构建后的文件交给部署系统。输出路径、文件名规则、是否带 hash，都会影响缓存和更新策略。

### 2.3 模式：告诉 Webpack 你现在是在开发还是发布

模式通常可以理解为运行场景提示：

- 开发模式：更关注调试体验
- 生产模式：更关注体积、速度和稳定性

它会影响 Webpack 的默认行为。你可以把它当成一句提醒：**“老兄，我现在是开发，还是上线。”**

#### 老赵给你画重点
- **入口**决定从哪里开始分析依赖
- **出口**决定打包结果放哪里
- **模式**决定构建策略偏向开发还是生产

#### 赵老师避坑提醒
很多初学者只盯着出口文件名，却忘了入口才是依赖分析的起点。Webpack 不是扫整个文件夹，而是从入口开始顺着关系找出来的。

## 三、Webpack 解决了哪些问题：它不是单纯压缩工具

### 3.1 开发与发布的不同需求

开发阶段，我们希望改完代码马上看到效果，报错定位要快；发布阶段，我们希望文件更小、加载更稳、用户打开更快。Webpack 的作用，就是把这两种需求统一进一套配置体系里。

### 3.2 压缩、合并、处理资源

Webpack 在构建中会把多个模块整合成一个或多个 bundle，并对资源做处理，比如：

- 把多个 JS 模块组织成可执行代码
- 把 CSS 从模块中抽离或注入
- 把图片、字体等资源变成可引用的输出结果

你在源码里可以按模块舒服地拆，到了构建阶段，Webpack 再按规则整理好。对团队协作来说，这种方式很重要，因为大家都按模块开发，最后由构建工具统一收口，工程会稳定很多。

### 3.3 兼容与工程化流程

前端项目里常有一些浏览器不直接认识的内容，比如更现代的语法、模块化写法，甚至各种静态资源引用方式。Webpack 的价值之一，就是把这些内容转成最终能运行的形式。

它不是简单搬运文件，而是在构建过程中完成转换。源码进去，成品出来，这就是它的工作方式。

#### 老赵给你画重点
- Webpack 不只是“压缩工具”，更像**项目构建流水线**
- 它把“开发时的舒服”和“发布时的可靠”连接起来
- 资源处理是重要组成部分，不止 JS

#### 赵老师避坑提醒
别把“打包”简单理解成“把文件塞进一个大文件”。真实情况更灵活：有时是一个 bundle，有时是多个 chunk；有时会抽离公共部分。构建结果不是越少文件越好，而是要看场景。

## 四、构建产物长什么样：从入口文件到 bundle

### 4.1 什么是构建产物？

构建产物就是 Webpack 最终生成的结果文件，通常位于输出目录中，是浏览器真正加载的对象。

这些文件不一定长得像源码，可能被重新命名、压缩，或者拆成多个部分。文件名、目录结构、是否带 hash，都是构建过程设计出来的结果。

### 4.2 从入口到 bundle 的基本过程

这个过程可以简单理解为三步：

1. 从入口文件开始
2. 读取入口依赖的模块和资源
3. 按规则转换、整理，生成输出文件

最后得到的 bundle，本质上是一个能够承载依赖关系和运行逻辑的打包结果。Webpack 会帮你处理依赖顺序和加载关系，你不需要手动拼接文件。

### 4.3 为什么要关心构建产物？

因为你开发时写的代码，和浏览器最终执行的代码不是一回事。理解构建产物，有助于你判断：

- 为什么某个文件变大了
- 为什么资源被拆出来了
- 为什么上线后路径和本地不一样

如果只会配、不看产物，就很容易出现页面能跑但不知道为什么这么跑的情况。真正成熟的前端工程化，不只是会写配置，更是能看懂构建结果。

#### 老赵给你画重点
- 构建产物不是源码原样复制
- 它是 Webpack 按规则整理后的结果
- 理解产物，才能判断构建是否合理

#### 赵老师避坑提醒
看到输出目录里文件名很长、带 hash，别急着嫌乱。很多时候这是为了缓存和更新策略服务的，先搞清楚它为什么这么做。

## 五、Webpack 和 Vite、Rollup 等工具有什么不同？

### 5.1 先建立正确预期

这些工具都和前端构建有关，但侧重点不同。学 Webpack 的重点，不是先比谁更快，而是先搞明白：**前端构建到底是怎么从源码走到产物的**。

### 5.2 你可以这样理解

- **Webpack**：通用型构建平台，能力全面，生态成熟，适合复杂项目
- **Rollup**：更偏库打包，输出结果通常更干净
- **Vite**：更强调开发体验，启动快、热更新体验好

Webpack 不一定是“最快启动”的，但它在通用能力和可配置性上很强，这也是它在很多存量项目和中大型项目里依然常见的原因。对不少团队来说，它的价值还在于“稳”。

#### 老赵给你画重点
- 工具没有绝对优劣，关键看场景
- Webpack 的强项是**通用、可扩展、可控制**
- 学 Webpack，学的是构建原理和配置思路，这些能力能迁移到其他工具

#### 赵老师避坑提醒
别把“Vite 很快”理解成“Webpack 过时了”。工具会进化，但工程思维不会过时。

接下来真正要记住的，不是某个配置项的名字，而是这条主线：**入口 → 依赖分析 → 资源处理 → 输出产物**。后面我们讲 loader、plugin、开发服务器、source map 的时候，都是在这条线上的不同环节。

# 第2章：入口、出口、模式，先把一个最小 Webpack 项目跑起来

上一章我们先摸了下 Webpack 的脾气。这一章别急着啃大概念，先动手搭一个**最小可运行的 Webpack 项目**。前端工程化里，很多东西只看定义会很虚，真正跑起来一次，你才会明白：Webpack 到底从哪进、往哪出、怎么决定打包环境。

这一章只讲三个最核心的配置项：**entry、output、mode**。把这三个吃透，后面 loader、plugin、资源处理和优化，都会顺很多。

## 一、Webpack 项目初始化流程：安装、目录结构、基本命令

### 1. 先把项目骨架搭起来

最小 Webpack 项目不用一上来就搞复杂结构，先让它跑起来再说：

```bash
mkdir webpack-demo
cd webpack-demo
npm init -y
npm install webpack webpack-cli -D
```

这几步分别是：

- `npm init -y`：生成 `package.json`
- `webpack`：Webpack 核心包
- `webpack-cli`：让你能在命令行执行 `webpack`

基础目录建议这样放：

```text
webpack-demo
├─ src
│  └─ index.js
├─ dist
├─ webpack.config.js
└─ package.json
```

这里可以把它理解成三层分工：

- `src`：源码
- `webpack.config.js`：告诉 Webpack “怎么打”
- `dist`：打包产物

很多人学工程化时容易把源码、配置、产物混在一起，项目越做越乱，最后自己都分不清哪些该改、哪些是生成出来的。

### 2. 基本命令怎么跑

最常见两种方式：

```bash
npx webpack
```

或者在 `package.json` 里加脚本：

```json
{
  "scripts": {
    "build": "webpack"
  }
}
```

然后执行：

```bash
npm run build
```

Webpack 默认会找 `webpack.config.js`。它确实有默认行为，但“默认能跑”不等于你已经掌握了它。学习 Webpack 最怕的就是只知道结果，不知道为什么。

### 3. 一个最小入口文件

先在 `src/index.js` 里写一句：

```js
console.log('Webpack is running!')
```

执行构建后，如果正常，`dist` 里会生成打包结果。这个结果虽然简单，但意义很明确：Webpack 已经从源码出发，完成了从“源代码”到“构建产物”的转换。

### 老赵给你画重点

- 最小骨架就是：`src` 放源码，`dist` 放产物，`webpack.config.js` 放配置。
- `webpack` 和 `webpack-cli` 是基础组合，没有 CLI 就不好执行命令。
- 先别急着上 loader、plugin，先把“项目能跑”这件事搞定。
- 学 Webpack 的第一步，是先看到构建结果。

### 赵老师避坑提醒

- 别把源代码和打包结果混在一起放。
- 别以为装了 Webpack 就自动会打包，`entry`、`output`、`mode` 不写清楚，项目虽然能跑，但你很难控制产物。
- `dist` 一般是构建生成的，不建议手工写业务代码。
- 第一次跑不通，先看目录和路径，十有八九是基础问题。

## 二、入口 entry 的作用：从哪里开始找依赖

### 1. entry 到底是什么

`entry` 可以理解成：**Webpack 开始递归查找依赖关系的起点**。它不只是“页面入口”，更是依赖图的起点。Webpack 会从这个文件出发，顺着 `import`、`require` 往下找，把所有依赖收进来。

比如：

```js
// src/index.js
import './a.js'
import './b.js'
```

Webpack 会先读 `index.js`，再找到 `a.js`、`b.js`，然后继续往下追，构建一张**依赖图**。

### 2. entry 的常见写法

最基础的写法：

```js
module.exports = {
  entry: './src/index.js'
}
```

更明确一点，也可以写成对象：

```js
module.exports = {
  entry: {
    main: './src/index.js'
  }
}
```

单页项目常用字符串写法，多页或复杂项目更适合对象写法。入口一复杂，多入口就很常见。

### 3. 为什么入口这么重要

入口决定了这次构建从哪里开始算。Webpack 只会从 `entry` 出发，沿着依赖关系去找显式引入的模块。没被入口链路连上的文件，默认不会进产物。

所以，`entry` 不是单纯的路径配置，而是 Webpack 构建思路的起点。入口错了，后面就容易出现模块找不到、构建结果不完整、页面引不进代码这些问题。

### 老赵给你画重点

- `entry` 是 Webpack 构建依赖图的起点。
- 它决定“先从谁开始找”。
- 单入口用字符串，多入口用对象。
- Webpack 不是扫目录打包，而是从入口顺着依赖找。

### 赵老师避坑提醒

- 别把 `entry` 理解成 HTML 里的 `<script>` 标签。
- `entry` 路径写错，Webpack 会直接报错，初学者最常见的问题就是路径写歪。
- 入口文件里如果没真正引入其他模块，打包结果会很单薄，这不是 Webpack 没干活，而是你没给它依赖可追。
- 多入口项目里，入口名和输出名要提前想清楚，不然产物命名会乱。

---

## 三、出口 output 的作用：打包结果输出到哪里、叫什么名字

### 1. output 是干什么的

`output` 负责告诉 Webpack：**打包后的文件放哪、叫什么**。

最基础的配置如下：

```js
const path = require('path')

module.exports = {
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: 'bundle.js'
  }
}
```

这里两个关键点：

- `path`：输出目录，必须是绝对路径
- `filename`：输出文件名

entry 决定“从哪出发”，output 决定“打完之后落在哪”。

### 2. 为什么必须理解 output

构建产物不是自然长出来的，它必须有明确的落点。Webpack 会把打包后的代码生成到指定目录，再由 HTML 去引用这些产物。

如果 `output` 不清楚，你会发现：

- 文件不知道输出到哪里
- 文件名不稳定，调试麻烦
- 后续做缓存策略不好推进

### 3. 文件名为什么不能随便写

最简单可以写死：

```js
filename: 'bundle.js'
```

但真实项目里通常会带占位符：

```js
filename: '[name].js'
```

`[name]` 会替换成入口名称。比如入口叫 `main`，最后就会输出 `main.js`。多入口项目里，这样更好维护。

### 老赵给你画重点

- `output.path` 决定输出目录，`output.filename` 决定输出文件名。
- `path.resolve(__dirname, 'dist')` 是最常见写法，因为输出目录要绝对路径。
- 构建产物是否好管理，很大程度看 output 配得清不清楚。
- 产物命名清楚，后面调试、部署、缓存都会顺一点。

### 赵老师避坑提醒

- `path` 一定要是绝对路径，别直接写 `'dist'`。
- 别把输出文件名永远写死成 `bundle.js`，项目一复杂就不好维护。
- 多入口项目里，`filename` 写法要谨慎，否则不同入口可能互相覆盖。
- 构建成功但找不到产物，先查输出路径。

## 四、模式 mode 的作用：development、production、none 的区别

### 1. mode 是什么

`mode` 用来告诉 Webpack：**当前是开发环境、生产环境，还是不启用默认优化**。

```js
module.exports = {
  mode: 'development'
}
```

它不是装饰项，会直接影响构建行为。你可以把它理解成 Webpack 的“工作模式开关”。

### 2. 三种模式怎么选

#### development

开发模式，强调：

- 构建速度快
- 调试友好
- 更适合开发阶段

本地开发最重要的是看得清、改得快、报错能看懂，不是一上来就追求极致压缩。

#### production

生产模式，强调：

- 产物更小
- 默认会做一些优化
- 更适合上线发布

正式部署一般应该用它。

#### none

不使用 Webpack 的默认优化，适合你想自己完全控制构建行为的时候。初学阶段了解即可，常用还是 development 和 production。

### 3. mode 为什么值得单独讲

同一份代码，在不同 mode 下，构建结果可能不同，比如是否压缩、是否更适合调试、是否默认做性能优化。

所以，`mode` 不只是一个字符串，它是 Webpack 行为策略的总开关之一。

### 老赵给你画重点

- `development` 适合开发调试，`production` 适合上线发布，`none` 适合自己控制一切。
- `mode` 会影响构建默认优化行为，不是“写着好看”的配置。
- 开发和生产要分开思路：开发求快，生产求稳和小。
- 这是后面优化策略的起点。

### 赵老师避坑提醒

- 别忘了设置 `mode`，不设置时行为可能不符合预期。
- 开发和生产不要混用同一套思路。
- 初期想先跑起来，`development` 更适合你观察打包过程。
- 别把 `development` 当成临时写法，它是开发阶段的正式配置。

# 第3章：loader 和 plugin，Webpack 真正变强的关键

前面你已经搞懂了 Webpack 的入口、出口和模式，这一章就进入核心：**Webpack 像一台打包机器，loader 和 plugin 才是让它真正干活的关键。**

## 一、loader 是什么：把非 JS 文件转换成 Webpack 能理解的模块

### 1. loader 的本质是什么？

Webpack 天生擅长处理 JavaScript 模块，但项目里不只有 JS。比如：

```js
import logo from './logo.png'
```

Webpack 自己不懂 `.png` 怎么处理，这时就要靠 loader 把它翻译成可管理的模块。

你可以把 loader 理解成一条“文件加工线”：

- 读到某种文件
- 按规则交给对应 loader
- 转成 Webpack 能处理的内容
- 进入模块依赖图

一句话：**loader 的作用是“翻译文件”，让非 JS 资源进入打包体系。**

### 2. loader 的工作方式

loader 一般写在 `module.rules` 里：

```js
module.exports = {
  module: {
    rules: [
      {
        test: /\.css$/,
        use: ['style-loader', 'css-loader']
      }
    ]
  }
}
```

最容易记错的是执行顺序：**`use` 里从后往前执行。**  
也就是先 `css-loader`，再 `style-loader`。

原因很简单：

- `css-loader` 先把 CSS 解析成依赖
- `style-loader` 再把样式注入页面

顺序反了，常见结果就是样式不生效。

### 3. loader 主要解决什么问题？

loader 适合处理这类“文件转换”需求：

- CSS / SCSS / LESS 转成可处理的样式依赖
- 图片变成模块路径或资源
- 字体文件变成可引用资源
- TS / JSX 转成浏览器能懂的 JS
- Markdown、CSV、XML 等特殊格式

只要它不是原生 JS 模块，但你希望它参与依赖管理，通常就要靠 loader。

### 4. 一个更实战的判断标准

如果你的目标是：

- 把某种文件读进来
- 把它转成另一种 Webpack 能继续处理的格式
- 让它进入模块依赖图

那优先考虑 loader。

### 老赵给你画重点

- loader 的核心作用：**转换文件**
- 主要处理对象：**非 JS 资源**
- 配置位置：`module.rules`
- 执行顺序：**从右到左**
- 它的目标是让 Webpack “看懂更多文件”

### 赵老师避坑提醒

- 不要把 loader 和 plugin 混为一谈
- 不要乱堆 loader，先想清楚“文件要变成什么”
- `use` 顺序写错，是最常见的坑之一
- loader 不负责全局流程控制，它只负责加工模块

---

## 二、plugin 是什么：在打包生命周期中扩展功能

### 1. plugin 解决的是什么问题？

如果说 loader 像流水线上的工人，那 plugin 就像车间里的调度员。它不负责某个文件的转换，而是**介入 Webpack 的整个构建过程**，在关键节点做事。

比如：

- 打包前清空目录
- 打包后生成 HTML
- 构建时注入环境变量
- 输出完成后做统计分析
- 在某个阶段压缩代码

这些事情，loader 干不了，plugin 更合适。

### 2. plugin 的本质

plugin 是通过 Webpack 的钩子机制扩展功能的。可以理解为：Webpack 在构建过程中会不断“发出事件”，plugin 负责监听并处理。

所以 plugin 的特点是：

- 介入的是**构建流程**
- 修改的是**打包行为**
- 影响的是**产物生成、优化、注入、清理、分析**等环节

例如：

```js
const HtmlWebpackPlugin = require('html-webpack-plugin')

module.exports = {
  plugins: [
    new HtmlWebpackPlugin({
      template: './src/index.html'
    })
  ]
}
```

这个插件不是转译 HTML，而是帮助你**自动生成 HTML，并把打包结果注入进去**。这就是 plugin 的典型思路：它不改文件格式，而是优化整个构建流程。

### 3. plugin 适合处理哪些事？

常见的 plugin 场景有：

- 生成 HTML：`HtmlWebpackPlugin`
- 清理输出目录：`CleanWebpackPlugin`
- 定义环境变量：`DefinePlugin`
- 抽离 CSS：`MiniCssExtractPlugin`
- 压缩 JS / CSS：压缩类插件
- 复制静态资源：`CopyWebpackPlugin`
- 分析包体积：`webpack-bundle-analyzer`

你会发现，plugin 更像“项目管理工具”，而不是“文件翻译工具”。它通常出现在构建前、中、后，用来补足 Webpack 默认不做的事。

### 4. 一个更实战的判断标准

如果你的目标是：

- 在打包前后做一件额外的事
- 控制构建过程的某个阶段
- 生成额外产物、注入信息、清理目录、做优化

那优先考虑 plugin。

### 老赵给你画重点

- plugin 的核心作用：**增强构建能力**
- 主要处理对象：**打包流程**
- 配置位置：`plugins`
- 常见能力：生成、清理、压缩、注入、复制、分析

### 赵老师避坑提醒

- plugin 必须 `new` 出来，不是直接塞函数
- 别把“能处理文件”都误判成 plugin
- plugin 太多会让配置变复杂，先解决核心问题
- 不要迷信“插件越多越高级”，可维护性更重要

---

## 三、loader 和 plugin 的区别与配合方式

### 1. 最核心的区别：一个管文件，一个管流程

最简单的判断方法就是：

- **loader：处理某种文件怎么进来**
- **plugin：处理 Webpack 打包过程中怎么运行**

对比一下更清楚：

| 对比项 | loader | plugin |
|---|---|---|
| 作用对象 | 单个文件/模块 | 整个构建流程 |
| 核心职责 | 转换内容 | 扩展能力 |
| 配置位置 | `module.rules` | `plugins` |
| 典型场景 | CSS、图片、字体、TS | HTML、清理、压缩、注入 |
| 触发方式 | 按规则处理 | 挂载生命周期钩子 |

### 2. 它们怎么配合？

真实项目里，它们通常一起工作。比如 CSS 处理链路：

1. `css-loader` 读取 CSS，并处理 `@import` 和 `url()`
2. `style-loader` 或 `MiniCssExtractPlugin` 决定样式如何输出
3. `HtmlWebpackPlugin` 把产物自动注入 HTML
4. 压缩插件在生产环境进一步优化

也就是说，**loader 负责让资源进入模块系统，plugin 负责让构建结果更完整、更好用。**

### 3. 一个实战判断法

遇到需求时，先问自己两个问题：

- 这个需求是不是针对某类文件的转换？
- 这个需求是不是要介入打包流程、生成额外产物或做全局控制？

前者更明显，就优先想 loader；后者更明显，就优先想 plugin。

### 4. 什么时候容易混？

最容易混淆的地方，通常有两个：

- **文件处理后还要影响产物输出**：比如图片、字体、CSS 抽离，看起来既像文件处理，又像构建输出。这时先看“主要任务”是什么：如果是让资源进入模块系统，偏 loader；如果是抽成文件、注入页面、优化输出，偏 plugin。
- **工具名字看起来像插件**：但它实际做的是资源转换，那还是 loader 思路。

所以别只看名字，先看它到底解决什么问题。

### 老赵给你画重点

- loader 和 plugin 是互补，不是对立
- loader 解决“内容怎么进来”
- plugin 解决“构建怎么变强”
- 很多功能是两者配合完成的
- 先判断“文件问题”还是“流程问题”

### 赵老师避坑提醒

- 不要见到第三方扩展就叫 plugin
- 不要因为配置复杂，就默认需要插件
- 很多问题其实是 loader 顺序、规则匹配或输出配置写错了

## 四、常见 loader、plugin 的使用场景总览

### 1. 常见 loader

#### 处理 JavaScript：`babel-loader`
把现代语法转成兼容性更好的 JS，常配合 `@babel/core`、`@babel/preset-env` 使用。像箭头函数、`const`、可选链这些语法，在一些环境里不能直接跑，就需要它。

#### 处理 CSS：`css-loader`、`style-loader`
- `css-loader`：解析 CSS 中的依赖
- `style-loader`：把样式注入页面

如果要把 CSS 抽离成文件，还会配合 `MiniCssExtractPlugin.loader`。开发环境和生产环境的处理方式通常不一样。

#### 处理预处理语言：`sass-loader`、`less-loader`
把 SCSS、LESS 转成 CSS，再交给后续 loader 处理。

#### 处理图片和字体
旧方案常用 `file-loader`、`url-loader`，新版本 Webpack 也可以直接用资源模块。目标都一样：**让图片、字体能被模块化引用。**

### 2. 常见 plugin

#### `HtmlWebpackPlugin`
自动生成 HTML，并把打包产物注入进去。几乎是 Webpack 项目的标配。

#### `CleanWebpackPlugin`
打包前清理输出目录，避免旧文件残留。

#### `DefinePlugin`
定义环境变量，常用于区分开发和生产环境。

#### `MiniCssExtractPlugin`
把 CSS 从 JS 中抽离出来，适合生产环境。

#### `CopyWebpackPlugin`
复制静态资源，比如不需要参与编译的 public 目录文件。

#### 压缩类插件
压缩 JS、CSS，减少体积，提高加载速度，一般放在生产环境。

### 3. 先记场景，再记名字

你不用一口气背完所有工具，先记住它们对应的典型问题：

- 语法兼容：`babel-loader`
- 样式处理：`css-loader`、`style-loader`
- 资源抽离：`MiniCssExtractPlugin`
- HTML 注入：`HtmlWebpackPlugin`
- 清理输出：`CleanWebpackPlugin`
- 环境区分：`DefinePlugin`

### 老赵给你画重点

- loader 负责翻译资源
- plugin 负责生成、清理、注入、压缩、复制
- 最常见组合：JS 处理 + CSS 处理 + HTML 生成 + 生产优化

### 赵老师避坑提醒

- 不要机械背名字，先记它们解决什么问题
- 不同版本里，某些 loader 可能已经被新方案替代
- 别照抄别人的配置，先看自己项目有没有这个需求

## 五、一个最小可运行的配置：先跑起来，再谈优化

很多人学到这里还是会卡住：概念懂了，代码不会写。  
所以先看一个最小可运行的例子，把 loader 和 plugin 串起来。

### 1. 典型目标

我们先实现这些事：

- 入口是 `src/index.js`
- JS 用 Babel 处理
- CSS 能被引入并注入页面
- HTML 自动生成
- 输出到 `dist`

### 2. 配置示例

```js
const path = require('path')
const HtmlWebpackPlugin = require('html-webpack-plugin')

module.exports = {
  mode: 'development',
  entry: './src/index.js',
  output: {
    filename: 'bundle.js',
    path: path.resolve(__dirname, 'dist')
  },
  module: {
    rules: [
      {
        test: /\.js$/,
        exclude: /node_modules/,
        use: 'babel-loader'
      },
      {
        test: /\.css$/,
        use: ['style-loader', 'css-loader']
      }
    ]
  },
  plugins: [
    new HtmlWebpackPlugin({
      template: './src/index.html'
    })
  ]
}
```

### 3. 这份配置分别在做什么？

- `entry`：告诉 Webpack 从哪里开始找依赖
- `output`：告诉 Webpack 打包后放到哪里
- `babel-loader`：处理现代 JS 语法
- `css-loader`：让 CSS 进入模块系统
- `style-loader`：把样式注入页面
- `HtmlWebpackPlugin`：自动生成 HTML 并注入 bundle

这套配置不复杂，但已经能跑起来了。  
学习 Webpack 最重要的一点就是：**先建立最小闭环，再逐步加功能。**

### 4. 为什么要先从最小配置开始？

因为 Webpack 的很多问题不是“不会配”，而是“配太多”。先跑通最小项目，你才能知道：

- 哪个 loader 负责让文件被识别
- 哪个 plugin 负责让页面看到结果
- 删除某一步后，项目会失去什么能力

这比死记配置更有效。

### 5. 一个最小实践建议

如果你现在就想动手，最合适的顺序是：

1. 先只配 `entry`、`output`
2. 再加 `babel-loader`
3. 再加 `css-loader` 和 `style-loader`
4. 最后加 `HtmlWebpackPlugin`

这样你会很清楚每一步到底增加了什么能力。

### 老赵给你画重点

- 最小可运行项目比大而全配置更重要
- loader 和 plugin 最好通过真实配置理解
- 先跑通 JS + CSS + HTML 这条链路，再扩展其他资源
- 能写出最小配置，才算真正开始入门

### 赵老师避坑提醒

- 不要一上来就装十几个插件
- 不要追求一步到位的“生产级完整配置”
- 先保证项目能跑，再谈优化和美化

## 六、如何判断一个需求该用 loader 还是 plugin

### 1. 三步判断法

#### 第一步：看对象
这个需求是针对某种文件，还是针对整个构建过程？

- 针对文件：优先 loader
- 针对流程：优先 plugin

#### 第二步：看结果
你是想让某个文件能被 Webpack 处理，还是想让打包多做一件事？

- 能被处理：loader
- 多做一件事：plugin

#### 第三步：看位置
这个功能应该写在 `module.rules`，还是 `plugins`？

- `module.rules` 基本就是 loader 的地盘
- `plugins` 基本就是 plugin 的地盘

### 2. 几个典型例子

#### 把 SCSS 转成 CSS
这是文件转换问题，应该用 loader。

#### 自动生成 HTML 并注入结果
这是构建流程增强问题，应该用 plugin。

#### 打包前删除 `dist` 目录
这是流程控制，应该用 plugin。

#### 给图片加 hash，方便缓存更新
如果是资源处理链路，更接近 loader 或资源模块配置；如果涉及最终输出和命名策略，也可能和 plugin 配合。不要死记，重点是理解资源处理和产物控制的关系。

### 3. 一个实用清单

你可以直接拿这几个问题判断：

- 这是在处理某种文件吗？
- 这是在把文件转成 Webpack 可理解的模块吗？
- 这是在某个构建阶段执行动作吗？
- 这是在生成额外文件吗？
- 这是在优化最终产物吗？

前两项偏多，想 loader；后两项偏多，想 plugin。

### 老赵给你画重点

- 判断 loader/plugin 的核心，不是名字，而是问题类型
- loader 解决输入资源，plugin 解决构建能力
- 先问“文件还是流程”，再决定配置位置
- 熟练的人，能快速定位需求归属

### 赵老师避坑提醒

- 不要一遇到问题就找“神奇插件”
- 不要把所有功能都交给一个工具链
- 不确定时，先用最小配置验证，再逐步加能力

---

## 七、结尾小结：先会分，再会配，最后才会调

这一章你只要记住一句话：  
**loader 负责把各种文件变成 Webpack 能理解的模块，plugin 负责在打包过程中扩展 Webpack 的能力。**

真正上手时，不要急着背一堆配置，先建立判断框架：

1. 这是文件转换问题，还是构建流程问题？
2. 这是 `module.rules` 管的事，还是 `plugins` 管的事？
3. 这个功能是让资源“进来”，还是让产物“变得更好”？

### 行动建议

接下来你可以做两件事：

- 先用一个最小项目练习 `babel-loader`、`css-loader`、`style-loader`
- 再加上 `HtmlWebpackPlugin`、`CleanWebpackPlugin` 这类基础 plugin，体会它们的分工

如果你愿意继续往前走一步，试着回答三个问题：

- 我这个需求到底是处理文件，还是控制流程？
- 我现在写的配置，真的必要吗？
- 如果删掉一个 loader 或 plugin，项目会发生什么变化？

把这一章吃透，后面处理 JS、CSS、图片、字体时，你就不会一头雾水了。因为 Webpack 真正的能力，不在于“它能打包”，而在于**它知道什么时候该让 loader 出手，什么时候该让 plugin 出手。**

### 老赵给你画重点

- 本章目标：学会判断需求该用 loader 还是 plugin
- loader 处理资源输入，plugin 处理构建增强
- 先跑通最小配置，再扩展功能
- 越早建立“问题分类”思维，后面配置越顺

### 赵老师避坑提醒

- 别被复杂配置吓住，Webpack 的本质并不玄
- 别急着记所有插件名，先记它们解决哪类问题
- 真正的提升来自“能判断、能验证、能改配置”，不是死背文档

# 第4章：处理 JavaScript：从 Babel 到基础代码兼容

## 开篇引入：为什么“写得出来”不等于“跑得起来”

全栈老赵先说句实话：前端里的 JavaScript，不是写完就能跑，还得让构建工具看懂、让浏览器吃得下、让不同环境都能执行。

你在项目里写的代码，常常会包含：

- ES6+ 语法，比如箭头函数、解构、`async/await`
- 模块写法，比如 `import/export`
- 浏览器不完全支持的新特性
- 只在开发阶段有用的调试代码
- 需要规范检查的风格问题

Webpack 负责“打包”，但 JS 能不能顺利进入打包流程，还要看它能不能被正确解析、转译和检查。本章赵老师就带你把 JS 资源处理讲清楚：Webpack 怎么看懂 JS 模块，Babel 为什么几乎是标配，ESLint 怎么放进构建流程，最后再把常见报错排查方法理顺。

你可以把这一章理解成：先让 Webpack “认得”你的 JS，再让它“处理得稳”，最后让产物“跑得通”。

---

## 一、Webpack 中 JS 模块的处理流程：它到底怎么“看懂”你的代码？

### 1. Webpack 处理 JS 的基本思路是什么？

Webpack 对 JS 的处理，不是直接执行代码，而是按流程做分析和转换：

1. 从入口文件开始
2. 读取文件内容
3. 解析 `import` / `require`
4. 找到依赖模块
5. 对模块做转译和处理
6. 生成依赖图
7. 输出 bundle 文件

也就是说，Webpack 关心的不是你代码写得多花，而是：

- 这个文件是不是模块
- 它依赖了谁
- 这些依赖要不要转译
- 最后要不要被合并进产物

比如 `main.js` 里写了 `import Header from './Header'`，Webpack 不会把它当普通代码看过去，而是顺着依赖把 `Header` 找出来，再继续找它的依赖，最后搭出一张依赖图。

### 2. 为什么 JS 是 Webpack 里最核心的资源？

因为 JS 往往是前端应用的控制层。页面加载后，谁来组织逻辑、发请求、渲染组件、管理状态，基本都在 JS 里。

所以 Webpack 处理 JS 的价值主要有三个：

- **统一模块管理**：把散落的模块组织成依赖图
- **语法兼容处理**：让现代语法能在目标环境里运行
- **辅助开发质量**：配合 Babel、ESLint、source map 提升体验

很多人第一次学 Webpack，会把它理解成“压缩工具”，其实远不止。它更像一个工程组织器，而 JS 是它最先接触、也最常处理的资源。

### 3. 处理 JS 时，常见的链路长什么样？

典型链路通常是：

`JS 源码 → loader 转译 → Babel 降级语法 → ESLint 质量检查 → Webpack 打包输出`

关键点是：**Webpack 本身不负责把 ES6+ 语法变成低版本语法**，这件事通常交给 Babel。Webpack 负责“打包”，Babel 负责“转译”。

简单说，Webpack 像总包，Babel 像翻译工，ESLint 像质检员。

### 老赵给你画重点

- Webpack 处理 JS 的核心是“分析依赖 + 组织输出”
- JS 是模块化的核心入口，也是构建链路里最重要的资源类型
- `Webpack + Babel + ESLint` 是 JS 处理的常见组合拳

### 赵老师避坑提醒

- 不要把“Webpack 能打包 JS”理解成“Webpack 自己会降级语法”
- `import`、`require`、`export` 是模块组织方式，和 Babel 的语法转译不是一回事
- 浏览器报语法错时，先看 Babel，别急着怀疑 Webpack

---

## 二、Babel 的作用：转译 ES6+ 语法与兼容不同运行环境

### 1. Babel 到底解决什么问题？

一句话：**Babel 负责把现代 JavaScript 语法，转换成目标运行环境更容易理解的版本。**

比如：

- 箭头函数转成普通函数
- 解构赋值转成基础赋值写法
- `async/await` 转成 `Promise` 相关代码
- 某些新语法按目标环境进行降级

这里要分清两件事：

- **语法转译**：把新语法变成旧语法
- **API 兼容**：比如 `Promise`、`Map` 这些对象是否存在，往往还要靠 polyfill 或运行环境支持

也就是说，Babel 不是万能兼容器，它更擅长处理“写法”，不一定能凭空补齐运行时 API。

### 2. 为什么现代项目几乎都要配 Babel？

因为前端要面对的环境太杂了：

- Chrome、Edge、Safari、Firefox 版本不一致
- 可能要兼容移动端 WebView
- 可能还要兼容企业内网环境
- 团队代码会用很多现代特性

不做转译，代码很容易出现“本地没问题，线上旧环境直接炸”的情况。开发时你觉得 `async/await` 很顺手，但如果线上用户的浏览器不认识这些语法，页面可能在解析阶段就报错。

### 3. Babel 常见配置思路是什么？

常见思路有这些：

- 使用 `babel-loader` 接入 Webpack
- 配置 preset，比如 `@babel/preset-env`
- 根据目标环境决定降级范围
- 按需引入 polyfill 或避免污染全局
- 配合缓存减少重复编译耗时

`@babel/preset-env` 很常见，因为它能根据目标环境自动决定哪些语法需要转译，避免“全部降级”带来的性能浪费。

### 4. 什么时候需要 polyfill？

当你用到某些运行时能力，而目标环境不支持时，就要考虑 polyfill。

例如：

- 某些浏览器没有 `Promise`
- 某些环境不支持 `Array.prototype.includes`
- 某些新对象或新方法缺失

注意，polyfill 不是语法降级，而是补运行时能力。Babel 负责“把句子改写得更朴素”，polyfill 负责“把词典里没有的词补上”。

### 老赵给你画重点

- Babel 解决的是 **JS 语法兼容**
- Webpack 管模块组织，Babel 管现代语法转译
- 语法转译和运行时补齐是两条线，别混在一起

### 赵老师避坑提醒

- 只配 Babel，不代表所有兼容问题都解决了
- `@babel/preset-env` 不是装上就万事大吉，还要结合目标浏览器
- 别把 polyfill 当成越多越好，乱加会增大体积，还可能污染全局

---

## 三、常见 JS 处理配置：规则、排除、包含、缓存

### 1. `rule` 规则怎么写才合理？

Webpack 处理 JS，通常用 `module.rules` 匹配文件。核心就三件事：

- 用什么规则匹配文件
- 用什么 loader 处理
- 处理哪些目录、排除哪些目录

常见思路是：

- 只处理 `.js` / `.mjs`
- 排除 `node_modules`
- 必要时用 `include` 限定范围
- 给 Babel loader 开缓存

如果源码都放在 `src` 目录里，就优先只处理 `src` 下的 JS 文件，既明确又高效。

```js
const path = require('path');

module.exports = {
  mode: 'development',
  entry: './src/index.js',
  output: {
    filename: 'bundle.js',
    path: path.resolve(__dirname, 'dist'),
    clean: true
  },
  module: {
    rules: [
      {
        test: /\.m?js$/,
        include: path.resolve(__dirname, 'src'),
        exclude: /node_modules/,
        use: {
          loader: 'babel-loader',
          options: {
            cacheDirectory: true,
            presets: [['@babel/preset-env']]
          }
        }
      }
    ]
  }
};
```

这个配置里，几个点很关键：

- `test: /\.m?js$/`：匹配 `.js` 和 `.mjs`
- `include`：只处理 `src` 里的源码
- `exclude: /node_modules/`：跳过第三方依赖
- `cacheDirectory: true`：开启缓存，提高二次构建速度
- `@babel/preset-env`：负责按目标环境做语法转译

如果想让配置更干净，也可以把 Babel 配置单独抽到 `babel.config.js` 或 `.babelrc`。

### 2. 为什么通常要排除 `node_modules`？

因为 `node_modules` 里大多数依赖已经是可直接使用的构建产物，没必要每次都重新转译。否则会：

- 构建变慢
- 处理更复杂
- 可能引入额外兼容问题

但也不是绝对。某些第三方包输出的是现代语法，或者需要特殊处理，这时不能一刀切。通常先默认排除，遇到兼容问题再针对性放开。

### 3. `include` 和 `exclude` 怎么理解？

- `exclude`：排除不需要处理的目录
- `include`：只处理指定目录

一般来说，**优先考虑 `include` 限定源码目录**，更明确，也更容易控制构建范围。你可以把它理解成“先圈地，再施工”。

### 4. 缓存为什么重要？

JS 编译，尤其是 Babel 转译，成本不低。开发阶段如果每次改一点代码都全量重编译，体验会很差。

所以常见做法是：

- 开启 loader 缓存
- 配合开发模式减少不必要的优化
- 利用持久化缓存提升二次构建速度

缓存的意义很直接：第一遍慢一点没关系，后面快很多。

### 老赵给你画重点

- JS 处理配置的核心是：**匹配、排除、包含、缓存**
- `node_modules` 通常不处理，但不是永远不处理
- 开发体验好不好，很多时候就看范围控制和缓存有没有做好

### 赵老师避坑提醒

- 不要写成“全项目无脑转译”，构建会越来越慢
- `exclude` 和 `include` 同时用时要小心逻辑冲突
- 路径写法注意跨平台问题，尽量按 Webpack 推荐方式配置

## 四、ESLint 与代码质量检查在构建流程中的位置：它是干什么的？

### 1. ESLint 解决的不是“能不能跑”，而是“写得对不对”

ESLint 不是编译工具，它主要做三件事：

- 发现语法和规范问题
- 提前暴露潜在 bug
- 统一团队代码风格

也就是说，它更像“代码质检员”，不是“代码翻译员”。

比如未使用变量、缩进混乱、命名不规范，这些问题不一定会让程序立刻崩掉，但会让代码越来越难维护。ESLint 的作用，就是在代码进入构建之前先拦一层。

### 2. ESLint 放在构建链路哪个位置更合理？

常见两种方式：

#### 方案一：构建前检查
先跑 ESLint，再执行构建。

优点：
- 早发现问题
- 构建更纯粹

缺点：
- 多一步流程

#### 方案二：构建中检查
借助插件把 ESLint 集成进 Webpack。

优点：
- 一条命令解决
- 问题直接在构建输出里看到

缺点：
- 检查过多可能拖慢构建
- 需要控制好告警和错误策略

个人练习项目里，构建中检查一般够用；团队项目里，则要考虑规则、提交流程和 CI 怎么配合。

### 3. ESLint 的价值在团队协作里更明显

如果只有一个人写代码，风格问题还能忍；一旦多人协作：

- 缩进不统一
- 变量命名乱
- 未使用变量越来越多
- 潜在错误没人提前发现

这些问题会迅速放大。ESLint 不能保证代码一定正确，但能把很多低级问题挡在前面。

### 老赵给你画重点

- ESLint 是代码质量检查，不是编译工具
- 它通常放在构建前或构建流程中辅助检查
- 团队项目里，ESLint 比你想象得更重要

### 赵老师避坑提醒

- 不要把 ESLint 错配成“运行时报错工具”
- 规则太严格影响效率，太宽松又起不到作用
- 构建失败时，先分清是语法错误还是 lint 错误

## 五、JS 相关常见报错与排查思路：别慌，按顺序查

### 1. 常见报错都有哪些类型？

JS 构建报错大致分四类：

#### 语法类
比如 Babel 没处理好，导致新语法被旧环境直接报错。

#### 模块类
比如路径写错、文件后缀没配、导入导出方式不一致。

#### 配置类
比如 loader 顺序错误、规则没命中、插件冲突。

#### 质量检查类
比如 ESLint 发现变量未定义、规则不符合、格式问题。

只要先分清类别，很多报错其实没那么吓人。真正麻烦的是看到红字就慌，然后乱改配置。

### 2. 排查时按什么顺序最省力？

赵老师建议你按这个顺序：

#### 第一步：看报错信息
重点看：
- 出错文件
- 行号
- 报错类型
- 是编译错误还是运行错误

#### 第二步：看规则是否命中
检查 `module.rules` 是否真的匹配到了目标 JS 文件。

#### 第三步：看 Babel 是否生效
如果新语法没被转译，先查 loader 和 preset 配置。

#### 第四步：看模块路径
确认 `import` 路径是否正确，文件名、后缀、别名有没有问题。

#### 第五步：看 ESLint 是否拦截
如果构建卡住但语法没问题，可能是 lint 规则报错。

排查问题不是靠感觉，而是靠链路。源码进来以后，在哪一环出错，就查哪一环。

### 3. 一个实用判断法：报错出在“写法”还是“配置”？

- 如果代码单独拿出来也不合法，可能是写法问题
- 如果代码本身没问题，但构建系统不认，通常是配置问题
- 如果本地可跑，线上报错，优先怀疑兼容和目标环境

比如你用了 `import`，浏览器直接报错，不一定是 JS 不能写 `import`，而是构建链路没处理好，或者你打开的是未经打包的原始文件。再比如本地开发环境正常，换到旧版浏览器就白屏，很多时候不是业务逻辑错了，而是 Babel 没按目标环境完成转译，或者兼容范围设得不对。

### 老赵给你画重点

- JS 报错别乱猜，先分类型：语法、模块、配置、质量检查
- 排查顺序比“瞎改配置”更重要
- 高效调试，是先定位问题类别，再改对应环节

### 赵老师避坑提醒

- 不要一报错就删配置重来，越改越乱
- 遇到模块解析失败，先检查路径和后缀，不要先怀疑 Babel
- 遇到兼容问题，不要只盯着构建日志，也要看目标运行环境

## 结尾小结：JS 处理，本质上是让代码“可构建、可兼容、可维护”

这一章你真正要记住的，不只是怎么配 Babel、怎么挂 ESLint，而是背后的整体逻辑：

- Webpack 负责识别并组织 JS 模块
- Babel 负责把现代语法转成目标环境能接受的形式
- `rule`、`exclude`、`include`、`cache` 决定处理范围和效率
- ESLint 负责提前发现代码质量问题
- 报错排查要先分类型，再按链路逐步定位

如果你把这条链路想明白，后面再看 CSS、图片、字体这些资源的处理，就不会再把 Webpack 当成一个黑盒配置器了。

### 行动建议

1. 先把一个最小 JS 入口跑通

# 第5章：处理 CSS：样式文件、预处理器和样式提取

前面我们把 Webpack 的骨架搭起来了，现在轮到一个很现实的问题：**CSS 怎么进入 Webpack 的世界**。

很多同学会觉得，`import './index.css'` 看起来很自然，Webpack 应该能直接懂。赵老师告诉你：**代码写起来顺手，不代表 Webpack 天生就认识 CSS。** Webpack 先理解的是 JavaScript 依赖关系图，CSS、图片、字体这些资源要接入打包流程，通常都得靠 **loader**。而 CSS 又有个特点：开发时希望改完马上生效，生产时又希望单独抽离出来，方便缓存和性能优化。所以它不是“能打进去就完事”，而是要兼顾 **开发体验** 和 **生产策略**。

这一章咱们就把 CSS 的处理链路讲清楚：`css-loader`、`style-loader` 的顺序怎么配，Sass、Less 这些预处理器怎么接，再到生产环境怎么把 CSS 抽成独立文件。你把这一章吃透了，后面做项目配置的时候，样式这块就不会再一头雾水。

## 一、CSS 在 Webpack 里为什么不能直接“想当然”地打包

### 1. Webpack 天然更懂 JS，不懂 CSS 语义

Webpack 的工作方式，是从入口开始递归分析依赖。JS 里的 `import`、`require` 很明确：这是模块依赖。  
但 CSS 不是 JS 模块，它描述的是样式规则，不是执行逻辑。所以 Webpack 不能像处理 JS 那样，直接把 `.css` 文件“看懂然后打包完事”。

CSS 要进入构建流程，通常要先被 loader 处理成 Webpack 能消费的内容，再决定是注入页面，还是抽离成独立文件。你可以把它理解成：**Webpack 先搭好流水线，CSS 再按规则进厂加工。**

### 2. CSS 的处理目标分两种

CSS 在不同环境下，目标不一样：

- **开发阶段**：改完样式能马上生效，最好还支持热更新
- **生产阶段**：CSS 独立输出，方便缓存、压缩和性能优化

所以 CSS 配置不能一套走到底。开发重效率，生产重质量，策略必须分开。

### 3. CSS 配置影响的不只是“样式能不能显示”

CSS 的处理方式，会直接影响这些东西：

- 页面首屏加载速度
- 样式刷新是否及时
- 浏览器缓存是否友好
- 构建产物是否清晰
- 后续维护是否省心

所以别把 CSS 当成小配角，它其实和开发体验、性能优化、构建产物理解都绑得很紧。

#### 老赵给你画重点
- Webpack 先天理解 JS 依赖，不天然理解 CSS 语义
- CSS 要通过 loader 接入构建流程
- 开发和生产对 CSS 的处理方式通常不同
- CSS 影响的不只是样式，还有体验和性能

#### 赵老师避坑提醒
- 别以为 `import './a.css'` 就等于 Webpack 自动懂了
- 别把开发和生产共用一套最简配置
- CSS 处理顺序很重要，顺序错了样式可能失效

## 二、`css-loader` 和 `style-loader`：先读懂，再注入

### 1. `css-loader`：负责把 CSS 里的依赖关系理顺

`css-loader` 的任务，不是把 CSS 直接变成页面样式，而是让 Webpack 看懂 CSS 文件内部的依赖。比如：

- `@import './reset.css'`
- `url('./logo.png')`

这些写法在 CSS 里很常见，但 Webpack 如果不经过 `css-loader`，就不一定知道该怎么处理这些引用。`css-loader` 做的事情，就是把这些依赖纳入模块图，让后续构建继续往下走。

### 2. `style-loader`：负责把样式插进页面

`style-loader` 的作用，是把处理后的 CSS 动态插入到页面里的 `<style>` 标签中。  
所以开发阶段常用它：你改完代码，样式可以很快反映到页面上，体验比较顺。

### 3. Loader 顺序为什么是反的

常见写法是：

```js
use: ['style-loader', 'css-loader']
```

但实际执行顺序是**从右到左**：

1. 先执行 `css-loader`
2. 再执行 `style-loader`

原因很简单：后一个 loader 处理前一个 loader 的输出。先把 CSS 解析成 Webpack 能处理的内容，再把它注入页面，顺序不能反。

### 4. 最常见的基础配置

```js
module.exports = {
  module: {
    rules: [
      {
        test: /\.css$/i,
        use: ['style-loader', 'css-loader']
      }
    ]
  }
}
```

这个配置的意思就是：遇到 `.css` 文件，先让 `css-loader` 解析依赖，再由 `style-loader` 把样式挂到页面上。

#### 老赵给你画重点
- `css-loader` 负责解析 `@import` 和 `url()`
- `style-loader` 负责把样式注入页面
- loader 顺序从右到左执行
- 开发阶段最常见的组合就是这两个 loader

#### 赵老师避坑提醒
- 别把两个 loader 的职责搞反
- 别忽略执行顺序
- `css-loader` 处理完，不代表样式已经显示，真正注入的是 `style-loader`

## 三、Sass、Less、Stylus 等预处理器怎么接入

### 1. 预处理器解决什么问题

Sass、Less、Stylus 这些工具，本质上是为了让 CSS 更好写、更好维护。常见能力包括：

- 变量
- 嵌套
- 混入
- 函数
- 模块化组织

项目一复杂，纯 CSS 很容易重复、散乱、难统一。预处理器的价值，就在于提升样式组织能力，而不是单纯“换一种写法”。

### 2. 典型接入链路

预处理器接入 Webpack 的思路很统一：**先编译成标准 CSS，再交给 `css-loader` 处理。**  
以 Sass 为例，常见链路是：

```js
use: ['style-loader', 'css-loader', 'sass-loader']
```

执行顺序是：

1. `sass-loader`：把 Sass 语法编译成标准 CSS
2. `css-loader`：解析 CSS 依赖
3. `style-loader`：注入页面

Less、Stylus 也是同样套路，只是 loader 和编译器不同。

### 3. 一个 Sass 的完整小例子

假设你有一个 `index.scss`：

```scss
$primary: #409eff;

.container {
  color: $primary;
  .title {
    font-size: 20px;
  }
}
```

Webpack 配置可以这样写：

```js
module.exports = {
  module: {
    rules: [
      {
        test: /\.scss$/i,
        use: ['style-loader', 'css-loader', 'sass-loader']
      }
    ]
  }
}
```

安装依赖时也别漏了 Sass 本体：

```bash
npm i -D style-loader css-loader sass-loader sass
```

这里要注意，`sass-loader` 只是把 Sass 交给编译器处理，真正干活的底层实现还需要 `sass`。

### 4. 预处理器不是必选项，但很常用

小项目纯 CSS 完全够用；中大型项目、组件较多的场景，预处理器会更省心。  
它不是为了显得高级，而是为了让样式更容易管理。比如变量统一管理主题色、嵌套组织组件样式，这些在实际项目里都挺常见。

#### 老赵给你画重点
- 预处理器负责把增强语法编译成标准 CSS
- 常见链路是“预处理器 → css-loader → style-loader”
- Sass/Less/Stylus 的核心思路一致
- 预处理器提升的是可维护性，不是炫技

#### 赵老师避坑提醒
- 别只装 loader，不装预处理器本体
- 别把顺序写反
- 别过度嵌套，嵌套太深会让 CSS 更难维护

## 四、CSS 提取到独立文件：生产环境为什么更爱这么干

### 1. 为什么生产环境要提取 CSS

开发时把样式注入 `<style>` 标签很方便，但生产环境通常更适合把 CSS 单独输出成文件，因为这样：

- CSS 和 JS 分开加载，结构更清晰
- CSS 可以单独缓存
- JS 体积更小，首屏更友好
- 避免样式加载和 JS 执行强耦合

说白了，开发看的是“改起来快”，生产看的是“上线后稳不稳、快不快”。

### 2. 常见做法：开发注入，生产提取

这一点非常实战，基本可以记成默认思路：

- **开发环境**：`style-loader + css-loader`
- **生产环境**：`MiniCssExtractPlugin + css-loader`

也就是说，开发时 CSS 先注入页面，方便热更新；生产时把 CSS 抽离成独立文件，交给浏览器单独下载。

### 3. 为什么提取更适合生产

`style-loader` 是运行时注入样式，适合开发，但生产会让 CSS 和 JS 绑得太紧。  
抽离成独立文件后，浏览器可以并行加载，也更利于长期缓存；如果再配合文件名 hash，样式更新后缓存失效也更可控。

一个常见思路是：

```js
const MiniCssExtractPlugin = require('mini-css-extract-plugin')
```

```js
module.exports = {
  plugins: [
    new MiniCssExtractPlugin({
      filename: 'css/[name].[contenthash:8].css'
    })
  ],
  module: {
    rules: [
      {
        test: /\.css$/i,
        use: [
          process.env.NODE_ENV === 'production'
            ? MiniCssExtractPlugin.loader
            : 'style-loader',
          'css-loader'
        ]
      }
    ]
  }
}
```

这个写法很直观地表达了一个核心逻辑：**同样是 CSS，开发和生产的出口不一样。**

### 4. 提取后别忘了产物怎么进页面

抽离 CSS 以后，样式就不再塞进 JS 了，这时构建产物会多出独立的 `.css` 文件。  
如果你使用的是 HTML 插件或者自动注入模板，通常构建工具会帮你把 CSS 资源引进页面；如果是更手工的配置，那就要保证 HTML 中能正确引用到这个 CSS 文件。

这一点很重要：**提取不是结束，能被页面正确加载才算闭环。**

#### 老赵给你画重点
- 开发用注入，生产用提取，是最常见的 CSS 策略
- 独立 CSS 文件更利于缓存和性能优化
- 提取插件的目标是把 CSS 从 JS 中分离出来
- 环境差异配置是 Webpack 实战常规动作

#### 赵老师避坑提醒
- 生产环境还用 `style-loader`，通常不够优
- 提取 CSS 后，别忘了 HTML 或构建产物的正确引入方式
- 开发和生产别混着配

## 五、开发环境和生产环境的 CSS 配置，别一把梭

### 1. 开发环境：优先调试效率

开发阶段最关心的是：

- 改完样式能快点看到
- 出错时好定位
- 构建速度尽量快

所以常见配置是：

- `style-loader`
- 简洁的 CSS 规则
- 配合 source map
- 预处理器按需开启

核心目标就一个：**先让页面稳定跑起来，反馈要快。**

例如开发配置可以这样组织：

```js
module.exports = {
  mode: 'development',
  module: {
    rules: [
      {
        test: /\.css$/i,
        use: ['style-loader', 'css-loader']
      }
    ]
  }
}
```

如果是 Sass，就继续往后加 `sass-loader`：

```js
use: ['style-loader', 'css-loader', 'sass-loader']
```

### 2. 生产环境：优先输出质量

生产环境更关注：

- CSS 是否提取
- 文件是否压缩
- 缓存策略是否合理
- 是否减少无用代码

常见做法是：

- 独立 CSS 文件输出
- CSS 压缩
- 文件名带 hash
- 更严格的优化策略

例如生产环境可以这样做：

```js
module.exports = {
  mode: 'production',
  module: {
    rules: [
      {
        test: /\.css$/i,
        use: [MiniCssExtractPlugin.loader, 'css-loader']
      }
    ]
  }
}
```

这类配置的核心，不是“换个 loader 名字”，而是让不同环境走不同策略。

### 3. 一个实用判断方法

你可以用下面这个思路来选：

- **要快速改样式**：用注入方式
- **要减少首屏负担**：把 CSS 提取出去
- **要方便上线缓存**：文件名加 hash
- **要提高可维护性**：上预处理器

别死记配置，先看目标，再选工具。

### 4. 读懂配置背后的逻辑更重要

记住每个工具的职责：

- `style-loader`：让样式马上生效
- `css-loader`：让 Webpack 看懂 CSS 依赖
- 预处理器 loader：把增强语法转成标准 CSS
- 提取插件：把样式从 JS 中分离出来

理解目标后，配置就是组合问题，不是背诵题。

#### 老赵给你画重点
- 开发重效率，生产重性能和缓存
- CSS 配置要按场景切换
- 先理解为什么这么配，再动手写
- 搞清楚工具职责，配置就不容易乱

#### 赵老师避坑提醒
- 别让开发和生产共用同一套 CSS 策略
- 别只盯着“能运行”，忽略上线后的性能
- 别死记 loader 名字，先弄清职责

# 第6章：处理图片和字体：静态资源在 Webpack 里的正确姿势

很多人学 Webpack，前面把 JS、CSS 搞明白了，一到图片和字体就开始懵：  
“这不就是静态文件吗，直接放 public 目录不就行了？”  
赵老师告诉你，这话只对了一半。

如果项目里只有一两张图，当然简单；但一旦进入真实项目，图片、字体、SVG、媒体文件会和代码、样式一起构成完整的构建产物。你不把它们纳入构建管理，就容易遇到路径错乱、缓存失效、资源丢失、线上 404、包体积失控这些老问题。Webpack 不是只管 JS，它管的是**整个前端资源链路**。

这一章，老赵带你把图片和字体讲透，核心就一句话：  
**静态资源也要像代码一样，纳入统一的构建、输出、引用和优化流程。**

---

## 一、图片、字体、媒体资源为什么也要纳入构建管理？

### 1. 它们不是“附属品”，而是构建产物的一部分

一个页面能不能正常显示，靠的不只是 JS，还包括：

- 图片是否能正确加载
- 字体是否能正确渲染
- 图标、背景、SVG 是否路径有效
- 媒体文件是否按预期输出

Webpack 的价值就在于：它能把这些资源跟模块系统打通。你在 JS 里 `import` 一张图片，在 CSS 里 `url()` 一个字体，Webpack 都能识别并处理，最后输出到合适的位置。

换句话说，Webpack 处理的不只是“代码”，而是“页面最终要用到的一切资源”。只要资源参与页面渲染，它就应该进入构建流程。这样做的好处很直接：引用统一、路径统一、输出统一，后期维护也更省心。

### 2. 不纳入构建管理会出现什么问题？

最常见的坑有这几个：

- **路径写死**：本地能跑，部署后路径错了
- **资源散落**：项目里到处是图片副本，不好维护
- **缓存不好控**：更新了图片，用户浏览器还在用旧缓存
- **发布不一致**：开发、测试、生产环境路径配置不同
- **体积不好管**：大图直接进主包，首屏加载慢

资源往往分散在组件、页面、样式文件里。今天改一个组件，可能顺带改一张图；明天换主题，字体也得换。如果没有统一管理，项目越大，资源越难控。

### 3. 资源分类要先想清楚

在 Webpack 里，静态资源一般可以分为：

- **图片**：png、jpg、jpeg、gif、webp、svg 等
- **字体**：woff、woff2、ttf、eot、otf
- **媒体**：mp4、mp3、webm 等
- **其他文件**：pdf、txt、wasm 等，视项目需要而定

不同类型资源处理方式类似，但策略可以不同：  
比如小图片可以内联，大图片输出文件；字体一般直接输出文件；视频通常按文件引用，不建议塞进主包。

### 老赵给你画重点

- 静态资源不是“放着就行”，它们是构建链路的一环。
- 资源处理的核心目标是：**正确引用、正确输出、正确缓存、正确优化**。
- 先分类，再决定处理策略，这是最省心的思路。

### 赵老师避坑提醒

- 别一上来就把所有资源都 inline，包体积会炸。
- 别手写一堆相对路径，构建后很容易失效。
- 别忽视字体资源，很多页面“看起来不对”，问题就出在字体没加载成功。

## 二、Webpack 5 中 asset modules 的基本用法

### 1. 什么是 asset modules？

Webpack 5 提供了处理静态资源的新方式：**asset modules**。  
你可以把它理解成：Webpack 原生支持把文件当作资源模块处理，不必再依赖很多传统 loader 组合。

常见类型有四种：

- `asset/resource`：输出文件，返回资源 URL
- `asset/inline`：转成 Base64，直接内联到代码里
- `asset/source`：把文件内容当作字符串导入
- `asset`：自动判断，小文件内联，大文件输出

这套机制的好处是统一。以前处理图片、字体、文本文件，可能要配很多 loader；现在很多场景用原生能力就够了，配置更清楚，维护也更轻松。

### 2. 最常见的配置方式

比如处理图片和字体：

```js
module.exports = {
  module: {
    rules: [
      {
        test: /\.(png|jpe?g|gif|webp|svg)$/i,
        type: 'asset',
        parser: {
          dataUrlCondition: {
            maxSize: 8 * 1024
          }
        }
      },
      {
        test: /\.(woff2?|eot|ttf|otf)$/i,
        type: 'asset/resource'
      }
    ]
  }
}
```

这段配置的意思很直白：

- 小图自动内联，减少请求数
- 大图单独输出，避免主包过大
- 字体统一输出为文件，浏览器按 URL 加载

Webpack 不是“魔法处理资源”，而是把资源处理规则显式写出来。规则越清楚，项目越稳定。

### 3. 什么时候选哪一种？

简单记：

- **asset/resource**：适合大资源、字体、视频、不可内联资源
- **asset/inline**：适合很小的图标、少量 SVG
- **asset/source**：适合需要源码内容的场景，比如读文本文件
- **asset**：适合你不想每次都手动判断的时候

实际项目里，最常用的通常就是 `asset` 和 `asset/resource`。前者负责“自动判断”，后者负责“明确输出”。如果你是团队协作，建议尽量统一规则，不要每个人都随手决定资源怎么处理。

### 4. asset modules 的使用边界

`asset` 类能力适合的是**文件型静态资源**：图片、字体、音频、视频、文本这类东西。  
但它不是万能的，下面几种场景还是要注意：

- 你想对图片做压缩、裁剪、转格式，这通常还要配额外工具或插件
- 你想兼容老项目的旧 loader，不能指望一次全换完
- 你想对某些资源做特殊命名、特殊目录分发，还是要靠 `generator.filename` 或 `output.assetModuleFilename` 配好规则

也就是说，asset modules 负责“识别和输出”，但“优化和策略”还是你来定。

### 老赵给你画重点

- Webpack 5 里，资源处理更统一了，很多场景不用再纠结传统 loader。
- `asset` 类能力，本质是在帮你做“资源判断 + 输出策略”。
- 先理解“输出文件”还是“内联进代码”，你就掌握了资源处理的大方向。

### 赵老师避坑提醒

- 不要把字体也做成 inline，大概率得不偿失。
- 小图内联不是越多越好，太多 Base64 会让 JS 变大。
- `asset` 很方便，但项目里最好有统一规范，不然不同人写法会飘。

## 三、图片资源的打包、引用与输出命名

### 1. 图片在代码里怎么引用？

图片通常有两种常见引用方式：

**在 JS 中引用：**
```js
import logo from './logo.png'
const img = document.createElement('img')
img.src = logo
document.body.appendChild(img)
```

**在 CSS 中引用：**
```css
.banner {
  background-image: url('./banner.jpg');
}
```

Webpack 会从这些语法里识别依赖关系，然后把图片纳入构建图谱。也就是说，图片不再是“手工拷贝的文件”，而是模块依赖的一部分。只要这个依赖关系建立起来，Webpack 就能在打包时帮你一起处理。

### 2. 图片最终会输出到哪里？

这取决于你的输出配置。通常会配置：

- `output.path`：总输出目录
- `output.publicPath`：资源在浏览器里的访问前缀
- 文件名规则：方便缓存和管理

例如：

```js
module.exports = {
  output: {
    path: path.resolve(__dirname, 'dist'),
    publicPath: '/',
    assetModuleFilename: 'assets/[name].[contenthash:8][ext]'
  }
}
```

这里的关键点是：

- `[name]` 保留原始文件名
- `[contenthash:8]` 用内容哈希做缓存控制
- `[ext]` 保留扩展名

统一输出到 `assets/` 后，查找和清理都会更方便。

### 3. 为什么要做内容哈希命名？

因为浏览器缓存很“聪明”，也很“固执”。  
如果文件名不变，用户可能一直拿着旧缓存不放。  
而文件内容一变，hash 也变，浏览器就会重新请求新文件。

这就是前端缓存控制里最常见的一招：  
**靠文件名变化，驱动浏览器刷新资源。**

所以真实项目里经常看到：

- `logo.8f2d1a.png`
- `main.3c91a2.css`
- `app.f1a8c8.js`

它们看起来很“技术味”，其实就是为了让缓存可控、发布可靠。

### 4. 图片资源常见策略

老赵建议你按下面规则思考：

- logo、图标：可以小图内联或单独输出
- 大背景图：单独输出文件
- 内容图：单独输出，方便缓存
- SVG：简单图标可 inline，复杂图按资源文件处理

另外，图片格式也值得注意。比如：

- 能用 `webp` 就尽量用 `webp`
- 高清图片注意尺寸，不要直接把原图丢进页面
- 适当压缩图片，往往比堆配置更有效

### 老赵给你画重点

- JS、CSS 里都可能引用图片，Webpack 要能统一识别。
- 图片输出命名最好带 hash，方便缓存更新。
- 资源目录最好有层次，不要所有图片都扔一个文件夹里。

### 赵老师避坑提醒

- 别把背景图路径写成绝对路径硬编码，部署后容易挂。
- 别忽视 CSS 里的 `url()`，图片问题很多都藏在样式里。
- 别忘了 `publicPath`，它决定了浏览器真正去哪里找资源。

## 四、字体资源的处理方式与路径映射

### 1. 字体为什么比图片更容易出问题？

字体文件通常不是直接显示在页面上，而是被 CSS 间接引用。  
所以字体出问题时，很多人第一反应不是字体，而是“页面怎么突然变样了”。

典型症状包括：

- 字体没生效，页面回退成默认字体
- 图标字体不显示
- 控制台报字体加载 404
- 线上和本地显示不一致

还有一种情况也很常见：页面功能没坏，但视觉气质变了。标题变窄了、按钮换行了、图标空白了，这类问题追起来往往比 JS 报错更费时间。

### 2. 字体怎么配置？

一般字体资源直接走 `asset/resource` 就够了：

```js
{
  test: /\.(woff2?|eot|ttf|otf)$/i,
  type: 'asset/resource',
  generator: {
    filename: 'fonts/[name].[contenthash:8][ext]'
  }
}
```

然后在 CSS 里正常写：

```css
@font-face {
  font-family: 'MyFont';
  src: url('./fonts/MyFont.woff2') format('woff2');
  font-display: swap;
}
```

Webpack 会把字体复制到输出目录，并把 CSS 里的引用重写为正确的构建后路径。

这里最关键的是：**源码里写的是相对路径，浏览器实际访问的是构建后的路径。** 一旦映射错了，字体就会加载失败。

### 3. 路径映射的关键：让 CSS 能找到字体

字体的核心不是“能不能输出”，而是“输出后浏览器能不能找到”。  
所以你要关注两件事：

- 字体输出目录是否合理
- CSS 中生成的 URL 是否正确

如果项目部署在子路径下，比如 `/app/`，`publicPath` 就要特别留意，不然字体文件可能请求错地址。

### 4. 字体资源的最佳实践

- 只保留项目真正需要的字体格式
- 优先使用 `woff2`
- 图标字体要谨慎，能用 SVG 图标就别滥用字体图标
- 配合 `font-display: swap`，减少字体加载导致的空白期

字体越多，维护越复杂。很多团队一开始图省事，把所有格式都塞进去，结果下载体积大、排查麻烦、样式还不稳定。真要做项目，字体最好少而精。

### 老赵给你画重点

- 字体有独立的加载和路径问题，不要和图片混着看。
- 处理字体最关键的是：**输出路径正确 + 引用路径正确**。
- 字体格式不用全家桶都上，够用就行。

### 赵老师避坑提醒

- 别把字体文件名随便改掉，CSS 里的引用和输出要对应。
- 别忽略部署子路径场景，很多字体 404 就是这里翻车。
- 别把图标字体当万能方案，维护成本其实不低。

## 五、静态资源缓存与体积控制的基础思路

### 1. 为什么资源缓存这么重要？

因为资源文件通常比 JS 更适合长期缓存。  
你今天改的是页面文案，不代表图片和字体也得重新下载。  
所以最理想的状态是：

- 资源没变，浏览器继续用缓存
- 资源变了，浏览器自动拉新版本

这就是 hash 文件名的意义。

从用户体验看，它可以减少重复下载；从服务器角度看，它可以减轻带宽压力。尤其在内容型网站、电商网站或者资源较多的后台系统里，静态资源缓存做得好不好，体验差别很明显。

### 2. 哪些地方适合做缓存控制？

重点看这几个地方：

- 图片文件名使用 `contenthash`
- 字体文件名使用 `contenthash`
- JS 和 CSS 也用类似方式配合长期缓存
- `publicPath` 保持环境一致，避免缓存失效

如果你把资源命名统一起来，后续发布就会很顺。只要内容变化，文件名变化；文件名变化，浏览器自动更新。

### 3. 体积控制怎么做？

静态资源的体积控制，核心思路就三条：

#### 第一，按大小区分策略
小文件可以 inline，减少请求数；大文件应该单独输出，避免主包膨胀。

#### 第二，按场景选择格式
图片尽量选更合适的格式，字体尽量只保留必要格式。

#### 第三，按使用范围拆分
不是所有资源都必须进主入口。  
有些资源只在某个页面使用，就让它跟着页面按需加载。

这三条其实都指向同一件事：不要让“静态资源”变成“静态负担”。

### 4. 资源管理的检查清单

你可以每次项目上线前问自己：

- 图片是否都能正常访问？
- 字体是否在生产环境可用？
- 输出文件名是否带 hash？
- `publicPath` 是否正确？
- 有没有无意义的大图、大字体文件？
- 是否有重复资源被打包多次？

这份清单不复杂，但很实用。尤其是上线前做一遍，能避免很多低级但致命的问题。

### 老赵给你画重点

- 缓存的核心是“文件变了，地址变；文件没变，地址不变”。
- 体积控制不是一刀切，而是按资源类型做策略。
- 资源管理最终服务的是：加载更快、部署更稳、维护更省心。

### 赵老师避坑提醒

- 别为了缓存把所有资源都拆得太碎，浏览器请求数也有成本。
- 别只看开发环境，静态资源问题常常在线上才暴露。
- 别忘了检查输出目录，很多“资源没了”的问题其实是构建规则没配对。

## 六、从零搭建静态资源可运行的基础项目

如果你现在要从零做一个能跑起来的 Webpack 项目，静态资源这一块至少要具备下面能力：

1. 能处理 JS 引入图片  
2. 能处理 CSS 里的 `url()`  
3. 能输出字体文件  
4. 能在开发和生产环境下都正确访问资源  
5. 能通过 hash 控制缓存  

一个最小思路可以是：

- `entry` 入口引入主 JS
- JS 里 import 图片
- CSS 里引用字体和背景图
- `module.rules` 用 `asset` / `asset/resource` 处理资源
- `output` 配好目录、文件名和 `publicPath`
- 运行后检查 `dist` 目录和浏览器访问是否正常

实际操作时，你不妨按这个顺序来：

第一步，先只接一张图片，看 `import` 后能不能正常显示。  
第二步，再补一个 CSS 背景图，确认样式里的 `url()` 也能被识别。  
第三步，加入字体文件，验证 `@font-face` 能不能正常加载。  
第四步，打开浏览器开发者工具，看 Network 里资源请求是否正确、路径是否匹配、是否有 404。  
第五步，再把输出文件名加上 hash，确认构建后资源更新能否生效。

你不用一开始就追求复杂，先把“资源能正确进来、正确出去、正确显示”这件事跑通，后面再谈优化就顺理成章了。

### 老赵给你画重点

- 从零搭建时，先把图片和字体打通，项目就已经过了一个重要门槛。
- 资源能否正确构建，直接决定项目后续能不能稳定扩展。
- 真正靠谱的 Webpack 项目，静态资源处理一定不是临时补丁，而是配置体系的一部分。

### 赵老师避坑提醒

- 别只验证“打包成功”，还要验证“浏览器里真能显示”。
- 别忽略 dist 目录里的真实输出结构，构建产物比配置文件更能说明问题。
- 别等资源越堆越多了才回头整理，越早规范越省事。

## 二、webpack-dev-server 的作用和工作方式：它到底在干啥？

### 2.1 它不是“把文件打到磁盘上再给你看”

`webpack-dev-server` 是一个**内存里的开发服务器**。它负责：

- 启动本地 Web 服务
- 监听文件变化
- 重新编译代码
- 直接把最新结果提供给浏览器
- 支持自动刷新、热更新

它适合开发环境，不适合正式部署，因为它追求的是“快”，不是“稳”。

### 2.2 它和 `webpack --watch`、手动打包有什么区别？

- `webpack --watch`：持续监听变化，改了就重新打包，但**你还得自己刷新浏览器**
- 手动打包：每次改完都手动执行构建命令，再切浏览器看结果，最原始，也最费劲
- `webpack-dev-server`：监听、编译、服务、刷新、更新一起做，省掉大量重复动作

所以它的价值不只是“自动编译”，而是**把编译、服务、刷新、更新串起来了**。

### 2.3 它的工作流程怎么理解？

简单说就是：

1. 浏览器访问本地服务
2. devServer 返回页面和内存中的打包结果
3. 你修改源代码
4. Webpack 重新编译
5. devServer 通知浏览器更新
6. 浏览器根据配置选择整页刷新或局部替换

关键点是：**构建结果通常不需要真正写进磁盘**。  
这也是它比“手动打包 + 手动刷新”顺手得多的原因。

从构建产物角度看，开发环境里的“结果”更多是**给浏览器看的运行态产物**，而不是你硬盘里那个最终文件。也就是说，你在页面上看到的变化，往往来自 devServer 持有的内存结果；磁盘上的 `dist` 不一定每次都同步变化。这个区别要先想明白，后面你看日志、看输出目录，心里才不乱。

### 2.4 最基础的使用思路

开发环境里常见的配置能力包括：

- `devServer.static`：静态资源目录
- `devServer.port`：端口
- `devServer.open`：自动打开浏览器
- `devServer.host`：监听地址
- `devServer.hot`：热更新

先记住它的职责边界：**Webpack 负责构建，devServer 负责把开发中的项目顺畅跑起来。**

### 2.5 一个最小可运行示例

```js
// webpack.config.js
const path = require('path');

module.exports = {
  mode: 'development',
  entry: './src/index.js',
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: 'bundle.js',
  },
  devServer: {
    static: path.resolve(__dirname, 'public'),
    port: 3000,
    open: true,
    hot: true,
  },
};
```

这个配置的意思很简单：

- `mode: 'development'`：开发模式
- `entry`：从 `src/index.js` 开始打包
- `output`：开发中主要走内存，但输出结构先配好
- `static`：托管 `public` 目录
- `port`：本地端口是 3000
- `open`：启动后自动打开浏览器
- `hot`：开启热更新

### 2.6 常用配置项一眼看懂

| 配置项 | 作用 | 常见场景 |
|---|---|---|
| `static` | 托管静态目录 | 图片、favicon、固定文件 |
| `host` | 指定监听主机 | 本机、局域网访问 |
| `port` | 指定端口 | 避免端口冲突 |
| `open` | 启动后自动打开浏览器 | 提升启动效率 |
| `hot` | 开启热更新 | 局部替换模块 |
| `proxy` | 开发代理 | 联调后端接口 |
| `historyApiFallback` | 路由回退到入口页 | SPA 刷新不 404 |
| `overlay` | 页面覆盖显示错误 | 快速发现编译问题 |

### 老赵给你画重点

- `webpack-dev-server` 是开发服务器，不是生产部署方案
- 核心价值是：**编译快、访问快、更新快**
- 结果多在内存里，不一定落盘
- 它能省掉“手动打包 + 手动刷新”的低效动作

### 赵老师避坑提醒

- 不要把 devServer 当成生产服务器用
- 开发配置和生产配置要分开
- 改代码后没变化，先查编译是否成功，再查浏览器是否连上 devServer

## 三、本地开发代理、静态资源服务与本地访问：怎么让项目跑得顺手？

### 3.1 本地访问：为什么要有 devServer 地址？

开发时不要直接 `file://` 打开页面，而要通过本地服务访问。  
只有这样，Webpack 才能接管自动刷新、热更新、代理转发这些能力。

常见访问方式就是：

- `http://localhost:8080`
- `http://127.0.0.1:3000`

本地服务不只是“能打开页面”，更是整个开发流程的入口。

### 3.2 静态资源服务：哪些文件由它来托管？

开发中，有些文件你可能不想参与打包，或者希望原样提供，比如：

- `public` 目录里的图片
- 固定 HTML
- favicon
- 某些第三方静态资源

这时可以通过 devServer 的静态资源配置进行托管。  
简单说就是：**Webpack 负责打包，devServer 负责把静态目录和打包结果一起提供给浏览器。**

### 3.3 开发代理：为什么前端经常要配 proxy？

假设前端跑在 `localhost:3000`，后端在 `localhost:5000`。浏览器直接请求后端可能跨域，这时候就可以让 devServer 做转发：

- 浏览器请求前端开发服务器
- devServer 转发到后端接口
- 对浏览器来说仍像同源请求
- 跨域问题在开发阶段被绕开

比如前端统一写 `/api/user/list`，开发环境走代理，生产环境再由网关或部署配置决定最终地址，这样代码就不用频繁改接口前缀。

### 3.4 一个更完整的代理实战案例

```js
fetch('/api/user/list')
  .then(res => res.json())
  .then(data => {
    console.log(data);
  });
```

```js
devServer: {
  proxy: {
    '/api': {
      target: 'http://localhost:5000',
      changeOrigin: true,
    },
  },
}
```

这时请求流程变成：

1. 浏览器请求 `http://localhost:3000/api/user/list`
2. devServer 识别到 `/api` 前缀
3. 转发到 `http://localhost:5000/api/user/list`
4. 后端返回数据
5. 浏览器拿到结果，感觉像在请求同一个站点

### 3.5 带 `pathRewrite` 的案例：路径到底要不要改？

如果后端不认 `/api` 前缀，但前端希望统一写 `/api`，就要靠 `pathRewrite`。

```js
devServer: {
  proxy: {
    '/api': {
      target: 'http://localhost:5000',
      changeOrigin: true,
      pathRewrite: {
        '^/api': '',
      },
    },
  },
}
```

意思是：

- 请求先命中 `/api`
- 转发到 `http://localhost:5000`
- 再把路径里的 `/api` 去掉
- 最终访问后端的 `/user/list`

反过来，如果后端本来就要求 `/api/user/list`，那就别写 `pathRewrite`。关键不是“必须改路径”，而是前后端路径要对上。

### 3.6 代理不生效时怎么排查？

按这个顺序看：

- 前端请求路径有没有写错
- `proxy` 的前缀是否匹配到了
- `target` 地址是否正确
- 是否需要 `changeOrigin`
- 是否配置了 `pathRewrite`
- 后端实际接口路径是不是和转发后的路径一致

常见坑就两个：

- 你以为走了代理，其实请求根本没匹配上
- 你以为后端是 `/api/user/list`，实际上后端只认 `/user/list`

### 3.7 `historyApiFallback`、`overlay`、`watchFiles`、`allowedHosts` 各自解决什么问题？

#### `historyApiFallback`
适用场景：单页应用使用 history 路由。  
典型问题：页面内跳转正常，一刷新就 404。  
它的作用：把未知路径回退到入口页，让前端路由接管。

#### `overlay`
适用场景：开发中希望第一时间看到编译错误。  
它的作用：把错误直接覆盖显示在页面上。

#### `watchFiles`
适用场景：除了 JS/CSS，还想监听一些额外文件变化。  
它的作用：把额外文件也纳入监听范围。

#### `allowedHosts`
适用场景：局域网访问、临时外部访问、主机校验导致访问失败。  
它的作用：限制或放行允许访问开发服务的主机。

### 3.8 代理匹配失败怎么查：现象、原因、顺序

如果接口一直不通，按下面顺序排：

1. 请求有没有发出去
2. 浏览器访问的是前端服务，还是直接访问后端地址
3. `proxy` 的前缀有没有命中
4. `target` 和 `pathRewrite` 是否写对
5. 后端返回的路径是否和转发后的路径一致
6. 是否因为 `changeOrigin` 或主机限制导致失败

### 老赵给你画重点

- devServer 不只是“开网页”，还负责静态资源和开发代理
- `proxy` 是前端联调接口的常用手段
- 开发时统一用本地服务访问，不要直接打开静态文件
- `historyApiFallback` 对单页应用特别关键
- `pathRewrite` 解决的是前端写法和后端真实路径不一致的问题

### 赵老师避坑提醒

- 代理写错时，常见情况不是报错，而是请求悄悄没转过去
- 接口地址怪，优先检查代理匹配规则
- 静态资源目录和打包输出目录别混淆
- SPA 刷新 404，先看是不是少了 `historyApiFallback`

## 四、热更新 HMR 的基本概念和使用场景：为什么它比自动刷新更香？

### 4.1 自动刷新和热更新，不是一回事

它们的区别很明确：

- **自动刷新**：代码变了，浏览器整页重载
- **热更新 HMR**：只替换变化的模块，不整页刷新

自动刷新简单，但会丢失页面状态；HMR 更聪明，能尽量保住当前状态。比如表单输入到一半时，整页刷新会清空内容，而 HMR 可能只更新样式或局部逻辑。

### 4.2 一个更直观的对比案例

假设你正在调一个页面，里面有输入框、样式和展开状态。  
你分别修改三类内容：

#### 改 CSS
- 自动刷新：整页重载，输入内容和状态会丢
- HMR：只替换样式，页面状态通常还能保住

#### 改 JS 业务逻辑
- 自动刷新：整页重载，所有状态重来
- HMR：如果模块边界清楚，可能只更新相关逻辑

#### 改页面状态相关代码
- 自动刷新：状态完全清空
- HMR：如果项目支持得好，局部更新后状态还在；否则仍可能回退整页刷新

这就是 HMR 的意义：**尽量少动不必要的部分**。

### 4.3 HMR 适合哪些场景？

特别适合：

- 修改 CSS
- 修改局部组件逻辑
- 页面状态复杂
- 不希望丢失输入状态、滚动位置

不一定适合：

- 改动范围很大
- 模块边界不清楚
- 项目复杂到局部更新收益不高

HMR 不是“必须全开才高级”，而是要看场景是否值得。

### 4.4 HMR 的工作思路

你可以这样理解：

1. 修改某个模块
2. Webpack 重新构建受影响部分
3. devServer 通知浏览器
4. 浏览器拿到最新模块
5. 页面不一定整页刷新，只替换变化内容

核心是**模块级别的更新**。模块拆得越清楚，HMR 往往越容易发挥作用。

### 4.5 为什么 JS 模块热更新有时会失效？

HMR 能不能保住现场，关键看两件事：

1. 这个模块是不是可热替换的边界
2. 更新后状态能不能继续接上

CSS 通常没有复杂状态，替换掉就行；但 JS 常常带着数据、事件、引用关系。  
如果一个模块里既定义 UI，又保存状态，又触发副作用，Webpack 很难判断到底该局部替换到什么程度，于是它可能选择保守策略：**整页回退**。

所以你会发现：

- 模块边界清楚，HMR 更容易成功
- 状态依赖少，HMR 更容易保留
- 副作用多、关联广，HMR 更容易退回刷新

### 4.6 CSS HMR / JS HMR / 自动刷新对比

| 方式 | 作用 | 是否自动刷新 | 是否局部更新 | 典型用途 |
|---|---|---:|---:|---|
| 自动刷新 | 页面整页重载 | 是 | 否 | 简单稳定 |
| CSS HMR | 替换样式模块 | 是 | 是 | 样式调整 |
| JS HMR | 替换脚本模块 | 是 | 是 | 保留状态的业务开发 |

你可以把它们理解成三档：

- 自动刷新：最稳，状态会丢
- CSS HMR：最实用，体验提升明显
- JS HMR：最灵活，也最依赖项目结构

### 4.7 使用 HMR 的现实建议

实际项目里，建议是：

- CSS 热更新优先开启
- JS 视项目情况开启
- 对复杂状态页面谨慎测试
- 不稳定就回退自动刷新

开发体验的目标是“顺”，不是“炫”。

### 老赵给你画重点

- 自动刷新是整页重载，HMR 是局部替换
- HMR 最大价值是**保留状态、减少重刷**
- CSS 热更新最稳定、最常见
- 不是所有改动都适合 HMR，要看模块边界和场景
- `--watch`、live reload、HMR 不是一个东西，别混着记

### 赵老师避坑提醒

- HMR 不是开了就完美，部分改动还是会触发整页刷新
- 如果状态丢了，先看更新范围是不是太大
- 复杂场景下，稳定比“看起来高级”更重要

## 五、开发环境中常见的便捷配置：端口、打开浏览器、压缩与否

### 5.1 端口：怎么选更合理？

端口就是本地服务的访问入口。常见如 `8080`、`3000`、`5173`，关键不是号码，而是**别冲突**。

建议：

- 团队统一默认端口
- 支持本地手动切换
- 文档写清启动地址

### 5.2 自动打开浏览器：省一步是一步

`open: true` 这类配置很实用，启动服务后自动打开浏览器，省掉复制地址的步骤。适合日常开发和调试初始页面。

### 5.3 开发环境要不要压缩？

一般**不建议**。原因很简单：

- 压缩增加构建成本
- 开发更看重速度
- 压缩后的代码不利于调试

开发环境要快、好调、好看；生产环境才追求体积小、加载快、输出稳。

### 5.4 还有哪些常见便捷项？

常见还有：

- `client.overlay`：错误直接覆盖显示
- `historyApiFallback`：单页应用刷新不 404
- `watchFiles`：监听额外文件变化
- `allowedHosts`：控制可访问主机

其中 `historyApiFallback` 对 SPA 特别重要，路由跳转没问题，但刷新 404 时，通常就要看它。

### 5.5 这些配置分别在什么场景下用？

- `overlay`：编译报错时，页面上直接提醒你
- `watchFiles`：除了源码，还想监听某些模板、文档或外部配置
- `allowedHosts`：团队内通过局域网访问，或避免主机校验导致访问失败
- `historyApiFallback`：前端路由用 history 模式，刷新后仍能回到入口页

### 老赵给你画重点

- 端口要可控，别冲突
- `open` 能提升启动效率
- 开发环境通常不追求压缩
- `historyApiFallback` 对 SPA 很关键
- `overlay` 和 `watchFiles` 都是为了减少来回折腾

### 赵老师避坑提醒

- 别把生产优化搬进开发环境，容易拖慢速度
- 刷新后路由 404，先想是不是缺了 `historyApiFallback`
- 端口问题先查占用，不要先怀疑 Webpack 坏了

## 六、开发体验提升的核心思路：快、稳、少折腾

### 6.1 快：让反馈尽量短

开发体验的第一原则就是快。写完代码后越快看到结果，心流就越不容易断。

提升“快”的方法：

- 开发环境开启 devServer
- 使用热更新减少整页刷新
- 减少不必要的额外编译
- 保持配置简洁

### 6.2 稳：别让开发环境老出幺蛾子

稳定比花哨更重要。一个热更新时灵时不灵、改样式没反应的环境，会让人很烦。

让开发环境稳起来的思路是：

- 配置清晰
- 代理规则简单
- 热更新失败时有回退方案
- 开发和生产配置分开管理

### 6.3 少折腾：别在开发时做太多无意义的事

开发环境的任务不是模拟所有线上复杂机制，而是高效写代码。所以要删繁就简：

- 不必要的压缩先关掉
- 不必要的复杂优化先别上
- 先保证流程流畅，再逐步加细节

### 6.4 一个实用判断标准

如果你每次修改后都在做这些事，说明开发体验不顺：

- 手动刷新很多次
- 频繁重启服务
- 不知道改动有没有生效
- 经常被跨域、端口、路径问题卡住

顺手的开发环境应该是：

- 改完自动响应
- 浏览器自动打开
- 页面更新尽量少丢状态
- 接口联调少改配置

### 老赵给你画重点

- 开发体验的核心是：**快、稳、少折腾**
- 先把基础流程跑顺，再追求高级优化
- 配置是为开发服务的，不是为了展示技巧

### 赵老师避坑提醒

- 不要为了“配置完整”把开发环境搞复杂搞慢
- 热更新不稳定时，先降级成自动刷新，保证开发不中断
- 项目越大，开发体验问题越明显，前期就要重视

## 七、从自动刷新到热更新：实际项目里怎么选？

### 7.1 不是所有场景都必须用 HMR

学会热更新后，也不要想着把所有更新都做成局部替换。现实里很多项目会这样取舍：

- 样式层面优先 HMR
- 业务逻辑视情况而定
- 不稳定就回退自动刷新
- 保证团队协作成本可控

开发体验的目标不是“技术最先进”，而是“大家都用得顺手”。

### 7.2 CSS 热更新为什么最好用？

CSS 天生适合热更新，因为它大多没状态。你改颜色、间距、布局，不需要重新初始化业务逻辑，也不容易影响数据，所以 CSS 的 HMR 往往最稳定、最直观。

### 7.3 JS 热更新为什么更容易出问题？

JS 通常牵涉状态、依赖和模块边界。一个模块改动后，Webpack 需要判断：

- 组件状态怎么保留
- 哪些引用要重新绑定
- 哪些副作用要重新执行
- 哪些场景要整页重载

所以 JS 的热更新比 CSS 复杂，也更依赖项目结构。

### 7.4 实战建议：先保底，再升级

刚开始搭项目，建议按这个顺序来：

1. 先把 devServer 跑起来
2. 确保页面能访问
3. 先实现自动刷新
4. 再尝试开启热更新
5. 先验证 CSS HMR，再验证 JS HMR

这样最稳，不容易把自己绕晕。

### 7.5 HMR 失败时的处理思路

如果你在项目里发现：

- 样式改了没反应
- JS 改了直接整页刷新
- 页面状态总是丢
- 控制台提示更新失败

先按这个顺序看：

1. devServer 是否正常启动
2. 浏览器是否连接到了正确端口
3. `hot` 是否开启
4. 当前文件是否真的进入了模块更新链路
5. 是否存在语法错误导致回退刷新

很多时候，问题只在一个很小的配置点上。

### 7.6 热更新推演：改三种东西，页面会怎样？

#### 场景一：改 CSS
比如你把按钮颜色从蓝色改成红色。  
通常发生的是：样式模块被替换，页面立刻变色，输入框、滚动位置、展开状态大概率都还在。  
这是最理想、最常见的热更新效果。

#### 场景二：改组件状态相关逻辑
比如一个列表页，里面有“展开/收起”状态。你改了渲染列表的方法。  
如果模块边界清楚，Webpack 可能只替换相关模块；如果状态和副作用耦得太紧，就可能直接整页刷新。  
所以你看到的不是“热更新一定失败”，而是“项目结构决定它能不能保住现场”。

#### 场景三：改接口请求逻辑
比如把请求地址、请求参数或数据处理方式改了。  
如果这些逻辑被拆在独立模块里，HMR 有机会局部生效；如果请求、状态、渲染全塞在一个文件里，局部更新就更难判断。  
这也是为什么老项目里常说“模块拆分越合理，开发体验越好”。

### 老赵给你画重点

- HMR 不是必选项，稳定落地才重要
- CSS 热更新最容易做，收益也最直观
- JS 热更新更复杂，适合结构清晰时推进
- 实战要遵循“先保底，再升级”

### 赵老师避坑提醒

- 别一上来就追求所有模块都无痛热更新
- 更新后逻辑异常，先回退到整页刷新，确认基础可用
- 结构不清晰时，HMR 的收益未必有想象中大

## 八、从零搭一个能跑起来的开发环境：把前面的内容串起来

前面讲了这么多，咱们最后把思路收一收。一个可用的 Webpack 开发环境，通常至少要满足下面几个条件：

### 8.1 最小配置清单

- 一个入口文件，比如 `src/index.js`
- 一个 HTML 模板，方便挂载页面
- 一个基础 Webpack 配置
- `webpack-dev-server` 提供本地服务
- 必要时配置代理、静态目录、自动打开、热更新

这几个东西凑齐了，项目才能真正“跑起来”。

### 8.2 目录和启动思路

通常你可以按这样的方式组织：

- `src/`：业务源码
- `public/`：静态资源
- `webpack.config.js`：开发配置
- `package.json`：启动命令

启动流程也很简单：

1. 安装依赖
2. 写好入口和 HTML 模板
3. 配好 devServer
4. 执行启动命令
5. 打开浏览器验证页面是否正常
6. 修改样式、脚本，看是否能自动响应

### 8.3 一个最小项目应该怎么验证

如果你是第一次搭，建议按这个清单走：

- 页面能正常打开
- 控制台没有构建报错
- 修改 `src/index.js` 能触发重新编译
- 修改 CSS 能看到页面变化
- 接口请求能通过代理转发
- 刷新 history 路由不会 404

这几个点都通了，说明最基础的开发链路已经搭起来了。

### 8.4 典型开发流程

你启动项目后，一般是这样的链路：

1. 执行启动命令
2. Webpack 读取开发配置
3. devServer 在本地起服务
4. 浏览器自动打开页面
5. 你修改代码
6. Webpack 监听变化并重新编译
7. 页面自动刷新或热更新

整个过程的关键不只是“能编译”，而是“编译后怎么顺畅地展示给你看”。

### 8.5 验证顺序建议

如果你是第一次搭，建议按这个顺序排查：

1. 能不能启动服务
2. 浏览器能不能打开页面
3. 修改代码后会不会重新编译
4. 会不会自动刷新
5. CSS 能不能热更新
6. 接口请求代理是否生效
7. 刷新路由是否 404

这个顺序基本能把大部分问题定位出来。

### 8.6 为什么这一章很重要？

因为很多人学 Webpack 到最后，还是会卡在开发阶段：

- 配好了打包，却不会起服务
- 能访问页面，却不会联调接口
- 能自动刷新，却不会热更新
- 能热更新，却总是 404 或跨域

这章的目的就是把这些“看起来不大、实际很烦”的问题一次讲清。

### 老赵给你画重点

- 开发环境不是附属品，而是 Webpack 项目的重要组成部分
- 一个能跑起来的项目，离不开 devServer、入口、模板和基础配置
- 开发流程顺了，后面讲生产优化才有意义

### 赵老师避坑提醒

- 不要只盯着最终 `dist`，开发体验同样重要
- 配置写完先验证能不能跑，再考虑优雅不优雅
- 只要项目还在开发中，devServer 就是高频工具

## 九、实战补充：常见开发问题怎么快速处理

### 9.1 页面打开了，但样式没生效

先查这几处：

- CSS 是否被正确引入
- loader 是否配置正常
- HMR 是否生效
- 浏览器是否缓存了旧结果

很多时候不是 Webpack 没更新，而是样式入口没接好。

### 9.2 改了代码，浏览器没反应

通常看：

- `devServer` 是否正常运行
- 终端里有没有重新编译日志
- 热更新是否开启
- 页面是否连上了正确端口

如果终端都没编译，那是监听没起来；如果终端编译了但页面没变，那就重点看热更新链路。

### 9.3 接口请求报跨域

先看：

- `proxy` 是否配置
- 路径是否匹配
- 后端地址是否正确
- 请求是否走了开发服务器

别一看到跨域就先改后端，很多时候前端代理一调就通了。

### 9.4 刷新页面后路由 404

这通常就是 SPA 的 history 路由问题。  
优先检查：

- 是否启用了 `historyApiFallback`
- 路由模式是不是 history
- 服务器是否把未知路径回退到了入口页

### 9.5 端口被占用怎么办

这个问题很常见：

- 换端口
- 关闭占用进程
- 配置端口自动递增
- 文档同步更新

别在端口问题上耗太久，先让项目跑起来再说。

### 9.6 浏览器提示主机不允许访问怎么办

如果你通过局域网地址、虚拟机地址，或者修改了主机名后访问失败，优先检查：

- `allowedHosts` 配置是否限制了访问
- 当前访问地址是否与监听地址一致
- 是否需要开放给本机以外的主机访问

这类问题经常不是代码错了，而是开发服务器做了主机校验。

### 9.7 终端一直报错但页面还能打开，怎么办？

这种情况常见于：

- 编译有错误，但 devServer 仍保留了旧页面
- 页面上的错误覆盖层没有打开
- 你没有注意终端日志

建议先打开 `overlay`，把错误直接显示到页面上。

### 9.8 文件改了但监听不到，怎么查？

如果你发现某些文件改动后没有触发更新，可以检查：

- 文件是否在 devServer 的监听范围内
- 是否需要配置 `watchFiles`
- 文件是否被排除在构建流程之外
- 文件路径是否写错

有些项目不是“没更新”，而是“压根没监听到”。

### 9.9 自动刷新老是全页闪一下，能不能优化？

可以。思路一般是：

- 优先让 CSS 走热更新
- 能局部更新的就别整页刷新
- 页面状态比较重要的部分，尽量拆成独立模块
- 复杂页面逐步优化，不要一口气把所有逻辑揉在一起

### 9.10 调试时为什么建议优先看终端和浏览器控制台？

因为开发服务器的问题，很多都会直接反映在这两个地方：

- 终端看构建日志和编译错误
- 浏览器看运行时报错和网络请求
- 两边一起看，定位效率最高

### 老赵给你画重点

- 开发问题优先看“服务、编译、代理、路由”四个方向
- 多数故障不是大问题，而是某个配置链路没接通
- 养成按顺序排查的习惯，效率会高很多

### 赵老师避坑提醒

- 不要一出问题就怀疑 Webpack 本身有 bug
- 先看日志，再看配置，最后才考虑代码逻辑
- 开发环境的小毛病，往往比大 bug 更消耗时间

# 第8章：source map：出问题时怎么快速定位到源码

前面几章里，我们已经把 Webpack 的打包流程、资源处理、开发服务器串起来了。真到项目里写代码，你很快就会碰到一个麻烦：**代码一旦经过打包、压缩、合并，报错信息就不再像源码那样好懂**。控制台里常见的可能只是 `main.js:1:23456`，你根本不知道是哪个文件、哪一行出了问题。

这时候，**source map** 就派上用场了。你可以把它理解成一张“映射表”：它负责把构建后的代码位置，重新对应回源码位置。对开发来说，它是“定位地图”；对排障来说，它是“事故回放”。

说得直白一点，source map 解决的不是“代码为什么错”，而是先帮你回答一个更基础的问题：**错到底发生在哪儿**。位置找对了，后面的分析才有方向。

---

## 一、source map 是什么，为什么能把压缩代码映射回源码

### 1.1 source map 解决的是什么问题？

Webpack 打包后，代码通常会经历这些变化：

- 多个文件合并成 bundle
- ES6+ 代码被转成兼容代码
- 代码被压缩、去空格、混淆
- CSS、图片等资源也可能被重命名或抽离

结果就是：**浏览器执行的是构建产物，但你调试时更想看到源码**。source map 就是用来建立这两者关系的。

简单说：

- 浏览器报错定位的是打包后文件
- source map 告诉浏览器：这个位置对应源码里的哪个文件、哪一行、哪一列

所以它不是把代码“变回去”，而是**保留一份映射关系**。

### 1.2 它是怎么工作的？

可以把它理解成三层信息：

1. **源码**：你写的 `src/index.js`
2. **构建产物**：Webpack 输出的 `dist/main.js`
3. **映射文件**：`main.js.map`

浏览器如果能读到 `.map` 文件，就能通过映射关系反查源码位置。开发者工具里看到的就不只是压缩后的 bundle，而是源码视图。

### 1.3 为什么它很重要？

现代前端项目几乎都绕不开这些情况：

- 使用 Babel、TypeScript、JSX
- CSS 经过预处理和抽离
- 生产环境开启压缩
- 一个页面里有多个入口和 chunk

没有 source map，调试会很痛苦；有了 source map，定位问题的效率会高很多。尤其当项目里 loader 和 plugin 变多后，报错不一定直接指向源码，source map 就成了回头路。

---

## 二、常见 source map 类型与适用场景

### 2.1 为什么 source map 还分很多种？

因为“生成快、定位准、体积小、安全性高”这几个目标没法同时全拿。Webpack 通过 `devtool` 提供不同选择，本质上就是在做取舍。

你可以把它分成两类理解：

- **更适合开发调试**：生成快、定位准
- **更适合生产排查**：尽量保留定位能力，同时控制风险

### 2.2 常见类型怎么选？

#### 1. `source-map`
- 生成完整、独立的 `.map` 文件
- 定位信息完整
- 适合生产环境做错误追踪

特点：**最标准，但生成和体积成本也更高**

#### 2. `cheap-source-map`
- 生成较快
- 通常只到行级，不一定精确到列
- 适合开发环境

特点：**够用、速度快，但精度一般**

#### 3. `eval-source-map`
- 开发阶段常见
- 利用 `eval` 包裹模块
- 重新构建速度通常不错

特点：**开发体验好，不适合生产**

#### 4. `inline-source-map`
- source map 以内联形式放进 bundle
- 不需要额外 `.map` 文件
- 便于调试

特点：**简单直接，但体积大，不适合生产**

#### 5. `hidden-source-map`
- 生成 `.map` 文件，但不在产物里直接暴露引用
- 常用于生产环境错误监控
- 不容易被外部用户直接看到映射

特点：**适合“要定位问题，但不想明着暴露 map 文件”**

### 2.3 适用场景怎么判断？

可以按这个思路选：

- **本地开发**：优先调试效率
- **联调环境**：希望错误能定位，但构建别太慢
- **生产环境**：重点考虑安全和成本，必要时只给监控系统保留映射

一句话总结：  
**开发看效率，生产看风险。**

---

## 三、开发环境和生产环境的 source map 选择策略

### 3.1 开发环境怎么配最舒服？

开发环境的核心目标是：**快、准、顺手**。

通常建议：

- 优先用构建速度较快的配置
- 能看到源码、行号、列号
- 浏览器控制台报错能快速回到源码

很多团队会在开发环境使用 `eval-source-map`、`cheap-module-source-map` 或相近配置。重点不是死记名字，而是理解原则：

- **开发环境要让定位问题尽可能轻松**
- **构建慢一点可以接受，但不能慢到影响反馈效率**

### 3.2 生产环境怎么配才稳妥？

生产环境的目标变了：

- 用户访问要快
- bundle 体积要小
- 源码不希望被直接暴露
- 但线上出问题时，团队最好还能定位

常见策略有三种：

#### 策略一：完全关闭 source map
适合对安全要求高、排查主要靠日志和监控的项目。  
缺点是线上报错定位困难。

#### 策略二：生成 source map，但不公开
常见做法是配合错误监控系统内部存档使用。构建时生成 `.map`，部署时不对外暴露。

#### 策略三：使用 `hidden-source-map`
这是比较常见的折中方案。它生成映射文件，但不会把映射地址直接挂到产物里，用户不容易直接拿到源码映射。

生产环境别想着“先开着再说”。一旦源码映射暴露出去，很多实现细节都会跟着暴露，对一些业务项目来说，这不只是调试问题，也是安全问题。

### 3.3 一套实用判断标准

赵老师给你一个很好用的判断法：

- 如果最痛的是“开发调试慢” → 优先优化开发环境 source map
- 如果最痛的是“线上报错看不懂” → 关注生产环境可追踪性
- 如果最痛的是“源码不能泄露” → 优先控制生产环境暴露方式

source map 不是“必须全开”的开关，而是**按场景配置的工具**。

---

## 四、调试时如何借助 source map 快速定位问题

### 4.1 看到报错后先看什么？

控制台报错时，先按这个顺序看：

1. **错误类型**：语法错、运行时错、Promise reject、资源加载失败
2. **报错位置**：文件名、行号、列号
3. **是否能跳回源码**：开发者工具是否显示原始文件
4. **是否是构建后代码位置**：如果是 bundle 位置，检查 source map 是否生效

很多人一上来就盯着堆栈最后一行看，其实应该先判断：这是不是一个“可映射”的错误。

### 4.2 一个简单的报错定位流程

你可以照这个流程来：

**第一步：确认报错来自哪里**  
先看控制台堆栈，是业务代码、第三方库，还是构建后的 bundle。

**第二步：检查 source map 是否可用**  
打开 DevTools 的 `Sources` 面板，看看能不能找到 `webpack://`、原始目录结构，或者直接跳到源码文件。

**第三步：根据映射位置回到源码**  
如果堆栈从 `main.js:1:45678` 变成了 `src/components/Login.vue:32:15`，就说明映射成功了。接下来直接看那一行附近的逻辑。

**第四步：结合上下文判断原因**  
常见问题往往是这些：
- 变量未定义
- 入参为空
- 异步状态还没准备好
- 边界条件漏判断
- 第三方库调用方式不对

**第五步：回头看构建链路**  
如果源码没问题，但打包后报错怪怪的，再去看 loader、plugin、Babel、压缩配置是否影响了结果。

这个流程的核心不是“马上修好”，而是先把问题从黑盒里拽出来，变成你能看懂的源码问题。

### 4.3 如何验证 source map 是否真的生效？

你可以做三个检查：

#### 检查一：浏览器开发者工具里能否看到源码
打开 `Sources` 面板，看左侧是否出现 `webpack://` 或原始目录结构。  
如果只有压缩后的 `main.js`，说明 source map 可能没生效。

#### 检查二：报错位置是否指向源码文件
如果错误从 `main.js:1:45678` 变成了 `src/components/Login.vue:32:15`，说明映射已经起作用。

#### 检查三：构建产物中是否存在 `.map`
开发环境一般能看到生成文件；生产环境则要看你是否有意隐藏或不部署它。

如果前两步都不对，大概率不是代码本身的问题，而是 Webpack 配置没配好，或者构建后没有正确生成映射。

---

## 五、source map 的成本、性能与安全性考虑

### 5.1 它不是免费的

很多人一上来就把 source map 全开，结果项目越来越慢。原因很简单：

- 生成 source map 需要额外计算
- 文件会变大
- 构建时间可能增加
- 某些模式下调试工具解析也会消耗性能

所以要明白：**source map 是调试成本和构建成本之间的平衡**。

### 5.2 对性能有哪些影响？

主要有三类影响：

- **构建性能**：大项目生成 map 会拖慢打包速度
- **网络传输**：如果公开部署，浏览器可能额外请求它
- **调试体验**：开启后更方便，但某些模式下也可能影响热更新或首屏构建

结论很简单：  
**开发环境可以更重，生产环境要更克制。**

### 5.3 安全风险不能忽视

source map 里可能暴露很多信息：

- 源码结构
- 业务逻辑
- 接口路径
- 注释和变量命名
- 甚至一些不该对外暴露的实现细节

所以如果生产环境直接公开 `.map` 文件，就等于把源码“半透明”地交出去。对安全敏感的项目来说，这必须慎重。

赵老师提醒你一句：  
**能不能公开，不是看“别人会不会发现”，而是看“你愿不愿意承担被完整还原的风险”。**

### 5.4 实用建议清单

你可以用这份清单做决策：

- 开发环境：优先保证调试效率
- 联调环境：优先保证定位能力
- 生产环境：优先考虑安全和用户体验
- 线上报错追踪：可以考虑内部保留 map 文件
- 对外发布：慎重公开完整映射

最稳妥的做法通常是：**开发开，生产慎开，线上只给内部排查用**。

---

## 老赵给你画重点

1. **source map 的本质是映射关系，不是“还原代码”**。  
2. **开发环境重调试，生产环境重安全**，别一套配置用到底。  
3. `source-map`、`cheap-*`、`eval-*`、`hidden-source-map` 各有场景，没有绝对最优。  
4. 调试时先确认 source map 是否生效，再去定位源码。  
5. source map 会带来体积、构建和安全成本，不能无脑全开。  
6. 它能帮你快速回到源码位置，但真正修复问题还得回到业务逻辑里分析。  
7. 真正好用的不是“开了 source map”，而是“知道什么时候开、开到什么程度、怎么收口”。

---

## 赵老师避坑提醒

1. **别把生产环境的 source map 直接公开部署**，尤其是业务逻辑复杂的项目。  
2. **别只看名字选配置**，先想清楚你要的是速度、精度还是安全。  
3. **别以为有 source map 就万事大吉**，它只能帮你定位位置，不能替你修 bug。  
4. **别忽略团队流程**，有些项目会把 `.map` 文件交给错误监控平台，而不是给用户浏览器直接下载。  
5. **别把开发环境和生产环境混成一套配置**，这往往是调试慢、线上不安全的根源。  
6. **别在构建慢的时候只怀疑 Webpack 本体**，先看看是不是 source map 生成模式太重。  
7. **别忘了验证映射是否真的可用**，有些项目只是生成了 `.map`，但浏览器并没有正确读取。

---

## 小结：把“看不懂报错”变成“能快速回到源码”

source map 的价值，说白了就是四个字：**缩短定位**。  
它让你从“我只看到压缩后的报错”变成“我能直接跳到源码那一行”。对前端工程化来说，这不是锦上添花，而是基本能力。

你接下来要建立的思维是：

- 开发时，优先让自己看得懂、改得快
- 上线时，优先让用户访问稳、让团队排查有路可走
- 配置时，别迷信某一种 devtool，按场景做取舍

如果你以后在浏览器里看到一串看不懂的 bundle 堆栈，别慌，先看看 source map 有没有生效，再按“报错位置 → 源码文件 → 上下文逻辑”这条线往回找。  
这就是前端工程化里很实用的一项基本功。

下一章我们会继续往下讲，看看 Webpack 如何通过 **code splitting** 把大包拆开，让首屏更快、加载更灵活。

# 第9章：code splitting：把包拆开，让加载更聪明

前面我们已经把 Webpack 的基础配置、资源处理和开发体验摸了个大概。到了项目稍微一大，很多同学都会发现：**打出来的包怎么这么肥？** 页面还没开始干活，浏览器先下载一大坨 JS，首屏自然慢。

这时候，`code splitting` 就该上场了。

说白了，代码分割不是为了炫技，而是为了让构建产物更合理：**首屏先加载该用的，不急着用的后面再拿，公共的别重复打，第三方库也别和业务代码搅在一起。** Webpack 的目标不是把所有东西塞进一个文件，而是把依赖关系组织成一组更聪明的资源。

---

## 一、code splitting 的目标：为什么“大包”不一定好？

如果把一个项目比作搬家，一个大 bundle 就像把所有家具、衣服、锅碗瓢盆全塞进一辆车。能搬走，但装卸慢、找东西慢，到了新家也不好整理。

Webpack 里的代码分割，核心就是解决三个问题：

### 1. 减少首屏体积
首屏真正需要的，通常只是首页、基础框架、当前路由相关代码。后台页、图表库、编辑器、重组件，不一定要第一次就下载。

### 2. 提升加载效率
包太大，不只是下载慢，还会拖累解析和执行。JS 文件越大，浏览器主线程压力越重，移动端尤其明显。

### 3. 提高缓存命中率
如果所有代码都打成一个文件，业务改一点，整个 bundle 的 hash 可能都变了，缓存容易失效。拆分后，公共库、运行时代码、业务代码可以分别缓存，更新更稳。

你可以把它理解成：**把“会变的”和“相对稳定的”分开存放。** 这样浏览器不用每次都重新下载整包，用户体验会舒服很多。

### 老赵给你画重点
- `code splitting` 的本质是**按需加载 + 合理拆包**。
- 它不是越碎越好，而是要让**首屏更轻、缓存更稳、加载更快**。
- 拆包不是为了“拆得好看”，而是为了“拆得有收益”。

### 赵老师避坑提醒
- 别一上来就追求很多包，包太碎会增加请求数。
- 别只盯着体积，**解析和缓存**同样重要。
- 小项目别过度优化，维护成本会反过来拖累你。

---

## 二、入口分割、动态导入、按需加载：代码分割怎么落地？

Webpack 的代码分割不是空喊口号，而是能落到配置和写法上的。最常见的方式有三类：**入口分割、动态导入、按需加载。**

### 1. 入口分割：从入口层面拆开
如果项目天然有多个独立页面，比如 `index`、`admin`、`mobile`，就可以配置多个入口：

```js
module.exports = {
  entry: {
    main: './src/index.js',
    admin: './src/admin.js'
  }
}
```

Webpack 会根据入口生成不同的依赖图。不同入口之间共享的模块，再配合 `splitChunks` 做公共抽取。入口分割更适合“天然就分开”的项目，比如企业官网和后台系统、PC 端和移动端入口。

### 2. 动态导入：真正的按需加载
单页应用里，更常见的是通过 `import()` 动态导入模块：

```js
button.addEventListener('click', async () => {
  const module = await import('./heavy-module')
  module.run()
})
```

这里的关键是：**`import()` 不是静态依赖**。Webpack 看到它，会把对应模块拆成单独的 chunk，运行时真正触发时再去加载。它特别适合“用户点了才需要”的功能，比如高级筛选、弹窗、编辑器、图表等。

### 3. 按需加载：业务层面的拆分思路
按需加载不只是语法问题，更是业务判断问题。你要先想：这个模块是不是“首次就必须用”？

常见判断标准：
- 首屏必须展示的：留在主包
- 交互后才会打开的：适合动态导入
- 低频功能：适合延迟加载
- 大型依赖库：适合独立拆分

赵老师常说：**先站在用户操作路径上想一遍，再决定拆不拆。** 别站在目录结构上想，目录整齐不等于体验更好。

### 老赵给你画重点
- 入口分割适合**多入口项目**。
- `import()` 是最实用的**动态导入**方式。
- 按需加载的核心，是先判断**先用什么，后用什么**。

### 赵老师避坑提醒
- 动态导入后，记得处理 loading 和错误兜底。
- 路由懒加载别把首屏关键组件也拆出去，否则页面会空很久。
- 某些模块虽然不常用，但首次交互必需，就别拆得太晚。

---

## 三、splitChunks：Webpack 怎么自动帮你拆公共代码？

如果说 `import()` 是“你告诉 Webpack 什么时候拆”，那 `splitChunks` 就是“Webpack 帮你判断哪些该拆”。

它主要解决的是：**公共依赖重复打包** 的问题。

比如两个入口都依赖 `lodash`，不处理的话，可能会打两份，体积变大，也浪费缓存。

### 1. splitChunks 的基本思路
Webpack 会根据模块的复用情况、体积等因素，把满足条件的模块抽出来，形成独立 chunk。

常见配置如下：

```js
module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all'
    }
  }
}
```

`chunks: 'all'` 的意思是：**同步和异步模块都参与拆分**。这是最常见的起点配置。先开 `all`，再看效果，最后再细调规则，通常更稳。

### 2. 一个最小可用的配置示例

```js
module.exports = {
  entry: './src/index.js',
  output: {
    filename: '[name].[contenthash:8].js',
    path: path.resolve(__dirname, 'dist'),
    clean: true
  },
  optimization: {
    runtimeChunk: 'single',
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        vendors: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendors',
          chunks: 'all'
        },
        common: {
          minChunks: 2,
          name: 'common',
          chunks: 'all'
        }
      }
    }
  }
}
```

这段配置里有三个动作：

- `vendors`：把第三方库单独拎出来
- `common`：把多个模块都用到的公共代码抽出来
- `runtimeChunk: 'single'`：把运行时代码单独拆一份，减少业务代码变动时的缓存抖动

这就是最基本、也最常见的拆包方向。

### 3. 常见拆分方向
#### 公共业务代码
多个页面都用到的工具函数、组件、校验逻辑，可以抽出来。比如日期格式化、手机号校验、通用弹窗，这些东西每个页面都打一次，就很浪费。

#### 第三方库
像 `react`、`vue`、`lodash`、`axios` 这种大库，通常很适合独立拆分，便于缓存。业务代码经常改，但库本身不一定跟着变。

#### 异步模块
通过 `import()` 进来的模块，本身就天然适合拆成异步 chunk，Webpack 往往已经能做出不错的判断。

### 4. 拆分时常看的几个维度
实际配置中，常见关注点有：

- `minSize`：模块最小多大才值得拆
- `maxSize`：太大的 chunk 可以继续切小
- `minChunks`：至少被多少处复用才抽离
- `cacheGroups`：对不同类型模块做分组规则

一个常见思路是把第三方库和业务公共代码分开：

```js
optimization: {
  splitChunks: {
    chunks: 'all',
    cacheGroups: {
      vendors: {
        test: /[\\/]node_modules[\\/]/,
        name: 'vendors',
        chunks: 'all'
      },
      common: {
        minChunks: 2,
        name: 'common',
        chunks: 'all'
      }
    }
  }
}
```

### 老赵给你画重点
- `splitChunks` 是**自动抽公共代码**的核心工具。
- 好的拆分要按**复用率、体积、缓存价值**来判断。
- `chunks: 'all'` 可以作为入门默认思路。

### 赵老师避坑提醒
- 别把 `splitChunks` 配得太复杂，先理解默认规则。
- 拆得太细会增加请求数，反而拖慢页面。
- 很小的公共模块没必要硬拆，可能得不偿失。

---

## 四、公共代码、第三方库和异步模块：到底该怎么拆？

这个问题最关键。很多人会问：**哪些放主包，哪些拆出去？**

### 1. 公共代码：优先看复用范围
如果工具函数、组件、配置逻辑在多个页面里都会用到，可以考虑抽成公共 chunk。

判断标准很简单：
- 是否跨页面复用
- 是否频繁变动
- 是否稳定，适合缓存

如果某段代码只在一个页面里用，别强行抽出去。拆包不是为了文件列表更长，而是为了加载更合理。

### 2. 第三方库：大库优先独立
第三方库通常体积稳定、更新频率低，适合单独分包。比如 UI 库、图表库、富文本编辑器、基础运行依赖。

独立出来的好处很明显：**业务代码更新时，第三方库缓存还能继续复用。**

### 3. 异步模块：交给运行时加载
页面点击后才弹出来的对话框、某个路由页面、复杂筛选面板，都适合异步拆分。

拆异步模块的原则：
- 首次屏幕不需要的，往后放
- 交互触发的，延迟加载
- 失败后要有兜底

比如路由懒加载时，最好配一个加载态，避免用户点了链接却看到空白页。

### 4. 一点更实在的判断方法
如果你现在拿到一个项目，不知道怎么拆，就按这个顺序看：

1. 先找首屏必需的代码，留在主包
2. 再找重复出现的公共依赖，交给 `splitChunks`
3. 最后找用户点了才会用的模块，改成 `import()`

这个方法不花哨，但很实用。很多项目的优化收益，往往就来自这三步，而不是更复杂的参数微调。

### 老赵给你画重点
- 公共代码看“复用”，第三方库看“体积和稳定性”，异步模块看“使用时机”。
- 拆包不是按文件类型拆，而是按**访问路径和更新频率**拆。
- 优先照顾用户体验，而不是目录整齐。

### 赵老师避坑提醒
- 别把很小的工具库也单独拆成 chunk。
- 别忘了异步模块的失败处理。
- 第三方库拆分后，版本控制不好会让缓存策略变复杂。

---

## 五、chunk、bundle、runtime：代码分割后到底怎么看构建产物？

这部分最容易混。很多人看到构建结果里一堆文件，脑子就打结：哪个是 chunk？哪个是 bundle？runtime 又是什么？

### 1. chunk：Webpack 里的“代码块概念”
从 Webpack 的角度看，chunk 是打包过程中的一个逻辑块。它可以来自入口、动态导入、公共抽取，或者 Webpack 自己的优化结果。

你可以把它理解成：**Webpack 处理过程中形成的一个代码单元。**

### 2. bundle：最终输出的文件
bundle 更偏向最终产物，也就是你在 `dist` 目录里看到的 `.js` 文件。

简单理解：
- chunk 是过程概念
- bundle 是输出文件

一个 chunk 最终可能对应一个 bundle，也可能因为优化策略，输出结果更复杂。

### 3. runtime：负责串起这些包的运行时代码
runtime 里包含 Webpack 运行时需要的逻辑，比如模块加载、chunk 加载、缓存处理等。它体积不大，但很关键。

可以把它理解成“调度员”。主包、公共包、异步包虽然各自独立，但最终能顺利运行，靠的就是它把这些资源串起来。

### 4. 拆分后的整体理解
整个过程可以理解为：
- 主入口生成主 chunk
- 动态导入生成异步 chunk
- `splitChunks` 抽出公共 chunk
- runtime 负责协调加载和执行

### 5. 这些文件分别在干什么
如果你在构建产物里看到：

- `main.xxx.js`：通常是业务入口代码
- `vendors.xxx.js`：通常是第三方库
- `common.xxx.js`：通常是公共业务模块
- `runtime.xxx.js`：通常是运行时引导逻辑

当然，文件名不是绝对的，具体还要看你的配置。你不必死记名字，重点是看它们在依赖链里的职责。

### 老赵给你画重点
- `chunk` 是“过程概念”，`bundle` 是“输出文件”。
- `runtime` 是“调度员”，负责加载和组织拆出来的包。
- 看构建结果时，别只盯文件名，要看它在依赖关系里扮演什么角色。

### 赵老师避坑提醒
- 别把 chunk 和 bundle 当成一回事。
- 有些项目里 runtime 单独抽出，是为了减少主包变动导致的缓存失效。
- 看到多个文件别慌，先判断它们是主包、公共包还是异步包。

---

## 六、实战思路：怎么判断一个项目需不需要 code splitting？

赵老师平时看项目，会先问四句：

1. **首屏是不是太重？**  
   如果首页 JS 很大，先考虑按需加载和公共抽离。

2. **有没有明显的低频功能？**  
   比如编辑器、报表、大弹窗、复杂图表，优先动态导入。

3. **有没有大量第三方库重复出现？**  
   如果有，优先考虑 `splitChunks`。

4. **更新时是不是经常整包失效？**  
   如果是，说明缓存粒度太粗，需要把 runtime、第三方库、业务代码分开。

### 一套简单的落地顺序
如果你现在就要开始做，建议按这个顺序来：

1. 先把页面关键路径跑通  
2. 给低频模块加 `import()`  
3. 开启 `splitChunks`  
4. 检查公共依赖是否重复  
5. 观察首屏体积和缓存效果，再细调规则  

这套顺序不花哨，但能很快看到收益。尤其是中大型项目，先做“最值钱”的拆分，通常比一上来猛调参数更有效。

如果你已经在项目里用了路由懒加载，那么下一步就别急着继续拆很多小块，先看首屏是不是已经变轻、缓存是不是更稳定。优化这件事，讲究的是**先见效，再精修**。

---

## 本章小结

代码分割不是 Webpack 里最复杂的功能，但它是**最能直接改善用户体验**的能力之一。你只要记住一个核心原则：**把现在必须要的留在前面，把以后再说的放到后面。**

今天你应该建立起这几个认知：

- `code splitting` 的目标是减少首屏体积、提升加载效率、增强缓存效果
- 入口分割适合多入口项目，`import()` 适合异步按需加载
- `splitChunks` 用来自动抽公共代码和第三方库
- 公共代码、第三方库、异步模块要按复用率和使用时机来拆
- `chunk`、`bundle`、`runtime` 是理解构建产物的关键概念

### 老赵给你画重点
- 拆包不是目的，**加载更聪明**才是目的。
- 先从动态导入和 `splitChunks` 下手，最容易看到效果。
- 构建结果看不懂没关系，抓住“谁负责加载、谁负责执行、谁负责缓存”这条线就行。

### 赵老师避坑提醒
- 不要为了拆而拆，拆分要有业务依据。
- 不要忽略加载失败、首屏空白、请求数过多这些副作用。
- 代码分割是优化的一部分，不是万能药，别指望一配就飞。

下一章我们再接着聊 tree shaking，看看怎么把没用到的代码尽量摇出去，让最终产物再瘦一点。

# 第10章：tree shaking：把没用的代码尽量摇掉

## 开篇引入：为什么你的代码“明明没写多少”，包还是不小？

全栈老赵先说句实话：前端包体积大，很多时候不是业务真复杂，而是**写进去了但没用上**。比如一个工具库只用了一个函数，结果整个库都被打进来了；或者某个通用模块只有一小段被页面用到，其余代码也跟着进包。

这类问题在大项目里特别常见。你以为只是多引了几个模块，实际上构建产物已经悄悄膨胀。等到线上首屏变慢、加载变卡，你才会想：是不是有冗余代码没清掉？

这时候，Webpack 里的一个重要优化能力就派上用场了——**tree shaking**。它的目标很直接：**把未使用的导出代码尽量摇掉**，让最终产物更小、更干净。

但赵老师先提醒一句：tree shaking 不是自动魔法，它有前提，也很吃代码写法。代码越规范，Webpack 越容易把无用部分清走；写法越随意，效果越打折扣。

---

## 1. tree shaking 的核心目标：到底摇掉的是什么？

tree shaking 关注的不是“文件有没有被引入”，而是**模块里哪些导出真的被用了，哪些没有**。

### 1.1 它的工作对象是“导出级别”的代码

```js
// utils.js
export function add(a, b) {
  return a + b;
}

export function minus(a, b) {
  return a - b;
}
```

如果别的文件只用 `add`：

```js
import { add } from './utils';

console.log(add(1, 2));
```

理想情况下，最终产物里只保留 `add`，`minus` 会被剔除。也就是说，tree shaking 做的是**模块内部的精细裁剪**，不是简单删文件。

### 1.2 它解决的是“静态可分析”的无用代码

tree shaking 是构建时分析，不是运行时猜测。Webpack 会根据依赖关系、导入导出关系，判断哪些符号没被使用，然后尽量删除。

你可以把它理解成：

- 先搭一棵依赖树
- 再从入口往下看哪些分支真的会走到
- 没走到的分支，就尽量剪掉

### 1.3 它和“打包成一个文件”不是一回事

**打包**解决的是“把模块组织起来，变成浏览器能加载的资源”；  
**tree shaking**解决的是“在打包时把没用的代码尽量去掉”。

一个是收纳，一个是先做减法。

#### 老赵给你画重点
- tree shaking 的核心目标：**移除未使用的导出代码**
- 它不是删文件，而是删模块里没用到的导出
- 它依赖静态分析，代码越规整，效果越好

#### 赵老师避坑提醒
- 不是“引入了模块就一定全打包”
- 也不是“写了 ES Module 就一定自动变小”
- 如果模块里有副作用，Webpack 可能不敢随便删

---

## 2. ES Module 为什么是 tree shaking 的基础？

tree shaking 最关键的前提之一，就是 **ES Module（import/export）**。因为它天然适合静态分析。

### 2.1 为什么 ES Module 适合分析？

```js
import { a } from './m';
export const b = 1;
```

这种语法在代码执行前就能解析出依赖关系。Webpack 不需要真的跑代码，就能知道从哪儿导入、导入了什么、谁导出了什么。

### 2.2 CommonJS 为什么不那么友好？

像 `require()` 这种写法，依赖关系和导出内容往往不够静态：

```js
const m = require('./m');
```

它可能写在条件里，导出对象也可能动态变化，构建时不容易精确判断。所以在 Webpack 语境里，**ES Module 是 tree shaking 的天然搭档**。不是说 CommonJS 不能用，而是它会让静态分析更保守。

### 2.3 不要把“能导入”误解成“可摇树”

有些写法看起来像模块化，实际上会让 tree shaking 很难工作，比如动态访问属性、混合导出结构、运行时才决定用哪个导出。构建工具看不清楚，就只能保守处理。

#### 老赵给你画重点
- **ES Module 是 tree shaking 的基础**
- 因为它的导入导出关系更容易被静态分析
- 尽量统一模块体系，别让分析变复杂

#### 赵老师避坑提醒
- 别把 `import` 和 `require` 混着乱用
- 写库时导出方式要规整
- 动态访问会直接降低优化效果

---

## 3. sideEffects、纯函数与可摇树代码：怎么写才更容易被清掉？

tree shaking 不只看你“有没有导出”，还要看你“有没有副作用”。

### 3.1 什么叫副作用？

副作用就是：**代码执行时除了返回值之外，还会影响外部环境**。比如修改全局变量、改 DOM、发请求、挂原型，或者引入 CSS 让样式立刻生效。

如果模块一被引入就会做这些事，Webpack 就不能轻易把它删掉，因为删了可能影响页面行为。

### 3.2 为什么有些代码摇不掉？

```js
// math.js
export function add(a, b) {
  return a + b;
}

export function minus(a, b) {
  return a - b;
}

console.log('math 模块被加载了');
```

即使入口只用了 `add`，这个模块顶层还是有副作用，Webpack 就会更保守。

再比如样式引入：

```js
// style.js
import './base.css';

export function initPage() {
  console.log('init');
}
```

`base.css` 一旦引入就会生效，这类代码天然带副作用，不能随便删。

### 3.3 `sideEffects`：告诉 Webpack 哪些文件不能乱删

在 `package.json` 里可以配置：

```json
{
  "sideEffects": false
}
```

意思是：这个包里的文件基本没有副作用，可以放心做 tree shaking。

如果有些文件确实有副作用，比如全局样式文件，可以单独声明：

```json
{
  "sideEffects": [
    "*.css",
    "*.less"
  ]
}
```

意思是：CSS、Less 有副作用，别乱删，其它 JS 模块尽量优化。

### 3.4 纯函数为什么更利于 tree shaking？

纯函数的特点是：**相同输入，总是得到相同输出，并且不影响外部状态**。

```js
export function sum(a, b) {
  return a + b;
}
```

这种函数更适合被摇掉或保留，因为它没有隐藏行为。模块越干净，Webpack 越敢动手。

#### 老赵给你画重点
- `sideEffects` 是 tree shaking 的重要配合项
- 纯函数、细粒度导出、少副作用，更容易被摇掉
- 副作用不是坏事，但要明确告诉构建工具

#### 赵老师避坑提醒
- `sideEffects: false` 不是随便一配就完事，配错了可能删掉有用代码
- CSS 通常不要直接当成“无副作用”
- 顶层执行代码越多，tree shaking 越保守

---

## 4. 开发中哪些写法会影响 tree shaking 效果？

很多时候不是 Webpack 不行，而是代码写法把它难住了。

### 4.1 这些写法容易拖后腿

**第一类：大而全的默认导出。**

```js
export default {
  add,
  minus,
  multiply
};
```

然后外部再按属性取值。这样构建工具很难像处理命名导出那样精确判断用了哪部分。

**第二类：模块顶层有明显副作用。**

```js
console.log('模块被执行了');
initSomething();
```

只要引入就会执行，Webpack 会更保守。

**第三类：动态访问属性。**

```js
const fn = utils[name];
```

静态分析难度高，优化空间小。

**第四类：混用 CommonJS 和 ES Module。**

不是绝对不行，但分析链路会更复杂。

### 4.2 更推荐的写法

- 用命名导出，不要把所有东西塞进一个默认对象
- 把初始化逻辑从业务工具模块里拆出去
- 需要副作用的文件单独命名、单独声明
- 能静态写死的路径，不要动态拼来拼去

如果你在重构老项目，先从工具模块开始改最划算。把“什么都往一个文件里塞”的习惯改掉，tree shaking 往往就会好很多。

### 4.3 一个快速判断方法

判断一个模块是否“可摇树”，可以看四点：

1. 构建时能不能看懂依赖关系？
2. 有没有顶层副作用？
3. 导出是不是细粒度且稳定？
4. 有没有被配置成可安全分析？

如果有多条不满足，tree shaking 效果大概率不理想。

#### 老赵给你画重点
- tree shaking 很吃代码风格，不只是吃配置
- 命名导出、静态路径、少顶层副作用，更友好
- “能不能摇掉”本质上是“构建工具敢不敢删”

#### 赵老师避坑提醒
- 别把初始化逻辑混进工具模块
- 别依赖动态对象属性去调用导出
- 别以为压缩后看着小，就代表 tree shaking 生效了

---

## 5. tree shaking 和压缩、代码分割之间是什么关系？

这三个词经常一起出现，但不是一回事。

### 5.1 tree shaking 负责“删不用的”

它是在构建分析阶段尽量移除未使用导出，属于**结构级优化**。

### 5.2 压缩负责“把留下的写得更短”

压缩通常会做去空格、改变量名、简化表达式、删除开发环境代码。它优化的是字节数和传输体积，但**不是** tree shaking 本身。

### 5.3 代码分割负责“把代码切开”

代码分割的目标是把不同场景需要的代码拆成多个 chunk，按需加载。它更关注首屏更轻、路由按需加载、避免一次性加载全部资源。

### 5.4 它们怎么协作？

可以这么理解：

- tree shaking：先把不用的剪掉
- 压缩：再把留下的压小
- 代码分割：最后把不同功能拆开，按需发给浏览器

这三者组合起来，才是比较完整的体积优化思路。别把问题搞混：明明是没做按需加载，却怪 tree shaking 不够强；或者明明是模块写法不规范，却以为换个压缩插件就能解决。

#### 老赵给你画重点
- tree shaking、压缩、代码分割不是同一个东西
- tree shaking 侧重“删没用的代码”
- 压缩侧重“缩小保留代码”
- 代码分割侧重“拆包按需加载”

#### 赵老师避坑提醒
- 不要把“包变小”全归功于 tree shaking
- 压缩器强，可能让你误以为 tree shaking 很成功
- 代码分割做得好，不代表单个 chunk 里没有冗余代码

---

## 结尾小结：写得规范，优化才会真的发生

这一章你要记住一句话：**tree shaking 不是玄学，它建立在模块规范、静态分析和副作用控制之上。**

你可以把它理解成一场“清理无用代码”的流程：

1. 用 ES Module 组织导入导出
2. 尽量保持模块纯净、少副作用
3. 用 `sideEffects` 明确告诉 Webpack 哪些文件不能随便删
4. 避免动态、混乱、顶层执行太多的写法
5. 再结合压缩和代码分割，进一步把包体积压下来

如果你现在就要检查项目里的 tree shaking 效果，老赵建议先做三件事：

- 看是不是统一使用了 ES Module
- 看 `package.json` 里有没有合理配置 `sideEffects`
- 看工具模块里有没有不必要的顶层副作用

### 最后给你的行动建议

- 把常用工具函数改成命名导出
- 把全局初始化、样式引入、环境配置拆开管理
- 检查是否存在 CommonJS 和 ES Module 混用
- 在构建后对比产物大小，确认优化是否真的生效

这样你会发现，tree shaking 不是“点一下就有”的功能，而是**写法、配置、构建策略一起配合**的结果。懂了这个，你才算真正开始看懂 Webpack 的优化逻辑了。

#### 老赵给你画重点
- 先写对，再谈优化
- 先让构建工具看懂，再让它帮你删
- tree shaking 的本质是“规范代码后的自动减法”

#### 赵老师避坑提醒
- 别把 tree shaking 当成万能瘦身工具
- 别只盯着结果大小，不看代码结构
- 别忽略副作用和模块系统统一性，它们往往才是关键

# 第11章：多环境配置和常见优化：开发、测试、生产要分开看

前面你已经把 Webpack 的基本盘摸得差不多了：入口、出口、loader、plugin，以及各种资源处理。到了这一章，咱们就从“能跑起来”往“跑得舒服、跑得稳、跑得快”再迈一步。

全栈老赵先说句大实话：**Webpack 真正拉开差距的，不是会不会堆 loader，而是能不能把开发、测试、生产三种场景分开看、分开配、分开优化。** 因为这三种环境的诉求天然不同：

- **开发环境**：要快，改完能立刻看到效果，报错要清楚。
- **测试环境**：要稳，配置尽量接近线上，方便验证问题。
- **生产环境**：要小、要稳、要可缓存，尽量少出问题。

如果把三种需求揉成一套配置，最后通常就是：开发卡、生产大、排查难、维护累。

---

## 一、为什么要做多环境配置：开发、测试、生产关注点不同

先问一个关键问题：**为什么不能一套配置走天下？**

答案很简单，不同环境的目标天然冲突。

### 1. 开发环境：先保证体验

开发时最需要的是：

- 启动快
- 修改快
- 热更新快
- 报错清楚
- Source Map 好用

这时候不太关心压缩不压缩，文件名长一点短一点都无所谓。只要能快速定位问题，效率就高。

### 2. 测试环境：尽量接近生产

测试环境通常要验证：

- 接口是否正常
- 静态资源是否能正确加载
- 路由、懒加载、分包是否可用
- 线上会不会因为配置差异出问题

所以测试环境一般更接近生产，但有时会保留一些调试能力，比如稍微详细一点的 source map。它的角色就是上线前的预演。

### 3. 生产环境：尽量为用户负责

生产环境最关心的是：

- 包体积小不小
- 首屏加载快不快
- 缓存好不好用
- 出问题后是否容易定位
- 是否有多余代码

所以生产环境一般会启用压缩、分包、长期缓存命名、tree shaking 等优化。说白了，生产环境不是给开发者图方便的，而是给用户负责的。

### 4. 一个典型误区

很多初学者喜欢在 `webpack.config.js` 里写一堆判断：

```js
if (process.env.NODE_ENV === 'development') { ... }
if (process.env.NODE_ENV === 'production') { ... }
```

能跑，但很快就会乱。更好的方式是：**把公共配置、环境配置拆开管理，再按环境合并。**

### 老赵给你画重点

- 不同环境目标不同，配置不能一锅端。
- 开发看速度，测试看接近线上，生产看性能和稳定性。
- 多环境配置的本质，是把公共部分和差异部分分开。

### 赵老师避坑提醒

- 别把开发专用配置带到生产里，比如过于详细的日志、无脑 source map。
- 也不要把生产优化强行放进开发环境，不然本地改一个文件等半天。
- 环境分层的目的不是炫技，是降低维护成本。

---

## 二、常见配置拆分方式：基础配置、环境配置、合并策略

那具体怎么拆？思路很朴素。

### 1. 拆成三层最常见

通常会拆成：

- **基础配置**：所有环境都共用的部分
- **开发配置**：只给开发环境用
- **生产配置**：只给生产环境用

例如：

- `webpack.common.js`
- `webpack.dev.js`
- `webpack.prod.js`

基础配置里放公共内容，比如：

- 入口 `entry`
- 输出 `output`
- 常用 loader
- 资源处理规则
- 公共插件

开发配置里放：

- `devServer`
- source map
- 热更新相关设置

生产配置里放：

- 压缩
- 分包
- 文件哈希
- 缓存策略

### 2. 合并策略：不是复制粘贴

拆分后，最关键的一步是**合并**。你可以把它理解成：公共骨架 + 环境补丁。好处很直接：

- 避免重复写配置
- 环境差异一眼能看出来
- 后期维护更轻松

### 3. 一个实用的组织方式

```text
config/
  webpack.common.js
  webpack.dev.js
  webpack.prod.js
  webpack.test.js
```

然后按不同命令加载对应配置。意义不是文件变多，而是**职责更清晰**。

### 4. 推荐的合并思路

```js
// webpack.dev.js
const { merge } = require('webpack-merge')
const common = require('./webpack.common.js')

module.exports = merge(common, {
  mode: 'development',
  devtool: 'eval-source-map',
  devServer: {
    hot: true,
    open: true
  }
})
```

生产环境同理：

```js
// webpack.prod.js
const { merge } = require('webpack-merge')
const common = require('./webpack.common.js')

module.exports = merge(common, {
  mode: 'production'
})
```

这样公共配置只写一次，环境差异单独维护，改 loader 也不用三份文件一起改。

### 5. 什么时候该继续拆？

如果配置文件开始出现这些信号，就该考虑再细分了：

- 同一个文件里出现大量环境判断
- 插件和规则越来越多，阅读困难
- 开发和生产差异越来越明显
- 团队里不同人对配置理解不一致

### 老赵给你画重点

- 基础配置放公共逻辑，环境配置放差异逻辑。
- 拆分不是目的，**可维护**才是目的。
- 合并配置的核心思想，是减少重复、降低认知负担。

### 赵老师避坑提醒

- 别为了拆分而拆分，项目特别小时过度拆文件只会增加复杂度。
- 环境配置里不要偷偷修改公共规则，容易引起排查灾难。
- 配置文件命名要统一，不然团队协作时很容易看晕。

---

## 三、命令行怎么切环境：开发、测试、生产切换要有入口

光把文件拆开还不够，你还得让项目知道“现在跑的是哪个环境”。

### 1. 最简单的切换方式

通常会在 `package.json` 里写不同命令：

```json
{
  "scripts": {
    "dev": "webpack serve --config config/webpack.dev.js",
    "build": "webpack --config config/webpack.prod.js",
    "test": "webpack --config config/webpack.test.js"
  }
}
```

这样一来：

- `npm run dev` 启动开发环境
- `npm run build` 生成生产包
- `npm run test` 跑测试环境配置

### 2. 结合环境变量更灵活

有些项目还会配合 `NODE_ENV` 或自定义环境变量控制行为，比如：

```json
{
  "scripts": {
    "dev": "NODE_ENV=development webpack serve --config config/webpack.dev.js",
    "build": "NODE_ENV=production webpack --config config/webpack.prod.js"
  }
}
```

这样做的好处是，插件和代码里也能感知当前环境，比如某些调试日志只在开发环境显示。

### 3. 真实项目里怎么用

可以理解成三层开关：

- **命令行选配置文件**
- **配置文件里再按环境补充规则**
- **代码里根据环境决定是否打印调试信息**

这样环境就分清楚了，不会出现“看起来是生产，实际跑着开发规则”的尴尬。

### 老赵给你画重点

- 命令行要有明确入口，别让环境切换靠猜。
- `dev`、`build`、`test` 最好分开命令。
- 环境变量是辅助，不是替代配置拆分。

### 赵老师避坑提醒

- 不要只改 `NODE_ENV`，却还在用同一份大而全的配置。
- Windows 和 macOS/Linux 的环境变量写法可能不同，团队里要统一方案。
- 命令语义要清楚，别把开发包叫成生产包。

---

## 四、常见优化手段：缓存、压缩、分包、资源命名

说完分环境，咱们进入大家最关心的部分：**怎么优化打包产物？**

### 1. 缓存：让浏览器别老是重新下

缓存是最基础也最值钱的优化之一。思路很简单：**没变的文件，就尽量让浏览器继续用旧的。**

最常见的做法是给文件名加内容相关的哈希，比如：

- `app.8d3f1a.js`
- `style.91ac2c.css`

这样当内容变了，文件名就变，浏览器会重新请求；内容没变，文件名不变，就能继续命中缓存。这个策略对生产环境特别重要。

### 2. 压缩：让体积更小

生产环境一般会对 JS、CSS 做压缩。压缩的目的很直接：

- 减少传输体积
- 缩短下载时间
- 降低首屏等待

可以把它理解成给文件“瘦身”。代码逻辑没变，但打包后的体积更小。

### 3. 分包：别把所有东西都塞一个包

如果一个入口把所有业务、第三方库、工具代码全打成一个大包，用户首次加载会很痛苦。

分包的思路是把不同性质的代码拆开：

- 业务代码和第三方库分开
- 首屏必要代码和非首屏代码分开
- 不同路由模块分开

这样初始加载更小，更新更局部，缓存也更有效。

举个简单场景：项目里有首页、后台管理页，还有地图页面。首页访问最多，地图页面却很少有人点。那就没必要一上来把地图相关代码全打进首屏包里，按需加载更合理。

### 4. 资源命名：为长期缓存服务

文件命名不是形式主义，它和缓存策略直接相关。

常见做法有：

- JS、CSS 使用内容哈希
- 图片字体等静态资源也可按需加 hash
- 保持输出目录整洁，比如按类型分类

核心目标是：**资源一变，文件名就变；资源不变，浏览器就别重新下。**

### 老赵给你画重点

- 缓存解决“重复下载”。
- 压缩解决“文件太大”。
- 分包解决“首屏太重”。
- 资源命名是缓存策略的一部分，不是随便起名。

### 赵老师避坑提醒

- 不要只顾压缩，不顾可排查性，开发和生产要分开。
- 文件名哈希要和构建输出策略配套，否则缓存可能失效。
- 分包不是越碎越好，太碎会增加请求数量。

---

## 五、构建速度优化：减少重复工作、启用缓存、缩小范围

很多人一上来就问“怎么让打包更快”，老赵的回答一般是：先别急着上大招，先把重复劳动干掉。

### 1. 减少重复工作

构建慢，往往是因为重复处理太多东西。你可以从这几个方向看：

- 有没有每次都重新处理完全没变化的文件
- 有没有每次都扫描太大的目录
- 有没有没必要的 loader 链
- 有没有开发环境里也在做生产级重活

原则就一句：**只做当前环境需要做的事。**

### 2. 启用缓存

缓存的核心思想是：**能复用的结果尽量复用。**

比如某些 loader、编译结果、模块解析结果，如果能被缓存起来，下次构建就不用全重来。这在大型项目里特别明显，项目越大，缓存越值钱。

### 3. 缩小处理范围

有些慢，不是 Webpack 不行，而是你让它干活的范围太大。

常见优化思路：

- 只处理需要的目录
- 排除 `node_modules` 中不需要处理的内容
- 尽量精确匹配文件类型
- 不要对所有文件都套一层重型规则

### 4. 开发环境只做“开发必须项”

开发环境里最重要的是反馈速度，所以很多生产优化可以先关掉：

- 不压缩
- 少做重处理
- 保留更好的报错信息
- 尽量缩短编译链路

### 老赵给你画重点

- 构建慢，先看是不是重复工作太多。
- 缓存是提升速度的常用手段。
- 缩小处理范围，比盲目加配置更有效。
- 开发环境不要背太多生产包袱。

### 赵老师避坑提醒

- 不是所有缓存都天然有效，缓存策略要和文件变化机制配套。
- 别把整个项目都交给一套重型规则处理，速度会很难看。
- 优化前先观察慢在哪，别凭感觉乱改。

---

## 六、打包产物优化：体积、加载、长期缓存的基础认知

最后这一块，咱们聊聊“产物优化”到底在优化什么。你可以把它分成三件事：**体积、加载、缓存**。

### 1. 体积：尽量别让包太胖

体积大，用户下载就慢，移动网络下更明显。控制体积的基础思路有：

- 去掉无用代码
- 拆掉不必要的大依赖
- 压缩 JS/CSS
- 按需加载非核心模块

### 2. 加载：让重要内容先出来

用户不关心你包里有多少代码，用户只关心页面什么时候能用。

所以优化加载顺序时，要优先保证：

- 首屏必要资源先加载
- 非核心功能后加载
- 大模块按需引入

这就是为什么分包和懒加载很重要。你把“马上要用的”先送到用户面前，把“暂时用不到的”往后放，体验就会好很多。

### 3. 长期缓存：让没变的资源一直可用

长期缓存的核心不是“缓存越久越好”，而是：

- 变动频繁的资源及时更新
- 稳定不变的资源尽量长期缓存

比如框架库、基础样式、稳定的公共模块，通常比业务页更适合做长期缓存。这样用户下次访问时，可以少下载很多内容。

### 4. 一个判断标准

老赵一般会看三件事：

- 首次加载是不是太重
- 更新时会不会把无关资源一起失效
- 资源命名和拆分是不是服务于缓存策略

### 老赵给你画重点

- 产物优化不是只看包大小，而是看用户怎么加载。
- 体积、加载、缓存是三位一体的。
- 长期缓存的前提是资源命名策略得跟上。

### 赵老师避坑提醒

- 别把“压缩后变小”当成全部，加载路径和缓存策略同样重要。
- 不要让一个小改动导致全站资源失效。
- 资源拆分要服务于业务访问路径，不要纯粹为了分而分。

---

## 七、从零搭一个能跑起来的多环境项目：先跑通，再优化

如果你现在要从零搭一个能跑起来的项目，赵老师建议你按下面的思路走：

### 1. 先准备基础配置

先写公共配置，保证项目能正常打包。这里面至少要有：

- 入口 `entry`
- 出口 `output`
- 常用资源规则
- 基础插件

目标不是高级，而是先让项目有一个稳定的骨架。

### 2. 再补开发配置

开发配置重点是体验：

- `devServer`
- 热更新
- source map
- 适合本地调试的输出方式

这样你改代码能快速看到结果，排查问题也方便。

### 3. 再补生产配置

生产配置重点是交付：

- 文件哈希
- 压缩
- 分包
- 更合理的缓存策略

这一步做完，才算是一个像样的线上构建方案。

### 4. 最后把切换入口接好

在 `package.json` 里把命令串起来：

```json
{
  "scripts": {
    "dev": "webpack serve --config config/webpack.dev.js",
    "test": "webpack --config config/webpack.test.js",
    "build": "webpack --config config/webpack.prod.js"
  }
}
```

如果你还想更稳一点，可以再配合 `webpack-merge` 管理公共配置和环境配置。这样一个项目的基本闭环就出来了：**能开发、能测试、能生产、能优化。**

### 老赵给你画重点

- 先把基础配置搭起来，再分开发和生产。
- 命令行要能明确切换环境。
- 一个合格的基础项目，至少要兼顾开发体验和生产产物优化。

### 赵老师避坑提醒

- 不要一开始就堆一堆优化，先确保项目能稳定跑起来。
- 环境拆分后，记得检查公共配置有没有被误改。
- 每加一个优化，都要想清楚它是在解决什么问题。

这一章最重要的一句话，老赵想送给你：**Webpack 配置不是越多越牛，而是越清楚越好。**

你要记住这几个核心判断：

- 开发、测试、生产关注点不同，所以配置必须分层。
- 基础配置管公共能力，环境配置管差异能力。
- 优化不只是压缩，还包括缓存、分包、命名和构建速度。

# 第12章：手写一个能跑起来的基础 Webpack 项目

前面几章已经把 Webpack 的概念、loader、plugin、资源处理、开发体验和优化思路拆开讲过了。这一章，全栈老赵不讲空话，直接把这些知识串起来，做一个**能跑、能开发、能打包**的基础项目。

你会发现，Webpack 真正难的不是某一个配置项，而是：**能不能把项目结构、入口出口、资源处理、开发服务器、构建优化连成一条线**。这一章就是把这条线搭起来。你跟着做，就能明白一个基础 Webpack 项目到底怎么从零跑起来。

---

## 一、先把项目目录搭明白：源码、产物、静态资源各归各位

先别急着写 `webpack.config.js`，第一步应该先把目录搭顺。目录不合理，后面配置只会越来越乱。很多人刚学 Webpack，喜欢把所有东西塞进根目录，能跑是能跑，但一加图片、字体、多环境配置，就容易失控。

### 1. 常见目录结构

一个基础但够用的结构，通常可以这样设计：

```bash
my-webpack-demo/
├─ config/
│  ├─ webpack.common.js
│  ├─ webpack.dev.js
│  └─ webpack.prod.js
├─ public/
│  └─ index.html
├─ src/
│  ├─ assets/
│  │  ├─ images/
│  │  └─ fonts/
│  ├─ styles/
│  │  └─ main.css
│  ├─ js/
│  └─ index.js
├─ dist/
├─ package.json
└─ webpack.config.js
```

先记住这个原则：**源码归源码，产物归产物，静态资源归静态资源**。

### 2. 每个目录的职责

- **src/**：源码目录，业务代码从这里开始
- **dist/**：打包后的输出目录，构建产物都放这里
- **public/**：不参与编译、原样使用的静态资源或 HTML 模板
- **config/**：多环境配置文件，方便拆分开发与生产逻辑
- **assets/**：图片、字体等静态资源集中管理
- **styles/**：样式文件单独存放，避免和逻辑代码混在一起

### 3. 为什么要这样分

Webpack 项目一旦长起来，最怕“所有东西堆一起”。目录清晰后，你更容易判断：

- 哪些文件要被 Webpack 处理
- 哪些文件要原样拷贝
- 哪些配置属于开发环境
- 哪些配置属于生产环境

这就是给后面的构建流程打地基。目录清楚，配置不容易乱；配置不乱，排查问题也轻松。

### 老赵给你画重点

- `src` 是源码，`dist` 是产物，别混用。
- `public` 放不编译或作为模板使用的资源。
- 先理目录，再谈配置，效率更高。

### 赵老师避坑提醒

- 不要把图片、字体、JS、CSS 全塞一个文件夹，后面找资源会很痛苦。
- `dist` 不要长期手动维护，它应该是构建结果，不是源码仓库。
- `public` 和 `src/assets` 要分清：前者偏原样静态资源，后者偏参与打包的资源。

---

## 二、从零编写基础配置：入口、出口、模式、loader、plugin 怎么写？

这一部分就是 Webpack 配置的骨架。你可以把它理解成：**告诉 Webpack 从哪儿进、往哪儿出、以什么姿态工作、遇到不同文件怎么处理**。骨架搭对了，后面加功能才不会乱。

### 1. 入口与出口

先写一个最基础的配置：

```js
const path = require('path');

module.exports = {
  entry: './src/index.js',
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: 'js/bundle.js',
    clean: true
  },
  mode: 'development'
};
```

#### 入口 `entry`
入口是 Webpack 的起点。它会从 `src/index.js` 出发，递归分析依赖。你在入口里 `import` 了什么，Webpack 就顺着往下找什么。

#### 出口 `output`
出口决定打包结果放哪儿、叫什么名字。`clean: true` 表示每次构建前先清空 `dist`，避免旧文件残留。

#### 模式 `mode`
- `development`：开发模式，便于调试，构建快
- `production`：生产模式，默认开启压缩和优化
- `none`：不启用内置优化，适合特殊场景

先用 `development` 跑通流程，再切到生产模式看差异，最稳。

### 2. loader：让 Webpack 看懂非 JS 文件

Webpack 默认只懂 JS 和 JSON，遇到 CSS、图片、字体就得靠 loader。loader 的作用就是：**把 Webpack 不认识的文件翻译成它能处理的内容**。

比如处理 CSS：

```bash
npm i -D style-loader css-loader
```

```js
module.exports = {
  // ...
  module: {
    rules: [
      {
        test: /\.css$/,
        use: ['style-loader', 'css-loader']
      }
    ]
  }
};
```

这里要记住：Webpack 执行 loader 是**从后往前**。`css-loader` 先解析 CSS，`style-loader` 再把样式注入页面。

### 3. plugin：补充 Webpack 的能力

plugin 更像“外挂能力”。比如自动生成 HTML，省掉手动维护打包后脚本引用的麻烦。

```bash
npm i -D html-webpack-plugin
```

```js
const HtmlWebpackPlugin = require('html-webpack-plugin');

module.exports = {
  // ...
  plugins: [
    new HtmlWebpackPlugin({
      template: './public/index.html'
    })
  ]
};
```

它会在打包时自动把 JS 注入 HTML 文件里，开发和发布都省事。

### 老赵给你画重点

- `entry` 决定从哪开始构建。
- `output` 决定产物放哪。
- `mode` 决定默认优化策略。
- `loader` 负责“翻译文件”，`plugin` 负责“增强能力”。

### 赵老师避坑提醒

- `style-loader` 和 `css-loader` 顺序不能乱，Webpack 是从后往前执行。
- `output.path` 必须是绝对路径。
- 有了 plugin 不代表不用 loader，它们职责不同。

## 三、资源处理怎么接入：JS、CSS、图片、字体分别怎么管？

这一步决定项目是不是“真能跑”。很多人会配 JS，CSS 一报错就懵，图片字体一进来更乱。别慌，按类型拆开就好。Webpack 不只是打包 JS，它是把整个前端资源链路串起来。

### 1. JS 怎么处理

JS 通常先解决兼容性，再谈优化。最常见的做法是用 Babel。

#### 使用 Babel 处理 JS

```bash
npm i -D babel-loader @babel/core @babel/preset-env
```

```js
{
  test: /\.js$/,
  exclude: /node_modules/,
  use: {
    loader: 'babel-loader',
    options: {
      presets: ['@babel/preset-env']
    }
  }
}
```

这意味着项目里的 JS 会先经过 Babel 转译，再进入 Webpack 打包流程。这样你可以写新语法，同时兼顾目标浏览器。

### 2. CSS 怎么处理

基础流程通常是：

```js
{
  test: /\.css$/,
  use: ['style-loader', 'css-loader']
}
```

如果你在 JS 中 `import './styles/main.css'`，Webpack 就会沿着这条链把 CSS 处理进去。后面要支持 Less、Sass、PostCSS，也是在这个基础上继续加 loader。

### 3. 图片怎么处理

图片可以直接用 Webpack 5 的资源模块，不一定非要装一堆 loader。

```js
{
  test: /\.(png|jpg|jpeg|gif|svg)$/i,
  type: 'asset',
  parser: {
    dataUrlCondition: {
      maxSize: 10 * 1024
    }
  },
  generator: {
    filename: 'images/[hash][ext][query]'
  }
}
```

含义很简单：

- 小图片转成 Base64，减少请求数
- 大图片单独输出到 `images/` 目录

你以后看到 `dist/images` 下有一堆哈希文件，就知道这是 Webpack 帮你整理好的结果。

### 4. 字体怎么处理

字体和图片类似：

```js
{
  test: /\.(woff2?|eot|ttf|otf)$/i,
  type: 'asset/resource',
  generator: {
    filename: 'fonts/[hash][ext][query]'
  }
}
```

字体文件一般体积不小，而且一旦路径错了，页面看着可能没事，实际上字体却没加载成功，所以输出路径和引用路径一定要认真看。

### 老赵给你画重点

- JS：Babel 负责兼容性转译。
- CSS：`style-loader` + `css-loader` 是基础组合。
- 图片：优先理解 Webpack 5 的资源模块。
- 字体：和图片一样，核心是正确输出路径。

### 赵老师避坑提醒

- 图片路径别手写死，尽量通过 `import` 引入。
- 字体文件常因路径错导致“看起来正常，实际上没加载”。
- `asset`、`asset/resource`、`asset/inline` 要分清，别混着用。

## 四、把开发服务器、source map 和基础优化放进同一个可跑闭环

项目能打包还不够，开发体验也要顺手。否则你每改一行都手动刷新，调试会很崩溃。一个真正能用的 Webpack 项目，一定要做到改完就能看到效果。

### 1. 开发服务器怎么配

安装：

```bash
npm i -D webpack-dev-server
```

配置：

```js
module.exports = {
  devServer: {
    static: './dist',
    open: true,
    port: 3000,
    hot: true
  }
};
```

它的作用是：

- 启动本地服务
- 自动打开浏览器
- 热更新页面
- 不用每次手动重新打开文件

配合 `HtmlWebpackPlugin`，开发体验会更顺滑。你改 JS、改 CSS，浏览器能及时看到变化，这就是工程化最直接的价值。

### 2. source map 怎么选

`source map` 的核心作用是：**让你在报错时能定位到源码，而不是只看到打包后的 bundle 文件**。

开发环境常见配置：

```js
devtool: 'eval-source-map'
```

这个选项一般调试体验不错，适合开发阶段快速定位问题。生产环境则要更谨慎，有些项目不开，有些项目选低泄露风险的方式，具体看要求。

### 3. 基础优化配置有哪些

虽然现在只是基础项目，还是可以顺手做好几件事：

- **`clean: true`**：避免旧文件残留
- **开发和生产分开**：减少配置混乱
- **少用无关 loader**：别给所有文件都套重型处理
- **留出缓存思路**：后面还能继续扩展

这里的优化不追求极致，重点是让结构稳定、产物清晰、调试成本更低。

### 老赵给你画重点

- `devServer` 提升开发效率。
- `source map` 是调试利器。
- 基础优化不是极限压榨性能，而是先把结构做对。

### 赵老师避坑提醒

- `devServer` 只服务开发，不是最终产物。
- 不同 `devtool` 影响调试速度和代码暴露程度，别乱抄。
- 热更新没生效时，先确认页面是不是通过 devServer 打开的。

## 五、手写一个完整可运行的基础项目：从安装依赖到看到构建产物

到这一步，咱们把所有东西收一遍，形成一个完整可运行项目。你只要把依赖装齐、配置写对，就可以从零跑起来。真正学会 Webpack，不是会背概念，而是能把一个项目自己搭出来。

### 1. 初始化项目并安装依赖

先创建项目并初始化：

```bash
npm init -y
```

安装核心依赖：

```bash
npm i -D webpack webpack-cli webpack-dev-server \
babel-loader @babel/core @babel/preset-env \
style-loader css-loader html-webpack-plugin
```

如果你要用图片、字体资源，Webpack 5 的资源模块已经够用，不需要额外再装图片 loader。

### 2. 编写入口文件和样式文件

`src/index.js`：

```js
import './styles/main.css';
import logo from './assets/images/logo.png';

const title = document.createElement('h1');
title.textContent = 'Webpack 项目跑起来了';
document.body.appendChild(title);

const img = document.createElement('img');
img.src = logo;
img.alt = 'logo';
document.body.appendChild(img);

console.log('Webpack 项目跑起来了');
```

`src/styles/main.css`：

```css
body {
  margin: 0;
  font-family: sans-serif;
  padding: 24px;
}

h1 {
  color: #333;
}
```

如果你要测试字体，可以再加一段：

```css
@font-face {
  font-family: 'DemoFont';
  src: url('../assets/fonts/demo.woff2') format('woff2');
}

body {
  font-family: 'DemoFont', sans-serif;
}
```

这段代码虽然简单，但它验证了几个关键链路：JS 能跑、CSS 能进来、图片能正确引用、字体也能参与构建。

### 3. 准备 HTML 模板

`public/index.html`：

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Webpack Demo</title>
</head>
<body>
  <div id="app"></div>
</body>
</html>
```

这个模板会被 `HtmlWebpackPlugin` 使用，最后自动注入打包后的脚本。

### 4. 写完整的 Webpack 配置

`webpack.config.js`：

```js
const path = require('path');
const HtmlWebpackPlugin = require('html-webpack-plugin');

module.exports = {
  entry: './src/index.js',
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: 'js/bundle.js',
    clean: true
  },
  mode: 'development',
  devtool: 'eval-source-map',
  module: {
    rules: [
      {
        test: /\.js$/,
        exclude: /node_modules/,
        use: {
          loader: 'babel-loader',
          options: {
            presets: ['@babel/preset-env']
          }
        }
      },
      {
        test: /\.css$/,
        use: ['style-loader', 'css-loader']
      },
      {
        test: /\.(png|jpg|jpeg|gif|svg)$/i,
        type: 'asset',
        parser: {
          dataUrlCondition: {
            maxSize: 10 * 1024
          }
        },
        generator: {
          filename: 'images/[hash][ext][query]'
        }
      },
      {
        test: /\.(woff2?|eot|ttf|otf)$/i,
        type: 'asset/resource',
        generator: {
          filename: 'fonts/[hash][ext][query]'
        }
      }
    ]
  },
  plugins: [
    new HtmlWebpackPlugin({
      template: './public/index.html'
    })
  ],
  devServer: {
    static: './dist',
    open: true,
    port: 3000,
    hot: true
  }
};
```

### 5. 配置运行脚本

`package.json`：

```json
{
  "scripts": {
    "dev": "webpack serve --mode development",
    "build": "webpack --mode production"
  }
}
```

开发时跑 `npm run dev`，上线前跑 `npm run build`，职责就清楚了。

### 6. 理解打包前后文件怎么对应

这一步很重要，别只看“能跑”，还要看“产物是怎么来的”。

- `src/index.js` 是入口，最后会被打包成 `dist/js/bundle.js`
- `src/styles/main.css` 不会单独留在 `dist` 里，而是被注入到页面运行时
- `src/assets/images/logo.png` 可能会变成 `dist/images/xxx.png`
- `src/assets/fonts/demo.woff2` 会变成 `dist/fonts/xxx.woff2`
- `public/index.html` 会在构建时生成最终可访问的 HTML，并自动引入脚本

也就是说，Webpack 不是简单地“拷贝文件”，而是在帮你重组构建产物：  
**JS 被编译，CSS 被注入，图片和字体被重新命名后输出，HTML 被自动拼装。**

### 7. 验证构建结果

最后检查这些点：

- 页面能否正常打开
- JS 是否执行
- CSS 是否生效
- 图片是否能显示
- 字体是否能正确引用
- 打包后 `dist` 中是否出现合理的产物结构

如果这些都通了，恭喜你，你已经从“看懂 Webpack”进化到“能把 Webpack 用起来”了。

### 老赵给你画重点

- 一个能跑的 Webpack 项目，核心不是配置多，而是链路通。
- 入口、资源、插件、服务器、产物输出，五个环节必须连起来。
- 先跑通基础版，再谈拆分公共配置、环境变量和高级优化。

### 赵老师避坑提醒

- `public/index.html` 要准备好，否则 `HtmlWebpackPlugin` 没模板可用。
- `npm run build` 和 `npm run dev` 目标不同，别拿生产配置调试。
- 出问题时别先怀疑 Webpack，先检查路径、依赖、文件名拼写和 loader 顺序。
- 如果字体或图片没生效，优先看引用路径和资源类型配置，而不是先改业务代码。
