# 第1章 先把 Vue3 认识清楚：它到底解决什么问题

## 开篇引入：你已经会 HTML、CSS、JavaScript，这章就看 Vue3 解决什么问题

如果你已经会 HTML、CSS、JavaScript，那我们就不从“前端是什么”讲起了，直接说重点：**Vue3 到底解决什么问题**。

你大概率写过这些页面交互：按钮一点击，标题变化；表单一提交，列表新增一条；接口数据回来后，再把内容补到页面上。  
刚开始用原生 JavaScript 做这些事没问题，但页面一复杂，麻烦就来了：

- 一个数据要在多个地方同步显示
- 一个交互会牵扯多个 DOM 节点
- 一个功能改动，容易带出一串联动问题
- 代码越写越长，后面自己都不好维护

说白了，**不是页面不会动，而是页面动起来以后不好管**。  
Vue3 要做的，就是帮你把“数据怎么变”“页面怎么跟着变”“功能怎么拆”这三件事理顺。它像一个前端项目的调度员，你只要定好规则，更新这件事它来帮你处理。

---

## 一、Vue3 是什么：从“页面怎么动起来”理解框架价值

你可以把 Vue3 理解成一套前端页面的组织方式。  
原生 JavaScript 更像你自己下厨房，锅碗瓢盆都得自己找；Vue3 则像给你配好了流程，你更专注在“做什么”，不用每次都从零搭灶台。

在实际开发里，Vue3 主要帮你做两件事：

1. **把页面拆成组件**
   - 页面不再是一大坨代码，而是一个个职责清楚的小零件。
   - 比如导航栏、商品卡片、弹窗、表单、分页器，都可以单独做成组件。

2. **让数据变化自动驱动页面更新**
   - 你只管改数据，页面会自己跟着变。
   - 不用频繁手写 `document.querySelector`、`innerHTML` 这些低层 DOM 操作。

比如做“购物车数量”：

- 原生 JavaScript：你要找到数字节点，手动改文本，还要照顾多个位置同步更新。
- Vue3：你只要改“数量”这个数据，页面上相关位置会自动刷新。

所以 Vue3 的核心价值就一句话：**让你把注意力放在数据和结构上，而不是到处追着 DOM 跑。**

---

## 二、Vue3 和原生 JavaScript 的区别：为什么要用框架

很多刚接触 Vue3 的同学都会问：既然 JS 能写页面，为什么还要学框架？

答案很简单：**小页面用原生 JS 没问题，项目一大，框架会明显降低维护成本。**

### 1. 原生 JavaScript：灵活，但容易乱

原生 JS 的优点是直接、自由、没有额外门槛。  
但页面一复杂，问题就容易冒出来：

- 数据散在各个函数里，不好统一管理
- DOM 操作和业务逻辑混在一起
- 多处依赖同一个状态，改一处容易连带出 bug
- 重复代码多，复用困难

它像把一堆文件摊在桌子上，刚开始好找，后面想改一个点，就得翻半天。

### 2. Vue3：把“状态”和“视图”关系理顺

Vue3 的思路很明确：**数据是源头，页面是结果。**

你先定义数据，再定义页面如何展示这些数据。数据变了，页面自动更新。  
这套模式最大的好处是可预测——你能更清楚地知道“哪里变了、为什么变、会影响谁”。

### 3. 用框架不是为了炫技，而是为了协作

真实项目通常不是一个人写完，而是多人协作。  
Vue3 的组件化、约定式写法和清晰的数据流，能让团队更容易分工：

- 你写列表组件
- 我写搜索组件
- 他写弹窗组件

最后拼成完整页面。  
这就是框架的价值：**把复杂项目拆成可管理的小块。**

## 三、Vue3 的核心特点：组件化、响应式、易上手

这部分是你后面学习 `ref`、`reactive` 这些核心语法前，最该先建立的直觉。

### 1. 组件化：像搭积木一样做页面

组件化就是把页面拆成一个个独立小块。  
一个页面不再是大杂烩，而是由很多职责明确的组件拼起来。

例如商品列表页，可能拆成：

- `Header`：顶部导航
- `SearchBar`：搜索框
- `ProductCard`：商品卡片
- `Pagination`：分页器

好处很直接：

- **复用**：一个卡片写好，多个页面都能用
- **维护**：某个功能出问题，只改对应组件
- **阅读**：每个文件职责单一，代码更清楚

你可以把组件想成乐高积木。单个积木不复杂，但拼起来就能搭出一整栋房子。

### 2. 响应式：数据变了，页面自动变

“响应式”是 Vue3 最核心的能力之一。  
简单说，就是你修改数据后，Vue3 会自动帮你更新页面。

比如：

- `count` 从 1 变成 2
- 列表新增一项
- 表单输入内容改变

这些变化都不需要你手动刷新页面。  
这就像有个勤快的助理，你只管改文件，展示板会自动同步更新。

后面你会学到 `ref`、`reactive`、`computed`、`watch`，它们就是响应式体系里最常用的工具。先记住一句话：**Vue3 的强大，离不开响应式。**

### 3. 易上手：语法清晰，适合从基础到实战

Vue3 对初学者友好的地方在于：

- 模板语法直观，接近 HTML
- 逻辑组织清楚，容易拆分
- API 用起来有规律，学会一套能迁移到很多场景

对已经掌握 HTML、CSS、JavaScript 的你来说，上手 Vue3 的关键不是“从零学编程”，而是“换一种组织前端代码的方式”。

## 四、本书学习路线：从基础语法到完整小项目

这本书不会一上来就把你扔进复杂项目里，而是按“先认识，再会用，最后能做项目”的路径推进。

### 1. 先建立基础认知

你会先接触：

- Vue3 是什么
- 开发环境怎么搭
- 模板语法怎么写
- 数据怎么绑定到页面

这一阶段的目标很明确：**能看懂 Vue3 项目的基本结构，知道页面是怎么渲染出来的。**

### 2. 再掌握核心语法与组件思维

接下来会重点讲：

- `ref`
- `reactive`
- `computed`
- `watch`
- `props`
- `emit`
- `slot`
- `provide/inject`

这些都是组件开发的常用工具。  
你可以把它们理解为“组件之间传数据、收数据、共享数据的不同方式”。

### 3. 再进入路由与状态管理入门

当页面不止一个，或者多个组件需要共享状态时，你就会接触：

- **Vue Router 基础**

到那一步，你会明显感受到：组件、路由、状态管理、表单交互，其实是一套完整的开发方法，而不是一堆散点知识。

老赵建议你先别急着背术语，第一步不是记概念，而是把开发环境搭起来，让项目真正跑起来。前端开发就像搭积木，工具顺手，后面的每一步才有手感；工具不顺手，你会把大量精力浪费在“为什么跑不起来”“为什么一改就报错”这些琐事上。

## 2.1 开发工具准备：Node.js、编辑器、浏览器调试工具

### 这一节要回答的问题：我需要准备哪些工具？

做 Vue3 开发，最少准备三样东西：

1. **Node.js**
2. **代码编辑器**
3. **浏览器调试工具**

你可以把它们理解成前端开发的“三件套”。

### 1）Node.js：项目的发动机

Vue3 项目虽然最终跑在浏览器里，但项目创建、依赖安装、开发服务器启动都离不开 Node.js。它就像发动机，不直接决定页面长什么样，却决定项目能不能顺利开起来。

安装后先检查版本：

```bash
node -v
npm -v
```

只要能看到版本号，说明基础环境大体没问题。初学阶段不必追求“最新”，稳定、可用、少折腾，才是最舒服的状态。

### 2）编辑器：写代码的主战场

推荐使用 **VS Code**。它对 `.vue` 文件支持好，语法高亮、格式化、插件生态都很成熟。

建议先装这些就够了：

- Vue 语言支持相关插件
- ESLint
- Prettier

新手别一上来装太多插件，插件多不等于效率高，反而容易冲突。初学阶段，你要的是“顺手”，不是“花哨”。

### 3）浏览器调试工具：你的放大镜

推荐 Chrome 或 Edge 的开发者工具。页面出了问题，很多时候不是坏了，而是你还没找到它坏在哪。

至少先会看这几个地方：

- **Console**：看报错
- **Elements**：看页面结构
- **Network**：看资源请求
- **Vue Devtools**：后面调试组件很有用

### 常见误区

**误区1：环境装完就算学会了**  
这只是开工前把工具摆好，真正学习从项目跑起来开始。

**误区2：插件越多越专业**  
初学阶段插件太多不但没帮助，还可能引发冲突。先保证能写、能跑、能看报错就够了。

### 判断标准

当你能在终端执行命令、在编辑器打开项目、在浏览器里查看页面并定位报错，说明你的基础工具链已经准备好了。

## 2.2 使用 Vite 创建 Vue3 项目

### 这一节要回答的问题：Vue3 项目怎么最快创建？

现在做 Vue3，老赵建议优先用 **Vite**。你可以把它理解成一个“启动很快的项目脚手架”，它帮你把项目结构、开发服务器、热更新这些基础能力都准备好。

### 创建步骤

打开终端，进入要放项目的目录，执行：

```bash
npm create vite@latest
```

然后按提示选择：

- 项目名称
- 框架：Vue
- 版本：Vue 3
- 是否使用 TypeScript：按学习路径选择

如果你是刚入门，老赵建议先用 **JavaScript 版本**。先把 Vue3 的核心语法、组件开发、数据绑定这些基本功练熟，再去碰 TypeScript，会轻松很多。

### 从安装到验证的完整流程

1. 安装并确认 Node.js 可用
2. 进入项目目录
3. 执行 `npm create vite@latest`
4. 按提示创建 Vue3 项目
5. 进入项目目录
6. 执行 `npm install`
7. 执行 `npm run dev`
8. 打开浏览器访问本地地址
9. 修改页面内容，确认热更新生效

这条链路跑通以后，你就不只是“看过教程”，而是真的把 Vue3 项目从零启动了一遍。

### 安装依赖并启动项目

创建完成后进入项目目录：

```bash
cd 项目名
npm install
npm run dev
```

成功后，终端会输出本地访问地址，例如：

```bash
http://localhost:5173
```

打开浏览器，看到默认页面，说明你已经真正拥有了一个能跑的 Vue3 项目。

### 为什么推荐 Vite？

可以把它理解成“轻装上阵”：

- 启动快
- 热更新快
- 配置少
- 对 Vue3 友好

对初学者来说，少折腾配置、多关注代码本身，是最划算的学习路线。

### 常见误区

**误区1：把 `npm install` 跳过去**  
结果就是依赖没装全，项目一跑就报错。

**误区2：拿 Vue2 老教程直接照搬**  
Vue3 的项目创建方式和语法风格都已经变了，不能混着学。

### 检查清单

- 项目创建成功
- 依赖安装完成
- 开发服务器启动成功
- 浏览器能正常打开页面

这四项都过了，说明你已经迈过了 Vue3 入门的一道关键门槛。

## 2.3 项目目录结构速览：src、components、views、assets 等

### 这一节要回答的问题：项目文件夹到底是干什么的？

刚创建好的 Vue3 项目目录会有点多，初学者第一次见到容易发懵。其实不用怕，不需要一口气背完，先抓住几个核心目录就够了。

### 1）`src`：源码主战场

`src` 是我们真正写业务代码的地方。你可以把它看成房子的主体空间，后续页面、组件、逻辑大多都在这里。

常见内容包括：

- `main.js`：项目入口
- `App.vue`：根组件
- 你自己创建的组件和页面

以后你学到 `ref`、`reactive`、`computed`、`watch`，这些核心语法也基本都会写在 `src` 里的某个 `.vue` 文件或模块里。

### 2）`main.js` 和 `App.vue`：为什么它们是入口？

`main.js` 可以理解成“开门的人”。它负责把 Vue 应用创建出来，并把根组件挂载到页面上。  
`App.vue` 则像“总控制台”，页面最外层的内容通常先从它开始。

你可以暂时这样记：

- `main.js` 负责启动应用
- `App.vue` 负责承载最外层页面结构

### 3）`components`：可复用零件仓库

`components` 通常放可复用组件，比如按钮、导航栏、卡片、表单项、弹窗。

组件思维很重要。你可以把组件理解成乐高积木：每个小块不大，但拼起来就能搭出完整页面。前端越往后学，越会发现“会不会拆组件”，很大程度上决定了项目是不是清爽、好维护。

### 4）`views`：页面级组件

`views` 一般放页面，比如首页、关于页、用户中心页。

组件和页面的区别可以这样记：

- **components**：偏小零件，可复用
- **views**：偏页面级，通常对应路由

后面学习 Vue Router 时，这个目录的意义会更明显：一个路由通常对应一个页面，也就是一个 `view`。

### 5）`assets`：静态资源区

`assets` 常放图片、字体、样式资源，比如 logo、背景图、图标。

你可以把它看作仓库里的“物料区”，页面和组件在这里拿素材，展示更方便。

### 新手先记住这四个就够了

先记住：

- 代码主要写在 `src`
- 可复用块放 `components`
- 页面放 `views`
- 图片、样式等资源放 `assets`

这套认识先建立起来，后面做组件开发、页面拆分、路由组织时，就不会乱。

### 常见误区

**误区1：所有东西都堆到一个文件里**  
这样后面维护时会非常乱。

**误区2：不区分组件和页面**  
结果就是结构混乱，写到后面不知道哪里该复用、哪里该拆分。

### 判断标准

当你能说清“这个文件是组件还是页面，它放在哪个目录里更合适”，说明你的目录思维已经开始建立了。

## 2.4 启动、修改、热更新与常见报错排查

### 这一节要回答的问题：为什么我改了代码页面会自动变？

这是前端开发里很爽的一点：**热更新**。你改代码，浏览器页面会自动刷新或局部更新，不需要每次手动刷新。

### 启动流程回顾

通常流程是：

1. 创建项目
2. 安装依赖
3. 启动开发服务
4. 浏览器打开页面
5. 修改代码，观察变化

这就是后面学习 Vue3 的基本工作节奏。

### 什么是热更新？

热更新就是你修改文件后，开发服务器把变化尽快同步到浏览器里。它最大的价值不是“酷”，而是**反馈快**。反馈快，学习才快；你改一处，马上看到效果，才能更容易建立“代码—结果”的对应关系。

### 常见报错排查思路

#### 1）端口被占用

如果启动时提示端口冲突，常见做法：

- 关闭占用端口的程序
- 换一个端口启动

#### 2）依赖安装失败

可能原因包括：

- 网络问题
- Node 版本不合适
- 缓存异常

处理方法：

- 重新安装依赖
- 检查 Node.js 版本
- 删除 `node_modules` 后重装

#### 3）页面空白

页面空白最容易让人心慌，但排查顺序很明确：

- 浏览器控制台有没有报错
- `main.js` 有没有正常挂载
- `App.vue` 有没有正确写模板
- 文件路径有没有写错

### 一个实用的排错顺序

1. 看终端报错  
2. 看浏览器 Console  
3. 看文件路径和拼写  
4. 看组件是否正确导入  
5. 再考虑重新安装依赖

老手和新手最大的区别之一，不是“从不报错”，而是“知道先查哪里”。报错不是敌人，它只是给你线索。

### 操作系统上的小提醒

- **Windows**：注意终端权限和路径里是否有空格。  
- **macOS**：切换多个 Node 版本时，要确认当前使用的是你期望的版本。  
- **Linux**：权限问题更常见，若安装提示权限不足，先看当前目录是否允许写入。

# 第3章 模板语法入门：让数据和页面真正连起来

如果你已经会写 HTML、CSS、JavaScript，那么学 Vue3 最先感受到的变化就是：**你不用再手动找 DOM、改文本、改属性、绑事件了**。  
你只要把“数据是什么”“用户做了什么”“页面该怎么变”说清楚，Vue 就会帮你把页面更新好。

你可以把模板语法理解成 Vue 组件的“说明书”：HTML 负责骨架，CSS 负责外观，模板语法负责把 JavaScript 里的数据、状态和动作真正连到页面上。

这一章先把最常用的几块打牢：

- `{{ }}` 插值表达式怎么显示数据
- `v-bind` 怎么绑定属性
- `v-on` 怎么绑定事件
- 如何动态控制文本、类名、样式
- 模板里的表达式能写什么、不能写什么

这一章吃透了，后面学组件、表单、列表渲染、条件渲染，会轻松很多。

---

## 一、插值表达式：`{{ }}` 到底是干什么的？

### 1.1 最基础的用法是什么？

插值表达式就是把数据显示到页面上。

```vue
<template>
  <h1>{{ title }}</h1>
  <p>{{ message }}</p>
</template>

<script setup>
const title = '欢迎学习 Vue3'
const message = '数据会自动显示到页面上'
</script>
```

这里的 `title` 和 `message` 是 JavaScript 变量，写在 `{{ }}` 里后，Vue 会把它们的值渲染到页面上。  
你可以把它理解成：**`{{ }}` 就是把数据装进页面的勺子。**

更准确地说，`{{ }}` 输出的是**文本内容**。以后变量变了，页面也会跟着变，这就是 Vue 的响应式基础味道。

### 1.2 插值表达式适合用在哪些场景？

一般适合显示：

- 文本内容
- 数字、字符串
- 计算结果
- 方法返回值
- 简单的逻辑表达式

例如：

```vue
<template>
  <p>价格：{{ price }} 元</p>
  <p>数量：{{ count }}</p>
  <p>总价：{{ price * count }}</p>
  <p>{{ isLogin ? '已登录' : '未登录' }}</p>
</template>

<script setup>
const price = 88
const count = 3
const isLogin = true
</script>
```

这些写法都很常见，短、直接、清楚。

### 1.3 常见误区

#### 误区 1：把 HTML 标签直接写进插值里

```vue
{{ '<strong>你好</strong>' }}
```

这只会显示成普通文本，不会渲染成加粗标签。  
`{{ }}` 默认是**文本插值**，不是 HTML 解析。

#### 误区 2：在插值里写太复杂的逻辑

比如：

```vue
{{ list.filter(item => item.status === 'active').length > 3 ? '很多' : '不多' }}
```

这虽然能用，但不建议。模板一复杂，就难读、难维护。更好的做法是交给 `computed`，后面会学到。

#### 误区 3：把所有展示内容都硬拼在模板里

例如：

```vue
<p>{{ firstName + ' ' + lastName + ' 欢迎你' }}</p>
```

简单场景可以接受，但一旦逻辑变多，模板很快就乱了。复杂格式化应该放到脚本里处理，模板只负责展示结果。

---

## 二、属性绑定：`v-bind` 怎么控制标签属性？

### 2.1 为什么不能直接写死属性？

HTML 里属性可以写死，但在 Vue 项目里，很多属性来自数据：

- 图片地址可能来自接口
- 链接地址可能根据状态变化
- `disabled` 可能要跟着表单状态走
- `class`、`style` 常常要动态切换

这时就要用 `v-bind`。

### 2.2 `v-bind` 的基本用法

```vue
<template>
  <img v-bind:src="avatarUrl" v-bind:alt="userName">
</template>

<script setup>
const avatarUrl = 'https://example.com/avatar.png'
const userName = '老赵'
</script>
```

`v-bind:` 可以简写成 `:`：

```vue
<img :src="avatarUrl" :alt="userName">
```

这个简写后面会非常常用。

你可以把 `:` 理解成：**把 JavaScript 的值塞到 HTML 属性里**。  
页面就不再是写死的，而是能跟着数据变化。

### 2.3 属性绑定的判断标准

只要右边是变量或表达式，就优先考虑 `v-bind`：

- `src`
- `href`
- `title`
- `disabled`
- `value`
- `class`
- `style`

例如：

```vue
<button :disabled="isLoading">提交</button>
<a :href="link">去详情页</a>
```

如果 `isLoading` 是 `true`，按钮就不能点；如果是 `false`，按钮正常可点。  
这就是 Vue 的核心思路：**页面由数据驱动。**

### 2.4 一个小例子：根据状态控制按钮

```vue
<template>
  <button :disabled="isDisabled">保存</button>
</template>

<script setup>
const isDisabled = true
</script>
```

这种写法在实战里很常见，比如：

- 表单没填完时禁用提交按钮
- 请求未完成时防止重复提交
- 用户未登录时禁用某些入口

### 2.5 `v-bind` 和 `{{}}` 的区别

- `{{}}` 是**显示内容**
- `v-bind` 是**绑定属性**

例如：

```vue
<h2>{{ title }}</h2>
<img :src="logo">
```

一个是放文本内容，一个是放标签属性。位置不同，用途也不同。

---

## 三、事件绑定：`v-on` 怎么让页面“会响应”？

### 3.1 事件绑定是干什么的？

页面不光要展示数据，还要能响应用户操作，比如：

- 点击按钮
- 输入内容
- 提交表单
- 鼠标移入移出

这些都靠事件绑定。  
如果说 `v-bind` 是让页面跟着数据变，那 `v-on` 就是让页面听用户指挥。

### 3.2 `v-on` 的基本用法

```vue
<template>
  <button v-on:click="handleClick">点我</button>
</template>

<script setup>
function handleClick() {
  console.log('按钮被点击了')
}
</script>
```

`v-on:` 也可以简写成 `@`：

```vue
<button @click="handleClick">点我</button>
```

这是 Vue 里最常见的写法之一。

### 3.3 事件绑定的核心理解

- `v-bind` 是“把数据挂到标签属性上”
- `v-on` 是“给标签安一个开关”

用户一操作，这个开关就会触发对应函数。  
Vue 的好处就在于：你不用自己写一堆 `addEventListener`，模板里直接声明就行。

### 3.4 常见写法

#### 写法 1：直接调用方法

```vue
<button @click="handleClick">点击</button>
```

#### 写法 2：传参数

```vue
<button @click="handleAdd(1)">加 1</button>
```

```vue
<script setup>
function handleAdd(num) {
  console.log('增加数量：', num)
}
</script>
```

#### 写法 3：获取事件对象

```vue
<button @click="handleClick">点击</button>
```

```vue
function handleClick(event) {
  console.log(event)
}
```

### 3.5 常见误区

#### 误区 1：把函数写成字符串

```vue
<button @click="handleClick()">点我</button>
```

这不是绝对错误，但初学阶段容易混淆。  
更稳妥的方式是先记住：**能写函数名，就先写函数名**。

#### 误区 2：把模板当成随便写 JS 的地方

模板更像“声明”，不是“命令式脚本”。  
这一点先建立起来，后面写组件时会更顺。

---

## 四、动态文本、类名、样式：让页面跟着状态变

这一部分非常实战。很多页面效果，本质上就是“根据状态换文字、换颜色、换样式”。

### 4.1 动态文本：内容跟状态联动

```vue
<template>
  <p>{{ statusText }}</p>
</template>

<script setup>
const statusText = '加载中...'
</script>
```

如果状态变化，页面文本也会跟着变。  
比如：

```vue
<p>{{ isEmpty ? '暂无数据' : '数据加载完成' }}</p>
```

这种写法简单直接，适合小型判断。

### 4.2 动态类名：`class` 怎么跟着状态变？

#### 写法一：对象形式

```vue
<template>
  <div :class="{ active: isActive }">菜单项</div>
</template>

<script setup>
const isActive = true
</script>
```

意思是：如果 `isActive` 为真，就加上 `active` 这个类名。  
这就像一个开关，开着就亮，关着就不亮。

#### 写法二：数组形式

```vue
<template>
  <div :class="['item', activeClass]">列表项</div>
</template>

<script setup>
const activeClass = 'active'
</script>
```

数组写法适合组合多个类名。

#### 更实用的例子

```vue
<template>
  <button :class="{ primary: isPrimary, disabled: isDisabled }">
    提交
  </button>
</template>

<script setup>
const isPrimary = true
const isDisabled = false
</script>
```

这里类名和状态绑定在一起，页面样式会跟着数据跑。

### 4.3 动态样式：`style` 怎么跟着状态变？

#### 对象形式

```vue
<template>
  <p :style="{ color: textColor, fontSize: fontSize + 'px' }">
    这是一段文字
  </p>
</template>

<script setup>
const textColor = 'red'
const fontSize = 18
</script>
```

#### 预先定义样式对象

```vue
<template>
  <div :style="boxStyle">盒子</div>
</template>

<script setup>
const boxStyle = {
  width: '100px',
  height: '100px',
  backgroundColor: '#42b883'
}
</script>
```

动态样式常用于：

- 状态提示色
- 进度条
- 选中高亮
- 错误边框

### 4.4 一个小例子：按钮状态切换

```vue
<template>
  <button
    :class="{ primary: isPrimary, disabled: isDisabled }"
    :disabled="isDisabled"
  >
    提交
  </button>
</template>

<script setup>
const isPrimary = true
const isDisabled = false
</script>
```

这个例子里，类名和属性都由状态控制。  
这就是 Vue 很典型的声明式写法：你只管告诉它状态，怎么显示由框架处理。

## 五、模板中的表达式与常见限制：哪些能写，哪些别乱写？

### 5.1 模板表达式是什么？

模板表达式就是写在 `{{ }}`、`v-bind`、`v-on` 里的 JavaScript 内容，例如：

```vue
{{ count + 1 }}
:class="{ active: isActive }"
@click="handleClick()"
```

### 5.2 可以写什么？

通常可以写：

- 变量
- 算术运算
- 三元表达式
- 简单函数调用
- 简单属性访问

例如：

```vue
<p>{{ isLogin ? '已登录' : '未登录' }}</p>
<p>{{ user.name }}</p>
<p>{{ price * quantity }}</p>
```

这些都短、清楚、直接，适合放在模板里。

### 5.3 常见限制是什么？

#### 限制 1：不要写复杂语句

模板里不适合写这种：

```vue
{{ if (a > 1) { ... } }}
```

复杂判断应该放到 `computed` 或方法里。

#### 限制 2：不要让模板变成逻辑黑洞

表达式太长、太绕、太难读，会让维护变得很痛苦。  
模板的目标是“清楚展示”，不是“炫技”。

#### 限制 3：不要在模板里做重计算

筛选、排序、复杂拼接这类逻辑，最好抽出去。模板会频繁更新，逻辑太重不利于维护，也影响性能。

### 5.4 判断标准：该放模板还是该放脚本？

你可以用这条简单标准判断：

- **展示层的小判断**：可以放模板
- **复杂逻辑、重复计算、需要复用**：放 `computed` 或方法
- **触发行为**：放事件函数

这条原则后面学组件时会一直用到。

---

## 六、这一章你真正要建立的是“模板思维”

很多初学者学模板语法，只盯着 `{{}}`、`v-bind`、`v-on` 这些符号。  
但更重要的是：**开始用“数据驱动页面”的方式思考问题。**

以后你写 Vue 页面时，脑子里最好先过一遍：

1. 这个内容是显示数据，还是要绑定属性？
2. 这个按钮是要响应事件，还是只是展示？
3. 这个样式是固定的，还是要根据状态切换？
4. 这个逻辑能不能放模板里，还是应该提到脚本里？

只要你开始这么想，就已经从“写 HTML”迈向“写 Vue 组件”了。

## 结尾小结：把页面交给数据，把操作交给事件

这一章我们把 Vue3 模板语法最基础、最常用的部分串起来了：

- `{{ }}` 用来显示数据
- `v-bind` / `:` 用来绑定属性
- `v-on` / `@` 用来绑定事件
- `class` 和 `style` 可以根据状态动态变化
- 模板表达式能写简单逻辑，但别把复杂业务塞进去

你现在不需要追求“全都会”，先形成两个习惯就够了：

- **页面内容尽量由数据驱动**
- **用户操作通过事件响应**

后面学组件通信、表单、列表渲染、组合式 API 时，你会越来越明显地感觉到：模板语法就是 Vue 的门面，也是你搭建页面的起点。

### 老赵提醒

模板语法看起来简单，但它是 Vue3 的基本功。  
很多人学 Vue 卡住，不是因为不会高级特性，而是 `{{}}`、`v-bind`、`v-on` 这些基础没吃透。

# 第4章 响应式与数据绑定：ref、reactive、computed、watch 一次讲透

## 开篇引入：Vue3 为啥能“自动更新页面”？

写过原生 JavaScript 的人，大多都碰到过这个问题：数据改了，页面还得自己去找 DOM、改文本、改样式。页面一多，维护起来就很累。

Vue3 的响应式机制，解决的就是这件事：**数据变了，页面自动跟着变**。你只管改数据，Vue 帮你把相关视图更新掉，不用反复操作 DOM。后面学组件开发、表单、列表、路由，你都会越来越依赖这个思路。

本章把 **ref、reactive、computed、watch** 一次讲清楚。先把它们理解成四个分工不同的工具：

- **ref**：装一个明确的值
- **reactive**：管理一组关联数据
- **computed**：自动算出结果
- **watch**：盯着变化，变化后做事

这四个 API，几乎贯穿 Vue3 日常开发。弄明白它们，Vue3 的门就算正式进了一大半。

---

## 一、什么是响应式：像“自动记笔记”的页面更新机制

### 1.1 响应式到底在解决什么问题？

响应式最核心的一句话就是：**数据变，视图跟着变**。

比如计数器点击 `+1` 后，数据更新，页面上的数字也自动变了。你不需要手动找元素、改 `innerText`，Vue 会把“数据”和“视图”连起来。你改数据，它负责刷新页面；你专心写业务就行。

### 1.2 响应式怎么理解？

响应式过程可以概括成三步：

1. 定义数据
2. 页面使用数据
3. 数据变化后自动刷新相关区域

Vue 不是让你直接操作页面，而是让你围绕数据来写页面。这就是 Vue 很重要的思维方式：**数据驱动视图**。

### 1.3 一个最直观的小例子

```vue
<script setup>
import { ref } from 'vue'

const count = ref(0)

function add() {
  count.value++
}
</script>

<template>
  <div>
    <p>当前数量：{{ count }}</p>
    <button @click="add">+1</button>
  </div>
</template>
```

这里你只改了 `count.value`，页面上的“当前数量”就会自动更新。这就是响应式，像“自动记笔记”一样：你在数据这边写了一笔，页面那边立刻同步。

---

## 二、ref 的使用：基础值、对象包裹与访问方式

### 2.1 ref 是干什么的？

`ref` 是 Vue3 里最常见的响应式 API，通常用来保存数字、字符串、布尔值、对象、数组等数据。它最关键的一点是：**在组合式 API 里，`ref` 的值需要通过 `.value` 访问和修改**。

你可以把它理解成一个“带封条的盒子”。盒子里装着值，平时要按规定方式去拿、去改，这样 Vue 才知道值变了，需要更新页面。

### 2.2 基础值怎么写？

```vue
<script setup>
import { ref } from 'vue'

const count = ref(0)

function add() {
  count.value++
}
</script>

<template>
  <div>
    <p>当前数量：{{ count }}</p>
    <button @click="add">+1</button>
  </div>
</template>
```

最容易混淆的是：

- **JS 里操作时，要写 `count.value`**
- **模板里展示时，通常直接写 `count`**

也就是说，`.value` 这个“封条”，在模板中 Vue 会帮你处理一部分，但在脚本里别忘了它。

### 2.3 ref 包对象可以吗？

可以，而且很常见。

```js
const user = ref({
  name: '赵老师',
  age: 30
})
```

访问和修改时仍然要先 `.value`：

```js
user.value.name
user.value.age = 31
```

可以把它理解为：一个盒子里装着一个小文件夹。只是访问字段时，先打开盒子。

### 2.4 ref 的适用场景

通常适合：

- 计数器
- 单个输入值
- 开关状态，比如 `isLoading`
- 某个明确的标记状态，比如 `isShow`
- 需要拿到某个 DOM 节点的场景

简单说，如果你手里是一个“单独的值”，优先考虑 `ref`。

### 2.5 常见误区

#### 误区 1：在 JS 中忘记写 `.value`

```js
count++
```

大概率是错的，应该写成：

```js
count.value++
```

#### 误区 2：以为模板里也要写 `.value`

模板里一般直接写 `count` 就行。

#### 误区 3：所有状态都塞进 ref

建议养成习惯：**单值优先 ref，对象和结构化数据再考虑 reactive。**

---

## 三、reactive 的使用：适合对象和复杂数据结构

### 3.1 reactive 和 ref 有啥区别？

`reactive` 适合把一个对象变成响应式对象。  
如果说 `ref` 是一个盒子，那 `reactive` 更像把整个文件夹交给 Vue 管理，文件夹里的字段都能被追踪。

```vue
<script setup>
import { reactive } from 'vue'

const form = reactive({
  username: '',
  password: '',
  remember: false
})
</script>
```

使用时不需要 `.value`，直接访问字段就行：

```js
form.username = 'zhangsan'
```

### 3.2 reactive 适合什么数据？

通常适合：

- 表单对象
- 用户信息对象
- 多字段配置对象
- 嵌套对象
- 业务状态集合

比如登录表单、个人资料编辑、商品信息、筛选条件这些，都是多个字段一起管理，`reactive` 会更顺手。

### 3.3 reactive 的优势

- **写法直观**：对象字段直接访问，像原生 JS 一样自然
- **适合多字段状态**：不用为每个字段单独写一个 `ref`
- **更适合表单**：表单本来就是多个字段一起变

### 3.4 最小可运行示例：登录表单

```vue
<script setup>
import { reactive } from 'vue'

const loginForm = reactive({
  username: '',
  password: '',
  remember: false
})

function submit() {
  console.log('提交表单：', loginForm)
}
</script>

<template>
  <div>
    <label>
      用户名：
      <input v-model="loginForm.username" placeholder="请输入用户名" />
    </label>

    <label>
      密码：
      <input v-model="loginForm.password" type="password" placeholder="请输入密码" />
    </label>

    <label>
      <input v-model="loginForm.remember" type="checkbox" />
      记住我
    </label>

    <button @click="submit">登录</button>
  </div>
</template>
```

这个例子很贴近真实业务：一个表单里多个字段一起变化，用 `reactive` 就很顺。

### 3.5 常见误区

#### 误区 1：把 reactive 当成 ref 用

```js
form.value.username
```

这是错的。`reactive` 返回的是响应式对象，不需要 `.value`。

#### 误区 2：把 reactive 对象整体替换掉

```js
form = { username: 'a' }
```

这不是推荐写法，更常见的是改属性，而不是整体替换。

#### 误区 3：无脑把所有东西都 reactive

如果只是一个简单数字，没必要硬上 reactive。工具要趁手，不是越复杂越高级。

---

## 四、computed 的使用：派生数据和缓存计算

### 4.1 computed 是干什么的？

当你有一份数据，需要根据它自动算出另一份数据时，就该用 `computed`。

比如：

- 商品总价 = 单价 × 数量
- 完整姓名 = 姓 + 名
- 过滤后的列表 = 原列表筛选结果
- 是否显示某个标签 = 多个条件组合判断

这类数据不是原始数据，而是从其他数据“推出来”的结果，叫做**派生数据**。

### 4.2 一个典型例子

```vue
<script setup>
import { ref, computed } from 'vue'

const price = ref(99)
const count = ref(2)

const total = computed(() => price.value * count.value)
</script>

<template>
  <p>单价：{{ price }}</p>
  <p>数量：{{ count }}</p>
  <p>总价：{{ total }}</p>
</template>
```

这里的 `total` 不是手动改的，而是 Vue 根据 `price` 和 `count` 自动算出来的。只要这两个值变了，`total` 就会跟着变。

### 4.3 computed 和普通函数有什么区别？

你当然也可以直接写函数，但 computed 有两个实用特点：

- **有缓存**：依赖没变时，会复用结果
- **适合模板频繁使用**：结果要多处展示时更合适

你可以把 computed 理解成“提前算好、还会记住结果的计算器”。

### 4.4 最小可运行示例：字数等级自动判断

```vue
<script setup>
import { ref, computed } from 'vue'

const content = ref('')

const wordCount = computed(() => content.value.length)

const level = computed(() => {
  if (wordCount.value === 0) return '还没开始'
  if (wordCount.value < 10) return '短内容'
  if (wordCount.value < 30) return '正常'
  return '长内容'
})
</script>

<template>
  <div>
    <textarea v-model="content" placeholder="输入内容试试"></textarea>
    <p>字数：{{ wordCount }}</p>
    <p>等级：{{ level }}</p>
  </div>
</template>
```

你输入内容，字数自动变，字数等级也自动变。它们都不是手工修改，而是“根据输入算出来的”。

### 4.5 什么时候该用 computed？

满足下面几个条件，就优先考虑 computed：

- 能从已有数据推导出来
- 结果会被多处使用
- 逻辑偏“计算结果”，不是“执行动作”

### 4.6 常见误区

#### 误区 1：把 computed 当成随便写逻辑的地方

computed 更适合“纯计算”，别把请求、打印、修改别的数据这些副作用操作塞进去。

#### 误区 2：该用 computed 却用 methods

如果你得到的是一个“结果”，computed 更自然；如果是“点一下执行一次动作”，那更像 methods 的事。

---

## 五、watch 的使用：监听变化、执行副作用、处理异步场景

### 5.1 watch 是干什么的？

如果说 computed 是“算结果”，那 watch 就像“盯着变化，变化了就做点事”。

它最适合处理：

- 数据变化后要发请求
- 输入框变化后要联动
- 某个状态变化后要存储、打印、校验
- 异步场景中的监听逻辑

### 5.2 watch 的基本用法

```vue
<script setup>
import { ref, watch } from 'vue'

const keyword = ref('')

watch(keyword, (newVal, oldVal) => {
  console.log('新值：', newVal)
  console.log('旧值：', oldVal)
})
</script>
```

当 `keyword` 变化时，回调函数就会触发。这个特性在真实开发里很常见，比如搜索联想、筛选联动、自动保存草稿。

### 5.3 watch 适合哪些场景？

- **搜索框联想**：用户输入关键词变化后，请求接口获取建议
- **表单联动**：比如选择“省份”后，自动加载“城市”
- **数据持久化**：某个状态变了，自动保存到本地存储
- **异步处理**：某个值一变化，就发起请求更新数据

### 5.4 最小可运行示例：监听输入并模拟异步请求

```vue
<script setup>
import { ref, watch } from 'vue'

const keyword = ref('')
const result = ref('请输入关键词')

watch(keyword, async (newVal) => {
  if (!newVal) {
    result.value = '请输入关键词'
    return
  }

  result.value = '正在搜索中...'

  await new Promise(resolve => setTimeout(resolve, 500))
  result.value = `已找到：${newVal} 相关内容`
})
</script>

<template>
  <div>
    <input v-model="keyword" placeholder="输入关键词" />
    <p>{{ result }}</p>
  </div>
</template>
```

这个例子很贴近真实开发：输入变化后，页面先显示“正在搜索中”，过一会儿再更新结果。  
这就是 watch 的典型用法：**监听变化，再去做副作用操作**。

### 5.5 watch 和 computed 的区别

一定要分清：

- **computed**：用来“算出一个值”
- **watch**：用来“监听变化并执行动作”

简单记：

- 你要的是“结果”——用 computed
- 你要的是“动作”——用 watch

### 5.6 watch 的常见误区

#### 误区 1：把所有逻辑都放 watch

watch 不是万能工具。  
如果只是派生值，优先 computed；如果只是方法执行，优先函数。

#### 误区 2：监听对象时不理解深层变化

对象、数组这类复杂数据，监听时要先想清楚自己要盯哪一层。

#### 误区 3：把 watch 当成计算器

watch 不是来返回一个值的，它更像“监听器 + 执行器”。

## 六、四个 API 怎么选：一张实战判断表

### 6.1 选 ref 的时候

适合：

- 单个值
- 简单状态
- 你想明确控制 `.value`

### 6.2 选 reactive 的时候

适合：

- 对象
- 表单
- 多字段状态
- 结构更复杂的业务数据

### 6.3 选 computed 的时候

适合：

- 结果由其他状态计算而来
- 需要缓存
- 模板里频繁使用

### 6.4 选 watch 的时候

适合：

- 监听变化
- 做异步请求
- 做联动、副作用、日志、存储

你可以把它们想成一个小团队：

- `ref/reactive`：负责“存数据”
- `computed`：负责“算结果”
- `watch`：负责“盯变化并干活”

如果这个分工记牢了，后面写组件时，状态就不容易乱。

## 七、综合实战：一个可统计字数、显示等级、监听输入变化的表单

下面把 `ref`、`reactive`、`computed`、`watch` 串起来，做一个更完整的小例子。

需求很简单：

1. 用户输入内容
2. 页面实时统计字数
3. 自动显示字数等级
4. 监听内容变化，模拟保存草稿

```vue
<script setup>
import { reactive, computed, watch } from 'vue'

const form = reactive({
  title: '',
  content: ''
})

const wordCount = computed(() => form.content.length)

const level = computed(() => {
  if (wordCount.value === 0) return '未输入'
  if (wordCount.value < 20) return '内容较短'
  if (wordCount.value < 50) return '内容正常'
  return '内容较长'
})

watch(
  () => form.content,
  (newVal) => {
    console.log('自动保存草稿：', newVal)
  }
)
</script>

<template>
  <div>
    <input v-model="form.title" placeholder="标题" />
    <textarea v-model="form.content" placeholder="请输入正文内容"></textarea>

    <p>字数：{{ wordCount }}</p>
    <p>等级：{{ level }}</p>
  </div>
</template>
```

这个例子里：

- `reactive` 管理表单对象，适合多个字段一起变
- `computed` 负责统计字数和判断等级
- `watch` 负责监听正文变化，做自动保存这类副作用

你会发现，Vue3 写表单时不是堆代码，而是把每个任务分给最合适的工具。  
这就是组件开发前最重要的一步：**先把状态安排明白**。

这一章我们把 Vue3 响应式的核心四件套讲了一遍：

- **ref**：保存单值，简单直接
- **reactive**：管理对象和复杂数据
- **computed**：负责派生结果，带缓存
- **watch**：负责监听变化，处理副作用

你只要建立起这三个关键词的判断：

- **存数据**
- **算结果**
- **盯变化**

后面的组件开发、表单处理、列表渲染、路由联动、状态管理入门，都会越来越顺。

### 老赵提醒

很多初学者学 Vue3 时，最容易犯的错不是“不会写”，而是“不会选”。看到数据就乱用 API，最后代码自己都读不懂。记住老赵这句话：

> 简单值先看 ref，复杂对象看 reactive；  
> 能算出来的交给 computed；  
> 有副作用、有异步、有联动，再用 watch。

再补一句：别光记概念，一定要把它们放进真实场景里练，比如计数器、表单、搜索联想、草稿保存。这样你到了组件开发章节，状态就不会乱成一锅粥。

# 第5章 组件开发的第一步：props、emit、slot、provide/inject

## 开篇引入：为什么学 Vue3，最后都会走到“拆组件”这一步？

如果把一个 Vue 页面比作一辆车，那**组件**就是车轮、发动机、方向盘这些零件。页面简单时，写在一个 `.vue` 文件里没问题；但项目一复杂，重复结构、超长文件、多人协作、复用困难这些问题就会冒出来。

所以，**组件思维**不是高级技巧，而是 Vue 开发的基本功。  
本章你要掌握的，不只是“会写组件”，而是学会：**父子组件怎么传数据、怎么传事件、怎么留内容口子、怎么跨层共享信息**。这四件事，就是 Vue3 组件开发最基础的地基。

换句话说，组件开发不是把页面切碎，而是把页面整理成一套边界清晰、职责明确、便于协作的零件系统。后面你做表单、弹窗、列表、页面布局，都会反复用到这套思路。

---

## 一、为什么要拆组件：把一个大页面拆成可复用的零件

### 1.1 组件拆分到底在解决什么问题？

你可以把页面想成一个“拼装模型”。如果所有零件都焊死在一起，后面想改样式、换结构、复用弹窗或列表项，都会很麻烦。

拆组件主要解决三件事：

1. **复用**：同一结构和逻辑可重复使用  
2. **维护**：一个组件只管一件事，问题更容易定位  
3. **协作**：多人开发时，各写各的组件，互不干扰

本质上，组件化是把“页面级思维”变成“零件级思维”：先想哪些区域固定，哪些会变，哪些值得抽出来，哪些以后可能复用。

### 1.2 怎么判断该不该拆组件？

不是看到页面就拆，拆组件要有标准：

- **是否有重复结构**
- **是否职责单一**
- **是否可能复用**
- **是否需要独立维护**

比如商品列表页，常见拆法可以是：

- `SearchBar`：搜索区
- `ProductCard`：商品卡片
- `Pagination`：分页器
- `EmptyState`：空状态
- `Header`：头部区域

这样页面主文件负责组织，子组件负责细节，代码会清楚很多。

### 1.3 一个简单的拆分思路

如果拿到一个页面不知道怎么拆，可以按这三步来：

1. **先看结构**：页面里有哪些大块和小块  
2. **再看职责**：每块是在展示、输入还是触发动作  
3. **最后看复用**：哪些部分以后还能用

比如“用户中心页”，你可以拆成用户信息卡片、功能入口列表、最近动态列表、统计信息区域。父页面管布局，子组件管细节，思路会顺很多。

### 1.4 先别急着拆太碎

很多初学者喜欢一上来就“组件化”，结果把一个简单页面拆成十几个小组件，最后自己都找不到入口。

记住：**组件拆分不是为了显得专业，而是为了更好维护。**  
如果一个组件只有一两个标签，拆出去反而增加阅读成本。能独立维护、确实会复用、职责足够清楚，再拆。

## 二、props：父组件向子组件传值与类型校验

### 2.1 props 是什么？

`props` 可以理解成**父组件给子组件发的任务单**。父组件把数据传进去，子组件负责展示或处理，但**不能随便改父组件的数据**。

你也可以把它理解为：父组件是“老板”，子组件是“员工”。老板下发任务，员工按要求完成，但不能擅自改总账。这样数据来源清楚，问题也更好查。

### 2.2 最小可运行示例：把用户信息传进卡片

父组件：

```vue
<UserCard :name="userName" :age="18" />
```

子组件：

```vue
<script setup>
defineProps({
  name: String,
  age: Number
})
</script>

<template>
  <div>
    <p>姓名：{{ name }}</p>
    <p>年龄：{{ age }}</p>
  </div>
</template>
```

注意两点：

- `:` 表示动态绑定
- 子组件用 `defineProps()` 接收数据

也就是说，父组件负责传，子组件负责用。

### 2.3 类型校验为什么重要？

类型校验就像收快递前先核对单子。传错类型，组件显示可能异常，逻辑也可能报错。

```vue
defineProps({
  title: {
    type: String,
    required: true,
    default: '默认标题'
  },
  count: {
    type: Number,
    default: 0
  }
})
```

常见校验项有：

- `type`：数据类型
- `required`：是否必传
- `default`：默认值
- `validator`：自定义校验规则

组件一旦被复用，使用者不一定是你自己，校验能帮你提前挡掉很多低级错误。

### 2.4 props 常见误区

- **把 props 当成子组件自己的数据随便改**：不推荐，props 应尽量只读
- **所有东西都往 props 里塞**：会让组件变成“信息垃圾桶”
- **只传值，不传状态**：有时还要传 `disabled`、`loading`、`active` 这类状态，组件才知道怎么表现

你可以把 `props` 想成“门牌号”：父组件把地址贴给子组件，子组件按地址找内容。地址越清楚，组件越好用。

---

## 三、emit：子组件向父组件传事件

### 3.1 为什么子组件不能直接控制父组件？

Vue 的数据流通常是**父向子传数据**，**子向父抛事件**。这就像门店和总部：

- 总部给门店规则和货品：父传子
- 门店遇到情况向总部汇报：子传父

这样结构清晰，不会出现子组件偷偷改父组件状态的混乱问题。

### 3.2 最小可运行示例：子组件按钮通知父组件

子组件：

```vue
<script setup>
const emit = defineEmits(['submit'])
</script>

<template>
  <button @click="emit('submit')">提交</button>
</template>
```

父组件：

```vue
<Child @submit="handleSubmit" />
```

```vue
<script setup>
const handleSubmit = () => {
  console.log('子组件提交了')
}
</script>
```

这就是“子组件发通知，父组件接通知”。

### 3.3 emit 最适合用在什么场景？

常见场景有：

- 点击按钮通知父组件
- 子组件输入完成后告知父组件
- 弹窗的关闭、确认、取消
- 列表项选中后同步状态

尤其是弹窗和表单组件，`emit` 几乎是必修课。比如封装确认弹窗时，子组件只负责告诉父组件“我确认了”，真正业务逻辑由父组件处理。

### 3.4 事件参数怎么传？

子组件：

```vue
emit('change', 100)
```

父组件：

```vue
<Child @change="handleChange" />
```

```js
const handleChange = (value) => {
  console.log(value)
}
```

如果要传多个参数，也可以继续加。但要注意，参数越多，说明组件职责可能越复杂，得想想要不要拆一下。

### 3.5 emit 的实操提醒

- **事件名要清楚**：建议用 `save`、`cancel`、`update`、`select` 这类语义明确的名字
- **不要把 emit 当成跨组件万能通信**：它主要适合父子之间
- **一个按钮发太多事件**：逻辑要克制，避免职责发散

你可以把 `emit` 理解成“举手报告”：子组件不拍板，只把事情上报给父组件。

---

## 四、slot：给组件留“插槽”，让内容更灵活

### 4.1 slot 是什么？

如果说 props 是“给组件送食材”，那 slot 就是“把菜放进指定餐盘”。组件有固定骨架，但内部内容可以由外部决定。

很多场景里，我们需要的是“一个通用外壳 + 可变内容”，比如：

- 弹窗
- 卡片
- 页面布局
- 提示框
- 容器组件

这类组件结构固定，内容却变化很大，slot 就是专门解决这个问题的。

### 4.2 最小可运行示例：卡片内容由外部塞进去

子组件：

```vue
<template>
  <div class="card">
    <slot></slot>
  </div>
</template>
```

父组件：

```vue
<Card>
  <p>这是插入到卡片里的内容</p>
</Card>
```

默认插槽适合只有一个内容入口的组件，比如卡片容器、面板容器、提示盒子。

### 4.3 具名插槽：给不同位置留不同口子

当组件有多个位置需要填内容时，就要用具名插槽。

子组件：

```vue
<template>
  <header><slot name="header"></slot></header>
  <main><slot></slot></main>
  <footer><slot name="footer"></slot></footer>
</template>
```

父组件：

```vue
<Layout>
  <template #header>顶部区域</template>
  中间内容
  <template #footer>底部区域</template>
</Layout>
```

具名插槽的作用，就是让组件像“空壳房子”，外部可以按需要往不同房间里填内容。

### 4.4 slot 默认内容

有时候父组件没传内容，组件也不能空着。这个时候可以给 slot 放一个默认内容。

```vue
<template>
  <div class="card">
    <slot>这里是默认提示内容</slot>
  </div>
</template>
```

如果外部没传内容，就显示默认文案。这个设计很实用，尤其是提示框、空状态、布局页头部之类的组件。

### 4.5 slot 的价值与边界

slot 的核心价值是：**组件提供结构，外部决定内容**。  
像弹窗组件，外层负责蒙层、标题、按钮、关闭逻辑；正文则可能是提示语、表单、确认信息，这部分就很适合交给 slot。

要注意的是：

- slot 适合“结构稳定、内容变化”的场景
- 不适合把所有逻辑都塞进去
- slot 过多，往往说明组件已经开始变“胖”了

---

## 五、provide/inject：跨层级共享数据的基本思路

### 5.1 为什么还需要 provide/inject？

如果父组件只传给直接子组件还好，但层级一深，继续一层层传 props 就会很麻烦。

比如：

- 顶层布局提供主题色
- 中间组件只是“转发”
- 深层组件真正使用主题色

这种情况就像接力传话，太绕。`provide/inject` 的作用，就是**让祖先组件直接提供数据，后代组件直接注入使用**。

### 5.2 最小可运行示例：主题色跨层传递

祖先组件：

```vue
<script setup>
import { provide, ref } from 'vue'

const theme = ref('dark')
provide('theme', theme)
</script>
```

后代组件：

```vue
<script setup>
import { inject } from 'vue'

const theme = inject('theme')
</script>

<template>
  <div>当前主题：{{ theme }}</div>
</template>
```

关键不是语法，而是先判断：这是不是一个适合跨层共享的数据。

### 5.3 什么时候适合用？

适合：

- 主题色
- 语言环境
- 用户信息
- 表单容器与表单项共享状态
- 深层组件共享配置

比如表单容器 `provide` 表单规则，内部表单项 `inject` 使用，就不用层层手动传了。

### 5.4 它和 props 有什么区别？

- `props`：适合明确的父子传值
- `provide/inject`：适合跨层级共享
- `props` 更直观
- `provide/inject` 更像隐式通道，适合复杂树结构

简单说，`props` 像当面递文件，`provide/inject` 像把文件放进共享柜，后面的人自己去取。

### 5.5 使用时要注意什么？

`provide/inject` 很方便，但不要滥用。它会让数据来源不那么直观，别人看组件时可能要往上找很久。

建议只在这些场景使用：

- 层级深
- 数据需要被很多后代共享
- 不想层层传递

如果只是父传子、子传父，优先用 `props` 和 `emit`，更清晰。

---

## 六、把这四个能力串起来：一个可落地的小页面案例

假设你要做一个“商品卡片列表”页面，页面结构可以这样拆：

- `ProductList` 负责渲染列表
- `ProductCard` 负责单个商品展示
- 卡片里显示商品名、价格、状态
- 按钮区域允许外部自定义
- 点击“加入购物车”通知父组件
- 页面顶部统一提供主题色

这个例子里，四个能力会同时上场。

### 6.1 props：把商品数据传给卡片

父组件把单个商品对象传进去：

```vue
<ProductCard :product="item" />
```

子组件接收后展示：

```vue
<script setup>
defineProps({
  product: {
    type: Object,
    required: true
  }
})
</script>

<template>
  <div class="product-card">
    <h3>{{ product.name }}</h3>
    <p>价格：{{ product.price }}</p>
  </div>
</template>
```

这里的重点是：**父组件负责列表数据，子组件负责单项展示**。

### 6.2 emit：按钮动作交给父组件处理

子组件里点“加入购物车”：

```vue
<script setup>
const emit = defineEmits(['add'])
</script>

<template>
  <button @click="emit('add', product)">加入购物车</button>
</template>
```

父组件接收事件：

```vue
<ProductCard :product="item" @add="handleAdd" />
```

```js
const handleAdd = (product) => {
  console.log('加入购物车：', product)
}
```

子组件只管发消息，不管业务落地，这样职责更清楚。

### 6.3 slot：按钮区域留给外部扩展

有些商品卡片除了“加入购物车”，还可能有“收藏”“对比”“查看详情”。这时按钮区就适合用 slot。

子组件：

```vue
<template>
  <div class="product-card">
    <h3>{{ product.name }}</h3>
    <p>价格：{{ product.price }}</p>
    <slot name="actions">
      <button @click="emit('add', product)">加入购物车</button>
    </slot>
  </div>
</template>
```

父组件：

```vue
<ProductCard :product="item" @add="handleAdd">
  <template #actions>
    <button @click="handleCollect(item)">收藏</button>
  </template>
</ProductCard>
```

这样，组件既保留默认能力，也允许外部改造。

### 6.4 provide/inject：给整页提供统一主题

如果整个列表页都要用同一种主题色，可以在页面根组件提供：

```vue
<script setup>
import { provide } from 'vue'
provide('themeColor', 'blue')
</script>
```

深层组件注入后直接使用：

```vue
<script setup>
import { inject } from 'vue'
const themeColor = inject('themeColor')
</script>
```

这个方案适合“整页统一配置”，比如主题、语言、布局参数。  
但如果只是单个卡片的临时数据，不必绕到 `provide/inject`，直接 `props` 就够了。

## 七、开发组件时的一套实用检查清单

写一个组件前，可以先问自己四个问题：

1. **这个组件需要接收哪些外部数据？**  
   - 用 `props`

2. **这个组件完成动作后，要通知谁？**  
   - 用 `emit`

3. **这个组件是否需要外部插入自定义内容？**  
   - 用 `slot`

4. **这个组件是否需要从上层拿公共配置？**  
   - 用 `provide/inject`

先把这四个问题想明白，组件边界就不会乱。很多时候，代码写得好不好，不在于你用了多少高级语法，而在于你是否先把职责划清楚了。

本章你已经迈出了 Vue3 组件开发最关键的一步：

- 知道为什么要拆组件
- 会用 `props` 让父组件给子组件传值
- 会用 `emit` 让子组件向父组件发事件
- 会用 `slot` 给组件预留内容入口
- 会用 `provide/inject` 做跨层级共享

这些能力看起来分散，但本质上都在回答同一个问题：**组件之间怎么合作，才能既灵活又清晰。**

后面不管是表单、弹窗、列表，还是路由页面、状态管理，组件通信的思路都会反复出现。  
所以这章不是语法点堆砌，而是你进入 Vue3 组件开发世界的第一把钥匙。

### 老赵提醒

组件开发最怕两件事：一是所有东西都堆在一个组件里，二是为了拆而拆。  
记住老赵这句话：**组件不是越多越好，而是职责越清楚越好。**  
先想清楚数据从哪来、事件往哪去、内容谁来填、公共信息谁来管，再动手写代码，效率会高很多。  
另外，`props`、`emit`、`slot`、`provide/inject` 各有适用边界，别拿一个 API 解决所有问题，真正顺手的写法，往往是把它们搭配着用。

# 第6章 事件、表单、条件渲染和列表渲染：把页面做得像样一点

前面我们已经搭好了 Vue3 的基本骨架，认识了 `ref`、`reactive` 这些“数据怎么动”的工具。到了这一章，咱们就正式把页面“盘活”——让按钮能点、输入框能输、内容能切换、数据能一条条显示出来。

你可以把这一章理解成：**从静态页面走向可交互页面**。HTML 负责结构，CSS 负责样子，Vue3 负责让页面跟着数据和用户动作动起来。

学完这一章，你至少要能做到：

- 处理点击、输入、提交等常见事件
- 用 `v-model` 处理表单数据
- 用 `v-if / v-else-if / v-else` 控制显示
- 用 `v-for` 渲染列表
- 做出一个基础可交互的待办列表雏形

---

## 一、先把交互思路捋清：事件就是“有人动了页面”

在原生 JavaScript 里，我们写过 `addEventListener('click', fn)`。  
Vue3 里更常见的是 `@事件名`，它其实就是 `v-on:` 的简写。

你可以把它理解成：**给元素装一个“反应器”**，用户一操作，Vue 就把对应函数叫起来。

### 1. 点击事件：最基础，也最常用

```vue
<template>
  <button @click="handleClick">点我</button>
</template>

<script setup>
const handleClick = () => {
  console.log('按钮被点击了')
}
</script>
```

真实项目里，点击事件常用于：

- 打开弹窗
- 进入详情页
- 删除一条数据
- 切换某个状态

### 2. 输入事件：用户每敲一个字，页面都能接住

```vue
<template>
  <input @input="handleInput" placeholder="请输入内容" />
</template>

<script setup>
const handleInput = (e) => {
  console.log('输入内容：', e.target.value)
}
</script>
```

这里的 `e.target.value` 就是输入框当前的值。  
Vue 并没有推翻原生事件，而是把常用写法封装得更顺手。

### 3. 提交事件：表单提交时别整页刷新

```vue
<template>
  <form @submit.prevent="handleSubmit">
    <input placeholder="请输入用户名" />
    <button type="submit">提交</button>
  </form>
</template>

<script setup>
const handleSubmit = () => {
  console.log('表单提交了')
}
</script>
```

`.prevent` 用来阻止默认提交行为。  
在单页应用里，表单提交后通常不希望页面刷新，这一步很关键。

### 4. 常见修饰符

- `.prevent`：阻止默认行为
- `.stop`：阻止事件冒泡
- `.self`：只在当前元素本身触发

```vue
<div @click="parentClick">
  <button @click.stop="childClick">点我</button>
</div>
```

这类写法在弹窗、遮罩层、下拉菜单里特别常见。

---

## 二、表单绑定：`v-model` 就是表单和数据之间的“自动对话”

表单是前端绕不开的部分，登录、搜索、新增、编辑、筛选，基本都会碰到。  
如果每次都手动监听输入、取值、赋值，代码会很散。`v-model` 的作用就是：**把表单控件和数据双向绑定起来**。

你改数据，输入框变；你在输入框里输入，数据也跟着变。就像两边接了一根电话线，谁说话，另一边都能听见。

### 1. 输入框中的 `v-model`

```vue
<template>
  <input v-model="username" placeholder="请输入用户名" />
  <p>当前用户名：{{ username }}</p>
</template>

<script setup>
import { ref } from 'vue'

const username = ref('')
</script>
```

这比原生写法省掉了“监听 + 取值 + 赋值”这一整套重复操作。

### 2. 单选按钮

```vue
<template>
  <label>
    <input type="radio" value="male" v-model="gender" /> 男
  </label>
  <label>
    <input type="radio" value="female" v-model="gender" /> 女
  </label>

  <p>当前选择：{{ gender }}</p>
</template>

<script setup>
import { ref } from 'vue'

const gender = ref('male')
</script>
```

这里的 `value` 可以理解成选项编号，`v-model` 会根据它判断当前选中谁。

### 3. 多选框

#### 多个兴趣爱好

```vue
<template>
  <label><input type="checkbox" value="篮球" v-model="hobbies" /> 篮球</label>
  <label><input type="checkbox" value="音乐" v-model="hobbies" /> 音乐</label>
  <label><input type="checkbox" value="电影" v-model="hobbies" /> 电影</label>

  <p>已选爱好：{{ hobbies }}</p>
</template>

<script setup>
import { ref } from 'vue'

const hobbies = ref([])
</script>
```

这里 `hobbies` 是数组，勾选哪个就往里面加哪个值。

#### 单个确认项

```vue
<template>
  <label>
    <input type="checkbox" v-model="isAgree" />
    我已阅读并同意协议
  </label>
</template>

<script setup>
import { ref } from 'vue'

const isAgree = ref(false)
</script>
```

记住一句话：**单个 checkbox 对应布尔值，多选 checkbox 对应数组**。

### 4. `v-model` 要对上数据类型

常见坑就这几个：

- 输入框一般用字符串
- 单选一般用字符串
- 多选一般用数组
- 勾选确认一般用布尔值
- `radio` 别忘了写 `value`

## 三、条件渲染：让页面会“看情况说话”

有些内容不是一直显示的，比如：

- 没登录时显示“请先登录”
- 登录后显示“欢迎回来”
- 请求没回来前显示“加载中...”
- 列表为空时显示“暂无数据”

这种根据状态切换显示的需求，就要用条件渲染。

你可以把它理解成页面里的“门牌灯”：条件满足就亮，不满足就灭。

### 1. 基本写法

```vue
<template>
  <p v-if="isLogin">欢迎回来！</p>
  <p v-else>请先登录</p>
</template>

<script setup>
import { ref } from 'vue'

const isLogin = ref(false)
</script>
```

如果条件更复杂，可以继续往下分：

```vue
<template>
  <p v-if="score >= 90">优秀</p>
  <p v-else-if="score >= 60">及格</p>
  <p v-else>继续加油</p>
</template>
```

### 2. `v-if` 和 `v-show` 的区别

- `v-if`：条件不满足时，元素直接不渲染
- `v-show`：元素还在，只是通过 `display: none` 隐藏

简单理解：

- `v-if` 像“没装上去”
- `v-show` 像“装上了但盖起来了”

### 3. 什么时候用哪个？

- 切换不频繁，用 `v-if`
- 切换很频繁，用 `v-show`

比如弹窗、菜单这类频繁开关的内容，`v-show` 往往更顺手；而空状态、权限控制、模块级显示，`v-if` 更自然。

---

## 四、列表渲染：`v-for` 不是复制粘贴，而是让数组自己“长出来”

页面里很多内容都是成组出现的，比如商品、文章、评论、待办事项、菜单项。  
如果每一项都手写，代码会越来越长。`v-for` 的作用就是：**根据数组自动渲染多个相同结构的元素**。

你可以把它理解成流水线：模板是模具，数据是一批零件，`v-for` 负责把它们一个个装进去。

### 1. 基本用法

```vue
<template>
  <ul>
    <li v-for="item in list" :key="item.id">
      {{ item.title }}
    </li>
  </ul>
</template>

<script setup>
import { ref } from 'vue'

const list = ref([
  { id: 1, title: '学 Vue3' },
  { id: 2, title: '练响应式' },
  { id: 3, title: '做小项目' }
])
</script>
```

数组有几条，页面就渲染几行。

### 2. `key` 要认真写

`key` 就像每条数据的身份证号。Vue 更新列表时，要靠它识别哪条变了、哪条删了、哪条只是换了位置。

### 正确原则

- `key` 尽量用稳定且唯一的值，比如 `id`
- 少用数组下标当 `key`

```vue
<li v-for="item in list" :key="item.id">
```

比下面这种更稳：

```vue
<li v-for="(item, index) in list" :key="index">
```

一旦列表会增删、排序、插入，`index` 就容易带来复用错位的问题。输入框列表、勾选状态列表、可编辑行，很多坑都出在这里。

## 五、把前面四块连起来：做一个可交互的待办列表雏形

前面我们分别练了事件、表单、条件渲染、列表渲染。  
真实项目里，它们通常是一起用的。

咱们直接做一个待办列表雏形，功能不复杂，但已经很接近真实页面：

### 需求

1. 输入待办事项
2. 点击按钮添加到列表
3. 列表为空时显示提示
4. 每条待办可以删除
5. 用 `v-for` 展示列表
6. 用 `v-if` 控制空状态

### 完整示例

```vue
<template>
  <div class="todo-box">
    <h2>待办列表</h2>

    <form @submit.prevent="addTodo">
      <input v-model="newTodo" placeholder="请输入待办事项" />
      <button type="submit">添加</button>
    </form>

    <p v-if="todos.length === 0">暂无待办，请先添加一条。</p>

    <ul v-else>
      <li v-for="item in todos" :key="item.id">
        <span :class="{ done: item.done }">{{ item.text }}</span>
        <button @click="toggleDone(item.id)">完成/取消</button>
        <button @click="removeTodo(item.id)">删除</button>
      </li>
    </ul>
  </div>
</template>

<script setup>
import { ref } from 'vue'

const newTodo = ref('')
const todos = ref([
  { id: 1, text: '学习 Vue3 事件', done: false },
  { id: 2, text: '练习 v-model', done: true }
])

const addTodo = () => {
  const text = newTodo.value.trim()
  if (!text) return

  todos.value.push({
    id: Date.now(),
    text,
    done: false
  })

  newTodo.value = ''
}

const removeTodo = (id) => {
  todos.value = todos.value.filter(item => item.id !== id)
}

const toggleDone = (id) => {
  const target = todos.value.find(item => item.id === id)
  if (target) target.done = !target.done
}
</script>

<style scoped>
.done {
  text-decoration: line-through;
  color: #999;
}
</style>
```

### 这段代码串起来看

- `v-model="newTodo"`：把输入框和数据同步起来
- `@submit.prevent="addTodo"`：监听提交并阻止刷新
- `v-if="todos.length === 0"`：处理空状态
- `v-for="item in todos"`：把待办数组渲染成列表
- `:key="item.id"`：让 Vue 准确识别每一项
- `@click="removeTodo(item.id)"`：删除指定待办
- `@click="toggleDone(item.id)"`：切换完成状态

这就把“输入、展示、切换、删除”串成了一个完整闭环。

- `v-if` 是门口招牌，决定要不要展示某块内容

# 第7章 组合式 API 上手：用 setup 把逻辑组织清楚

# 第7章 组合式 API 上手：用 `setup` 把逻辑组织清楚

## 开篇引入：为什么你会需要组合式 API？

如果说选项式 API 像把“数据、方法、计算属性、监听器”分别放进不同抽屉里，那组合式 API 更像按“功能模块”摆放：和搜索有关的放一起，和表单有关的放一起，和列表有关的放一起。对于刚接触 Vue3 的你来说，前面几章可能已经习惯了 `data / methods / computed / watch` 这种写法，但一旦组件稍微复杂一点，就会出现一个问题：**同一个功能的逻辑被拆散在不同位置，读起来像在翻好几本书。**

组合式 API 的价值，就在于**按功能组织代码**。比如一个“用户资料编辑页”，可能同时要处理表单输入、数据校验、请求加载状态、提交按钮禁用、成功提示、页面标题变化。如果继续用传统写法，相关逻辑可能分散在 `data`、`methods`、`watch`、`mounted` 里；而用 `setup`，你可以把这些和“编辑资料”有关的内容放在一起，读起来更像一个完整功能块。

所以这一章你要掌握的，不只是“会写 `setup`”，而是建立一种新的组件组织思维：**从“按选项分类”转向“按业务功能聚合”**。这会直接影响你后面做组件开发、抽离复用逻辑，甚至写中小型项目的能力。

---

## 一、为什么要学组合式 API：按功能组织代码

### 1. 选项式 API 的问题，不是不能用，而是不够灵活

选项式 API 很适合入门，因为你一眼就能知道哪里放数据，哪里放方法。  
但当一个组件越来越大时，会出现一个常见尴尬：

- 一个按钮的点击逻辑在 `methods`
- 一个联动计算在 `computed`
- 一个数据同步在 `watch`
- 一个初始化请求在 `mounted`

这些代码虽然都属于同一个功能，但被分散在不同区域。就像修电脑时，把螺丝、电源线、显卡、内存条分别放在不同房间，找东西很费劲。你不是不会修，而是先花太多时间找零件。

### 2. 组合式 API 的核心优势：逻辑更容易聚拢

组合式 API 鼓励你按“业务块”组织代码。比如：

- `useForm()`：负责表单字段、校验、提交
- `useCountdown()`：负责倒计时逻辑
- `useList()`：负责列表加载、分页、筛选
- `useTitle()`：负责页面标题变化

这样做的好处很直接：

- 同一功能的状态和操作靠得更近
- 复杂组件更容易拆分
- 复用逻辑更自然
- 后期维护更省心

你会越来越明显地感受到：**组件不是变量的堆积，而是一个个功能模块的组合。**

### 3. 什么时候该优先考虑组合式 API？

你可以简单记一个判断标准：

- **组件很小、逻辑很少**：选项式或组合式都能用
- **组件开始有多个相关状态和操作**：组合式更舒服
- **同一段逻辑要在多个地方复用**：组合式更合适
- **项目准备往中小型甚至更复杂方向发展**：建议尽早适应组合式

一句话：**不是为了“新潮”学组合式，而是为了让逻辑更好管。**

---

## 二、`setup` 的基本写法与数据暴露规则

### 1. `setup` 是什么？

`setup` 是组合式 API 的入口。你可以把它理解成：**组件一开始运行时，先进入 `setup`，把需要的状态、方法、计算逻辑准备好，再交给模板使用。**

```vue
<script>
export default {
  setup() {
    return {}
  }
}
</script>
```

如果你使用的是更常见的 `<script setup>`，写法会更简洁，后面项目里也会经常见到。你可以先把它理解成“省去了手动 return 的加强版写法”。

### 2. `setup` 中能做什么？

在 `setup` 里，通常会做这几件事：

- 定义响应式数据
- 定义计算属性
- 定义监听器
- 定义方法
- 调用可复用逻辑函数
- 返回给模板使用的内容

也就是说，`setup` 不是“装饰语法”，而是把一个组件真正会用到的逻辑集中起来。

### 3. 数据如何暴露给模板？

在普通 `setup()` 写法里，**你在 `setup` 中声明的变量，默认不会自动出现在模板里**，必须 `return` 出去。

```vue
<script>
import { ref } from 'vue'

export default {
  setup() {
    const name = ref('赵老师')

    function changeName() {
      name.value = '老赵'
    }

    return {
      name,
      changeName
    }
  }
}
</script>
```

模板里才能直接使用：

```vue
<template>
  <div>
    <p>{{ name }}</p>
    <button @click="changeName">改名字</button>
  </div>
</template>
```

你可以把这个过程理解成：`setup` 里是在“准备食材”，`return` 是把食材摆上餐桌，模板才看得见、用得上。

### 4. 一个重要规则：`ref` 在 JS 里用 `.value`

在 `setup` 里，如果你用 `ref` 定义数据，在 JavaScript 中访问时要用 `.value`。  
但在模板中，Vue 会帮你自动解包，所以模板里不用写 `.value`。

你可以先记住一句话：

- **JS 里改值，看 `.value`**
- **模板里展示值，不用管 `.value`**

---

## 三、在 `setup` 中把 `ref`、`reactive`、`computed`、`watch` 串起来

这一节最重要的，不是分别背这四个 API，而是看它们在同一个组件里怎么配合。实际开发里，你不会只孤零零地写一个 `ref`，而是经常把它们放在一起，组成一段完整逻辑。

### 1. `ref`：适合单个值，像一个“小盒子”

`ref` 可以包装一个基本类型值，也可以包装对象。你可以把它理解成一个“只有一个格子的盒子”，里面放一个值，Vue 帮你跟踪这个值变化。

```js
import { ref } from 'vue'

const count = ref(0)
count.value++
```

**适合场景：**

- 数字：`count`
- 字符串：`title`
- 布尔值：`loading`
- DOM 引用

如果你做一个“点赞按钮”，点赞数就是典型的 `ref` 使用场景。

### 2. `reactive`：适合对象，像一整套“文件夹”

`reactive` 用来处理对象或数组这类复杂数据。

```js
import { reactive } from 'vue'

const form = reactive({
  username: '',
  password: ''
})
form.username = 'admin'
```

你可以把 `reactive` 理解成“整套资料都被 Vue 接管了”。它更适合表单、对象配置、嵌套数据。

### 3. `computed`：适合派生结果，不要重复存一份

`computed` 的作用是：**根据已有数据，自动算出一个新结果**。

```js
import { ref, computed } from 'vue'

const firstName = ref('赵')
const lastName = ref('老')

const fullName = computed(() => `${lastName.value}${firstName.value}`)
```

**适合场景：**

- 拼接名字
- 计算总价
- 判断按钮是否可点击
- 过滤列表结果

如果某个值能由已有数据推导出来，就尽量用 `computed`，别手动再存一份。比如注册表单里“密码是否符合长度要求”：

```js
const canSubmit = computed(() => username.value && password.value.length >= 6)
```

### 4. `watch`：适合“观察变化后做事”

`watch` 不是拿来“算值”的，而是拿来“响应变化”的。你可以把它理解成一个“盯梢员”：某个数据变了，它就去执行额外动作。

```js
import { ref, watch } from 'vue'

const keyword = ref('')

watch(keyword, (newVal, oldVal) => {
  console.log('关键词变化了：', oldVal, '=>', newVal)
})
```

**适合场景：**

- 输入框变化后发请求
- 某个开关变化后同步存储
- 表单字段变化后联动别的字段
- 观察路由参数变化

### 5. 一个完整小组件示例：搜索 + 过滤 + 提示

下面这个例子把四个 API 串起来，逻辑会更像真实项目里的一个小功能块。

```vue
<script setup>
import { ref, reactive, computed, watch } from 'vue'

const state = reactive({
  keyword: '',
  sourceList: ['Vue3 入门', 'React 入门', 'Vue3 实战', 'JavaScript 基础'],
  tips: ''
})

const filteredList = computed(() => {
  return state.sourceList.filter(item => item.includes(state.keyword))
})

const resultCount = computed(() => filteredList.value.length)

watch(
  () => state.keyword,
  (newVal) => {
    state.tips = newVal ? `正在搜索：${newVal}` : '请输入关键词开始搜索'
  },
  { immediate: true }
)
</script>

<template>
  <section>
    <input v-model="state.keyword" placeholder="输入关键词" />
    <p>{{ state.tips }}</p>
    <p>匹配到 {{ resultCount }} 条结果</p>
    <ul>
      <li v-for="item in filteredList" :key="item">{{ item }}</li>
    </ul>
  </section>
</template>
```

这个例子里你能看到：

- `reactive` 管整体状态
- `computed` 管过滤结果和统计数量
- `watch` 管输入变化后的提示更新

这才是组合式 API 的日常用法：**不是背定义，而是把功能一块块拼出来。**

---

## 四、逻辑抽离：把重复代码整理成可复用函数

### 1. 什么叫逻辑抽离？

当你在多个组件里写了相似逻辑，比如倒计时发送验证码、表单校验、页面加载状态、请求分页列表，如果每个组件都复制一遍，后面改起来会很痛苦。逻辑抽离的意思就是：**把这类重复逻辑提炼成一个函数，哪里需要就调用哪里。**

在 Vue3 里，这种写法经常被叫做“组合式函数”或 `useXxx` 函数。

### 2. 一个简单的抽离例子：倒计时

```js
import { ref } from 'vue'

export function useCountdown(seconds = 60) {
  const count = ref(seconds)
  const isRunning = ref(false)
  let timer = null

  function start() {
    if (isRunning.value) return
    isRunning.value = true

    timer = setInterval(() => {
      count.value--
      if (count.value <= 0) {
        clearInterval(timer)
        timer = null
        isRunning.value = false
        count.value = seconds
      }
    }, 1000)
  }

  return {
    count,
    isRunning,
    start
  }
}
```

组件里就可以直接用：

```vue
<script setup>
import { useCountdown } from './useCountdown'

const { count, isRunning, start } = useCountdown(10)
</script>

<template>
  <button :disabled="isRunning" @click="start">
    {{ isRunning ? `${count}秒后重试` : '发送验证码' }}
  </button>
</template>
```

这个例子很像短信验证码按钮：点一下开始倒计时，没结束前不能再点。如果这个逻辑以后要在登录页、注册页、找回密码页都用到，抽出来就很划算。

### 3. 抽离时要注意什么？

不是所有代码都值得抽。可以用下面标准判断：

- 是否会在多个地方复用？
- 这段逻辑是否足够独立？
- 拆出去后，接口是否清晰？
- 组件里是否能少写很多重复代码？

如果只是某个组件里一次性的小逻辑，没必要过度抽离。**抽离的目的，是降低重复和复杂度，不是为了“看起来高级”。**

### 4. `useXxx` 命名习惯

通常组合式函数会以 `use` 开头，例如：

- `useForm`
- `useCountdown`
- `useFetch`
- `useTitle`

这个命名不是硬性规定，但它能帮助你一眼识别：**这是一个可复用逻辑块，不是普通变量。**

## 五、组合式 API 与组件结构的配合方式

### 1. 组合式 API 不是让组件更乱，而是让结构更清楚

很多人第一次接触组合式 API，会担心：变量都写在 `setup` 里，会不会更乱？答案是：**如果你只是把代码堆进去，确实会乱；但如果你按功能分组，它会比选项式更清楚。**

建议你在一个组件的 `setup` 里，按下面顺序组织：

1. 导入依赖
2. 定义响应式数据
3. 定义计算属性
4. 定义监听器
5. 定义方法
6. 调用抽离的组合式函数
7. 返回给模板使用的内容

这个顺序很符合人的阅读习惯：先看有什么，再看怎么计算，再看变化了怎么办，最后看怎么操作。

### 2. 推荐的思路：先按功能分区，再写模板

比如一个登录组件，你可以这样组织：

- 登录表单状态：`account`, `password`
- 表单验证结果：`canSubmit`
- 提交动作：`handleLogin`
- 提示信息：`message`
- 复用逻辑：`useCountdown`、`useForm`

这样你在看代码时，脑子里不会是“这是 data 那一块、这是 methods 那一块”，而是：

> 这段负责登录输入，这段负责按钮状态，这段负责提交，这段负责验证码倒计时。

这就是组件思维真正开始成型的地方。

### 3. 与模板配合的关键：返回什么，模板就用什么

在普通 `setup()` 写法中，模板只能使用 `return` 出去的内容。所以你要养成一个习惯：**模板需要什么，就明确返回什么，不要一股脑全扔出去。**

这样做的好处是：

- 模板更干净
- 组件接口更明确

你可以把它理解成“对外暴露的内容越少，组件越像一个标准工具箱，而不是杂物箱”。

### 4. 一个小型组件结构示意

```vue
<script setup>
import { ref, computed, watch } from 'vue'

const name = ref('')
const age = ref(18)

const isAdult = computed(() => age.value >= 18)

watch(age, (newVal) => {
  console.log('年龄变化：', newVal)
})

function submit() {
  console.log('提交：', name.value, age.value)
}
</script>

<template>
  <section>
    <h2>资料填写</h2>
    <input v-model="name" placeholder="请输入姓名" />
    <input v-model.number="age" type="number" />
    <p>{{ isAdult ? '成年人' : '未成年人' }}</p>
    <button @click="submit">提交</button>
  </section>
</template>
```

模板短、逻辑集中、职责清楚，这就是组合式 API 在小组件和中小项目里很舒服的原因。

## 六、从选项式思维过渡到组合式思维

这一章真正的任务，不是让你背会 `setup` 的语法，而是完成一次思维切换。

### 1. 选项式思维看“类别”，组合式思维看“功能”

选项式 API 更像把代码分栏目：

- 数据放一边
- 方法放一边
- 计算属性放一边
- 监听器放一边

组合式 API 更像把代码按任务打包：

- 登录相关的一起
- 列表相关的一起
- 表单相关的一起
- 倒计时相关的一起

对于中小项目来说，后者往往更好维护。因为你不是在找“某个 API 放哪了”，而是在找“这个功能的所有代码在哪儿”。

### 2. 从原生 JavaScript 迁移到 Vue3 的一个对照

如果你熟悉原生 JavaScript，可以这样理解：

- `ref` / `reactive`：相当于把变量变成 Vue 可追踪的状态
- `computed`：像一个自动更新的派生变量
- `watch`：像监听器回调
- `setup`：像把一个功能所需的初始化、状态和方法集中起来

也就是说，Vue3 并不是把你的 JS 逻辑推翻，而是帮你把“状态变化”这件事管理得更顺。

### 3. 一个实战判断标准

当你写组件时，如果你发现自己在不同位置来回切换思路，或者同一块功能逻辑已经写了两遍以上，就该想一想：

- 能不能把这块逻辑放进一个 `useXxx`？
- 能不能把相关状态放在一起？
- 能不能让模板只关心展示，不关心太多细节？

这几个问题，基本就是组合式 API 的日常工作方式。

## 七、本章小结：把逻辑组织清楚，后面项目才写得稳

这一章你应该带走的，不只是 `setup` 的写法，而是组合式 API 背后的组织方式。

你要记住下面几个关键点：

- `setup` 是组合式 API 的入口
- `ref` 适合单个值，`reactive` 适合对象
- `computed` 负责派生结果，`watch` 负责观察变化后的动作
- 逻辑抽离是为了复用和维护，不是为了炫技
- 组合式 API 的本质，是把同一个功能的代码放在一起

如果你能开始习惯“按功能组织代码”，后面做表单页、列表页、登录页、详情页时，你会越来越顺手。尤其到了后面的路由、状态管理和完整小项目实战，你会发现：组件逻辑清楚了，整个项目也就清楚了。

# 第8章 生命周期函数：组件什么时候创建、更新、销毁

## 开篇引入：组件也有“生老病死”

你可以把 Vue 组件理解成一个临时上岗的小员工：它会被创建、挂到页面上、随着数据变化不断更新，最后被移除。这个过程，就是**生命周期**。

为什么要懂它？因为很多事不是“想写就写”，而是要放在**对的时机**去做：

- 页面一打开就请求数据；
- 组件里开了定时器，离开页面时必须清理；
- 绑定了窗口事件，销毁时要解绑；
- 某些 DOM 操作，必须等页面真正渲染完成后才能做。

对刚接触 Vue3 的同学来说，生命周期不是一堆死记硬背的名词，而是写业务时的**时间管理工具**。很多页面出错，不是语法不会，而是代码放错了位置。

---

## 一、生命周期是什么：先认识组件的一生

生命周期就是**组件从创建到销毁的全过程**。在 Vue3 里，一个组件通常会经历四个阶段：

1. **创建阶段**：组件实例开始生成，数据和逻辑准备就绪；
2. **挂载阶段**：组件第一次渲染到页面上；
3. **更新阶段**：组件内部数据变化，页面重新渲染；
4. **卸载阶段**：组件从页面上移除，相关资源回收。

你可以把它想成一个包裹的流转过程：

- 创建阶段：打包；
- 挂载阶段：送到收件人手里；
- 更新阶段：内容变了，重新派送；
- 卸载阶段：退回或下架。

Vue 提供的生命周期钩子，就是在这些关键节点上插入业务代码。它的作用不是“多写几种 API”，而是让你精确控制：**这段代码什么时候执行最合适**。

### 为什么不能把所有代码都写在 setup 里？

因为有些操作依赖时机：

- 想拿到真实 DOM，必须等挂载后；
- 想在离开页面时释放资源，必须等卸载时；
- 想在数据变化后同步处理，通常要用 `watch`。

所以，生命周期的价值不是增加语法，而是帮你把代码放到正确时刻执行。就像做饭一样，盐不是越早放越好，火候也不是越大越好。

---

## 二、常见生命周期钩子及其触发时机

### 2.1 Vue3 里常用的钩子有哪些？

在组合式 API 中，最常用的生命周期钩子包括：

- `onBeforeMount()`：挂载前
- `onMounted()`：挂载后
- `onBeforeUpdate()`：更新前
- `onUpdated()`：更新后
- `onBeforeUnmount()`：卸载前
- `onUnmounted()`：卸载后

### 2.2 怎么记这些钩子？

记法很简单：**先看动作，再看前后**。

- `Mounted`：挂载
- `Updated`：更新
- `Unmounted`：卸载

前面加 `Before`，就是“之前”；不加就是“之后”。

也就是说：

- `onBeforeMount` = 挂载之前
- `onMounted` = 挂载之后
- `onBeforeUpdate` = 更新之前
- `onUpdated` = 更新之后
- `onBeforeUnmount` = 卸载之前
- `onUnmounted` = 卸载之后

### 2.3 各阶段适合做什么？

#### 挂载前：做准备，不碰 DOM

这个阶段适合做基础初始化，但**不要依赖真实 DOM**。页面结构还没真正落地，别急着操作元素。

```vue
<script setup>
import { onBeforeMount } from 'vue'

onBeforeMount(() => {
  console.log('组件即将挂载')
})
</script>
```

它适合做开场前检查，但不适合测量元素宽高。

#### 挂载后：请求数据、拿 DOM、初始化插件

挂载完成后，页面结构已经出来了。如果你要：

- 读取元素尺寸
- 聚焦输入框
- 初始化依赖 DOM 的插件
- 页面加载后请求初始数据

那就放在 `onMounted()` 里。

```vue
<script setup>
import { ref, onMounted } from 'vue'

const userList = ref([])
const loading = ref(false)

async function fetchUsers() {
  loading.value = true
  try {
    const res = await fetch('/api/users')
    userList.value = await res.json()
  } finally {
    loading.value = false
  }
}

onMounted(() => {
  fetchUsers()
})
</script>
```

列表页、详情页、首页推荐，几乎都离不开这个时机。

#### 更新阶段：数据变了，页面跟着变

当响应式数据变化后，Vue 会重新渲染页面，这就是更新阶段。

```vue
<script setup>
import { ref, onBeforeUpdate, onUpdated } from 'vue'

const count = ref(0)

onBeforeUpdate(() => {
  console.log('页面即将更新')
})

onUpdated(() => {
  console.log('页面已经更新')
})
</script>
```

这两个钩子更多用于调试、观察渲染过程，或者在少数场景中做更新前后的处理。

#### 卸载阶段：走之前先收尾

当组件从视图里消失时，比如：

- 路由跳转离开当前页
- 条件渲染 `v-if` 变成 false
- 父组件不再渲染它

这时候组件会进入卸载流程。最关键的一点就是：**清理资源**。不清理就像人都下班了，办公室电灯还一直开着。定时器、事件监听、第三方实例这些东西，最怕“人走了，东西没收”。

---

## 三、创建、挂载、更新、卸载：分别该做什么

### 3.1 创建阶段：先备好材料

创建阶段最重要的事是：**把组件需要的数据、方法、计算逻辑先准备好**。在组合式 API 里，你通常会在 `setup()` 里完成这些工作。

这个阶段还没有真实 DOM，所以别急着去操作页面元素。比如：

```js
document.querySelector('.box').innerText = 'hello'
```

常常会拿不到元素，因为组件还没挂载，页面还没真正形成。`setup()` 负责“准备材料”，不是“施工装修”。

### 3.2 挂载阶段：第一次站到页面上

挂载完成后，页面结构已经出来了。如果你要读取 DOM、自动聚焦、启动轮播、拉接口数据，都应该在这个阶段处理。

```vue
<script setup>
import { ref, onMounted } from 'vue'

const list = ref([])

onMounted(async () => {
  const res = await fetch('/api/users')
  list.value = await res.json()
})
</script>
```

核心思路是：**先渲染，再操作**。

### 3.3 更新阶段：内容变化了，就让 Vue 自己重绘

当响应式数据变化后，页面会重新渲染。比如：

```vue
<script setup>
import { ref, watch, onUpdated } from 'vue'

const count = ref(0)

watch(count, (newVal, oldVal) => {
  console.log('count 变化了', oldVal, '=>', newVal)
})

onUpdated(() => {
  console.log('组件已更新')
})
</script>
```

这里也顺便看出 `watch` 和生命周期的区别：

- `watch` 是盯着某个变量变没变；
- `onUpdated` 是看整个组件是不是完成了一轮更新。

如果你只关心某个数据变化，`watch` 往往更直接；如果你想知道组件整体渲染过没，生命周期钩子更合适。

### 3.4 卸载阶段：走之前把东西收好

卸载时最常见的就是做清理：

- 关掉定时器
- 解绑事件
- 销毁第三方对象
- 取消监听

这一步千万别偷懒。很多“莫名其妙重复执行”“切换页面后还在报警”的问题，本质上都是卸载时没收尾。

---

## 四、组合式 API 里怎么用生命周期钩子

Vue3 里通常这样导入：

```vue
<script setup>
import { ref, onMounted, onUnmounted } from 'vue'
</script>
```

然后直接在 `<script setup>` 中使用：

```vue
<script setup>
import { ref, onMounted, onUnmounted } from 'vue'

const count = ref(0)

onMounted(() => {
  console.log('组件已挂载')
})

onUnmounted(() => {
  console.log('组件已卸载')
})
</script>
```

如果你用的是 `<script setup>`，写法会更简洁，注意力能更多放在业务逻辑上。

### 一个实用原则：生命周期只做“阶段性任务”

如果这件事必须依赖“组件当前所处阶段”，就考虑生命周期钩子。比如：

- 初次进入页面请求数据 → `onMounted`
- 离开页面时销毁定时器 → `onUnmounted`
- 渲染完成后操作 DOM → `onMounted`
- 数据变化后联动处理 → 可能用 `watch` 更合适

### 生命周期和 watch 的区别

很多人会把生命周期和 `watch` 混在一起。简单说：

- **生命周期**：关心组件处于什么阶段；
- **watch**：关心某个数据有没有变化。

例如你想在 `count` 变化时同步输出日志：

```vue
<script setup>
import { ref, watch } from 'vue'

const count = ref(0)

watch(count, (newVal, oldVal) => {
  console.log('count 变化了', oldVal, '=>', newVal)
})
</script>
```

这个场景更适合 `watch`，而不是生命周期。因为生命周期不负责“某个变量变没变”，它负责“组件在哪个阶段”。

你可以这样理解：生命周期是“看大局”，`watch` 是“盯细节”。一个管出场和退场，一个管中途变化。

---

## 五、实战场景：页面加载请求、定时器清理、事件解绑

### 5.1 页面加载请求：组件一进来就拉数据

最常见的场景就是：**组件一进入页面，就请求接口拿数据**。比如商品详情页、用户列表页、文章页。

```vue
<script setup>
import { ref, onMounted } from 'vue'

const loading = ref(false)
const userList = ref([])

async function fetchUsers() {
  loading.value = true
  try {
    const res = await fetch('/api/users')
    userList.value = await res.json()
  } finally {
    loading.value = false
  }
}

onMounted(() => {
  fetchUsers()
})
</script>
```

这个写法很稳：页面挂载完成后再请求，既符合时机，也方便展示 loading 状态。

### 5.2 定时器清理：页面走了，计时也要停

如果组件里开了一个轮询定时器：

```js
const timer = setInterval(() => {
  console.log('每 3 秒执行一次')
}, 3000)
```

组件离开页面后，这个定时器还在跑，就会造成无效消耗、重复执行，甚至内存泄漏。正确写法应该是：

```vue
<script setup>
import { onMounted, onUnmounted } from 'vue'

let timer = null

onMounted(() => {
  timer = setInterval(() => {
    console.log('轮询中...')
  }, 3000)
})

onUnmounted(() => {
  clearInterval(timer)
})
</script>
```

这就是生命周期最典型的价值：**用时创建，不用时销毁**。

### 5.3 事件解绑：别让监听器“赖着不走”

有时候你会给 `window`、`document` 绑定事件，比如监听窗口大小变化：

```vue
<script setup>
import { onMounted, onUnmounted } from 'vue'

function handleResize() {
  console.log('窗口大小变化了')
}

onMounted(() => {
  window.addEventListener('resize', handleResize)
})

onUnmounted(() => {
  window.removeEventListener('resize', handleResize)
})
</script>
```

原则很简单：**凡是注册出去的东西，基本都要在销毁时注销回来。**

### 5.4 一个小结：什么时候该用哪个钩子？

你以后写代码时，可以先自查：

- 这段逻辑是否依赖真实 DOM？
  - 是 → `onMounted`
- 这段逻辑是否只需要执行一次初始化？
  - 是 → `onMounted`
- 这段逻辑是否会持续运行，比如定时器、监听器？
  - 是 → 记得在 `onUnmounted` 清理
- 这段逻辑是否依赖某个数据变化？
  - 是 → 优先考虑 `watch`

很多 bug 不是难，而是没按时机做事。

---

## 结尾小结：把生命周期当成“时机管理器”

这一章你只要抓住一句话就够了：

> **生命周期不是为了让代码更炫，而是为了让代码在正确的时间做正确的事。**

你现在应该能分清：

- 组件的一生：创建、挂载、更新、卸载；
- 常见钩子：`onMounted`、`onUpdated`、`onUnmounted` 等；
- 什么时候该请求数据；
- 什么时候该清理定时器和事件；
- 在组合式 API 中怎么使用这些钩子。

后面做项目时，你会发现生命周期几乎无处不在。不管是列表页、详情页，还是弹窗、轮播图，只要涉及“进入页面做事、离开页面收尾”，生命周期就是你的得力工具。掌握它，你写 Vue 组件就不再是“碰运气”，而是“按步骤办事”。

### 老赵提醒

生命周期最容易犯的错就两个：**把需要 DOM 的代码写早了，和把需要清理的代码忘了收尾。**  
记住：**挂载后再碰 DOM，卸载时一定善后。** 这就是前端写得稳不稳的分水岭。还有一点别忘了，生命周期管的是“时机”，不是“变量变化细节”；变量联动这件事，很多时候还是 `watch` 更合适。

### 本章练习

1. 用自己的话解释什么是生命周期，并写出四个阶段的名称。  
2. 分别说出 `onMounted` 和 `onUnmounted` 适合做什么。  
3. 写一个组件：页面挂载后请求一次模拟数据，并在页面上展示加载状态。  
4. 写一个组件：启动一个定时器，并在卸载时清除它。  
5. 给窗口添加一个 `resize` 监听，并在组件销毁时解绑。  
6. 思考：如果某个逻辑是“某个数据变化后执行”，你会优先用生命周期还是 `watch`？为什么？  
7. 进阶一点：做一个“倒计时提示条”组件，进入页面后开始倒计时，离开页面时停止计时。

# 第9章 Vue Router 基础：让页面有“路”可走

## 开篇引入：为什么 Vue 项目离不开路由？

你可以把一个 Vue 单页应用（SPA）想成一栋大楼：楼还是同一栋，但用户进来后，不是重新盖楼，而是根据“走哪条门、进哪个房间”来切换内容。这个负责切换规则的东西，就是**前端路由**。

传统多页网站点一次链接，浏览器通常会重新请求一个完整页面；而在 Vue3 的单页应用里，页面外壳往往不变，只是中间内容切换。这样做的好处很直接：

- 切换更快，体验更顺
- 页面结构更清晰，方便组件化
- 适合后台管理、内容站、表单系统等复杂项目

所以，**Vue Router** 就是 Vue3 项目里负责“页面去哪儿”的工具。你可以先把它理解成项目里的导航员：你告诉它“去首页”“去详情页”“去个人中心”，它负责把页面带到对应位置。

对于已经会 HTML、CSS、JavaScript 的你来说，路由并不是新知识，而是把“页面切换”升级成更适合组件开发的一套组织方式。学会它，后面做小项目时，你才能把首页、列表页、详情页、登录页这些页面像搭积木一样组织起来。

---

## 一、什么是前端路由：像在 SPA 里开不同房间

### 1. 前端路由到底解决什么问题？

只要项目里出现“首页 / 列表页 / 详情页 / 登录页 / 个人中心”这些不同界面，就需要一种机制把它们组织起来。前端路由做的事情，就是把**URL 和页面内容**建立对应关系。

比如：

- `/` 对应首页
- `/about` 对应关于页
- `/user/1001` 对应用户详情页

当地址栏变化时，Vue Router 根据规则决定显示哪个组件。要记住：**路由不是页面本身，而是页面之间的映射规则**。

### 2. 它和传统跳转有什么区别？

传统跳转像换了一栋楼，服务器重新返回一整页 HTML。前端路由更像在同一栋楼里换房间：楼体不变，只换房间内容。

这样带来的好处是：

- 更快
- 更平滑
- 更适合组件化开发

换句话说，路由把“页面”也组件化了。你不再拿着一堆散乱的 HTML 页面拼接，而是用 Vue 的方式，把页面拆成一个个能复用、能维护的模块。

### 3. 初学者最容易误解的点

很多同学会以为“路由就是链接”，其实不是。链接只是入口，**路由是规则系统**。你点一个链接，router 根据路径决定渲染谁，这才是核心。

所以学习路由，真正要记住的不是“点哪里跳哪里”，而是“**什么路径，渲染什么组件**”。

---

## 二、安装与配置 Vue Router：先把导航系统装起来

### 1. 安装方式

在 Vue3 项目里，通常直接安装官方路由库：

```bash
npm install vue-router
```

如果你是用 Vite 创建的 Vue3 项目，这一步很常见。安装完以后，路由就像给项目装上了一套导航系统，接下来要做的，就是把地图画出来。

### 2. 创建路由实例

一般会单独建一个路由文件，比如 `src/router/index.js`：

```js
import { createRouter, createWebHistory } from 'vue-router'
import Home from '../views/Home.vue'
import About from '../views/About.vue'

const routes = [
  { path: '/', component: Home },
  { path: '/about', component: About }
]

const router = createRouter({
  history: createWebHistory(),
  routes
})

export default router
```

这里要抓住三个关键词：

- `routes`：路由表，定义“什么路径对应什么组件”
- `history`：路由模式
- `createRouter`：创建路由实例

其中 `routes` 最好理解，它就是一张“地址—页面”对照表。`createWebHistory()` 则让 URL 更自然，没有多余的 `#`，适合大多数项目。

### 3. 注册到 Vue 应用中

然后在 `main.js` 里挂载：

```js
import { createApp } from 'vue'
import App from './App.vue'
import router from './router'

createApp(App).use(router).mount('#app')
```

这一步的意思是：把“导航系统”交给整个应用使用。没有这一步，路由表写得再好也不会生效。你可以把它理解成地图已经画好，但还得把导航设备接到车上。

### 4. 新手建议记住的配置顺序

可以按这个顺序理解：

1. 安装 Vue Router
2. 写路由表
3. 创建 router 实例
4. 挂载到 Vue 应用
5. 在页面里放路由出口

这个顺序很重要，很多报错都来自少了一步。尤其是初学者最常见的问题就是“路由文件写好了，但页面不显示”，这时候先检查有没有正确 `use(router)`。

---

## 三、路由表、路由视图、路由入口：页面是怎么显示出来的？

### 1. 路由表是什么？

路由表就是一张“地址—组件对照表”。

例如：

| 路径 | 对应页面 |
|---|---|
| `/` | Home.vue |
| `/about` | About.vue |
| `/user` | User.vue |

它的作用很像地址簿：用户访问哪个地址，就去找对应组件渲染。

### 2. 路由视图是什么？

`<router-view />` 是路由的“显示窗口”，可以把它理解成一个占位框：当前地址对应哪个组件，就把哪个组件渲染进去。

在 `App.vue` 中通常这样写：

```vue
<template>
  <div>
    <nav>
      <router-link to="/">首页</router-link>
      <router-link to="/about">关于</router-link>
    </nav>

    <router-view />
  </div>
</template>
```

上面是导航，中间的 `<router-view />` 负责展示当前路由组件。也就是说，页面骨架可以固定，变的只是中间那块内容。这就是 Vue3 组件开发里很重要的思路：**布局固定，内容按需替换**。

### 3. 路由入口是什么？

路由入口通常指用户进入不同页面的方式，常见有两种：

- 页面上的菜单或按钮
- 地址栏直接输入路径

也就是说，用户既可以点，也可以直接访问 URL。路由和普通组件切换最大的不同就在于：**路由是可被地址记录和分享的页面切换方式**。

比如你把详情页链接发给同事，他直接打开就能看到；但如果只是普通组件切换，通常没法通过地址直接定位到那个状态。

### 4. 页面级组件和普通组件要分清

这是 Vue3 项目组织里很关键的一步。

- **路由组件**：对应页面级内容，比如首页、列表页、详情页
- **普通组件**：按钮、表单、卡片、弹窗等局部模块

不要把所有东西都塞进路由组件里，否则后面会越来越难维护。一个健康的项目结构，通常是“页面负责拼装，组件负责复用”。

---

## 四、页面跳转：router-link 和编程式导航怎么选？

### 1. `router-link`：最适合做页面跳转按钮

`router-link` 是 Vue Router 提供的“声明式导航”方式，适合做菜单、列表跳转等：

```vue
<router-link to="/about">去关于页</router-link>
```

它的优点是写法简单、自带路由跳转逻辑、可维护性好。你可以把它理解成：**一个会自动认路的链接**。

### 2. 编程式导航：适合在代码里控制跳转

有些跳转不是用户点链接触发，而是业务逻辑触发，比如登录成功后跳首页、表单提交成功后跳详情页、倒计时结束后自动跳转。这时更适合编程式导航：

```vue
<script setup>
import { useRouter } from 'vue-router'

const router = useRouter()

const goHome = () => {
  router.push('/')
}
</script>

<template>
  <button @click="goHome">返回首页</button>
</template>
```

这种写法更像“程序自己决定去哪儿”，而不是“用户手动点哪里去哪儿”。

### 3. `push` 和 `replace` 的区别

- `push`：会留下历史记录，用户可以后退
- `replace`：替换当前记录，不会多占一个历史位置

比如登录页跳首页，常常用 `replace`，避免用户登录后按返回键又回到登录页：

```js
router.replace('/dashboard')
```

### 4. 如何判断用哪种方式？

简单记：

- **页面中固定导航**：用 `router-link`
- **逻辑触发跳转**：用编程式导航
- **登录、重定向等场景**：优先考虑 `replace`

---

## 五、动态路由和简单参数传递：一个页面如何接不同数据？

### 1. 什么是动态路由？

有些页面结构一样，但内容不同，比如：

- `/user/1`
- `/user/2`
- `/user/3`

这类页面不需要写三套组件，只需要一套详情页，根据参数不同显示不同内容。这个就是**动态路由**。你可以把它想成模板房间：装修不变，住进去的人不同，显示的信息也不同。

### 2. 动态路由怎么写？

```js
const routes = [
  {
    path: '/user/:id',
    component: () => import('../views/UserDetail.vue')
  }
]
```

这里的 `:id` 就是动态参数，意思是 `id` 这一段可以变化，路由会把它当作参数传给组件。

### 3. 在组件里怎么拿到参数？

```vue
<script setup>
import { useRoute } from 'vue-router'

const route = useRoute()
console.log(route.params.id)
</script>
```

`route.params.id` 就能拿到路径中的 `id`。在 Vue3 里，`useRoute()` 和 `useRouter()` 经常一起出现：前者是“拿当前路由信息”，后者是“控制跳转”。

### 4. 简单参数传递还有什么方式？

除了动态路由，还可以通过查询参数传值：

```js
router.push({
  path: '/search',
  query: { keyword: 'vue3' }
})
```

组件里读取：

```js
const route = useRoute()
console.log(route.query.keyword)
```

一般来说：

- **路径参数**：适合详情页、分类页这类结构性资源
- **query 参数**：适合筛选条件、搜索关键词、分页信息

判断标准很简单：

- 这是“页面身份”的一部分吗？用 `params`
- 这是“附加筛选信息”吗？用 `query`

---

## 六、一个从安装到跳转的最小实战：首页、列表页、详情页跑起来

这一段别只看概念，老赵带你把最小闭环走通。只要这一套能跑起来，你就真的摸到 Vue Router 的门路了。

### 1. 路由表设计

我们先做三个页面：

- 首页：`/`
- 列表页：`/list`
- 详情页：`/article/:id`

`src/router/index.js` 可以这样写：

```js
import { createRouter, createWebHistory } from 'vue-router'
import Home from '../views/Home.vue'
import List from '../views/List.vue'
import ArticleDetail from '../views/ArticleDetail.vue'

const routes = [
  { path: '/', component: Home },
  { path: '/list', component: List },
  { path: '/article/:id', component: ArticleDetail }
]

const router = createRouter({
  history: createWebHistory(),
  routes
})

export default router
```

### 2. App 里放路由出口和导航

```vue
<template>
  <div>
    <header>
      <router-link to="/">首页</router-link> |
      <router-link to="/list">列表页</router-link>
    </header>

    <main>
      <router-view />
    </main>
  </div>
</template>
```

这里的 `router-view` 就像舞台中央的位置，谁被路由选中了，谁就在这里演出。

### 3. 首页跳转到列表和详情

`src/views/Home.vue`：

```vue
<template>
  <div>
    <h1>首页</h1>
    <p>这里是项目入口。</p>

    <router-link to="/list">去列表页</router-link>
    <button @click="goDetail">看文章 101</button>
  </div>
</template>

<script setup>
import { useRouter } from 'vue-router'
const router = useRouter()

const goDetail = () => {
  router.push('/article/101')
}
</script>
```

### 4. 列表页里带参数跳转

`src/views/List.vue`：

```vue
<template>
  <div>
    <h1>列表页</h1>
    <ul>
      <li>
        <router-link to="/article/201">文章 201</router-link>
      </li>
      <li>
        <button @click="openArticle(202)">文章 202</button>
      </li>
    </ul>
  </div>
</template>

<script setup>
import { useRouter } from 'vue-router'
const router = useRouter()

const openArticle = (id) => {
  router.push(`/article/${id}`)
}
</script>
```

### 5. 详情页读取动态参数

`src/views/ArticleDetail.vue`：

```vue
<template>
  <div>
    <h1>文章详情页</h1>
    <p>当前文章 ID：{{ id }}</p>
  </div>
</template>

<script setup>
import { computed } from 'vue'
import { useRoute } from 'vue-router'

const route = useRoute()
const id = computed(() => route.params.id)
</script>
```

这样一来，你就完成了一个完整的路由闭环：

- 安装路由
- 配置路由表
- 注册到应用
- 用 `router-view` 展示页面
- 用 `router-link` 和 `router.push()` 跳转
- 用动态路由接收参数

这已经很像一个真实项目的骨架了。

## 七、路由在项目里怎么和其他能力配合？

### 1. 路由和组件开发要配合

路由只负责“页面去哪儿”，页面里的具体内容还是要靠组件拆分来完成。比如列表页里可以继续拆成：

- 搜索栏组件
- 商品卡片组件
- 分页组件

这样做的好处是，页面结构清楚，后期维护也轻松。

### 2. 路由和状态管理不是一回事

路由负责位置变化，不负责共享数据。如果多个页面要共用登录状态、用户信息、购物车数据，后面要靠 **Pinia** 来处理。

简单理解：

- 路由像“你现在在哪个房间”
- 状态管理像“你手里拿着什么”

这两个概念别混了。

### 3. 动态页面要考虑异常情况

真实项目里，详情页不能只写“有数据就展示”，还要考虑：

- 数据还在加载时怎么显示
- 参数不存在怎么办
- 资源被删了怎么提示

你可以先放一个简单的“返回列表”按钮，后面再把加载状态、空状态补齐。

## 结尾小结：先把“页面能走通”这件事做扎实

这一章你要掌握的核心，不是背 API，而是建立一个清晰模型：

- 前端路由就是 SPA 里的页面导航系统
- `routes` 是路由表
- `<router-view />` 是页面出口
- `router-link` 适合声明式跳转
- `useRouter()` 适合编程式跳转
- `:id` 是动态路由参数，`query` 适合附加信息传递

如果你已经学会把页面拆成“路由组件 + 普通组件”，那你在 Vue3 项目里的思路就已经往前走了一大步。更重要的是，你会开始按照“页面骨架先定好，再往里填内容”的方式来做项目，这就是路由带来的组织能力。

### 老赵提醒

路由不是越多越高级，**先把最基础的路径映射、页面跳转、参数传递弄明白**，后面学嵌套路由、守卫、权限控制才不会乱。

还有一个很重要的习惯：**页面级组件放在 `views`，可复用组件放在 `components`**，别一开始就混着写，不然后面项目大了会很难收拾。  
另外，别忘了路由解决的是“去哪儿”，不是“数据怎么共享”，这个边界一定要分清。  
记住一句话：**路由是项目页面组织的骨架**，骨架搭稳了，后面加功能才不容易散。

1. 新建一个 Vue3 项目，安装并配置 Vue Router。  
2. 至少创建 3 个页面：`Home`、`List`、`ArticleDetail`。  
3. 在首页中同时使用 `router-link` 和 `router.push()` 完成跳转。  
4. 给文章详情页添加动态路由 `/:id`，并在页面中显示当前参数。  
5. 再增加一个 `query` 参数，比如搜索关键词 `keyword`，并读取出来。  
6. 思考一下：你的项目里哪些页面适合做成路由组件，哪些适合做成普通组件。  
7. 尝试把首页、列表页、详情页串成一条完整浏览路径，检查能否正常返回和前进。

# 第10章 Pinia 入门：把项目里的状态管起来

## 开篇引入：为什么组件一多，数据就开始“打架”？

前面我们已经用过 `props`、`emit`、`slot`、`provide/inject` 做组件通信。它们都很好，但一旦项目变复杂，比如：

- 顶部导航要显示登录用户
- 购物车角标要在多个页面同步变化
- 登录状态、主题、语言要跨页面共享

这时你会发现，数据像接力棒一样在组件之间来回传，代码很快就乱了。

状态管理要解决的，就是**把多个组件都要用的数据集中起来统一管理**。  
你可以把它理解成一个“全局共享仓库”：

- 不用层层传数据
- 数据来源清晰
- 修改逻辑集中
- 页面之间更容易同步状态

在 Vue3 里，Pinia 就是最常用、也最适合入门的状态管理工具。它的思路很简单：**把需要共享的状态单独拿出来，统一放进 store 管。**

你可以把它想成项目里的“总账本”：每个组件管自己的小事，凡是大家都要看的数据，就统一记在这里。

---

## 一、状态管理要解决什么问题：多个组件共享数据

### 1.1 先看一个常见痛点

假设你做一个电商小项目，页面里有这些组件：

- `Header`：显示购物车数量
- `ProductList`：商品列表，点击“加入购物车”
- `CartPanel`：购物车详情
- `CheckoutPage`：结算页

如果不用状态管理，数据可能要从商品列表一路传到父组件，再传给 `Header`、`CartPanel`，路由切到 `CheckoutPage` 后还得再处理一遍。

这就像一家人买东西，消息要靠“口口相传”传到每个人耳朵里。人少还能凑合，人一多就容易漏、容易乱。

### 1.2 什么时候该用 Pinia？

可以按这个标准判断：

- 多个组件都要读同一份数据
- 多个页面都要用同一份状态
- 某个数据变化后，其他地方必须同步更新
- 不想再靠层层 `props` 传来传去

如果只是父子组件之间临时通信，`props` / `emit` 就够了。  
如果是跨层级、跨页面、多人共用的状态，Pinia 更合适。

### 1.3 Pinia 不是替代所有通信

Pinia 不是让你以后什么都往 store 里扔。

更合理的做法是：

- **组件局部状态**：留在组件内部，比如输入框文本、弹窗开关
- **跨组件共享状态**：放进 Pinia，比如用户信息、购物车、主题、权限
- **简单父子通信**：继续用 `props` 和 `emit`

这样结构才清楚，不会变成“大杂烩”。

---

## 二、Pinia 的基本概念：store、state、getter、action

### 2.1 store：状态仓库

`store` 就是专门放数据和操作方法的仓库。  
项目里每一种业务状态，都可以有自己的 store。

比如：

- `useUserStore`：用户信息
- `useCartStore`：购物车
- `useThemeStore`：主题设置

你可以把 store 理解为某个业务模块的小管家，负责收好这一类数据，也负责说明怎么改。

### 2.2 state：原始数据

`state` 是最基础的数据，像仓库里的库存。

例如购物车 store 里可能有：

- `items`：购物车商品列表
- `count`：商品数量
- `totalPrice`：总价

这些值本身是供页面读取的基础数据。

### 2.3 getter：派生值

`getter` 是从原始数据算出来的结果，和 `computed` 很像。

比如：

- 购物车总价
- 是否已登录
- 是否有商品选中
- 商品数量是否大于 0

如果 `state` 是底料，那 `getter` 就是加工后的成品。

### 2.4 action：修改数据的方法

`action` 就是修改状态的动作。

比如：

- `addToCart(item)`：加入购物车
- `removeFromCart(id)`：删除商品
- `login(userInfo)`：登录并保存用户信息
- `logout()`：清空登录状态

记住这句口诀：

> **state 负责存，getter 负责算，action 负责改。**

---

## 三、创建并使用一个简单 store

下面用最常见的计数器 store 看清 Pinia 的骨架。

### 3.1 创建 store

一般建一个 `stores` 目录，专门放状态管理代码。

例如 `src/stores/counter.js`：

```js
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'

export const useCounterStore = defineStore('counter', () => {
  const count = ref(0)

  const doubleCount = computed(() => count.value * 2)

  const increment = () => {
    count.value++
  }

  const decrement = () => {
    count.value--
  }

  return {
    count,
    doubleCount,
    increment,
    decrement
  }
})
```

这里的关键点：

- `defineStore`：定义一个 store
- `count`：状态
- `doubleCount`：派生状态
- `increment` / `decrement`：修改状态的方法

### 3.2 在入口文件注册 Pinia

在 `main.js` 或 `main.ts` 中：

```js
import { createApp } from 'vue'
import { createPinia } from 'pinia'
import App from './App.vue'

const app = createApp(App)
app.use(createPinia())
app.mount('#app')
```

这一步就是告诉 Vue：Pinia 要启用了。  
如果没注册，后面组件再怎么找这个状态都找不到。

### 3.3 在组件里使用 store

```vue
<script setup>
import { useCounterStore } from '@/stores/counter'

const counterStore = useCounterStore()
</script>

<template>
  <div>
    <p>当前数量：{{ counterStore.count }}</p>
    <p>翻倍结果：{{ counterStore.doubleCount }}</p>
    <button @click="counterStore.increment">加一</button>
    <button @click="counterStore.decrement">减一</button>
  </div>
</template>
```

读取和修改都很直接。  
这就是 Pinia 的优势：**像普通对象一样用，但背后是响应式的。**

## 四、一个最小可运行的购物车 store：把职责分清楚

真正的业务里，最常见的是“列表 + 角标 + 总价”这种共享场景。

### 4.1 创建 cart store

`src/stores/cart.js`：

```js
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'

export const useCartStore = defineStore('cart', () => {
  const items = ref([])

  const totalCount = computed(() => items.value.length)

  const totalPrice = computed(() => {
    return items.value.reduce((sum, item) => sum + item.price, 0)
  })

  const addItem = (product) => {
    items.value.push(product)
  }

  const removeItem = (id) => {
    items.value = items.value.filter(item => item.id !== id)
  }

  const clearCart = () => {
    items.value = []
  }

  return {
    items,
    totalCount,
    totalPrice,
    addItem,
    removeItem,
    clearCart
  }
})
```

这里很典型：

- `items` 是 `state`
- `totalCount` 和 `totalPrice` 是 `getter`
- `addItem`、`removeItem`、`clearCart` 是 `action`

### 4.2 在商品卡片里新增数据

`ProductCard.vue`：

```vue
<script setup>
import { useCartStore } from '@/stores/cart'

const props = defineProps({
  product: Object
})

const cartStore = useCartStore()

const addToCart = () => {
  cartStore.addItem(props.product)
}
</script>

<template>
  <div class="product-card">
    <h3>{{ product.title }}</h3>
    <p>价格：{{ product.price }}</p>
    <button @click="addToCart">加入购物车</button>
  </div>
</template>
```

### 4.3 在头部组件里读取全局状态

`Header.vue`：

```vue
<script setup>
import { useCartStore } from '@/stores/cart'
const cartStore = useCartStore()
</script>

<template>
  <header>
    <span>购物车（{{ cartStore.totalCount }}）</span>
    <span>总价：{{ cartStore.totalPrice }}</span>
  </header>
</template>
```

你点商品卡片上的“加入购物车”，头部角标和总价会立刻变化。  
这就是全局状态联动：**一个地方改，多个地方跟着动。**

### 4.4 在结算页里继续使用同一份状态

`CheckoutPage.vue`：

```vue
<script setup>
import { useCartStore } from '@/stores/cart'
const cartStore = useCartStore()
</script>

<template>
  <div>
    <h2>结算页</h2>
    <p>商品数量：{{ cartStore.totalCount }}</p>
    <p>应付金额：{{ cartStore.totalPrice }}</p>

    <ul>
      <li v-for="item in cartStore.items" :key="item.id">
        {{ item.title }} - {{ item.price }}
      </li>
    </ul>
  </div>
</template>
```

从商品列表页跳到结算页，数据还是在。  
这就说明 Pinia 不只是“组件之间传值更方便”，它更适合**跨页面共享状态**。

## 五、在组件中读取和修改全局状态：让页面真的联动起来

### 5.1 读取状态：像读普通变量一样自然

Pinia 的 state 是响应式的，所以模板里直接用就行：

```vue
<p>用户：{{ userStore.nickname }}</p>
<p>购物车数量：{{ cartStore.items.length }}</p>
```

只要 store 里的数据变化，页面会自动更新。

### 5.2 修改状态：优先走 action

实战里更推荐通过 action 统一修改：

```js
const userStore = useUserStore()
userStore.login({ name: '老赵' })
```

这样做的好处是：

- 修改逻辑集中
- 方便加校验
- 后面加接口请求也容易
- 便于调试和维护

### 5.3 一个登录状态雏形

`src/stores/user.js`：

```js
import { defineStore } from 'pinia'
import { ref, computed } from 'vue'

export const useUserStore = defineStore('user', () => {
  const nickname = ref('')
  const token = ref('')
  const isLogin = computed(() => !!token.value)

  const login = (payload) => {
    nickname.value = payload.nickname
    token.value = payload.token
  }

  const logout = () => {
    nickname.value = ''
    token.value = ''
  }

  return {
    nickname,
    token,
    isLogin,
    login,
    logout
  }
})
```

`LoginPage.vue`：

```vue
<script setup>
import { useUserStore } from '@/stores/user'

const userStore = useUserStore()

const handleLogin = () => {
  userStore.login({
    nickname: '老赵',
    token: 'abc123'
  })
}
</script>

<template>
  <div>
    <button @click="handleLogin">模拟登录</button>
    <p v-if="userStore.isLogin">欢迎你，{{ userStore.nickname }}</p>
  </div>
</template>
```

`Header.vue`：

```vue
<script setup>
import { useUserStore } from '@/stores/user'
const userStore = useUserStore()
</script>

<template>
  <header>
    <span v-if="userStore.isLogin">当前用户：{{ userStore.nickname }}</span>
    <span v-else>未登录</span>
  </header>
</template>
```

当你在登录页点击按钮后，头部组件会自动更新。  
这就是共享状态的价值：登录页负责改，其他页面负责显示，大家用的是同一份数据。

## 六、Pinia 和组件通信、路由页面的配合使用

### 6.1 Pinia 和 props/emit 怎么搭配？

很多初学者会以为“用了 Pinia 就不用 `props` 和 `emit` 了”，其实不是。

更合理的分工是：

- **父子之间传临时参数**：用 `props`
- **子组件通知父组件**：用 `emit`
- **跨页面共享数据**：用 Pinia

你可以把 `props` 和 `emit` 看成面对面说话，适合近距离沟通；Pinia 则像项目广播站，适合所有人都要听见的信息。

### 6.2 Pinia 和路由页面的配合

路由一切换，组件会销毁和重建。  
如果数据只放在页面组件的局部状态里，页面一跳转，数据就没了。

但放进 Pinia 后就不一样了：

- 页面切走，store 还在
- 返回页面，状态还能保留
- 多个路由页面可以共享同一份数据

比如：

- `ProductList` 页加入购物车
- 跳到 `CartPage` 查看列表
- 再跳到 `CheckoutPage` 结算

整个流程里，购物车数据都由 `cartStore` 统一管理。

### 6.3 结合路由的登录判断

很多项目里，进入“个人中心”或“订单页”前会先判断登录状态：

```js
import { useUserStore } from '@/stores/user'
import router from '@/router'

const userStore = useUserStore()

if (!userStore.isLogin) {
  router.push('/login')
}
```

这里 Pinia 就像一个“全局门禁卡”，路由页面可以直接检查它。

### 6.4 实战中的常见配合方式

可以总结成三种模式：

1. **列表页写入 store**：商品列表、详情页完成数据修改  
2. **详情页读取 store**：购物车页、用户中心页直接取状态  
3. **页面初始化读取 store**：例如判断是否登录，未登录就跳登录页

## 七、常见误区：新手最容易踩的几个坑

### 7.1 把所有数据都放进 Pinia

不需要。局部状态放组件里更简单。  
Pinia 只适合共享状态，不适合当万能垃圾桶。

比如输入框内容、弹窗开关、临时折叠状态，放在组件内部更合适。

### 7.2 在很多地方直接乱改 state

能跑不代表好维护。  
尽量统一通过 action 修改，后面排查问题会轻松很多。

### 7.3 store 设计太大

一个 store 只管一类业务，别把用户、购物车、主题、弹窗全塞进去。

比较推荐的拆法是：

- `userStore` 管用户登录态
- `cartStore` 管购物车
- `themeStore` 管主题
- `settingsStore` 管偏好设置

### 7.4 只会用，不理解为什么会自动更新

Pinia 底层依然依赖 Vue3 的响应式系统。  
它不是魔法，只是把 Vue3 的响应式能力包装成了更适合跨组件、跨页面使用的管理方案。

这一章你要真正拿下的，不只是会写几个 API，而是建立一种项目思维：

- 哪些数据需要共享
- 哪些数据应该集中管理
- 哪些数据保持在组件内部

Pinia 的价值就在于：它让 Vue3 项目的全局状态有了清晰的组织方式。

你现在至少应该能做到：

- 明白状态管理要解决什么问题
- 理解 `store`、`state`、`getter`、`action`
- 会创建并使用一个简单 store
- 会在组件中读取和修改全局状态
- 知道 Pinia 如何和组件通信、路由页面配合
- 能做出一个最小的购物车或登录状态雏形

这一步走稳了，后面做登录、购物车、权限控制、主题切换，都会顺很多。

# 第11章 综合实战：做一个完整的 Vue3 小项目

学到这里，你已经把 Vue3 常用零件认识得差不多了：`ref`、`reactive`、`computed`、`watch`、`props`、`emit`、`slot`、`provide/inject`、生命周期、路由、Pinia。接下来最重要的，不是继续背概念，而是把它们串起来，做成一个能跑、能改、能扩展的小项目。

这一章我们按真实开发的思路来走：先拆需求，再搭骨架，然后做页面、拆组件、接状态，最后检查和优化。你会发现，Vue3 不是一堆孤立 API，而是一套很适合“组件化搭积木”的开发方式。会了这些，你就不只是“看懂代码”，而是开始具备“自己做项目”的能力了。

---

## 一、先拆需求：这个项目到底要做什么？

很多新手一上来就直接写页面，最后页面关系乱了，数据不知道放哪，组件也越写越重复。正确做法永远是：**先拆需求，再动手**。

### 1. 选一个足够完整的小项目

这一章我们以一个“待办事项管理”小项目为例。它不算大，但五脏俱全，特别适合练手：

- 能看列表
- 能新增待办
- 能编辑待办
- 能删除待办
- 能标记完成状态
- 能按状态筛选
- 能查看详情
- 能做简单统计

你可以把它理解成一个小店铺：

- 列表页像货架，先看有什么
- 详情页像说明书，看细节
- 表单页像录入口，负责新增和修改
- 管理页像控制台，负责整理和调度

如果一开始连页面类型都没想清楚，后面组件怎么拆、状态怎么放，都会变乱。

### 2. 页面结构怎么定？

一个 Vue3 小项目，本质上都能拆成几类页面：

- **列表页**：展示数据，方便浏览
- **详情页**：查看单条数据的完整内容
- **表单页**：新增或编辑数据
- **管理页**：搜索、筛选、分页、状态切换

比如这个待办项目可以这样分：

- `/list`：待办列表页
- `/detail/:id`：待办详情页
- `/form`：新增待办页
- `/form/:id`：编辑待办页
- `/manage`：待办管理页

关键是：**路径要有意义，参数要清楚。**  
详情页带 `id`，就像快递单号；新增和编辑共用一个表单页，也可以通过有没有 `id` 来区分模式，结构会更统一。

### 3. 功能列表怎么列？

别急着写代码，先把需求写下来，越朴素越好。至少回答这些问题：

- 能不能看列表？
- 能不能进详情？
- 能不能新增和编辑？
- 能不能删除？
- 能不能搜索和筛选？
- 需要登录吗？
- 页面之间要不要共享状态？

比如待办项目可以列成：

- 查看待办列表
- 新增待办
- 编辑待办
- 删除待办
- 标记完成
- 按状态筛选
- 进入详情页查看单条待办
- 统计待办总数、已完成数、未完成数

这样一拆，你会发现很多“看起来复杂”的项目，其实只是几个基础能力的组合。

### 4. 技术方案怎么选？

核心原则只有一个：**够用就好。**

- **组件开发**：页面由多个小组件拼起来
- **路由**：负责页面切换
- **Pinia**：负责共享状态
- **响应式数据**：负责页面自动更新
- **表单处理**：负责新增和编辑
- **生命周期**：负责初始化加载

可以把它想成盖房子：

- 路由是门和走廊，负责进出
- Pinia 是公共仓库，放大家都要用的东西
- 组件是砖块和房间，负责具体功能
- `ref`、`reactive`、`computed`、`watch` 是施工工具，负责数据联动

如果你能说清楚“哪个数据放页面里，哪个放 Pinia 里，哪个交给子组件”，这个项目就成功了一半。

---

## 二、项目怎么搭？目录、路由、状态先规划好

### 1. 目录规划：像收纳箱一样分区

清晰的目录结构，能让项目后期不乱。建议这样分：

```bash
src/
  assets/
  components/
    common/
    business/
    layout/
  views/
    ListView.vue
    DetailView.vue
    FormView.vue
    ManageView.vue
  router/
    index.js
  stores/
    todo.js
  utils/
  App.vue
  main.js
```

你可以这样理解：

- `components/common`：通用组件，比如按钮、弹窗、分页
- `components/business`：业务组件，比如待办卡片、筛选条
- `components/layout`：布局组件，比如头部、侧边栏
- `views`：页面级组件
- `stores`：Pinia 状态
- `router`：路由配置

目录不是为了“看起来专业”，而是为了让你后面找代码、改代码、复用代码都更轻松。

### 2. 路由规划：先画地图再出门

路由就是页面地图。先想好页面之间怎么跳，比写页面本身更重要。比如待办项目可以规划成：

- `/list`：列表页
- `/detail/:id`：详情页
- `/form`：新增页
- `/form/:id`：编辑页
- `/manage`：管理页

新增和编辑共用一个表单页时，可以这样理解：

- 没有 `id`，就是新增
- 有 `id`，就是编辑

这就像去医院挂号：第一次来是新建档案，后面拿着病历号去复诊，入口可以是同一个窗口。

### 3. 状态规划：哪些数据放 Pinia？

不是所有数据都要放 Pinia，判断标准很简单：

- **只在当前页面用**：放组件内部，用 `ref` 或 `reactive`
- **多个页面都要用**：放 Pinia
- **会被多个组件共享**：放 Pinia
- **只是某个子组件局部状态**：留在子组件里

比如待办项目中：

- 待办列表、筛选条件、总数：适合放 Pinia
- 表单输入值：通常放表单页内部
- 弹窗开关：看是否跨组件复用，常见是页面内状态

很多人一开始喜欢“全都放全局”，结果项目没变简单，反而更乱。记住一句话：**局部状态别上升，能本地解决就本地解决。**

---

## 三、核心页面怎么做？列表、详情、表单是主战场

### 1. 列表页：先把数据展示出来

列表页是项目里最常见的入口，它最重要的任务只有三个：

- 读数据
- 展示数据
- 响应操作

一个典型流程是：

1. 页面加载时请求数据
2. 用 `ref([])` 或 `store` 存列表
3. 用 `v-for` 渲染每一项
4. 给每条数据加“查看 / 编辑 / 删除”按钮
5. 点击按钮触发路由跳转或状态更新

列表页最容易犯的错，是把所有逻辑都塞进模板里。更好的做法是：

- 展示交给模板
- 计算交给 `computed`
- 异步加载和联动交给方法或 `watch`

比如筛选后的列表，不要直接在模板里写一长串判断条件，而是让 `computed` 先算好，再渲染。

### 2. 详情页：靠路由参数找到目标数据

详情页的核心就一句话：**根据 `id` 找到对应记录。**

常见做法是：

- 从路由参数里取 `id`
- 调接口，或者从 Pinia 中查找
- 渲染详情内容

如果项目还小，数据直接从列表状态里找就行；如果后面要接真实接口，就建议抽成统一方法。这样无论是列表跳详情，还是其他入口跳详情，都能复用同一套逻辑。

详情页本质上就是“把一条数据讲完整”，所以字段展示最好统一规范，避免列表页和详情页内容对不上。

### 3. 表单页：新增和编辑最好复用一套结构

表单页最能体现组件思维。建议遵循一个原则：**新增和编辑共用一个表单组件。**

因为这两个功能本质上是同一张表，只是：

- 新增时，初始值是空的
- 编辑时，初始值来自已有数据
- 提交时，一个是创建，一个是更新

这时会用到：

- `ref`：接收表单对象
- `reactive`：管理表单整体状态
- `watch`：监听路由变化或编辑数据变化
- `computed`：控制按钮文案、提交模式

比如“新增待办”和“编辑待办”只是模式不同，UI 大部分都可以复用。拆成两个页面会增加维护成本，合并成一个表单页反而更清楚。

---

## 四、组件怎么拆？别把页面写成一坨

### 1. 通用组件：能复用的就别重复写

通用组件最值钱，因为它能帮你省掉大量重复劳动。常见的有：

- 通用按钮
- 弹窗
- 分页器
- 搜索框
- 标签页

这类组件通常通过 `props` 接收参数，通过 `emit` 向外抛事件。比如按钮组件只负责样式和点击，不负责点击后具体做什么，至于保存、删除还是跳转，交给父组件决定。

这就是组件化的精髓：**组件负责表现，父组件负责业务。**

### 2. 业务组件：服务某一块场景

业务组件比通用组件更贴近项目，比如：

- 待办卡片
- 筛选条
- 详情信息块
- 编辑表单项组合

这类组件一般会用到：

- `props` 传数据
- `emit` 通知父组件操作
- `slot` 插入自定义内容

`slot` 很像“留一个插槽给别人塞东西”。比如一个卡片组件，标题和正文可以固定，但右上角按钮留给外部插入，这样既保留统一样式，又能适配不同需求。

### 3. 布局组件：统一页面骨架

布局组件负责统一外壳，比如：

- 顶部导航
- 左侧菜单
- 主内容区

有了布局组件，就不需要每个页面都复制一遍页面框架。以后无论你加新页面还是改整体风格，都只要动一个地方，维护成本会低很多。

### 4. `provide/inject` 适合什么场景？

当组件层级比较深，祖先组件要给很多后代共享一些环境信息时，可以用 `provide/inject`。它适合：

- 主题色
- 全局配置
- 某个模块内共享状态

它像“上级统一发通知，下面各层都能收到”，省得一层层传 `props`。但它适合模块内共享，不建议滥用成全局状态工具。真正跨页面、跨模块的共享，还是更适合交给 Pinia。

## 五、怎么把响应式、表单、组件通信、路由和 Pinia 串起来？

这一节是项目真正落地的关键。

### 1. 响应式：让页面自动跟着数据变

`ref` 和 `reactive` 是 Vue3 的底层基础。

- `ref` 适合基本类型和单值
- `reactive` 适合对象和复杂结构

你可以把它理解成：

- `ref` 像一个带标签的小盒子
- `reactive` 像一整套带联动的柜子

只要绑定的是响应式数据，数据一变，界面就会自动刷新。这就是 Vue3 最省心的地方：你不用手动告诉页面“重画一遍”，它自己会跟着数据动。

### 2. `computed`：把“算出来的值”单独放一边

有些值不是手动输入的，而是根据已有数据算出来的，比如：

- 完成待办数
- 当前筛选后的列表
- 提交按钮是否禁用

这些都很适合放到 `computed` 里。它的好处是：

- 模板更干净
- 逻辑更清晰
- 依赖变化时自动重新计算

简单说，`computed` 就像自动计算器。你给它原料，它帮你产出结果，适合放那些“有公式”的东西。

### 3. `watch`：专门盯着变化做事

`watch` 适合做“监听后动作”，比如：

- 监听路由参数变化，重新请求详情
- 监听筛选条件变化，刷新列表
- 监听表单字段变化，做联动校验

记住一个实用区别：

- `computed` 是“算结果”
- `watch` 是“等变化后执行动作”

如果只是想得到派生值，用 `computed`；如果是数据一变就要执行某个操作，用 `watch`。

### 4. 生命周期：什么时候去加载数据最合适？

项目实战里，生命周期也很关键。比如：

- 组件挂载后去请求列表数据
- 路由切换后刷新详情数据
- 组件销毁前清理定时器或监听

在 Vue3 里，你经常会在组件进入页面后做这些事。它就像“人到场再开始干活”，时机对了，很多问题就少了。比如列表页初次加载时请求数据，表单页进入后读取编辑内容，都是很典型的生命周期应用场景。

### 5. 组件通信：父子、兄弟、跨层级都要会

项目里常见的通信路径有：

- **父传子**：`props`
- **子传父**：`emit`
- **兄弟通信**：通过父组件中转，或用 Pinia
- **跨层级**：`provide/inject` 或 Pinia

实战里最推荐的思路是：**先用父子通信解决局部问题，再用 Pinia 解决跨页面共享。**

不要一上来就想着全局广播，那样容易把项目做得很难维护。小范围的问题，小范围解决；需要共享时，再升级方案。

### 6. Pinia：把共享数据放到一个统一仓库

Pinia 入门后，你至少要会三件事：

- 定义一个 store
- 存放共享状态
- 提供修改状态的方法

在项目中，Pinia 很适合放：

- 列表数据
- 用户信息
- 筛选条件
- 统一弹窗状态
- 多页面共享的计数或配置

它就像一个公共仓库，谁要用都来这里拿，避免每个页面各存一份，最后数据对不上。尤其是当列表页、详情页、管理页都要看同一批数据时，Pinia 会非常顺手。

## 六、项目闭环怎么做？从“能跑”到“算完成”

### 1. 一个完整流程应该长什么样？

一个真正完整的小项目，不只是“页面能打开”，而是要能形成闭环。以待办项目为例，完整流程应该是：

1. 进入列表页，看到待办数据
2. 点击“新增”，进入表单页
3. 填写表单，提交后更新列表
4. 点击某条待办，进入详情页
5. 在详情页查看完整信息
6. 返回列表，编辑或删除这条数据
7. 根据状态筛选出已完成或未完成项

这才叫一个小项目。它不是几个静态页面拼起来，而是“数据流动起来了”。

### 2. 组件、路由、状态怎么真正配合？

这一步最能看出你有没有掌握 Vue3 核心语法：

- 列表页通过路由跳转到详情页
- 表单页通过 `props`、`emit` 或路由参数区分新增和编辑
- 列表数据交给 Pinia 统一管理
- 筛选条件用 `computed` 算出结果
- 路由变化后用 `watch` 重新加载数据
- 页面初始化用生命周期去拉取内容

你会发现，前面学过的每个知识点，在这里都能找到位置。它们不是孤立的，而是拼在一起才成事。

### 3. 验收标准：做完算不算完成？

项目做完后，不要急着说“完成了”，先按清单过一遍：

- 路由跳转是否正常？
- 列表是否能正确显示？
- 新增、编辑、删除是否可用？
- 表单校验是否正常？
- 详情页是否能根据 `id` 正确加载？
- 组件通信是否有断层？
- Pinia 状态刷新后是否还能保持合理行为？
- 页面切换后是否会出现数据错乱？

如果这些都没问题，说明你的项目至少已经具备了“能交付”的基础。

### 4. 常见问题排查

新手最容易踩的坑，通常是这些：

- **数据没响应**：把普通变量当响应式数据用了
- **组件不更新**：修改方式不对，没触发响应式更新
- **路由参数取错**：`params` 和 `query` 混了
- **表单值不同步**：初始化和编辑填充逻辑没处理好
- **Pinia 用太多**：把本地状态也塞进全局，导致项目变重

如果遇到问题，先问自己三个问题：

1. 数据是从哪来的？
2. 数据是放在哪里的？
3. 数据变化后，页面为什么没跟着变？

这三问，基本能帮你定位大多数 Vue3 问题。

### 5. 优化思路

如果功能已经跑通，可以继续做这些优化：

- 提取重复组件，提升复用
- 用 `computed` 简化模板逻辑
- 用 `watch` 处理联动场景
- 把页面状态和共享状态分开
- 给关键操作加 loading 和错误提示
- 给表单提交和删除操作加确认弹窗

优化不是锦上添花，它其实是在帮你把项目从“能用”推向“好用”。

---

## 结尾小结：从“会写”到“会做项目”

这一章的重点，不是让你记住多少 API，而是让你形成一套 Vue3 项目思路：

1. 先拆需求，再写代码  
2. 先搭目录和路由，再做页面  
3. 先明确状态归属，再决定用 `ref`、`reactive` 还是 Pinia  
4. 先做组件拆分，再做页面组合  
5. 用生命周期负责初始化，用 `watch` 处理变化，用 `computed` 处理派生值  
6. 最后用检查清单把项目收口  

做到这一步，你就不再是“会几个 Vue3 语法点”，而是开始具备独立完成一个小项目的能力了。Vue3 的核心语法、组件开发思维、路由、Pinia、生命周期，这些东西只有真正落到项目里，才会变成你的本事。

# 第12章 复盘与进阶方向：把 Vue3 学成自己的工具

学到这里，你已经不是只会“看懂 Vue3”的人了，而是开始真正“拿 Vue3 干活”的人。前面我们一路学了 **Vue3 核心语法、组件开发、ref、reactive、computed、watch、props、emit、slot、provide/inject、生命周期、Vue Router 基础、Pinia 入门**，也做过小项目。到了这一章，老赵不再继续堆新概念，而是带你做三件更重要的事：**把知识串起来、判断自己会不会用、规划后续怎么继续进步**。

前端学习最怕的，不是没学过，而是“学过很多，真到自己写项目时又卡住”。所以这一章的目标很明确：把你学到的东西复盘成一张清晰的能力地图，再给你一份能落地的自检清单，最后告诉你下一步往哪儿走。

## 一、全书知识回顾：你已经掌握了哪些 Vue3 核心能力

如果把 Vue3 比作一套装修工具，那它不是让你背按钮，而是教你怎么把页面拆开、拼起来、管起来。现在你手里，至少已经有了这几类工具。

### 1. 你已经会的，不只是语法，而是一整套页面组织方式

- **模板语法**：把数据展示到页面上
- **响应式机制**：数据变了，页面自动更新
- **组件开发**：把大页面拆成可复用的小零件
- **组件通信**：让这些零件顺畅“说话”
- **组合式 API**：按功能整理逻辑，不再乱成一团
- **路由与状态管理**：负责页面切换和共享数据

所以 Vue3 的核心，不是“会几个 API”，而是你开始拥有了**组件思维**。  
看到一个页面，你会下意识去想：哪些地方该拆成组件，哪些数据只在本地用，哪些数据要共享，哪些逻辑该抽出去复用。

### 2. 这些 API，放在一张地图里更容易记

你可以把它们理解成一支分工明确的团队：

- **ref**：像一个小抽屉，适合放单个值，比如 `count`、`keyword`
- **reactive**：像文件柜，适合放一组相关数据
- **computed**：像自动计算器，原料一变，结果自动更新
- **watch**：像盯梢员，专门观察变化并处理额外逻辑
- **props**：父组件把数据传给子组件
- **emit**：子组件把消息回传给父组件
- **slot**：预留位置，让组件更灵活
- **provide/inject**：像跨楼层传话，适合层级较深时共享数据
- **生命周期**：组件从创建、挂载到销毁的全过程
- **Vue Router**：把项目拆成多个页面管理
- **Pinia**：给共享状态找一个统一的家

如果你能把这些能力放在正确的位置上，说明你已经从“会写代码”开始走向“会设计代码”了。

---

## 二、从学会到会用：独立做项目的自检清单

### 1. 你真的会做 Vue3 项目了吗？

很多同学会有一个错觉：我会 `v-for`、会 `ref`、会 `props`，应该算会 Vue 了吧？

老赵的判断标准更直接：**你能不能独立完成一个小项目。**  
比如待办事项、博客列表、商品管理、记账本、简易后台页面。只要你能从零拆出来、写出来、改出来，就说明你已经从“学语法”进入“做应用”了。

### 2. 开新项目前，先过一遍这份自检清单

#### 需求层面
- 页面要分成几个组件？
- 哪些是展示型组件，哪些是业务型组件？
- 有没有列表、表单、弹窗、详情页这些常见结构？
- 这个项目最核心的业务动作是什么？

#### 数据层面
- 哪些数据是局部的，用 `ref` 或 `reactive` 就够了？
- 哪些数据需要多个组件共享，应该放到 `Pinia`？
- 哪些数据是由现有数据计算出来的，适合用 `computed`？
- 哪些变化需要触发额外处理，适合用 `watch`？

#### 组件层面
- 父子之间靠 `props` 和 `emit` 传什么？
- 有没有需要复用的内容区域，可以用 `slot`？
- 有没有跨层级通信需求，可以考虑 `provide/inject`？
- 哪些逻辑应该放在公共组件里，哪些逻辑应该留在页面里？

#### 页面层面
- 是否需要多个路由？
- 是否要区分列表页、详情页、编辑页？
- 返回、跳转、路由参数是否已经设计好？
- 页面之间的共享数据怎么拿，怎么更新？

#### 交互层面
- 表单提交怎么处理？
- 输入校验怎么做？
- 条件渲染、列表渲染是否清晰？
- 是否考虑加载中、空状态、错误状态？

这份清单看着多，其实就是把一个项目拆成几类问题。你每次做项目时只要有意识地过一遍，独立完成能力就会明显提升。

### 3. 一个会做项目的人，通常会先做这几步

1. 先画页面结构图  
2. 再拆组件  
3. 再梳理数据流向  
4. 再决定哪些地方用 `ref`、`reactive`、`computed`、`watch`  
5. 再设计 `props`、`emit`、`slot` 的关系  
6. 最后才考虑 `Router` 和 `Pinia` 要不要上

这个顺序很重要。它能帮你避免一上来就“先把所有技术塞进去”，最后代码写得像仓库一样乱。

## 三、常见学习误区：只背 API，不做项目

### 1. 为什么“背会了”不等于“会了”？

这是新手最常见的坑。很多人学 Vue3 的方式是看视频、记笔记、背概念、抄代码，结果一到自己写项目，脑子里一片空白。

原因很简单：**API 不是孤立存在的，它们是服务于场景的。**

比如：

- 你知道 `computed` 是计算属性，但不知道它什么时候比方法更合适
- 你知道 `watch` 能监听变化，但不知道它什么时候用来处理异步请求
- 你知道 `props` 能传值，但不知道如何配合 `emit` 完成子父组件联动
- 你知道 `Pinia` 是状态管理，但不知道小项目里哪些数据根本不需要放进去

所以真正的学习，不是“记住名词”，而是“在场景里做选择”。

### 2. 常见误区有哪些？

#### 误区一：把所有数据都塞进一个组件
项目一大，代码就会变成“一个页面写到天荒地老”。正确做法是先拆组件，再拆数据职责。

#### 误区二：一上来就想学复杂技术
还没把 `ref`、`computed`、`props`、`emit` 用顺，就急着看源码、看高级封装，等于还没学会骑车就想练特技。

#### 误区三：只会抄，不会改
抄一个待办事项很简单，但你能不能把它改成记账本、商品筛选、留言板？如果不能，说明你还没真正掌握。

#### 误区四：把状态管理当成万能解药
Pinia 很好用，但不是所有数据都要放到全局。局部状态放局部，只有共享数据、跨页面数据、复杂业务状态，才值得上状态管理。

#### 误区五：只看懂了页面，没看懂数据流
很多人界面能跑，但不知道按钮点下去后数据怎么走。真正会做项目的人，不只看“页面长什么样”，还会看“数据怎么流”。

### 3. 正确的学习姿势是什么？

一句话：**先做小，再做全。**

- 先写一个最小可运行版本
- 再加组件拆分
- 再加表单和交互
- 再加路由
- 再加 Pinia
- 最后再考虑优化和重构

这样你更容易形成“从需求到代码”的完整链路。

## 四、后续进阶方向：更复杂组件、工程化、性能优化

### 1. 进阶不是跳坑，是继续把工具箱补齐

当你能独立做出一个 Vue3 小项目后，下一步不是盲目刷新概念，而是继续补强三块能力：**更复杂组件、工程化、性能优化**。

#### 更复杂组件
你会开始接触业务型表格、筛选器、分页器、弹窗表单、组合型布局、可配置的公共组件。这时 `slot`、`props`、`emit`、`provide/inject` 的价值会更明显。组件不是“写完就算”，而是“写得能复用、能扩展、能维护”。

#### 工程化
工程化说白了，就是让项目更像一个真正可协作的产品，而不是单页练习题。你可以逐步关注：

- 目录结构怎么设计
- 组件怎么分层
- 请求怎么封装
- 统一错误处理怎么做
- 环境变量怎么管理
- 代码风格怎么统一

这些内容会让你从“能写页面”走向“能参与团队开发”。

#### 性能优化
性能优化不是一上来就追求极致，而是先有意识。你可以先留意：

- 列表是否渲染太多
- 不必要的响应式是否太多
- 组件是否频繁重渲染
- 图片和资源是否合理加载
- 路由页面是否按需加载

真正的优化，通常不是炫技，而是减少浪费。

### 2. 你现在最该补的，不是难度，是深度

很多同学一学完基础就想冲“高级技巧”，但基础没打牢，后面全靠运气。老赵建议你先把下面这些内容吃透：

- `ref` 和 `reactive` 的使用边界
- `computed` 与 `watch` 的区别
- `props`、`emit`、`slot` 的组合用法
- `provide/inject` 适合什么场景
- 生命周期里每个阶段该做什么
- Router 和 Pinia 在项目中的真实位置

这些东西看似基础，但它们决定了你后面的上限。

### 3. 下一步学习路线怎么走？

如果你想继续往前走，建议按这个顺序来：

1. **再做 1 个小项目**，把组件拆分和数据流转彻底练熟  
2. **加入 Vue Router**，练习列表页、详情页、编辑页的切换  
3. **加入 Pinia**，把共享状态从“到处传”变成“统一管”  
4. **开始做工程化整理**，学会目录规划、接口封装和代码复用  
5. **再看性能优化**，关注按需加载、列表渲染和减少无效更新

这个路线不绕路，适合已经有 HTML、CSS、JavaScript 基础的前端学习者继续往上爬。

## 五、学习建议：继续用小项目练手，巩固实战能力

### 1. 最好的复习方式，是换一个项目再做一遍

学完这本书后，别急着收藏就完事。最有效的方式，是继续做一个新项目，把知识重新用一遍。

你可以尝试这些题目：

- 待办事项升级版
- 简易记账本
- 博客文章管理
- 商品筛选与购物车
- 个人资料管理页
- 笔记本应用

做新项目时，尽量强迫自己独立思考：

- 先画结构，再写代码
- 先拆组件，再联调
- 先做基础功能，再加细节
- 先局部状态，再考虑全局状态
- 先跑通流程，再做美化

### 2. 你可以按这个节奏持续练习

#### 第一轮：复刻
找一个简单项目，把核心功能完整做出来。目标不是花哨，而是把基础语法再过一遍。

#### 第二轮：改造
在原有项目上加功能，比如搜索、筛选、分页、弹窗编辑、本地缓存。这一步最能检验你是否真的理解了 Vue3 的核心机制。

#### 第三轮：独立设计
不看教程，自己设计一个小项目。哪怕功能不多，只要你能从页面结构、组件拆分、数据流转、路由规划、状态管理这些角度独立完成，就说明你开始真正掌握 Vue3 了。

### 3. 复盘的重点，不是写得多，而是想得清

每做完一个项目，建议你都回答这几个问题：

- 这个项目里，哪些地方用到了 Vue3 核心语法？
- 哪些组件设计得合理，哪些组件可以再拆？
- 数据流有没有绕路？
- `props`、`emit`、`slot` 用得是否自然？
- `provide/inject`、`Router`、`Pinia` 是否真的解决了问题？
- 如果重做一遍，我会先改哪里？

这些问题比“我又写完一个项目了”更重要，因为它们能逼你真正成长。

---

## 结尾小结：把 Vue3 变成你的趁手工具

学 Vue3，不是为了背下一堆 API 名字，而是为了把它变成你手里顺手的工具。当你遇到一个页面，脑子里能自动想到怎么拆组件；当你看到一份需求，知道哪些地方该用 `ref`、哪些地方该用 `computed`、哪些地方该上 `Pinia`；当你能独立完成一个小项目，并且知道下一步该怎么优化——这时候，Vue3 才真正属于你。

记住一句话：**会用，才算学会。**  
而“会用”不是看完就有的，是一次次做项目、改项目、复盘项目磨出来的。
