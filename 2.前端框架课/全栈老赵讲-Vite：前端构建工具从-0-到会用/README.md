# 第1章：为什么前端项目需要 Vite

## 开篇引入：前端开发，大家最烦的是什么

做过前端项目的人，大多都被这几件事折腾过：

- 项目一启动就要等很久
- 改一行代码，热更新慢，甚至不稳定
- 配置越来越多，想跑起来先翻半天文件
- 项目一大，构建时间明显变长，反馈越来越迟钝

这些问题看起来不同，本质上就一句话：**工具开始拖后腿了**。  
Vite 出现的意义，不是再造一个更复杂的构建工具，而是把前端开发里最常见的痛点重新整理了一遍：**启动快、更新快、配置轻**。

下面老赵不绕弯，直接讲清楚它为什么有用。

---

## 一、前端项目最常见的痛点是什么？

### 1. 开发时最怕“等”

前端开发最消耗人的地方，不是写业务，而是反复等待：

- 启动开发服务器慢
- 页面首次打开慢
- 保存文件后重新编译慢
- 改一点点，整个页面却要重来一遍

项目小时，这些问题不明显；项目一大，等待时间就会被放大。开发者本来该把时间花在思考和修改上，结果却花在看进度条上。等得久了，尝试次数会变少，效率也会跟着掉。

### 2. 构建时最怕“全量重来”

传统构建流程里，你只是改了一个小模块，工具却可能重新分析、重新打包一大堆内容。  
这就像你只想换一个螺丝，工具却要求你把整面墙拆下来再装回去。

常见表现就是：

- 依赖分析重
- 编译链路长
- 变更影响范围大
- 热更新不稳定时只能频繁刷新

组件多、页面多、依赖多的项目里，这种问题会更明显。改一个按钮样式，整个页面都可能重新编译；改一个路由配置，开发服务也要等很久才响应。

### 3. 配置时最怕“越来越复杂”

很多项目不是一开始就复杂，而是随着需求增加，配置逐渐膨胀：

- 路径别名一堆
- 代理规则一堆
- 环境变量一堆
- 插件一堆
- 构建优化一堆

最后你会发现，项目还没开始写，配置已经先占了一大页。配置越多，问题越容易藏起来，工具本来是帮忙的，最后却变成维护负担。

---

## 二、传统构建工具在大型项目中的典型问题

这里不是说传统工具不好，而是它们更适合当年的场景。前端生态变了，项目规模变了，大家对开发体验的要求也变了。

### 1. 启动阶段成本高

传统方案通常会先把整个应用打包一遍，再启动开发服务。  
项目越大，首次启动越慢。对于频繁打开、频繁切换分支、频繁拉起项目的人来说，这种成本很明显。

### 2. 热更新链路长

传统工具也能做热更新，但往往要先经过较重的打包流程。你改了一个组件，工具要先重新处理依赖，再决定哪些内容需要刷新。这个过程一长，体验就会变差。

热更新一旦不稳定，开发者就会频繁手动刷新页面，状态丢失、定位困难、调试效率下降，这些问题会连锁出现。

### 3. 配置和约定容易混在一起

很多老项目到后期都会变成这样：**业务逻辑还算清楚，构建配置已经没人敢轻易碰。**

原因很简单，配置和插件耦合太深，新人看不懂，老手也怕改坏。尤其当项目需要接入多个环境、多个代理、多个构建策略时，配置就容易变成“只有少数人敢碰”的区域。

---

## 三、Vite 解决的核心问题是什么？

### 1. 启动快：先让你跑起来

Vite 的核心思路，是**开发时不再把整个应用先打成一个大包**。  
它利用浏览器对原生模块的支持，开发服务器直接按需提供文件。

你可以把它理解成：  
不是先把整箱货物打成一个巨包再发，而是你要哪个，先拿哪个。

这样带来的直接好处就是：

- 启动更快
- 项目越大，优势越明显
- 本地调试等待更少

这对开发者很重要。你不用每次都先“等工具准备好”，而是可以更快进入写代码、看效果、再修改的节奏。

### 2. 更新快：改哪儿看哪儿

Vite 在开发阶段对更新处理得更轻，文件变更后，通常只需要处理受影响的部分。  
这意味着你改一个组件，不一定要整个页面重新来一遍。

对开发者来说，这种体验很直接：

- 保存后反馈快
- 调试节奏顺
- 心流不容易断

不管是 Vue 组件还是 React 页面，最怕的就是改完之后半天没反应。Vite 让反馈更及时，调试时你能更快确认这次改动有没有生效。

### 3. 配置轻：默认已经够用

Vite 的设计思路不是让你一上来就写一堆配置，而是尽量提供一套“开箱能跑”的体验。  
很多常见需求，默认就能满足；真需要改时，再通过配置文件补上。

这对中小型项目尤其友好：

**少写配置，就少出错；少出错，就更容易维护。**

也就是说，Vite 不逼你一开始就把工程化细节补满，而是先让项目跑起来，再按需加规则。这个顺序对大多数团队都更舒服。

---

## 四、哪些类型的项目适合优先考虑 Vite？

不是所有项目都必须立刻迁移，但下面这些场景，Vite 通常值得优先考虑。

### 1. 新项目

新项目最适合直接用 Vite。  
因为没有历史包袱，不需要迁移旧配置，也不用兼容一堆早年留下来的构建习惯。直接用更轻的工具，通常最省事。

### 2. 中大型前端项目

项目进入多人协作阶段后，启动慢、更新慢的问题会被放大。  
Vite 在开发体验上的优势，会直接体现在团队效率上，尤其适合：

- 页面多
- 模块多
- 组件复用多
- 改动频繁

### 3. Vue / React 项目

这两类项目本来就是 Vite 的常见使用场景。  
后面你会看到，Vite 对 Vue 和 React 的支持都很顺手，创建项目、接入插件、配置代理、管理环境变量都很自然。**如果你做的是 Vue 或 React，Vite 基本可以作为默认优先项。**

### 4. 想少折腾配置的项目

如果你的目标是“先把业务跑起来，再逐步完善工程能力”，Vite 很合适。  
它的默认体验比较平衡，不会逼你一开始就把工程化细节补到满格。

## 五、从“工具箱”的角度，怎么理解 Vite 的位置？

老赵喜欢把前端工具理解成工具箱里的不同扳手，不要一上来就争“谁最强”，关键看场景。

### 1. Vite 不是替代所有工具，而是更适合现代前端开发节奏

它重点解决的是：

- 开发启动
- 热更新
- 配置维护
- 基础构建体验

也就是说，Vite 更像一个**适合日常高频使用的主力工具**。  
它不一定把所有能力都做满，但把最常用、最影响效率的部分做轻了。

### 2. 真正重要的是“用起来顺手”

如果一个工具每次打开都很慢、每次改动都很重、每次配置都很烦，那么它再“成熟”，对开发者来说也未必友好。  
Vite 的价值就在于：它把很多常见问题做轻了，让你把时间留给业务。

这也是为什么它在 Vue、React 项目里越来越常见。不是因为“新”本身有多厉害，而是它确实让日常开发更顺。

## 六、先跑起来：一个最小入门示例

如果你现在就想感受一下 Vite，最简单的方式就是先创建一个项目跑起来。

```bash
npm create vite@latest my-vite-app
cd my-vite-app
npm install
npm run dev
```

这几行命令做的事很直接：

- 创建一个 Vite 项目
- 进入项目目录
- 安装依赖
- 启动开发服务器

你会很快看到一个能跑的前端项目，而不是先面对一堆复杂配置。  
这就是 Vite 最直观的优势：**先把开发环境跑顺，再慢慢补工程能力。**

---

## 可复制的配置示例

下面给一个最基础、能直接看懂的 `vite.config.js` 示例。

```js
import { defineConfig } from 'vite'

export default defineConfig({
  server: {
    port: 5173,
    open: true
  },
  build: {
    outDir: 'dist'
  }
})
```

这个例子里：

- `server.port`：开发服务端口
- `server.open`：启动后自动打开浏览器
- `build.outDir`：构建输出目录

你可以先把它当成配置文件的起点。后面再逐步加代理、环境变量、插件和多环境构建。

## 老赵实操建议

1. **新项目优先直接用 Vite**，别先上复杂构建链路。  
2. **把开发体验放第一位**，启动速度和热更新速度会直接影响效率。  
3. **配置别一次写满**，先让项目跑起来，再按需补充。  
4. **Vue 和 React 项目都可以先用 Vite 起步**，后面再根据业务补插件和构建规则。  
5. **团队里尽量统一配置风格**，别一个人一套写法，最后没人敢维护。  
6. **先用最小命令验证环境**：`npm create vite@latest`、`npm run dev`，跑通再谈优化。

# 第2章：Vite 和传统构建工具到底差在哪

## 开篇引入：别只知道“Vite 很快”

很多人第一次用 Vite，第一反应就是：**快**。项目一创建，开发服务器很快就起来；改一行代码，页面也能迅速看到变化。于是大家自然会把它理解成“比 Webpack 更快的工具”。

这话不算错，但只说到了一半。

如果只把 Vite 看成“快一点的打包器”，后面在配置、插件、生产构建和兼容性上很容易踩坑。因为 Vite 和传统构建工具真正的差别，不只是速度，而是**工作方式不同**。工作方式一变，开发体验、配置思路、插件机制和构建逻辑都会跟着变。

这一章就把这件事讲清楚：  
**Vite 到底和传统构建工具差在哪，为什么它快，适合什么项目，又有哪些边界。**

---

## 一、先把概念说透：传统工具和 Vite 的思路不一样

### 1. 传统工具：先打包，再给浏览器用

以 Webpack 这类传统构建工具为代表，常见思路是：

1. 读取入口文件  
2. 分析所有依赖  
3. 处理 JS、CSS、图片等资源  
4. 统一打成一个或多个 bundle  
5. 开发时把这些 bundle 提供给浏览器

好处是浏览器拿到的是整理好的结果；问题也很明显：开发阶段很多工作提前做了。哪怕只改一行代码，工具也可能要重新分析依赖、重建 bundle、重新输出文件。项目越大，这个过程越重。

### 2. Vite：开发时按需提供，构建时再打包

Vite 的思路不同：

- **开发阶段**：不先整体打包，而是让浏览器直接按需加载模块
- **生产构建阶段**：再用打包器把代码整理成适合上线的产物

也就是说，Vite 把“开发”和“生产”分开处理了。开发时追求快和轻；上线时追求稳定和优化。  
你可以把它理解成：

- 传统工具像“先把整本书复印好再发给你”
- Vite 像“你翻到哪页，我先把哪页给你”

所以它在开发阶段会明显更省事，启动快、更新快。

### 3. 关键差别不是“有没有打包”，而是“什么时候打包”

很多人误以为 Vite 不打包，其实不是。

更准确地说：

- **开发时**：尽量不做大规模预打包
- **构建时**：仍然会打包，只是交给底层打包工具完成

所以 Vite 不是“不要打包”，而是把打包从开发体验里挪开了。  
它最本质的变化是：**开发阶段从“先整理再使用”变成“先使用再按需整理”。**

---

## 二、开发阶段与生产构建阶段，Vite 怎么分开处理

### 1. 开发阶段：优先让你“马上写、马上看”

开发时，Vite 的重点只有两个：

- 让服务尽快启动
- 让修改尽快反映到页面

因此它会尽量减少启动时的工作量，不做大范围扫描和全量打包。浏览器请求哪个模块，就按需返回哪个模块。直接结果就是：

- 项目越大，启动优势越明显
- 改动越小，热更新越快
- 开发时的等待感大幅下降

比如你改一个组件里的按钮文案，传统工具可能要先走一遍构建链路；Vite 更像“只处理这个组件相关的变化”，所以反馈更快。

### 2. 生产构建阶段：回到“该怎么上线就怎么上线”

到了生产环境，Vite 不会继续用开发模式那套“按需加载”方式直接发包，而是会做正式构建：

- 压缩代码
- 处理静态资源
- 拆分依赖
- 生成适合部署的产物

这一步的目标不是“快启动”，而是“上线可用、体积合理、性能稳定”。  
所以要记住：**Vite 的快，主要体现在开发阶段；生产构建仍然需要认真优化。**

### 3. 为什么浏览器能直接按模块请求

传统工具通常会先把依赖整理成一个大块，浏览器拿到的是打包好的结果。Vite 在开发阶段更接近原生 ESM，也就是浏览器本来就支持的模块加载方式。

简单说就是：

1. 页面先加载入口 HTML  
2. HTML 引用入口 JS  
3. 入口 JS 继续通过 `import` 引用其它模块  
4. 浏览器按需请求对应文件  
5. Vite 只负责把请求来的模块转换成浏览器能读的内容

所以它不是先把所有东西都做成一个大包再给浏览器，而是让浏览器自己顺着模块关系去拿。这就少了大量“先整体整理”的工作，自然也就更快。

---

## 三、为什么 Vite 在启动和热更新上更快

### 1. 启动快：少做事，先把服务跑起来

传统工具在启动时，往往要先梳理依赖关系，再进行整体处理。Vite 开发阶段更像“即开即用”，不要求一上来把所有资源都准备齐。

它省下的主要是：

- 大范围依赖分析
- 全量 bundle 生成
- 开发期不必要的编译成本

所以你会感觉项目一建好，服务马上能跑。对前端开发来说，这种“打开就能干活”的体验很重要，尤其是反复重启、切页面、调样式的时候。

### 2. 热更新快：只更新变了的那部分

热更新慢，很多时候不是“页面刷新慢”，而是工具找变更、重新编译、再通知页面这整套链路太长。

Vite 在开发阶段更偏向模块级更新：

- 哪个模块变了，就只处理哪个模块
- 相关依赖尽量最小化影响
- 页面不需要整页刷新就尽量不刷新

所以你改一个样式文件或组件文件，页面响应会很快。对组件化项目来说，这种体验尤其明显：你不需要等整站重新编译，修改和预览之间几乎没有明显延迟。

### 3. 改一行代码后，页面到底经历了什么

可以简单理解为：

1. 你保存了一个 `.vue` 或 `.tsx` 文件  
2. Vite 监听到文件变化  
3. 它只重新处理这个模块及其相关依赖  
4. 浏览器通过热更新通道收到通知  
5. 页面局部替换，尽量不整页刷新

和传统工具相比，少了“先全量重建再通知”的大动作。  
这就是它“快”的具体来源，不是某个神奇黑科技，而是把更新范围控制得更小。

## 四、把差异整理成一张对照表，更容易记住

| 对比项 | 传统构建工具 | Vite |
| --- | --- | --- |
| 启动方式 | 先分析、先打包，再提供服务 | 开发时按需提供模块，启动更轻 |
| 热更新 | 影响范围较大，链路较长 | 更偏模块级更新，反馈更快 |
| 依赖处理 | 启动时要大量处理依赖 | 开发阶段尽量少做全量工作 |
| 生产构建 | 开发和构建思路更接近 | 开发与构建分离，构建时再打包 |
| 配置复杂度 | 往往更重，定制项多 | 默认更轻，常用场景更清爽 |
| 适用场景 | 历史项目、复杂工程、强定制场景 | 现代前端应用，尤其是 Vue/React |
| 调试体验 | 有时要等构建完成才能看变化 | 看到变化更及时，适合高频修改 |

这不是说传统工具不好，而是它们的设计目标不同。一个偏“统一处理”，一个偏“开发阶段尽量少处理”。

## 五、Vite 的优势边界：适合什么，不适合什么

### 1. 适合什么

Vite 特别适合这些场景：

#### 适合前端应用开发
Vue、React 这类现代前端项目，用 Vite 做开发体验很好。  
如果你的项目主要是组件开发、页面开发、前后端分离应用，Vite 很合适。

#### 适合快速启动和快速迭代的团队
如果团队经常改页面、调样式、改组件，Vite 的优势会很明显。尤其是项目中后期，代码量上来之后，开发速度差异更直观。

#### 适合标准化程度较高的工程
比如：

- 单页应用
- 使用现代语法
- 依赖关系清晰
- 项目结构相对规范

这类项目迁移到 Vite 会比较顺。

### 2. 不太适合什么

Vite 不是万能钥匙，下面这些情况要谨慎：

#### 老项目迁移成本高
如果项目里有很多旧依赖、历史包袱、特殊构建逻辑，直接切 Vite 可能会碰到兼容问题。不是不能做，而是要评估迁移成本。

#### 对深度定制构建流程依赖很重
有些项目需要非常特殊的产物、复杂的打包策略。这种情况下，关键不是“快不快”，而是“配置和插件能不能接住”。

#### 问题根本不在构建工具
有时候项目慢，不是构建工具慢，而是代码分包、资源管理、接口请求或业务逻辑本身有问题。  
这时换工具可能只能解决“启动慢”，解决不了“整体慢”。

### 3. 迁移前先检查什么

如果你准备把老项目迁到 Vite，先别急着动手，建议先看这几项：

- 旧插件是否有替代方案
- 路径别名是否统一
- 环境变量写法是否需要调整
- Node 版本是否满足要求
- 入口结构是否清楚
- 静态资源引用方式是否规范

这一步不做，迁移时很容易一边改配置，一边补历史坑。

### 4. 两个更贴近实际的场景

#### 场景一：新建 Vue 项目
如果你在做一个新的后台管理系统、活动页面或中型业务站点，Vite 往往是更省心的选择。原因很简单：依赖更清楚，开发频繁，热更新体验能直接提升效率。

#### 场景二：老旧多入口项目
如果项目已经跑了很多年，入口多、脚本杂、历史配置重，先别急着切。  
这类项目更适合先做评估：入口怎么拆、旧插件能不能替代、上线链路是否要改。  
有时候不迁移，反而是更稳的方案。

### 5. 判断是否适合的简单方法

你可以先问自己三个问题：

1. 我是做现代前端应用，还是维护一个很老的工程？  
2. 我更在意开发体验，还是更在意复杂构建能力？  
3. 我现在的瓶颈，是启动慢，还是项目本身复杂？

如果答案偏向“现代应用、开发体验、想要更快迭代”，那 Vite 大概率适合你。

## 六、常见误区：快不等于万能

### 误区 1：Vite 快，所以它一定比所有工具强

不对。快只是一个维度。工具选型还要看：

- 生态兼容性
- 插件成熟度
- 现有项目结构
- 团队熟悉度

有些项目不是“不该用 Vite”，而是“不能只看速度”。

### 误区 2：用了 Vite，生产构建就不用管了

也不对。  
Vite 开发体验好，不代表上线就自动优秀。你还是要关注：

- 打包体积
- 资源拆分
- 懒加载策略
- 静态资源管理
- 环境区分

开发快，只是第一步。

### 误区 3：Vite 不需要配置

更不对。Vite 默认简单，不代表你不需要配置。真正落到项目里，还是会碰到：

- 别名配置
- 代理配置
- 环境变量
- 插件接入
- 构建参数调整

正确姿势不是“完全不配”，而是“按需配置”。

### 误区 4：所有项目都应该立刻迁移到 Vite

也别这么想。  
如果项目稳定、团队熟悉、构建链路够用，没必要为了“新”去折腾。迁移本身也是成本，尤其是业务重、历史久的项目。

## 七、Vite 在 Vue 和 React 项目里分别扮演什么角色

### 1. 在 Vue 项目里

Vue 项目用 Vite，最直接的收益就是：

- 开发启动快
- 单文件组件体验顺
- 修改组件后反馈及时
- 配置相对清爽

如果你从传统工具迁过来，会明显感受到“少了很多启动等待”。尤其是 Vue 的 `.vue` 文件本身就适合模块化开发，和 Vite 的按需加载思路很契合。

这里要先说明一点：这一节不是讲 Vue 的语法，而是让你理解 **Vite 在 Vue 项目里扮演什么角色**。  
它负责工程底座，Vue 负责视图和业务。两者分工清楚，项目才不容易乱。

### 2. 在 React 项目里

React 项目用 Vite 同样合适，尤其适合组件化开发和快速迭代。

你通常会得到这些好处：

- 本地开发更轻
- 热更新体验好
- 工程配置更集中
- 更容易按项目需求加插件

不管是 Vue 还是 React，Vite 的核心价值都不是“替你写业务”，而是让你**更少等待、更快反馈**。  
这对前端团队来说，往往比单纯“构建速度快一点”更有价值。

## 八、可复制的配置示例：最小可用 Vite 项目思路

```ts
// vite.config.ts
import { defineConfig } from 'vite'
import path from 'node:path'
import vue from '@vitejs/plugin-vue'
// import react from '@vitejs/plugin-react'

export default defineConfig({
  plugins: [
    vue(),
    // react(),
  ],
  resolve: {
    alias: {
      '@': path.resolve(__dirname, 'src')
    }
  },
  server: {
    host: '0.0.0.0',
    port: 5173,
    open: true
  },
  build: {
    outDir: 'dist',
    sourcemap: false
  }
})
```

这个配置的核心用途很简单：

- `plugins`：接入 Vue 或 React 支持
- `resolve.alias`：给 `@` 配路径别名，少写相对路径
- `server`：配置开发服务器
- `build`：配置构建输出

### 这个配置为什么这么写

- `defineConfig()`：让配置更清晰，也方便类型提示
- `path.resolve(__dirname, 'src')`：把 `@` 指向 `src`，后面写代码更顺手
- `host: '0.0.0.0'`：方便局域网访问和容器环境调试
- `port: 5173`：指定开发端口，避免冲突
- `open: true`：启动后自动打开浏览器
- `outDir: 'dist'`：构建产物输出到 `dist`
- `sourcemap: false`：生产环境默认先关掉，避免调试映射暴露

### 哪些是必需的，哪些是按需可删的

- **必需**：框架插件、基础入口结构
- **常用**：`resolve.alias`、`server.port`
- **按需**：`open`、`host`、`sourcemap`、`outDir`

也就是说，配置不是越多越好。先把最小可用链路跑通，再一点点加。

### 最小可运行项目说明

如果你要直接跑起来，通常需要先准备这些依赖：

- `vite`
- `@vitejs/plugin-vue` 或 `@vitejs/plugin-react`
- `vue` 或 `react` / `react-dom`

然后按项目类型选择一种插件：

- **Vue 项目**：启用 `vue()`，不要启用 `react()`
- **React 项目**：启用 `react()`，不要启用 `vue()`

入口文件也要对应：

#### Vue 项目入口示意

```ts
import { createApp } from 'vue'
import App from './App.vue'
import './style.css'

createApp(App).mount('#app')
```

#### React 项目入口示意

```tsx
import React from 'react'
import ReactDOM from 'react-dom/client'
import App from './App'
import './style.css'

ReactDOM.createRoot(document.getElementById('root')!).render(
  <React.StrictMode>
    <App />
  </React.StrictMode>
)
```

这两种写法都很直观：Vite 负责开发和构建，框架负责 UI 逻辑。  
记住一点：**Vite 是项目的工具底座，不是业务代码的替代品。**

## 九、常见坑：迁移和接入时最容易卡住的地方

### 1. 插件不能照搬
有些旧项目里的插件在 Vite 里不能原样使用，尤其是和构建流程强绑定的插件。别一上来就复制配置，先看它到底解决什么问题，再找 Vite 里的替代方式。

### 2. 别名没统一
项目里如果同时存在多套路径写法，迁移后很容易出现找不到模块的问题。建议先统一入口别名，再处理业务代码。

### 3. 环境变量写法不一致
传统工具和 Vite 在环境变量读取上有差别，最常见的问题就是“代码里拿不到值”。迁移时要先确认前缀、注入方式和运行环境。

### 4. Node 版本太旧
如果本地 Node 版本太老，可能会遇到依赖安装、启动或构建问题。这个坑很基础，但很常见。

### 5. 静态资源路径没处理好
图片、字体、公共目录资源这类问题，迁移时经常被忽略。页面能跑不代表资源路径完全正确，上线前一定要做完整检查。

## 十、老赵实操建议：别被“快”带偏了

### 1. 先看项目类型，再决定是否上 Vite
新项目，尤其是 Vue/React 应用，Vite 基本是优先选项。老项目先评估依赖兼容性和迁移成本，不要冲动重构。

### 2. 不要拿“启动速度”当唯一指标
启动快很爽，但真正影响效率的，还有：

- 热更新是否稳定
- 配置是否清晰
- 插件是否好找
- 构建是否可控

### 3. 配置要少而清楚
Vite 的优点之一就是默认配置已经够用。别一上来就堆很多插件和复杂参数，先把项目跑顺，再按需求加。

### 4. 先掌握“开发阶段”和“生产阶段”两套思路
很多坑都来自这点：开发时方便，不代表上线时自动正确。要知道哪些配置影响开发，哪些配置影响构建，这样排查问题才快。

### 5. 项目慢，不一定是 Vite 的锅
如果你感觉项目慢，先别急着怪构建工具。可以先按这个顺序排查：

- 是启动慢，还是页面交互慢？
- 是首屏加载慢，还是热更新慢？
- 是代码太大，还是图片、字体这类资源太重？
- 是依赖安装慢，还是构建过程慢？

很多时候，真正拖慢速度的，是业务代码、资源体积、分包策略，而不是 Vite 本身。

### 6. 最小落地动作建议
如果你现在就要在项目里试 Vite，可以按这个顺序做：

1. 先建一个新目录跑通最小项目  
2. 只保留一个框架插件和一个入口页面  
3. 先把别名、端口、启动命令配好  
4. 再接环境变量和代理  
5. 最后再补插件和构建优化

这样做的好处是，问题来了容易定位，不会一上来就把配置堆成一锅粥。

## 一、使用脚手架创建项目的基本流程

### 1. 最常见的创建方式

Vite 官方最常用的方式，是通过脚手架工具直接生成项目骨架。你可以把它理解成“帮你把基础目录、依赖、启动命令都配好”。

典型流程如下：

1. 打开终端
2. 执行创建命令
3. 选择模板
4. 输入项目名称
5. 安装依赖
6. 启动开发服务器

常见命令一般是：

```bash
npm create vite@latest
```

或者：

```bash
pnpm create vite
```

它会引导你一步一步选模板。对新手来说，这种方式最稳，不需要先手搓配置。刚接触 Vite 时，先把项目生成出来，看看默认长什么样，比死磕配置更有效。

### 2. 创建时你会遇到什么选择

创建过程中通常会让你选几项：

- 项目名称
- 框架类型：Vue、React、Svelte、Vanilla 等
- 语言类型：JavaScript 或 TypeScript

如果你是前端开发者，建议先选你最熟悉的框架。别为了“学习新东西”去选陌生组合，结果把注意力浪费在框架本身，而不是 Vite。

比如你平时写 Vue，就直接选 Vue；写 React，就直接选 React。这样你关注的重点会更纯粹：Vite 到底简化了什么，默认工程长什么样，热更新体验体现在哪。

### 3. 最小可用项目的判断标准

一个 Vite 项目是否真的创建成功，不是看命令有没有执行完，而是看这几个标准：

- 依赖安装成功
- `npm run dev` 能启动
- 浏览器能打开默认页面
- 修改文件后页面能自动更新

只要这四项成立，你就已经跨过搭建门槛了。

老赵提醒一句：**先别追求页面好看，先追求链路顺。** 只要开发、修改、刷新这一套能顺畅跑通，后面加组件、加路由、加请求都不慌。

## 二、选择 Vue、React 或其他模板时怎么选

### 1. 先按你的项目栈选，不要按“感觉”选

Vite 是工具，不是框架。它本身不决定你写 Vue 还是 React。模板的作用，是帮你把对应框架的基础工程搭好。

#### 如果你做 Vue 项目
优先选 Vue 模板。这样会得到更贴近 Vue 生态的目录结构、入口写法和推荐配置。后面在 `App.vue`、组件拆分、样式组织这些地方，都会更顺手。

#### 如果你做 React 项目
选 React 模板。这样入口、JSX、开发默认配置更符合 React 习惯，不用为了兼容模板去改一堆无关细节。

#### 如果你只是想试试 Vite
可以先选 Vanilla 模板，体会 Vite 的基础工作方式。但如果目标是实战，还是直接选要落地的框架。因为真正开发时，你最终还是要回到业务技术栈上。

### 2. 怎么判断选 JavaScript 还是 TypeScript

这个选择很现实：

- 团队项目本来就用 TypeScript：直接选 TS
- 想尽快上手、先把流程跑通：先选 JavaScript
- 后面一定会切 TS：别拖，直接用 TS

老赵的原则是：**模板不是学习负担，模板是降低试错成本的工具。** 如果团队最终会用 TypeScript，你一开始就别绕远路。反过来，如果现在只是想理解创建、启动和配置逻辑，先用 JavaScript 也完全没问题。

### 3. 新手常见误区

- 为了“高级感”选自己不熟的框架
- 模板选完后不看目录，直接删默认代码
- 混淆“Vite 模板”和“业务模板”，以为它会替你搭完整业务框架

记住：Vite 先给你的是“起跑线”，不是“终点站”。它解决的是项目启动和开发构建这一步，业务层面的目录规划、状态管理、权限控制，还得你自己搭。

## 三、项目目录结构快速认识

### 1. 创建完以后，先看哪几个文件

新建的 Vite 项目通常会有这些关键内容：

- `index.html`
- `src/`
- `src/main.js` 或 `src/main.ts`
- `src/App.vue` 或 `src/App.jsx`
- `vite.config.js` 或 `vite.config.ts`
- `package.json`

你不需要一次把每个文件背下来，但至少要知道它们分别负责什么。否则以后页面改了，却不知道是入口、组件还是配置出了问题。

### 2. 目录结构怎么看才高效

#### `index.html`
这是入口页面。很多传统前端项目习惯把 HTML 放在 `public` 里，但 Vite 的思路更直接：**HTML 本身就是入口。**

这意味着你不只是写页面内容，还要理解页面是怎么把脚本和样式接进来的。后面理解 Vite 的工作机制时，这一点很关键。

#### `src/`
这里放业务代码。大部分页面组件、样式、逻辑，都从这里开始。简单说，真正写业务的地方，基本都在这里。

#### `main`
这是程序入口文件，负责把框架实例挂到页面上。可以理解成“启动应用的第一脚”。如果这个文件挂载错了，页面就不可能正常出来。

#### `App`
这是默认根组件。项目刚创建时，它通常负责显示第一页内容。后面你会慢慢把它拆成页面组件、公共组件，而不是把所有东西堆在这里。

#### `vite.config`
这是 Vite 的配置入口。后面会在这里配置代理、别名、插件、构建规则等。它不一定一开始就改，但你得知道它的位置。

#### `package.json`
这里记录依赖和脚本命令，最重要的是 `dev`、`build`、`preview`。以后跑项目、打包、预览产物，基本都绕不开它。

### 3. 先别急着删文件

有些人创建完项目后，第一件事就是把默认代码删光。老赵不建议这样开始。

正确做法是：

1. 先启动
2. 看默认页面
3. 明白入口关系
4. 再逐步替换成自己的页面

这样你才能知道自己改的是哪一层。删得太快，后面页面不显示了，连问题出在哪都不好找。

## 四、启动开发服务器并查看默认页面

### 1. 启动命令怎么用

项目创建好之后，进入目录，执行：

```bash
npm install
npm run dev
```

如果你用的是 pnpm：

```bash
pnpm install
pnpm dev
```

启动后，终端一般会告诉你本地地址，例如：

```bash
http://localhost:5173
```

打开浏览器访问这个地址，就能看到默认页面。

### 2. 这个页面说明了什么

默认页面不只是“欢迎页”，它在告诉你：

- 开发服务器已经启动
- 入口文件已经生效
- 框架模板已经接上
- 热更新链路大概率是通的

如果你改一下 `src/App` 里的内容，页面能立刻更新，就说明你已经进入 Vite 的正常工作状态。这个阶段不要小看，它是后面理解所有配置的基础。

### 3. 热更新体验是什么样

你改代码，页面不需要手动刷新，这就是 Vite 带来的开发体验之一。它不是简单的自动刷新，而是尽量只更新变动部分，让你写代码时更顺手。

判断热更新是否正常，可以看这几点：

- 保存文件后页面有没有变化
- 控制台有没有报错
- 改样式是否能立即生效
- 改组件内容是否即时显示

如果都顺畅，说明开发环境基本没问题。反过来，如果改了不生效，先检查文件路径、组件导入、终端报错和浏览器控制台，不要先怀疑 Vite。

## 五、第一个可复制的初始化配置示例

这一节给你一个够用、能直接放进项目里的最小配置。先别追求花哨，先把“能用、清楚、好维护”做到位。

### 1. `vite.config.ts`

```ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import path from 'node:path'

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: {
      '@': path.resolve(__dirname, 'src')
    }
  },
  server: {
    host: '0.0.0.0',
    port: 5173,
    open: true
  }
})
```

### 2. 这份配置做了什么

- `plugins: [vue()]`：告诉 Vite 这个项目要支持 Vue
- `alias`：让你可以用 `@/components` 代替很长的相对路径
- `host: '0.0.0.0'`：允许局域网访问，方便真机测试
- `port: 5173`：固定开发端口，避免每次变来变去
- `open: true`：启动后自动打开浏览器

这几个配置项已经能覆盖大部分新项目初始化阶段的需求。你不需要一开始就把所有服务器参数都配满，先把最常用的用顺。

### 3. 配置项先记住这几个就够

刚上手时，不要一股脑把所有配置都加上。先掌握最常用的：

- `plugins`
- `resolve.alias`
- `server.host`
- `server.port`
- `server.open`

这些配置足够你搭一个像样的开发环境了。后面学代理、环境变量、多环境构建时，也是在这个基础上继续加。

## 六、如何在 Vue 中使用 Vite

### 1. Vue 项目里最基本的关系

Vue + Vite 的组合很常见。创建后通常会有：

- `App.vue`：根组件

这份清单很实用。每次换机器、换项目、改配置后，都可以快速扫一遍，避免把时间浪费在低级错误上。

# 第4章：开发服务器与热更新，Vite 为什么这么快

## 开篇引入：快，不只是启动快

很多人第一次用 Vite，第一反应都是：**怎么一下子就起来了？**  
再点保存，页面几乎立刻更新，改一个组件也不用整站刷新。

但 Vite 的“快”不是魔法，它靠的是一套很朴素的思路：

- 开发时尽量**不做重活**
- 浏览器要什么，就**现取现用**
- 依赖这种“很少变”的东西，提前处理好
- 代码改动后，只更新**真正变了的那一小块**

它不是靠“更拼命地构建”，而是靠“**少做无用功**”。

这一章，我们把 Vite 的开发服务器、热更新、依赖预构建讲清楚。你不一定要记住所有内部细节，但要知道它在干什么、为什么快、出问题怎么排。

---

## 一、开发服务器到底在干什么？

### 1.1 开发服务器的作用是什么？

执行 `vite` 或 `npm run dev` 后启动的本地服务，主要做三件事：

1. 给浏览器提供页面入口  
2. 按需处理模块请求  
3. 监听文件变化，推动页面更新  

和传统“先打包，再运行”不同，Vite 开发时更像一个**按需供应者**：浏览器请求哪个模块，它就处理哪个模块并返回。

### 1.2 Vite 的开发服务器为什么快？

传统工具在开发时通常先把整个项目打成一个大包，项目越大，启动和更新就越慢。

Vite 的做法更直接：

- 启动时先把服务器跑起来
- 首屏入口先返回
- 其余模块按浏览器请求逐个加载
- 只有少数依赖提前预处理

所以你看到的是：

- 启动快
- 首次进入快
- 改动反馈快

关键不是“更强的算力”，而是“更少的工作量”。

### 1.3 开发服务器的工作方式，按流程看

简单理解成下面这个流程：

1. 浏览器请求 `index.html`
2. Vite 返回 HTML，并注入入口脚本
3. 浏览器继续请求入口模块
4. Vite 按需处理源码后返回
5. 文件变化时，Vite 通过 WebSocket 通知浏览器更新

你可以把它理解成：**浏览器是主动消费者，Vite 是按需服务员**。  
这也是 Vite 开发体验顺手的第一层原因。

---

## 二、热更新 HMR 到底是什么？

### 2.1 HMR 解决的是什么问题？

HMR 就是热更新机制，可以先记成一句话：

> **代码改了，不用整页刷新，也不用重启整个应用，只更新变化的部分。**

它的价值很直接：

- 表单内容不容易丢
- 页面状态尽量保留
- 调试效率高
- 组件改动反馈更快

### 2.2 Vite 的热更新是怎么工作的？

热更新不是“自动刷新页面”，而是尽量做**局部更新**。

基本逻辑是：

1. 你修改了某个文件
2. Vite 监听到变化
3. 它分析这个文件依赖了谁、被谁引用
4. 能局部更新就局部更新
5. 不行再退回到整页刷新

HMR 依赖的是**模块关系**。  
如果代码边界清楚，组件独立，热更新通常就顺；如果状态散得到处都是，更新就容易失控。

### 2.3 开发时你会感受到什么？

热更新体验通常有三种层级：

- **组件级更新**：只刷新改动的组件，状态尽量保留
- **模块级更新**：某个 JS/CSS 模块更新了，浏览器局部替换
- **整页刷新**：热更新链路断了，只能全量刷新

真正好用的 HMR，不是“永不刷新”，而是“**能局部就不全量**”。

比如你改的是 Vue 组件里的模板或样式，体验通常很顺；如果你改的是影响全局初始化的逻辑文件，整页刷新也很常见。

### 2.4 常见误区

很多人以为“Vite 快 = HMR 永远精准”。其实不是。

以下情况都可能让更新退回到整页刷新：

- 改了全局状态文件
- 组件外部共享变量太多
- 某些插件改写了模块关系
- CSS 能热更，JS 却触发整页刷新

所以，HMR 不是万能的，关键是理解它依赖的是**模块边界**。  
状态尽量放在清楚的边界里，别到处散。

---

## 三、依赖预构建：为什么它能把“慢依赖”提前处理掉？

### 3.1 什么叫依赖预构建？

开发阶段，Vite 会把一些第三方依赖先做一次预处理，这一步叫**依赖预构建**。

它主要解决两类问题：

- 依赖太多，浏览器一次次加载很慢
- 某些依赖不是浏览器友好的模块格式，直接用会出问题

你可以把它理解成：  
**把容易拖慢开发体验的第三方包，先整理成更适合开发服务器使用的形式。**

### 3.2 预构建具体做了什么？

通常会有这些作用：

- 合并处理多个依赖，减少请求压力
- 处理 CommonJS、UMD 等不够浏览器原生的格式
- 提前扫描依赖关系，减少首次访问卡顿
- 缓解深层依赖带来的加载问题

它的核心价值是：**把不该在开发时反复处理的东西提前做掉。**

### 3.3 为什么它对开发体验重要？

如果没有这一步，浏览器要面对很多碎片化请求，兼容问题也更明显，结果就是：

- 页面打开慢
- 控制台报错多
- 第一次运行体验差

### 3.4 什么时候会遇到预构建相关问题？

常见情况有：

- 新增依赖后，页面异常但重新启动就好了
- 某个包升级后，开发环境报错
- 依赖缓存没更新，导致改动不生效

这时先别急着怀疑业务代码，优先考虑是不是预构建缓存的问题。  
换了依赖、升级了包、改了引用方式后表现不对，先重启开发服务往往最省事。

---

## 四、更新不生效，通常卡在哪？

### 4.1 为什么你保存了文件，页面却没反应？

排查顺序建议如下：

#### 第一步：先看最简单的
- 文件是否真的保存成功
- 编辑器是否保存到了正确路径
- 当前页面是否引用了这个文件

#### 第二步：再看开发服务器
- 是否启动的是当前项目
- 是否改了配置后忘了重启
- 是否端口、代理或插件影响了更新链路

#### 第三步：再看热更新边界
- 这个改动是不是超出了 HMR 可控范围
- 是组件内部变化，还是全局状态变化
- 是否被第三方库包了一层，导致更新链路断掉

很多时候，“没更新”不是没变化，而是你改的地方不在当前页面看到的那条链路上。

### 4.2 更系统的排查步骤

如果你想快点定位问题，可以按下面这套顺序来：

1. **确认文件确实保存了**
2. **确认终端里 Vite 有没有收到文件变化**
3. **确认浏览器控制台有没有 HMR 报错**
4. **确认页面是不是被缓存、状态或旧数据盖住了**
5. **确认是不是需要重启开发服务**

这套顺序的好处是，先看“有没有变化”，再看“变化有没有传过去”，最后才看“业务逻辑有没有挡住变化”。  
别一上来就怀疑框架，很多问题其实是配置和缓存。

### 4.3 常见原因清单

高频坑包括：

- 修改了 `.env` 但没重启开发服务
- 改了 Vite 配置却没重新启动
- 缓存没清理，导致旧依赖还在生效
- 某些插件拦截了模块更新
- 组件中有全局单例状态，热更新后状态没按预期恢复
- CSS 和 JS 的更新行为不同，误以为都该完全无感

尤其要注意 `.env` 和 `vite.config.ts`，它们通常不是改完就能自动生效的，很多时候需要重启。

### 4.4 先定位，再处理

可以按这个顺序排：

1. **确认是否真的触发了文件变化**
2. **确认 Vite 是否收到变化**
3. **确认 HMR 是否发送到浏览器**
4. **确认浏览器是否接受更新**
5. **确认是不是业务代码逻辑导致的“看起来没更新”**

很多时候不是 Vite 没更新，而是页面状态、缓存逻辑或者数据层把变化盖住了。先看终端日志、浏览器控制台，再看页面数据来源，通常能很快缩小范围。

## 五、开发阶段的配置怎么写，才能更顺手？

### 5.1 可复制配置示例

```ts
// vite.config.ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  server: {
    host: '0.0.0.0',
    port: 5173,
    open: true,
    strictPort: true,
    proxy: {
      '/api': {
        target: 'http://localhost:3000',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, '')
      }
    }
  },
  optimizeDeps: {
    include: ['axios']
  }
})
```

### 5.2 这几个配置项分别干什么？

- `host: '0.0.0.0'`：局域网设备可访问
- `port: 5173`：固定开发端口，方便联调
- `open: true`：启动后自动打开浏览器
- `strictPort: true`：端口占用时直接报错，避免悄悄换端口
- `proxy`：开发环境代理接口，避免跨域
- `optimizeDeps.include`：把常用依赖提前纳入预构建

### 5.3 这份配置会影响什么行为？

这份配置主要影响开发阶段的三个体验点：

- **访问方式**：本机、局域网都能访问
- **接口联调**：前端请求自动转发到后端
- **启动和依赖处理**：常用依赖提前预构建，减少首次卡顿

如果你在 Vue 项目里起步，这份配置能直接用；如果是 React 项目，写法类似，只是插件换成 React 对应插件就行。  
开发服务器这块，思路是通的，框架只是挂载方式不同。

### 5.4 代理配置为什么常配在开发阶段？

前端项目经常遇到接口跨域。开发时直接让浏览器请求后端，通常会撞到同源限制。Vite 代理就是常用解法。

开发时：

- 前端请求 `/api/user`
- Vite 转发到 `http://localhost:3000/user`
- 浏览器看起来像同源请求
- 实际由开发服务器帮你转发

这比手动改接口地址更稳，也更贴近真实项目流程。

---

## 六、Vue 和 React 项目里，Vite 怎么用？

### 6.1 在 Vue 中使用 Vite

Vue 项目里，Vite 基本是默认答案之一。最常见的起步方式：

```bash
npm create vite@latest my-vue-app
```

然后选择 Vue 模板，安装依赖并启动。

如果是已有 Vue 项目，核心就是确保：

- 安装了 `vite`
- 配置了 `@vitejs/plugin-vue`
- `index.html` 的入口符合 Vite 习惯
- `src/main.ts` 或 `src/main.js` 正常挂载应用

迁移时最常见的变化不是业务代码，而是入口方式和构建方式。到了 Vite 后，要更习惯从 `index.html` 看项目入口。

### 6.2 在 React 中使用 Vite

React 项目同理：

```bash
npm create vite@latest my-react-app
```

然后选择 React 模板，常见配置包括：

- `@vitejs/plugin-react`
- `main.tsx` 或 `main.jsx`
- JSX/TSX 语法支持
- 开发阶段热更新体验

React 场景下，Vite 的热更新体验也很直接：改组件、保存、页面局部更新，反馈通常很快。

### 6.3 Vue 和 React 使用 Vite 的共同点

不管是 Vue 还是 React，你都可以把 Vite 理解成：

- 项目启动器
- 开发服务器
- 依赖处理器
- 构建工具入口

框架不同，Vite 的职责类似；差别主要在插件和模板。

## 七、老赵实操建议：怎么把开发体验真正用好？

### 7.1 别一上来就堆复杂配置

先把这些基础跑通：

- 能正常启动
- 页面能打开
- 热更新正常
- 接口代理正常
- 环境变量可读
- 构建能成功

基础不稳，后面所有配置都是空中楼阁。先用最少配置跑通，再一点点加，问题更容易定位。

### 7.2 修改这些东西后，优先重启

以下内容改动后，建议直接重启开发服务：

- `.env` 文件
- `vite.config.ts`
- 依赖版本
- 插件配置
- 代理规则

不要指望热更新把配置本身也处理掉，很多配置类文件本来就是启动时读取一次。

### 7.3 遇到更新不生效，先做四步

1. 看控制台有没有报错  
2. 看终端里 Vite 有没有监听到文件变化  
3. 关掉缓存、重启服务，再验证一次  
4. 还是不行，就对照模块边界，看看是不是全局状态或插件把更新挡住了  

这几步能解决很大一部分“明明保存了却没变化”的问题。

### 7.4 开发阶段优先关注两件事

- **模块边界**：谁改了会影响谁
- **依赖缓存**：哪些东西需要重启才能刷新

把这两件事搞清楚，Vite 的开发体验就会稳定很多。

---

## 结尾小结：快，是一套策略，不是一个按钮

这一章你要记住的，不是“Vite 很快”这句结论，而是它为什么快：

- 开发服务器按需提供模块
- 热更新只更新变化部分
- 依赖预构建提前处理慢依赖
- 配置尽量围绕开发效率展开

如果你是 Vue 或 React 开发者，现在就可以把本章的配置示例加到项目里试一下，重点观察三件事：

1. 启动速度  
2. 保存后的更新速度  
3. 接口代理是否顺畅  

**老赵建议你把“改一行代码，立刻看结果”当成日常标准。**  
只要你把 Vite 的开发服务器、HMR、预构建这三件事搞明白，后面学配置、插件、构建和环境区分都会顺很多。

# 第5章：配置文件基础——Vite 配置怎么写才顺手

## 开篇引入：先把配置文件看明白

很多人第一次接触 Vite，会觉得它很轻，装上就能跑。  
但真到改项目、接接口、加别名、分环境打包时，还是得回到 `vite.config.js` 或 `vite.config.ts`。

这章只讲一件事：**怎么把 Vite 配置写得清楚、好维护，还方便以后扩展。**

老赵的经验是：配置文件不是“越多越专业”，而是“越清楚越省事”。你要把它当成项目的总开关。项目跑得稳不稳，很多时候不在代码，而在配置有没有理顺。

Vite 的配置不难，难的是知道哪些该默认，哪些该改，哪些别乱碰。真正顺手的配置，往往只有三个字：**够用、清晰、能扩展。**

---

## 一、`vite.config.js / ts` 的基本结构：配置文件到底长什么样？

Vite 的配置文件通常放在项目根目录，常见名字是：

- `vite.config.js`
- `vite.config.ts`

如果项目偏 TypeScript，或者你想要更好的类型提示，用 `.ts` 更顺手。

### 1. 最基础的结构

一个最小可用的配置文件，大概长这样：

```ts
import { defineConfig } from 'vite'

export default defineConfig({
  // 配置项写在这里
})
```

不用 `defineConfig` 也能写，但老赵建议默认就用它。原因很简单：  
**它能让编辑器更好识别配置结构，补全更准，类型提示更清楚。**

### 2. 为什么推荐 `vite.config.ts`

如果项目已经在用 TypeScript，直接用 `vite.config.ts` 往往更舒服：

- 配置项有提示
- 写别名、插件参数时少出错
- 后面拆分配置更自然

注意：**TypeScript 配置文件不代表业务代码也必须是 TS。**  
它只是让“配置”这块更稳一点。

### 3. 一个清爽的文件开头

建议你把配置文件开头写得干净一点，先把基础能力准备好，再往下加内容：

```ts
import { defineConfig } from 'vite'
import path from 'path'
```

先把导入写清楚，后面看配置时会更容易分清：哪些是 Vite 自带能力，哪些是额外逻辑。

---

## 二、`defineConfig` 的作用和常见写法：为什么它值得保留？

`defineConfig` 不是摆设，而是很实用的入口。

### 1. 它解决什么问题？

它主要做两件事：

- 让配置对象更容易被识别
- 提升编辑器提示和类型体验

这样你写 `server`、`build`、`resolve` 时，少靠记忆硬写，少拼错字段。

### 2. 常见写法

最常用的是直接传对象：

```ts
import { defineConfig } from 'vite'

export default defineConfig({
  server: {
    port: 3000
  }
})
```

如果需要根据环境做判断，也可以写成函数：

```ts
import { defineConfig } from 'vite'

export default defineConfig(({ mode }) => {
  return {
    server: {
      port: mode === 'development' ? 3000 : 4173
    }
  }
})
```

这种写法适合区分开发/生产、读取不同环境变量、动态拼接配置。

### 3. 什么时候用函数写法？

当你需要：

- 区分开发/生产
- 按模式读取环境变量
- 动态拼接配置

这时候函数写法更方便。  
但别为了“看起来高级”而上函数。**能用对象就先用对象，能简单就别复杂。**

---

## 三、常用配置项怎么写：`root`、`base`、`server`、`build`、`resolve`

这一节是重点。你以后改项目，80% 的配置调整基本都绕不开这几个字段。

### 1. `root`：项目入口目录在哪？

`root` 用来指定项目根目录。默认情况下，Vite 认为当前目录就是根目录。  
如果前端代码不在根目录，而是在子目录里，`root` 才有用。

```ts
export default defineConfig({
  root: 'src'
})
```

老赵提醒你：**除非目录结构确实特殊，不要随便改 `root`。**  
一改根目录，静态资源、HTML 路径、别名、构建输出都会受影响。

### 2. `base`：静态资源部署路径前缀

`base` 决定构建后资源引用的前缀。项目部署在根路径还是子路径，这个字段要配对。

```ts
export default defineConfig({
  base: '/'
})
```

部署在子目录时：

```ts
export default defineConfig({
  base: '/admin/'
})
```

判断标准很简单：

- 部署在域名根下，用 `/`
- 部署在子路径下，就写对应路径

这个字段不对，开发时可能没事，上线后资源就可能 404。

### 3. `server`：开发服务器怎么跑？

`server` 是开发阶段最常改的配置，常见内容有：

- `port`：端口
- `host`：监听地址
- `open`：启动后自动打开浏览器
- `proxy`：接口代理

例如：

```ts
export default defineConfig({
  server: {
    port: 5173,
    host: '0.0.0.0',
    open: true
  }
})
```

### 什么时候要改 `host`？

如果你想让局域网设备访问开发环境，比如手机真机调试，就要把 `host` 配成 `0.0.0.0`。  
默认只监听本机时，外部设备访问不到。

### 4. `build`：打包行为怎么控制？

`build` 是生产构建相关配置，常见会改这些：

- `outDir`：输出目录
- `assetsDir`：静态资源目录
- `minify`：是否压缩
- `sourcemap`：是否生成 sourcemap
- `rollupOptions`：更细的打包控制

示例：

```ts
export default defineConfig({
  build: {
    outDir: 'dist',
    assetsDir: 'assets',
    sourcemap: false
  }
})
```

实操上，线上排查问题时可以临时开 `sourcemap`，想改输出目录就调 `outDir`，需要更细控制入口、分包规则时再碰 `rollupOptions`。  
**不要一上来就把 `build` 写得很复杂。**

### 5. `resolve`：路径别名和模块解析

`resolve` 最常见的用途就是配别名，前端项目里通常把 `@` 指向 `src`。

```ts
import path from 'path'

export default defineConfig({
  resolve: {
    alias: {
      '@': path.resolve(__dirname, './src')
    }
  }
})
```

代码里就能这样导入：

```ts
import UserCard from '@/components/UserCard.vue'
```

项目一大，`../../../` 这种相对路径会很难读。  
别名的作用就是让路径更直观、更稳定，也方便团队统一写法。

---

## 四、如何拆分配置：让文件更清楚，不要一坨堆到底

项目小的时候，一个配置文件就够了。项目大了，插件、别名、代理、环境判断一起上，配置就容易乱。

### 1. 拆分的目标

拆分不是为了“看起来专业”，而是为了：  
**一眼知道哪里管什么。**

常见拆法：

- 基础配置：公共项
- 开发配置：`server`、代理
- 生产配置：`build`
- 插件配置：单独封装

### 2. 一个比较顺手的拆法

```ts
// vite.config.ts
import { defineConfig, mergeConfig } from 'vite'
import baseConfig from './build/vite.base'
import devConfig from './build/vite.dev'
import prodConfig from './build/vite.prod'

export default defineConfig(({ mode }) => {
  const isDev = mode === 'development'
  return mergeConfig(baseConfig, isDev ? devConfig : prodConfig)
})
```

分别放：

- `build/vite.base.ts`
- `build/vite.dev.ts`
- `build/vite.prod.ts`

这样公共项、开发项、生产项各管各的，查找和维护都更直接。

### 3. 一个简单的分层思路

你可以把配置理解成三层：

1. **基础层**：别名、通用插件、通用路径
2. **环境层**：开发、测试、生产的差异
3. **业务层**：项目自己的特殊要求，比如接口代理、构建路径

这么拆，后面加配置不会乱。

### 4. 什么时候该拆？

满足下面任意一条，就可以考虑拆：

- 配置文件超过一屏还在增长
- 开发和生产差异明显
- 插件越来越多
- 团队多人维护，希望一眼能看懂

### 5. 拆分的注意点

别拆太碎。  
配置项本来就不多，硬拆成五六个文件，只会更难找。  
**配置拆分的标准，是可维护，不是文件数量多。**

---

## 五、把“基础配置”和“环境配置”分开：这是最实用的做法

这一点很重要，尤其适合已经开始做真实项目的团队。

### 1. 为什么要分层？

因为很多配置并不是一直一样的。比如：

- 开发环境需要代理
- 生产环境可能不需要代理
- 开发环境可以开 sourcemap
- 生产环境可能要关掉 sourcemap

这些差异如果全写在一个对象里，后面很容易看花。

### 2. 一个更贴近实战的组织方式

```ts
// vite.config.ts
import { defineConfig, mergeConfig } from 'vite'
import baseConfig from './config/vite.base'
import devConfig from './config/vite.dev'
import prodConfig from './config/vite.prod'

export default defineConfig(({ mode }) => {
  if (mode === 'development') {
    return mergeConfig(baseConfig, devConfig)
  }
  return mergeConfig(baseConfig, prodConfig)
})
```

基础配置里放公共内容：

```ts
// config/vite.base.ts
import path from 'path'

export default {
  resolve: {
    alias: {
      '@': path.resolve(__dirname, '../src')
    }
  }
}
```

开发配置里放开发专属内容：

```ts
// config/vite.dev.ts
export default {
  server: {
    port: 5173,
    open: true,
    host: '0.0.0.0'
  }
}
```

生产配置里放生产专属内容：

```ts
// config/vite.prod.ts
export default {
  build: {
    outDir: 'dist',
    sourcemap: false
  }
}
```

### 3. 这么拆的好处

- 公共逻辑和环境逻辑分开
- 以后改代理、端口、打包策略更直观
- 新同学接手时，不用从头读一大坨配置

老赵建议：**项目一旦开始有团队协作，分层配置就很值。**

---

## 六、一份可直接复制的基础配置模板：先跑起来，再按需改

下面这份配置，适合 Vue 或 React 项目直接作为起点使用。

```ts
import { defineConfig } from 'vite'
import path from 'path'

export default defineConfig(({ mode }) => {
  const isDev = mode === 'development'

  return {
    base: '/',
    resolve: {
      alias: {
        '@': path.resolve(__dirname, './src')
      }
    },
    server: {
      host: '0.0.0.0',
      port: 5173,
      open: true,
      proxy: {
        '/api': {
          target: 'http://localhost:3000',
          changeOrigin: true,
          rewrite: (p) => p.replace(/^\/api/, '')
        }
      }
    },
    build: {
      outDir: 'dist',
      assetsDir: 'assets',
      sourcemap: isDev,
      minify: 'esbuild'
    }
  }
})
```

### 这份模板怎么用？

- `base`：默认部署到根路径
- `alias`：统一用 `@` 指向 `src`
- `server.host`：支持局域网访问
- `proxy`：开发环境转发接口
- `build.sourcemap`：按模式控制调试信息

### 复制后先检查这几件事

1. `src` 目录是不是你的前端源码目录  
2. `proxy.target` 是不是你的后端地址  
3. 项目最终是不是部署在根路径  
4. 端口 `5173` 有没有被占用  
5. `outDir` 是否和你现有发布流程冲突  

这份模板不追求最强，只追求**稳、常用、好改**。  
拿到新项目，先贴进去，再按实际情况删改。没有接口代理就去掉 `proxy`，部署在子路径就改 `base`。

---

## 七、Vue 和 React 项目里，这份配置怎么落地？

### 1. 在 Vue 中使用 Vite

Vue 项目通常配合官方插件使用：

```ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import path from 'path'

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: {
      '@': path.resolve(__dirname, './src')
    }
  }
})
```

Vue 项目里最常见的做法，就是先把 `plugins`、`alias`、`server` 配好，再按需要补 `base` 和 `build`。

### 2. 在 React 中使用 Vite

React 项目一般用：

```ts
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import path from 'path'

export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      '@': path.resolve(__dirname, './src')
    }
  }
})
```

### 3. 关键点

Vue 和 React 的配置主干其实一样，差别主要在插件：

- Vue：`@vitejs/plugin-vue`
- React：`@vitejs/plugin-react`

也就是说，**Vite 配置的骨架相同，框架插件不同。**

---

## 八、老赵实操建议：先保守，后扩展

### 1. 先只配必要项

新项目别一上来把所有配置都写满。先配：

- `resolve.alias`
- `server.proxy`
- `build` 基本项

够用就行。

### 2. 代理配置别当万能转发

代理只解决开发环境跨域问题，不是后端接口设计的替代品。  
它适合本地联调，不适合拿来替代线上网关。

### 3. 别滥用 `root`

大部分项目默认根目录就够了。`root` 一改，路径、静态资源、构建目录都会连带变化，排错更费劲。

### 4. 配置文件配注释

尤其团队项目，像 `base`、`proxy`、`outDir` 这些字段，建议写一句注释，避免后面的人不知道为什么这么配。

```ts
// 部署在子路径时要改这里
base: '/admin/'
```

### 5. 出问题先看这几个点

如果配置改完项目不对劲，先按这个顺序查：

1. 端口有没有冲突  
2. `base` 是否和部署路径一致  
3. `alias` 路径有没有写错  
4. `proxy` 的 `target` 能不能访问  
5. 生产环境有没有把 `sourcemap`、`outDir` 搞乱  

很多问题不是 Vite 难，而是配置改得太散，自己把自己绕进去了。

---

## 结尾小结：这一章你至少要带走什么？

这章最重要的，不是背字段，而是形成配置思路：

1. `vite.config.js/ts` 是项目配置中心  
2. `defineConfig` 让配置更清楚、更好写  
3. `root`、`base`、`server`、`build`、`resolve` 是最常用的基础项  
4. 配置可以拆，但不要拆乱  
5. 基础配置和环境配置分开，最适合真实项目  
6. Vue 和 React 主要差在插件，配置骨架基本一致  

如果你现在手里已经有一个 Vite 项目，建议立刻做三件事：

- 检查 `alias` 有没有统一
- 看看 `server.proxy` 是否满足联调
- 确认 `base` 是否符合部署路径

**老赵实操建议：先把这份基础模板贴到项目里，再按实际需求删改。别追求一开始就完美，先让配置服务项目，再谈优化。**

# 第6章：环境变量与多环境配置，开发、测试、生产怎么区分

## 开篇引入：为什么环境变量是 Vite 项目里的“安全阀”

前端项目最常见的问题，就是同一套代码要面对开发、测试、生产三种场景：本地连本地接口，联调连测试服务器，上线又切正式环境。  
如果把这些信息写死在代码里，项目很快就会乱：

- 开发时改得快，发布时忘了改；
- 地址散在多个文件里，排查困难；
- 测试和生产配置混在一起，切换容易出错。

Vite 的思路很直接：**把会变的东西从代码里拿出来，放到环境变量里管理**。代码只管逻辑，配置按环境走，切换更稳。

你可以把环境变量理解成项目里的“安全阀”：

- 平时开发，走开发配置；
- 联调时，切到测试配置；
- 上线前，换成生产配置；
- 代码主体尽量不动，只换配置。

这一章讲清楚 Vite 里环境变量怎么放、怎么读、怎么区分不同环境，以及最容易踩的坑。核心就是一条链路：**文件怎么命名、怎么加载、怎么读取、怎么切环境、怎么排查**。

---

## 一、环境变量文件的命名规则和加载方式

### 1.1 Vite 默认认哪些环境文件

Vite 会按当前模式自动加载对应的 `.env` 文件，常见的有：

- `.env`：所有环境都会加载
- `.env.development`：开发环境
- `.env.test`：测试环境
- `.env.production`：生产环境

如果还有预发、灰度，也可以继续加，比如：

- `.env.staging`

加载顺序可以记成一句话：**先公共，后覆盖**。  
也就是先读 `.env`，再读当前模式对应文件，同名变量以后者为准。

常见做法是：

- 公共配置放 `.env`
- 环境差异放 `.env.development`、`.env.production` 这类文件

### 1.2 加载顺序怎么理解

实际项目里不用死记规则，只记一个原则：

- **通用配置放公共文件**
- **环境差异放对应模式文件**
- **同名变量以后加载的为准**

例如：

```env
# .env
VITE_APP_NAME=我的项目
VITE_REQUEST_TIMEOUT=8000
```

```env
# .env.development
VITE_API_BASE_URL=/api
VITE_DEBUG=true
```

```env
# .env.production
VITE_API_BASE_URL=https://api.example.com
VITE_DEBUG=false
```

这样配置后：

- 开发时接口走 `/api`
- 生产时切到正式地址
- 公共信息不用重复写

### 1.3 一条完整链路怎么跑

这件事连起来看就很清楚：

1. 启动项目时，Vite 先知道当前是什么 mode；
2. 然后去读对应的环境文件；
3. 再把符合规则的变量暴露给前端；
4. 代码里通过 `import.meta.env` 读取；
5. 请求封装、页面标题、调试开关都可以用同一套配置来源。

也就是说，环境变量不是单独一块内容，它是**从启动到运行的一条链路**。  
链路清楚了，后面排查问题也会快很多。

## 二、如何读取不同环境变量并在代码里使用

### 2.1 先记住一个硬规则：必须以 `VITE_` 开头

Vite 里有一条很重要的规则：  
**默认只有以 `VITE_` 开头的变量，才会暴露给前端代码使用。**

也就是说，`.env` 里写了不代表前端能直接读到。Vite 这么做，是为了避免把不该暴露的配置带到浏览器里。

正确写法：

```env
VITE_API_BASE_URL=/api
VITE_APP_NAME=前端工具箱
```

前端读取：

```ts
const baseUrl = import.meta.env.VITE_API_BASE_URL
const appName = import.meta.env.VITE_APP_NAME
```

错误写法：

```env
API_BASE_URL=/api
```

这种变量默认读不到。

### 2.2 在代码里怎么用

Vite 通过 `import.meta.env` 提供统一入口。常见内置字段有：

- `import.meta.env.MODE`：当前模式
- `import.meta.env.DEV`：是否开发环境
- `import.meta.env.PROD`：是否生产环境
- `import.meta.env.BASE_URL`：基础路径
- `import.meta.env.VITE_XXX`：自定义变量

示例：

```ts
if (import.meta.env.DEV) {
  console.log('当前是开发环境')
}

console.log('接口地址：', import.meta.env.VITE_API_BASE_URL)
```

再比如：

```ts
const isDebug = import.meta.env.VITE_DEBUG === 'true'

if (isDebug) {
  console.log('开启调试模式')
}
```

注意环境变量通常是字符串，不要直接当布尔值用，最好自己转换一下。

### 2.3 开发、测试、生产在代码里的区别

这里别只盯着“文件名”，更重要的是“场景”。

- **开发环境**：本地开发，页面热更新频繁，接口通常走代理，方便调试；
- **测试环境**：联调和验收用，接口指向测试后端，配置要尽量接近线上；
- **生产环境**：正式上线，接口指向正式地址，调试输出要关掉，配置以稳定为主。

代码里可以这样判断：

```ts
if (import.meta.env.DEV) {
  console.log('开发环境才显示的日志')
}

if (import.meta.env.PROD) {
  // 生产环境才执行的逻辑
}
```

如果你需要更细的区分，建议通过 `MODE` 再做一层判断：

```ts
const mode = import.meta.env.MODE

if (mode === 'test') {
  console.log('当前是测试模式')
}
```

### 2.4 实战建议：别把环境变量当成业务逻辑开关

环境变量更适合放“配置”，不是放复杂业务规则。

适合放的内容：

- 接口地址
- 请求超时时间
- 调试开关
- 应用名称
- 基础路径
- 是否启用 mock

不适合放的内容：

- 数据库密码
- 私钥
- 真正敏感的授权密钥
- 复杂且频繁变动的业务规则

记住一句话：**前端环境变量是配置，不是保险箱。**

## 三、开发、测试、生产环境如何区分

### 3.1 先分清“模式”和“环境”

很多人会把“模式”和“环境”混着说，其实不是一回事。

- **模式（mode）**：Vite 用来决定加载哪个 `.env.xxx` 文件
- **环境场景**：你实际在什么地方用，比如开发、测试、生产

可以简单理解为：

- 模式是“配置选择器”
- 环境是“实际使用场景”

常见用法：

- 本地开发：`vite`
- 生产构建：`vite build`
- 指定测试模式：`vite --mode test`

### 3.2 怎么设计三套环境

比较稳妥的拆法如下：

#### 开发环境
- 接口走本地代理
- 开启调试日志
- 保留热更新
- 出错时方便排查

#### 测试环境
- 接口走测试服务器
- 关闭过多调试输出
- 用于联调和验收
- 配置尽量接近线上

#### 生产环境
- 接口走正式服务器
- 关闭无关日志
- 配合压缩、缓存、分包策略
- 以稳定和性能为主

### 3.3 推荐的文件组织

建议这样放：

```bash
.env
.env.development
.env.test
.env.production
```

如果还有预发环境，可以再加：

```bash
.env.staging
```

### 3.4 不同环境文件里放什么

这一点要讲清楚，不然容易乱。

#### `.env`
放通用值，比如：

- 项目名称
- 超时时间默认值
- 统一的功能开关默认值

#### `.env.development`
放开发阶段专用内容，比如：

- 本地代理路径
- 开发调试开关
- 本地 mock 开关

#### `.env.test`
放测试联调内容，比如：

- 测试接口地址
- 测试环境专用开关
- 接近线上但允许调试的参数

#### `.env.production`
放正式上线内容，比如：

- 生产接口地址
- 生产环境关闭调试
- 线上可接受的默认值

### 3.5 判断标准：什么时候该拆环境

不是每个值都必须拆成多份，但满足下面任意一条，基本就该分开：

- 接口地址不同
- 调试开关不同
- 静态资源基础路径不同
- 第三方平台配置不同
- 构建产物策略不同

如果只是临时改一个值，可以先放公共文件；  
如果这个值长期随环境变化，就单独放到对应文件里。

## 四、常见踩坑：变量前缀、打包后不可变等问题

### 4.1 变量前缀不对，代码里读不到

这是最常见的问题。很多人写了 `.env` 文件，却发现代码里读不到，最后一查，变量名前少了 `VITE_`。

错误示例：

```env
APP_API_URL=/api
```

正确示例：

```env
VITE_APP_API_URL=/api
```

如果团队有固定命名规范，就统一一套，不要混用。

### 4.2 环境变量是“打包时写死”的，不是运行时动态读的

前端里的环境变量通常在构建时就被替换进代码了。  
也就是说，`npm run build` 之后，产物里的值基本就固定了。

这带来两个结果：

1. 部署完之后不能指望随便改 `.env` 就生效；
2. 如果想“运行时动态改配置”，那是另一套方案，不是普通 `.env` 能解决的。

所以设计环境变量时，要先想清楚“构建时确定”这件事。

### 4.3 不要把敏感信息放进前端环境变量

凡是前端能拿到的内容，都不能当秘密。  
如果一段信息会出现在浏览器里，用户就有可能看到。

所以这些东西不要放：

- 数据库密码
- 后端私钥
- 真正敏感的授权密钥
- 只应在服务端保存的信息

前端环境变量适合公开配置，或者即使被看到也不会造成安全问题的内容。

### 4.4 常见排查清单

当环境变量没生效时，按下面顺序查，通常很快就能定位：

1. 文件名是否正确，是否符合 `.env.xxx`
2. 变量名是否以 `VITE_` 开头
3. 是否重启了开发服务器
4. 当前 mode 是否正确
5. 代码里是否用 `import.meta.env.xxx` 读取
6. 是否被其他环境文件覆盖
7. 读取值时有没有把字符串转成需要的类型，比如数字、布尔值

特别提醒：**改完 `.env` 文件后，记得重启 Vite。**  
很多“没生效”其实就是这个原因。

### 4.5 环境问题和代理、构建的关系

环境变量不是孤立的，它经常和代理、构建一起出现。

- 开发环境通常配代理，接口写成 `/api`，再由 Vite 转发；
- 测试和生产往往直接切真实域名；
- 构建时如果基础路径不对，静态资源也会出问题。

所以你排查环境问题时，别只盯着 `.env`，还要顺手看：

- 代理地址有没有跟着变
- 构建命令是不是用了正确的 `--mode`
- 资源路径是不是和部署目录一致

这几项经常是一起错的。

### 5.1 `.env`

VITE_APP_NAME=全栈老赵讲Vite
VITE_REQUEST_TIMEOUT=8000
VITE_LOG_LEVEL=info

### 5.2 `.env.development`

### 5.5 在代码里使用

```ts

  timeout: Number(import.meta.env.VITE_REQUEST_TIMEOUT),

import axios from 'axios'

    },
  }
})
```

适合做一些构建期注入，比如版本号、应用名、固定常量。

## 六、老赵实操建议：怎么把环境配置做得稳一点

### 6.1 先统一规范，再谈灵活

最实用的做法不是“谁想怎么配都行”，而是先定规则。

建议统一成这几条：

- 所有前端可见变量统一用 `VITE_` 前缀
- `.env` 放公共值
- `.env.development / .env.test / .env.production` 放差异值
- 接口地址统一从环境变量读取，不要散落在业务代码里

这样后续排查、联调、部署都会轻松很多。

### 6.2 给变量起能看懂的名字

变量名别图省事，后面维护的人会很痛苦。  
推荐写得明确一点：

- `VITE_API_BASE_URL`
- `VITE_APP_NAME`
- `VITE_REQUEST_TIMEOUT`
- `VITE_ENABLE_MOCK`

不要写得太短：

- `VITE_URL`
- `VITE_NAME`
- `VITE_T`

名字清楚，团队协作时少很多沟通成本。

### 6.3 开发环境优先本地代理，别直接打正式接口

开发阶段直接连正式接口，问题不少：

- 网络慢
- 跨域麻烦
- 容易污染线上数据
- 联调不稳定

更稳的方式是：

- 开发环境接口统一写成 `/api`
- 通过 Vite 代理转发到本地或测试后端

这样前端代码不用跟着切来切去，体验也更稳定。

### 6.4 变更环境变量后记得重启

这条很重要，但经常被忽略。  
如果你改了 `.env` 文件，页面没变化，先别急着怀疑代码，先重启 Vite 服务。

记住一句话：

**改环境文件，先重启。**

### 6.5 最后给你一份检查顺序

真要落地，老赵建议你按这个顺序做：

1. 先建好 `.env`、`.env.development`、`.env.test`、`.env.production`
2. 把接口地址、调试开关、应用名统一迁进去
3. 代码里统一从 `import.meta.env` 取值
4. 开发环境接口先走 `/api`，配合代理
5. 每次改完 `.env` 先重启，再验证
6. 构建前确认 `--mode` 没写错，避免打包进错环境

这套顺下来，环境问题基本就不会卡你太久。

## 结尾小结：环境变量不是小配置，是项目分层的基础

这一章只要抓住三件事，就够用了：

1. **环境变量文件按模式分开管理**，公共值和差异值分层放；
2. **前端只能读 `VITE_` 开头的变量**，并通过 `import.meta.env` 读取；
3. **打包后的变量是固定的**，所以环境区分要在构建阶段做好。

如果你现在就要落地，建议直接做这三步：

- 建好 `.env / .env.development / .env.test / .env.production`
- 把接口地址、调试开关、应用名统一迁到环境变量里
- 在请求封装和配置入口统一读取，不要散写

**老赵实操建议**：  
先别追求配置多高级，先追求配置清楚。一个项目只要环境变量规范了，后面的代理、打包、部署、联调都会顺很多。

# 第7章：代理配置与接口联调，前后端一起干活

## 开篇引入：为什么联调时总要先配代理

前端页面能跑起来，一请求接口就报错，这几乎是联调常态。多数时候不是代码错了，而是浏览器的跨域限制在拦你。开发阶段前端通常跑在 `localhost:5173`，后端可能是 `localhost:3000`、`localhost:8080`，只要协议、域名、端口有一个不同，就可能被判定为跨域。

Vite 的代理配置就是干这个的：

- 浏览器只请求前端开发服务器
- Vite 再把接口转发给真实后端
- 浏览器看到的是同源请求
- 后端收到的还是原来的接口请求

这样前端不用在代码里写死后端地址，后端也不用为了开发阶段临时改 CORS 策略。更重要的是，前后端可以并行开发，联调时由 Vite 把双方接起来，少很多环境切换麻烦。

---

## 一、为什么开发阶段常常要配代理？

### 1. 解决跨域，不让浏览器先拦你

前端页面在开发服务器上运行，接口却在另一个地址。直接请求真实后端时，浏览器会先做同源检查，不满足规则就直接拦截。

代理的作用，就是把“前端直接访问后端”改成“前端访问本地 Vite，再由 Vite 转发”。浏览器只看到本地请求，跨域问题就被 Vite 接住了。

### 2. 避免接口地址写死

如果你在代码里写：

```js
fetch('http://localhost:3000/api/user')
```

开发、测试、预发、线上一切换就得改代码，维护起来很麻烦。

更稳的方式是：

```js
fetch('/api/user')
```

前端只关心路径，真正的后端地址交给 Vite 配置。这样切环境时只改配置，不动业务代码，也是很多项目统一接口前缀的原因。

### 3. 方便前后端并行开发

接口没完全定下来时，前端可以先写页面，后端继续开发接口。代理配好后，前端能直接联调真实接口；如果后端还没准备好，也能先接 mock。总之，代理能让前后端各干各的，联调时再接上。

---

## 二、`server.proxy` 的基本写法

Vite 的代理配置主要写在 `vite.config.ts` 或 `vite.config.js` 里，核心是 `server.proxy`。先记住一个最小可用方案：**前端请求统一带前缀，代理把请求转到后端，必要时再重写路径。**

### 1. 最基础的代理配置

```ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:3000',
        changeOrigin: true
      }
    }
  }
})
```

这表示：

- 访问以 `/api` 开头的请求
- 由 Vite 转发到 `http://localhost:3000`
- `changeOrigin: true` 会把请求来源改成目标地址

### 2. 这个配置怎么理解

比如前端请求：

```js
fetch('/api/user/list')
```

Vite 会把它转发成：

```text
http://localhost:3000/api/user/list
```

默认情况下，路径不会自动去掉 `/api`，会原样转发。  
所以很多项目会统一加一个前缀，比如 `/api`、`/backend`、`/dev-api`，方便代理识别。

### 3. `changeOrigin` 为什么常开

有些后端会检查请求头里的 `Origin` 或 `Host`。如果直接从 `localhost:5173` 转发，后端可能觉得来源不对。

`changeOrigin: true` 会让请求头更像是从目标地址发出的，联调时通常更省事。大多数开发代理场景都建议开着。

---

## 三、接口路径转发与重写规则，别把路径弄乱

代理不只是转发地址，很多时候还要处理路径。  
这部分最容易出问题，因为请求看似发出去了，实际上路径拼错了。

### 1. 什么时候需要路径重写？

假设前端请求：

```js
fetch('/api/user/list')
```

后端真实接口却是：

```text
http://localhost:3000/user/list
```

这时就要把 `/api` 去掉，再转发给后端，这就是 `rewrite` 的作用。

### 2. 重写规则写法

```ts
proxy: {
  '/api': {
    target: 'http://localhost:3000',
    changeOrigin: true,
    rewrite: (path) => path.replace(/^\/api/, '')
  }
}
```

这样：

- `/api/user/list`
- 会转发成 `/user/list`

这类写法很常见，尤其是老项目或后端接口前缀不统一时，用重写能把前后端路径习惯对齐。

### 3. 判断要不要重写的标准

可以直接按这几条判断：

- 前端前缀只是为了区分请求，后端不需要这个前缀，就写 `rewrite`
- 后端本来就要求带前缀，就不要重写
- 团队统一用 `/api`，那就直接转发，不动路径

### 4. 最容易踩的两个坑

#### 坑一：代理前缀和请求路径不一致

比如代理配的是 `/api`，代码却写：

```js
fetch('/v1/user')
```

这时请求不会走代理，自然也不会被转发。  
所以前端请求路径一定要和代理前缀对齐。

#### 坑二：前后端都在拼前缀

比如代理配置里已经写了 `rewrite`，前端代码又请求：

```js
fetch('/api/api/user')
```

结果转发后路径就乱了。  
所以团队里最好统一规则：前缀到底谁来加，谁来去。建议前端只写一次前缀，或者封装请求时统一加，别散落在页面里手写。

## 四、联调中常见问题：先按顺序排查

接口联调出问题时，别急着改一堆配置。先按顺序看，通常很快就能定位。

### 1. 先看代理有没有命中

第一步先看请求有没有走代理。

检查这几项：

1. 请求路径是否以代理前缀开头，比如 `/api`
2. `vite.config` 改完后有没有重启开发服务器
3. 浏览器 Network 里请求地址是不是还是前端本地地址
4. 后端服务有没有真正启动

很多人改完配置忘了重启 Vite，结果白排查半天。还有一种情况是，浏览器报跨域，但根因其实是路径没对上，或者后端服务根本没启动。

### 2. 再看路径是否拼错

路径问题特别常见。建议检查：

- 请求里有没有多写一层前缀
- `rewrite` 后的路径是不是后端真实接口
- 请求封装里有没有自动拼接 `baseURL`
- 页面里有没有硬编码完整域名

最稳的做法是，前端统一走一个请求封装，比如：

```ts
const request = (url: string, options?: RequestInit) => {
  return fetch(url, options)
}
```

页面里只传：

```js
request('/api/user/list')
```

不要一会儿相对路径，一会儿绝对路径。  
一旦代码里混进真实域名，代理就失效了，环境切换也会变麻烦。

### 3. 最后看 Cookie 和登录态

联调时经常出现：登录接口成功了，返回了 Cookie，下一次请求却没带上。

#### 情况一：前端请求没带凭证

如果你用 `fetch`，要显式开启：

```js
fetch('/api/user', {
  credentials: 'include'
})
```

如果你用 axios，要配：

```js
axios.defaults.withCredentials = true
```

这一步很关键。请求成功不代表浏览器会自动带上跨站凭证。

#### 情况二：后端 Cookie 属性不对

Cookie 可能受这些属性影响：

- `SameSite`
- `Secure`
- `Domain`
- `Path`

开发阶段即使走了代理，某些登录态场景还是要检查后端返回的 Cookie 配置。尤其是跨站请求时，`SameSite` 设得太严格，很容易导致 Cookie 不生效。

#### 情况三：代理后看起来同源，实际逻辑仍有差异

浏览器眼里，走代理是同源请求；但 Cookie 是否真正落下，还要看后端和浏览器策略。  
所以别以为“配了代理就万事大吉”，登录态问题还是要结合请求头和响应头一起看。

## 五、一份可以直接用在项目里的代理配置示例

下面这份配置比较实用，适合 Vue 或 React 项目直接改。

```ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig(({ mode }) => {
  const isProd = mode === 'production'

  return {
    plugins: [vue()],
    server: {
      host: '0.0.0.0',
      port: 5173,
      proxy: {
        '/api': {
          target: 'http://localhost:3000',
          changeOrigin: true,
          rewrite: (path) => path.replace(/^\/api/, '')
        }
      }
    },
    build: {
      outDir: 'dist',
      sourcemap: !isProd
    }
  }
})
```

### 配套使用方式

前端请求统一这样写：

```js
fetch('/api/user/list', {
  credentials: 'include'
})
```

如果你用 axios，也建议封装成统一实例：

```ts
import axios from 'axios'

const request = axios.create({
  baseURL: '/api',
  withCredentials: true
})

export default request
```

业务里直接：

```ts
request.get('/user/list')
```

如果后端接口本身就带前缀，那就把 `rewrite` 去掉，保持前后端一致即可。

## 六、如何在 Vue 中使用 Vite 联调接口？

Vue 项目里用 Vite 很自然，做法就是在 `vite.config.ts` 里加代理，然后页面里统一走相对路径。

### Vue 场景建议

- 接口统一前缀：`/api`
- 请求封装放在 `src/utils/request.ts`
- 页面里不要直接写完整后端域名
- 登录态接口要重点检查 Cookie

示例：

```ts
// src/utils/request.ts
import axios from 'axios'

export const request = axios.create({
  baseURL: '/api',
  withCredentials: true
})
```

Vue 组件里通过这个实例调接口就行，不管是组合式 API 还是选项式 API，都建议统一走请求封装。这样组件只关心数据展示，不用分心处理地址和环境。

如果项目里有多个后端服务，也可以拆成多个请求实例，比如一个管业务接口，一个管文件上传接口，思路一样，别全堆一起。

---

## 七、如何在 React 中使用 Vite 联调接口？

React 项目同样适用。  
Vite 不区分你用 Vue 还是 React，代理逻辑是通用的。

### React 场景建议

- 在 `vite.config.ts` 里配置 `server.proxy`
- 请求层单独封装
- 组件里只负责调用，不写环境判断
- 多个后端服务时拆多个代理前缀

示例：

```ts
import axios from 'axios'

export const api = axios.create({
  baseURL: '/api',
  withCredentials: true
})
```

组件或 hooks 中直接调用：

```ts
api.get('/user/list')
```

React 项目尤其要注意，别把接口地址散落在各个组件里。React 组件拆得细，如果每个组件都自己写请求地址，后期改起来会很乱。最好的方式还是集中封装请求，再在 hooks 或 service 层里调用。

## 八、老赵实操建议：代理配置怎么用才不乱

### 1. 先定接口前缀，再写代码

团队里最容易乱的，不是配置本身，而是命名没统一。建议一开始就约定：

- 开发接口前缀：`/api`
- 测试接口前缀：`/api`
- 生产环境由构建或网关处理

这样前端代码不用换，变化集中在配置上，联调会省心很多。

### 2. 请求封装只保留一个入口

别在项目里到处 `fetch`、`axios` 混着写。最好统一成一个请求模块，这样：

- `baseURL` 好改
- token 好加
- 错误处理好统一
- 代理调试也更清楚

多人协作时尤其重要。你改好了代理，别人又在别处写死真实地址，最后还是会乱。

### 3. 改完代理一定重启 Vite

很多人配置写对了，结果没重启开发服务器。Vite 虽然快，但代理相关配置改完，最好先重启再判断。

### 4. 排查顺序别乱

建议按这个顺序来：

1. 浏览器 Network 看请求有没有发出
2. 看请求路径有没有走代理前缀
3. 看响应状态码
4. 看后端日志有没有收到请求
5. 再查 Cookie 和权限问题

别一上来就怀疑框架、怀疑插件。很多问题其实只是前缀写错，或者请求封装少配了一项。

---

## 小结：代理不是花活，是联调基本功

Vite 的代理配置，本质上就是帮你把本地开发和真实后端接起来。它能解决跨域、避免地址写死、简化前后端并行开发。记住几个关键点就够了：

- 前端请求尽量写成相对路径
- 代理前缀统一，比如 `/api`
- `changeOrigin` 通常建议开启
- 是否重写路径，看后端是否需要前缀
- Cookie 问题要同时看前端请求和后端响应
- 修改代理配置后，记得重启开发服务器

### 这章你可以立刻做的事

1. 在项目里加上 `server.proxy`
2. 统一接口前缀为 `/api`
3. 把散落的请求地址收拢到一个请求封装里
4. 用浏览器 Network 检查一次真实请求路径
5. 测试登录接口，看 Cookie 是否正常带回

把这几步做顺了，前后端联调会轻松很多。代理不是为了绕过问题，而是为了让开发阶段少被环境切换和跨域折腾。

# 第8章：插件机制入门，Vite 怎么扩展能力

## 开篇：为什么你迟早会碰到插件

Vite 核心已经够快、够顺手，但项目一复杂，你很快会发现：有些事不是改几项配置就能解决的。

比如：

- 自动导入常用 API，少写重复 `import`
- 把特定文件当资源处理，而不是普通代码
- 给路径做别名、重写，兼容旧写法
- 在构建时生成页面、注入环境信息、处理 Markdown、SVG、图标
- 统一团队的代码规则、入口规则、打包规则

这些需求很多都超出了 Vite 核心配置的范围。  
这时候，**插件**就是 Vite 的扩展口。

你可以把 Vite 理解成底盘很强的工具箱，插件就是挂上去的功能模块。核心逻辑交给 Vite，特殊能力交给插件，优点很直接：

1. **主程序保持轻**  
2. **按需扩展**  
3. **生态灵活**  
4. **特殊场景可以自己补能力**

记住一句话：

> 当你发现“配置已经不太够用，但又不想大改项目结构”时，插件通常就是最合适的入口。

这一章老赵就把插件讲明白：**插件能解决什么问题、怎么跑、怎么配、怎么排错，以及怎么实际写一个能用的配置。**

---

## 插件到底能改什么，不能改什么？

先说清楚：**插件很强，但不是万能胶。**

### 插件能做的事

插件通常能介入这些环节：

- 读取和识别文件
- 转换源码内容
- 处理资源引用
- 增加构建时动作
- 修改输出结果
- 给开发和构建流程加规则

所以它适合做这些活：

- 自动导入常用 API
- 自动注册组件
- 处理 Markdown、SVG、图标、文本
- 注入版本号、时间戳、环境标识
- 构建完成后生成额外文件或提示信息
- 给某些文件类型定制读取方式

### 插件不能替你解决的事

下面这些问题，通常先别急着上插件：

- 简单的别名映射
- 基础代理配置
- 环境变量读取
- 页面逻辑本身写错了
- 路由、状态管理、接口封装这些业务问题

也就是说：

> 能用 Vite 原生配置解决的，先别上插件。  
> 插件是扩展能力，不是替你重写项目。

这个边界先立住，后面你才不会越配越乱。

---

## 插件能解决什么问题？

### 1. 解决“构建前后要插一手”的问题

有些工作不属于业务代码，但又必须在构建时做掉，比如：

- 自动替换文本
- 构建完成后输出提示
- 生成额外文件
- 压缩、转换、注入内容

这类任务很适合插件，因为它们属于工程流程，不属于页面逻辑。  
比如你想把版本号写进产物，或者在打包完成时提醒部署同学“静态资源有更新”，放在插件里就很合适。

### 2. 解决“Vite 默认不认识”的问题

Vite 默认能处理很多常见文件，但项目一复杂，就会遇到它不擅长的类型：

- `.md`
- 特殊方式导入的 `.svg`
- 设计稿导出的资源
- 自定义语法文件

插件可以让 Vite 学会“怎么读这些东西”。  
比如你想直接把 Markdown 文件当内容页使用，页面里读取标题、正文、摘要，而不是先手动转成 HTML 或 JSON，这就很适合插件处理。

### 3. 解决“团队约定和工程化”的问题

插件也常用来统一工程规则：

- 自动补路径别名
- 自动导入组件和 API
- 做代码检查
- 给开发环境加调试信息

一句话总结：

**凡是“不是页面业务，但会影响开发和构建流程”的事，都值得先想想能不能用插件解决。**

## Vite 插件的基本思路和生命周期概念

### 插件的本质是什么？

你可以把 Vite 插件理解成：

> 一组在特定时机被 Vite 调用的函数，用来参与解析、转换、构建、输出等流程。

插件不是外挂脚本，而是被 Vite 调度的参与者。  
Vite 会在不同阶段问插件：

- 这个文件你认识吗？
- 这个内容要不要改一下？
- 构建结束后要不要补个动作？

所以插件不是你直接命令它干活，而是 Vite 在合适的时间把任务交给它。

### 生命周期怎么理解？

不用死记一堆钩子名，先抓住三个阶段就够了。

#### 1. 初始化阶段

Vite 启动时，会加载插件配置。  
这时候通常做：

- 读取配置
- 初始化状态
- 准备辅助数据

可以理解成“开工前准备”。

#### 2. 开发阶段

你访问页面、修改文件、刷新页面时，插件会参与：

- 文件解析
- 模块转换
- 资源处理
- 热更新协作

这个阶段直接影响开发体验：改完代码能不能马上看到结果、资源路径会不会乱、热更新会不会失效，都和它有关。

#### 3. 构建阶段

执行 `vite build` 时，插件会进入另一套流程：

- 参与打包
- 处理产物
- 修改输出内容
- 做构建收尾

同一个插件，开发时和构建时可能做不同的事。  
所以别只看“能不能用”，更要看“在哪个阶段用”。

### 记住三个关键词

- **读**：怎么理解文件
- **改**：要不要改内容
- **出**：输出时要不要补动作

插件机制的核心，就是这三件事。

---

## 常见插件类型：构建辅助、路径处理、资源处理

### 1. 构建辅助类插件：帮你把工程活干顺

这类插件不一定直接影响页面，但能让项目更省心。

常见用途：

- 自动导入常用 API
- 自动注册组件
- 生成构建信息
- 注入版本号、时间戳、环境标识

适合：

- 团队项目
- 中大型前端应用
- 需要统一工程规范的项目

比如 Vue 项目里常要反复导入 `ref`、`computed`、`reactive`；React 项目里也会频繁引入工具函数。自动导入类插件的价值，就是把这些机械重复省掉。

判断标准：

> 如果一件事“每个页面都可能碰到，但又不该手写重复代码”，就适合构建辅助插件。

### 2. 路径处理类插件：让 import 更顺手

你可能会遇到：

- 相对路径太深，`../../../../`
- 某些目录经常导入，太啰嗦
- 旧项目里的别名规则要兼容

这类方案通常负责：

- 路径别名
- 重写导入路径
- 简化模块引用方式

严格说，`alias` 本身是 Vite 配置，但当路径规则更复杂时，也可能借助插件进一步处理，比如统一前缀、兼容老代码写法。

判断标准：

> 如果你在代码里经常写很长的路径，就该考虑路径处理方案。

### 3. 资源处理类插件：让 Vite 认识更多文件

资源处理类插件，重点是把某种文件变成可用资源。

例如：

- 把 Markdown 转成页面内容
- 把 SVG 当组件用
- 处理图片、字体、音视频
- 定制读取 JSON、文本、配置文件

这类插件很常见，因为很多项目不是纯 JS/TS 页面，还会混合内容资源。  
尤其是官网、文档站、组件库，资源处理几乎绕不开。

判断标准：

> 只要你发现“这个文件类型 Vite 默认处理得不合胃口”，就可以找资源处理插件。

## 一个完整的插件使用流程

别上来就配。老赵建议按这个顺序来：

### 第一步：先确认需求是不是插件该管的

先问自己三个问题：

- 原生配置能不能解决？
- 这个需求是开发期用，还是构建期用？
- 这个能力会不会影响别的插件？

如果只是路径别名、代理、环境变量，那先用 Vite 原生配置。  
如果是自动导入、资源转换、构建增强，再考虑插件。

### 第二步：安装并确认版本兼容

安装前先看插件说明，重点看：

- 是否支持当前 Vite 版本
- 是否支持你的框架
- 是否有额外依赖
- 是否有已知限制

很多插件不是不能用，而是版本不对。  
所以先看兼容性，再动手。

### 第三步：引入并放进 `plugins`

插件一般在 `vite.config.ts` 里引入，然后放进 `plugins` 数组。

### 第四步：配置最小参数

先用最少配置跑起来，不要一开始就把所有选项都打开。  
能先看见效果，才好判断对不对。

### 第五步：观察效果

检查三个地方：

- 开发服务器有没有变化
- 控制台有没有报错
- 打包产物有没有变化

### 第六步：出问题就按顺序排查

先看版本，再看配置位置，最后看报错日志。  
别一上来就怀疑 Vite 核心。

## 安装、配置和排查插件问题

### 1. 安装插件：先看它适配谁

Vite 生态里的插件通常分场景：

- 面向 Vue
- 面向 React
- 面向通用资源
- 面向构建增强

先确认三件事：

1. 是否支持当前 Vite 版本  
2. 是否支持你的框架  
3. 是否和现有插件冲突  

安装一般就是常规依赖安装，然后在 `vite.config` 里引入。  
老赵建议先看官方 README，重点看“适用版本”和“使用方式”。很多插件不是不能用，而是你装对了、配错了。

### 2. 配置插件：顺序往往比你想的更重要

很多人配置失败，不是插件坏了，而是顺序和参数不对。

重点看：

- 是否需要放在数组前面
- 是否依赖别的插件先处理
- 是否要区分开发和生产环境
- 是否需要传入路径、开关、白名单等参数

比如一个资源转换插件，可能要先让另一个插件把路径处理好，它再接着处理内容。  
插件数组不是“谁先写都一样”，有时候顺序就是结果。

### 3. 排查插件问题：先抓最常见的四类

#### 问题一：插件不生效

先看：

- 有没有正确引入
- 有没有写进 `plugins`
- 配置项是否写错
- 环境条件是否没满足

最常见的是：插件写了，但条件没触发。比如你把插件限定在 `build` 阶段，它在开发时当然不会动。

#### 问题二：只在开发环境生效，打包不生效

通常是：

- 插件只参与 dev
- 构建模式没开启
- 插件本身只支持某个阶段

排查前先确认它到底在哪个阶段执行，别一上来就怀疑 Vite。

#### 问题三：顺序冲突

多个插件处理同一类文件时，可能互相影响。  
解决办法通常是：

- 调整插件顺序
- 缩小作用范围
- 调整插件参数

比如一个插件想把 SVG 变成组件，另一个又把 SVG 当普通资源处理，就很容易打架。

#### 问题四：产物异常

如果打包后内容不对，重点查：

- 插件是否改坏了源码
- 是否影响了路径
- 是否破坏了资源引用

有些问题开发时看不出来，到了构建后才冒出来，因为开发模式更宽容，构建阶段更严格。

### 排查口诀

**先看日志，再看顺序；先看环境，再看范围。**

## 一个可复制的插件使用示例

下面这个示例，演示如何在 Vite 里使用一个通用插件，并结合别名、开发/生产环境判断做基础配置。  
你可以把它理解成“插件配置模板”。

### `vite.config.ts`

```ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import path from 'path'

// 示例插件：用一个简单的自定义插件演示思路
function logPlugin() {
  return {
    name: 'log-plugin',
    apply: 'build',
    transform(code: string, id: string) {
      if (id.includes('src')) {
        return code
      }
      return null
    },
    buildEnd() {
      console.log('构建结束：log-plugin 已执行')
    }
  }
}

export default defineConfig(({ mode }) => {
  return {
    plugins: [
      vue(),
      logPlugin()
    ],
    resolve: {
      alias: {
        '@': path.resolve(__dirname, 'src')
      }
    },
    define: {
      __APP_MODE__: JSON.stringify(mode)
    }
  }
})
```

### 这个示例会带来什么变化？

- `vue()` 让 Vue 项目里的 `.vue` 文件正常工作
- `logPlugin()` 只在构建时生效，开发时不会执行
- 打包结束后，控制台会输出一条提示
- `@` 可以直接指向 `src`，少写很多相对路径
- `__APP_MODE__` 可以在代码里读到当前模式

如果你在业务代码里写：

```ts
console.log(__APP_MODE__)
```

它会在构建时被替换成当前 `mode` 对应的字符串值。  
这就是插件和 Vite 配置一起工作的典型样子。

### 实战里你最常改的地方

1. `plugins` 数组里加你需要的插件  
2. 调整插件顺序  
3. 为不同环境传不同参数  
4. 根据项目结构补充 `alias`

## Vue 和 React 项目里怎么用插件？

很多人不是单独研究 Vite，而是直接落到 Vue 或 React 项目里。

### 在 Vue 中使用 Vite 插件

Vue 项目里最常见的是：

- Vue 官方插件
- 自动导入 API 的插件
- 组件自动注册插件
- SVG 处理插件

通常先把 Vue 基础插件配好，再叠加工程能力。  
比如先保证 `.vue` 文件能正常编译，再考虑自动导入 `ref`、`computed`，或者把某个目录下的组件自动注册起来。这样开发时会轻松很多，模板也更干净。

### 在 React 中使用 Vite 插件

React 项目里常见的是：

- React 官方插件
- 路径别名
- 环境变量注入
- 资源处理插件
- 构建优化插件

React 项目更容易遇到 JSX、自动导入、路由按需加载等工程问题，插件通常就是用来收住这些细节的。  
比如你在组件里频繁使用工具函数，或者希望统一控制 JSX 转换行为，插件都能帮上忙。

### 选择原则

不管 Vue 还是 React，插件都别贪多。  
先想清楚：

- 这插件是不是解决我当前真问题
- 会不会引入额外复杂度
- 团队成员能不能看懂、维护
- 版本更新后会不会有兼容问题

能用配置解决的，先别急着上插件。  
插件是扩展能力，不是让项目变复杂的理由。

## 老赵的插件使用检查清单

每次加插件前，先过一遍：

- 这个需求能不能先用 Vite 原生配置解决？
- 插件是否和当前框架匹配？
- 是否确认支持当前 Vite 版本？
- 它在开发还是构建阶段生效？
- 插件顺序是否合理？
- 有没有和别的插件冲突？
- 出问题时有没有最小化复现方式？

尤其是最后一条，**最小化复现**特别重要。插件一多，问题就容易互相干扰；你只要能把问题缩小到最小配置，排查速度会快很多。

## 常见误区：别把插件当万能胶

### 误区一：所有问题都靠插件

不是。  
有些问题直接改配置就行，比如别名、代理、环境变量。  
原生配置能解决的，没必要再引入依赖。

### 误区二：插件越多越强

不是。  
插件越多，越容易冲突，构建也可能更慢。  
成熟项目往往是“插件少，但用得准”。

### 误区三：只看教程，不看生效范围

很多插件只在 dev 有效，或者只在 build 有效。  
你要先知道它在哪个阶段工作，不然很容易误判为“没生效”。

---

## 小结：插件不是附加题，是 Vite 的扩展方式

你只要记住一句话：

> Vite 插件的价值，不是让配置看起来更高级，而是让 Vite 处理那些默认不覆盖、但项目里很常见的需求。

把插件当成工程能力的补丁和扩展口，而不是炫技工具。  
真正会用插件的人，不是装得多，而是知道什么时候该装、为什么装、装完怎么稳。

### 老赵实操建议

1. **先用原生配置，再考虑插件**：能少一个依赖就少一个  
2. **插件只装解决问题的那几个**：别为了“看起来专业”乱加  
3. **优先选社区成熟方案**：少踩兼容坑  
4. **自己写插件前先拆最小需求**：很多需求一个简单钩子就够  
5. **按这个顺序排查问题**：先确认版本兼容，再确认配置位置，最后看控制台报错  
6. **养成看生效范围的习惯**：开发、构建、预览别混着理解

下一章就该把“环境区分”和“多环境打包”接起来看了，因为插件、环境变量、打包配置，往往是一起配合使用的。

# 第9章：在 Vue 项目中使用 Vite

## 开篇引入：Vue 项目为什么更适合先上 Vite

做 Vue 项目的人，大多都踩过这几个坑：项目小的时候很快，一旦组件、页面、依赖一多，启动变慢、热更新不稳、配置越来越散，最后花时间最多的不是写业务，而是修工具链。

Vite 的作用，就是把前端开发里最常见的动作做快、做直。对 Vue 来说，它不是简单换个打包器，而是换一套更顺手的工作方式：

- 开发启动快
- 热更新更稳
- 常用配置更集中
- Vue 官方生态支持好，上手成本低

这一章只讲 Vue 项目里真正会用到的内容：怎么创建、怎么启动、目录怎么对应、常用配置怎么写、别名和资源怎么处理、问题怎么排查，以及一份能直接复制的 Vue 项目模板。

---

## 1. Vue + Vite 的项目创建与启动方式

### 1.1 最常见的创建方式是什么

Vue 新项目最推荐直接用 Vite 创建，尤其是 Vue 3。

```bash
npm create vite@latest my-vue-app
```

然后选择：

- 框架：Vue
- 变体：JavaScript 或 TypeScript

如果团队对类型有要求，建议直接选 TypeScript，后面少很多补救。

创建完成后：

```bash
cd my-vue-app
npm install
npm run dev
```

默认启动在 `localhost:5173`，打开就能开发。

### 1.2 Vue 项目里要先看懂哪几个目录和文件

刚创建完的 Vue + Vite 项目，重点看这些文件：

- `index.html`：入口 HTML
- `src/main.ts` 或 `src/main.js`：应用入口
- `src/App.vue`：根组件
- `src/assets`：业务静态资源
- `public`：原样输出的静态文件
- `vite.config.ts`：Vite 配置文件

可以这样理解：

- `index.html` 负责把页面接起来
- `main.ts` 负责把 Vue 应用启动起来
- `App.vue` 负责先把页面画出来
- `vite.config.ts` 负责把开发和构建规则定下来

### 1.3 Vue 项目里你要先看懂哪几个命令

`package.json` 里通常会有这三个脚本：

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview"
  }
}
```

含义很简单：

- `dev`：开发服务器
- `build`：打生产包
- `preview`：本地预览打包结果

别只跑 `dev`，上线前至少要跑一次 `build` 和 `preview`，提前发现打包报错、资源路径、环境变量等问题。

### 1.4 Vue 2 能不能用 Vite

能，但要看项目情况。

这章重点是 Vue 3，因为它和 Vite 配合更自然，生态也更完整。老 Vue 2 项目如果依赖很多旧生态，建议先评估是否值得升级框架，再切构建工具，别想着一次把框架和工具链一起换掉。

---

## 2. Vue 项目中的常用配置关注点

### 2.1 Vue 项目里最常改的配置有哪些

Vite 在 Vue 项目里，常见配置主要是这几类：

- `alias`：路径别名
- `server`：端口、代理
- `css`：样式处理
- `build`：打包配置
- `plugins`：Vue 插件、自动导入、按需加载等

简单说就是：

- 开发时管访问
- 写代码时管路径
- 联调时管代理
- 发布时管打包

### 2.2 配置文件放哪里

通常在根目录下放 `vite.config.js` 或 `vite.config.ts`。如果你用 TypeScript，建议直接用 `vite.config.ts`，维护更方便。

最基础的配置是：

```ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()]
})
```

这已经足够让 Vue 项目跑起来。先把最小可用配置跑通，再逐步加需求。

### 2.3 配置别一次写死，先按项目需求分层

建议把配置分成三层：

- 基础配置：别名、端口、代理、构建输出
- 业务配置：sourcemap、压缩、全局样式变量
- 团队配置：自动导入、组件注册、质量检查插件

这样后面排查问题时，知道该看哪一层，不容易把所有配置搅在一起。

## 3. 别名、样式、静态资源怎么处理

### 3.1 别名怎么配，为什么 Vue 项目里很常用

Vue 项目里最常见的别名就是 `@` 指向 `src`，这样不用天天写长相对路径。

```ts
import HelloWorld from '@/components/HelloWorld.vue'
```

配置如下：

```ts
import path from 'path'
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: {
      '@': path.resolve(__dirname, 'src')
    }
  }
})
```

好处很直接：导入路径更稳定，项目变大后也更好维护。

如果用了 TypeScript，别忘了同步到 `tsconfig.json`，否则会出现“运行没问题，但编辑器一直报红”的情况。

### 3.2 样式在 Vue 项目里怎么接

Vue 单文件组件里，样式通常直接写在组件内部：

```vue
<style scoped>
.title {
  color: #1677ff;
}
</style>
```

适合组件自己的局部样式，不容易污染全局。

全局样式建议单独放到 `src/styles`，然后在入口文件统一引入：

```ts
import './styles/global.css'
```

如果用 SCSS、LESS，Vite 也能直接支持，装对应依赖即可，不需要再手写一堆 loader 配置。

### 3.3 静态资源怎么放最省心

Vite 对静态资源的处理很直接：

- `src` 里的资源通过 `import` 使用
- `public` 目录下的资源原样保留
- 业务相关资源放 `src/assets`
- 不需要打包处理的文件放 `public`

常见写法：

```vue
<img src="@/assets/logo.png" alt="logo" />
```

或：

```ts
import logo from '@/assets/logo.png'
```

建议记住一句：**业务资源放 `src/assets`，纯静态资源放 `public`。**

### 3.4 常见误区

几个高频坑：

- 图片全扔进 `public`，后面难管理
- 别名只配了 Vite，TS 没配，编辑器报红
- 全局样式和组件样式边界不清，互相覆盖
- 路径写得太随意，后面改目录时全项目受影响

## 4. Vue 项目里的开发服务器与热更新，怎么理解才不绕

### 4.1 Vite 的开发体验为什么好

在 Vue 项目里，Vite 的体验好，最直接的感受就是：

- 启动快
- 页面打开快
- 改一个组件，通常不会整页重载
- 报错更容易定位到具体文件

它不是先把整个项目打成大包再给浏览器，而是更偏“按需提供”。你改某个 `.vue` 文件时，通常只影响相关模块，不会每次都把整个应用重新加载。

### 4.2 热更新失效时先看什么

如果改代码后页面没反应，先按这个顺序排查：

1. 组件是不是被缓存了
2. 改的是不是实际被引用的文件
3. 路径有没有写错
4. CSS 是否被浏览器缓存
5. 插件是否干扰了 HMR

很多问题不是热更新机制本身，而是导入链路、缓存或插件配置出了问题。

如果是 Vue 页面改了但浏览器完全没反应，优先看控制台和终端日志，通常会直接提示某个模块没加载成功，或者某个依赖导入失败。

## 5. Vue 项目常见问题和排查方向

### 5.1 为什么别名能用，但类型报错

这在 TypeScript 项目里很常见。

Vite 里的别名配好了，不代表 TS 也认识。你还需要同步改 `tsconfig.json`：

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
```

判断方式：

- 运行时能找到文件，但编辑器红线报错，多半是 TS 配置没跟上
- 运行时也找不到，先查 `vite.config` 里的别名配置

### 5.2 为什么接口请求在开发时跨域

通常不是 Vite 的问题，而是浏览器跨域限制。

开发期最常见的办法就是配代理。比如后端在 `http://localhost:3000`，前端统一走 `/api`：

```ts
server: {
  proxy: {
    '/api': {
      target: 'http://localhost:3000',
      changeOrigin: true,
      rewrite: (path) => path.replace(/^\/api/, '')
    }
  }
}
```

前端请求时：

```ts
fetch('/api/user/list')
```

这样浏览器看到的是同源请求，联调更顺。

### 5.3 为什么样式改了但页面看起来没变

先看这几项：

1. 样式是不是写在 `scoped` 里，作用范围不对
2. 全局样式有没有被组件样式覆盖
3. 引入顺序是不是错了
4. 浏览器缓存是否影响了显示
5. 有没有用了更高优先级的选择器

Vue 项目里样式问题很常见，很多时候不是没生效，而是被别的规则盖住了。

### 5.4 为什么静态资源路径会错

如果图片或字体路径不对，先分清资源来源：

- `src/assets` 里的资源，尽量用 `import`
- `public` 里的资源，直接按根路径引用
- 不要混着写相对路径，尤其是构建后路径容易乱

如果上线后资源 404，第一件事就是看 `build` 结果里的路径是不是正确。开发时能看到，不代表生产环境也一定对。

### 5.5 Vue 项目排查的实用顺序

建议按这个顺序看：

1. 代码是否真的被引用
2. 路径是否正确
3. 别名是否同时配置到 Vite 和 TS
4. 代理是否生效
5. 样式是否被覆盖
6. 第三方库是否兼容当前版本
7. 打包后资源路径是否正确

这个顺序很实用，能少走很多弯路。

## 6. 一份 Vue 项目可复制配置示例

### 6.1 `vite.config.ts`

```ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import path from 'path'

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: {
      '@': path.resolve(__dirname, 'src')
    }
  },
  server: {
    host: '0.0.0.0',
    port: 5173,
    open: true,
    proxy: {
      '/api': {
        target: 'http://localhost:3000',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, '')
      }
    }
  },
  css: {
    preprocessorOptions: {
      scss: {
        additionalData: `@use "@/styles/variables.scss" as *;`
      }
    }
  },
  build: {
    outDir: 'dist',
    sourcemap: false
  }
})
```

### 6.2 `tsconfig.json` 的路径配置

```json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
```

### 6.3 `main.ts`

```ts
import { createApp } from 'vue'
import App from './App.vue'
import '@/styles/global.css'

createApp(App).mount('#app')
```

### 6.4 一个最小目录建议

```text
src/
  assets/
  components/
  styles/
    global.css
    variables.scss
  App.vue
  main.ts
```

这套配置的特点是：

- 路径清楚
- 代理够用
- 样式入口明确
- 后续扩展方便

可以直接抄到项目里，再按需求调整。

## 7. 插件思路：Vue 项目里怎么“按需加功能”

Vite 的插件思路很简单：

**核心负责基础能力，额外需求交给插件。**

在 Vue 项目里，常见插件有：

- `@vitejs/plugin-vue`：支持 `.vue`
- 自动导入插件：减少重复 `import`
- 组件自动注册插件：减少手写注册
- SVG 处理插件：统一图标管理

但插件不是越多越好。判断标准很简单：

1. 能不能不用插件就解决
2. 插件是否稳定
3. 会不会增加排查成本
4. 是否真的提升效率

**老赵的意思是：**插件是工具，不是装饰。能少则少，能稳先稳。项目里插件太多，最后往往是把自己搞复杂了。Vue 项目先把“基础配置 + 必要项”跑稳，再考虑自动化增强。

## 8. 老赵实操建议

### 8.1 Vue 项目迁移到 Vite，先按这个步骤来

如果你是从旧 Vue 项目迁过来，建议不要一口气全改，按顺序来更稳：

1. 先创建一个新的 Vite Vue 项目
2. 把 `src` 里的业务代码逐步搬过去
3. 先保证 `main.ts`、`App.vue`、路由能跑起来
4. 再补别名、全局样式、环境变量
5. 最后再接代理、插件和构建优化

这样做的好处是：哪一步出问题，都能快速定位。

### 8.2 团队项目里建议统一的规范

建议尽早统一这些东西：

- `@` 指向 `src`
- 接口前缀统一用 `/api`
- 样式目录统一放 `src/styles`
- 环境变量命名统一
- 构建输出目录统一

这样后面换人、扩功能、查问题都会轻松很多。

### 8.3 实际落地时先改哪些文件

如果你要把一套 Vue 项目模板落地，最少先动这几个文件：

- `vite.config.ts`：别名、代理、样式预处理
- `tsconfig.json`：路径别名
- `src/main.ts`：全局样式入口
- `src/styles/global.css`：基础样式
- `src/styles/variables.scss`：变量文件

改完后执行：

```bash
npm run dev
npm run build
npm run preview
```

重点检查这三件事：

- 页面能不能正常打开
- 别名能不能正常导入
- 代理和样式有没有按预期工作

### 8.4 什么时候该重新检查 Vite 配置

出现下面情况时，优先看配置：

- 开发环境接口突然不通
- 别名失效
- 热更新不生效
- 打包结果不符合预期
- 某个第三方库突然报错
- 构建后资源 404

别上来就大改代码，先查配置通常更快。

Vue 项目接入 Vite，关键不是背配置，而是掌握一条最实用的路径：

# 第10章：在 React 项目中使用 Vite

## 开篇引入：React 项目为什么要上 Vite

做过 React 项目的人，大多遇到过这些问题：项目一大启动慢，改一行代码要等半天，配置文件越写越像工程说明书。

Vite 的价值很直接：**让开发时更快、配置更少、上手更轻**。放到 React 场景里，它不是替你写业务，而是把常见痛点先压下去：

- 项目启动更快
- 热更新更直接
- 配置更清爽
- JSX、别名、静态资源更好处理
- 构建结果更容易掌控

如果你以前用 webpack 做 React 项目，应该很有感触：很多时间不是花在写页面，而是花在等、改配置、查报错。Vite 的思路不一样，它先把本地开发这一步做顺，让你少被工具拖住。

这一章直接讲：**React + Vite 怎么创建、怎么配、常见问题怎么排，最后怎么落成一个能复用的模板。**

---

## 一、React + Vite 的项目创建与基本结构

### 1. 怎么创建一个 React + Vite 项目

最常见的方式就是用官方脚手架：

```bash
npm create vite@latest my-react-app
```

然后按提示选择：

- Framework：`React`
- Variant：`JavaScript` 或 `TypeScript`

进入项目后安装依赖：

```bash
cd my-react-app
npm install
npm run dev
```

如果你用 pnpm 或 yarn，也可以替换成对应命令。核心就一句：**先创建项目，再跑开发服务器，确认基础链路通了。**

别跳过 `npm run dev` 这一步。很多项目一开始就急着改目录、加插件、配别名，结果基础链路没跑通，后面排查会很费劲。先确认默认模板能启动，再动手改。

### 2. React + Vite 的基本结构怎么看

一个典型的 React + Vite 项目，常见结构如下：

```text
my-react-app
├─ public/
├─ src/
│  ├─ assets/
│  ├─ App.jsx
│  ├─ main.jsx
│  └─ index.css
├─ index.html
├─ vite.config.js
└─ package.json
```

重点看这几个地方：

- `index.html`：Vite 直接把它当入口之一
- `src/main.jsx`：React 入口文件，通常在这里挂载应用
- `src/App.jsx`：主组件，业务一般从这里展开
- `vite.config.js`：Vite 配置入口
- `public/`：放不需要打包处理、原样访问的静态资源

React 刚接触 Vite 时，最不一样的一点是：**入口文件不再被打包工具“藏起来”**。Vite 直接以 `index.html` 作为开发入口之一，项目结构会更直白。

### 3. 先建立一个判断标准

React 项目上 Vite，先别急着改配置，先确认三件事：

1. 页面能打开  
2. JSX 能正常渲染  
3. 改代码后能快速更新  

这三点成立，说明底层链路基本没问题。后面再谈别名、代理、环境变量，就不会乱。

老赵建议你把这三件事当成开工检查表：先看控制台有没有报错，再改 `App.jsx` 看能不能马上更新，最后确认图片资源能不能正常显示。基础链路不稳，后面所有配置都可能白忙。

---

## 二、React 项目中的常用配置点

### 1. React 项目里最常改的配置有哪些

在 React + Vite 里，常见配置通常就这些：

- `resolve.alias`：路径别名
- `server.port`：开发端口
- `server.host`：局域网访问
- `server.proxy`：接口代理
- `define`：编译期常量
- `build.outDir`：构建输出目录
- `build.assetsDir`：静态资源目录
- `plugins`：插件接入

不要一上来就把配置文件写得很复杂。**够用、清楚、能维护** 才是重点。真正实用的配置，通常都围绕开发协作展开：别人拉下来能跑、接口能通、路径不乱、构建结果可预期。

### 2. 一个基础的配置思路

React 项目里，配置优先级一般是：

1. 先把路径别名、端口、代理处理好
2. 再按需加环境变量
3. 最后再考虑插件和构建细节

这个顺序很实用，因为它对应的是最常见的问题：

- 引入路径太长
- 前后端联调跨域
- 不同环境接口地址不一样
- 打包后资源路径出问题

先把日常操作顺手了，再去处理进阶能力。别一上来就研究很偏的构建细节，项目还没开始写，配置先把人绕晕了。

---

## 三、JSX、别名、静态资源与开发体验

### 1. JSX 在 Vite 里怎么用

React + Vite 天然支持 JSX。你通常只要在 `src/main.jsx`、`src/App.jsx` 里正常写 JSX 就行，不需要额外绕很多配置。

```jsx
export default function App() {
  return <h1>Hello Vite + React</h1>
}
```

如果 JSX 不生效，先检查：

- 文件后缀是不是 `.jsx` 或 `.tsx`
- React 相关依赖是否安装正确
- 入口文件是否挂载到了 DOM 上

如果是老项目迁移过来，记得留意文件后缀。很多时候不是 JSX 写错了，而是文件被当成普通 JS 处理了。

### 2. 路径别名为什么建议早点配

项目一大，下面这种相对路径会很痛：

```js
import Button from '../../../components/Button'
```

更推荐直接配别名，比如 `@` 指向 `src`：

```js
import Button from '@/components/Button'
```

别名的意义不只是“写起来短”，更重要的是：项目结构调整时，能少改很多导入路径。React 项目尤其适合早配别名，因为组件、页面、工具函数很快就会分层，路径会越写越深。

### 3. 静态资源怎么放更合适

React + Vite 里，静态资源一般分两类：

- **会被代码引用并参与打包的资源**：放 `src/assets`
- **原样放出、直接可访问的资源**：放 `public`

例如：

```jsx
import logo from './assets/logo.png'

export default function App() {
  return <img src={logo} alt="logo" />
}
```

如果放在 `public` 下，可以直接访问：

```jsx
<img src="/logo.png" alt="logo" />
```

记住这个区别：`src` 里的资源会跟着构建流程走，适合组件内引用；`public` 里的资源不会被处理，适合固定路径直接访问的文件。

### 4. 开发体验上，Vite 在 React 项目里最值钱的点

React 项目最直接的体验提升，通常体现在：

- 启动快
- HMR 快
- 改一个组件，页面更新快
- 配置成本低

这意味着你可以把时间花在业务逻辑和组件拆分上，而不是和构建工具较劲。尤其是组件开发阶段，热更新快带来的不是一点点省时，而是思路不会被频繁打断。

## 四、React 项目常见问题和排查方向

### 1. JSX 页面不渲染，先查什么

按这个顺序查：

1. `main.jsx` 是否正确执行
2. `App.jsx` 是否被正确引入
3. `ReactDOM.createRoot(...)` 是否写对
4. `index.html` 里是否有挂载节点，比如 `id="root"`

示例：

```jsx
import React from 'react'
import ReactDOM from 'react-dom/client'
import App from './App'

ReactDOM.createRoot(document.getElementById('root')).render(
  <React.StrictMode>
    <App />
  </React.StrictMode>
)
```

这类问题大多不是 Vite 本身坏了，而是入口链路断了。先确认 `document.getElementById('root')` 能拿到节点，再确认 `App` 真正被渲染了。

### 2. 别名不生效，通常是哪一步漏了

最常见的是只配了 Vite，没配编辑器和 TypeScript。

如果你用了 `@`，一般要同时确认：

- `vite.config.js` 里已经配置 alias
- `jsconfig.json` 或 `tsconfig.json` 里也同步路径映射
- 重启开发服务器和编辑器

别忘了，编辑器智能提示和运行时解析是两回事。Vite 里配了别名，不代表 IDE 立刻就认识。先检查项目配置文件有没有同步更新，再重启一次开发服务。

### 3. 样式加载异常，先别急着怀疑 CSS

React 项目里样式异常，常见原因有这几个：

- 样式文件没被入口引入
- CSS 文件路径写错
- 类名拼错
- 组件样式被全局样式覆盖

如果是模块化样式，也要注意导入方式是不是对的。先从最简单的入口检查起：`main.jsx` 里有没有引入全局样式，组件里有没有正确挂样式文件。很多时候不是样式不会加载，而是被别的样式盖住了。

### 4. 图片、字体、SVG 加载异常，怎么排

先分情况：

- 放在 `src` 里，推荐通过 import 引入
- 放在 `public` 里，直接用绝对路径访问
- 如果打包后路径不对，检查 `base`
- 如果生产环境资源 404，检查部署目录和 `build.outDir`

出现资源异常时，先别怀疑 Vite 不会处理图片。大多数情况是资源放错了位置，或者部署路径和构建配置没对上。先看“资源在哪里”“构建输出到哪里”“部署时怎么访问”这三件事。

### 5. JSX 报错时的排查清单

如果你看到 JSX 相关报错，按这个顺序看：

- 文件是不是 `.jsx` / `.tsx`
- 是否安装了 `react` 和 `react-dom`
- `@vitejs/plugin-react` 是否启用
- 入口文件有没有正确导入 React 组件
- 控制台是不是有语法错误或路径错误

这类问题通常不复杂，关键是别一下子去怀疑构建工具。先把文件后缀、依赖、入口链路这三项过一遍，基本就能定位。

---

## 五、配置文件基础：React 项目该怎么写 Vite 配置

下面这份配置覆盖 React 项目最常见的需求：别名、端口、代理、构建输出。

```js
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import path from 'path'

export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      '@': path.resolve(__dirname, './src')
    }
  },
  server: {
    port: 3000,
    host: '0.0.0.0',
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,
        rewrite: (p) => p.replace(/^\/api/, '')
      }
    }
  },
  build: {
    outDir: 'dist',
    assetsDir: 'assets'
  }
})
```

### 这份配置各自干什么

- `plugins: [react()]`：处理 React 和 JSX
- `alias`：让路径更短、更清晰
- `port`：固定开发端口
- `host`：允许局域网访问
- `proxy`：解决开发阶段跨域
- `outDir`：控制构建输出位置
- `assetsDir`：控制资源输出目录

多人协作时，建议把这份基础配置作为起点，再按实际需求往上加。配置文件最怕的不是少，而是乱。一个清楚的配置，比十条看不懂的规则更有价值。

---

## 六、插件思路：React 项目里插件怎么理解

### 1. 插件不是“越多越好”

插件的作用是扩展能力，不是堆功能。React 项目里最基础的就是 `@vitejs/plugin-react`，它负责：

- 处理 JSX
- 支持 React Fast Refresh
- 让开发体验更顺

可以把它理解成 React 项目的基础配套。没有它，React 在 Vite 里的开发体验不完整；有了它，常见的 JSX、刷新、热更新流程就顺了。

### 2. 什么时候才考虑加额外插件

通常是这些场景：

- 需要处理特殊语法
- 需要自动导入
- 需要 SVG 组件化
- 需要压缩、分析、按需加载等增强能力

判断标准很简单：**如果一个需求能通过简单配置解决，就别先上插件。**

插件越多，项目启动和维护成本越高。对大多数 React 项目来说，先把基础能力用好，已经足够解决 80% 的问题。剩下的再按需加，不要为了“看起来高级”而堆插件。

---

## 七、环境区分：开发、测试、生产怎么分

### 1. 为什么 React 项目一定要做环境区分

因为本地开发、测试环境、生产环境往往接口都不一样。  
如果你把地址写死，后面切环境会很麻烦。

### 2. Vite 里常见的环境变量写法

你可以在项目根目录放这些文件：

```text
.env
.env.development
.env.production
```

例如：

```env
VITE_API_BASE=/api
```

React 代码里通过 `import.meta.env` 使用：

```js
const baseURL = import.meta.env.VITE_API_BASE
```

注意：前缀通常要带 `VITE_`，不然前端代码里拿不到。

环境变量适合放会变、但不敏感的内容，比如接口前缀、页面标题、开关状态。密码、私钥这类东西不要放前端环境变量里，前端项目本来就不是安全存储的地方。

### 3. 环境区分的实操建议

- 本地调试优先用 `.env.development`
- 生产配置写到 `.env.production`
- 不要把敏感信息直接放前端环境变量里
- 接口地址、标题、开关类配置可以放环境变量里

## 八、一份 React 项目可复制配置示例

下面这份模板可以直接起步，适合“从空项目到能跑页面”的最短路径。

### 1. 创建与启动

```bash
npm create vite@latest my-react-app
cd my-react-app
npm install
npm run dev
```

创建时选择：

## 九、老赵实操建议

### 1. 迁移时先看入口，再看配置，最后看页面

React 老项目迁到 Vite，老赵建议你按这个顺序查：

1. **先确认入口文件**：`index.html`、`main.jsx`、`App.jsx` 是否连起来了  
2. **再确认 Vite 配置**：插件、别名、代理、base 是否正确  
3. **最后确认页面渲染结果**：控制台、网络请求、静态资源是否正常  

这个顺序很重要。很多人一报错就去改配置，结果真正的问题是入口没挂上。

### 2. 别名一定要配，但不要滥用

`@` 指向 `src` 很好用，但不要搞成十几个别名。团队项目里，别名越多，沟通成本越高。

### 3. 代理和环境变量要一起看

很多人只配代理，不分环境，最后一上线就乱。  
记住一句话：**开发代理解决联调，环境变量解决切换。**

### 4. 先把默认链路打通，再谈优化

先把这些做好：

- React 正常渲染
- JSX 正常工作
- API 正常代理
- 图片正常加载
- 打包正常输出

这些都通了，再做性能优化和工程增强，顺序不要反。

### 5. 模板要“少而稳”

如果你准备把 React + Vite 作为团队模板，建议先保留最核心的东西：

- React 插件
- 别名
- 代理
- 环境变量
- 基础构建配置

其他能力按项目需要再加。模板的作用是让新项目更快起步，不是把所有可能性一次性塞进去。

# 第11章：构建与打包基础，怎么把项目稳稳发出去

## 开篇：别把“能跑”当成“能发”

开发时能打开，不代表生产环境就一定稳。  
Vite 在开发模式下，很多东西是按需处理；到了构建阶段，源码要整理、依赖要打包、静态资源要重命名和搬运，最后生成一份可以直接部署到服务器上的产物。

这章只讲一件事：**生产构建到底在干什么，怎么检查，怎么避免常见坑**。你不需要先变成构建专家，但至少要知道：项目发出去之前，哪些地方最容易出问题，怎么提前看出来。

很多项目上线翻车，不是逻辑写错，而是构建阶段被忽略了：路径不对、资源没打进去、环境变量没带上、路由刷新后 404。问题不复杂，但很烦，而且往往都是上线后才暴露。

---

## 一、开发模式和生产构建模式的区别

### 1. 开发模式：追求快，很多事先不做完

开发模式的核心目标就两个字：**快**。  
Vite 开发服务器利用浏览器原生 ESM，尽量少做打包工作。你改一个文件，它只处理这个文件和相关依赖，响应很快。

开发模式的特点很明确：

- 文件改动后，马上看到效果
- 模块按需加载，不是一次性全打包
- 方便调试，报错更直观
- 一些生产环境才会出现的问题，开发时看不出来

换句话说，开发模式更像“边做边看”，重点是让你改得快、预览快、定位问题快，所以很多优化、压缩、合并动作都不会完全展开。

### 2. 生产构建：追求稳，必须把东西整理好

生产构建的目标不是快，而是**能稳定发出去**。  
`vite build` 会把项目源码做成最终可部署文件，一般包括：

- 代码压缩、合并、拆分
- 样式和资源一起处理
- 资源加 hash，方便缓存管理
- 生成 HTML、JS、CSS 等静态产物

你可以把它理解成“收尾整理”。开发时文件散在各处，构建时就要统一清点：哪些代码进主包，哪些依赖拆出来，哪些资源要复制，哪些路径要改写。做得好，部署就省心；做不好，线上就容易出错。

### 3. 一眼看懂两者差别

| 项目 | 开发模式 | 生产构建 |
| --- | --- | --- |
| 目标 | 快速调试 | 稳定发布 |
| 资源处理 | 按需处理 | 统一整理、重命名、搬运 |
| 代码形态 | 更接近源码 | 更接近最终交付物 |
| 问题暴露 | 方便看见开发错误 | 更容易暴露路径、资源、环境问题 |

所以，开发模式下能用，不代表构建后能用。  
比如这些问题，往往只在构建后暴露：

- 图片路径错了
- 动态导入的文件名变化了
- 某个依赖体积太大
- 运行时依赖 `window`、`document` 这类浏览器对象
- 环境变量写法不对，生产环境取不到值

最实用的判断方式就是：**开发能看，不代表构建能发；构建能发，还要预览验证。**

---

## 二、build 输出目录、资源处理和压缩，分别是什么

### 1. 输出目录：构建结果放哪

Vite 默认把构建结果输出到 `dist` 目录。这个目录就是你最终部署的对象。

常见内容通常有：

- `index.html`
- `assets/` 下的 JS、CSS、图片等资源
- 带 hash 的文件名，用来避免缓存问题

你可以通过 `build.outDir` 自定义输出目录。重点不是名字，而是：**上线用的就是这个目录里的内容**。

### 2. 资源处理：不是所有文件都“原样搬过去”

构建时，Vite 会处理很多资源引用：

- JS 里的 `import`
- CSS 里的 `url(...)`
- HTML 里的静态资源引用
- 图片、字体、SVG 等静态文件

资源处理的重点是：

- 该打包的打包
- 该复制的复制
- 该改名的改名
- 该改路径的改路径

最常见的坑是：**源码里的路径，不一定是构建后的真实路径**。  
比如手写了绝对路径 `/src/assets/a.png`，开发时可能还能看见，构建后就可能失效。因为生产环境下，源码目录结构不再直接暴露给浏览器，真正能访问的是构建产物里的静态文件。

更稳的做法是：

- 图片、字体等资源尽量通过 `import` 引入
- 需要原样放置、不参与打包的文件，放到 `public`
- 不要依赖“字符串拼路径”来引用构建资源

### 3. 压缩：让产物更小，但别乱压

生产构建默认会做压缩，减少体积，提高加载速度。  
但压缩不是越狠越好，常见要注意：

- 太大的依赖包，压缩了还是大
- 代码拆分不合理，会导致首屏压力高
- 某些调试信息要在构建中去掉
- sourcemap 要不要生成，要看场景

如果你对线上排查有要求，可以保留 sourcemap；如果你更在意包体安全和体积，就要谨慎开启。  
简单说：**压缩是手段，不是目的。目的永远是让用户打开更快、线上更稳。**

---

## 三、构建产物怎么检查，别只看“成功了”

### 1. 第一件事：先看 `dist` 里有什么

构建后不要只看命令成功了，要真的打开 `dist` 看一眼：

- 有没有 `index.html`
- JS/CSS 是否都在 `assets` 里
- 文件名是否带 hash
- 图片是否也被正确放进去
- 引用路径是否正常

很多问题只要肉眼扫一遍，就能发现一半。比如 HTML 里脚本路径不对、资源目录少了文件、某个图片根本没打进去。

### 2. 第二件事：本地模拟一次部署

更稳妥的方式是本地做一次静态预览，确认构建产物可用。

流程很简单：

1. 执行构建命令
2. 再用预览模式打开构建结果
3. 检查页面是否正常打开
4. 点击路由、请求接口、加载图片，看是否正常

这一步很重要，因为它更接近真实部署环境。开发服务器和真正的静态产物不是一回事。预览通过，至少说明“构建出来的东西本身没明显问题”。

### 3. 第三件事：做最基础的检查清单

每次构建后，至少过一遍：

- 首页是否能正常打开
- 刷新页面是否 404
- 静态资源是否加载成功
- 路由跳转是否正常
- 图片、字体、样式是否缺失
- 控制台是否有明显报错
- 网络请求是否走到了正确环境

如果是后台项目，还要多看一眼登录态、接口返回、权限页面跳转。很多上线问题并不在页面本身，而是在构建后的资源路径和接口环境上。

---

## 四、常见构建问题，按顺序排查最省事

构建出问题，别一上来就乱改配置。老赵建议你按这个顺序来：

### 1. 先看路径

先确认：

- `base` 配置对不对
- 项目是不是部署在子路径下
- 页面里有没有写死 `/src/...` 这类开发路径
- 路由是不是 history 模式，但服务器没做回退

**最常见现象：**

- 页面白屏
- 刷新后 404
- JS/CSS 资源找不到

如果项目部署在 `/my-app/` 下面，但 `base` 还是默认的 `/`，那线上资源路径大概率会错。

### 2. 再看资源

如果路径没问题，再看资源本身：

- 图片有没有打进产物
- 字体有没有丢
- `public` 里的文件有没有按预期访问
- 动态拼接出来的路径能不能被构建工具识别

建议规则很简单：

- 需要构建处理的资源，尽量用 `import` 引入
- 真正不需要处理、只是原样复制的文件，再放 `public`
- 不要依赖“字符串拼路径”来引用构建资源

比如模板里写一个变量拼出来的图片路径，开发时可能能用，但构建工具未必能识别。最稳的是先 `import imgUrl from './a.png'`，再直接绑定使用。

### 3. 最后看体积和报错信息

如果路径和资源都没问题，再看：

- 构建后体积是不是异常变大
- 是否引入了大依赖包
- 是否把整个工具库都打进去了
- 是否有构建报错、警告被忽略了

体积大时，先找“大户”，不要先怪 Vite：

1. 看构建产物里最大的文件
2. 找出哪个依赖最重
3. 检查是否可以按需加载
4. 考虑动态导入重型模块
5. 大资源改为外链或独立静态资源

最常见的情况是：只用了某个库里的一个小功能，但把整个库都打进去了。还有一种情况是，UI 图标、编辑器、地图这类重型功能被直接放进首屏，包体一下就上去了。该拆就拆，该懒加载就懒加载。

## 五、可复制的构建配置示例

下面这份配置偏实用，适合大多数 Vue 或 React 项目做基础构建控制。

```ts
import { defineConfig } from 'vite'
import path from 'path'

export default defineConfig(({ mode }) => {
  const isProd = mode === 'production'

  return {
    base: isProd ? '/my-app/' : '/',
    resolve: {
      alias: {
        '@': path.resolve(__dirname, 'src')
      }
    },
    build: {
      outDir: 'dist',
      assetsDir: 'assets',
      sourcemap: false,
      minify: 'esbuild',
      rollupOptions: {
        output: {
          chunkFileNames: 'assets/js/[name]-[hash].js',
          entryFileNames: 'assets/js/[name]-[hash].js',
          assetFileNames: assetInfo => {
            const name = assetInfo.name || ''
            const ext = name.split('.').pop() || ''

            if (/\.(png|jpe?g|gif|svg|webp)$/i.test(name)) {
              return 'assets/images/[name]-[hash][extname]'
            }

            if (/\.(css)$/i.test(name)) {
              return 'assets/css/[name]-[hash][extname]'
            }

            return `assets/${ext}/[name]-[hash][extname]`
          }
        }
      }
    },
    preview: {
      port: 4173,
      host: true
    }
  }
})
```

### 这份配置里要看懂的点

- `base`：部署路径，子路径部署时特别重要
- `outDir`：输出目录
- `assetsDir`：资源目录
- `sourcemap`：是否生成 sourcemap
- `minify`：压缩方式
- `rollupOptions.output`：控制输出文件命名规则
- `preview`：本地预览构建结果

### 常用参数说明

- `base`：如果部署在域名根路径，就用 `/`；如果部署在 `/xxx/` 下，就必须改成对应路径
- `sourcemap`：线上排查需要时可以开，但要考虑安全和体积
- `minify`：`esbuild` 是常用默认值，够快也够稳
- `assetsDir`：把静态资源统一放一个目录，后面查问题更方便
- `preview.host`：方便局域网或容器环境里预览
- `rollupOptions.output`：想把 JS、图片、CSS 分目录输出时，这里最好用

这份配置不是唯一答案，但足够让你在项目里直接起步。后面如果要做 CDN、子路径部署、资源分类输出，都可以在这基础上继续加。

## 六、老赵实操建议：构建不是最后一步，是上线前的检查门

### 1. 每次发版前，先跑一遍构建和预览

不要只在 CI 里看结果，自己本地也要预览一次。  
养成习惯：**构建成功 ≠ 能上线，预览通过才算基本合格**。

### 2. 子路径部署一定先配 `base`

如果项目不是部署到域名根路径，而是部署到 `/xxx/` 下面，`base` 不配对，后面一堆资源和路由问题都会冒出来。  
这类问题很典型：本地好好的，线上一打开白屏。往往就是部署路径没处理好。

### 3. 大资源别硬塞进前端包里

视频、大图片、超大字体、很重的图标库，能拆就拆，能外链就外链。  
前端包不是仓库，别把所有东西都往里堆。

### 4. 先检查产物，再谈优化

很多人一上来就研究“怎么把包压得更小”，但最先应该确认的是：

- 打包后能不能跑
- 路径对不对
- 资源有没有丢
- 页面有没有白屏

稳定性没过关，优化没意义。先把“能稳定发出去”做成习惯，后面再谈性能优化才有基础。

## 结尾：把“构建成功”升级成“可稳定发布”

生产构建，说白了就是把开发期源码整理成一份可部署、可访问、可维护的静态产物。你只要记住三件事：

1. **开发模式和生产构建不是一回事**
2. **构建后一定要检查产物和路径**
3. **出现问题先按“路径—资源—体积/报错”这个顺序排查**

如果你能把这章的检查流程跑顺，后面无论是 Vue 项目还是 React 项目，发版时都会稳很多。  
下一步，不是继续背概念，而是拿自己项目跑一次 `vite build`，打开 `dist`，再用预览模式把首页、路由、图片和接口全过一遍。这样你才是真正开始会用 Vite。

# 第12章：用 Vite 搭一个实用项目模板，并解决常见问题

## 开篇：为什么要把 Vite 变成“模板”

前面我们已经把 Vite 的基础用法、配置、环境变量、代理和插件思路过了一遍。真正做项目时，最怕的不是不会写配置，而是每开一个新项目都要从头折腾：别名怎么配、代理怎么写、环境变量怎么分、ESLint/Prettier 怎么接、Vue 或 React 插件怎么装。项目还没写，配置先把人搞累了。

所以这章只解决一个问题：**怎么把 Vite 变成团队能复用、能快速落地的项目模板**。

模板不是把配置堆满，而是把最常用、最稳定、最容易踩坑的部分提前整理好。这样新项目一建出来，大家就能直接写业务，少走弯路，少重复劳动。

---

## 一、如何整理一个适合团队复用的 Vite 项目模板

一个好模板，标准很朴素：**启动快、结构清楚、配置少而稳、扩展方便**。如果模板看着“高级”，但新人接手后找不到入口、改一处坏一片，那就不合格。

### 1. 模板里应该有哪些东西

建议至少包含这些内容：

- 基础目录结构
- Vite 基础配置
- 环境变量区分
- 代理配置
- 常用别名
- 基础 ESLint/Prettier 约定
- Vue 或 React 的基础接入方式
- 一份清楚的 README

如果团队项目更规范，还可以补上：

- 请求封装
- 通用布局
- 路由基础结构
- 组件和工具函数目录

原则很简单：**先放每个项目都要用的东西，把每个项目都不一样的东西留给业务层**。

### 2. 模板不要一上来就过度设计

很多模板一开始就想“做全”，最后变成谁都不敢动。老赵建议：**模板只保留高频共性，不把业务细节塞进去**。比如登录页、列表页、详情页可以留示例，但别把真实业务逻辑写死。模板一旦绑定某个具体业务，就很难复用。

更稳的做法是：模板里保留“骨架”，不保留“血肉”。骨架包括目录、配置、基础组件、请求方式；血肉留给具体业务自己长。

## 二、目录结构、基础配置、环境变量和代理怎么组合

这部分决定模板能不能落地。结构乱，配置再好也没用。真正好用的模板，不是配置多，而是各部分职责清楚。

### 1. 一个实用的目录结构

下面这个结构适合大多数 Vue 或 React 项目：

```bash
src/
  assets/
  components/
  layouts/
  pages/
  router/
  stores/
  services/
  utils/
  styles/
  main.ts
public/
.env.development
.env.production
vite.config.ts
```

思路很直白：

- `pages` 放页面级组件
- `components` 放通用组件
- `services` 放接口请求
- `utils` 放工具方法
- `styles` 放全局样式
- `layouts` 放布局壳
- `stores` 放状态管理

如果团队已有自己的习惯，也可以微调，但核心是：**一看目录就知道东西该放哪**。

### 2. 基础配置要抓住哪些点

Vite 配置里，最常用的是这些：

- `resolve.alias`：简化路径
- `server.port`：固定开发端口
- `server.open`：自动打开浏览器
- `server.proxy`：本地代理接口
- `build.outDir`：构建输出目录

这些项不需要写很多，但最好在模板里直接固定下来，因为它们属于高频基础设施。

### 3. 环境变量怎么做才不乱

环境变量的目标不是“写得多”，而是**不同环境有不同配置，但代码里使用方式统一**。

例如：

```ts
// .env.development
VITE_API_BASE=/api

// .env.production
VITE_API_BASE=https://api.example.com
```

代码里统一读取：

```ts
const baseURL = import.meta.env.VITE_API_BASE
```

这样业务代码不需要关心当前是开发、测试还是生产，只管拿到自己需要的地址。

注意两点：

- 只有 `VITE_` 开头的变量才会暴露到前端
- 不要把敏感信息当成前端环境变量用

前端能读到的东西，默认就不是秘密。

### 4. 代理配置怎么搭

开发阶段最常见的问题就是跨域。模板里建议直接把代理配好，避免每个新项目都从头查。

```ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()],
  server: {
    proxy: {
      '/api': {
        target: 'https://api.example.com',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, '')
      }
    }
  }
})
```

前端请求 `/api/user`，开发时会被转到真实后端地址。联调时只要约定好接口前缀，前端这边不用改一堆请求地址。

## 三、常见问题怎么排查：启动慢、更新失效、构建报错、插件冲突

模板真正有价值，不只是“能跑”，而是出问题时好查。一个能长期使用的模板，必须自带排查思路。

### 1. 启动慢，先看是不是依赖太重

如果项目启动慢，常见原因有：

- 依赖包太多
- 插件装得太杂
- 首次预构建文件过大
- 代码里静态导入太多大文件

排查顺序建议：

1. 看 `node_modules` 是否过重
2. 检查插件是否重复
3. 观察是否有特别大的静态资源
4. 看控制台有没有明显警告

很多时候，启动慢不是 Vite 本身慢，而是项目自己太“胖”了。该拆包的拆包，该按需加载的按需加载。

### 2. 更新失效，先看缓存和依赖写法

热更新不生效，常见原因有：

- 文件改动没被正确监听
- 组件引用方式不对
- 浏览器缓存影响
- 插件改写了模块行为

如果业务代码更新不生效，先重启开发服务器。重启后好了，通常是缓存或监听问题；还不行，再查插件和路径写法。

另外，文件名、导入路径、大小写这些小问题，也很容易让更新失灵，尤其在不同系统之间切换时更明显。模板里最好先把导入规范定好。

### 3. 构建报错，通常是配置或兼容问题

构建报错经常出在这些地方：

- 语法没被正确处理
- 第三方库不兼容
- 别名配置不一致
- 环境变量写错
- 输出目录被误删或权限异常

老赵建议：**先看报错第一行，再看最后一行**。第一行通常告诉你问题类型，最后一行通常告诉你出错文件。不要一上来就改一堆配置，先定位，再动手。

### 4. 插件冲突，优先做减法

插件冲突最常见的表现是：

- 启动报错
- 热更新异常
- 打包结果不对
- 某些文件被重复处理

处理方式很简单：**先注释掉非必要插件，再逐个恢复**。插件思路最重要的不是装得多，而是知道每个插件在干什么。

## 四、Vue 和 React 模板的通用做法与差异点

Vite 做模板时，Vue 和 React 的大框架思路一样，但入口插件不同。也就是说，模板的“底盘”可以共用，框架部分再分开。

### 1. 通用做法

不管 Vue 还是 React，都可以共用这些思路：

- 统一目录结构
- 统一环境变量写法
- 统一代理配置
- 统一路径别名
- 统一构建输出规则
- 统一错误排查方式

这就是 Vite 的好处：底层思路一致，框架差异主要集中在插件和入口文件，不会把模板拆得特别碎。

### 2. Vue 模板怎么接

Vue 项目一般用 `@vitejs/plugin-vue`。

```ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import path from 'path'

export default defineConfig({
  plugins: [vue()],
  resolve: {
    alias: {
      '@': path.resolve(__dirname, 'src')
    }
  }
})
```

Vue 项目模板建议顺手把页面、组件、布局、状态管理这些基本目录定好，后面开发时不容易乱。

### 3. React 模板怎么接

React 项目一般用 `@vitejs/plugin-react`。

```ts
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'
import path from 'path'

export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      '@': path.resolve(__dirname, 'src')
    }
  }
})
```

React 模板里同样建议把路由、状态管理、hooks、services 这些基础目录提前安排好。

### 4. 两者的差异点

差异主要在：

- 插件不同
- 组件语法不同
- 状态管理和路由生态不同
- 项目习惯不同

但从 Vite 模板角度看，**底层配置思路基本一致**。如果团队同时做 Vue 和 React，可以把通用模板部分抽出来，只替换框架插件和入口文件，维护成本会低很多。

## 五、老赵实操建议：怎么从模板快速落地到真实项目

模板不是拿来供着的，是拿来改的。老赵给你一个最稳的顺序：先跑通，再统一，再扩展。

### 1. 先把模板跑通

新项目创建后，先确认这几件事：

- 能启动
- 能访问代理接口
- 环境变量能读到
- 路径别名可用
- 打包能成功

这一步最基础，也最关键。模板如果连基本链路都没跑通，后面加什么都不稳。

### 2. 再替换团队自己的约定

比如：

- 接口地址
- 页面布局
- 全局样式
- 图标资源
- 登录态处理
- 请求拦截器

模板不是照搬，而是要适配自己的开发习惯。把这些约定统一起来，后面协作成本会低很多。

### 3. 最后再加业务功能

不要一边搭模板一边写业务。最稳的做法是：**先把骨架固定，再填业务内容**。这样后面新人接手也容易，出了问题也知道该去哪里找。

### 4. 模板维护要定期做

模板不是一劳永逸。项目一多，模板也要跟着更新：

- 新插件是否需要加入
- 构建配置是否要优化
- 代理规则是否变化
- 环境变量规范是否统一

模板维护得好，后面的项目就越来越省事；维护得乱，项目越多，麻烦越大。

## 本章小结

这章的重点，不是教你写一个“看起来完整”的 Vite 配置，而是教你做一个**真正能复用、能上线、能排查问题的项目模板**。

你可以记住这几个判断标准：

- 能快速创建新项目
- 配置尽量少，但关键项不缺
- 环境变量和代理要提前整理好
- 插件思路要清楚，别乱堆
- Vue 和 React 只保留框架差异，其他尽量通用

**老赵实操建议：**  
下次你新开一个 Vite 项目，不要从零手搓。先拿这套模板起步，按这个顺序做：先复制目录和基础配置，再接环境变量和代理，接着确认 Vue 或 React 插件是否正常，最后跑一次构建和联调检查。只要这四步都过了，模板就算真正能用了。这样你会发现，Vite 真正好用的地方，不只是开发快，而是它能让项目从一开始就更清爽、更好维护。
