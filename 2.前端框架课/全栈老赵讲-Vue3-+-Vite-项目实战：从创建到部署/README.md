# 第1章 项目开工：先把要做的东西想明白

## 开篇引入：别急着写代码，先把项目“定住”

很多同学一上来就想先开 `Vue3`、装 `Vite`、拉 `axios`，结果边做边想，最后页面越写越乱，接口一联调就开始返工。

老赵做项目，第一步从来不是敲代码，而是先想清楚四件事：

- 这个项目到底要做什么？
- 最后要交付成什么样？
- 用什么技术栈最合适？
- 页面、路由、接口、状态管理怎么配合？

本章只干一件事：先把全书贯穿的那个**完整可运行项目**定下来。后面所有章节，都会围绕这个项目一步一步推进，直到你能独立完成创建、开发、联调、打包和部署。

## 一、项目背景、业务场景与最终交付物说明

### 1.1 这个项目是做什么的？

本书围绕一个典型的前端业务项目展开，你可以把它理解成一个小型后台系统，用来完整走一遍 `Vue3 + Vite` 的项目流程。

它不是静态首页，也不是几个按钮演示，而是一个**可以运行、可以联调、可以部署**的完整项目。我们做的不是“学组件”，而是在做一套真正能跑起来的前端系统：页面要能看，数据要能动，接口要能通，最后还要能打包上线。

### 1.2 最终要交付到什么程度？

到本书结束时，你应该得到这样一个成果：

- 项目能本地启动
- 页面能正常访问
- 路由能切换
- 公共组件能复用
- 接口能通过 `axios 请求封装` 统一管理
- 状态能通过 `Pinia` 维护
- 环境变量能区分开发与生产
- 项目能完成 `打包配置`
- 打包后的产物能部署到生产环境基础服务器或静态资源服务上

也就是说，我们要做的是一个**完整可运行项目**，而不是只学概念。你不仅要知道 `Vue Router`、`Pinia` 是什么，还要把它们放进同一个项目里，分别解决页面跳转、跨页面状态和接口数据管理的问题。

### 1.3 统一本书的项目命名与主线

为了避免后面章节项目名称混乱，本书统一使用同一个示例项目：**“全栈老赵运营后台”**。

这个项目面向业务管理场景，核心目标很明确：

- 有清晰的登录入口
- 有统一的页面布局
- 有列表、详情、新增、编辑等常见页面
- 有接口联调
- 有状态共享
- 有打包部署

后面所有章节，不管是页面拆分、组件复用，还是路由、请求封装、环境变量和部署，都会围绕这个项目展开。

### 1.4 为什么要先明确业务场景？

因为前端项目不是单点知识拼图。你今天学路由，明天学状态管理，后天学接口封装，如果没有同一个项目串起来，知识点很容易散。

所以本书的策略是：  
**先定项目，再讲技术，再落到页面，再接接口，再做部署。**

这样做的好处很直接：

- 你知道每个知识点为什么出现
- 你知道它在项目里解决什么问题
- 你不会把代码写成互不相干的片段

## 二、为什么选 Vue3 + Vite 作为技术栈

### 2.1 为什么是 Vue3？

如果你已经会 `Vue3` 基础，那这本书正好适合你。我们不从语法糖开始讲，而是直接进入项目实战。

选择 `Vue3` 的原因很直接：

- 组件化能力更成熟，适合做中小型项目
- `Composition API` 更方便组织业务逻辑
- 和现代前端工程化配合更自然
- 更容易和 `Pinia`、`Vue Router`、`Vite` 协作

一旦项目有页面布局、列表展示、表单编辑、登录权限这些需求，`Vue3` 的组织方式就会很顺手。

### 2.2 为什么是 Vite？

如果说 `Vue3` 负责“怎么写页面”，那 `Vite` 就负责“怎么把项目跑起来、构建起来”。

选 `Vite`，主要因为它：

- 启动快，开发体验好
- 热更新快，适合边做边看效果
- 配置清爽，适合实战入门
- 和 `Vue3` 配合天然顺手

对于要从创建一路讲到部署的项目来说，`Vite` 很合适。它把地基打好，让你后面专心做业务和工程组织，不必卡在复杂构建配置里。

### 2.3 这套技术栈的组合价值

本书采用的组合是：

- `Vue3`：负责页面和业务逻辑
- `Vite`：负责项目创建与构建
- `Vue Router`：负责页面路由
- `Pinia`：负责状态管理
- `axios`：负责请求与接口联调

这套组合基本就是前端项目从开发到上线的主干骨架。后面不管你做后台管理系统还是业务型中台页面，思路都差不多。

## 三、项目功能清单与页面范围确认

### 3.1 先列功能，再动手

很多项目做不起来，不是因为技术难，而是因为功能边界不清楚。所以开工前，老赵建议你先列一张功能清单。

本书项目范围可以概括为：

- 登录页：完成系统入口
- 首页或概览页：展示核心信息
- 列表页：展示数据列表
- 详情页：查看单条信息
- 新增/编辑页：完成基础表单操作
- 404 或异常页：处理无效路由
- 基础布局：头部、侧边栏、主内容区

这些页面不复杂，但足够覆盖一个前端项目的常见结构。你做完这一套，基本就把“页面布局、组件拆分、路由配置、接口联调、状态管理”这些关键点都踩一遍了。

### 3.2 页面范围怎么定？

判断一个页面要不要做，有两个标准：

1. 它是否服务于核心业务流程
2. 它是否能帮助你串起项目主线

如果一个页面只是“看起来酷”，但和项目主流程没关系，就先放后面。

比如：登录页是系统入口；列表页适合练习接口请求、分页、筛选和状态更新；详情页则能让你看清列表到明细的数据流转。我们优先保证的是：**每一个页面都能在完整链路里找到位置。**

### 3.3 页面拆分的好处

提前确认页面范围，后面做 `页面布局` 和 `组件拆分` 时就不会乱。

比如：

- 顶部导航可以做成公共组件
- 左侧菜单可以做成布局组件的一部分
- 列表区可以拆成表格组件
- 表单区可以拆成可复用表单组件

这样做的目的很简单：让项目不至于随着功能增加而失控。前面多花一点时间把边界定清楚，后面就少踩很多重复造轮子的坑。

## 四、开发流程预览：从创建到部署的全链路

### 4.1 这本书不会只讲一段

本书的路线不是“讲完 Vue3 就结束”，而是按一个完整项目的真实流程推进。大致会经历这些阶段：

1. **创建项目**：使用 `Vite` 初始化 `Vue3` 项目  
2. **整理目录**：搭好项目结构  
3. **页面拆分**：把首页、列表页、详情页等拆开  
4. **组件复用**：抽公共布局和通用组件  
5. **路由配置**：用 `Vue Router` 管页面跳转  
6. **请求封装**：用 `axios 请求封装` 统一处理接口  
7. **状态管理**：用 `Pinia` 管跨页面共享数据  
8. **环境变量**：区分开发、测试、生产配置  
9. **打包部署**：完成 `打包配置` 和生产发布  
10. **常见问题处理**：修掉项目里最常见的坑  

你会发现，这条链路不是零散知识点，而是一个能闭环的工程流程。

### 4.2 为什么要按这个顺序学？

因为前端项目本来就是这样运转的：先有项目骨架，再有页面结构，再有路由流转，再有接口数据，再有共享状态，最后才是构建部署。

如果顺序反了，比如先学请求再学布局，或者先讲部署再讲页面，读起来就会很别扭，也不容易真正上手。按照项目推进的顺序走，你每学一步，项目就往前跑一步，成就感也更强。

### 4.3 这本书的节奏怎么把握？

你可以把整本书理解成一条清晰的实战流水线：

- 前半段先把项目搭起来
- 中间把页面、路由、接口、状态串起来
- 后半段把环境配置、打包和部署收尾

这样一路走下来，你拿到的不是一堆分散知识点，而是一个**从创建到部署的完整可运行项目**。这才是最有价值的地方。

## 1. 使用 Vite 创建 Vue3 项目

### 1.1 为什么用 Vite

本书项目选 **Vue3 + Vite**，不是为了追新，而是为了让开发更轻、更快、更顺手。Vite 启动快、热更新快、初始化简单，适合边做边调，也更适合一个从创建到部署的完整可运行项目。

对我们这个项目来说，Vite 的价值很直接：

- 启动快，适合高频修改页面和样式
- 热更新快，改完能立刻验证
- 配置相对简单，前期不容易被工程化细节绊住
- 后续接入 Vue Router、Pinia、axios 请求封装也比较自然

简单说，**Vite 不是让你少学东西，而是让你把精力更多放在项目本身。**

### 1.2 创建项目的标准动作

直接创建项目：

```bash
npm create vite@latest
```

然后按提示选择：

- 项目名称
- 框架：Vue
- 变体：Vue 或 Vue + TypeScript

如果你是第一次跟着做，老赵建议先用 **Vue + JavaScript** 跑通全流程。先把完整项目做起来，再考虑切到 TypeScript，节奏更稳。

创建完成后进入目录并启动：

```bash
cd 项目名
npm install
npm run dev
```

如果浏览器能打开 Vite 默认页面，说明第一步过了。这个默认页不是最终目标，但它证明项目已经具备最基础的运行条件。

### 1.3 创建成功的判断标准

项目创建成功，不是看命令敲完没有，而是看这几项是否成立：

- 项目目录生成正确
- 依赖安装没有报错
- 开发服务器可以启动
- 浏览器能正常访问默认页面
- 代码修改后热更新生效

这五项没问题，就说明**项目骨架已经立住了**。

## 2. 项目初始化后的目录与基础文件认识

### 2.1 先认清默认目录

Vite 创建后会生成一套默认结构，核心文件一般包括：

- `index.html`
- `src/main.js`
- `src/App.vue`
- `src/assets`
- `package.json`
- `vite.config.js`

老赵建议你先别急着改，先弄清楚每个文件的作用。很多人一上来就乱删默认内容，结果把入口删断，页面直接白屏。

### 2.2 每个基础文件负责什么

#### `index.html`
项目的 HTML 入口，应用挂载从这里开始。

#### `src/main.js`
Vue 应用启动入口，负责创建应用实例并挂载根组件。后面接路由、状态管理、全局样式，通常也从这里开始。

#### `src/App.vue`
根组件，是整个应用最外层的容器。后面的页面布局和路由出口都围绕它展开。

#### `src/assets`
放静态资源，比如图片、图标、字体、基础样式等。

#### `vite.config.js`
Vite 配置入口。后面做路径别名、代理转发、打包配置优化，都要用它。

#### `package.json`
项目说明书，依赖、启动命令、打包命令都在这里，排查问题时也经常要看它。

### 2.3 最容易犯的误区

初始化阶段最怕这几种操作：

- 入口文件没看懂就乱删
- 把 `App.vue` 当业务页直接堆内容
- 目录还没理顺就急着接接口和路由
- 默认结构都没跑通就开始改复杂配置

老赵提醒你一句：**先理解骨架，再谈功能。**骨架没稳，后面页面、路由、接口、状态管理都容易越做越乱。

## 3. 安装依赖并启动开发服务器

### 3.1 先把开发环境跑通

创建项目后，第一件事就是安装依赖并启动开发服务器：

```bash
npm install
npm run dev
```

如果你习惯用别的包管理工具，也可以对应执行：

```bash
pnpm install
pnpm dev
```

或者：

```bash
yarn
yarn dev
```

本书不强制你用哪一个，关键是先把项目顺利跑起来。因为后面你还要做页面布局、路由配置、接口联调、打包部署，这些都要求开发环境稳定。

### 3.2 启动成功后看什么

开发服务器启动后，别只看页面能打开，还要检查这些：

- 控制台有没有报错
- 浏览器是否正常显示默认页面
- 页面刷新是否稳定
- 代码修改后热更新是否生效
- 终端监听是否正常

这些都正常，说明项目的基础开发链路是通的。也就是说，你可以放心继续往下做。

### 3.3 为什么这一步必须认真

很多人做项目，前期图快，后面一出问题就开始怀疑 Vue3、Vite、Pinia、Router 哪个配错了。其实根源可能更基础：

- 依赖没有装完整
- Node 环境版本不合适
- 启动命令没跑对
- 目录结构被误改
- 安装过程有残留

## 一、项目页面结构总览与路由页面清单

### 1. 先把页面清单列出来

写页面之前，老赵建议你先把**页面清单**列出来。这一步会直接影响路由设计、目录结构和组件拆分方式。

按本书这个项目的节奏，页面先分成这几类：

- **首页**：项目入口，展示整体概览、推荐内容或业务入口
- **列表页**：展示某一类内容列表，支持基础筛选、分页、跳转详情
- **详情页**：展示单条数据的完整信息
- **公共页面**：如登录页、404 页面、无权限页，后续再补

这一章重点先把前三个页面跑起来。首页管“看全局”，列表页管“看集合”，详情页管“看单条”，这是很多 Vue3 项目里最常见的页面模型。把这三种页面做顺了，后面再加别的业务页，思路也会很清楚。

### 2. 路由清单怎么定

页面一多，路由就容易乱。老赵建议你按“**业务页面优先，公共页面其次**”来组织。

可以先这样设计：

- `/`：首页
- `/list`：列表页
- `/detail/:id`：详情页
- `/login`：登录页（后续使用）
- `/:pathMatch(.*)*`：404 页面

这里有个关键点：**详情页最好用动态路由参数**，比如 `:id`。这样列表页点进去，可以直接根据 id 进入对应详情页，后面联调接口也更自然。现在即使没接接口，也可以先用假数据验证流程，比如跳到 `/detail/1001`，页面先把这个 id 显示出来，至少能确认：**页面跳转通了，动态路由生效了**。

### 3. 路由清单和页面命名统一

本书建议统一使用这套命名：

- 首页：`HomeView`
- 列表页：`ListView`
- 详情页：`DetailView`
- 路由路径：`/`、`/list`、`/detail/:id`

这样好处很明显：

- 代码里一看就懂
- 路由名和页面职责一致
- 后续做 Vue Router 配置不会混乱
- 接口联调时更容易对应页面场景

如果今天叫“文章页”，明天叫“内容页”，后天又叫“商品页”，项目很快就会跑偏。咱们这本书是一个完整可运行项目，名字先统一，后面才好一路往下走。

### 4. 什么时候算设计合理

你可以用这三个标准判断：

- **页面职责单一**：一个页面只负责一类核心展示
- **路由语义清楚**：看路径就知道页面干什么
- **后续可扩展**：新增页面时不用推翻原结构

如果你看路由表，已经能一眼看懂“用户怎么从首页到列表，再从列表进详情”，这一步就算做对了。页面结构越早理顺，后面越不容易返工。

## 二、首页、列表页、详情页等核心页面拆分

### 1. 先按业务拆页面，再考虑组件复用

很多人一上来就问：“是不是先把组件拆细一点？”  
老赵告诉你：**先拆页面，再拆组件。**

顺序应该是：

1. 先确定有哪些页面
2. 再明确每个页面的职责
3. 再决定哪些部分抽成公共组件

这样页面边界更清楚，不会一开始就陷进组件迷宫。Vue3 的组件化是优势，但如果拆得太早、太碎，最后就会变成“组件很多，逻辑很散”。

### 2. 首页负责什么

首页是整个项目的“门面”。在本项目里，首页可以先做成一个**信息概览页**，包括：

- 顶部欢迎区
- 核心数据卡片
- 推荐内容入口
- 快捷导航区域

首页不用一开始就做得很复杂，关键是让用户进入项目后知道：  
**这个系统是干什么的，接下来可以去哪。**

### 3. 列表页负责什么

列表页是最常见的业务页面，通常负责：

- 展示一批数据
- 支持分页、筛选、搜索
- 点击某项进入详情页

列表页最重要的不是“多炫”，而是**信息层次清楚**。你要让用户快速找到目标内容，而不是在装饰里迷路。一个典型结构就是：上面搜索栏，中间内容列表，下面分页器。这个顺序也方便后面接接口。

### 4. 详情页负责什么

详情页是列表页的“下钻页面”，重点展示某条数据的完整信息，比如：

- 标题
- 基本描述
- 详细内容
- 相关标签
- 时间信息
- 返回列表入口

详情页要注意：**不要把它做成第二个列表页**。它的核心是“单条数据完整展开”，不是继续堆平级信息。老赵建议你保留一个清楚的“返回列表”按钮，别让用户看完详情找不到回去的路。

### 5. 页面之间怎么串起来

这三个页面可以理解成一条完整路径：

**首页 → 列表页 → 详情页**

这个顺序符合用户习惯：

- 从首页进入整体入口
- 从列表页选择目标
- 在详情页查看完整信息

如果页面跳转顺畅，用户就不会觉得项目“散”。这条链路也是后面接口联调的基础，因为接口通常就是围绕“首页概览、列表获取、详情查询”这条线展开的。

## 三、基础页面布局搭建：头部、侧边栏、内容区

### 1. 为什么先搭布局

页面布局就是项目的骨架。  
骨架不立，功能没地方放。

在 Vue3 项目里，常见的基础布局一般包括：

- **头部 Header**：项目名称、用户信息、操作入口
- **侧边栏 Sidebar**：页面导航
- **内容区 Content**：当前路由页面展示区域

这一步先搭好，后面首页、列表页、详情页直接往内容区塞就行。

### 2. 一个适合实战的布局结构

推荐的结构思路是：

- 外层是整个应用布局容器
- 顶部放 Header
- 左侧放 Sidebar
- 右侧主区域放 `router-view`

这样路由切换时，**只有内容区变化，头部和侧边栏保持不动**。这是很多后台类项目最常用的布局方式，也非常适合我们这种完整可运行项目的实战路线。

老赵提醒你，这种布局能把公共区域和页面内容分开，后面接 Vue Router 的时候更自然。路由一变，页面内容自动跟着变，但整体框架不动，这就是布局设计的价值。

### 3. 布局和页面职责要分开

这一章只讲页面拆分和基础布局，不把组件复用、请求封装、接口联调那些内容展开太多，避免你前脚页面还没立稳，后脚就被一堆功能绕晕。

你可以先记住一个原则：  
**布局负责框架，页面负责内容。**

也就是说：

- Header、Sidebar、主容器属于布局层
- 首页、列表页、详情页属于业务页面层

这样分层后，后面要做 Vue Router、Pinia、axios 请求封装、接口联调、环境变量、打包配置，都会顺很多。现在先把页面骨架跑起来，后续内容才有承接点。

### 4. 常见误区

#### 误区一：每个页面都自己写一套头部和侧边栏
这样重复代码多，维护也麻烦。  
正确做法是：**公共布局抽出来，页面只负责自己的内容。**

#### 误区二：布局和业务逻辑混在一起
比如列表页里又写布局，又写请求，又写筛选逻辑。  
正确做法是：**布局归布局，业务归业务。**

#### 误区三：一开始就追求复杂 UI
先别想着做得特别花。  
本章阶段先保证：**结构清楚、跳转顺畅、页面可运行**。

你现在做的是项目主干，不是视觉大赛。先跑通，再优化，这才是实战节奏。

## 四、页面间关系与展示顺序设计

### 1. 页面不是孤立的，要有走法

很多初学者写页面时，只想着“有页面就行”，但页面之间没有关系。这样项目虽然能打开，却像散装零件，没法形成完整体验。

老赵建议你先想清楚：

- 用户从哪进来？
- 先看到什么？
- 下一步点哪里？
- 点完去哪个页面？

这就是页面之间的**展示顺序设计**。实战项目里，页面不是孤立的，它们必须组成一条完整路径，项目才真的像项目。

### 2. 推荐的展示顺序

最稳妥的顺序是：

1. **首页展示项目概览**
2. **首页进入列表页**
3. **列表页点击进入详情页**
4. **详情页返回列表页**
5. 后续再从首页扩展更多入口

这个顺序符合真实用户操作，也方便你一步一步验证路由和布局是否正常。

你可以先在首页放一个“去列表页”的按钮；列表页里每一项都能跳到详情页；详情页里再放一个“返回列表”的按钮。这样一条完整链路就打通了。先别急着加搜索、过滤、收藏、点赞这些扩展功能，把基本流转做好，后面再加。

### 3. 如何判断是否合理

你可以用这张自检表：

- 首页是否能自然引导用户进入列表页？
- 列表页是否能快速进入详情页？
- 详情页是否方便返回列表页？
- 每个页面职责是否明确？
- 路由跳转后布局是否一致？

如果这些都满足，说明页面关系设计已经具备项目实战的基本样子了。换句话说，你现在不是在“写几个页面”，而是在搭一个能持续扩展的项目结构。

## 五、先完成静态页面骨架，再逐步补功能

### 1. 为什么要先做静态骨架

因为这是最稳的开发方式。  
不要一开始就急着接接口、上 Pinia、做复杂交互。应该先把页面静态结构跑出来，再逐步补功能。

所谓静态骨架，就是先完成这些内容：

- 页面基本结构
- 布局区域划分
- 路由跳转
- 基础占位内容
- 样式层级和视觉关系

这一步做完，你就已经能看到一个像样的项目雏形。对 Vue3 + Vite 项目来说，这种循序渐进的方式特别重要，因为 Vite 启动快、热更新快，很适合边搭骨架边验证。

### 2. 正确推进顺序

老赵建议你按这个顺序推进：

#### 第一步：搭布局
先把 Header、Sidebar、Content 区搭好。

#### 第二步：建页面
把首页、列表页、详情页先建出来，哪怕只是占位文本。

#### 第三步：接路由
把页面和路由对应起来，确保能切换。

#### 第四步：做基础样式
先保证结构清晰、层级正常。

#### 第五步：补交互入口
比如列表页跳详情页、返回按钮等。

这样做的好处是：项目始终可运行，不会出现“写一半就卡住”的情况。这个状态很重要，因为后面还要继续做 Vue Router、Pinia、axios 请求封装、接口联调、环境变量、打包配置和生产部署，任何一步都依赖前面的结构稳定。

### 3. 后续功能怎么补

静态骨架稳定后，再逐步加入：

- 接口联调
- Vue Router 细化配置
- Pinia 状态管理
- axios 请求封装
- 环境变量区分
- 打包配置优化
- 生产部署基础处理

也就是说，这一章做的不是终点，而是**给后面所有功能铺路**。你现在搭的是“能继续长大”的项目，不是写完就丢的示例代码。

# 第4章 组件复用：把通用部分做成可重复使用的积木

这一章我们要做的事很明确：**把项目里那些长得像、逻辑像、交互也像的部分抽出来，做成可复用组件。**  
前面页面已经搭起来，接口也开始联调了，这时候如果还把所有内容都堆在页面里，项目一大，代码就会散，改一个样式要翻好几个文件，改一个弹窗还可能牵动多个页面。

老赵做项目有个很实在的原则：**能复用的尽量复用，必须个性化的再单独写。**  
这一章我们就围绕这个原则，结合 Vue3 + Vite 的实战，把按钮、表单项、分页、弹窗这些通用部分拆出来，做成项目里的“积木”。

## 5.1 先看再拆：什么东西值得抽成组件？

先别急着写组件，第一步是先看页面结构。

很多同学喜欢一上来就把页面里的小块全拆开，结果组件太碎，目录看着热闹，维护起来反而更乱。  
老赵给你一个简单标准：**不是看它小不小，而是看它有没有重复使用的可能。**

### 1. 适合抽成组件的几类情况

项目里最常见的可复用内容，通常有这几种：

- **UI 结构重复**：统一风格的按钮、卡片、查询区
- **交互逻辑重复**：确认弹窗、分页切换、提示状态
- **数据结构相似**：列表页的搜索区、操作区、分页区
- **样式规则统一**：标题、间距、表单布局一致

抽出来以后，页面会更清爽，组件也更好维护。  
你可以简单理解成：**页面负责业务，组件负责通用结构。**

### 2. 不建议一上来就拆的情况

有些东西看着能复用，但其实不适合太早抽：

- 只有一个页面用到，未来大概率也不会复用
- 内部逻辑差异太大，强行参数化会写出一堆 `if/else`
- 业务还不稳定，需求经常改

老赵见过不少项目，刚开始把“可能会复用”的东西拆得特别细，结果需求一变，组件参数也跟着改，最后不是省事，而是更绕。  
所以你要记住：**组件不是拆得越早越好，而是拆得越合适越好。**

### 3. 老赵的三问法

动手前先问自己三个问题：

1. 它会不会在别的页面再出现？
2. 它的外观和行为是不是比较稳定？
3. 它能不能通过 `props`、`slot` 之类的方式控制差异？

如果大多数答案都是“是”，那就值得抽。  
如果总是“看情况”，先放在页面里观察一下更稳。

## 5.2 按钮、表单项、分页、弹窗怎么拆？

这一节我们直接看项目里最常见的四类复用组件怎么落地。  
注意，这一章只讲**组件复用**，不和页面拆分混在一起。页面拆分是页面层的事，组件复用是把通用块抽出来，两个概念要分开。

### 5.2.1 按钮：统一项目操作入口

按钮是项目里最容易重复的地方。  
比如列表页里的“查询”“重置”“新增”“删除”，文字不同，但样式规则、禁用状态、加载状态往往差不多。

#### 适合抽象的点

- 按钮类型：primary、default、danger
- 尺寸：large、default、small
- 状态：loading、disabled
- 图标：前置图标、后置图标

#### 复用思路

按钮别抽得太复杂。  
如果项目只需要统一基础样式，可以先做一个轻量级 `BaseButton`，负责：

- 统一圆角、间距、字体
- 支持 `type`
- 支持 `loading` 和 `disabled`
- 通过 `slot` 放按钮内容

```vue
<BaseButton type="primary" :loading="saving">保存</BaseButton>
```

按钮还有一个很实用的点：**把“能不能点”交给外部控制。**  
比如接口提交中按钮进入 loading，同时禁用点击，避免重复提交。

---

### 5.2.2 表单项：把输入规范统一起来

表单项是最容易越写越散的地方。  
同一个输入框，有的 label 在左边，有的在上面；有的带必填星号，有的没有；有的有提示文案，有的没有。最后用户体验不统一，代码也不好收拾。

#### 表单项适合抽的内容

- label 与输入框布局
- 必填标记
- 提示信息
- 错误信息位置
- 不同类型输入控件的外层结构

#### 推荐拆法

表单项通常有两种拆法：

1. **基础包裹型**：统一布局，内部控件由父组件传入
2. **业务增强型**：在基础布局上封装项目常用逻辑

在 Vue3 项目里，老赵更推荐先做第一种。  
先把“表单行”统一起来，不要一上来就把“姓名输入框”“手机号输入框”都封成组件。

这样做的好处是：

- 灵活性高
- 复用成本低
- 不容易被业务绑死

尤其在**接口联调**阶段，字段很可能随着后端返回结果变化。基础包裹型组件更稳，输入控件怎么变，父组件自己调整就行。

---

### 5.2.3 分页：列表页最典型的公共块

分页组件非常适合复用，因为只要是列表页，基本都会有：

- 当前页
- 每页条数
- 总条数
- 页码切换
- pageSize 改变

这部分逻辑重复度高，而且和**接口联调**关系很紧。

#### 分页组件的复用重点

- 接收分页参数：`currentPage`、`pageSize`、`total`
- 触发切换事件：`change`、`size-change`
- 不把接口请求写死在组件里
- 只负责展示和抛出事件

这里要特别提醒：**分页组件不要直接请求接口。**  
它应该是一个“纯组件”，只负责把变化通知给父组件，由页面去重新拉数据。

这样分页组件就不会和某个业务页面绑死，别的列表页也能直接用。  
你可以把它理解成页面和接口之间的传话筒：用户切页，分页把信息发给页面，页面再去请求新数据。

---

### 5.2.4 弹窗：复用价值最高的交互组件之一

弹窗在项目里出现得非常频繁：新增、编辑、确认删除、查看详情，都离不开它。

#### 弹窗复用时要考虑什么？

- 标题是否可配置
- 内容是否通过插槽传入
- 是否支持显示/隐藏控制
- 是否支持确认、取消事件
- 是否有统一宽度、遮罩和关闭行为

#### 推荐设计

弹窗最好分两层：

- **基础弹窗层**：负责外壳、标题、按钮、关闭行为
- **业务内容层**：通过 slot 填入不同内容

比如“新增用户”和“编辑订单”可以共用一个弹窗外壳，只是内部表单不同。  
这样抽出来以后，项目里能少很多重复结构。

弹窗还有一个关键点：**不要让它替你做业务判断。**  
比如“确认删除后要不要刷新列表”“保存成功后要不要提示”，这些都应该由页面控制。弹窗只负责把“确认”和“取消”事件抛出去，这样它才真正通用。

---

## 5.3 props、emit、slot：组件复用的三把钥匙

组件能不能真正复用，不取决于它写没写出来，而取决于父子组件之间能不能顺畅沟通。  
这里最常用的三个工具就是：`props`、`emit`、`slot`。

### 5.3.1 props：父组件把数据传给子组件

`props` 的作用很直接：**把可变部分交给外部控制。**  
比如按钮文字、弹窗标题、分页总数、表单字段值，这些都应该尽量通过 `props` 传入。

#### 适合放到 props 的内容

- 文案
- 状态值
- 配置项
- 显示隐藏控制
- 样式相关的可配置值

#### 误区

有些同学喜欢把所有东西都写死在组件里，这样组件看着简单，其实一点也不复用。  
老赵建议你：**组件内部保留默认值，外部通过 props 覆盖。**

这样组件既能开箱即用，又能适应不同页面的差异。  
比如同一个弹窗，在新增场景下标题叫“新增数据”，在编辑场景下标题叫“编辑数据”，这类差异就特别适合通过 `props` 控制。

---

### 5.3.2 emit：子组件把动作通知给父组件

`emit` 负责“往外说话”。  
比如：

- 点击确认按钮，通知父组件执行保存
- 点击取消按钮，通知父组件关闭弹窗
- 分页切换，通知父组件重新请求数据

注意，子组件一般不直接做业务决策，而是把事件抛出去，让父组件处理。  
这样组件会更纯，也更容易复用。

老赵建议你写复用组件时，先想清楚两件事：

1. 这个组件内部只负责什么？
2. 它需要向外告诉父组件什么？

这两件事定住了，组件边界基本也就清楚了。

---

### 5.3.3 slot：把不确定的内容交给外部填充

`slot` 很适合处理“壳固定、内容变化”的场景。  
比如：

- 弹窗主体内容不固定
- 表单项内控件不固定
- 卡片内部展示内容不固定

slot 的价值就是：**组件负责结构，外部负责内容。**

你可以把它理解成一个“预留位置”。  
页面想放什么，就往里塞什么。

在 Vue3 里，`slot` 和 `props`、`emit` 配合起来，基本就能覆盖大部分通用组件场景。  
如果一块内容既要统一外壳，又要允许内部变化，那优先考虑 `slot`。

---

## 5.4 局部组件和全局组件：边界要分清

组件复用不是越“全局”越好。  
很多项目后期难维护，不是因为组件不够，而是因为**全局组件滥用**。

### 5.4.1 什么是局部组件？

局部组件就是某个页面、某个模块专门用的组件。  
比如订单列表页里的筛选区、用户详情页里的信息卡片，这类一般放在页面目录下，按需引入。

#### 适合局部的情况

- 只被一个页面使用
- 业务逻辑强，改动频繁
- 结构专属，复用价值低

局部组件最大的好处就是贴业务，跟页面近，后面改需求时查找和修改都方便。

### 5.4.2 什么是全局组件？

全局组件通常是全项目复用频率很高的基础组件。  
比如：

- 通用按钮
- 通用弹窗
- 通用分页
- 通用空状态
- 通用加载态

这类组件可以在项目入口统一注册，或者单独维护一个组件目录。

### 5.4.3 边界怎么判断？

老赵给你一个简单标准：

- **高频使用、低业务耦合**：考虑全局
- **低频使用、强业务耦合**：保留局部
- **还能继续变化，但已经形成稳定模式**：先局部，成熟后再升级为全局

别为了“高级感”把所有组件都全局化。  
全局组件太多，后面你会不知道它到底被谁用了，改动也会越来越谨慎，反而拖慢开发。

实际项目里，老赵一般会先让组件在局部场景里跑通，等它在两个以上页面都稳定用了，再考虑提升为全局。这样更稳，也更符合真实开发节奏。

## 5.5 复用组件在项目中的落地方式：怎么从页面改造成积木？

思路有了，接下来就是落地。  
老赵带你走一个实战流程：**从现有页面里识别重复块，再逐个抽离。**

### 第一步：先看页面结构

通常一个列表页会分成这几块：

- 顶部标题
- 查询条件区
- 操作按钮区
- 数据列表区
- 分页区
- 弹窗区

先别急着拆，先在脑子里把结构过一遍。  
看哪些块只是外观重复，哪些块是业务重复。

如果一个区域只是视觉上很像，但内部字段和交互完全不一样，那就先别抽。  
如果一个区域“外面看着不一样，里面其实逻辑一样”，那通常值得考虑复用。

### 第二步：抽基础组件

优先抽这些：

- `BaseButton`
- `BaseDialog`
- `BasePagination`
- `BaseFormItem`

因为它们复用价值高，而且不太依赖具体业务。

老赵建议你抽组件时，不要一口气把所有可能都做进去。  
先做“够用版”，先服务当前项目。等后面真遇到新场景，再慢慢扩展能力。

### 第三步：让页面只保留业务逻辑

页面组件应该主要负责：

- 发请求
- 控制状态
- 传参给子组件
- 接收子组件事件
- 组织业务流程

而 UI 的重复部分尽量交给通用组件。  
这样页面就会变“薄”，后期维护成本会明显下降。

做完这一步，你会发现页面代码更像“业务编排”，而不是“堆结构”。这就是组件复用最直接的收益。

### 第四步：验证是否真的复用成功

一个复用组件是否合格，不是看你写得顺不顺，而是看它能不能满足下面几个条件：

- 别的页面拿来能直接用
- 新页面接入时改动少
- 逻辑不会跟具体业务绑死
- 出问题时定位清晰

如果某个组件每接一个页面就要改一大堆，那它其实还不算真正复用。  
真正好用的组件，应该是换个页面也不怕，最多传几个参数、换一段 slot 内容，就能继续干活。

---

## 5.6 实战检查清单：抽完以后别忘了验收

组件拆完之后，不是“写完就行”，还得做一轮小检查。  
老赵建议你按下面这张清单过一遍。

### 1. 组件是否真通用

先看它是不是只服务了当前页面。  
如果只是换了个文件名，内容还是完全贴着某个业务，那还不算真正的通用组件。

### 2. props 是否够清楚

看参数有没有命名统一、语义明确。  
别出现一堆 `type1`、`type2`、`flagA` 这种看不懂的名字，后面连自己都记不住。

### 3. emit 是否只做事件通知

组件内部不要顺手把接口请求、列表刷新、路由跳转都包进去。  
这些事应该交给父组件处理，子组件只管发事件。

### 4. slot 是否真的必要

不是所有地方都要加 slot。  
如果内容固定，写 slot 反而增加复杂度。能简单就简单，别把通用组件做成“万能组件”。

### 5. 全局注册是否过量

项目里真正该全局的组件并不多。  
如果你发现全局组件越来越多，先停下来想一想，是不是抽得太早、抽得太碎了。

## 5.7 本章小结：复用不是偷懒，是工程化

组件复用这件事，说白了不是为了少写几行代码，而是为了让项目更稳、更清楚、更容易扩展。  
在 Vue3 + Vite 的项目里，通用组件一旦抽好，后面的路由页面、接口联调、状态管理都会轻松很多，因为页面结构更统一了，业务边界也更清楚了。

### 老赵带你做

这一章你真正要动手完成的是：

1. 识别当前项目里可复用的 UI 块
2. 抽出按钮、表单项、分页、弹窗这几类基础组件
3. 学会用 `props`、`emit`、`slot` 把组件做活
4. 分清局部组件和全局组件的边界
5. 让页面回归业务，让组件负责通用结构

### 赵老师提醒

- 不要为了复用而复用，先看是不是有真实重复场景
- 不要把业务逻辑塞进基础组件里，组件越纯越好复用
- 不要滥用全局组件，边界不清后期会很难维护
- 复用组件的目标不是“写得漂亮”，而是“后面页面越做越省力”

下一章我们继续往下走，进入路由配置，把这些页面和组件真正串成一个完整可运行项目。

# 第5章 配路由：让页面之间能顺畅切换

前面我们已经把项目骨架搭起来了，首页、列表页、详情页这些基础页面也都准备好了。接下来要做的，就是把这些页面真正串起来，让它们能跳转、能带参数、能根据用户行为切换。这样一来，项目才算从“静态页面集合”变成一个完整应用。

这一章老赵就带你把 **Vue Router** 配起来，顺手把我们这个完整可运行项目的页面流转打通。你会发现，路由不是简单装个插件就结束了，而是要结合项目目录、页面布局、导航菜单、详情页跳转和基础守卫一起设计。后面接着做 **Pinia 状态管理、axios 请求封装、接口联调** 时，整个链路才会顺。

---

## 一、先把路由安装好：项目里要有一条清晰的“路”

在 Vue3 + Vite 项目里，路由是非常标准的基础能力。咱们先装上它：

```bash
npm install vue-router
```

安装完以后，先把目录理顺。老赵建议专门建一个路由目录，集中管理路由表和路由实例：

```bash
src/router/
  index.ts
  routes.ts
```

这样做的好处很直接：路由配置统一放一处，后面查改方便；页面、菜单、守卫、参数也都围着同一套路由体系走，不容易乱。

### 1. 创建路由表

先把页面和路径对应起来。咱们这个项目里，页面命名尽量统一，老赵这里按这套来：

- `Home`：首页
- `ArticleList`：文章列表页
- `ArticleDetail`：文章详情页
- `Login`：登录页
- `UserCenter`：个人中心页

`src/router/routes.ts`：

```ts
export const routes = [
  {
    path: '/',
    name: 'Home',
    component: () => import('@/views/Home.vue'),
  },
  {
    path: '/articles',
    name: 'ArticleList',
    component: () => import('@/views/ArticleList.vue'),
  },
  {
    path: '/articles/:id',
    name: 'ArticleDetail',
    component: () => import('@/views/ArticleDetail.vue'),
    props: true,
  },
  {
    path: '/login',
    name: 'Login',
    component: () => import('@/views/Login.vue'),
  },
  {
    path: '/center',
    name: 'UserCenter',
    component: () => import('@/views/UserCenter.vue'),
    meta: { requiresAuth: true },
  },
]
```

这一步最重要的不是条数多，而是先把页面映射关系定下来。后面新增页面，也按这个规范继续加。

### 2. 创建路由实例并挂载到项目里

`src/router/index.ts`：

```ts
import { createRouter, createWebHistory } from 'vue-router'
import { routes } from './routes'

const router = createRouter({
  history: createWebHistory(),
  routes,
})

export default router
```

然后在 `main.ts` 里挂载：

```ts
import { createApp } from 'vue'
import App from './App.vue'
import router from './router'

createApp(App).use(router).mount('#app')
```

这里用的是 `createWebHistory()`，地址栏更干净，体验也更像正式应用。不过这种模式下，后面打包部署时服务器要配合，否则刷新页面可能会 404。这个坑先记着，后面讲部署时还会回来处理。

### 3. 先检查路由是否跑通

先做最朴素的验证：

- 能不能访问首页 `/`
- 能不能切到文章列表 `/articles`
- 能不能进详情页 `/articles/1`
- 页面切换后地址栏会不会同步变化
- 刷新后是否还停留在当前页面

这几项正常，说明 Vue Router 的基础骨架已经搭好了。

---

## 二、路由表设计与页面映射：别让路径写成“绕口令”

路由这东西，刚开始看着简单，真到项目一大就容易乱。老赵见过很多项目，前期页面不多，路径随便写；后面页面一多，`/page1`、`/list2`、`/detailInfo` 混在一起，谁看谁头疼。

所以这一章咱们重点讲一个原则：**路径负责表达页面用途，name 负责表达程序内部身份**。

### 1. 路径要语义化

建议按业务来写，而不是按文件名来写：

- `/`：首页
- `/articles`：文章列表
- `/articles/:id`：文章详情
- `/login`：登录页
- `/center`：个人中心

好处很直接：

- 用户一眼能看懂；
- 分享链接更友好；
- 后期排查问题更快；
- 接口联调时也更容易对上业务。

### 2. name 要统一

`name` 是给程序内部跳转用的，建议统一成一套风格：

- `Home`
- `ArticleList`
- `ArticleDetail`
- `Login`
- `UserCenter`

不要出现 `home`、`HomePage`、`indexPage` 混着写。看起来只是名字不同，实际会影响路由跳转、菜单激活、权限判断等一串逻辑。

### 3. 页面映射关系要和目录保持一致

路由和页面目录最好一一对应。比如：

```bash
src/views/
  Home.vue
  ArticleList.vue
  ArticleDetail.vue
  Login.vue
  UserCenter.vue
```

这样你在路由里看到一个名字，就能立刻知道页面文件在哪儿。项目做大以后，这种一致性特别重要。

### 4. 子路由先留个口子

如果后面个人中心还会拆成“基本信息”“我的收藏”“我的订单”，那就可以把它设计成子路由。现在不急着展开复杂结构，但先把思路定下来：**父页面负责布局，子页面负责内容切换**。这样扩展起来会很顺。

---

## 三、导航菜单与页面切换：让用户知道自己在哪儿

路由配好以后，还得有入口。没有导航菜单，用户不知道页面怎么去，也不知道当前在哪儿。一个完整可运行项目，不能只有页面，还得有清楚的流转入口。

### 1. 用 `RouterLink` 做基础导航

如果是顶部导航栏，直接用 `RouterLink` 就行：

```vue
<template>
  <nav class="nav">
    <RouterLink to="/">首页</RouterLink>
    <RouterLink to="/articles">文章列表</RouterLink>
    <RouterLink to="/login">登录</RouterLink>
    <RouterLink to="/center">个人中心</RouterLink>
  </nav>
</template>
```

它有几个好处：

- 不会整页刷新；
- 自动和路由联动；
- 当前激活项容易处理；
- 写法比原生 `a` 标签更适合 Vue 项目。

### 2. 用程序式跳转处理业务动作

有些跳转不是点菜单，而是点按钮、提交表单、登录成功之后自动跳。这时候就用 `useRouter()`。

比如从列表页跳到详情页：

```vue
<template>
  <div v-for="item in list" :key="item.id">
    <span>{{ item.title }}</span>
    <button @click="goDetail(item.id)">查看详情</button>
  </div>
</template>

<script setup lang="ts">
import { useRouter } from 'vue-router'

const router = useRouter()

const goDetail = (id: number) => {
  router.push({
    name: 'ArticleDetail',
    params: { id },
  })
}
</script>
```

这里建议优先用 `name + params` 的写法。这样哪怕后面路径微调，跳转逻辑也不至于全改。

### 3. 菜单和页面要保持同一套命名

这一点很容易被忽略。比如菜单上写“文章详情”，路由名却叫 `DetailPage`，页面路径又叫 `/articleInfo`。短期看能用，长期一定乱。

老赵建议你保持统一：

- 菜单名称：文章列表、文章详情、登录、个人中心
- 路由名称：`ArticleList`、`ArticleDetail`、`Login`、`UserCenter`
- 页面文件：`ArticleList.vue`、`ArticleDetail.vue`

这样一套下来，阅读、维护、联调都会舒服很多。

---

## 四、动态路由参数与详情页跳转：同一张页面展示不同内容

列表页点进去看详情，这是最常见的业务流。这个场景最适合动态路由参数。

### 1. 动态参数怎么写

比如：

- `/articles/1`
- `/articles/2`
- `/articles/3`

这里的 `id` 就是动态参数：

```ts
{
  path: '/articles/:id',
  name: 'ArticleDetail',
  component: () => import('@/views/ArticleDetail.vue'),
  props: true,
}
```

`props: true` 的意思是把路由参数转成组件属性。这个写法更干净，组件拿参数时也更清楚。

### 2. 详情页怎么接参数

如果你想直接从路由对象里取，也可以：

```ts
import { useRoute } from 'vue-router'

const route = useRoute()
const id = route.params.id
```

如果用 `props: true`，就能直接在组件里接收：

```vue
<script setup lang="ts">
defineProps<{
  id: string
}>()
</script>
```

老赵建议你记住这两个方式的区别：

- `route.params`：上手快，直接取；
- `props`：组件更独立，更适合后面做复用和测试。

### 3. 列表页跳详情页的完整动作

```ts
const goDetail = (id: number) => {
  router.push({
    name: 'ArticleDetail',
    params: { id },
  })
}
```

这一步看着简单，但它已经把“列表 -> 详情”串起来了。后面接上接口联调，这个 `id` 就会真正参与请求，详情页的数据也会随之变化。

### 4. 这里最容易踩的坑

- 路由里写了 `:id`，跳转时却没传；
- 传的是数字，页面里按字符串处理，类型混乱；
- 详情页刷新后只显示空白，因为没有根据参数重新请求；
- 页面能跳，但数据没跟上，用户以为页面坏了。

所以动态路由不是只负责“跳过去”，而是要配合后面的接口请求，把数据也带过去。这个链路要固定住：

1. 列表页拿到数据；
2. 点击某条数据，带着 `id` 跳转；
3. 详情页读取 `id`；
4. 调接口拿详情；
5. 页面渲染真实内容。

这才是完整可运行项目里该有的详情页。

## 五、路由守卫：给需要保护的页面加一道门

有些页面不是谁都能进，比如个人中心、订单页、后台页，这时候就要用路由守卫。

### 1. 守卫的基本作用

路由守卫就是在进入页面前先检查一下：

- 用户有没有登录；
- 当前页面是不是登录后才能看；
- 已登录用户还要不要进登录页；
- 某些页面是否需要特殊权限。

它的本质不是“拦人”，而是“把流程理顺”。

### 2. 基础全局前置守卫

```ts
router.beforeEach((to, from, next) => {
  const token = localStorage.getItem('token')

  if (to.path === '/login' && token) {
    next('/')
    return
  }

  if (to.meta.requiresAuth && !token) {
    next('/login')
    return
  }

  next()
})
```

路由里配合 `meta` 一起用：

```ts
{
  path: '/center',
  name: 'UserCenter',
  component: () => import('@/views/UserCenter.vue'),
  meta: { requiresAuth: true },
}
```

这样就很清楚了：页面自己声明是否需要登录，守卫统一检查。后面如果要扩展更多页面，也只要继续加 `meta`，不用重写一套判断。

### 3. 守卫里尽量只做“判断”，别塞太多业务

老赵提醒你，守卫适合做这几件事：

- 判断是否登录；
- 判断是否允许进入；
- 做简单跳转。

不适合在里面塞：

- 大量接口请求；
- 很复杂的业务逻辑；
- 一堆嵌套判断。

原因很简单：守卫应该快、准、轻。逻辑一多，页面切换就会拖慢，调试也会变麻烦。

### 4. 基础场景先做透

这一章我们先把最常见的两类情况处理好就行：

- 没登录，不能进个人中心；
- 已登录，别再去登录页。

后面如果项目需要更细的权限控制，再继续加角色权限、按钮权限、菜单权限。先把基础链路走顺，别一开始就把系统做复杂了。

---

## 六、和后续章节怎么衔接：路由先通，数据再跟上

这一章虽然主要讲路由，但它不是孤立的。它实际上是在给后面的章节铺路。

### 1. 和 axios 请求封装的关系

详情页拿到 `id` 之后，下一步就是请求数据。也就是说，路由参数会直接进入后面的 `axios 请求封装` 和 `接口联调`。如果路由没设计好，后面请求层也会跟着乱。

### 2. 和 Pinia 的关系

登录状态、用户信息、菜单激活状态，这些都可以和 Pinia 配合起来。路由负责跳转，Pinia 负责存状态，两者配合，页面才会更自然。

### 3. 和页面布局的关系

导航菜单、顶部栏、侧边栏这些页面布局元素，本质上都要服务于路由切换。路由一通，布局就知道该显示什么、切到哪里。

# 第6章 封装请求：让接口联调不再到处写重复代码

前面几章，我们已经把页面框架、路由和组件搭好了。接下来，真正让这个 **Vue3 + Vite 完整可运行项目**“活起来”的关键，就是把后端数据接进来。

很多同学第一次做项目时，接口请求基本都是这样：这个页面点一下就 `axios.get()`，那个页面提交一下又 `axios.post()`，再来一个页面还得重新写 `baseURL`、请求头、错误提示、token 处理。写着写着，代码越来越乱，联调也越来越痛苦。

所以这一章，老赵就带你把这件事理顺：**统一封装请求、统一管理接口、统一处理错误、统一做联调。** 以后你做 Vue3 项目，不管是列表、详情还是提交表单，都能按同一套套路走。

## 一、axios 基础安装与二次封装：先把“请求底座”搭稳

### 1.1 为什么要先封装，再调用？

封装请求，不是为了显得高级，而是为了后面少踩坑。

如果不封装，请求代码会散落在各个页面里，常见问题有：

- `baseURL` 到处写，后面改接口地址很麻烦
- token 携带逻辑重复
- 成功、失败提示不统一
- 统一错误处理没法维护
- 接口联调时不好定位问题

所以在本书里，**axios 二次封装**就是把“请求公共能力”单独抽出来，让页面只关心“我要调哪个接口”，不用关心“请求怎么发”。

### 1.2 基本安装

先装 axios：

```bash
npm install axios
```

然后在 `src/services/request.js` 或 `src/utils/request.js` 中统一封装。老赵建议你把请求层放在 `src/services`，接口文件也统一收纳，结构会更清楚，也方便后面按业务模块拆分接口。

### 1.3 一个最小可用的封装思路

核心就三步：

1. 创建 axios 实例
2. 设置基础配置
3. 暴露统一请求方法

```js
import axios from 'axios'

const request = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL,
  timeout: 10000
})

export default request
```

先把“请求底座”搭起来，后面再补拦截器、统一返回格式和错误处理。做项目最怕一上来什么都想做全，结果反而卡住。

---

## 二、请求拦截器、响应拦截器与统一错误处理：把公共逻辑集中起来

### 2.1 请求拦截器要做什么？

请求拦截器的作用，就是请求发出去之前统一处理一遍。

常见场景包括：

- 自动带上 token
- 设置统一请求头
- 处理加载状态
- 根据环境切换参数

比如登录后需要鉴权的接口，通常都要带 token。这个逻辑不应该每个页面手写一遍，正确做法就是在请求拦截器里统一加上。

```js
request.interceptors.request.use(
  (config) => {
    const token = localStorage.getItem('token')
    if (token) {
      config.headers.Authorization = `Bearer ${token}`
    }
    return config
  },
  (error) => Promise.reject(error)
)
```

如果后面你用 **Pinia** 管理登录态，也可以把 token 放到 store 里再读取，思路一样：统一拿、统一塞、统一发。

### 2.2 响应拦截器要做什么？

响应拦截器就是请求回来以后统一收口。

你要关心的不是每个页面怎么判断接口返回，而是：

- 成功时返回什么
- 失败时怎么提示
- 业务错误怎么拦截
- token 失效时怎么处理

很多后端返回结构不一样，但项目里最好统一成一种风格。比如约定：

- `code === 0` 表示成功
- 其他 code 代表业务失败
- 网络错误单独处理

```js
request.interceptors.response.use(
  (response) => {
    const res = response.data
    if (res.code === 0) {
      return res.data
    }
    return Promise.reject(new Error(res.message || '请求失败'))
  },
  (error) => {
    let message = '网络异常，请稍后重试'
    if (error.response?.status === 401) {
      message = '登录已失效，请重新登录'
    } else if (error.response?.status === 404) {
      message = '接口不存在'
    }
    return Promise.reject(new Error(message))
  }
)
```

这样页面拿到的就不是杂乱的原始响应，而是更容易使用的数据。

### 2.3 统一错误处理的判断标准

老赵给你一个实战判断：

- **前端可判断的错误**：参数没传、按钮重复点击、必填项未通过校验
- **后端返回的业务错误**：权限不足、数据不存在、状态不允许操作
- **网络层错误**：断网、超时、服务器异常

这三类错误不能混着处理，不然调试会很痛苦。比如参数没传，本来是前端表单问题，你却提示成“网络异常”；或者后端返回了业务错误，你却只在控制台打一行日志，用户根本不知道发生了什么。

### 2.4 常见误区

很多人会把所有错误都 `console.log` 一下了事，开发阶段看似能跑，上线后完全不够用。

正确方式是：**页面负责展示，封装层负责判断，调用层负责接收结果。**

页面不应该直接参与“怎么识别错误”的细节，它只要知道：成功就渲染，失败就提示。这样分层清楚，后面不管是文章管理、商品管理还是后台列表，都能复用。

---

## 三、接口模块化管理与接口地址规划：别让接口文件堆成一锅粥

### 3.1 接口为什么要单独管理？

项目里接口一多，如果还写在页面里，维护成本会很高。

所以我们要把接口按业务模块拆开，比如：

- 用户相关接口
- 商品相关接口
- 列表页接口
- 详情页接口
- 表单提交接口

好处很直接：

- 查找快
- 修改集中
- 复用方便
- 新人接手不迷路

这一步已经进入“和后端真正联调”的阶段了。接口混在组件里，排查问题会很慢，哪怕只是改一个字段名，也可能要翻好几个页面。

### 3.2 推荐目录结构

```bash
src/
  services/
    request.js
    user.js
    article.js
    order.js
```

小项目不用把目录搞得太复杂，先按业务模块拆开就够了，关键是把接口层和页面层分离。

### 3.3 接口地址规划怎么做？

接口地址最好遵守“资源化”思路：

- 列表：`GET /articles`
- 详情：`GET /articles/:id`
- 新增：`POST /articles`
- 更新：`PUT /articles/:id`
- 删除：`DELETE /articles/:id`

接口语义清楚，前后端沟通会简单很多，页面上的增删改查也更容易组织。

### 3.4 一个模块的写法示例

```js
import request from './request'

export function getArticleList(params) {
  return request.get('/articles', { params })
}

export function getArticleDetail(id) {
  return request.get(`/articles/${id}`)
}

export function createArticle(data) {
  return request.post('/articles', data)
}
```

页面里只调用方法，不关心底层怎么请求，这就是接口模块化的价值：页面专注展示和交互，请求层专注通信和规范。

## 四、列表、详情、提交等常见接口联调：一步一步把数据跑通

这一部分最关键，因为这就是项目真正进入“可用状态”的地方。

### 4.1 列表接口联调：先让页面有数据

列表接口最常见的场景，就是页面进入后自动加载数据。

基本流程：

1. 页面挂载时发请求
2. 先显示加载状态
3. 接口返回后渲染列表
4. 失败时展示空状态或错误提示

```js
import { onMounted, ref } from 'vue'
import { getArticleList } from '@/services/article'

const loading = ref(false)
const list = ref([])

const loadList = async () => {
  loading.value = true
  try {
    list.value = await getArticleList()
  } finally {
    loading.value = false
  }
}

onMounted(() => {
  loadList()
})
```

先把“最小闭环”跑通，再慢慢加分页、筛选和搜索，这是最稳的做法。

### 4.2 详情接口联调：先拿 id，再查详情

详情页通常依赖路由参数。

实战思路很简单：

- 先从路由中拿到 `id`
- 再调用详情接口
- 接口返回后渲染页面

```js
import { useRoute } from 'vue-router'
import { getArticleDetail } from '@/services/article'

const route = useRoute()

const loadDetail = async () => {
  const data = await getArticleDetail(route.params.id)
  detail.value = data
}
```

这里 Vue Router 就派上用场了。路径参数定下来后，详情页联调会很顺：路由负责传值，请求负责取数，页面负责展示。

### 4.3 提交接口联调：表单校验后再发请求

新增和编辑页面最容易出问题，常见坑有：

- 表单字段名和后端不一致
- 提交时多传了无用字段
- 编辑时没有处理初始值
- 保存成功后没跳转

建议流程：

1. 先做前端表单校验
2. 再整理提交数据
3. 调用新增或更新接口
4. 成功后提示并跳转

不要直接把整个响应式对象扔给接口，先整理一遍数据，能少很多参数异常问题。

### 4.4 列表、详情、提交串起来看

老赵建议你把这三类接口放在同一个项目主线里理解。比如我们这个内容管理小项目：

- 首页进入后，先拉文章列表
- 点击列表中的某一项，进入文章详情页
- 在编辑页里修改内容后提交保存
- 保存成功后回到列表，看到最新数据

这样联调就不是孤立地“调一个接口”，而是把前端页面、路由跳转、请求参数、后端返回串成一条线。你会发现，真正难的不是发请求，而是让请求在正确的时机、正确的页面、正确的数据结构里跑起来。

### 4.5 联调时最重要的两个习惯

**第一，先看请求参数。**  
很多“接口不通”问题，其实就是参数名写错了。你以为传的是 `articleId`，后端可能要的是 `id`。

**第二，先看响应结构。**  
不要凭感觉开发，先打印一次真实返回，再决定页面怎么渲染。这样调试最快。

## 五、加载状态、异常状态与提示信息处理：让页面不再“静悄悄失败”

### 5.1 为什么要处理状态？

一个成熟的项目，不能只做到“能请求”，还要做到“过程让用户看得懂”。

用户最怕的不是慢，而是：

- 点了按钮没反应
- 数据加载了一半没提示
- 请求失败了页面却一片空白
- 重复点击导致重复提交

所以联调时，别只盯着接口通没通，还要看用户体验有没有跟上。

### 5.2 加载状态怎么做？

准备一个 `loading` 状态即可：

- 请求前设为 `true`
- 请求后设为 `false`
- 按钮和列表都能复用

```js
const loading = ref(false)
```

按钮上可以直接绑定：

```vue
<button :disabled="loading">
  {{ loading ? '提交中...' : '提交' }}
</button>
```

这个小细节不只是“好看一点”，更是在告诉用户：系统已经收到操作，正在处理中。

### 5.3 异常状态怎么做？

异常状态不能只靠弹窗。对列表页、详情页，最好有清晰反馈：

- 没数据：展示空状态
- 请求失败：展示错误提示
- 权限不足：提示无权限
- 会话失效：跳转登录页

如果后面接 **Pinia** 管理登录态，这些处理会更方便。这里先记住思路：异常不是“报一下就完了”，而是要给用户明确反馈。

### 5.4 提示信息怎么统一？

提示不要每个页面各写一套，最好统一风格：

- 成功：`操作成功`
- 失败：`操作失败，请稍后重试`
- 校验错误：`请先完善表单`
- 业务错误：显示后端返回 message

这样项目体验才会更像一个完整产品，而不是拼起来的页面集合。

## 六、接口命名、返回值字段和环境变量的统一约定

这一节看起来小，其实很重要。因为你这一章做的是请求封装，它会直接影响后面 **环境变量** 和 **打包配置** 的衔接。

### 6.1 接口地址统一从环境变量读取

在开发环境、测试环境和生产环境里，接口地址通常不一样，所以不要把地址硬写死在代码里。

建议统一使用：

```js
baseURL: import.meta.env.VITE_API_BASE_URL
```

这样后面切环境时，只需要改环境变量文件，不用把整套请求代码重写一遍。

### 6.2 接口模块名要统一

如果你这一章叫 `article.js`，下一章又写成 `posts.js`，再下一章突然变成 `content.js`，读者就会乱。

所以建议全书保持一致，比如：

- 用户接口：`user.js`
- 文章接口：`article.js`
- 评论接口：`comment.js`

名称统一，后面路由、页面、接口联调的逻辑就更清楚。

### 6.3 返回值字段也要约定好

前面拦截器里老赵已经示范过，建议把后端返回和前端使用分开处理，统一成一种前端好用的数据结构。

比如约定：

- `code`：状态码
- `message`：提示信息
- `data`：业务数据

这样页面层拿到的逻辑会非常清晰，不需要到处判断一大串字段。

# 第7章 上 Pinia：把项目状态管起来

前面几章里，我们已经把**页面、路由、接口、登录流程**基本跑通了。接下来真正拉开项目工程化差距的，就是把状态管起来。

做项目时，你很快会遇到这些场景：

- 登录后，头部要展示用户信息
- 左侧菜单要随权限变化
- 多个页面共用同一份全局配置
- 列表页和详情页之间要保留筛选条件
- 请求成功后，多个页面都要同步感知最新状态

如果这些数据还散在各个组件里，项目很快就会乱。  
所以这一章，老赵带你把 **Pinia** 上起来，让项目从“能跑”变成“好维护、好协作、好扩展”。

---

## 一、为什么这个项目必须引入 Pinia？

先想一个问题：**项目里的状态应该放哪儿？**

在这个完整可运行项目里，状态大致分三类：

1. **组件内部状态**  
   比如输入框内容、弹窗显示隐藏、分页当前页。只在当前组件内使用，留在组件里最合适。

2. **跨页面共享状态**  
   比如登录用户信息、菜单列表、全局配置、字典数据。多个页面都要用，不能重复请求、重复维护。

3. **影响业务流程的全局状态**  
   比如是否登录、当前选中的项目、权限树。它一变，路由跳转、权限判断、页面渲染都会受影响。

如果把这些都塞进组件里，常见结果就是：

- 页面切换后状态丢失
- 同一份数据重复请求
- 兄弟组件通信越来越绕
- 维护时不知道数据从哪来、改了会影响谁

所以，Pinia 的作用不是替代所有数据，而是把**应该共享、应该统一管理的状态**集中起来。后面你再做**接口联调、路由守卫、页面布局、组件拆分**，整个项目会顺很多。

换句话说，Pinia 解决的不是“能不能写数据”，而是“数据该放哪、谁来改、什么时候改”。

---

## 二、Pinia 的安装与基础仓库创建

### 1. 安装 Pinia

在 Vue3 + Vite 项目里，直接安装：

```bash
npm i pinia
```

然后在入口文件里创建并挂载：

```ts
// src/main.ts
import { createApp } from 'vue'
import { createPinia } from 'pinia'
import App from './App.vue'

const app = createApp(App)

app.use(createPinia())
app.mount('#app')
```

到这里，Pinia 就已经接入项目了。

### 2. 建议的目录结构

老赵建议按功能拆仓库，而不是把所有 store 堆在一起：

```bash
src/
  stores/
    user.ts
    app.ts
    permission.ts
```

大致职责可以这样分：

- `user.ts`：登录态、用户信息
- `app.ts`：全局配置、主题、布局状态
- `permission.ts`：菜单、权限相关状态

这样做的好处很直接：

- 按业务拆分，容易找
- 每个仓库职责清晰
- 后期扩展不容易互相污染

后面如果再加“收藏列表”“购物车”“文章草稿”之类的状态，也可以继续按模块拆，不会把一个 store 写成大杂烩。

## 三、状态、getter、action 怎么用才顺手？

Pinia 最核心的就是三块：**state、getter、action**。

### 1. state：存数据

`state` 就是仓库里最基础的状态，表示“我现在手里有哪些数据”。

```ts
// src/stores/user.ts
import { defineStore } from 'pinia'

export const useUserStore = defineStore('user', {
  state: () => ({
    token: '',
    userInfo: null as null | { id: number; name: string; avatar?: string }
  })
})
```

这里要注意两点：

- `state` 必须写成函数
- 初始值尽量明确，别让状态类型飘掉

### 2. getter：算结果

`getter` 不是存新数据，而是从已有状态里“算出一个结果”。

比如：

- 当前是否登录
- 用户显示名
- 是否有管理员权限

```ts
export const useUserStore = defineStore('user', {
  state: () => ({
    token: '',
    userInfo: null
  }),
  getters: {
    isLogin: (state) => !!state.token,
    userName: (state) => state.userInfo?.name || '未登录'
  }
})
```

判断标准很简单：  
如果这个值能由现有状态推导出来，就尽量放在 getter，不要重复存一份。

这样界面、路由、按钮权限都可以直接读结果，逻辑更统一，也更不容易出错。

### 3. action：改状态、做异步

`action` 用来处理“怎么变”，包括：

- 修改状态
- 发请求
- 登录、退出
- 拉取用户信息
- 清空本地数据

```ts
export const useUserStore = defineStore('user', {
  state: () => ({
    token: '',
    userInfo: null
  }),
  getters: {
    isLogin: (state) => !!state.token
  },
  actions: {
    setToken(token: string) {
      this.token = token
    },
    setUserInfo(info: any) {
      this.userInfo = info
    },
    logout() {
      this.token = ''
      this.userInfo = null
    }
  }
})
```

### 4. 最容易犯的三个误区

- **把计算结果塞进 state**，会导致重复存储和不一致
- **状态修改散落在页面里**，仓库就失去了统一入口的意义
- **action 里不敢放异步**，其实登录、拉用户信息、拉菜单都应该放进 action

老赵提醒一句：**仓库不是摆设，它是项目状态的统一操作台。** 页面里少直接改数据，多走 action，后面维护会轻松很多。

---

## 四、用户信息、菜单状态、全局配置怎么落地？

这一节是本章最重要的实战部分。  
别只把 Pinia 当语法练习，要把它放进真实业务。

### 1. 用户信息：登录态的核心仓库

在本项目里，用户信息通常包括：

- token
- 用户 ID
- 用户名
- 头像
- 角色或权限标识

推荐把“登录”和“获取用户信息”分开：

```ts
actions: {
  async login(params: { username: string; password: string }) {
    // 调接口拿 token
  },
  async fetchUserInfo() {
    // 调接口拿用户信息
  }
}
```

这样做的好处是：

- 登录接口专注返回凭证
- 用户信息接口专注返回资料
- 业务逻辑更清晰，也方便和路由联动

实际项目里，登录成功后一般连续做几件事：

1. 保存 token
2. 拉取用户信息
3. 获取菜单权限
4. 跳转首页

把流程拆清楚，后面排查问题会快很多。

### 2. 菜单状态：和权限系统绑在一起

菜单状态通常有两种来源：

- 后端返回菜单树
- 前端按角色过滤菜单

不管哪种方式，建议把菜单状态放到独立仓库里，比如 `permission.ts`：

```ts
import { defineStore } from 'pinia'

export const usePermissionStore = defineStore('permission', {
  state: () => ({
    menus: [] as any[],
    activeMenuPath: ''
  }),
  actions: {
    setMenus(menus: any[]) {
      this.menus = menus
    },
    setActiveMenuPath(path: string) {
      this.activeMenuPath = path
    }
  }
})
```

菜单状态常见用途：

- 左侧导航渲染
- 面包屑生成
- 动态路由匹配
- 当前菜单高亮

菜单不只是“展示数据”，它还参与路由和权限判断，所以单独抽出来很有必要。

### 3. 全局配置：让页面保持统一风格

全局配置适合放在 `app.ts` 这类仓库中，比如：

- 布局模式：侧边栏 / 顶部导航
- 页面尺寸：紧凑 / 舒适
- 主题色
- 是否显示标签页
- 是否开启多语言

```ts
export const useAppStore = defineStore('app', {
  state: () => ({
    theme: 'light',
    sidebarCollapsed: false,
    showTabs: true
  }),
  actions: {
    toggleSidebar() {
      this.sidebarCollapsed = !this.sidebarCollapsed
    },
    setTheme(theme: string) {
      this.theme = theme
    }
  }
})
```

这类状态不是某个页面专属，而是整个项目都可能用到。  
如果你前面已经把页面布局拆成头部、侧边栏、内容区，那这些配置就会直接影响布局组件的展示方式，Pinia 正好可以把它们统一管起来。

## 五、跨页面共享状态与最小持久化方案

Pinia 很实用的一点，就是解决“页面一跳转，状态就没了”的问题。  
不过要先分清楚：**Pinia 能共享状态，但刷新页面后默认会丢失。**

### 1. 跨页面共享怎么理解？

比如：

- 登录页拿到 token
- 进入首页后，顶部组件直接读取用户名称
- 进入个人中心页后还能继续用同一份用户信息

这就是跨页面共享状态。

使用时你只要在不同页面中引入同一个 store：

```ts
const userStore = useUserStore()
console.log(userStore.userInfo)
```

因为仓库是全局单例逻辑，组件之间可以直接共享。

### 2. 刷新丢失怎么办？

这是很多新手第一次用 Pinia 时最容易踩的坑：  
**页面一刷新，内存状态就没了。**

所以像 `token`、`userInfo` 这类关键数据，通常要做持久化处理。老赵这里建议先用项目里最容易落地的最小方案。

#### 方案一：手动持久化

在 action 里同步写入本地存储：

```ts
setToken(token: string) {
  this.token = token
  localStorage.setItem('token', token)
}
```

初始化时再读出来：

```ts
state: () => ({
  token: localStorage.getItem('token') || ''
})
```

#### 方案二：只持久化必要字段

别把整个接口响应都塞进本地存储，通常只保留：

- token
- 用户名
- 必要的角色标识

这样更轻，也更容易控制清理逻辑。

### 3. 持久化时要注意什么？

- 不要把敏感信息乱存
- 只存必要字段，别把整个接口响应原样塞进去
- 本地存储只负责“续命”，真正权限判断还是要靠接口或后端校验
- 登录失效时要及时清空缓存，避免状态污染

老赵顺手提醒一句：**状态持久化不是永不失效，只是让用户体验更顺滑。**

## 六、Pinia 怎么和路由、请求模块联动？

这一节是项目实战的关键：**状态不是孤立的，它要和路由、请求打通。**

### 1. 和路由联动：控制访问权限

典型场景：

- 用户未登录，访问后台页面，跳转到登录页
- 登录后自动进入首页
- token 失效时，跳回登录页

这时路由守卫可以直接读取 Pinia 中的登录状态：

```ts
const userStore = useUserStore()

router.beforeEach((to) => {
  if (to.meta.requiresAuth && !userStore.isLogin) {
    return '/login'
  }
})
```

这样路由判断就不必在组件里到处传来传去，直接依赖统一状态。

如果项目里还做了权限菜单，那路由和菜单状态也能一起联动：登录后生成动态路由，退出时清掉，整个访问流程就闭环了。

### 2. 和请求模块联动：自动带 token

请求封装里通常会用 axios 拦截器，把 token 自动加到请求头：

```ts
import axios from 'axios'
import { useUserStore } from '@/stores/user'

const request = axios.create({ baseURL: '/api' })

request.interceptors.request.use((config) => {
  const userStore = useUserStore()
  if (userStore.token) {
    config.headers.Authorization = `Bearer ${userStore.token}`
  }
  return config
})
```

这一步很关键，意味着：

- 页面不用每次手动传 token
- 接口层统一管理认证信息
- 后面 token 规则变了，只改请求层即可

这就是工程化的价值：**让变化集中在一处，别让每个页面都跟着改。**

### 3. 接口联调时怎么衔接状态？

在真实的接口联调里，常见流程通常是这样的：

1. 登录接口返回 token
2. token 写入 Pinia，同时写入本地存储
3. 请求拦截器从 Pinia 读取 token，自动带上请求头
4. 拉取用户信息和菜单数据，写入对应 store
5. 路由守卫根据登录态决定能不能进页面
6. 若接口返回未登录或 token 失效，则清空 store 并跳转登录页

这就是一个完整的状态闭环。  
你会发现，Pinia 不只是“存点数据”，而是把登录、路由、请求这三条线串起来了。

# 第8章 配环境变量：开发、测试、生产分开管

## 开篇引入：为什么项目一上来就要把环境分开

前面我们已经把 **Vue3 + Vite** 的项目骨架、页面布局、路由和请求封装搭起来了。接下来这一步，很多新手容易忽略，但老赵必须提醒你：**环境变量一定要尽早规范起来**。

因为一个完整可运行项目，通常不止一套运行环境：

- **开发环境**：本地调接口，改代码快，方便调试
- **测试环境**：给测试同学验收，用测试接口
- **生产环境**：真正上线给用户访问，用正式接口

如果把接口地址、开关参数、调试配置全写死在代码里，后面会很麻烦：

- 切环境要到处改代码
- 容易把测试地址发到线上
- 敏感信息可能误提交到仓库
- 请求封装和部署都不好维护

所以这一章，我们就把 **Vite 环境变量** 理顺。目标很明确：让项目具备 **开发、测试、生产分开管理** 的能力，并且能在 **axios 请求封装**、**构建流程** 里真正用起来。

一句话记住：  
**把写死在代码里的配置，挪到按环境管理的配置文件里。**

---

## 一、Vite 环境变量的基础写法：先把规则搞明白

### 1.1 Vite 里环境变量文件怎么放

在 Vite 项目里，环境变量一般放在项目根目录，常见文件名是：

- `.env`：通用配置
- `.env.development`：开发环境配置
- `.env.test`：测试环境配置
- `.env.production`：生产环境配置

同一个项目，开发时接口可以走本地代理，测试时走测试服务器，生产时走正式服务器。代码不改，只改配置文件，项目行为就变了。

### 1.2 变量命名要注意什么

在 Vite 中，前端可读取的环境变量通常要以 `VITE_` 开头，比如：

```env
VITE_APP_TITLE=全栈老赵讲 Vue3 项目
VITE_BASE_API=https://api.example.com
VITE_ENABLE_MOCK=true
```

前端代码里通过 `import.meta.env` 读取：

```js
console.log(import.meta.env.VITE_BASE_API)
```

你可以这样记：  
`.env` 是配置仓库，`import.meta.env` 是前端取配置的入口。

### 1.3 你需要先记住的三个判断标准

1. **通用配置**，放到 `.env`
2. **按环境区分的配置**，放到 `.env.development`、`.env.test`、`.env.production`
3. **要给前端访问的变量**，前缀必须是 `VITE_`

### 1.4 一个最小可用示例

**`.env.development`**

```env
VITE_BASE_API=/api
VITE_ENABLE_MOCK=true
VITE_APP_ENV=development
```

**`.env.test`**

```env
VITE_BASE_API=https://test-api.xxx.com
VITE_ENABLE_MOCK=false
VITE_APP_ENV=test
```

**`.env.production`**

```env
VITE_BASE_API=https://api.xxx.com
VITE_ENABLE_MOCK=false
VITE_APP_ENV=production
```

这样一来，开发走 `/api`，测试走测试域名，生产走正式接口，一套代码对应三套环境，才像一个完整项目。

---

## 二、开发、测试、生产环境配置拆分：怎么分才不乱

### 2.1 为什么要拆分

环境拆分不是为了“看起来专业”，而是为了真实项目更好维护。

最常见的场景就是：

- 开发时用本地代理，请求走 `/api`
- 测试时走测试服务器
- 生产环境走正式接口

如果不拆分，每次切环境都要手动改请求地址，风险很高，尤其在做 **axios 请求封装**、登录态、分页、上传这些功能时，一旦地址错了，整条链路都可能出问题。

### 2.2 推荐的拆分方式

#### 开发环境 `.env.development`
重点放：

- 接口代理前缀
- 是否开启 mock
- 调试开关

#### 测试环境 `.env.test`
重点放：

- 测试接口地址
- 是否关闭 mock
- 是否保留调试开关

#### 生产环境 `.env.production`
重点放：

- 正式接口地址
- 关闭 mock
- 关闭不必要调试能力

### 2.3 在项目里怎么识别当前环境

Vite 会根据命令加载不同文件。比如：

- `vite` 或 `npm run dev`：开发环境
- `vite build --mode test`：测试环境
- `vite build`：生产环境

也可以通过这些变量判断：

```js
import.meta.env.MODE
import.meta.env.DEV
import.meta.env.PROD
```

比如排查环境问题时：

```js
console.log('当前模式：', import.meta.env.MODE)
console.log('是否开发环境：', import.meta.env.DEV)
console.log('是否生产环境：', import.meta.env.PROD)
```

### 2.4 常见误区

别把“环境变量”和“接口地址切换”混成一件事：

- **环境变量**：负责提供配置
- **代码逻辑**：负责读取配置并做决定

环境变量本身不执行逻辑，它只是数据来源；真正让项目切到不同环境的，是配置文件和构建命令一起配合完成的。

---

## 三、接口地址、开关配置与环境切换：项目里最常用的三类变量

### 3.1 接口地址：请求封装的核心入口

在项目里，axios 请求封装会统一读取接口基地址：

```js
const baseURL = import.meta.env.VITE_BASE_API
```

这样写的好处很直接：

- 开发环境自动走开发接口
- 测试环境自动走测试接口
- 生产环境自动走生产接口

以后切环境，不用改请求代码，只改环境文件就行。

### 3.2 开关配置：让项目具备“可控能力”

环境变量还适合控制这些内容：

- 是否开启 mock
- 是否开启调试日志
- 是否显示某些测试功能

示例：

```env
VITE_ENABLE_MOCK=true
VITE_ENABLE_DEBUG=true
```

代码里判断：

```js
if (import.meta.env.VITE_ENABLE_DEBUG === 'true') {
  console.log('当前处于调试模式')
}
```

开关变量建议统一用字符串判断，别混着写 true、false、1、0，容易乱。

### 3.3 环境切换的推荐做法

常见脚本可以这样配：

```json
{
  "scripts": {
    "dev": "vite",
    "build:test": "vite build --mode test",
    "build:prod": "vite build --mode production"
  }
}
```

对应使用方式也很清楚：

- 本地开发：`npm run dev`
- 打测试包：`npm run build:test`
- 打生产包：`npm run build:prod`

### 3.4 你该怎么检查有没有切对

每次切环境后，做三步：

1. 看 `.env.*` 是否被正确加载
2. 打印 `import.meta.env.VITE_BASE_API`
3. 发一个接口请求，看是否真的走到对应服务

这三步很朴素，但联调时非常管用。

## 四、在请求封装和构建流程中使用环境变量：真正把配置用起来

### 4.1 axios 请求封装怎么接入环境变量

把请求封装改成这样：

```js
import axios from 'axios'

const service = axios.create({
  baseURL: import.meta.env.VITE_BASE_API,
  timeout: 10000
})

service.interceptors.request.use((config) => config)

service.interceptors.response.use(
  (response) => response.data,
  (error) => Promise.reject(error)
)

export default service
```

这样 `baseURL` 不再写死，而是由环境变量控制。请求封装也就真正接入了环境体系。

### 4.2 如果有本地代理，怎么配合开发环境

开发环境常配 Vite 代理，比如：

```js
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'https://test-api.xxx.com',
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, '')
      }
    }
  }
})
```

这时候可以把 `VITE_BASE_API` 设置成 `/api`，请求统一走代理。好处是：

- 前端代码不用关心跨域
- 本地开发更顺手
- 测试接口切换更方便

注意：开发环境里的 `/api` 不是后端真实地址，而是前端代理入口。

### 4.3 构建流程里也要用环境变量

环境变量不仅请求要用，构建时也能用。

比如：

```js
console.log(import.meta.env.MODE)
```

或者让首页标题跟环境关联：

```js
document.title = `${import.meta.env.VITE_APP_TITLE}-${import.meta.env.MODE}`
```

还可以根据环境决定是否显示版本号、调试信息、测试功能等，这些都属于工程化里很实用的小能力。

### 4.4 哪些东西适合放环境变量里

适合放的：

- 接口地址
- 是否启用 mock
- 应用标题
- 版本标识
- 调试开关

不适合直接放在前端环境变量里的：

- 密码
- 私钥
- 真实支付密钥
- 必须绝对保密的信息

前端环境变量不是保险箱，它只是公开配置入口。

---

## 五、避免把敏感信息写死在代码里：这一步千万别偷懒

### 5.1 为什么不能写死

新手常把这些东西直接写在代码里：

```js
const baseURL = 'https://api.xxx.com'
const tokenKey = 'abcd1234'
const secret = 'xxxxx'
```

这样在小练习里可能能跑，但放到真实项目里就危险了：

- 提交代码后大家都能看到
- 上线后修改成本高
- 安全风险大
- 后期维护很痛苦

尤其到 **接口联调** 和 **生产部署基础** 阶段，写死的配置会让你改一次、崩一次。

### 5.2 正确思路是什么

- **接口地址** 放环境变量
- **开关配置** 放环境变量
- **敏感信息** 放后端或安全存储
- **前端只拿必要的公开配置**

一句话：前端负责读取配置，不负责保存秘密。

### 5.3 一套实用检查清单

提交代码前检查：

- 有没有把正式接口地址写死在请求里
- 有没有把测试开关写死在组件里
- 有没有把本地调试信息留在生产构建中
- 有没有把不该公开的内容放进 `VITE_` 变量里

### 5.4 常见误区

- **误区一：所有配置都塞进 `.env`**  
  不对，能公开的才放，不能公开的别放。

- **误区二：开发环境能跑就行**  
  不对，要考虑测试和上线。

- **误区三：环境变量只管接口地址**  
  不对，它还能管开关、标题、构建行为等很多内容。

---

## 六、和第7章、第10章怎么衔接：环境变量不是孤立配置

这一章不是单独存在的，它要和前后的章节接起来，项目才会顺。

### 6.1 和第7章请求封装保持一致

第7章里我们已经做了请求封装，这一章只是把原来写死的 `baseURL` 改成从环境变量里读取。  
也就是说，**请求封装的结构不变，变的是配置来源**。

建议你统一成这样的写法：

```js
const baseURL = import.meta.env.VITE_BASE_API
```

后面无论是登录接口、列表接口，还是上传接口，都统一走这套方式。

### 6.2 和第10章打包配置保持一致

到了打包阶段，环境变量会直接影响构建结果。  
比如开发包、测试包、生产包分别读取不同的 `.env.*` 文件，这样你打出来的包才不会混用接口地址。

所以你要记住：

- **环境变量** 决定配置内容

- **请求封装** 决定怎么使用配置

## 一、生产环境打包流程与产物目录认识

### 1. 打包到底做了什么？

在 Vue3 + Vite 项目里，开发时依赖热更新和开发服务器；到了生产环境，浏览器真正加载的是构建后的静态文件，包括 HTML、JS、CSS、图片等资源。

打包可以简单理解为三步：

1. **代码转换**：把 Vue 单文件组件、TS、ESM 语法转成浏览器可执行代码。
2. **资源整理**：对 JS、CSS、图片、字体等进行拆分、压缩和重命名。
3. **输出产物**：生成可部署目录，默认是 `dist`。

开发和打包最大的区别是：  
**开发看过程，打包看结果。**

---

### 2. `dist` 目录里有什么？

执行：

```bash
npm run build
```

默认会生成 `dist` 目录，通常包括：

- `index.html`
- `assets/`
- 带哈希的 JS/CSS 文件
- 图片、字体等资源

文件名带哈希，是为了缓存控制。只要内容变化，文件名就会变化，浏览器会重新拉取新文件，避免旧缓存干扰。

例如：

```text
assets/index-8f3a2d1e.js
assets/index-1a2b3c4d.css
```

构建结束后，别急着直接交给服务器，老赵建议你先做一次检查：

- `index.html` 是否存在
- `assets` 是否完整
- 资源路径是否正确
- 入口文件有没有引用丢失
- 刷新页面会不会出错

#### 老赵带你做
先本地跑一次 `npm run build`，再打开 `dist` 看输出结构，最后用静态服务器预览一下，确认页面能正常打开。

#### 赵老师提醒
`build` 成功不等于生产可用。**构建成功 ≠ 生产可用**，路径和资源引用才是真考验。

## 二、Vite 构建配置基础：从默认打包到可控打包

### 1. 配置入口在哪里？

Vite 的构建配置主要写在 `vite.config.ts` 或 `vite.config.js` 中。  
建议直接用 `vite.config.ts`，类型提示更完整。

基础配置如下：

```ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'

export default defineConfig({
  plugins: [vue()]
})
```

实际项目里，通常还会配置：

- `base`
- `resolve.alias`
- `build.outDir`
- `build.assetsDir`
- `build.sourcemap`

---

### 2. 常用构建参数怎么理解？

#### `base`
控制项目部署后的公共基础路径。部署在根目录通常默认即可；如果部署在子路径，比如 `/admin/`，这里必须配置。

#### `outDir`
输出目录，默认是 `dist`。

#### `assetsDir`
静态资源子目录，常见默认是 `assets`。

#### `sourcemap`
是否生成源码映射。联调排错时可能有用；正式上线时通常要谨慎使用。

这些配置看起来不复杂，但它们决定了构建结果是不是能顺利交给生产部署环境。  
如果你前面已经做了路由、接口和环境变量，这里就要让它们和打包结果统一起来，不能开发一套、上线一套。

---

### 3. 一个适合实战项目的基础配置

```ts
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import path from 'path'

export default defineConfig({
  plugins: [vue()],
  base: './',
  resolve: {
    alias: {
      '@': path.resolve(__dirname, './src')
    }
  },
  build: {
    outDir: 'dist',
    assetsDir: 'assets',
    sourcemap: false
  }
})
```

这里要注意：  
**`base: './'` 不是万能解法，但对不少相对路径部署场景很实用。**

如果你的项目后面会部署到子目录，或者前后端分离后由服务器统一托管，那 `base` 就不能随便写，必须和真实访问路径一致。

#### 老赵带你做
先把 `vite.config.ts` 的基础配置补上，至少把 `alias` 和 `build` 相关项配好。

#### 赵老师提醒
构建配置不是越多越好，而是**先保证稳定，再做优化**。

## 三、路径别名、静态资源和公共路径怎么处理？

### 1. 路径别名为什么要配？

项目一多，层层相对路径会很难维护，比如：

```ts
import UserList from '../../../components/UserList.vue'
```

所以通常会配置 `@` 指向 `src`，之后就能写成：

```ts
import UserList from '@/components/UserList.vue'
```

路径统一后，页面、组件、路由、接口都更好维护。  
这对整个 Vue3 + Vite 项目的代码组织很重要，尤其是后面页面拆分、组件复用、路由配置越来越多时，别名能省掉很多麻烦。

---

### 2. 静态资源怎么引用更稳？

在 Vue3 + Vite 中，静态资源常见有两种方式：

#### 方式一：放在 `src` 里，用模块方式引入

```ts
import logo from '@/assets/logo.png'
```

这种方式适合参与打包的资源，Vite 会帮你处理引用关系。

#### 方式二：放在 `public` 目录

`public` 里的资源不会经过模块处理，适合固定名称、原样拷贝的静态内容。

```html
<img src="/favicon.ico" />
```

如果是首页图标、固定下载文件、第三方验证文件这类不想被打包处理的资源，放 `public` 更合适。  
如果是页面里的图片、组件里的背景图，优先放到 `src/assets`，让 Vite 统一管理。

---

### 3. 公共路径为什么容易出问题？

如果项目不是部署在根目录，而是部署到子目录，比如：

- `https://example.com/app/`
- `https://xxx.com/admin/`

那如果打包后资源路径还是按根目录写，页面就可能出现：

- JS/CSS 加载失败
- 图片 404
- 刷新后白屏

这就是 `base` 配置的重要性。  
很多“首页能打开，点一下就挂了”的问题，本质都是部署路径和资源路径没对齐。

实际排查时，先别急着怀疑 Vue、Router 或 Pinia，先打开浏览器控制台和 Network 看资源地址。很多时候一眼就能发现：资源请求还在找 `/assets/...`，但你实际访问路径已经在 `/admin/` 下面了。

#### 老赵带你做
把项目里常见资源梳理一遍：logo、图标、背景图、配置文件、静态文档。分清哪些该进 `src`，哪些该放 `public`。

#### 赵老师提醒
很多线上白屏，不是 Vue 写错了，而是**资源路径和部署路径没对齐**。排查时先看浏览器 Network，通常很快就能找到问题。

---

## 四、部署在子目录时，Vite 打包怎么配？

### 1. 子目录部署是什么场景？

有些项目不会直接放在网站根目录，而是部署在一个子路径下面，比如后台管理系统常见的：

```text
https://example.com/admin/
```

页面还是同一个应用，但访问入口已经不在根目录了。  
如果还按默认根路径打包，浏览器找资源时就会找错地方。

---

### 2. `base` 应该怎么写？

如果项目部署在 `/admin/` 下，就可以这样改：

```ts
export default defineConfig({
  plugins: [vue()],
  base: '/admin/',
  resolve: {
    alias: {
      '@': path.resolve(__dirname, './src')
    }
  }
})
```

这个配置告诉 Vite：  
构建出来的资源引用，统一按 `/admin/` 这个前缀生成。

核心原则只有一个：**打包路径要和线上访问路径一致。**

如果后面的生产部署采用的是 Nginx 或其他静态服务器，那么服务端的访问前缀也要和这里同步。这样前后两边才会对得上，不会出现“构建看着没问题，线上一刷新就丢资源”的情况。

---

### 3. 改完之后要看什么？

改完 `base` 后，立即做这三步：

1. 重新执行 `npm run build`
2. 用静态预览工具打开 `dist`
3. 检查资源请求路径和页面刷新效果

重点看：

- `index.html` 里资源引用前缀是否正确
- JS、CSS 是否加载成功
- 刷新二级路由会不会白屏

如果你的项目用了 Vue Router 的历史模式，刷新时更要注意服务端回退策略；不过那部分我们放到后面的部署章节再展开讲，这里先把打包配置这一步做好。

#### 老赵带你做
先按 `/admin/` 的场景改一次 `base`，重新构建后看 `dist/index.html` 的资源引用变化。

#### 赵老师提醒
子目录部署最容易出现“本地正常、线上异常”。不是代码有问题，而是**路径前缀没对上**。

## 五、如何按需优化构建结果与打包体积？

### 1. 为什么要关注包体积？

包太大，会直接影响：

- 首屏加载速度
- 用户体验
- 服务器传输压力
- 缓存效果

项目越做越大，体积问题就越明显。  
特别是做后台管理系统、内容平台这类完整项目时，页面、组件、图表、编辑器、工具库一多，主包很容易膨胀。

---

### 2. 先看清“包大”通常大在哪

常见大头一般有：

- UI 组件库
- 图表库
- 日期处理库
- 富文本编辑器
- 大图资源
- 未拆分的业务代码
- 重复引用的工具库

先别急着优化，先判断：

1. 是不是引入了过大的依赖
2. 能不能按需加载
3. 有没有重复包
4. 是否需要路由懒加载
5. 主包里有没有不必要的资源

这一步的目标不是“做成极致轻量”，而是先让上线包更合理、更稳定。

---

### 3. 实战里最常用的优化思路

#### 路由懒加载
把不常访问的页面拆出去：

```ts
const UserList = () => import('@/views/UserList.vue')
```

这样首屏只加载必要代码。  
前面我们已经把路由搭起来了，这里正好顺手做一次优化：把登录后才会访问的页面都改成懒加载，主包体积通常会立刻好看不少。

#### 组件按需引入
不要为了省事把整个库都引进来，能单个引就单个引。

#### 图片资源优化
- 压缩大图
- 使用合适格式
- 非必要图片放 CDN 或静态服务器

#### 清理无用依赖
定期检查 `package.json`，把不用的删掉。

---

### 4. 做一个简单对比：拆分前和拆分后

如果首页、用户列表、订单列表、设置页全部在启动时一次性打包进主包里，首屏压力会很大。  
如果把这些页面改成懒加载，主包里只保留入口、登录、布局和少量公共逻辑，首屏体验通常会更好。

你不一定要在这里追求极致压缩，但至少要明白：  
**首屏先跑起来，非首屏再按需加载。**

对于一个完整可运行项目来说，这种优化思路非常实用：不是为了炫技，而是为了让项目上线后真正可用、可维护。

---

### 5. 构建优化不要只看“更小”，还要看“更稳”

有些优化短期看着很爽，但后期维护会很痛。老赵建议你按这个顺序来：

1. 先保证功能完整
2. 再做路由拆分
3. 再清理无效依赖
4. 再考虑资源压缩和缓存策略
5. 最后再做更细的构建优化

#### 老赵带你做
挑一个非首屏页面改成路由懒加载，再重新打包看体积变化。

#### 赵老师提醒
优化不是一上来就追求极致。**先把大头砍掉，再做精细化处理**，最省时间，也最容易见效。

## 六、常见构建报错与修复思路

### 1. 路径报错：资源找不到

常见表现：

- 图片 404
- CSS 丢失
- JS 文件加载失败
- 刷新后页面空白

排查顺序建议如下：

1. 看构建是否成功
2. 看浏览器控制台报错
3. 看 Network 里的资源请求路径
4. 检查 `base`
5. 检查资源引用方式

如果你的项目本地没事，部署后有问题，十有八九就是路径问题。别忘了，构建产物和开发环境不是一回事，生产环境下路径更严格。

---

### 2. 别名报错：`@` 找不到

常见原因是 `vite.config.ts` 没配别名，或者 TypeScript 配置没同步。

需要同时确认：

- `vite.config.ts` 配了 `resolve.alias`
- `tsconfig.json` 里有对应路径映射
- 编辑器和构建工具识别的是同一套规则

否则你会看到：代码编辑器里能识别，真正打包时却报错。  
这种问题看着烦，其实只要把配置统一就能解决。

---

### 3. 环境变量未生效

构建时经常会遇到环境变量不对，比如：

- 开发接口和生产接口混了
- 配置读取不到
- 打包后还在走本地地址

这说明你没有把 `.env.development`、`.env.production` 分清楚。  
如果前面已经做了接口封装，这里更要注意：开发时接口联调用环境变量，生产时接口地址切换也靠它。

### 4. 一个具体报错案例：图片路径 404

```vue

```

- 打包后资源前缀和实际部署前缀不一致

1. 确认图片是参与构建还是原样访问
2. 需要参与构建的，改成 `import` 或 `new URL()` 引入
3. 检查 `base`
4. 重新构建并在预览环境验证

## 一、生产部署前的检查清单：上线之前先别急着传文件

很多项目上线出问题，不是服务器不行，而是**部署前没检查干净**。前端最怕“本地没问题，上线就翻车”。

### 1. 先确认项目已经处于生产可打包状态

先在本地执行一次正式构建：

```bash
npm run build
```

Vite 默认会生成 `dist` 目录，这就是我们真正要部署的内容。上线前先确认下面几件事：

- `npm run build` 能成功
- `dist` 目录完整生成
- 打包后静态文件没有明显报错
- 接口地址没有写死在开发环境

这几项过不了，先别上服务器，问题大概率本地就能解决。

### 2. 检查接口地址是否已切到生产环境

前面我们做过 axios 请求封装，通常会通过环境变量区分开发和生产。上线前一定要确认：

- 开发环境指向测试接口
- 生产环境指向正式接口
- 代码里没有残留 `localhost`、`127.0.0.1` 或内网地址

一个常见问题是：页面能打开，但接口 404 或跨域失败。很多时候就是环境变量没切对。先打开浏览器控制台，看请求到底发到了哪儿，这一步很关键。

### 3. 检查路由模式是否适合部署

如果项目用了 Vue Router 的 history 模式，上线时服务器必须支持路由回退；否则刷新子页面就会 404。这个问题后面讲 Nginx 时会重点说。

### 4. 检查资源引用路径

Vite 打包后，静态资源路径如果配置不对，可能出现：

- 页面能打开，但 CSS、JS 加载失败
- 图片 404
- 首屏空白

所以要确认 `vite.config.js` 里的 `base` 配置是否和部署路径一致。比如项目不是挂在域名根路径，而是挂在 `/admin/` 下，就不能默认不管。

## 二、静态资源部署方式与服务器目录认识：dist 目录到底放哪儿

Vue3 + Vite 项目打包后，本质上就是一堆静态文件：`index.html`、JS、CSS、图片等。上线时，服务器并不是“运行 Vue 项目”，而是**把这些静态文件发布出去**。

### 1. 先理解 dist 目录

Vite 打包后通常会生成这样的结构：

```bash
dist/
  index.html
  assets/
    index-xxxx.js
    index-xxxx.css
```

这个目录就是生产环境的成品包。上线时，我们就是把 `dist` 里的内容上传到服务器上的某个目录，比如：

```bash
/data/apps/my-vue-app/current
/var/www/project
/usr/share/nginx/html
```

在本书这个项目里，咱们就统一按 `/data/apps/my-vue-app/current` 这个发布目录来理解，后面 Nginx 和路由配置也都围绕它来配，这样前后能对得上。

### 2. 静态资源部署的常见方式

常见有三种：

- **直接放到 Nginx 的静态目录**：最简单，也最常见。
- **放在独立 Web 目录**：每个项目单独建目录，便于管理。
- **对象存储或 CDN**：适合资源多、访问量高的项目。

### 3. 服务器目录要怎么理解

你只要记住这条线：

- **本地开发目录**：源码
- **打包产物目录**：`dist`
- **服务器发布目录**：存放 `dist` 内容的地方
- **Nginx 根目录**：实际对外提供访问的目录

上线时，真正需要服务的是构建后的静态资源，不是 `src` 目录。

### 4. 上传前的目录整理建议

建议服务器这样规划：

```bash
/data/apps/
  my-vue-app/
    current/
    backup/
```

- `current`：当前线上版本
- `backup`：旧版本备份

每次上线前先备份，出问题时能快速回滚，这个习惯非常实用。

#### 老赵带你做

记住一句话：**Vue3 + Vite 项目上线，本质是把 dist 发布出去。**  
你不需要在服务器上“安装 Vue”，你要做的是让服务器正确提供这些静态文件。

#### 赵老师提醒

别把源码直接丢到服务器就以为能跑。生产环境要部署的是打包结果，不是开发目录。目录分清楚，后面排错会轻松很多。

## 三、Nginx 基础配置与前端路由支持：为什么刷新会 404

前端项目部署到服务器后，最常用的静态服务工具就是 Nginx。它轻量、稳定、配置简单，尤其适合 Vue3 这种 SPA 项目。

### 1. Nginx 在这里做什么

在我们的项目里，Nginx 主要负责三件事：

- 提供静态文件访问
- 处理前端路由刷新问题
- 反向代理接口，配合后端联调

先看一个最基本的配置：

```nginx
server {
    listen 80;
    server_name your-domain.com;

    root /data/apps/my-vue-app/current;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

### 2. `try_files` 为什么关键

Vue Router 如果用了 history 模式，浏览器地址可能是：

- `/`
- `/user`
- `/order/detail`

这些不是服务器真实文件路径，而是前端路由。  
如果你直接刷新 `/user`，服务器会去找 `/user` 文件，当然找不到，就 404 了。

`try_files $uri $uri/ /index.html;` 的意思就是：

- 先找同名文件
- 再找同名目录
- 都没有就回退到 `index.html`

然后由 Vue Router 接管路由渲染。

### 3. 反向代理接口，解决联调和跨域

上线时，接口常常还要走代理。比如：

```nginx
location /api/ {
    proxy_pass http://backend-server:8080/;
}
```

前端请求 `/api/user/list`，Nginx 会转发到后端服务。这样做有两个好处：

- 前端不用关心后端真实地址
- 减少跨域问题

前面做过 axios 请求封装的话，这里就能明显体会到统一接口前缀的好处：开发环境和生产环境只需要切换基础地址，业务代码基本不用动。

### 4. 关于部署路径 base 的配合

如果项目不是部署在域名根路径，而是类似：

```bash
https://example.com/admin/
```

那就要同时修改 Vite 的 `base` 配置和 Nginx 的 `location` 路径。两边必须一致，不然静态资源路径很容易错。

比如这种情况，`vite.config.js` 里可以这样写：

```js
export default defineConfig({
  base: '/admin/',
})
```

同时 Nginx 也要对应把站点挂在 `/admin/` 下。只改一边不行，前后必须配套。

#### 老赵带你做

Nginx 这块先抓住两个核心：**静态文件怎么出；history 路由怎么回退。**  
这两件事解决了，Vue 项目上线就顺了。

#### 赵老师提醒

很多人看到线上 404 就以为是代码错了，其实可能只是 Nginx 没配 `try_files`。前端单页应用部署，路由回退是必考题。

## 四、前后端联调后的上线验证流程：别只看首页能不能打开

打开浏览器后先看：

- 页面是否正常渲染
- JS、CSS 是否都加载成功
- 图片是否能显示

### 2. 再验证路由跳转和刷新

建议按这个顺序走：

- 打开首页
- 点击菜单进入子页面
- 刷新子页面
- 直接输入子页面地址访问

如果都能通过，说明 Vue Router 和 Nginx 配合基本正常。

### 3. 再验证接口联调是否稳定

前面已经做过 axios 请求封装，所以上线后重点看这些点：

- 登录接口是否正常
- 列表接口是否正常
- token 是否正确携带
- 响应拦截是否生效
- 401 是否能正确处理

如果生产环境接口和开发环境接口不一样，先确认环境变量是否生效，再查 Nginx 代理是否正常。

### 4. 最后做一次完整业务流程验证

建议按真实用户路径走一遍，例如：

1. 打开首页
2. 登录
3. 进入列表页
4. 查看详情页
5. 新增或编辑一条数据
6. 刷新页面
7. 检查数据是否正常展示

这一步验证的不是单个页面，而是**完整可运行项目**的闭环。

## 五、部署后常见问题与排查方向：线上翻车时先看哪里

部署上线后，出问题很正常。关键不是“会不会出问题”，而是“出了问题知道先查哪”。

### 1. 页面空白或白屏

常见原因：

- JS 文件没加载成功
- `base` 路径不对
- 打包产物放错目录
- 浏览器控制台报错未处理

排查顺序：

1. 看 Network 是否有资源 404
2. 看控制台是否有报错
3. 检查 Nginx 根目录是否指向 `dist`
4. 检查 Vite `base` 配置

### 2. 刷新子路由 404

这是 SPA 部署最常见的问题。重点检查：

- Vue Router 是否用了 history 模式
- Nginx 是否配置了 `try_files`
- 路由访问路径是否与部署路径一致

### 3. 接口请求失败

常见原因：

- 生产环境接口地址没切换
- Nginx 代理没配置或配置错误
- 后端服务没启动
- 跨域设置不完整

排查时先看请求地址，再看响应状态码。  
如果请求根本没发出去，先查前端代码；如果返回 4xx/5xx，再查后端和代理。

### 4. 图片、字体、静态文件丢失

常见原因：

- 相对路径错了
- 构建后资源路径不对
- 部署目录层级变化了
- `base` 和服务器路径不一致

### 5. 更新后用户看到旧页面

这通常跟缓存有关。浏览器缓存、Nginx 缓存、CDN 缓存都可能导致这个问题。排查方向：

- 强制刷新页面
- 检查静态资源是否带版本哈希
- 适当配置缓存策略
- 必要时清理旧资源

#### 老赵带你做

线上问题排查，先按顺序看四层：**资源、路由、接口、缓存。**  
大部分问题都能落在这四类里。

#### 赵老师提醒

别一上来就怀疑后端，也别一上来就怀疑 Nginx。先看浏览器报错、网络请求和控制台信息，前端问题通常都藏在这些地方。

## 12.1 页面空白、路由不生效等基础问题排查：先别慌，按顺序查

### 这类问题通常怎么出现？

最常见的就是：

- 项目启动后白屏，控制台一堆红字
- 点击菜单没反应，地址变了但页面不切换
- 子页面找不到组件
- 首屏正常，切路由后空白

本质上通常不是“项目坏了”，而是入口、路由、挂载点某一环出了偏差。前端项目最怕入口级问题：入口、路由、挂载错了，后面功能再多也显示不出来。

### 老赵给你的排查顺序

#### 1）先看浏览器控制台

先看 `Console`，别急着改代码。重点抓第一条真正有价值的报错：

- `Failed to resolve component`
- `Cannot read properties of undefined`
- `Uncaught SyntaxError`
- `ChunkLoadError`
- `router is not defined`

很多时候，一条报错就能直接定位文件。别被红字吓住，先找到“第一现场”。

#### 2）检查页面入口是否正常挂载

看 `main.js` / `main.ts`：

- `createApp(App)` 是否正确
- `app.use(router)` 是否注册
- `app.use(pinia)` 是否注册
- `app.mount('#app')` 的挂载点是否存在

如果 `index.html` 没有 `#app`，或者挂载 id 不一致，页面就会空白。这个问题很基础，但实战里特别常见，尤其是复制代码后容易改乱。

#### 3）检查根组件与路由出口

`App.vue` 里通常应该有：

```vue
<template>
  <router-view />
</template>
```

如果删了 `router-view`，或者放错位置，路由页面当然不会显示。还有一种情况是布局套得太深，把路由出口“包没了”，看起来就像没渲染。

#### 4）检查路由配置

常见错误有：

- 路径写错
- 组件导入路径写错
- 子路由没配 `children`
- `redirect` 指向不存在的路径

比如子路由一般这样写：

```js
{
  path: '/user',
  component: Layout,
  children: [
    {
      path: 'list',
      component: () => import('@/views/user/List.vue')
    }
  ]
}
```

注意子路由路径通常写 `list`，不是 `/list`。写成绝对路径，层级和菜单就容易乱。

### 常见误区

- 白屏就怀疑 Vite 有问题，其实多半是代码报错
- 路由配置对了，但忘了在 `App.vue` 放 `router-view`
- 组件路径用了别名 `@`，但 Vite 没配好
- 路由路径和菜单路径不一致，导致能跳转却不显示

### 检查清单

- [ ] `main.js` 是否注册了 router、pinia
- [ ] `App.vue` 是否有 `router-view`
- [ ] 路由路径是否拼写正确
- [ ] 组件导入路径是否正确
- [ ] 控制台是否有明显报错

## 12.2 接口跨域、请求失败与数据异常处理：联调别只看“发出去没”

### 为什么联调最容易出问题？

前面我们做了 **axios 请求封装**，真正联调时，问题往往不在“有没有发请求”，而在：

- 请求发出去了，但浏览器拦了
- 请求成功了，但后端返回结构和前端预期不一致
- 接口偶尔成功、偶尔失败
- 页面拿到空数据，却没有提示

所以接口联调的核心不是“能请求”，而是 **请求、响应、异常处理** 三件事都要稳。

### 1）跨域问题怎么判断？

如果控制台出现：

- `CORS policy`
- `No 'Access-Control-Allow-Origin' header`
- `Network Error`

那大概率是跨域问题。也可能是代理没生效，或者请求地址写成绝对地址，绕开了 Vite 代理。

### 2）跨域问题怎么处理？

开发阶段最常见的方法是用 Vite 代理：

```js
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:3000',
        changeOrigin: true,
        rewrite: path => path.replace(/^\/api/, '')
      }
    }
  }
})
```

前端请求 `/api/user/list`，开发服务器会自动转发到后端。这样不仅能解决跨域，也能避免接口地址写死在页面里。

### 3）请求失败怎么处理？

建议把错误统一收口，不要每个页面自己乱写。axios 封装里一般要做到：

- 请求前设置超时
- 成功时统一判断业务码
- 失败时统一提示
- 把错误信息返回给调用方

这样页面更干净，排错也更集中。以后接口或后端返回格式变化，主要改请求层，不用到处找页面。

### 4）数据异常怎么处理？

接口成功，不等于数据可用。比如：

- 后端返回 `null`
- 字段名和前端不一致
- 数组为空
- 分页结构变化

前端不要假设接口永远完美，拿数据前最好做保护：

```js
const list = res?.data?.list || []
```

页面渲染时也要准备空状态、加载状态、错误状态。特别是列表页，没有数据时别硬渲染，用户会以为页面坏了。

### 常见误区

- 只写 `then`，不写 `catch`
- 认为返回 200 就万事大吉
- 不看响应结构，直接 `res.data.list.map(...)`
- 开发环境能调通，生产环境却忘了改 `baseURL`
- 代理生效了，但请求写成绝对 URL，导致代理失效

### 老赵带你做

联调阶段按这个顺序走：

1. 先用 Postman 或浏览器确认接口本身可用  
2. 再看 axios 封装里的 `baseURL` 是否正确  
3. 然后检查 Vite 代理是否生效  
4. 最后核对响应结构是否和页面一致  
5. 页面上补齐空态、错态、加载态

这样排查，效率比一上来怀疑页面逻辑高得多。

## 12.3 状态管理、路由跳转与权限相关问题：别让 Pinia 和路由打架

### 为什么状态和权限问题容易乱？

因为这类问题通常不是单点错误，而是链路问题。比如：

- 登录后，Pinia 里有 token，但菜单没刷新
- 路由跳转成功了，但按钮权限没生效
- 退出登录后，状态清了，缓存菜单还在
- 动态路由加进去了，刷新后又没了

你要明白：**状态管理负责存，路由负责跳，权限负责拦。三者分工要清楚。**

### 1）Pinia 状态没同步怎么办？

如果 token、用户信息、菜单都放在 Pinia 里，要注意两件事：

- 是否做了持久化
- 是否在刷新后重新初始化

因为页面一刷新，内存状态会丢。如果没把 token 持久化到 `localStorage`，登录态就会断。很多同学以为登录成功就完了，结果一刷新又回到未登录，这就是状态没落地。

### 2）路由跳转为什么没生效？

常见原因有：

- `router.push` 路径写错
- 路由守卫里提前返回
- 动态路由还没添加完就跳转
- 组件内导航和权限判断冲突

调试时先把守卫逻辑简化，确认基础跳转没问题，再逐步加权限判断。不要一开始把登录校验、菜单生成、动态路由、按钮权限全揉在一起，不然问题来了很难查。

### 3）权限判断要怎么做更稳？

常见权限有三种：

- **路由级权限**：能不能进入页面
- **菜单级权限**：左侧菜单显示什么
- **按钮级权限**：新增、删除、编辑能不能点

建议分层处理：

- 路由守卫负责“能不能进”
- 菜单数据负责“显示什么”
- 组件内部负责“按钮能不能用”

这样权限逻辑更清晰，后期也好维护。

### 常见误区

- 登录后只改了 Pinia，没有更新路由和菜单
- 退出登录只清了 token，没清动态路由
- 权限判断写得太散，后期维护困难
- 把所有判断都塞进一个守卫里，最后自己也看不懂

### 赵老师提醒

权限模块最怕“补丁式开发”。今天这里加一段，明天那里补一个 `if`，最后连你自己也不敢改。  
**建议你把登录、菜单、动态路由、退出清理这条链路一次性理顺。**

## 12.4 打包后资源路径和刷新 404 问题：线上能不能跑，关键看这一关

### 为什么本地正常，线上就出问题？

本地开发时，Vite 会帮你兜底很多事情；但打包上线后，浏览器只认真实路径。于是常见问题就来了：

- 页面一刷新就 404
- JS、CSS 资源找不到
- 图片路径失效
- 子路由地址访问不了

这类问题大多和 **打包配置**、**部署路径**、**服务器配置** 有关。

### 1）资源路径错了怎么办？

先检查 `vite.config.js` 里的 `base`。

如果项目不是部署在域名根路径，而是放在子目录下，比如 `/admin/`，那 `base` 就不能用默认值：

```js
export default defineConfig({
  base: '/admin/'
})
```

`base` 不对，打包后的静态资源引用就会错位。尤其是部署到二级目录时，这个问题特别高发。本地没事，上线一堆资源 404，通常就是这里没配好。

### 2）刷新 404 怎么处理？

前端路由如果用的是 History 模式，刷新后浏览器会直接请求当前路径。  
如果服务器没有做“重写到入口页”的配置，就会 404。

解决思路有两个：

- 生产服务器配置路由重写
- 或改用 Hash 模式，部署更省事，但 URL 不够美观

本书项目更建议你理解并掌握 History 模式的重写，因为这更接近真实生产环境。

### 3）图片、字体、静态资源失效怎么办？

建议统一使用：

- `import` 引入
- `new URL(..., import.meta.url)`
- 或放到 `public` 目录按规则访问

不要在代码里乱写死路径，开发时可能能看，打包后就容易出问题。布局页里的 logo、背景图、图标字体，最容易先坏的就是这些资源。

### 检查清单

- [ ] `vite.config.js` 的 `base` 是否正确
- [ ] 路由模式是否和服务器配置一致
- [ ] 静态资源引用方式是否正确
- [ ] 服务器是否配置了前端路由重写
- [ ] 线上访问路径是否与部署目录一致

### 老赵带你做

部署前先做这几步：

1. 本地执行 `npm run build`，确认打包成功  
2. 用 `dist` 目录在测试服务器跑一遍  
3. 刷新任意子页面，看是否 404  
4. 打开 Network，看资源有没有 404  
5. 如果有问题，先查 `base` 和服务器重写规则

把这几步走完，你对“线上能不能跑”就心里有数了。

## 12.5 整个项目从开发到部署的复盘与优化建议：把项目真正收住

### 这一章真正想教你的是什么？

不是为了列一堆报错，而是让你形成完整的项目收尾习惯。一个能跑的 Vue3 + Vite 项目，至少要经过这些确认：

- 开发环境能启动
- 页面布局完整
- 路由切换正常
- Pinia 状态可用
- axios 请求封装稳定
- 接口联调可控
- 打包配置正确
- 生产部署可访问

项目能不能交付，不只看功能数量，更看链路是否完整。前端项目做到最后，拼的就是稳定性和可维护性。

### 项目复盘建议：按这四步走

#### 第一步：看基础链路

从 `main.js`、`App.vue`、`router`、`pinia` 开始查，确认项目骨架没问题。基础链路不稳，后面问题会一层层放大。

#### 第二步：看业务链路

从页面布局、组件拆分、请求封装、状态流转一路查到页面渲染结果。看看数据是不是按预期从接口进入页面，中间有没有断层、错层。

#### 第三步：看构建链路

检查环境变量、代理配置、`base`、打包结果、静态资源路径。很多项目开发时正常，一打包就出问题，往往就是这条链路没复盘。

#### 第四步：看部署链路

确认服务器重写、静态资源访问、刷新策略、缓存更新是否正常。上线不是把文件传上去就结束了，关键是传上去以后还能不能正常访问。

### 优化建议

- 请求封装统一错误处理，别让页面重复写逻辑
- 路由和权限逻辑分层，别互相缠在一起
- 组件拆分要适中，别拆得太碎
- 环境变量区分开发、测试、生产
- 打包前先检查 `dist` 和资源路径
- 上线前做一次全链路冒烟测试

### 赵老师提醒

项目做到最后，最容易犯的错误就是“差不多就上线”。  
老赵提醒你：**开发时的小问题，到了生产环境往往会被放大。** 所以收尾阶段最重要的不是继续加功能，而是把已有功能跑稳、跑顺、跑全。
