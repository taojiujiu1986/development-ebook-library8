# 第1章 先搞懂 Nuxt：它和 Vue3 到底是什么关系

## 开篇引入：为什么 Vue3 已经会了，还要学 Nuxt？

很多已经会 Vue3 的同学第一次听到 Nuxt，都会问：**我组件会写、响应式会用、路由也能配，为什么还要再学一个框架？**

这个问题很正常。因为 Nuxt 不是来否定 Vue3 的，它更像是站在 Vue3 之上，把一个页面升级成一个更完整、更适合上线的网站。你可以把 Vue3 理解成“把页面做出来的能力”，把 Nuxt 理解成“把页面组织成一个可维护、可扩展、适合生产环境的网站的能力”。

Vue3 更关注“怎么写页面”，Nuxt 更关注：

- 页面怎么自动生成路由
- 布局怎么统一管理
- 数据怎么在服务端先拿到
- 页面标题和描述怎么更好地服务 SEO
- 目录怎么按约定组织，团队怎么协作
- 内容站、展示站、博客怎么更快搭起来

所以，学 Nuxt 不是推翻你会的 Vue3，而是让你用 Vue3 做出更完整的项目。你已经熟悉 Vue3 之后，再学 Nuxt 往往会更顺，因为组件写法、组合式 API、响应式思路，大多还是熟悉的那套。

### 老赵经验分享

老赵做项目最怕的不是功能少，而是项目写着写着就散了。前期图快，后面目录像迷宫。Nuxt 的价值之一，就是先把项目长相定下来，后面协作会省很多事。

### 赵老师提醒

不要把 Nuxt 当成“Vue 的替代品”。它不是换语言，而是**给 Vue3 增加工程化、渲染和约定能力**。会 Vue3 是前提，会 Nuxt 才是把 Vue 用到更完整场景里的关键一步。

## 一、Nuxt 是什么：它解决了 Vue 开发中的哪些问题？

Nuxt 可以理解为一个基于 Vue 的上层框架。它围绕 Vue 的应用开发，补齐从组件到项目的关键能力，更适合做网站型应用。

### 1.1 解决“页面组织混乱”的问题

纯 Vue 项目做到一定规模后，常见问题就来了：

- 路由越来越长
- 页面、布局、组件、资源混在一起
- 不同开发者写法不统一
- 新人接手时不知道入口在哪

这些问题本质上不是不会写，而是缺少统一的组织方式。Nuxt 的思路很直接：**用约定代替大量配置**。文件放在哪里，框架就默认它是什么角色。页面放在 `pages`，布局放在 `layouts`，组件放在 `components`，这就是**约定式开发**。

它的好处很明确：不用先想“路由怎么写、入口在哪里”，而是按约定放文件，项目就自然成型。对 Vue3 开发者来说，这一点尤其友好，因为 Nuxt 不是让你多写一套东西，而是帮你少写那些重复且容易出错的配置。

### 1.2 解决“首屏和 SEO 不够友好”的问题

很多 Vue SPA 先给浏览器一个空壳，再靠前端渲染内容。这样开发简单，但在一些场景会有两个现实问题：

1. 首屏体验不稳定  
2. 搜索引擎抓取内容不够直接

Nuxt 提供 SSR（服务端渲染）和 SSG（静态站点生成）能力，让页面可以在服务端或构建时就产出内容，更适合内容站、博客、产品展示站这类对曝光和首屏有要求的项目。

### 1.3 解决“团队协作成本高”的问题

Vue3 项目如果完全靠个人习惯组织，很容易出现多套目录、多种写法、多个数据请求方式。Nuxt 把很多规则提前定好，团队统一之后，协作成本会明显下降。新人只要熟悉目录约定，就能快速知道页面、布局、组件该放哪。

### 老赵经验分享

老赵一直觉得，框架最值钱的地方不是“功能多”，而是“大家能不能用同一套方式做事”。Nuxt 这种约定式框架，特别适合团队项目，也特别适合后面还要继续扩展的站点型应用。

### 赵老师提醒

约定式开发很省心，但前提是**你要尊重约定**。自己随意改目录、乱放文件，最后还是会把框架优势抵消掉。

## 二、Nuxt 和 Vue3 的关系：在 Vue 之上增加了哪些能力？

一句话说清两者关系：**Vue3 负责视图和响应式能力，Nuxt 负责应用级组织与渲染能力。**

### 2.1 Vue3 是基础，Nuxt 是“带规则的应用框架”

在 Nuxt 里，你依然是在写 Vue 组件、用组合式 API、写模板、用响应式数据。也就是说，**Vue3 的核心语法基本都能沿用**。

Nuxt 在此之上补了几层：

- **文件系统路由**：不用手写路由表
- **页面与布局系统**：页面天然分层
- **服务端数据获取**：更适合 SSR
- **SEO 能力**：页面元信息更好配置
- **运行时约定**：减少重复配置和样板代码

你可以把 Vue3 理解成“砖瓦”，Nuxt 则像“规划好户型、楼层和门窗的建筑方案”。材料没变，搭建方式更系统。

### 2.2 从“写组件”到“搭系统”

Vue3 更多关注单个页面或局部交互；Nuxt 更关注整个站点如何运行。比如一个产品展示站，Vue3 可以做出来，但你可能要自己处理：

- 路由怎么配
- 首页和详情页怎么统一布局
- 首屏怎么渲染
- 页面标题怎么随内容变化
- 生产环境怎么部署

Nuxt 往往把这些变成默认能力。你要做的，是按约定把文件和逻辑放对位置。

### 2.3 你会 Vue3，迁移 Nuxt 并不难

很多 Vue3 开发者第一次上手 Nuxt，会担心是不是要重新学一套语法。其实大多数情况下，你只是多学几个项目级概念：

- 页面文件怎么对应路由
- 哪些逻辑放页面里，哪些抽到组合函数里
- 数据请求什么时候在服务端执行
- 如何用布局包住页面

所以，Nuxt 和 Vue3 的关系不是断裂式的，而是递进式的。你会 Vue3，就已经拿到了 Nuxt 学习的大半门票。

### 老赵经验分享

老赵建议 Vue3 开发者学 Nuxt 时，先分清一件事：**这是组件级问题，还是应用级问题？** 组件级的，Vue3 就够；路由、布局、SSR、SEO 这类应用级问题，交给 Nuxt。

### 赵老师提醒

不要以为“会 Vue3 就等于会 Nuxt”。语法相通，不代表思维相通。Nuxt 真正难的地方，不在组件写法，而在**约定、渲染时机、页面组织方式**。

## 三、Nuxt 的约定式开发特点：文件结构、目录约定和自动路由

如果说 Nuxt 最有代表性的地方是什么，那一定是**约定式开发**。这不是一个小特性，而是它整个开发体验的核心。

### 3.1 文件放哪，角色就基本定了

在 Nuxt 里，很多时候你不用先写一堆配置，再去告诉框架“这是页面、这是布局、这是组件”。相反，你只要把文件放到对应目录里，框架就知道该怎么处理。

常见目录先记住这几个：

- `pages/`：页面目录，自动生成路由
- `layouts/`：布局目录，用来包裹页面外壳
- `components/`：组件目录，页面中直接使用
- `composables/`：可复用逻辑目录
- `assets/`：需要构建处理的静态资源
- `public/`：直接原样输出的静态资源

这套结构最大的意义，不只是整齐，而是让团队里的每个人都用同一套方式理解项目。

### 3.2 自动路由：页面就是路由

在 Nuxt 里，通常不用单独写路由配置文件。页面文件本身就能映射为路由。比如：

- `pages/index.vue` 对应首页
- `pages/about.vue` 对应 `/about`
- `pages/blog/[id].vue` 对应动态路由

这对 Vue3 开发者很友好：你不必先搭路由表，再把组件挂进去，而是先把页面写好，路由自然就出来了。尤其是做内容站、博客、展示站时，这种方式很顺手。

### 3.3 目录约定带来的实际价值

约定式开发不是为了限制你，而是为了减少沟通成本和重复劳动。你从 Vue3 过渡到 Nuxt 后，会慢慢形成一种新习惯：不是先想“我怎么配置”，而是先想“我应该把这个文件放哪”。

这种变化看起来小，但项目越大越明显。它让项目结构更清楚，也让后续扩展更稳定。

### 老赵经验分享

老赵很喜欢文件系统路由，因为它把“目录结构”和“页面结构”统一了。项目越大，这种一致性越值钱，后面接手的人一看目录就知道大概怎么走。

### 赵老师提醒

约定式开发看起来简单，但前提是**按约定做事**。目录乱了，框架的优势也就没了。你要是把页面、组件、工具文件混着放，最后还是会回到“自己维护自己看得懂”的老路上。

## 四、Nuxt 适合做什么：重点放在内容站、展示站和博客

很多人会问：Nuxt 到底适合做什么？答案不是“什么都适合”，而是看场景。

### 4.1 很适合：内容站、展示站、博客、官网

这类项目通常有几个特点：

- 页面结构相对稳定
- 需要较好的首屏和 SEO
- 内容由文章、产品、案例、文档组成
- 需要统一布局和多页面管理

Nuxt 在这些场景里优势明显，因为页面生成方式、布局系统、服务端数据获取都很对口。比如做博客首页，你可以把文章列表放在首页，详情页用动态路由承接，整站通过统一布局串起来。

### 4.2 也能做：中小型后台

Nuxt 也能做管理后台，尤其是后台里有统一布局、登录、权限、列表详情等模块时，体验不错。只是后台通常对 SEO 不敏感，Nuxt 的优势不一定是核心。如果后台同时还要做对外展示页、帮助中心、文档中心，Nuxt 仍然是不错的选择。

### 4.3 不一定优先：高度交互、强客户端状态的复杂系统

如果项目更偏实时协作、复杂图表、强交互编辑器，Nuxt 当然也能做，但你要更注意客户端渲染和状态边界。这种场景里，Nuxt 的价值主要是应用框架能力，不一定是 SEO。

### 老赵经验分享

老赵有个简单判断：**如果项目页面多、内容多、入口多、展示多，Nuxt 往往更合适。**如果项目交互重、状态重、实时性强，就要评估它是不是最合适的方案。

### 赵老师提醒

不要为了学而学，更不要看到 Nuxt 就想“所有项目都上”。学习阶段，优先拿它做**博客首页、产品展示站、内容型官网**，最容易把优势吃透。

## 五、学习路径说明：从 Vue3 过渡到 Nuxt 的正确打开方式

你已经会 Vue3，学 Nuxt 最好的方式不是从头背概念，而是沿着“熟悉的地方进，新能力逐步补”的路线走。

### 5.1 先对齐 Vue3 能力

至少要熟悉这些基础：

- 组件拆分与传参
- 组合式 API
- 响应式状态
- 生命周期
- 条件渲染与列表渲染

这些在 Nuxt 里还会继续用到。换句话说，Nuxt 不会让你抛弃 Vue3，而是继续复用你的 Vue3 经验。

### 5.2 再理解 Nuxt 的新增心智

重点不是“多了多少语法”，而是这几件事：

- 页面如何生成路由
- 布局如何套用
- 数据如何服务端获取
- SEO 信息如何配置
- 项目结构如何遵守约定

这些能力串起来之后，你会发现 Nuxt 的开发节奏和普通 Vue SPA 不太一样。它更像是在搭一个有规则的网站，而不是随意拼装一个页面。

### 5.3 最后通过项目建立手感

学习 Nuxt 最快的方式，是做一个小而完整的站点，比如：

- 博客首页
- 产品展示站
- 公司官网首页
- 活动落地页

先把页面、布局、路由、数据、SEO 串起来，再去学更细的能力，理解会牢很多。

### 老赵经验分享

老赵建议你别一上来就钻复杂源码。先做一个“能跑、能看、能部署”的站点，感受 Nuxt 的默认能力，再回头看原理，会轻松很多。

### 赵老师提醒

从 Vue3 过渡到 Nuxt，最大的误区是只盯着模板写法，忽略了“页面怎么诞生、数据什么时候拿、内容怎么被搜索引擎看到”。这几个问题，才是 Nuxt 的核心。

## 一、创建 Nuxt 项目：脚手架选择与初始化流程

### 1.1 Nuxt 项目怎么创建？

最稳妥的方式是用官方脚手架初始化项目。入门阶段别手搓目录，也别急着改模板，先按官方流程创建一个标准项目。原因很简单：你现在的目标不是证明自己会搭架子，而是尽快进入 Nuxt 的工作流。

标准流程可以理解为三步：

1. 执行初始化命令；
2. 按提示选择项目名、包管理器等选项；
3. 安装依赖并启动开发服务器。

最终你会得到一个默认结构清晰、可直接运行的 Nuxt 项目。这个默认项目很重要，因为它不是“空壳”，而是 Nuxt 的标准起点。后面像自动路由、布局系统、服务端数据获取，都是从这个起点延伸出来的。

如果你习惯 Vue3 项目里先建 `src`、再配 router，Nuxt 则相反：它先给你一个框架认可的组织方式，你再按约定往里填内容。这样做的好处是，项目越大越省心，尤其适合博客、内容站、产品展示站这类结构清晰的项目。

### 1.2 初始化时重点看什么？

初始化时，常见要关注这些点：

- **项目名称**：简洁清楚即可；
- **包管理器**：pnpm、npm、yarn 都行，团队最好统一；
- **TypeScript**：如果你会，建议直接开启，后面写组件和接口更顺；
- **额外模块**：首次学习建议少装，先跑通默认项目。

老赵给你一个判断标准：

- **只想快速入门**：先选最基础配置；
- **准备长期维护项目**：一开始就统一包管理器和编码规范；
- **Vue3 基础好，也会一点 TS**：尽早开启 TypeScript，后面少补课。

还有一点很关键：初始化时别追求“一步到位”。Nuxt 的扩展能力都可以后加，先把默认项目跑起来，比一开始就堆模块更有学习价值。你要先知道哪些能力是 Nuxt 默认就有的，哪些是你自己加出来的。

### 1.3 为什么不要急着魔改初始化选项？

很多刚接触 Nuxt 的同学，初始化完第一件事就是装一堆库：状态管理、UI 组件库、请求库、图标库……  
老赵的建议是：**先让最小可运行项目跑起来，再加功能**。

因为你现在最需要的是理解 Nuxt 的默认行为，而不是把项目改成“另一个 Vue 项目”。  
先熟悉默认目录、默认路由、默认页面渲染逻辑，后面你才知道哪些配置是 Nuxt 自动帮你做的，哪些是你自己加的。

比如你做的是博客首页，先把首页、文章页、导航和基础样式跑通，再考虑接入文章列表接口、Markdown 渲染、搜索和标签筛选。这样你每一步都能明确知道，项目是在 Nuxt 的哪一层能力上推进的。

### 老赵经验分享

我带过不少从 Vue 过渡到 Nuxt 的同学，最大的问题不是不会写代码，而是“太想马上像成熟项目一样搭全家桶”。结果初始化阶段就把自己绕晕了。  
**先跑通，再扩展**，这是 Nuxt 入门最稳的路径。

### 赵老师提醒

初始化时别忽略“团队一致性”。  
哪怕是个人项目，也建议你一开始就固定包管理器、Node 版本和代码风格。项目一大，环境不统一会非常折腾。

## 二、开发环境准备：Node、包管理器、编辑器与插件建议

### 2.1 Nuxt 对开发环境的基本要求是什么？

Nuxt 本质上是建立在 Node 生态上的前端框架，所以基础环境要干净、稳定。这个阶段最重要的不是“越新越好”，而是“稳定、兼容、可复现”。

建议检查这些方面：

- **Node 版本**：保持在项目可用且稳定的区间；
- **包管理器**：选一种并坚持使用；
- **编辑器**：推荐 VS Code；
- **常用插件**：Vue、TypeScript、ESLint、Prettier 等。

如果你之前做的是纯 Vue3 项目，可能会觉得这些准备很普通。但到了 Nuxt，这些基础更重要。因为 Nuxt 涉及编译、服务器渲染、预渲染和运行时配置，环境一旦不稳，问题常常不是“页面不显示”这么简单，而是构建失败、服务启动异常、首屏报错等更隐蔽的问题。

### 2.2 编辑器和插件怎么配？

如果你用 VS Code，建议至少具备这些能力：

- Vue 文件高亮与语法提示；
- TypeScript 类型提示；
- 自动格式化；
- ESLint 代码检查；
- 文件快速跳转与路径补全。

Nuxt 项目很依赖目录约定和文件命名，编辑器补全越强，你越不容易在“文件放哪、组件怎么命名、页面怎么识别”这些基础问题上浪费时间。尤其是 `.vue`、`.ts` 和配置文件混在一起时，编辑器提示会直接影响效率。你不需要记住所有路径，只要让编辑器帮你快速定位文件，把注意力放到业务逻辑上就行。

### 2.3 环境准备的判断标准

环境是否准备好，不看你装了多少工具，而看你能不能做到：

- 创建项目时不报环境错误；
- 安装依赖速度正常；
- 运行开发命令后页面能打开；
- 保存文件后能够热更新；
- 编辑器能正确识别 `.vue`、`.ts` 文件。

最简单的验证方法就是：创建一个 Nuxt 项目，打开默认页面，改一行文字，看浏览器是否立刻更新。这个动作虽然简单，但能很好地验证环境链路是否完整。

### 老赵经验分享

做前端项目最怕“我机器上能跑”。  
环境越早统一越省事，尤其是 Nuxt 这种会涉及服务端渲染、构建和预渲染的框架，环境不一致带来的问题比纯前端项目更麻烦。

### 赵老师提醒

别迷信“装更多插件就更专业”。真正有用的是：**能稳定识别代码、减少低级错误、让项目保持一致**。插件不是越多越好，够用、稳定、统一才重要。

## 三、项目启动与目录初览：认识默认生成的结构

### 3.1 启动之后你会看到什么？

项目创建完成后，接下来就是启动开发服务。  
一旦启动成功，你通常会看到一个默认首页，这说明 Nuxt 的基础链路已经打通：**源码 → 编译 → 服务端/客户端渲染 → 浏览器展示**。

这一步不只是“能跑”，更是在告诉你：Nuxt 默认已经帮你安排好了很多结构。Vue3 开发者通常习惯从空白项目往里加东西，而 Nuxt 是先给你一个骨架，再往上填内容。这个差别看着不大，实际会影响你后面组织页面和维护代码的方式。

### 3.2 先认识几个最关键的默认目录

Nuxt 的约定式开发核心，就体现在默认目录上。你不用手工注册路由，也不用从零配置页面入口，框架会根据目录约定自动识别。

先记住几个常见目录：

- **`pages/`**：页面目录，和路由生成强相关；
- **`components/`**：组件目录，放可复用组件；
- **`layouts/`**：布局目录，负责页面骨架；
- **`assets/`**：源文件资源，如样式、图片等；
- **`public/`**：静态资源目录，直接按路径访问；
- **`server/`**：服务端相关能力目录；
- **`nuxt.config`**：框架配置入口。

你现在不必一次全记住，但要建立一个直觉：  
**Nuxt 不是先写路由配置再写页面，而是先按目录放文件，框架再帮你生成行为。**

这就是它跟 Vue3 SPA 很不一样的地方。Vue3 更像灵活的工具箱，而 Nuxt 更像完整的工程化模板。你只要按规则放文件，页面、路由、布局、资源引用就会跟着成立。

### 3.3 默认结构的价值在哪里？

对 Vue3 开发者来说，最熟悉的是“组件拼页面”。  
而 Nuxt 在这个基础上多了一层“框架帮你组织项目”的能力。页面、布局、公共逻辑不再靠人工到处串联，而是通过目录约定自然形成结构。

这意味着：

- 页面文件放对位置，路由自动有了；
- 布局文件写好，页面可以直接套用；
- 公共组件命名合理，自动可用；
- 配置入口集中，项目更容易维护。

如果你准备做内容站或展示站，这种结构尤其好用。因为这类站点页面不复杂，但通常有统一的头部、底部、导航和 SEO 规则，Nuxt 的默认结构刚好适合这种“内容为主、结构稳定”的场景。

### 老赵经验分享

很多人第一次看 Nuxt 目录会觉得“怎么这么像一个已经搭好骨架的项目”。  
没错，这正是 Nuxt 的优势：**它不是要你从零设计规则，而是给你一套默认可落地的规则。**

### 赵老师提醒

目录约定不是死规矩，但你先别急着挑战。  
入门阶段最重要的是“按默认方式做事”，先把框架的习惯吃透，再谈个性化组织。

## 四、基础配置文件：`nuxt.config` 的用途与常见设置

### 4.1 `nuxt.config` 是干什么的？

如果把项目比作房子，`nuxt.config` 就是总开关和基础说明书。  
它负责配置框架行为，而不是写具体页面逻辑。

常见用途包括：

- 项目基础信息；
- 全局样式引入；
- 模块配置；
- 构建与运行相关设置；
- SEO 默认配置；
- 服务端与客户端通用策略。

对新手来说，`nuxt.config` 不是一上来就要精通的地方，而是先知道它管什么、不管什么。页面内容、组件结构、局部交互，不应该塞进这里；全局生效的设置、环境相关配置、全站统一信息，才适合放在这里。

### 4.2 适合新手先掌握的配置项

入门阶段，你只需要先知道几个方向：

- **应用基础信息**：名称、描述、默认 head 信息；
- **CSS 引入**：全局样式文件；
- **模块使用**：后续扩展功能会靠这里；
- **运行时配置**：不同环境下的参数管理；
- **构建设置**：当项目有额外编译需求时使用。

记住一个原则：  
如果是全站通用的东西，就考虑放到配置里；如果只是某个页面独有的内容，就留在页面或组件里处理。

比如做产品展示站，网站标题、默认描述、全局字体、基础主题色，通常适合放配置里；而某个产品卡片的文案、按钮状态和局部动画，则应该写在组件里。

### 4.3 配置的原则：少而清晰

新手最容易犯的错误，是把 `nuxt.config` 当成万能杂物间。  
结果所有东西都往里塞，最后谁也找不到。

更好的原则是：

1. 全局性配置放这里；
2. 页面级逻辑写到页面里；
3. 组件逻辑放组件里；
4. 服务端接口相关的东西放对应目录；
5. 不要把临时试验配置长期留在项目里。

这样做的好处很明显：项目结构更清楚，后面回来看时，能一眼知道哪个配置影响全局，哪个代码只影响某个页面。

### 4.4 一个实用判断：什么时候该改 `nuxt.config`？

如果你要做的是这些事情，通常就该考虑配置文件：

- 全局引入样式；
- 定义应用名称、描述；
- 配置某个模块；
- 统一运行环境变量；
- 定制构建行为。

如果只是某个页面的局部逻辑，别急着进配置文件，直接在页面或组件里处理更合适。

### 老赵经验分享

我很喜欢看一个项目有没有“干净的配置文件”。  
配置文件越清楚，接手的人越容易理解项目骨架。Nuxt 项目尤其如此，因为它很多能力都靠约定和默认配置驱动。

### 赵老师提醒

别把 `nuxt.config` 当成“越复杂越高级”。  
真正成熟的项目配置是：**能说明问题，但不喧宾夺主**。复杂配置应该有明确目的，不要为了“看起来专业”而堆设置。

## 五、常用开发命令：启动、构建、预览、调试

### 5.1 新手至少要掌握哪些命令？

Nuxt 项目从开发到上线，通常会经历几个阶段。你最少要会这几类命令：

- **开发启动**：本地热更新开发；
- **生产构建**：生成生产环境产物；
- **预览检查**：模拟上线后的效果；
- **调试排错**：观察构建与运行问题。

它们分别对应：

- 开发时快速改页面；
- 发布前确认代码能构建；
- 上线前检查实际表现；
- 出问题时定位错误来源。

这些命令看起来平常，但它们其实是你理解 Nuxt 工程流程的入口。你一旦知道“开发”和“构建”不是同一回事，就会开始用更工程化的视角看项目，而不是只盯着页面能不能打开。

### 5.2 为什么不能只会“启动”？

很多同学一上来只会跑开发命令，觉得页面能打开就行。  
但 Nuxt 项目真正要走向实战，你必须知道构建和预览，否则等到部署阶段才发现报错，就会非常被动。

你至少要明白：

- 开发环境能跑，不代表生产环境能跑；
- 本地页面正常，不代表打包后没问题；
- 预览成功，才更接近真实上线状态。

尤其是做内容站、博客站、展示站时，首屏效果、静态资源路径、Meta 信息、页面生成方式，往往会在构建和预览阶段暴露问题。只停留在开发模式，很容易在上线前吃亏。

### 5.3 调试时重点看什么？

第一次接触 Nuxt 的时候，调试建议重点关注：

- 页面有没有正常渲染；
- 控制台是否报错；
- 网络请求是否成功；
- 路由跳转是否正常；
- 样式是否按预期生效。

如果是服务端渲染项目，还要特别留意首屏返回内容是否正常、是否存在 hydration 相关异常。

调试顺序建议是：先看终端，再看浏览器控制台，再看页面表现，最后回到代码定位问题。这样排查效率更高，也不容易被表面的样式问题带偏。

### 老赵经验分享

我建议你养成一个习惯：**每次改完一块核心功能，不只看浏览器界面，还要顺手跑一次构建或预览。**  
这样你会更早发现“开发环境没暴露的问题”。

### 赵老师提醒

不要把“本地能看见”误认为“项目没问题”。  
Nuxt 比纯前端项目更接近真实交付流程，开发、构建、预览这三步都要过一遍，心里才踏实。

## 六、第一次运行项目：检查页面是否正常渲染

### 6.1 第一次运行要检查什么？

项目启动后，第一件事不是急着改页面，而是确认基础链路有没有正常工作。  
你可以按这个顺序检查：

1. 浏览器是否打开默认页面；
2. 页面文本是否正确显示；
3. 热更新是否生效；
4. 控制台是否有明显报错；
5. 修改一行内容后页面是否同步更新。

这一步是在验证你的 Nuxt 项目“真的活了”。

对 Vue3 开发者来说，这一步还有另一个意义：你要开始接受 Nuxt 的页面不是手工挂载出来的，而是由框架按照约定自动生成并渲染出来的。你的思维方式，会从“写组件并在入口挂载”逐渐过渡到“按目录组织页面，让框架帮你建立页面体系”。

### 6.2 如果页面没正常显示，怎么排查？

新手常见问题一般集中在这些方面：

- 依赖没装完整；
- Node 版本不合适；
- 包管理器混用；
- 端口被占用；
- 目录文件放错位置；
- 配置文件语法错误。

排查顺序建议是：

1. 看终端报错；
2. 看浏览器控制台；
3. 看项目目录是否有基础文件缺失；
4. 回到配置文件检查最近改动。

如果你在练页面生成和布局，还要注意是不是把页面文件放错目录了。Nuxt 对目录约定很敏感，放错位置就不会按预期生效，这也是约定式开发的特点之一。

### 6.3 用第一次运行建立“框架感”

第一次看到 Nuxt 页面正常渲染，你要建立两个认知：

- **页面不是你手工注册出来的，而是框架根据约定生成的**；
- **你看到的结果不仅来自 Vue 组件，还来自 Nuxt 的渲染机制与项目结构**。

这就是从 Vue3 过渡到 Nuxt 的第一步：  
你不再只是“写组件”，你开始“按框架规则组织页面、路由和布局”。

如果后面你要做博客首页、文章详情页、产品展示页，这种框架感会很有用。它能帮助你更快判断：这个东西应该放页面、放组件，还是放布局；这个数据应该前端请求，还是服务端提前获取。

### 老赵经验分享

很多人第一次成功跑起 Nuxt 的时候，最开心的不是页面漂亮，而是“终于知道它到底是怎么工作的了”。  
这种感觉很重要，它会让你后面学路由、布局、数据获取时更有底气。

### 赵老师提醒

别在项目刚跑通时就立刻大规模重构。  
先保留默认结构，先理解默认行为，再逐步替换成自己的业务逻辑，这样学习效率最高。

## 七、从初始化走向页面开发：下一步该怎么接上

到这里，你已经完成了 Nuxt 入门最关键的“起跑动作”。  
项目能创建、依赖能安装、开发服务能启动、默认页面能渲染，说明你已经把环境和骨架都跑通了。接下来要做的，不是继续在环境里打转，而是自然进入 Nuxt 最核心的约定式开发阶段。

下一章我们就会接着看：

- `pages/` 为什么能自动生成页面；
- `layouts/` 如何统一页面骨架；
- 页面文件如何决定路由；
- Vue3 开发者该怎样从“写组件”过渡到“写页面”。

你可以把这一章理解成“把发动机点着”，下一章才是真正开始上路。

### 老赵经验分享

学习 Nuxt 最怕两种节奏：  
一种是没跑起来就急着学高级能力，另一种是项目跑起来了却一直停留在配置和命令。  
**先能跑，再理解规则，再进入页面开发**，这是最顺的节奏。

### 赵老师提醒

如果你现在还在纠结某个插件装不装、某个模块加不加，先停一下。  
先保证你能独立创建一个干净的 Nuxt 项目，并且在本地稳定运行。基础稳了，后面所有能力才接得住。

# 第3章 页面与布局系统：从首页到通用框架

如果说上一章把 Nuxt 的“骨架”搭起来了，这一章要解决的就是：**骨架怎么长肉**。  
很多 Vue3 开发者第一次进 Nuxt，最容易下意识地想：先写组件，再手动拼路由、页面、头部、侧栏和页脚。结果会发现，Nuxt 不是“你想怎么拼就怎么拼”，而是“你按它的约定写，它帮你自动组织”。

这正是 Nuxt 最舒服的地方之一：**页面生成方式 + 布局系统**。  
前者负责“路由怎么来”，后者负责“公共框架怎么复用”。理解这两层，基本就能快速搭出内容站、展示站，或者把博客首页、列表页、详情页跑起来。

这一章，老赵带你把它讲透。你会发现，这其实就是 Vue3 开发者过渡到 Nuxt 的第一道分水岭：  
**从“我来安排一切”，转到“让框架按约定帮我安排一切”。**

## 一、页面生成方式：`pages` 目录如何自动生成路由？

### 1. Nuxt 为什么不用手写路由？

在 Vue3 里，很多人已经习惯了 `vue-router` 的显式配置：先写路由表，再写页面组件，最后在入口里挂载。  
而 Nuxt 更偏“约定式”——**把页面文件放进 `pages` 目录，Nuxt 会按文件结构自动生成路由**。

它的好处很直接：

- 不用维护路由配置
- 目录结构就是路由结构
- 新增、删除、重命名页面时，路由跟着变
- 对内容站、展示站这类结构清晰的项目特别高效

例如：

```bash
pages/
  index.vue
  about.vue
  products/
    index.vue
    [id].vue
```

对应大致是：

- `pages/index.vue` → `/`
- `pages/about.vue` → `/about`
- `pages/products/index.vue` → `/products`
- `pages/products/[id].vue` → `/products/:id`

这就是 Nuxt 的页面生成方式：**文件名即路由，目录即层级**。  
对 Vue3 开发者来说，这种方式很好上手，因为你不用先学一套复杂路由配置，直接用文件系统组织页面就行。

### 2. 页面组件应该怎么写？

Nuxt 页面本质上还是 Vue 组件，你依然可以用熟悉的 `<template>`、`<script setup>`、`<style scoped>`。

例如首页：

```vue
<template>
  <main class="home">
    <h1>欢迎来到全栈老赵的 Nuxt 世界</h1>
    <p>这里是首页内容。</p>
  </main>
</template>

<script setup lang="ts">
useHead({
  title: '首页 - Nuxt Demo'
})
</script>

<style scoped>
.home {
  padding: 24px;
}
</style>
```

页面层除了渲染内容，还会承担更多职责，比如：

- 自动识别路由
- 支持布局切换
- 配置 SEO
- 支持服务端渲染时的数据获取

所以可以把页面理解为：  
**“负责承载一个完整访问路径的组件”。**

### 3. 页面和组件别混了

新手最容易把“页面”和“组件”混在一起。简单记：

- 放在 `pages` 里的文件：通常是页面，会参与路由生成
- 放在 `components` 里的文件：通常是可复用部件，不会自动变路由

比如导航栏、商品卡片、作者信息块，适合放 `components`。  
而首页、关于页、文章详情页、产品列表页这些有明确 URL 的内容，应该放在 `pages`。

判断标准很实用：  
**凡是用户会直接通过 URL 访问到的，优先放 `pages`；凡是页面内部重复使用的，优先放 `components`。**

另外，动态路由命名也要尽早记住：

- `[id].vue` 表示动态参数
- `[...slug].vue` 表示可匹配多级路径

文件名不是随便起的，它直接决定访问路径。

### 4. 路由和页面的对应关系，要在脑子里画出来

老赵建议你把 Nuxt 的页面生成方式想象成一张“文件目录图 → URL 图”的映射表。  
比如：

```bash
pages/
  index.vue
  blog/
    index.vue
    [slug].vue
  about.vue
```

对应访问路径就是：

- `/`
- `/blog`
- `/blog/:slug`
- `/about`

这件事看起来简单，但它是 Nuxt 约定式开发的核心之一。  
你不需要在某个配置文件里把路由一条条写出来，而是通过目录和命名规则，让框架自己读懂你的意图。

### 老赵经验分享

老赵做内容站时，最怕的不是页面多，而是路由乱。  
用 Vue 手动配路由，小项目还行；页面一多，配置文件就容易膨胀。Nuxt 的好处是，把站点结构放回目录里，改起来特别直观。博客、文档站、产品展示站这类“结构稳定”的项目，和它特别合拍。

### 赵老师提醒

别因为 Nuxt 自动生成路由，就以为自己不用理解路由。  
你必须知道文件结构会如何映射成 URL，否则一到动态路由、嵌套路由、布局切换时就容易迷糊。  
**自动化不等于不用理解规则。**

## 二、页面与组件：一个标准 Nuxt 页面该怎么组织？

### 1. 页面不只是写 HTML

一个页面通常不只是“把内容写出来”，而是要同时承担几件事：

- 定义页面结构
- 调用页面级数据
- 配置 SEO
- 决定使用哪个布局
- 组织内部子组件

所以页面层更像“总控台”。

比如一个产品首页可以拆成：

- 页面层：负责整体结构、首屏数据、meta、布局选择
- 组件层：负责 Banner、产品卡片、推荐列表、FAQ、底部行动按钮

这种拆法的好处是：页面层清楚，组件层可复用，后期维护轻松。  
从 Vue3 过渡到 Nuxt，最值得调整的习惯就是：**页面负责装配，组件负责零件**。

### 2. 推荐的页面组织顺序

建议页面代码按这个顺序看：

1. `<template>`：先看结构
2. `<script setup>`：再看数据、逻辑、配置
3. `<style>`：最后看样式

例如：

```vue
<template>
  <section class="article-page">
    <ArticleHeader :title="article.title" />
    <ArticleContent :content="article.content" />
  </section>
</template>

<script setup lang="ts">
const route = useRoute()
const id = route.params.id

const article = await useFetch(`/api/articles/${id}`)
</script>
```

这类写法很适合页面级内容展示。  
如果是内容站，首页、分类页、详情页的结构往往类似，但内容不同，所以页面层尽量保持“清楚、直接、少纠结”。

### 3. 页面层和组件层的边界

简单区分：

- **页面层**：和 URL 强绑定，负责场景
- **组件层**：和 URL 弱绑定，负责复用

比如：

- 页面层适合写：获取文章详情、设置标题、决定展示哪个布局
- 组件层适合写：文章摘要卡、作者头像、分页器、标签列表

这样拆开后，你在做博客、产品站、展示站时会非常顺手，因为这类站点本来就是“页面很多，但复用模块也很多”。

### 4. 页面写得好不好，关键看“装配感”

Nuxt 页面最好的状态，不是把所有逻辑堆满，而是像一个“装配层”。  
你在页面里做三件事就够了：

- 选择这个页面要用哪些组件
- 决定页面级数据怎么来
- 决定页面最终呈现什么场景

至于组件内部怎么排版、列表项怎么渲染、卡片怎么交互，尽量交给组件自己处理。

### 老赵经验分享

老赵见过不少 Vue 开发者到了 Nuxt 里，还是习惯把所有逻辑塞进一个页面文件。短期看快，长期会很痛苦。  
正确做法是：页面负责“装配”，组件负责“零件”。这样后面想换首页 Banner、重做列表卡片，基本不用碰路由和页面框架。

### 赵老师提醒

页面文件别写成“万能大杂烩”。  
如果一个页面里已经出现太多重复块、太多条件分支、太多视觉片段，说明该拆组件了。  
Nuxt 鼓励约定式开发，但不是鼓励你把所有东西都堆在页面里。

## 三、布局系统的作用：统一头部、侧栏、页脚等公共区域

### 1. 什么是布局系统？

布局系统解决的是一个常见问题：很多页面的外壳是一样的。  
比如：

- 顶部导航一致
- 底部版权一致
- 左侧栏一致
- 主内容区不同

如果每个页面都复制一遍这些结构，后面改一次头部，就得改很多页面。  
Nuxt 的布局系统，就是把这些公共区域抽出来，形成一个页面外壳。

你可以把它理解成：

- 页面：内容不同
- 布局：框架相同

这对内容站和展示站尤其重要，因为它们的公共外壳稳定，页面内容变化更频繁。

### 2. 默认布局是什么？

Nuxt 通常会有一个默认布局概念。  
如果没有特别指定，页面会放进默认布局里渲染。默认布局一般适合站点基础壳：

- 顶部导航
- 主体区域
- 页脚

例如：

```vue
<!-- layouts/default.vue -->
<template>
  <div>
    <SiteHeader />
    <main>
      <slot />
    </main>
    <SiteFooter />
  </div>
</template>
```

这里的 `<slot />` 是页面内容插入的位置。  
这套思路和 Vue 插槽很像，只是 Nuxt 把它提升成了“页面级容器”。

布局不是页面附属品，而是页面的承载框。  
页面是展品，布局是展馆；展品可以换，展馆结构尽量稳定。

### 3. 自定义布局怎么做？

如果默认布局不够用，可以定义多个布局。  
比如：

- `default`：普通站点页
- `dashboard`：后台控制台页
- `blank`：纯内容页或登录页

例如：

```vue
<!-- layouts/dashboard.vue -->
<template>
  <div class="dashboard-layout">
    <AdminSidebar />
    <div class="content">
      <DashboardHeader />
      <slot />
    </div>
  </div>
</template>
```

然后页面里切换布局：

```vue
<script setup>
definePageMeta({
  layout: 'dashboard'
})
</script>
```

这样就能实现页面共用壳子，但不同场景用不同外框。

### 4. 布局系统在内容站里的价值

内容站、博客站、展示站很适合用布局系统，因为它们通常有几种固定场景：

- 首页：顶部横幅 + 内容推荐 + 页脚
- 列表页：侧栏 + 分类列表 + 分页
- 详情页：正文 + 作者信息 + 推荐阅读

这些页面内容不同，但壳子很相似。  
没有布局系统，就得在每个页面里重复头部和页脚，维护成本会很高。

更进一步，布局系统还能统一品牌感：导航、页脚、宽度、边距、响应式结构一旦统一，站点整体观感会稳很多。

### 5. 什么时候直接写页面，什么时候用布局？

这个问题很实战。老赵给你一个很实用的判断：

- 如果只是某个页面里一小段重复内容，用组件解决
- 如果多个页面共享整套外壳，用布局解决
- 如果页面只出现一次，而且结构很特别，直接写页面就行

也就是说，布局是给“场景复用”准备的，不是给每个小模块都套壳。  
很多人刚接触 Nuxt 会想把一切都做成布局，其实没必要。页面、组件、布局三者各有边界，分工越清楚，项目越好维护。

### 老赵经验分享

老赵做展示站时，最喜欢布局系统。  
它能把“长期不变的部分”稳稳抽出来，这样你改文案、改内容时，不会一边改一边担心导航坏掉。布局做得好，整站会显得特别统一，后期改版也轻松。

### 赵老师提醒

别把布局当成“样式容器”这么简单。  
布局本质上是“结构复用”。  
如果只是为了加个边框，没必要上布局；如果是在处理整站公共区域，那布局就非常值得用。  
**布局是骨架，不是装饰。**

## 四、默认布局与自定义布局：如何切换和复用？

### 1. 先把默认布局做好

在实际项目里，建议你先把 `layouts/default.vue` 做扎实，因为这是大多数页面都会走的入口。  
默认布局里通常包含：

- 顶部导航
- 主内容容器
- 页脚
- 可能还有通知条、面包屑、搜索入口

如果默认布局结构清晰，后面新增页面几乎不用动壳子，只管往里填内容。

### 2. 再按需要增加自定义布局

自定义布局适合明显不同的页面，比如：

- `blank`：登录页、注册页、活动页
- `dashboard`：后台管理页
- `docs`：文档站页
- `content`：内容阅读页

例如，一个更适合文章阅读的布局可以这样：

```vue
<!-- layouts/content.vue -->
<template>
  <div class="content-layout">
    <SiteHeader />
    <div class="content-shell">
      <aside class="left-sidebar">
        <CategoryMenu />
      </aside>
      <main class="article-main">
        <slot />
      </main>
      <aside class="right-sidebar">
        <HotList />
      </aside>
    </div>
    <SiteFooter />
  </div>
</template>
```

然后文章列表页或详情页使用它：

```vue
<script setup>
definePageMeta({
  layout: 'content'
})
</script>
```

这样就非常适合内容站、知识站、博客站的场景。

### 3. 复用布局的思路

布局复用不是复制粘贴，而是提炼共性。  
比如多个页面都有：

- 顶部导航
- 右侧推荐栏
- 页脚

那就可以放到一个通用布局里，页面只负责中间内容。  
如果某些页面不需要右侧栏，再单独定义一个轻量布局。

这套方法在内容站里尤其好用。  
文章列表页和文章详情页可以共用内容型布局，而首页和活动页则用更轻的布局，既减少重复，也更符合业务语义。

### 4. 不要过度设计布局

实际项目里，不建议一上来设计太多布局。  
通常先从这两个开始就够了：

- `default`：网站主布局
- `blank`：空白布局，适合登录页或独立落地页

后面真的有后台系统，再加 `dashboard` 也不迟。  
布局过多，反而会提高理解成本。

一个原则是：**布局应该服务于页面场景，而不是为了“看起来有架构感”硬拆。**

### 老赵经验分享

老赵的经验是：布局数量宁少勿多。  
很多项目一开始喜欢给每种页面都搞一个布局，结果半年后自己都记不住哪个页面该挂哪个壳。  
先把最常见的结构打稳，再扩展特殊布局，这是最稳的。

### 赵老师提醒

布局不是越细越好。  
过度拆分布局，会让你在页面切换时频繁判断“这个页面到底该用哪个壳”。  
如果一个布局只被一两个页面使用，而且没有复用价值，那它很可能只是过度设计。

## 五、页面与布局的组合实战：首页、列表页、详情页的骨架搭建

这一节我们用一个最常见的内容站结构来走一遍。你会发现，Nuxt 做博客首页、产品展示站，其实并不复杂，关键就是把页面、布局、组件的关系摆顺。

### 1. 项目场景：一个简洁的内容站

假设我们要做一个“全栈老赵专栏站”，它有这几个页面：

- 首页：展示站点定位、推荐内容、热门专题
- 列表页：展示文章列表，支持分类浏览
- 详情页：展示文章正文、作者信息、相关推荐

这类站点特别适合 Nuxt，因为：

- 结构清晰
- 页面类型固定
- 需要良好的 SEO
- 适合服务端渲染和静态生成
- 公共框架复用度高

### 2. 首页：做“入口”和“导航”

首页通常不是信息最多的页面，但它是最重要的入口。  
对于内容站或展示站，首页建议承担这些职责：

- 提供站点定位
- 展示核心内容入口
- 引导用户进入列表页或详情页

骨架上可以拆成：

- 首屏 Banner
- 推荐内容区
- 分类入口区
- 热门文章或产品区

首页页面只需要组织这些模块，不用重复写头尾。  
它的职责很清楚：不是百科全书，而是站点门面和导航枢纽。

### 3. 列表页：做“筛选”和“分发”

列表页的核心任务是把内容分发出去。  
比如文章列表、产品列表、案例列表。它通常包括：

- 标题区
- 分类/筛选区
- 列表区
- 分页区

如果是内容站，列表页很适合配合布局系统，把公共导航和侧栏统一起来，页面内部专注渲染列表即可。

列表页还经常结合查询参数做筛选，比如分类、标签、排序、页码。后面讲路由和数据时会展开，这里先记住：**列表页本质上是“聚合和分发内容”的页面。**

### 4. 详情页：做“阅读”和“转化”

详情页最重要的不是复杂，而是清晰。  
它通常包含：

- 标题
- 发布时间
- 作者信息
- 正文
- 相关推荐
- CTA 按钮或下一篇链接

对于展示站来说，详情页也可以是“案例详情”“产品详情”“服务介绍详情”。  
本质都是：让用户理解一件事，并愿意继续操作。

详情页特别适合发挥布局系统和组件拆分的优势。正文变化大，但作者卡片、相关推荐、标签区这些模块很容易复用。

### 5. 一个最小骨架示例

你可以这样组织文件：

```bash
layouts/
  default.vue
  content.vue

pages/
  index.vue
  posts/
    index.vue
    [slug].vue

components/
  SiteHeader.vue
  SiteFooter.vue
  HeroBanner.vue
  PostCard.vue
  PostMeta.vue
  RelatedPosts.vue
```

对应关系大概是：

- `layouts/default.vue`：站点主壳
- `layouts/content.vue`：阅读型页面壳
- `pages/index.vue`：首页
- `pages/posts/index.vue`：文章列表页
- `pages/posts/[slug].vue`：文章详情页
- `components/*`：各类复用模块

这套结构已经足够支持一个内容站的基础框架了。  
你会看到，Nuxt 的约定式开发不是限制你，而是帮你快速形成清晰结构。

### 6. 页面与布局的协同原则

记住这三句话：

- 布局负责共性
- 页面负责场景
- 组件负责复用

三者一旦分层清楚，后面做功能时就不会东一块西一块。  
比如首页新增一个推荐区，你只改首页；  
比如全站导航改名，你改布局；  
比如文章卡片样式调整，你改组件。

这就是 Nuxt 真正好用的地方。

### 老赵经验分享

老赵做过很多内容站，最实用的经验就是：先把首页、列表页、详情页这三类页面骨架定住。  
只要这三页跑通，项目就已经有 80% 的样子了。  
后面补 SEO、补数据、补交互，都是在这个骨架上加血肉。

### 赵老师提醒

别一开始就追求页面效果拉满。  
页面与布局的第一目标是“结构正确、组织清晰、可持续扩展”，不是“首屏惊艳”。  
骨架搭歪了，后面再漂亮也会越来越难维护。

## 六、常见问题：为什么页面渲染了但布局没生效？

这是新手在 Nuxt 里很常见的问题。  
页面能显示，说明路由和页面文件没大问题；但布局没生效，通常说明布局机制某个环节没接上。

### 1. 先检查默认布局是否存在

先确认 `layouts/default.vue` 是否真的存在，并且结构里有没有 `<slot />`。  
如果没有 `<slot />`，页面内容插不进去。

```vue
<template>
  <div>
    <SiteHeader />
    <slot />
    <SiteFooter />
  </div>
</template>
```

这是最基本的要求。

### 2. 再检查页面是否指定了其他布局

有时候页面不是没走布局，而是走了别的布局。  
比如：

```vue
<script setup>
definePageMeta({
  layout: 'blank'
})
</script>
```

这时它会去找 `layouts/blank.vue`。  
如果这个布局里没有你想要的头部页脚，看起来就像“布局没生效”。

### 3. 检查布局文件命名是否正确

Nuxt 的约定式开发很讲究命名。  
布局文件名、页面元信息、目录结构，只要有一个拼错，效果就会不对。  
常见问题包括：

- 文件名大小写不一致
- `default.vue` 写错
- 布局里忘了放 `<slot />`
- 页面 meta 指向了不存在的布局名

这类错误不一定报得很明显，但结果就是页面样式和结构不符合预期，排查时要细心。

### 4. 检查是否被页面级结构覆盖了

有时你以为是布局没生效，其实是页面内部结构把它盖住了。  
比如页面自己写了全屏容器、背景色、定位、层级，视觉上也会误判。

所以排查时，别只盯着布局文件，也要看页面有没有把布局区域挤没或盖住。

### 5. 布局排查清单

老赵建议你直接按这个清单查：

1. `layouts/default.vue` 是否存在  
2. 是否包含 `<slot />`  
3. 页面是否指定了其他布局  
4. 布局命名是否正确  
5. 页面内部样式是否覆盖了布局区域  
6. 页面是否真的用了当前布局对应的文件名  
7. 是否有错误的嵌套容器把布局内容挡住了

你会发现，大部分“布局没生效”的问题，都不是框架坏了，而是约定没有对上。

### 老赵经验分享

我见过太多人把“布局没生效”当成 Nuxt 的怪问题，其实大多数时候都是文件名、`slot`、或 `layout` 指定错了。  
Nuxt 很多地方像“自动驾驶”，但前提是你得把路标放对。

### 赵老师提醒

如果页面渲染正常但布局不对，先别急着怀疑框架。  
先看约定有没有遵守。  
Nuxt 的很多问题，最终都能回到一句话：**你有没有按它规定的方式放文件、写结构。**

这一章我们把 Nuxt 的页面与布局系统理顺了。你现在应该能清楚分辨：

- `pages` 是什么：自动生成路由的页面目录
- 页面和组件怎么分工：页面负责场景，组件负责复用
- 布局系统干什么：统一站点公共框架

- 布局为什么没生效：优先检查约定是否遵守

**别再把路由、页面、公共外壳都手动硬拼，把组织权交给 Nuxt，自己专注内容和业务。**

换句话说，Nuxt 的约定式开发不是让你少思考，而是让你把思考放在更值钱的地方：  
页面要讲什么、内容怎么组织、站点框架怎么复用，而不是把时间耗在重复配置和拼装上。

## 一、文件系统路由如何工作：目录结构如何映射到 URL？

### 1.1 先记住一句话：页面就是路由

在 Nuxt 里，最常见的页面目录是 `pages/`。你只要在这个目录下创建页面文件，Nuxt 就会自动把它识别成路由。

```bash
pages/
  index.vue
  about.vue
  blog/
    index.vue
```

通常对应：

- `pages/index.vue` → `/`
- `pages/about.vue` → `/about`
- `pages/blog/index.vue` → `/blog`

这和 Vue3 手动配路由不一样。Vue3 常见做法是先写组件，再去 `router/index.ts` 注册；Nuxt 则是**先有文件，再自动生成路由**。

它带来的好处很直接：

1. 目录结构就是路由文档；
2. 新增页面不用再补路由配置；
3. 团队协作时，页面结构更清楚。

### 1.2 为什么这对内容站特别友好？

内容站、博客站、展示站的页面通常很规律：

- 首页
- 关于页
- 文章列表页
- 文章详情页
- 分类页
- 标签页

这类站点天然适合文件系统路由。你不用维护一大坨路由表，只要按业务结构放文件，页面就能自动生成。

例如博客站可以这样设计：

```bash
pages/
  index.vue
  posts/
    index.vue
    [slug].vue
  category/
    [name].vue
```

这已经很像站点的信息架构了。**这就是 Nuxt 的约定式开发：用目录表达业务，用约定减少重复配置。**

### 1.3 它和传统路由配置有什么区别？

传统 Vue Router 的思路是先定义路由表，再把页面组件挂到路由上；Nuxt 的思路则是先规划目录，页面文件天然就是路由，路由结构和目录结构基本一致。

这意味着你在 Nuxt 里做页面设计时，不只是在画 UI，还在顺手画站点的信息结构。对于 Vue3 开发者来说，这个转变很关键：**从“配置路由”变成“组织目录”**。

### 1.4 最容易犯的误区

很多刚从 Vue3 过来的同学会想：那是不是以后都不用配置路由了？

不是。更准确地说是：

- **常规页面**交给文件系统路由；
- **特殊规则**、权限控制、复杂跳转，仍然会用到中间件、配置或程序化控制。

你可以把 Nuxt 路由理解为“默认自动生成，必要时再补充控制”。

#### 老赵经验分享
我带过不少 Vue 转 Nuxt 的同学，最容易卡住的不是代码，而是习惯。大家总想先找“router 配置文件在哪”。其实先把 `pages/` 当成路由入口来理解，思路就顺了。

#### 赵老师提醒
文件系统路由不是偷懒，而是规范化。但前提是目录命名要清晰，否则页面一多，你会发现自己不是在写路由，而是在和文件名打架。

## 二、动态路由的写法：参数页、详情页、分类页

### 2.1 什么叫动态路由？

动态路由就是 URL 里某一段不是固定值，而是变化的参数。比如：

- `/posts/1`
- `/posts/nuxt-router`
- `/category/frontend`

页面模板是同一个，但内容要根据参数变化。

在 Nuxt 里，动态路由通常用方括号表示：

```bash
pages/
  posts/
    [slug].vue
  category/
    [name].vue
```

这里：

- `[slug].vue` 常用于文章详情页
- `[name].vue` 常用于分类页

URL 中变化的部分，会作为路由参数传进页面。

### 2.2 参数页、详情页、分类页怎么设计？

#### 1）详情页
最常见的是文章、商品、作品详情页。

```bash
pages/posts/[slug].vue
```

页面里再根据 `slug` 去请求对应数据。

#### 2）分类页
分类页常用于内容站、知识库、产品目录。

```bash
pages/category/[name].vue
```

#### 3）参数页
有些页面不是“详情”，而是根据参数切换内容，比如：

- `/search/vue`
- `/archive/2025`
- `/user/123`

本质上也都是动态路由。

### 2.3 动态路由开发时要注意什么？

动态路由不能理解成“传个字符串就行”。实际开发里，参数页至少要处理三件事：

1. **参数格式合法**
   - 是否为空？
   - 是否含非法字符？
   - 是否符合业务规则？

2. **数据是否存在**
   - 找得到文章吗？
   - 找得到分类吗？
   - 找不到怎么办？

3. **异常如何展示**
   - 返回 404
   - 提示内容不存在
   - 引导回列表页

### 2.4 读取参数时，别只看“能拿到”，还要看“拿得对不对”

在 Nuxt 的页面里，路由参数通常可以直接读取。读到以后，建议先做一次基本规范化处理：

- 去掉空值；
- 判断是否是预期类型；
- 根据业务规则做白名单判断；
- 再发起数据请求。

比如文章详情页里，`slug` 最好满足一个明确规则：只允许字母、数字、连字符这类安全字符。这样做不是矫情，而是为了让 URL 更稳定、接口更好处理、页面更容易排错。

### 2.5 缺失参数和无效参数怎么处理？

你不能假设用户一定会按正常路径进入页面。现实里常见情况是：

- 用户手动输入错误地址；
- 别人复制了过期链接；
- SEO 抓取到了不存在的页面；
- 链接改版后旧地址还在被访问。

这时页面要有明确处理方式，常见有三种：

- **返回 404**：内容已经不存在，且没有替代内容；
- **重定向到列表页**：适合文章详情回文章列表；
- **显示空状态页**：适合“内容暂时为空”而不是“地址错误”。

#### 老赵经验分享
做内容站最舒服的一点，就是动态路由几乎是刚需。你只要把“列表页拿 slug，详情页按 slug 拉内容”这条链路跑通，基本就抓住了 Nuxt 路由实战的核心。

#### 赵老师提醒
动态路由不是“能访问就行”，而是“访问后要给出正确结果”。别让用户点开详情页却看到空白页或报错页，那种体验很伤站点可信度。

## 三、嵌套路由与路由层级：适合哪些业务场景？

### 3.1 什么是嵌套路由？

嵌套路由可以理解为：一个大页面下面还有子页面区域。比如：

- 用户中心
- 后台管理
- 商品详情下的评论、参数、推荐
- 文章详情下的目录、评论、相关推荐

这些场景里，页面不是简单跳转，而是在同一父级结构下切换子内容。

在 Nuxt 里，路由层级通常和目录层级相对应，也可以结合布局和嵌套结构做更清晰的页面分区。

### 3.2 哪些业务适合嵌套路由？

以下场景很适合：

- **后台管理系统**：例如 `/admin/users`、`/admin/posts`
- **用户中心**：例如 `/account/profile`、`/account/security`
- **多标签详情页**：例如 `/product/123/specs`、`/product/123/reviews`
- **内容详情辅助区**：例如文章详情页下的评论区、目录区、相关阅读区

### 3.3 什么时候不要硬上嵌套？

如果页面之间只是普通跳转，没有共享结构，也没有持续保留的父级布局，就没必要复杂嵌套。很多人为了“看起来高级”，把简单内容站搞成层级很深的路由树，最后维护成本暴涨。

判断标准很简单：

- 父页面结构是否需要长期保留？
- 子页面是否共享同一套导航、侧边栏、标题区？
- 切换时是否要保留某些状态？

答案大多是“是”，才考虑嵌套路由。

### 3.4 Nuxt 里更常见的思路：把“层级”优先交给目录和布局

对内容站来说，很多时候不需要把所有层级都做成复杂子路由。你完全可以通过目录分组、布局复用、组件拆分来实现页面层级感。

也就是说：

- 路由负责“地址”；
- 布局负责“外壳”；
- 组件负责“内容块”。

这个分工很适合 Nuxt，也更适合展示站和博客站。别为了嵌套而嵌套，结构清楚比层级复杂更重要。

#### 老赵经验分享
我做后台或内容管理页时，优先看“结构复用”而不是“路由好不好看”。只要顶部导航、左侧菜单、主内容区能稳定复用，嵌套就值得做。

#### 赵老师提醒
别把所有层级都往路由里塞。很多时候，组件复用、布局复用比“多一层路由”更重要。路由应该服务业务，而不是绑架业务。

## 四、页面跳转与导航：链接、编程式跳转、返回上一页

### 4.1 最常见的跳转方式：`<NuxtLink>`

在 Nuxt 中，页面之间跳转最常用的是 `NuxtLink`，类似 Vue Router 的 `RouterLink`，但更符合 Nuxt 的使用习惯。

```vue
<NuxtLink to="/posts">文章列表</NuxtLink>
<NuxtLink :to="`/posts/${item.slug}`">查看详情</NuxtLink>
```

它的好处是：

- 支持前端无刷新切换；
- 对页面预取更友好；
- 写法直观，适合模板导航。

### 4.2 编程式跳转：什么时候用？

有些场景不适合直接点链接，而是需要代码控制跳转，比如：

- 表单提交成功后跳转；
- 登录后跳转到目标页；
- 条件满足后自动进入详情页；
- 按钮点击后根据业务判断路径。

```vue
<script setup>
const goHome = async () => {
  await navigateTo('/')
}
</script>

<template>
  <button @click="goHome">返回首页</button>
</template>
```

### 4.3 返回上一页怎么做更稳妥？

直接后退不一定安全，因为：

- 用户可能直接打开详情页；
- 可能从外链进入；
- 历史记录不一定存在；
- 有些页面后退不符合业务预期。

更稳妥的做法是加兜底：能后退就后退，不能后退就回列表页或首页。

内容站详情页里，返回按钮通常优先回文章列表，其次回首页，或回分类页。

### 4.4 导航的实战原则

导航不是“能跳就行”，而是要考虑用户路径：

1. 首页 → 列表页
2. 列表页 → 详情页
3. 详情页 → 列表页
4. 分类页 → 详情页
5. 详情页 → 相关内容页

这条链路越顺，站点越像一个成熟产品。

#### 老赵经验分享
做内容站时，导航设计比页面内容更容易被忽略。真正影响转化的，往往就是这几次点进点出的路径是否顺手。

#### 赵老师提醒
不要只写“跳转成功”，还要考虑“跳转之后用户下一步去哪”。好的路由设计，是为业务路径服务的，不是把页面连上就结束。

## 五、路由参数读取与校验：如何安全地处理 URL 参数？

### 5.1 参数从哪里来？

在动态路由页面里，URL 参数会随着路径进入页面。比如：

- `/posts/nuxt-router`
- `/category/frontend`

这里的 `nuxt-router`、`frontend` 都是参数。

拿到参数后，通常要做两件事：

1. 用参数请求数据；
2. 检查参数是否符合预期。

### 5.2 为什么必须校验？

因为 URL 参数是用户可控的。用户可以手动改地址栏：

- 输入空值
- 输入不存在的 slug
- 输入恶意字符
- 输入超长字符串

如果不做校验，轻则页面报错，重则出现异常请求、错误展示，甚至影响 SEO 和用户体验。

### 5.3 校验的基本思路

可以按这几个层次判断：

#### 1）格式层
参数是不是字符串？是不是为空？是不是符合命名规则？

#### 2）业务层
这个 slug 对应的文章存在吗？这个分类能查到吗？

#### 3）结果层
如果不存在，返回 404 还是展示“内容不存在”？

### 5.4 实战建议：不要把校验和请求混成一团

常见坏味道是：

- 拿到参数后直接请求；
- 请求失败后什么都不处理；
- 页面最后只剩空白或报错提示。

更稳妥的做法是：

1. 先检查参数；
2. 再发起数据请求；
3. 根据结果决定页面展示；
4. 找不到内容时给出明确反馈。

### 5.5 一个更贴近内容站的判断方式

比如文章详情页，你可以这样想：

- URL 里是不是有 `slug`？
- `slug` 是否符合站点规则？
- 文章列表或接口里能不能查到这个 `slug`？
- 查不到时，是不是应该跳回文章列表，而不是让用户困在错误页里？

这类判断看起来琐碎，但在内容站里非常实用。尤其是博客、知识库、产品介绍站，路由稳定性直接影响阅读体验和搜索引擎抓取效果。

#### 老赵经验分享
我做过很多内容页，真正麻烦的不是“获取不到数据”，而是“获取不到数据后不知道怎么收场”。校验和兜底写好，页面质量立刻高一截。

#### 赵老师提醒
不要信任 URL 参数。它不是接口里的可信字段，而是用户随时可能改写的输入。凡是用户输入，就要有基本防线。

## 六、路由实战：内容站列表页到详情页的完整链路

现在把整套链路串起来，做一个最典型的内容站案例：**文章列表页 → 文章详情页 → 返回列表页**。

### 6.1 页面结构设计

```bash
pages/
  index.vue
  posts/
    index.vue
    [slug].vue
```

对应业务：

- `/`：站点首页
- `/posts`：文章列表页
- `/posts/:slug`：文章详情页

### 6.2 列表页：展示文章入口

列表页一般展示文章标题、摘要、发布时间，并把标题做成链接。

```vue
<template>
  <main>
    <h1>文章列表</h1>
    <ul>
      <li v-for="post in posts" :key="post.slug">
        <NuxtLink :to="`/posts/${post.slug}`">
          {{ post.title }}
        </NuxtLink>
        <p>{{ post.summary }}</p>
      </li>
    </ul>
  </main>
</template>
```

重点不在 UI，而在入口设计：

- 列表页负责提供入口；
- 详情页负责承接内容；
- 链接路径要稳定。

### 6.3 详情页：根据 slug 读取内容

详情页 `[slug].vue` 的职责很明确：拿到参数，找到对应文章，展示内容。

逻辑可以分三步：

1. 读取 `slug`
2. 请求文章数据
3. 判断是否存在

存在就展示正文，不存在就展示 404 或提示页。  
你会发现，动态路由页面其实就是一个“内容加载器”。

```vue
<script setup>
const route = useRoute()
const slug = route.params.slug
// 这里省略具体请求，实现时可以接接口或本地数据源
</script>
```

这里最重要的不是语法，而是思路：**详情页本质上是一个参数驱动的内容展示页**。只要参数稳定、数据能查到、异常有兜底，这个页面就能长期稳定运行。

### 6.4 返回列表页：别让用户迷路

详情页里最好提供一个明确的返回入口：

- 返回文章列表
- 返回首页
- 返回分类页

这对内容站尤其重要，因为用户阅读到一半时，常常希望继续浏览相近内容，而不是重新找入口。

```vue
<template>
  <div>
    <NuxtLink to="/posts">返回文章列表</NuxtLink>
  </div>
</template>
```

如果你想更稳一点，返回按钮还可以做成“优先回列表页，必要时回首页”的兜底逻辑，这样即使用户是直接打开详情页，也不会迷路。

### 6.5 这条链路为什么重要？

因为它几乎覆盖了 Nuxt 路由实战的核心：

- 文件系统路由
- 动态路由
- 页面跳转
- 参数读取
- 数据校验
- 用户导航闭环

你只要把这条链路跑通，后面做博客、知识库、产品展示站都会很顺手。

对于 Vue3 开发者来说，这也是最自然的一步过渡：你不再是单独写组件，而是开始用 Nuxt 的方式组织完整页面流转。**页面之间真正连起来，项目才算进入可用状态。**

#### 老赵经验分享
很多人学路由，只会写“点一下跳转”。真正能落地的能力，是把“列表页、详情页、返回路径、异常兜底”一起做完整。这个闭环一通，项目就像样了。

#### 赵老师提醒
做内容站时，不要只盯着页面能不能打开，更要盯着用户能不能顺着内容一路浏览下去。路由的价值，不只是连接页面，更是组织阅读路径。

## 本章小结：先把路由做顺，Nuxt 才算真正开始

这一章我们把 Nuxt 的路由能力从头走了一遍：

- **文件系统路由**：目录即路由，页面即入口；
- **动态路由**：参数页、详情页、分类页是内容站核心；

- **页面跳转**：`NuxtLink` 负责自然跳转，编程式跳转负责业务控制；

- **内容站实战链路**：列表页到详情页，形成完整浏览闭环。

如果你是 Vue3 开发者，最重要的过渡不是“学会另一个 API”，而是理解 Nuxt 的开发哲学：**把路由交给约定，把精力留给业务**。下一步你可以继续做两件事：

1. 用自己的博客或展示站目录，手工画一张路由结构图；
2. 按 Nuxt 的方式先把首页、列表页、详情页搭起来，再补数据和 SEO。

路由通了，页面之间才真正活起来。接下来，咱们就可以继续往更上层走：布局、数据、SEO 和完整项目整合。

# 第5章 组件在 Nuxt 里怎么用：从复用到自动导入

## 开篇引入：Vue 组件会了，到了 Nuxt 为什么还要重新学一遍？

如果你已经会 Vue3，组件这件事大概率不陌生：`props` 传值、`emit` 通信、`slot` 插槽、`setup` 里写逻辑，基本都能上手。  
但一进 Nuxt，不少人会发现：**组件怎么不用 import 了？为什么有些组件放进去就能直接用？为什么页面、布局、组件都像“约定好的”？**

这正是 Nuxt 的特点：**约定式开发**。  
它不是推翻 Vue 的组件体系，而是把“组件如何组织、如何被发现、如何被使用”做成了一套更统一的规则。

简单说，Vue3 里你主要关心“怎么写组件”，Nuxt 里还要多想一层：**组件放哪里、框架如何识别、适合在哪些场景自动使用。**

本章重点讲四件事：

1. Nuxt 里的组件自动导入机制怎么工作；
2. 组件如何分层，基础组件和业务组件怎么区分；
3. `props`、`events`、`slots`、`composables` 怎么配合；
4. 怎么把这套思路迁移到页面、布局和内容站场景里。

如果你是从 Vue3 过渡到 Nuxt，这一章很关键。后面写页面、布局、内容站或产品展示站，都会反复用到这套思路。

### 老赵经验分享
我带项目时最常见的问题，不是不会写组件，而是组件越多越找不到。到了 Nuxt，自动导入能省很多操作，但真正决定项目质量的，还是目录和命名是否清晰。

### 赵老师提醒
别把“自动导入”理解成“随便放都行”。  
Nuxt 给你的是便利，不是免管理。**组件越容易被找到，就越要命名清楚、职责明确。**

## 一、组件自动导入机制：为什么在 Nuxt 里更省事？

### 1.1 Nuxt 的组件为什么“写了就能用”？

在纯 Vue3 项目里，组件一般要先 `import` 再注册，才能使用。  
Nuxt 默认支持**组件自动导入**：你把组件放进约定目录，Nuxt 会自动扫描并注册，在页面、布局或其他组件里直接使用即可。

这就是 Nuxt 约定式开发的典型体现：**不是你告诉框架怎么找，而是框架按规则帮你找。**

例如你在 `components/BaseButton.vue` 里写一个按钮组件，页面里通常可以直接用：

```vue
<template>
  <BaseButton>立即查看</BaseButton>
</template>
```

不用手动导入，开发体验会顺很多。

### 1.2 自动导入和 Vue3 习惯的差异

如果你刚从 Vue3 迁移过来，最直观的差别就是：

- **Vue3 常见做法**：先 `import`，再使用；
- **Nuxt 默认做法**：放到约定目录，符合规则后直接用；
- **Vue3 更强调显式引用**；
- **Nuxt 更强调约定发现**。

这不是少学一套知识，而是把“组件注册”交给框架处理。  
对于内容站、博客站、产品展示站这类页面较多、模块重复率高的项目，自动导入非常实用。

### 1.3 自动导入带来的好处

项目一大，优势就很明显：

- 减少样板代码；
- 页面更清爽；
- 组件组织更统一；
- 多人协作更容易找文件。

尤其是内容站、博客站、产品展示站这种项目，页面模块化程度高，自动导入会让你更快搭出首页、专题页、详情页的骨架。

### 1.4 自动导入不是“随便放都行”

自动导入省事，但**不等于没有规则**。  
项目越大，越要按用途整理组件：

- `components/base/`：基础通用组件；
- `components/layout/`：布局相关组件；
- `components/content/`：内容展示组件；
- `components/business/`：业务逻辑更强的组件。

这样文件好找，职责也清楚。否则自动导入只会让“能用”变成“乱用”。

### 老赵经验分享
我做 Vue 项目时，最怕的不是写组件，而是“组件越写越多，最后谁也找不到”。Nuxt 的自动导入确实方便，但真正能让项目稳住的，还是目录结构。

### 赵老师提醒
自动导入是便利，不是魔法。**命名不规范、目录不清晰，自动导入只会把混乱放大。**

## 二、基础组件与业务组件：到底该怎么分？

### 2.1 什么叫基础组件？

基础组件就是**和具体业务弱相关、可跨页面复用的最小单元**，通常只负责展示，不掺杂复杂业务。

常见例子：

- `BaseButton`
- `BaseTag`
- `BaseImage`
- `BaseCard`
- `BaseInput`

它们的特点是：

- 输入少；
- 输出清晰；
- 样式稳定；
- 复用范围大。

可以把它理解成“UI 零件”。

### 2.2 什么叫业务组件？

业务组件是**面向某类场景封装出来的功能模块**。  
比如内容站里的：

- 文章卡片；
- 推荐列表；
- 头部导航；
- 首页 Banner；
- 产品卖点区块。

这类组件通常会包含：

- 数据展示；
- 条件渲染；
- 事件处理；
- 与接口数据绑定。

它不只是“长得像一个组件”，而是“承担了一块明确业务”。

### 2.3 如何划分：一个实用判断标准

先问三个问题：

1. 这个组件能不能脱离当前项目单独复用？
2. 这个组件是不是只负责一个很小的视觉/交互单元？
3. 这个组件是否包含明显业务语义？

判断结果：

- 偏向“能、是、否” → 更像基础组件；
- 偏向“不能、不是、是” → 更像业务组件。

比如纯按钮基本是基础组件；而一个包含作者、发布时间、阅读量、分类标签、跳转逻辑的卡片，就更像业务组件。

### 2.4 推荐的组织方式

```bash
components/
  base/
    BaseButton.vue
    BaseCard.vue
  layout/
    AppHeader.vue
    AppFooter.vue
  content/
    ArticleCard.vue
    ArticleList.vue
  business/
    ProductFeature.vue
    HeroSection.vue
```

你从目录名就能知道组件用途。以后写 `<ArticleCard />`，不用翻半天目录就知道它是谁、干什么的。

### 2.5 从 Vue3 组件思维迁移到 Nuxt 组件组织

如果你以前做 Vue3 项目，可能会习惯“先写页面，再看哪里重复，最后抽组件”。  
这个思路在 Nuxt 里也能用，但要多一层“约定式组织”的意识：**不是抽出来就完了，还要让框架能稳定地发现它、复用它、维护它。**

你可以把迁移思路记成三步：

- **Vue3 习惯**：先实现功能；
- **Nuxt 习惯**：先考虑组件放哪一类目录；
- **Nuxt 成熟做法**：让基础组件、业务组件、布局组件各归其位。

### 老赵经验分享
我一般建议，项目初期先“保守拆分”。宁可粗一点，也不要一开始切太碎。过度拆分会导致文件太多、关系太复杂，最后你会发现自己在管理组件，而不是做业务。

### 赵老师提醒
不要把“能复用”理解成“必须抽成组件”。  
很多新手喜欢把所有小块都拆出来，结果页面里一堆嵌套，阅读成本反而更高。**只有当组件有稳定复用价值、或者职责清晰时，再拆。**

## 三、props、events、slots：Nuxt 里组件通信怎么写更自然？

### 3.1 props：把数据传进去

`props` 在 Nuxt 和 Vue3 里没有本质区别，还是“父传子”的核心方式。

例如一个内容卡片组件：

```vue
<script setup>
defineProps({
  title: String,
  summary: String,
  cover: String
})
</script>

<template>
  <article class="card">
    <img :src="cover" alt="" />
    <h3>{{ title }}</h3>
    <p>{{ summary }}</p>
  </article>
</template>
```

父组件传入：

```vue
<ArticleCard
  title="Nuxt 入门"
  summary="从 Vue 过渡到 Nuxt 的第一步"
  cover="/images/nuxt.jpg"
/>
```

适合字段明确、结构稳定的展示场景，比如文章摘要、产品简介、功能点介绍。

### 3.2 events：把动作传回去

如果组件里有点击、展开、收藏、切换等交互，就用 `emit` 往外抛事件：

```vue
<script setup>
const emit = defineEmits(['select'])

function handleClick() {
  emit('select')
}
</script>

<template>
  <button @click="handleClick">查看详情</button>
</template>
```

父组件接收行为：

```vue
<ArticleCard @select="goDetail" />
```

这样做的好处是把“展示”和“行为”分开。组件不关心点完后去哪里，只负责通知外层“用户点了我”。

### 3.3 slots：把结构留给外部决定

很多内容展示组件更适合用 `slots`，因为外层可能希望决定某些区域怎么填。

```vue
<template>
  <div class="panel">
    <header><slot name="header" /></header>
    <main><slot /></main>
    <footer><slot name="footer" /></footer>
  </div>
</template>
```

这样你能复用结构，同时保留内容灵活性。  
标题固定、正文变化大的场景，比如专题区块、功能介绍、列表组合，都很适合 slot。

### 3.4 三者怎么选？

简单记：

- **数据明确、结构固定**：用 `props`
- **需要触发外部动作**：用 `events`
- **外部决定内容结构**：用 `slots`

实战里通常会混合使用。比如文章卡片：标题和摘要用 props，点击通过事件通知父层，顶部标签区则可以用 slot 扩展。

### 老赵经验分享
内容站组件真正难的，往往不是样式，而是“到底该传数据还是传结构”。我的经验是：**内容变化大，就多用 slot；只是字段展示，就多用 props。**

### 赵老师提醒
别把一个组件做成“万能大盒子”。  
`props` 太多、事件太多、slot 太多，最后组件会变得难测、难维护。**组件边界越清楚，后面越省心。**

---

## 四、组合式 API 与 composables：组件逻辑怎么抽出来？

### 4.1 组件里不要只堆模板

Vue3 的组合式 API 让逻辑拆分更自然，Nuxt 也延续了这套风格。  
很多可复用逻辑适合从组件里抽出去，放到 `composable` 中，比如：

- 获取导航数据；
- 处理筛选条件；
- 管理页面状态；
- 封装格式化函数；
- 统一处理加载、错误、空状态。

这样能让组件更轻，不会一边管界面一边管逻辑。

### 4.2 一个典型例子：文章列表状态

```vue
<script setup>
const { articles, pending, refresh } = useArticleList()
</script>

<template>
  <section>
    <div v-if="pending">加载中...</div>
    <ArticleList v-else :items="articles" @refresh="refresh" />
  </section>
</template>
```

页面只管结构，逻辑交给 composable。  
以后换成产品列表，也可以复用类似的拆法。

### 4.3 组件与 composable 的分工

建议记住这条线：

- **组件负责展示与交互**
- **composable 负责可复用逻辑**
- **页面负责组装**

这三层分开后，Nuxt 项目会很清楚。  
尤其在内容站、展示站里，这种分工很舒服：页面拼模块，组件管长相，composable 管数据与状态。

### 老赵经验分享
我很喜欢把“和页面视觉无关、和业务逻辑相关”的代码抽到 composable 里。这样组件会轻很多。尤其是内容站项目，列表拉取、筛选、分页、排序这些逻辑经常重复，抽出去后复用效果很明显。

### 赵老师提醒
不要为了“高内聚”把所有东西都塞进 composable。  
如果某段逻辑只在一个组件里出现一次，抽出去未必更好。**抽象也是有成本的，别过度设计。**

---

## 五、常见组件拆分思路：头部、导航、卡片、列表项怎么拆？

### 5.1 头部组件：负责品牌与入口

头部通常包含：

- Logo；
- 主导航；
- 搜索入口；
- 用户区或行动按钮。

建议拆成：

- `AppHeader`：整体容器；
- `NavMenu`：导航菜单；
- `SearchBar`：搜索框；
- `UserAction`：按钮/入口。

这样既方便复用，也方便局部修改。比如以后要做移动端折叠菜单，只动导航相关组件即可。

### 5.2 导航组件：要支持状态变化

导航组件要特别注意：

- 当前激活项高亮；
- 移动端折叠菜单；
- 路由变化后的状态同步。

在 Nuxt 中，导航常和路由配合，组件最好只负责显示，路由判断尽量外置或通过组合逻辑处理。这样组件不会过度依赖某个页面状态，也更容易复用到不同布局里。

### 5.3 卡片组件：内容站的核心

内容站或展示站里，卡片几乎是高频组件。  
常见场景有：

- 文章卡片；
- 产品卡片；
- 功能卡片；
- 推荐卡片。

卡片建议统一字段风格，比如：

- `title`
- `summary`
- `cover`
- `tags`
- `to`

这样列表页、推荐模块、首页专题都能复用。换一组数据，就能生成不同版块，开发效率会很高。

### 5.4 列表项组件：适合“重复渲染”的场景

如果一个列表项结构比较复杂，建议单独拆一个 `Item` 组件，而不是把所有逻辑堆在 `List` 里。

例如：

- `ArticleList` 负责遍历；
- `ArticleListItem` 负责单项展示。

这样列表逻辑和单项展示解耦，样式或字段变化时更容易改。  
当你要在首页、分类页、推荐页使用同一套列表时，这种拆法会特别省时间。

### 老赵经验分享
我做内容站时，最先复用起来的往往不是大组件，而是“卡片”和“列表项”。因为页面内容虽然不同，但展示结构很像。你只要把这两个组件设计好，很多页面就能很快搭出来。

### 赵老师提醒
拆组件时要避免层级过深。  
比如一个首页只展示 3 个模块，却拆出十几个文件，这就失去效率了。**拆分的目标是复用和维护，不是凑技术感。**

---

## 六、组件实战：构建一个可复用的内容展示模块

下面我们做一个适合博客首页或产品展示站的内容模块，目标是实现：

- 一个模块标题；
- 一个简介；
- 多个内容卡片；
- 支持插槽扩展；
- 可以在首页和专题页重复使用。

这很符合 Nuxt 的实际应用，因为内容站和展示站本来就适合“模块化 + 复用”的搭法。

### 6.1 先设计组件职责

我们拆成三层：

1. `SectionBlock`：通用区块容器；
2. `ContentCard`：内容卡片；
3. 页面组合：负责传数据和摆放。

### 6.2 通用区块容器

```vue
<template>
  <section class="section-block">
    <header class="section-block__header">
      <slot name="title" />
      <slot name="desc" />
    </header>
    <div class="section-block__body">
      <slot />
    </div>
  </section>
</template>
```

它只管框架，不管内容，适合承载“推荐阅读”“热门产品”“功能亮点”等专题区块。

### 6.3 内容卡片

```vue
<script setup>
defineProps({
  title: String,
  summary: String,
  cover: String,
  link: String
})
</script>

<template>
  <NuxtLink :to="link" class="content-card">
    <img :src="cover" :alt="title" />
    <h3>{{ title }}</h3>
    <p>{{ summary }}</p>
  </NuxtLink>
</template>
```

这里直接用 `NuxtLink` 做站内跳转，更适合内容站和展示站，也更符合 Nuxt 的路由体系。

### 6.4 页面中组合使用

```vue
<script setup>
const cards = [
  { title: 'Nuxt 入门', summary: '从 Vue 过渡到 Nuxt', cover: '/img/1.jpg', link: '/posts/nuxt-start' },
  { title: '服务端渲染', summary: '理解页面生成方式', cover: '/img/2.jpg', link: '/posts/ssr' },
  { title: 'SEO 基础', summary: '让页面更容易被发现', cover: '/img/3.jpg', link: '/posts/seo' }
]
</script>

<template>
  <SectionBlock>
    <template #title><h2>推荐阅读</h2></template>
    <template #desc><p>适合想快速掌握 Nuxt 基础的内容。</p></template>

    <div class="grid">
      <ContentCard
        v-for="item in cards"
        :key="item.title"
        v-bind="item"
      />
    </div>
  </SectionBlock>
</template>
```

这一套结构非常适合内容站或展示站：

- 上层是模块；
- 中层是卡片；
- 下层是数据数组；
- 页面只负责组合。

以后不管放首页、专题页还是栏目页，只要换数据，不用重写结构。

### 6.5 这个模块为什么适合 Nuxt？

因为它充分利用了 Nuxt 的几个特点：

- **自动导入**减少导入负担；
- **组件分层**让结构清晰；
- **`NuxtLink`** 适合站内导航；
- **页面与组件分离**便于服务端渲染和扩展。

更重要的是，它很符合内容站的开发方式：页面不是一块块手写出来的，而是用可复用模块拼出来的。

### 6.6 这套思路怎么帮助你做内容站或展示站？

如果你的目标是做博客首页、产品展示页、课程列表页、活动专题页，那么组件组织方式基本都离不开这套方法：

- 首页用“头部 + 横幅 + 推荐区 + 列表区”；
- 专题页用“标题区 + 分类筛选 + 卡片列表”；
- 展示站用“卖点区 + 图文卡片 + 行动按钮”。

这些页面的共同点是：**内容会变，但模块逻辑很像。**  
Nuxt 的组件自动导入、约定目录和组合式写法，刚好适合这种“拼装式开发”。

### 老赵经验分享
实战里最值钱的，不是某个组件本身，而是“这套组件以后能不能继续被别的页面拿来用”。如果你能把首页推荐区、专题页列表区、文章聚合区都做成同一种模式，项目开发速度会越来越快。

### 赵老师提醒
内容展示模块很容易写成“看起来能用，但一换数据结构就崩”。  
所以设计时一定先想清楚：**字段是否统一、卡片是否可扩展、区块是否允许替换内容。**

## 结尾小结：把 Nuxt 组件思维真正用起来

这一章我们从组件自动导入讲到组件拆分，再讲到 `props`、`events`、`slots` 和 `composables` 的配合，最后落到一个可复用的内容展示模块。你现在应该能抓住 Nuxt 组件体系的核心思路：

- **Nuxt 让组件使用更省事**，自动导入减少样板代码；
- **组件不是越多越好，而是职责越清楚越好**；
- **基础组件和业务组件要分开**，便于维护；
- **`props`、`events`、`slots` 各司其职**，别乱用；
- **逻辑抽到 composable，展示留在组件里**，这是从 Vue3 过渡到 Nuxt 很重要的一步；
- **内容站、展示站特别适合这种组件组织方式**。

如果你接下来要继续写 Nuxt 项目，建议你马上做两件事：

1. 按本章方法整理一次你的 `components/` 目录；
2. 选一个页面，尝试把“头部 + 列表 + 卡片”拆成可复用模块。

你会明显感觉到：**Nuxt 的强大，不在于它把 Vue 变复杂了，而在于它把很多重复劳动变少了。**

### 老赵经验分享
真正开始做 Nuxt 项目后，你会发现最有价值的能力不是“会写一个组件”，而是“会把一堆页面拼成一套可复用体系”。这才是从 Vue 开发者过渡到 Nuxt 开发者的关键一步。

### 赵老师提醒
别只盯着单个组件好不好看，**要从整个页面结构去看组件是否值得复用**。能服务内容站、展示站、列表页、详情页的组件，才是真正有价值的组件。

# 第6章 数据获取：服务端拿数据、客户端拿数据都要会

## 开篇引入：为什么到了 Nuxt，数据获取就不只是“发个请求”了

在 Vue3 里，我们通常在 `onMounted` 里拉数据：页面先渲染，组件挂载后再请求接口，数据回来再更新视图。这套思路做 SPA 没问题。

但到了 Nuxt，核心价值变成了 **服务端渲染（SSR）**：页面在发给浏览器之前，服务端就先把 HTML 生成好了。这样做的意义很直接：

1. 首屏更快；
2. 搜索引擎更容易抓取完整内容；
3. 分享链接时预览更完整。

所以在 Nuxt 里，数据获取不能只看“浏览器里怎么发请求”，还要看“页面渲染前数据从哪来、什么时候拿、怎么进入 HTML”。

你可以把它理解成一句话：

> **既要会服务端取数，也要会客户端补数；既要关注数据，也要关注页面状态。**

这一章，老赵带你把 Nuxt 的数据获取思路讲清楚，顺手把 `useFetch`、`useAsyncData`、错误处理、空状态，以及内容站首页和详情页联动这些实战点串起来。

### 老赵经验分享

我做内容站时，最怕首页打开先空两秒，等接口回来才出列表。改成 Nuxt 后，首页文章直接在服务端渲染出来，站点一下就“像样”了。很多时候，不是页面不够好，而是数据来得太晚。

### 赵老师提醒

别把“服务端取数”理解成“所有逻辑都丢到服务端”。SSR 的目标是让**关键内容尽早出现**，不是把项目搞复杂。该客户端加载的，还是可以客户端加载。

---

## 一、Nuxt 的数据获取思路：为什么 SSR 场景更强调服务端取数？

### 1. SSR 里，数据不是“渲染后再补”，而是“渲染前就准备好”

在纯 Vue SPA 里，页面结构先出来，数据后补进来；在 Nuxt SSR 场景里，很多时候页面渲染前就要把关键数据准备好。这样服务端返回给浏览器的不是空壳，而是带内容的 HTML。

比如内容站首页，理想流程是：

1. 用户访问 `/`
2. Nuxt 服务端先请求文章列表
3. 服务端把列表渲染进 HTML
4. 浏览器拿到页面直接看到内容

这比“先白屏，再转圈加载”更适合内容类站点。

### 2. 为什么内容站、展示站尤其需要服务端取数

内容站和产品展示站的共同点是：**页面内容本身就是价值**。

- 博客首页展示文章列表
- 文章详情页展示正文、作者、发布时间
- 产品站展示产品特点、案例、价格、FAQ

这些内容如果能在服务端提前拿到，就能提升首屏体验、增强收录、减少闪烁，也更适合社交分享。

### 3. 什么时候还是适合客户端请求？

Nuxt 不是“所有请求都必须服务端做”。有些数据天然更适合客户端请求，比如：

- 登录后才能看的个人信息
- 点击按钮后才加载的评论区
- 滚动分页加载的列表
- 依赖用户交互的筛选结果

所以正确姿势不是“只服务端”或者“只客户端”，而是：

> **首屏核心内容尽量服务端取，交互性强或实时性强的内容可以客户端补。**

### 4. 从 Vue 过渡到 Nuxt，要先换一个思维方式

Vue3 开发者容易把注意力放在“请求写在哪个生命周期里”。到了 Nuxt，你还要多想一层：

- 这个数据是否影响首屏？
- 是否需要被搜索引擎看到？
- 是否只在用户操作后才需要？
- 是否和路由强绑定？

思路一变，你会发现 Nuxt 更像“页面级编排”，而不只是“组件里写请求”。

### 5. 页面生成方式也决定了取数策略

Nuxt 的页面生成方式，常见可以理解为三类：

- **服务端渲染**：每次请求时在服务端拿数并生成页面；
- **预渲染/静态生成**：构建时把页面内容提前生成好；
- **客户端补充渲染**：页面先出来，部分数据后加载。

这三种方式经常混着用。比如首页用 SSR 保证首屏，列表筛选区用客户端请求，产品详情页用服务端数据再叠加评论模块的客户端加载。对 Vue3 开发者来说，这就是从“组件渲染”过渡到“页面生成”的关键一步。

### 老赵经验分享

我做展示站时，通常先把首页、列表页、详情页这三类页面做好 SSR。评论、登录态、收藏这些后面再加。先把搜索引擎和首屏体验打牢，站点基本盘就稳了。

### 赵老师提醒

别为了“全都服务端”把项目搞复杂。内容站的原则是：**关键内容优先，次要内容按需补。**

---

## 二、`useFetch`、`useAsyncData`：这两个 API 到底怎么用，差别在哪？

### 1. `useFetch`：面向接口请求的常用选择

`useFetch` 可以理解成 Nuxt 里更偏“直接请求接口”的方式，适合你已经有 HTTP 接口，想直接拉数据并绑定到页面。

```vue
<script setup>
const { data, pending, error, refresh } = await useFetch('/api/posts')
</script>

<template>
  <div>
    <p v-if="pending">加载中...</p>
    <p v-else-if="error">加载失败</p>
    <ul v-else>
      <li v-for="item in data" :key="item.id">{{ item.title }}</li>
    </ul>
    <button @click="refresh">重新加载</button>
  </div>
</template>
```

它的好处是直观：请求、状态、刷新都给你了，上手快。

### 2. `useAsyncData`：更适合“异步拿数据并做处理”的场景

`useAsyncData` 更像“我有一个异步函数，Nuxt 帮我纳入渲染流程”。适合：

- 自己写异步逻辑
- 请求多个接口并组合结果
- 需要加工返回数据
- 想统一管理页面状态

```vue
<script setup>
const { data, pending, error } = await useAsyncData('home-data', async () => {
  const posts = await $fetch('/api/posts')
  const banners = await $fetch('/api/banners')
  return { posts, banners }
})
</script>
```

### 3. 对照理解：它们到底怎么选？

| 对比项 | `useFetch` | `useAsyncData` |
|---|---|---|
| 核心定位 | 直接拉接口 | 异步逻辑编排 |
| 适合场景 | 列表、详情、简单接口 | 多接口聚合、数据加工、复杂依赖 |
| 使用感受 | 像“带状态的请求封装” | 像“纳入 Nuxt 渲染流程的异步函数” |
| 推荐场景 | 文章列表、产品详情、推荐接口 | 首页组合数据、跨接口聚合、复杂页面初始化 |

简单判断：

- **只是请求一个接口，优先用 `useFetch`**
- **需要更灵活的异步处理，用 `useAsyncData`**

### 4. 常见误区

**误区一：把 `useFetch` 当成普通 `fetch`。**  
它不只是请求封装，还和 Nuxt 的渲染、缓存、状态系统有关。

**误区二：总在 `onMounted` 里请求。**  
如果首屏内容重要，就别让它只能在客户端出现。

**误区三：多个页面共用同一个 key 却不管理。**  
尤其 `useAsyncData` 里，key 很重要，否则可能出现缓存混乱、数据复用异常。

### 5. 实战选择建议

如果你在做内容站首页、文章详情页、产品介绍页，通常建议这样选：

- 首页列表：`useFetch`
- 详情正文：`useFetch`
- 首页多个模块组合：`useAsyncData`
- 先拿主数据，再加工推荐列表：`useAsyncData`

思路清楚，后期维护也清楚。

### 老赵经验分享

很多 Vue 开发者会想：“不就是把 `axios.get()` 放进去吗？” 思路不算错，但 Nuxt 的厉害之处在于，它不只帮你请求，还帮你决定“什么时候请求、在哪边请求、拿到后怎么进页面”。

### 赵老师提醒

别纠结“哪个 API 更高级”。真实项目里，关键不是名字，而是**数据是否参与首屏渲染**、**是否需要跨服务端和客户端共享状态**。先看场景，再选工具。

## 三、服务端数据获取的完整流程：请求发起、渲染前拿到数据、状态处理、异常兜底

这一节把流程拆开讲清楚，不然很多人会觉得“我会写 `useFetch` 了”，但一到真实页面还是慌。

### 1. 第一步：请求发起

当用户访问页面时，Nuxt 会先进入页面初始化阶段。如果你在页面 `setup` 里写了 `await useFetch(...)`，Nuxt 会在渲染流程里先执行这个请求。

这意味着数据不是晚一点补，而是**在渲染前尽量拿到**。  
对内容站来说，这一步非常关键，因为它决定首屏到底是不是“有内容的页面”。

### 2. 第二步：渲染前拿到数据

拿到数据后，Nuxt 会把它放进当前页面的渲染上下文里。页面模板一旦渲染，就可以直接使用这些数据。

你可以简单理解成：

- 服务端先发请求
- 等数据回来
- 再生成 HTML
- 浏览器接收时已经是有内容的页面

这也是 Nuxt 和普通 Vue SPA 最明显的区别之一。

### 3. 第三步：状态处理

真实项目里，数据不是“拿到了”就结束了。你必须处理三种状态：

- `pending`：正在加载
- `error`：请求失败
- `data`：请求成功

```vue
<script setup>
const { data, pending, error, refresh } = await useFetch('/api/posts')
</script>

<template>
  <section>
    <div v-if="pending">文章列表加载中...</div>

    <div v-else-if="error">
      <p>文章加载失败，请稍后重试。</p>
      <button @click="refresh">重新加载</button>
    </div>

    <ul v-else>
      <li v-for="item in data || []" :key="item.id">
        {{ item.title }}
      </li>
    </ul>
  </section>
</template>
```

### 4. 第四步：异常兜底

异常兜底不是开发时顺手写一下，它是内容站的基本功。因为真实环境里，接口超时、网络波动、后端报错都很正常。

兜底可以分三层：

- **文案兜底**：给用户看的提示
- **交互兜底**：提供重试按钮
- **页面兜底**：避免结构崩掉

如果是详情页，还可以在接口失败时展示一个“返回首页”按钮，给用户下一步操作路径。

### 5. 一个完整流程的思路总结

你在做 Nuxt 数据页面时，脑子里最好始终有这条线：

> 发起请求 → 服务端渲染前拿到数据 → 页面按状态展示 → 出错可重试 → 没数据也不塌

这条线跑顺了，列表页、详情页、推荐模块就都能套进来。

### 老赵经验分享

我见过不少页面，功能都能跑，但只要接口慢一点，页面就像“没装修完”。所以我特别强调：数据获取不是只管成功，状态处理才是项目成熟度的分水岭。

### 赵老师提醒

服务端取数不是为了“让代码看起来高级”，而是为了让页面先有内容再谈交互。别把顺序搞反了。

## 四、服务端请求和客户端请求：列表页、详情页、推荐模块分别怎么分工？

### 1. 列表页：首页、栏目页、文章列表页

列表页最适合服务端取数，因为它通常是内容站的入口页。

比如博客首页：

- Banner
- 最新文章
- 热门推荐
- 分类导航

这些内容最好在服务端一次性准备好，用户打开首页就能看到完整布局。产品展示站也一样：产品亮点、解决方案、案例、咨询入口，本质上都是给所有访问者看的内容，应该尽量早点出现。

### 2. 详情页：正文一定优先服务端渲染

详情页是 SSR 最值得做的场景之一。

比如文章详情页：

- 标题
- 作者
- 发布时间
- 正文
- 标签
- 推荐阅读

其中正文是核心内容，必须尽量在服务端拿到。否则页面会显得“还没生成好”，用户体验和 SEO 都会受影响。

更稳妥的做法是：详情页的数据请求和路由绑定，路由变了，文章也跟着变，页面结构更清晰。

### 3. 推荐模块：可以服务端，也可以客户端

推荐模块通常有两种思路：

- **与正文紧密相关的推荐**：适合服务端取数
- **个性化推荐、实时推荐**：适合客户端补充

如果只是“同分类相关文章”，和详情页一起在服务端取出来很合适；如果推荐依赖用户行为，那就更适合客户端加载。推荐模块的定位要清楚：**它是锦上添花，不是首屏主角。**

### 4. 客户端请求适合什么？

客户端请求更适合这些场景：

- 用户登录后才显示的个人中心信息
- 点开“加载更多”时才出现的列表分页
- 筛选条件变化后的局部刷新
- 评论、点赞、收藏等交互行为

这类内容的共同点是：**不影响页面第一眼的核心内容**，但能增强交互体验。

### 5. 一个实用判断法：是否影响首屏与收录

可以用这些问题判断要不要服务端取数：

- 会不会影响用户第一眼看到的内容？
- 会不会影响搜索引擎理解页面？
- 会不会影响分享预览？
- 会不会因延迟加载导致空页面感？

如果有两项以上答案是“会”，那这块数据大概率应该优先服务端获取。

### 老赵经验分享

做展示站时，我通常建议先把首页、详情页、列表页这三类页面做好 SSR。别一开始就盯着评论、登录态、收藏这些，先把搜索引擎和首屏体验打牢，基本盘就稳了。

### 赵老师提醒

推荐模块别拆太碎。一个详情页如果挂十几个请求，SSR 也会被拖慢。内容站的原则是：**少量关键请求，换取更稳的首屏。**

## 五、客户端请求与服务端请求的差异：到底差在哪儿？

### 1. 执行环境不同

- **服务端请求**：运行在 Node 侧，页面生成前执行
- **客户端请求**：运行在浏览器里，页面挂载后执行

同样是请求文章列表，服务端请求会更早进入 HTML，而客户端请求会晚一点出现在页面里。

### 2. 请求时机不同

服务端请求更早，所以适合首屏内容；客户端请求更晚，所以适合交互型数据。

这也是很多页面采用“首屏服务端、次级内容客户端”的原因。既保住体验，也不会让服务端压力过大。

### 3. 能力边界不同

客户端请求能直接拿到浏览器环境，比如：

- cookie
- localStorage
- 用户交互状态

服务端请求更适合处理：

- 首屏页面数据
- 可缓存数据
- 不依赖浏览器环境的数据

所以不要把所有逻辑都往一边放，数据从哪来，决定了它更适合在哪边执行。

### 4. 常见坑：服务端和客户端拿到的数据不一致

很多 Vue 开发者刚上 Nuxt 时会踩这个坑：

- 服务端拿到一份数据
- 客户端挂载后又请求一份不同数据
- 页面出现闪动或水合不一致

所以要尽量保持服务端和客户端数据来源一致，或者明确哪些数据只在客户端更新。

### 5. 实战建议：把请求分层

可以这样分：

- **第一层：首屏必需数据，服务端取**
- **第二层：用户交互数据，客户端取**
- **第三层：实时变化数据，客户端定时刷新或按需刷新**

这样更容易规划项目，也更容易排查问题。

### 老赵经验分享

我常跟团队说：**服务端负责先把门面搭起来，客户端负责把细节补齐。** 按这个思路切请求，项目会清楚很多。

### 赵老师提醒

不要让客户端去补首屏内容。那样你写的是 Nuxt，体验却像老式 SPA。Nuxt 的价值，首先体现在“首屏数据提前准备”。

---

## 六、加载状态、错误状态、空状态：数据没回来之前，页面也要体面

### 1. 为什么状态管理重要？

页面不是只有“有数据”和“没数据”两种情况，通常还要处理：

- 加载中
- 出错了
- 请求成功但没有内容

如果只写 `v-if="data"`，页面很容易显得粗糙。尤其是内容站，用户对页面是否正常工作非常敏感。

### 2. 加载状态怎么做

加载状态不是“转个圈”就完事，而是让用户知道页面正在工作。常见方式有：

- 骨架屏
- 文案提示
- 局部 loading
- 整页 loading

列表页可以先展示骨架，再替换成真实内容，这样视觉更稳定。

### 3. 错误状态怎么做

错误状态至少要包含：

- 简要说明
- 重试按钮
- 必要时的降级提示

```vue
<template>
  <div v-if="error">
    <p>内容暂时加载失败，请稍后重试。</p>
    <button @click="refresh">重新加载</button>
  </div>
</template>
```

如果是产品展示站，还可以补一句“你也可以先浏览其他页面”，给用户一个继续浏览的出口。

### 4. 空状态怎么做

空状态常被忽略，但在内容站里很重要。比如：

- 某分类下没有文章
- 推荐区暂时没有数据
- 搜索结果为空

空状态要告诉用户两件事：

1. 现在为什么没内容；
2. 接下来可以怎么做。

比如“暂无文章，先看看热门推荐”就比“暂无数据”友好得多。

### 5. 一个实用检查清单

每写一个数据页面，都检查一下：

- 有没有 `pending` 状态？
- 有没有 `error` 状态？
- 有没有空数组/空对象处理？
- 有没有重试入口？
- 没数据时页面会不会塌掉？

这套检查不复杂，但很救命。

### 老赵经验分享

真正成熟的页面，不是“有数据的时候很漂亮”，而是“没数据的时候也不尴尬”。很多页面出问题，不是接口坏了，而是状态没兜住。

### 赵老师提醒

别把空状态和错误状态当成开发时才看的附属品，它们其实是用户体验的一部分，尤其在网络差、接口慢、接口偶发失败的时候，真的能救命。

## 七、数据获取实战：做一个内容站首页与详情页的联动

下面用一个小型内容站把前面的知识串起来：**首页展示文章列表，详情页展示文章正文，并带推荐阅读。**

### 1. 首页：服务端拉文章列表

首页的任务很简单：

- 拉文章列表
- 展示标题、摘要、发布时间
- 点击跳转详情页

```vue
<script setup>
const { data, pending, error } = await useFetch('/api/posts')
</script>

<template>
  <section>
    <h1>最新文章</h1>

    <div v-if="pending">首页加载中...</div>
    <div v-else-if="error">首页数据加载失败</div>

    <ul v-else>
      <li v-for="post in data || []" :key="post.id">
        <NuxtLink :to="`/posts/${post.id}`">{{ post.title }}</NuxtLink>
        <p>{{ post.summary }}</p>
      </li>
    </ul>
  </section>
</template>
```

关键不是代码本身，而是思路：**首页作为入口页，优先服务端渲染。**

### 2. 详情页：根据动态路由拉正文数据

详情页通常是 `/posts/[id]` 这种动态路由。

```vue
<script setup>
const route = useRoute()
const { data, pending, error } = await useFetch(`/api/posts/${route.params.id}`)
</script>

<template>
  <article>
    <div v-if="pending">详情加载中...</div>
    <div v-else-if="error">文章加载失败</div>

    <template v-else>
      <h1>{{ data.title }}</h1>
      <p>{{ data.author }} · {{ data.createdAt }}</p>
      <div v-html="data.content"></div>
    </template>
  </article>
</template>
```

最重要的是：**正文内容要尽量在服务端拿到，并参与首屏 HTML 输出。**

如果是产品展示站，这一页可以换成产品介绍、参数说明、案例展示、咨询入口，逻辑一样。

### 3. 推荐模块：详情页下方的相关文章

推荐阅读可以再拉一个接口，比如根据当前文章分类获取相关文章。

```vue
<script setup>
const route = useRoute()
const { data: related } = await useFetch(`/api/posts/${route.params.id}/related`)
</script>
```

然后在页面下方展示同分类文章、热门文章或最新文章。

### 4. 这种联动为什么适合 Nuxt

因为 Nuxt 擅长做这三件事：

1. 首页先把核心内容渲染好；
2. 详情页先把正文和关键元信息渲染好；
3. 局部模块再按需补充。

这就是内容站和展示站特别适合 Nuxt 的原因。它不是单纯做页面，而是把“内容呈现”这件事处理得更顺。

### 5. 最后检查：这个小项目是否合格？

你可以用这份清单自测：

- 首页文章列表是否服务端可见？
- 详情页正文是否首屏就出现？
- 推荐模块是否不影响首屏主内容？
- 加载、错误、空状态是否完整？
- 页面跳转后是否流畅？
- 是否保留了 SEO 需要的标题和描述配置？

### 6. 项目交付结果长什么样？

如果这是一个真实的小项目，最后至少应该交付出这些东西：

- 一个可访问的首页 `/`
- 一个可访问的文章详情页 `/posts/[id]`
- 一个相关文章推荐模块
- 完整的加载、错误、空状态处理
- 支持 Nuxt SSR 的页面渲染结果
- 基础 SEO 标题和描述配置

你会发现，做到这里，已经不是“学会一个 API”了，而是能交出一个像样的 Nuxt 内容站骨架。

### 老赵经验分享

做内容站最怕“看起来像站，实际上是组件拼接”。真正好用的 Nuxt 内容站，应该是用户一进来就能看到内容，搜索引擎也能抓到内容，编辑和维护也方便。这个平衡点，Nuxt 很擅长。

### 赵老师提醒

实战里别一开始就追求复杂架构。先把“首页列表 + 详情页 + 推荐模块 + 基础状态处理”做好，你就已经完成了一个能上线的 Nuxt 小项目骨架。

## 本章小结：数据获取不是技术细节，而是 Nuxt 体验的核心

这一章要记住的，不是某个 API 的名字，而是 Nuxt 的数据获取思路：

- **SSR 场景更强调服务端取数**
- **`useFetch` 适合直接请求接口**
- **`useAsyncData` 适合更灵活的异步编排**
- **列表、详情、推荐模块都要按场景选择服务端或客户端**
- **加载、错误、空状态必须认真处理**
- **内容站和展示站最能体现 Nuxt 的优势**

如果你是 Vue3 开发者，过渡到 Nuxt 时最大的变化，不是“多学几个 API”，而是学会用“页面渲染流程”思考数据。

### 行动建议

下一步你可以直接做三件事：

1. 用 `useFetch` 改写一个 Vue 页面里的接口请求；
2. 新建一个动态详情页，练习首页到详情页的数据联动；
3. 给页面补齐 `pending`、`error`、空状态处理。

把这三步做完，你对 Nuxt 的数据获取就不再是“知道”，而是“会用了”。

### 为什么这正是 Vue3 到 Nuxt 的关键变化

因为在 Vue3 里，你更多是在想“组件什么时候拿到数据”；而在 Nuxt 里，你必须进一步思考“页面在渲染前就要把哪些关键数据准备好”。这一步思维转换，正是 Vue3 过渡到 Nuxt 的关键变化。

# 第7章 中间件与页面守卫：把流程控制住

# 第 8 章 中间件与页面守卫：把流程控制住

如果你写过 Vue 单页应用，对这种场景一定不陌生：页面一进来，先判断用户状态，再决定要不要继续展示。比如没登录就去个人中心，先跳登录页；已经买过课了，就别再看购买页；某些内容只允许特定角色访问。  
在 Nuxt 里，这类逻辑不适合散落在组件里反复写 `if...else`，更适合交给**中间件**统一处理。

Nuxt 的中间件，核心价值就一句话：**在页面真正渲染之前，把流程控制住。**  
它能做访问判断、跳转、拦截、权限控制，也能和数据获取配合，减少无效请求。对 Vue3 开发者来说，这一章很关键，因为它直接关系到你能不能把 Vue 的页面思维，顺利过渡到 Nuxt 的约定式开发思维。

这一章，老赵就带你把“页面守卫”这件事讲清楚。你会知道中间件是什么、它和全局中间件有什么区别、常见场景怎么写，以及在内容站、展示站里怎么用得顺手。更重要的是，你会明白：**Nuxt 的这套入口控制，为什么会比你在 Vue 里自己拼路由守卫更顺。**

---

## 一、中间件是什么：在页面渲染前能做什么？

先别把中间件想得太复杂。按 Nuxt 的语境，它更像是**页面进入前的门卫**。它会在路由切换、页面渲染之前执行，你可以在里面判断条件，然后决定：

1. 继续进入页面；
2. 跳转到别的页面；
3. 终止本次访问；
4. 做一点轻量预处理。

它的意义很直接：**把不该进入的请求挡在页面外面。**  
比如用户没登录却访问 `/profile`，没必要先把页面渲染出来，再闪一下、报个错、再跳走。中间件可以更早一步做决定，体验更自然，逻辑也更集中。

### 1. 中间件适合做什么

最常见的就是这些：

- 登录校验：没登录就跳登录页
- 权限控制：普通用户不能进管理页
- 访问跳转：老页面自动跳新页面
- 业务拦截：某些活动页仅限指定条件访问
- 页面预判：根据用户状态决定展示哪个版本页面

你可以把它理解成“进门前先看门禁卡”，而不是“进了房间才发现不让进”。这类逻辑非常适合放在 Nuxt 中间件里，因为它本来就处在页面生命周期的早期阶段。

### 2. 中间件不适合做什么

中间件不是业务大杂烩，以下事情不建议放进去：

- 大量数据请求
- 复杂计算
- 频繁调用第三方接口
- 长时间阻塞逻辑
- 依赖复杂组件状态的处理

原因很简单：中间件执行越早，越应该轻、快、明确。它的任务是“判断和引导”，不是“把所有事情干完”。  
如果你把它写成重业务入口，页面跳转就会变慢，用户只会感觉“点了没反应”。

### 3. 从 Vue3 过渡过来怎么理解

Vue3 项目里，你可能会在路由守卫里写类似逻辑：

- `beforeEach`
- `beforeEnter`
- `meta` 判断权限

Nuxt 仍然保留“路由进入前控制”的思想，但更强调**约定式开发**。你不需要先手工配置一大套路由守卫体系，很多页面级逻辑可以直接按文件约定放到对应位置，维护起来更顺手。  
这就是 Nuxt 和 Vue3 很重要的一点关系：**Nuxt 不是推翻 Vue 技能，而是把这些技能放进更有约定的系统里。**

### 老赵经验分享

老赵做内容站时，最怕两种代码：一种是所有页面都写一遍判断，另一种是判断写得太重。前者难维护，后者拖慢首屏。中间件最适合做“轻判断、快分流”，这才是它真正的价值。

### 赵老师提醒

记住一句话：**中间件是入口控制，不是业务实现层。**  
你在里面做的每一件事，都应该问自己：这是不是“进入页面前必须决定的事”？如果不是，尽量别放。

---

## 二、路由中间件与全局中间件有什么区别？

Nuxt 的中间件至少要分清两类：**路由中间件**和**全局中间件**。很多人刚开始写 Nuxt 时，最容易把它们混用，结果调试半天不知道为什么会被拦截。

### 1. 路由中间件：只管某个页面或某组页面

路由中间件通常作用于单个页面，或者某些指定页面。适合场景：

- 个人中心页需要登录
- 后台管理页需要权限
- 某个活动页需要特定时间段开放

它的特点是“按需使用”，不会影响所有页面。  
这很符合 Nuxt 的约定式开发思路：页面需要什么，就在页面附近声明什么。后面看代码时，不用东翻西找，就能知道这个页面有哪些进入限制。

### 2. 全局中间件：每次路由切换都要执行

全局中间件更像系统级拦截器。只要页面发生跳转，它就会执行。适合做：

- 全站登录态检查
- 全局语言切换判断
- 站点级重定向
- 全局活动开关判断

但全局中间件一定要慎用。因为它会频繁执行，如果写得太重，整个站点都会被拖慢。  
尤其是内容站或展示站，页面本来就追求轻快，全局中间件更应该保持克制。

### 3. 两者怎么选

判断标准可以很简单：

- **只影响一个页面**：用路由中间件
- **影响一组页面**：路由中间件复用
- **影响所有页面**：才考虑全局中间件
- **逻辑轻量且高频**：适合全局
- **逻辑依赖页面特性**：更适合路由级

如果不知道怎么选，先问两个问题：  
这段逻辑是不是每个页面都必须执行？如果不是，别急着放全局。  
这段逻辑是不是跟当前页面强相关？如果是，优先放页面附近。

### 4. 常见误区

很多人一上来就写全局中间件，结果每次跳转都查权限、请求接口，页面切换一卡一卡的。  
还有一种错误是，把某个页面特有的判断放到全局里，后面别的页面也跟着受影响，维护成本很高。

### 老赵经验分享

老赵的习惯是：**能局部解决的，就别全局；能简单判断的，就别复杂判断。**  
你越早把中间件边界分清，后面页面扩展就越轻松。内容站和展示站页面多、逻辑并不复杂，最适合按职责拆开。

### 赵老师提醒

别把“全局”理解成“高级”。  
全局中间件不是越多越好，它只适合站点级公共逻辑。你用得越少、越克制，系统越稳定。

## 三、常见场景：登录校验、权限控制、访问跳转

中间件最实用的地方，不在于语法，而在于它能解决什么问题。下面这三类，几乎是所有 Nuxt 项目都会遇到的。

### 1. 登录校验：没登录就别进

这是最经典的场景。比如访问 `/profile`、`/order`、`/admin` 时，先检查是否有登录状态：

- 有：继续进入页面
- 没有：跳转到登录页
- 登录后再回来：保留原始访问地址

这个逻辑建议尽量简洁，不要在中间件里做复杂的身份验证。你只需要判断“当前有没有可用登录态”。更完整的认证流程，交给后端或认证系统去做；前端中间件负责“先拦一下”。

### 2. 权限控制：不同角色看到不同页面

权限控制比登录校验更进一步。比如：

- 游客只能看公开内容
- 普通用户能看个人中心
- 管理员才能看后台页
- 某些企业内页仅白名单账号可见

权限控制的核心是“角色判断”。你可以把用户角色、权限标识存在状态里，然后在中间件里读取并决定跳转。很多项目会把权限判断放在 `meta` 或统一配置中，这样页面越多，维护成本越低。

如果你做的是管理后台，通常会这样组织：

- 页面 `meta` 标记需要的角色
- 中间件统一读取当前用户角色
- 角色不匹配则跳到无权限页或首页

这比把权限条件写死在组件里要清楚得多。因为组件更关注展示，中间件更关注进入门槛，两者职责分开，代码才不乱。

### 3. 访问跳转：把老入口导到新入口

这是内容站、营销站特别常见的场景。比如新版页面上线后，旧链接还在流量里流转，这时候可以通过中间件做：

- 老 URL → 新 URL
- 默认空路径 → 推荐首页
- 某些地区访问 → 指定版本页
- 活动过期 → 跳转到常规页

这类跳转很适合在中间件里做，因为它发生在页面渲染之前，用户体验比较自然。  
如果你做的是产品展示站，旧活动页、旧落地页、旧专题页很容易出现这种情况，中间件就很适合拿来做“入口修路”。

比如一个内容站改版，旧地址 `/posts/xxx` 改成了 `/articles/xxx`，你可以在中间件里识别旧路径，直接重定向到新路径。这样既保住访问体验，也减少搜索和收藏入口失效的问题。

### 4. 具体判断原则

写中间件时，可以遵循一个简单顺序：

1. 先判断是否需要登录
2. 再判断角色权限
3. 最后判断是否跳转
4. 条件满足就放行，不满足就拦截

顺序不要乱。很多页面逻辑本来就是层层递进的，先过门槛，再看权限，再决定去向。  
如果顺序混了，后面自己也很难判断到底是哪一层把用户挡住了。

### 老赵经验分享

老赵最喜欢把这类逻辑画成“通行证流程图”。因为一旦开始写代码，判断会混在一起；但画成流程后，登录、权限、跳转这三件事一目了然，后面写起来就不容易乱。

### 赵老师提醒

权限判断不要只看前端状态。  
前端中间件能提升体验，但不能替代真正的服务端鉴权。尤其是敏感数据和管理后台，前端只是“拦一下”，不是“最终裁判”。

## 四、中间件如何与页面数据获取配合？

这一部分，是从“会写中间件”走向“会用中间件”的关键。

Nuxt 的强项之一是服务端数据获取。如果把中间件和数据获取配合好，就能做到：

- 先判断是否有资格访问
- 再请求页面数据
- 避免无效请求
- 减少闪烁和错误页

### 1. 推荐的协作顺序

比较稳妥的思路是：

**中间件先判断 → 再进入页面 → 页面里再做数据获取**

比如一个文章详情页：

- 如果文章已下架，先在中间件里判断并跳转
- 如果用户允许访问，再进入页面请求文章详情
- 页面再根据数据渲染内容

这样可以避免先请求再发现不能看，白白浪费一次请求。  
对于展示站来说，这个顺序尤其重要，因为页面多、内容多，任何无效请求累计起来都会影响整体性能。

### 2. 哪些情况适合先判断

以下情况特别适合中间件先拦：

- 明显无权限页面
- 已知不可访问资源
- 已过期活动页
- 需要切换版本的入口页

这类逻辑一般不需要等到页面数据完全回来才决定。只要身份、状态、时间条件已经明确，就可以先在中间件里处理掉。

### 3. 哪些情况不适合放到中间件

如果判断依赖大量后端数据，或者必须先拿到完整资源详情，通常更适合放在页面数据获取里，而不是中间件里。  
因为中间件应该轻，过重就会影响跳转速度。

简单说就是：

- **入口层判断**：中间件
- **页面内容判断**：数据获取
- **展示细节判断**：组件内部

### 4. 一个实用组合

你可以这样设计：

- 中间件：判断用户是否能进入
- 页面数据获取：获取页面主体内容
- 组件层：处理展示细节

这样职责分明，后面维护会舒服很多。  
也就是说，中间件不要抢页面的活，页面也不要把入口规则全吞掉。

### 老赵经验分享

老赵做内容页时，经常先在中间件里挡掉明显无效的访问，比如过期专题、错误入口、未授权页面。这样页面的数据获取压力就小很多。真正省性能的不是“少写代码”，而是“少做无效请求”。

### 赵老师提醒

不要把所有业务判断都前置到中间件。  
判断越多，越容易让路由逻辑变成一团线。中间件和页面数据获取要分工明确：一个管入口，一个管内容。

## 五、中间件实战：内容站的推荐跳转或访问拦截

Nuxt 很适合做内容站、博客站、产品展示站，因为这些站点通常都有一个共同点：**页面入口多、内容类型明确、跳转规则清晰。**  
中间件在这类项目里非常好用。

### 1. 场景一：新老内容页跳转

假设你做了一个内容站，旧版栏目页是 `/posts`，新版栏目页改成了 `/articles`。这时候可以通过中间件在访问旧地址时自动跳转：

- 旧栏目页 → 新栏目页
- 旧专题页 → 新专题页
- 旧活动页 → 推荐页

用户不会看到 404，也不会觉得站点坏了，体验更平滑。  
这在站点改版时很常见，尤其是已经上线一段时间的内容站，旧链接几乎一定会存在。

### 2. 场景二：推荐内容拦截

比如你想做一个“推荐阅读”逻辑：

- 新用户进入首页时，优先引导看热门专题
- 已阅读过某类文章的用户，优先跳到相关分类页
- 某些来源流量进站后，直接去指定落地页

这类场景不一定需要复杂推荐算法，甚至只靠简单条件就能完成。中间件就能承担这个“入口分流”的工作。  
对于展示站来说，这种分流很有价值，因为它能让不同来源的访客尽快进入最相关的内容。

### 3. 场景三：访问拦截

比如有些内容需要满足条件才可访问：

- 活动内容只在有效期内开放
- 专题页仅对登录用户开放
- 某些下载页需要确认用户身份

这时中间件可以先做粗拦截，不符合条件就直接跳到说明页或登录页。  
注意这里是“粗拦截”，不是最终鉴权。真正的敏感校验还是要交给服务端。

### 4. 一个简单的实战思路

你可以按下面流程实现内容站入口控制：

1. 定义需要拦截的页面规则
2. 在对应页面或全局中间件里判断路径
3. 检查用户状态、时间状态、活动状态
4. 满足条件则放行，不满足则重定向
5. 保持逻辑轻量，避免重复请求

如果想做得更稳一点，还可以把规则抽成配置表：哪些路径需要登录、哪些路径需要重定向、哪些路径在活动期间开放。这样后面改规则时，只改配置，不必到处找代码。

### 老赵经验分享

内容站最值钱的不是“页面写得花”，而是“入口分发顺”。老赵见过很多站点首页做得很漂亮，但用户一进来不知道该去哪；后来只靠中间件把不同用户导向不同内容页，转化和停留就明显顺了。

### 赵老师提醒

推荐跳转别做得太激进。  
如果你把所有用户都硬塞到某一个页面，用户会觉得站点不透明。推荐要有边界，拦截要有理由，最好让用户知道“为什么跳过去”。

## 六、开发注意事项：避免在中间件里做重活

这一节是避坑重点。中间件写不好，Nuxt 项目就容易出现页面卡顿、跳转混乱、调试困难等问题。

### 1. 中间件要轻

中间件最核心的原则就是：**快进快出。**  
只做必要判断，不做复杂业务。

你可以把它当作“决策点”，而不是“执行中心”。

### 2. 不要在里面做重请求

比如：

- 请求大列表
- 请求多个接口再拼装
- 等待很多异步操作完成
- 进行复杂计算后再跳转

这些都不适合放在中间件里。  
如果真需要数据，请尽量让中间件只拿“最小判断数据”，其余放到页面里完成。

### 3. 避免逻辑重复

很多页面都需要登录判断时，不要每个页面复制一份中间件逻辑。可以考虑：

- 提取公共判断函数
- 复用统一的中间件
- 把页面级差异参数化

这样后面修改规则时，不用到处改。  
这也是 Nuxt 实战里很重要的一点：约定式开发不是把代码写散，而是把职责摆正。

### 4. 注意首屏与跳转体验

由于中间件会影响页面进入速度，如果逻辑慢，用户会觉得“点了没反应”。因此要尽量：

- 判断条件少而明确
- 跳转动作果断
- 不要多层嵌套
- 不要反复重定向

### 5. 检查清单

每次写中间件前，可以问自己这五个问题：

- 这件事是不是必须在进入页面前决定？
- 这个判断能不能更简单？
- 会不会导致重复请求？
- 会不会让所有页面都变慢？
- 失败时跳到哪里，用户是否能理解？

如果有两个以上答不清楚，说明这段中间件可能还没想明白，先别急着写。

### 老赵经验分享

老赵一直觉得，中间件写得好不好，差别不在“写没写”，而在“有没有克制”。真正成熟的写法，往往都很朴素：少判断、少请求、少分支，但每个分支都清楚。

### 赵老师提醒

如果你发现中间件越来越长，十有八九说明它开始越界了。  
这时候不要硬撑，先拆分职责，再看哪些逻辑该移回页面或服务端。

## 本章小结：把入口控制好，Nuxt 才更顺

中间件在 Nuxt 里不是装饰品，而是非常实用的流程控制工具。  
你可以把它理解成“页面入口前的守门人”，负责做登录校验、权限控制、访问跳转和轻量拦截。

这一章你要真正记住的，不是某个语法点，而是这几个判断原则：

- **路由中间件**适合局部页面控制
- **全局中间件**适合站点级公共逻辑
- **登录、权限、跳转**是最常见的使用场景
- **中间件和数据获取要分工明确**
- **内容站、展示站特别适合用中间件做入口分发**
- **中间件要轻，不要做重活**

如果你已经会 Vue3，那么到了 Nuxt 这里，关键不是“重新学一套框架”，而是把原来熟悉的路由守卫思维，升级成 Nuxt 的约定式页面控制思维。  
下一步，你就可以把中间件和页面布局、数据获取、SEO 联动起来，真正做出一个结构清晰、体验稳定的 Nuxt 内容站。

### 老赵经验分享

老赵做 Nuxt 项目时，最先梳理的往往不是页面，而是入口规则。页面是给人看的，入口是给流程走的。入口顺了，整个站就顺了。

### 赵老师提醒

别让中间件变成“什么都想管”的地方。  
它只负责把关，不负责包办。把边界守住，Nuxt 才好维护。

# 第8章 SEO 与 meta 配置：让 Nuxt 更适合内容站

如果你会 Vue3，就已经具备了组件、响应式、状态管理这些基本功。但当项目从内部系统转向内容站、展示站、官网、博客时，问题就变了：页面不仅要能用，还要能被搜到、被分享、首屏能快点出来。

这正是 Nuxt 的优势。它把服务端渲染、页面生成、路由和头部信息管理整合到一套更适合网站交付的方案里。对内容站和展示站来说，SEO 不是附加项，而是基础能力。

## 为什么 Nuxt 更适合做 SEO 友好的页面？

结论很简单：**Nuxt 天然支持服务端渲染和页面级 meta 管理，所以更适合 SEO 友好页面。**

纯 Vue SPA 通常先返回一个空壳 HTML，再靠 JS 拉数据和渲染页面。交互没问题，但搜索引擎抓取、首屏展示、社交分享卡片都会受影响。Nuxt 可以先在服务端把页面内容和 head 信息生成好，用户和爬虫拿到的是更完整的 HTML。

对博客、产品官网、课程页、活动页这类站点，这个差异非常关键。你可以把它理解成：

- **Vue3** 是前端能力本身
- **Nuxt** 是在 Vue3 之上，把“页面交付”做完整

所以 Nuxt 不是替代 Vue，而是把 Vue 从“组件框架”扩展成“更适合做网站交付的框架”。如果你做的是内容站，页面价值不只是交互，更在于“被发现”。

从内容分发角度看，Nuxt 的页面生成方式也很适合这件事。首页、列表页、详情页、专题页都可以按需生成，既保留 Vue 的开发体验，又提升可抓取性和首屏表现。这就是 Nuxt 特别适合做内容站的原因。

### 老赵经验分享
我做内容站时，最怕的不是页面不好看，而是“页面很好看但搜不到”。很多团队前期只盯交互，等上线才补 SEO，往往要返工。Nuxt 的好处是：你一开始就能把标题、描述、分享信息和首屏渲染纳入开发流程。

### 赵老师提醒
不要把“用了 Nuxt”理解成“SEO 自动满分”。Nuxt 只是基础更好，真正的收录、排名和分享表现，还要看内容质量、链接结构、标题策略和页面性能。

## 页面标题、描述、关键词等 meta 配置方法

页面 meta 最基础的就是：

- 标题 `title`
- 描述 `description`
- 关键词 `keywords`
- 视口 `viewport`
- 机器人指令 `robots`

在 Nuxt 里，关键不是背 API，而是记住一个原则：**页面头部信息要跟页面内容绑定，而不是全站写死。**

很多人一开始会把所有页面都写成同一个标题，比如“我的网站”。看似省事，实际上不利于搜索和分享，因为用户和搜索引擎都需要知道当前页面到底讲什么。

比如：

- 首页标题：`全栈老赵讲 Nuxt 基础：Vue 开发者的服务端渲染入门`
- 章节页标题：`第9章 SEO 与 meta 配置：让 Nuxt 更适合内容站`

描述要简洁明确，能概括页面内容；关键词适量即可，不要堆砌。

### 实战写法思路

不同页面的 meta 策略要区分开：

- **首页**：品牌、定位、入口
- **列表页**：分类、专题、内容聚合
- **详情页**：标题、摘要、发布时间
- **专题页**：主题、标签、精选内容

在 Nuxt 里，常见做法是在对应页面配置 head，让它和页面数据同步。这样内容变了，meta 也能跟着变。

标题结构尤其重要。一个好的标题，既要概括页面，又要让用户一眼知道它属于什么场景。内容站首页可以用“品牌词 + 主题词 + 价值主张”，详情页则用“文章标题 + 栏目名”，统一风格，也方便搜索识别。

### 老赵经验分享
我写内容站时，习惯先把页面分成三类：入口页、聚合页、内容页。三类页面的 meta 策略完全不同。比起“全站一个标题模板”，这种方式更符合用户搜索习惯。

### 赵老师提醒
meta 不是越复杂越好。优先保证一致性、准确性和可读性。标题里别塞一长串词，页面看起来像关键词堆砌。

## 动态 meta 的写法：列表页、详情页、专题页

真正的内容站，页面大多是动态内容，所以 meta 也不能写死，而要跟数据变化。

### 1）列表页：强调聚合主题

列表页常见于分类页、文章列表页、产品列表页，重点不是每一条内容，而是这个页面聚合了什么。

例如：

- 标题：`Nuxt 教程列表 - 全栈老赵`
- 描述：`整理 Nuxt 入门、布局、路由、数据获取和 SEO 实战文章，适合 Vue3 开发者快速上手。`

用户一看就知道这是专题集合，而不是单篇文章。

### 2）详情页：强调单篇内容

详情页要围绕具体内容来写，尤其是文章页和产品页。

例如文章详情页：

- 标题：`第9章 SEO 与 meta 配置：让 Nuxt 更适合内容站`
- 描述：`本章讲解 Nuxt 的 SEO 优势、meta 配置、Open Graph 分享信息以及内容站优化思路。`

如果是产品页，就要突出卖点、适用场景、价格区间等信息，方便用户快速判断。

### 3）专题页：强调主题和精选

专题页一般围绕一个主题组织内容，比如“新手入门专题”“春季活动专题”“推荐文章合集”。meta 的重点是让用户一眼知道：这里不是普通列表，而是整理过的主题入口。

### 动态 meta 的判断标准

你可以用这四个问题自检：

1. 标题是否能单独看懂？
2. 描述是否概括了页面核心内容？
3. 页面换了数据，meta 是否会跟着变？
4. 是否避免了标题和描述重复？

这四点基本成立，你的动态 meta 就算合格。

如果你前面已经接触过页面和动态路由，这里会更好理解：动态页面不仅是内容变化，头部信息也应该随内容一起变化。这正是 Nuxt 约定式开发和页面级管理的价值。

### 老赵经验分享
做内容站时，我会先按“入口页、聚合页、内容页”去设计 meta。这样比全站套模板更有效，也更符合搜索和分享场景。

### 赵老师提醒
动态 meta 不等于复杂 meta。先保证准确、统一、可读，再考虑细化。别把标题写成关键词清单。

## Open Graph 和社交分享信息的基础配置

很多人只盯搜索引擎，却忽略社交分享。其实在内容站和展示站里，朋友圈、社群、IM 工具里的卡片展示也很重要。

Open Graph 的作用很简单：**让页面在被分享时，显示更完整、更清晰的卡片信息。**

基础信息通常包括：

- `og:title`
- `og:description`
- `og:image`
- `og:url`
- `og:type`

文章页适合用封面图，产品页适合用主视觉。它的价值在于：链接被转发出去时，卡片更清楚、更可信，也更容易提高点击率。

### 一个实用原则

Open Graph 不必花哨，但必须一致：

- 标题和页面一致
- 描述和页面一致
- 图片清晰且比例合适
- 链接地址规范

尤其是图片，尽量统一尺寸和清晰度，不然不同平台裁切后容易出现文字被截断、主体被裁掉的问题。

如果是内容站，建议把封面图也纳入页面设计的一部分。也就是说，文章内容、标题、摘要、分享图要尽量形成一套完整表达，而不是各写各的。对展示站来说也是一样，首页主视觉、产品图、介绍文案最好保持同一风格。

### 老赵经验分享
内容站的传播，很多时候不是靠搜索，而是靠分享。一个清楚的标题、一张像样的图、一个准确的摘要，往往比花哨特效更有用。

### 赵老师提醒
分享图不要偷懒。图片太小、太糊，或者内容不相关，都会直接影响点击意愿。SEO 之外，分享体验也是内容分发的一部分。

## SEO 实战：内容站和展示站常见优化点

讲完配置，再看落地。Nuxt 做内容站或展示站，SEO 优化不能只停在 head。

### 1）保持语义清晰的结构

页面标题层级要清楚，正文结构要有逻辑：

- 一个主标题
- 若干二级标题
- 每段只讲一个点

这样用户更容易读，搜索引擎也更容易理解页面主题。不要把文章写成一大段碎片，那样不利于阅读，也不利于抓取。

### 2）让首屏尽快可见

首屏体验影响停留，也影响搜索表现。核心内容、标题、摘要、主视觉，尽量提前呈现，不要让用户先看到大面积空白。

对内容站来说，首屏最重要的不是炫技，而是“先把有价值的信息亮出来”。Nuxt 的服务端渲染在这里很有价值：页面内容和基础 meta 可以先输出，用户打开就能看到主要信息。

### 3）控制重复内容

内容站容易出现列表分页、标签页、专题页带来的相似页面，这时要注意：

- 避免标题重复
- 避免描述重复
- 同一内容不要有太多入口版本

先想清楚每种页面的职责，不要让它们看起来像同一页的不同副本。

### 4）给图片和链接留出可理解的信息

图片要有替代信息，链接文字尽量明确，避免“点击这里”这种空泛表达。  
“查看 Nuxt 页面布局示例”就比“点击这里”清楚；“产品主图”配合说明，也比一张没上下文的图更好理解。

### 5）围绕转化目标优化

内容站关注阅读、收藏、传播；展示站关注咨询、了解、点击。你在写标题和描述时，就要把目标想清楚。比如：

- 博客文章页：突出主题、价值、适用人群
- 产品展示页：突出卖点、解决什么问题、下一步怎么联系
- 专题页：突出精选、合集、系列内容

SEO 不只是让页面被找到，更是让用户找到后愿意继续往下看。

### 老赵经验分享
我做内容站时，通常只盯三个词：**唯一、清楚、稳定**。内容唯一，标题描述清楚，结构和链接稳定，基本就不会太差。

### 赵老师提醒
别把 SEO 只理解成“给搜索引擎看”。真正优秀的 SEO 页面，本质上是给人看的好页面。用户看得懂、愿意停留、愿意分享，搜索引擎自然更容易认可。

## 页面可访问性与首屏体验的基础思路

最后一个容易被忽略的点，是可访问性。内容站和展示站不只是“好看”，还要“好用”。

至少要关注这几件事：

- 标题层级是否合理
- 按钮和链接是否有明确文本
- 图片是否有替代说明
- 首屏加载是否足够快
- 页面内容是否能在无 JS 或弱网络下尽量可读

Nuxt 的服务端渲染和页面生成能力，正好帮助你提升首屏可见性。对博客、文档、官网这类页面来说，这一点尤其重要：用户一打开就能看到标题、摘要、正文，体验会稳很多。

可访问性和 SEO 往往是一起推进的。你把结构写清楚，把内容组织好，搜索引擎更容易理解，用户也更容易使用。换句话说，这不是额外负担，而是内容站质量的一部分。

### 老赵经验分享
做内容分发类页面，我最看重“第一眼体验”。用户不需要等半天才看到正文，也不需要猜这页到底讲什么。首屏清晰了，后面的转化和传播才有基础。

### 赵老师提醒
可访问性不是额外负担，它往往和 SEO 同向优化。你把结构写清楚，把内容组织好，很多问题会自然减少。

## 小结：把 SEO 当成 Nuxt 页面设计的一部分

这一章你只要记住一句话：**在 Nuxt 里，SEO 不是后期补丁，而是页面设计的一部分。**

从 Vue3 过渡到 Nuxt 后，要尽快建立这样的思维：

- 页面不仅有组件，还要有 head
- 内容不仅要渲染，还要可被抓取
- 分享不仅是复制链接，还要有卡片信息
- 页面不仅要能打开，还要尽量快、清楚、稳定

如果你正在做内容站或展示站，下一步最值得练习的，就是给首页、列表页、详情页、专题页分别配置不同的标题、描述和分享信息，并检查首屏体验是否足够清晰。你也可以顺手把页面结构、图片替代信息、链接文本一起整理好，这样一轮下来，站点基础质量会明显提升。

### 最后练习建议

你可以用一个小项目来落地这章内容：

1. 做一个博客首页
2. 做一个文章列表页
3. 做一个文章详情页
4. 给每个页面配置不同 meta
5. 加上 Open Graph 分享信息
6. 检查标题、描述、封面图是否统一

做完之后你会发现：Nuxt 的优势，不只是“能写 Vue 页面”，而是它真的更适合把页面做成一个能传播、能收录、能落地的产品。

### 老赵经验分享
真正把 Nuxt 用熟的人，不会只关心代码能不能跑，还会关心“这页出去以后会发生什么”。能不能被搜到，能不能被分享，能不能让用户第一时间看懂，这些才是内容站的核心问题。

### 赵老师提醒
下一步别停留在理论，直接动手给你的首页和详情页补上 meta、OG 和首屏优化。SEO 这件事，越早做越省事。Nuxt 做内容站的优势之一，就是它能把页面生成、服务端渲染和头部信息管理连成一体，让你更容易做出真正可传播的网站。

# 第9章 静态资源、构建与部署：把项目真正发布出去

前面几章走到这里，Nuxt 项目已经有了页面、布局和数据能力，但很多同学会卡在最后一步：**本地跑得很好，一上线就出问题**。图片丢了、路径错了、SEO 没了、环境变量读不到，甚至首页直接 500。  
所以这一章不再只讲“怎么写”，而是讲“怎么发出去”。老赵一直觉得，**一个前端项目能不能顺利上线、上线后稳不稳，才是真正检验你有没有掌握框架基础的地方**。

Nuxt 特别适合内容站、博客、产品展示站、文档站，因为它把“页面、路由、SEO、构建、发布”连成了一条线。你要理解的，不只是组件怎么拼，而是：**静态资源怎么放、构建时发生了什么、生产环境和开发环境差在哪、不同部署方式适合什么场景**。这章我们就把这些事情讲清楚，尽量讲得短一点、实一点。

---

## 10.1 静态资源与 `public`、`assets` 的使用差异

先回答最常见的问题：**图片、字体、图标、样式文件，到底放哪？**

在 Nuxt 里，`public` 和 `assets` 不是一回事。

### 1）`public`：原样公开，直接访问
`public` 目录里的文件会被直接对外提供，不参与构建处理。比如：

```bash
public/
  favicon.ico
  images/logo.png
  robots.txt
```

可以直接这样引用：

```html
<img src="/images/logo.png" alt="Logo" />
<link rel="icon" href="/favicon.ico" />
```

它适合放站点图标、robots.txt、分享图这类“路径固定、无需打包加工”的内容。

### 2）`assets`：参与构建，交给打包工具处理
`assets` 更适合放要被构建处理的资源，比如背景图、字体、全局样式：

```bash
assets/
  styles/main.scss
  images/banner.jpg
  fonts/inter.woff2
```

样式里常这样引用：

```scss
.hero {
  background-image: url('~/assets/images/banner.jpg');
}
```

打包工具会帮你处理路径、压缩和缓存哈希，生产环境更稳。

### 一个实用判断
- **不需要编译处理、路径固定、直接公开的**，优先放 `public`
- **需要参与打包优化、被样式或模块引用的**，优先放 `assets`

### 老赵经验分享
老赵做内容站时，最常用的分法就是：**Logo、favicon、robots.txt 放 `public`，页面背景图、样式变量、字体放 `assets`**。边界清楚，排查问题会快很多。

### 赵老师提醒
不要把“能访问”理解成“应该放 `public`”。**适合构建处理的资源，放到 `assets` 往往更稳**，尤其是样式里引用的图片和字体。

---

## 10.2 图片、字体、样式怎么组织，项目才不乱

资源一多，项目就容易乱，所以最好从一开始就建立规范。

### 一套实用的资源组织方式

```bash
public/
  favicon.ico
  robots.txt
  og/
    home.jpg

assets/
  styles/
    main.scss
    variables.scss
    reset.scss
  images/
    hero/
      banner.jpg
    common/
      arrow.svg
  fonts/
    inter.woff2
```

### 推荐原则

#### 1）样式分层
- `reset.scss`：基础重置
- `variables.scss`：颜色、间距、字号变量
- `main.scss`：全局入口样式

在 `nuxt.config.ts` 中引入：

```ts
export default defineNuxtConfig({
  css: ['~/assets/styles/main.scss']
})
```

这样就不必在每个页面重复引基础样式，也更利于维护。

#### 2）图片按场景分类
- `hero/`：首页首屏、Banner
- `common/`：通用图标、装饰图
- `article/`：文章封面图
- `product/`：产品图

内容站和展示站后期最容易增长的就是封面图和分享图，分类不清楚会很痛苦。

#### 3）字体统一管理
字体文件建议放 `assets/fonts`，样式中统一声明 `@font-face`。如果字体文件小且稳定，也可以放 `public`，但要看是否需要构建优化。

### 实战建议
如果你做的是内容站或展示站，资源结构最好跟页面结构同步，比如：

```bash
assets/images/home
assets/images/about
assets/images/products
```

页面改版时，你会很清楚该去哪里找素材。

### 老赵经验分享
老赵最怕的不是代码多，而是“没人管资源”。项目早期看着无所谓，后面一旦开始做 SEO 图、社交分享图、专题图，资源没规范，改一个地方要翻半天。

### 赵老师提醒
资源管理不是“美观问题”，而是**部署稳定性问题**。很多上线后资源 404，其实不是代码写错，而是目录策略没定好。

## 10.3 构建与打包流程：开发环境和生产环境差在哪

很多人以为“开发能跑 = 上线能跑”，这在 Nuxt 里很危险。  
**开发环境**和**生产环境**的差异，主要体现在构建优化、运行方式、资源加载和环境变量。

### 1）开发环境：关注开发效率
开发阶段一般执行：

```bash
npm run dev
```

特点是：

- 代码修改后热更新
- 错误提示更详细
- 不做极致优化
- 方便调试、看日志

这个阶段重点验证的是“功能是否正确”和“页面结构是否合理”。

### 2）生产环境：关注稳定和性能
上线前通常执行：

```bash
npm run build
npm run preview
```

生产环境会做这些事情：

- 组件和依赖打包
- CSS、JS 压缩
- 资源文件哈希化
- 服务端渲染或静态生成
- 更严格的错误处理

### 构建流程怎么理解
Nuxt 构建会把页面、组件、路由、布局、数据请求和样式资源整理成适合部署的产物。  
如果是 SSR，产物会包含服务端运行所需内容；如果是静态生成，则会输出可直接托管的静态文件。

所以要记住：**构建不是简单压缩，而是在为运行环境做重组**。某些开发环境里“看起来可以”的写法，到了构建阶段会暴露问题，比如路径别名不规范、运行时变量使用不当、某些 API 只能在客户端执行。

### 先判断项目类型
- **需要动态数据、用户交互、服务端渲染**：偏 Node 服务部署
- **内容固定、更新频率低**：可以考虑静态站
- **希望省心、自动扩容**：考虑平台部署

### 老赵经验分享
老赵有个习惯：**每次改完关键页面，都会跑一次 build 再预览**。开发环境看不出来的问题，常常在构建时才暴露，比如路径别名、资源引用和环境变量读取方式。

### 赵老师提醒
别把 build 当形式主义。**真正上线前，必须至少完整跑一遍构建流程**，否则你是在把问题留给用户。

## 10.4 常见部署方式：Node 服务、静态站、平台部署怎么选

Nuxt 的部署没有唯一答案，要看项目类型和团队条件。最常见有三种方式。

### 1）Node 服务部署
适合：

- 需要 SSR
- 需要动态数据
- 需要登录态、接口协同
- 内容更新频繁

一般做法是把 Nuxt 作为 Node 应用运行起来，再通过 Nginx、PM2、Docker 等管理。

**优点：**
- 灵活
- 支持服务端渲染
- 更适合复杂应用

**缺点：**
- 运维成本更高
- 对服务器环境要求更高

### 2）静态站部署
适合：

- 博客
- 文档站
- 产品展示站
- 内容几乎不需要服务端逻辑

如果使用静态生成策略，最终得到的是一组静态文件，可以直接放到 Nginx、OSS/CDN、GitHub Pages 或静态托管平台。

**优点：**
- 部署简单
- 性能好
- 成本低

**缺点：**
- 动态能力有限
- 某些运行时数据需要额外处理

### 3）平台部署
比如部署到支持 Nuxt 的云平台、容器平台或前端托管平台。适合想少折腾运维的团队，平台通常会处理构建、发布、域名和 HTTPS。

**优点：**
- 上手快
- 运维压力小
- 适合个人项目和小团队

**缺点：**
- 对平台依赖更高
- 成本和限制要提前评估

### 怎么选？
如果你做的是**内容站或展示站**，老赵通常建议：

- 内容稳定：静态站
- 需要服务端个性化：Node 服务
- 想快速上线：平台部署

### 老赵经验分享
老赵做展示站时，最看重两个词：**简单和稳定**。能静态化的尽量静态化，能放 CDN 的尽量放 CDN。这样便宜，也省心。

### 赵老师提醒
别一上来就追求“最高级”的部署方式。**适合项目的才是最好的**，部署方案选错了，后面维护会很痛苦。

## 10.5 上线前检查清单：路由、资源、SEO、环境变量怎么查

上线前别只看首页能不能打开，真正的检查要系统一点。  
老赵建议你每次发布前都过一遍下面这份清单。

### 1）路由检查
- 首页、列表页、详情页是否都能访问
- 动态路由是否匹配正确
- 刷新后是否 404
- 子路径部署时 base 路径是否正确

尤其是部署到子目录时，很多同学会忽略基础路径配置，结果页面能进，资源和跳转却全乱了。

### 2）资源检查
- 图片是否能正常加载
- `public` 中资源路径是否正确
- `assets` 中引用的资源构建后是否可用
- 字体和图标是否跨页面正常显示

### 3）SEO 检查
- 每个页面是否有独立 title、description
- 是否有正确的 og 图和分享信息
- 重要页面是否支持服务端输出 meta
- 是否设置了 robots、sitemap（如果项目需要）

对内容站和展示站来说，SEO 不是锦上添花，而是基础能力。

### 4）环境变量检查
- 开发和生产环境变量是否一致命名
- 前端可访问变量是否遵守约定前缀
- API 地址是否切到正式环境
- 密钥类信息是否误打包到前端

很多线上事故不是代码逻辑错，而是“本地连测试环境，线上连不到正式接口”。

### 5）功能检查
- 表单提交是否正常
- 异步数据是否报错
- 空状态是否显示正确
- 404 页面是否友好

### 一个实用发布流程
你可以把上线前检查做成固定流程：

1. 本地 `build`
2. 本地 `preview`
3. 打开首页、详情页、错误页
4. 看资源是否 404
5. 检查控制台是否报错
6. 检查 meta 和分享图
7. 再发布

### 老赵经验分享
老赵最怕“我在本地看着没问题啊”。很多问题不是功能错，而是**上线后路径、缓存、环境变量、CDN 配置**出了问题。上线前检查，就是把事故消灭在发布前。

### 赵老师提醒
不要只用“首页打开了”来判断发布成功。**真正的上线成功，是核心页面、资源、SEO、环境变量都正常**。

5. 统一管理环境变量和日志

**优点：**
- 灵活
- 支持动态内容
- 更适合复杂业务

- 首页：展示最新文章和专题

- 构建：生成可部署产物
- 发布：静态站或 Node 服务二选一

# 第10章 完整实战：做一个 Nuxt 博客首页或产品展示站

到了这一章，咱们把前面学过的页面、布局、路由、数据获取、SEO 和部署串起来，做成一个真正能落地的小项目。  
我建议你把它理解成两类最常见的内容型站点：**博客首页**，或者**产品展示站**。这两类项目都很适合 Nuxt：结构清晰、内容驱动、SEO 重要，也最能体现 Nuxt 的约定式开发优势。

如果你是从 Vue3 过渡过来的，会发现 Nuxt 最大的变化不是语法，而是开发思路。以前更像在拼页面；现在是在搭站点，页面怎么长、路由怎么来、数据什么时候取、布局怎么统一，Nuxt 都已经预设好了路线。你要做的，是顺着这条路线把项目搭扎实。

## 一、项目目标拆解：先明确你要做的是博客首页还是产品展示站

先别急着写代码，先把目标说清楚。很多 Vue 开发者一上来就想先搭组件，结果做到一半发现路由不顺、布局混乱、数据不好接，项目就容易散。Nuxt 的好处就在于：你先想明白页面角色，后面大部分结构都能顺着约定自然落地。

这次我们把项目收束成一个**可交付的小站点**，你可以二选一：

### 方案 A：博客首页
适合展示文章内容、知识输出、技术分享。最终页面清单可以是：

- 首页
- 文章列表页
- 文章详情页
- 关于页

### 方案 B：产品展示站
适合展示产品卖点、案例和转化入口。最终页面清单可以是：

- 首页
- 产品列表页
- 产品详情页
- 联系我们页

不管你选哪一个，本章都按“**首页 + 列表页 + 详情页 + 公共布局 + SEO**”这个闭环来做。这样你学到的就不是零散功能，而是一套完整的 Nuxt 小项目思路。

### 1. 这类站点为什么适合 Nuxt

博客和展示站本质上都属于**内容站或展示站**。它们的核心不是复杂交互，而是**清晰展示信息、方便检索、利于 SEO**。这正是 Nuxt 最擅长的场景。  
尤其当页面内容需要被搜索引擎收录时，Nuxt 的页面生成方式、服务端数据获取和 meta 配置，会比纯前端 SPA 更顺手。

### 2. 页面最终要解决什么问题

做这类站点，你不能只想着“页面好不好看”，还要想：

- 用户进来第一眼能不能看懂站点主题
- 内容能不能快速进入列表和详情
- 页面标题和描述能不能被搜索引擎识别
- 数据为空时页面会不会直接崩掉

这几个问题想明白了，项目就不会跑偏。

### 老赵经验分享

我做内容型站点时，先画的不是效果图，而是“信息层级图”：哪些先看、哪些后看、哪些需要点进去。这个图一出来，页面结构、路由结构、数据结构就都清楚了。

### 赵老师提醒

不要把展示站做成业务后台的思路。展示站的关键是阅读体验和内容组织，不是把所有功能都塞进去。越克制，越像一个成熟项目。

## 二、项目架构设计：目录、组件、布局、路由怎么组织？

Nuxt 最有价值的地方之一，就是它的**约定式开发**。你不用手写一堆配置去声明路由和页面关系，只要把文件放到对应目录里，Nuxt 就会自动帮你生成页面和路由。

### 1. 目录怎么分

以一个简单的博客或展示站为例，可以这样组织：

- `pages/`：页面文件
- `components/`：可复用组件
- `layouts/`：布局文件
- `content/` 或 `data/`：内容数据
- `assets/`：需要构建处理的静态资源
- `public/`：直接公开访问的静态资源

页面负责“去哪儿看”，组件负责“长什么样”，布局负责“整体骨架”，数据目录负责“内容从哪来”。这就是 Nuxt 约定式开发的价值：不是限制你，而是帮你把项目组织好。

### 2. 布局先行

如果网站有统一的头部、底部、导航栏，就先做布局。比如：

- 默认布局：适合首页、列表页、详情页
- 简化布局：适合登录页或活动页

Nuxt 的布局系统很适合这类项目。你把公共骨架放在 `layouts/default.vue`，页面只负责内容部分，整个项目会很干净。头部导航改一次，所有页面一起生效，不用每个页面重复改。

### 3. 路由由文件决定

在 Vue 里，路由通常是单独配置的；而在 Nuxt 里，页面文件本身就代表路由。  
例如：

- `pages/index.vue` 对应首页
- `pages/posts/index.vue` 对应文章列表页
- `pages/posts/[slug].vue` 对应文章详情页

这就是 Nuxt 的典型约定式开发体验：**先定文件，再得路由**。你只要把页面放对位置，路由就会自动生成，开发效率会明显提升。

### 4. 建议的最终工程结构

你可以把这个小项目组织成下面这样：

- `pages/index.vue`：首页
- `pages/posts/index.vue`：文章列表页
- `pages/posts/[slug].vue`：文章详情页
- `pages/about.vue`：关于页
- `layouts/default.vue`：默认布局
- `components/SiteHeader.vue`：头部导航
- `components/SiteFooter.vue`：底部信息
- `components/PostCard.vue`：文章卡片
- `components/HeroBanner.vue`：头图区
- `data/posts.ts`：示例文章数据

这样一来，项目骨架非常清楚，后面写页面就不会乱。

### 老赵经验分享

从 Vue3 过渡到 Nuxt 时，最容易困惑的就是“为什么我没配路由，页面却能访问”。别慌，这不是魔法，是 Nuxt 把常见约定帮你做了。你要学会利用它，而不是和它对着干。

### 赵老师提醒

目录不要乱堆。页面、组件、布局、数据一定要分开，否则项目一复杂，你自己都很难判断一个文件该放哪儿。越早建立目录习惯，后面越省事。

## 三、首页搭建：头图、推荐区、列表区、底部信息怎么排？

首页是整个项目的门面，也是最能体现“信息组织能力”的地方。  
无论你做博客还是产品展示站，首页都要回答一个问题：**用户进来后，能不能迅速知道你是谁、你做什么、下一步看什么**。

### 1. 头图区：先给第一印象

头图区一般包括：

- 标题
- 简短副标题
- 核心按钮
- 背景图或视觉元素

博客首页可以写成：

- 标题：全栈老赵的 Nuxt 学习笔记
- 副标题：从 Vue3 走向服务端渲染与约定式开发
- 按钮：查看最新文章

产品展示站则可以强调：

- 标题：专注内容生产与展示
- 副标题：高效搭建企业官网、产品页、案例页
- 按钮：查看产品方案

头图区的任务不是“炫”，而是“说清楚”。一句主题明确的标题，比一堆装饰性文案更有用。

### 2. 推荐区：把重点内容先推出来

推荐区的作用是避免首页只是信息堆砌。  
你可以放：

- 最新文章
- 热门文章
- 精选产品
- 核心案例

这里建议把最值得访问的内容优先展示出来，减少用户寻找成本。对于内容站来说，推荐区就是你对用户的第一轮引导。

### 3. 列表区：用结构承接内容

列表区适合用卡片展示。卡片里建议包含：

- 标题
- 摘要
- 封面图
- 发布时间
- 标签或分类

这部分可以直接复用组件，比如 `PostCard`。这样页面会更清晰，也更符合 Nuxt 的组件化思路。你不用在页面里写一大堆重复结构，而是让组件去承接内容展示。

### 4. 底部信息：别忽略收尾

底部信息可以包括：

- 版权声明
- 联系方式
- 社交链接
- 站点说明

首页不是只要“好看”，更重要的是让用户知道下一步怎么走。一个完整的首页，应该像一条清晰的参观路线，而不是一个没有出口的展厅。

### 老赵经验分享

我做首页时，喜欢遵循“先结论，再展开”的原则。先告诉用户这站点是干嘛的，再给重点，再给详细列表。这样内容站的阅读路径会非常自然。

### 赵老师提醒

首页不要把所有内容平均铺开。内容越平均，重点越模糊。首页一定要有主次，不然用户看完也不知道该点哪里。

## 四、列表页与详情页联动：动态路由和数据获取怎么配合？

这是 Nuxt 很关键的实战点。  
博客和展示站一定会有“列表 → 详情”的链路，而这正好适合用动态路由来实现。

### 1. 列表页负责入口

比如文章列表页展示所有文章，用户点击某一条后进入详情页。  
在 Nuxt 里，你可以把详情页写成动态路由文件，例如：

- `pages/posts/[slug].vue`

这样当用户访问 `/posts/nuxt-basic` 或 `/posts/fullstack-note` 时，就会进入对应文章详情。动态路由的好处是，页面模板只有一份，但可以承接很多内容。

### 2. 详情页负责展示内容

详情页要做的事很明确：

- 根据路由参数拿到文章标识
- 请求对应内容
- 渲染标题、正文、作者、时间等信息

如果你做的是产品展示站，也可以是：

- 根据产品 slug 获取产品信息
- 展示介绍、规格、案例、联系方式

这里建议你尽量统一参数风格，比如博客统一用 `slug`，产品统一用 `slug` 或 `id`，不要一会儿一个写法。这样后续维护和跳转会更清楚。

### 3. 数据获取要考虑首屏

Nuxt 的一个重要优势，就是可以做服务端数据获取。  
这对列表页、详情页特别有帮助，因为页面内容可以更快地呈现给搜索引擎和用户，首屏体验也更稳定。

你不需要在客户端等很久再把内容补上，而是尽量让页面在服务端就拿到数据。对于内容站来说，这一点非常重要，因为页面的核心价值就在内容本身。

### 4. 一个简单的联动思路

你可以这样设计：

- 首页展示 3 条精选文章
- 列表页展示全部文章
- 详情页根据 `slug` 拉取单篇文章
- 文章卡片点击后跳转到详情页
- 详情页顶部和底部都保留返回列表的入口

这样用户路径就很完整：**首页发现内容 → 列表页浏览内容 → 详情页深入阅读**。

### 老赵经验分享

详情页最怕两件事：参数不稳定，空数据没处理。你在设计动态路由时，最好先明确 slug 或 id 的规则，后面数据接口和页面跳转都会轻松很多。

### 赵老师提醒

动态路由不是“文件名加中括号”这么简单，更重要的是统一参数规范。别今天用 id，明天用 slug，后面自己维护会很痛苦。

## 五、SEO 与交互完善：标题、描述、分享信息、空状态怎么处理？

内容站和展示站，SEO 基本是标配。  
Nuxt 在 SEO 这块比纯前端 SPA 更顺手，尤其适合做首页、列表页、详情页这种需要被搜索引擎收录的页面。

### 1. 每个页面都要有自己的标题和描述

首页、列表页、详情页的 meta 信息不应该都一样。  
你至少要根据页面内容设置：

- `title`
- `description`
- `keywords`（按需）
- 分享图片

这样无论是搜索结果，还是社交分享，页面都更专业。比如首页强调品牌和站点主题，详情页强调具体内容，列表页强调分类或集合页性质，这样搜索引擎和用户都更容易理解页面价值。

### 2. 分享信息要和内容匹配

比如文章详情页，可以让分享卡片显示：

- 文章标题
- 摘要
- 封面图

产品详情页则可以显示：

- 产品名
- 一句话卖点
- 产品图

这些细节看起来不大，但会明显提升内容站的专业感。尤其当你的站点被分享到社交平台时，展示效果会比普通页面好很多。

### 3. 空状态不能忽略

如果接口返回空数据，页面不能直接空白。你至少要给出：

- 暂无内容提示
- 返回首页按钮
- 刷新提示

空状态不是坏情况，而是用户体验的一部分。真正成熟的页面，不是只有数据正常时才好看，而是任何情况下都能给出明确反馈。

### 4. 交互保持轻量

展示站不需要复杂交互，简单、明确、稳定就够了。比如：

- 列表 hover 效果
- 按钮跳转
- 标签筛选
- 返回顶部

内容站的目标是“看得舒服、找得方便、打开快”，不是堆很多动画。交互越轻，内容越突出。

### 老赵经验分享

我常说，SEO 不是最后补的，而是页面设计阶段就该考虑的。标题怎么写、摘要怎么放、封面图怎么选，这些都影响最终效果。

### 赵老师提醒

不要只给首页配 SEO，列表页和详情页也要做。尤其是内容站，真正有价值的往往是详情页，而不是首页。
